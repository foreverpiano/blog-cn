本文介绍的是我们在 Anthropic 构建的核心基础设施之一：一个名为 Garçon 的工具，它旨在支持可解释性研究。

面临的问题

在 Anthropic，除了其他研究项目外，我们还专注于可解释性研究——试图理解语言模型在运行时内部究竟发生了什么。我们采用多种方法，但投入大量精力在“Circuits”风格的机制可解释性上，力求深入挖掘模型实际计算的内部机制。

这类工作需要在广阔且灵活的范围内“探索”模型。我们希望检查模型任意层中的单个激活值；进行修改或消融个别组件的实验；以及访问和操作模型的“内部结构”，而不仅仅是它的输入和输出。

我们还希望将这项工作扩展到 Anthropic 所使用的最大规模模型上。现代 Transformer 模型可能非常庞大，而大型模型的规模之大，使得它们无法在一张 GPU 上、甚至在一台配备多张 GPU 的单机上高效运行。

对于小型模型，可解释性工作通常使用 Colab 或 Jupyter Notebook（或类似工具），借助 PyTorch hooks 等功能来获取中间激活。然而，当模型规模超出单个节点时，这种工作流就失去了明显的迁移途径。Garçon 正是为了解决这个问题而设计的，它能让 Anthropic 可能训练的任意模型都能开展可解释性研究。正如我后面会提到的，它带来的好处已经超出了最初的目标。

Garçon 的核心接口

使用 Garçon 时，通常需要启动一个新的服务器。启动服务器只需提供服务器名称和模型在分布式存储中的路径即可，其他细节（如模型配置和 GPU 数量）都会自动检测：

python -m garcon.launch --snapshot PATH-TO-MODEL --name my-garcon

服务器启动后，你可以从交互式 Notebook 或用于自动化分析的脚本中连接到它：

rmodel = garcon.connect("my-garcon")

（我们习惯用“r”前缀表示通过 Garçon 运行的“远程”模型）。

服务器也可以直接从 Notebook 中启动，接口类似：

rmodel = garcon.launch_and_connect('path-to-model')

以这种方式启动的服务器会根据模型路径自动命名，这意味着在 Notebook 中重新运行该单元格时，它能检测到服务器已在运行并直接重连现有服务器。此外，它们被设置为在 1 小时无活动后自动关闭，因此研究者无需过于担心实验后的清理工作。

当你有一个 Garçon 客户端连接到模型后，最基本的操作是运行前向传播，默认会返回每个 token 的 logits：

logits = rmodel.forward(rmodel.encode("Hello, world"))

然而，Garçon 的真正强大之处在于它的“hooks”接口，它允许在前向传播过程中访问和修改内部状态。Garçon 模型会暴露一系列“探测点”（具体集合可能因模型架构和规模而异），每个探测点对应模型内一个可以访问或修改张量的具名位置。你可以在任意探测点上附加一个“probe”，然后带着这些 probe 运行前向传播（或反向传播，针对用户提供的损失函数计算梯度）。

probe 的基本接口是你可以提供一个“探测函数”。探测函数接受两个参数：一个“保存上下文”（用于保存激活或数据供后续使用），以及当前模型中该位置所代表的张量。探测函数可以返回一个更新后的张量（它会替换计算中的原张量），也可以返回 None 来使用原始值（这个约定借鉴自 PyTorch hooks）。

因此，我们最常用的两种简单模式分别是读取激活值：


def save_tensor(save_ctx, tensor):
  save_ctx.tensor = tensor

point_name = 'layers.4.mlp.post_activation'
rmodel.forward(
  tokens, 
  probes=[rmodel.probe_points[point_name].probe(save_tensor)]
)

或者通过将其置零来消融某个组件（实际中，我们也可能将其设置为合适的平均激活值或其他实验设置）：


def ablate_neuron(layer, mlp_idx):
  def hook(_, tensor):
    tensor[:, :, unit] = 0
    return tensor
  point_name = f'layers.{layer}.mlp.pre_activation'
  return rmodel.probe_points[point_name].probe(hook)
rmodel.forward(tokens, probes=[ablate_neuron(4, 123))

从这个例子可以看出，我们能够动态创建新的 hook 函数并将其发送到服务器。我们使用 cloudpickle 模块来支持向服务器发送任意 Python 代码对象。

save_ctx 对象由 Garçon 服务器统一保存（每个连接到服务器的客户端独立，所以多个用户可以共享一个服务器），读取结果可通过 rmodel.recordings() 获取，它返回一个以探测点名称为索引的字典。在内部，Garçon 会处理不同探测点可能位于不同节点的情况，并自动进行适当的 scatter/gather 操作，对用户透明地传输输入和数据。

“probe”接口的设计动机

Garçon 的“probe”接口虽然灵活，但使用起来略显繁琐；它会给服务器引入状态，而且访问激活值也需要一些仪式——你需要创建一个 probe、运行前向传播，然后再单独取回激活值。很自然会有人问，为什么我们不选择更简单的方案，比如允许事后访问任意激活值。

probe 接口被设计为一个“基础”接口，能够以合理效率支持我们所有的用例。具体来说，我们的设计基于以下几个目标：

仅在被请求时才捕获数据

有人可能会想直接捕获所有中间值，以便后续随意检查。但对于大型模型来说，这会产生海量数据，因此只保存被请求的激活值至关重要。

支持在服务器端进行归约

有时我们并不需要完整的张量，而只需要它在某个投影下的结果——可能是只取某个 token 位置的值，或者只想要 L2 范数这样的汇总统计量。通过允许在服务器端执行任意计算，我们就可以在服务端完成这种汇总。这带来两个好处：

减少带宽需求，只需向客户端发送更少的数据；同时让我们能够利用模型在多个 GPU 上并行运行的特点，因为不同 GPU 可以并发计算各自的激活值。

支持在服务器端进行有状态的计算

我们有时需要向模型输入海量样本，并在所有样本上计算激活值的聚合统计量。例如，我们会为模型中的 MLP 神经元收集“数据集样本”；我们希望向模型输入大量（可能数百万）来自训练语料的样本，并计算哪些 token 会让每个神经元产生最大激活。

通过使用持久化的 save_ctx 对象，我们可以编写一个 hook，将“前 10 个最大激活”保存在每个 MLP 层本地的小型数据结构中，并在以最快速度向模型输入样本的过程中持续增量更新它。如果每次都要把完整激活值返回给用户，这类计算的速度会慢几个数量级。

Garçon 包装器

在实际实验中，某个具体任务往往并不需要完整的“probe”功能集。我们还提供了一个名为 easy_garcon 的包装器，它提供了一个更简单但功能稍弱的接口，用于对单个上下文在模型中传播时的激活进行丰富分析。对于许多实验来说，这个接口已经足够了。

我们设想随着对自身需求和常见模式的深入了解，会在核心 probe 这个“汇编语言”接口之上构建更多抽象层。

参数访问

Garçon 服务器还通过与探测点相似的命名方式暴露模型参数：

W = rmodel.get_parameter('layers.4.mlp.up_proj')

对于权重，也可以直接从静态存储中下载，但通过研究者已经在使用的同一接口来访问会更加方便。

实现说明

Garçon 的实现相对直接，大约包含 1000 行代码（但 heavily 依赖我们现有的分布式和机器学习基础设施）。

服务器的运行方式是为每个 GPU 启动一个进程；这些进程基本保持同步运行，使用我们标准的集体通信机制进行通信。其中一个指定的进程（“rank 0”）负责监听 socket 上的传入请求并处理 RPC 协议。它会将请求广播给所有 rank；每个 rank 同步执行每个请求，必要时再执行 gather 操作将数据发回 rank 0。

如前所述，我们使用 cloudpickle 作为序列化工具，在服务器与客户端以及服务器各 rank 之间传递任意数据结构（包括 Python 代码对象）。

性能表现

Garçon 在设计上优先考虑灵活性而非极致性能，但我们仍努力保持合理的高效；我们相信性能本身也是一项特性，而且某些类型的实验正是由规模和效率所赋能的。特别值得一提的是，虽然我们使用 pickle 来编码普通的 Python 数据，但会尽量更直接、高效地传输大型张量对象。在一次实验中处理数十 GB 数据的情况并不少见，在这个规模下，如果性能上过于马虎就会出问题。

采用情况

我们发现 Garçon 对研究帮助极大。现在我们几乎所有可解释性工作都在使用它，其他团队也采用它来进行模型的临时探索。即使对于那些能塞进单个 Notebook 的模型，我们也受益于 Garçon 带来的一致性接口以及性能优势。将一个中等规模的模型加载到 GPU 上仍会花费不少时间，而有了 Garçon，我们可以长期运行服务器来托管常用模型，这大大缩短了新实验的“首次出图时间”[1]。

结束语

我们在这里介绍了 Garçon 的基本设计和设计动机，希望对其他有兴趣在自家模型上开展可解释性研究的实验室有所帮助。

虽然本文重点介绍了我们在 Garçon 中实现的具体接口和方法，但我们认为最有价值的贡献并不在于这些具体细节，而在于它所体现的理念，以及它如何改变了我们的可解释性团队与模型、与组织内其他团队的互动方式。特别值得一提的是，我们发现以下几个关键特性极具价值：

Anthropic 训练的任何模型（无论规模多大、架构细节如何）都能立即被可解释性研究者（以及其他人）所使用。新模型的实验准备工作几乎没有额外摩擦，与训练模型的研究者之间也不存在交接成本。可解释性研究者得以将 Notebook 式工作流的灵活性和开放性，与我们集群的规模和性能结合起来。即使对于那些确实能塞进单张 GPU 的模型，Garçon 的工作流也带来了显著优势。例如，研究者可以在同一个 Notebook 中研究多个不同模型，或是将模型分布到多张 GPU 上以获得更高吞吐量。另一个宝贵之处在于，你可以随时打开一个新 Notebook，连接到一个已运行的服务器，立即开始提出研究问题，而无需等待权重下载或模型初始化。
