本文介绍的是我们在 Anthropic 为支持可解释性研究而构建的一项核心基础设施：一个我们称之为 Garçon 的工具。

面临的问题

在 Anthropic，除了其他研究项目外，我们还从事可解释性研究——试图理解语言模型在工作时内部究竟发生了什么。我们采取了多种方法，但投入大量精力在“电路”（Circuits）风格的机制可解释性上，力求深入挖掘模型所执行计算的实际机制。

这类工作需要以宽泛而灵活的方式“探查”模型。我们希望检查模型任意层中的单个激活值；进行修改或消融个别组件的实验；以及访问和操作模型的“内部结构”，而不仅仅是它的输入和输出。

我们还希望将这项工作扩展到 Anthropic 所使用的最大规模模型上。现代 Transformer 模型往往非常庞大，而大型模型的规模可能大到无法在一张 GPU 上、甚至在一台多 GPU 机器上高效运行。

对于小型模型，可解释性工作通常使用 Colab 或 Jupyter Notebook（或类似工具），借助 PyTorch hooks 等功能来获取中间激活值。然而，当模型规模超过单个节点时，这种工作流程就难以直接迁移。Garçon 正是为了解决这个问题而设计，让 Anthropic 训练的任意模型都能开展可解释性研究。正如后面会提到的，它的实际价值已经超出了最初的目标。

Garçon 的核心接口

使用 Garçon 时，通常需要启动一个新的服务器。启动服务器只需提供服务器名称和模型在分布式存储中的路径；模型配置、GPU 数量等其他细节会自动检测：

python -m garcon.launch --snapshot PATH-TO-MODEL --name my-garcon

服务器启动后，你可以从交互式 Notebook 或自动化分析脚本中连接到它：

rmodel = garcon.connect("my-garcon")

（我们习惯用“r”前缀表示通过 Garçon 运行的“远程”模型。）

也可以直接从 Notebook 中启动服务器，接口类似：

rmodel = garcon.launch_and_connect('path-to-model')

以这种方式启动的服务器会根据模型路径自动命名，这意味着在 Notebook 中重新运行该单元格时，能检测到服务器已在运行并直接重连现有服务器。此外，它们被配置为在 1 小时无活动后自动关闭，因此研究者无需过于担心实验后的清理工作。

当你拥有一个连接到模型的 Garçon 客户端后，最基本的操作是运行前向传播，默认会返回每个 token 的 logits：

logits = rmodel.forward(rmodel.encode("Hello, world"))

然而，Garçon 的真正强大之处在于它的“hooks”接口，该接口允许在前向传播过程中访问和修改内部状态。Garçon 模型会暴露一组“探针点”（probe points，具体集合可能随模型架构和规模而异），每个探针点对应模型内部一个可以访问或修改张量的具名位置。你可以在任意探针点上附加一个“探针”（probe），然后带着这些探针运行前向传播（或反向传播，针对用户提供的损失函数求梯度）。

探针的基本接口是提供一个“探针函数”。探针函数接受两个参数：一个“保存上下文”（save context），用于保存激活值或数据供后续使用；另一个是该探针点所代表的张量。探针函数可以返回一个更新后的张量（会替换计算中的原张量），也可以返回 None 来使用原始值（这一约定借鉴自 PyTorch hooks）。

因此，我们常用的两种最简单模式分别是读取激活值：


def save_tensor(save_ctx, tensor):
  save_ctx.tensor = tensor

point_name = 'layers.4.mlp.post_activation'
rmodel.forward(
  tokens, 
  probes=[rmodel.probe_points[point_name].probe(save_tensor)]
)

或者通过置零来消融某个组件（实际中我们也可能将其设为合适的平均激活值或其他实验设置）：


def ablate_neuron(layer, mlp_idx):
  def hook(_, tensor):
    tensor[:, :, unit] = 0
    return tensor
  point_name = f'layers.{layer}.mlp.pre_activation'
  return rmodel.probe_points[point_name].probe(hook)
rmodel.forward(tokens, probes=[ablate_neuron(4, 123))

从这个例子可以看出，我们能够动态创建新的 hook 函数并发送到服务器。我们使用 cloudpickle 模块来支持向服务器发送任意 Python 代码对象。

save_ctx 对象由 Garçon 服务器保存（每个服务器连接独立，因此多个用户可以共享一个服务器），可以通过 rmodel.recordings() 读取结果，该方法返回一个以探针点名称为索引的字典。在内部，Garçon 会处理不同探针点可能位于不同节点的情况，并自动进行 scatter/gather 操作，对用户透明地传输输入和数据。

“探针”接口的设计动机

Garçon 的“探针”接口虽然灵活，但使用起来稍显繁琐：它会给服务器引入状态，而且获取激活值需要一些步骤——必须先创建探针、运行前向传播，然后再单独取回激活值。人们很自然会问，为什么不采用更简单的方式（例如允许事后访问任意激活值），而选择了这种方法。

探针接口被设计为一个“原语”级接口，能够以合理的效率支持我们所有的用例。具体来说，我们的设计 motivated 于以下目标：

仅在请求时捕获数据

有人可能会想直接捕获所有中间值，以便后续检查。但对于大型模型来说，这会产生海量数据，因此只保存被请求的激活值非常重要。

支持在服务器端进行归约

有时我们并不需要完整的张量，而只关心它的某个投影——可能是只需要特定 token 位置的值，或者是 L2 范数之类的汇总统计量。通过允许在服务器端执行任意计算，我们可以在服务端完成汇总。这带来两个好处：

减少带宽需求，只需向客户端传输更少数据；同时能充分利用模型在多 GPU 上并行运行的特点，因为不同 GPU 可以并发计算各自的激活值。

支持在服务器端进行有状态计算

我们有时需要向模型输入大量（成千上万乃至数百万）样本，并对所有样本的激活值计算聚合统计。例如，我们会为模型中的 MLP 神经元收集“数据集样本”；需要让大量（可能数百万）来自训练语料的样本通过模型，并计算哪些 token 会使每个神经元产生最大激活。

通过使用持久化的 save_ctx 对象，我们可以编写一个 hook，在每个 MLP 层本地维护一个小型的“top 10 激活”数据结构，并在以最快速度跑样本的过程中逐步更新它。如果每次都要把完整激活值返回给用户，这类计算的速度会慢几个数量级。

Garçon 封装器

在实际实验中，某个具体实验往往不需要完整的“探针”功能集。我们还提供了一个名为 easy_garcon 的封装器，它提供了一个更简单但功能稍弱的接口，用于对单个上下文通过模型时的激活值进行表达性分析。对于许多实验来说，这个接口已经足够用了。

随着我们对自身需求和常见模式的了解加深，我们计划在核心探针这一“汇编语言”接口之上构建更多抽象层。

参数访问

Garçon 服务器还以类似探针点的命名方式暴露模型参数：

W = rmodel.get_parameter('layers.4.mlp.up_proj')

对于权重，也可以直接从静态存储中下载，但通过研究者已经在使用的同一接口来访问会更加方便。

实现说明

Garçon 的实现相对直观，大约包含 1000 行代码（但在很大程度上依赖于我们现有的分布式和机器学习基础设施）。

服务器为每个 GPU 运行一个进程；这些进程基本保持同步，使用我们标准的集体通信机制进行通信。其中一个指定进程（“rank 0”）负责监听 socket 上的 incoming 请求并处理 RPC 协议。它会将请求广播给所有 rank；每个 rank 同步执行请求，必要时再通过 gather 操作把数据传回 rank 0。

如前所述，我们使用 cloudpickle 作为序列化工具，在服务器与客户端之间以及服务器各 rank 之间传递任意数据结构（包括 Python 代码对象）。

性能表现

Garçon 的设计优先考虑灵活性而非极致性能，但我们仍努力保持合理的效率；我们相信性能本身也是一项特性，而且某些类别的实验正是靠规模和效率才得以实现。特别地，虽然我们用 pickle 来编码普通的 Python 数据，但对于大型张量对象，我们会尽量采用更直接、高效的传输方式。在实验中处理数十 GB 数据的情况并不少见，在这个规模下，性能上不能有太大浪费。

采用情况

我们发现 Garçon 对研究帮助极大。现在，我们几乎所有的可解释性工作都在使用它，其他团队也采用它来进行模型的临时探索。即使对于那些能放在单个 Notebook 里的模型，我们也受益于 Garçon 带来的一致性接口和性能优势。将一个中等规模的模型加载到 GPU 上仍会花费一些时间，而有了 Garçon，我们可以保持长期运行的服务器来托管常用模型，这大大降低了新实验的“首次出图时间”（time to first plot）[1]。

结束语

我们在这里介绍了 Garçon 的基本设计和动机，希望对其他有兴趣在自己模型上开展可解释性研究的实验室有所帮助。

虽然本文重点放在 Garçon 所实现的具体接口和方法上，但我们认为它最有价值的贡献并不在于这些具体细节，而在于其背后的哲学，以及它如何改变我们的可解释性团队与模型、与组织内其他团队的互动方式。特别地，我们发现以下关键特性极具价值：

Anthropic 训练的任何模型（无论规模多大、架构细节如何），可解释性研究者（以及其他人）都能立即使用。启动新模型进行实验时不会产生额外摩擦，也无需与训练模型的研究者进行交接。可解释性研究者得以将 Notebook 式工作的灵活性和开放性，与我们集群的规模和性能结合在一起。即使对那些确实能放在单张 GPU 上的模型，我们也发现 Garçon 工作流带来了优势。例如，研究者可以在一个 Notebook 中同时研究多个不同模型，或者将模型分布在多张 GPU 上以获得更高吞吐量。另一个显著好处是：可以打开一个新 Notebook，立即连接到一个已运行的服务器开始提出研究问题，而无需等待权重下载或模型初始化。
