在 Erlang 进程组间进行负载均衡

2009-09-12 · 阅读原文

在我们正在开发的应用程序中，数据会依次经过一系列步骤，每个步骤中都会对数据进行转换。这是一个 Erlang 系统，每个步骤都有一个进程组，其中包含一个或多个进程（每个进程都是 gen_server）。给定进程组中的任意成员都可以处理任意文件，因此抽象来看，其逻辑大致如下：

Data = <<"data">>,
Steps = [stage_1_group, stage_2_group, stage_3_group],
lists:foldr(fun(Group, Data) ->
    Pid = pg2:get_closest_pid(Group),
    gen_server:call(Pid, {process, Data})
  end, Data, Steps).

这形成了一个非常灵活的数据处理流水线，但当我们从实现功能转向进行负载测试时，开始注意到进程组内的工作分布不均的情况。在足够高的负载下，组内某个 pid 可能会积累二十个作业的队列，而另一个 pid 的队列却为空。

问题的根源在于 pg2:get_closest_pid/1，它采用了一种简单的 pid 选择算法：

如果存在本地进程，则随机选择一个本地进程，否则随机选择一个远程进程。

我们临时讨论了如何解决这个问题，并想出了一个（在我看来）相当新颖的方案。我们所有的 gen_server 调用都是同步的，这意味着进程的消息队列长度就等同于分配给它的未处理作业数量。

因此，我们可以简单地遍历进程组，然后选择队列最短的那个进程。我们可以编写一个 get_best_pid/1 来替代 get_closest_pid/1。（抱歉这个名字很糟糕。我另一个备选是 get_unencumbered_pid/1，但可能又有点太长了。）

get_best_pid(Group) ->
  Members = pg2:get_members(Group),
  Members1 = lists:map(fun(Pid) ->
      [{message_queue_len, Messages}] = erlang:process_info(Pid, [message_queue_len]),
      {Pid, Messages}
    end, Members),
  case lists:keysort(2, Members1) of
    [{Pid, _} | _] -> Pid;
    [] -> {error, empty_process_group}
  end.

将前面的例子中的 pg2:get_closest_pid/1 替换为 get_best_pid/1 后，现在就能在所有进程组之间进行负载均衡了。这本来是一个可能比较棘手的问题，但 Erlang 让解决方案变得相当简洁。

作为一个额外的好处，一位备受尊敬的同事指出，可以使用 erlang:process_info 返回的 stack_size 值作为队列作业数相同的进程组之间的决胜因子。其理由是，正在处理数据的进程不一定会有额外的消息排队，因此无法区分一个空闲进程和一个正在处理数据的进程。
