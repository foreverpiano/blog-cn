在 GCP 上用 Python 创建 Slack 应用

2019-11-06 · 阅读原文

上周我和一位正在开发应用的开发者聊了聊，那款应用旨在帮助大家更好地进行 1:1 会议以及 管理不断壮大组织的工具。最让我印象深刻的是这样一个想法：如果把这个工具做成 Slack 应用，而不是普通的 Web 应用，或许能更快实现，并且用户体验也会更便捷。

这让我产生了一个有趣的问题：Slack 的生态系统和工具链是否已经发展到，使用 Slack 技术栈比使用传统的 Web 技术栈更快、更容易的地步了？

带着这个疑问，我决定花些时间研究 Slack API，亲身感受它的开发体验和灵活性。为了在减少基础设施复杂性的同时保留一条通往生产环境的路径，我选择将其构建为在 GCP Cloud Functions 上运行的若干无服务器函数。

以下是我的笔记。

要构建什么？

过去一年左右，我一直在工作中 ，让大家了解我的工作重点，同时也方便撰写 Julia Evans 所说的“炫耀文档”（brag document），也就是一份用来跟踪自己进度并撰写自我总结的成就清单。发送每周 5-15 更新。

我之前尝试过用一个简单的 Web 应用来处理这件事，但这个问题其实并不一定需要 Web 应用。实际上，很容易想象出一个简洁的实现，只需两个命令就够了：/reflect 和 /recall。

/reflect 用来记录工作：

/reflect finished writing reviews #reviews #mgmt
/reflect implemented prototype of load balancing tool #programming

/recall 用于查看你的记录：

/recall #mgmt
/recall #programing
/recall last 7 days #mgmt

这是一个简单的界面，但应该已经足够了。

起步

应用需要在特定的 workspace 中开发，因此我先创建了一个新的 Slack workspace，然后在其中创建了一个名为“Reflect”的 Slack App。

Slack 将 /recall 这样的命令称为 Slash Command。每次你在 Slack 中输入 Slash Command 并提交，Slack 都会处理该命令，并向你为该命令注册的端点发送一个 POST 请求。

你的端点可以返回 text/plain 类型的纯文本，在用户界面中显示；也可以返回 application/json 来支持更复杂的渲染，我们后续会深入探讨。

为了将特定命令映射到正确的后端代码，你可以为每个 Slash Command 指定不同的端点。或者，你也可以检查 Slack 发来的请求中的 command 键值对，根据其值进行分发。

配置 Cloud Functions

为了注册我们的 Slash Command，其中一个必填字段是 Request URL，即每次命令被触发时接收 POST 请求的 HTTPS 端点。虽然 ，但我希望模拟一个更接近生产环境的体验，因此决定使用 Google Cloud Functions 来托管这些端点。2019 年一些令人愉悦的开发者体验。

首先我在 GitHub 上创建了 reflect-slack-app 仓库，并克隆到本地：

git clone git@github.com:lethain/reflect-slack-app.git
cd reflect-slack-app

然后我按照这些说明创建了一个名为 ReflectSlackApp 的新 GCP 项目。

接着我在该项目中启用了 Cloud Functions API。

题外话：必须逐个启用 API，绝对是 GCP 开发者 onboarding 体验中最糟糕的部分。我相信这个设计有其合理性（避免意外计费等），但我觉得 GCP 如果能默认把所有 API 都打开，同时给每个功能设置一个较低的默认预算上限，会好得多。当然，这需要他们实现严格的预算上限，而我相信他们目前还没有。但我认为这在提升 onboarding 速度和减少用户流失方面是非常值得的。

API 平台是否应该引入 FaaS？

在继续之前，有一个有趣的问题值得思考：API 平台是否应该要求用户自己去搭建函数即服务（FaaS）环境，还是直接为用户托管函数更好？

目前 Google Cloud Functions、AWS Lambda 等已经比较容易设置，但仍然会给用户带来不小的 onboarding 摩擦，这也是为什么 Twilio Functions 这样的方案在简化 onboarding 方面占据了很大空间。

从长期来看，我认为很少有公司值得自己投入基础设施来支撑生产负载——AWS 和 GCP 在与整体工作流集成方面会比 Twilio 或 Slack 做得更好。但在早期 onboarding 和实验阶段，生产级别的质量要求反而成了摩擦。

我很希望看到一种标准化的模式：让 Slack 或 Twilio 这样的平台成为托管简单集成的发射台，当用户的集成达到一定复杂度后，能一键导出到 AWS/Azure/GCP。这能让新用户更快地在这些平台上实验，对平台和用户都是双赢，同时也不会把完整的生产级复杂性强加给用户或 API 平台。

更重要的是，这对 API 平台自身还有一个隐藏的好处：托管长尾的集成能让你获得这些集成的实现细节和控制权。有了这些访问权限，你就可以 它们，例如即使维护者已经不活跃，也能自动将它们从已弃用的功能上迁移。这一点非常有价值，因为长尾的缓慢废弃是成功 API 平台的核心限制之一。以编程方式重构 Ruby 代码

开发循环

格式化响应

脚手架搭好后，现在我们可以把响应格式化成真正有用的样子了。Slack 消息由一系列格式化块（blocks）组成，你可以使用 Block Kit Builder 快速实验。

我们希望端点返回类似以下结构的 JSON：

{
  "blocks": [{}, {}, {}],
}

有很多种 block 类型，但我们最初的渲染会主要使用 section 和 divider。Divider 本质上就是一条水平分割线（类似 hr），非常简单：

{
  "type": "divider"
}

Section 可以渲染 Slack 称之为 mrkdwn 的部分 Markdown 语法，结构如下：

{
  "type": "section",
  "text": {
    "type": "mrkdwn",
    "text": "This is *sort of* Markdown"
  }
}

你熟悉的很多 Markdown 语法在这里无法使用，具体细节请参考 mrkdwn 文档。

把这些组合起来，一个完整的响应大致是这样的：

{
  "blocks": [
    {
      "type": "section",
      "text": {
        "type": "mrkdwn",
        "text": "This is *sort of* Markdown"
      }
    },
    {
      "type": "divider"
    }
  ]
}

现在我们需要更新 Flask 的响应格式以符合这个结构。提醒一下，完整代码在 GitHub 上，不需要从这些片段中自己拼凑。

我们目前还没有把通过 /reflect 发送的信息存储起来，所以暂时会随机生成一些假数据用于渲染：

def recall(team_id, user_id, text):
    "Recall for (`team_id`, `user_id`) filtered by parameters in `text`"
    import random
    return ["I did something {}".format(x)
            for x in range(random.randint(3, 10))]

这个函数会返回一个包含若干字符串的列表：

[
  "I did something 0"
  "I did something 1"
  "I did something 2"
]

我们将在更新后的 recall_post 函数中使用它：

def recall_post(request):
    data = request.form
    team_id, user_id, text = data['team_id'], data['user_id'], data['text']
    items = recall(team_id, user_id, text)
    items_text = "\n".join(["%s. %s" % (i, x)
                  for i, x in enumerate(items, 1)])

    block_args = [
        ('mrkdwn', "Recalling `{}`".format(text)),
        ('divider',),
        ('mrkdwn', items_text),
        ('divider',),
        ('mrkdwn', "_Trying filtering_ `/recall last 7 days #mgmt`."),
        ('mrkdwn', "_Share your response by adding_ `public`"),
    ]

    resp = {
       "text": items_text,
       "blocks": [block(*args) for args in block_args]
    }
    return jsonify(resp)

block 函数是一个辅助函数，它将类型和可选的文本元组转换为 section，例如：

>>> block(tuple('divider'))
{
    "type": "divider"
}

它的实现如下：

def block(typ, text=None):
    if typ == "mrkdwn":
        return {
            "type": "section",
            "text": {
                "text": text,
                "type": "mrkdwn"
            }
        }
    else:
        return {
            "type": typ
        }

现在当我们使用 /reflect 时，响应已经格式良好：

如果使用真实数据，效果当然会更好，但我们已经可以看到应用各个部分如何协同工作，而且我们只写了非常少的样板代码（文本界面真香）。

公开还是临时消息

你可以通过响应中的 response_type 字段来控制响应是发送到频道还是仅私下发送给个人。默认情况下只向发出命令的用户展示，这等价于将 response_type 设置为 ephemeral：

{
  ...
  "response_type": "ephemeral",
  ...
}

或者，我们也可以让频道中的所有人看到：

{
  ...
  "response_type": "in_channel",
  ...
}

经过一些实验，我决定让用户自己控制消息可见性：在使用 /recall 时，如果消息文本中包含 public 参数，就公开显示，例如：

/recall last 7 days #mgmt public

这条命令就会发送到频道而不是仅自己可见。这个功能我用一行代码简单扩展了上面的 recall_post 函数：

resp = {
    "text": items_text,
    "response_type": "in_channel" if "public" in text else "ephemeral",
    "blocks": [block(*args) for args in block_args]
}

在实际实现中，你肯定需要对内容进行分词，避免文本中出现 #public 这种标签意外触发公开标志等问题。

可发现性

我认为尝试类似 public 标志这样的想法对 Slack 应用能否成功非常重要。因为根据我使用 Slack 的经验，Slash Command 面临的最大挑战之一就是可发现性。命令的可发现性长期以来一直困扰着 IRC 等纯文本媒介。

我用过的唯一在命令发现方面做得特别好的文本媒介是多用户地下城（MUD），它们提供类似 commands 的指令来列出所有可用操作，并通过增强的游戏性来奖励玩家学习它们。（我记得 Slack 曾经支持过 /commands 但后来移除了，大概是出于某种实现上的限制。）

因此，在 Stripe 内部的事件沟通 Slack 应用等工具中，我们非常重视在发到频道的每条文本中提升命令的可发现性，并在用户使用某个命令时提示其他相关命令。例如，当你在 recall 中使用 public 标志时，响应会告诉其他人如何使用这个命令：

Try filtering by tag and date `/recall last 7 days #mgmt`
Share with the room by adding `public` anywhere in your response

你可以想象一个“学习型”版本：它会记录你使用某个命令的次数，随着使用增多逐渐减少提示。或者在你掌握基础用法后，开始逐步增加更高级的提示。

验证请求

在把这个原型称为完成之前的最后一步，我想实现请求验证，确保我们只处理来自 Slack 本身的请求。如果不做验证，别人就可以伪造流量发送到你的端点，那会非常糟糕。

我在 中详细写了生成签名的细节，所以这里直接给出 verify 函数，不再赘述。verify 应该放在每个 Slash Command 处理函数的第一步。Python 和 Flask 中的 HMAC SHA256 签名

def verify(request,secret):
    body = request.get_data()
    timestamp = request.headers['X-Slack-Request-Timestamp']
    sig_basestring = 'v0:%s:%s' % (timestamp, body.decode('utf-8'))
    computed_sha = hmac.new(secret,
                            sig_basestring.encode('utf-8'),
                            digestmod=hashlib.sha256).hexdigest()
    my_sig = 'v0=%s' % (computed_sha,)
    slack_sig = request.headers['X-Slack-Signature']
    if my_sig != slack_sig:
        err_str = "my_sig %s does not equal slack_sig %s" % \
                   (my_sig, slack_sig))
        raise Exception(err_str)

def recall_post(request):
    signing_secret = b'your secret from some config tool'
    verify(request, signing_secret)
    return "Signatures match, yay."

接下来的问题是，我们应该如何安全地存储签名密钥（signing secret），让 Cloud Function 可以读取它，同时避免把它提交到我想公开放在 GitHub 上的仓库中。

最简单的方式是将密钥放在环境变量中，使用 --env-vars-file 标志指定一个包含密钥的文件。

我们将创建 reflect/env.yaml，内容如下：

SLACK_SIGN_SECRET: your-secret-goes-here

然后更新 recall_post，从环境变量中读取密钥。


def recall_post(request):
    signing_secret = os.environ['SLACK_SIGN_SECRET'].encode('utf-8')
    verify(request, signing_secret)

现在部署函数时需要执行：

cd reflect
gcloud functions deploy \
recall_post --env-vars-file env.yaml \
--runtime python37 --trigger-http

注意，第一次部署函数时只需要最后两个参数，但后续再次指定也无妨，根据你的实际情况保留或省略即可。

这篇博客中描述的将密钥存储在 Google Cloud Key Management Service 中的方案从安全角度来看要好得多。如果你正在构建真正重要的东西，应该采用那种方式，而不是把密钥直接塞进环境变量。

结束思考

做到这一步后，我最想做的是继续完善它，让它成为一个完整、可用的应用。目前排在前四位的功能是：

添加 App Home 页面，展示过去几周的记录，并支持一定程度的内联排序和筛选。使用 Events API 让用户可以给消息打标签，以便后续 recall。甚至允许给别人的消息打标签，用于他们的 recall，让团队成员可以互相支持彼此的工作。或许，嗯，加一个数据库来真正存储数据，而不是随机生成。把 Reflect 发布到应用目录，让其他人也能使用。
