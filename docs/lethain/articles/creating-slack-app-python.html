在 GCP 上用 Python 创建 Slack 应用

2019-11-06 · 阅读原文

上周我和一位正在开发应用的人聊了聊，他想让 1:1 会议变得更好，包括 管理不断扩张组织的工具。最让我印象深刻的是这样一个想法：如果把这个工具做成 Slack 应用，而不是网页应用，可能会更快，也能带来更好的用户体验。

这让我产生了一个有趣的问题：Slack 的生态系统和工具链是否已经发展到，使用 Slack 技术栈比使用传统的 Web 技术栈更快、更简单了？

带着这个疑问，我决定花些时间试验 Slack API，感受一下它的开发体验和灵活性。为了在减少基础设施复杂性的同时保留通往生产环境的路径，我决定用 GCP 的 Cloud Functions 构建几个无服务器函数。

以下是我的笔记。

要做什么？

过去一年左右，我在工作中 ，让大家了解我的工作重点，也方便撰写 Julia Evans 所说的“炫耀文档”（一份用来记录成就、追踪进度并撰写自我评估的清单）。发送每周 5-15 更新。

我之前尝试过用一个简单的 Web 应用来处理这件事，但这个问题其实并不需要 Web 应用。确实，很容易就能想象出一个简化的实现，只需要两个命令：/reflect 和 /recall。

/reflect 用来记录工作：

/reflect finished writing reviews #reviews #mgmt
/reflect implemented prototype of load balancing tool #programming

/recall 用来查看你的记录：

/recall #mgmt
/recall #programing
/recall last 7 days #mgmt

这是一个简单的界面，但应该已经足够了。

起步

应用需要在特定工作空间内开发，所以我先创建了一个新的 Slack 工作空间，然后创建了一个名为“Reflect”的 Slack App。

Slack 把 /recall 这样的命令称为 Slash Command。每次你在 Slack 中输入 Slash Command，Slack 都会处理它，并向你为该命令注册的端点发送一个 POST 请求。

你的端点可以返回 text/plain 类型的文本，直接显示在用户界面中；也可以返回 application/json 以支持更复杂的渲染，我们后面会深入讨论。

为了将特定命令映射到正确的后端代码，你可以为每个 Slash Command 指定不同的端点。或者，你也可以检查 Slack 发来的请求中的 command 键值对，根据其值进行分发。

配置 Cloud Functions

为了注册 Slash Command，其中一个必填字段是 Request URL，即每次命令被触发时接收 POST 请求的 HTTPS 端点。虽然 ，但我想模拟一个更接近生产的体验，因此选择使用 Google Cloud Functions 来托管这些端点。2019 年一些令人愉悦的开发者体验

首先我在 Github 上创建了 reflect-slack-app 仓库并克隆到本地：

git clone git@github.com:lethain/reflect-slack-app.git
cd reflect-slack-app

然后按照说明创建了一个名为 ReflectSlackApp 的新 GCP 项目。

接着在这个新项目中启用了 Cloud Functions API。

题外话：必须逐个启用 API 绝对是 GCP 开发者 onboarding 体验中最糟糕的部分。我相信这个设计有其合理性（防止意外计费等），但我觉得如果 GCP 默认把所有服务都打开，并设置一个较低的单功能预算上限，用户体验会好得多。当然，这需要他们实现硬性预算上限，而我认为他们目前还没有。但我认为为了加快 onboarding 速度、减少用户流失，这是值得的。

接下来是搭建 reflect-slack-app/ 的脚手架，参考了 helloworld 示例的大致结构。

python3 -m venv venv
source venv/bin/activate

我们先从最简单的 Slash Command 处理程序开始，它会忽略传入的消息，并返回一段静态的 text/plain 文本。虽然现在什么都做不了，但可以用来验证连通性是否正确。

def reflect_post(request):

在上传函数之前，我确保将 gcloud 配置指向了刚创建的新项目（好吧，我承认我一开始忘了，结果花了不少时间排查）：

gcloud projects list

...

...

然后就可以部署函数了：

cd reflect-slack-app/reflect
gcloud functions deploy reflect_post --runtime python37 --trigger-http

第一次运行时，它会询问是否允许未经身份验证的调用（这里的身份验证指的是 Google ID Token 认证），如果你希望 Slack 能够访问，就必须允许：

Allow unauthenticated invocations of new function [reflect_post]?
(y/N)?
y

部署完成后，就可以通过 curl 测试了：

curl https://your-url-here.cloudfunctions.net/reflect_post
Reflect!

太好了，现在我们有了一个端点，可以指向新的 Slash Command，然后就可以回去继续配置 Slack App 了。

API 平台是否应该引入 FaaS？

在继续之前，有一个有趣的问题值得思考：API 平台是否应该让用户自己去搭建函数即服务（FaaS）环境，还是直接为用户托管函数？

Google Cloud Functions、AWS Lambda 如今设置起来已经相当简单，但仍然会给用户带来明显的 onboarding 摩擦，这也是为什么 Twilio Functions 这样的方案能在简化 onboarding 方面大受欢迎。

从长远来看，我认为很少有公司值得投入基础设施来支撑生产负载——AWS 和 GCP 与你整体工作流的集成会比 Twilio 或 Slack 更好。但在早期 onboarding 和试验阶段，生产级别的质量标准其实只是摩擦。

我希望看到一种标准化的模式：让 Slack 或 Twilio 这样的平台成为托管简单集成的发射台，当用户的集成达到一定复杂度后，能一键导出到 AWS/Azure/GCP。这能让新用户更快地进行试验，对平台和用户都是双赢，同时不会把完整的生产级摩擦强加给任何一方。

对 API 平台自身而言，还有一个更重要的隐藏好处：托管长尾集成能让你获得对这些集成实现的访问权和控制权。有了这些访问权限，你就可以 它们，例如即使维护者已经不活跃，也能自动把它们从已废弃的功能上迁移。这一点非常有价值，因为长尾中的缓慢废弃是 API 平台成功的核心限制之一。用程序化方式重构 Ruby 代码

开发循环

这也展示了迭代这些命令的开发反馈循环：修改代码，部署更新后的函数，执行命令并查看响应。

当出现问题时，我发现通过 Google 的 Stackdriver 查看错误信息来进行调试还是比较直观的。我确实希望 Slack 能记录我最近几百条错误信息并在仪表盘中展示，以便更轻松地调试，但使用服务端可见性也已经足够好了。

格式化响应

脚手架搭好后，现在我们可以把响应格式化成有用的样子了。Slack 消息由格式化块（blocks）组成，你可以用 Block Kit Builder 快速试验。

我们希望端点返回类似以下结构的 JSON：

{
  "blocks": [{}, {}, {}],
}

有很多种 block 类型，但我们最初会使用 section 和 divider。Divider 本质上就是一条水平分割线，非常简单：

{
  "type": "divider"
}

Section 可以渲染 Slack 称为 mrkdwn 的部分 Markdown 语法，长这样：

{
  "type": "section",
  "text": {
    "type": "mrkdwn",
    "text": "This is *sort of* Markdown"
  }
}

你熟悉的很多 Markdown 语法在这里都不生效，具体细节请参考 mrkdwn 文档。

把这些组合起来，一个完整的响应大概是这样的：

{
  "blocks": [
    {
      "type": "section",
      "text": {
        "type": "mrkdwn",
        "text": "This is *sort of* Markdown"
      }
    },
    {
      "type": "divider"
    }
  ]
}

现在我们需要更新 Flask 的响应格式以符合这个结构。提醒一下，完整代码在 Github 上，不需要从这些片段中拼凑。

我们还没有把通过 /reflect 发送的消息存起来，所以目前会随机生成一些假消息用于渲染：

def recall(team_id, user_id, text):
    "Recall for (`team_id`, `user_id`) filtered by parameters in `text`"
    import random
    return ["I did something {}".format(x)
            for x in range(random.randint(3, 10))]

它会返回一个包含可变数量字符串的列表：

[
  "I did something 0"
  "I did something 1"
  "I did something 2"
]

我们将在更新后的 recall_post 函数中使用这个函数：

def recall_post(request):
    data = request.form
    team_id, user_id, text = data['team_id'], data['user_id'], data['text']
    items = recall(team_id, user_id, text)
    items_text = "\n".join(["%s. %s" % (i, x)
                  for i, x in enumerate(items, 1)])

    block_args = [
        ('mrkdwn', "Recalling `{}`".format(text)),
        ('divider',),
        ('mrkdwn', items_text),
        ('divider',),
        ('mrkdwn', "_Trying filtering_ `/recall last 7 days #mgmt`."),
        ('mrkdwn', "_Share your response by adding_ `public`"),
    ]

    resp = {
       "text": items_text,
       "blocks": [block(*args) for args in block_args]
    }
    return jsonify(resp)

block 函数是一个辅助函数，用于将类型和可选文本的元组转换成 section，例如：

>>> block(tuple('divider'))
{
    "type": "divider"
}

它的实现是：

def block(typ, text=None):
    if typ == "mrkdwn":
        return {
            "type": "section",
            "text": {
                "text": text,
                "type": "mrkdwn"
            }
        }
    else:
        return {
            "type": typ
        }

现在当我们使用 /recall 时，响应已经格式良好：

如果使用真实数据肯定会更好，但我们已经能看到应用各部分如何组合在一起了，而且我们只写了非常少的样板代码（文本用户界面真棒）。

公开还是临时消息

你可以通过 response_type 字段控制响应是发送到频道还是仅私下显示给个人。默认情况下只显示给发出命令的用户，这等价于将 response_type 设置为 ephemeral：

{
  ...
  "response_type": "ephemeral",
  ...
}

或者，我们也可以让频道里的每个人都看到：

{
  ...
  "response_type": "in_channel",
  ...
}

试验之后，我决定让用户自己控制消息可见性：在输入 /recall 时，如果消息文本中 anywhere 位置包含 public 参数，例如：

/recall last 7 days #mgmt public

就会发送到频道而不是只显示给自己。这通过对上面 recall_post 的一行扩展实现得很粗糙：

resp = {
    "text": items_text,
    "response_type": "in_channel" if "public" in text else "ephemeral",
    "blocks": [block(*args) for args in block_args]
}

在真正的实现中，你肯定需要对内容进行分词，避免文本中出现 #public 这样的标签就触发公开标志等情况。

可发现性

我认为试验 public 这样的标志对成功的 Slack 应用非常重要。因为我使用 Slack 的经验是，Slash Command 最大的挑战之一就是可发现性。命令的可发现性长期以来一直困扰着 IRC 等纯文本媒介。

我用过的唯一在命令发现方面做得特别好的文本媒介是多人地下城（MUD），它们提供类似 commands 的指令来列出所有可用操作，并通过增强的游戏性来奖励玩家学习它们。（我记得 Slack 以前支持过 /commands 但后来移除了，可能是受某些实现限制的影响。）

因此，在 Stripe 内部的事故沟通 Slack 应用等工具中，我们非常重视在发到频道的任何文本中增加命令的可发现性，并在用户使用命令时提示其他可用命令。一个同时体现两者的例子是：当你在 recall 中使用 public 标志时，你的响应会告诉其他人如何使用这个命令：

Try filtering by tag and date `/recall last 7 days #mgmt`
Share with the room by adding `public` anywhere in your response

你可以想象一个“学习型”版本：跟踪用户使用命令的次数，随着时间推移逐渐减少提示。或者在用户熟悉基础功能后，再逐步增加提示。

验证请求

在把这个原型称为完成之前的最后一步，我想实现请求验证，以确保我们只处理来自 Slack 本身的请求。如果不做验证，别人就可以伪造流量发到你的端点，那就太糟糕了。

我在 中详细写了生成签名的细节，所以这里就直接给出 verify 函数，不再解释。verify 应该是每个 Slash Command 处理程序中的第一步。Python 和 Flask 中的 HMAC SHA256 签名

def verify(request,secret):
    body = request.get_data()
    timestamp = request.headers['X-Slack-Request-Timestamp']
    sig_basestring = 'v0:%s:%s' % (timestamp, body.decode('utf-8'))
    computed_sha = hmac.new(secret,
                            sig_basestring.encode('utf-8'),
                            digestmod=hashlib.sha256).hexdigest()
    my_sig = 'v0=%s' % (computed_sha,)
    slack_sig = request.headers['X-Slack-Signature']
    if my_sig != slack_sig:
        err_str = "my_sig %s does not equal slack_sig %s" % \
                   (my_sig, slack_sig))
        raise Exception(err_str)

def recall_post(request):
    signing_secret = b'your secret from some config tool'
    verify(request, signing_secret)
    return "Signatures match, yay."

接下来的问题是，我们应该如何安全地存储签名密钥（signing secret），让 Cloud Function 可以读取它，同时避免把它提交到我希望公开放在 Github 上的仓库里。

最简单的方法是把密钥放到环境变量中，用 --env-vars-file 标志指定一个包含密钥的文件。

我们将创建 reflect/env.yaml，内容为：

SLACK_SIGN_SECRET: your-secret-goes-here

然后更新 recall_post，从环境变量中读取密钥。


def recall_post(request):
    signing_secret = os.environ['SLACK_SIGN_SECRET'].encode('utf-8')
    verify(request, signing_secret)

现在部署函数时需要运行：

cd reflect
gcloud functions deploy \
recall_post --env-vars-file env.yaml \
--runtime python37 --trigger-http

注意，其实只有第一次部署函数时才需要最后两个参数，但后面再指定也无妨，你可以根据情况保留或省略。

这篇博客中描述的把密钥存到 Google Cloud Key Management Service 的方式在安全性上要好得多。如果你正在构建重要的东西，最好采用那种方式，而不是把密钥塞进环境变量。
