大规模健康检查

2019-10-27 · 阅读原文

几天前在 Stripe 的每周事故复盘会上，我们开始讨论一个总是出人意料地容易引发争议的话题：健康检查。从那以后我一直在思考这个问题，并把自己的所学所得写了下来。

我刚加入 Uber 时，我们依靠 HAProxy 在各个进程之间路由流量。那时候 HAProxy 的配置现在大概会被描述为 sidecar 模式。

我们在每台服务器上运行一个 HAProxy 实例，并通过检查配置数据库 Clusto 中的元数据来生成该服务器的路由配置。Clusto 与 Consul 或 etcd 有一些相似之处，但在两个基本设计选择上不同：它选择了 (a) 分布式系统词汇表，以及 (b) 放弃广泛的商业成功。

在 Clusto 中，每个服务会声明 (1) 它应该监听的端口，(2) 哪些类型的宿主机可以路由流量给它，(3) 它应该运行在哪些宿主机上，以及 (4) 它的健康检查协议和端点。

Clusto 的聚合元数据会被编译成每台服务器的 HAProxy 配置，这样运行在订阅主机类型上的进程就会把流量发往 localhost:$DEST_SERVICE_PORT，并被路由到目标服务的健康实例上。

每个 HAProxy 实例负责检查其下游服务的健康状况。这一点可配置，但对绝大多数服务来说，就是发送一个 HTTP 请求到 /health，并检查响应的状态码。如果返回 200，就认为可用，否则不可用。

人类和软件都可以通过类似 status-down 和 status-up 的脚本手动干预进程的健康状态，这些脚本会被 /health 端点在决定返回什么状态码时进行检查。

这种方式有一些很好的特性。它能在网络分区的情况下快速自动恢复。你可以构建任意复杂的工具来操纵 status-down 脚本，以表明某个进程不应该接收流量——我们的部署工具就用它在升级前排空流量。此外，这个方案的移动部件很少，很容易维护和扩展。

然而，它也有一些缺点：健康检查的数量会随着服务和主机数量的增加而乘积式增长。大致来说，健康检查次数的计算公式是：

number of hosts *
average number of services per host *
average number of downstream services per service *
average number of instances per services

代入一些数字，假设我们有 100 台主机，每台运行 10 个服务，每个服务依赖 3 个其他服务，每个服务有 20 个实例。

得到的结果是：

100 * 10 * 3 * 20 = 60,000 healthchecks per period

我们不必每秒都做健康检查，假设我们能容忍 15 秒的延迟，那么我们大约每秒要做 4000 次健康检查。请注意，这些数字还很小。实际上，我们的主机、服务、下游依赖和实例数量都要多得多。

数字很快就变得很大。

我们后来在每台服务器上增加了一个高性能的健康检查缓存，它提供缓存的响应，并异步刷新健康检查结果，以减轻用 Python、Node.js 等较慢语言实现的服务上的负载。但最终，巨大的网络流量和花在健康检查上的 CPU 时间还是成了瓶颈。

这时候你有三种选择：(1) 开始限制服务发现只在 pod 内部进行；(2) 把健康检查职责卸载给一个中心化或部分中心化的机制；或者 (3) 依靠检查实际流量（即被动健康检查）来判断健康状态，而不是主动健康检查。

Uber 对这三种方案都进行了实验和部分采用。最终我想论证的是：在适当的规模和复杂度下，你也应该同时采用这三种方法。

Pod 范围路由

减少能够相互通信的服务器数量——我将其命名为 pod-scoped routing——至少有三个明显的好处。

最重要的是，它允许你建立清晰的 描述故障域（故障域）隔离，从而一个 pod 失败不会影响其他执行相似工作的 pod。最常见的行业案例是，在高可用或容灾架构中限制跨地域流量。这些独立的故障域会成为特别有效的部署目标，尤其适合通过 Puppet 或 Terraform 进行的较慢的基础设施变更。

Pod 还能让你只允许流量流向附近的宿主机，从而最小化延迟。如果 pod 规模足够小，就可以与下游进程保持已建立的连接，同时避免只连接部分下游服务带来的负载分布偏差，也能限制连接开销消耗的内存和 CPU。

最后，当规模达到一定程度，如果不小心规划网络流量，网络成本可能会成为基础设施总成本的重要组成部分。Pod 感知的路由是减少昂贵跨网络流量的有效方式。

顺便提一句，有些人试图通过限制每台主机只知道下游服务的一个随机子集来降低健康检查开销。这本质上是一种临时且难以推理的 pod 实现。它会让部署策略变得特别难以分析：即使是一个很小的增量发布，也可能导致某些主机完全失去容量——如果它恰好只认识那些正在发布的特定主机。总体来说，随机子集是一种应该尽量避免的方法，尽管作为一种拖延基础设施灾难的最后手段，它还是能用的。

中心化健康检查

以增加一些基础设施复杂度和对网络分区恢复能力略有降低为代价，你可以通过中心化健康检查职责来避免海量健康检查的轰炸。不再让每个 HAProxy 实例（或你选择的任何代理）自己做健康检查，而是有一个中心化机制替你执行检查，然后要么 (a) 把健康数据广播给订阅者，要么 (b) 提供一个高效的接口，让代理能快速、低成本地获取它们关心的最新健康数据。

在中心化检查器的设计中，你可以做很多最佳情况与最坏情况之间的优化，以减少这种方案的缺点。例如，你不必从几千个代理各自检查下游健康，变成只有一个进程做检查。你可能会希望让 3 到 5 个冗余进程共同检查每个下游的健康，以便在某个检查器出问题时仍能正常工作。

大多数中等规模的技术公司最终都会实现一个大致等价于 Envoy 做法的方案，但这里的用例其实已经相当通用，适合被整合到更少、更通用的实现中。

在容易获取的技术支持方面，Envoy 对这种模式有很好的支持。你首先实现一个负责健康检查的 Endpoint Discovery Service（EDS），然后每个 Envoy 实例会去查询 EDS 获取路由数据，而不是自己做本地判断。

检查流量

虽然主动健康检查是你更新路由表以反映有意变更（例如部署、主机升级等）的主要工具，但永远不要忘记，绝大多数主动健康检查的实现大致是这样的：

@route("/health")
def healthcheck(req):
    if exists("/etc/status_down"):
        return "DESPAIR", 500
    return "OK", 200

这种相当无用的标准实现使得它们无法很好地代表进程的真实状况。如果你想要响应迅速、能快速对退化进程做出反应的路由机制，那么只靠主动健康检查是不够的。

你需要引入被动健康检查。

被动健康检查可以简单到只检查下游进程的响应码，如果错误率超过阈值，就把它从轮询中移除。即使是非常严格的阈值——比如超过 50% 的请求返回错误就移除——实际效果也出奇地好。Envoy 的 outlier detection 机制就是一个有趣的实际例子。

被动健康检查的价值在于减少错误对上游用户和依赖进程的影响。想想常见的金丝雀部署模式：你先把新版本部署到 5 台主机上，如果错误率和现有水平差不多，就继续扩大部署。

如果你金丝雀部署的软件有 bug——比如调用了一个测试环境有但生产环境没有的方法，导致金丝雀主机处理的 100% 请求都在失败。这时你的 /health 端点不太可能调用那个路径，因此还会继续返回健康状态，让金丝雀继续留在流量池里，直到你手动触发回滚。即使在最好的情况下，回滚通常也需要几分钟，如果你不得不“fail forward”（反模式）走新构建、测试、部署的流程，那可能要花更长时间。

如果这个金丝雀占 1% 的流量，而你只依赖主动健康检查做路由，那么你将持续让 1% 的用户请求失败好几分钟，直到回滚完成。这是一个很坏的结果，哪怕你的软件只是用来传搞笑猫视频，而不是救命。相反，即使是非常保守的被动健康检查阈值，也能在不到一分钟内发现这些主机行为异常并把它们踢出轮询。

把“缓解”（把坏主机踢出轮询）和“修复”（回滚到更好版本）分开，是实现快速恢复和最小化用户影响的关键。这在处理更慢的变更时（比如推送 Puppet 配置、在生产中验证新的数据库版本等）尤为重要——把流量切走仍然很快，但回滚却危险且缓慢。最重要的是，这让你能在诊断问题之前就完成恢复。而在复杂的分布式系统中，诊断通常是最慢的一步。

一旦下游进程被标记为不健康，恢复机制就类似熔断器模式。你会等待一段时间，然后发送固定数量的探测请求给不健康的实例。如果它们响应良好，就重新标记其为健康并继续发送流量。

有时人们会纠结于更新路由配置来实现被动健康检查的复杂性，但其实也可以通过扩展你的 /health 等价端点，让它查看本地缓存的响应码，并根据最近的结果修改健康状态。这种方式会受“每个进程都要定制”的诅咒，但它允许你在不大幅修改现有路由和健康检查基础设施的情况下 rollout 被动健康检查。

Uber 已经下线的 Hyperbahn 特别依赖被动健康检查，它彻底取消了代理进行主动健康检查的概念（尽管如前所述，一个中心化健康检查系统能通知代理其可路由下游的更新，这可以提供主动健康检查的大部分好处）。

相反，它完全依靠下游进程是否正常响应传入流量，如果不行就将其移除轮询。这与对幂等操作自动重试的清晰语义相结合，能够最大限度减少故障向上游泄漏。它原本还打算用同样的语义实现《The Tail at Scale》中描述的一些提前重试机制，不过我不记得最后有没有落地。

你应该三者都用

从长远来看，我非常确信任何规模较大的部署最终都会希望同时进行主动和被动健康检查、在故障域范围的 pod 内路由，并中心化健康检查以减少检查量。我知道有人成功地把其中某些做法推迟了很久，但每一种都能带来巨大价值，我建议尽早采用，而不是拖到后面。
