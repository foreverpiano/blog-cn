何时编写策略，以及写多少？

2024-08-25 · 阅读原文

即使你认为策略总体上很有用，决定“今天就开始写工程策略”依然很难。一旦开始写，又很容易写得过多，导致组织被淹没，最终忽略你的策略，而不是投入时间去理解它。

幸运的是，这些是普遍存在的问题，有一些实用的心智模型可以帮助我们避免两个极端。本章将讨论：

何时开始编写策略，特别是那些出现跨团队摩擦等痛点，或迎来 senior hire 等机会的时刻，都是适合启动的好时机；组织能承受多少策略，避免写得太多导致被忽略，或写得太少而收效甚微；利用策略高度（strategy altitude）——即策略的宽严程度及其适用范围——来控制策略带来的管理开销；以及用于调试当前策略工作是过多还是过少的一些机制。

读完本章后，你应该对以下方面有清晰的认识：何时开始写策略、决定要写多少份策略，以及在决定大量编写策略时，如何利用策略高度来降低开销。

本章选自《Crafting Engineering Strategy》。

何时编写策略

在成为 Calm 的 CTO 不久后，我打开一个文档，命名为“Engineering Strategy”，然后盯着空白页面发呆，最后把它搁置了一年。一年后，我重新打开，写下了三条指导原则：选择无聊的技术（choose boring technology）、用好奇心化解冲突（resolve conflict with curiosity），以及优先使用 vendor 提供商品化功能（prefer vendors for commoditized functionality）。这几句简单的话极大减少了决策中的冲突，让我们能把更多精力放在改进产品上。一开始，我觉得我们需要更清晰的策略，但当时不知道该写什么，所以什么也没写。

很多时候，什么都不写反而是最好的选择。事实上，对领导者常见的批评就是他们“想显得有战略性”，暗示他们过于关注抽象概念，而忽略了当下的具体需求。这个指责背后有一个重要事实：策略工作并不总是你能做的最有价值的事。有时候做策略只是为了逃避更重要的事情，就像吃零食一样。

在开始策略工作之前，你必须判断现在是否是正确时机，这取决于组织当前的战略状态、战略状态随时间的变化趋势，以及你是否拥有足够上下文来有效开展工作。

这三个标准中的第一个是“战略状态”的概念。以 我们是否应该分解单体架构？ 为例，你的工程组织可能处于以下三种战略状态之一：

全局一致（Globally consistent）：存在一个被清楚认可的策略，即使没有写下来。当你询问团队不同成员如何解决某个问题时，你会得到相似的答案。例如，所有人都同意在现有的单体代码库中编写新的产品功能。团队内部一致（Consistent within teams）：组织内部某些小组有清晰的策略，但在不同小组之间存在不一致。例如，产品工程团队认为所有新功能都应放在共享 monorepo 的新服务中，而平台工程团队则认为应该在单体中实现。高度分散（Highly varied）：工程团队内部不同个体在解决问题的方法上几乎没有共识。例如，有些工程师想在 monorepo 的新服务中开发，有些想在 polyrepo 的新服务中开发，还有些人认为应该在现有的单体服务中实现新功能。

如果你的组织处于全局一致的状态，那么除非大家一致采用的是一个不好的方法，否则继续投入更多策略工作很可能没有价值。如果你处于后两种状态，那么现在很可能是一个适合写一些策略的好时机。

即使当前状态良好，如果组织正朝着更差的状态演变，那也是开始策略工作的宝贵时机。反之，如果当前状态还可以，并且正朝着更好的方向发展，那可能就不是一个有价值的时机。有一些反复出现的原因会导致状态突然、有时是意想不到地转变：

你正在或没有进行招聘的规模。Uber 在四年内每六个月就将工程团队人数翻倍，同时开设了许多分布式工程办公室，这导致了高度多样化的方法。同时，大多数工程师的司龄很低，进一步加剧了不一致性。新聘用的外部领导者是更倾向于遵循 playbook，还是更愿意响应组织当前的具体情境。虽然在 担任 CTO 或 VP Engineering 后的前 90 天 中这是一个众所周知的反模式，但许多领导者急于尽快展现影响，以至于忘记先诊断新环境就做出大规模变革。这会在那些追随新方向的团队和那些维护现有软件与基础设施的团队之间制造战略裂痕。你进行重大组织变革（如重组或裁员）的频率。这些事件可能会打破传播文化的机制，而这些微妙的“胶水工作”常常在用电子表格驱动的练习中被忽视。你对历史决策的文档化程度，以及在 onboarding 过程中沟通的 effectiveness。有些公司会系统地向新员工灌输决策方式，另一些则期望团队在本地完成培训。这两种方式都可能很好，也都可能很差。

最后，即使当前状态很差且正在恶化，你还必须评估自己是否足够了解组织，从而开始做有用的策略工作。许多新领导者急于上手，在没有验证假设的情况下就做出判断，然后 大型迁移。这可能感觉像是在大胆推动战略，但大多只是用甘特图包装起来的焦虑或自负。

你应该问自己的问题是：你是否了解你想改变的那些领域的历史、做出决策的人，以及当时让那些决策成为好决定的上下文。如果你对你关注的领域了解这些信息，那么你就准备好进入策略工作了。如果不了解，那么值得放慢脚步，先建立必要的关系和上下文，让后续工作真正产生价值。

如果事情可以变得更好，或者正在恶化，而你对公司有足够的了解可以开始，那么就是开始策略工作的时候了。

要写多少策略？

开始策略工作后，你会遇到的下一个问题是：你应该承担多少策略工作？是关于编程语言选择？还是服务拆分？或者是如何优先处理 bug？还是关于数据仓库？要不要四件事同时做？

由于潜在的策略工作几乎是无限的，很难决定从哪里开始。最有价值的决策就是 为什么限制在制品数量有效，即使这意味着从比你期望更小的范围开始。通常我发现最有效的方式是先从小事做起，在小块内容上迭代直到它真正生效，然后再去处理更大的事情。每次只限制自己开发一到两个策略。这能让你有足够的精力确保这些策略真正发挥作用。

要在限制同时进行的策略开发数量的同时保持有效性，拥有一个清晰但不僵化的长期目标观点非常重要。有一个策略目的地，能让这些较小的部分最终都能服务于一个更大的整体。

用一个具体例子来说明：在 Uber，我们的单体 Python 代码库导致了可靠性和生产力问题。我的团队没有权限禁止往那里提交代码，但我们有能力让服务开通变得非常、非常容易。因此我们制定了一个策略，专注于让服务的开通和运维尽可能无痛。这个策略的目标是解决后续拆分和脱离单体的问题，但我们并没有直接去解决它。我们专注于第一步，认为这是后续步骤的必要前提。在我们验证了第一步之后，才开始着手后续步骤的策略工作。

如果我们一开始就制定更宽泛的策略，我们可能会陷入关于未来应该如何的抽象争论，并需要许多不同团队在没有任何今天可采取的具体步骤的情况下就买下我们的未来愿景。通过缩小范围，我们能够对前提条件进行迭代，并将建立共识的工作推迟到需要大家采取具体行动的时候。那时，已经没有关于可行性的抽象争论，因为大多数人已经在按照我们期望的方式工作了。

减少同时进行的策略数量所面临的一个挑战是，它看起来不够有雄心。在 Uber 的例子中，我们需要解决在单体代码库中开发的问题，但我们却在谈论服务开通，从远处看好像我们偏离了主题。这是有效策略开发中反复出现的问题：它可能显得过于保守。尽管在实践中这通常是解决根本问题的最快方法，但往往给人感觉缓慢或迂回。要解决“看起来不够有雄心”的问题，需要主动向利益相关者讲故事，既解释当前的增量举措，也说明它随着时间推移将扩展到的更广阔愿景。

有时候这不仅仅是利益相关者的问题，你自己也会觉得进展太慢。在那些时刻，我会试着记住 摩擦不等于速度。，并想起我加入 Digg 时的工程策略。当时我们有一个极其清晰且一致的架构（PHP 前端、Python 服务、所有存储都用 Cassandra），但公司依然在我们周围崩塌了。几个真正有效的策略，比在一栋着火的建筑里拥有一堆策略（即使是好的策略）要有价值得多。

策略高度

有时候你确实想快速制定一个宽泛而全面的策略，这违反了每次只做一个策略的一般规则，但有一个有帮助的概念通常能让这成为可能，那就是策略高度（strategy altitude）。

通过几个在不同高度运作的例子，最容易解释这个概念：

开发者体验团队希望提升代码质量。他们创建了一个机制，允许团队为自己的构建定义 lint 规则。开发者体验团队提供了一些强意见的默认规则供团队采用，但每个团队都有权在本地覆盖这些默认值。这是一个在工程组织高度（engineering organization altitude）的宽松策略（permissive strategy）。CTO 希望提升代码质量。他们强制要求每个 pull request 都必须包含测试，并且 CI/CD 应该阻止那些降低代码覆盖率的合并请求。这是一个在工程组织高度的指令性策略（proscriptive strategy）。某个产品工程团队希望减少软件中的安全漏洞。他们告诉工程师，在实现软件时要考虑一系列安全问题，并提供了供工程师自学的资源。这是一个在团队高度的宽松策略。某个产品工程团队希望减少影响用户的问题。他们决定在规划 sprint 时优先安排 bug 修复，只有清空 bug backlog 之后才安排新功能。这是一个在团队高度的指令性策略。

宽松策略比指令性策略成本更低，因为它们几乎不需要执行。低高度的策略（例如团队策略）比高高度的策略（例如组织或公司策略）成本更低，因为它们可以依赖本地机制来进行推广和维护，而不是依赖那些已经被过度使用、损耗严重的宽泛沟通机制（例如在全工程的聊天频道里沟通，最好的情况也是效果不佳）。

将这些想法结合起来，增加策略数量的公式就是：要么降低高度，要么增加宽松度，或者两者都做。

举一个具体例子，当我加入 Carta 时，我在入职前六个月在整个工程团队推动了相当多的策略工作。其中一些是记录已有的策略，因此不需要太多采用开销。其他部分则是方法的转变，所以我们重点制定宽松的策略。每份策略都包含一个“逃生出口”，支持本地定制，通常要求每个团队的 导航者（负责该领域的 Staff-plus 工程师）根据情况覆盖策略。只有在一个地方我采取了高度指令性的做法，那就是开通新服务——在那里的逃生出口更加严格，需要升级到 CTO。

由于我们专注于宽松策略，我们能够在较高的高度覆盖广泛的话题。如果我当时更指令性，这种做法肯定会失败，尽管我可能会显得像一个更有勇气的领导者。令人恼火的是，看起来有效和真正有效之间的相关性通常很低。

你是否做得太多了？

虽然很多工程师觉得自己的公司没有清晰的工程策略，但根据我的经验，更多领导者是因为尝试了过多的策略工作而失败，而不是因为做得太少。

要调试自己是否做得太多，最有价值的问题是：你之前的策略工作是否影响了后续所做的决策。

如果你分享了大量策略工作，但它似乎并没有影响软件的编写方式，那么你就应该缩减规模。相反，先专注于让单一一份策略真正有效，深入理解之前努力中哪里出了问题。只有在此之后，再回去修复之前的工作。最后，只有在完成前面这些步骤之后，才进一步扩展。

你也可能是做了正确的工作，但只是用过多的内容淹没了组织。采用新方法本来就很难，同时改变一切会让人不知所措。调整你的策略高度，让策略更容易被采用，并在现有策略被完全采纳之前，放慢新增策略的速度。

总结

读完本章后，你知道了何时编写策略是有效的，以及如何把握节奏来编写适量策略。你可以使用策略高度让策略更容易被采纳，也能调试自己是否用过多的策略工作让组织不堪重负。

如果你只从本章带走一件事，那就试着始终只专注于一份策略。做更多感觉像是在进步，但通常会失败。做得更少则永远是一个错过的机会。
