代理作为重复任务的脚手架

2026-04-12 · 阅读原文

我有一个天赋，也可以说是一种诅咒，那就是无休止地痴迷于如何优化流程。职业生涯早期短暂的一段时间里，我专注于改善人类协作的方式，但很快便转向思考如何最大限度减少人类的参与，并尽可能消除人与人之间的交接。最近，每当我执行一项重复性任务——或者看到别人在做——我就会思考如何通过引入代理（agents）来完全消除人类的参与。这个思路既取得了不错的效果，也遭遇过失败，我想分享一下我发现的这个有用模式。

举一个具体的例子，所有软件公司都面临的一个问题是修复安全漏洞。我们也面临同样的问题，我会定期查看我们的安全仪表盘，确保没有出现异常。有时在查看仪表盘时，我会注意到某个发现已经非常接近我们的解决SLA，这时我就会自己去修复，或者找到合适的团队来处理。然而，这感觉像是一个不应该需要我亲自检查的过程。

大约五六个月前，我把 Github Dependabot 的 webhook 作为输入加入到我们内部的代理框架中。然后我设置了一个代理来处理这些 webhook，包括将传入的消息过滤为最高优先级的问题。大约一个月前，当我从 GPT 4.1 升级到具有高推理能力的 GPT 5.4 时，我发现它非常擅长使用 Github MCP 来确定某个问题的合适负责人，它采用的正是人类会使用的各种技巧：查看可用的 Codeowners 文件，查看仓库最近的提交记录等等。这些警报和负责人信息已经被接入到一个 Slack 频道。

就这样，它成功了！然而实际效果并不那么理想，因为尽管我反复迭代 prompt，甚至加入了大量“CRITICAL: you must...”的声明，它仍然无法可靠地将自己限制在 critical 严重程度的警报上。它还会包含一些 high 严重程度的警报，甚至偶尔会出现 medium 严重程度的警报。这是将代理作为现成软件替代品时反复出现的问题：它们并不完美，而打扰同事则需要接近完美的准确率。

如果我雇佣了安全团队的人来通知各个团队关于 critical 警报，而他们偶尔标记了非 critical 的警报，最终会有人跑到我私信里问我出了什么问题。但在这里这种情况没有发生，因为我知道那些私信会出现，这阻止我更激进地推送通知。编码代理通过运行测试、类型检查或 linting 来解决这类问题，但对于结构化程度较低的任务，验证则要么更难，要么成本更高。例如，我本可以增加一个 eval，在允许它发送到 Slack 之前验证消息没有提及 medium 或 high 严重程度的任务，但我发现尽管知道它能生效，却还是有些不满意。

后来，在拖延了一阵其他任务之后，我终于让 Claude 更新这个代理，让它依赖于 构建内部 Agent：代码驱动 vs LLM 驱动的工作流，即默认由软件来管理流程控制，仅在合适的情况下才将控制权交给代理。该工作流如下：

DependabotScript 收到 webhook，提取严重程度和动作（例如是新问题还是已解决的问题），过滤掉低优先级或无法操作的 webhook；代码将元数据打包成问题和仓库的列表；代码将每个以仓库为范围的 bundle 传递给一个拥有我们内部所有权技能的代理，并使用 Github MCP 来确定每个问题应该通知哪些人；将问题和所有权数据传递给第二个代理，由它将它们格式化为 Slack 消息。

这个方案每次都能 100% 正常工作，同时仍然允许我们依靠内部所有权技能来确定针对某个问题最应该通知的团队或个人。现在我可以更激进地将其推广开来。

紧接着的快速跟进是一个每周对未解决 critical 问题的跟进提醒，同样依赖于确定性行为与代理行为的这种拆分。下一步改进将是自动化生成漏洞修复补丁，这样人类的参与就只剩下在它自动部署前进行审查。（我们 ，但根据我的经验，Dependabot 只能解决已发现问题中合理的一部分，远非全部。）自动合并 Dependabot PR

这就是我发现的有效模式：

先用代理驱动的工作流来原型验证，直到我对整个流程及其难点建立感觉；然后逐步重构，移除代理驱动的控制，越来越多地依靠代码驱动的工作流；最终形成一个版本，它只在代理擅长的领域（比如识别代码所有者这类模糊问题）狭义地使用它们。

这个方法几乎在我遇到的每一个问题上都效果良好。最终结果是更快、更便宜，也更易于维护。而且转变成本很低，通常我只需要把最近几次运行的日志、代理的 prompt 和一些简短说明扔给 Codex 或 Claude，几分钟内就能得到一个可用的替代方案。
