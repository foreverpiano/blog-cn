如何整合 Stripe 收购的 Index？（2018 年）

2025-02-27 · 阅读原文

关于收购的讨论通常聚焦于工程团队在并购中的角色以及是否应该进行收购。但收购完成后的整合工作可能更为复杂。在工程领域，很少有不可逆的“陷阱式”决策，但整合初期所做的决定往往具有惊人的持久性。

本工程策略探讨了 Stripe 在 2018 年收购 Index 后的整合方法。虽然商业书籍会重点讨论收购本身的理由，但在这里，收购理由只是定义整合权衡的诊断依据之一。本文的核心关注点是整合本身。

和大多数收购一样，负责整合的团队是在交易完成之后才了解到这个项目。这意味着早期的工作是一场紧急摸索，要通过策略测试：避免瀑布式策略陷阱，通过迭代优化。来区分乐观的日期预估与真实的技术情况。

本文是《Crafting Engineering Strategy》中的一章。

政策与运作

由于被收购方和收购方工程团队之间共享的背景知识很少，而我们只有六个月的时间来推出联合产品，因此我们最初的政策结合了对共同细化的承诺以及若干临时性架构策略：

在初始版本发布完成前，至少每周召开一次会议：Stripe 和 Index 的相关领导将每周举行同步会议，持续优化我们的方法，直至完成初始发布时间表。该会议由 Stripe 的流量工程负责人和 Index 的工程负责人共同主持。最小化对 tokenization 环境的修改：由于销售点（POS）设备会直接处理客户支付信息，直接支持 POS 设备的 API 必须位于我们存储支付信息的受保护环境中。但除此之外的任何其他功能都不得加入我们的 tokenization 环境。所有其他功能必须部署在标准环境中：除了必须迁移到 tokenization 环境的最小必要功能外，所有其他部分都必须运行在我们标准的、非 tokenization 的环境中。特别是任何需要频繁变更或引入复杂外部依赖的软件，都应存在于标准环境中。将引入 Java 的决策推迟到以后再定：引入 Java 与我们现有的工程策略不符，但目前我们也未能与利益相关方就如何处理该决策达成一致。此外，我们认为尝试解决这个问题会分散精力，影响我们在六个月内推出联合产品的及时目标。我们将在初始版本发布后再展开这项讨论。升级问题需提交给配对领导：鉴于团队间共享背景有限，所有升级问题必须同时提交给 Stripe 的流量工程负责人和 Index 的工程负责人。对影响 tokenization 环境的变更进行安全审查：我们需要快速推出结合 POS 与支付的产品，但绝不能为了加快发布而在安全上走捷径。任何涉及我们 tokenization 环境的整合决策，都必须纳入安全审查并获得明确批准。

诊断

收购通常可分为四类：人才收购（引入优秀团队）、业务收购（购买公司的收入和产品）、技术收购（增加内部难以开发的差异化能力），以及上市时间收购（虽然内部可以开发，但通过收购能显著加快速度）。

虽然大多数收购都会兼具上述几个维度，但本次收购主要属于上市时间收购，旨在解决以下限制：

我们几家最大的客户正在敦促我们提供与 API 驱动支付生态系统集成的销售点设备。其中至少有一家暗示，如果我们不能在承诺的时间内提供该功能，他们可能流失到竞争对手那里。我们目前在开发或集成 POS 设备等硬件方面缺乏内部专业知识。根据公司内部其他从零到一的项目经验，我们认为招聘团队、开发并推出集成到平台的最小可用 POS 产品大约需要一年时间。虽然我们在通过 API 支持网页支付方面采取了横向扩展的方法，但我们的竞争对手之一 Square 采取了垂直整合的策略。虽然他们的 API 生态系统不如我们的成熟，但对于那些威胁要流失的客户来说，他们是一个可信的选择。我们认为，如果我们最好的承诺是在 12 个月后推出 POS 解决方案，至少有一家企业客户会流失。因此，我们决定收购一家小型 POS 初创公司，以此承诺在六个月内为我们的 API 生态系统提供集成的 POS 设备支持。我们需要快速整合这家被收购的初创公司以满足该时间表。目前我们只掌握少量细节，尚不清楚具体需要做什么。但我们知道 POS 设备会直接操作支付信息（例如，POS 设备知道它读取的信用卡详细信息）。我们的合规义务将此类活动限制在我们的“tokenization 环境”中，这是一个高度安全且隔离的环境，能够直接访问支付详细信息。该环境会将支付详细信息转换为唯一令牌，其他环境可以使用该令牌进行支付相关操作，而无需承担直接访问底层支付信息的合规负担。在开始这次技术整合时，我们对被收购公司的技术栈了解甚少。我们只知道他们主要是一家使用 Java 的公司，运行在 AWS 上，而我们主要是一家使用 Ruby（辅以少量 Go）的公司，同样运行在 AWS 上。

探索

在本次收购之前，我们已经完成过几次小型收购。但那些收购都没有需要与我们产品进行有意义整合的实际产品，因此我们内部并没有多少可参考的 playbook 来指导我们的方法。

不过，我们在之前任职的公司有过整合技术收购的有限经验，也与在其他公司工作的同行交流过，吸取了他们的经验。综合这些经验，我们发现了一些反复出现的模式：

通常交易团队已经做出某些承诺，或者被收购团队理解为某些承诺，而这些承诺可能会难以兑现。当你不知道这些承诺可能是什么时，情况就更是如此。如果有人表现异常，很可能就是这类误解，值得直接沟通以澄清困惑。收购应该有一位高管赞助人，而这位赞助人通常是询问公司意图的最佳人选。如果你找不到这位高管赞助人，或者他们不够投入，那么与其在没有赞助人的情况下勉强推进，不如尝试招募一位新的高管赞助人。在文化摩擦较小的地方快速弥合文化差距，在信任不足的地方则要谨慎行事。我们确实需要将被收购公司融入我们的文化，但我们有好几年的时间来完成这件事。最成功的案例倾向于通过人员在被收购团队内外流动的方式，而不是强行推行。长期支持新的技术栈成本很高，而且与我们尽量减少编程语言种类以实现技术战略整合的目标相冲突。这不是可以灵活妥协的地方，因为新栈中的每一个额外功能都会让你离期望的结果越来越远。最后，找到一种方法来降低关键人员离职的风险。事情可能会迅速恶化。最简单的切入点之一是立即整合基础设施，即使产品或软件的整合需要更长时间。

总的来说，这次探索并不那么令人安心：它有些抽象，而且我们的很多调研都得到了强烈坚持但相互冲突的观点。或许收购就像创办一家新公司一样，属于那些根本不存在绝对正确做法的领域。
