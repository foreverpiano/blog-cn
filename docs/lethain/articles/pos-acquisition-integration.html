如何整合 Stripe 收购的 Index？（2018）

2025-02-27 · 阅读原文

关于收购的讨论通常聚焦于 工程团队在并购中的角色 以及 是否应该进行收购。 然而，收购完成后的整合过程往往更为复杂。 工程领域很少有不可逆的“无悔”决策， 但整合初期做出的决定往往具有惊人的持久性。

本工程策略探讨了 Stripe 在 2018 年收购 Index 后的整合方法。 商业书籍可能会重点讲述收购本身的理由， 但在这里，这些理由只是定义整合权衡的诊断的一部分。 整合本身才是我们关注的重点。

和大多数收购一样，负责整合的团队是在交易完成后才了解到这个项目， 这意味着初期的工作是一场紧急摸索， 需要运用 策略测试：通过迭代优化避免瀑布式策略陷阱 来区分乐观的日期预估与真实的技术现实。

这是《Crafting Engineering Strategy》中的一章。

政策与运营

我们起步时，收购方与被收购方的工程团队之间共享的上下文很少，却需要在六个月内推出联合产品。 因此，我们最初的政策结合了对共同迭代的承诺以及若干临时架构策略：

在初始版本发布完成前，至少每周举行一次会议：Stripe 和 Index 的相关领导将每周召开同步会议，持续优化我们的方法，直到达成初始发布的时间线。该会议由 Stripe 的流量工程负责人和 Index 的工程负责人共同主持。最小化对 tokenization 环境的修改：由于销售点（POS）设备直接处理客户支付信息，直接支持 POS 设备的 API 必须部署在我们存储支付详情的安全环境中。不过，任何其他功能都不得加入我们的 tokenization 环境。所有其他功能必须部署在标准环境中：除了必须迁移到 tokenization 环境的最小必要功能外，其他一切都必须运行在我们标准的、非 tokenization 的环境中。特别是任何需要频繁变更、或引入复杂外部依赖的软件，都应放在标准环境中。推迟关于引入 Java 的决策：引入 Java 与我们现有的工程策略不兼容，但目前我们也无法让利益相关方就如何处理这一决策达成一致。此外，我们认为尝试解决这个问题会分散注意力，影响我们在六个月内推出联合产品这一紧迫目标。我们将在初始版本发布后再讨论这个问题。升级问题需提交给配对领导：鉴于团队间共享的上下文有限，所有升级事项必须同时提交给 Stripe 的流量工程负责人和 Index 的工程负责人。对影响 tokenization 环境变更的安全审查：我们需要快速推出整合的 POS 和支付产品，但绝不能为了加快发布而牺牲安全。任何涉及 tokenization 环境的整合决策，都必须包含安全团队的参与并获得其明确批准。

诊断

收购通常可分为四类：人才收购（引入优秀团队）、业务收购（购买公司的收入和产品）、技术收购（增加内部难以开发的核心能力），以及加速上市收购（虽然内部可以开发，但通过收购能显著更快地实现能力）。

虽然大多数收购都会兼具上述几个维度，但本次收购主要是一次加速上市收购，旨在解决以下限制：

我们几个最大的客户强烈要求我们提供与 API 驱动的支付生态系统集成的销售点设备。其中至少有一家暗示，如果我们不能按承诺的时间表提供该功能，他们可能会流失到竞争对手那里。我们目前在开发或集成 POS 设备等硬件方面没有自有的专业知识。根据公司内部其他从零到一的项目经验，我们认为招聘团队、开发并推出集成到平台的最小可用 POS 设备产品大约需要一年时间。虽然我们通过 API 以横向方式支持 Web 支付，但我们的竞争对手之一 Square 采取了垂直整合的策略。尽管他们的 API 生态系统不如我们成熟，但对于那些威胁要流失的客户来说，他们是一个现实的选择。我们认为，如果我们能做出的最好承诺是在 12 个月后推出 POS 解决方案，那么至少有一家企业客户将会流失。因此，我们决定收购一家小型 POS 初创公司，以此承诺在六个月内支持与我们的 API 生态系统集成的 POS 设备。为了满足这一时间表，我们需要快速整合这家被收购的初创公司。目前我们只了解其中很少的细节。我们知道 POS 设备会直接操作支付信息（例如，设备知道它读取的信用卡详情）。我们的合规义务将此类操作限制在我们的“tokenization 环境”中，这是一个高度安全且隔离的环境，可直接访问支付详情。该环境将支付详情转换为唯一 token，其他环境可以使用该 token 处理支付相关操作，而无需承担直接访问底层支付详情的合规成本。在开始这次技术整合时，我们对被收购公司的技术栈知之甚少。我们只知道他们主要是一家使用 Java 的公司，运行在 AWS 上，而我们主要是一个使用 Ruby（辅以一些 Go）的团队，同样运行在 AWS 上。

探索

在本次收购之前，我们已经完成过几次小型收购。但那些收购都没有需要与我们产品进行实质性整合的内容，因此我们内部并没有成熟的 playbook 来指导本次整合。

我们确实从之前任职的公司中积累了一些整合技术收购的有限经验，也与在其他公司工作的同行交流过他们的经验。综合这些经验，我们发现了一些反复出现的模式：

交易团队通常已经做出某些承诺，或者被收购团队已经理解了某些承诺，而这些承诺可能很难兑现。当你不知道这些承诺具体是什么时，情况更是如此。如果有人表现异常，可能就是其中某项误解造成的，直接沟通以澄清困惑是值得的。收购应该有一位高管赞助人，而这位赞助人通常是询问公司意图的最佳人选。如果你找不到这位高管赞助人，或者他们不够投入，那么与其在没有赞助人的情况下勉强推进，不如尝试招募新的高管赞助人。在文化摩擦较小的地方快速弥合文化差异，在信任不足的地方则需谨慎推进。我们确实需要将被收购公司融入我们的文化，但我们有多年时间来完成这件事。最成功的案例更多依靠人员在收购团队内外流动，而不是强行推动。长期支持一项新技术栈的成本很高，而且与我们尽可能合并编程语言的技术策略相冲突。在这个问题上不应该妥协，因为新栈中每增加一项特性，都会让你离期望的结果更远。最后，找到降低关键人员离职风险的方法。事情可能会迅速恶化。一个最简单的切入点是立即整合基础设施，即使产品或软件的整合需要更长时间。

总的来说，这次探索并不那么令人安心：它有些抽象，而且我们的研究得出了许多强烈但相互冲突的观点。或许收购就像创办一家新公司一样，属于那些根本不存在完美做法的领域。
