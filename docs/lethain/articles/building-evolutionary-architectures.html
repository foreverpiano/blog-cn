构建演进式架构笔记

2019-11-15 · 阅读原文

我最近读了 Neal Ford、Rebecca Parsons 和 Patrick Kua 合著的《Building Evolutionary Architectures》。这本书在我脑海里与 Accelerate 对开发者生产力的定义 和 《软件设计哲学》笔记 属于同一类，都是经验丰富的软件从业者分享他们对软件开发的通用方法论。我非常喜欢这本书，它更优雅地阐释了许多我在 收回不合理的软件 中试图表达的观点。

以下是我阅读《Building Evolutionary Architectures》时做的笔记。

内容概要

这本书开头提出了一个我经常思考的问题：“当一切都在不断变化时，如何才能进行长期规划？”他们的答案是演进式架构（evolutionary architecture），即“支持在多个维度上进行有引导的、增量式变化”的架构。

增量式变化既指“团队如何构建软件”，也指“他们如何部署软件”。以这种方式构建软件，需要持续交付有价值的小块功能，从而远离“大爆炸式软件开发”的悲剧。而增量式部署软件，则采用《Accelerate 对开发者生产力的定义》中所描述的现代开发实践。

有引导的变化是指定义“适应度函数”（fitness functions），用以衡量安全性、可用性等重要属性的状态。然后依靠这些适应度函数来评估每次变更，确保系统朝着预期的方向前进。这些适应度函数在部署流水线中自动运行，将架构师从“看门人”角色中解放出来，让他们专注于引导而非强制执行。

多个维度指的是你希望确保的任何方面，例如安全性、数据结构、可靠性、延迟、可观测性等等——任何重要的属性。每个维度都应该有一个或多个适应度函数来支持其有引导的变化，或者说“对该维度进行投影”。

适应度函数

书中将适应度函数定义为：“一种架构适应度函数为某些架构特性提供客观的完整性评估。”适应度评估通常在部署流水线中进行，最好以单元测试的形式，这样可以在本地运行，获得最快的开发反馈循环。

原子型 vs 整体型

适应度函数有两种主要类型：原子型和整体型。

原子型适应度函数“针对单一上下文运行，只验证架构的某一个特定方面”。例如 Sorbet 在代码库中断言类型有效性，就是原子型适应度函数的例子。断言代码库中没有不兼容的依赖关系也属于此类。

整体型适应度函数“针对共享上下文运行，会同时验证多个架构方面，例如安全性和可扩展性”。确保没有将个人身份信息（PII）写入日志系统就是一个整体型适应度函数。监控代码变更后延迟是否增加也属于整体型。

触发型 vs 持续型

适应度函数还有另外两个维度：触发型和持续型。

触发型适应度函数“基于特定事件运行，例如开发者执行单元测试”。这些是在部署流水线中按需运行的验证，也包括本地开发时的检查：如代码 lint、测试、模糊测试、覆盖率检查等。

持续型测试“不是按计划运行，而是持续进行验证”。这可能包括对延迟发出告警，或者确保基础设施成本朝着预算目标发展。

静态型 vs 动态型

这个分类体系还可以进一步扩展到静态型和动态型适应度函数。

静态型适应度函数“具有固定的评估结果，例如单元测试的通过/失败二元结果”。可接受的延迟范围、可接受的测试覆盖率、单元测试通过与否等都属于这一类。

动态型适应度函数“依赖于额外上下文而变化的定义”。例如在数据新鲜度和请求量之间进行权衡：在高流量基础设施下，允许较低的新鲜度（从而使用更多缓存）。

自动型与手动型

关于适应度函数的最后一个区分是自动型和手动型，顾名思义。

设计适应度函数

你应该在项目生命周期的早期就识别出适应度函数，因为它们是防止质量退化的棘轮机制。然而，由于在系统真正大规模运行之前你无法完全理解它，因此必然会错过一些潜在有用的适应度函数。为了解决这个问题，应该定期（至少每年一次，不过这个频率似乎还是偏低）召开会议，刷新和重新评估系统的适应度函数。

增量式变化

当你采用服务架构时，要确保客户端能够按照自己的节奏升级，而不是假设所有客户端都会立即同步升级（它们不会）。同时，要自动化停用不再接收流量的服务和版本。（根据我的经验，逐步淘汰旧版本的棘轮模式特别有用。）

建议在服务内部进行版本管理，而不是让客户端传递版本号。这样可以标记传入请求并将其路由到正确的实现，但客户端调用的端点保持不变。“无论哪种情况，都要严格限制支持的版本数量”，特别要“努力同时只支持两个版本，而且只是临时性的”。

可测试性对实现增量式变化至关重要，它支持快速的开发反馈循环。它也让我们摆脱“严格的开发规范（以及随之而来的官僚式指责）”。

在开发过程中，适应度函数之间必然存在权衡，关键是要尽早用它们来进行结构化的讨论。同时，它们也是很好的安全阀，能让你及时意识到自己正在走向不可接受的权衡路径。

他们推荐采用假设驱动开发（hypothesis-driven development），“而不是收集正式的需求……而是利用科学方法”。这是一个非常有启发性的想法，让我想起 逃离构建陷阱笔记 中对产品开发的愿景。

架构耦合

模块化是“相关代码的逻辑分组”，也是限制架构耦合的最重要工具之一。将相关功能组织成模块，以最大化功能内聚性。目标是将模块范围设定为架构量子（architectural quantum），即“一个具有高功能内聚性的可独立部署组件”。

小模块更容易修改，因此通常倾向于更小的模块，但找到正确的边界是平衡耦合与复杂度的关键。

书中讨论了不同代码库风格的可演进性：大泥球、单体应用、分层架构、模块化单体（例如有强制模块边界的单体）、微内核（“带有一个允许插件增强的 API 的核心系统”）、事件驱动架构、中介者模式、面向服务的架构、微服务、基于服务的架构以及无服务器架构。选择哪一种并不如把实现设计好更重要。

演进式数据

架构演进面临的最大阻力之一来自底层数据，这种阻力催生了演进式数据（evolutionary data）实践。这要求 schema 必须是（1）可测试的、（2）带版本的、（3）增量式的。（我个人认为 django-migrations 在这方面提供了很好的模式值得学习。）

理想情况下应该采用共享无（shared-nothing）架构，应用不直接对接同一个数据库。如果你必须这么做，可以考虑“展开/收缩模式”（expand/contract pattern），它允许你支持更广泛的功能、逐步过渡，然后通过 、代码棘轮等手段移除旧的实现。以编程方式重构 Ruby 代码

书中还提出了“不当数据耦合”的概念，例如事务会强制产生较大的架构量子。事务中的任何部分都需要与其他参与该事务的组件一起部署。事务通常还由数据库管理员或基础设施团队负责，这又引入了跨团队协调的问题。

这一部分还敏锐地指出 DBA 工具非常薄弱，为什么 IDE 这么好而 DBA 工具却这么差？他们将原因归于 DBA 的“厂商即宗教”行为，但把工具不足完全归咎于 DBA 对厂商的忠诚，似乎有点过于简化。

构建可演进的架构

构建可演进架构的建议：

“消除不必要的可变性”，通过采用不可变基础设施、长期存在的特性开关等手段。“让决策可逆”，让回滚部署变得容易。相比缓慢回滚旧版本，更应该立即将流量从故障的新版本上切走。相比重新部署，更倾向于通过翻转开关来禁用新功能，等等。“宁要可演进，不要可预测”。如果你只针对已知的架构挑战进行优化，最终会陷入困境，因为未知的挑战至少和已知的一样多。能够快速响应问题，远比干净地解决当前已知的问题更好。“构建防腐层”。这主要意味着构建良好的接口，以便将来可以替换底层实现。增加接口本身也有成本，因此需要与“最后责任时刻”原则进行平衡。“构建可牺牲的架构”。要接受你做出的权衡不会永远有效，偶尔丢弃已有实现也没关系。书中举了 eBay 在七年里从 Perl 重写到 C++ 再到 Java 的例子。“缓解外部变化”。例如，不要直接依赖全局包仓库，而是把需要的包复制到本地。这样你就可以自主控制升级时机，同时掌握构建流水线的可靠性。“库与框架之争”。作者反对使用框架，因为使用框架时你是在编写与框架集成的代码，而不是编写调用库的代码。因此框架会导致更紧密的耦合。“在服务内部进行版本管理”。在之前的笔记中已经讨论过，不要将版本标识泄露给用户，而是检查传入请求并进行恰当处理。由服务来管理这种复杂性，比让所有客户端来处理要容易得多。“产品而非项目”。围绕长期存在的产品而不是短期项目来组建团队，并由此塑造架构。“应对外部变化”。你的客户端（即向你的服务发送请求的软件）需求会随时间变化，要定义明确的契约来表述这些约定，或许可以采用服务水平目标（Service Level Objectives）。“实验文化”。演进建立在结构化、可衡量的实验基础上，这需要 。从容易摘到的果实开始。小胜利会带来大胜利，从容易的地方起步。（我本周早些时候和 Keith Adams 聊天，他描述了一个幂函数，用来表示哪些文件/系统经常被修改，因此或许应该从改动最频繁的地方开始。）探索的量级

最后感想

这是一本非常棒的书，很容易和《Accelerate》以及《A Philosophy of Software Design》一起归入同一稀有类别。我完全可以想象要求正在合作的团队一起阅读这本书，并反思其中的实践。如果你还没有机会阅读它，我强烈推荐。
