构建演进式架构的笔记

2019-11-15 · 阅读原文

我最近读了 Neal Ford、Rebecca Parsons 和 Patrick Kua 合著的《Building Evolutionary Architectures》。这本书在我脑海里与 Accelerate 对开发者生产力的定义 和 《软件设计哲学》笔记 处于相似的位置，都属于经验丰富的软件从业者分享他们对软件的通用方法论的著作。总体来说，我非常喜欢它，它也更优雅地阐明了我之前在 收回不合理的软件 一文中试图表达的许多观点。

以下是我阅读《Building Evolutionary Architectures》时做的笔记。

概要

这本书一开始就提出了一个我经常思考的问题：“当一切都在不断变化时，如何才能做好长期规划？”他们的答案是演进式架构，即“能够在多个维度上支持受引导的、增量式演变的架构”。

增量式变化既体现在“团队如何构建软件”，也体现在“他们如何部署软件”。以这种方式构建软件，需要持续交付具有增量价值的小单元，从而远离“大爆炸式”软件开发带来的悲剧。而增量部署软件，则采用的是 Accelerate 对开发者生产力的定义 中所描述的现代开发实践。

受引导的变化是指识别出“适应度函数”（fitness functions），用以衡量安全性、可用性等重要属性的当前状态。然后依靠这些适应度函数来评估每次变更，确保它们正朝着预期的目标前进。这些适应度函数在部署流水线中自动运行，从而把架构师从“守门人”的角色中解放出来，让他们可以专注于引导而非强制执行。

多个维度指的是你希望确保的任何方面，例如安全性、数据结构、可靠性、延迟、可观测性等等——任何重要的属性。每个维度都应该有一个或多个适应度函数来支持其受引导的变化，或者说“投影该维度”。

适应度函数

书中将适应度函数定义为：“一个架构适应度函数对某些架构特性提供客观的完整性评估。”适应度评估通常在部署流水线中进行，最好是以单元测试的形式，这样可以在本地运行，获得最快的开发反馈循环。

原子型 vs 整体型

适应度函数有两种主要类型：原子型和整体型。

原子型适应度函数“针对单一上下文运行，只检验架构的某一个特定方面”。例如 Sorbet 在代码库中断言类型是否有效，就是一个原子型适应度函数；再比如断言代码库中不存在不兼容的依赖，也属于此类。

整体型适应度函数“针对共享上下文运行，会同时检验多个架构方面，例如安全性和可扩展性”。确保没有将个人身份信息（PII）写入日志系统就是一个整体型适应度函数；监控代码变更后延迟是否增加，也属于整体型。

触发型 vs 持续型

适应度函数还有另外两个维度：触发型和持续型。

触发型适应度函数“基于特定事件运行，例如开发者执行单元测试”。这些是在部署流水线中按需运行的验证，也包括本地开发时的检查：如代码 lint、测试、模糊测试、覆盖率检查等等。

持续型测试“不是按计划运行，而是持续进行验证”。这可能包括对延迟的告警，或者确保基础设施成本朝着预算目标发展。

静态型 vs 动态型

这个分类体系还可以进一步扩展到静态型和动态型适应度函数。

静态型适应度函数“具有固定的判断结果，例如单元测试的通过/失败二元结果”。可接受的延迟范围、可接受的测试覆盖率、单元测试通过等都属于这一类。

动态型适应度函数“依赖于额外上下文而不断变化的定义”。例如，它可能体现新鲜度和请求量之间的权衡：在高流量基础设施下，容忍较低的新鲜度（从而使用更多缓存）。

自动化与手动

关于适应度函数的最后一个区分是自动化和手动，这和字面意思一致。

设计适应度函数

你应该在项目生命周期的尽早阶段就识别出适应度函数，因为它们就像防止质量下降的棘轮。然而，由于在系统真正大规模运行之前你无法完全理解它，因此一定会遗漏一些有价值的适应度函数。为了解决这个问题，需要定期（至少每年一次，虽然这个频率似乎还是偏低）召开会议，刷新并重新评估系统的适应度函数。

增量式变化

当你处于服务化架构中时，要确保客户端能够按照自己的节奏升级，而不是假设所有客户端都会立即同步升级（它们不会）。同时要自动化下线不再接收流量的服务和版本。（根据我的经验，逐步淘汰旧版本的棘轮式推进模式特别有用。）

书中推荐在服务内部进行版本管理，而不是让客户端传递版本号。这样可以给 incoming 请求打上指纹并路由到正确的实现，而客户端调用的端点本身无需改变。“无论哪种情况，都要严格限制支持的版本数量”，特别是“力争同时只支持两个版本，而且只是临时性的”。

可测试性对增量式变化至关重要，它支持快速的开发反馈循环。同时也能摆脱“严格的开发规范（以及随之而来的官僚式训诫）”。

在开发过程中，适应度函数之间必然存在权衡，关键是要尽早利用它们进行结构化的讨论。它们也是一个很好的安全刹车，能让你及时意识到自己正走向一条不可接受的权衡路径。

他们建议采用假设驱动开发（hypothesis-driven development），“与其收集正式的需求……不如利用科学方法”。这是一个非常有意思的想法，让我想起 逃离构建陷阱笔记 中对产品开发的愿景。

架构耦合

模块化是“将相关代码进行逻辑分组”，是限制架构耦合的最重要工具之一。将相关功能组织成模块，以最大化功能内聚。目标是将模块范围控制在架构量子（architectural quantum）层面，即“一个具有高功能内聚的、可独立部署的组件”。

小的模块更容易变更，因此一般倾向于更小的模块，但找到正确的边界才是平衡耦合与复杂性的关键。

书中讨论了不同代码库风格的可演进性：大泥球、单体应用、分层架构、模块化单体（例如单体但强制实施模块边界）、微内核（“带有一个允许插件扩展的 API 的核心系统”）、事件驱动架构、中介者模式、面向服务的架构、微服务、基于服务的架构以及 Serverless。选择哪种风格其实没有那么重要，更重要的是把选定的实现设计好。

演进式数据

架构演进中最大的阻力之一来自底层数据，这种阻力催生了演进式数据（evolutionary data）实践。这要求数据 schema 必须是（1）可测试的、（2）带版本的、（3）增量式的。（我个人认为 django-migrations 在这方面提供了很好的学习模式。）

理想情况下应该采用共享无（shared-nothing）架构，应用不直接访问同一个数据库。如果你必须这么做，可以考虑“扩展/收缩模式”（expand/contract pattern），它允许你支持更广泛的功能、逐步过渡，然后通过代码重写 用程序化方式重构 Ruby 代码、代码棘轮等方式移除旧实现。

书中还引入了“不恰当的数据耦合”这一概念，例如事务会强制形成大的架构量子。事务内的所有部分都需要与其他参与该事务的组件一起部署。此外，事务通常由数据库管理或基础设施团队拥有，这又引入了跨团队的协调问题。

这一部分还敏锐地指出了 DBA 工具的薄弱之处——为什么 IDE 如此优秀而 DBA 工具却如此简陋？他们将原因归咎于 DBA 的“厂商即宗教”行为，但把工具缺失完全归因于 DBA 对厂商的忠诚，似乎有些过于简化了。

构建可演进的架构

构建可演进架构的建议如下：

“消除不必要的可变性”，通过采用不可变基础设施、长期存在的特性开关等手段。“让决策可逆”，让回滚部署变得容易。相比缓慢回滚到旧版本，更应该立即把流量从有问题的版本上切走；相比重新部署，更倾向于通过切换开关禁用新功能，等等。“宁要可演进，不要可预测”。如果你只针对已知的架构挑战做优化，就会陷入困境，因为未知的挑战至少和已知的一样多。能够快速响应问题，远比干净地解决当前已知的问题更重要。“构建防腐层”。这主要指构建良好的接口，以便能在下面更换具体实现。增加接口本身也会有成本，因此要与“最后责任时刻”（last responsible moment）这一原则进行平衡。“构建牺牲式架构”。假设你做的某些权衡不会永远有效，并接受偶尔丢弃已有实现。书中举了 eBay 在七年里从 Perl 重写到 C++ 再到 Java 的例子。“缓解外部变化”。例如，不要直接依赖全局的包仓库，而是把需要的包拷贝到本地。这样你就可以自主控制升级时机，同时掌握构建流水线的可靠性。“库与框架”。作者反对使用框架，因为使用框架时是你写的代码去适配框架，而使用库时则是你的代码去调用库，因此框架会带来更紧密的耦合。“在服务内部做版本管理”。前面笔记中已经讨论过，不要把版本标识泄露给用户，而是通过检查 incoming 请求来恰当处理。对服务自身来说，管理这种复杂性比让所有客户端都处理它要容易得多。“产品而非项目”。围绕长期存在的产品，而不是短期项目，来组建团队，并由此塑造架构。“应对外部变化”。你的客户端（即向你的服务发送请求的软件）需求会随时间变化，要定义明确的契约来表述这些约定，或许可以采用服务水平目标（Service Level Objectives）。“实验文化”。演进建立在结构化的、可度量的实验之上，而这需要 。从容易摘到的果子开始。小胜利会带来大胜利，从容易的地方入手。（我这周早些时候和 Keith Adams 聊天，他描述了一个幂函数，用来衡量哪些文件或系统被频繁修改，因此或许应该从变化最频繁的地方开始。）探索的量级。

最后感想

这是一本非常出色的书，很容易与《Accelerate》和《A Philosophy of Software Design》归为同一类稀有好书。我完全可以想象让正在合作的团队一起阅读这本书，并反思其中的实践。如果你还没有机会读它，我强烈推荐。
