负载生成小记

2016-12-18 · 阅读原文

Stripe 正在西雅图组建一个负载生成团队（职位虽然写在旧金山，但同样适用于西雅图），因此我最近对负载生成这个话题思考得更多了。具体来说，我意识到自己对这个领域的了解远没有达到想要的程度，于是整理了一批资料和阅读笔记。

希望很快就能把这些内容整合成一篇可读性较强的文章！

有趣的问题

可能因为很多公司从未开发出成熟的负载生成方案，而且开源工具中也没有哪个广为人知（也许 JMeter 算一个例外？），这个领域往往充斥着远超平均水平的各种意见，因此值得深入思考的问题也特别多。

让我们先来探讨其中几个。

你是否应该做负载测试？令人惊讶的是，只有很少的公司会在负载测试上投入大量资源，因此在某个具体时间点是否应该投入，始终不是特别明确。根据我的经验，那些“相信 QA”的公司往往较早就会投资负载测试，因为他们有专职人员可以构建工具和集成；而大多数其他公司则倾向于忽略它，直到他们不得不进行大量计划外的可扩展性投入。换句话说，对大多数公司而言，负载测试是一种将计划外的可扩展性工作转化为计划内工作的机制。 你是否应该做负载测试（续）？除了是否要投入资源构建负载测试工具之外，我的同事 Davin 提出了一个有趣的视角：负载测试产生的大部分指标，其实也可以通过对现有流量进行 thoughtful 的埋点和分析来获得。 你应该对基础设施的哪一层进行负载测试？根据你所运行的应用不同，对外部接口（网站、API 等）产生负载可能比较容易，但当你深入基础设施内部时，你可能希望针对特定服务或有状态系统（Kafka、数据库等）施加负载。 你应该在什么环境里运行测试？推出负载测试时最常见的争论之一，就是应该针对现有的 QA 环境、专用的性能测试环境，还是生产环境运行。这在很大程度上取决于你测试的层次，以及你是在做负载测试（系统对这种流量如何反应？）还是压力测试（系统在多大负载下会失效？）。 你应该如何对流量进行建模？从最简单的 Siege 开始，有很多不同的思路来生成负载。你是应该用高并发发送少量请求模式，还是用状态机（用简单脚本或 DSL 编码）来建模流量，抑或直接回放经过脱敏的生产流量？ 集成测试和负载测试的区别是否只是规模问题？仔细想想，集成测试就是向服务器发送请求并确保结果合理，这和负载测试本质上几乎是一回事。这让人很想用同一个工具同时解决这两个问题。 你应该如何配置负载测试？配置应该放在哪里？加入到“配置是否是代码”的大讨论中，负载测试的配置应该放在哪里？理想情况下它应该放在服务的代码仓库里，对吧？还是说为了更灵活地探索和测试，应该存放在某个动态配置数据库里？嗯。

好了，带着这些问题，是时候去读一些论文了。

压力与负载测试研究

在研究过程中，我发现得克萨斯大学阿灵顿分校软件工程研究组整理了一份非常好的压力与负载测试论文清单。我下面提到的很多论文都来自那里，它也是一个很好的阅读起点！

支持负载测试分析的方法论

《A Methodology to Support Load Test Analytics》（2010）以一个极好的观点开头，解释了为什么负载测试正变得越来越重要且复杂：

对于[超大规模系统]来说，分析人员不可能浏览海量的性能计数器来找到所需信息。相反，分析人员只会使用自己从过去经验、性能专家和领域趋势中了解到的少数关键性能计数器作为“经验法则”。在超大规模系统中，没有任何一个人对端到端的地理分布式系统活动拥有完整知识。

这和我自己的经验非常吻合。

随着系统越来越复杂，要真正找到性能瓶颈变得极为困难，而负载测试的目标就是提供分布式系统领域的“性能分析器”。（这也是为什么 QA 环境经常以失败告终：随着系统日益复杂，创建一个有用的仿真环境变得相当困难。）

另外几个有趣的想法包括：

相当朴素的软件就能把高度相关的指标批量聚合，从而大大减少人类需要搜索的空间来理解哪里在退化。 大多数测试设计意味着它们只能偶尔运行（而非持续运行），而干扰性负载（例如在你做负载测试时恰好运行的每周批处理任务）很容易让这些不频繁的运行结果失效。 许多测试在非生产环境（如 QA）中运行时会受到人为约束，例如面对算力不足或配置错误的数据库。 他们使用“主成分分析”来找出相互不相关的极简主成分，从而减少需要探索的冗余数据。 在找到关键主成分后，他们再将其转换回底层可被人理解的计数器，以便进一步分析。 理想情况下，你应该能够利用历史数据构建负载特征，这样就能快速判断系统根本的约束是否发生了变化（例如你终于修复了核心瓶颈却出现了新的瓶颈，或者其他地方退化成了新的核心瓶颈）。

特别地，我的 takeaway 是：合适的负载生成工具可能应该从一个相当简单、人工挑选关键指标的方法开始，然后逐步转向使用机器学习，来避免我们对系统哪里应该慢的固有偏见。

地理分布式网络流量生成的统一负载生成器

《A Unified Load Generator for Geographically Distributed Generation of Network Traffic》（2006）是一篇硕士论文，却意外地成为了一篇非常优秀的关于负载生成学术思想和主题的综述。

其中一个有趣的想法是：

要设计一个准确的人工负载生成器，使其能够在不同情况下灵活工作，我们不仅需要一个负载模型，还需要一种形式化方法来描述真实的负载。

我不完全同意我们需要一个形式化模型才能从负载测试中获得价值，毕竟我们只是想把计划外的可扩展性工作转化为计划内的工作。但我有很强的行业视角，所以“甚至可以尝试在这里建立形式化模型”这个想法本身就让我觉得非常有意思。

它还引入了一套更精确的词汇来讨论负载生成：

工作负载或负载 L=L (E, S, IF, T) 表示由环境 E 在时间区间 T 内，通过定义良好的接口 IF 向服务系统 S 提供的请求总序列。

或许更有趣的是，它强调了QoS、成本与配额如何迫使我们重新定义负载测试的目标：

对能够提供数据、语音和视频等通信服务的电信网络的需求，促使我们向用户交付可接受的服务质量（QoS）水平，而其成功取决于有效拥塞控制机制的发展。

我觉得这是一个非常有意思的点。随着你的系统开始包含更多系统的负载丢弃机制，要把它们推出平衡状态会变得越来越困难，因为它们（通常）会通过降低 yield 来保护 harvest。因此，仅仅说系统在某个负载水平下应该或不应该失败是不够的，你还必须开始衡量它是否根据负载水平进行了适当的降级。

在 3.5 节中，它解释了（看似众所周知但我之前并不知道的）UniLog，也称为统一负载生成器。（它可能基于这篇论文，可惜被 paywall 挡住了。）UniLog 有一个有趣的架构，带有 PLM、ELM、GAR、LT、ADAPT 和 EEM 这样令人望而生畏又兴奋的组件名称。据我所知，它是一个极其通用的运行和评估负载实验的架构。第一次读起来感觉有点过度设计，但也许当你在这个负载生成领域钻得更深之后，它就会变得更有意义。

在 4.4 节中，它讨论了集中式与分布式负载生成，这感觉是你构建此类系统时需要做出的核心设计决策之一。我的感觉是，你最终很可能需要采用分布式方式，至少是为了避免被基于 per-IP 限流的 QoS 完全限制住。

论文的其余部分聚焦于一些案例研究等。总的来说，它是一篇令人惊喜的、相当全面的相关研究入门读物。

负载测试结果的自动化分析

《Automated Analysis of Load Testing Results》探讨了如何使用自动化手段来理解负载测试结果（同时使用负载测试的执行日志和测试期间的整体系统指标）。

它将分析负载测试结果的挑战总结为：文档过时、进程级 profiling 成本过高、负载测试通常出现在开发周期后期且时间紧张，以及负载测试的输出可能大到令人难以招架。

我认为对我来说最有趣的 takeaway 是，非常明确地将性能数据的采集与分析解耦。例如，你可以很早就开始记录性能数据（而且很可能你的指标工具，比如 Graphite，已经在采集这些数据了），并在更晚的时候再投入更复杂的分析。其中特别关注跨多个负载测试运行的结果对比，这至少可以帮助缩小性能“位置”在你的指标体系中的范围。

更多论文……

另外几篇论文及简短总结：

《Converting Users to Testers》——这篇论文讨论了记录用户流量作为负载测试输入，以减少编写负载生成脚本所花费的时间。

《Automatic Feedback, Control-Based, Stress and Load Testing》——这篇论文探讨了这样一类系统：它们尝试驱动并维持系统负载在目标阈值上。这是一个有趣的想法，因为它能让你持续对生产环境施加负载。唯一的 caveat 是，你必须首先确定你想用来影响负载的输入，因此你仍然需要对流入流量进行建模才能将其作为输入（或者记录并清洗真实流量），但一旦你有了模型，就可以以更抽象的方式使用它（如果你的目标是制造负载，你不一定需要模拟真实的流量，你可以用类似 n-armed bandit 的方法来“优化”你的负载，使其对系统产生正确量的压力）。（类似地，另一篇论文尝试使用遗传算法来实现这一点。）

现有工具

负载测试工具 surprisingly 很少，虽然 Wikipedia 有一个简短列表。在那个列表里，我多年前确实用过 JMeter，我也挺喜欢这篇对 HP Loadrunner 工具的简短吐槽。

我简单看了下 Gatling，它是一个用 Scala 写的轻量级 DSL，可以很容易地被 Jenkins 等运行。这似乎是一个构建负载生成工具的有趣潜在起点。特别是把负载测试当作可以签入代码仓库的东西，这种理念感觉很对，能让你像对待其他代码一样迭代你的负载测试。 阅读另外几篇关于 Gatling 的博客文章后，我更强烈地感觉到它可能是整体负载测试系统的一个有用组件（例如允许在不同端点上运行多个实例等）。

还有其他我遗漏的重要工具吗？

根据 UniLoG 方法的 Web 工作负载生成

正如标题所示，《Web Workload Generation According to UniLoG Approach》研究了如何将 UniLoG 方法适配到 Web 领域。它也很好地总结了 UniLoG 的方法：

UniLoG 设计和阐述的基本原则是：从对抽象负载模型的形式化描述开始，然后使用一个接口相关的适配器，将抽象请求映射到真实接口上服务提供组件所能“理解”的具体请求。

它还很好地探讨了生成请求的各种方式，尽管最终还是回到要么使用现有流量的日志，要么生成一个定义工作负载的模型。这里有一个有趣的混合方案：使用实际使用量的分布作为生成负载的输入（而不是一对一地复制负载）。

不过遗憾的是，我从这篇论文里并没有收获太多。
