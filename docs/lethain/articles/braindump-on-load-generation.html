关于负载生成的思考倾倒

2016-12-18 · 阅读原文

Stripe 正在西雅图组建一个负载生成团队（职位招聘信息写的是旧金山，但同样适用于西雅图），因此我最近对负载生成这个话题思考得更多了。特别是，我意识到自己对这个领域的了解远不如自己期望的那么多，所以就整理了一份资料清单和阅读笔记。

希望很快能将这些内容提炼成一篇容易阅读的文章！

有趣的问题

可能是因为很多公司从未开发出成熟的负载生成方案，而且开源解决方案中也没有哪个获得广泛认知（也许 JMeter 算一个？），这个领域往往充斥着远超平均水平的各种意见，因此值得深入思考的有趣问题也相当多。

让我们先来探讨其中几个。

你是否应该做负载测试？令人意外的是，只有极少数公司会在负载测试上投入大量资源，所以在某个时间点是否值得投入并不总是很清楚。我的经验印象是，那些“相信 QA”的公司倾向于较早投资负载测试，因为他们有专职人员可以构建工具和集成；而大多数其他公司则会忽略它，直到他们不得不进行大量计划外的可扩展性投入。换句话说，对大多数公司而言，负载测试是一种将计划外的可扩展性工作转化为计划内工作的机制。你是否应该做负载测试（续）？除了是否应该投资构建负载测试工具之外，我的同事 Davin 提出了一个有趣的观点：大多数由负载测试产生的指标，也可以通过对现有流量进行细致的埋点和分析来获得。你应该针对基础设施的哪一层进行负载测试？取决于你所运行的应用，你可能很容易对外部接口（网站、API 等）产生负载，但当深入基础设施内部时，你可能希望针对特定服务或有状态系统（Kafka、数据库等）施加负载。你应该在什么环境上运行测试？推出负载测试时最常见的争议之一，就是应该针对现有的 QA 环境、专用的性能测试环境，还是生产环境运行。这在很大程度上取决于你测试的层次，以及你是在做负载测试（系统对这些流量如何反应？）还是压力测试（系统在多大负载下会失效？）。你应该如何建模流量？从最简单的 Siege 开始，有很多不同的方式来思考如何生成负载。你是应该以高并发发送少数几种请求模式？还是应该使用状态机（编码成简单脚本，或者用 DSL）来建模流量，抑或是直接重放经过清洗的生产流量？集成测试和负载测试的区别是否只是规模问题？仔细思考后会发现，集成测试就是向服务器发送请求并确保结果合理，这和负载测试几乎是完全一样的事情。这让人很想用一个工具同时解决这两个问题。你应该如何配置负载测试？配置应该放在哪里？融入“配置是否是代码”这个大讨论，负载测试的配置应该存放在哪里？理想情况下，它应该放在服务的代码仓库里，对吧？还是说应该存放在某个动态配置数据库中，以便进行更自然的探索和测试？嗯。

好吧，带着这些问题，是时候读一些论文了。

压力和负载测试研究

在研究过程中，我发现得克萨斯大学阿灵顿分校软件工程研究组整理了一份非常优秀的压力和负载测试论文清单。下面的很多论文都来自那里，这也是一个很好的阅读起点！

支持负载测试分析的方法论

《支持负载测试分析的方法论》（2010）以一个绝佳的观点开篇，解释了为什么负载测试正变得越来越重要且复杂：

对于[超大规模系统]来说，分析人员不可能浏览海量的性能计数器来找到所需信息。相反，分析人员只会使用少数几个来自过去实践、性能专家和领域趋势的“经验法则”关键性能计数器。在超大规模系统中，没有任何人拥有对端到端地理分布式系统活动的完整知识。

这和我自己的经验非常一致。

随着系统日益复杂，真正找到性能瓶颈点变得非常困难，而负载测试的目标就是提供分布式系统领域的性能分析器。（这也是为什么 QA 环境经常以失败告终：随着系统越来越复杂，创建一个有用的仿真环境变得相当困难。）

其他几个有趣的想法包括：

相当朴素的软件就能将高度相关的指标批量处理，从而大幅缩小人类需要理解的搜索空间，以找出系统哪里在退化。大多数测试设计意味着它们只能偶尔运行（而非持续运行），而干扰的工作负载（例如在负载测试期间运行的周批处理任务）很容易使这些不频繁运行的数据失效。许多测试在非生产环境（如 QA）中运行时会遇到人为的限制，例如遇到算力不足或配置错误的数据库。他们使用“主成分分析”来找出彼此不相关的最小主成分，从而减少需要探索的冗余数据。在找到关键主成分后，他们再将其转换回底层计数器，这些计数器是人类可以理解的，以便进一步分析。理想情况下，你应该能够利用历史数据构建负载特征，这样就能快速判断系统根本的约束是否发生了变化（例如，你终于修复了核心瓶颈却出现了新的瓶颈，或者其他地方退化了，导致它不再是核心瓶颈）。

特别地，我的 takeaways 是：正确的负载生成工具很可能从一个相对简单、人工识别关键指标的方法开始，然后逐步转向使用机器学习，以避免我们在系统应该在哪里变慢这件事上的隐性偏见。

地理分布式网络流量生成的统一负载生成器

《地理分布式网络流量生成的统一负载生成器》（2006）是一篇硕士论文，恰好对负载生成领域的学术思想和主题做了一个相当出色的综述。

这里的一个有趣想法是：

要设计一个在不同情况下都能灵活行动的精确人工负载生成器，我们不仅需要一个负载模型，还需要一种形式化方法来描述真实的负载。

我不完全同意我们需要一个形式化模型才能从负载测试中获得价值——毕竟我们只是想把计划外的可扩展性工作转化为计划内的工作，但我有着如此强烈的行业视角，以至于“甚至要去尝试创建一个形式化模型”这件事本身就让我觉得非常吸引人。

它还引入了一套更具体的词汇来讨论负载生成：

工作负载或负载 L=L (E, S, IF, T) 表示由环境 E 在时间间隔 T 内，通过定义良好的接口 IF 向服务系统 S 提供的请求总序列。

更有趣的是，它强调了 QoS、成本与配额 如何迫使我们重新定义负载测试的目标：

对能够提供数据、语音和视频等通信服务的电信网络的需求，推动了向用户交付可接受 QoS 水平的目标，其成功取决于有效拥塞控制方案的发展。

我觉得这一点非常有意思。随着你的系统开始包含更多系统的负载丢弃机制，将它们推出平衡状态会变得越来越困难，因为它们（通常）会通过降低 yield 来保护 harvest。因此，仅仅说你的系统在某个负载水平下应该或不应该失败是不够的，你还必须开始衡量它是否根据负载水平进行了适当的降级。

在 3.5 节中，它解释了（看似众所周知但我之前并不知道的）UniLog，也称为统一负载生成器。（它可能基于这篇论文，可惜被付费墙挡住了。）UniLog 有一个有趣的架构，包含 PLM、ELM、GAR、LT、ADAPT 和 EEM 这样令人望而生畏的组件名称。据我所知，它是一个用于运行和评估负载实验的极其通用的架构。从第一遍阅读来看，它感觉有点过度设计，但也许当一个人在负载生成这个深渊中待得更久后，它就会开始变得有道理了。

在 4.4 节中，它讨论了集中式与分布式负载生成，这感觉是构建此类系统时需要做出的核心设计决策之一。我的感觉是，你最终很可能需要采用分布式方法，哪怕只是为了避免被基于单 IP 速率限制的 QoS 完全限流。

论文的其余部分聚焦于一些案例研究等。总体而言，它是一篇令人惊讶的全面的相关研究入门读物。

负载测试结果的自动化分析

《负载测试结果的自动化分析》探讨了如何使用自动化来理解负载测试结果（同时使用负载测试的执行日志和测试期间的整体系统指标）。

它将分析负载测试结果的挑战总结为：文档过时、进程级 profiling 成本过高、负载测试通常发生在开发周期后期且时间紧迫，以及负载测试的输出可能大到令人难以招架。

我认为对我来说最有趣的 takeaways 是，非常明确地将性能数据的采集与其分析解耦。例如，你可以很早就开始记录性能数据（而且很可能你的指标工具，例如 Graphite，已经在采集这些数据了），然后在更晚的时候再投入更复杂的分析。其中特别关注在多次负载测试运行之间进行比较，这至少可以缩小性能“所在位置”在你的指标中的范围。

更多论文……

一些其他论文及简短总结：

将用户转化为测试者——这篇论文讨论了记录用户流量作为负载测试输入，以减少编写负载生成脚本所花费的时间。

基于自动反馈和控制的压力与负载测试——这篇论文探讨了尝试驱动并维持系统负载在目标阈值的系统。这是一个有趣的想法，因为它允许你持续对生产环境施加负载。唯一的 caveat 是，你必须首先确定想要用来影响负载的输入，因此你仍然需要对传入流量进行建模才能将其作为输入（或者记录并清洗真实流量），但一旦你有了模型，就可以在如何使用该模型上更加抽象（如果你的目标是制造负载，你不一定需要模拟真实的流量，你可以使用类似 n-armed bandit 的方法来“优化”你的负载，以产生系统所需的正确负载量）。（类似地，这篇论文尝试使用遗传算法来实现这一点。）

现有工具

负载测试工具出奇地少，虽然 Wikipedia 有一个简短列表。在那个列表中，我多年前确实用过 JMeter，而且我很喜欢这篇对 HP Loadrunner 工具的简短吐槽。

我简单看了一下 Gatling，它是一个用 Scala 写成的轻量级 DSL，可以很容易地由 Jenkins 等运行。这似乎是一个构建负载生成工具的有趣潜在起点。特别是将负载测试视为可以签入代码仓库的东西，这个理念感觉很正确，让你可以像对待其他任何东西一样迭代你的负载测试。阅读其他几篇关于 Gatling 的博客文章让我更强烈地感觉到，这可能是整体负载测试系统的一个有用组件（例如，允许多个实例针对不同端点运行等）。

还有其他我遗漏的工具吗？

根据 UniLoG 方法的 Web 工作负载生成

顾名思义，《根据 UniLoG 方法的 Web 工作负载生成》研究了如何将 UniLoG 方法适配到 Web 上。它也很好地总结了 UniLoG 的方法：

UniLoG 设计和阐述的基本原则是，从对抽象负载模型的形式化描述开始，然后使用一个接口相关的适配器，将抽象请求映射到真实接口上服务提供组件所能“理解”的具体请求。

它还很好地探讨了生成请求的各种方式，尽管最终还是回到了要么使用现有流量的日志，要么生成一个定义工作负载的模型。这里有一个有趣的混合方案，即使用实际使用量的分布作为生成负载的输入（而不是一对一地使用负载）。

尽管如此，很遗憾，我从这篇论文中并没有获得太多收获。
