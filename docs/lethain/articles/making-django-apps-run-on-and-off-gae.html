让 Django 应用在 GAE 上和非 GAE 环境下都能运行

2009-03-10 · 阅读原文

目前有一个新兴且不断发展的“家庭手工业”，专门致力于弥合 Google App Engine（GAE）上的 Django 与标准 Django 部署之间的差异。其中历史最久的项目是 Google App Engine Helper for Django，它主要帮助将现有的 Django 应用迁移到 GAE；而最近 django-gae2django 的知名度也在不断提高，它支持将项目往相反方向迁移（即从 GAE 迁移到普通 Django）。

这两个方案都不是即插即用的替代方案，都需要对代码进行一些特殊的调整或修改。事实上，考虑到 Bigtable 与传统关系型数据库在能力和设计上的巨大差异，我认为一个“一刀切”的即插即用解决方案可能永远不会出现。

尽管如此，我们仍然可以编写能在普通部署和 GAE 部署下都能良好工作的可插拔 Django 应用，并在必要时优雅地降级。这正是我在将 django-springsteen 移植到 GAE 时所采用的策略。

又一个抽象层

这种方法带来的痛苦在于，它需要引入又一层抽象。下面是我第一次尝试将 Springsteen 的缓存机制移植到 GAE 的代码。

# springsteen/utils.py
try:
    import google.appengine.api
    def cache_get(key):
        pass
    def cache_put(key, value, duration):
        pass
except ImportError:
    import django.core.cache
    def cache_get(key):
        return django.core.cache.cache.get(key)
    def cache_put(key, value, duration):
        django.core.cache.cache.set(key, value, duration)

在第一次尝试中，我愿意接受这种优雅降级的解决方案。随后在其他代码中，我像这样使用这些函数：

from springsteen.utils import cache_get, cache_put
cache_put("yada", "yadayada", 100)
ab = cache_get("yada")

在 GAE 上实际测试后，我很快意识到对 Springsteen 而言，优雅降级的方案还不够完善，于是我补全了之前占位的 cache_get 和 cache_put 函数。

# springsteen/utils.py
try:
    import google.appengine.api
    def cache_get(key):
        return google.appengine.api.memcache.get(key)
    def cache_put(key, value, duration):
        google.appengine.api.memcache.set(key, value, duration)
except ImportError:
    import django.core.cache
    def cache_get(key):
        return django.core.cache.cache.get(key)
    def cache_put(key, value, duration):
        django.core.cache.cache.set(key, value, duration)

接下来我做的适配就没有那么通用了，而是更加针对 Springsteen 的特性。Springsteen 可以选择记录所有查询以便后续分析，默认使用 Python 的 logging 模块来实现。

然而，虽然把查询记录到 queries.log 文件中后续解析和分析非常方便，但如果把查询记录到 GAE 的管理后台日志查看器中，后续几乎无法对这些数据进行有效分析。

因此，我决定让 GAE 版本将查询写入 Bigtable 数据结构中，后续可以通过查询该结构来进行分析并生成统计信息。

使用这种模式，我能够根据不同的部署场景以不同方式开启查询日志，也可以根据 settings.py 中 SPRINGSTEEN_LOG_QUERIES 的值完全禁用它。

上面这段代码的使用方式正如你所预期的那样：

from springsteen.utils import log_query
log_query("python")

稍加想象你就会明白，如何将这个概念扩展出去，为两个平台上的数据创建、编辑、查询和删除操作编写包装器。

这并不漂亮——也不免费——但也没有特别复杂。

成本与收益

这种方法最大的问题在于，它不允许开发者使用他们熟悉的功能，而是让每个应用都重新发明一个属于自己的最小轮子。

从另一方面来说，它让完全没有 Google App Engine 经验的开发者也能将应用部署到 GAE 以及普通环境，而无需对代码做任何修改。

此外，每个应用都能以最适合自身性能和功能需求的方式优雅降级或模拟功能。这使得我们可以比那些更雄心勃勃的 Django-GAE 和 GAE-Django 项目进行更加细粒度的优化。

我并不指望这种方法会流行起来，但对于某些可复用、兼容性差异较小的应用来说，它是一种相当合理的方案，能够减轻用户在部署方面的负担。
