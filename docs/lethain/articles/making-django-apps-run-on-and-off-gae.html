让 Django 应用在 GAE 和非 GAE 环境下都能运行

2009-03-10 · 阅读原文

目前有一个规模虽小但发展迅速的生态圈，致力于弥合 Google App Engine（GAE）上的 Django 与标准 Django 部署之间的差异。其中历史最久的是 Google App Engine Helper for Django，它主要帮助将现有的 Django 应用迁移到 GAE；最近 django-gae2django 的知名度也在不断提升，它则支持将项目从 GAE 迁移回普通 Django 环境。

这两个方案都不是即插即用的替代方案，都需要对代码进行一些特殊的调整或修改。考虑到 Bigtable 与传统关系型数据库在能力和设计上的根本差异，我认为真正“一刀切”的即插即用解决方案几乎不可能存在。

尽管如此，我们仍然可以编写兼容两种部署环境的即插即用 Django 应用，并在必要时优雅降级。这正是我在将 django-springsteen 迁移到 GAE 时采用的策略。

接下来的适配工作没那么通用，而是更针对 Springsteen 的具体需求。Springsteen 可以选择性地记录所有查询以供后续分析，默认情况下它使用 Python 的 logging 模块来实现。

虽然将查询记录到 queries.log 文件便于后续解析和分析，但如果把查询记录到 GAE 的管理后台日志查看器中，后续的数据分析几乎无法进行。

于是我决定让 GAE 版本将查询写入 Bigtable 数据结构中，后续可以对其进行查询来完成分析并生成统计信息。

成本与收益

这种方法最大的问题是，它不允许开发者直接使用他们熟悉的功能，而是让每个应用都不得不重新发明一个属于自己的微型轮子。

另一方面，它让完全没有 Google App Engine 经验的开发者也能将应用部署到 GAE 和普通环境，而无需对他们的代码做任何修改。

此外，每个应用都能以最适合自身性能和功能需求的方式优雅降级或模拟功能。这使得我们可以比那些更雄心勃勃的 Django-GAE 和 GAE-Django 项目进行更加细粒度的优化。

我并不指望这种方法会广泛流行，但对于某些可复用、兼容性差异较小的应用来说，它是一种相当合理的方式，能够减轻用户在部署上的负担。
