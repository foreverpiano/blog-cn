让 Django 应用同时能在 GAE 上和独立环境运行

2009-03-10 · 阅读原文

目前有一个新兴且不断发展的领域，专门致力于弥合 Google App Engine（GAE）上的 Django 与标准 Django 部署之间的差距。其中历史最久的是 Google App Engine Helper for Django，它主要帮助将现有的 Django 应用迁移到 GAE；而最近 django-gae2django 的知名度逐渐提高，它支持将项目从 GAE 迁移回普通 Django 环境。

不过这两者都不是开箱即用的解决方案，都需要对代码进行一些特殊调整或修改。考虑到 Bigtable 与传统关系型数据库在能力和设计上的差异，我认为真正意义上的一次性、完全兼容的解决方案可能永远不会出现。

尽管如此，我们仍然可以编写同时兼容普通部署和 GAE 部署的可插拔 Django 应用，并在必要时优雅降级。这正是我将 django-springsteen 移植到 GAE 时所采用的策略。

又一层抽象

这种方法带来的代价是需要再引入一层抽象。下面是我第一次尝试将 Springsteen 的缓存机制移植到 GAE 的代码：

# springsteen/utils.py
try:
    import google.appengine.api
    def cache_get(key):
        pass
    def cache_put(key, value, duration):
        pass
except ImportError:
    import django.core.cache
    def cache_get(key):
        return django.core.cache.cache.get(key)
    def cache_put(key, value, duration):
        django.core.cache.cache.set(key, value, duration)

在第一次尝试中，我愿意接受优雅降级的方案。随后在其他代码中，我像这样使用这些函数：

from springsteen.utils import cache_get, cache_put
cache_put("yada", "yadayada", 100)
ab = cache_get("yada")

在 GAE 上实际测试后，我很快意识到对于 Springsteen 来说，优雅降级的方案还不够理想，于是我补全了之前留空的 cache_get 和 cache_put 函数。

# springsteen/utils.py
try:
    import google.appengine.api
    def cache_get(key):
        return google.appengine.api.memcache.get(key)
    def cache_put(key, value, duration):
        google.appengine.api.memcache.set(key, value, duration)
except ImportError:
    import django.core.cache
    def cache_get(key):
        return django.core.cache.cache.get(key)
    def cache_put(key, value, duration):
        django.core.cache.cache.set(key, value, duration)

接下来的调整则没那么通用，而是更针对 Springsteen 自身特点。Springsteen 可以选择记录所有查询以便后续分析，默认情况下它使用 Python 的 logging 模块来实现。

虽然将查询记录到 queries.log 文件便于后续解析和分析，但如果把查询记录到 GAE 的管理后台日志查看器中，后续的数据分析几乎就无法进行了。

因此，我决定让 GAE 版本将查询写入 Bigtable 数据结构，后续可以通过查询这个结构来进行分析并生成统计信息。

我使用上述代码的变体实现了这个功能。

    <span class="k">class</span> <span class="nc">QueryLog</span><span class="p">(</span><span class="n">db</span><span class="o">.</span><span class="n">Model</span><span class="p">):</span>
        <span class="n">text</span> <span class="o">=</span> <span class="n">db</span><span class="o">.</span><span class="n">StringProperty</span><span class="p">()</span>

    <span class="k">def</span> <span class="nf">log_query</span><span class="p">(</span><span class="n">msg</span><span class="p">):</span>
        <span class="n">logged</span> <span class="o">=</span> <span class="n">QueryLog</span><span class="p">()</span>
        <span class="n">logged</span><span class="o">.</span><span class="n">text</span> <span class="o">=</span> <span class="n">msg</span><span class="o">.</span><span class="n">lower</span><span class="p">()</span>
        <span class="n">logged</span><span class="o">.</span><span class="n">put</span><span class="p">()</span>
<span class="k">else</span><span class="p">:</span>
    <span class="k">def</span> <span class="nf">log_query</span><span class="p">(</span><span class="n">msg</span><span class="p">):</span>
        <span class="k">pass</span>

通过这个模式，我能够根据不同的部署场景以不同方式启用查询日志，也可以根据 settings.py 中 SPRINGSTEEN_LOG_QUERIES 的值完全禁用它。

上述代码的使用方式和大家预期的一样：

from springsteen.utils import log_query
log_query("python")

稍加想象你就能看出，如何将这个思路扩展，为两个平台上的数据创建、编辑、查询和删除操作编写封装层。

它算不上优雅——也不免费——但也不算特别复杂。

成本与收益

这种方法最大的问题在于，它不允许开发者直接使用自己熟悉的功能，而是每个应用都要重新造一个最小化的轮子。

另一方面，它让完全没有 Google App Engine 经验的开发者也能将应用部署到 GAE 以及普通环境，而无需对代码做任何修改。

此外，每个应用都能以最适合自身性能和功能需求的方式进行优雅降级或模拟功能。这使得我们可以比那些更宏大的 Django-GAE 和 GAE-Django 项目进行更加细粒度的优化。

我并不指望这种方法会广泛流行，但对于某些可重用、兼容性问题相对较小的应用来说，它是一种相当合理的方案，能够减轻用户在部署上的负担。
