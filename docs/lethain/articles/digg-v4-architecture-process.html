Digg v4 的架构与开发流程

2012-08-19 · 阅读原文

一个月前，随着 Digg v1 的第二次上线，历史重新开始，许多记忆也逐渐模糊——因为 Digg 团队大部分成员在四个月前就已加入 SocialCode。因此，现在似乎是个好时机，来描述一下从 2010 年 5 月到 2012 年 5 月间支撑 Digg.com 运行和开发的系统与团队架构。

这里不会有争议，甚至没有太多故事性，只是一份关于我们当时的工作方式以及所构建架构的客观描述。

团队结构、规模与组织方式

我们需要先提供一些背景，介绍公司的规模、团队的组织形式，以及这一结构如何受到一系列裁员和后续招聘的影响。

为了聚焦主题，我不会涉及销售、财务、广告管理、设计、人力资源、业务开发等团队；他们都是公司的重要组成部分，但不是这个故事的核心。

我们的故事始于一个相当传统的公司布局，设有明确的产品、工程和运维领导团队。产品团队规模较小，只有 4 人；运维团队约有 8 名工程师，QA 团队约 6 名工程师，开发团队则大约有 20 名开发者。

开发团队本身按四个横向团队（前端、API、平台和基础设施）和两个纵向团队（广告、分析）进行组织。产品团队则采用垂直所有权模式，负责特定功能模块，并在各个横向开发团队之间进行协调。

在经历多次裁员和人员离职之后，组织结构最终回归到更简单的形态。

在过去的一年里，我们的运维团队有 3 人，工程团队有 7 人，广告工程团队有 4 人。

代码审查与持续部署

一套精简的核心开发实践让我们能够先扩展到 40 名工程师，随后又从 40 人缩减到 14 人仍能有效运作。让我们先从代码的合并、审查和部署流程开始，来看看我们的开发实践。

对上图稍作展开说明：

  1. We used Git for source control, and Gerrit for code review. Every piece of code had be reviewed and approved by a peer, as well as pass all unittests.
  2. Each time a patchset was submitted to Gerrit for code review, Jenkins would automatically runs its unittests, and when the tests finished would update Gerrit with the success or failure of the tests.This meant that code reviewers didn’t have to waste their time reviewing failing patches. It also meant that we never merged unittest broken code into our Git repositories.
  3. Once a Gerrit patchset passed its tests and was approved by a code reviewer, then it would be merged into the Git master branch, and would be automatically deployed via Puppet to our alpha environment. The final step of deployment to the alpha environment (and after successfully running integration tests against the alpha environment), the new patchset would also be merged into the production branch in Git.
  4. We deployed to our production environment by manually building a Jenkins job, which would then work with Puppet to deploy the updated code.We started out with continuous deployment to production, but after a few disasterous late night deployments we decided that having a human in the loop before going to production was going to work better for us.If we had stuck with continuous deployment, we would have eventually improved our tests to the extent that very few bad changes got through, but that didn’t seem like the right investment of time for us at that point.

在我看来，这套审查、测试和部署代码的系统是 Digg 开发工作中最重要、最成功的部分。它既有足够的结构来保证 40 人团队的代码标准和一致性，后期又足够轻量，不会对规模小得多的团队造成负担。

自然演化的流程与实践

我们还采用了一些其他实践，但其中大部分都是在实践中自然形成的，而非刻意决定的结果。

  1. We started out with extremely high unittest coverage, but as the team shrank, we ended up writing very few new tests. This wasn’t an explicit policy, but stemmed from the belief that unittests didn’t help prevent the types of breakages we experienced most: systemic failures involving multiple components under production load, and frontend rendering issues.Unlike our unittests which continued providing value years later, our Selenium tests rotted almost immediately once we stopped actively maintaining them, and the Selenium tests departed soon after the QA team.
  2. We used Thrift for defining interfaces between our frontend and platform teams, which generally made communication and coordination between the teams straightforward. We did end up with some poorly designed interfaces, which created much confusion, but in general using Thrift for defining the types and interfaces between teams was a great communication aid.
  3. We rarely changed behavior of existing Thrift interfaces, rather we would push out a new interface with the desired functionality, update the clients to use that functionality, and then remove the old interface. This was a somewhat awkward process, but since we deployed frontend and backend code independently (and doing a full rollout of all frontend or backend servers took a few minutes), it was a safe, sane way to ensure we didn’t break ourselves.
  4. We launched all frontend changes with a mechanism to roll them out to a subset of users, or to disable them if they ran into problems. This allowed us to separate deployment from rollout, which made deploying code more peaceful, and gave us the ability to time rolling out features precisely.We had initially intended to use this mechanism for A/B testing new features, but it ended up being most valuable for managing releases and getting feedback from small trusted groups of users.We also dark launched backend features which we expected to have a performance or load impact, to avoid bringing down the world while we stared helplessly at a Jenkins progress bar.

讲完我们如何开发，接下来看看我们所开发的系统。

康威定律如是说，或“我们的架构”

如果你看看我们在设计 v4 架构时的组织结构，再看看最终开发出的架构，基本上就是康威定律（Conway’s Law）的生动写照。

我们有 API 团队和 API Server，前端团队和前端 Server，平台团队和后端 Server，广告团队和广告 Server，由基础设施团队管理的众多数据存储，以及为分析团队准备的 Hadoop 集群。

尽管如此，对于我们这种规模的团队来说，这仍然是一种非常标准的架构：前端团队使用无状态的 PHP/HTML/JS 开发，后端服务器负责状态和存储管理，并通过消息队列处理长时间运行和非事务性的任务。

最不寻常的部分大概是后端服务器——我们采用了基于 gevent 的 Thrift Server。不论好坏——我个人认为完全是坏处——当时并没有一个标准的高性能 Python Thrift Server，因此我们花了大量时间研究 gevent 并构建 gevent 安全的客户端连接池。如果再让我选择，我可能不会再在 Python 服务端使用 Thrift，只是为了避免维护这样一个自定义的 Server。

同时拥有 PHP 和 Python 服务端一直让我有些在意，觉得“如果重新规划肯定不会这么做”，但实际运行中问题并不大：在最后一年左右的时间里，几乎整个团队都能自如地在两种语言间切换，并没有太多抱怨。

同样，作为一个有完美主义倾向的系统设计者，同时使用 Tornado、Apache+mod_wsgi+Pylons 和 Python gevent Server 也让我有些不安，但实际中并没有造成太大问题（如果我们没有 Jenkins 和 Puppet 部署系统，我相信技术的过度扩散会带来更大的痛苦）。

总结思考

总的来说，我认为我们的流程和架构相当合理，也很好地适应了我们的需求。如果今天重新开始，我们肯定会采用不同的方法；或者如果团队规模没有大幅缩减，或者我们不需要同时背负遗留系统、API 和契约等技术债务，这些都是很有意思的话题，值得以后再展开讨论。

另外，还有一篇关于 Digg 数据库和技术扩散的文章值得写（涉及 Cassandra、MySQL、Redis、Memcache、HDFS、Hive、Hadoop、Tornado、Thrift servers、PHP、Python、Pylons、Gevent 等），我希望能把它整理出来。

或者深入思考我们的组织结构如何影响了我们的工作方式（如果你对这个话题感兴趣，一定要去看 Adam Pisoni 关于适应性组织的演讲）。

一切都需等待合适的时机。
