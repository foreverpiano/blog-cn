Digg v4 的架构与开发流程

2012-08-19 · 阅读原文

一个月前，随着 Digg v1 的第二次上线，历史重新开始，许多记忆也逐渐模糊——因为 Digg 团队大部分成员在四个月前就已加入 SocialCode。因此，现在似乎是个好时机，来描述一下从 2010 年 5 月到 2012 年 5 月间支撑 Digg.com 运行和开发的系统与团队架构。

这里不会有争议，甚至没有太多故事性，只是一份关于我们当时的工作方式以及所构建架构的客观描述。

团队结构、规模与组织方式

我们需要先提供一些背景，介绍公司的规模、团队的组织形式，以及这一结构如何受到一系列裁员和后续招聘的影响。

为了聚焦主题，我不会涉及销售、财务、广告管理、设计、人力资源、业务开发等团队；他们都是公司的重要组成部分，但不是这个故事的核心。

我们的故事始于一个相当传统的公司布局，设有明确的产品、工程和运维领导团队。产品团队规模较小，只有 4 人；运维团队约有 8 名工程师，QA 团队约 6 名工程师，开发团队则大约有 20 名开发者。

开发团队本身按四个横向团队（前端、API、平台和基础设施）和两个纵向团队（广告、分析）进行组织。产品团队则采用垂直所有权模式，负责特定功能模块，并在各个横向开发团队之间进行协调。

在经历多次裁员和人员离职之后，组织结构最终回归到更简单的形态。

在过去的一年里，我们的运维团队有 3 人，工程团队有 7 人，广告工程团队有 4 人。

代码审查与持续部署

一套精简的核心开发实践让我们能够先扩展到 40 名工程师，随后又从 40 人缩减到 14 人仍能有效运作。让我们先从代码的合并、审查和部署流程开始，来看看我们的开发实践。

我们使用 Git 进行源代码管理，使用 Gerrit 进行代码审查。每一段代码都必须经过同行审查和批准，并通过所有单元测试。每次提交 patchset 到 Gerrit 进行审查时，Jenkins 会自动运行单元测试，测试完成后会将结果更新到 Gerrit 上。这意味着代码审查者不必浪费时间去审查失败的补丁，也确保我们从未将单元测试失败的代码合并到 Git 仓库中。一旦某个 Gerrit patchset 通过测试并获得审查者批准，它就会被合并到 Git 的 master 分支，并通过 Puppet 自动部署到 alpha 环境。在成功完成针对 alpha 环境的集成测试后，最后一步是将该 patchset 合并到 Git 的 production 分支。我们通过手动触发 Jenkins 任务来部署到生产环境，该任务会与 Puppet 协作完成代码更新。我们最初采用的是持续部署到生产环境，但在经历了几次灾难性的深夜部署事故后，我们决定在上线生产前加入人工把关会更适合我们。如果当时坚持持续部署，我们最终可能会不断完善测试以减少错误上线，但在那时，这似乎不是最值得投入时间的方向。

在我看来，这套审查、测试和部署代码的系统是 Digg 开发工作中最重要、最成功的部分。它既有足够的结构来保证 40 人团队的代码标准和一致性，后期又足够轻量，不会对规模小得多的团队造成负担。

自然演化的流程与实践

我们还采用了一些其他实践，但其中大部分都是在实践中自然形成的，而非刻意决定的结果。

我们最初拥有极高的单元测试覆盖率，但随着团队缩减，我们后来几乎不再编写新的测试。这并非明确的政策，而是因为我们认为单元测试无法有效防止我们最常遇到的两类问题：涉及多个组件在生产负载下的系统性故障，以及前端渲染问题。与那些多年后仍能提供价值的单元测试不同，我们的 Selenium 测试一旦停止积极维护，几乎立刻就腐化了，并在 QA 团队解散后不久便被淘汰。我们使用 Thrift 来定义前端和平台团队之间的接口，这通常让团队间的沟通和协作变得简单直接。虽然最终出现了一些设计糟糕的接口，造成了不少困惑，但总体而言，用 Thrift 来定义团队间的类型和接口是一种极好的沟通辅助手段。我们很少修改现有 Thrift 接口的行为，而是推出新的接口来实现所需功能，更新客户端使用新接口，然后再移除旧接口。这个过程略显繁琐，但由于我们可以独立部署前端和后端代码（完成所有前端或后端服务器的完整 rollout 只需几分钟），这是一种安全、合理的方式，避免把自己搞崩。我们上线所有前端改动时，都会带上一个机制，可以将其逐步 rollout 给部分用户，或在出现问题时快速关闭。这让我们得以将部署和 rollout 分离，既让部署过程更加平稳，也能精准控制功能上线时机。我们原本打算用这个机制来进行新功能的 A/B 测试，但后来发现它在管理发布和从一小批信任用户那里获取反馈方面价值更高。我们还会对预期会带来性能或负载影响的后端功能进行暗中上线（dark launch），以避免在盯着 Jenkins 进度条无助等待时把整个系统拖垮。

讲完我们如何开发，接下来看看我们所开发的系统。

康威定律如是说，或“我们的架构”

如果你看看我们在设计 v4 架构时的组织结构，再看看最终开发出的架构，基本上就是康威定律（Conway’s Law）的生动写照。

我们有 API 团队和 API Server，前端团队和前端 Server，平台团队和后端 Server，广告团队和广告 Server，由基础设施团队管理的众多数据存储，以及为分析团队准备的 Hadoop 集群。

尽管如此，对于我们这种规模的团队来说，这仍然是一种非常标准的架构：前端团队使用无状态的 PHP/HTML/JS 开发，后端服务器负责状态和存储管理，并通过消息队列处理长时间运行和非事务性的任务。

最不寻常的部分大概是后端服务器——我们采用了基于 gevent 的 Thrift Server。不论好坏——我个人认为完全是坏处——当时并没有一个标准的高性能 Python Thrift Server，因此我们花了大量时间研究 gevent 并构建 gevent 安全的客户端连接池。如果再让我选择，我可能不会再在 Python 服务端使用 Thrift，只是为了避免维护这样一个自定义的 Server。

同时拥有 PHP 和 Python 服务端一直让我有些在意，觉得“如果重新规划肯定不会这么做”，但实际运行中问题并不大：在最后一年左右的时间里，几乎整个团队都能自如地在两种语言间切换，并没有太多抱怨。

同样，作为一个有完美主义倾向的系统设计者，同时使用 Tornado、Apache+mod_wsgi+Pylons 和 Python gevent Server 也让我有些不安，但实际中并没有造成太大问题（如果我们没有 Jenkins 和 Puppet 部署系统，我相信技术的过度扩散会带来更大的痛苦）。

总结思考

总的来说，我认为我们的流程和架构相当合理，也很好地适应了我们的需求。如果今天重新开始，我们肯定会采用不同的方法；或者如果团队规模没有大幅缩减，或者我们不需要同时背负遗留系统、API 和契约等技术债务，这些都是很有意思的话题，值得以后再展开讨论。

另外，还有一篇关于 Digg 数据库和技术扩散的文章值得写（涉及 Cassandra、MySQL、Redis、Memcache、HDFS、Hive、Hadoop、Tornado、Thrift servers、PHP、Python、Pylons、Gevent 等），我希望能把它整理出来。

或者深入思考我们的组织结构如何影响了我们的工作方式（如果你对这个话题感兴趣，一定要去看 Adam Pisoni 关于适应性组织的演讲）。

一切都需等待合适的时机。
