正如我常遇到的那样，灵感来源于我当前的工作。我们正在进行年度策略更新，讨论如何处理，而将建模融入策略制定过程，已成为一个出奇有效的头脑风暴工具。基础设施：介于成本中心与自我陶醉之间

问题陈述

我们希望撰写一份策略，描述我们处理可靠性的方法。这份需要令人信服地回答四个问题：写作策略与愿景

当前的现实状态如何？这是收集数据和背景信息，以确保我们的方法能应对真实的需要和挑战，同时也包括我们的目标。我们将采用哪些指导原则来应对当前状态？这些指导原则会引导我们采取哪些行动来应对当前状态？考虑到我们的，我们实际会采取哪些行动？基础设施规划：用户、基线与时间框架

即使你已经在这个问题上工作多年，并且在当前公司工作了很长时间，要简洁地回答这些问题也并不容易。如果你要支持的产品和基础设施正在快速扩展，情况也不会变得更容易。

这正是系统建模发挥作用的地方。

以下系统模型将使用我去年编写的 systems 库来定义。希望其中的语法易于阅读，且图表包含了大部分细节。唯一需要说明的是，流（即 @ 后面的部分）要么是速率，要么是转换。

速率将输入存量转移到输出存量，用整数或公式表示。转换则将输入存量乘以一个转换因子，把结果加到输出存量中，并清空输入存量。转换用小数表示。

创建关于事故的数据

构建可靠性模型的一个起点，可以是从事故的角度出发。我们的软件中时刻都在发生变化，其中一些是我们可控的，比如部署新版本，而许多是我们无法控制的，比如硬件故障、发现新的漏洞等等。

大多数变更都能顺利进行，但有些则不然。当变更出现问题时，有时会演变为事故。每次事故都是我们未能达到可靠性目标的事件，而一旦我们重新达到可靠性目标，就意味着我们缓解了该事故。

从一个非常简单的模型开始，假设变更为事故的速率是固定的，缓解事故的速率也是固定的：

[Changes] > Incidents @ 2
Incidents > Mitigated @ 1

在这个模型中，我们会慢慢积累越来越多的事故，开放事故的数量将一直高于已缓解事故的累计数量。这太可怕了。

这是一个非常基础的模型，但我认为即使从中也能学到一些有用的东西。例如：

要理解我们的可靠性，我们需要检测和衡量很多东西。我们需要衡量变更、事故和缓解的数量。如果我们能精确地衡量这些，就能找出系统中将变更转化为事故、以及将事故转化为已缓解事故的真实速率。我们没有任何（已认知的）从事故到变更的反馈循环，如果没有这种循环，我们会预期未缓解的事故数量会随着时间推移而增长。缓解事故的速率似乎是整个系统中最重要的流，特别是当我们不想降低变更速率的时候——因为大多数业务都依赖于提高变更速率。

至此，这个简单的模型已经告诉我们，策略文档要发挥作用需要包含哪些内容。特别是，它会凸显为什么事故管理程序是管理可靠性的前提：这是获取数据、并基于事实讨论什么有效、什么无效的唯一途径。

如果你还没有建立类似的东西，我的建议是停止阅读，花接下来一年的时间去建立并运行它，等有了数据后再回来。虽然如何建立事故管理程序可能超出了本文能涵盖的范围，但 Tammy Butow 的文章是一个极好的入门读物。

开发者在改变事物

前一个模型的一个弱点是，事故的数量可能不是一个固定速率，而是取决于变更的数量。而变更的数量很可能取决于开发者的数量，在一个成长型公司中，这个数字通常是不断增加的。

[Hires] > Developers   @ 1
[Plans] > Changes      @ Developers * 2
Changes > Incidents    @ 0.2
Incidents > Mitigated @ 1

这就是缺乏从未缓解事故到变更的反馈循环变得非常可怕的地方，因为我们可以看到事故数量随时间快速增长，并超过变更速率。

然而，如果你曾在发生过多起事故的公司工作过，你就会知道实际情况并非完全如此。随着事故数量上升，产品变更的速率会下降，因为大家会把注意力转移到缓解工作上。

这就是我们一直在寻找的反馈循环。

[Hires] > Developers   @ 1
[Plans] > Changes      @ (Developers * 2) - Incidents
Changes > Incidents    @ 0.2
Incidents > Mitigated @ 1

如果我们将这种动态建模为从计划到变更的流会受到开放事故数量的抑制，我们会发现一个令人惊讶的结果。

如果我们持续招聘更多开发者，但不提升缓解事故的能力，那么我们会很快达到一个临界点：继续招聘不再能让我们做出更多变更。

这个结果引出了我们可靠性策略的一个重要指导原则：只有在同等提升缓解事故能力的前提下，招聘才能提高生产力。

题外话：反向反馈循环

总有一个问题是模型要做到多详细。值得注意的是，由缓解引发的新变更本身也有缺陷率。因此，事故因有缺陷的缓解尝试而引发新事故的情况并不少见，这就形成了一个与我们刚刚建模的反馈循环对抗的反向反馈循环。

我选择不将这一部分纳入模型，但对你的具体情况而言，这一点可能非常重要。决定对什么建模、对什么忽略，取决于基于数据的判断。两家不同公司的有效可靠性模型，会包含和省略不同的方面。

提升缓解带宽

既然我们已经确定事故是我们可靠性和生产力的共同瓶颈，那就围绕减少事故来扩展我们的模型。虽然成功的缓解能解决一个开放事故，但通常对防止未来事故作用不大。而补救措施能消除某类潜在事故，我们需要对缓解和补救两者的能力进行建模，才能理解减少开放事故的选择空间。

许多公司采用的一种策略是引入 SRE 角色，专注于缓解事故。假设我们每招聘五名工程师就配一名 SRE，而每名 SRE 可以管理两个事故。

[Hires] > Developers @ 5
[Hires] > SREs @ 1
[Plans] > Changes @ (Developers-Incidents) * 2
Changes > Incidents @ 0.2
Incidents > Mitigated @ SREs * 2

按 1:5 的比例招聘 SRE 相对较高，但看起来这应该能真正解决问题！

有趣的是，它确实解决了一半的问题。我们避免了之前变更速率的平台期，随着招聘更多开发者，我们能继续做出更多变更，因此生产力重新上升。不幸的是，开放事故的数量仍在增加，只是增速大幅放缓。单纯招聘人员来缓解事故，似乎不足以应对我们的挑战。

接下来，我们建模进行补救工作以降低缺陷率（即变更导致事故的速率）。这里我们假设每轮进行一次补救，并随着补救次数增加而降低缺陷率。

[Hires] > Developers @ 5
[Hires] > SREs @ 1
[Plans] > Changes @ (Developers-Incidents) * 2
Changes > Incidents @ Conversion(1 / (1 + Remediated))
Incidents > Mitigated @ SREs * 2
Mitigated > Remediated @ 1

突然间，我们重回正轨，即使持续做出越来越多变更，也能将事故数量控制在一定范围内。

既然我们已经能通过增加补救获得理想结果，我好奇是否可以完全移除模型中的 SRE 部分，将缓解速率固定为每轮一次，看是否还能达到相同结果。

[Hires] > Developers @ 5
[Plans] > Changes @ (Developers-Incidents) * 2
Changes > Incidents @ Conversion(1 / (1 + Remediated))
Incidents > Mitigated @ 1
Mitigated > Remediated @ 1

结果并不完全奏效，但有趣的是，即使是非常小的固定缓解和补救数量，也能让我们从增加招聘中获益，我觉得这个结果令人惊讶。

如果我们愿意做一个小的调整，比如假设每增加一百名工程师就能让我们多缓解一个事故——考虑到模型中他们在事故期间无法进行变更，这似乎是合理的——那么这个很小的变化就能解决我们的可靠性挑战。

[Hires] > Developers @ 5
[Plans] > Changes @ (Developers-Incidents) * 2
Changes > Incidents @ Conversion(1 / (1 + Remediated))
Incidents > Mitigated @ Rate(1 + (Developers / 100))
Mitigated > Remediated @ 1

这使得我们能够持续改进，并将事故数量保持在固定水平。

在我看来，这是一个非常有力的结果，它意味着只要你能适度扩展缓解能力，在稳态下，对补救工作进行很小的固定投入，就能支撑一个既可靠又高效的环境。

思考从中得出的指导原则，对我来说最突出的两点是：确保我们始终投入一部分无法被挪用的资源用于补救工作；固定规模的缓解模型是行不通的。我们不能简单地招聘一个 8 人的 SRE 团队来处理所有缓解，并将其视为问题的解决。相反，如果我们设计一个与整体工程团队保持固定比例（比如 1:20）的 SRE 组织，且专门专注于缓解工作，就能达成目标。

如果他们同时专注于缓解和补救，效果会更好。但有趣的是，在模型中，最重要的是提升缓解带宽，而不是增加补救数量。如果我们保持缓解带宽不变而大幅增加补救（这听起来更有效），会得到一个有些反直觉的结果。

[Hires] > Developers @ 5
[Plans] > Changes @ (Developers-Incidents) * 2
Changes > Incidents @ Conversion(1 / (1 + Remediated))
Incidents > Mitigated @ 1
Mitigated > Remediated @ Rate(1 + (Developers / 100))

这实际上并没有达成我们的可靠性目标。

这是因为每次补救能预防许多未来的事故，这使得它们在数量较少时杠杆效应很高，但在数量很大时杠杆效应会下降。相反，缓解的杠杆效应不大，但在任何规模下都是必要的。

潜在事故

系统思考的核心观察之一是，有效的解决方案最初往往不起作用，因为它们正在排空一个巨大的初始存量。这在可靠性工作中经常发生：人们开始关注可靠性，着手记录事故，结果一个季度后发现事故反而更多了。

这种令人抓狂的经历，往往是我所说的“潜在事故”导致的结果。这些是等待发生的问题，由之前的变更引入，但尚未触发必要的边界情况成为真正的事故。启动可靠性项目的人通常拥有一个庞大而不可见的潜在事故存量，排空这个存量的过程常常给人一种“有效的可靠性项目正在失败”的错觉。

[Hires] > Developers(10) @ 5
[Plans] > Changes @ (Developers-Incidents) * 2
Changes > Latent(1000) @ Conversion(1 / (1 + Remediated))
Latent > Incidents @ 10
Incidents > Mitigated @ Rate(1 + (Developers / 100))
Mitigated > Remediated @ 1

具体来说，如果我们建模一个包含一千个潜在变更的大存量，那么初期数据显示我们的可靠性在变差，只有当这个存量被排空之后，我们才能稳定可靠性和生产力。

考虑到这一点，我们的指导原则中应该包含减少或至少衡量环境中潜在事故的措施，否则我们会对稳定性做出不准确的评估。

模型还可以继续扩展

这仅仅是用演化可靠性模型来制定专注、有效策略的开端。你可以想象继续扩展这个模型的几种方式包括：

事故检测时间如何影响缓解时间？失败的缓解尝试如何制造更多事故或降低缓解速率？培训工程师如何影响缺陷率？

这并不只是扩展模型的问题，还在于利用模型根据什么真正有帮助来排列行动优先级。我们可以抽象地讨论更多补救如何降低未来变更的缺陷率，但现实中很可能存在某一项特定的补救，能将你未来的缺陷率降低 90%，而要找出它，你必须回顾那些最频繁发生的事故的根本原因。

建模的微妙力量在于，它能以很低的成本让我们想象多种未来，并为哪些最有可能达成目标提供一些温和的指引。下次当你面对一个特别困难的问题时，试着演化一个简单的模型，将其作为引导注意力、评估选项的工具。

它们在头脑风暴中也非常有用，特别是能帮助你在选择方法之前，明确哪些信息是重要的。
