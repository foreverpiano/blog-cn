基础设施：介于成本中心与自我陶醉之间

2017-03-05 · 阅读原文

最近我面试一位工程经理候选人，问她为什么考虑离开现在的工作，她说了一件让我深有同感的事：她的基础设施工程团队还有大量工作要做，却没有人力可用。

这就是基础设施作为成本中心的写照。

另一方面，在里，我也见过基础设施团队对自身优先级感到困惑，同时组建多个目标重叠的竞争性团队。更糟糕的是，他们会为同一个问题配置相互竞争的解决方案，却完全不投入人力去做最紧急的工作。在这种情况下，关键的生产系统持续崩溃，而周围却是人员充足、目标模糊的“炫目”项目。超级增长时代的生产力

这就是基础设施的自我陶醉。

尽管这两种极端情况的危害都显而易见，但要找到一个务实的思考框架来优先级排序基础设施工作，依然充满挑战。这个挑战如此之大，以至于这些年来我逐渐整理出一套思考辅助工具，帮助自己对 incoming 请求进行优先级排序，并决定应该主动启动哪些项目。

它的用法是：思考你当前提供的能力、收到的功能请求以及潜在的新能力，对每一项都从以下六个维度寻找改进机会。这些维度按大致优先顺序呈现，但你的优先级当然不一定和我完全一样。

基础设施为公司和客户提供以下六个主要价值：

安全性不止是“把东西锁起来”，而是要优化流程，让同样的任务能在相同工作量下完成得更加安全。（如果你在寻找灵感，BeyondCorp 和 Security Keys 是很棒的读物！）可靠性不止是 uptime、harvest 或 yield，还包括强化你的接口，并确保 oncall 负担足够低，让告警能被真正处理而不是被忽视。易用性是让你的软件更容易被正确使用。如果开通一个新服务需要二十步，你能不能把它减少到十二步？如果创建一个 S3 bucket 需要审批，你能否至少自动预批几种常见情况？如果人们总是误解你的文档或不知道如何调试你的系统，你怎样才能让它更直观？如果工程师必须念一段咒语才能安全部署，你能否加上安全防护，让正确做法比错误做法更容易？杠杆效应是通过让你的原语和抽象更加强大（有人认为是对面向服务计算的改进），或者提供全新的能力（例如提供任务或批处理系统），来提升团队内外工程师的生产力。成本是指以更低的价格提供你的服务。这既可以是降低维护开销以便投入更多时间到功能开发上，也可以是更好地选择合适的 AWS 或 GCP 实例。在 Stripe，我们把成本管理当作一项基础设施特性——由基础设施工程团队主导，而不是一项财务举措——看到 Aditya、Cory 和 Davin 把这件事变成一项赋能特性，真的很令人振奋。（相关阅读是一篇令人困惑但有趣的文章，讨论。）延迟既包括减少到达你服务器的时间（通过 POP、active-active 多地域/数据中心拓扑，或建立连接池），也包括减少在你系统内部花费的时间（通过更好的负载均衡策略、请求追踪来发现延迟热点、优化数据库查询）。无服务器架构：把关机制与利润空间QoS、成本与配额

这当然不是一个完整的框架，但我在规划会议中发现它非常有用。特别是，它能帮助我避免基础设施工程团队常犯的几个错误：

把安全责任推给一个规模小得多的安全团队，而自己却在构建大多数需要被保护的平台。认为基础设施的易用性不重要，因为用户是工程师。这是不对的：即使是工程师也受注意力分散、打字错误和时间限制的影响。更糟糕的是，内部用户因为易用性问题而放弃一个平台的频率，远高于因为真正缺失功能而放弃（你有多少次被告知在 Y 平台上“其实可以”做 X 任务，然后听到一个复杂的 workaround？），因此在这方面投入不足，往往会造成巨大——而且在我看来常常是错误的——压力去构建新的平台。优先选择那些看似炫目（通常也很复杂）的项目，只是碰巧解决了一个问题（方案在寻找问题），而不是采取最直接的路径去解决眼前的问题。接受当前现状，认为“已经够好了”，满足于一个还行的系统，而不再继续推动它变得卓越。把成本意识委托给另一个不了解你系统实际工作方式的组织，迫使对方在缺乏足够上下文的情况下试图推动成本降低。（看来常见错误还真不少。）

通过在规划时系统性地思考这六个特性，我发现自己更不容易掉进那些诱人的思维陷阱。

过去大约六个月里，我一直在使用这个框架的粗略版本，并且相当满意。不过直到写这篇文章时，我才真正厘清了易用性和杠杆效应之间的细微差别，而且我无疑会一直对它进行迭代。你有使用类似的东西吗？你是怎么避免掉入基础设施规划中的常见陷阱的？
