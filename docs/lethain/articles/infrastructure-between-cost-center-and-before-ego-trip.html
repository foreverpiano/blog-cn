基础设施：介于成本中心与自我陶醉之间

2017-03-05 · 阅读原文

最近我面试一位工程经理候选人，问她为什么考虑离开当前职位，她说了一件让我深有共鸣的事：她的基础设施工程团队还有大量工作要做，却没有足够的人头来完成。

这就是基础设施作为成本中心的写照。

另一方面，在里，我也见过基础设施团队对优先级感到困惑，同时组建多个目标重叠的竞争团队。更糟糕的是，他们会为同一个问题配备相互竞争的解决方案，却完全不投入人力去解决最紧迫的工作。在这种情况下，关键的生产系统持续崩溃，而周围却堆满了人员充足、目标模糊的“ glamour 项目”。超高速增长时代的生产力

这就是基础设施的自我陶醉。

尽管这两种极端情况的危险都显而易见，但要找到一个务实的思考框架来优先排序基础设施工作，依然极具挑战性。正因为难度够高，这些年来我逐渐整理出一套思考工具，帮助自己对 incoming 请求进行优先级排序，并决定应该主动发起哪些项目。

使用方法是：思考你当前提供的能力、收到的功能请求以及潜在的新能力，对每一项都从这六个维度寻找机会。这些维度是按照大致的优先顺序排列的，当然你的优先级很可能和我并不完全一致。

基础设施为公司和客户提供以下六大主要价值：

安全性不仅仅是“锁紧东西”，而是要让同样的任务在相同努力下能以更安全的方式完成。（如果你在寻找灵感，BeyondCorp 和 Security Keys 是很好的阅读材料！）可靠性不仅仅是 uptime、harvest 或 yield，还包括强化你的接口，确保 oncall 负载足够低，让告警能被真正处理而不是被忽略。易用性是让你的软件更容易被正确使用。如果开通一个新服务需要二十步，你能不能把它减少到十二步？如果创建一个 S3 bucket 需要审批，你能否至少自动预审批一些常见情况？如果人们总是误解你的文档或不知道如何调试你的系统，你怎样才能让它更直观？如果工程师每次安全部署都要念一段咒语，你能否加上安全护栏，让“做对”比“做错”更容易？杠杆效应是通过让你的基础组件和抽象能力更强大（有人认为是对面向服务的计算的重大改进），或者提供全新的能力（例如提供任务或批处理系统），从而让团队内外工程师的生产力都得到提升。成本是指以更低的价格提供服务。这既包括降低维护开销以便把更多时间花在功能开发上，也包括更好地选择合适的 AWS 或 GCP 实例。在 Stripe，我们把成本管理当作一项基础设施特性来推动——由基础设施工程团队主导，而不是财务驱动——看到 Aditya、Cory 和 Davin 把这件事变成一项赋能特性，过程相当令人振奋。（相关推荐：一篇令人费解但精彩的文章。）延迟既包括减少到达你服务器的时间（通过 POP、active-active 多区域/数据中心拓扑，或使用连接池与已建立连接），也包括减少在你技术栈内部花费的时间（通过更好的负载均衡策略、使用请求追踪找到延迟热点、优化数据库查询等）。无服务器架构：守门机制与利润空间QoS、成本与配额

这当然不是一个完整的框架，但我发现它在规划会议中非常实用。特别是，它能帮助我避免基础设施工程团队常犯的一些错误：

把安全责任推给规模小得多的安全团队，而自己却在构建大多数需要被保护的平台。认为基础设施的易用性不重要，因为用户是工程师。这是不对的：即使是工程师也会受注意力分散、打字错误和时间限制的影响。更糟糕的是，内部用户因为易用性问题而放弃一个平台的概率，远高于因为真正缺少特性（你有多少次被告知在 Y 平台上“其实可以”做 X 任务，然后听到一个复杂的 workaround？）。因此，在这方面投入不足往往会导致巨大压力，让人去构建新平台——在我看来，这通常是错误的。优先选择那些看似光鲜、通常也非常复杂的项目（一个解决方案在寻找问题），而不是直接去解决眼前的问题。接受当前的现状，认为“已经够好了”，满足于一个还不错的系统，而不是继续推动它变得卓越。把成本意识委托给另一个对你的系统实际工作方式缺乏洞察的组织，迫使他们不得不在信息不足的情况下推动成本降低。（看来常见错误还真不少。）

通过在规划时系统性地思考这六大价值，我发现自己更不容易掉进那些诱人的思维陷阱。

过去六个月左右，我一直在使用这个框架的简化版本，总体相当满意。虽然直到写这篇文章时，我才真正把易用性和杠杆效应之间的细微差别梳理清楚，而且毫无疑问我还会一直迭代下去。你是否在使用类似的东西？你又是如何避免掉入基础设施规划中的常见陷阱的呢？
