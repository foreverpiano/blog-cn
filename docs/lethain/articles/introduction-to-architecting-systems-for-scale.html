构建可扩展系统的架构导论

2011-04-04 · 阅读原文

很少有计算机科学或软件开发课程会教授构建可扩展系统的基本知识。通常，这些系统架构的技能都是在工作中，通过承受产品不断增长带来的痛苦，或者与已经在这一过程中积累经验的工程师合作而逐步掌握的。

在这篇文章中，我将尝试记录自己在 Yahoo! 和 Digg 开发系统时学到的一些可扩展性架构经验。

我会尽量为图表保持统一的颜色约定：

  • green is an external request from an external client (an HTTP request from a browser, etc),
  • blue is your code running in some container (a Django app running on mod_wsgi, a Python script listening to RabbitMQ, etc), and
  • red is a piece of infrastructure (MySQL, Redis, RabbitMQ, etc).

理想的系统在增加硬件时，容量能够线性增长。在这样的系统中，如果你有一台机器，再增加一台，容量就会翻倍；如果你有三台，再增加一台，容量就会提升 33%。我们将这种特性称为水平扩展。

在故障方面，理想的系统不会因为失去一台服务器而中断。失去一台服务器只会使系统容量下降相当于它加入时增加的容量。我们将这种特性称为冗余。

水平扩展和冗余通常都是通过负载均衡来实现的。

（本文不会讨论垂直扩展，因为对于大型系统来说，这通常是一种不理想的特性——最终增加一台机器的成本会比给单台机器增加资源的成本更低，而且冗余和垂直扩展往往是相互矛盾的。）

负载均衡是指根据某些指标（随机、轮询、根据机器容量加权随机等）以及当前状态（可接受请求、没有响应、错误率升高等），将请求分发到多个资源上的过程。

负载不仅需要在用户请求和 Web 服务器之间进行均衡，还需要在系统的每个环节都进行均衡，才能实现完全的可扩展性和冗余。一个中等规模的系统可能需要在三个层面进行负载均衡：

  • user to your web servers,
  • web servers to an internal platform layer,
  • internal platform layer to your database.

实现负载均衡有多种方式。

智能客户端

将负载均衡功能加入到你的数据库（缓存、服务等）客户端中，通常对开发者来说很有吸引力。它吸引人是因为这是最简单的方案吗？通常不是。它吸引人是因为它最健壮吗？遗憾，不是。它吸引人是因为它易于复用吗？可惜，也不是。

开发者倾向于使用智能客户端，因为他们是开发者，习惯于通过编写软件来解决问题，而智能客户端本身就是软件。

带着这个前提，什么是智能客户端？它是一个可以获取服务主机池、在它们之间均衡负载、检测已宕机的主机并避免向其发送请求的客户端（它还需要能检测恢复的主机、处理新增主机等，这使得它们调试起来很有趣，但设置起来却极其麻烦）。

硬件负载均衡器

最昂贵但性能极高的负载均衡方案是购买专用的硬件负载均衡器（例如 Citrix NetScaler）。虽然它们能解决范围惊人的问题，但硬件方案价格极高，而且配置也“非同小可”。

因此，即使是预算充足的大型公司，通常也不会将专用硬件用于所有的负载均衡需求；它们一般只将其用作用户请求进入基础设施的第一个接触点，而在内部网络流量上使用其他机制（智能客户端或下节讨论的混合方案）。

软件负载均衡器

如果你想避免编写智能客户端的痛苦，而购买专用硬件又过于奢侈，那么上天很友好地提供了折中方案：软件负载均衡器。

HAProxy 就是一个很好的例子。它在你的每台机器上本地运行，你希望负载均衡的每个服务都在本地绑定一个端口。例如，你可以将平台机器通过 localhost:9000 访问，数据库读池通过 localhost:9001，数据库写池通过 localhost:9002。HAProxy 负责健康检查，并根据你的配置将机器从池中移除或重新加入，同时在池内的所有机器之间进行负载均衡。

对于大多数系统，我建议从软件负载均衡器起步，只有在真正有明确需求时再转向智能客户端或硬件负载均衡。

负载均衡帮助你在不断增加的服务器上实现水平扩展，而缓存则能让你更高效地利用已有资源，同时让原本难以达到的产品需求变得可行。

缓存包括：预先计算结果（例如前一天每个引荐域名的访问次数）、预先生成昂贵的索引（例如根据用户点击历史推荐的故事），以及将频繁访问的数据副本存储在更快的后端（例如使用 Memcache 而不是 PostgreSQL）。

在实践中，缓存的重要性在开发流程中通常早于负载均衡。从一开始就采用一致的缓存策略能为你后续节省大量时间。它还能确保你不会去优化那些无法用缓存机制复制的访问模式，或者在加入缓存后性能已不再重要的访问模式（我发现许多经过大量优化的 Cassandra 应用，如果数据库的缓存策略无法应用于你的访问模式，就很难干净地加入缓存，因为 Cassandra 和缓存之间的数据模型通常并不一致）。

应用缓存 vs 数据库缓存

缓存主要有两种方式：应用缓存和数据库缓存（大多数系统都同时 heavily 依赖两者）。

应用缓存需要在应用代码中显式集成。通常它会先检查缓存中是否存在某个值；如果没有，则从数据库中获取该值，然后将其写入缓存（如果你使用的是最近最少使用算法的缓存，这种模式尤其常见）。代码通常看起来像这样（这里展示的是一个 read-through 缓存，如果缓存中缺失则会从数据库读取并放入缓存）：

key = "user.%s" % user_id
user_blob = memcache.get(key)
if user_blob is None:
    user = mysql.query("SELECT * FROM users WHERE user_id=\"%s\"", user_id)
    if user:
        memcache.set(key, json.dumps(user))
    return user
else:
    return json.loads(user_blob)

另一面则是数据库缓存。

当你启动数据库时，会获得一些默认配置，这些配置会提供一定程度的缓存和性能。这些初始设置是为通用场景优化的，通过针对你系统的访问模式进行调整，通常可以显著提升性能。

数据库缓存的美妙之处在于，你的应用程序代码无需修改就能“免费”获得加速，一位优秀的 DBA 或运维工程师可以在完全不改动代码的情况下大幅提升性能（我的同事 Rob Coli 最近花时间优化了我们 Cassandra 的行缓存配置，效果显著到他花了一周时间用图表不断“骚扰”我们，展示 I/O 负载大幅下降，请求延迟也显著改善）。

内存缓存

从原始性能角度看，最强大的缓存是将全部数据存储在内存中的缓存。Memcached 和 Redis 都是内存缓存的例子（注意：Redis 可以配置成将部分数据持久化到磁盘）。这是因为访问 RAM 的速度比访问磁盘要快几个数量级。

另一方面，你能使用的 RAM 通常远少于磁盘空间，因此你需要一种策略，只把数据中的热数据子集保留在内存缓存中。最直接的策略是最近最少使用（LRU），Memcache 采用的就是这种策略（Redis 从 2.2 版本开始也可以配置为使用 LRU）。LRU 的工作原理是淘汰不常用数据，保留常用数据，几乎在所有情况下都是合适的缓存策略。

内容分发网络

对于提供大量静态媒体的网站，有一种特殊的缓存形式（有人可能对这个术语有异议，但我认为很贴切），就是内容分发网络（CDN）。

CDN 将提供静态媒体的负担从你的应用服务器（通常被优化用于提供动态页面而非静态媒体）上卸下来，并提供地理分布能力。总体而言，你的静态资源加载会更快，对服务器的压力也会更小（但会带来新的业务开支）。

在典型的 CDN 设置中，请求会首先向 CDN 请求静态媒体，如果 CDN 本地有该内容，就会直接提供（通过 HTTP 头来配置 CDN 如何缓存特定内容）。如果没有，CDN 会向你的服务器请求该文件，然后在本地缓存并提供给用户（此时它扮演了 read-through 缓存的角色）。

如果你的网站规模还不足以拥有自己的 CDN，你可以通过将静态媒体放在单独的子域名（例如 static.example.com）上，使用像 Nginx 这样的轻量级 HTTP 服务器来提供服务，从而为未来切换到 CDN 做好准备，后续只需将 DNS 从你的服务器切换到 CDN 即可。

缓存失效

虽然缓存非常棒，但它要求你在缓存和数据源（即数据库）之间保持一致性，否则可能会导致非常诡异的应用行为。

解决这个问题被称为缓存失效（cache invalidation）。

如果你只在一个数据中心内运行，这通常是一个相对直接的问题，但如果你有多个代码路径向数据库和缓存写入数据（如果你在写应用时没有提前考虑缓存策略，这几乎一定会发生），就很容易引入错误。从高层来看，解决方案是：每次值发生变化时，将新值写入缓存（这称为 write-through 缓存），或者直接删除缓存中的当前值，让 read-through 缓存后续再去填充（选择 read-through 还是 write-through 取决于你的应用细节，但通常我更喜欢 write-through 缓存，因为它能降低后端数据库被“踩踏”的概率）。

当涉及模糊查询（例如你在全文搜索引擎如 SOLR 前加入应用层缓存）或修改未知数量元素（例如删除一周前创建的所有对象）时，失效会变得更有挑战性。

在这些场景中，你需要考虑完全依赖数据库缓存、为缓存数据设置激进的过期时间，或者重构应用逻辑来规避问题（例如，与其执行 DELETE FROM a WHERE...，不如先查出所有符合条件的数据，失效对应的缓存行，然后通过主键显式删除这些行）。

随着系统变得越来越复杂，几乎总是需要执行一些无法与客户端请求同步完成的操作——要么是因为它会产生不可接受的延迟（例如你想将用户的行为传播到整个社交图谱），要么是因为它需要定期执行（例如生成每日分析汇总）。

消息队列

对于你希望与请求同步执行但又太慢的操作，最简单的解决方案是创建一个消息队列（例如 RabbitMQ）。消息队列允许你的 Web 应用快速向队列发布消息，然后由其他消费者进程在客户端请求的范围和时间线之外完成处理。

如何划分离线消费者处理的工作和 Web 应用实时完成的工作，完全取决于你向用户暴露的界面。通常你会选择以下两种方式之一：

  1. perform almost no work in the consumer (merely scheduling a task) and inform your user that the task will occur offline, usually with a polling mechanism to update the interface once the task is complete (for example, provisioning a new VM on Slicehost follows this pattern), or
  2. perform enough work in-line to make it appear to the user that the task has completed, and tie up hanging ends afterwards (posting a message on Twitter or Facebook likely follow this pattern by updating the tweet/message in your timeline but updating your followers’ timelines out of band; it’s simple isn’t feasible to update all the followers for a Scobleizer in real-time).

消息队列还有另一个好处，它允许你建立一个单独的机器池来执行离线处理，而不是给 Web 应用服务器增加负担。这样你就可以针对当前性能或吞吐量瓶颈来针对性地增加资源，而不是在瓶颈和非瓶颈系统上均匀地增加资源。

调度周期性任务

几乎所有大型系统都需要每天或每小时执行的任务，但遗憾的是，这似乎仍然是一个尚未有广泛接受的、能轻松支持冗余的解决方案。目前你可能还是得依赖 cron，但你可以让 cron 任务向消费者发布消息，这样 cron 机器就只负责调度，而不需要承担所有实际处理工作。

有没有人知道公认的能解决这个问题的工具？我见过很多自研系统，但没有看到干净且可复用的方案。当然，你可以把 cron 任务保存在 Puppet 配置中，这样在丢失机器时恢复起来比较容易，但仍然需要手动恢复，这虽然可以接受，但并非完美。

Map-Reduce

如果你的大型应用要处理海量数据，那么在某个阶段你很可能需要引入 map-reduce 支持，通常会使用 Hadoop，可能还会结合 Hive 或 HBase。

加入 map-reduce 层后，你就可以在合理的时间内完成数据密集型或计算密集型的操作。你可以用它来计算社交图谱中的推荐用户，或者生成分析报告。

对于足够小的系统，你通常可以用 SQL 数据库做即席查询，但一旦数据量或写负载大到需要对数据库进行分片，这种方式就很难平滑扩展，而且通常需要专门的从库来执行这些查询（到了那个地步，你可能更愿意使用专门为分析海量数据而设计的系统，而不是和数据库硬刚）。

大多数应用一开始都是 Web 应用直接与数据库通信。这种方式对大多数应用来说已经足够，但加入平台层有几个 compelling 的理由，让你的 Web 应用先与平台层通信，再由平台层与数据库通信。

首先，将平台层和 Web 应用分离后，你可以独立扩展各个部分。如果你添加了一个新的 API，可以增加平台服务器，而无需为 Web 应用层增加不必要的容量。（通常，将服务器角色专门化后，可以进行更深层次的配置优化，这是通用机器无法实现的；数据库机器通常有很高的 I/O 负载，会受益于固态硬盘，而配置良好的应用服务器在正常运行时可能完全不读盘，但可能从更多的 CPU 中获益。）

其次，加入平台层是一种在多个产品或界面（Web 应用、API、iPhone 应用等）之间复用基础设施的方式，而无需编写大量重复的处理缓存、数据库等的样板代码。

第三，平台层有时被低估的一个方面是，它能让组织更容易扩展。在最佳情况下，平台会暴露一个清晰的、与具体产品无关的接口，屏蔽掉实现细节。如果做得好，这就能让多个独立团队基于平台的能力进行开发，同时还有另一个团队负责实现和优化平台本身。

我原本打算详细讨论多数据中心的处理，但这个主题确实值得单独写一篇文章，所以我只简单提一下：在那个阶段，缓存失效和数据复制/一致性会变成相当有趣的问题。
