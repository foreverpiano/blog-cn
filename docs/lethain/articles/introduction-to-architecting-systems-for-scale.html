构建可扩展系统的架构导论

2011-04-04 · 阅读原文

很少有计算机科学或软件开发课程会尝试教授构建可扩展系统的基本组件。通常，系统架构是在工作中通过应对产品不断增长带来的痛苦逐步掌握的，或者是通过与已经历过这一过程的工程师合作习得的。

在这篇文章中，我将尝试记录我在 Yahoo! 和 Digg 开发系统时所学到的一些可扩展性架构经验。

我尝试为图表保持统一的颜色约定：

绿色代表来自外部客户端的外部请求（例如浏览器发出的 HTTP 请求）；蓝色代表运行在某个容器中的你的代码（例如运行在 mod_wsgi 上的 Django 应用、监听 RabbitMQ 的 Python 脚本等）；红色代表基础设施组件（MySQL、Redis、RabbitMQ 等）。

理想的系统在增加硬件时，容量能够线性增长。在这样的系统中，如果你有一台机器，再添加一台，容量就会翻倍；如果你有三台，再添加一台，容量会增加 33%。我们把这种特性称为水平扩展。

在容错方面，理想的系统不会因为某台服务器宕机而中断服务。失去一台服务器只会让系统容量下降相当于它加入时所增加的容量。我们把这种特性称为冗余。

水平扩展和冗余通常都是通过负载均衡来实现的。

（本文不会讨论垂直扩展，因为对于大型系统来说这通常不是理想属性——最终增加一台机器的成本会比给单台机器增加资源更低，而且冗余与垂直扩展往往是相互矛盾的。）

负载均衡是指根据某种指标（随机、轮询、按机器容量加权随机等）以及当前状态（是否可接受请求、是否无响应、错误率是否升高等），将请求分发到多个资源上的过程。

负载不仅需要在用户请求和 Web 服务器之间进行均衡，还需要在系统的每一个环节都做好均衡，才能实现整体的可扩展性和冗余。一个中等规模的系统通常会在三个层面进行负载均衡：

用户到 Web 服务器、Web 服务器到内部平台层、内部平台层到数据库。

实现负载均衡有多种方式。

智能客户端

在你的数据库（缓存、服务等）客户端中加入负载均衡功能，通常对开发者来说很有吸引力。它是因为最简单吗？通常不是。它是因为最健壮吗？遗憾，不是。它是因为易于复用吗？可惜，也不是。

开发者倾向于使用智能客户端，因为他们是开发者，习惯于写代码解决问题，而智能客户端就是软件。

带着这个前提，什么是智能客户端？它是一个知道一组服务主机列表，并在它们之间进行负载均衡的客户端，能够检测宕机的主机并避免向其发送请求（同时还要能检测恢复的主机、处理新增主机等，这使得它们实现起来很有趣，但配置起来却很麻烦）。

硬件负载均衡器

最昂贵但性能极高的负载均衡方案是购买专用的硬件负载均衡器（例如 Citrix NetScaler）。虽然它们能解决大量问题，但硬件方案价格高昂，而且配置也并不简单。

因此，即使是预算充足的大型公司，通常也不会把专用硬件用于所有负载均衡需求；而是仅将其作为用户请求进入基础设施的第一个接触点，内部网络流量则使用其他机制（智能客户端或下文讨论的混合方案）。

软件负载均衡器

如果你既不想承受开发智能客户端的痛苦，又觉得购买专用硬件过于奢侈，那么上天很贴心地提供了混合方案：软件负载均衡器。

HAProxy 就是这类方案的优秀代表。它运行在你的每台服务器上，你想均衡的每个服务都对应一个本地端口。例如，你可以将平台机器绑定到 localhost:9000，数据库读池绑定到 localhost:9001，写池绑定到 localhost:9002。HAProxy 负责健康检查，会根据配置动态添加或移除机器，同时在池内各机器之间进行负载均衡。

对大多数系统而言，我建议从软件负载均衡器起步，只有在明确有需要时再转向智能客户端或硬件负载均衡。

负载均衡帮助你在不断增加的服务器数量上实现水平扩展，而缓存则能让你对已有资源进行更高效的利用，同时让原本难以实现的产品需求变得可行。

缓存包括：预先计算结果（例如前一天每个引荐域名的访问次数）、预先生成昂贵的索引（例如基于用户点击历史推荐的故事），以及将频繁访问的数据存放在更快的基础设施中（例如用 Memcache 代替 PostgreSQL）。

在实践中，缓存的重要性通常比负载均衡更早出现。从一开始就采用一致的缓存策略能为你后续节省大量时间。它还能避免你去优化那些无法被缓存机制复制的访问模式，或者在加入缓存后性能已不再重要的访问模式（我发现很多经过深度优化的 Cassandra 应用，如果数据库的缓存策略无法应用到你的访问模式上，后期再加入缓存会非常困难，因为两者之间的数据模型通常是不一致的）。

应用缓存与数据库缓存

缓存主要有两种方式：应用缓存和数据库缓存（大多数系统都会同时 heavily 依赖两者）。

应用缓存需要在应用代码中显式地进行集成。通常它会先检查缓存中是否有值，如果没有，则从数据库获取，然后将结果写入缓存（在使用最近最少使用算法的缓存时，这种模式尤其常见）。代码通常像下面这样（这里展示的是 read-through 缓存，即当缓存中缺失时会从数据库读取并放入缓存）：

key = "user.%s" % user_id
user_blob = memcache.get(key)
if user_blob is None:
    user = mysql.query("SELECT * FROM users WHERE user_id=\"%s\"", user_id)
    if user:
        memcache.set(key, json.dumps(user))
    return user
else:
    return json.loads(user_blob)

另一面则是数据库缓存。

当你启动数据库时，会获得一套默认配置，其中已经包含了一定程度的缓存和性能优化。这些初始设置是针对通用场景优化的，通过根据你系统的访问模式进行调整，通常可以显著提升性能。

数据库缓存的优点在于，你的应用程序无需修改代码就能“免费”获得性能提升。一位优秀的 DBA 或运维工程师可以在不改一行代码的情况下大幅提高性能（我的同事 Rob Coli 最近花了一些时间优化我们 Cassandra 的 row cache 配置，效果显著，以至于他用了一周时间不断给我们看图表：I/O 负载大幅下降，请求延迟也显著改善）。

内存缓存

就原始性能而言，最强大的缓存是将全部数据都存储在内存中的缓存。Memcached 和 Redis 都是内存缓存的例子（注意：Redis 可以配置为将部分数据持久化到磁盘）。这是因为访问内存比访问磁盘要快几个数量级。

另一方面，你能获得的内存容量通常远小于磁盘空间，因此需要一套策略，只把热点数据子集保留在内存缓存中。最直接的策略是最近最少使用（LRU），Memcache 默认采用这种策略（Redis 从 2.2 版本开始也可以配置为使用 LRU）。LRU 的工作原理是淘汰不常用的数据，为更常用的数据腾出空间，几乎在所有情况下都是合适的缓存策略。

内容分发网络

对于提供大量静态媒体的网站来说，一种特殊的缓存形式（有人可能对这个用法有异议，但我认为很贴切）就是内容分发网络（CDN）。

CDN 将提供静态媒体的负担从你的应用服务器上卸下来（应用服务器通常被优化用于动态页面而不是静态文件），并提供地理上的分布式加速。总体而言，你的静态资源加载会更快，对服务器的压力也更小（但会带来新的运营成本）。

在典型的 CDN 配置中，用户请求会先向 CDN 请求静态资源，如果 CDN 本地有缓存，就会直接返回（通过 HTTP 头信息配置 CDN 如何缓存特定内容）。如果没有，CDN 会从你的服务器获取该文件，缓存到本地后再返回给用户（此时它充当了 read-through 缓存的角色）。

如果你的网站规模还不足以拥有自己的 CDN，可以先把静态资源放在独立子域名（例如 static.example.com）下，用 Nginx 这类轻量级 HTTP 服务器提供服务，未来再将 DNS 切换到 CDN 上，这样能为后续迁移打好基础。

缓存失效

虽然缓存非常强大，但你必须在缓存和数据源（即数据库）之间保持一致性，否则可能会导致十分诡异的应用程序行为。

解决这个问题被称为缓存失效（cache invalidation）。

如果你只有一个数据中心，这通常是一个相对简单的问题。但如果你有多条代码路径同时写入数据库和缓存（如果你在写应用时没有提前考虑缓存策略，这几乎是必然会发生的），就很容易引入错误。从高层来看，解决方案是：每次值发生变化时，要么把新值写入缓存（称为 write-through 缓存），要么直接把缓存中的当前值删除，让 read-through 缓存后续再填充（选择 read-through 还是 write-through 取决于你的应用细节，不过我通常更喜欢 write-through，因为它能降低后端数据库被“踩踏”的概率）。

当涉及模糊查询（例如在全文搜索引擎如 SOLR 前面加应用层缓存）或修改数量不确定的元素（例如删除一周前创建的所有对象）时，失效会变得更具挑战性。

在这些场景下，你可能需要完全依赖数据库缓存、给缓存数据设置激进的过期时间，或者重构应用逻辑来规避这个问题（例如，与其执行 DELETE FROM a WHERE...，不如先查出所有符合条件的数据，失效对应的缓存行，然后根据主键显式删除这些行）。

随着系统变得越来越复杂，几乎总是需要执行一些无法在客户端请求路径上同步完成的操作——要么是因为会产生不可接受的延迟（例如你想把用户的某个行为传播到整个社交图谱），要么是因为它需要定期执行（例如生成每日分析汇总）。

消息队列

对于那些你希望在请求路径中执行但又太慢的操作，最简单的解决方案是引入消息队列（例如 RabbitMQ）。消息队列允许 Web 应用快速地将消息发布到队列中，然后由其他消费者进程在客户端请求之外的范围和时间线内完成处理。

如何划分离线消费者完成的工作与 Web 应用在线完成的工作，完全取决于你向用户暴露的界面。一般来说，你会选择以下两种方式之一：

在消费者中几乎不做实际工作（只是调度一个任务），然后告诉用户任务会在后台执行，通常通过轮询机制在任务完成后更新界面（例如在 Slicehost 上开通一台新虚拟机就采用这种模式）；或者在线上完成足够多的工作，让用户感觉任务已经完成，然后在后台处理收尾工作（在 Twitter 或 Facebook 上发消息很可能采用这种模式：先更新你自己的时间线，但把粉丝的时间线更新放在带外进行；实时更新 Scobleizer 所有粉丝的时间线是完全不现实的）。

消息队列还有另一个好处，就是允许你组建一个独立的机器池来处理离线任务，而不用给 Web 应用服务器增加负担。这样你就可以针对当前性能或吞吐量瓶颈定向增加资源，而不是在整个系统中（包括非瓶颈部分）统一扩容。

定期任务调度

几乎所有大型系统都需要每天或每小时执行的任务，但遗憾的是，这似乎仍然是一个没有广泛认可的、能轻松支持冗余的解决方案。目前你可能还是得继续使用 cron，但可以让 cron 任务只负责向消费者发布消息，这样 cron 机器就只需承担调度职责，而不必执行所有实际处理工作。

有没有人知道公认的、能很好解决这个问题的工具？我见过很多自研系统，但没有看到干净且可复用的方案。当然，你可以把 cron 任务放在 Puppet 配置中，这样丢失机器后恢复起来比较容易，但仍然需要手动干预。这虽然可以接受，但并不完美。

Map-Reduce

如果你的大型应用要处理海量数据，那么在某个阶段你很可能会引入 map-reduce 支持，通常会使用 Hadoop，可能还会用到 Hive 或 HBase。

加入 map-reduce 层后，你就可以在合理的时间内完成数据密集型或计算密集型的操作。你可能会用它来计算社交图谱中的推荐用户，或者生成分析报告。

对于规模较小的系统，你通常可以用 SQL 数据库做临时查询，但一旦数据量或写负载大到需要对数据库进行分片，这种方式就很难继续扩展，而且通常需要专用的从库来执行这些查询（到了那个地步，你或许更愿意使用专门为分析海量数据而设计的系统，而不是和数据库死磕）。

大多数应用一开始都是 Web 应用直接和数据库通信。这种方式对大多数应用来说已经足够，但引入平台层——即 Web 应用不直接访问数据库，而是通过一个平台层来和数据库打交道——有几个 compelling 的理由。

首先，将平台层和 Web 应用分离后，你可以独立扩展各个部分。如果新增了一个 API，你可以只增加平台服务器，而无需为 Web 层增加不必要的容量。（通常来说，让服务器角色更专一能带来额外的配置优化空间，这是通用用途机器无法实现的；数据库机器通常 I/O 压力很大，受益于使用固态硬盘；而配置良好的应用服务器在正常运行时可能完全不读磁盘，但更需要 CPU 资源。）

其次，加入平台层能让你在多个产品或界面（Web 应用、API、iPhone 应用等）之间复用基础设施，而不必为处理缓存、数据库等逻辑写大量重复的样板代码。

第三，平台层有一个有时被低估的好处，那就是它能让组织更容易扩展。在理想情况下，平台会暴露一个清晰的、与具体产品无关的接口，隐藏底层实现细节。如果做得好，这就能让多个独立团队基于平台的能力进行开发，同时还有另一个团队负责实现和优化平台本身。

我原本打算详细讨论多数据中心的问题，但这个话题确实值得单独写一篇文章，所以这里只简单提一句：在那个阶段，缓存失效和数据复制/一致性会变成非常有趣的难题。
