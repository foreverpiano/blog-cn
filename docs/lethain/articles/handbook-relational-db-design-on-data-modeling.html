《关系数据库设计手册》数据建模笔记

2019-09-13 · 阅读原文

我最近在阅读 Candace Fleming 和 Barbara von Halle 合著的《Handbook of Relational Database Design》，这本书于 1989 年首次出版。它雄心勃勃地试图同时定义两方面的最佳实践：一是以数据库无关的方式进行数据建模，二是解决数据库实现和调优中的实际问题。我最终会为这两部分都写笔记，这里记录的是关于本书前半部分——定义数据模型的内容。

快速总结：我没有上过大学级的数据库课程，和几个上过的人聊过之后，发现这本书涵盖了其中大部分内容。虽然书中有些内容已经过时，但它是对基础知识极好的回顾，也填补了我作为实践者先入行、缺少理论支撑所留下的诸多空白。花时间读它，绝对不后悔。

三模式方法

三模式方法要求数据建模人员开发三种模式：外部模式（external schema）、概念模式（conceptual schema）和内部模式（internal schema）。建模从开发多个外部模式开始，每个外部模式代表某一用户群体的视角（例如在租房应用中，可以是租户视角或房东视角）。收集足够多的用户视图后，建模者将其整合为统一的概念模式，该模式协调了多种用户视图，形成一个由数据库管理员负责、独立于任何特定存储技术的统一模式。最后一步是将概念模式转换为内部模式，即底层存储技术实际使用的模式（例如具体的 MySQL schema）。

从这个概念中我有几个主要收获。首先，早在 1975 年 ANSI 委员会就为此提出了一份正式的标准文档。其次，它非常刻意地将技术约束与数据建模解耦。我个人曾严重倾向于从技术角度出发进行建模，现在回想起来，我确信这种初始做法让我的模型质量打了折扣。

后面的笔记主要聚焦于概念模式，书中也常将其称为逻辑数据模型（logical data model）。本文会在一定程度上交替使用这两个术语，不过用于开发概念模式的技术同样适用于开发外部模式。

有效数据模型的特性

一个好的数据模型应当具备（1）正确性、（2）一致性、（3）可共享性以及（4）灵活性。这样的模型将易于使用，并在需求演进过程中持续保持价值。

正确性是指模型真实反映了它所建模的业务过程。它不会用取巧的方式掩盖真实世界的复杂行为，而是完整地将其呈现出来。一致性对应 ACID 中的 Consistency：系统状态永远不会进入无效配置。如果你在为租房业务建模，那么租户的房屋和房屋的租户信息永远不应反映出相互矛盾的现实。可共享的模型能够被多个不同应用使用。对房屋租赁这一底层过程的准确表示，应该能够支撑租户申请房屋的应用、房东管理出租物业的应用、计费应用、与维修公司对接的集成等。灵活的模型具有可进化性，当它所代表的真实系统发生变化时，仍能保持其正确性。

我特别喜欢这些特性的地方在于，它们既强调了建模的价值（准确反映真实系统），也承认维护一个成功模型的大部分工作是在初始建模之后完成的。成功的系统必须不断适应一系列越来越意想不到的需求，才能使用迭代淘汰赛来进行时间线权衡。

开发数据模型

数据建模最重要的方面是采用数据驱动的方法。不要从实现约束出发，在第一遍建模时完全忽略那些约束，把注意力放在业务想要达成的目标上。

在这个方法论之下，具体步骤为：

开发逻辑数据模型的流程

构建用户视图骨架。明确你正在为哪些类型的用户构建系统，为每个用户群体记录他们视角下的主要实体和关系。利用这些信息建立整个系统的数据字典（你将终身维护它）。为用户视图添加键。首先确定能唯一标识某个实体的键的组合（主键），以及用于检索的键的组合（候选键）。其次，确定将在模型间使用的外键。最后，明确管理数据变更的业务规则（例如合法的插入、删除和更新行为）。为用户视图添加细节。增加不属于主键的属性（“非键属性”）。这一部分特别反对使用枚举值（例如用“1032”代表“MEDICAL INDUSTRY”），因为这会让数据难以理解。当然，后续的规范化技术很可能也会要求你把行业做成一张单独的表。通过规范化验证用户视图。本书介绍了一系列“范式”，每种范式都是将带有冗余信息的 schema 转换为冗余更少的 schema 的过程。我本来打算把它们都整理出来，但算了，不做了——直接去读一篇数据库规范化的文章吧。如果你不太想死记那些规则，一个粗略的经验法则是：对任何实体进行的修改，都应该可以通过一个范围很窄的更新来完成，例如你的查询的 where 子句应该只影响一行记录。确定额外的属性业务规则。引用书中的话：“如果不理解与信息完整性相关的规则，那么理解业务中信息的结构是毫无意义的。”这一节讲述了如何为每个属性定义域（基于它们所代表的事物，什么是合法的值、最大值、最小值等等），确保主键唯一，定义外键关系的规则（哪些是可选的，哪些是有效的等），以及定义触发器（数据库在变更事件上强制执行的检查）。整合用户视图。现在你已经完善了每个用户视图，将它们合并成一个统一模型，使其能够满足所有用户视图的需求。

这本书做得特别好的一点是，通过案例研究逐步演示如何将上述每种技术应用到具体问题上。

建模技巧

开发有效逻辑数据模型的技巧包括：

与用户紧密合作。通常用户是在建模过程后期才被引入的，尤其是在采用实现中心而非数据中心方法的情况下。这会导致模型的正确性降低。正确的做法是从用户开始，然后再回到实现层面。遵循结构化的方法论。设计数据模型是一种基础设施工程中的产品管理，受益于同样严谨、有意的方法论。使用结构和完整性约束。为每个属性的合法值域定义明确的约束，并控制对象之间关系的修改，以确保底层数据始终保持正确。使用概念化和规范化技术。利用大量正式的规范化方法，将数据模型简化为冗余最少的形式。尽可能使用图表。纯文字描述的模型比图表模型更难让人直观理解，而图表的信息密度要高得多。建立数据字典。以文档或文本形式，自动或手动地收集与数据模型相关的所有信息，与图表配合使用，作为持久的真相来源。

词汇表

“实体（Entity）是你希望记录事实的某个人、地点、事物或概念”“关系（Relationship）是两个实体之间的关联”“属性（Attribute）是描述实体且不可再分解的信息片段”主键（Primary key）是“标识属性或属性集合”“外键（Foreign key）是一个属性或属性集合，通过标识关联实体来完成一个关系。‘外’这个词传达了该属性‘属于’或引用另一个……实体的意思。”一对多关系描述一个实体（例如一位作者）与多个其他实体（例如多本书）的关联。一对一关系描述一个实体（例如一本书）恰好与另一个实体（例如它的出版社）相关联。业务规则描述了模型的合法状态。它们通过限制假设的值（例如必填字段和可空引用）来维护完整性。触发操作是一种业务规则，在变更（插入、更新和删除）时被执行。完整性有三种形式：实体完整性、参照完整性和域完整性。实体完整性描述单个属性，特别是主键的所有组成部分都必须存在。参照完整性管理跨表的外键，特别是引用中的外键必须真实存在。域完整性应用于列，例如数据类型、默认值、唯一性等。

一些评论

放下笔记者的角色，我真的很享受阅读这种结构化数据建模的愿景。这本书写于敏捷或看板等方法出现之前，处在一个明显以瀑布式开发为主、更多单体应用和服务的时代，也是一个还没有互联网规模应用的年代。

早期的 NoSQL 运动很大程度上是为了不再提供那些无法横向扩展的功能，迫使数据建模直接面对互联网规模带来的后果。这种思路与本书所倡导的方法完全相反——本书让我们在开发出逻辑数据模型之前，先忽略技术约束。

类似地，大多数新产品在创建时都没有产品-市场匹配（product-market-fit），希望通过快速迭代来找到匹配。这使得前期建模的想法变得更具挑战性，但我也能看到，如果缺乏有意识的建模，大多数公司在增长曲线的某个阶段生产力都会受到严重制约，直到他们能够重新梳理数据——而这往往隐藏在更大的重构项目之中。

三模式概念中另一个让我着迷的地方是对用户视图的强调，我在行业里几乎没见过这种做法。它们整体上有点像异类，在当下这个许多生产数据库由构建其上的产品工程师而非数据库管理员来建模的世界里，或许已经不再那么重要。

还有，哇，触发器！现代开发的核心原则之一是将逻辑放在一起，以便能够通过部署进行原子化修改（可部署、可灰度、可回滚），而数据库触发器因为难以满足这些特性，已经大幅减少使用。读这本书时，回想那种以触发器为导向的开发方式，感觉特别有意思——因为在我所处的行业圈子里，它们早已失宠。在当今的新开发项目中，还有哪些领域仍然大量依赖触发器吗？

最后一点思考，我觉得逻辑数据模型的可共享性这一概念，在与服务边界结合时特别有意思。我们希望服务拥有自己的数据管理权，但我们仍然需要一个共享的逻辑数据模型来跨服务边界进行推理，这正是我想象中在现代架构中特别适合应用三模式方法的一个场景。
