《关系数据库设计手册》数据建模笔记

2019-09-13 · 阅读原文

我最近在阅读 Candace Fleming 和 Barbara von Halle 合著的《Handbook of Relational Database Design》，这本书于 1989 年首次出版。它雄心勃勃地试图同时定义两方面的最佳实践：一是以数据库无关的方式进行数据建模，二是解决数据库实现和调优中的实际问题。我最终会为这两部分都写笔记，这里记录的是关于本书前半部分——定义数据模型的内容。

快速总结：我没有上过大学级的数据库课程，和几个上过的人聊过之后，发现这本书涵盖了其中大部分内容。虽然书中有些内容已经过时，但它是对基础知识极好的回顾，也填补了我作为实践者先入行、缺少理论支撑所留下的诸多空白。花时间读它，绝对不后悔。

三模式方法

三模式方法要求数据建模人员开发三种模式：外部模式（external schema）、概念模式（conceptual schema）和内部模式（internal schema）。建模从开发多个外部模式开始，每个外部模式代表某一用户群体的视角（例如在租房应用中，可以是租户视角或房东视角）。收集足够多的用户视图后，建模者将其整合为统一的概念模式，该模式协调了多种用户视图，形成一个由数据库管理员负责、独立于任何特定存储技术的统一模式。最后一步是将概念模式转换为内部模式，即底层存储技术实际使用的模式（例如具体的 MySQL schema）。

从这个概念中我有几个主要收获。首先，早在 1975 年 ANSI 委员会就为此提出了一份正式的标准文档。其次，它非常刻意地将技术约束与数据建模解耦。我个人曾严重倾向于从技术角度出发进行建模，现在回想起来，我确信这种初始做法让我的模型质量打了折扣。

后面的笔记主要聚焦于概念模式，书中也常将其称为逻辑数据模型（logical data model）。本文会在一定程度上交替使用这两个术语，不过用于开发概念模式的技术同样适用于开发外部模式。

有效数据模型的特性

一个好的数据模型应当具备（1）正确性、（2）一致性、（3）可共享性以及（4）灵活性。这样的模型将易于使用，并在需求演进过程中持续保持价值。

  • Correct means that the model reflects the reality of the process it models. It doesn’t hide the complexity of the real-world behavior in creative ways, it represents it fully.
  • Consistent is ACID’s Consistency: state should never reach invalid configurations. If you’re modeling rental homes, a renter’s home and the home’s renter should never reflect different realities.
  • Sharable models are usable by many different applications. An accurate representation of the underlying process of renting homes should make it possible to support an application for renters applying for homes, for home owners to manage their rental properties, a billing application, an integration with a maintenance company for repairs, and so on.
  • Flexible models are evolvable, preserving their correctness as the real systems they represent continue to change.

我特别喜欢这些特性的地方在于，它们既强调了建模的价值（准确反映真实系统），也承认维护一个成功模型的大部分工作是在初始建模之后完成的。成功的系统必须不断适应一系列越来越意想不到的需求，才能使用迭代淘汰赛来进行时间线权衡。

开发数据模型

数据建模最重要的方面是采用数据驱动的方法。不要从实现约束出发，在第一遍建模时完全忽略那些约束，把注意力放在业务想要达成的目标上。

在这个方法论之下，具体步骤为：

开发逻辑数据模型的流程

  1. Build skeletal user views. Identify the kinds of users you are building for, and for each user document the major entities and relationships from their perspective. Use this to build a data dictionary of all data within the system (you’ll be maintaining this forever).
  2. Add keys to user views. First, determine the combination of keys which uniquely define an entity (primary keys), and also the combination of keys that will be used for retrieval (alternate keys). Second, determine foreign keys that will operate across models. Finally, identify the business rules that govern mutation (e.g. what are legal insert, delete and update behaviors).
  3. Add detail to user views. Add attributes which are not used in primary keys (“nonkey attributes”). This section makes a particular callout against using enumerated values (e.g. “1032” as a coded value for say “MEDICAL INDUSTRY”), as they make data hard to understand. That said, the later normalization technique would likely want you to make industry into a separate table anyway.
  4. Validate user views through normalization. The book introduces a number of “normal forms”, each of which is a transformation of a schema with redundant information into a schema with less redundant information. I started typing them all up, but wow, nope not doing that, just read an article on database normalization instead. If you’re less excited to memorize those rules, a rule of thumb is roughly: any modification you make to any entity should be achievable with a narrowly scoped update, e.g. the where clause on your query should only edit a single row.
  5. Determine additional attribute business rules. To quote, “It is useless to understand the structure of information within the business without understanding rules pertaining to that information’s integrity.” This section goes through defining domains for each attribute (what are the legal values for each attribute based on the thing they’re representing, maximum values, minimum values, and so on), ensuring primary keys are unique, defining rules about foreign key relationships (which are optional, which are valid, etc), and defining triggers (what are database enforced checks on mutation events).
  6. Integrate user views. Now that you’ve refined each of your user views, merge them together into a unified model that incorporates each user view’s needs.

这本书做得特别好的一点是，通过案例研究逐步演示如何将上述每种技术应用到具体问题上。

建模技巧

开发有效逻辑数据模型的技巧包括：

  1. Work closely with users. Often users are brought into a modeling process late, particularly in cases where folks are taking an implementation-centric approach as opposed to a data-centric approach. This leads to less correct models. Instead start with users and work back to implementation second.
  2. Follow a structured methodology. Designing a data model is a 基础设施工程中的产品管理, and benefits from the same rigorous, intentional methodology.
  3. Use structural and integrity constraints. Define explicit constraints on the domain of legal values for each attribute, and control the modification of the relations between objects to ensure the underlying data remains correct.
  4. Use conceptualization and normalization techniques. Use the numerous formal normalization methods to simplify the data model into its least redundant possible form.
  5. Use diagrams whenever possible. Prose models are harder for readers to intuit than diagram model, and diagrams have much higher information density.
  6. Build a data dictionary. An automated or manual collection of all information related to your data model, in document or textual format, to pair with your diagrams and serve as an enduring source of truth.

词汇表

  • “Entity is a person, place, thing or concept about which you wish to record facts”
  • “Relationship is association between two entiities”
  • “Attribute is a nondecomposable piece of information describing an entity”
  • Primary key is the “identify attribute or set of attributes”
  • “Foreign key is an attribute or set of attributes that completes a relationship by identifying the associated entity. The term foreign conveys the idea that the attribute ‘belongs’ or refers to another… entity.”
  • One-to-many relationship describes one entity (e.g. an author) relating to many others (e.g. books).
  • One-to-one relationship describes an entity (e.g. a book) relating to exactly one other (e.g. its publisher)
  • Business rules describe valid model states. They preserve integrity by limiting assumed values, for example required fields and nullable references
  • Triggering operations are a kind of business rule which are applied during mutation (insert, update and delete)
  • Integrity comes in three flavors: entity, referential and domain. Entity integrity describes individual attributes, in particular that all components of a primary key exist. Referential integrity governs foreign keys across tables, in particular that a foreign key in a reference does exist. Domain integrity applies to columns, for example the data type, default value, uniqueness, and so on.

一些评论

放下笔记者的角色，我真的很享受阅读这种结构化数据建模的愿景。这本书写于敏捷或看板等方法出现之前，处在一个明显以瀑布式开发为主、更多单体应用和服务的时代，也是一个还没有互联网规模应用的年代。

早期的 NoSQL 运动很大程度上是为了不再提供那些无法横向扩展的功能，迫使数据建模直接面对互联网规模带来的后果。这种思路与本书所倡导的方法完全相反——本书让我们在开发出逻辑数据模型之前，先忽略技术约束。

类似地，大多数新产品在创建时都没有产品-市场匹配（product-market-fit），希望通过快速迭代来找到匹配。这使得前期建模的想法变得更具挑战性，但我也能看到，如果缺乏有意识的建模，大多数公司在增长曲线的某个阶段生产力都会受到严重制约，直到他们能够重新梳理数据——而这往往隐藏在更大的重构项目之中。

三模式概念中另一个让我着迷的地方是对用户视图的强调，我在行业里几乎没见过这种做法。它们整体上有点像异类，在当下这个许多生产数据库由构建其上的产品工程师而非数据库管理员来建模的世界里，或许已经不再那么重要。

还有，哇，触发器！现代开发的核心原则之一是将逻辑放在一起，以便能够通过部署进行原子化修改（可部署、可灰度、可回滚），而数据库触发器因为难以满足这些特性，已经大幅减少使用。读这本书时，回想那种以触发器为导向的开发方式，感觉特别有意思——因为在我所处的行业圈子里，它们早已失宠。在当今的新开发项目中，还有哪些领域仍然大量依赖触发器吗？

最后一点思考，我觉得逻辑数据模型的可共享性这一概念，在与服务边界结合时特别有意思。我们希望服务拥有自己的数据管理权，但我们仍然需要一个共享的逻辑数据模型来跨服务边界进行推理，这正是我想象中在现代架构中特别适合应用三模式方法的一个场景。
