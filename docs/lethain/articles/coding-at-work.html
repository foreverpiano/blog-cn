工作中的编码（时隔十年后）

2025-11-19 · 阅读原文

自从六个月前加入 Imprint 担任大约 50 人工程团队的 CTO 以来，我已经合并了 104 个 pull request，平均每周略多于四个。其中很多只是非常小的配置和文档调整，而且没有一个是当时最难或最紧急的任务；我更像是一个 pull request 拾荒者，专门寻找那些不会打乱运营团队工作节奏的机会。

尽管如此，这些 pull request 中仍有相当一部分代表了有意义的软件开发工作，而且这 104 个 pull request 比我过去十年工作中完成的总和还要多——Uber 是我上次大量提交 pull request（或者说 Phabricator 当时叫 pull request 的等价物）的地方。从那以后，我主要在管理经理，而不再在工作中亲手编写软件。

这是一次令人着迷的转变，我想写下一些思考：这对软件是否有益，对我自己是否有益，是否有趣，以及我是如何在个人层面适应 的。“优秀工程管理”只是一时风潮

另外，我确实很喜欢 Peter Seibel 的《Coders at Work》（2009 年）。

管理者写代码可疑的投入产出比

我大学主修计算机科学，在成为工程经理之前是一名软件工程师。当我还是基层经理时，我继续编写软件，成为经理后也继续在业余时间做一些小项目。能够在工作中写代码的想法一直对我很有吸引力。

然而，当我成为管理经理的经理后，我停止了在工作中写代码。我想写软件，但它在时间回报上总是感觉不如做其他事情。比如，如果我把时间用来为团队多招聘一名工程师，他们无疑会比我产出更多。同样，如果我花时间改进我们的规划，那会比我自己写一段代码产生更高的影响。最终我陷入了一个陷阱：写软件显然是有价值的，但它总是比其他事情价值更低。我花在写软件上的每一小时，对整体业务来说都是不划算的，也是一种判断力可疑的表现。

但在理解代码库这件事上，情况并非如此。我一直试图——虽然成功程度不一——对所管理的代码库建立一定程度的可行认知。尽管如此，自从离开基层管理岗位后，我从未真正成功地做到超出表面层次的理解。我的经验是，只有亲手写代码才能真正有效地理解 ，而大多数初创公司的软件都是不合理的，因为它们是由不断变化的人员迭代设计出来的，这些人对所建模的领域理解也在不断演进。收回不合理的软件

只需要对代码库有最低限度的理解，再身边围绕着优秀的工程师，你可以向他们提出有价值的问题并得到诚实的回答，就能走得很远。对于大事来说，这通常已经足够，但这也意味着你无法真正参与小问题的讨论，否则就要占用工程师的时间，或者做出判断力较低的决策。

管理者写代码是否有价值，归根结底取决于你是否相信：更快地做出重要决策、减少拉取上下文的中断——以及能够做出大量原本过于昂贵而无法有效做出的小决策——最终能否转化为更有影响力的管理。这不是给别人的宣告，但对我来说，我真的很享受重新回到工作中写代码的状态，很大程度上是因为过去几年里，投入这项工作所需的时间成本已经大幅下降。

寻找写代码的小块时间

当我作为管理者写代码时，最大的具体挑战是找到连续的思考时间块，来理解问题或者实现解决方案。即使是简单的修复，也需要对正在处理的代码库有有效的心理模型。

当你关注工作的长期影响时，这一点就变得不可避免。比如，添加大量测试可能有用，但设计不佳的测试往往会随着时间被丢弃，因为它们与其他现有测试重叠、变得不稳定，或者整体运行缓慢。我认为传统上，很多管理者写代码都落入了这个看似有用但长期价值存疑的范畴。高质量的工作需要足够完整的心理模型，而这对时断时续写代码的人来说太难了。

新一代 AI 工具如 Claude Code 或 OpenAI Codex 非常容易产生低质量的提交，但我的经验是，如果使用得当，它们也能提供几个创造有价值代码贡献的机会。它们擅长：

回答关于代码库的问题，例如“我们在处理认证和授权时最常见的模式是什么？每个模式都有哪些好的例子？”；编写符合现有代码库模式和结构的代码，特别是如果有一个写得好的 AGENTS.md 提供指导；根据一般性反馈修改方案，例如“在代码库中寻找已有的日期计算工具并复用它们”。

最重要的是，这些事情每次都可以在几分钟内完成。在工作中的会议间隙，我通常会切换到几个 Claude Code 会话之一，看看它在某个任务上进展如何，审查代码，并给出下一步建议。

值得承认的是，要做好这件事有一个显著的学习曲线。我在过去一年里花了相当多的时间学习用这种方式写软件，而且每个月都会有新的注意事项需要我去理解。慢慢地，我逐步建立起了两个心理模型：如何用 AI 写软件，以及 Imprint 的代码库是如何运作的。

随着我对两者越来越熟悉，我重新找回了在工作中写代码的能力，因为我可以在其他项目之间的零碎时间里取得进展，再加上每周一两个小时更深入地思考复杂问题的方案。

判断力 / 问题选择

虽然新的 AI 工具让管理者比以往任何时候都更容易在工作中写出有用的软件，但它也让写出无用软件变得前所未有的容易。特别是在高级职位上，很容易写出让你自己感觉有帮助、但实际上对团队毫无帮助、甚至让他们比以前更忙的代码。

我为自己总结的几条有用规则是：

永远不要参与真正时间敏感的事情，除非它是一件我今天就能从头到尾完全解决的受限任务。如果不是这样，我通常会在试图帮忙的同时拖慢进度。优先选择那些团队很难顾及、但长期明显有价值的事情。例如清理技术债、小型用户请求的功能，或者缺失的监控指标。偶尔承担一个公司战略项目——它没有负责人，而我自己有能力完成。一个真实的例子是我们第一个基于 AI 代理的 Interactive Voice Response 系统，它明显有价值，但很难在团队现有工作中排上优先级。在发布自己的软件、监控发布效果、解决它引发的问题等方面，对自己设定比对他人更高的标准。如果我没有时间做这些事情，那我就是在从团队那里偷时间，而不是帮助他们。倾向于在 pull request 中实现他人的反馈，即使我认为它大体上是中性的。因为别人给我反馈的成本很高，所以当他们给出反馈时，我有责任主动去采纳它。

这些规则意味着我没有去做一些我本来想做的事情，但我认为它们很好地帮助我建立了对我们软件的判断力，同时没有妨碍那些承担绝大多数繁重工作的团队。我相信这些规则一定有更好的版本，但总的来说，我猜测忽略它们的管理者差不多已经接近“帮倒忙”的边界了。

你应该在工作中写代码吗？

我相当确信，“管理者是否应该在工作中写代码？”远没有人们想象的那么有趣，一个有意义的答案高度依赖于每个具体情况的细节。然而，对我来说显而易见的是，在工作中写代码的门槛已经比几年前大幅降低了。如果你之前不在工作中写代码，仅仅是因为它会占用太多直接管理团队的时间：那么在你学会新一代工具之后，这些约束已经发生了深刻的变化。

用 AI 代理写软件的学习曲线肯定不是零，但你可以用几美元的 token 和几十个小时，在一些写完就可以丢弃的个人项目上学会它。这感觉像是一笔值得的投资，能让你在自己选择的职业中保持有效。
