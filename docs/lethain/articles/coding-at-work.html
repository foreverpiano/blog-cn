工作中的编程（阔别十年之后）

2025-11-19 · 阅读原文

自从六个月前加入 Imprint 担任一支约 50 名工程师团队的 CTO 以来，我已经合并了 104 个 pull request，平均每周略多于四个。其中很多只是非常小的配置和文档调整，而且没有一个是当时最难或最紧急的任务；我更像是一个 pull request 拾荒者，专门寻找那些不会打乱运营团队节奏的机会。

尽管如此，其中仍有相当一部分是有意义的功能开发任务，而这 104 个 pull request 比我过去十年工作中提交的总数还要多——Uber 是我上次大量提交 pull request（或者当时 Phabricator 称之为 pull request 的等价物）的地方。从那以后，我主要是在管理经理，而不再在工作中亲手写软件。

这是一次有趣的转变，我想写下一些思考：这对软件是否有益，对我自己是否有益，是否令人愉快，以及我是如何适应 的。“优秀的工程管理”不过是一股潮流

另外，我确实很喜欢 Peter Seibel 在 2009 年写的《Coders at Work》。

经理写代码值得吗？

我大学主修计算机科学，在成为工程经理之前一直担任软件工程师。当我还是基层经理时，我继续写软件；即使成为更高层的经理后，我仍然会在业余时间做一些小项目。对我来说，在工作中写软件一直都很有吸引力。

然而，当我成为经理的经理后，我就停止在工作中写软件了。我想写，但总觉得这比做其他事情的回报更低。例如，如果我把时间花在为团队多招一名工程师上，他无疑能完成比我更多的工作。同样，如果我把时间花在改进我们的规划上，其影响也会比我亲自写一段代码大得多。最终我陷入了这样一个困境：写软件显然是有价值的，但总有其他事情价值更高。我花在写软件上的每一小时，对整体业务来说都是不划算的，也是一种判断力可疑的表现。

但理解代码库的情况则不同，我一直试图——尽管成功程度不一——对所管理的代码库保持一定程度的了解。尽管如此，自从我离开一线管理岗位后，我就再也没有真正成功地超越表面层次去理解代码。我的经验是，只有亲自写软件，才能对 建立真正有效的理解，而大多数初创公司的软件都是“不合理的”，因为它们是由一批不断变化的开发者，在对所建模领域的理解不断演变的过程中迭代设计出来的。收回不合理的软件

你可以仅凭对代码库的极少了解，再加上身边一群优秀的工程师——你可以向他们提出有价值的问题并得到诚实的答案——就能走得很远。对于大事来说，这通常就足够了，但这意味着你无法真正参与小问题的讨论，否则就会占用工程师的时间，或者做出低判断力的决策。

经理写代码是否有价值，归根结底在于你是否相信：更快地做出重大决策、减少打断和上下文拉取的次数，并且能够做出大量原本过于昂贵而难以有效完成的小决策——这些是否能转化为更有影响力的管理。这不是给别人的宣言，但对我而言，我非常享受重新开始在工作中写软件，这在很大程度上是因为过去几年里，投入这项工作所需的时间成本已经大幅下降。

寻找写代码的小块时间

我作为经理时写代码面临的最大具体挑战，是找到成块的思考时间来理解问题或实现解决方案。即使是简单的修复，也需要对正在处理的代码库有一个有效的心理模型。

当你关注工作的长期影响时，这一点就变得无法回避。例如，添加大量测试可能有用，但设计糟糕的测试往往会随着时间推移被丢弃，因为它们与其他现有测试重复、容易失败，或者整体运行缓慢。我认为传统上，很多经理写代码都落入了这种“表面上有用、长期价值存疑”的类别。想要高质量地完成工作，就需要一个足够完整的心理模型，而这对那些时断时续写代码的人来说几乎不可能。

新一代 AI 工具（如 Claude Code 或 OpenAI Codex）非常容易产生低质量的提交，但我的经验是，如果使用得当，它们也能为创建有用的代码贡献提供不少机会。它们擅长：

回答关于代码库的问题，例如“我们在处理认证和授权时最常见的模式是什么？每个模式分别有什么好的示例？”；编写符合现有代码库模式和结构的代码，尤其是在有写得好的 AGENTS.md 指导的情况下；根据通用反馈修改方案，例如“在代码库中寻找已有的日期计算工具并复用它们”。

最重要的是，这些事情每次只需要几分钟就能完成。在工作中的会议间隙，我通常会切回到几个 Claude Code 会话中，看看它在某个任务上进展如何，审查代码，然后给出下一步建议。

值得承认的是，要做好这件事存在显著的学习曲线。我在过去一年花了大量时间学习以这种方式写软件，而且每个月都会遇到新的需要理解的注意事项。慢慢地，我逐渐建立起了两个心理模型：如何用 AI 写软件，以及 Imprint 的代码库是如何运作的。

随着我在这两方面越来越熟练，我重新找回了在工作中写软件的能力，因为我可以在其他项目之间的零碎时间里取得进展，再加上每周一两个小时深入思考更复杂的问题。

判断力 / 问题选择

虽然新的 AI 工具让经理比以往任何时候都更容易在工作中写出有用的软件，但也让他们比以往任何时候都更容易写出无用的软件。特别是在高级职位上，很容易写出让自己感觉有帮助、但实际上对团队毫无帮助、甚至让他们比以前更忙的代码。

我为自己总结的几条有用规则是：

绝不参与真正时间敏感的项目，除非它是一个我今天就能从头到尾独立解决的受限任务。如果不是这样，我通常会拖慢进度，尽管我本意是帮忙。优先选择那些团队很难抽空去做、但长期明显有价值的事情。例如技术债清理、用户请求的小功能，或者缺失的监控指标。偶尔接手一个公司战略项目，它没有负责人，而且我能独立完成。一个真实的例子是我们第一个基于 AI Agent 的 Interactive Voice Response 系统，它显然很有价值，但很难在团队现有工作中排上优先级。在发布自己的软件、监控发布情况、修复它造成的问题等方面，我对自己设定的标准要高于对别人的要求。如果我没有时间做这些事，那我就是在从团队那里偷时间，而不是帮助他们。倾向于在 pull request 中实现他人的反馈，即使我觉得那些意见大体上是中性的。因为别人给我反馈的成本很高，所以当他们给出反馈时，我有责任主动去采纳。

这些规则意味着我没有去做一些我本来想做的项目，但我认为它们很好地帮助我建立了对我们软件的判断力，同时没有妨碍到那些承担了绝大部分重活的团队。我相信这些规则还有更好的版本，但总体来说，我猜测那些忽略这些规则的经理，差不多已经接近“帮倒忙”的边缘了。

你应该在工作中写代码吗？

我非常确定，“经理是否应该在工作中写代码？”远没有人们想象的那么有趣，一个有意义的答案取决于每个具体情境的细节。然而，对我来说明确的是，在工作中写软件的门槛比几年前低了很多。如果你之前没有在工作中写代码，仅仅是因为它会从直接管理团队的时间中占用太多：那么在你学会了新一波工具之后，这种限制已经发生了深刻的变化。

用 Agent 写软件的学习曲线肯定不是零，但你只需要花几美元的 token 和几十个小时在一些之后可以扔掉的个人项目上就能学会。这感觉是对自己所选择职业保持有效性的一项值得的投资。
