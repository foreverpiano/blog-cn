如何采用大语言模型（LLMs）？

2024-05-14 · 阅读原文

无论你是产品工程师、产品经理，还是工程高管，你很可能都被推动去考虑使用大型语言模型（Large Language Models，简称 LLMs）来扩展你的产品或优化你的流程。2023-2024 年是 LLM 采用的一个有趣时代，这些能力已进入主流，许多公司担心自己正在落后，尽管大多数集成看起来仍停留在表面。

这一背景让 LLM 采用成为战略案例研究的绝佳主题。本文档是一份工程战略文档，探讨了一家假设的公司——Theoretical Ride Sharing——如何采用 LLMs。

在深入战略之前，先补充一下场景：Theoretical 拥有 2000 名员工，其中 300 人为软件工程师。公司已融资 4 亿美元，年收入 5000 万美元，目前在北美和欧洲的 200 个城市运营。他们是一家网约车公司，类似于 Uber 或 Lyft。不过，他们的创新在于使用更大的车辆——本质上是在重塑公共交通。

这是《Crafting Engineering Strategy》中的一章。

政策

Theoretical Ride Sharing 使用 LLMs 的综合政策如下：

在成熟市场开发一套基于 LLM 的流程，用于重新激活已离职和被暂停的司机。 通过对 进行建模，我们发现缩短新司机入驻时间对活跃司机总数影响很小。因此，我们将重点放在重新激活已离职和被暂停司机的机制上，这是唯一能够显著影响活跃司机数量的机会。每月在 Exec Weekly Meeting 中报告进展，由 #exec-weekly 负责协调。从 Anthropic 开始。我们使用 Anthropic 的模型，可通过我们现有的云供应商 AWS Bedrock 访问。为了避免维护多种实现，且鉴于我们认为底层基础模型的质量差异并不明显，目前我们不打算广泛采用多种 LLMs。这一决策基于我们的 。例外情况将由 #ml-review 中的 Machine Learning Review 审核。 开发者体验团队（DX）必须提供至少一款基于 LLM 的开发者生产力工具。 该工具应能提升使用 TypeScript 编写软件的体验、速度或质量。该工具应帮助我们为明年形成更清晰的判断，从而对是否增加（或减少）投入有坚定信心。该工具应向全体工程师开放。采用一款工具是最低要求，如果 DX 发现其他有趣的工具，例如 Github Copilot，他们有权向 Engineering Exec 团队提出申请并接受评审。评审将重点平衡我们的学习速度、供应商成本和数据安全。我们已 。供应商审批将在 #cto 中进行评审。 内部工具团队（INT）必须提供至少一款支持临时提示的 LLM 工具。 该工具应支持任意非工程类的 LLM 使用场景，例如文本提取、笔记改写等。它必须能在使用客户数据的同时，严格遵守我们现有的数据处理承诺。该工具应向全体员工开放。供应商审批将在 #coo 中进行评审。 六个月后刷新政策。 我们的首要目标是在这个我们内部专业知识有限的陌生领域快速学习，然后再评估是否应该加大投入。将问题和建议标记在 #cto。建模司机入职流程Wardley 地图分析 LLM 生态系统建模 LLM 对开发者体验的影响

诊断

以下是 Theoretical Ride Sharing 在采用 LLMs 时面临的主要挑战总结：

内部至少有三类不同的需求需要我们解决（可分别解决或用同一方案覆盖）： 面向非工程师的生产力工具，例如临时文档改写、文档总结； 面向工程师的生产力工具，例如类似 Github Copilot 的高级自动补全工具； 产品功能扩展，例如司机入驻流程中的高质量文档提取。 在上述需求中，我们认为产品功能扩展有可能形成战略差异化，而另外两类属于工作流优化，能提升生产力，但不一定让我们在行业中脱颖而出。我们看到的一些战略差异化机会包括： 重新激活已离职和被暂停的司机是我们增加活跃司机数量的最大杠杆，这一点已在我们的 中得到验证； 减少人工介入的更快司机入驻虽然不会增加活跃司机数量，但我们看到 LLM 有明确机会降低运营成本，即使不能解决活跃司机的核心问题，这仍可能值得投入； 通过提高响应速度和质量来改善客户支持。 我们目前在公司内部和整个行业中使用 LLMs 的经验和专业知识都十分有限。尽管有大量思想领导力文章与之相反，但真正以规模化、差异化方式使用 LLMs 的公司或产品寥寥无几。目前我们也是如此。 我们希望在不做出不可逆转承诺的前提下发展自身专业能力。我们认为内部专业知识是有效选择问题和利用 LLMs 的限制因素，而培养这一能力将帮助我们在未来迭代决策中变得更有效。反之，我们相信在尚未建立内部专业能力之前就进行重大投入，风险较高且回报较低，因为目前行业内其他玩家似乎也尚未找到显著优势。 在基础模型和基础模型提供商之间切换的成本很低。这在经济上（资金承诺低）和集成成本（各家 API 和使用方式基本一致）上都是如此。 基础模型和提供商正在快速演进，该领域的未来走向尚不明确。目前的基础模型提供商很可能还会再训练一两代使用更大数据集的基础模型，但到某个阶段，继续训练的成本将变得极其高昂（例如 OpenAI 或 Anthropic 的下一个主要版本训练成本可能超过 5 亿美元）。届时差异化可能转向开发者体验。开源模型如 LLaMa 可能在成本上获得显著优势，也可能出现完全不同的情况。未来充满各种可能。我们构建了一张 Wardley 地图来理解 。 针对我们的需求，训练一个基础模型的成本高到无法承受。我们已融资 4 亿美元，而要训练一个能与 Anthropic 或 OpenAI 提供的基础模型相竞争的模型，成本大约在 300 万到 1 亿美元之间。建模司机入职流程Wardley 地图分析 LLM 生态系统

探索

大语言模型（LLMs）构建在基础模型之上。训练这些基础模型极为昂贵，而且随着对更复杂模型的竞争加剧，成本还在不断上升。据称 Meta 训练 LLaMa 2 花费了 2000-3000 万美元，而 LLaMa 1 的训练成本约为 300 万美元。OpenAI 的 GPT-4 据称训练成本达 1 亿美元。在语料质量及其与任务相关性存在一定差异的前提下，较大模型通常优于较小模型，因此除非你拥有大量独特的数据集，否则没有太多动力去训练更小的基础模型。即使有独特数据集，你也可能更适合做微调（fine-tuning）或上下文学习（In-Context Learning，简称 ICL）。

Anthropic 对每百万输入 token 的收费在 0.25 到 15 美元之间，输出 token 略高一些。OpenAI 的收费则在 0.50 到 60 美元之间，输出同样略高。英文平均每个单词约 1.3 个 token，这意味着你可以完成大量 LLM 工作，而花费远低于大多数风投支持的初创公司在零食上的开支。

关于 LLMs 是否已达到性能提升将放缓的阶段，目前存在大量争议。这很像围绕摩尔定律是否已死亡的持久争论，我们不清楚未来 LLM 性能还能提升多少。从训练成本角度看，企业不太可能仅靠增加算力投入就能持续改进基础模型。很少有公司能承受 10 亿美元的训练成本，能承受 100 亿美元的就更少了，很难想象会有公司在建造价值 1000 亿美元的模型。不过，算法改进和对数据集的投资很可能在不显著增加算力成本的情况下推动性能提升。在这个领域唯一能高度确定的预测是：未来 3 年内，模型性能很可能还会再翻一到两次，之后可能继续按此速度提升，也可能在这个性能水平上趋于平稳——两种结果都有可能。

对于某些决策，必须从一开始就做对。例如，从 AWS 迁移到 Azure 成本极高，因为定制化和锁定程度很高。然而，LLMs 似乎不属于这一类别。与行业同行交流后发现，大多数公司都在同时试验来自 Anthropic、OpenAI 以及其他厂商（例如 Mistral）的多种模型。不同模型的行为确实存在差异，但现有模型的行为也会随时间变化（例如据称 GPT-3.5 变得越来越“懒”），这意味着即使只采用一种模型，处理模型差异的开销也难以避免。从技术角度看，模型的供应商锁定程度较低。不过，监管要求——如更新数据处理协议（Data Processing Agreements）——在切换供应商时会带来一定摩擦。

尽管人工智能领域正经历投资热潮，但大多数规模化的科技公司仍在寻找如何将这些能力用于超越 GitHub Copilot 这类明显且普遍实践的用途。例如，Stripe 正在大力投资 LLMs 以提升内部生产力，其中很可能包括让模型完成此前由员工负责的某些内部任务，比如验证公司网站是否与其在入驻申请中提供的信息一致。但目前还不清楚他们是否已经找到一种能显著改变其产品或用户体验的方法。

更具体地看网约车公司，目前似乎也没有出现突破性的行业特定做法。Uber 同样在采用 LLMs 来提升内部生产力，并取得了一些运营效率改进，这些在其 2023 年 8 月发布的关于使用 LLMs 进行内部开发者和运营生产力投入的文章，以及 2024 年 5 月更详细介绍这些努力的文章中均有记录。
