如何投资技术基础设施

2019-05-19 · 阅读原文

我将在 2019 年 6 月 12 日的 Velocity 大会上演讲“Stripe 如何投资技术基础设施”，这篇文章概述了演讲内容。我对这次演讲非常期待，因为它把之前我写过的许多想法统一起来，而这些想法一直都非常实用！这不是演讲的逐字稿，实际演讲会更多地围绕具体案例展开，而不是这个提纲。

我是 Will Larson，今天要和大家聊聊如何投资技术基础设施，特别是 Stripe 在这方面是如何演变的。这些想法代表了我们在组织层面学到的东西，也包括我个人在基础设施工程团队中关于优先级排序和计划执行的经验。

如果一切顺利，你们离开时会带走三到四个实用的工具，用来带领团队、制定计划和确定优先级。

先简单介绍一下我的背景：

我在 Stripe 工作——我们的使命是提升互联网的 GDP——过去三年我一直领导 Foundation 工程团队，负责基础设施、数据以及内部和外部开发者工具。在加入 Stripe 之前，我在 Uber 工作，创立了 SRE 和平台工程团队。就在几周前，我出版了《An Elegant Puzzle》一书，里面涵盖了今天要讨论的几个核心想法。

演讲主题

今天我们将用大约五分钟一个板块的方式，依次讨论以下内容：

引言：自我介绍、什么是基础设施、为什么重要基础：强制工作 vs 自主工作、短期 vs 长期救火：从救火模式中走出来投资：引入产品管理方法原则：全面覆盖所有基础统一方法：用户、基线和时间框架结语：你现在处于什么位置、从哪里开始

好的，我们开始吧！

什么是技术基础设施？

在过去的工作中，我偶尔会遇到一些人，他们把“基础设施”理解为“团队不想做的任何事情”，但这个定义其实非常模糊。我们来给出一个更好的定义。

技术基础设施是指我们用来创建、演化和运营业务的软件和系统。本次演讲中使用的更精确定义是：“被多个团队用于关键工作负载的工具。”

技术基础设施的一些例子包括：

云服务：AWS、Azure、GCP开发者工具：构建系统、编译器、部署工具、编辑器、Git、Github路由与消息传递：Envoy、gRPC、Thrift数据基础设施：Kafka、Hadoop、Airflow、TensorFlow胶水层：Chef、Consul、Puppet、Terraform还有很多其他东西也符合！

如你所见，我们采用的是一个相当宽泛的定义。

为什么基础设施重要？

这类基础设施提供了一个难得的机会，让你能做真正具有杠杆效应的工作。如果你把构建时间缩短五分钟，而每天要执行一百次构建，那就节省了八小时的时间，可以投入到更有价值的事情上。

如果基础设施做得不好，后果同样严重。如果你构建的软件不可靠，用户就无法充分利用你创造的价值。你和同事就会把时间花在缓解和修复故障上，而不是去构建用户真正喜欢的东西。

当然，我的观点受个人经历影响，但我真心相信，每一家成功扩张的公司背后，都有一支优秀的基础设施团队在做非凡的工作。没有强大的基础设施，企业在规模化时不可能成功。

基础概念

在讨论如何投资和演变之前，先建立一套共同的词汇来描述我们需要处理的不同类型工作会很有帮助。每家公司对这些工作都有自己的委婉说法，比如“KTLO”、“研究”、“原型”、“技术债”、“关键”、“最关键”等等。

等我们花几分钟建立这个词汇表后，我们就可以开始讨论 Stripe 基础设施团队这些年来遇到的具体挑战和限制，以及我们是如何适应并克服它们的。

第一个重要区分是强制工作和自主工作。强制工作是必须完成的事，可能由关键发布、决定公司命运的重要用户、安全漏洞、性能下降等驱动。自主工作则开放得多，你可以从整个可能性空间中选择：开发新产品、重构、引入新技术等等。

第二个区分是短期工作和长期工作。短期可能是本周需要给所有服务器打上新的安全补丁。长期可能是构建自动化和工具，把计算实例的 p99 年龄降下来，从而让未来打补丁更快、更安全。

当我们把这两个维度组合起来时，事情就开始变得真正有趣了。

现在我们有了这个矩阵，工作可以落在两个连续谱上。你可能会说其中某些组合不存在，但我确信它们都真实存在，而且都非常常见：

强制、短期——各种形式和规模的紧急事件。强制、长期——为未来必须完成且需要大量投入的工作做准备。在某些文化中承认这类工作可能具有颠覆性，但它是真实存在的，让这类工作可见是合理投资基础设施的核心。自主、短期——通常是小的、由用户反馈驱动的调整，用来提升可用性、针对性的可靠性修复。自主、长期——往往是对现有系统进行代际改进，比如从批处理转向流式计算范式、从单体架构转向服务化（SoA）等等。

你可以把每个项目标在矩阵中的某个位置，也可以把团队整体标进去。要标团队，只要把团队所有项目的向量加总即可。

这引出了一个有趣的问题：你希望自己的团队或组织落在矩阵的哪个区域？

这是很多人最初以为自己想加入的团队。然而，完全缺乏强制和短期工作，通常意味着几乎没有人使用你的软件，或者用户与开发者之间的反馈循环完全不存在。

你经常会在被称为“研究团队”的小组中看到这种情况。

这是另一个常见情况，通常出现在资源相对其职责严重不足的团队，他们从一个火场跳到另一个火场，试图先稳定今天，梦想着在遥远的未来再创新。

没多少人想加入这类团队，但有时离开后又会后悔，因为这类团队有极其清晰的优先级，而且领导层非常认可他们的工作。

我认为团队应该努力处于这个位置。你需要一些强制工作，因为这意味着有人在用你的系统做重要的事情。另一方面，你也需要一些自主工作，以确保自己在持续积累。构建技术杠杆

好的，我们已经有了一个心智模型，现在可以开始讨论 Stripe 在基础设施投资方法上的演变了。

救火模式

基础设施工程的一个重要特点——也常常是它与产品工程的区别——在于必须完成的工作占比很高。最常见的情况是公司反复出现故障，比如 Twitter 的“失败鲸”时代。

我相信 Twitter 大多数人当时都不想去做稳定性工作，但事情已经发展到不可能优先做其他任何事情的地步。

在我们的框架中，这就是一个被强制、短期工作主导的团队，大家给它起了很多名字，其中“救火”是最流行的之一。

关键要点：

尽可能把工作往未来推，减少“强制”工作。当你超负荷时会非常艰难。最重要的问题是：是否有证据表明你在往外走——长期会变得更好——还是在继续落后。要开始脱困，有时需要创新，找到更有杠杆的方法，多几次挑战约束条件，确保自己没有过于死板。目标是找到既能解决当前“强制”工作，又能减少未来“强制”工作的任务。即使是小的胜利也会开始累积成脱困的力量。我的同事 Davin Bogan 说“交付是一种习惯”，我非常认同！与“交付是一种习惯”相关的是：少做一点！当 Uma Chingunde 开始领导 Stripe 的 Compute 工程团队时，她专注于把多个正在进行的尽量合并，包括暂停其中一些。只有完成工作才能产生价值，而不是单纯地在上面花时间。有时候你会发现“强制”工作无法被推后，比如可靠性问题，或者马上要没钱了，需要降低 AWS 账单。如果你无法减少强制工作且还在持续落后，那就必须通过招聘来解决问题。持续招聘，直到看到你在脱困的证据。在脱困之前不要招聘，那样会让你招得过多，而且长时间招聘需要长时间培训，反而会拖慢恢复速度。迁移：解决技术债务唯一可扩展的办法。

演讲中的例子：

集中处理并行迁移，包括 Kubernetes、Envoy、Ubuntu Xenial 等加固和扩展 MongoDB 的模式、客户端和集群，以支持数据、用户和应用的增长用限流器扩展你的 API

投资

一旦团队彻底从救火模式中走出来，你就会面临一个新问题：你什么都可以做！把这称为问题似乎不对，但根据我的经验，大多数基础设施团队在从紧急事件带来的极度清晰焦点，转变为摆脱强制、短期工作暴政后的极其宽广的机会时，都会非常挣扎。

事实上，我认为大多数基础设施团队很少有机会处于长期、自主的工作模式，所以当他们遇到这种情况时往往会踉跄。而这些踉跄又常常把他们重新扔回温暖、充满明确性的救火地狱。

如果你意识到这种转变，就可以有意地管理它，这时候事情才真正变得有趣！你必须非常有意识地去做。

关键要点：

你过去习惯于不用太多努力就有清晰优先级：火情很容易被发现。但现在这套行不通了，你必须非常刻意地决定要做什么以及如何去做。其实，你接下来要做的是开始应用产品管理的基本方法：发现问题、对问题排序、验证你计划的方案。发现。当你有多余的工程产能时，大家通常已经有一长串想做的事情，很多团队会立刻扑上去，但我认为最好先克制这种冲动，退后一步，做一次有意识的发现。撒一张非常大的网，不要过滤掉看起来不好的想法，尽可能多地收集想法。有效的方法包括：用户调研、喝咖啡聊天、用户组讨论、确定 SLA、和同行公司交流、学术和行业研究。如果你没有人在强烈要求你正在尝试构建的东西——如果其他团队没有因为你不能更快交付而感到沮丧——那你很可能在解决错误的问题。排序。你必须给问题排优先级。我喜欢用投资回报率（ROI）作为排序依据，但还有很多其他方法。要理解长期 ROI，你需要两样东西：对用户需求的清晰理解，以及团队长期愿景（大概三年的样子）。如果你在排序时没有让用户声音出现在房间里，那你的优先级就是错的。验证。当你选定了要开始解决的问题后，应该进入一个有意尝试推翻自己方案的阶段。你想先找到最难的问题，然后用最小的投入调整方案。晚发现问题要糟糕得多。这里可用的一些技巧包括：嵌入到用户团队/公司中、构建原型、先解决最难的用户（而不是像有些人那样先做最简单的）、设定清晰的成功指标并经常检查。必须保持团队有足够体量才能持续创新。如果把创新团队搞得太小，或者把人借去干其他事，他们就干不下去。我们判断新团队成功的一个标准是，他们一上来就进入创新模式，而不是救火模式。我们通过来实现这一点。作为推论，如果你没有很好地挑选问题和方案，一家运转良好的公司就会减少你团队的资源。拥有大量自主预算是一种需要挣得且需要维护的机会。考虑在基础设施组织中引入产品经理。不是每个团队一直都需要，但只要有几个能帮助团队完成从救火到创新转变的产品经理，就会非常有帮助。工程团队的规模设定

关于这个话题的一些随机想法：

什么时候使用云服务？当它们已经商品化的时候。公司会追逐收入和利润率，而商品的利润率会被竞争压缩，于是公司会推出差异化的新产品来提升利润率——远离那些，你就会受益！什么时候该自己建数据中心？当你有特殊的服务器工作负载，且容量配比很特别的时候，比如需要大量硬盘。举例来说，Google 允许你设计自己的 SKU，但底层还是真实的服务器。随着公司规模变大，你会被拉到容量规划的细节中。经验法则是自己运维能便宜 30%，但规模经济和竞争很可能正在进一步压缩这个数字。而且这只是直接节省，还没算机会成本——如果你做的业务有价值，这个省略就很重要。“技术迁移”。你经常会看到有人从一家公司跳到另一家，把自己的技术栈也带过去，然后你整个创新预算都被用来做没有清晰目标的改动。最后往往以悲剧收场。

原则

至此，我们已经有了一个帮助团队走出救火模式的清晰框架，也有一个帮助团队成功并保持在创新模式的框架，所以理论上一切都应该很好。

但实际情况往往并非如此。

可能是一个明显但被忽视的可扩展性问题突然爆发。也可能是一家公司不得不放下一切去满足 GDPR 截止日期的要求。在这两种情况下，我发现常常是长期、强制的工作长期缺乏资源，最终变成一波意料之外的短期、强制工作雪崩。

我们采用了一种我称之为“基础设施五原则”的方法，来帮助我们以结构化的方式思考这类问题。

关键要点：

识别一些宽泛的类别，来涵盖你希望基础设施保持的不同属性。对我们的基础设施团队来说，我们一直使用的是：安全性、可靠性、可用性、效率和延迟。对你来说，类别可能会略有不同。对于每一个属性，你都需要定义什么是可接受的表现基线。比如，对于基础设施支出，你可能设定一个目标：每 1000 次交易的成本不能超过某个绝对数字，或者设定收入与基础设施支出之间的固定比例。每次做规划时，都要回顾这些基线以及当前表现相对于基线的变化。然后往前看一到两年：趋势线到那时会怎样？如果你表现还不错，那就很好，继续按照创新导向的方法前进。如果趋势在往错误的方向发展，那就快速头脑风暴一下需要做什么样的工作才能回到好的状态，并粗略估算需要花多少时间。如果需要多个季度才能搞定，而你距离截止时间也只剩几个季度，那么恭喜：你发现了强制、长期的工作！哦，对了，你还必须把它排进优先级并且真正完成它。

统一方法

到目前为止我们已经讲了很多！救火、创新、基线等等。如果你只负责一个团队或较小的组织，那么这些内容可能已经足够指导你的基础设施团队未来一到两年的工作了。

然而，当你要协调一个拥有几十个基础设施团队的组织时，事情就会变得相当复杂——这正是我们去年年底面临的问题。

面临的挑战是，如何把所有这些想法整合起来，为众多不同的团队提供有用的指导，同时还要考虑到有些团队处于创新模式，有些处于救火模式，还有些处于两者之间。

接下来我们要讲的是，Stripe 的 Foundation 工程团队（大约 200 名工程师）如何代表全公司大约 600 名工程师进行规划。

关键要点：

“用户第一”是 Stripe 的经营原则之一，这也是我们规划的起点。依赖你的用户群体中，最优先的前五到十个诉求是什么？我们为每一项基础设施属性（安全性、可靠性等）确定基线，同时观察近期和长期的表现。为了维护这些基线，我们需要做哪些项目和投入？我们会挑选两到三个“关键举措”，这些是大项目，需要 Foundation 组织内很大一部分人共同合作才能取得进展。如果我们只能做几个大项目，哪些是最重要的？我们把这些项目限制在六个月以内，以保持对新信息的灵活反应能力——如果我们执行得好，今天最大的机会六个月后很可能就不是了！我们将时间按以下比例分配：40% 用于用户诉求（直接解决用户现有问题的事项）、30% 用于平台质量（维护基线的工作）、30% 用于关键举措。用户诉求和平台质量的投入由各个团队自行排序，关键举措则由 Foundation 领导层排序。这种划分既保留了团队大部分自主性，也为高层领导提供了一定的预算来做调整。总体来说，效果相当不错！实施中最大的挑战是来自其他团队的计划外工作，经常溢出团队的“用户诉求”预算。不过这个方法还是提供了一些应对工具，通常的表现形式是关键举措的时间线往后推。诚然，这并不那么愉快，但预算足够大，我们可以将延期明确地体现在一个地方，而不是让多个小项目的预算都偷偷延期，从而提高了整体可预测性。这是最终的方法吗？我希望是，但历史告诉我们不是。我很期待看到我们下一步会如何演进这个方法。

结束思考

好的，让我们简单回顾一下今天讨论的内容。

不存在一种能在所有时候都适合你的单一基础设施投资方法。找到有效的方法取决于认清你当前面临的约束，并正确地应对它们。虽然没有人彻底解决这个问题，但已经有很多好的模式可以复用：

如果你的团队正在做强制、短期的工作，那就通过提升运营卓越性来脱困。如果你的团队刚开始体验自主、长期工作的乐趣，那就投入精力提升产品管理能力。如果你有自主预算，却仍然发现自己在不同问题之间疲于奔命，那就找出能平衡方法的原则，并为每个原则设定基线。

和任何一样，这里最难的部分其实是培养对当前情况诚实且有自我觉察的能力。一旦你理解了自己的处境，设计解决方案就只需要深入的思考、严格地研究需求，并持续地调整方向。写作策略与愿景
