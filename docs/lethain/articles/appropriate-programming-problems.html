为编程面试挑选合适的问题

2020-04-19 · 阅读原文

最近有人给我发消息，询问他们内部用于面试 Staff 工程师的流程是否合理。他们特别担心的是，面试中遇到的一些 Staff-plus 工程师在编写查找回文或反转数组的代码时遇到了困难。

程序员圈子里一直流传着一个说法：有些人就是不会编程。2007 年 Imran Ghory 提出了 Fizzbuzz 问题，这个想法很好地捕捉到了这一现象，其中最经典的 Fizzbuzz 题目是：

写一个程序，打印从 1 到 100 的数字。但对于 3 的倍数，打印“Fizz”而不是数字；对于 5 的倍数，打印“Buzz”；对于同时是 3 和 5 倍数的数字，打印“FizzBuzz”。

一个特别简单直接的 Python3 解决方案可能是：

for i in range(100):
    div_3 = i % 3 == 0
    div_5 = i % 5 == 0
    if div_3 and div_5:
        print("Fizzbuzz")
    elif div_5:
        print("Buzz")
    elif div_3:
        print("Fizz")
    else:
       print(str(i))

老实说，我从未愿意给候选人出 Fizzbuzz 这样的问题。最好的情况是它让人觉得敷衍，最坏的情况则是对候选人真正不尊重。我也从未面试过完全写不出这类题目的软件工程师，尽管在职业生涯中，我确实面试过系统管理员等相邻岗位的候选人，他们写不出这样的程序。

在面试 Staff-plus 工程师时，我确实认为有必要验证他们是否仍然能够深思熟虑地创建软件，同时要尽量避免被那些无关紧要的信号所干扰。我工作过的公司很少因为缺乏具备深厚计算机科学或数学能力的人才而受限。这并非因为这些能力不重要，而是因为你通常已经拥有大量这样的人才。在极少数那些技能严重缺失的情况下，我们真正需要的是一位在特定领域（分布式数据库、编译器等）的世界级专家，而不是泛泛之才。

如果你要招聘世界级专家，当然应该针对他们的专长，用定制、具体且有难度的题目深入考察他们。如果这个专长恰好是计算机科学的某个分支，那就针对那个分支严格考核！然而，对于大多数高级工程师，我发现直接考察计算机科学知识并不是特别好的评估方式。更好的做法是寻找真实世界中的问题，这些问题会引入该领域的一些方面，但不会以它们为中心。

几年前，当 时，我们做了大量电话面试。其中我记得的一个题目是：写一个函数，返回每条提及（mention）和 hashtag 的起始和结束位置，以便在网页、移动应用或短信中以不同方式渲染它们。Digg 团队如何被 acquihire（收购人才）

举例来说，你可能会有这样一条推文：

Hey @lethain, did you know about a #typo on page 24 of your book?

对应的输出可能是这样的：

[
  {kind: "mention", name: "lethain", start: 5, end: 7},
  ...
]

我非常喜欢这个问题，因为它是一个真实、诚恳的问题，是你在实际工作中会遇到的。你必须理解问题、理解其目的，然后去解决它。同时还有许多有趣的边界情况值得思考，比如从用户名中排除标点符号等等。

当时我没有太多编写 tokenizer 的经验，所以不太记得自己是怎么做的。但现在我可能会尝试这样来解决：

txt = "Hey @lethain, did you know about a #typo on page 24 of your book?"

WORD = 'word'
MENTION = 'mention'
HASH = 'hash'

HASH_START = '#'
MENTION_START = '@'
WHITESPACE_START = ' '
PUNCTUATION = '!?,;:'


def make_token(kind, txt, start, end):
    return (kind, txt, start, end)


def tokenize(txt):
    tokens = []
    acc = ""
    start = 0
    kind = WORD
    for i, ch in enumerate(txt):
        if ch in WHITESPACE_START or ch in PUNCTUATION:
            if acc:
                token = make_token(kind, acc, start, i)
                tokens.append(token)
            acc = ""
            start = i
            kind = WORD
        elif acc == "" and ch == HASH_START:
            kind = HASH
        elif acc == "" and ch == MENTION_START:
            kind = MENTION
        else:
            acc += ch

    if len(acc) > 0:
            token = make_token(kind, acc, start, len(txt))
                    tokens.append(token)

    return tokens

print(tokenize(txt))

这个问题有很多值得喜欢的地方：它是真实的，问题容易解释，几乎不需要脚手架或样板代码就能开始，也不要求掌握很多库或内置方法。

另一方面，这个问题作为面试题也有一些难点。首先，文本分词是一项相当特定的任务，如果你职业生涯中做过几次，就会比从未做过的人占有明显优势。我第一次遇到这个问题时，从来没有做过文本分词，后来我才积累了一些编写系统库的经验。好的面试不应该测试特定知识，而应该考察问题解决能力。我面试过的工程师中，只有极少数人会在工作中真正去写 tokenizer。即使他们需要复杂的分词功能，我预计他们也会使用像 ANTLR 这样的工具，而不是自己动手写。

我对这个具体问题的另一个顾虑是，它属于那种当所有细节都在你脑中时会相当简单，但一旦出现一个思维失误，所有部分就会瞬间崩塌的问题。我一个人在房间里写这段代码时就已经把自己搞得有点糊涂，很容易想象在有时间限制、有人盯着你的面试中卡住。

在 Calm，我们过去一直依赖一个单一的 staging 环境，所有软件都在一个完整环境中进行测试。但最近团队推出了多个 staging 环境。这是一个重大改进，也引出了一个有趣的问题：我们应该如何为人们分配 staging 环境？

一个足够好的解决方案是为每个团队分配一个 staging 环境，但理论上的理想方案可能是维护一个想要使用环境的队列，然后在环境可用时动态地从池子里分配给他们。

我当时想，这可能是一个有趣的面试问题。它是一个相当真实的问题，不需要太多背景知识就能回答，而且避开了像文本分词那样带来的心理负担或特定领域经验的要求。

POOL = ['a', 'b', 'c', 'd']
ASSIGNMENTS = {key: None for key in POOL}
WAITING = []

def status():
    txt = "Status\n"
    for key in POOL:
        val = ASSIGNMENTS[key]
        val_txt = val if val else ""
        txt += "\t" + key + ": " + val_txt + "\n"
    txt += "\nwaiting: %s" % (WAITING,)
    print(txt)


def queue(name):
    for key, val in ASSIGNMENTS.items():
        if val is None:
            print("UPDATE")
            ASSIGNMENTS[key] = name
            return
    WAITING.append(name)


def pop(name):
    for key, val in ASSIGNMENTS.items():
        if val == name:
            first = None
            if len(WAITING) > 0:
                first = WAITING.pop(0)
            ASSIGNMENTS[key] = first
            return


ops = [
    (queue, "will"),
    (pop, "will"),
    (queue, "will"),
    (queue, "jill"),
    (queue, "bill"),
    (queue, "phil"),
    (queue, "chill"),
    (queue, "quill"),
    (queue, "fill"),
    (pop, "chill"),
    (pop, "bill"),
    (pop, "chill"),
]

status()
for cmd, val in ops:
    cmd(val)
    status()

这类问题的特点是很容易写出一个能跑的版本，然后观察候选人在调试过程中遇到的问题。一旦有人写出初始解决方案，你就可以想象出多种增加复杂度的办法，要求他们重构代码。例如，你可以增加一个使用环境的最长时间限制，超时后自动释放，等等。

好问题的要求

综合以上，我认为适合用来评估高级和 Staff-plus 候选人编程能力的优秀问题应该具备以下特点：

支持简单的初始解决方案和逐步增加的要求；可以用几十行代码解决；需要算法思维，但不需要知道特定算法；不需要在脑中同时 juggling 多个变量；支持调试和演进代码；不依赖特定领域经验来给某些人优势；要求用候选人选择的语言编写实际代码；在真实的代码编辑器中完成。

我相信还有其他重要的标准，但总体来说，上面这些是一个很好的起点。

最后，作为对数学问题的警告，我还清楚地记得年轻时，我认为给有数学背景的候选人出一道比较简单但又不是太简单的 Project Euler 题目是个好主意，结果适得其反——他们立刻给出了闭式方程，而不是写代码来解决。

正如如果你选错问题类型，有些人会觉得你出的题人为地太难，你也会发现另一些人会觉得它们人为地过于简单。选择那些从简单开始、能在面试过程中逐步演变为更复杂问题的通用题目，能让你最大程度地同时兼顾这两类人。
