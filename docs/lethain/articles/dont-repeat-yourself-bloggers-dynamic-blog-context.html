写博客也应避免重复：LifeFlow 中的动态博客上下文

2008-01-09 · 阅读原文

LifeFlow 的设计很大程度上源于三点观察：

Markdown 让写作变得有趣。链接让博客更出色。而写链接很烦人。

基于这些观察，Dynamic Blog Context（简称 DBC）应运而生。

DBC 本质上是一组自动生成的引用，你可以在撰写博客文章时直接使用。你可能经常需要临时引用某个标签、某个项目，或者烦恼于如何找到上一篇博客的链接，又或者记不住某个系列文章第一篇的地址。

动态博客上下文（DBC）致力于让这些事情变得稍微轻松一些。

让我们来看一个例子：

Please take a look [at my articles about Japan][tag japan].

这里的神奇之处（如果算得上神奇的话）在于，你只需这样写就能正常工作，而不必手动写成下面这样：

[tag japan]: /tags/japan/
Please take a look [at my articles about Japan][tag japan].

这是一种令人愉快的便利，它帮助你的文章从具体的 URL 和博客实现细节中解脱出来。使用 DBC 后，即使你重新调整了博客结构，也只需重新保存文章（DBC 是在保存时计算的），它们就会自动更新为新的结构。

还有更多标签正在开发中（它们实现起来相当简单，我正在想办法让用户能够贡献自己的标签，同时又不破坏他们的 SVN checkout。目前你可以通过查看 lifeflow/markup/lifeflowmarkup.py 来添加，相信不久的将来这部分代码会得到清理）——请查看项目页面了解最新详情——下面是目前可用的 DBC 列表。

[tag slug] - 生成指向标签 @slug 的链接 [comment pk] - 生成指向评论 ID 为 @pk 的链接（对任何文章下的评论都有效） [project slug] - 生成指向项目 @slug 的链接 [author] - 如果博客只有一位作者，则生成指向作者传记页面的链接；如果作者数量不是一个，则生成指向 /author/ 页面的链接 [comments] - 生成指向当前文章评论区的链接 [projects] - 生成指向 /projects/ 页面的链接 [series] - 生成指向 /articles/ 页面的链接 [tags] - 生成指向站点标签云的链接

即将推出的其他标签（很可能今晚就能上线）：

[previous] - 指向上一篇文章的链接（仅当前一篇文章存在时有效） [next] - 指向下一篇文章的链接（仅当下一篇文章存在时有效） [series number_of_entry] - 指向当前文章所属的第一个系列中的第 n 篇文章（从 1 开始计数，而非 0）。由于极少有文章同时属于多个系列，这种处理在 99% 的情况下都是合理的 [series slug number_of_entry] - 从 slug 为 @slug 的系列中获取第 n 篇文章 [freq alias] - 允许你为常用链接定义别名，本质上就是给你的链接准备的一个哈希表

毫无疑问，动态博客上下文还可以应用在其他地方，我非常欢迎大家提出建议。如果你有好的想法，请告诉我！

实现原理

（如果你对实现细节感到困惑，建议先阅读这篇关于扩展 Python-Markdown 的文章。如果你对此不感兴趣，可以直接跳到结语部分。）

DBC 的实现相当简单。我为 Python-Markdown 添加了一个新的预处理器，其主要执行函数是 run：

def run (self, lines):
        def clean(match):
            return match[-1]
        text = u"\n".join(lines)
        refs = self.LIFEFLOW_RE.findall(text)
        cleaned = [ clean(x) for x in refs ]
        processed = [ self.process_dynamic(x) for x in cleaned]
        dynamic_refs = [ x for x in processed if x is not None ]
        static_refs = self.build_static_references()
        return static_refs + dynamic_refs + lines

run 函数由 Markdown 库在将 Markdown 渲染为 HTML 之前调用。它接收一个参数（除了常用的 self 之外）：lines。lines 是一个包含所有传递给 Markdown 渲染器的文本行的列表。

整个过程大致如下：

def markdown(self, text):
    lines = text.split(u"\n")
    preprocessor.run(lines)

接下来，我把这些行重新组合成一个大文本块（有点多余，但如果你想遍历这些行就必须这么做），然后扫描文本寻找引用链接。基本上任何看起来像这样的内容：

[this is a description][and this is an id]

一旦找到引用链接，我会检查是否已经处理过这个 id，如果处理过就忽略。否则我会将它的 id 通过几个判断逻辑，检查它是否匹配我已知的任何模式。如果匹配，我就为它创建一个新的引用链接。在处理完所有引用链接后，我会把新创建的引用添加到文本顶部，然后将其传递给后续的预处理器（最终被转化为 HTML）。

你可能注意到我在“我将它的 id 通过几个循环……”这个地方写得有点模糊。我想先解释整体流程，现在再来详细说明这一部分。

DBC 生成的引用有两种类型（有点讽刺）：静态和动态。静态上下文是指那些不会变化的内容，例如 [tags] 这个引用。它永远都会指向 '/tags'（除非博客软件的结构发生改变，那时对应的字符串也需要更新）。静态上下文总是被添加到文本顶部。它不需要访问数据库，多它一个也无妨（在最终 HTML 生成时它就会消失得无影无踪）。

动态上下文的处理方式则不同。这些内容无法用固定不变的字符串表示，必须通过计算得出。其中很多计算需要查询数据库，因此只有当确实存在引用链接指向它们时，才会进行计算（同时也会注意只构建一次引用并缓存起来，以免多次引用造成浪费）。

当前的代码还有点丑陋（嵌套的流程控制一大堆），你可以在 SVN 中查看它的实现。

结语

总的来说，我认为这是一种相当优雅的方式，能让撰写博客文章变得更简单、更快速。它将“Don't Repeat Yourself”的理念带到了博客写作过程中，我认为这是一大胜利。

我喜欢的另一个方面是，它在你的博客与它所引用的 URL 和资源之间提供了一层抽象。也许你经常引用维基百科上关于 Archaic Felines 的页面，结果维基百科的编辑们开了一个闭门会议，把词条改名为 Archaic-but-not-in-a-demeaning-sense-Felines。这时你只需要在常用链接列表中修改一次，而不用在所有文章中逐一修改（还容易忘记）。

同理，如果某个健忘的实现者（比如我）把标签页的地址从 /tags/ 改到了 /important-stuff/tags/，动态博客上下文能让这次改动变得完全透明。

我很乐意听到任何想法（看来在 IE 7 中发表评论已经可以正常工作了——甚至可能是 IE 6？——虽然这不是我故意实现的）。

更新：1月13日

过去几天，这个系统得到了大幅度的优化和改进。最大的变化是它现在基于 Python-Markdown 的 SVN 最新版本，而不是之前相当老旧的 0.9 版本。这意味着之前存在的许多问题在一夜之间消失了。不过，我也发现新的 Python-Markdown 对我正在做的这种动态扩展支持度稍差（至少在集成方面如此，不过底层代码主体基本保持一致）。

同时也新增了一些上下文实现。

[previous] - 上一篇文章 [next] - 下一篇文章 [series nth] - 系列中的第 @nth 篇文章 [series slug nth] - slug 为 @slug 的系列中的第 @nth 篇文章 [file name] - 名称为 @name 的文件（图片或其他文件） [f name] - file 的快捷写法
