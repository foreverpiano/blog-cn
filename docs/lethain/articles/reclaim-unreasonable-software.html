收回不合理的软件

2019-07-28 · 阅读原文

《大泥球》（Big Ball of Mud）发表至今已二十年，其观点在今天依然成立：在成功且处于增长阶段的公司中，最普遍的架构其实是“无架构”。清晰的模式逐渐被快速修复带来的混乱触手所覆盖，而Accelerate 对开发者生产力的定义则逐渐趋近于零。

在生产力长期为零之后，许多公司会转向“大迁移”模式，彻底重写他们的软件。这些重写项目极具挑战性，而且常常以失败告终。

我曾在你无法对一大团乱泥进行推理。一文中提到另一种路径：停止尝试对软件进行推理，而是转向通过实证实验来指导软件变更。实验方法能带来比重写更一致的结果，但缺点是速度非常慢。

在这篇文章中，我将尝试勾勒第三条路径：通过已验证的行为（verified behaviors）和已断言的属性（asserted properties）来收回不合理的软件。这种方法既是实验和重写之外的替代方案，也是一套维护合理软件的通用框架。

优秀的 Jessica Kerr 也写过《让我们一起思考行为》（Let’s reason about behavior），探讨了这些想法。

黄金时代与末日

有些软件从未成功解决它所期望处理的领域问题，好消息是，你至少不需要维护这样的软件——因为维护是留给有价值的东西的。

如果你的软件确实成功地解决了问题领域，它就变成了“黄金时代软件”。黄金时代软件是处于最佳环境中的最佳软件。维护它的团队正是当初设计它的团队，对其所有 quirks 都了如指掌。它解决的问题大多是它被设计来解决的问题，也在它被设计所满足的约束之内。

在某个时刻，你会发现一个特别优雅的扩展，能让你解决一个不在原始设计之内的重要新问题。这个方案会被称赞为软件灵活性的证明，但事后你会意识到，这正是黄金时代终结的开端：那个优雅的解决方案其实预示着人们越来越无法对软件进行推理。

时间会滋生复杂性，也会让软件腐化。团队同样会腐化，人们会转去其他项目或公司。总有一天你抬起头，会发现自己正在维护“后末日软件”（Post-Apocalyptic software），它的演化过程已成为“失落的技术”，操作或扩展都令人心惊。你有一本咒语书，似乎能让它继续运转，但没有人敢放心地做出有意义的修改。

重写还是收回

那位名叫“商业价值”的抽象神祇并不关心你的软件是否易于推理，但它非常关心你能否发布新功能，以及能否稳定地运行软件以留住用户。到了某个阶段，速度放缓会成为规划和战略会议上的讨论主题，而所有人都会反复提到同一个观点：现状已经行不通了。

这时，许多公司（或许是大多数公司）会选择重写软件。把它标记为失败事业，设计一个替代方案，并制定周密的迁移：解决技术债务唯一可扩展的办法。来降低风险。（有时也会引入新的风险，例如从单体架构转向开发面向服务的架构。）

然而，我越来越确信重写并非不可避免。你可以有意识地通过将信念演化成行为和属性，来收回已经进入后末日阶段的软件。

信念与属性

后末日软件之所以难以修改，是因为它的行为不可预测，你拥有的只是关于它如何工作的“信念”。以下是一些你可能对软件持有的信念：

所有由 HTTP 请求引起的状态变更都是原子写入的。进程总是先尝试从 Redis 读取状态，再从 MySQL 读取。在写之后进行的读只有在主库上才是安全的，在从库上则不安全，除非当前时间已超过写入时间加上当前的复制延迟。进程没有状态，因此无论哪个进程处理请求，结果都正确。

基于信念来编写软件是非常困难的，因为信念常常是错的，所以你不得不一步步通过实验来验证你的方案。或者说，不断失败其实是一种非常缓慢、无指导意义的实证验证形式。

我们通过将每个信念转化为“行为”或“属性”，让不合理的软件重新变得合理。行为是可以针对实际环境进行经验验证的软件特性；属性则是可以通过静态分析或本地执行来验证的软件特性。

两者的区分有些微妙，你可能会发现某个公司的行为是另一个公司的属性，反之亦然。下面通过例子来探讨这种区别：

“每个文件至少有一个测试”是你可以在构建服务器上强制执行的属性。“99.99% 的请求在两秒内完成”是你可以在生产环境中监控的行为。“每个执行分支都被测试覆盖”是一个属性，因为可以通过在主机或构建主机上运行覆盖率测试来验证，它不需要特定的运行环境。“所有写后读操作都在主数据库上执行”——大多数公司会通过（a）记录日志并验证日志中的行为，或（b）实时断言在错误的写后读行为时报错——这两种方式都把它归为行为。“每个请求的状态变更都在单个事务中处理”——你可以通过强迫所有变更进入一个具有合适语义的受限接口来静态验证，这就让它成为一个属性。当然，有些公司可能不愿意对行为施加如此强的约束，而是选择监控每个请求的事务数，那它就变成了行为。

让我们进一步完善这个分类体系。对于行为，有三个值得关注的梯度：

被观察的行为（Observed behaviors）是你能在日志、指标或仪表盘中注意到的行为。被跟踪的行为（Tracked behaviors）是当它们发生变化时你会收到通知的行为，但只有在更新后的软件在环境中运行之后才会触发，例如一条告警告诉你生产环境的延迟上升了。已验证的行为（Verified behaviors）是你可以确信始终为真的行为，因为存在一个及时的机制在部署完成前确保它们。最常见的三种确保行为的机制是：（a）端到端集成测试，（b）常规触发相关失败模式的故障注入，（c）在完成部署前验证软件的负载或性能测试。

虽然确认已验证的行为有些烦人（因为它们需要一次尝试部署），但围绕它们进行设计却很容易，因为你可以确信它们会保持为真。被跟踪的行为很有趣，因为理论上它们应该很容易围绕其进行设计（毕竟它们是被跟踪的！），但如果没有一个来确保团队修复回归，它们往往会随时间退化。大多数公司并没有为所有相关行为设立这样的项目，因此在实践中，围绕被跟踪的行为进行设计相当困难，每次架构变更之前，都需要先花一段时间修复被跟踪行为的回归，才能进行预期的改动。项目：掌控不可控之事

类似的梯度也适用于属性：

期望的属性（Intended properties）是你要求团队在软件中维护的内容，通常通过设计评审、培训、最佳实践文档等方式传达。被跟踪的属性（Tracked properties）是会被报告但没有强制执行机制的属性。对许多公司来说，代码覆盖率就属于这一类——他们会报告变化，但不会阻塞部署。已断言的属性（Asserted properties）是在部署开始前就被强制执行的属性，通常通过静态分析、代码 linter 或单元测试实现。

我觉得属性特别有趣的一点是：在最坏的情况下，它们会产生误导和伤害——谁没经历过有人抱怨某个团队没有遵守一个未写明但被期望的属性呢？而在最好的情况下，它们是最容易围绕其进行设计的，也能带来远超其他方式的开发体验。

已断言的属性相比行为（即使是已验证的最好行为）在生产力上的优势，在比较大型代码库在动态类型和静态类型编程语言中的生产力时最为明显。静态类型语言能在几类错误上提供即时反馈，而这些错误在动态语言中通常需要完整的部署周期才能发现。

绝大多数公司目前都没有任何已验证的行为，几乎也没有已断言的属性，但这并不是因为这件事特别困难，而仅仅是因为他们从未意识到，让软件变得可以被推理有多么强大。

相反，大多数能够长期保持执行速度的公司，都拥有数量可观的已验证行为或已断言属性，而且通常两者都有。每家公司只被允许重写一次，之后你就必须学会如何收回自己的软件。

软件收回

回到你的后末日软件：如何重新获得做出修改的信心？把所有你需要确信才能放心修改软件的信念都列出来，然后为每个信念找到一种将其在信念-属性阶梯上向上演化的方法。

最好的结果是将信念演化成已断言的属性，其次是已验证的行为。但将它们提升到被跟踪的行为或属性也能带来惊人的价值，因为这能帮助你了解在重新开始对软件进行推理之前，需要投入多少工作。

如果最终的评分足够低，你就会知道收回软件比重写更容易。如果评分足够高，那么重写可能确实更简单。

这里提出的方法不仅适用于收回软件，它也是一种从一开始就防止软件在可推理性上退化的有效机制。预防永远是最好的解决办法。
