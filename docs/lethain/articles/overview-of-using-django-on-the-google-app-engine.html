在 Google App Engine 上使用 Django 的概述

2008-06-17 · 阅读原文

使用 Google App Engine 开发 Django 时，最令人惊讶的是那些简单的事情有多么相似。在 App Engine 上，一个简洁的首页视图可能看起来像这样：

from snippet.models import Snippet
def index(request):
    recent = Snippet.all().order("-entry_time")[:5]
    return render_to_response(
        'snippets/index.html',
        {'recent':recent},
        RequestContext(request, {}))

将其翻译成普通的 Django 视图只需要改动一处：Snippets.all().order("-entry_time')[:5] 变成 Snippets.all().order_by('-entry_time')[:5]。这就是 Google App Engine 令人安心的一面：在大多数情况下，熟悉 Django 的人可以直接开始编码，只是偶尔需要翻看文档。然而，这并没有讲出全部故事。幸运的是，我现在很有讲故事的心情，所以我们会深入探讨，而不仅仅停留在表面上的“就是他妈的一回事”这个角度。

实际上，要真正讲清楚这里的差异，需要讲两个故事：第一个是关于 Google App Engine 平台的简短故事，第二个则是更长的关于在 Google App Engine 上使用 Django 的故事。

Google App Engine 平台

这个平台才是 App Engine 的真正吸引力所在。因为 Google 让开发和部署应用变得极其简单。如果 Google App Engine 提供的只是免费的世界级独立服务器访问权限，我认为它对开发者的吸引力远不如现在这个版本。

轻松部署

简而言之，这个平台为你处理了部署的所有麻烦事（我的 PostgreSQL 用户名是什么来着，我把表命名为啥了，还有为什么 SSH 突然不接受我的密钥自动登录了？）。部署过程之简单令人难以置信。你只需填写一个简单的 YAML 文件，然后在命令行运行一条简单的命令。或者，你可以使用更简单的图形界面来完成部署。上传和同步可能需要一两分钟，但你实际参与的时间只有五秒钟，而且完全不费力气。

BigTable

GAE 不仅让你免于大部分部署的困难，还让你免于处理扩展的许多细节。你不需要设置服务器或对数据库进行分片，而是只需向 Google 支付更多费用。或者说，至少这是使用 BigTable 而非关系型数据库集群的理想场景。扩展最终能表现如何还有待观察，成功扩展的关键（或者至少是失败的关键）仍然牢牢掌握在开发者和他们的应用设计选择手中。

一旦多个 GAE 应用取得成功并对平台提出更高要求，这将是一个值得关注的领域。另外——顺便一提——确实存在一个空白领域，迫切需要一些很棒的教程来讲解如何为 BigTable 设计模型。

Google 账号与邮件

另一个好处，虽然从长远来看可能没那么重要，就是能够与 Google 账号集成，并通过 Google 的邮件服务器发送邮件。对于面向技术用户的应用，前者是一个很棒的功能，因为那个群体中的大多数人已经拥有 Google 账号。 在不太懂技术的用户群体中，我猜测 Google 账号的普及率要低得多，但它仍然是一个有用的选项。

使用 Google 服务器发送邮件也是一个不错的小福利，对于许多 Web 应用来说这几乎是必不可少的，如果 GAE 没有这个能力，使用它会变得相当困难。除了说一句“我很高兴不用自己配置 Postfix”之外，在这方面没什么更多可说的了。

现在我们已经简单了解了 Google App Engine 平台，接下来让我们继续看看在 Google App Engine 上部署 Django 的喜悦与苦恼。

在 Google App Engine 上使用 Django

上一段开头就说平台才是 App Engine 的真正吸引力，但不可避免的是，其恩赐的源头同时也是不便和挫折的源头。Django 和 GAE 并不是糟糕的搭档，但 GAE 有时确实有抢被子的倾向。

框架越大，其灵活性就越低。人们经常带着沮丧的表情抱怨 Ruby on Rails，说“当你按照它希望的方式去做时，它确实工作得很好。”Django 很大程度上避免了这个命运，因为它的设计目标是拥有可互换的组件（使用你自己的模板系统、使用你自己的 ORM 等），但它并非完全不受底层问题的影响：标准化让重复变得容易，却让适配变得困难。

尽管只使用 Django 的子集是可行的，但这样做会让你之前在那些被替换部分上的经验失效。因此，从其他地方转到 GAE 的 Django 开发者必须调整自己的眼光来理解新环境，即使这里面大多是熟悉的景象。

模型与 BigTable

对 Django 开发者来说最大的变化是模型框架：Django 的 ORM 被 Google 设计的方案所取代。这是一个必要的改变，因为模型不再存在于关系型数据库中，而是存在于 BigTable 中，但这也是尝试将应用从 Django@Elsewhere 移植到 Django@GoogleAppEngine 时遇到最多阻力的地方。

举个例子，让我们看看我在 GAE 上那个简单的语法高亮应用中所使用的 Snippet 模型的一部分。

from appengine_django.models import BaseModel
from google.appengine.ext import db
CHOICES = ('Scheme','Python','Ruby') # etc, etc
class Snippet(BaseModel):
    title = db.StringProperty(required=True)
    highlighter = db.StringProperty(required=True, default='Python',choices=CHOICES)
    content = db.TextProperty(required=True)
    url_hash = db.StringProperty()
    parent_hash = db.StringProperty()

我没有存储指向父 Snippet 的直接链接，而是存储了父级的哈希值。这意味着我可以在不进行额外查询的情况下构建指向父 Snippet 的链接。但我如何获取父级的标题呢？一种做法是这样的：

from django.shortcuts import render_to_response
from models import Snippet
def view_snip(request, hash):
    snip = Snippet.all().filter("url_hash =", hash)
    parent = Snippet.all().filter("url_hash =", snip.parrent_hash)
    return render_to_response(
        'snippets/snippet_detail.html',
        {'object':snip,'parent_title':parent.title},
        RequestContext(request, {}))

但这种做法是关系型数据库的做法，而既然我们使用的是 BigTable，这就被认为是错误的方式。相反，我们通过预先将父级的名称存储在子项中来“获取”它。因此我们会将模型改成这样：

class Snippet(BaseModel):
    title = db.StringProperty(required=True)
    highlighter = db.StringProperty(required=True, default='Python',choices=CHOICES)
    content = db.TextProperty(required=True)
    url_hash = db.StringProperty()
    parent_hash = db.StringProperty()
    parent_title = db.StringProperty()

并且我们只会在创建 Snippet 的时候进行一次必要的获取操作。

# assuming parent_hash variable exists in environment
new_snip = form.save(commit=False)
parent = Snippet.all().filter("url_hash =", parent_hash)
snip.parent_hash = parent_hash
snip.parent_title = parent.title

对于习惯了关系型数据库的人来说，这感觉有点别扭——我是说搞什么鬼，为什么要把数据缓存在模型本身里？——但这就是最佳利用 BigTable 的方式：通过复制数据来避免额外的查找。对于那些变化非常频繁的数据，可能需要频繁获取（这时你就会开始使用另一种缓存：memcached），但通常简单的数据冗余就足以大幅减少实际执行的查询数量。

当然，这种数据冗余也带来了一定的代价。例如，如果你修改了一个 Snippet 的标题怎么办？嗯，你必须修改 Snippet 本身的标题，以及其每个子 Snippet 的标题。代码可能看起来像这样：

def update_title(hash, title):
    parent = Snippet.all().filter("url_hash =", hash)
    parent.title = title
    parent.put()
    for snip in Snippet.all().filter("parent_hash =", hash):
        snip.parent_title = title
        snip.put()

公平地说，这相当丑陋。这种数据重复的成本和收益将完全取决于你的数据被重复的程度（如果平均每个 Snippet 没有子项，那么它就没有性能成本，虽然编写额外代码会有程序员成本），以及你进行修改的频率（如果一个 Snippet 无法修改标题，那么所有这些不便就突然变得无关紧要了）。

我认为这里最重要的一点是要记住，要有效使用 BigTable，需要采用不同的缓存和设计模式。这是使用 Django on Google App Engine 带来的最非表面化的差异之一，在设计要在 GAE 上运行的应用时需要仔细考虑。

Django.contrib.* 与中间件

在 Google App Engine 上无法使用的另一大块 Django 功能是许多中间件和 django.contrib 应用。特别是认证和会话框架会让人怀念。正如人们所预料的，Google 提供了可用的——在某些方面或许更有用的——替代品，但这又是 Django 中另一个被替换、需要重新学习的部分。

与 BigTable 和关系型数据库之间的不匹配不同，这里的差异是细节层面的而非概念层面的。移植后的应用需要重写一些代码块，但应用本身——在大多数情况下——不需要重新设计。

Django Helper 项目

有很多链接和模糊但乐观的赞誉指向 Django Helper 项目，该项目旨在抽象掉 Django@Elsewhere 和 Django@GAE 之间的差异。最终，我认为这是一个有点误入歧途——虽然出发点良好，有时也有帮助——的努力。问题在于，在两个不同事物之上创建抽象层会导致两者的最小公共子集。想象一下试图创建一个库来抽象你是使用 Git 还是 Mercurial 作为仓库：你会失去两者的独特功能，最终得到的东西比单独使用任何一个都缺乏吸引力。

我的经验是，这个 helper 在很多方面并没有像宣传的那样工作，更合理的做法是尽可能使用 Django 的功能，然后用 Google 的框架组件来补充 Django，而不是把两者的第三种混合物倒进 koolaid 里。

结束思考

说真的，我在 Google App Engine 上的开发体验非常积极，我期待着完善我现有的项目，也期待在上面尝试新的项目。它消除了部署 Web 应用的痛苦，这通常是推出新项目最困难——或者至少是最烧钱——的部分。在 App Engine 出现之前，对于预算有限的项目（大部分是小型个人项目），我有两种选择：

把它放在 VPS 上，每月多付 20 到 40 美元；或者把它放在共享主机上，接受经常很糟糕的性能。

现在，Google App Engine 给了我第三种选择，它兼具前两者的多数优点，为此我很感激。是否需要进一步降低 Web 应用的门槛，这是留给另一天的讨论，但 GAE 无疑是一个令人兴奋的实验，值得观察和参与。

如果你已经尝试过用 GAE 开发，你的印象如何？你认为它会成为 Web 应用的可行平台吗？

我的一位学生最近做了一个演讲，标题是「世界のみんなは同じだ」或者说《世界上的人都是一样的》。这是一个令人愉快的想法，通常是在被缺乏细节或过多细节所麻痹之间得出的，但它似乎并不特别真实。同样，Django on Google App Engine（DOGAE？）和 Django in Other Places（DIOP？）之间的区别也是如此：它可能看起来一样，但其实不是。↩这也正是 Google App Engine 真正瞄准的目标人群：缺少资金、意愿或技术能力来处理其 Web 应用部署和扩展的小型开发团队。↩好吧，除了那些已经认定 Google 正在变成一个要避开的可怕生物的人。我很确定那些人无论如何都不会乐于使用 Google App Engine 应用……↩
