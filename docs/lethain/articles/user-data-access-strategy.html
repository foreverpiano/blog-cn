如何控制用户数据的访问权限？

2025-02-07 · 阅读原文

在初创公司发展的某个阶段，他们会决定需要在18个月内为上市做好准备，随之而来的是大量IPO准备工作迅速启动。 本策略聚焦于一家正为IPO做准备的公司，该公司发现自己在管理用户数据访问的内部控制上存在差距。 这是一家希望实质性提升用户数据访问安全态势的公司，但过去几年里，其多项安全举措都以失败告终。

这些举措大多失败，是因为它们严重影响了客服等团队的内部工作流程，导致初期进展逐渐被推翻和规避，最终难以产生长期效果。 本策略代表首席信息安全官（CISO）在履行IPO准备义务的同时，试图承认并克服这些历史挑战——最重要的是，真正为用户做好事。

这是《Crafting Engineering Strategy》中的一章。

政策与操作

我们的新政策及其运行机制如下：

在IPO前，必须大幅强化用户数据访问控制。 高层领导、法律、合规和安全团队一致认为，我们无法以当前的用户数据访问控制现状接受作为一家上市公司。 我们必须在IPO准备工作中，实质性提升资源级访问控制的质量（例如，如何确定用户有权访问哪些行，而非哪些表）。 我们的安全团队对解决这一风险的具体机制和方法负责。 我们将继续优先采用资源访问控制的混合解决方案。这是我们迄今为止的做法，也是目前最快的可选路径。 向用户直接开放资源级访问日志。 我们将构建一个用户可访问的公司所有用户数据访问日志，并确保我们能够解释每一次访问。 此外，这意味着每次访问的理由都必须从用户视角来看是可理解且合理的。 这一点很重要，因为它将我们的做法与用户的视角对齐。 用户将能够评估我们如何访问他们的数据，并根据是否认同我们的使用方式来决定是否继续使用我们的产品。 良好的安全讨论不会将决策描述为安全与可用性之间的妥协。 我们将采用有价值的权衡是多维度的。，同时提升安全性和效率。 每当我们将讨论框定为安全与效用之间的权衡时，这就表明我们在进行错误的讨论，应该重新思考我们的方法。 我们将优先采用既能自动授权、又能记录客户数据访问理由的机制。最明显的例子是，自动授予客服人员对其负责的、存在未结支持工单的用户数据的访问权限（并在工单被重新分配或解决后移除该权限）。 以“有用户可理解的自动化理由支撑的客户数据访问请求”的百分比来衡量进展。 这将把我们的工作锚定在同时提升用户数据安全性和同事内部工具可用性上。 如果我们仅增加访问客户数据的要求，我们不会将其视为进展，因为它不是自动化的（因此很可能鼓励大家绕过规则来快速解决问题）。 同样，如果我们只提升可用性，图表也不会将其显示为进展，因为我们没有增加被支持的请求数量。 作为这项工作的一部分，我们将创建一个私有频道，让安全和合规团队能够看到所有手动访问用户数据的理由，并将通知那些反复使用手动理由访问用户数据的人员的经理。 使未使用角色过期，以推进最小权限原则。 目前我们的基于角色的访问控制（RBAC）系统中，有不少角色被授予给了并未使用这些权限的用户。 为解决这个问题，我们将在用户90天未使用某角色权限后，自动移除该角色。 处于活跃值班轮换中的工程师是这一自动权限清理的例外。 在看到进展前每周进行审查；之后永久保持每月访问审查。 从现在开始，安全工程团队、负责客户数据访问项目的团队以及CISO之间将每周进行同步会议。该会议将聚焦于快速迭代和解决问题。 这明确是一个持续进行策略测试：避免瀑布式策略陷阱，通过迭代优化。的论坛，由CISO担任会议发起人，其首席安全工程师担任会议引导者。 会议将持续进行，直到我们明确如何实现100%使用用户可理解的自动化理由来访问客户数据。 另外，我们还将启动每月对抽样的客户数据访问进行审查，以确保我们构建的理由创建机制得到正确使用和运行。 该会议的目标是审查访问理由的质量和适当性，短期内通过抽样审查理由，长期则找出更多自动化机制来识别高风险访问进行审查。 任何例外必须由CISO书面批准。 虽然我们总体工程策略指出我们遵循《Facilitating Software Architecture》中描述的顾问式架构流程，但客户数据访问政策属于例外，必须由CISO明确批准并记录在案。请在#ciso频道启动该流程。

诊断

我们已经具备了稳固的基于角色的访问控制（RBAC）和审计日志基础。 然而，我们在确保已分配角色遵循最小权限原则方面的机制有限。 这一点在员工更换团队或角色时尤为突出：有些人在公司工作五年以上，积累了大量未使用的角色。 同样，我们的审计日志虽然持久且覆盖全面，但我们缺乏主动识别异常使用的机制。通常只在通过其他方式发现事件后，才用它们来追溯发生了什么。 对于资源级访问控制，我们依赖第三方平台处理传入的用户请求与我们自己产品内的审批机制相结合的混合方式。 在这两个系统间提供访问理由需要人工操作，而这些理由后续会以批量方式进行人工适当性审查。 我们当前资源级访问控制方法存在两个主要持续问题。 首先，提出请求的团队将其视为一种繁重的义务，对自己或用户都没有太大好处。 其次，由于理由审查步骤是手动的，因此无法验证审查的质量。 我们没有发现用户数据被滥用的证据。 当同事访问用户数据时，我们始终一致地发现存在清晰且合理的访问理由。例如，用户支持系统中用户提出的问题工单。 然而，我们记录的理由质量一直较低，因为这依赖于忙碌的人一天多次手动复制大量信息。 由于理由质量低，对这些理由的验证也带有一定任意性。 从字面合规角度看，我们确实提供了理由并对其进行了审计，但很难说大多数审计是否真正提升了用户数据的安全性。 历史上，我们进行过大量安全投入，曾暂时提升安全态势。 但一年后再看这些举措，很多情况下我们会看到严格审查后逐渐被废止或规避新机制的模式。 我们发现其中大部分都增加了其他内部团队必要工作的摩擦。在完成工作的自然秩序中，这些团队会悄然削弱这些改进，因为它妨碍了他们的即时目标（例如支持客户请求）。 因此，根据我们的过往记录，我们高度确信历史方法可以在内部制造表面上的胜利，但对于能否在没有重大、不太可能的内部变化（例如同事明年明显比现在清闲）的情况下带来长期改善，我们信心有限。 看来我们需要一种新方法来真正改变对此类问题的立场。

探索

我们的经验是，管理内部用户数据访问的最佳实践探索策略。，其他情况下则很难找到。确切原因难以确定，但可能是因为这个话题大家普遍不愿公开讨论，以免未来产生责任和合规问题。

在探索过程中，我们发现了两个标准化的维度（基于角色的访问控制、审计日志）和一个高度差异化的维度（资源特定访问控制）：

基于角色的访问控制（RBAC）目前已是一种高度标准化的方法。 其核心前提是将用户映射到一个或多个角色，每个角色被授予一组特定权限。例如，代表客服人员的角色可能被授予停用账号的权限，而代表销售工程师的角色则可能被允许配置新账号。 审计日志同样已经标准化。所有资源的访问和变更都应在持久日志中关联到执行操作的人员。这些日志应被汇集到一个集中、可查询的系统中。 核心挑战之一在于如何主动利用这些日志来发现问题，而不是在问题已被其他机制标记后被动响应。 资源级访问控制的标准化程度远低于RBAC或审计日志。我们发现公司采用了三种截然不同的模式，且不同公司在采用哪种模式上缺乏一致性。

这三种资源级访问控制模式分别是：

第三方丰富化：在第三方系统（如Zendesk）中管理对资源的访问。 这需要用产品中这些对象所在系统的数据和元数据来丰富第三方系统中的对象。 同时还需要在该平台上实现操作（如归档或配置），让它们完全生活在该平台的权限结构中。 这种方法的缺点是与平台供应商紧密耦合、受限于该平台固有的任何限制，以及需要维护同时熟悉内部技术栈和平台供应商技术栈的工程团队。 第一方工具实现：包括用户问题创建和管理在内的所有活动都在核心产品内部进行管理。这种模式在早期公司或客服领导“在组织内成长起来”、未过多接触同行公司做法的公司中最常见。 这种方法的优势在于存在一个单一、紧密集成且可无限扩展的平台来管理交互。 缺点则是你必须在内部构建和维护所有这些工作，而不是将其推给本应能在工具上投入更多的供应商。 混合解决方案：使用第三方平台处理大部分操作，同时用它来控制第一方系统内的资源级访问。 例如，只有当用户在第三方平台创建了未结工单并分配给你时，你才能访问该用户的数据。 这种方法的优势在于能支持不符合平台限制的复杂工作流，同时避免产品与供应商平台之间产生复杂的耦合。

总体而言，我们的经验是所有公司都会实施RBAC、审计日志，以及某种资源级访问控制机制。 大多数公司要么采用第三方丰富化模式，并配备一个规模可观、长期存在的团队负责平台实施；要么依赖混合解决方案，从而能够避免设立长期专职团队，而是将相关工作分散到现有团队中。
