我们应该如何控制用户数据的访问权限？

2025-02-07 · 阅读原文

在初创公司发展的某个阶段，他们会决定需要在18个月内做好上市准备，于是大量IPO readiness（首次公开募股准备）工作便随之启动。 本策略针对一家正为IPO做准备的公司，该公司发现自己在管理用户数据访问的内部控制上存在差距。 这是一家希望切实提升用户数据访问安全态势的公司，但过去几年中曾有过多次安全举措失败的经历。

过去那些举措大多失败，是因为它们严重影响了客服等团队的内部工作流程，导致最初的改进随着时间推移被逐步撤销和规避，最终几乎没有产生长期效果。 本策略是首席信息安全官（CISO）在履行IPO准备义务的同时，承认并克服这些历史挑战的尝试——最重要的是，要真正为用户负责。

这是《Crafting Engineering Strategy》中的一章。

策略与操作机制

我们新的策略及其执行机制如下：

在IPO前，必须大幅强化用户数据访问控制。 高层领导、法律、合规和安全团队一致认为，我们无法以当前的用户数据访问控制现状作为上市公司。 作为IPO准备工作的一部分，我们必须显著提升资源级别访问控制的质量（例如，如何确定用户有权访问哪些具体行记录，而非仅限于表格）。 我们的安全团队对解决此风险的具体机制和方法承担责任。 我们将继续优先采用混合方案来实现资源访问控制。这是我们迄今为止的做法，也是目前最快的可选路径。 向用户直接开放资源级别访问日志。 我们将逐步构建一个用户可访问的公司访问用户数据的所有日志，并确保我们能够对每一次访问都给出清晰合理的解释。 这也意味着每一次访问的理由都必须从用户视角来看是可理解且合理的。 这一点很重要，因为它将我们的做法与用户的视角对齐。他们将能够评估我们如何访问他们的数据，并基于是否认同我们的使用方式来决定是否继续使用我们的产品。 良好的安全讨论不会将决策描述为安全与可用性之间的妥协。 我们将追求有价值的权衡是多维度的。，同时提升安全性和效率。 每当我们将讨论框定为安全与效用之间的权衡时，这就表明我们在进行错误的讨论，应该重新思考我们的方法。 我们将优先采用既能自动授权、又能自动记录访问理由的机制。最明显的例子是，自动授予客服人员对其负责的、处于开放状态的支持工单对应用户的访问权限（并在工单重新分配或解决后撤消该权限）。 以“用户可理解的自动化理由”所覆盖的客户数据访问请求比例来衡量进展。 这将把我们的工作锚定在同时提升用户数据安全性和同事内部工具易用性上。 如果我们只是增加访问客户数据的限制条件，我们不会将其视为进展，因为它没有实现自动化（因此很可能促使团队为快速解决问题而采取变通方法）。 同理，如果我们只是提升了易用性，图表也不会将其显示为进展，因为我们没有增加被支持的请求数量。 作为这项工作的一部分，我们将创建一个私密频道，让安全和合规团队能够看到所有手动填写的用户数据访问理由，并会对反复使用手动理由访问用户数据的同事通知其经理。 自动过期未使用的角色，推进最小权限原则。 目前我们的基于角色的访问控制（RBAC）系统中，有大量授予给同事的角色权限从未被使用。 为解决这个问题，我们将在同事90天未使用某角色权限后，自动移除该角色。 正在参与on-call轮值的值班工程师是此自动权限清理的例外情况。 在看到进展前每周进行审查；之后转为永久的每月访问审查。 从现在开始，安全工程团队、负责客户数据访问工作的各团队以及CISO之间将每周进行一次同步会议，重点是快速迭代和解决问题。 这明确是一个用于持续策略测试：通过迭代优化避免瀑布式策略陷阱的论坛，由CISO担任会议发起人，其Principal Security Engineer担任会议引导者。 该会议将持续进行，直到我们对“100%覆盖用户可理解的自动化访问理由”路径有清晰认识为止。 另外，我们还将启动每月对抽样的客户数据访问进行审查，以确保我们构建的理由生成机制被正确使用和运行。 该会议的目标是通过短期抽样审查访问理由的质量和适当性，并找出更多自动化方法来识别高风险访问，以便未来进行审查。 例外情况必须由CISO以书面形式批准。 虽然我们总体工程策略中提到我们遵循《Facilitating Software Architecture》中描述的顾问式架构流程，但客户数据访问策略属于例外，必须由CISO明确批准并留存文档记录。请在#ciso频道启动该流程。

诊断

我们已经具备了较强的基于角色的访问控制（RBAC）和审计日志基础。 然而，我们在确保分配的角色遵循最小权限原则方面的机制仍然有限。 这在员工换岗或角色发生变化时表现得尤为明显：有些人在公司工作五年以上，积累了大量从未使用过的角色权限。 同样，我们的审计日志虽然持久且覆盖广泛，但我们缺乏主动识别异常使用的机制，通常只在通过其他方式发现事件后，才用它们来追溯发生了什么。 在资源级别访问控制方面，我们采用的是第三方平台（用于接收用户请求）和我们自己产品内的审批机制相结合的混合方案。 在这两个系统之间提供访问理由需要大量手动工作，而且这些理由之后还会以批量方式进行人工审查以判断是否适当。 我们当前资源级别访问控制方法存在两个主要持续问题。 第一，提出访问请求的团队将其视为一种负担重重的义务，对他们自己或对用户都没有明显好处。 第二，由于理由审查步骤是手动的，因此无法验证审查的质量。 我们没有发现任何滥用用户数据的证据。 当同事访问用户数据时，我们一直都能发现存在清晰且合理的访问理由，例如用户支持系统中用户提出的问题工单。 然而，我们记录的理由质量普遍较低，因为这依赖于忙碌的人每天多次手动复制大量信息。 由于理由质量低，对这些理由的验证也带有一定随意性。 从字面合规角度看，我们确实提供了理由和对理由的审计，但很难说大多数此类审计是否真正提升了用户数据的安全性。 历史上，我们做过大量安全投入，短期内显著提升了安全态势。 但一年后再看这些举措，很多情况下我们会看到严格审查之后逐渐出现机制被废弃或规避的现象。 我们发现，这些举措大多增加了其他内部团队必要工作的摩擦。在完成工作的自然秩序中，这些团队会悄然削弱改进措施，因为这妨碍了他们的即时目标（例如支持客户请求）。 因此，根据我们的过往记录，我们高度确信过去的做法能够在公司内部制造表面上的胜利，但我们对它能否带来长期改进信心不足，除非发生重大且不太可能出现的内部变化（例如同事们一年后明显没有现在这么忙）。 我们很可能需要一种新的方法来真正改变对此类问题的立场。

探索

我们的经验是，管理内部人员访问用户数据的最佳实践探索策略空间，其他情况下则很难找到。确切原因难以确定，但可能是因为这个话题涉及潜在的未来责任和合规问题，大家普遍不愿意公开讨论。

在探索过程中，我们发现有两个标准化的维度（基于角色的访问控制、审计日志），以及一个高度分化的维度（资源特定访问控制）：

基于角色的访问控制（RBAC）目前已经是一种高度标准化的方法。 其核心前提是将用户映射到一个或多个角色，每个角色被授予一组特定权限。例如，代表客服专员的角色可能被授予停用账号的权限，而代表销售工程师的角色则可能被允许配置新账号。 审计日志也同样标准化。所有资源的访问和变更都应在持久日志中与执行该操作的人绑定。这些日志应被汇聚到一个可集中查询的系统中。 核心挑战之一在于如何主动利用这些日志来发现问题，而不是在问题已被其他机制标记后被动响应。 资源级别的访问控制则远不如RBAC或审计日志那么标准化。我们发现了三种被不同公司采用的明显不同模式，各公司在选择哪种模式上缺乏一致性。

这三种资源级别访问控制模式分别是：

第三方增强模式：在第三方系统（如Zendesk）中管理对资源的访问。 这需要将产品中这些对象所在系统的数据和元数据丰富到第三方系统中。 还需要在该平台上实现操作，例如归档或配置，使其完全生活在该平台的权限结构中。 这种方法的缺点是与平台供应商紧密耦合，受限于该平台的任何限制，并且需要维护同时熟悉公司内部技术栈和平台供应商技术栈的工程团队。 第一方工具实现模式：所有活动（包括用户问题的创建和管理）都在核心产品内部进行管理。这种模式在早期公司或客服领导“在组织内部成长起来”、没有太多机会接触同行公司做法的公司中最常见。 这种方法的优势是拥有一个单一、紧密集成且可无限扩展的平台来管理交互。 缺点是你必须在内部构建和维护所有这些工作，而不是将其交给本应能投入更多资源打磨工具的供应商。 混合解决方案：使用第三方平台处理大部分操作，同时利用它来控制第一方系统内的资源级访问。 例如，只有当第三方平台中有该用户创建的、分配给你的开放工单时，你才能访问该用户的数据。 这种方法的优势在于，它既能支持不适合平台限制的复杂工作流，又能避免产品与供应商平台之间产生复杂的耦合。

总体而言，我们的经验是所有公司都会实现RBAC、审计日志，以及上述三种资源级别访问控制机制中的一种。 大多数公司要么采用第三方增强模式，配备一个规模可观、长期存在的团队来负责平台实现；要么依赖混合解决方案，通过将相关工作分散到现有团队中，避免设立长期专职团队。
