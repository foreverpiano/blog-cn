重视已被解决的问题

2019-02-23 · 阅读原文

企业级产品的产品市场契合度，很大程度上取决于客户第一次遇到你所解决的问题的时机。 如果你卖给一家刚刚遭遇该问题的公司，就能直接向他们推销产品的价值。 但一家成熟公司很可能已经有了可用的解决方案，你就只能靠降低总体拥有成本（TCO）来销售，这要难卖得多。

这使得判断是否适合大客户变得困难：你无法通过现有的大型企业来验证。 相反，你只能等待那些早期采用你产品、解决了初始问题的初创公司慢慢成长为大公司。

这种动态最终塑造了大多数企业级产品，下面是几个例子。

指标与仪表盘

很长一段时间里，想做指标仪表盘的公司选择有限。 大多数最终都用了 Graphite，或者稍晚一些的 Grafana。 这些都是运维复杂的系统，于是围绕它们出现了一个 IaaS 生态，包括 Datadog 和 SignalFx。

很多新公司默认会选择其中一家 IaaS 厂商。它们需要指标仪表盘，又不想把工程时间花在 Graphite 的部署、维护和扩容上，因此价值主张非常清晰。

而老牌公司已经在运行 Graphite 上积累了能力，或者已经开发了自己的方案（如 Uber 的 M3）。要说服它们切换，必须拿出可信的理由，证明这是以更低成本维持现有工具价值的办法，还得算上 迁移：解决技术债的唯一可扩展方案 的机会成本。

大多数公司做不到。

请求追踪

过去十年，凡是读过 Google Dapper 论文的人几乎都梦想拥有请求追踪。 这最终催生了一个丰富的开源生态，包括 OpenTracing 和 Jaeger，同时也有商业产品如 AWS X-Ray 和 LightStep。

然而，真正把这些工具成功融入调试流程的现有公司并不多。 它们早已有了自研方案——可能不够优雅，只是把 request id 透传下去，然后在 ELK 或 Splunk 里过滤日志——但够用，而且不需要工程师学习新工具。

现代实时请求追踪与基于日志的方案不同，它把 trace 存在内存里。 在内存中存储原始事件能以更高的性价比支持高基数指标，远胜于依赖预聚合的数据点指标方案。 这是一项新能力，但也往往导致这类方案的总拥有成本高于公司现有的日志方案。

成熟公司通常早已解决了这些需求，而成本模型又让请求追踪产品很难在总成本上竞争。 这使得基于内存的请求追踪几乎不可能渗透进今天的大型公司，同时也危及其在明天的大型公司中的契合度。

一个潜在的例外是正在转向 开发面向服务的架构 的公司。 跨服务调试的需求为请求追踪创造了创造价值的机会，即使在技术已经很成熟的公司里也是如此。

申请人跟踪系统

申请人跟踪系统（ATS）是一个非基础设施领域的典型例子。 很多较新的公司采用了 Greenhouse 或 Lever 作为 ATS，效果良好。 而许多老公司仍在使用内部开发的 ATS，其中一些相当先进且针对自身需求做了深度定制（比如 Google），但也有不少——仔细看就会发现——其实只是通过邮件共享的未版本化 Excel。

后一类公司中的大多数其实会从现代 ATS 中受益，它们常常难以招到愿意使用高效工具的招聘人员。 但因为它们“已经解决了问题”，只能从成本节约而非功能能力上去评估产品价值。

结果通常是不切换。

还有很多其他例子可以讨论：

Slack 早期很难取代已经用了 Hipchat、甚至私有 IRC 服务器的公司，最终却有些出人意料地收购了 Hipchat。 不同规模和年龄的公司对 ELK 与 Splunk 的采用情况。

它们大多重复同样的模式，所以我就不详细展开了，但每个例子在细节上都很有意思。

总结来说：公司如何评估你的产品，更多取决于它们自身所处的发展阶段，而非你的产品本身。 今天卖不进大客户，并不意味着你对明天的大客户没有产品市场契合度。 如果能在它们早期就与之建立联系，那么当它们成长为大公司时，你很可能已经能够很好地服务它们。

你不应该想当然地认为自己已经有了契合度，只是目前还无法确定而已。
