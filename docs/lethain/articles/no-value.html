评估已解决的问题。

2019-02-23 · 阅读原文

企业级产品的产品市场契合度，关键取决于客户首次遇到你所解决的问题的时机。 如果你面向的是刚刚遇到该问题的公司，那你就可以向他们推销产品的价值。 但对于成熟的公司，他们很可能已经有了可用的解决方案，你就只能靠降低总体拥有成本（TCO）来销售，而这要难得多。

这就导致很难判断你的产品是否适合大型客户：你无法通过现有的大型企业来验证。 相反，你只能等待那些早期采用你产品的初创公司，在它们解决初始问题并成长为大型企业之后再去验证。

这种动态最终塑造了大多数企业级产品，下面是几个例子。

指标与仪表盘

长期以来，想要构建指标仪表盘的公司选择很少。 大多数最终都采用了 Graphite，或者稍晚一些的 Grafana。 这些系统运维复杂，随后出现了一个 IaaS 生态，其中包括 Datadog 和 SignalFx。

许多新公司默认会选择其中一家 IaaS 厂商。它们需要指标仪表盘，又不想投入工程精力去部署、维护和扩展 Graphite，因此这是一个容易被接受的价值主张。

而 older 的公司已经积累了运行 Graphite 的能力，或者开发出了自己的解决方案（如 Uber 的 M3）。要考虑切换，它们必须拿出可信的理由，证明这是维护现有工具价值的一种更便宜的方式，同时还要考虑 的机会成本。迁移：解决技术债务唯一可扩展的办法。

大多数公司都做不到。

请求追踪

过去十年里，任何读过 Google Dapper 论文的人都梦想着实现请求追踪。 这最终催生了一个丰富的开源生态，包括 OpenTracing 和 Jaeger，以及商业产品如 AWS X-Ray 和 LightStep。

然而，真正成功将这些工具融入调试流程的现有公司并不多。 相反，它们已经有了内部自研的解决方案——可能不够优雅，比如在 ELK 或 Splunk 中通过请求栈传递的 request id 来过滤日志——但已经够用，而且不需要工程师学习新工具。

现代的实时请求追踪与基于日志的方案不同，它将 trace 存储在内存中。 在内存中存储原始事件能以更高的性价比支持高基数（high-cardinality）指标，优于那些依赖预先聚合数据点的基于指标的方法。 这是一项新能力，但往往导致这类方案的总体拥有成本高于公司现有的基于日志的解决方案。

成熟公司通常早已解决了这些需求，而成本模型又让请求追踪产品很难在总成本上竞争。 这使得内存请求追踪几乎不可能渗透进今天的大型公司，同时也让它在面对明天的大型公司时面临契合风险。

一个潜在的例外是那些正在转向 的公司，在这种情况下，跨服务调试为请求追踪创造了创造价值的机会，即使在成熟的技术公司里也是如此。开发面向服务的架构

申请跟踪系统

申请跟踪系统（Applicant Tracking Systems，简称 ATS）是一个很好的非基础设施领域的例子。 许多较新的公司都采用了 Greenhouse 或 Lever 作为 ATS，并取得了不错的效果。 然而，许多老牌公司仍在使用内部开发的 ATS，其中一些相当先进且高度定制（如 Google），但也有很多——仔细看就会发现——其实只是通过邮件共享的未版本控制的电子表格。

后面这类公司中的大多数其实会从转向现代 ATS 中受益，它们常常难以招聘到愿意使用高效工具的招聘人员。 但因为它们已经解决了这个问题，所以只能从成本节省的角度评估产品，而不是从能力提升的角度。

结果是它们通常不会切换。

还有很多其他例子可以讨论：

Slack 早期难以取代已经采用 Hipchat、甚至私有 IRC 服务器的公司，最终出人意料地收购了 Hipchat。 不同规模和年限的公司对 ELK 与 Splunk 的采用情况。

它们大多重复相同的模式，所以我就不展开了，但每一个例子在细节上都很有意思。

总结来说：公司如何评估你的产品，更多取决于它们自身所处的发展阶段，而不是你的产品本身。 今天无法卖给大客户，并不一定意味着你对未来的大客户没有产品市场契合。 如果你能早期接触它们，那么当它们成长为大型用户时，你很可能就能很好地服务它们。

你不应该假设自己已经有契合了。你只是还不知道答案而已。
