自建还是采购。

2020-04-05 · 阅读原文

几年前我负责与 Splunk 进行合同谈判，我们反复遇到对方看似极不合理的定价结构。他们要价数百万美元购买一份为期三年的许可证，这相当于为了一串特定的 32 个 ASCII 字符支付高昂费用。即使拿到许可证，我们仍需自己负责运维，并承担运行所需的容量成本。

我们决定通过计算自建 ELK Stack 集群的成本来进行谈判，具体做法是用可靠数据加上适当的合理推断得出结果。我们用这个计算结果确定 Splunk 对我们的价值，最终成功将价格压低到我们算出的数值，而不是他们最初的收费结构——尽管我怀疑我们可能把价值估高了一些，在可达成协议区间里落在了偏高的位置。

最近 Calm 正在考虑是否将部分工作流迁移到无头 CMS，因此我也更多地思考如何做好这类“自建还是采购”的决策，特别是如何评估“采购”这一选项。归根结底，我认为核心在于风险、价值和成本三方面。

风险

使用供应商就等于承担了一笔未偿债务。你知道自己必须长期支付利息，而且对方还有很小的可能性随时要求提前还款。

从风险角度看，要求提前还款并不意味着供应商把你当作人质勒索巨款——尽管在竞争不充分的情况下，涨价风险确实存在。最严重的风险其实是：供应商倒闭、调整定价导致与你的使用场景不兼容、发生严重安全漏洞迫使你终止合作，或者直接取消该业务线（有人认为这正是 Google 在新平台上难以获得 traction 的原因之一）。

部分风险可以通过法律合同来管理，另一些可以通过购买保险来应对，还有些风险则只能自己判断是否可以接受。

在自建还是采购的决策中，大多数公司把大部分精力放在识别风险上，这固然重要，但往往会演变成强烈的“非我发明”（Not Invented Here）文化，抢走核心业务本应获得的关注。为了避免这种结果，必须至少花同样多的时间去评估“采购”所能带来的价值。

价值

企业靠向用户提供有用的东西来获得成功。直接服务于这一目标的工作是核心工作，其余的都是辅助工作。管理良好、注重效率的企业通常只会给辅助工作分配刚好足够的资源，以避免核心工作出现瓶颈，并将大部分资源投入核心工作。这种对效率的执着其实是一个微妙的错误，因为它把辅助工作视为与价值创造无关的成本中心。

现实中，价值是由包括辅助工作在内的整个系统创造的。很多公司从辅助工作中创造的价值远超核心工作，例如一个平平无奇的产品搭配出色的营销；也有公司因为对辅助工作投入不足而拖累核心业务，比如一群工程师长期等待设计指导。

要计算供应商的价值，就拿供应商的方案与你今天愿意实际构建的东西进行对比。完美的内部工具永远优于供应商当前的产品，但你现在并不会去构建那个完美的内部工具——你实际会构建的是什么？

此外，这两种方案的质量和能力会如何随时间演变？大多数公司，尤其是规模较小的公司，无法理性地持续投入改进内部工具，导致它们相对于活跃的供应商会越来越落后。如果你持有相反假设，应该深入审视这些假设。那些销售内部工具的供应商有着与你完全不同的激励机制，而这种激励机制要求他们必须持续投入改进产品。

当公司发展到一定规模，就可能形成内部规模经济，支持对自有工具的持续投入。Uber 在工程师规模达到约 2000 人后，著名的自建了替代 Greenhouse 和 Zendesk 的系统，但在达到这个规模之前，他们广泛依赖外部供应商。

人们有时会把供应商的价值直接贬为零，理由是担心供应商根本不够好。这种观点隐含了一个假设：质量存在一个“够用”和“不够用”的明确布尔分界线。这是一种僵化的思维，不符合现实——质量不是非黑即白的。供应商的功能肯定会有缺口，你应该明确找出这些缺口并理解弥补它们的代价，但要避免把自己的需求当成不可变动的绝对标准。

谈到自建还是采购时，那句经常被提起却很少被真正遵循的箴言其实是很好的建议：如果你，那么当供应商提供的服务不在你公司的核心竞争力范围内时，通常能创造显著价值；而在核心竞争力范围内，采购往往会拖慢你的速度。你在科技公司工作吗？

成本

理解供应商能带来的价值后，就必须考虑成本。需要重点关注的成本包括：集成成本、财务成本、运营成本和演进成本。

集成成本是供应商开始创造价值之前你需要付出的前期投入。这也是如果当前供应商未来不再存续时，更换供应商的成本。大多数与供应商的讨论都在这个环节花费最多时间。

财务成本是合同本身的费用，包括预测未来使用量以预估后续支出。这也是供应商选择过程中通常受到极大关注的领域，但往往过于强调降本，而对价值的关注不足。

运营成本是使用供应商过程中产生的费用，根据我的经验，这部分常常没有被充分考虑。它包括供应商宕机或性能下降，以及更微妙的问题，比如供应商升级平台时强制要求你同步升级集成。Stripe 的 Payment Intents API 比之前的 Charge API 强大得多，但知道有更好的方案可用，和去年突然得知因 PSD2 的 SCA 要求必须升级才能继续向欧盟买家销售，是完全不同的两回事。

你使用供应商的方式会随时间变化，这使得演进成本也必须纳入考虑，而它和运营成本一样，常常被忽视。这正是供应商架构发挥重大作用的地方，架构设计优秀的供应商会因此脱颖而出。一个典型例子是无头 CMS：它们专注于工作流中的某一环节，因此非常灵活。如果某部分工作流不适合你支持的特定场景，你只需把那一部分从无头 CMS 中剥离，而不需要一次性替换整个系统。

有些供应商方案会制造强大的引力，试图让任何组件都难以脱离它们的生态，这样的供应商应该避免。人们常常关注“供应商无关”（vendor-agnostic），比如能否整体从一个供应商迁移到另一个；而我认为更重要的是追求“供应商灵活性”（vendor-flexible），即能够把部分工作迁移到更适合的工具上。

你的总体成本模型应当涵盖上述所有成本，这将成为合同谈判中特别有力的工具。

综合决策

当你全面思考过价值、风险和成本后，最终还是要做出决定。我的经验法则是：首先判断是否存在高到无法接受的风险。如果风险可以接受，那就做一个简单的价值与成本对比计算，并接受计算结果。

通常，让这个显而易见的方法脱轨的两个反复出现的原因是：法务审查（过度强调那些不太可能发生或可以缓解的风险）和预算不可互换（使用供应商总体上更便宜，但公司把人力预算和采购预算视为完全独立的池子）。

这两者都是过去失误留下的官僚化疤痕，目的是保护企业。从平均水平看，它们可能为公司带来了正确的结果，但在特定决策上未必如此。如果你足够确信当前情况属于例外，那么最终我发现你需要一位高管赞助人来推动落实。

关于供应商管理的一点补充

在结束前再补充一个想法：我观察到很多公司在供应商管理上做得相当差，却很擅长自己构建东西。因此他们的计算总是显示供应商比自建差，而对他们当前的状态来说，这可能确实成立。

要从供应商那里获得全部价值，就必须投入精力做好供应商管理。在这方面做得特别出色的是 Amazon，他们会给供应商发放季度报告卡，根据合同和期望对其表现进行评分。从供应商那里获得优秀结果需要主动管理他们。如果你忽视管理而得到糟糕结果，那是你自己的责任。
