自建还是采购。

2020-04-05 · 阅读原文

几年前，我参与了一次与 Splunk 的合同谈判，我们反复碰到一个感觉极不合理的定价结构。他们要几百万美元换取一份为期三年的许可证，这相当于为一行特定的 32 个 ASCII 字符支付高昂费用。即使拿到许可证，我们仍需自己负责运维，并承担运行所需的容量成本。

我们决定通过计算自建 ELK Stack 集群的成本来进行谈判，这个数字是基于可靠数据和合理估算得出的。我们用这个结果来衡量 Splunk 对我们的价值，最终成功让 Splunk 把价格降到我们计算出的数值，而非他们最初的收费结构。不过我怀疑我们可能把价值估得稍高了一些，在可达成协议的区间里落在了偏上的位置。

最近 Calm 正在考虑是否将部分工作流迁移到无头 CMS，因此我对“自建还是采购”这类决策思考得更多，尤其是如何评估“采购”这一选项。归根结底，我认为核心在于风险、价值和成本。

风险

使用供应商就像承担一笔未偿债务。你知道自己必须长期支付利息，而且对方随时有可能要求提前还款，尽管概率很小。

从风险角度看，“要求提前还款”并非供应商挟持你支付巨额费用——当然，如果市场竞争少，涨价风险确实存在。更严重的风险是供应商倒闭、调整定价导致与你的使用场景不兼容、遭遇严重安全漏洞迫使你终止合作，或直接取消该业务线（有人认为这正是 Google 在新平台上难以获得牵引力的原因之一）。

部分风险可以通过法律合同来管理，另一些可以通过购买保险来应对，还有一些则只能由你自己判断是否可以接受。

在自建还是采购的决策中，大多数公司把主要精力放在识别风险上，这固然重要，但往往会形成强烈的“非我发明”文化，抢走核心业务的注意力。为了避免这种结果，必须至少花同样多的时间去思考采购决策能带来的价值。

价值

企业通过向用户销售有用的东西来获得成功。直接服务于这一目标的工作是核心工作，其余都是辅助工作。管理良好、注重效率的企业通常只给辅助工作分配刚好够用的资源，以避免核心工作出现瓶颈，把大部分资源留给核心工作。这种对效率的执着其实是个微妙的错误，因为它把辅助工作当作与价值创造无关的成本中心。

现实中，价值是由整个系统创造的，其中包括辅助工作。许多公司从辅助工作中创造的价值超过核心工作，例如一个平平无奇的产品配上出色的营销。也有公司因为对辅助工作的投入不足而拖累了核心工作，比如一群工程师长期等待设计指导。

要计算供应商的价值，就拿供应商的方案和你今天愿意自建的东西做比较。完美的内部工具永远比供应商当前的产品更好，但你现在并不会去打造那个完美的内部工具——你实际会去打造的是什么？

此外，这两种方案的质量和能力会如何随时间演变？大多数公司，尤其是小公司，很难理性地持续投入改进内部工具，导致它们相对于活跃的供应商会逐渐落后。如果你持相反假设，应该好好审视一下那些假设。销售这类内部工具的供应商和你有着完全不同的激励机制，而他们的激励机制要求他们必须持续投入产品迭代。

当公司达到一定规模，内部会形成规模经济，足以支持对内部工具的持续投入。Uber 在工程师规模达到约 2000 人后， famously 自建了替代 Greenhouse 和 Zendesk 的系统，但在那之前，他们一直大量依赖外部供应商。

有人有时会把供应商的价值直接归零，理由是担心供应商根本不够好。这种想法假设质量存在一个明确的“是或否”分界线。这是一种僵化的思维，与现实不符：质量不是二元的。供应商的功能肯定会有缺口，你当然应该找出这些缺口并理解弥补它们的代价，但不要陷入把自己的需求当作固定绝对值的思维。

谈到自建还是采购时，那句常被提及却很少被真正遵守的建议其实很有道理：如果你，那么当供应商提供的方案不在你公司的核心竞争力范围内时，通常能带来显著价值；而在核心竞争力范围内，它们往往会拖慢你的速度。你在科技公司工作吗？

成本

一旦明白了供应商能带来的价值，接下来就要考虑成本。主要成本包括：集成成本、财务成本、运营成本和演化成本。

集成成本是供应商开始创造价值之前的前期投入。这也是如果当前供应商未来某天不再存在，你需要替换它的成本。大多数与供应商的讨论把大部分时间花在这个环节。

财务成本是合同本身的费用，包括对未来使用量进行预测以了解后续开支。这也是供应商选择过程中通常被高度关注的领域，但往往过于强调降本，而对价值的关注不够。

运营成本是使用供应商过程中产生的费用，在我的经验里，这一项很少被充分考虑。其中包括供应商的故障或性能下降，也包括更微妙的问题，比如供应商升级平台时强制要求你同步升级集成。Stripe 的 Payment Intents API 比之前的 Charge API 强大得多，但知道有更好的方案可用，和去年突然被告知因为 PSD2 的 SCA 要求必须升级才能继续向欧盟用户销售，是完全不同的两回事。

你使用供应商的方式会随时间变化，因此演化成本也必须纳入考量，而它和运营成本一样，常常被忽视。这正是供应商架构非常重要的地方，设计优秀的供应商会在这里脱颖而出。一个好架构的例子是无头 CMS：它们因为只专注工作流中的某一环节而非常灵活。如果其中某一部分不适合你支持的特定小众流程，只要把那一部分剥离即可，不需要一次性替换整个系统。

有些供应商方案会试图制造强大的吸引力，让你难以把任何组件移到它们的生态之外，这类供应商应当避免。人们常常关注“供应商无关性”，比如能否整体从一家供应商迁移到另一家；而我认为更重要的是“供应商灵活性”——能够把部分工作迁移到更适合的工具上。

你的总体成本模型应当包含上述所有成本，这也会成为合同谈判中特别有力的工具。

综合考量

当你彻底思考过价值、风险和成本后，就需要做出决定。我的经验法则是：先判断是否存在高到无法接受的风险。如果风险可以接受，就做一个简单的价值与成本对比，然后接受计算结果！

通常，让这个显而易见的办法脱轨的两个反复出现的因素是：法务审查（过度强调那些不太可能发生或可以缓解的风险）和预算不可互换（整体使用供应商更便宜，但公司把人力预算和供应商预算视为完全独立的池子）。

这两者都是过去失误留下的官僚化伤疤，目的是保护企业。总体而言，它们很可能为公司带来了正确的结果，但在特定决策上可能并非如此。如果你足够确信这是例外情况，那么最终我发现你需要一位高管赞助者来推动它落地。

关于供应商管理的一点说明

在结束前再补充一点想法：我观察到许多公司在供应商管理上做得相当糟糕，却很擅长自己构建。因此他们的计算总是显示供应商比自建差，而对他们当前的状态来说，这可能确实是对的。

要从供应商身上获得全部价值，就必须投入精力做好供应商管理。亚马逊在这方面做得特别出色，他们每季度给供应商发成绩单，根据合同和期望评估其表现。从供应商那里获得优秀结果需要主动管理。如果你忽视他们而得到糟糕结果，那是你自己的责任。
