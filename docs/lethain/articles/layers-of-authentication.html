认证的层次

2008-09-25 · 阅读原文

这是 Django、jQuery & Ajax 系列的第三篇，接着《Custom Django Views for Happier Ajax》继续往下讲。这一次我们将探讨如何在 Ajax 应用中正确处理认证。

“如何在 Ajax 应用中处理认证？”这个问题的简短答案和你在其他任何应用中的做法是一样的，但还有一个更长的答案。

因为我似乎擅长对那些通常只有简短答案的问题给出冗长的回答，所以这正好适合我。

认证的两个层次，以及两种风格

当我们考虑 Django 中的认证时，首先可能会想到在模板中为已认证和未认证的用户呈现不同的内容。

{% if user.is_authenticated %}
<p> Hi there { { user.get_full_name }}. Welcome to Notes! </p>
{% for note in notes %}
<p>{ { note }}</p>
{% endfor %}
{% else %}
<p>
We don't take kindly to strangers around here.
<a href="/register/">Try registering!</a>
</p>
{% endif %}

在这种情况下，我们进行认证是为了防止不希望看到的数据被查看。

{% if user.is_authenticated %}
<form type="POST" action="/create/">
<label for="title">Title</label>
<input type="text" name="title">
<input type="submit" value="create">
</form>
{% else %}
<p> Nothing to see here. </p>
{% endif %}

现在你可能会认为我们是在阻止数据修改，但事实并非如此。如果攻击者发现了表单的 URL，他们仍然可以手动向其 POST 数据。

我们在这里所做的并不是为了保护我们的系统，而是通过隐藏不可用的功能来提升用户界面。这很重要，因为我们不希望 UI 误导用户，但它并不会提升应用的安全性。

第三种也是最后一种风格，是在视图层进行认证。

python create(request):
    if request.user.is_authenticated():
        return render_template("my_app/i_trust_you.html")
    return render_template("my_app/no.html")
# or even more simply
from django.contrib.auth.decorations import login_required
@login_required
def create(request):
return render_template("my_app/i_trust_you.html")

在这三种场景中，认证的层次和风格有一些重叠，但我们最终得到几个重要的概念需要考虑：

  1. For modification, we must perform authentication at the view layer.
  2. For presentation, we may perform authentication at either the view or template layer.
  3. Synchronizing the user interface with permissions does not provide security for your app, but does provide security from your rioting users triyng to stab you.

你可以将这些想法归结为两个简单的问题：在用户界面层，我是否应该暴露这个？在 API 层，我是否应该允许这个？

是时候开始 Notes 的审讯了。

设置用户认证

但是，首先我们得停下来开个茶会。嗯，也许不算真正的茶会，但我们确实需要先设置账号创建功能。

第一步是打开 settings.py，确认 django.contrib.auth 已经在 INSTALLED_APPS 列表中。如果没有，请添加它。

第二步，我们需要为登录和登出操作配置 URL。打开 ajax_tut/urls.py，添加以下两个 URL：

# Authentication Views
(r'^accounts/login/$', 'django.contrib.auth.views.login'),
(r'^accounts/logout/$', 'django.contrib.auth.views.logout'),

接下来我们需要创建一些简单的模板。

从项目目录 ajax_tut/ 开始，先创建两个文件夹：

mkdir templates
mkdir templates/registration

然后我们需要创建两个简单的模板。首先是 registration/login.html：

{% extends "base.html" %}
{% block content %}
{% if form.errors %}
<p>Your username and password didn't match. Please try again.</p>
{% endif %}
<form method="post" action=".">
<table>
<tr><td>{ { form.username.label_tag }}</td><td>{ { form.username }}</td></tr>
<tr><td>{ { form.password.label_tag }}</td><td>{ { form.password }}</td></tr>
</table>
<input type="submit" value="login" />
<input type="hidden" name="next" value="{ { next }}" />
</form>
{% endblock %}

第二个是 registration/logged_out.html：

{% extends "base.html" %}
{% block content %}
<p> You have been logged out. </p>
{% endblock %}

现在模板已经创建好了，我们还需要在 settings.py 中设置 LOGIN_REDIRECT_URL。打开 ajax_tut/settings.py，添加下面这行：

LOGIN_REDIRECT_URL = u"/"

然后我们来修改基础模板 base.html，添加一个登录/登出链接（以及一个返回首页的导航链接）。

在 <body> 标签开始之后，立即插入以下 HTML：

<div class="navbar">
  <a href="/">Home</a>
  <span> | </span>
  {% if user.is_authenticated %}
  <a href="/accounts/logout/">Logout</a>
  {% else %}
  <a href="/accounts/login/">Login</a>
  {% endif %}
</div>

现在如果你运行开发服务器，你会看到我们已经可以登录、登出，而且 login|logout 按钮会显示正确的选项。

我是否应该暴露这个？

我们要回答的两个问题中的第一个是“我是否应该暴露这个？”

在这个例子中，这意味着我们将查看 notes/note_list.html 和 notes/note_detail.html 模板，并对未登录的用户隐藏编辑功能。

我们先从 notes/note_list.html 模板开始。

我们需要做的就是用模板的 if 语句把 <div class="new"> 这个 div 和 <script> 标签包裹起来，让它们变成下面这样：

{% if user.is_authenticated %}
<div class="new">
  <h2> Create a new note. </h2>
  <form method="post" action="/create/">
  <label for="title">Title</label> <input type="text" name="title" id="title">
  <label for="slug">Slug</label> <input type="text" name="slug" id="slug">
  <input id="create" type="submit" value="create note">
  </form>
</div>
{% endif %}

以及这样：

{% if user.is_authenticated %}
<script>
// lots of JavaScript here
</script>
{% endif %}

分别对应上面两部分。

然后回到应用，分别在登录和未登录状态下查看首页的变化。

接下来我们需要对 notes/note_detail.html 模板做同样的处理。

首先我们像之前一样把 JavaScript 部分排除掉：

{% if user.is_authenticated %}
<script>
// lots more JavaScript
</script>
{% endif %}

然后我们还需要处理显示的内容。因为未认证的用户无法进行修改，所以不应该向他们显示输入框或文本框。相反，我们只用几个 <span> 和一个 <p> 来显示内容。

<div class="detail">
  {% if user.is_authenticated %}
  <form method="post" action="update/">
  <div class="text">
    <label for="title">Title</label>
    <input type="text" name="title" id="title" value="{ { object.title }}">
    <label for="slug">Slug</label>
    <input type="text" name="slug" id="slug" value="{ { object.slug }}">
  </div>
  <textarea name="text" id="text">{ { object.text }}</textarea>
  <input class="submit" type="submit" value="update note">
  </form>
  {% else %}
  <span>Title: { { object.title }}</span>
  <span>Slug: { { object.slug }}</span>
  <p> { { object.text }} </p>
  {% endif %}
</div>

现在运行应用，登录登出多切换几次，看看不同的笔记（以及笔记列表），感受一下。

我们的 UI 现在已经能向用户表明可用的权限了，但我们还需要实际强制执行这些权限。进入下一节。

我是否应该允许这个？

添加认证的最后一步是回答第二个问题：“我是否应该允许这个？”

我们的四个自定义视图都允许创建或修改数据，因此答案非常简单：不，不，不，不。

要实现这一点，需要在 notes/views.py 中额外添加五行代码。

首先在文件顶部添加这个 import：

from django.contrib.auth.decorators import login_required

然后给每个视图加上这个装饰器：

@login_required
def create_note(request):
    # etc etc
@login_required
def ajax_create_note(request):
# etc etc
@login_required
def update_note(request):
# etc etc
@login_required
def ajax_update_note(request):
# etc etc

保存应用，然后通过手动在浏览器输入对应的 URL（比如 /create/、note/<slug>/update/ 等）来测试这些视图是否已经无法正常工作。

现在我们珍贵的笔记终于真正安全了。

继续前进

虽然我们没有特别强调，但值得一提的是，这个小小的测试应用现在已经能在四种不同的用户场景下正确运行：有 JavaScript 无认证、有 JavaScript 有认证、无 JavaScript 无认证、无 JavaScript 有认证。

当我们谨慎地设计系统时，就可以只关注简单的二分法（JavaScript 与无 JavaScript、已认证与未认证），而不是不得不处理更大范围的指数级复杂组合。
