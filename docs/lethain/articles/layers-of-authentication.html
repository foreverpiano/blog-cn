认证的层次

2008-09-25 · 阅读原文

这是 Django、jQuery 与 Ajax 系列的第三篇文章，接续《Custom Django Views for Happier Ajax》之后的内容。这一次我们将探讨如何在 Ajax 应用中正确处理认证。

“如何在 Ajax 应用中处理认证？”这个问题的简短答案和你在其他任何应用中的做法是一样的，但也有一个更详细的答案。

既然我似乎擅长给出那些通常只有简短答案的问题的长答案，这显然正合我意。

认证的两个层次，以及两种风格

当我们在 Django 中考虑认证时，首先想到的可能是根据用户是否已认证，在模板中展示不同的内容。

在这种情况下，我们进行认证是为了防止不希望的数据被查看。

你可能会认为这里我们是在防止数据被修改，但事实并非如此。如果攻击者发现了表单的 URL，他们仍然可以手动提交 POST 数据。

我们在这里所做的并不是为了保护系统，而是通过隐藏不可用的功能来改善用户界面。这一点很重要，因为我们不希望用户界面误导用户，但它并不会提升应用的安全性。

第三种也是最后一种风格，是在视图层进行认证。

在这三种场景中，认证的层次和风格有一些重叠，但我们最终可以归纳出几个重要的概念：

对于数据修改，必须在视图层进行认证。对于内容展示，可以在视图层或模板层进行认证。让用户界面与权限保持同步并不能为你的应用提供安全保障，但能保护你不被愤怒的用户用刀捅。

你可以将这些想法浓缩为两个简单的问题：在用户界面层，我应该暴露这个吗？在 API 层，我应该允许这个吗？

是时候开始 Notes 应用的拷问了。

继续前进

虽然我们没有大张旗鼓地强调，但值得注意的是，这个小小的测试应用现在已经能在四种不同的用户场景下正确运行：有 JavaScript 未认证、有 JavaScript 已认证、无 JavaScript 未认证、无 JavaScript 已认证。

当我们谨慎地设计系统时，就可以只关注简单的二分法（JavaScript 与无 JavaScript、已认证与未认证），而不是去处理更大范围的组合所带来的指数级复杂性。
