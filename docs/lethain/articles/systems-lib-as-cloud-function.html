将系统库作为 Cloud Function 运行

2019-06-16 · 阅读原文

我最近和朋友 Bobby Powers 聊天，他提到自己正在开发一个系统动力学（systems dynamics）应用。这次对话激励我去完成一个一直搁置的项目：把一个系统以 HTTP 接口的形式暴露出来，并运行在 Google Cloud Function 中。

这个练习的大致目标是：（1）通过 HTTP API 暴露系统功能；（2）以函数形式（即 serverless）运行，最大程度减少维护工作和费用；（3）开发流程要足够简单，因为我隔一段时间就会忘记它，到时候还能快速上手；（4）要具备扩展性，以便后续可以添加一个 JavaScript GUI 来调用这个 API。

这些目标最终都实现了，虽然过程比我预想的要麻烦一些。

我之前已经安装好了 Google Cloud SDK，所以跳过了这一步。接下来我创建了一个新的 Git 仓库：

cd sys-app
git init

最初仓库里只有三个文件。第一个是位于 sys-app/functions/run-model/main.py 的 HTTP 函数：

def hello_get(request):
    return 'Hello World!'

第二个文件在同一目录下，名为 sys-app/functions/run-model/requirements.txt，用于指定唯一的 Python 库依赖：

systems==0.1.0

最后一个文件是用于 Cloud Build 的构建配置文件：

steps:
  - name: 'gcr.io/cloud-builders/gcloud'
    args: ['functions',
           'deploy',
           'run_model',
           '--trigger-http',
           '--runtime',
           'python37'
          ]
    dir: 'functions/run-model'

接着我在 Github 上创建了一个新的私有仓库，并将本地仓库同步上去：

git remote add origin git@github.com:lethain/sys-app.git
git push -u origin master

然后我在 GCP 的 Cloud Source Repositories 中设置了镜像，同步 lethain/sys-app。我其实也可以直接连接 Github 上的仓库，而不用先镜像过来。但不知道为什么，我更喜欢先镜像，然后在 Cloud Source 里直接操作，这样感觉耦合度更低一些。

之后我开始按照步骤设置自动构建。首先启用了 Cloud Build，然后创建了一个构建触发器，在 sys-app 的 master 分支有推送时触发。

需要说明一下，虽然界面上显示来源是 Github，但我实际选择的其实是 Cloud Source 的镜像。据我观察，这应该只是个 UI 的小 bug。

倒数第二步是按照文档说明，给 Cloud Builder 授予 Cloud Function 的部署权限。我一开始漏掉了这一步，即使按照文档逐字操作也觉得有点困惑，但最终还是成功了（我是继续往下走，边调试边尝试，直到一切正常）。

至此，我又向 sys-app 仓库提交了一次修改并触发部署，构建触发器成功触发，函数被创建，一切都正常工作了。

说实话，我在这个环节卡了挺久。表面上看一切正常，每次部署都会创建新版本，但实际运行的代码却完全没有更新。我之前是通过 UI 创建的这个函数，日志里也没什么有用的提示说明为什么没有更新。于是我干脆删掉了它，改由 Cloud Build 配置来创建和更新函数，这之后就一切正常了。

现在我可以通过 gcloud CLI 来验证这个函数：

gcloud functions call run_model \
--data '{"definition": "a > b @ 1"}' \
--project=PROJECT

或者，也可以用 Python 通过 HTTP 调用它：

import requests
definition = """[a] > b @ 5
b > c @ 4"""
resp = requests.post('https://$MY-FUNCTION-URL',
                     json={'definition': definition})
print(resp.content.decode("utf-8"))

现在我只要修改 sys-app，推送新的提交，函数就会在后台自动更新，这基本达成了我最初的目标。

和我之前做的 不同，这次我无需额外创建任何服务来处理构建完成后调度升级之类的事情，这点非常 nice。（看着 kubectl cloud builder，我觉得应该能找到一种不需要服务监控 build pub-sub 队列就能实现 k8s 持续部署的方式，不知道这是新功能，还是我上次没注意到。）在 GKE 上使用 gke_ci 实现简单的持续部署

如果我打算经常使用这种开发流程，下一步应该是想办法在每次构建时以阻塞方式运行测试。但目前看对 Python 支持不太友好（cloud-builder 里没有 pip），所以可能需要准备一个 Dockerfile 来跑测试。虽然完全可行，但我不是特别有热情去做。

总体来说，GCP 提供的体验已经很接近「很好用了」，但真正让人惊喜的体验其实只差一步。想象一下，如果我新建一个 Cloud Function 后能勾选一个选项，以后每次在 Cloud Source 仓库有改动就自动部署，那该多好？再进一步，如果我能放一个 test.py，系统会在部署更新前自动运行测试，那又会多么美好？

这些功能你当然可以自己全部搭建出来，但为什么每个用户都要重复做这种「胶水」工作呢？这也是为什么尽管云厂商已经提供了所有底层组件，像 Netlify 这样的平台依然不断涌现。这种演进让我想起 AWS 尝试向下游拓展个人虚拟机市场推出的 Amazon Lightsail——晚了几年才去做其他主机商（比如当年的 Slicehost 和现在的 Digital Ocean）早就明白用户想要的东西。

这对我们所有人都是一个很好的提醒：我们应该每个季度都花几个小时，从零开始集成自己的产品，看看还有哪些粗糙的边缘地带。
