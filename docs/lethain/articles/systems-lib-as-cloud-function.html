将系统库作为 Cloud Function 运行

2019-06-16 · 阅读原文

之前和朋友 Bobby Powers 聊天时，他提到自己正在开发的一个系统动力学应用。这次谈话激励我想要完成一个长期搁置的项目——将系统以 HTTP 接口的形式暴露出来，并在 Google Cloud Function 中运行。

这个练习的大致目标是：(1) 通过 HTTP API 暴露系统；(2) 以函数（即 Serverless）形式运行，最大程度减少维护和成本；(3) 开发流程要足够简单，因为我时不时就会把它忘掉，否则下次再看的时候会完全不知道怎么用；(4) 要有扩展性，以便后续可以添加一个调用该 API 的 JavaScript GUI。

这些目标最终都实现了，虽然过程比我预想的要棘手一些。

我已经安装好了 Google Cloud SDK，所以跳过了这一步。接下来我创建了一个新的 Git 仓库：

cd sys-app
git init

最初仓库里只有三个文件。第一个是位于 sys-app/functions/run-model/main.py 的 HTTP 函数：

def hello_get(request):
    return 'Hello World!'

第二个文件同样位于该目录下，名为 sys-app/functions/run-model/requirements.txt，它指定了唯一的 Python 库依赖：

systems==0.1.0

最后一个文件是用于 Cloud Build 的构建配置文件：

steps:
  - name: 'gcr.io/cloud-builders/gcloud'
    args: ['functions',
           'deploy',
           'run_model',
           '--trigger-http',
           '--runtime',
           'python37'
          ]
    dir: 'functions/run-model'

然后我在 Github 上创建了一个新的私有仓库，并将本地仓库同步上去：

git remote add origin git@github.com:lethain/sys-app.git
git push -u origin master

接着我更新了 GCP 上的 Cloud Source Repositories，让它镜像 lethain/sys-app。我本来也可以直接连接 Github 上的仓库，而不用先镜像过来，但不知道为什么，我更喜欢先镜像一份，然后在 Cloud Source 里直接操作，这样耦合度更低一些。

随后我开始按照步骤设置自动构建。首先启用了 Cloud Build，然后创建了一个构建触发器，在 sys-app 的 master 分支每次有提交时触发。

需要说明的是，虽然界面上显示来源是 Github，但我实际选择的来源是 Cloud Source 的镜像。据我所知，这只是个奇怪的 UI Bug。

倒数第二步是按照文档说明，授予 Cloud Builder 云函数部署权限。我一开始漏掉了这一步，即使严格按照文档操作也觉得有些困惑，但最后还是搞定了（我是通过继续后续步骤，然后不断调试直到它正常工作才解决的）。

此时，我又向 sys-app 仓库提交了一次修改并触发部署，结果触发器成功触发，函数被创建，一切都正常运行了。

说实话，我在这里卡了挺长时间。表面上看一切正常，每次部署都会创建新版本的函数，但实际运行的代码却完全没有更新。我是通过 UI 创建的这个函数，日志里也没有什么有用的信息说明为什么没有更新。最后我干脆删掉了它，依靠 Cloud Build 配置来创建和更新函数，这之后才正常工作。

我现在可以通过 gcloud CLI 来验证这个函数：

gcloud functions call run_model \
--data '{"definition": "a > b @ 1"}' \
--project=PROJECT

或者，也可以用 Python 通过 HTTP 调用它：

import requests
definition = """[a] > b @ 5
b > c @ 4"""
resp = requests.post('https://$MY-FUNCTION-URL',
                     json={'definition': definition})
print(resp.content.decode("utf-8"))

现在我可以修改 sys-app，推送新的提交，然后函数就会在后台自动更新，这基本就是我最初的目标。

和我之前不同，这次我不需要创建任何服务来处理构建完成后调度升级之类的操作，这点非常好。（看着 kubectl cloud builder，我觉得应该能找到一种不需要服务监控 build pub-sub 队列就能实现 k8s 持续部署的方法，不知道这是新功能，还是我上次没注意到。）在 GKE 上使用 gke_ci 实现简单的持续部署

如果我打算频繁使用这个工作流，下一步可能是研究如何在每次构建时以阻塞方式运行测试，但目前看来 Python 似乎没有特别好的办法（他们没有提供 pip 作为 cloud-builder，所以我可能需要写一个 Dockerfile 来做测试，这虽然可行，但我不是特别感兴趣）。

总的来说，GCP 提供的体验距离真正优秀只差临门一脚。想象一下，如果我在创建一个新的 Cloud Function 时能勾选一个选项，让它在 Cloud Source 仓库每次变更时自动部署，那体验会有多棒？再进一步，如果我能放一个 test.py，让它在部署更新之前自动运行测试，那又会如何？

这些功能你当然可以自己全部搭建起来，但为什么每个用户都要自己去粘这些胶水呢？这也是为什么尽管云厂商拥有所有底层组件，像 Netlify 这样的平台仍然不断涌现。这种演进让我想起 AWS 试图向下游进入个人虚拟机市场推出的 Amazon Lightsail——只是比 Slicehost 以及现在的 Digital Ocean 等主机商意识到用户需求的时机晚了几年。

这对我们所有人都是一个很好的提醒：我们应该每个季度都花几个小时，从零开始集成自己的产品，看看有哪些粗糙的边缘体验。
