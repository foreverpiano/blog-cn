Digg v4 发布：源于迫切的乐观。

2018-07-02 · 阅读原文

Digg 正经历着艰难的一年。我入职的前一天，CEO 就离职了。资深工程师们一个个悄无声息地走人，生产力持续下滑，还带走了他们剩下的朋友。虚假投票团伙绕过了我们的算法，在首页兜售曝光位置，甚至因为我们修改算法阻止滥用而威胁我们的生命。开发者环境的配置工具彻底坏掉，没人知道怎么修复，于是我们只好把新入职员工塞进已离职同事留下的僵尸虚拟机。

但今天与这些无关。今天是为了扭转过去两年一直困扰 Digg 的最大难题。我们即将推出完全重写的 Digg。我们决定今天必须上线。我们一致同意不再推迟发布。我们也清楚，新版本——第四版——其实还没准备好。

新的一天开始了。我们当时太天真了。现实很快就会给我们上一课。

如果你有幸被邀请到我们那间由仓库改造而成、宽敞得有些空旷的办公室，感受到那股躁动的氛围，你大概会以为正在举办一场庆典。从 Digg v3.5 到 Digg v4 的重写已经断断续续进行了近两年，它承诺将我们从一个单一的、由社区驱动的新闻聚合网站，转变为一个无限个性化的聚合器——通过融合你的社交图谱、顶级影响者以及全球新闻风潮来实现。

尽管产品需求在上周还在不断变化，但通往 Digg v4 的道路早在几年前就已确定，那时 Digg 刚被 Google 的 Panda 算法更新重创。随着那次搜索更新在一个月内缓慢生效，我们的命运像亵渎了神灵一样急转直下：我们刚迎来公司第一个——也是唯一一个——盈利的月份，随后便开始持续下滑，直到月度流量腰斩。一个月前，公司正走完五年通往盈利的漫长道路；下一个月，就成了自由落体、不得不在弱势地位筹集资金的困境。

推出 v4 是我们重返互联网巨头行列的机会。那间被员工戏称为“谋杀教堂”的宽敞办公室，也为这一天被精心重新布置。房间中央摆放了一张巨大的木桌，作为“作战室”。四周环绕着一圈沙发，其他人可以站在旁边随时支援。身着正装的侍者托着寿司、精致小食和冰镇香槟在房间里穿梭。吧台已经搭好，提供各种酒水。有人则溜到楼上打几局乒乓球。

问题开始慢慢浮现。

曾经有位兴奋的工程师宣称，整个重写版本只用两台服务器就能跑。虽然我们简陋的 QA 环境规模比这大得多，但我们最后竟真的差点只用两台服务器就上线。上线前一周，容量规划的任务被交给了 Rich 和我。我们硬着头皮装上 JMeter，针对这个复杂、密集且不断快速变化的重写系统，尽可能多地生成性能数据。这并非我职业生涯中最没底气的一次——我还记得四年级时在去学校的巴士上写过一篇从没读过的书的读书报告——但我们很可能是在对系统能否正常工作几乎毫无把握的情况下就上线了。

我们隐约觉得这可能也没那么重要，因为反正我们也来不及在上线前向数据中心订购和安装新硬件。现有容量够用，因为那是我们全部的家底。

大约上午十点，有人问什么时候开始切换，Mike 好心地插话：“我们已经开始重新配置 v3 的服务器了。”我们的容量实在太少，所以决定把所有现有服务器全部重装系统，然后在新软件栈上重新配置。从降低成本的角度看，这很聪明，但其中蕴含的乐观也带着一丝疯狂。

随着重生的火焰吞噬了旧的基础设施，一件奇怪的事情发生了，或者说没发生。新网站并没有真正起来。运维团队赶紧推出维护页面，我们则聚集在那张漂亮的木桌周围，昂贵的椅子和越来越强烈的焦虑感笼罩着大家。情况不太妙。我们没有回滚计划。桌子旁随机聚集的工程师们一致认为，唯一的选择就是继续往前冲，于是我们就这样做了。一个小时后，旧的基础设施彻底消失，取而代之的是 Digg 第四版。

服务器在重新配置，维护页面安抚着访客，整个办公室弥漫着一种“罗马末日”的氛围。香槟和开放式酒吧持续供应，乒乓球台一直有人，公司的其他人则在一旁看着，不知如何帮忙，也逐渐接受了 Digg 最后一次孤注一掷已经搞砸的事实。大堂里那幅加框的《福布斯》封面，成了彻底的过去，而绝非未来的预兆。

时间一分一秒过去，人们陆续离开，但聚集在中央桌子旁的工程师们还有很多工作要做。我们成功配置了新网站，但它仍在负载下踉跄前行，大部分页面都无法加载。主要瓶颈是我们的 Cassandra 集群。Rich 和我躲进一间会议室，加大了 memcache 作为写穿缓存的使用来保护 Cassandra；几小时后，网站对未登录用户开始能正常加载了。

不过，已登录用户访问网站时依然看到错误页面。罪魁祸首是这次重写的核心功能——MyNews。它本应为每篇文章提供你的朋友与它互动的社会化上下文，并将所有这些活动合并成个性化的新闻流。至少理论上是这样。而实际上，它此时只会优雅地抛出“初创蓝”的错误页面。

天色渐暗，我们把用户的默认首页从 MyNews 改成了仍在正常加载的 TopNews，这样用户至少可以登录并使用网站。MyNews 页面仍然会出错，但这已经足够让我们带着醉意和挫败感回家，成为这场重新发布庆典的幸存者。

第二天一早，人们陆续回到办公室，我们重新集结。MyNews 彻底坏了，网站每四小时就会准时崩溃一次，而在这些核心问题背后，还有几十个小问题不断冒出来。我们发现重启所有进程可以解决周期性崩溃，但一直无法定位具体是哪些进程导致的，所以决定先集中解决 MyNews。

Rich 和我再次把自己关在会议室，这次的目标是从零重写 MyNews 的实现。当前版本往 Cassandra 里写数据，它的负载正在压垮集群，破坏社交功能，并连带拖垮其他所有功能。我们决定改用 Redis 存储数据，但数据量太大，单台服务器存不下，因此我们需要推出新的实现、新的分片策略，以及管理这些工具的工具。

而我们做到了！

在接下来的两天里，我们实现了一个分片的 Redis 集群，并成功完成了迁移。它还有一些 bug——在 Digg 剩下的日子里，我会偷偷从 MyNews 集群删除大量数据，因为我们既负担不起正确扩容所需的成本，也无法就如何处理达成一致，所以每次我都偷偷删掉多余数据来维持网站运行——但它确实工作了，我们珍视的重写版本终于冲出起跑线，开始一瘸一拐地沿着赛道前进。

它确实是一瘸一拐的，每四个小时就需要手动重启所有进程。我们花了一个月才追踪到这个 bug，到最后只剩下三个人还在坚持。我过于沉迷于理解这个问题，和运维团队的 Jorge、Mike 一起工作，以至于我甚至不知道接下来那个月是否还有其他人来过办公室。不理解这个崩溃成了一种冒犯，随着大多数人逐渐退出——大概是开始投简历了，因为他们还算理智——我却被一种执念占据，一定要把它修好。

而我们做到了！

我们的 API 服务器是一个 Python Tornado 服务，它会调用 Python 后端服务，后端叫 Bobtail（前端叫 Bobcat）。其中一个访问最频繁的端点用于根据名字或 ID 获取用户。因为它同时支持按名字或 ID 查询，所以为两个参数都设置了默认空列表。这是个非常合理的设计！然而，Python 只会在函数首次被评估时初始化默认参数，这意味着每次调用函数时使用的都是同一个列表。因此，如果你修改了这些值，修改会跨越多次调用而累积。

在这个案例中，每次调用都会把用户 ID 和名字追加到默认列表中。几个小时后，这些列表每次请求会检索数万个用户，甚至压垮了 memcache 集群。这个 bug 花了这么长时间才被发现，是因为我们以字典形式返回结果，而字典里总是包含必要的值，只是碰巧还包含了数万个多余的值，所以它从不会以明显的方式失败。这个 bug 的影响被进一步放大，因为我们假设用户不会传入重复 ID，却会愉快地为单个请求反复获取同一个 ID。

我们推出了这个最后的关键修复，Digg V4 终于算彻底上线了。一周后，我们最后一位 CEO 入职。一个月后，我们进行了第三轮裁员。一年后，我们卖掉了公司。但在那一刻，我们赢了。

我即将迎来入职六个月纪念日。

Digg V4 有时被当作灾难性发布的反面教材，暗示我们不该推出它。曾经我也这么认为，但现在我觉得我们做了正确的决定。当时我们的流量大幅下滑，每月都在烧钱，最近刚融过资，也知道很难再融到下一轮。如果我们能在推出伟大产品和糟糕产品之间选择，我们当然会选伟大的那个，但现实是我们只能在最后挥一次棒，还是安静地把球棒上交之间做出选择。

我很高兴我们挥出了那一棒；也为我们熬过了那次糟糕的发布而自豪。

另一方面，我至今仍震惊于我们在发布过程中的鲁莽。我还记得那次决定继续推进发布的会议，Mike 当时强烈反对。据我回忆，我全程保持沉默。我希望自己从那次经历中有所成长，因为即使现在，我也无法理解这样一群才华横溢的人，怎么会做出那样一场堪称荒唐的表演。
