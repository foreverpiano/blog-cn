《事务模型》论文阅读笔记

2009-08-18 · 阅读原文

在读完 Lampson 的《计算机系统设计中的提示》之后，最让我着迷的主题是容错（fault tolerance）和故障恢复。它本身就极具吸引力，而在我们正努力为正在构建的复杂系统赋予“失败时仍保持理性”的能力时，这个主题又增添了额外的吸引力。因此，我接下来阅读的论文是 Jim Gray 在 1980 年发表的《A Transaction Model》。

从宏观上看，《A Transaction Model》讨论了系统如何发生故障、并发问题、一致性级别、如何判断具有一致性要求的系统中并发事务的合法性、并发事务所带来的风险、并发事务的解决方案、分布式数据库，以及面向事务的编程语言可能具备的特性。

事务

作为对后续总结的简短铺垫，我们最好先引用 Gray 对事务的定义，他提出了两个核心要求：

必须被精确执行一次（可靠性）。必须与其他并发执行的事务所引入的一致性约束临时违背相隔离（一致性）。

对许多开发者（包括曾经的我）来说，事务通常只在选择 MySQL 存储引擎时被讨论，或者用来辩论 MySQL 和 PostgreSQL 的相对优劣。然而，我逐渐产生一个想法：事务其实可以应用在更高层次上，而且大多数系统都可以被描述为一系列事务——只是需要说明的是，它们并不特别追求可靠性和一致性。

例如，考虑一个试图发布推文的 Twitter 客户端。其预提交阶段是先将推文写入本地，提交阶段则是真正发送给 Twitter 并在客户端 GUI 中展示出来。但有可能（根据你每天接触的吐槽量来看，甚至是极有可能）Twitter 服务不可用，或者你暂时被限制在接下来一小时内无法继续调用 API，这种情况下客户端就需要撤销预提交的操作（从 GUI 中删除那条推文），然后要么重新尝试预提交和提交阶段，要么彻底放弃整个事务。

我不确定用事务模型来描述这个 Twitter 客户端的逻辑是否特别有价值，但如果抱有更大的野心，我能想象出一些更有趣的例子，在那些场景中，将整个程序视为一系列事务，将成为一个强大且简化的建模方式。

可靠性

论文详细梳理了各种类型的错误——我在这里就不一一忠实复述了——但从最宽泛的层面来说，它讨论了两种失败：事务重启和系统重启。两者的区别正如这两个术语字面所表达的那样。

更有意思的是 Gray 将资源分成了四类：

真实资源（real resources）代表物理实体（比如 ATM 机吐出的真实货币）；稳定资源（stable resources）代表能在系统重启后继续存在的实体（比如写入磁盘的文件）；易失资源（volatile resources）是在系统重启时会丢失的实体（比如某个变量的当前值）；可恢复易失资源（volatile-recoverable resources）以快速访问的形式存在，但同时有备份机制，能在系统重启后重建（比如使用内存存储但同时持久化到磁盘的 Mnesia）。

用这种分类方式思考的最大好处在于，它能更清晰地判断事务应该回退到哪个点，同时也能帮助判断你的系统是否不可恢复（即是否依赖某个易失值来完成系统重启后的恢复）。

最后一个我要提到的概念——类似于 Lampson 在《计算机系统设计中的提示》中讨论的事件日志——是撤销日志（undo logs）和重做日志（redo logs），它们能让系统回滚一个事务的预提交操作。

本质上，在执行预提交步骤之前，这些操作会先被写入重做日志。然后每执行一步，就从重做日志中弹出，并推入撤销日志中。这样一来，任何时候都可以完整地执行或回滚预提交阶段的所有事件。

有了稳定的撤销日志和重做日志，就可以在系统重启时，理性地撤销那些正在进行中的事务。这是一个相当惊人的特性，许多系统如果能具备它将会获益匪浅，但真正做到的却很少。

并发

我不会在此过多赘述，因为论文对此并没有进行非常深入的探讨。但核心理论是：当并发事务被以某种方式记录到日志中，使得它们等价于某一组串行事务时，会产生若干正面特性。

如果并发事务无法被记录成等价于某个串行事务的历史，那么系统的理性就值得怀疑了。

一致性级别

在探讨如何实现一致性事务的具体方案之前，Gray 定义了三种一致性级别：

3 级一致性之前被定义为一种获取锁来覆盖所有操作、并将所有锁保持到事务提交的协议。它被证明能够防止并发异常。为了支持事务重启，所有系统都会获取 X 模式锁来覆盖写操作并保持到事务提交，这被称为 1 级一致性锁协议。如果系统额外获取 S 模式锁来覆盖读操作，但是在提交前释放这些锁，则提供 2 级一致性。

关于使用不够严格的 1 级和 2 级一致性在性能上的相对表现，Gray 写道：

在我们所做的实验中，3 级一致性在成本（吞吐量和处理器开销）上与较低级别的一致性几乎无法区分。

我发现他对为什么其他人仍然在使用 supposedly 同等高效但一致性更差的 1 级和 2 级一致性的简短评论相当有趣，或者说至少令人感慨。

很多次我都见过其他人——当然也包括我自己——拼命为我们已经用错误方式做过的事情寻找解释，然后试图说明它其实是一个理性的决定，而非一个欠考虑的选择。Gray 给出的两个借口是：实现的复杂性，以及想象中但未经证实的性能收益。这两种说法在我听来都相当熟悉。

分布式问题

论文讨论了当一个事务在其整个生命周期中跨越多个不同节点时，如何重启的问题，这与我们当前工作中正在解决的最棘手问题高度吻合。

Gray 的建议是，每个节点必须记录它从哪个源节点接收到某个事务，记录在自身节点上发生的重做-撤销历史，并记录该事务接下来要发往的节点。这样，就可以在多个节点之间维护一份完整的重做-撤销历史。

这里还有大量有趣的思考空间，尤其是关于内存文件备份数据库——它们本身就是一种分布式数据库——以及如何将这些内存和文件后端部分进一步分布到多个节点上。

事务与编程语言

在论文的最后部分，Gray 非常简要地描述了如何将他在事务方面的研究成果融入未来的编程语言。其中描述的一部分语言特性与 Java 或 Objective-C 的方法级锁非常相似（在 Java 中，你可以在方法上加上 synchronized 关键字，它会透明地生成一个锁）。

另一部分特性则较少被采用（虽然我觉得 McCarthy 设计的 Elephant 语言——我对它的全部了解就是它的口号是“大象永不忘记”——可能与之相关），但看起来非常吸引人：

在语言层面提供支持来维护事务所需的重做和撤销日志；在语言层面提供支持来标记属性为真实（real）、稳定（stable）、可恢复易失（recoverable-volatile）和易失（volatile），并让语言实现负责维护实现稳定和可恢复易失属性所需的所有记录工作。

这可能是我年轻导致的局限，但我目前还没见过哪种通用编程语言真正融入了这些特性。不过我认为，为 Python（或其他你喜欢的语言）开发一个支持这种面向事务和面向持久化编程范式的库，应该是一件相当直截了当的事情。

最后感想

《A Transaction Model》是一篇非常易读的论文，包含了许多有趣的想法，同时也是学习事务的绝佳入门读物。阅读一篇已经发表二十六年却依然完全切题的论文，总让人感到不可思议，而这篇论文无疑属于这一类。

对我来说最有意思的部分——正如之前提到的——是容错和对失败事务的恢复，我接下来会去查阅论文中引用的文献，寻找更多阅读材料。
