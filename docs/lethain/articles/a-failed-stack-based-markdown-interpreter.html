一个失败的基于栈的 Markdown 解释器

2009-09-27 · 阅读原文

我周末的一个项目是尝试用 Erlang 写一个基于栈的 Markdown 解释器。首先要承认，这个项目在完整性和性能上都失败了。

Markdown 的行内语法用栈来解析非常直截了当：

*test*
**test**
`test`
[test][http://test.com/ "test")
[test]: http://test.com/ "test"
[test][test]

即使是像 *test **this** out `please *if you won't mind* it`* 这样相当复杂的嵌套组合，用基于栈的解释器也容易处理，尽管如果用正则表达式来实现可能会非常复杂。

然而，Markdown 的多行结构用朴素的实现就变得非常棘手，或者至少在缺乏前期规划的朴素实现下是如此。

以无序列表的语法为例：

- this is a list
- yep, still a list
- still a list

在创建每个 <li> 元素之前，你需要检查栈上是否已经存在 <ul> 元素。如果没有，就添加它，否则继续。关闭标签则更复杂一些，需要在关闭 <li> 元素时检查下一行内容并做出判断。

接下来是引用块（blockquotes），其行为与 <ul> 类似，只是栈上没有 <li> 元素来帮助跟踪当前位置。

然后是代码块，其行为与引用块类似。

再就是段落，默认情况下没有被其他标签包裹的文本都会被视为段落。

将这些结构与多级缩进以及对换行符处理不一致（引用块里的换行会变成空格，而 pre 块里的换行仍保持换行等）结合起来，这次初始实现中缺乏规划的问题就显得极为致命。

下面是这个初始实现取得的一些进展细节，但我现在要重新从头设计多行解析的部分。我还没决定是否继续为多行解析保留基于栈的概念，但我倾向于先做一个预编译阶段，构建出所有多行结构的 DOM，然后只对单行内容使用栈解析器。

性能

对于大型文档来说，性能也相当糟糕。其中有一些明显的 O(n^2) 操作（将累积的二进制数据合并成字符串再转回二进制不可能是个廉价操作），此外即兴实现也可能带来一些不那么明显的性能问题。
