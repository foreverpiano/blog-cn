一个失败的基于栈的 Markdown 解释器

2009-09-27 · 阅读原文

我周末的一个项目是使用 Erlang 写一个基于栈的 Markdown 解释器。首先我要承认，这个项目在完整性和性能上都失败了。

Markdown 的行内部分使用栈来解析非常直截了当：

*test*
**test**
`test`
[test][http://test.com/ "test")
[test]: http://test.com/ "test"
[test][test]

即使是 *test **this** out `please *if you won't mind* it`* 这样相当复杂的组合，用基于栈的解释器处理也很容易，尽管如果依赖正则表达式来解决可能会相当复杂。

然而，Markdown 的多行结构用朴素的实现方式会变得非常 awkward，至少在缺乏规划的朴素实现中是如此。

考虑无序列表的语法：

- this is a list
- yep, still a list
- still a list

在创建每个 <li> 元素之前，你需要检查栈上是否已经存在 <ul> 元素。如果没有，就添加它，否则继续。关闭操作则更为复杂，需要在关闭 <li> 元素时检查下一行并做出判断。

然后是 blockquote，其行为与 <ul> 类似，只是栈上没有 <li> 元素可用于跟踪当前位置。

接着是代码块，其行为类似于 blockquote。

再然后是段落，对于没有被封闭标签包围的文本会默认出现。

将这些东西与多级缩进以及对换行符不一致的处理（blockquote 中的换行会变成空格，而 pre 块中仍保留换行，等等）结合起来，这次第一个实现中缺乏规划就显得极为致命。

下面是一些关于这个第一个实现所取得进展的更多细节，但我得回到绘图板重新设计多行部分的处理。我目前还没有决定是否继续为多行解析坚持使用基于栈的概念，但我倾向于先做一个预编译阶段，构建所有多行结构的 DOM，然后仅对单独的行使用栈解析器。

第一个问题可以通过在输入末尾添加一个换行符来解决，但它其实应该在当前形式下就能正常工作。第二个问题揭示了根本性的规划缺失，这导致这个部分实现变得极其难以修改，也使得它永远无法完全符合标准。

你会注意到测试并没有覆盖多层级结构。设计上已经考虑到了它们，我也相当确信让它们工作起来会比较直接，但老实说，多行解析的整体设计存在足够严重的缺陷，不值得再花功夫去完善。

性能

test_performance(N) ->
    Str1 = "* **this is a test** *and so is this*\n* another line\n\n1. a line\n2. a line2\n3. another line\n\n",
    Str2 = ">> blockquote\n>> blockquote2\n\n    pre block1\n    same pre block\n\n",
    Str3 = "[test](http://test.com \"this\")\ this out\n ``code block``\n\n",
    Str = lists:append([Str1, Str2, Str3]),
    LongStr = lists:append(lists:map(fun(_n) -> Str end, lists:seq(0,100))),
    {Time, _} = timer:tc(markdown, markdown, [LongStr]),
    Seconds = Time / 1000000.0,
    io:format("~p chars took ~p seconds~n", [length(LongStr), Seconds]).

对于大型文档来说，性能也远谈不上好看。存在一些明显的 O(n^2) 操作（将累积的二进制数据合并成字符串然后再转换回二进制不可能是个廉价操作），而且这个临时实现的其他一些性能影响可能还不那么明显。

经过一些后续工作之后……

我把多行逻辑重构为更系统化的形式（概念与之前的逻辑类似，但实现上更加系统化），现在它已经能通过所有测试了。唯一缺失的功能是缩进列表。这点 admittedly 还是相当重要的。
