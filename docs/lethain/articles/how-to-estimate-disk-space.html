如何估算磁盘空间

2022-07-08 · 阅读原文

几年前在为 Nelson Elhage 面试 Staff Engineer 时，他提到“估算”是一项特别有价值的技能。当时我并没有深入思考过估算作为一项技能，但他的话让我想起自己做过的最棒的一次架构面试。候选人通过询问几个关键细节（据我回忆是：每秒查询数、预期行数以及必要的列），显著缩小了可能的解决方案范围。

一直以来，我在估算磁盘空间方面都不太擅长，于是决定花几个小时专门练习这项技能，结果就整理成了这些笔记，希望对其他想提升估算能力的人也有帮助。我会先分享几个估算磁盘空间的有用规则，然后提供一个 SQLite3 示例代码来说明如何验证估算结果。

Kilobytes（1000 字节）和 Kibibytes（1024 字节）

估算大小时第一个容易混淆的地方是：1 kilobyte 到底是 1024 字节还是 1000 字节？“正确答案”是“kilobyte”（kB）等于 1000 字节，而“kibibyte”（KiB）等于 1024 字节。这种区分也适用于其他单位，例如 megabyte（MB，1000^2）与 mebibyte（MiB，1024^2），以及 gigabyte（GB，1000^3）与 gibibyte（GiB，1024^3）。

这里有三个关键点：（1）同时理解 kilobyte 和 kibibyte 这两种单位；（2）意识到和你沟通的人可能不熟悉 kibibyte 系列单位；（3）根据对方的熟悉程度调整自己的表达方式。在现实中，过于追求技术上的绝对正确并不会得分。

UTF-8、整数等类型的尺寸估算

虽然值得熟悉的数据类型有很多，但最常用的是以下几种：

maxRepresentableIntegerInNBytes(N) = 2 ^ (N bytes * 8 bits) - 1

2 ^ (2 bytes * 8 bits) -1 = 65535
UTF-8 字符的编码长度为 1-4 字节。你应该按 1、2、3 还是 4 字节来估算，取决于你要编码的内容。例如，如果只编码 ASCII 字符，那么 1 字节就足够了。最重要的是能够解释你的理由。比如，说你采取最保守的情况，按每个字符 4 字节计算，是合理的。 以 UTF-8 尺寸作为基准，你可以估算 string、varchar、text 或其他类似字段的大小。这些字段的具体开销会根据实际使用的存储技术有较大差异。 整数的尺寸取决于你要存储的最大值，一个好的基准是 4 字节。如果你想更精确，可以先确定整数的最大值，然后计算出表示它需要的字节数。例如，用 2 字节能表示的最大数字是 65535。 float 通常用 4 字节存储。 boolean 在很多数据库中（例如 MySQL）用 1 字节整数表示。 enum 在很多数据库中（例如 MySQL）用 2 字节整数表示。 datetime 在很多数据库中（例如 MySQL）用 5 字节表示。

掌握这些规则后，我们来做一次实战练习，估算一个数据库的大小。假设数据库中有 10,000 个人，我们记录每个人的年龄和姓名。平均姓名长度为 25 个字符，我们支持的最大年龄是 125。这个数据库大概需要多少空间？

bytesPerName = 25 characters * 4 bytes = 100 bytes
bytesPerAge = 1 byte  # because 2^(1 bytes * 8bits) = 255
bytesPerRow = 100 bytes + 1 byte
totalBytes = 101 bytes * 10,000 rows
totalKiloBytes = (101 * 10000) / 1000          # 1,100 kB
totalMegaBytes = (101 * 10000) / (1000 * 1000)   # 1.1 MB

所以，大约需要 1.1 MB 来存储这些数据。或者说是 0.96 MiB，计算过程如下：

(101 * 10000) / (1024 * 1024)  # 0.96 MiB

现在你已经可以估算各种数据集的大致大小了。

索引、复制等因素

理论上存储数据的成本和实际在数据库中存储数据的成本之间存在差距。你可能在使用基于副本的系统，例如 MongoDB 或 Cassandra，它们会为每份数据保存三份拷贝；也可能在使用主从复制系统，为每份数据保存两份拷贝。这种情况下存储开销很好计算（分别是基础成本的 3 倍或 2 倍）。

索引是典型的用额外存储换取更短查询时间的 tradeoff，但它具体会占用多少存储空间取决于索引本身的细节。一个简单的索引估算方法是：计算索引中包含的列的总大小，乘以索引的行数，然后把这个结果加到基础数据的存储成本上。如果创建一个包含所有字段的索引，那么可以粗略估计总存储成本会变成原来的两倍。

根据所使用的具体数据库，还会有其他功能也会占用空间。要真正理解它们对总体大小的影响，需要更深入地了解那个数据库。而最好的方法，就是直接用该数据库去验证你的估算。

使用 SQLite3 进行验证

好消息是验证数据大小相对简单，下面我们就用 Python 和 SQLite3 来演示。我们将重新创建前面提到的场景：10,000 行记录，每行包含一个 25 字符的姓名和一个年龄。

import uuid
import random
import sqlite3

def generate_users(path, rows):
    db = sqlite3.connect(path)
    cursor = db.cursor()
    cursor.execute("drop table if exists users")
    cursor.execute("create table users (name, age)")
    for i in range(rows):
        name = str(uuid.uuid4())[:25]
        age = random.randint(0, 125)
        cursor.execute("insert into users values (?, ?)", (name, age))
    db.commit()
    db.close()

if __name__ == "__main__":
    generate_users("users.db", 10000)

之前我们估算的结果是 0.96 MiB，但实际运行这个脚本后发现只有 344 KiB，大约是预期空间的三分之一多一点。稍微调试一下计算过程，我们会发现之前假设每个字符占 4 字节，但实际生成的姓名（截断后的 UUID4）全是 ASCII 字符，因此每个字符实际只占 1 字节。让我们据此重新估算：

bytesPerName = 25 characters * 1 byte = 25 bytes
bytesPerAge = 1 byte
bytesPerRow = 26 bytes
totalKibiBytes = (26 * 10,000) / 1024  # 245 KIB

现在这个结果已经相当接近了，当然还会存在一些额外的开销。比如 SQLite3 会自动创建一个“rowid”列作为主键，它是一个 64 位整数，需要 4 字节。如果我们把这 4 字节加到之前每行 26 字节的估算中，就会得到大约 293 KiB 的估算值，和实际结果已经非常接近了。

去估算大小吧

估算数据大小是一项相对简单易学的技能，它同时具有（a）很容易一直没学过和（b）一旦学会就非常有用的特点。它在系统架构设计、调试复杂分布式系统问题，以及面试中讨论架构问题时都很有帮助。磁盘空间估算能帮助你回答以下一些关键问题：

数据能否放进内存？能否放在一台带 SSD 的服务器上？这部分数据是否需要分片到多台服务器？需要多少台？这 个索引能否放在一台服务器上？如果不能，应该如何合理地对索引进行分区？等等。

尽管我已经使用这项技巧有一段时间了，但仍然惊讶于它能如此有效地收窄解决方案的空间。
