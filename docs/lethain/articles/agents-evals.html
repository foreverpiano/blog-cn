构建内部 Agent：用 Evals 验证工作流

2025-12-31 · 阅读原文

每当有新的 pull request 提交到我们 Agent 的 GitHub 仓库时，我们都会对它运行一系列 CI/CD 操作。我们会运行严格的 linter、类型检查，以及大量单元测试。这些措施效果都不错，但它们都无法对完整的工作流进行端到端测试。为此，我们引入了 eval 流水线。

这是 构建内部 Agent 系列文章的一部分。

为什么 Evals 很重要

运行 Agent 的执行框架虽然有很多有趣的细节，但整体上还是相当简单的：虚拟文件管理、工具调用以及上下文窗口管理。然而，即便所有底层组件都正确，也非常容易写出效果不佳的 prompt。Evals 就是解决这个问题的一种工具，它能将你的 prompt 和工具放在一起运行，并对结果进行评分。

我们如何实现它

我有幸主导了 Imprint 的 Sierra 在聊天和语音支持上的实现，我想在此感谢他们的方案，它深刻影响了我对什么可行、什么不可行的判断。

Sierra 方法的核心组成部分包括：

Sierra 将 Agent 实现为 React 风格的代码与执行框架的结合，前者提供工具和逐步披露的上下文，后者负责运行这些代码。Sierra 允许你的代码为对话打上标签，例如“otp-code-sent”或“lang-spanish”，这些标签可用于过滤对话，也支持后续会提到的其他用例。Sierra Agent 的每个工具都同时提供真实实现和模拟实现。例如，一个搜索知识库的工具，其真实版本会直接调用 API，而模拟版本则返回静态（或本地生成）的结果，供测试使用。Sierra 将其 eval 实现称为“simulations”。你可以在代码中或通过 UI 功能创建任意数量的 simulations。每项评估都包含一个初始 prompt、供执行框架使用的场景元数据，以及用于判断评估是否成功的评判标准。这些评判标准同时包含主观和客观两类。主观标准采用“agent as judge”的方式，判断某些条件是否满足（例如回复是否友好）。客观标准则是特定标签是否被添加（“login-successful”）或未被添加（“login-failed”）到对话中。

虽然我们大体上遵循了 Sierra 方案所铺设的路线，但在标签（tags）这个概念上我们做了调整。对于客观评估，我们完全依赖于工具是否被调用。Sierra 的标签机制更加灵活，但由于我们的工作流主要是由 prompt 驱动而非代码驱动的，因此对我们来说并不容易采用。

总体而言，遵循这个标准实现对我们来说效果良好。

实际效果如何？

目前运行得还不错，但远没有达到我原本的预期。核心挑战在于这些 eval 测试引入的非确定性：实践中，当它们全部失败时能给出很强的信号，全部通过时也能给出很强的信号，但大多数运行结果都处于两者之间。这在很大程度上是因为 eval prompt 和模拟工具返回结果写得比较粗糙，我相信通过一些投入（比如我之前通过仔细调优，让我们的 Sierra 测试几乎总是通过，虽然也并非完全可靠），可以让它们更稳定地通过。

最大的问题是，我们依赖 prompt 驱动的工作流而非代码驱动的工作流，这带来了大量非确定性，而我目前还没有办法在不做上述 prompt 和 mock 调优的情况下解决这个问题。

接下来要做什么？

有三个显而易见的后续方向：

对 prompt 和模拟工具调用进行更多调优，使 eval 在概率上更可靠；我虽然不太好意思说出口，但我怀疑我们需要对失败的 eval 进行重试（例如“3 次中至少通过 1 次”），这样才能将其作为 CI/CD 中的阻塞机制；这也凸显了 LLM 驱动工作流的普遍局限性，我怀疑对于更复杂的工作流，我最终还是得将其从 LLM 驱动的方式迁移出去，才能让它们工作得更稳定。

总之，我非常庆幸我们引入了 evals，它们已经成为我们评估工作流不可或缺的机制，只是我们发现很难将其稳定地落地为一个可靠的阻塞工具，而更多是作为具有方向性参考意义的信息。
