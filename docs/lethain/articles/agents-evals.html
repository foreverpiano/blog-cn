构建内部 Agent：用 Evals 验证工作流

2025-12-31 · 阅读原文

每当有新的 pull request 提交到我们 Agent 的 GitHub 仓库时，我们都会对其运行一系列 CI/CD 操作。我们会运行严格的 linter、类型检查，以及大量单元测试。这些措施效果都不错，但它们都无法对完整的工作流进行端到端测试。为此，我们引入了 eval pipeline。

本文是 构建内部 Agent 系列的一部分。

为什么 Evals 很重要

运行 Agent 的执行框架虽然包含很多有趣的细节，但整体上相当简单：虚拟文件管理、工具调用，以及上下文窗口管理。然而，即便所有底层组件都正确，也很容易写出效果不佳的 prompt。Evals 正是解决这一问题的工具，它能让你的 prompt 和工具协同工作，并对结果进行评分。

我们的实现方式

我有幸主导了 Imprint 基于 Sierra 实现的聊天和语音支持系统，我想在此感谢他们的方案，它深刻影响了我对什么可行、什么不可行的判断。

Sierra 方案的核心组成部分包括：

Sierra 将 Agent 实现为 React 风格的代码与执行框架的组合，前者提供工具和渐进式上下文披露，后者负责运行这些代码。Sierra 允许你的代码为对话打上标签，例如 “otp-code-sent” 或 “lang-spanish”，这些标签可用于过滤对话，也支持后面会提到的其他场景。Sierra 中为 Agent 实现的每种工具都同时提供真实实现和 mock 实现。例如，对于搜索知识库的工具，真实版本会直接调用其 API，而 mock 版本则返回静态（或本地生成）的结果，用于测试。Sierra 将其 eval 实现称为 “simulations”（模拟）。你可以在代码中或通过 UI 功能创建任意数量的模拟。每个评估都包含初始 prompt、供执行框架使用的场景元数据，以及用于判断评估是否成功的评估标准。这些评估标准同时包含主观和客观两类。主观标准采用 “agent as judge”（Agent 作为裁判）的方式，判断某些条件是否满足（例如回复是否友好）。客观标准则检查对话是否添加了特定标签（例如 “login-successful”）或未添加特定标签（例如 “login-failed”）。

虽然我们大体上遵循了 Sierra 实现所提供的路线，但在标签（tags）概念上我们做了调整。对于客观评估，我们完全依赖于工具是否被调用。Sierra 的标签机制更加灵活，但由于我们的工作流主要是 prompt 驱动而非代码驱动，因此对我们来说并不容易采用。

总的来说，遵循这一标准实现对我们来说效果良好。

实际效果如何？

目前运行得还不错，但远没有达到我最初的预期。核心挑战在于这些 eval 测试引入的非确定性：实践中，当所有测试都失败时信号非常强烈，当全部通过时信号也很强，但大多数运行结果都介于两者之间。这在很大程度上是因为 eval 的 prompt 和 mock 工具返回结果写得较为粗糙。我相信通过一些努力可以让它们更稳定地通过（例如，我曾通过仔细调优让我们的 Sierra 测试几乎总是通过，尽管即使那样也并非完全可靠）。

最大的问题是，我们对 prompt 驱动工作流的依赖而非代码驱动的工作流，引入了大量非确定性，而我目前还没有办法在不进行上述 prompt 和 mock 调优的情况下解决这个问题。

接下来做什么？

有三个明显的后续方向：

对 prompt 和 mocked 工具调用进行更多调优，使 eval 在概率上更加可靠；虽然说出来有点尴尬，但我怀疑我们需要对失败的 eval 进行重试（例如“三次中至少通过一次”），才能将其作为 CI/CD 中的阻塞机制；这也凸显了 LLM 驱动工作流的普遍局限性，我怀疑对于更复杂的工作流，我最终需要将其从 LLM 驱动的方式转向其他实现，才能让它们工作得更稳定。

总而言之，我非常高兴我们引入了 evals，它们是我们评估工作流的重要机制，但我们发现很难将其一致地落地为一个可以依赖的阻塞工具，而更多是作为具有方向性参考意义的信息。
