Reacji 和自定义表情

Slack 的表情回应（emoji reactions），也叫 reacji，是大家在频道中与消息互动的常见方式。

在我们正在开发的应用中，我考虑加入 :ididit: 和 :udidit: 这两个表情符号。这样大家就可以用它们把自己的完成事项加入成就清单，也可以用它们把别人的成就加到对应人的清单里。我注意到有些人不喜欢或不愿意记录自己的成就，这个设计可以让团队和社区以一种轻松有趣的方式来帮助他们。

通过工作区左上角菜单中的“Customize Slack”选项来添加这些表情。

接着点击“Add custom emoji”，然后想办法创建一张图片。我当时用的是 Omnigraffle，因为它正好开着，不过你大概会用别的工具。

上传你的图片，将其命名为 :udidit:，然后点击保存。之后再用同样的方法添加 :ididit: 表情。

现在我们有了自定义表情，接下来需要想办法在有人使用它们时收到通知。

订阅 reaction_added 事件

每当有人添加表情时，如果你的应用订阅了对应事件，Events API 就会触发一个 reaction_added 事件。

要订阅的话，请前往应用仪表盘的“Event Subscriptions”页面，展开“Subscribe to workspace events”，然后选择 reaction_added。

记得点击下方的“Save Changes”，并用新的权限重新安装你的应用。

处理 reaction_added 事件

现在我们已经能收到这些事件，需要扩展 event_callback_event 函数，让它能够处理 reaction_added 事件，而不是直接报错。

def event_callback_event(request, parsed):
    event_type = parsed['event']['type']
    if event_type == 'app_home_opened':
        return app_home_opened_event(request, parsed)
    elif event_type == 'reaction_added':
        return reaction_added_event(request, parsed)
    else:
        raise Exception("unable to handle event_callback event type: %s" % \
                        (event_type,))

对于 reaction_added_event 的第一次实现，我们先简单地把收到的消息记录下来，以便查看它的参数结构。

def reaction_added_event(request, parsed):

我们首先要做的是筛选出我们关心的反应。我们只对之前添加的两个表情 :ididit: 和 :udidit: 做出响应，并且只处理针对消息（message）的反应，忽略文件等其他类型。

def reaction_added_event(request, parsed):
    event = parsed['event']
    if event['reaction'] in ('ididit', 'udidit'):
        if event['item']['type'] == 'message':
            print(parsed)
            print("yes, handling this message")

    return "Ok"

过滤出合适的消息后，我们仍然无法确定消息的具体内容：你或者对方到底完成了什么？要解决这个问题，我们需要调用 conversations.history 接口，具体方法可参考“Retrieving messages”文档。

添加 channels:history 权限

在调用 channels.history 接口之前，我们需要先申请 channels:history 这个 OAuth 权限。进入应用仪表盘，点击“OAuth & Permissions”，向下滚动找到 Scopes 区域，添加 channels:history。

完成后，重新安装你的应用以申请新增的 OAuth 权限。我们之前一直使用的是 bot token，而不是 OAuth token，因此还需要把 OAuth token 加入到 env.yaml 文件中。你的 OAuth token 可以在应用管理页面的“OAuth & Permissions”中找到，字段名为 OAuth Access Token。

SLACK_SIGN_SECRET: your-secret
SLACK_BOT_TOKEN: your-bot-token
SLACK_OAUTH_TOKEN: your-oauth-token

配置好之后，我们就可以使用这个新权限了。

调用 channels.history

之前我们实现了一个 slack_api 工具函数来简化 Slack API 调用，但这次无法直接复用它，原因有两个。首先，conversations.history 要求使用 application/x-www-form-urlencoded 格式，而其他接口接受 application/json；其次，这个接口需要使用 GET 方法而不是 POST，不过这一点可以通过把 requests 的方法名作为字符串传入来轻松解决。

为了快速绕过这些限制，我们将编写一个 get_message 函数直接调用 API，而不是在 slack_api 的基础上扩展，尽管这有点令人遗憾。

def get_message(channel, msg_ts):
    url = "https://slack.com/api/conversations.history"
    bot_token = os.environ['SLACK_OAUTH_TOKEN'].encode('utf-8')
    params = {
        'token': bot_token,
        'channel': channel,
        'latest': msg_ts,
        'limit': 1,
        'inclusive': True
    }
    resp = requests.get(url, params=params)
    return resp.json()

然后我们更新 reaction_added_event，让它使用这个新函数。

def reaction_added_event(request, parsed):
    print(parsed)
    event = parsed['event']
    if event['reaction'] in ('ididit', 'udidit'):
        item = event['item']
        if item['type'] == 'message':
            print("yes, handling this message")
            channel = item['channel']
            msg_ts = item['ts']
            msg = get_message(channel, msg_ts)
            print(msg)
    return "Ok"

我们真正关心的是 messages/0/user 和 messages/0/text，根据使用的是 :ididit: 还是 :udidit:，我们可以把这条消息分别加入说话者或被标记者的成就列表。

整合到一起

比较明显的是，我们目前还没有数据库来存储这些数据，这部分将留到下一篇中解决。现在我们先定义一个存储数据的接口，也就是 reflect 函数。

def reflect(team_id, user_id, text):
    print("Reflected(%s, %s): %s" % (team_id, user_id, text))

接着更新 reaction_added_event，让它调用这个函数。

def reaction_added_event(request, parsed):
    event = parsed['event']
    if event['reaction'] in ('ididit', 'udidit'):
        item = event['item']
        event_user_id = event['user']
        if item['type'] == 'message':
            channel = item['channel']
            msg_ts = item['ts']
            msg_resp = get_message(channel, msg_ts)
            msg = msg_resp['messages'][0]
            msg_team_id, msg_user_id, text  = \
              msg['team'], msg['user'], msg['text']
            if event['reaction'] == 'ididit':
                reflect(msg_team_id, msg_user_id, text)
            elif event['reaction'] == 'udidit':
                reflect(msg_team_id, event_user_id, text)
    return "Ok"

再次部署后，我们就成功集成了 reacji！

把 reacji 当作界面

刚开始使用 Slack 时，我以为 reacji 只是个小花招，后来当我看到大家自然而然地用 :plus: 表情对消息进行投票时，才恍然大悟。没有人要求他们投票，却自然而然地发生了。这种自然的自由，配合严格的约束（它们只是带计数的小图片），催生出了许多新颖的使用模式。

没有哪个 Slack 应用必须集成 reacji，但我见过很多富有创意的集成，它们理解用户已有的行为模式，并通过自动化操作来增强这些模式。

reacji 作为用户界面的另一个优势是，它比 Slash Command 更容易被发现，后者通常对其他用户是隐藏的。有机增长和采用率是一款成功应用的基础，而 reacji 正是实现这一目标的强大机制。

集成中的摩擦

我必须承认，自己对让 reacji 正常工作花了多长时间感到有些惊讶。因为我开始写这篇文章时以为大部分必要工作已经完成，只需引入一个新事件即可。

结果我需要增加一种新的 API 集成方式，因为 conversations.history 不支持 JSON 格式；同时还需要一个新的 API token，因为之前我一直使用 bot token 而不是 user token。单独来看，Slack 的每个 API 都设计得非常优秀，但放在一起使用时就会显现出一定程度的摩擦。

这是所有庞大而复杂 API 都面临的共同挑战。我目前正在阅读《Building Evolutionary Architectures》，它对我之前在收回不合理的软件一文中讨论的想法进行了更好、更系统的阐述。API 的退化是可以预防的，但需要非常刻意地使用我文中所说的“asserted properties”，或者 Ford/Parsons/Kua 所说的“fitness functions”。
