让 Slack 应用响应表情回应（reacji）。

2019-11-09 · 阅读原文

这篇文章延续了在 GCP 上用 Python 创建 Slack 应用系列，在在 Python 中为 Slack 应用添加 App Home之后继续撰写。Slack 中许多微妙而自然产生的沟通模式，都是通过给消息添加表情符号（emoji）来实现的。我觉得在当前正在开发的这个应用中利用这种趣味性，会是一件很有意思的事。

本文从 commit 4120 开始，到 commit 08eb 结束。

表情回应（Reacji）和自定义表情

Slack 的表情回应（emoji reactions 或称 reacji）是大家在频道中与消息互动的常用方式。

在我们正在开发的应用中，我考虑加入 :ididit: 和 :udidit: 两个表情符号。大家可以用它们把自己的成就加入到成就清单，也可以用它们把别人的成就加到对方的清单里。我注意到有些人不喜欢或不重视记录自己的成就，这个设计或许能以一种有趣的方式，让团队和社区来帮助他们完成记录。

通过工作区左上角菜单中的“Customize Slack”选项来添加这些表情。

进入后点击“Add custom emoji”，然后想办法创建一张图片。我当时用 Omnigraffle 是因为它正好开着，不过你大概会用其他工具。

上传你的图片，将其命名为 :udidit: 并点击保存。然后再为 :ididit: 表情重复相同的操作。

现在我们有了自定义表情，接下来需要弄清楚如何在它们被使用时收到通知。

订阅 reaction_added 事件

每当有人添加表情符号时，如果您已订阅，就会向 Events API 触发一个对应的 reaction_added 事件。

要订阅，请前往应用仪表盘的“Event Subscriptions”页面，展开“Subscribe to workspace events”，然后选择 reaction_added。

记得点击下方的“Save Changes”，并用新的权限重新安装你的应用。

处理 reaction_added 事件

现在我们已经能收到这些事件，需要扩展 event_callback_event 来处理 reaction_added 事件，而不是让它报错。

def event_callback_event(request, parsed):
    event_type = parsed['event']['type']
    if event_type == 'app_home_opened':
        return app_home_opened_event(request, parsed)
    elif event_type == 'reaction_added':
        return reaction_added_event(request, parsed)
    else:
        raise Exception("unable to handle event_callback event type: %s" % \
                        (event_type,))

我们首先要做的是筛选出我们关心的表情回应。我们只对之前添加的两个表情（:ididit: 和 :udidit:）做出反应，并且只处理针对消息（message）的回应，忽略文件等其他类型。

def reaction_added_event(request, parsed):

        if event['item']['type'] == 'message':

筛选出合适的消息后，我们仍然不清楚消息的具体内容：你或者对方到底完成了什么？要解决这个问题，我们需要调用 conversations.history 接口，具体方法可参考“Retrieving messages”文档。

添加 channels:history 权限

在调用 channels.history 接口之前，我们需要先申请 channels:history 这个 OAuth 权限。进入应用仪表盘，点击“OAuth & Permissions”，向下滚动找到 Scopes 区域，添加 channels:history。

之后，重新安装你的应用以申请新增的 OAuth 权限。我们目前一直使用的是 bot token 而非 OAuth token，因此还需要把 OAuth token 添加到 env.yaml 文件中。你的 OAuth token 可以在应用管理后台的“OAuth & Permissions”页面中找到，字段名为“OAuth Access Token”。

SLACK_SIGN_SECRET: your-secret
SLACK_BOT_TOKEN: your-bot-token
SLACK_OAUTH_TOKEN: your-oauth-token

配置完成后，我们就可以使用新的权限了。

调用 channels.history

我们之前实现了一个 slack_api 工具函数来简化 Slack API 调用，但这次无法轻易复用它。原因有两个：首先，conversations.history 需要 application/x-www-form-urlencoded 格式的请求，而其他接口接受的是 application/json；其次，这个接口要求使用 GET 而不是 POST（虽然用 requests.request 函数传入 HTTP 方法字符串就能解决）。

为了快速绕过这些限制，我们将编写一个 get_message 函数直接调用 API，而不是基于 slack_api 来实现，虽然这有点不太理想。

def get_message(channel, msg_ts):
    url = "https://slack.com/api/conversations.history"
    bot_token = os.environ['SLACK_OAUTH_TOKEN'].encode('utf-8')
    params = {
        'token': bot_token,
        'channel': channel,
        'latest': msg_ts,
        'limit': 1,
        'inclusive': True
    }
    resp = requests.get(url, params=params)
    return resp.json()

接着我们更新 reaction_added_event，让它使用这个新函数。

def reaction_added_event(request, parsed):
    print(parsed)
    event = parsed['event']
    if event['reaction'] in ('ididit', 'udidit'):
        item = event['item']
        if item['type'] == 'message':
            print("yes, handling this message")
            channel = item['channel']
            msg_ts = item['ts']
            msg = get_message(channel, msg_ts)
            print(msg)
    return "Ok"

整合起来

比较明显的是，我们目前还没有数据库来存储这些数据，这个问题将在下一篇文章中解决。目前我们先定义一个存储数据的接口，也就是 reflect 函数。

def reflect(team_id, user_id, text):
    print("Reflected(%s, %s): %s" % (team_id, user_id, text))

然后更新 reaction_added_event，让它调用这个函数。

def reaction_added_event(request, parsed):
    event = parsed['event']
    if event['reaction'] in ('ididit', 'udidit'):
        item = event['item']
        event_user_id = event['user']
        if item['type'] == 'message':
            channel = item['channel']
            msg_ts = item['ts']
            msg_resp = get_message(channel, msg_ts)
            msg = msg_resp['messages'][0]
            msg_team_id, msg_user_id, text  = \
              msg['team'], msg['user'], msg['text']
            if event['reaction'] == 'ididit':
                reflect(msg_team_id, msg_user_id, text)
            elif event['reaction'] == 'udidit':
                reflect(msg_team_id, event_user_id, text)
    return "Ok"

再次部署后，我们就成功接入了 reacji 功能！

Reacji 作为交互界面

刚开始使用 Slack 时，我以为 reacji 只是个小把戏，但后来当我看到大家自然而然地用 :plus: 表情对消息进行投票时，我突然开了窍。没有人要求他们投票，这种行为却自然而然地出现了。正是这种自然的自由，加上严格的约束（它们只是带计数的微小图片），催生出了大量新颖的使用模式。

并非每个 Slack 应用都必须接入 reacji，但我见过很多富有创意的集成，它们先承认用户已有的行为模式，再通过自动化动作来增强这些模式。

reacji 作为用户界面的另一个巨大优势是，它比 Slash Commands 更容易被发现，后者通常对其他用户是隐藏的。有机增长和采用率是应用成功的基础，而 reacji 正是一种强大的实现机制。

集成中的摩擦

我得承认，这次让 reacji 正常工作花费的时间比我预想的要长。我开始写这篇文章时，本以为大部分准备工作已经完成，只需要引入一个新事件就行了。

结果我需要增加一种新的 API 调用方式，因为 conversations.history 不支持 JSON 格式；同时还需要申请一个新的 API token，因为之前一直用的是 bot token 而不是 user token。单独来看，每个 Slack API 都设计得非常优秀，但组合在一起使用时，就会显现出一定的摩擦。

这是大型、复杂 API 普遍面临的问题。我目前正在阅读《Building Evolutionary Architectures》，它对我在收回不合理的软件中讨论的思想进行了更好、更系统的阐述。API 的退化是可以预防的，但需要非常刻意地使用我文中称为“asserted properties”，而在 Ford/Parsons/Kua 的书中称为“fitness functions”的机制。
