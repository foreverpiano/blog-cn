衡量工程组织

2023-01-02 · 阅读原文

过去几年，我一直主持一个由工程高管组成的学习圈。最常讨论的话题是职业管理——下一步我该做什么？第二常见的话题则是如何衡量工程团队和组织——我的 CEO 要求我每月汇报工程指标，我到底应该在报告里放些什么？

任何关于衡量工程组织的讨论，都会迅速引发强烈的意见。“除了冲刺点数（sprint points）什么都行！”“直接用 SPACE 框架！”“跟踪事故频率！”“等等，绝对不要跟踪事故频率！”“随便做一张好看的图表就好，反正他们也不会仔细看！”所有这些回答，甚至包括最后一个，都包含一定道理，但它们都跳过了一个重要的前提：衡量工程的原因有很多，提出需求的利益相关方也各不相同，应对每一种需求都需要不同的方法。

衡量工程组织没有单一的解决方案，而是存在多种衡量模式，每一种都适用于特定的场景。成为一名高效的工程高管，就是不断丰富自己的工具箱，并保持灵活性，根据不同需求选择合适的方法。

你可以使用《Engineering Metrics Update》模板来汇报这些指标。

这是 O'Reilly 出版的《The Engineering Executive’s Primer》一书中未经编辑的章节。

为自己而衡量

当你进入一个新的高管职位时，CEO 很可能会随口说一句，你需要在“三周后的下一次董事会会议上准备一张工程相关的幻灯片”。这是一个非常令人紧张的时刻——我该怎么做才能不在第一次董事会会议上出丑！——但即使你第一次正式的衡量成果是一张董事会幻灯片，我也不建议从为董事会准备有用的指标开始你的衡量工作。

相反，先从为自己衡量开始。你需要哪些信息才能有效运营工程组织？在开始记录衡量目标时，我建议从以下四个不同的类别入手：

为规划而衡量：什么信息能帮助你与跨职能利益相关方达成一致，决定在一个季度、半年或一年内要交付什么？关键在于，这不是关于你如何交付（“我们是否在使用敏捷？”），而是你要支持项目选择和优先级排序。你需要一个单一的地方来展示工作对业务、产品和工程的影响。你可能会说规划是产品团队的责任，但只有工程团队才能完整呈现工程正在进行的所有项目（例如，产品团队不太可能把你的数据库迁移列入路线图）。从按团队统计已交付项目的数量，以及每个项目的影响开始。为运营而衡量：为了确信你的软件和团队每天都在有效运行，你需要知道什么？把这些看作质量指标会很有帮助，因为它们背后的真正问题是：你如何判断是应该继续执行既定路线图，还是应该紧急集中力量去修复一个关键问题？一些好的起点包括：跟踪事故数量（每次事故都对应一份事故复盘报告）、面向用户的 API 和网站停机分钟数、面向用户的 API 和网站的延迟、相对于核心业务指标归一化的工程成本（例如，通过用每月 API 请求量除以当月工程支出，计算服务最重要 API 的成本）、用户对产品的评分（例如应用商店评分），以及产品 onboarding 流程是否顺利完成的一个宽泛指标（例如，成功访问你网站的用户中有多少百分比最终转化成正式用户？）为优化而衡量：为了有效投入时间提升工程生产力，你需要知道什么？如果你把工程看作一个系统，你如何理解这个系统的反馈回路？值得注意的是，这往往是工程师自己用来衡量在公司工作体验的方式。从 SPACE 框架或其前身 Accelerate 开始。如果这些太重，那就从开发者生产力调查开始。为激励与愿景而衡量：如何简洁地向业务传达工程的变革性影响？如何让潜在候选人、新来的跨职能高管或董事会成员对工程为业务成功做出的贡献感到振奋？维护一份技术投入清单，这些投入把原本不可能的事（“我们无法在不影响整个用户群生产环境的情况下修改破坏性 API”）变成了理所当然、不值一提的事（“我们允许每个 API 集成根据自身情况升级 API 版本，而不是必须按照我们的时间表”）。在公司会议上发言时，以这类跨代际的改进为锚点，并尽量在每个年度规划周期中都纳入至少一项这样的改进。

当讨论衡量时，经常有人反问是否衡量得足够多——我们是不是还应该衡量数据库 CPU 负载、Pull Request 周期时间等等？良好衡量的秘诀其实是真正去衡量某件事。衡量最大的风险是，因为想衡量一切而最终什么都没衡量。你随时可以衡量更多，而且衡量更多是有价值的，但要通过许多小迭代来逐步推进，不要害怕今天就去衡量一些快速且简单的东西。

为利益相关方而衡量

之所以要关注快速衡量而不是完美衡量，一个原因是你公司内部有很多人希望你去衡量各种东西。有些东西你自己认为有内在价值去衡量，但也有 CEO 想让你衡量的、财务部门向你要的、要在月度状态会上汇报的，等等。

虽然需求很多，但好消息是这些请求在各公司之间非常相似，通常可以归入以下四个类别之一：

为 CEO 或董事会而衡量。许多经验丰富的管理者（很可能包括你的 CEO）会通过“inspect”（审查与信任的边界）来管理。这意味着他们希望你衡量某件事、设定一个具体目标，并定期更新达成该目标的进展。他们没有工程背景来管理你的技术决策，因此会把你达成这些目标的能力当作你工程领导力质量的代理。如果他们深入研究你的衡量指标，他们会关注工程对业务战略本身的贡献，而不是工程日常工作中的微观优化。这些指标不需要新颖，最好的做法是复用你为自己而做的衡量。最常见的是复用规划或运营相关的指标。要避免的最大错误是用“为优化而衡量”的指标去向 CEO 汇报。虽然直觉上大家都同意更高的效率会让工程更有影响力，但大多数 CEO 不是工程师，往往无法自然地完成这个跳跃。此外，高效仅仅意味着工程有可能产生影响，而不代表它实际上正在产生影响。为财务部门而衡量。财务团队通常对工程有三个主要问题。第一，实际人力数量与预算人力数量的趋势如何？第二，实际供应商成本与预算供应商成本的趋势如何？第三，哪些工程成本可以被，以及在审计时如何证明其合理性？你通常需要在财务的预算流程框架内与他们配合，这些流程因公司而异，但在同一公司内通常是统一的。资本化与费用化的问题更为微妙，值得详细讨论；我想说的是，默认的方法往往比较繁琐，但几乎总能在财务、审计师和工程师的优先级之间找到一个合理的交汇点——这个方案会让各方都稍有不满，但又能满足所有各方的要求。虽然财务很少主动要求，但我发现与财务在工程投资逻辑上达成一致非常有价值，特别是关于如何在不同业务优先级和业务单元之间分配产能的问题。到了某个阶段，公司内的业务单元会开始争论如何将工程成本分摊到不同项目上（因为工程成本很高，如果分摊太多，会让他们的新项目显示出巨额亏损而不是前景光明），这时拥有一份清晰记录的分配方案会让对话变得建设性得多。为战略性同级组织而衡量。你最好的同级组织会主动与你合作，最大化工程对业务的贡献。乐观地说，这是因为这些职能由开明的业务 visionary 领导。更现实地说，是因为他们的影响力受限于工程的影响力，所以优化工程的影响力，也就同时优化了他们自己的影响力。通常你会发现产品、设计和销售等职能非常适合与工程建立战略合作伙伴关系。你通常可以使用规划所需的相同指标来与这些战略性同级组织有效对齐。为战术性同级组织而衡量。虽然战略性同级组织可能同意根据工作的影响来衡量工程，但更战术性的组织通常会要求基于更具体的成果来衡量工程。例如，客户成功（Customer Success）团队可能会推动以用户工单接受率和解决时间来衡量工程。法务团队可能也希望用法律相关工单的解决时间来衡量你。战术性组织之所以是战术性的，并不是因为它们缺乏战略思考能力，而是因为它们的组织完全以战术方式被考核。如果它们与工程对齐去最大化工程的影响，它们的组织反而会被认为表现不佳。战术性组织自己被具体、可衡量的数字所考核，因此也希望用具体、可衡量的数字来考核工程。找到一个你和同级组织都能同意的指标，确定一个节奏来讨论这个指标在多大程度上真正代表了跨组织的真实需求，并随着时间不断迭代。如何资本化工程成本

为利益相关方衡量往往很耗时，有时甚至会让人觉得有点浪费时间。但如果做得好，虽然仍然耗时，但能节省时间，因为它把混乱、反复出现的讨论，转化成了更简单、更可预测的契约——即维持某些具体、可衡量的结果。

安排你的衡量顺序

光是为自己而衡量的清单就已经很长了，再加上利益相关方的需求，合并后的清单可能会非常冗长。确实，有一条普遍公认的真理：一位工程高管总是渴望有更多工程师来支持自己衡量现有的“必须有”指标清单。你永远不可能真正衡量所有你想衡量的东西。不过，在一两年内，你能够把最重要的部分落地，持续迭代，并建立起对它们真正含义的信心。

我曾试图列出一个具体的清单，明确告诉你第一步应该衡量什么，以避免精力过于分散，但效果并不好。上下文实在太多了，固定清单没有太大用处。相反，我提供三条安排衡量顺序的规则：

有些事情很难衡量，只有当你确定会真正把这些数据纳入决策时才去衡量它们。如果你不太可能根据数据改变自己的方法或优先级，那就衡量一些简单的东西，哪怕它只是。有些事情很容易衡量，即使你不觉得它们特别准确，也要愿意去衡量，以此与利益相关方建立信任。大多数利益相关方更看重你的意图和付出的努力，而不是实际的输出。这是你愿意为工作负责的证明，而不是对被衡量事物的证明。只要可能，每次只承担一项新的衡量任务。衡量 surprisingly 具有挑战性。数据采集可能会出错，数据可能会存在细微偏差。同时引入多个新指标会占用你自己或组织中擅长验证新数据的那一小部分人大量时间，对大多数组织来说，同时做多个衡量都很有挑战。不可量化的度量指标

先从每个类别中各选一个东西去衡量，从而在这些维度上建立一个基准。然后，你不会就此结束，而是很可能想重新开始，只是这次优先级和关注度会稍低一些。衡量不是一次性任务，而是一个持续迭代的过程。你所处具体情境中的各种背景因素，总是会让你优先选择略有不同的衡量方法。

这没有问题！不要拘泥于完全按照这个计划执行，选取其中对你最有用的部分即可。

反模式

衡量充满了反模式。你能把衡量搞砸的方式简直数不胜数，但有一些反模式出现得特别频繁，值得专门指出来：

在信任缺失才是根本问题时，却把重点放在衡量上。有时你会陷入一个衡量循环。CEO 要求你提供工程指标，你提供了那些指标。CEO 似乎并不满意，反而要求另一套完全不同的指标。这背后的根本问题往往是信任缺失。虽然指标可以帮助建立信任，但它们很少能单独解决问题。相反，应该去推动 CEO（或那个尽管提供了更多指标却仍然不满的人），挖掘他们真正的挫败感，直到找到隐藏在“需要更多指标”背后的真实担忧。不要让完美成为优秀的敌人。很多衡量项目一直没有进展，就是因为最好的方案需要一些你目前还没有的数据。采集这些数据的任务被放进了路线图，但始终得不到优先级。一年后，你还是什么都没衡量。相反，要推动任何合理的东西落地，哪怕它存在缺陷。用优化指标来判断绩效。人们很容易被诱惑去用优化指标来评估个人或团队的表现。例如，如果一个团队产生的 Pull Request 数量远少于同等规模的其他团队，很容易判断这个团队生产力较低。这可能是事实，但也可能完全不是。相反，应该基于规划或运营指标来评估团队。衡量个人而非团队。编写和运营软件是一项团队活动，虽然这个 sprint 一位工程师可能专注于写代码，但另一位工程师可能专注于做“胶水工作”，让前者能够专注。查看个人数据在诊断问题时可能有用，但它不是衡量绩效的好工具。相反，应该专注于组织和团队层面的数据。如果发现哪里不对，再考虑深入到个人数据去做诊断，而不是直接用于评估。过于担心衡量数据被滥用。很多领导者担心他们的 CEO 或董事会会误用数据。比如，他们可能会因为很多工程师一周只发布代码两次而大发雷霆——这是不是说明工程师很懒？要认识到这些讨论线确实非常令人沮丧，但回避它们并不能解决问题！相反，要花时间去教育那些正在以非建设性方式解读数据的利益相关方。保持开放的心态，总能学到一些东西，即使某个特定解读是错误的。独自决定衡量指标，而不是在群体中共同决定。我确实建议在讨论衡量时带着清晰的观点，说明你看到过哪些做法效果很好，但这必须与多轮反馈和迭代紧密结合。尤其当你刚加入一家公司时，很容易把对上一份工作的理解投射到新公司，这会损害信任。相反，通过吸纳团队和同级同事的反馈来建立信任。

如果你避开了这些反模式，并不能保证你走在了正确的道路上，但可能性相当高。

后记：对数据建立信心

当你推出新的工程衡量指标后，你可能会发现它们没有太大用处。这可能是因为不同群体对它们的解读完全不同（“为什么财务对数据库供应商成本上升这么生气，而我们的总成本仍然在预算之内？”）。也可能是这些指标与团队对系统的实际工作体验相矛盾（“为什么 Scala 团队一直抱怨构建延迟，而平均构建延迟明明在下降？”）。

现实是，衡量本身并不具有内在价值，只有通过反复对数据施加压力，你才能从中获得真正的价值。以下是一些对数据“施压”以榨取更多价值的方法建议：

每周固定节奏审查数据。确保审查时会查看过去一个月、一个季度或一年来的变化趋势。只要可能，也要设定一个明确的目标进行对比，因为设定目标和未达到目标都能帮助你聚焦在最需要学习的地方。针对数据变化保持一个假设。如果数据变化违背了你的假设（“每请求成本应该随着每秒请求数上升而下降，但这次请求数上升时成本反而上升了，这是为什么？”），那就深入挖掘，直到你能完全解释自己为什么错了。用这个新洞见来完善你的假设和所跟踪的指标。避免独自与数据相处太久，而是带上拥有不同观点的其他人一起对数据施压。这会带来许多关于数据如何反应的不同假设，也能让整个群体一起学习。对数据进行分段，以捕捉不同的体验。欧洲的可靠性和延迟如果你的数据中心和绝大多数用户都在美国，就会完全看不见——而且可能相当糟糕。同样，Scala、Python 和 Go 的底层测试和构建策略各不相同；构建时间平均在下降，并不意味着 Scala 工程师的构建体验很好。讨论客观衡量结果与数据所代表的主观体验之间是否一致。如果构建速度变快了，但触发构建的工程师却没有感觉到更快，那就深入调查——你漏掉了什么？

当然，还有很多其他推动数据的方法，但遵循以上几点就能让你走上正确路径，去理解自己数据的细节和局限性。如果你不在数据上花这类功夫，就很容易做到数据驱动、信息充分，却得出错误的结论。一些最严重的高管错误，正是源于过度依赖带有细微缺陷的数据，但只要稍作努力，这类错误是完全可以避免的。
