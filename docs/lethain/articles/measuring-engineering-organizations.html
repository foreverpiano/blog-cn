衡量工程组织。

2023-01-02 · 阅读原文

过去几年，我一直主持一个由工程高管组成的学习小组。最常被讨论的话题是职业管理——下一步我该做什么？第二个最常见的话题则是衡量工程团队和组织——我的 CEO 要求我每月汇报工程指标，我到底应该在报告里放些什么？

任何关于衡量工程组织的讨论，都会迅速引发强烈的意见。“除了 sprint 点数什么都行！”“就用 SPACE 框架！”“追踪事故频率！”“等等，绝对不要追踪事故频率！”“随便做一张好看的图表就行，反正他们也不会仔细看！”所有这些回答，甚至包括最后一个，都包含一定的道理，但它们都忽略了一个重要的前提：衡量工程有多种目的，不同利益相关方索要指标的诉求也各不相同，应对每一种情况都需要不同的方法。

衡量工程组织没有单一的解决方案，而是存在多种衡量模式，每一种都适用于特定的场景。成为一名高效的工程高管，就是不断往自己的工具箱里添加更多方法，并在面对任何具体需求时，保持灵活，选择最合适的那一种。

你可以使用《Engineering Metrics Update》模板来汇报这些指标。

这是 O'Reilly 出版的《The Engineering Executive’s Primer》一书中未经编辑的章节。

为自己而衡量

当你刚进入一个新的高管职位时，CEO 很可能会随口说一句，你需要在“三周后的下一次董事会会议上准备一份工程相关的幻灯片”。这是一个非常让人专注的时刻——我怎么才能不在第一次董事会会议上出丑！——但即使你第一次正式的衡量成果是一张董事会幻灯片，我也不建议你从为董事会准备有用的指标开始你的衡量工作。

相反，先从为自己衡量开始。你需要哪些信息来有效地运营工程组织？ 在开始记录你的衡量目标时，我建议从以下四个不同的类别入手：

**为规划而衡量**：什么信息能帮助你与跨职能利益相关方达成一致，决定在一个季度、半年或一年内要交付什么？关键在于，这不是关于你如何交付（“我们用敏捷吗？”），而是支持项目选择和优先级排序。你需要一个单一的视图，能同时展示业务、产品和工程工作带来的影响。 你可能会说规划是产品团队的责任，但只有工程团队才能完整呈现工程正在进行的所有项目（例如，产品团队不太可能把你的数据库迁移列入路线图）。可以先从按团队统计已交付项目的数量，以及每个项目的影响开始。 **为运营而衡量**：你需要了解什么，才能确信你的软件和团队在日常工作中运转良好？ 把这些指标看作质量指标会很有帮助，因为它们背后的真正问题是：你如何判断是应该继续按照既定路线图推进，还是应该紧急动员去修复一个关键问题？ 一些好的起点包括：追踪事故数量（每次事故都对应一份事故复盘报告）、面向用户的 API 和网站停机分钟数、面向用户的 API 和网站的延迟、按核心业务指标归一化的工程成本（例如，你最重要的 API 的服务成本，可以简单地用每月 API 请求数除以当月工程支出计算得出）、用户对产品的评分（例如应用商店评分），以及一个广义的指标——你的产品新手引导流程是否顺利完成（例如，成功访问你网站的访客中有多少百分比最终转化成用户？）。 **为优化而衡量**：你需要了解什么，才能有效地投入时间来提升工程生产力？ 如果你把工程看作一个系统，你会如何理解这个系统的反馈循环？ 值得注意的是，这通常也是工程师自己用来衡量在公司内工作体验的方式。 可以从 SPACE 框架或其前身 Accelerate 开始。如果这些框架太重，那就从开发者生产力调查开始。 **为激励与愿景而衡量**：你如何简洁地向业务传达工程带来的变革性影响？如何让潜在的候选人、新来的跨职能高管或董事会成员对工程为业务成功做出的贡献感到振奋？ 维护一份技术投入清单，记录那些把“不可能”变成“理所当然”的事情（例如，“我们无法在不影响整个用户群生产环境的情况下修改 API”，后来变成“我们允许每个 API 集成按自己方便的时间升级版本，而不是必须按照我们的时间表”）。在公司会议上发言时，以这些代际改进为锚点，并尽量在每个年度规划周期中都纳入至少一项这样的改进。

当讨论衡量时，一个常见的反驳是：我们是否衡量得足够多——难道不应该同时衡量数据库 CPU 负载、Pull Request 周期时间等等吗？良好衡量的秘诀其实是真正去衡量某件事。衡量最大的风险，是因为试图衡量一切而最终什么都没衡量。你永远可以衡量更多，而且衡量更多是有价值的，但要通过许多次小的迭代来推进，不要害怕今天就先去衡量一些快速且容易获取的东西。

为利益相关方而衡量

之所以要优先做快速衡量而不是完美衡量，一个原因是你公司内部有很多人希望你去衡量各种东西。有些是你自己认为内在有价值去衡量的，但也有 CEO 想让你衡量的、财务部门向你要的、要在月度状态会上汇报的，等等。

虽然需求很多，但好消息是这些请求在不同公司之间往往是相似的，通常可以归到以下四个类别之一：

**为 CEO 或董事会衡量**。许多经验丰富的管理者（很可能包括你的 CEO）倾向于 。这意味着他们希望你衡量某件事，设定一个明确的目标，并定期汇报针对该目标的进展。他们没有工程背景来管理你的技术决策，因此会把你达成这些目标的能力视为你工程领导力质量的代理。如果他们深入研究你的指标，会重点关注工程对业务战略本身的贡献，而不是工程日常工作中的微观优化。 这些指标不必新颖，最好的做法是复用你为自己而衡量的那些指标。最常见的是复用规划或运营类指标。 要避免的最大错误是用“为优化而衡量”的指标去向 CEO 汇报。虽然直观上大家都同意更高的效率可能让工程更有影响力，但大多数 CEO 不是工程师，往往无法完成这个直觉上的跳跃。而且，极高的效率仅仅意味着工程“有可能”产生影响，而不等于它“实际”产生了影响！ **为财务部门衡量**。财务团队通常对工程有三个主要问题。第一，实际人力数量与预算人力数量的趋势如何？第二，实际供应商成本与预算供应商成本的趋势如何？第三，哪些工程成本可以 ，以及在审计时如何证明这一点？ 你通常需要按照财务部门的预算流程来配合他们，不同公司的流程有所不同，但在同一公司内通常是统一的。资本化与费用化的问题更为微妙，需要详细讨论；我想说的是，默认的方法往往比较繁琐，但几乎总能在财务、审计和工程师的优先级之间找到一个合理的交集——虽然各方都会稍有不满，但仍能满足所有方的核心要求。 虽然我很少遇到财务主动要求，但我发现与财务就工程的投资逻辑达成一致特别有价值，即如何在不同业务优先级和业务单元之间分配工程容量。到了某个阶段，公司内的业务单元会开始争论如何将工程成本分摊到不同项目上（因为工程成本很高，如果分摊太多，会让它们的新项目看起来严重亏损而非充满潜力），这时如果有一份清晰记录的分配方案，会让对话变得建设性得多。 **为战略伙伴型组织衡量**。你最好的跨职能伙伴是那些主动与你合作、最大化工程对业务影响的组织。乐观地说，这是因为这些职能由开明的业务 visionary 领导。更现实地说，是因为他们的成功受限于工程的成功，因此优化工程的影响力，同时也优化了他们自己的影响力。产品、设计和销售部门通常都是与工程建立战略伙伴关系的合适对象。 你通常可以使用为规划而衡量的那些指标，来与这些战略伙伴型组织进行有效对齐。 **为战术型伙伴组织衡量**。虽然战略伙伴型组织可能同意按工程工作的影响来衡量工程，但更战术型的组织通常会要求用更具体的产出来衡量工程。例如，客户成功团队可能会推动用用户工单的接受率和解决时间来衡量工程。法务部门可能也想用法律相关工单的解决时间来衡量你。战术型组织之所以“战术”，并不是因为它们缺乏战略思考能力，而是因为它们的组织是用完全战术性的方式来考核的。如果它们与工程合作去最大化工程的影响，反而可能让自己的组织被认为表现不佳。 战术型组织自己要为具体、明确的数字负责，因此也想让工程为它们自己的一套具体、明确的数字负责。找到一个你和对方都能同意的指标，确定一个讨论节奏，来评估这个指标在多大程度上真正代表了跨组织的真实需求，然后随着时间不断迭代。检查与信任的边界如何资本化工程成本

为利益相关方衡量往往很耗时，有时甚至会让人觉得有点浪费时间。但如果做得正确，虽然依然耗时，却能节省时间——因为它把混乱、反复出现的讨论，转化成了更简单、更可预测的契约：共同维护一些具体、可衡量的结果。

排列你的衡量顺序

仅仅为你自己而需要衡量的东西就已经够多了，一旦再加上利益相关方的需求，整个清单会变得异常冗长。事实上，有一条放之四海而皆准的真理：一位工程高管总是渴望有更多工程师，来支持他们衡量现有那份“必须拥有”的指标清单。 你永远不可能真的把所有想衡量的都衡量完。但在一两年内，你可以把最重要的部分落地，不断迭代，并建立起对它们真实含义的信心。

我曾尝试列出一份具体的清单，精确告诉你应该先衡量什么以避免分散精力，但效果并不好。因为上下文差异实在太大，一份死板的清单没什么用。 因此，我提供三条排列衡量优先级的规则：

有些事情很难衡量，只有当你真正会把这些数据纳入决策时才去衡量。如果根据这些数据你不太可能改变自己的方法或优先级，那就换一个简单的东西来衡量，即使它只是 。 有些事情很容易衡量，即使你觉得它们不是特别准确，也要愿意去衡量，以此来建立与利益相关方的信任。大多数利益相关方更看重你的意图和投入，而不是实际产出的精确度。这是在表明你愿意为自己的工作负责，而不是在证明被衡量的事物本身。 尽可能每次只承担一项新的衡量任务。衡量工作出奇地具有挑战性。数据采集可能出错，数据可能存在细微偏差。同时引入多个新指标，会占用你或团队中擅长验证新数据的那部分人大量时间，对大多数组织来说都很难驾驭。为不可衡量之事制定指标

先从每个类别中都选一些东西来衡量，从而在这些维度上建立基线。然后，你不会就此结束，而是很可能想重新开始，只是优先级和关注度会稍低一些。衡量不是一次性任务，而是一个持续迭代的过程。你所处的具体情境总会有一些独特的背景，让你可能需要采取略有不同的衡量策略。

没关系！不要纠结于完全照搬这个计划，选取其中对你最有用的部分即可。

反模式

衡量工作中充满了反模式。你把衡量搞砸的方式多到数不胜数，但有一些发生得特别频繁，值得专门指出来：

**在真正的问题是信任缺失时，却聚焦于衡量**。有时你会发现自己陷入了一个衡量循环。CEO 要求你提供工程指标，你提供了。结果 CEO 似乎并不满意，又要求另一套不同的指标。通常，这背后的根本问题是信任缺失。虽然指标可以帮助建立信任，但它们很少能独自解决问题。 相反，应该去追问 CEO（或任何尽管提供了更多指标却仍然不满的人），把他们的挫败感挖到根源，直到找到隐藏在“需要更多指标”背后的真正担忧。 **不要让完美成为良好的敌人**。许多衡量项目迟迟没有进展，因为最好的方案需要目前没有的数据。采集这些数据被放进了路线图，但一直没有真正被优先安排。一年后，你还是什么都没在衡量。 相反，应该推动任何合理的东西落地，即使它存在缺陷。 **用优化指标来评判绩效**。人们很容易忍不住用优化类指标来评判个人或团队的表现。例如，如果一个团队产生的 Pull Request 远少于同等规模的其他团队，很容易判断这个团队生产力较低。这可能确实如此，但也可能并非如此。 相反，应该基于规划或运营指标来评估团队。 **衡量个人而非团队**。编写和运营软件是一项团队活动。虽然在这个 sprint 里，一名工程师可能专注于写代码，但另一名工程师可能专注于做“胶水工作”，让前者能够专注。查看个人数据在诊断问题时可能有用，但它不是衡量绩效的好工具。 相反，应该重点衡量组织和团队层面的数据。如果发现哪里不对劲，再考虑深入到个人数据去做诊断，而不是直接用于评估。 **过于担心指标被滥用**。许多领导者担心他们的 CEO 或董事会会误用数据。例如，他们可能会因为很多工程师一周只发布代码两次而大发雷霆：这是不是说明工程师很懒？要意识到，这类讨论虽然非常令人沮丧，但回避它并不能解决问题！ 相反，应该花时间去教育那些用非建设性方式解读数据的利益相关方。保持开放的心态，总能学到一些东西，即使某个特定解读是错误的。 **独自决定衡量指标，而不是在群体中共同决定**。我确实建议你在衡量时带着清晰的观点，分享自己看到过哪些做法效果良好，但这必须与多轮反馈和迭代紧密结合。特别是在你刚加入一家新公司时，很容易把上一个工作的理解投射到新环境中，从而损害信任。 相反，应该通过吸纳团队和同侪的反馈来建立信任。

如果你避开了这些反模式，虽然不能保证一定走在正确的道路上，但可能性已经相当高。

后记：建立对数据的信心

当你推出新的工程衡量指标后，可能会发现它们并没有那么有用。这可能是因为不同群体对它们的解读不一样（“为什么财务对数据库供应商成本上升这么不满，而我们的总成本仍然在预算之内？”）。也可能是这些指标与团队实际的工作体验产生了冲突（“为什么 Scala 团队一直抱怨构建延迟，而平均构建延迟明明在下降？”）。

现实是，衡量本身并不天然有价值，只有通过反复地“推敲”数据，你才能从中获得真正的价值。以下是一些推敲数据的建议，能帮助你从中提取更多价值：

以每周的节奏回顾数据。确保回顾时会查看过去一个月、一个季度或一年的变化趋势。只要可能，也要设定一个明确的目标来进行对比——无论是达成目标还是错过目标，都能帮助你聚焦在最值得学习的地方。 为数据变化保持一个假设。如果数据变化违背了你的假设（“每请求成本应该随着每秒请求数上升而下降，但这次请求数上升时成本反而上升了，这是为什么？”），那就深入挖掘，直到你能完整解释自己为什么错了。用这个新洞见来同时优化你的假设和追踪的指标。 避免独自与数据相处太久，而是带上拥有不同观点的其他人，一起推敲数据。这会汇集多种关于数据如何反应的假设，让整个群体共同学习。 对数据进行分段，以捕捉不同的体验。欧洲的可靠性和延迟情况，如果你的数据中心和绝大多数用户都在美国，将是不可见的——而且可能相当糟糕。同样，Scala、Python 和 Go 会有不同的底层测试和构建策略；仅仅因为平均构建时间在下降，并不意味着 Scala 工程师的构建体验很好。 讨论客观衡量结果与数据所代表的主观体验之间是否一致。如果构建速度变快了，但触发构建的工程师却没有感觉到更快，那就深入调查——你遗漏了什么？

当然，还有很多其他推敲数据的方式，但遵循上述建议就能让你走上正确路径，去理解自己数据的细节和局限性。如果你不在数据上花这类时间，就很容易做到“数据驱动、信息充分”，却得出错误的结论。一些最严重的执行错误，正是源于过度依赖有细微缺陷的数据，但只要稍作努力，这种错误是可以避免的。
