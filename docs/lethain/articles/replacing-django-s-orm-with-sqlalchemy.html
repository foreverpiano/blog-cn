用 SQLAlchemy 替换 Django 的 ORM

2008-07-23 · 阅读原文

在展示 Django 松耦合的第一个示例中，我们介绍了如何用 Jinja2 替换其模板系统。本文我们将探讨如何用 SQLAlchemy 替换 Django 默认的 ORM。这是一次较大的改动，在深入之前，让我们先来看看切换到 SQLAlchemy 会对应用产生哪些影响。

在本系列的引言中，我提到 Django 的实现遵循了松耦合哲学，但当我们考虑从 Django ORM 切换到 SQLAlchemy 所带来的变化时，可能需要对这句话打上几粒盐。首先，我们将无法再使用 Django 的 models.py 文件来描述模型，而是改用 SQLAlchemy 的 ORM 来定义表和字段（两者看起来会相当相似）。

随之而来的是，我们无法再通过简单的 python manage.py syncdb 命令为项目创建数据表，也无法使用 python manage.py loaddata 或 python manage.py dumpdata 来生成 fixture，作为初始数据或 Django 测试框架的脚手架。如果我们严格只使用 SQLAlchemy，甚至连 Django Admin、sessions middleware、authentication middleware 等贡献的组件都无法使用。

这里想传递的信息是：虽然 Django 是松耦合的，但“松耦合”并不意味着解耦没有代价。更改某些系统（如模板渲染）后果很小，但其他系统——比如 Django ORM——远非即插即用。这一点无法避免，因为完美的解耦会给开发者增加额外负担，也会让 Django 项目更慢、更复杂地启动和运行。当你刚开始使用 Django 时，很难判断哪些子系统解耦的代价较高，因此强烈建议先使用默认的 Django 技术栈，在积累更多经验后再负责任地进行调整。

（完全披露：将 Django ORM 和 SQLAlchemy 一起使用是可行的。这意味着你仍然可以利用 Django 的 sessions middleware（以及大多数其他组件），同时在应用的某些部分使用 SQLAlchemy。本教程不会构建这样一个“弗兰肯斯坦”，因为它只专注于探索松耦合这一方面，但这么做也不会特别困难。不过，在某些方面可能会显得有些别扭。）

现在，让我们开始点石成金吧。

现在，这个示例的实际价值不像之前使用 Jinja2 的那个那么一目了然，但它仍然展示了关于 Django 的两个重要观点。首先，Django 是用 Python 编写的，因此你在 Django 中可以做任何在 Django 之外能做的事情。其次，Django 是松耦合的，但有时候松耦合也是有代价的，解耦某些子系统——尤其是 ORM——并不轻松。

作为最后一点，我想为本文对 SQLAlchemy 做的“亏待”道歉。SQLAlchemy 是一个功能极其丰富、用途广泛的系统，而这里的用法让它看起来像是 Django ORM 的镜像。事实远非如此。SQLAlchemy 可以像 Django ORM 那样进行抽象，但它能让你更容易地深入底层，同时还暴露了更多高级功能，比如连接池。

好吧，最后的最后一点：我认为本教程已经不言自明，但我不会建议在没有极其充分理由的情况下从 Django ORM 中解耦。它是 Django 所有子部件中耦合度最高的，替换它绝非易事。

对于那些因为我没有同时展示 Django ORM 和 SQLAlchemy ORM 而觉得我对 Django 不公平的人，请放心，本系列的下一个示例将会探讨类似的内容（但会是一个稍微更现实的场景）。
