用 SQLAlchemy 替换 Django 的 ORM

2008-07-23 · 阅读原文

在 Django 松耦合的第一个示例中，我们介绍了如何用 Jinja2 替换模板系统。本文中，我们将探讨如何用 SQLAlchemy 替换 Django 默认的 ORM。这是一次相当大的跨越，在深入之前，我们先来看看切换到 SQLAlchemy 会对我们的应用产生什么影响。

在本系列的引言中，我曾说过 Django 的实现遵循了松耦合哲学。但当我们考虑从 Django ORM 切换到 SQLAlchemy 所带来的变化时，可能需要对这句话多加几分考量。首先，我们将无法再使用 Django 的 models.py 文件来描述模型，而是要使用 SQLAlchemy 的 ORM 来定义表和字段（两者看起来相当相似）。

随之而来的是，我们无法再用简单的 python manage.py syncdb 来为项目创建数据表，也无法使用 python manage.py loaddata 或 python manage.py dumpdata 来生成 fixture，作为初始数据或 Django 测试框架的脚手架。如果我们严格只使用 SQLAlchemy，甚至连 Django Admin、sessions middleware、authentication middleware 等贡献的资源都无法使用。

这里想传达的信息是：虽然 Django 是松耦合的，但“松耦合”并不意味着解耦没有代价。更改某些系统（如模板渲染）带来的影响很小，但其他系统——比如 Django ORM——远非即插即用。这无法避免，因为完美的解耦会给开发者个人增加额外负担，也会让 Django 项目启动变得更慢、更复杂。刚开始使用 Django 时，很难判断哪些子系统解耦的代价较高，因此强烈建议从默认的 Django 技术栈开始，随着经验积累再负责任地进行调整。

（免责声明：将 Django ORM 和 SQLAlchemy 一起使用是可行的。这意味着你仍然可以利用 Django 的 sessions middleware（以及大多数其他功能），同时在应用的某些部分使用 SQLAlchemy。本教程不会构建这样一个“弗兰肯斯坦怪物”，因为它只关注探索松耦合这一方面，但要实现也并非特别困难。不过在某些方面会显得有点别扭。）

现在，让我们开始点石成金吧。

在 Django 中使用 SQLAlchemy

首先我们需要安装 SQLAlchemy。最简单的方法是使用 easy_install： easy_install SQLAlchemy 你也可以从他们的下载页面获取 0.5 版本。本教程使用的是 0.5beta2，只要不使用 0.4 版本，代码应该都能正常运行。如果你选择手动下载文件，则需要执行以下安装步骤： tar zxvf SQLAlchemy-0.5.0beta2.tar.gz cd SQLAlchemy-0.5.0beta2 python setup.py install 如果你使用的是 Python 2.5 之前的版本，还需要同时安装 pysqlite 和 SQLite。 现在让我们确认安装是否成功： >>> import sqlalchemy >>> sqlalchemy.__version__ '0.5.0beta2' 如果 SQLAlchemy 无法正确导入，或者版本不是 0.5 的某个衍生版本，那么你需要重新检查前面的步骤。 创建一个 Django 项目和应用： django_admin.py startproject loose_coupling cd loose_coupling python manage.py startapp with_sqlalchemy 创建几个模板目录： mkdir templates cd ('django.middleware.common.CommonMiddleware',) INSTALLED_APPS = ('loose_coupling.with_sqlalchemy',) import os ROOT_PATH = os.path.dirname(__file__) TEMPLATE_DIRS = (os.path.join(ROOT_PATH,'templates'),) 由于我们不使用 Django ORM，因此不会用到任何依赖数据库的中间件或应用。 现在我们来编辑 loose_coupling/urls.py 文件： from django.conf.urls.defaults import * urlpatterns = patterns( 'loose_coupling', (r'^$', 'with_sqlalchemy.views.index'), ) 通常我们会把 with_sqlalchemy 应用的 urls.py 文件 include 到项目 urls.py 中，但这里我们尽量保持简单。 接下来我们将使用 SQLAlchemy ORM 创建一个简单的表来做实验。因为 models.py 文件已经存在，我们就把表的定义写进去。请打开 with_sqlalchemy/models.py： from sqlalchemy import Table, Column, Integer, String, MetaData, ForeignKey from sqlalchemy.ext.declarative import declarative_base Base = declarative_base() class Language(Base): __tablename__ = 'languages' id = Column(Integer, primary_key=True) name = Column(String) extension = Column(String) def __init__(self, name, extension): self.name = name self.extension = extension def __repr__(self): return u"Language(%s, %s)" % (self.name, self.extension) 我们可以看出，SQLAlchemy 定义模型的方式与 Django 非常相似。这里我们不深入讨论，但 SQLAlchemy 也可以做得更加底层，先定义数据库表，再将其映射到 Python 类。你甚至可以完全跳过 ORM，直接使用他们提供的 SQL 构造接口。 现在我们来编写 views.py 文件。首先是文件开头的导入部分： from django.shortcuts import render_to_response import sqlalchemy, sqlalchemy.orm from models import Base, Language 然后我们需要配置 SQLAlchemy，让 Language 类可以使用： engine = sqlalchemy.create_engine('sqlite:///loose.sqlite') Session = sqlalchemy.orm.sessionmaker(bind=engine) session = Session() Base.metadata.create_all(engine) sqlite:///loose.sqlite 这条指令会在相对路径 loose.sqlite 处创建一个 SQLite 数据库，也就是 with_sqlalchemy 目录内。SQLAlchemy 同样可以轻松指定绝对路径，或在内存中创建数据库。如果我们想让它更像 Django 的风格，可以在 settings.py 中指定 DATABASE_NAME，然后像下面这样加载： from django.conf import settings engine = sqlalchemy.create_engine(settings.DATABASE_ENGINE) 另外，Base.metadata.create_all(engine) 实际上只需要在 SQLAlchemy 第一次创建表时执行一次（多次执行也不会有问题），但这需要创建一个类似 python manage.py syncdb 的脚本，会让示例变得更复杂，所以我们暂时跳过这一步。 接下来，我们创建两个非常简单的工具函数，用于填充数据： def is_empty(): return len(session.query(Language).all()) <= 0 def populate(): new_langs = [Language('Python','py'),Language('Ruby', 'rb'), Language('Common Lisp', 'lisp'),Language('Objective-C', 'm')] session.add_all(new_langs) session.commit() 这些简单的函数将用来向数据库填充一些数据。同时也提供了一个最小的示例，展示了 SQLAlchemy 的查询和对象创建语法，它们与 Django ORM 非常相似。 index 视图都检查是否已创建测试数据，那样视图会变成这样： def index(request): langs = session.query(Language).all() return render_to_response('with_sqlalchemy/index.html',{'langs':langs}) 这看起来几乎和使用 Django ORM 时的写法一模一样（只是获取数据时的语法略有不同）。 现在我们需要创建正在渲染的 with_sqlalchemy/index.html 模板。首先创建一个基础模板，放在 loose_coupling/templates 目录下，命名为 base.html，内容如下： <html> <head> <title> Loosely Coupled Django </title> </head> <body> {% block content %} {% endblock %} </body> </html> 接下来创建 index.html 模板。打开 with_sqlalchemy/templates/with_sqlalchemy/index.html，填写以下内容： {% extends 'base.html' %} {% block content %} {% for lang in langs %} <p>{{ lang }}</p> {% endfor %} {% endblock %} 关于这些模板，最重要的一点是：我们传递给它们的是由 SQLAlchemy ORM 生成的实例，但模板看起来和使用 Django ORM 时完全一样。模板语言并不关心底层是 Django ORM 还是其他，它可以处理普通的 Django Model 实例，也可以处理普通的 Python 字典。 现在一切都准备好了，只等我们测试： python manage.py runserver 然后在浏览器中访问 http://127.0.0.1:8000/。 你会看到四个编程语言及其扩展名的简单展示。

现在，这个示例的实用性显然不如之前使用 Jinja2 的那个，但它仍然展示了关于 Django 的两个重要观点。首先，Django 是用 Python 编写的，所以你在 Django 中可以做任何在 Django 之外能做的事情。其次，Django 是松耦合的，但有时候这种松耦合是有代价的，解耦某些子系统——尤其是 ORM——并不轻松。

作为最后一点，我想为本篇对 SQLAlchemy 所做的“贬低”道歉。SQLAlchemy 是一个功能极其丰富且非常灵活的系统，而这里的用法让它看起来像是 Django ORM 的镜像。事实远非如此。SQLAlchemy 可以像 Django ORM 那样进行抽象，但它能让你更轻松地深入底层，同时还暴露了更多高级功能，比如连接池。

好了，最后的最后一点：我认为这个教程已经说得很清楚了，但我不会推荐在没有极其充分理由的情况下从 Django ORM 中解耦。它是 Django 所有子部件中耦合度最高的，替换它绝非易事。

对于那些因为我没有展示同时使用 Django ORM 和 SQLAlchemy ORM 而觉得我对 Django 不公平的读者，请放心，本系列的下一个示例将会探讨类似的内容（不过会是一个稍微更现实的场景）。
