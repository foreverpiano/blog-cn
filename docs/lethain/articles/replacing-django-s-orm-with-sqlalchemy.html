用 SQLAlchemy 替换 Django 的 ORM

2008-07-23 · 阅读原文

在 Django 松耦合的第一个示例中，我们介绍了如何用 Jinja2 替换模板系统。本文我们将探讨如何用 SQLAlchemy 替换 Django 默认的 ORM。这是一个相当大的跨越，在深入之前，让我们先看看切换到 SQLAlchemy 会对我们的应用产生怎样的影响。

在本系列的引言中，我提到 Django 的实现遵循了松耦合哲学，但在考虑从 Django ORM 切换到 SQLAlchemy 所带来的变化时，我们可能需要对这句话打上几粒盐。首先，我们将无法再使用 Django 的 models.py 文件来描述模型。取而代之的是，我们将使用 SQLAlchemy 的 ORM 来定义表和字段（看起来会非常相似）。

随之而来的是，我们无法再通过简单的 python manage.py syncdb 来为项目创建表。我们也无法使用 python manage.py loaddata 或 python manage.py dumpdata 来生成初始数据或为 Django 测试框架提供脚手架。如果我们严格坚持只使用 SQLAlchemy，甚至无法使用 Django Admin、sessions middleware 或 authentication middleware 等贡献的资源。

这里要传递的信息是：虽然 Django 是松耦合的，但“松耦合”并不意味着解耦没有代价。更改某些系统（如模板渲染）后果很小，但其他系统——比如 Django ORM——远非即插即用。这一点不可避免，因为完美的解耦会给开发者个人增加更多负担，也会让 Django 项目启动变得更慢、更复杂。当你刚开始使用 Django 时，很难判断哪些子系统解耦代价高昂，这就是为什么强烈建议从默认的 Django 技术栈开始使用，随着经验积累再负责任地进行必要调整。

（免责声明：将 Django ORM 和 SQLAlchemy 一起使用是可行的。这意味着你仍然可以利用 Django 的 sessions middleware（以及大多数其他功能），同时在应用的某些部分使用 SQLAlchemy。本教程不会构建这个“弗兰肯斯坦”，因为它只专注于探索松耦合这一方面，但要实现也并非特别困难。当然，在某些方面可能会显得有些别扭。）

现在，这个示例的实际价值不如之前使用 Jinja2 的那个那么一目了然，但它仍然展示了关于 Django 的两个重要观点。首先，Django 是基于 Python 的，所以你在 Django 中可以做任何在 Django 之外能做的事情。其次，Django 是松耦合的，但有时松耦合也是有代价的，解耦某些子系统——尤其是 ORM——并不轻松。

作为最后一点，我想为本篇文章对 SQLAlchemy 所做的“亏待”道歉。SQLAlchemy 是一个功能极其丰富且非常灵活的系统，而这里的用法让它看起来像是 Django ORM 的镜像。事实远非如此。SQLAlchemy 可以像 Django ORM 那样进行抽象，但它能让你更容易地进行底层操作，同时还暴露了更多高级功能，比如连接池。

好吧，最后的最后一点：我认为这个教程已经不言自明，但我不会推荐在没有极其充分理由的情况下从 Django ORM 中解耦。它是 Django 所有子部件中最紧耦合的一个，替换起来绝非易事。
