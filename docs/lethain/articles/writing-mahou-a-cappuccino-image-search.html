编写 Mahou：一款使用 Cappuccino 的图片搜索应用

2008-09-06 · 阅读原文

我今天大部分时间都用来熟悉 Cappuccino，并用它开发了一个简单但略有趣味的应用。首先我会快速介绍一下我开发的应用，然后再谈谈使用 Cappuccino 的开发体验。我利用 Vik Singh 改编的 Yahoo! Boss Mashup Framework（针对 Google App Engine）和 Cappuccino，构建了 Mahou 这款功能较为丰富的图片搜索工具。

Mahou 有两个特别有趣的功能：

  1. If you scroll down (using the mouse wheel), as you get near the end of the results, additional results will be retrieved and appended to the existing results.
  2. If you click on an image it will open up a small window (not a browser window, but a virtual window within the frame) with the image's meta data. If you click on the image's title (the white text), it will open the fullsize image in the browser.

尽管还有一些粗糙之处，但它已经是一款相当实用的图片搜索工具。自动加载更多图片（同时保留之前的结果）的设计，让浏览图片和在不同“页”之间来回切换比传统搜索引擎更快。

好了，接下来进入正题。

使用 Cappuccino 开发

我在 Objective-C 和 JavaScript 上都投入过大量开发时间，而 Cappuccino 的风格非常强烈地偏向 Objective-C。这不仅仅体现在语法上，Cappuccino 还很好地捕捉到了 Cocoa 开发的整体感觉。

在 Cocoa 开发中，你很少会“随便 hack”。相反，你会像一个认真负责的软件开发者一样进行软件开发。这种踏实写代码的感觉，在 Objective-J 开发中也能明显感受到。

这并不是说开发体验不好，而是说用 Objective-? 语言编程很少给人一种需要灵光一现的感觉，它更多的是正确地将预制模式套用到问题上。有时你需要稍微调整一下模式让它完美契合，但很少需要特别“元”地思考，或者从工具箱里拿出全新的技巧。

与此同时，在 Cocoa（以及 Cappuccino）中也有一些没有预制解决方案的地方，这时即兴创造新方案往往需要各种技巧，并且要抛开一些常规做法。本质上，你会精心设计应用的前 97%，然后为最后的 3% 拼命折腾，直到它完全按照你的预期运行。

Objective-? 语言的另一个相似之处在于学习曲线较长但并不特别陡峭。早期，每完成一个 Cocoa 程序后，我都会发现自己之前的设计没能充分利用 Cocoa 的各种优势。然后我就会推倒重来，重新设计，结果代码量减半，更干净，也更直观。

完成 Mahou 之后，我同样产生了这种感觉：我可以用一半的时间重写它，采用更具扩展性的设计，并减少各种 hack。这就是使用重量级框架的挫败感——这类框架天生带有强烈的意见，在你还没足够了解它、能预判其 quirks 之前，会悄悄地惩罚你做出的错误选择。

唉，没办法。

Cappuccino 开发的优势

  1. Developing an application with Cappuccino won't always be faster than developing a comparable application in another JavaScript framework, but it'll be hard to beat Cappuccino's unit-of-quality-per-unit-of-time ratio. Because the framework makes so many choices for you, and provides high quality widgets to grow familiarity with, many vectors of failure fade away. Particularly the perils of cross-browser development are largely erased with Cappuccino. That is a big win.
  2. You write web applications in a single unified language, instead of a medley of html/css/JavaScript/a-server-side-language. This decreases the minutiae to memorize. In particular, the pointless difficulty of writing cross-browser CSS is removed. Now, I tend to enjoy getting to write in four (three and a quarter, really, since we're discussing html) languages, but I think there is merit to this approach. Regardless of which most developers decide upon, having both options is better than having only one or the other.
  3. Cappuccino supports well segmented and reusable code with support for code importing, and also its ease of subclassing widgets and classes. While writing Mahou I put together a WLURLLabel class which subclassed CPTextField to allow specifying a URL to open when clicked. I also subclassed CPTextField to support displaying placeholder text when there isn't any content in a textfield and it isn't selected. Both of these things are easy enough to do, but once you get into the habit you can save a considerable amount of time by making the extra five minute effort to create reusable classes. Although you can subclass and extend in other JavaScript libraries, Cappuccino's being modeled after Cocoa puts it in rarified air as far as the versatility and ease of subclassing to customize behavior. In Cocoa, subclassing and delegates are the two solutions to all customized logic. The first step of every solution is figuring out the class to subclass--not the function to write or library to create--and you end up reusing a tremendous amount of code with that mentality.
  4. Its fun. Learning new things is always fun, right?

Cappuccino 开发的问题

  1. The most difficult issue I ran into with Cappuccino development is that it explicitly doesn't play well with html and css. This is one of its purported strengths, but is also quite awkward when trying to--for example--display html retrieved from another web service. Even displaying a small attribution link at the bottom of the screen involved subclassing a CPTextField to open a window with a specific URL when clicked. That said, this issue can be alleviated by developing a handful of new UI widgets. Specifically a textfield that rendered html and css would be excellent. Something akin to NSAttributedString in Cocoa development. Actually, I suppose it's most similar to the WebKit view, which would be a slightly ironic addition.
  2. A limited debugging toolkit. I developed with WebKit, and had my fair share of generic error messages from Cappuccino. Particularly ones letting me know that it can't parse something somewhere, or that there was a syntax error. Somewhere. I imagine some people will get pretty caustic while complaining about this, and I agree that it's fair from perfect. But it's workable as is, and some automated acceptance testing (something like what Peter Burns discussed in this blog post a while back) would make it much easier to detect problems as they arise.
  3. There is a limited amount of documentation and tutorials thus far. It was released a day ago, so that isn't particularly surprising, but you have to be willing to browse through the docs. The overall patterns and documentation style of Cappuccino is sufficiently Cocoa-like that Cocoa developers will be ready to dive right in, but someone more from the JavaScript side of things might have a bit of trouble getting started right away.

结束语

虽然开发过程中偶尔会遇到阻碍，但我今天在开发第一个 Cappuccino 应用时还是获得了极大的乐趣。我真的进入了心流状态，它与 Cocoa 编程的重叠度高得惊人。有些地方 JavaScript 知识会有帮助，但我的个人印象是，有经验的 Cocoa 程序员会比有经验的 jQuery 程序员更适应。当然，两者只要花点功夫都能很快上手。

公平地说，我当前版本的应用并没有特别发挥 Cappuccino 的优势，但它还是帮助我实现了一些有趣的功能。当我有时间完整实现 Mahou 的全部设想时，我相信它会成为一个更有价值的项目。

快去 Cappuccino.org 体验一下吧。
