编写 Mahou：一款 Cappuccino 图片搜索应用

2008-09-06 · 阅读原文

我今天大部分时间都用来熟悉 Cappuccino，并用它开发了一个简单但有点意思的应用。首先我会简单介绍一下我开发的应用，然后再谈谈使用 Cappuccino 的开发体验。我利用 Vik Singh 为 Google App Engine 适配的 Yahoo! Boss Mashup Framework，以及 Cappuccino，打造了 Mahou —— 一个功能还算丰富的图片搜索工具。

Mahou 有两个特别有趣的功能：

当你用鼠标滚轮向下滚动，在接近结果列表底部时，会自动加载更多结果并追加到现有列表中。点击一张图片，会弹出一个小窗口（不是浏览器新窗口，而是在页面框架内的虚拟窗口），显示该图片的元数据。如果点击图片标题（白色文字），则会在浏览器中打开原图。

虽然还有一些粗糙的地方，但它已经是一个相当实用的图片搜索工具。自动加载更多图片（同时保留之前的结果）的设计，让浏览图片以及在不同“页”之间回溯比传统搜索引擎更快。

好了，接下来进入正题。

使用 Cappuccino 开发

我在 Objective-C 和 JavaScript 上都花过大量时间，而 Cappuccino 的风格强烈倾向于前者。这不仅仅体现在语法上，Cappuccino 还很好地捕捉到了 Cocoa 开发的感觉。

在 Cocoa 开发中，你很少会“随便 hack”。相反，你会像一个乖乖的软件开发者一样认真地做软件开发。这种踏实写代码的感觉，在 Objective-J 开发中也能强烈地感受到。

这并不是说开发体验不好，而是说用 Objective-? 语言编程很少给人一种需要灵机一动、发挥创造力的感觉，它更多是在正确地将预制好的模式套用到问题上。有时候你会稍微调整一下模式让它更合适，但很少需要特别“元”地思考，或者从自己的工具箱里掏出全新技巧。

与此同时，在 Cocoa（以及 Cappuccino）中也有一些地方没有现成的解决方案，这时候即兴创造新方案往往需要各种花招和不拘一格的做法。本质上，你会精心设计应用的前 97%，然后为最后的 3% 拼命折腾，直到它完全按照你的想法工作。

Objective-? 语言的另一个相似之处是学习曲线很长但并不特别陡峭。早期，每写完一个 Cocoa 程序，我都会发现自己之前的设计没能充分利用 Cocoa 的各种优势。然后你就会扔掉旧代码重新设计，新代码通常只有原来一半长，更干净，也更直观。

完成 Mahou 之后，我又产生了同样的感觉：我完全可以用一半的时间重写它，做出一个扩展性更强、hack 更少的设计。这就是使用重量级框架的挫败感——这类框架天生带有强烈的意见，会在你做出错误选择时悄无声息地惩罚你，直到你足够了解它，能提前预判它的各种怪癖。

唉。

Cappuccino 开发的优势

用 Cappuccino 开发应用并不总是比用其他 JavaScript 框架更快，但它在“单位时间产出质量”这个比率上很难被超越。因为框架替你做了大量选择，并提供了高质量的控件让你快速熟悉，许多失败的可能性就消失了。 尤其是跨浏览器开发的各种坑，在 Cappuccino 中基本上被抹除了。这是一大胜利。你用一种统一的语言来编写 Web 应用，而不是混用 HTML、CSS、JavaScript 和服务器端语言。这减少了需要死记硬背的琐碎知识，特别是写跨浏览器 CSS 的那些无谓困难被彻底消除。 虽然我个人挺喜欢同时用四种语言（准确说是三种半，因为我们讨论的是 HTML）写代码，但我认为这种统一的方式也有它的价值。不管大多数开发者最终选择哪条路，能同时拥有两种选项总比只有一种好。 Cappuccino 支持良好分段且可复用的代码，提供了代码导入机制，也很容易对控件和类进行子类化。在开发 Mahou 时，我创建了一个 WLURLLabel 类，它继承自 CPTextField，允许指定点击后要打开的 URL。 我还子类化了 CPTextField，让它支持在文本框没有内容且未被选中时显示占位文字。这些功能做起来都不难，但一旦养成习惯，花额外的五分钟创建一个可复用类，就能节省大量时间。 虽然其他 JavaScript 库也支持子类化和扩展，但 Cappuccino 以 Cocoa 为蓝本，在子类化来定制行为的灵活性和简易性上处于领先地位。 在 Cocoa 中，子类化和委托是实现所有定制逻辑的两种方案。每个解决方案的第一步都是找到要继承的类——而不是去写一个函数或创建一个新库——这种思维方式能让你复用大量代码。 这很有趣。学习新东西总是很有趣的，对吧？

Cappuccino 开发的问题

我在使用 Cappuccino 开发时遇到的最大困难是，它明确地不与 HTML 和 CSS 友好配合。这本是它宣称的优势之一，但在某些场景下却相当尴尬——比如说，要显示从其他 Web 服务获取的 HTML。 甚至只是在屏幕底部显示一个小的署名链接，都需要子类化 CPTextField 来实现在点击时打开特定 URL 的窗口。 不过，这个问题可以通过开发一些新的 UI 控件来缓解。特别是如果有一个能渲染 HTML 和 CSS 的文本字段就好了，类似于 Cocoa 中的 NSAttributedString。其实，它最接近的是 WebKit 视图，加上这个控件多少带点讽刺意味。 调试工具集还比较有限。我用 WebKit 开发，遇到过不少 Cappuccino 抛出的通用错误信息。尤其是那些告诉我它在某处无法解析什么东西，或者某处有语法错误的提示。 我想有些人会对此大加抱怨，我同意它确实还不完美。但目前这样也还能用，如果加上一些自动化验收测试（类似 Peter Burns 前段时间在博客里讨论的内容），就能更容易地在问题出现时发现它们。 目前的文档和教程还比较少。它昨天才发布，所以这并不特别意外，但你得愿意去翻阅文档。Cappuccino 的整体模式和文档风格都非常接近 Cocoa，Cocoa 开发者可以直接上手，而更偏 JavaScript 背景的人可能一开始会遇到一些困难。

结束语

虽然开发过程中偶尔会卡住，但我今天开发第一个 Cappuccino 应用的过程非常愉快。我很快就进入了状态，它与 Cocoa 编程的重叠度高得惊人。虽然有些地方 JavaScript 知识会有帮助，但我的个人感觉是，经验丰富的 Cocoa 程序员会比经验丰富的 jQuery 程序员更适应。当然，两者只要稍作努力都能很快上手。

公平地说，我这个应用的当前版本并没有特别发挥 Cappuccino 的优势，但 Cappuccino 还是帮助我实现了些有趣的功能。当我有时间完整实现 Mahou 的愿景时，我相信它会成为一个更有价值的小项目。

去 Cappuccino.org 看看，试用一下吧。
