编写 Mahou：一款使用 Cappuccino 的图片搜索应用

2008-09-06 · 阅读原文

我今天大部分时间都用来熟悉 Cappuccino，并用它开发了一个简单但略有趣味的应用。首先我会快速介绍一下我开发的应用，然后再谈谈使用 Cappuccino 的开发体验。我利用 Vik Singh 改编的 Yahoo! Boss Mashup Framework（针对 Google App Engine）和 Cappuccino，构建了 Mahou 这款功能较为丰富的图片搜索工具。

Mahou 有两个特别有趣的功能：

当你用鼠标滚轮向下滚动，在接近结果列表末尾时，系统会自动获取更多结果并追加到现有列表中。点击某张图片，会弹出一个小窗口（并非浏览器新窗口，而是应用框架内的虚拟窗口），显示该图片的元数据。如果点击图片标题（白色文字），则会在浏览器中打开原图。

尽管还有一些粗糙之处，但它已经是一款相当实用的图片搜索工具。自动加载更多图片（同时保留之前的结果）的设计，让浏览图片和在不同“页”之间来回切换比传统搜索引擎更快。

好了，接下来进入正题。

使用 Cappuccino 开发

我在 Objective-C 和 JavaScript 上都投入过大量开发时间，而 Cappuccino 的风格非常强烈地偏向 Objective-C。这不仅仅体现在语法上，Cappuccino 还很好地捕捉到了 Cocoa 开发的整体感觉。

在 Cocoa 开发中，你很少会“随便 hack”。相反，你会像一个认真负责的软件开发者一样进行软件开发。这种踏实写代码的感觉，在 Objective-J 开发中也能明显感受到。

这并不是说开发体验不好，而是说用 Objective-? 语言编程很少给人一种需要灵光一现的感觉，它更多的是正确地将预制模式套用到问题上。有时你需要稍微调整一下模式让它完美契合，但很少需要特别“元”地思考，或者从工具箱里拿出全新的技巧。

与此同时，在 Cocoa（以及 Cappuccino）中也有一些没有预制解决方案的地方，这时即兴创造新方案往往需要各种技巧，并且要抛开一些常规做法。本质上，你会精心设计应用的前 97%，然后为最后的 3% 拼命折腾，直到它完全按照你的预期运行。

Objective-? 语言的另一个相似之处在于学习曲线较长但并不特别陡峭。早期，每完成一个 Cocoa 程序后，我都会发现自己之前的设计没能充分利用 Cocoa 的各种优势。然后我就会推倒重来，重新设计，结果代码量减半，更干净，也更直观。

完成 Mahou 之后，我同样产生了这种感觉：我可以用一半的时间重写它，采用更具扩展性的设计，并减少各种 hack。这就是使用重量级框架的挫败感——这类框架天生带有强烈的意见，在你还没足够了解它、能预判其 quirks 之前，会悄悄地惩罚你做出的错误选择。

唉，没办法。

Cappuccino 开发的优势

用 Cappuccino 开发应用并不总是比用其他 JavaScript 框架开发同类应用更快，但它在“单位时间产出质量”上的表现很难被超越。因为框架替你做了大量选择，并提供了高质量的控件让你快速熟悉，许多失败的风险点自然消失了。 尤其是跨浏览器开发的麻烦，在 Cappuccino 中基本被抹除。这是一大胜利。你用单一的统一语言编写 Web 应用，而不是 HTML/CSS/JavaScript/服务器端语言的大杂烩。这减少了需要记忆的琐碎细节。特别是编写跨浏览器 CSS 的无谓难度被彻底消除。 当然，我个人还是挺喜欢同时用四种语言（准确说是三种多一点，因为我们在讨论 HTML）来开发，但我认为这种统一方式也有其价值。不管大多数开发者最终选择哪条路，能同时拥有两种选择总比只有一种好。Cappuccino 支持良好分段且可复用的代码，支持代码导入，也很容易对控件和类进行子类化。在开发 Mahou 时，我创建了一个 WLURLLabel 类，它继承自 CPTextField，可以指定点击后要打开的 URL。 我还对 CPTextField 进行了子类化，让它能在文本框没有内容且未被选中时显示占位文本。这两件事本身都不难实现，但一旦养成习惯，花额外五分钟创建一个可复用类，就能节省大量时间。 虽然在其他 JavaScript 库中也能进行子类化和扩展，但 Cappuccino 以 Cocoa 为蓝本，使其在子类化的灵活性和易用性上处于领先地位。 在 Cocoa 中，子类化和委托是实现所有自定义逻辑的两种主要方式。每个解决方案的第一步都是决定要继承哪个类——而不是要写哪个函数或创建哪个库——这种思维方式能让你复用大量代码。 这很有趣。学习新东西总是很有趣，对吧？

Cappuccino 开发的问题

我在使用 Cappuccino 开发时遇到的最大困难是，它明确表示与 HTML 和 CSS 配合得不好。这本是它宣称的优势之一，但在某些场景下却相当尴尬——比如说，当你想显示从其他 Web 服务获取的 HTML 时。 即使是在屏幕底部显示一个小小的归属链接，也需要继承 CPTextField 来实现点击后打开特定 URL 的窗口。 不过，这个问题可以通过开发一些新的 UI 控件来缓解。特别是一个能渲染 HTML 和 CSS 的文本字段会非常有用。类似 Cocoa 中的 NSAttributedString。其实，我觉得它最接近 WebKit 视图，如果加上这个会有点讽刺意味。调试工具相对有限。我使用 WebKit 进行开发，遇到过不少来自 Cappuccino 的通用错误信息。尤其是那些告诉我某处无法解析，或者存在语法错误的提示。 我猜有些人会对此大加抱怨，我也同意它远非完美。但就目前而言还是能用的，如果再加上一些自动化验收测试（类似 Peter Burns 之前在博客中讨论的那种），就能更容易地在问题出现时发现它们。目前的文档和教程还比较有限。它昨天才发布，所以这并不特别意外，但你必须愿意花时间浏览文档。Cappuccino 的整体模式和文档风格与 Cocoa 非常相似，因此 Cocoa 开发者可以直接上手，而更偏向 JavaScript 背景的开发者可能需要花点时间才能快速进入状态。

结束语

虽然开发过程中偶尔会遇到阻碍，但我今天在开发第一个 Cappuccino 应用时还是获得了极大的乐趣。我真的进入了心流状态，它与 Cocoa 编程的重叠度高得惊人。有些地方 JavaScript 知识会有帮助，但我的个人印象是，有经验的 Cocoa 程序员会比有经验的 jQuery 程序员更适应。当然，两者只要花点功夫都能很快上手。

公平地说，我当前版本的应用并没有特别发挥 Cappuccino 的优势，但它还是帮助我实现了一些有趣的功能。当我有时间完整实现 Mahou 的全部设想时，我相信它会成为一个更有价值的项目。

快去 Cappuccino.org 体验一下吧。
