YouTube 可扩展性

2007-07-08 · 阅读原文

这场Tech Talk（可在以下链接观看）是西雅图可扩展性大会（Seattle Conference on Scalability）的一部分，主要介绍了 YouTube 如何应对可扩展性问题。这个话题我最近挺感兴趣的。（我正努力把这个网站从支持 1 个用户扩展到 5 个用户。）我最近订购了 Cal Henderson（Flickr 技术负责人）撰写的一本关于 Web 应用可扩展性的书，期待明天就能收到（同时还会收到一本纸质版的 SICP，死树版书籍在我的世界里依然是王道）。

这场演讲还算不错，但我更希望它能再具体一些，多讲讲他们成功的解决方案，而不是那些失败的尝试。（另外，像“我们现在用 Bigtable 来解决这个问题”这样的表述简直让我想找个角落哭一场，谢谢啊，那我们该去哪里搞 Bigtable？哦，还有支撑它的那几十万台服务器呢？难道去街头找可疑人士买吗？）好了，进入笔记环节。

可扩展性就是不断迭代、发现并修复瓶颈的过程 Python 在大多数时候“足够快” 用 Psycho 对 Python 进行 JIT 编译 对计算密集型部分（比如加密）编写 C 扩展 通过增加机器和负载均衡来扩展 用 Lighttpd 服务静态内容，Apache 服务动态内容 每个视频由一个小型集群托管（实现故障冗余和应对流量峰值） 保持硬件简单且廉价（支持成本更低、服务成本更低，也更容易找到现有资源获取帮助） 始终从简单方案开始，然后逐步构建 Lighttpd 默认是单进程的（在某些场景下会导致性能不佳） MySQL 数据库复制在写密集型系统中扩展性很差，写操作会挤占读操作 本地内存 > 其他任何存储，磁盘读取 < 其他任何方式 用 vmstat 进行性能分析 层层叠加的多级缓存 数据库分区是最佳的长期解决方案

简单阐述一下数据库分区：其核心思想是拥有大量小型数据库（这样就不会有复制延迟的问题），同时使用哈希机制来决定某条数据应该存储或查询哪个数据库。这能提高缓存的局部性（从而提升缓存命中率），同时这些更小的数据库也更易于移植、更容易放入内存，而且体积小也有利于数据复制（用于备份等）。

如你所见，我并没有捕捉到太多细节。唉，生活就是这样。哦，对了，西雅图可扩展性大会还有其他演讲者的多场 Tech Talk，或许其中一些会更具体一些。
