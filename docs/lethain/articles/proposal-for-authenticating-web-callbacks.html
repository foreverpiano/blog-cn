Web Callback 认证方案提议

2009-09-20 · 阅读原文

Web callback 是一个非常酷的想法，对我来说，无论是在概念上还是效率上，它都是对轮询方式的重大改进。

在轮询设计中，对服务状态一无所知的客户端需要负责检测服务何时发生变化。

这意味着客户端会反复 ping 服务以检查其状态是否发生变化，而且它无法提前判断自己是否在浪费自身（和服务端）的带宽，也不知道是否有新数据需要处理。

轮询就像忙等待（busy wait）一样。

另一方面，Web callback 非常类似于编程中的回调机制，最常见于 JavaScript 中作为单线程实现的权宜之计。

面对这个相当新颖的想法，我脑海中浮现出一个问题：Web callback 服务应该如何对客户端请求进行认证？在一个没有认证的世界里，服务可能会被用作发动 DOS 攻击的载体，而且在未经确认的情况下就向客户端发送消息，通常也是非常不礼貌的行为——我们应该先确认确实是客户端自己发出了请求。

经过思考，我提出两个我认为都可行的方案：

Allow: /api/callback/
  1. A three-way handshake which would begin with the client requesting a service, then the service would send the specified client's hostname a shared secret, which the client would then use to sign requests.
  2. Require an explicit allow line in robots.txt for the given API. Thus site owners would add something along this line in their robots.txt:and then the service would verify such a line exists for the given callback before adding the site to its list of verified callbacks.(This could potentially be done in a new convention file callbacks.txt instead.)

我个人更倾向于第二个方案（特别是希望使用独立的 callbacks.txt 文件），因为它不需要客户端做任何额外的开发工作，实现起来也不会特别困难。

大家有什么想法？

  1. 尽管 Web Workers 有可能在不久的将来（虽然还不是那么近）缓解 JavaScript 单线程的限制。↩
