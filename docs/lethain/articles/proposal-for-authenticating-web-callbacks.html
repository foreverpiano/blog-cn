Web Callback 认证方案提议

2009-09-20 · 阅读原文

Web callback 是一个非常酷的想法，对我来说，无论是在概念上还是效率上，它都是对轮询方式的重大改进。

在轮询设计中，对服务状态一无所知的客户端需要负责检测服务何时发生变化。

这意味着客户端会反复 ping 服务以检查其状态是否发生变化，而且它无法提前判断自己是否在浪费自身（和服务端）的带宽，也不知道是否有新数据需要处理。

轮询就像忙等待（busy wait）一样。

另一方面，Web callback 非常类似于编程中的回调机制，最常见于 JavaScript 中作为单线程实现的权宜之计。

面对这个相当新颖的想法，我脑海中浮现出一个问题：Web callback 服务应该如何对客户端请求进行认证？在一个没有认证的世界里，服务可能会被用作发动 DOS 攻击的载体，而且在未经确认的情况下就向客户端发送消息，通常也是非常不礼貌的行为——我们应该先确认确实是客户端自己发出了请求。

经过思考，我提出两个我认为都可行的方案：

Allow: /api/callback/
三次握手机制：客户端先请求服务，服务端会向客户端指定的主机名发送一个共享密钥（shared secret），客户端再使用该密钥对请求进行签名。或者，要求在 robots.txt 中为该 API 添加明确的 allow 行。这样网站所有者需要在他们的 robots.txt 中添加类似的内容，然后服务端会在将该站点加入已验证 callback 列表之前，检查是否存在这样一行。（也可以考虑使用一个新的约定文件 callbacks.txt 来实现。）

我个人更倾向于第二个方案（特别是希望使用独立的 callbacks.txt 文件），因为它不需要客户端做任何额外的开发工作，实现起来也不会特别困难。

大家有什么想法？

尽管 Web Workers 有可能在不久的将来（虽然还不是那么近）缓解 JavaScript 单线程的限制。↩
