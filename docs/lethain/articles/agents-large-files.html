构建内部 Agent：渐进式披露与处理大文件

2025-12-26 · 阅读原文

我为我们的工作流开发的最有用的早期扩展之一，就是自动将关联图片注入到上下文窗口中，从而显著提升了那些高度依赖截图的工单和消息的回复质量。这个改动实现起来很快，却让工作流变得强大得多。

最近，有不少工作流试图处理 PDF 或 DOCX 等大型复杂文件，而简单粗暴地把整个文件塞进上下文窗口的做法效果并不理想。本文将解释我们如何借鉴渐进式披露（progressive disclosure）原则，让内部 Agent 能够更好地处理大文件。

这是 构建内部 Agent 系列文章的一部分。

大文件与渐进式披露

渐进式披露是指只将当前必要的最少信息放入上下文窗口，并在后续根据需要逐步增加更多细节的做法。

一个典型的例子是 构建内部 Agent：为 Agent Skills 添加支持：

  1. 初始时，只把每个可用技能的描述加入上下文窗口；
  2. 随后根据需要按需加载对应的 SKILL.md 文件；
  3. SKILL.md 中可以进一步指定其他需要加载的辅助文件。

在我们的内部使用场景中，拥有 JIRA 格式化、Slack 格式化和 Notion 格式化这几项技能。部分工作流需要同时使用这三项，但绝大多数工作流最多只需要其中一项，Agent 也很容易判断当前任务需要哪些技能。

文件管理是一个特别有趣的渐进式披露问题：文件在很多场景下都非常有用，但体积又往往很大。例如，Slack 中求助的信息通常是“我遇到了这个登录问题”，如果不把相关图片放进上下文窗口，就根本无法解决。而在另一些工作流中，你可能需要分析一个每天导出的 5-10MB 大小的 PDF，但从中提取出的表格和文本其实只有 10-20KB。当需要对比多个大型 PDF 时，情况会变得更加复杂。

我们的方案

我们针对大文件问题的高层级方案如下：

Files:
  - id: f_a1
    name: my_image.png
    size: 500,000
    preloaded: false
  - id: f_b3
    name: ...
  1. Always include metadata about available files in the prompt, similar to the list of available skills. This will look something like:The key thing is that each id is a reference that the agent is able to pass to tools. This allows it to operate on files without loading their context into the context window.
  2. Automatically preload the first N kb of files into the context window, as long as they are appropriate mimetypes for loading (png, pdf, etc). This is per-workflow configurable, and could be set as low as 0 if a given workflow didn’t want to preload any files.I’m still of mixed minds whether preloading is worth doing, as it takes some control away from the agent.
  3. Provide three tools for operating on files:load_file(id) loads an entire file into the context windowpeek_file(id, start, stop) loads a section of a file into the context windowextract_file(id) transforms PDFs, PPTs, DOCX and so on into simplified textual versions
  4. Provide a large_files skill which explains how and when to use the above tools to work with large files. Generally, it encourages using extract_file on any PDF, DOCX or PPT file that it wants to work with, and otherwise loading or peeking depending on the available space in the context window

这个方案实现起来很快，却极大增强了 Agent 在各种大文件场景下的控制能力。它也是一个很好的例子，说明 LLM 与工具之间的“胶水层”其实是一个复杂而精密的应用层，而不仅仅是简单的粘合。

实际效果如何？

目前运行得很好。特别值得一提的是，我们有一个内部工作流，专门针对工单中附带的文件给出反馈，并与已有的类似文件进行对比。在采用这个方案之前，该工作流完全无法正常运作；而现在，即使没有针对这类大文件的专项支持，它也能工作得相当好，因为 large_files 技能以可复用的方式处理了这部分逻辑，工作流作者甚至无需感知其存在。

后续计划

总体来说，这已经是一套相对独立的完整功能，短期内不需要大量投入。但仍有三个方面需要继续完善：

  1. 在支持子 Agent（subagent）之前，我们的能力会受到限制。在很多场景下，处理大文件的最佳方式是将其交给一个拥有更大上下文窗口的子 Agent，让子 Agent 对内容进行总结，再把总结结果带回到主 Agent 的上下文中。
  2. extract_file 可能需要修改为返回一个可引用的虚拟 file_id，而不是直接返回内容，这个 file_id 可以后续用于 peek_file 和 load_file。这样即使处理非常大的文件，工具也会更加健壮。实际上，目前提取出来的内容一直都相当精简。
  3. 最后，由于我们运行在 AWS Lambda 上，必须使用纯 Python 包，而纯 Python 在解析 DOCX 等复杂的 XML 派生文档格式时速度较慢。最终我们可能会在 Lambda 中增加一层支持 lxml 依赖，未来某个时候可能会这么做。

总的来说，这是对我们内部工作流非常有帮助的一项扩展。
