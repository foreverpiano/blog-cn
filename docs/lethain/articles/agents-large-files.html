构建内部 Agent：渐进式披露与处理大文件

2025-12-26 · 阅读原文

我为工作流开发的最有用的早期扩展之一，就是自动将关联图像注入到上下文窗口中，从而显著提升了对那些高度依赖截图的工单和消息的响应质量。这个改动实现起来很快，却让工作流强大了许多。

最近，我们有不少工作流试图处理大型复杂文件，比如 PDF 或 DOCX。简单粗暴地把整个文件塞进上下文窗口的做法效果并不理想。本文将说明我们如何借鉴“渐进式披露”原则，让内部 Agent 能够更好地处理大文件。

这是 构建内部 Agent 系列文章的一部分。

大文件与渐进式披露

渐进式披露是指只向上下文窗口注入当前最少必要的信息，并在后续根据需要逐步增加更多细节。

一个典型的例子是 构建内部 Agent：为 Agent Skills 添加支持：

初始时，只把每个可用技能的描述放入上下文窗口 后续按需加载对应的 SKILL.md 文件 SKILL.md 可以进一步指定其他需要加载的辅助文件

在我们的内部场景中，我们有用于 JIRA 格式化、Slack 格式化和 Notion 格式化的技能。有些工作流需要同时使用全部三个，但绝大多数工作流最多只需要其中一个，Agent 可以轻松判断当前任务需要哪些技能。

文件管理是一个特别有意思的渐进式披露问题：文件在很多场景下都非常有用，但体积又往往很大。例如，Slack 中的求助请求常常是“我这个登录问题需要帮忙”，如果不把相关图片加入上下文，问题根本无法解决。而在另一些工作流中，你可能需要分析一个每天导出的 5-10MB 大小的 PDF，但从中提取出的表格和文本可能只有 10-20KB。当需要对比多个大型 PDF 时，情况会变得更加复杂。

我们的方案

我们针对大文件问题的高层次方案如下：

始终在 prompt 中包含可用文件的元数据，类似可用技能的列表。形式大致如下： Files: - id: f_a1 name: my_image.png size: 500,000 preloaded: false - id: f_b3 name: ... 关键在于每个 id 都是 Agent 可以传递给工具的引用。这让 Agent 可以在不把文件内容加载到上下文窗口的情况下操作文件。 自动将文件前 N KB 预加载到上下文窗口，前提是文件类型适合加载（png、pdf 等）。这个值可按工作流单独配置，如果某个工作流不希望预加载任何文件，可以将其设为 0。 我对是否值得预加载仍持保留态度，因为这会让 Agent 失去一部分控制权。 提供三个操作文件的工具： load_file(id)：将整个文件加载到上下文窗口 peek_file(id, start, stop)：将文件的某一段加载到上下文窗口 extract_file(id)：将 PDF、PPT、DOCX 等转换为简化的文本版本 提供一个名为 large_files 的技能，说明何时以及如何使用上述工具来处理大文件。它通常会建议对任何需要处理的 PDF、DOCX 或 PPT 文件先使用 extract_file，然后根据上下文窗口剩余空间决定是加载还是预览。

这个方案实现起来很快，却让 Agent 在面对各种涉及大文件的场景时获得了显著更多的控制权。它也很好地说明了 LLM 与工具之间的“胶水层”实际上是一个复杂而精密的应用层，而远非单纯的胶水代码。

实际效果如何？

效果很好。特别是一个围绕“对工单附件中的文档给出反馈，并与现有类似文档进行对比”的内部工作流。在采用这个方案之前，该工作流完全无法正常运转；现在它已经能 fairly 良好地运行，而且不需要为处理这类大文件编写工作流特定的代码，因为 large_files 技能以可复用的方式处理了这一切，工作流作者甚至无需感知它的存在。

下一步计划

总体来说，这套功能已经相对独立，不需要大量后续投入，但我们仍需在以下三个方面继续完善：

在支持 subagent 之前，我们的能力仍然受限。在很多情况下，处理大文件的最佳方式是将其交给一个拥有更大上下文窗口的 subagent，让 subagent 对其内容进行总结，再把总结结果带回主 Agent 的上下文。 extract_file 可能需要修改为返回一个可引用的虚拟 file_id，而不是直接返回内容，后续通过 peek_file 和 load_file 来操作这个虚拟文件。这样即使处理非常大的文件，工具也会更加健壮。实际上，目前提取出来的内容一直都相当精简。 最后，由于我们运行在 AWS Lambda 上，只能使用纯 Python 包，而纯 Python 在解析 DOCX 这类复杂的 XML 派生文档格式时速度较慢。最终的解决方案可能是为 Lambda 添加一层包含 lxml 依赖的环境，我们未来可能会这么做。

总的来说，这是对我们内部工作流非常有帮助的一次扩展。
