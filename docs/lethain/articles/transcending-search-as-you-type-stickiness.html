超越“输入即搜索”的粘滞感

2008-08-29 · 阅读原文

最近我一直在开发一款以搜索为核心功能的桌面应用，并朝着搜索框的理想境界迈出了重要一步。让我们花点时间来梳理一下搜索框的演进层级。

一个输入框 + 一个按钮

最基础的搜索框形式我们都极为熟悉：一个文本框加一个标着“Search”甚至“Go!”的按钮（如果作者在创建时特别有冒险精神的话）。

这种实现存在几个缺陷。首先，它要求用户同时使用键盘和鼠标来完成搜索，这会降低操作速度。其次，它无法为用户提供任何关于搜索质量的反馈。

比这高一档的是同样的搜索框，但增加了一项创新：允许用户按回车键而无需使用鼠标。

一个输入框 + 一个按钮 + 历史记录

再提升一个级别，我们可以为文本框添加某种历史记录功能。这能让用户轻松回到之前的搜索，也帮助他们记住曾经搜索过什么，从而进行优化——尽管由于缺乏快速反馈，他们仍然很难有效改进搜索。

一个神奇的输入框

再提升一个级别，我们直接扔掉按钮，而是在用户输入的同时实时显示搜索结果。这是一个重要的进步，因为它允许用户边输入边看到结果，并根据返回的内容快速调整查询。

然而，这种模式存在一个小缺陷。当搜索耗时超过输入一个字符的时间时，这种搜索方式就会导致界面变得粘滞或卡顿，输入的字符无法即时显示。

这种卡顿感足以让人分心，甚至产生“要不还是让他们按回车吧？那样也挺方便……”的想法，有些人因此又倒退回令人遗憾的“一个输入框 + 一个按钮”的老路。

好朋友们，这并不是终点。

一个神奇——且无延迟——的输入框

解决延迟问题有两个办法。第一个我们不讨论，就是把搜索本身变快。第二个则是延迟搜索，直到搜索变得可控，或者用户放慢了输入速度。

我认为第二种方案才是打造不粘滞且真正有帮助的搜索框的关键。

为了更好地说明，我们假设正在搜索一个具有以下特征的数据库（如果你在无法建立索引的场景下使用全文模糊匹配搜索——比如 SQLite 中的 LIKE——这个模式是相当现实的。即使具体数值不同，下面讨论的技术依然能显著提升界面响应性）。

如果你天真地实现“输入即搜索”，那么输入第一个字符后会暂停 0.5 秒，第二个字符后再暂停 0.3 秒（累计 0.8 秒），第三个字符后再暂停 0.2 秒（累计 1.0 秒），以此类推。

相反，考虑以下策略：输入一个字符后，我们等待 0.5 秒再执行搜索。如果在这段时间内输入了第二个字符，我们就取消第一个搜索，并为第二个搜索启动一个新的定时器（延迟 0.3 秒）。以此类推。

在这个策略下，执行一个 2 个字符的搜索需要 0.6 秒（0.3 秒等待 + 0.3 秒搜索），优于朴素实现的 0.8 秒；而执行 4 个字符的搜索只需 0.2 秒（朴素实现为 1.1 秒），超过四个字符的搜索只需 0.1 秒（朴素实现 ≥1.15 秒）。但如果用户放慢输入速度，搜索就会及时执行并显示引导性数据，帮助用户优化查询。此外，一旦结果足够快，我们也可以切回不延迟的“输入即搜索”模式，以最大程度地引导用户。

我们其实还能进一步优化，因为执行单字符搜索时没必要等满 0.5 秒，只需等待一个合理的时间（比输入下一个字符所需时间稍长即可）。如果这个时间是 0.2 秒，那么最坏情况（单字符搜索）的耗时就从第一种非朴素实现的 1.0 秒降低到 0.7 秒，同时保留了在常规情况（3 个字符以上）下的优秀性能。

另一种避免卡顿的类似方法，是在单独的线程中执行搜索，并在搜索完成时更新结果。这种方法理论上能兼具两者的优点（尽快返回数据，且界面无卡顿），但在所有方案中实现难度最大，尤其在浏览器环境中并不总是可行。

关于它的“实现难度最大”，可以想想这个场景：你输入一个字符后启动了一个搜索线程（需 0.5 秒完成），0.1 秒后又输入了第二个字符（需 0.3 秒完成，比第一个线程早 0.1 秒完成）。这时你会先显示两个字符的搜索结果，0.1 秒后又收到一个字符搜索完成的通知。也许你可以通过拒绝显示那些比当前结果更早启动的更新来解决——这只是增加了一些记录工作——但其他问题还会不断出现。

其中一个问题在于，根据你所使用的后端，同时执行多个查询可能会导致所有搜索都变慢（最多同时有 N 个查询，N 为搜索词的长度）。你可以通过在新搜索创建时终止所有正在进行的搜索来避免这一点，但最终我的经验是，使用上面详细描述的策略（非线程化的延迟启动搜索），你就能创建出极具吸引力的用户界面体验，而无需将搜索移到单独线程所带来的复杂性。
