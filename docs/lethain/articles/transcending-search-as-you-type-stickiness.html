超越“输入即搜索”的粘滞感

2008-08-29 · 阅读原文

最近我正在开发一款以搜索为核心功能的桌面应用，并朝着搜索框的理想状态迈出了重要一步。现在让我们花点时间来梳理一下搜索框的演进层次。

一个输入框 + 一个按钮

最基础的搜索框形式我们都非常熟悉：一个文本输入框搭配一个标着“Search”或“Go!”的按钮——如果开发者当时特别有创意的话。

这种实现方式存在几个缺陷。首先，它要求用户同时使用键盘和鼠标来完成搜索，这会降低操作效率。其次，它无法为用户提供任何关于搜索质量的反馈。

稍微改善一点的版本是同样的搜索框，但增加了一个创新：允许用户按回车键而不是必须用鼠标点击按钮。

一个输入框 + 一个按钮 + 历史记录

再提升一个层次，我们可以为文本框添加某种历史记录功能。这能让用户轻松回到之前的搜索，也帮助他们记住自己搜过什么，以便进一步优化查询——尽管由于缺乏快速反馈，他们仍然难以有效改进搜索。

一个神奇的输入框

继续升级，我们彻底抛弃按钮，转而在用户输入的同时实时显示搜索结果。这是一个重要的进步，因为它允许用户边输入边看到结果，并根据返回的内容快速调整查询。

然而，这种模式存在一个小缺陷。当搜索耗时超过输入一个字符所需的时间时，这种实时搜索就会导致界面出现“粘滞”或延迟的现象——用户敲下的字符无法立即显示出来。

这种卡顿感足以让人产生“我干脆让他们按回车好了？那样还是挺简单的……”之类的想法，甚至导致一些开发者无奈地退回到那个可怜的“一个输入框 + 一个按钮”的老策略。

好在朋友们，这并不是终点。

一个神奇——且无延迟——的输入框

针对延迟问题，有两种解决方案。第一种我们不考虑，就是让搜索本身变得更快。第二种则是延迟搜索，直到搜索变得可控或者用户放慢输入速度。

我认为第二种方案才是打造不卡顿且真正有帮助的搜索框的关键。

为了说明清楚，我们假设正在搜索一个具有以下特征的数据库（如果你在无法建立索引的场景下使用全文模糊匹配搜索——比如 SQLite 中的 LIKE——这个模式还是比较现实的。即使具体数值有所不同，下面讨论的技术仍能显著提升界面响应性）。

如果采用朴素的“输入即搜索”方式，你会在输入第一个字符后暂停 0.5 秒，第二个字符后再暂停 0.3 秒（累计 0.8 秒），输入第三个字符后暂停 0.2 秒（累计 1.0 秒），以此类推。

现在考虑这种策略：输入一个字符后，我们等待 0.5 秒再执行搜索。如果在这段时间内输入了第二个字符，我们就取消第一次搜索，并为第二次搜索启动一个定时器（延迟 0.3 秒）。以此类推。

在这种策略下，进行 2 个字符的搜索需要 0.6 秒（0.3 秒等待 + 0.3 秒搜索），而朴素实现需要 0.8 秒；进行 4 个字符的搜索仅需 0.2 秒（朴素实现为 1.1 秒），超过四个字符的搜索仅需 0.1 秒（朴素实现 ≥1.15 秒）。但如果用户放慢输入速度，搜索就会执行并显示引导性数据，帮助用户优化查询。此外，一旦结果返回足够快，我们可以切换回无延迟的“输入即搜索”模式，以最大程度地引导用户。

我们其实还能进一步优化，因为进行单字符搜索时并不需要等待整整 0.5 秒，只需等待一个合理的时间（比输入下一个字符略长一点即可）。如果这个时间设为 0.2 秒，那么最坏情况（单字符搜索）的耗时将从 1.0 秒（第一个非朴素实现）降低到 0.7 秒，同时保持在常规情况（3 个字符以上）下的优异性能。

另一种避免延迟的类似方法，是在单独的线程中执行搜索，并在搜索完成时更新结果。这种方法理论上能兼具两者的优点（尽快返回数据，且界面无卡顿），但在所有方案中实现难度最高，尤其在浏览器环境中不太现实。

关于“实现难度最高”，可以想象这样一个场景：你输入一个字符后启动了一个搜索线程（需要 0.5 秒完成），0.1 秒后又输入第二个字符（该搜索将在 0.3 秒后完成，比第一个线程早 0.1 秒结束）。这时你会先显示两个字符的搜索结果，0.1 秒后又收到一个字符搜索完成的通知。你或许可以通过拒绝显示比当前结果更早启动的更新来解决这个问题——这只是增加了一些记录工作——但还会产生其他问题。

其中一个问题是，根据你所使用的后端系统，同时执行多个查询可能会导致所有搜索都变慢（最多同时进行 N 个查询，N 为搜索词长度）。你可以通过在新搜索创建时终止所有正在进行的搜索来避免这一点。但最终我的经验是，使用上面详细介绍的策略（非线程化的延迟触发搜索），你就能打造出极具吸引力的用户界面体验，而无需承担将搜索移到独立线程的复杂性。
