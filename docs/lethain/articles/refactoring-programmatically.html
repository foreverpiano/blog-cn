用程序化方式重构 Ruby 代码

2018-02-13 · 阅读原文

当你加入一个新团队时，最先要搞清楚的事情之一就是他们偏好的编码风格。他们很可能已经配置了像 rubocop 或 flake8 这样的 linter，把风格争议交给计算机这些最较真的家伙去处理。不过有时候，你会发现有理由去修改一个代码仓库的编码风格，或者要合并另一个风格不同的代码库。

在一定规模下，你可能还能手动修复这些问题，但如果项目包含成千上万的文件，再多的咖啡因也掩盖不了其中的痛苦。

Linting 只是一个更广泛问题类别中的例子：如何重构大型代码库？虽然常见的回答是干脆不要大规模重构，但那往往会导致代码库随时间迅速劣化。其实可以做得更好！

大多数语言都提供了将源代码表示为 s-expression 的库，你可以以新的方式修改它们，进而生成修改后的源代码。对于 Ruby 来说，两个能完成这项任务的库是：

ruby_parser，它负责解析 Ruby 文件并输出其 s-expression；ruby2ruby，则负责将 s-expression 转换回 Ruby 代码。

让我们来试试看。（完整源代码可在 Github 获取。）

假设我们有一个名为 incr 的方法，之前需要传入两个参数，但大多数调用都是递增 1，因此我们给第二个参数添加了默认值 1。现在我们希望重写所有对 incr 的调用，只在第二个值与默认值不同时才显式传入。

于是我们可以想象有这样的代码：


def incr(x, i = 1)
  x + i
end
incr(5, 100)
incr(3, 1)
incr(10, 1)
incr(17, 17)

我们希望将其重写为：


def incr(x, i = 1)
  x + i
end
incr(5, 100)
incr(3)
incr(10)
incr(17, 17)

我们代码中最有趣的部分将在一个 rewrite 函数中，所以先来编写这个函数所依赖的脚手架，然后直奔有趣的部分。

脚手架部分很短，需要引入几个库，把标准输入解析为 s-expression，将这些 s-expression 重写为 Ruby 代码，最后输出到标准输出。


require 'ruby_parser'
require 'ruby2ruby'

def rewrite(expr)
  expr
end

parsed =  RubyParser.new.parse(ARGF.read)
puts Ruby2Ruby.new.process rewrite(parsed)

假设你把上面的示例输入保存在名为 refactor.input 的文件中，并将此脚本命名为 refactor.rb，那么可以这样运行它：


ruby refactor.rb < refactor.input

这其实已经很酷了，因为我们正在接收一段代码，对其进行解析，然后重新组合起来，但真正有趣的部分还在后面：对它进行修改！

细心的读者会注意到，输出版本中出现了一些多余的括号。我在这里略过是因为它们仍是等价的 Ruby 代码，但确实有点烦人，或许会有细心的读者提出一个不依赖正则表达式的解决方案。

rewrite 函数会被 ruby_parser 在顶层 s-expression 上调用，你可以从中递归地探索程序中的所有 s-expression。为了稍微了解单个 s-expression 的结构，我们来看下面这个输入：


incr(3, 1)

它被表示为一个 Ruby 对象，其结构是：


s(:call, nil, :incr, s(:lit, 1), s(:lit, 2))

按顺序，这些值的含义分别是：

:call 是这个 s-expression 的类型（其他常见的类型还有 :block、:lasgn 和 :defn），用于表示函数调用；第二个值 nil 对 :call 来说没有特别含义，但在其他类型中可能有意义；:incr 是被调用函数的名称；剩下的值则是传递给被调用函数的参数。

回到我们最初的问题：能否在调用 :incr 函数时，如果第二个参数与默认值相同，就将其移除？是的，我们现在已经掌握足够信息来编写这个函数：


def rewrite(expr)
  if expr.is_a? Sexp
    if expr[0] == :call &&
       expr[2] == :incr &&
       expr.size == 5 &&
       expr[4][0] == :lit &&
       expr[4][1] == 1

      # remove the second parameter                                                                                                                               
      expr.pop()
    end

    # descend into children                                                                                                                                       
    expr.each { |x| rewrite(x) }
  end
  expr
end

这里有三个值得注意的部分：

我们应该只对 s-expression 对象进行重写！如果我们正在调用 incr 并且第二个参数正是新的默认值（即字面量 1），那么应该把它移除。对每个 s-expression 的内容进行递归遍历，否则你只会看到顶层的 :block s-expression，那可就无聊了。

退后一步看，我觉得这相当了不起！我们现在能够用程序化的方式重写代码了。借助这个技术，我们甚至可以维护大型代码库，而无需进行大量枯燥的手工劳动。

让我们再试一次，做一点更有野心的事情。假设你招了一批 Python 程序员，他们总是不学 Ruby 的 each 写法，而继续写 Python 风格的 for 循环，我们希望把它们重写为使用 each 的形式。

你的输入可能是这样的：


def count(lst)
  i = 0
  for ele in lst
    i += 1
  end
end

而你希望得到的输出是：


def count(lst)
  i = 0
  lst.each { |ele| i = i + 1 }
end

再来尝试一次我们的 rewrite 函数，这次稍微复杂一些：


def rewrite(expr)
  if expr.is_a? Sexp
    if expr[0] == :for
      lst = expr[1]
      param = expr[2]
      func = expr[3]
      expr.clear
      expr[0] = :iter
      expr[1] = Sexp.new(:call, lst, :each)
      expr[2] = Sexp.new(:args, param[1])
      expr[3] = func
    end

    # descend into children                                                                                                                                       
    expr.each { |x| rewrite(x) }
  end
  expr
end

虽然有点乱，但一旦你开始玩转这项技术，这也是一个相当精彩的演示。例如，你可以想象只在重构后的 for 循环复杂度足够低时才进行转换。

接下来呢？

这些都是非常人为设计的例子，但我认为已经足以让你开始思考这项技术如何在实际工作中发挥作用，尤其是当你的工作涉及将大型代码库迁移到新实现时。Google 的《Large-Scale Automated Refactoring Using ClangMR》是一个在极大规模上实践这一思路的有趣案例，而《Source Code Rejuvenation is Not Refactoring》则是对这个主题的另一番探索。

最重要的是，我认为这是一个很好的提醒：对于大型迁移，不要陷入“我手动搞定就行”的思维模式，我相信这种模式最终会成为公司整体吞吐量的瓶颈。
