以编程方式重构 Ruby 代码

2018-02-13 · 阅读原文

当你加入一个新团队时，最先要搞清楚的事情之一就是他们偏好的代码风格。他们很可能已经配置了像 RuboCop 或 flake8 这样的 linter，把风格争议交给计算机这些至高无上的吹毛求疵者来处理。不过有时候，你会发现有理由去修改一个代码仓库的编码风格，或者要合并另一个采用不同风格的代码库。

在一定规模下，你可能还只能手动修复问题，但对于跨越数千个文件的项目来说，再多的咖啡因也无法掩盖其中的痛苦。

代码风格检查只是一个更大类问题中的例子：如何重构大型代码库？虽然常见的回答是“干脆不要大规模重构”，但这往往会导致代码库随着时间快速退化。其实是可以做得更好的！

大多数编程语言都提供库，能将源代码表示为 s-expression，然后你就可以通过新的方式修改它们，并生成修改后的源代码。对于 Ruby 来说，两个能实现这一目标的库是：

  • ruby_parser which parses a Ruby file and outputs its s-expressions,
  • ruby2ruby which translates s-expressions into Ruby code.

让我们来试试看它们。（完整的源代码可在 Github 上找到。）

假设我们有一个名为 incr 的方法，它曾经需要两个参数，但大多数调用都是递增 1，因此我们给第二个参数加上了默认值 1。现在我们希望重写所有对 incr 的调用，只有当第二个参数与默认值不同时才显式传入它。

于是我们可以想象有这样一段代码：


def incr(x, i = 1)
  x + i
end
incr(5, 100)
incr(3, 1)
incr(10, 1)
incr(17, 17)

我们希望将其重写为下面这样：


def incr(x, i = 1)
  x + i
end
incr(5, 100)
incr(3)
incr(10)
incr(17, 17)

我们代码中最有趣的部分会放在一个 rewrite 函数里，所以我们先来编写这个函数所依赖的脚手架代码，然后再冲向有趣的部分。

幸运的是，脚手架代码相当简短：引入几个必要的库，从标准输入解析成 s-expression，将这些 s-expression 转换回 Ruby 代码，最后输出到标准输出。


require 'ruby_parser'
require 'ruby2ruby'

def rewrite(expr)
  expr
end

parsed =  RubyParser.new.parse(ARGF.read)
puts Ruby2Ruby.new.process rewrite(parsed)

假设你把上面的示例输入保存在名为 refactor.input 的文件中，并将下面的代码保存为 refactor.rb，那么你可以用以下命令运行它：


ruby refactor.rb < refactor.input

这其实已经很酷了，因为我们正在接收一段代码，对其进行解析，然后重新组合成代码。但真正有趣的部分还在后面：对它进行修改！

细心的读者会注意到，输出版本中出现了一些多余的括号。我在这里略过不提，因为它们仍是等价的 Ruby 代码，只是稍微有点烦人，或许会有细心的读者提出一个不依赖正则表达式的解决方案。

rewrite 函数会被 ruby_parser 在顶层的 s-expression 上调用，你可以从中递归地探索程序中所有的 s-expression。为了稍微了解单个 s-expression 的结构，考虑以下输入：


incr(3, 1)

它在 Ruby 中被表示为一个具有如下结构的对象：


s(:call, nil, :incr, s(:lit, 1), s(:lit, 2))

按顺序，这些值的含义分别是：

  • :call is the kind of s-expression (some other common kinds are :block, :lasgn and :defn) for invoking a function,
  • the second value, nil, doesn’t contain anything interesting for :call, although it does for other kinds,
  • :incr is the name of the function invoked,
  • remaining values are the parameters passed to invoked function.

回顾我们最初的问题：如果调用 :incr 函数时第二个参数与默认参数值相同，我们能否将其移除？是的，现在我们已经掌握了足够的信息来编写这个函数：


def rewrite(expr)
  if expr.is_a? Sexp
    if expr[0] == :call &&
       expr[2] == :incr &&
       expr.size == 5 &&
       expr[4][0] == :lit &&
       expr[4][1] == 1

      # remove the second parameter                                                                                                                               
      expr.pop()
    end

    # descend into children                                                                                                                                       
    expr.each { |x| rewrite(x) }
  end
  expr
end

这里有三个值得注意的部分：

  • We should only rewrite objects that are s-expressions!
  • If we’re calling incr and the second parameter is the new default parameter, a lit of value 1, then we should remove it.
  • Recursively descend into the contents of each s-expression. Otherwise you’ll only see the top-level :block s-expression which is pretty boring.

退后一步想想，我觉得这真的很棒！我们现在可以编程式地重写代码了。利用这项技术，我们甚至能够维护大型代码库，而无需进行大量枯燥的手工劳动。

让我们再试一次，做一点更有野心的事情。想象一下，你招聘了一批 Python 程序员，他们总是写 Python 风格的 for 循环，而不愿意去学习 Ruby 的 each 惯用法，我们希望把这些代码重写成使用 each 的形式。

你的输入代码可能是这样的：


def count(lst)
  i = 0
  for ele in lst
    i += 1
  end
end

而你希望得到的输出是：


def count(lst)
  i = 0
  lst.each { |ele| i = i + 1 }
end

再来尝试一下我们的 rewrite 函数，这次要稍微复杂一些：


def rewrite(expr)
  if expr.is_a? Sexp
    if expr[0] == :for
      lst = expr[1]
      param = expr[2]
      func = expr[3]
      expr.clear
      expr[0] = :iter
      expr[1] = Sexp.new(:call, lst, :each)
      expr[2] = Sexp.new(:args, param[1])
      expr[3] = func
    end

    # descend into children                                                                                                                                       
    expr.each { |x| rewrite(x) }
  end
  expr
end

虽然有点乱，但一旦你开始尝试这种技术，它也能很好地展示你能做到的事情。例如，你可以想象只在重构后的 for 循环复杂度足够低时才进行转换。

接下来呢？

这些都是非常人为构造的例子，但我认为它们已经足以让你开始思考如何将这项技术有效地应用到自己的工作中，特别是当你的工作涉及将大型代码库迁移到新的实现时。Google 的《Large-Scale Automated Refactoring Using ClangMR》是一个在极大规模上进行此类工作的有趣案例研究，而《Source Code Rejuvenation is Not Refactoring》则是对这个主题的另一篇探讨文章。

最重要的是，我认为这是一个很好的提醒：对于大型迁移项目，要避免陷入“我就慢慢手动搞定它”的思维模式，我相信这种思维最终会成为公司整体吞吐量的瓶颈。
