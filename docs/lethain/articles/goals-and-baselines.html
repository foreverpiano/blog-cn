目标与基线

2018-07-05 · 阅读原文

每家公司成长到一定阶段，都会出现这样一个时刻：高层规划从讨论具体项目转变为讨论目标。这种转变会在各级领导范围内递归发生，因为所负责的领域变得过于宽泛或复杂，领导者已无法持续掌握每个项目的细节。

这可能是一个非常赋能的时刻，因为目标将“做什么”和“怎么做”解耦开来；但对所有人来说，这也可能是一次令人困惑的转变：写出清晰的目标需要一些练习。

定义目标

糟糕的目标和单纯的数字没什么区别，比如“我们的 p50 构建时间要低于 2 秒”或“我们要完成 8 个大型项目”。当你读完一个目标，却不确定它是否具有挑战性、是否真正重要时，它其实就只是一个数字。

好的目标由四类特定的数字组成：

  1. A target states where you want to reach,
  2. A baseline identifies where you are today,
  3. A trend describes the current velocity,
  4. A timeframe sets bounds for the change.

将这些组合在一起，一个结构良好的目标形式是：“在 Q3，我们要将首页渲染时间从 600ms（p95）降低到 300ms（p95）。在 Q2，渲染时间从 500ms 上升到了 600ms。”

一个有效目标要通过两项检验：不熟悉该领域的人能否从中感受到目标的难度，以及事后能否判断它是否成功达成。如果你明确定义了这四个方面，通常就能同时满足这两个标准。

投资目标与基线

有两类特别重要的目标：投资目标和基线目标。投资目标描述你希望达到的未来状态，基线目标则描述你希望维持的当前状态。

假设你想加快数据管道的速度，目标可能是：“到 Q3 结束时，核心批处理作业的完成时间应在 3 小时以内（p95）。当前需要 6 小时（p95），且在整个 Q2 期间变慢了 2 小时。”这是一个结构良好的目标，但还不够完整，因为你很可能明天就把集群规模翻倍来达成它，而这可能并不是理想的结果。

避免这类意外结果的最佳方式，是将投资目标与基线指标配对使用，后者有时被称为反制指标（countervailing metrics）。以数据管道为例，一些基线指标可能是：

  • Efficiency of running core batch jobs should not exceed current price of $0.05 per GB.
  • Core batch jobs should not increase alert load on teams operating or using the pipeline, currently alerting twice per week.

基线指标有助于缩小为达成投资目标而探索的方案空间，同时也能帮助你判断何时应该暂停追求当前目标，转而投入到平台质量建设中。例如，如果你正朝着推出新功能稳步推进，但站点稳定性已跌破基线，这个框架就能提供一种结构化的方式来触发优先级的重新平衡。

虽然基线通常是为了维持当前属性，但你也可以决定在触发优先级调整前接受一定程度的退化。比如，只要投资目标能够达成，你可以接受成本增加 10%。这种事先对权衡做出清晰界定的做法，威力相当强大。

计划与契约

目标最常见的用途是在规划流程中。通过与每个团队商定投资目标和基线目标的组合，你可以在设定清晰期望的同时，让团队完全拥有如何满足这些约束的自主权。我的经验是，投资目标的数量应该尽量少，或许三个就够，它们应当成为规划讨论的重点。

你可能需要设定的基线目标多于投资目标，但最好将两者分开讨论，以免让对话变得拖沓。理想情况下，基线目标应在多个规划周期中持续沿用，它们为投资目标提供框架，但在具体的规划会议中不需要占用太多讨论时间。

唯一可能的例外是，当你将某项基线作为与外部方的契约（通常是指定 SLO）时，这时你可能需要比其他基线更明确地讨论它：未能达成 SLO 很可能需要立即调整优先级，而其他大多数基线的缺失一般可以更系统地处理。

从 OKR 开始，有几十种不同的指标设定方法，但我发现这个格式是一种轻量且实用的起点。如果大家有发现其他更简单或更有用的方法，我很乐意听取你们的分享！
