构建工程策略的步骤

2025-03-27 · 阅读原文

你经常会看到一堆杂乱无章的想法被贴上“策略”的标签。即使这些文档里塞满了各种想法，也往往难以理解。这也是为什么大多数工程师会说他们公司没有清晰的策略，尽管根据我的经验，所有公司其实都在遵循某种策略，即便它没有被明确记录下来。

本章提出了一种可重复、结构化的策略起草方法。它会介绍该方法中的每个步骤，这些步骤将在各自的章节中进一步展开详细说明。本章将涵盖以下内容：

这五个步骤如何相互配合来帮助制定策略，特别是防止实践者跳过那些感觉别扭或具有挑战性的步骤。 步骤 1：探索你正在处理的策略所涉及的更广泛行业想法和实践。探索意味着了解哪些最新研究可能会改变你的方法，以及自你上次解决类似问题以来，行业最先进的方法发生了哪些变化。 步骤 2：诊断你问题的具体细节。在尝试解决问题之前，很难放慢脚步去清晰地理解问题，但如果没有清晰的诊断，要很好地解决任何问题会更加困难。 步骤 3：提炼是将一组原始、未经验证的想法与现实进行检验的过程。本章介绍了三种支持验证过程的技术：策略测试、系统建模和 Wardley 映射。 步骤 4：策略是通过制定权衡和决策来解决你的诊断结果。这些决策范围很广，从指定软件如何架构，到如何审查 Pull Request，再到如何在组织内分配人力。 步骤 5：运营机制是将策略转化为组织内部实际推动力的具体手段。这些可以是提醒你代码变更没有关联测试的提示，也可以是每周召开的用于审视迁移进展的会议。 无论这些步骤是必须严格遵守，还是可以根据情况调整和实验，以及在个人层面，当你觉得某些步骤效果不佳时，是否应该坚持尝试。

从本章的起点出发，你将获得策略制定中每个步骤的高层次概述，并可以决定接下来想深入阅读哪些部分。

本章出自《Crafting Engineering Strategy》。

这些步骤如何成为策略

制定有效的策略并不是机械地念诵公式。你不能仅仅按照这些步骤走，就保证能创造出一个伟大的策略。然而，我持续观察到的情况是，策略失败更多是由于可以避免的错误，而不是源于根本上不健全的思考。忙碌的人会跳过某些步骤，尤其是那些他们不喜欢或之前失败过的步骤。

这些步骤就是用来避免这类错误的脚手架。通过常规练习，你会建立强大的习惯和直觉，知道哪种方法最适合当前正在制定的策略。同时，它们也有助于将策略转化为一种社区实践，让你、你的同事以及更广泛的工程生态系统能够共同参与其中。

每个步骤都是流入下一个步骤的输入。你的探索是坚实诊断的基础。你的诊断帮助你在无限的政策空间中寻找当前最需要的方案。运营机制则帮助你将策略转化为支持你战略的实际力量，而不是停留在抽象的论述上。

如果你对这些步骤持怀疑态度，你当然应该保持这种怀疑，但请先尝试几次再完全放弃。你或许也会喜欢连接工程策略的理论与实践一章中关于理论与实践之间桥梁的讨论。

探索

探索是在允许自己承诺采用某一种方法之前，有意识地搜索策略的问题空间和解决方案空间的实践。它意味着了解其他公司和团队如何处理类似问题，以及他们的方法是否也适合你。它还包括理解为什么你在前东家取得巨大成功的方法，不一定是你当前组织的最佳解决方案。

诊断

诊断是在决定采用何种策略来应对上下文之前，正确识别该上下文的尝试。从你探索中获得的认知和你对当前情况的理解出发，建立诊断会迫使你在完全理解问题细微差别之前，暂缓思考解决方案。

诊断可以主要由数据驱动，比如 驾驭私募股权所有权：

我们的工程人力成本今年同比增长了 15%，前一年同比增长了 18%。人力分别增长了 7% 和 9%，人力与人力成本之间的差异来自薪酬等级调整（4%）、重点招聘高级职位（3%）以及在成本较高的地理区域增加招聘（1%）。

诊断也可以不那么依赖数据，而是旨在总结问题，比如 如何整合 Stripe 收购的 Index？（2018 年） 在收购完成前对技术整合已知和未知要素的总结：

我们需要快速整合收购的初创公司以满足这个时间表。我们只了解这项工作所涉及的少量细节。我们确实知道，销售点设备直接操作支付详细信息（例如，销售点设备知道它读取的信用卡详细信息）。我们的合规义务将此类活动限制在我们的“令牌化环境”中，这是一个高度安全且隔离的环境，可以直接访问支付详细信息。该环境会将支付详细信息转换为唯一令牌，其他环境可以使用该令牌操作支付详细信息，而无需承担直接访问底层支付详细信息的合规开销。

提炼（测试、映射与建模）

策略提炼是一套方法工具包，用于识别诊断中哪些部分最为重要，并验证你解决诊断的方法是否 действительно有效。本章深入探讨了三种特定方法的使用细节：策略测试：避免瀑布式策略陷阱，通过迭代优化。、用系统建模来完善策略 和 用 Wardley Mapping 完善策略。

一个常见的争议点是，提炼应该在诊断之前进行。另一个争议是，映射和建模是两个独立的步骤，映射应该在诊断之前进行，而建模应该在策略制定之后。还有一种观点认为，提炼应该是策略的最后一步，从而使整个流程变成一个循环。这些都是合理的观察，下面让我来解释我采用这种结构的理由。

对大多数策略而言，最大的风险远不是过早建模或过晚映射，而是完全跳过这两个步骤。我最关心的是如何降低映射和建模所需投入的门槛，让更多人真正去执行这些步骤。在探索和诊断之后进行提炼，能让你将精力集中在数量较少的关键领域上。

话虽如此，在策略制定过程中，你很可能需要在多个地方进行提炼。你有同样大的概率会进行三次小规模提炼，而不是一次大规模提炼。

策略

策略是将你的诊断转化为具体计划的过程。这个计划还需要能够真正落地，这就需要仔细研究公司内部哪些做法曾经有效，以及你在探索当前问题时发现的新想法。

策略的范围可以是从提供方向性指导，比如 如何控制用户数据的访问权限？ 中的指导原则：

良好的安全讨论不会将决策框定为安全与可用性之间的妥协。我们将追求多维度的权衡，以同时提升安全性和效率。每当我们将讨论框定为在安全性和实用性之间进行权衡时，这就表明我们正在进行错误的讨论，应该重新思考我们的方法。我们将优先采用既能自动授权、又能自动记录访问客户数据理由的机制。最明显的例子是，自动授予客服人员访问权限，让其处理分配给该人员的用户支持工单。（并且在工单被重新分配或解决后移除该权限。）

到承诺暂缓决策留待后续处理，比如 如何整合 Stripe 收购的 Index？（2018 年） 中的做法：

将是否引入 Java 的决策推迟到以后：引入 Java 与我们现有的工程策略不兼容，但目前我们也无法就如何处理该决策与利益相关者达成一致。此外，我们认为尝试解决这个问题会分散注意力，妨碍我们在六个月内推出联合产品的及时目标。我们将在推出初始版本后再进行讨论。

运营

即使是最好的策略也需要被解读。总会出现策略制定者从未预料到的新情况，而且策略可能在制定者离开组织很久之后仍在生效。运营机制就是你策略的具体实现形式。

最简单的机制是明确的升级路径，如 “我们是一家产品工程公司！”——Calm 的工程策略 中所示：

例外情况需由 CTO 批准，且必须以书面形式给出。上述策略是故意设计得较为严格的。有时它们可能是错误的，我们会为此做出例外处理。但每次例外都应是经过深思熟虑的，并且基于我们双方都认同需要解决的具体问题以及解决方式。如果我们都朝着自己偏好的解决方案分散发力，那么我们将为 Calm 创造负面杠杆，而不是成为推动产品发展的引擎。

这个结构是否神圣不可侵犯？

当有人在努力撰写策略文档时，别人经常推荐的第一个工具就是策略模板。模板很好：它们能将一个原本宽泛的项目中的模糊性降低到更易于处理的地步。如果你正在犹豫是否应该使用模板来制定策略：当然，可以用！

然而，我发现那些善意且经过深思熟虑的模板，往往会变成笨重、冷漠的文档，对任何人都没有太大帮助。好的模板的秘诀在于，必须有人来负责它，而这个人首先要关心的是模板的使用者，而不是那些想把各种要求塞进策略制定流程的各方利益相关者。你计划中的安全、合规和成本确实非常重要，但许多组织开始在这些文档中层层叠加越来越多的要求，直到撰写它们变得极其痛苦。

我能给正在尝试撰写策略的人最好的建议是，只要你能解释清楚某个要素原本想要达成什么目的，你就应该抛弃所有阻碍你的策略元素。例如，如果你正在起草一份策略，却没有找到任何适合的运营机制，那没关系，放弃这个部分也没问题。归根结底，这个结构本身并不是神圣不可侵犯的，真正重要的是各个部分背后的思考。
