Redis 驱动的 Python 数据结构

2010-09-05 · 阅读原文

最近在工作中我频繁使用 Redis，并且越来越喜欢它。后来我突然想到，用 Redis 作为 Python 最常用的数据结构——列表（list）和字典（dict）的后端，应该非常简单直接。这不仅实现起来容易，还能带来一些实际好处：更高的可读性、跨进程/线程/机器的分布式能力，以及对现有接口的熟悉度。

基于这些想法实现的代码已在 Github 上开源。在你跑去查看之前，我们先来看看这种方法几个简单却强大的应用场景：共享配置机制和经典的生产者-消费者示例。

共享配置

当系统规模扩大后，管理共享配置数据就成了一个越来越重要的问题。幸运的是，这是一个可以解决的问题。下面就是其中一种方案。

非常直截了当。长期运行的进程需要偶尔检查配置是否发生变化，虽然有点麻烦，但完全可行。

分布式生产者和消费者

当架构发展到一定阶段，大多数系统都会急需一个消息队列。很多时候人们最终会在 MySQL 上层实现一个奇怪的队列。还有不少人选择了 RabbitMQ，但它并不总是能完全兑现“开箱即用的消息传递”这一口号。让我们来看看另一种不同的方法。

系统中可以存在大量的生产者和消费者，而且它们不必运行在同一台机器上。你无需纠结于 Python 的线程或 multiprocessing，直接从命令行启动任意数量的实例即可。很不错，对吧？

配置良好的 Redis 集群可以在主库宕机时自动将写操作 failover 到从库，让系统在不丢失数据、且无需等待主库恢复的情况下继续运行；这些特性用 RabbitMQ 很难实现。对于更有野心的场景，可以通过 Redis 的 LTRIM 命令轻松限制队列的最大长度，从而保证队列的稳定性。最有野心的做法是，可以参考 Kestrel 的策略，监控队列大小，当队列过大时将消息拉出并写入文件，等队列恢复后再重新填充（这可以通过使用两个 Redis list 来实现，在不丢失消息顺序的前提下：对象从输入队列被移动到序列化文件或处理队列，当处理队列小于最小大小时优先填充处理队列，且在磁盘上还有剩余数据时，不直接将数据从输入队列写入处理队列）。
