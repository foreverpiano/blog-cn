史诗级 PyObjC 教程（二）：添加库与绑定

2008-08-24 · 阅读原文

在本系列第一部分中，我们介绍了如何在 Leopard 上开始使用 PyObjC，使用 XCode 创建了一个项目，对 InterfaceBuilder 有了一定了解，并基本搭建了一个应用程序的框架，接下来我们就要开始逐步将其完善。

如果你没有跟着第一部分操作，也可以直接下载这个包含项目的 zip 文件继续学习。更推荐的是，你可以访问本教程的 GitHub 仓库，这样就能看到所有的修改过程（包括那些惨痛的错误）。

首先，一个快速修正

打开 MWController.py，将 _results = [] 这行改为 results = []。修改后 MWController 类的字段应该如下所示：

class MWController(NSObject):
    tableView = objc.IBOutlet()
    textField = objc.IBOutlet()
    results = []

基本上，我犯了一个很明显的错误：方法名前面的下划线与 Python 和 Objective-C 之间的桥接不兼容。也许这是一个宝贵的教训：在方法名中使用下划线可能会产生意想不到的后果。

因此，我建议对方法和函数名使用驼峰命名法。例如使用 thisIsAMethod 而不是 this_is_a_method。虽然这样方法名看起来有点丑，但总比给自己埋下一堆地雷要好。

现在我们回到预定的教程内容。

metaweb.py 和 NSArrayController

本部分将介绍 PyObjC 的两个重要概念。首先，我们将以 metaweb.py 为例，展示如何在 PyObjC 项目中使用 Python 库。其次，我们将学习 Cocoa Bindings。

我们先从集成 metaweb.py 开始，这一步出奇地简单。而讲解 Cocoa Bindings 和 NSArrayController 会稍微复杂一些，但一旦你理解了绑定机制，你会惊叹于自己能多么快速地创建复杂的用户界面。

将 metaweb.py 集成到 MetaWindow.app 中

在开始之前，metaweb.py 有一个前提依赖：simplejson。你可以从 PyPI 下载，或者使用 easy_install 安装：

sudo easy_install simplejson

安装完 simplejson 后，我们需要下载 metaweb.py。进入你存放 svn 检出代码的目录（我偷偷用了 ~/svn/ 目录），然后检出仓库的副本：

svn checkout http://freebase-python.googlecode.com/svn/trunk/ freebase-python-read-only

现在在 XCode 中打开我们的 MetaWindow 项目。你可以先打开 XCode，然后选择 File->Open Recent Projects，或者直接从 Finder 中打开 MetaWindow/MetaWindow.xcodeproj 文件。

项目打开后，前往 Project 菜单，选择 Add to Project...（如果 Add to Project... 选项不可选，请返回项目窗口，点击左侧大纲视图最顶层的项目图标——标有 MetaWindow 的默认应用程序图标——然后再试一次。）

接着选择 freebase-python-read-only/metaweb-py/metaweb.py 文件，点击 Add。随后会弹出一个面板，提供一些将文件添加到项目的选项。勾选 Copy items into destination group's folder (if needed) 旁边的复选框，然后点击 Add。

在项目窗口中，将 metaweb.py 文件拖拽到 Other Sources 文件夹中。

顺便提一句，项目窗口中 Groups & Files 大纲视图里的文件夹都是逻辑结构，并非真实的文件系统文件夹。当你在组织器中（技术上称为“组”）创建一个文件夹时，文件系统上并不会真的创建一个对应文件夹。同样，当你把 metaweb.py 拖到 Other Sources 组里时，实际上并没有移动文件系统上的 metaweb.py 文件，只是让它在项目窗口中更容易找到。

接下来我们需要弄清楚如何使用 metaweb.py。我推荐熟悉新 Python 库的方法是直接去解释器里试用。所以我们进入 MetaWindow 目录（现在应该已经包含 metaweb.py），打开一个 Python 解释器。

>>> import metaweb
>>> dir(metaweb)
['MQLError', '__builtins__', '__doc__', '__file__', '__name__', 'cookiefile', 'cookiejar', 'cookielib', 'credentials', 'cursor', 'debug', 'escape', 'host', 'httplib', 'login', 'loginservice', 'os', 'permission', 'read', 'readall', 'readmulti', 'readservice', 'search', 'searchservice', 'simplejson', 'upload', 'uploadservice', 'urllib', 'urllib2', 'write', 'writeservice']

嗯，search 函数看起来很有意思，让我们看看它的文档字符串。

>>> print metaweb.search
<function search at 0x68a070>
>>> print metaweb.search.__doc__
None

啊，又失败了。search 似乎没有文档字符串。那我们就用 XCode 直接查看 search 函数。在 metaweb.py 的第 375 行，我们找到了一条注释描述 search：# Search for topics，这不算太有用，但我们找到了函数定义。

def search(query, type=None, start=0, limit=0):
    # implementation truncated - Will

看起来 search 只需一个参数，应该是个字符串，我们来试试。

>>> metaweb.search("Python")
[
 {u'name': u'Python',
  u'image': {u'id': u'/guid/9202a8c04000641f800000000515378e'},
  u'alias': [], u'article': {u'id': u'/guid/9202a8c04000641f800000000002f849'},
  u'guid': u'#9202a8c04000641f800000000002f83f',
  u'type': [{u'id': u'/common/topic', u'name': u'Topic'},
            u"additional types truncated by me - Will"],
  u'id': u'/guid/9202a8c04000641f800000000002f83f'},
  u"additional results truncated by me as well - Will",
]

很好。这正是我们想要的——一些结构化的数据，可以作为搜索结果放入我们的表格中。PyObjC 可以无缝（好吧，偶尔还是会有点缝隙）地将标准 Python 数据结构（特别是我们熟悉的 list 和 dict）转换为 Objective-C 数据结构，因此这个字典列表对我们的用途来说是非常理想的格式。

如果你对 Objective-C 数据结构不太了解，这里快速补个基础课。最常用的结构是 NSArray 和 NSDictionary。它们与 Python 的列表和字典相当接近，但有一个重要区别：它们是不可变的。因此，NSArray 其实更类似于 Python 的元组，而 NSDictionary 在 Python 中没有完全对应的类型。

相应地，PyObjC 会将 Python 的 list 映射到 NSMutableArray 类，将 Python 的 dict 映射到 NSMutableDictionary 类，它们与 NSArray 和 NSDictionary 相同，只是其中的数据可以被修改。这种模式在许多其他 Objective-C 类中也存在，比如 NSString 和 NSMutableString。

免责声明：这忽略了一个重要区别，即 Python 的 list 是链表，而 NSArray 是数组。这意味着两者在许多操作上的效率并不相同。想了解更多可以查看维基百科中关于链表（linked list）和数组（array）的条目。

现在我们需要做几件事来完成 metaweb.py 的集成。首先打开 main.py，添加对 metaweb.py 的导入，修改后的代码如下：

# import modules containing classes required to start application and load MainMenu.nib
import metaweb
import MetaWindowAppDelegate
import MWController

保存 main.py 后，接下来打开 MWController.py，完善我们之前留下的 search_ 方法存根。

首先，在 MWController.py 文件顶部的导入部分添加 metaweb，修改后应如下所示：

import objc, metaweb
from Foundation import *

然后向下滚动到 search_ 方法的定义处。

我们要做的是获取文本框当前的值，将其传递给 metaweb.search 函数，并把结果存入 self.results 字段。代码如下：

@objc.IBAction
def search_(self,sender):
    search_value = self.textField.stringValue()
    self.results = metaweb.search(search_value)
    NSLog(u"Search: %s" % self.results)

我们还修改了日志输出函数，以便确认一切是否如预期那样工作。现在点击 Build and Go 按钮（Command-Return），同时打开 XCode 控制台（Shift-Command-R）。在文本框中输入一些内容，然后点击搜索。你应该能在控制台窗口看到输出结果。

通过这些简单的步骤，我们已经将 metaweb.py 集成到了项目中。希望这能帮助你深刻理解我关于 PyObjC 的第一个原则：PyObjC 就是 Python。在接下来的部分，我们将努力阐明这句话的另一半——PyObjC 也是 Objective-C，通过展示如何几乎不写代码就能使用 Cocoa Bindings 来驱动我们的表格视图。（咳咳，如果我还没发表的话，我可能会把后半句改成“PyObjC 也是 Cocoa”。算了，就这样吧。）

Cocoa Bindings 入门

Cocoa Bindings 在 OS X Panther 版本中被加入到 Cocoa 中。如果使用得当，绑定可以帮助消除 Cocoa 应用程序中重复且常见的模式。最常见的场景（也是我们马上要看到的）是 NSArrayController 可以自动完成使用数组为表格视图提供内容的过程。

以前，将数组连接到表格视图需要你自己创建一个自定义类，实现 NSTableView 的 delegate 和 datasource 非正式协议。datasource 非正式协议需要实现以下三个方法：

- (id)tableView:(NSTableView *)aTableView objectValueForTableColumn:(NSTableColumn *)aTableColumn row:(int)rowIndex;
- (void)tableView:(NSTableView *)aTableView setObjectValue:anObject forTableColumn:(NSTableColumn *)aTableColumn row:(int)rowIndex;
- (int)numberOfRowsInTableView:(NSTableView *)aTableView;

此外，你还必须为 delegate 非正式协议实现若干方法。

用这种方式控制 NSTableView 并不难——只是有些繁琐——但在搭建第四或第五个表格视图之后，你就会开始觉得应该有更好的办法。

Cocoa Bindings 就是那个更好的办法。你在 InterfaceBuilder 中创建几个对象，连接一些 IBOutlets，根据应用情况可能再写几行代码，然后就完成了。

顺便说一句，这似乎是个合适的时机来发出一条中肯的信息：我仍然会在某些时候使用 datasource 和 delegate 方法来为表格视图提供数据。Cocoa Bindings 能让常见操作变得简单，但当你开始做一些非典型的事情时，它们往往无法完全胜任。

你的应用程序逻辑和工作方式越偏离常规，最终就越有可能遇到 Cocoa Bindings 无法帮到你的情况。

另一个题外话，如果你将 Core Data 与 Cocoa Bindings 结合使用，可以免费获得大量强大功能。本教程不会深入探讨这种强力组合，但随着你继续学习，非常值得花时间去研究。

我强烈推荐 CocoaDevCentral 上关于 Core Data 和 Cocoa Bindings 的文章作为起点。它是用 Objective-C 实现的，基于 OS X 10.4 时代，但仍然是非常棒的入门材料。

除了 NSArrayController 之外，还有其他几个类似的控制器：NSObjectController 用于普通对象，NSDictionaryController 用于字典，NSTreeController 用于树形数据，以及 NSUserDefaultsController 用于用户默认设置。它们都与 Cocoa Bindings 结合，让你的开发工作轻松一些。

刚开始你可能需要强迫自己去使用它们——Cocoa Bindings 的学习曲线确实有点陡峭——但掌握它们后，你会变得更高效，也更快乐。

search_ 方法

本部分的最后一步是重写 search_ 方法。这里有一个棘手的问题，它源于 Python、Objective-C 和 PyObjC 处理内存管理的方式。

关于 Python 和 Objective-C 垃圾回收机制差异的简短说明。

在 Python 中，内存管理对程序员通常是完全透明的。你创建对象，使用它们，直到不再需要。然后你就不再引用它们，如此而已。如果某个对象在某处仍有引用，它就会一直存在，否则垃圾回收器下次检查时就会回收它。简单又方便。

然而，在 Objective-C 中，你必须自己进行一些内存管理。通常有三个方法（存在于所有 Objective-C 对象中）用于管理内存：retain、release 和 autorelease。

每个对象在创建时都有一个计数器，初始值为零。每次调用 retain 方法，计数器就加一。每次调用 release 方法，计数器就减一。当计数器为零时，该对象就面临被垃圾回收器回收的危险。

autorelease 稍微复杂一些，它表示计数器将在当前运行循环结束时减一。基本上就是说你可以在短期内使用一个 autoreleased 对象，但它不会持久存在。

然而，要理解 Objective-C 中的内存管理，还有一个关键点：当你创建一个对象的新实例时，谁拥有它？或者继续用前面的解释，它的计数器初始值是多少？

答案并不是单一的，而是一套准则。如果你使用的方法名中包含 init 或 copy 来创建对象，那么你有责任释放该对象（即其初始计数器值为 1）；否则你应该假设该对象是 autoreleased 的，会在当前运行循环结束时被自动释放，而不需要你做任何事。

最后一个细节：大多数集合会 retain 它们包含的对象，直到集合本身被释放或者对象从集合中被移除。考虑下面这段代码：

NSMutableArray * a = [[NSMutableArray alloc] init];
NSString * myString = [NSString stringWithString:@"PyObjC is good times."];
[a addObject:myString];

因为我们创建 myString 时使用的方法名不包含 init 或 copy，所以它会在当前循环结束时被 autorelease，但由于我们把它加入了数组，数组会 retain 它，因此 myString 会一直存在，直到数组释放它（要么是数组被释放，要么是它从数组中被移除）。

我们想要的 search_ 方法的简单（但遗憾的是很幼稚）的实现如下所示：

@objc.IBAction
def search_(self,sender):
    search_value = self.textField.stringValue()
    self.results = metaweb.search(search_value)
    self.arrayController.rearrangeObjects()

新增的这行 self.arrayController.rearrangeObjects() 告诉控制我们 NSTableView 的 NSArrayController 重新显示其数据。这是必要的，因为每次搜索后数据都会发生变化。

实际上这几乎能工作，但当你运行程序时，它会开始喷出大量关于 Key Value Observers 和对象在到期前就被释放的错误。问题在于 NSTableView 和 NSArrayController 不会 retain 它们的内容（不像 NSArray），而 Python 的字典实例在两个垃圾回收器之间的“冥界”中丢失了。

解决这个问题的一个简单方法是将所有 Python 字典重新创建为 NSDictionary 的实例。幸运的是，这只需要增加一行代码。最终能正常工作的 search_ 方法定义如下：

@objc.IBAction
def search_(self,sender):
    search_value = self.textField.stringValue()
    lst = metaweb.search(search_value)
    self.results = [ NSDictionary.dictionaryWithDictionary_(x) for x in lst]
    self.arrayController.rearrangeObjects()

随着你继续使用 PyObjC，毫无疑问会偶尔遇到内存管理问题，让你困惑到底哪里出了错。这可能看起来令人生畏，但这些问题通常可以用以下两种方法之一轻松解决：

使用已有的 Objective-C 类（就像我们在 search_ 中所做的），或者在 Python 中子类化一个 Objective-C 类（即使只是从 NSObject 继承也足够）。

好了，我们已经完成了对 MWController 的修改，可以保存这些改动。
