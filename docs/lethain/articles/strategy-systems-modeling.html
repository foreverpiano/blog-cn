用系统建模来完善策略

2024-11-04 · 阅读原文

虽然我可能很晚才接触到策略测试：避免瀑布式策略陷阱，通过迭代优化。这个概念，但我在职业生涯早期可能太早接触了系统建模——在进入软件行业之前，我就偶然读到了 Donella Meadows 的《Thinking in Systems: A Primer》。多年来，我发现了许多误用系统建模的方式，但它仍然是我找到的调试复杂问题最有效、最灵活的工具。

在本章中，我们将依次探讨以下内容：

两分钟系统建模基础入门，以及为希望深入了解基础知识的读者提供的资源；系统建模在什么情况下特别有用，以及什么时候最好改用其他完善技术，比如 Wardley mapping 或 strategy testing；关于系统建模工具的讨论，为什么不存在完美的系统建模工具，以及我建议如何选择并熟练掌握一款工具；为当前面临的问题构建系统模型的步骤；如何记录从系统模型中获得的洞见，从而最大程度让他人重视它，而不是因为工具陌生或复杂而忽略它；以及即使你非常希望，系统建模也无法做到的事情。

读完本章对系统建模的概述后，你可以在本书中用于完善各项策略的多个系统模型里看到这些方法的具体应用。系统建模的理论固然有趣，但看到真实模型如何支撑具体的工程策略，希望能给你带来更大的启发。

两分钟入门

如果你想系统性地了解系统思考，最好的起点是 Donella Meadows 的《Thinking in Systems》。如果你想要一个没那么出色但更简短的版本，我写过一篇简短的系统思维导论，可以在网上找到，也收录在《An Elegant Puzzle》一书中。

系统建模就是利用各种存量和流量的配置，来理解那些可能表现出令人意外的行为，或是单纯通过测量难以快速理解的情况。

如果没有模型，你可能会陷入一场哲学辩论，讨论下游服务器对负载如此敏感有多么荒谬。而有了模型后，你会立刻明白保护它是值得的，尽管它这么敏感确实令人担忧。这就是模型的作用：当全面理解现实成本太高时，它提供了一种廉价的方式来理解现实。

系统建模在什么情况下有用？

虽然如何有效优化工程策略是制定任何策略的重要步骤，但针对特定策略，有些完善技术会更合适。系统建模在以下三种场景中特别有用：

当你不确定复杂系统中哪些是杠杆点时，建模能让你低成本地测试哪些杠杆真正有意义。例如，建模司机入驻流程显示，改善新手司机 onboarding 的重要性不如重新激活已经离开的司机。当你拥有大量真实数据可供对照时，建模能帮助你聚焦在真实数据与模型出现矛盾的地方。例如，我曾经超级增长时代的生产力，然后拿它与内部数据进行对比。当利益相关者的分歧源于他们未说出口的直觉时，模型能把这些直觉转化为结构化的形式，从而更有效地进行讨论。

在这三类场景中，建模都能让你比在团队中实际运行流程或技术实验更快地迭代思考。我有时会听到有人担心建模会拖慢进度，但这只是熟悉度的问题。练习得越多，建模就能比向行业同行征求意见更快。本书中的模型大多不到一小时就完成了（只有一个显著例外：建模 LLMs 对开发者体验的影响，它花了更长时间，因为我故意使用了一个不实用的工具，以此说明良好工具的重要性）。

此外，系统建模常常会揭示你正在处理的问题中反直觉的维度。例如，上面提到的关于 LLM 对开发者体验影响的模型显示，强大的 LLM 可能会让我们花更多时间编写和测试代码（但减少修复生产环境发现的问题所花费的时间）。这有点出乎意料，因为你可能会以为它们会减少测试时间，但减少测试时间只有在生产环境中发现的问题数量保持不变（或减少）时才有价值；如果生产问题反而增加，那么测试时间的减少并不会带来生产力的提升。

脱离实践的建模只会制造无根据的信念。然而，当与实践结合时，我很少遇到其他能同样加速学习的技术。

但这并不意味着它永远是最佳的完善技术。如果你已经对总体方向有坚定信念，只想打磨具体细节，那么策略测试：避免瀑布式策略陷阱，通过迭代优化。是更好的选择。如果你试图理解更广阔生态系统的演化，那么你可能会更倾向于使用 Wardley mapping。

工具选择

对于一个如此直观的想法，系统建模的工具却成了广泛采用的真正障碍。也许是因为早期许多流行的系统建模工具都相当昂贵，导致系统建模的工具生态长期处于碎片化状态。此外，似乎还有复杂的需求、专利集中以及被认为市场规模较小等多种因素，阻碍了出现一个能整合市场的现代解决方案。

前面我提到系统建模其实非常快速，但很多人却觉得它是一个缓慢且费力的过程。一部分原因是练习不足，但我认为建模工具的质量至少也是同样重要的挑战。在建模 LLMs 对开发者体验的影响中，我用一个越来越混乱的电子表格完成了建模的各个步骤。这既慢又困难，而且极其脆弱。即使模型完成后，我也无法有效地扩展它来测试新想法，还无意中在实现中引入了不少 bug。

我也反向探索过一些工具，比如 Sagemodeler 或 InsightMaker，它们看起来可能是比我通常使用的工具链更简单的选择。系统建模的入门工具链有很多，但我通常发现它们要么功能受限，要么学习曲线较陡，要么难以与他人分享模型。

最终我还是回到了自己使用的工具链上——那是我几年前写的一个工具：lethain/systems。它远非完美的工具链，但我觉得它在展示系统建模方面相当有效，原因有以下几点：

能快速创建模型并进行迭代；便于与他人分享模型，供他们检查和自主探索；模型本身出错的可能性相对较低；免费、开源、自托管的工具链，能很好地与 Jupyter 生态系统集成，用于画图、建模等。

你完全应该选择任何自己觉得顺手的工具，并持续练习直到能快速对各种场景建模。之后，我不建议在工具上花费太多心思：最重要的是快速构建模型并从中学习，只要经过有意识的练习，几乎任何工具都足以达到这个目标。

如何建模

学习系统建模需要一些练习，因此我们会从两个角度来介绍建模的具体方法。首先是记录一个通用的建模结构，其次是为本书中开发的模型提供索引，方便你深入探索特定的建模思路。

我认为有效的系统建模结构是：

在纸上或绘图应用（例如 Excalidraw、Figma、Whimsical 等）中画出存量和流量的草图。用你最顺手的工具即可。思考某个潜在变化会如何改变图中的流量。你预期哪些流量会上升，哪些会下降，这种变化如何帮助你判断策略是否有效？用你选择的电子表格工具实现这些存量和流量。先从左到右建模流量（例如主路径的流量）。等这个完全跑通后，再开始从右到左建模流量（例如异常路径的流量）。可以参考建模 LLMs 对开发者体验的影响模型，深入了解构建模型的具体细节。通过尝试不同的初始值并观察速率如何影响模型结果来验证模型。这本质上是在做敏感性分析。将上述步骤的工作成果整理成一份独立的文档。然后你可以从受益于该模型洞见的策略中链接到这份文档。你可以链接到策略的任意构建工程策略的步骤，具体取决于模型探讨的主题。我建议将模型与特定策略解耦，因为任何具体模型的细节通常会分散对策略本身的理解，最好避免这种分散，除非读者对结论感到意外，这时再通过链接深入细节。

一如既往，这只是我鼓励你遵循的步骤顺序，也是我自己通常遵循的顺序，但你应该根据手头具体问题进行调整。随着时间推移，我的经验是除文档之外的大部分步骤会融合成一个单一的迭代过程，而我会在多次迭代之后再把所有内容记录下来。

如何记录模型

正如让工程策略文档更具可读性所说，在专业环境中用模型进行沟通是一件具有挑战性的事。核心问题在于，模型的读者可以分为很多不同群体。有些人对你用来开发模型的工具不够熟悉。还有些人会试图通过钻研细节来完善或推翻你的模型。

我通过优先关注最不可能深入研究模型的受众来处理这些差异。我仍然会保留所有细节，最好以最原始的形式，以便其他人能自行操作模型，但这对我来说是次要目标。

根据经验，我推荐以下顺序（本书中的模型也采用了这个顺序，所以你会多次看到它在实践中的应用）：

以“学到了什么”部分开头，用图表展示模型带给你的洞见；画出并解释存量和流量；思考这个草图本身教会了我们什么；解释你是如何构建这个模型的，重点说明任何特别复杂的部分；通过测试改变流量和存量如何导致不同结果来验证模型。

如果你只记得一件事，那就是你的文档应该反映这样一个现实：大多数人并不关心你如何构建模型，他们只想要洞见。尽早把洞见给他们，并且要假定没有人会像你一样信任这个模型。模型是策略的输入，永远不能作为策略唯一可靠的支撑。

系统建模做不到什么

虽然我认为系统建模是一种独特而强大的加速学习方式，但我遇到过很多实践者，他们相信自己的模型就是现实，而不是对现实的反映。随着时间推移，我总结了一份简短的注意事项清单，帮助想要建模的人避免过度执着于模型的结论：

当你的模型与现实冲突时，现实永远是对的。在 Stripe，我们开发了撰写可靠性策略：用系统模型思考复杂问题。这个模型直观上看非常好，但它在现实中的结果好坏参半。对早期模型的执着分散了我们的注意力（在收集和分类数据上花了太多时间），也让我们迟迟没有着手解决最重要的问题（最大化稀缺缓解带宽的影响，以及增加缓解带宽）。如果我们直接接受现实给我们的教训，而不是寻找理由无视它，我们本可以产生更大的影响。模型是固定的，但现实不是。我曾经加入过一个组织，他们在招聘上投入了巨大精力，却仍然难以招到人。他们直观的模型促使他们花了多年时间优化漏斗顶部，后来又转向改善成交流程。他们没能发现的是，达成共识：解决工程经理招聘循环中候选人全被拒绝的问题才是招聘中最大的障碍。每个模型都会省略信息，有些省略了关键信息。Uber 的服务迁移就是一个很好的例子：建模明确告诉我们，必须采用更激进的方法才能成功完成服务迁移。后来我们确实成功了，但模型并没有研究完成迁移后的后果——那是一个非常具有挑战性的开发环境。这个模型捕捉了我团队（负责执行迁移的团队）关心的所有内容，却完全没有评估从整体来看这次迁移是否是个好主意。

在上述每种情况中，有两件事是同时成立的：模型极具价值，同时模型又在 subtly 把我们带偏了。即使没有模型，我们也可能会被带偏，所以要记住的关键点不是模型天生会误导人，而是过度相信自己模型的风险。模型是一种与判断力结合使用的强大工具，而不是判断力的替代品。

总结

系统建模并不完美。如果你已经确定了策略方向，只想完善细节，那么 strategy testing 可能是更好的选择。如果你试图理解一个不断演化的生态系统的动态，那么 Wardley mapping 是更合适的工具。

然而，如果你已经有了大致的轮廓，却对各个部分如何相互配合缺乏把握，系统建模就是一个了不起的工具。读完本章后，你已经知道如何选择合适的工具，以及如何使用这些工具对面临的问题进行建模。接下来，我们将通过对几个具体问题的系统建模，为这项技术的应用提供具体示例。
