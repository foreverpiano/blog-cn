有价值的权衡是多维度的。

2024-01-24 · 阅读原文

在行业内的某些圈子里，软件开发有一条公认的信条：快速部署软件与彻底测试软件是相互冲突的。团队相信这一点的一个原因是，完全自动化的部署流程意味着没有机会进行人工质量保证。而在行业的另一些圈子里，信条却截然不同：你可以通过使用 feature flags 将部署（交付代码）和发布（启用新功能）解耦，从而同时获得快速部署和人工质量保证。

随着职业生涯的深入，我越来越相信，这个例子中蕴含着一个可以普遍应用的模式，帮助我们做出有价值的权衡：

二维权衡总是会让某些人失望 通过引入一个新维度，你通常可以做出一个不会让任何人失望的权衡。

在“快速 vs 安全部署”的权衡中，新增的维度是将功能激活（“发布”）与交付实现该功能所需代码（“部署”）进行解耦。引入这个维度后，工程师可以获得快速、可预测的部署，而质量保证团队则有机会在向用户启用功能之前进行审查。

虽然大多数人已经在某种程度上直观地理解了这些规则，但我认为把它们明确地表述出来是一种轻度改变认知的体验，接下来我会深入探讨如何应用这些规则。

示例

在讨论识别维度以改进权衡的具体机制之前，让我们先简要看几个通过增加维度来获得更清晰权衡的例子：

项目预算——在年度规划期间，许多公司在是投资新市场的国际化扩张，还是优先考虑现有市场的问题上争论激烈。通过增加固定预算这个维度，他们可以在两者之间取得不同程度的平衡，而不是在“只能二选一”上进行存在主义的辩论。多元化投资组合——长期以来，投资者要么选择安全的投资（表现低于股市），要么选择高风险的投资（可能大幅跑赢市场，也可能归零）。Burt Malkiel 的《漫步华尔街》引入了“多元化”这个维度，让你既能获得接近市场水平的回报，又能降低风险。数据驱动的限制——你经常会听到产品团队和安全团队在“用户安全”与“产品易用性”之间的权衡争论。然而，通过采取数据驱动的方法，你往往可以兼得两者。例如，与其争论是否要移除用户的权限，不如先移除每个用户当前没有使用的所有权限。通过将真实世界的使用情况纳入权衡的维度，你通常能找到既提升安全性又不降低易用性的方案。Feature flags——正如引言中所讨论的，许多工程师认为我们必须在“慢而安全”的部署和“快而冒险”的部署之间二选一，但通过 feature flags 将部署和发布解耦，我们就能同时实现快速且安全的部署。

除了这几个小例子之外，我相信你能从自己的工作经历中找出更多这样的权衡：增加一个维度就把混乱的分歧变成了清晰的前进方向。当你与特别擅长这一点的人共事时，“权衡”这个概念本身开始逐渐消失，取而代之的是深思熟虑的解决方案。

如何增加维度

一旦你开始以这种方式思考权衡，你就会注意到那些已经在用这种方法改善决策的人。挑战在于，大多数人这样做是凭直觉，而不是遵循一套明确的步骤，这使得他们很难解释清楚。坦白说，我自己也面临这个挑战。随着时间推移，我在这件事上做得越来越好，但直到最近我才找到合适的词汇来描述它。

以下是我对这项实践进行逆向工程后得出的最佳步骤：

进入每一次权衡讨论时，都要相信存在一个可以添加的额外维度，它能极大地缓解当前的决策张力。将这个信念传递给其他人，让他们理解你的出发点，这可以简单到说一句：“我在想是否能增加一个维度，让这个权衡变得更容易。”把所有利益相关方的需求都弄得非常具体。缺失的维度通常只有在细节中才会显现，因此你需要迫使人们精确地表达他们的需求。如果你遇到无法精确表述需求的利益相关方，那么你应该花时间和他们一起工作以获得更多清晰度。是的，他们说不清自己的需求是他们的问题，但现在这也是你的问题。看到维度等同于看到多层上下文。。你需要么扩展自己对更多上下文层的认知，要么召集一个拥有广泛知识的工作小组。这不一定是决策利益相关方，只需是那些了解相关团队、技术和产品的人。测试新维度的有用性。最简单的方法是，在你的工作组中问：“我们如何用这个额外维度来简化这个权衡的纠缠？”关键是快速探索多个维度，试用它们是否有效，然后转向下一个。在某个维度显示出潜力之前，不要深入研究它。通过询问那些以前解决过类似权衡的人来“看到拐角”。我感觉自己像坏掉的唱片，但真的，只要去问那些以前解决过这个具体问题的人就很有效。这也是为什么建立同行网络如此宝贵。他们很可能直接告诉你缺失的维度是什么！最终，你应该只在某个维度能显著改善相关利益相关方的结果时，才将其添加到权衡中。一旦你开始思考这个想法，就会倾向于到处增加维度，但要避免那些不能大幅改善选项、却让决策更难解释的额外维度。

这个过程不会每次都奏效，因为有些工作组可能根本不了解缺失的维度，无法提出建议。这就是为什么如果你在某个权衡中找不到缺失维度，不要灰心；这也是为什么每隔几年重新审视一下棘手的权衡很有价值。上次你不知道那个缺失维度，并不意味着现在你仍然不知道。

职业生涯后期的能力

有时人们会说，工程师在五到七年里就能成为资深工程师，然后就能完全胜任工作。从某种意义上说这是对的——五年经验确实可以让你成为一名优秀的工程师——但它也忽略了许多在那时才刚刚开始生根的能力。为权衡增加维度就是一个很好的后一类例子：很少有人拥有必要的上下文层次和经验广度，能够熟练地识别出缺失维度，从而让困难的权衡变得更容易。总有更多东西值得学习。
