重构与测试我们的 Dynamo 克隆

2010-01-02 · 阅读原文

最近时间有点紧张。因此，在下一篇文章讨论物理时钟、逻辑时钟和向量时钟之前，我们先来做一些测试和重构工作。

接上上一篇的内容，本文我们将在继续实现之前，对代码库进行一些重构以使其更加清晰。我们的目标有四个：

简化变得越来越笨重的 kvs:store/1 函数，添加基于 EUnit 的单元测试，将客户端接口和服务器实现拆分到两个文件中，将基于消息传递的服务器重构为 Erlang gen_server。

让我们开始吧。

清理 store 函数

kvs:store/1 函数已经长得有点难看了。最初为了保持解释简洁，这样做或许还有道理，但现在时机已经过去了。

这个函数既包含了用于区分不同消息类型的模式匹配，也包含了每种消息的具体响应逻辑。一个快速的简化方法是将每种响应逻辑提取到独立的函数中。

模式匹配部分可以简化为：

store(Store = #kvs_store{data=Data, 
          pending_reads=Reads, pending_writes=Writes}) ->
    receive
        {Sender, retrieve, Client, Key} ->
            message_retrieve(Store, 
                Sender, Client, Key);
        %% and so on..

其中每个响应函数1 大致如下：

message_retrieve(Store, Sender, Client, Key) ->
    Sender ! {self(), retrieved, Client, 
        Key, proplists:get_value(Key, Data)},
    store(Store).

这样的调整把代码拆分成更易理解的模块，同时也为后续将服务器重写为 gen_server 奠定了基础。

这部分工作的变更集可在此处查看，如果你想看到完整的修改内容。

添加测试

没有测试的重构就像开车不看路标。在修改了大量功能之后，再去验证现有功能是否仍然正常工作是一件非常耗时的事情。而“耗时”其实是委婉说法——人类做这件事往往做得很糟糕，而且不可避免地会出错。

Erlang 提供了多种测试工具2，其中最简单的是 eunit，我们将用它来测试我们的项目。EUnit 可以和 [phpunit] 或 [junit] 相媲美，只是（或许）需要的样板代码更少一些。

我们最初的 eunit 测试会比较简单，随着后续功能的增加，我们可以逐步增强这些测试。

-module(kvs_tests).
-include_lib("eunit/include/eunit.hrl").
%% @doc test response when empty kvs process group
not_running_test() ->
kvs:stop(),
{error, not_running} = kvs:get(b),
{error, not_running} = kvs:set(c, 100)
%% @doc test most basic functionality
basic_test() ->
started = kvs:start(3),
{ok, undefined} = kvs:get(a),
{ok, updated} = kvs:set(a, 5),
{ok, 5} = kvs:get(a),
stopped = kvs:stop().
%% @doc test performing many concurrent reads
many_reads_test() ->
started = kvs:start(3),
{ok, updated} = kvs:set(b, 100),
Read = fun() -> {ok, 100} = kvs:get(b) end,
lists:foreach(fun(_) -> spawn(Read) end,
lists:seq(0, 100)),
stopped = kvs:stop().
%% @doc test performing many concurrent writes
many_writes_test() ->
started = kvs:start(3),
Write = fun() -> {ok, updated} = kvs:set(a, 101) end,
lists:foreach(fun(_) -> spawn(Write) end,
lists:seq(0, 100)),
stopped = kvs:stop().

分离接口与实现

这部分我们会快速带过，因为它并没有太多教学意义，但需要关注的要点包括：

将当前的 kvs.erl 拆分为 kvs.erl 和 kvs_server.erl，保持现有的客户端接口不变，因为我们有测试，所以可以放心地进行修改（回归测试），不添加任何新功能，继续使用 kvs 进程组（不必和文件名一一对应）。

从消息传递到 gen_server

本次重构的最后一步，是将我们基于消息传递的实现迁移到使用 OTP gen_server 的版本。gen_server 代表 generic server，正如其名。gen_server 在功能上与我们之前使用的消息传递方式完全等价，但它有几个重要优势：

它消除了大量的样板代码，与 Erlang OTP 的其他工具（如 supervisor、层级树等）能够很好地协作，其他 Erlang 程序员对此很熟悉，因此能更快地理解程序的整体结构。

大多数重要的 Erlang 项目要么一开始就使用 gen_server，要么最终会演化出至少一个 gen_server。

在进行这次重写时，请注意我们会保持客户端接口不变，这样假设的用户不会受到任何影响，我们也能继续运行已有的测试。剧透一下，经过一番折腾后，kvs.erl 和 kvs_server.erl 的总代码行数将从 200 行减少到 189 行。

现在来看我们的第一个改动：更新 kvs.erl 中启动 kvs 服务器的客户端接口实现。

%% old start function
start(N) ->
    pg2:create(kvs),
    lists:foreach(fun(_) ->
		    Store = #kvs_store{data=[],
			       	 pending_reads=[],
			         pending_writes=[]},
		    pg2:join(kvs, spawn(kvs_server, store, [Store]))
		  end, lists:seq(0, N)),
    started.
%% new start function
start(N) ->
lists:foreach(fun(_) ->
kvs_server:start_link().
end, lists:seq(0, N)),
started.

我们对 kvs:stop 也做了类似的修改。

%% old stop function
stop() ->
    lists:foreach(fun(Pid) ->
			  pg2:leave(kvs, Pid),
			  Pid ! stop
		  end, pg2:get_members(kvs)),
    stopped.
%% new stop function
stop() ->
lists:foreach(fun(Pid) ->
gen_server:call(Pid, stop)
end, pg2:get_members(kvs)),
stopped.

接下来需要更新更新和获取值的客户端接口实现。有两点值得注意：

我们免费获得了 gen_server:call 提供的“发送并阻塞等待返回”的结构，不再需要显式传递发送者的进程 ID，因为这同样可以免费获得。
%% old get implementation
get(Key, Timeout) ->
    Pid = pg2:get_closest_pid(kvs),
    Pid ! {self(), get, Key},
    receive
	{Pid, got, Value} ->
	    {ok, Value};
	{error, Error} ->
	    {error, Error}
    after 
	Timeout ->
	    {error, timeout}
    end.
%% new get implementation
get(Key, Timeout) ->
Pid = pg2:get_closest_pid(kvs),
gen_server:call(Pid, {get, Key}, Timeout).

更新值的部分也做了相同的修改。

%% old set implementation
set(Key, Val, Timeout) ->
    Pid = pg2:get_closest_pid(kvs),
    Pid ! {self(), set, Key, Val},
    receive
	{Pid, received, {set, Key, Val}} ->
	    {ok, updated};
	{error, Error} ->
	    {error, Error}
    after
	Timeout ->
	    {error, timeout}
    end.
%% new set implementation
set(Key, Val, Timeout) ->
Pid = pg2:get_closest_pid(kvs),
gen_server:call(Pid, {set, Key, Val}, Timeout).

完成对 kvs.erl 的修改后，接下来该处理 kvs_server.erl 了。如果把所有将代码转换为 gen_server 所需的修改都逐行看完会非常枯燥（这里有一个包含所有修改的变更集，可能很有参考价值）。因此，我们采用高层次的方式，指出其中一些有趣的细节。

在旧实现中，我们依赖 store/1 函数来分发收到的消息，但 gen_server 为我们完成了分发工作，转而要求我们实现 handle_call/3 函数。

%% excerpt from old implementation
store(Store) ->
    receive
        {Sender, get, Key} ->
            message_get(Store, Sender, Key);
        %% some other pattern matches
        stop ->
            ok
    end.
%% excerpt from new implementation
%% @doc handle explicit stop requests
handle_call(stop, Sender, State) ->
{stop, stopped, stopped, State};
handle_call({get, Key}, Sndr, State=#kvs_store{pending_reads=Read}) ->
%% implementation…

上面我们使用的是 handle_call，但在新的 kvs_server.erl 实现中还用到了一个类似的函数 handle_cast。两者的区别在于，从客户端视角来看，handle_call 是同步操作，而 handle_cast 是异步操作。

注意，handle_call 只需要从客户端视角是同步的即可，服务器完全可以将客户端请求暂存到自己的状态中，继续处理其他 incoming 请求，之后再返回对第一个请求的响应（这个实现大量使用了这种模式）。

gen_server 实现还有许多其他方面可以深入探讨，但我们很容易就会陷入其中难以自拔。从我们的角度来看，目标是将代码重新组织，以便在后续系列文章中能够进行针对性的算法修改。

迁移到 gen_server 的完整变更集可在此处查看。

呼。把所有这些代码都梳理完之后，我们终于摆脱了与 OTP 对抗的局面，现在开始真正与之协同工作了。再过几篇文章，等我们对核心实现做了进一步完善后，我们会回到这条线，继续利用 Erlang 的其他优秀特性（特别是 supervisor），但目前先把注意力放在算法实现上会更好。
