清理 erlang_markdown

2009-10-10 · 阅读原文

又花了几个小时后，erlang_markdown 已经清理得相当干净，并且几乎支持了 Markdown 规范的所有特性，只剩下多行标题语法尚未实现。你可以查看当前的测试套件来了解其完备性。

在这里，我将讨论并反思这个脚本的设计，最后再看看如何对该库进行性能调优。

单遍解析

从一开始，这个项目的目标就是创建一个单遍 Markdown 解释器。比我更优秀的人无疑能为这种做法给出充分理由，而我只是恰好想采用这种方式。在实践之后，以下是我对使用单遍还是多遍方法将 Markdown 转换为 HTML 的一些思考：

  1. The more irregular the language, the more painful to write a single-pass interpreter. In particular, languages with implicit termination pose problems for the single-pass approach.
  2. A single-pass interpreter to parse an irregular language will become more complicated, more brittle, and less extendable than a multi-pass parser.
  3. Markdown is both irregular and has implicit termination.
  4. The single-pass approach allows stream processing, and can thus facilitates constant memory use.
  5. Most usecases of Markdown don't readily facilitate stream processing (rendering comments for a website, blog entries, notes, etc), and instead expect to pass in a full string/binary and be returned the full translation as a string/binary.

考虑到以上情况，从长期可持续性和灵活性的角度来看，我始终推荐采用多遍方法。只有在多遍方法已被证明性能不足的情况下（例如 SAX 解析海量 XML 文档，而 DOM 解析因内存消耗变得不可行时），才应该尝试单遍方法。

或者，如果你的系统本来就是以流的形式处理数据。又或者，你只是觉得无聊。

erlang_markdown 的实际实现相当直截了当，尽管其中充满了足以让阅读者落泪的特殊情况。其核心函数是

line_start(<<Binary/binary>>, OpenTags, Acc, LinkContext, MultiContext).
single_line(<<Binary/binary>>, OpenTags, Acc, LinkContext, MultiContext).

markdown:line_start/5 在每一行的开头被调用，负责管理所有多行结构，例如段落、列表、引用块和预格式块。MultiContext 包含一个由打开的多行标签（ul、ol、li、p、pre、blockquote 等）组成的栈。

line_start/5 无疑是代码中最丑陋的部分，因为它需要检测多级缩进的终止（将缩进深度与 MultiContext 栈中打开的 ol 和 ul 标签数量进行比较），以及其他逻辑，例如判断一个没有任何语法标记的行应该被视为新段落、继续中的段落，还是已打开的 li 标签的一部分。

markdown:single_line/5 负责在剥离所有多行语法之后渲染一行。例如，* *this is a test* 在到达 single_line/5 时已经被简化成了 *this is a test*。

它使用 LinkContext 来存储之前使用 [test]: http://test.com/ "test" 语法声明的链接。在研究了 xmerl:eventp 之后，我会将函数定义重新实现为以下形式之一

line_start(<<Binary/binary>>, PropList).
single_line(<<Binary/binary>>, PropList).

line_start(<<Binary/binary>>, #markdown_parser{}).
single_line(<<Binary/binary>>, #markdown_parser{}).

当前的方法使得扩展 erlang_markdown 变得极为不便，而使用属性列表或 record 将大大改善这种情况。目前可能还没有强烈的动机进行这种重构，但如果我进行第三次重写，这将会是核心部分。

性能调优

我在 Erlang 性能方面学到的一个深刻教训是：空谈无益。关于调优 Erlang 应用性能有大量通用建议——其中很多确实普遍适用——但在你真正写出代码并生成一些数据之前，很难区分哪些是真实开销，哪些只是你想象中的开销。

（当然，无论使用哪种语言，这一点始终成立。但我——也许是由于相对缺乏经验——发现那些提供 Erlang 性能建议的人当中存在大量困惑。）

我使用以下函数生成可变长度的测试输入。

gen_string(N) ->
    Str1 = "* **this is a test** *and so is this*\n* another line\n\n1. a line\n2. a line2\n3. another line\n\n",
    Str2 = ">> blockquote\n>> blockquote2\n\n    pre block1\n    same pre block\n\n",
    Str3 = "[test](http://test.com \"this\")\ this out\n ``code block``\n\n",
    Str4 = "1. This is a test\n    2. so is this\n    3. yep...n4. yep\n\n* hi\n    * there\n    * ayep..\n * the end\n\n",
    Str = lists:append([Str1, Str2, Str3, Str4]),
    lists:append(lists:map(fun(_n) -> Str end, lists:seq(0,N))).

对于性能分析，我使用了 markdown_tests:test_performance/1 函数：

test_performance(N) ->
    test_performance(N, 10).
test_performance(N, Runs) ->
LongStr = gen_string(N),
Times = lists:map(fun(X) ->
timer:tc(markdown, markdown, [LongStr])
end, lists:seq(1,Runs)),
Time = lists:foldr(fun({Micros, }, Acc) ->
Micros + Acc
end, 0, Times),
Seconds = (Time / N) / 1000000.0,
Length = length(LongStr),
io:format("~p chars, ~p seconds, ~p us/char~n", [Length, Seconds, (Time/N)/Length]).

它首先生成测试字符串，然后将拼接后的字符串传入 markdown:markdown/1 函数。每个测试运行 Run 次（默认为 10 次），之后输出平均结果。当然，计算标准差、识别并排除异常值等会更有意义，但我决定不做得太过头。

这里的性能看起来相当不错，这让我颇为惊讶，因为我原本担心使用以下这种随着生成 HTML 片段而收集它们的写法：

Fragments = lists:foldr(fun(X,Acc) -> [magic(X) | Acc] end, [], Input)
InOrder = lists:reverse(Fragments),
AsStrings = lists:map(fun(X) -> binary_to_list(X) end, InOrder),
Merged = lists:append(AsStrings),
list_to_binary(Merged).

“先前置再反转”的收集方式在 Lisp 代码中很常见，但将二进制片段 awkward 地合并成单个 binary 的做法绝对不是标准做法。

因此，我第一次优化的尝试是去掉转换为列表的操作，转而尝试以下算法：

Fragments = lists:foldr(fun(X,Acc) -> [magic(X) | Acc] end, [], Input)
InOrder = lists:reverse(Fragments),
lists:foldr(fun(X, Acc) -> <<Acc/binary, X/binary>> end, <<"">>, InOrder).

接下来我很好奇，如果测试传入的是字符串而不是 binary，会对代码造成多大惩罚，因为它总是会将列表输入转换为 binary：

markdown(Text) when is_list(Text) ->
    markdown(list_to_binary(Text));
markdown(Binary) when is_binary(Binary) ->
    line_start(Binary, [], [], [], []).

看起来——虽然我强烈建议进行比这严苛得多的测试——将字符串转换为 binary 的成本不算太大，但也不能完全忽视。

我接下来的想法是，观察如果在处理过程中逐步聚合 binary，而不是在所有数据处理完之后再做最终聚合，是否能带来显著改进，于是上面的公式简化为：

lists:foldr(fun(X,Acc) -> X2 = magic(X), <<Acc/binary, X2/binary>> end, [], Input)

然而这个改动涉及相当多的代码修改，因此我决定不在 erlang_markdown 的代码上进行测试。它应该能稍微改善内存使用，但我认为整体提升会比较有限。

无论如何，以每秒约 400 万字符的速度，erlang_markdown 已经足够快，足以满足我能想象到的任何使用场景。
