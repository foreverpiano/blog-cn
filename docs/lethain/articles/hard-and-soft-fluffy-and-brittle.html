硬与软，蓬松与脆弱

2009-02-03 · 阅读原文

最近工作中我们开启了一个新的产品周期，一直在围绕设计展开讨论。由于在共同规划软件1方面经验不足，我对设计有着强烈的个人感受，却完全无法令人信服地解释清楚。随后我花了一周时间徒劳地与 XML 规范角力——就像一个尼安德特人摆弄 Zippo 打火机那样——我发现了火。

在软件设计中，隐式与显式、简单与具体、柔软与坚硬之间始终存在着一场持久的 battle。我的思维正卡在这块坚硬的石头和柔软的地方之间。如今我刚刚挣脱出来，让我们稍微探索一下这个任意的区分，看看它能带来什么。

硬风格

首先是显式的硬风格。XML——这个让随意设计者头疼的东西——正是这种设计风格2的典型代表。XML 规范以一种沉重而仇恨的态度消灭了所有歧义：

验证处理器必须根据用户选项，报告违反 DTD 中声明所表达的约束以及未能满足本规范中给出的有效性约束的情况。为此，验证 XML 处理器必须读取并处理整个 DTD 以及文档中引用的所有外部解析实体。

不仅是 XML，JSON、HTML 以及任何带有显式 schema 的东西都属于硬风格（作为软件工程师，你使用的大多数软件很可能都属于这一类）。

硬风格通过施加约束来最大化精确性。好的硬设计会用最少的约束来实现最高的精确度。

如果软件施加的约束无法被精确性证明其合理性，那它就不是硬，而是脆弱。此前我说 XML 是硬风格的典范，但它同时也是脆弱软件的代表。让我们来看一个 XML 中同时体现硬和脆弱的例子。关键的问题是：“这个约束是否被精确性所正当化？”

XML 的设计是在发现格式错误的数据后立即中断。通过在格式错误时中断，你消除了歧义解析。如果规范说“遇到格式错误的标签时的行为未定义”呢？那样你就得面对不同 XML 解析器之间的歧义，而我们都知道通往地狱的道路是由相互竞争的规范铺就的。这个约束使得我们可以对 XML 解析器如何处理坏的 XML 做出精确的假设，因此它被精确性所正当化。XML 规范中的另一个约束是在遇到非法实体列表时直接终止。限制在元素内使用 < 和 > 完全合理，但为什么要禁止垂直制表符、空字符以及其他几十个字符呢？限制这些实体只在一种情况下提升了精确性：你知道 XML 中不会包含这些实体。这个约束没有带来明确的精确性收益，因此它是一种脆弱的约束。

现在让我们来看看硬风格的互补面。

软风格

如果说硬风格致力于最大化精确性，那么软风格则致力于最小化复杂性。对于软软件来说，有趣的动态在于选择与选项之间；好的软件应该提供更多选项而非选择，而那些选择过多的就是蓬松（fluff）。

你可能会怀疑我在玩“给老词发明新定义然后大呼狼来了”的把戏，但在你反对我虐待羊之前，先听我说完。不管这些含义昨天是否真实，它们提供了一个有用的工具，来定义什么才构成好的软软件设计。

选项是选择的一个子集：即有用的选择子集。硬风格的精确性和约束有意忽略其用户，而软风格中选择与选项的区分则取决于特定的用户（或特定类别的用户）。选择无法成为选项有两种情况：

无法挑选的选择不是选项。想象一个素食主义者参加烤猪派对。未被充分理解或不想要的选择也不是选项。想象一个文本编辑器让用户选择以 UTF-8、UTF-16 或 ascii 保存文件，同时还能选择 2003 格式、2004 格式、2005 格式、txt 或 RTF3。对于“高级用户”来说这些可能是选项（你需要让妈妈能打开文件，而你知道她用的是 2003 版本，操作系统只能读取 Shift-JIS 编码），但对大多数人来说这只是一个任意的选择，阴影中潜伏着失败的代价。这些未被理解或不想要的选择，迫使从未见过枪的用户去玩俄罗斯轮盘。

创建有效的软软件，最关键的是确定你的目标受众，并无情地消除那些对该特定受众而言不是选项的选择。创建软件的人几乎总是领域专家，对他们来说大多数选择都是选项，如果不经过用户测试，他们的软件将完全是一个专家想要的样子，但对普通用户来说却是危险的4。

在软与硬之间做出选择

在选择与选项的泥潭中穿行，使得软选项的设计变得复杂，这也是为什么许多工程师——如果放任自流——会只创造硬选项的原因。其实不止工程师，所有领域专家都更喜欢为自己的领域采用硬设计。美国国税局（IRS）那些无与伦比的头脑几十年来一直在创建非常精确且无歧义的表格。精确且受限到如此程度，以至于围绕这些硬的税务表格成长起了一个庞大的软解决方案产业。这正是正确的做法：领域专家使用硬方案，并为缺乏经验的人创建软方案。

你的客户对问题拥有的领域知识越多，合适的解决方案就应该越硬。领域知识越少，解决方案就应该越软。

然而，这不仅仅与客户有关，也与问题本身有关。存在某个临界点，当一个问题变得足够复杂——或者需要足够高的精确度——以至于软方案会比硬方案更复杂且更不精确。在这个思路下，记住硬本身并不比软更困难，它只是需要更多的用户教育和知识。在某些情况下，培训用户的回报可能高于编写代码5。

无论硬还是软更适合我们团队即将开始的项目，有意识地做出这种硬与软的区分，已经让我更清楚地知道什么时候该偏好哪种方法。精确/约束与选择/选项之间的相互作用，也为我提供了一个更清晰的思维框架，用来判断哪些功能真的是功能，而哪些只是披着燕尾服的缺陷。
