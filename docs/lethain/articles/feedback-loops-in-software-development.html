软件开发中的反馈循环

2009-06-01 · 阅读原文

在一所小型文理学院学习计算机科学，一个令人怀念的优势就是可以随时去找教授，听他们讲故事。其中一个最喜欢、也反复出现的故事是：有些同学提交的项目根本无法编译。如果说忽略边缘情况是懒惰工程师的标志，那么提交无法编译的代码又该算谁的标志呢？

几年前，我还愿意把这视为失败工程师的标志，但——在自己也尝过几次失败的滋味后——我逐渐形成了一个不那么自鸣得意的诊断：这些人是没有认识到反馈循环重要性的人。

不管你认为 MIT 从 Scheme 转向 Python 是妥协还是灾难，我都不认为这两门语言都以 REPL 为核心是个错误；及时获得反馈是困惑与清晰之间的分界线。不仅缺失的反馈循环正在毁掉大学校园里的作业，它也在到处给软件工程制造混乱。

程序员的奖励循环

虽然软件工程师并非所有时间都在编程——很多人甚至大部分时间都不在编程——但编码拥有娱乐活动之外最纯粹的反馈循环之一。在各种编程方式中，最简单的反馈循环来自与集成良好的 REPL 进行交互。

如果你最终要用多种语言做大量工作，特别是像 JavaScript 和 Python 这样语义相似的语言，就很难记住哪种语言用 x.append、哪种用 x.push 来向列表末尾添加元素。你可以去 Yahoo 搜索答案，但问 REPL 更快，也更可靠。

>>> a = []
>>> a.append(10)
>>> a
[10]
>>> a.push(5)
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
AttributeError: 'list' object has no attribute 'push'

除了检查语法或查看对象实例，你也可以直接从 REPL 开发游戏或 Web 应用。如果说所有编程都带有强大的反馈循环，那么 REPL 就是其中的王冠。

反馈循环的质量与获得反馈所需付出的努力或时间成反比。前端程序员的反馈循环常常因为浏览器相关的渲染 bug 而被削弱（修改、重新部署、按照步骤重现问题、验证渲染、打开另一个浏览器……），而后端工程师的循环同样容易被繁重的编译或部署周期所拖累。

对于足够大的项目——即任何编译或部署阶段有明显延迟的项目——可脚本化的测试是对正在衰退的反馈循环的有效（甚至可能是唯一的）放大器。抛开意识形态层面的理由，可脚本化的测试在心理层面扮演着重要角色，它通过持续提供反馈来让程序员保持清醒和满足。有了良好的反馈，不仅能带来极大的满足感，还能带来高质量。

拿走程序员的反馈循环，我们就只剩下……

软件架构师的真空

在分析前端工程中的偏差时，其中一个主要原因是开发者在实现他们没有参与设计的东西。对前端开发者来说，这可能是实现设计师的工作；而对后端开发者来说，他们还有另一个历史宿敌：架构师。

正如无法编译的作业既是其自身的原因也是其自身的结果，“架构师不写代码”这一反模式既是受损反馈循环的结果，也是造成损害的根源。

即使与最优秀的专业人士共事，我也从未见过一个项目能让最初的设计在整个项目周期内完好无损地存活下来。但有些架构师扮演的正是这个角色：在真空中创建系统设计，然后把它交给负责实现的工程师。

这给工程师带来了挫败感，因为他们与系统有直接的反馈循环，因此不得不直接面对其不足之处。而对架构师来说，反馈循环被严重稀释，以至于——如果实现的工程师没有足够强烈地回馈他们的意见——架构师可能完全收不到反馈，并将一场灾难视为自己帽子上又一根漂亮的羽毛。

在这些情况下，标准的回答是建议架构师更多地参与编码，以保持对技术的敏感度，或维护同事对他们的尊重。这些当然是很好的理由，但核心在于，架构师必须参与到实现中，才能与自己的设计形成直接的反馈循环。

没有直接反馈，架构师对自己系统的理解将比实现者增长得更慢，因此架构师就要负责在上下文和理解都不充分的情况下做决策。

期望架构师在不参与实现的情况下就能充分设计系统，就像期望一位父亲通过一夜情就能养育出一个性格健全的孩子一样：这根本不可能奏效。

项目经理的恐慌

把焦点从同语反复转向悖论，正如断开连接的反馈循环中没有信号一样，过多的反馈循环也会让信号被遮蔽到几乎不存在。想想产品经理的角色，以及包围他们的那团过度生长的反馈循环。

一旦我们开始考察个人与群体之间的反馈循环，这些反馈循环就等同于沟通线路，并且会随着群体规模的扩大而迅速衰退。

由此得出的结论是，改善沟通的最佳方式是减少需要沟通的人数。交叉培训很重要，因为它能将多个角色合并到一个人身上，但如果前端工程师觉得自己有资格过问设计和后端工程的问题，并因此卷入额外的设计和后端讨论，反而会增加沟通线路。

有些人确实需要参与所有事情，但如果每个人都参与所有事情，而你的团队里有超过三四个有强烈意见的人，那你可能就麻烦了。

好的循环是专注的循环

较大团队用来控制反馈干扰的最常见技术是召开会议。我的观点是，会议是反馈循环贫乏的标志；而当出现“最后一刻”“全项目”“状态”和“澄清”这些词时，这种观点会变得更加坚定。

好的反馈循环意味着在尽可能少的组件之间建立紧密而直接的沟通线路。我们并非每个人都有幸每天和 Slime 对话，但朝着那个方向努力，我们至少能获得——如果不能得到救赎的话——内心的平静。
