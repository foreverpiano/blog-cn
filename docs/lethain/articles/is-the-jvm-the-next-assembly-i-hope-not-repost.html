JVM 是“下一代汇编”吗？我希望不是。（转载）

2007-06-04 · 阅读原文

这是一篇从原 Irrational Exuberance 博客移植的文章，写于 2007 年中期：距今已近两年。

本文最初的标题是“Is Java the 'next assembly'?”。大约一两年前，有人指出用 JVM 比 Java 更合适。迟到总比不到好，对吧？

最近我研究了一些构建在 JVM 之上的编程语言，并思考它们吸引人的地方。本来打算写一篇文章，分析在这些语言和 Java 之间进行互操作所需的代码，但写完后我发现那是一篇糟糕的文章，于是放弃了。取而代之的是，我开始思考这些语言所面临的困难、它们给我们程序员带来的影响，以及它们将如何融入编程语言的发展周期。

基于 JVM 的语言的优势

可以直接使用 Java 库

随着 JVM 改进而“免费”获得速度提升

JVM 的缺点

某些语言与 Java 融合得很差

SISC Scheme

(import s2j)
(import oo)
(import generic-procedures)
(define-java-class jstring |java.lang.String|)
(define-generic-java-methods length to-class hash-code)
(define str (java-new jstring))
(length str)    ; ==> 0
(hash-code str) ; ==> 0

Jython

import javas = java.lang.String("yes")
print s # ==> yes
s.length() # ==> 3
s.length # ==> its a method
sb = java.lang.StringBuffer()
print sb # ==> outputs a blank line, as sb is empty
sb.append(s) # ==> yes
sb.append("no") # ==> yesno
sb.append(java.lang.String("maybe")) # ==> yesnomaybe

Jython 的代码与我们在 CPython 中预期的大致相同，只是操作一些从其他地方导入的对象。相当干净，也很容易理解：很直观。而 SISC Scheme 的代码几乎让我大脑当机。它强行把 Scheme 变成一种过程式语言，我觉得完全不直观，用起来也相当困难（我多次没能成功给它初始化一个值）。举这两个例子的目的是想说明：每种语言在设计时都带有特定的技术和范式，而那些与 Java 设计范式不同的语言，很可能会成为奇怪的搭档。此外，那些对象模型和实现方式与 Java 差异很大的语言，在兼容性上也会吃亏（比如原型、泛型等等）。

某些功能被 Java 技术所限制

执行速度通常更差（但并非总是如此）

应用程序分发变得更加复杂

不可避免的怪癖
