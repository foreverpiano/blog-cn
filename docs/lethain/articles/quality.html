如何打造软件质量

2024-06-16 · 阅读原文

我最近在读 Steven Sinofsky 的《Hardcore Software》，特别喜欢 Zero Defects 一章中提到的一份备忘录里的这句话：

你可以提升自己的代码质量，如果你这么做，对你自己和对 Microsoft 的回报都将是巨大的。最难的部分，是下定决心要写出完美的代码。

如果我在公司内部备忘录里写下这句话，估计工程团队会造反，但软件质量确实是一个我持续在打磨自己认知的有趣话题。市面上有各种各样的软件质量方法论，我也越来越相信，这些方法论在它们适用的特定环境中都是有效的，但常常被误用。

比如，几乎每个创业公司的基础设施团队里，都有人坚信只要设计足够精细的自动化灰度发布策略，所有质量问题都能解决。在我服务于高频、强黏性用户场景的公司时，这通常是成立的；但在用户使用频率低或差异极大的环境中，却完全不成立。不出意外的是，只见过高频场景的人往往高估灰度发布技术的价值，而从未见过高频场景的人又往往低估它的价值。

这个观察是我关于如何打造软件质量的信念基础。基于这个观察，我想说服你接受两件事：

打造质量是强上下文相关的。应对本质领域复杂性、规模复杂性和偶然复杂性，需要不同的技术。例如，如果用户行为一致性很低，分阶段的自动化灰度发布就起不到太大作用。质量既是在单次开发循环内创造的，也是在多次开发迭代之间创造的。在循环内部的反馈比跨迭代的反馈能更快地创造质量。而跨迭代的反馈往往是在衡量质量，并为未来的质量提供信息，但并不一定直接创造质量。例如，软件名义上完成后发现的 bug 通常只会被局部修复，即便它们暴露了更深层的不合理设计。我见过有些项目毫无理由地用了 Redis，后来导致生产事故，只是因为开发者想学习 Redis，而当时再重构已经太晚，会牵扯大量工作。

这些话听起来不错。接下来我试试说服你，它们确实有意义。

定义质量

通常我认为质量是主观的，但我在互联网上写作的经验告诉我，如果我不给出一个定义，人们会不满。所以这里是我目前的工作定义：

软件的行为符合用户对其的预期；软件易于修改；软件满足合理的非功能性需求（延迟、成本等）。

毫无疑问，世界上有更好的定义，欢迎你代入自己的版本。

复杂性的种类

管理质量在很大程度上就是找到处理复杂性的有效方法。例如，一个代码库可能因为体量庞大而变得复杂。大型代码库的复杂性可以通过使用强类型语言、提高测试覆盖率等方式来管理。

我发现，区分复杂性主要是由高规模驱动（比如你每秒要处理几万甚至十几万请求），还是主要由复杂的业务领域驱动（比如你试图将开放式商业合同的意图捕捉到结构化数据库中），是非常有帮助的。我把前者称为“规模复杂性”（scale complexity），后者称为“本质领域复杂性”（essential domain complexity），这个说法延伸自 Fred Brooks 在《没有银弹》中的表述。

第三种常见的复杂性是偶然复杂性。如果你因为团队想“尝试新鲜事物”，而在产品的每个部分都用了不同的技术，那么你的问题很可能属于偶然复杂性。

打造质量是上下文特定的

我的经验是，科技行业的大多数人关于如何打造质量的坚定观点，都深深锚定在他们第一次真正参与工作的经历上。比如，很多早期工作经历包括以下场景的人：

高流量网站或 API 的从业者相信，由生产指标驱动的自动回滚是防止低质量发布影响用户的基本机制。然而，在用户行为不频繁、复杂且精确的领域——比如 Carta 所处的基金会计和股本管理领域——这些技术帮助有限。它们确实能阻止某些问题，但无法阻止很多其他问题，因为用户行为量不足以覆盖所有可能的配置。高流量面向消费者的应用从业者相信 A/B 测试可以确定质量。然而，Michelle Bu 在《Eagerly discerning, discerningly eager》一文中讨论了为什么许多验证质量的工具在 API 设计场景下并不适用。她提出用“摩擦日志”替代用户访谈，用试点项目替代 Beta 测试，用 dogfooding 替代 A/B 测试。在高度关键且问题空间狭窄的领域，可能需要多个异构实现进行投票，以在软件出错时确定正确答案，就像 Gloria Davis 1987 年的论文《An Analysis of Redundancy Management Algorithms for Asynchronous Fault Tolerant Control Systems》中描述的那样。然而，对于那些问题域宽泛且需要频繁变化的场景（这是初创公司的典型情况），维护和验证多个异构实现会极其昂贵。

这里的核心观察是：不存在一个“放之四海而皆准”的解决方案。即使是普遍认可的理想做法——“让一个高度尽责且拥有充分上下文的工程师独自完成所有工作”——在当前团队规模过小、无法满足期望工作量的情况下，也不是可行的方案。

总体而言，我认为你打造质量的方法会随着以下几个维度而变化：

本质领域复杂性——如果问题域的工作流和条件很少，通常可以通过观察用户真实使用情况来进行验证（比如 Instagram、TikTok 或 Calm 这类应用，软件内部的工作流和条件非常少，尽管它们需要支持的移动设备种类会增加本质复杂性）。如果问题域包含大量工作流或条件，就需要不同的方法，可能包括模拟使用或形式化规格说明。规模复杂性——足够多的用户流量能解决很多问题。在 Calm、Uber 或 Stripe，流量规模足够大，即使采用增量发布策略，错误也能立即在运维数据中显现。而在 Carta，由于用户使用模式差异很大，只有极其广泛的错误（这类错误通常比较容易通过自动化测试捕获）才会在运维数据中明显体现。团队的成熟度和在岗时间——对问题域有深厚上下文的团队，能够以更少的明确角色、更多的个人赋权和更少结构化流程来驱动质量。高流动率的团队通常会依赖更明确的角色分工，以便能快速建立上下文。同样，认为自己对高质量负有责任的团队，其行为方式也会与不这么认为的团队大不相同。

为了进一步展开，让我们思考两种组合，以及我们会如何以不同方式对待质量：

本质复杂性低、流量高、团队上下文深厚——一个完善的测试套件就能在很大程度上验证预期行为，而且团队对问题空间足够熟悉，工程师能在实现过程中有效地进行测试。如果确实遗漏了什么，通过生产运维指标来控制节奏的增量发布机制，很可能防止测试缺口对用户造成重大影响。本质复杂性高、流量低、团队上下文有限——设计有效的测试套件会非常具有挑战性，因为团队上下文不足且问题空间复杂。这意味着你可能需要专人负责构建测试框架，将领域上下文封装到可复用的测试支架或框架中，而不是依赖每个团队成员的个人上下文。这也可能意味着要重点使用高度定义的类型，将部分领域上下文直接编码到类型检查器中，而不是依赖每个写增量代码的人的意识。增量发布机制不太可能捕捉到测试遗漏的问题，因为不同用户之间的条件差异太大，即使少量灾难性失败的用户也很难达到触发回滚的阈值。

这些是截然不同的方法，如果你把一种组合下的解决方案生搬硬套到另一种组合上，你会制造大量动作，但不太可能产生多少实际效果。一旦你意识到这些组合的存在，你就能开始观察在类似问题上工作的人采用了哪些技术，同时这种意识也能帮助你逐步建立一个能在各种环境下打造质量的认知模型。

对错误的容忍度是一个重要维度吗？

在建立一个用于思考如何打造质量的模型之前，我想先对“错误容忍度”发表一些看法。我认为很多人会说，你对错误的容忍度是决定质量方法的重要维度，但坦白讲，我并没有发现这是一个有用的维度。

例如，如果你告诉我你们公司高度重视质量，所以配备了非常庞大的质量保障团队，或者实施了非常正式的验证流程，我的第一反应会是怀疑。质量保障团队在很多场景下都极其有用，正式验证流程在很多场景下也非常有用。然而，这两者都不是普遍最优的，而且两者都能被做得很糟糕。

根据我个人的经验，质量最高的组织是那些细节导向的团队工作的质量。这种由高管驱动的检查把质量提升为领导层的一等事务，并逐级向下传递。在这些组织中，通常也会有构建质量保障工具的团队，但这些团队是支持质量，而不是直接对质量负责。审查与信任的边界

其他人的个人经历可能完全相反，而这正是重点：我见过对错误零容忍的组织采用过各种各样的不同方法。同样，我也见过对错误容忍度高的组织，既有大力投入质量保障的，也有大力投入工程师主导质量的。因此，我不认为这是一个在思考如何打造质量时的重要维度。

迭代模型

我关于打造质量的模型最初是一个。制定可靠性策略：用系统模型思考复杂问题

这个模型有很多值得喜欢的地方，我认为“潜在事故”（latent incidents）这个概念特别有用，因为它承认：即使你改进了质量实践，也可能需要很长时间才能把潜在事故的积压清空，让你真正感觉到质量得到了提升。我猜很多团队其实已经解决了质量问题，却在清空积压之前不小心放弃了之前成功的做法，从而没有意识到自己已经解决了问题。

我在构建上述模型的时期，几乎完全聚焦于由 sprawling 代码库带来的偶然复杂性，以及由日益增长的并发使用量带来的规模复杂性。由于这种聚焦，我花在思考第三种复杂性来源——本质领域复杂性——上的时间太少了。

我在这里想做的是，构建一个同时纳入我之前模型的洞见，以及在我目前在 Carta 和之前在 Calm 的工作中，本质领域复杂性一直是质量问题最大来源这一事实的新模型。

我认为，从最小的软件迭代循环开始是很有帮助的，即 1964 年首次普及的 Read Eval Print Loop（简称 REPL）。

现代开发已经很少直接在 REPL 中进行了，但开发者主导的测试提供了一个非常相似的循环：单个开发者从编写一段代码，到为它编写测试，再到运行测试，最后根据测试反馈进行修改。

现在让我们引入这样一个事实：这个紧密的迭代循环只是交付软件的一个阶段。写完软件后，我们还需要将其发布到生产环境中。毕竟，正如 Steve Jobs 所说，真正的艺术家要交付作品！

特别值得注意的是发生在单个节点内部的循环与跨越节点之间的循环。在节点内部迭代要比跨越节点迭代快得多。

虽然我们已经开始接近了，但要真正讨论代码质量，我们还缺少几个关键要素。首先，即使代码发布了，仍可能存在缺陷率——实现未能完全解决领域中的本质复杂性，从而留下潜在缺陷。或者，生产环境中可能出现新的问题，原因可能是偶然复杂性（比如糟糕的环境配置），也可能是规模复杂性（比如意料之外的流量激增）。

其次，有时工程师即使非常努力，也无法真正理解他们正在尝试实现的功能。这可能是因为他们是团队新人，而问题空间又很复杂。也可能是因为他们与负责定义所需功能的产品经理之间出现了沟通偏差。

这个模型开始变得有趣了！首先要注意的是，从编写软件到如果需要重写软件，反馈的延迟有多严重。如果从产品到工程师的功能规格交接出了问题，可能需要几周才能发现问题。在“高基数”（high cardinality）的问题域中——用户使用方式和用户数据差异极大——这个问题更加严重：开发者可能要几个月甚至几个季度才能收到关于自己错误行为的反馈，而那时他们最多也只是模糊记得当初的意图。

像任何好的模型一样，你可以不断迭代它，以捕捉对你当前场景最有意义的细节：

如果你主要关注规模复杂性，那么发布流程对你来说很可能特别重要。如果你关注偶然复杂性，那么对软件设计的主动和被动控制——即对进入和离开软件开发集群的把关机制——会是最有趣的部分，比如，或者在 pull request 合并前。如果你关注本质领域复杂性，那么你关注的重点要么是功能规格说明，要么是软件开发的反馈循环。应对方法可能包括：让新员工嵌入到拥有高上下文的团队中，要求 pull request 必须由领域专家评审，或者开发一个全面的测试支架，让开发者能轻松地针对各种异常场景测试新功能。扩展技术一致性收回不合理的软件

体会任何模型最好的方式就是去实验它。删除那些对你来说不重要的部分，添加那些你认为缺失的部分，看看它能教会你什么。

衡量有助于（但不等于）创造质量

这个模型的一个重要观察是：在生产环境中甚至在发布阶段发现的错误，要比工程师在最初编写软件时发现的错误难有效解决得多。我把在软件工程师交接之后发现错误，主要看作是在衡量质量，而不是创造质量。我之所以做这个区分，是因为这种衡量带来的任何改进都发生在循环的下一轮迭代中，而不是在当前循环内部。

我认为这个区分很重要，因为它提供了一个词汇表，可以用来讨论软件工程团队和质量保障（QA）团队各自的角色。

软件工程团队编写软件来解决问题域复杂性和规模复杂性。如果做得好，开发者主导的测试会发生在小型、本地的开发循环内，因此实现和验证之间没有延迟，也没有协调开销。这样，开发者主导的测试在其编写的那个阶段就直接贡献了质量。

QA 团队编写软件（或执行手动流程）来衡量软件在问题域中的质量。QA 主导的测试发生在独立的步骤中，即使这个步骤是并行发生的，软件的初始设计也不会受到 QA 测试的影响。这种影响只有在质量循环下一次重复时才会发生。

这个区分很重要，因为问题发现得越晚，就越可能被战术性地而非结构性地解决。晚期发现的质量问题，更可能推动的是特定正确性的改进（修复这个测试用例），而不是根本方法的改进（重新设计架构）。这并不意味着 QA 主导的测试没有价值，它对于发现那些上下文狭窄的工程师不会想到去测试的跨功能 bug 非常有价值。但它的确意味着，开发者对自己当前工作的测试能更早地创造质量，而 QA 主导的测试则做不到这一点。

为了把这个观察落到实处，可以想想 John Ousterhout 在《Philosophy of Software Design》中提出的“把错误从存在中定义掉”（define errors out of existence）的理念。该原则认为，你可以通过设计接口来消除很多潜在的软件错误，从而让错误根本不会发生。例如，与其在我试图删除一个不存在的文件时抛出错误，不如直接确认文件不存在。QA 主导的测试可能会确保该函数只在正确的时间抛出错误，但只有开发者主导的设计（可能包括开发者主导的测试或 dogfooding）才能支持快速的迭代循环，从而彻底改变接口，把那个错误从存在中定义掉。

顺便说一句，这或多或少也是我在给 GitHub ReadME 投稿时试图表达的观点，只不过当时我聚焦在事故响应上。对以往事故和事故响应实例的衡量，是改进未来事故响应的输入，但并不能直接提升可靠性：只有完成那些能真正提升可靠性的项目才能做到这一点。当你没有完成任何项目时，投入更多精力去衡量并不能解决任何问题。

你应该怎么做？

整篇文章想要传达的核心信息，正好和我们在引言中开始的地方一样：打造质量是强上下文相关的。警惕直接照搬你以前见过的 playbook，即使那些 playbook 曾经极其成功。它们可能非常有效，但往往只有当你拥有一个有用的模型，能够理解它们为什么在之前的环境中有效时，才会继续有效。

“把错误从存在中定义掉”这个想法出自 John Ousterhout 的《Philosophy of Software Design》，在 TCL Lang wiki 的这个页面中有一些很棒的例子。本质复杂性与偶然复杂性的区分，在 Fred Brooks 的《Mythical Man Month》中的《No Silver Bullet》一文里有讨论，这是思考复杂性（进而思考质量）的一个宝贵维度。Michelle Bu 的《Eagerly discerning, discerningly eager》是一篇非常好的文章，讨论了 API 设计如何不同于许多其他类型的产品设计（例如，不能用 A/B 测试，但可以与其他公司作为设计伙伴合作）。Kent Beck 的《Tidy First?》讨论了许多在代码库中解决偶然质量问题（主要是由大型代码库中不一致实现导致的）的策略。我之前。收回不合理的软件记录了我关于如何在一个已经难以理解的代码库中打造质量的思考。用本文的词汇来说，它主要关注解决偶然复杂性和规模复杂性。《Staff Engineer》中的“Manage technical quality”一章描述了许多可以用来提升质量的工具。这里的讨论大多是与具体组合无关的，也就是说，是可能适用于各种组合的有用技术，当然你也可以用本文提出的质量模型来评估哪些技术最适合你的情况。Vaughn Vernon 的《Domain-Driven Design Distilled》是对领域驱动设计的一个很好的概述，这种软件开发方法特别适用于本质领域复杂性高的问题域。Hillel Wayne 的《Practical TLA+》是对形式化规格说明的一个实用入门，大多数软件工程师没有花时间思考这个话题，但它仍然是一个很有趣的领域。Ford、Parsons、Kua 和 Sadalage 合著的《Building Evolutionary Architectures》包含了许多关于代码库引导式演化的思想（这里有我对）。他们的建议总体上也是与具体组合无关的。《Tidy First?》笔记构建演进式架构笔记
