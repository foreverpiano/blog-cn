如何打造软件质量

2024-06-16 · 阅读原文

我一直在阅读 Steven Sinofsky 的《Hardcore Software》，特别喜欢他在《Zero Defects》章节中讨论的一份备忘录里的这段话：

你可以提升代码质量，如果你这么做，你自己和微软都将获得巨大回报。最困难的部分，是下定决心要写出完美的代码。

如果我在公司内部备忘录里写下这句话，我猜工程团队可能会造反，但软件质量确实是一个有趣的话题，我也在持续完善自己对它的思考。市面上有太多软件质量的“ playbook”，我越来越相信，这些 playbook 在其适用的场景下都是有效的，但往往被用错了地方。

比如，几乎每个创业公司的基础设施团队里，都会有一个人坚信，只要有足够精细的自动化灰度发布策略，就能解决所有质量问题。根据我的经验，这在高频、强用户黏性的环境中通常是成立的，但在用户使用频率低或差异很大的环境中则完全不成立。不出意外的是，只见过高频场景的人往往高估灰度发布技术的价值，而从未见过高频场景的人又往往低估它的价值。

这一观察正是我关于打造软件质量的核心信念。在此基础上，我想说服你两件事：

打造质量是高度依赖上下文的。解决本质领域复杂性、规模复杂性和意外复杂性，需要采用不同的技术。例如，如果用户行为一致性很低，那么分阶段自动化灰度发布就没什么帮助。质量既可以在单次开发循环内创造，也可以在多次开发循环之间创造。循环内的反馈比循环间的反馈能更快地创造质量。循环间的反馈往往是在衡量质量，并为未来改进提供信息，但并不一定直接创造质量。例如，在软件名义上完成后发现的 bug，通常只会被局部修复，即使它们揭示了更深层的不佳设计。我见过一些项目莫名其妙地用了 Redis，后来引发了生产事故，只是因为开发者想学习 Redis，而当时再重构移除它已经太晚了。

这些话听起来不错。下面让我试着说服你，它们确实有实际意义。

定义质量

通常我认为质量是见仁见智的，但我写互联网内容的经验告诉我，如果我不给出一个定义，大家会不高兴。所以这里是我目前的工作方向：

软件的行为符合用户预期；软件易于修改；软件满足合理的非功能性需求（延迟、成本等）。

毫无疑问，世界上有更好的定义，欢迎用你自己的来替换。

复杂性的种类

管理质量在很大程度上就是找到有效应对复杂性的方法。例如，一个代码库可能因为规模庞大而变得复杂。大型代码库的复杂性可以通过使用强类型语言、提高测试覆盖率等方式来管理。

我发现，区分复杂性主要是由高规模驱动（比如每秒处理数万或数十万请求），还是主要由复杂的业务领域驱动（比如试图将开放式业务合同的意图捕捉到结构化数据库中），是很有帮助的。我把前者称为“规模复杂性”（scale complexity），后者称为“本质领域复杂性”（essential domain complexity），这个说法延伸自 Fred Brooks 的《No Silver Bullet》。

第三种常见的复杂性是意外复杂性（accidental complexity）。如果你因为团队想“尝试新东西”，而在产品的不同部分使用了大量不同的技术，那么你的问题很可能属于意外复杂性。

打造质量是上下文相关的

我的经验是，技术领域的大多数人都会对打造质量形成强烈观点，而这些观点很大程度上锚定于他们最早的工作经历。例如，许多人的早期职业包括：

高流量网站或 API，他们相信由生产指标驱动的自动化回滚是防止低质量发布影响用户的基本机制。然而，在用户操作不频繁、复杂且精确的领域——比如 Carta 所处的基金会计和股本表管理领域——这些技术帮助有限。它们确实能阻止一些问题，但无法阻止很多其他问题，因为用户操作量不足以覆盖所有可能的配置。高流量面向消费者的应用，他们相信 A/B 测试可以确定质量。然而，Michelle Bu 的《Eagerly discerning, discerningly eager》一文讨论了为什么许多验证质量的工具在 API 设计中并不适用。她提出用摩擦日志（friction logs）替代用户访谈，用试点项目替代 beta 测试，用 dogfooding 替代 A/B 测试。高度关键且问题空间狭窄的场景，可能适合用多个异构实现进行投票，在软件出错时确定正确答案，正如 Gloria Davis 1987 年的论文《An Analysis of Redundancy Management Algorithms for Asynchronous Fault Tolerant Control Systems》所描述的那样。但对于那些问题域宽泛且需要频繁变化的场景（这是初创公司的典型情况），维护和验证多个异构实现会极其昂贵。

这里的关键观察是，不存在一个“放之四海而皆准”的解决方案。即使是普遍认可的理想做法——“让一个高度尽责且高上下文的工程师独自完成所有工作”——在当前团队规模太小、无法满足期望工作量的情况下，也不是可行的方案。

总体而言，我认为你打造质量的方法会随着以下维度而变化：

本质领域复杂性——工作流和条件很少的问题域，通常可以通过观察用户实际使用情况来验证（例如 Instagram、TikTok 或 Calm 这类应用，软件中的工作流和条件非常少，尽管它们需要支持的移动设备种类增加了本质复杂性）。而工作流或条件很多的问题域则需要不同的方法，可能包括模拟使用或形式化规格说明。规模复杂性——足够多的用户流量能解决很多问题。在 Calm、Uber 或 Stripe，规模足够大，即使采用增量发布策略，错误也能立即在运维数据中显现。而在 Carta，由于用户使用模式差异很大，只有极其广泛的错误（这类错误相对容易通过自动化测试捕获）才会如此。团队的成熟度和在岗时间——对问题域有深厚上下文的团队，能够以更少的明确分工、更多的个人赋权和更少结构化流程来驱动质量。而人员流动率高的团队，通常会依赖更明确的角色分工，以便快速建立上下文。同样，对高质量有强烈责任感的团队，行为方式也会与没有这种责任感的团队大不相同。

为了进一步阐述这一点，让我们考虑两种组合，并看看我们会如何以不同方式对待质量：

本质复杂性低、流量高、团队上下文深厚——一套完善的测试套件就能在很大程度上验证预期行为，团队对问题空间足够熟悉，工程师可以在实现过程中有效地进行测试。如果你漏掉了一些东西，采用增量发布机制，并用生产运维指标来控制发布节奏，很可能防止测试缺口对用户造成重大影响。本质复杂性高、流量低、团队上下文有限——由于团队上下文有限和问题空间复杂，设计有效的测试套件极具挑战性。这意味着你可能需要专人负责开发测试框架，将领域上下文封装到可复用的测试支架或框架中，而不是依赖每个团队成员的个人上下文。它还可能意味着要重点使用高度精确的类型系统，将部分领域上下文直接编码到类型检查器中，而不是依赖每个写增量代码的人的认知。增量发布机制不太可能捕捉到测试漏掉的问题，因为用户之间的条件差异太大，即使少量灾难性失败的用户也很难达到触发回滚的阈值。

这些是截然不同的方法，如果你天真地将一种组合的解决方案套用到另一种组合上，你会产生大量动作，但不太可能产生多少实际效果。一旦你意识到这些组合的存在，你就能开始观察类似问题领域的人采用了哪些技术，而这种意识也能帮助你逐步建立一个能在各种环境下打造质量的思考模型。

对错误的容忍度是一个重要维度吗？

在构建一个关于打造质量的思考模型之前，我想先对“容错度”做一些评论。我认为很多人会说，你对错误的容忍度是决定质量方法的重要维度，但坦白说，我并不觉得这是一个有用的维度。

例如，如果你告诉我你们公司高度重视质量，所以配备了非常庞大的质量保障团队，或者采用了非常正式的验证流程，我的第一反应会是怀疑。质量保障团队在很多场景下都极其有用，正式验证流程在很多场景下也非常有用。但两者都不是普遍理想的方案，而且两者都可能被执行得很糟糕。

根据我的个人经验，质量最高的组织，是那些细节导向的团队工作的质量。这种由高管驱动的检查，将质量提升为领导层的一等大事，并逐级向下传递。在这些组织中，通常会有团队构建质量保障工具，但这些团队是支持质量工作，而不是直接对质量负责。检查与信任的边界

其他人的个人经验可能完全相反，而这正是重点：我见过对错误零容忍的组织采用了各种各样的不同方法。同样，我也见过对错误容忍度高的组织，既有重视质量保障的，也有重视工程师主导质量的。因此，我不认为这是一个在思考打造质量时的重要维度。

迭代模型

我关于打造质量的模型最初是一个。撰写可靠性策略：用系统模型思考复杂问题

这个模型有很多可取之处，我认为“潜在事故”（latent incidents）的概念特别有用，因为它承认即使你改进了质量实践，也可能需要很长时间才能消化完积累的潜在事故，让你真正感觉到质量得到了提升。我猜很多团队其实已经解决了质量问题，却在消化完积压问题之前就意外放弃了成功的做法，结果未能意识到自己已经解决了问题。

我在构建上述模型时，几乎完全专注于由 sprawling 代码库带来的意外复杂性，以及由日益增长的并发使用量带来的规模复杂性。由于这种专注，我对第三种复杂性来源——本质领域复杂性——思考得太少。

我在这里想做的是，构建一个同时包含我之前模型的洞见，并且能反映出本质领域复杂性是我在 Carta 和 Calm 当前及之前职位中最大质量问题来源的模型。

我认为，从软件迭代的最小可能循环——Read Eval Print Loop（简称 REPL，1964 年首次流行）——开始，是很有帮助的。

如今已经很少有现代开发是直接在 REPL 中完成的，但开发者主导的测试提供了一个非常相似的循环：单个开发者从编写代码，到为代码编写测试，到运行测试，再到处理测试反馈，形成闭环。

现在，让我们引入这样一个事实：这个紧密的迭代循环只是交付软件的一个阶段。写完软件后，我们还需要将其发布到生产环境中。毕竟，正如 Steve Jobs 所说，真正的艺术家要交付作品！

特别值得注意的是，发生在单个节点内的循环与跨节点发生的循环。前者在节点内迭代要快得多。

虽然我们已经开始接近，但要推理代码质量，我们还缺少几个关键要素。首先，即使代码发布后，仍可能存在缺陷率，即实现并未完全解决领域的本质复杂性，从而产生潜在缺陷。或者，生产环境中可能出现由意外复杂性（例如糟糕的环境配置）或规模复杂性（例如意外流量高峰）导致的新问题。

其次，有时工程师即使非常努力，也无法完全理解他们试图实现的功能。这可能是因为他们是团队新人，而问题空间又很复杂。也可能是因为他们与负责定义所需功能的产品经理之间存在沟通失误。

这个模型开始变得有趣了！首先要注意的是，从编写软件到如果需要重写软件，反馈的延迟有多严重——如果这个反馈需要发布软件才能获得。如果产品到工程师的功能规格交接出了问题，可能需要几周才能发现问题。这在“高基数”（high cardinality）的问题域中更为明显，那里用户使用和用户数据存在巨大差异：开发者可能需要几个月甚至几个季度才能收到关于自己错误的反馈，而那时他们最多也只是忘记了当初很多的原始意图。

和任何好的模型一样，你可以不断迭代它，以捕捉对你而言最重要的细节：

如果你主要关注规模复杂性，那么发布流程对你来说可能特别重要。如果你关注意外复杂性，那么对软件设计的主动和被动控制——即对进入和离开软件开发集群的把关机制——会是最有趣的，比如，或者在 pull request 合并前。如果你关注本质领域复杂性，那么你关注的焦点要么是功能规格说明，要么是软件开发反馈循环。应对技术可能包括：将新员工嵌入到高上下文团队中，要求 pull request 必须由领域专家评审，或者开发一个全面的测试支架，让开发者能够轻松地针对所有异常场景测试新功能。提升技术一致性。收回不合理的软件

熟悉任何一个模型的最好方式，就是用它做实验。删掉对你来说不重要的部分，加上你觉得缺失的部分，看看它能教给你什么。

衡量有助于（但不等于）创造质量

这个模型得出的一个重要观察是，在生产环境或甚至发布阶段发现的错误，比工程师在最初编写软件时发现的错误，要更难有效解决。我把在软件工程师移交之后发现错误，主要看作是在衡量质量，而不是创造质量。我做此区分的原因是，这种衡量带来的任何改进，都发生在循环的下一次迭代中，而不是在当前循环内。

我认为这一区分很重要，因为它提供了一套词汇来讨论软件工程团队和质量保障（QA）团队各自的角色。

软件工程团队编写软件来解决问题域和规模复杂性。如果做得好，开发者主导的测试发生在小而局部的开发循环内，实现和验证之间没有延迟，也没有协调开销。这样，开发者主导的测试在其编写的那个阶段就直接贡献了质量。

QA 团队编写软件（或运行手动流程）来衡量该软件在问题域中的质量。QA 主导的测试发生在独立的步骤中，即使这个步骤是并行进行的，软件的初始设计也不会受到 QA 测试的影响。这种影响只有在质量循环下一次重复时才会发生。

这一区分很重要，因为问题发现得越晚，就越可能被战术性地而非结构性地解决。晚期发现的质量问题，更可能推动的是特定正确性的改进（修复测试用例），而不是根本方法的改进（重新设计架构）。这并不意味着 QA 主导的测试没有价值，它对于管理那些上下文有限的工程师不会想到去测试的跨功能 bug 非常有价值。但它的确意味着，开发者对自己当前工作的主导测试，能更早地创造质量，而 QA 主导的测试则做不到这一点。

为了让这个观察更具象化，可以想想 John Ousterhout 在《Philosophy of Software Design》中提出的“将错误定义出存在”的思想。该原则认为，你可以通过设计接口来消除许多潜在的软件错误。例如，当我试图删除一个不存在的文件时，与其抛出错误，不如直接确认文件不存在。QA 主导的测试可能会确保函数只在正确的时候抛出错误，但只有开发者主导的设计（可能包括开发者主导的测试或 dogfooding）才能支持快速迭代循环，从而彻底改变接口，将那个错误“定义出存在”。

顺便说一句，这或多或少也是我在为 GitHub ReadME 撰稿时试图表达的观点，只不过当时我关注的是事故响应。对以往事故和事故响应实例的衡量，是改进未来事故响应的输入，但并不能直接提升可靠性：只有完成那些能提升可靠性的项目才能做到这一点，而在没有完成任何项目的情况下投入更多精力去衡量，并不能解决任何问题。

你应该怎么做？

这一切的预期 takeaways 正是我们在引言中开始的地方：打造质量是高度上下文相关的。要警惕直接套用你以前见过的 playbook，即使那些 playbook 曾经极其成功。它们可能非常有效，但除非你有一个有用的模型来思考它们为什么在之前的环境中有效，否则往往不会奏效。
