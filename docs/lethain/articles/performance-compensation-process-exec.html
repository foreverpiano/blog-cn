绩效与薪酬（面向工程高管）。

2023-09-03 · 阅读原文

Uber 最初的绩效流程叫做“T3B3”，非常简洁：写下个人最重要的 3 项优势和 3 项劣势，然后直接当面把反馈分享给当事人。公司曾长期抵制甚至记录这些反馈，认为那样会妨碍坦诚。另一边，又有大量故事讲述有人花几个月精心准备 Google 的晋升材料，最终却没能获得晋升。在同时经历过 Uber 和 Google 晋升流程的人当中，既有支持者也有批评者，对于什么样的绩效流程才是理想的，完全没有共识。

薪酬问题则微妙不同，但同样不存在被普遍认可的薪酬流程。高度结构化、由中央统一 orchestration 的薪酬体系，往往导致同一层级的大多数人获得相似的报酬，即使他们的实际影响差异很大。而更灵活的薪酬体系则会大幅奖励顶级表现者，这又会引入偏见空间。

由于大家对应该采用哪种绩效或薪酬流程没有共识，你很可能需要在多种不同体系中工作。本文将深入探讨以下内容：

设计、运营和参与绩效与薪酬流程的人之间的目标冲突；如何运行绩效流程（包括校准会议）及其面临的挑战；如何有效地参与薪酬流程；绩效和薪酬周期应该多久运行一次；为什么你的目标应该是一个有效的流程，而不是一个完美的流程。

这些体系都充满取舍和陷阱，你需要保持警惕。读完本文后，你应该能够为自己的组织规划出正确的路径。

这是 O'Reilly 图书《The Engineering Executive’s Primer》中的一章，未经编辑。

相互冲突的目标

回到 Uber 的 T3B3 绩效流程——在每个半年期告诉你最重要的三件事和最需要改进的三件事——最值得注意的是它的极端简洁。它完全专注于为接收者提供有用的反馈。直到今天，我仍然觉得这种目标的清晰度非常了不起，也极为罕见。

大多数绩效和薪酬体系的目标清晰度要低得多，因为它们试图平衡来自众多利益相关方的多种优先事项。公司典型的流程通常试图兼顾以下所有目标：

员工：希望获得有助于成长的有用反馈，希望尽快晋升，希望最大化自己的薪酬，并且希望这一切越快越好。经理：希望给团队提供公平且有用的反馈，希望在合适的时候（并与自己对团队的各种承诺保持一致）为团队争取晋升，希望提供适当的薪酬（同样要与对团队的承诺一致）。哦，他们也希望这一切越快越好！人力（或人力资源）团队：希望确保员工收到有价值的反馈，为反馈质量设定一条“底线”，记录可用于后续绩效管理和法律场景的反馈以支持公司立场，需要展示绩效流程以满足合规要求（例如 SOC2 要求每年进行绩效评估），并创建结构化的输入用于计算薪酬。高管：根据经理们不一致的评估决定晋升谁，在固定薪酬预算下进行优化以实现组织目标，并尽量减少经验不足或立场不一致的经理对晋升和薪酬的影响。

我从未见过或听说过哪一个流程能优雅地解决所有这些问题。我的合理猜测是，根本不存在能在几百人规模上运行且不显得繁琐的流程。同时，也不可能完美平衡“客观一致的结果”与“认可杰出个体”这两个目标。

这些流程还有很多改进空间，也确实可以一直改进，但流程中的张力源于参与者相互冲突的目标。这些冲突的目标是真实的、根本的、不可避免的，在你决定流程如何运作时必须始终牢记。

绩效与晋升

我先来谈谈绩效流程，包括晋升。基础的绩效流程是每位经理为自己的直接下属提供书面反馈，其中包括是否晋升的决定，但其中有许多细节和变体值得考虑。

首先要考虑的变体是是否包含 peer（同级）和 upward（向上）反馈。向上反馈是一个受限的问题，因为每个人通常只有一个经理。最坏的情况是，收集向上反馈会产生低价值的结果，通常是因为员工不想批评自己的经理，但它不会占用太多时间。

同级反馈可能占用大量时间，特别是对那些人际网络很广的人来说，他们可能会被要求为十个或更多人提供同级反馈。通常会附带建议说，如果收到太多请求可以拒绝，但很多员工发现自己很难拒绝同级反馈请求，即使他们知道应该拒绝。

更重要的是，根据我的经验，同级反馈非常不一致，我逐渐相信每个团队对同级反馈价值的信念，决定了反馈是否真的有用。我管理过认为诚实地给出同级反馈太令人不适的团队，他们提供的同级反馈毫无价值：在这种情况下，收集同级反馈并不值得。我也管理过狂热相信同级反馈价值的团队，他们产出了有洞察力、有价值反馈。因此，我倾向于授权经理自行决定是否为自己的团队收集同级反馈。通常这是公司层面的政策决定，在这种情况下，我不会去争取改变。

职级与职级评估标准

如果没有书面标准来描述每个职级期望的表现维度，几乎不可能就绩效评级和谁应该被晋升达成一致。不过，在讨论职级评估标准之前，我们得先谈谈职级本身。

大多数公司会将职称和职级配对，例如：

Entry Level Engineer (Level 3) Software Engineer (Level 4) Senior Software Engineer (Level 5) Staff Software Engineer (Level 6)

具体职级在不同公司差异极大（有很多网站会展示各公司职级的对应关系），某公司的“Level 3”在另一家公司可能是“60”，在第三家公司又可能是“601”。各公司之间没有统一的职级标准。软件工程职级通常从“Level 3”开始，因为公司会在多个职能中使用同一套职级体系，而且往往把“Level 1”保留给入门要求更低的初级岗位。

职称在行业内的差异更大，根本不存在普遍适用的标准。如果你正在为公司设定职称，我建议采用比较典型的序列：Entry-Level Software Engineer、Software Engineer、Senior Software Engineer、Staff Software Engineer 以及 Sr Staff Software Engineer。如果你想尝试新的职称，请注意，这样做会让招聘流程更复杂，你需要解释这些职称的含义，还可能会失去一些担心非标准职称会损害自己职业轨迹的候选人。

一旦确定了工程团队的职称和职级，下一步就是编写职级评估标准（leveling rubrics），明确每个职级的工作期望（同样，有很多网站收集了多家公司公开的职级标准）。这可能是一项规模很大的工作，我建议跳过最难的部分：挑选一个网上现成的、还算不错的版本，组建一个工作组来微调细节，然后在每次绩效周期结束后根据出现的问题进行优化。

此外，我想强调几点自己多年来艰难学到的经验：

优先选择简洁而非面面俱到的职级标准：人们强烈希望职级标准能代表完整、清晰的晋升依据。当然，问题是很多人特别擅长针对具体标准“刷分”。例如，Stripe 的晋升标准包括导师指导，我就遇到过有人声称自己在指导他人，理由是未经对方请求就安排了一次会议，并认为这就构成了导师指导。简洁的标准需要更细致的解读，但试图刷标准的现象意味着所有实际选项都需要大量解读。你可以针对每一次刷分行为增加更详尽的文档，但你的标准很快就会变得难以使用，更注重防止坏行为，而不是为善意的人提供清晰指导。优先选择宽泛的职类而非狭窄的职类：一个经典的高管决策是，Site Reliability Engineer 和 Software Engineer 是否应该使用不同的职级标准。假设你认为分开更公平，那很好！那 Data Engineer、Data Scientist、Frontend Engineer 和 QA Engineer 是否也应该有各自的标准呢？是的，每个职能如果有自己的标准会更好，但维护标准成本很高，而且调优标准需要频繁使用它们来评估很多人。标准越多，通常意味着做出更多不够精准的晋升决策，也会让人觉得某些职能晋升更容易。我强烈建议尽可能复用和合并，尤其是对于人数少于十人的团队，不要维护定制标准：无论是否引入定制标准，在评估狭窄专业领域的绩效时，你最终都会使用特事特办的判断，而使用共享流程成本更低。同时记录“如何做”（行为）和“做什么”（结果）：有些标准极其关注展示某些能力，却没有明确表明要在文化上以公司认可的方式达成目标。我认为这是个遗憾，因为这意味着你可能会晋升那些有能力但达成目标的方式不符合公司期望的人。职级标准和晋升决策都应该清晰地释放信号：这个人正走在公司内部成功的道路上，而这只有在你明确行为期望时才可能实现。

关于职级和职级标准的最后一个话题是，你应该努力让它们诚实地反映实际情况。许多公司都有明面上的职级和晋升标准——通常围绕公平、透明等设计——但下面还存在大量看不见的流程在真正决定事情如何运作。只要可能，就把那些尴尬的部分说出来，让组织直面真实情况。如果晋升受制于可用预算和业务需求，最好直接承认，而不是让团队花费时间编造一套想象中的规则来解释意外的结果。

晋升与校准

有了职级标准，你现在可以基于事实讨论哪些人已经从一个职级跨越到另一个职级。大多数公司依赖经理先提出 tentative（暂定）的晋升提名，然后通过校准流程来批准该提名。校准通常是一群经理一起讨论每个人的暂定评级和晋升决定，目的是在整个组织内做出一致的决策。

在拥有几百名工程师的组织中，常见的校准流程是这样的：

经理提交他们的暂定评级和晋升决定。子组织（例如“Infrastructure Engineering”）的经理们组成 5-8 人的小组一起开会，其中包括负责整个子组织的主管（例如其他经理所汇报的“Director of Infrastructure Engineering”），讨论子组织内所有的暂定决定。向工程高管汇报的经理们与工程高管一起开会，重新审视整个组织的暂定决定。实践中人数太多，无法逐一详细审查，所以这一轮通常重点关注晋升、顶级表现者和最低表现者。工程高管会与人力团队一起 review 最终决定，然后与其他高管对齐，以在各组织间保持一定程度的一致性。他们还会查看拟定的评级和晋升决定对当前公司预算的影响。

上述例子中有三轮校准（子组织、组织、高管），每一轮通常会让参与的经理花费三到五个小时。这些决定会显著影响你团队的职业发展，整个流程也是一项重大的时间投入。

随着我参与的校准越来越多，我越来越相信结果在很大程度上取决于每位经理对流程的熟悉程度。减少经理对团队评级影响的一种方法，是为新经理和刚加入的经理举办校准练习 сессия，让他们在真正影响团队结果之前先模拟跑一遍流程。

另一种方法是，作为职能高管，你要对良好的校准规范有强烈的主见。你会遇到那些在讨论自己团队时滔滔不绝、不接受异议的经理，你必须突破这种阻挠，做出正确的决定。你还会发现有些经理非常不擅长在校准会议中展示团队的工作，你应该尽量降低这对他们团队评级的影响。在任何一种情况下，你在每次校准周期中最大的贡献，就是给你的经理们反馈，帮助他们在下一轮做得更好。

虽然大多数公司使用同一组人来校准绩效评级并决定晋升，但有些公司会为晋升决策单独设立晋升委员会，尤其是针对高级职位。这种做法的优势是可以把最有上下文的人拉进来决策，例如让 Staff-plus 工程师来仲裁 Staff-plus 级别的晋升，而不是完全依赖经理。缺点是流程更重，而且往往会在经理给出的反馈与晋升委员会的最终决定之间产生差距，让整个过程显得随意。

降级

晋升的反面是降级，通常用有些模糊的委婉语“down leveling”来指代。公司通常避免谈论这个概念，也很少在正式文档中承认它的存在，但它确实是真实发生的事情。

有三种变体需要考虑：

调整薪酬的降级：例如，你的职级从 Senior Engineering Manager (L6) 降到 Engineering Manager (L5)，薪酬也相应调整到适合 L5 的水平。当然，以这种方式调整股权授予会特别麻烦。不调整薪酬的降级：如上，职级从 L6 降到 L5，但薪酬不向下调整。这对你个人是好事，但在大多数薪酬体系中，你会超过（或接近超过）原职级的薪酬带，这意味着你后续的薪酬调整会非常有限。不调整职级的职称降级：你的职称从 Senior Engineering Manager 变为 Engineering Manager (L6)，但职级（L6）保持不变。这意味着薪酬体系仍会按原方式对待你，但在组织内部你会被视为较低职级的成员，例如不会被公开视为 Senior Engineering Manager，也不会被纳入 Senior Engineering Manager 的专属讨论组等。

所有这些方式都既公平又不公平，并且会带来或重或轻的后续官僚负担。这正是大多数公司尽量完全避免降级的原因。此外，“推定解雇”（constructive dismissal）的概念意味着降级需要和解雇一样详尽的文档记录。这肯定不是一种节省时间的方法。

我曾长期完全避免降级，但后来发现降级在某些情况下是有效的。首先，有时你对新员工的定级是错误的。他们可能以 Staff Engineer (L6) 的级别入职，但实际表现只相当于 Senior Engineer (L5)。在这种情况下，你的选项要么是保留一个表现不佳的 Staff Engineer，从而破坏整个组织的职级体系——这会让后续每一次晋升讨论都更加困难——要么就把他们的职级调低。我做过相对较少的降级，但“很少”不等于“零”。我曾在自己的组织中以及直接管理的下属中实施过降级，在那些觉得直接解雇不对的情况下，每次结果都比我预期的要好。

反馈底线

在设计流程时，我认为思考你是试图提高“预期结果的下限”（最坏情况，你每年至少能得到一次 decent 的反馈），还是试图提高“上限”（最好情况，你得到改变人生的反馈），会很有帮助。很少有流程能同时做到这两点，而大多数绩效流程都专注于提高反馈的下限。这一点从绩效流程中常出现的、听起来别扭但频繁出现的建议就能看出来：绩效流程中的反馈永远不应该让当事人感到意外。

由于绩效流程通常优化为让每个人都收到一些反馈，因此不宜将其作为给团队反馈的主要机制。相反，你应该实时、持续地给予反馈，不要过多依赖绩效流程。如果你在持续给予好的反馈，那么正式流程其实帮不上太大忙。

当你的团队越来越资深时，这一点尤其正确。如果资深员工只有在绩效流程中才得到绩效反馈，那一定是哪里出了严重问题。他们应该更频繁地收到反馈。

绩效管理最棘手的场景之一，是你最终要去管理一个自己从未亲自从事过的职能。你可能对管理软件工程师的绩效很有把握，但完全不知道如何评价 Data Scientist 或 QA Engineer。当你同时管理这三类人时，就会非常棘手。

我发现有效的做法是：

这当然很困难，但不要说服自己这不可能做到。在中等规模的公司里，大多数高管都要负责自己从未直接从事过的职能。

薪酬

作为工程高管，你通常是人力团队设计的薪酬流程的消费者。在这种情况下，你的参与可能简化为审查拟议的变更、检查奇怪的决定、收集高级经理对他们团队方案的反馈，以及针对特殊情况进行个别调整。

尽管如此，我发现对这些系统通常如何运作有更多了解还是很有帮助的。下面我将介绍这类流程的一些关键方面：

公司通常通过查看从薪酬 benchmarking 公司获得的总和数据来构建薪酬带。许多数据提供商依赖公司提交自己的数据，并试图在每家公司都使用各自不一致的职级标准的情况下，构建一个可靠的数据集。你经常会被推动把这些薪酬数据当作客观事实，但要意识到底层数据集远非完美，因此基于它的薪酬决策也必然 imperfect。薪酬 benchmarking 总是针对一个自己定义的 peer group（对标群体）进行的。例如，你可能会说要对标总部位于硅谷的 A 轮公司，或者总部位于“Tier 1 市场”之外的 B 轮公司（“Tier 1”本身也是一个模糊的概念）。通过调整对标群体，你可以实现大多数薪酬目标：如果你想要更高的薪酬，就选择更有竞争力的对标群体；如果想要更低的薪酬，则反之。选择对标群体更多是一门艺术而非科学，但如果你得到的数字感觉不对劲，这是另一个需要注意的细节。一旦有了 benchmark，你通常会用 compa ratio（comparative ratio，比较比率）来讨论薪酬。某人的薪酬是其职级 benchmark 的 90%，则 compa ratio 为 0.9；如果是 110%，则为 1.1。每家公司都会有一系列用 compa ratio 描述的薪酬政策。例如，大多数公司对新员工的目标 compa ratio 大约是 0.95，对刚晋升的人则希望他们在新职级上的 compa ratio 达到约 0.9。另一个常见的例子是，公司会对某个职级设置 1.1 compa ratio 的最高上限：达到这个比率后，你的薪酬只会随着市场调整薪酬带而增加，或者只有在晋升时才会增加。每家公司都会有地理调整作为薪酬带的一部分。在美国，一个简单且常见的做法是将地区分为三个 tier——Tier 1、Tier 2 和 Tier 3——Tier 2 薪酬降低 10%，Tier 3 降低 20%。Tier 1 可能是硅谷和纽约，Tier 2 可能是西雅图和波士顿，Tier 3 是其他所有地方。当然，有些公司在这些话题上会做得更深更细，但结构上大致就是这个样子。

无论薪酬系统算出的“正确结果”是什么，最终都必须与公司实际预算进行对比。如果两者不匹配，几乎总是薪酬系统要做出调整以符合预算。在你深入优化薪酬结果时请记住这一点：如果预算不支持，再怎么调整都没有意义。

无论最终数字是多少，请记住，呈现数字的方式至少和数字本身一样重要。如果一个团队习惯了每年 5-7% 的涨幅，那么即使市场数据显示当年薪酬带有所下降，3% 的涨幅也会让他们非常不满。如果你把数字计算背后的逻辑解释清楚，就能给团队提供一个理解这些数字的框架，帮助他们接受你不得不带来的任何意外。

周期应该运行多频繁？

每个人对公司绩效周期的频率都有强烈意见。如果你一年只跑一次，人们会不满那些刚好在周期结束后入职的新员工第一年可能得不到任何正式反馈。如果你每个季度都跑，团队又会抱怨花在流程上的时间太多，即使流程本身很轻量。这种普遍的焦虑其实是一种解脱，因为它意味着没有哪种选择能让所有人都满意，所以你可以直接做你认为最有效的那种。

对大多数公司而言，我推荐一年两次。有些公司一年做两次绩效，但只做一次晋升和薪酬调整，这样可以减少整体流程协调的时间。目前没有太多证据表明更频繁的绩效评估是有价值的。

我唯一会坚定反对的是那种以每个员工的入职日期和后续周年为锚点的流程。例如，每个员工在入职周年纪念日获得一次绩效评估。这种流程非常难以协调，难以进行流程改进，也无法查看整个组织的评级、晋升或薪酬分布。它在设计上看起来很美观，但实际上行不通。

避免追求完美

在《The Engineering Executive’s Primer》中关于“工程高管在招聘中的角色”一章里，我的建议是追求有效的招聘流程，而不是完美的流程，这个建议在这里同样适用。总有办法让你的绩效或薪酬流程变得更完整，但好的流程会时刻考虑每增加一步的成本。很多只有二十人的公司给的反馈太少，但几乎所有拥有一千名员工的公司，都把大部分时间花在了绩效相关的“ artifacts”（文档、表格等）上，而这些时间本可以用来给出更好的反馈，或者直接用于业务的核心工作，而不是关于工作的元讨论。工程高管的招聘角色

作为高管，你可能是唯一有能力在“有用”和“完美”之间做出取舍的人，我鼓励你认真对待这个责任。如果你放弃这个责任，你会逐渐把中层管理变成一个官僚化的推纸头职能，而不是一个充满活力的枢纽，把公司战略转化为有效的战术。每一次 incremental 的变化可能都很小，但累积起来会产生重大影响。

如果你想快速检查一下，只需问问你的团队——尤其是那些管理经理的经理——他们对当前流程的感觉如何，你就能知道这个流程是否在有效服务他们。如果他们都形容它缓慢且痛苦，尤其是那些在多家公司见过不同流程的人，那么你就该考虑自己是否走偏了。

总结

本文介绍了你在运营和演进工程组织绩效与薪酬流程时会遇到的核心挑战。有了这些背景，你将有能力解决第一批很可能遇到的问题，但请记住，这些都是非常深刻的话题，存在大量分歧，而且十年前的许多所谓最佳实践如今已被视为坏做法。
