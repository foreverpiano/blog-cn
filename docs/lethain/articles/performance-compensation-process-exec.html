绩效与薪酬（针对工程高管）。

2023-09-03 · 阅读原文

Uber 最初的绩效流程叫做“T3B3”，极其简单：写下个人的前 3 项优势和前 3 项劣势，然后当面直接把反馈分享给他们。公司曾经长期抵制将反馈书面记录下来，认为这会阻碍诚实沟通。另一方面，Google 有大量故事讲述人们花费数月精心准备晋升材料，最终却仍未获得晋升。在同时经历过 Uber 和 Google 晋升流程的人中，既有支持者也有批评者，对于什么是理想的绩效流程，完全没有共识。

薪酬是一组微妙不同的问题，但同样不存在普遍认可的薪酬流程。高度结构化、由中央统一 orchestration 的薪酬体系往往导致同一层级的大多数人获得相似的薪酬，即使他们的实际影响差异很大。而更灵活的薪酬体系则会大幅奖励顶尖表现者，这又为偏见留下了空间。

由于在应该采用怎样的绩效或薪酬流程上没有共识，你很可能最终会在多种不同体系中工作。本文将深入探讨：

设计、运营和参与绩效与薪酬流程的人之间相互冲突的目标；如何运行绩效流程（包括校准会议）及其面临的挑战；如何有效参与薪酬流程；绩效和薪酬周期应该多久运行一次；为什么你的目标应该是建立一个有效的流程，而不是完美的流程。

每一个这样的体系都充满权衡和陷阱，你需要保持警惕。读完本文后，你应该能够为自己的组织规划出正确的应对路径。

这是 O'Reilly 出版的《The Engineering Executive’s Primer》中的一章，未经编辑。

相互冲突的目标

回到 Uber 的 T3B3 绩效流程——每半年告诉一个人他们的前三项优势和前三项劣势——最值得注意的是它的极端简洁。它完全专注于向接收者提供有用的反馈。直到今天，我仍然觉得这种目标的清晰度非常了不起，也极为罕见。

大多数绩效和薪酬体系的目标清晰度要低得多，因为它们试图平衡来自众多利益相关方的多种优先事项。一家公司的典型流程通常试图同时兼顾以下所有目标：

个人：希望获得有用的反馈以实现成长，希望尽快获得晋升，希望最大化自己的薪酬，并且希望这一切尽快完成。经理：希望为团队提供公平且有用的反馈，希望在合适的时候（并与他们对团队做出的各种承诺保持一致）为团队成员争取晋升，希望提供合理的薪酬（同样要与对团队的承诺保持一致）。哦，他们也希望这一切尽快完成！人力（或人力资源）团队：希望确保个人收到有价值的反馈，为反馈质量设立底线，将反馈记录下来以便后续在绩效管理和法律场景中支持公司的立场，需要为合规目的展示绩效流程（例如 SOC2 要求每年进行绩效评估），并创建结构化的输入用于计算薪酬。高管：基于经理们不一致的评估来决定晋升谁，在固定薪酬预算内进行优化以实现组织目标，并尽量减少经验不足或立场不一致的经理对晋升和薪酬的影响。

我从未见过或听说过任何一个流程能优雅地解决所有这些问题。我有根据的猜测是，根本不存在一个能适用于数百人的流程而不显得有些繁琐。同样，也不可能完美平衡客观、一致的结果与认可杰出个人的目标。

这些流程还有很大的改进空间，而且确实可以一直被改进，但流程中的张力源于参与者相互冲突的目标。这些冲突的目标是真实的、根本的、不可避免的，在你为流程如何运作做决策时，必须时刻牢记这一点。

绩效与晋升

我将先从绩效流程（包括晋升）开始谈起。基本的绩效流程是每位经理为自己的直接下属提供书面反馈，包括是否晋升的决定，但其中有许多细节和变体需要考虑。

首先需要考虑的变体是是否纳入同事反馈和向上反馈。向上反馈是一个受限的问题，因为每个人通常只有一个经理。最坏的情况下，收集向上反馈会产生低价值的结果，往往是因为员工不想批评自己的经理，但它并不会占用太多时间。

同事反馈可能占用大量时间，尤其是对那些人际网络很广的人，他们可能会被要求为十个或更多人提供同事反馈。通常会附带建议说，如果请求太多你可以拒绝，但许多人发现即使知道应该拒绝，也很难拒绝同事反馈请求。

更重要的是，根据我的经验，同事反馈非常不一致，我逐渐相信每个团队对同事反馈价值的信念，决定了反馈是否真正有用。我管理过觉得诚实给出同事反馈太尴尬的团队，他们提供的反馈毫无价值：在那种情况下，收集同事反馈并不值得。我也管理过狂热相信同事反馈价值的团队，他们产出了富有洞见且有价值的信息。因此，我倾向于授权经理自行决定是否为团队收集同事反馈。通常这是公司整体的政策决定，在这种情况下，我不会选择为此争执。

职级与评级标准

如果没有书面标准来描述每个职级期望的表现维度，就几乎不可能就绩效评级和谁应该晋升达成一致。不过，在讨论评级标准之前，我们得先谈谈职级。

大多数公司将职称与职级配对，例如：

Entry Level Engineer (Level 3) Software Engineer (Level 4) Senior Software Engineer (Level 5) Staff Software Engineer (Level 6)

具体职级在不同公司差异极大（有很多网站展示各公司职级的差异），某公司的“Level 3”在另一家公司可能是“60”，在第三家公司可能是“601”。各公司之间没有一致的职级标准。软件工程职级通常从“Level 3”开始，因为公司会在多个职能中使用职级，且常常把“Level 1”留给入门要求较低的初级岗位。

职称在行业内的差异甚至更大，根本不存在一个通用的标准可供采用。如果你负责为公司设定职称，我建议采用较为典型的 progression：Entry-Level Software Engineer、Software Engineer、Senior Software Engineer、Staff Software Engineer 以及 Sr Staff Software Engineer。如果你想尝试新职称，请注意其 downside 是会让招聘流程变得更复杂，因为你必须解释这些职称的含义，而且会失去一些担心非标准职称会损害自己职业发展的候选人。

一旦确立了工程团队的职称和职级，下一步就是记录评级标准（leveling rubrics），明确每个职级的运作期望（同样，有很多网站收集了各公司公开的评级标准）。这可能是一项规模很大的工作，我建议跳过最难的部分：从网上挑选一个 reasonably good 的现成版本，组建一个工作组来调整细节，然后在每次绩效周期结束后根据出现的问题进行优化。

此外，我想强调几点我多年来吃亏后学到的教训：

优先选择简洁而非面面俱到的评级标准：人们强烈希望评级标准能代表晋升的完整、清晰准则。当然，挑战在于很多人特别擅长针对具体标准“刷分”。例如，Stripe 的晋升标准包括导师制，我遇到过有人声称自己在做导师，因为他们未经请求就和别人安排了一次会议，并认为这就构成了导师制。简洁的标准需要更细致的解读，但试图刷标准的做法意味着所有实际方案都需要大量解读。你可以针对每一次刷分尝试增加更详尽的文档，但你的标准会迅速变得难以使用，更注重防止不良行为，而不是为善意的人提供清晰指导。优先选择宽泛的职类而非狭窄的职类：一个经典的高管决策是，Site Reliability Engineer 和 Software Engineer 是否应该有不同的评级标准。假设你决定是的，单独的标准会更公平。那很好！那是否也应该为 Data Engineer、Data Scientist、Frontend Engineer 和 Quality Assurance Engineer 分别准备单独的标准呢？是的，每个职能如果有自己的标准会更好，但维护标准成本很高，而且调优标准需要频繁使用它们来评估很多人。拥有更多标准通常意味着做出更多调优不足的晋升决策，并造成某些职能晋升路径更轻松的印象。我强烈建议尽可能复用和整合，尤其对于人数少于十人的团队，不要维护定制标准：无论是否引入定制标准，你在评估狭窄专业领域表现时最终都会运用特殊判断，而使用共享流程的成本更低。同时记录“如何”（行为）和“做什么”（结果）：有些标准极其关注展示某些能力，却没有明确观点要求在达成目标时符合文化价值观。我认为这是缺失，因为这意味着你可能会晋升那些有能力但以公司不希望的方式达成目标的人。评级标准——以及晋升——应该发出清晰信号，表明某人正走在公司成功的道路上，而这只有在你维持行为期望时才可能实现。

关于职级和评级标准的最后一个话题是，你应该努力让它们诚实地反映实际运作方式。许多公司有明面上的职级和晋升标准——通常围绕公平、透明等设计——但下面还有一套庞大的隐形流程在真正决定事情如何运作。尽可能把那些尴尬的部分大声说出来，让你的组织去面对现实。如果晋升受预算和业务需求限制，那么承认这一点比让团队花费时间编造一套虚构的规则来解释意外结果要好。

晋升与校准

有了职级标准，你现在可以基于事实讨论哪些人应该从一个职级跨越到另一个职级。大多数公司依靠经理提出暂定的晋升提名，然后通过校准流程来批准该提名。校准通常是一场经理会议，大家逐一讨论每个人的暂定评级和晋升决定，目的是在整个组织内做出一致的决策。

在拥有几百名工程师的组织中，常见的校准流程如下：

经理提交他们的暂定评级和晋升决定。子组织（例如“基础设施工程”）的经理们组成 5-8 人的小组一起开会，包括负责整个子组织的主管（例如其他经理向其汇报的“基础设施工程总监”），讨论子组织内所有的暂定决定。向工程高管汇报的经理们与工程高管一起开会，重新审视整个组织的暂定决定。实践中人数太多无法逐一详细审查，因此这一轮通常聚焦于晋升、顶尖表现者和最底层的表现者。工程高管会与人力团队一起审查最终决定，然后与其他高管对齐，以在各组织间保持一定程度的一致性。他们还会审查拟定的评级和晋升决定对当前公司预算的影响。

上述示例有三轮校准（子组织、组织、高管），每一轮通常会让参与的经理花费三到五个小时。这些决定会显著影响团队成员的职业发展，整个流程是一项重大的时间投入。

我参与的校准会议越多，就越相信结果在很大程度上取决于每位经理对流程的熟悉程度。减少经理对团队评级影响的一种方法是，为新经理和刚加入的经理举办校准练习会议，让他们在真正影响团队绩效结果之前，先对流程进行一次模拟演练。

另一种方法是，作为职能高管，你对良好的校准卫生习惯要有强烈的观点。你会遇到那些在会议上为自己的团队长时间辩护以阻止异议的经理，你必须突破这种拖延，克服他们的阻力，做出正确的决定。你也会发现有些经理根本不擅长在校准会议上展示团队的工作，你应该尽量减少这对他们团队评级的影响。在任何一种情况下，你在每次校准周期中最大的贡献，就是给你的经理提供反馈，帮助他们在下一次周期中表现更好。

虽然大多数公司使用同一组人来校准绩效评级并决定晋升，但有些公司会为晋升决定设立单独的晋升委员会，尤其是针对高级职位。这种做法的优势在于，你可以让最具上下文的人参与决策，例如让 Staff-plus 工程师来仲裁 Staff-plus 级别的晋升，而不是完全依赖经理。缺点是流程会更重，而且常常会在经理给出的反馈与晋升委员会做出的决定之间产生差距，让整个过程显得随意。

降级

晋升的反面是降级，通常用有些模糊的委婉语“down leveling”来指代。公司通常避免公开谈论这个概念，也很少在任何正式文档中承认它的存在，但它确实是真实发生的事情。

有三种变体需要考虑：

调整薪酬的降级：例如，你的职级从 Senior Engineering Manager (L6) 降到 Engineering Manager (L5)，薪酬相应调整为适合 Engineering Manager (L5) 的水平。当然，以这种方式调整股权授予会特别麻烦。不调整薪酬的降级：如上，职级从 Senior Engineering Manager (L6) 降到 Engineering Manager (L5)，但薪酬不向下调整以匹配新职级。这对你来说是好事，但在大多数薪酬体系中，你会超过（或接近超过）原职级的薪酬区间，这意味着你未来将只能看到非常有限的调整。不调整职级的职称降级：你的职称从 Senior Engineering Manager 变为 Engineering Manager (L6)，但职级（L6）保持不变。这意味着薪酬体系仍会按原方式对待你，但在组织层面你会被视为较低职级成员，例如不会被公开认为是 Senior Engineering Manager，不会参加 Senior Engineering Manager 的专属会议等等。

所有这些方式都是公平与不公平的混合，并且会带来或重或轻的后续官僚负担。这些官僚挑战正是大多数公司尽量完全避免降级的原因。此外，“推定解雇”（constructive dismissal）的概念意味着降级需要与解雇相同程度的文档记录。这肯定不是一种节省时间的方法。

我很长一段时间完全避免降级，但我发现降级在某些情况下是有效的。首先，有些场景是你对新员工的定级出现了错误。他们可能以 Staff Engineer (L6) 的职级入职，但实际上表现得像 Senior Engineer (L5)。在这种情况下，你的选择要么是保留一位表现不佳的 Staff Engineer，从而破坏对所有人的职级体系——这会让后续每一次晋升讨论都变得更加困难——要么就把他们的职级调低。我做过相对较少的降级，但“较少”不是“零”。我曾在我管理的组织中以及直接管理的员工中做过降级，在所有那些觉得直接解雇不合适的情况下，结果都比我预期的要好。

反馈底线

当你在设计流程时，我认为思考你是试图提升预期结果的底线（“最坏情况，你每年至少能得到一次还不错的反馈”）还是试图提升上限（“最佳情况，你得到改变人生的反馈”）会很有帮助。很少有流程能同时做到这两点，而大多数绩效流程都专注于提升所交付反馈的底线。这一点从一个尴尬但常见的建议中可见一斑：绩效流程中的反馈永远不应该让人感到意外。

由于绩效流程通常优化为确保每个人至少收到一些反馈，因此依赖它作为给团队反馈的主要机制是不明智的。相反，你应该实时、持续地给予反馈，而不要过多依赖绩效流程来帮忙。如果你已经在给出好的反馈，那么绩效流程其实帮不上太大忙。

当你的团队越来越资深时，这一点尤其正确。如果资深员工只有在绩效流程中才能得到绩效反馈，那就说明出了很大的问题。他们应该获得反馈的频率要高得多。

管理其他职能

绩效管理最棘手的方面之一，是你最终要去管理一个自己从未亲自工作过的职能。你可能在管理软件工程师的绩效上已经校准得很好，但完全没有准备好如何评估 Data Scientist 或 Quality Assurance Engineer。当你同时管理这三者时，就会觉得非常棘手。

我发现以下做法很有效：

放下你早年职业生涯中可能形成的职能偏见（例如“QA 很简单”）。不要害怕领导，即使你对该领域不太了解。你是该职能领域的高管，如果你不在职能内推动绩效，其他人也不会去做。学习该领域的基础知识：观察他们的工作流程，阅读基础文献，参加技术分享，与公司内外领域专家交流等等。在内部寻找判断力强的人作为依靠、验证想法并征求意见。选择这些人时要小心，如果你依赖团队不尊重的人，可能会适得其反。优先招聘一位能担任该领域准高管的职能负责人。最终，你永远不会有足够的时间成为你所涉及的每个领域的专家，而且随着你在更大公司担任更高级的职位，这个问题只会更加严重。

这确实很棘手，但不要说服自己说这不可能做到。在中等规模的公司里，大多数高管都要负责自己从未直接工作过的职能。

薪酬

作为工程高管，你通常会成为由人力团队设计的薪酬流程的消费者。在这种情况下，你的参与可能仅限于审查提出的变更、检查异常决定、收集高级经理对他们团队方案的反馈，以及针对特殊情况进行个别调整。

尽管如此，我发现对这些系统通常如何运作多一些上下文很有帮助，下面我将介绍这些流程的一些关键方面：

公司通常通过查看从薪酬 benchmarking 公司获取的聚合数据来构建薪酬区间。许多数据提供商依赖公司提交自己的数据，并试图在各公司使用不一致的评级标准的情况下构建可靠的数据集。你经常会被要求把薪酬数据当作客观事实接受，但要意识到底层数据集远非完美，这意味着基于该数据集的薪酬决策也必然是不完美的。薪酬 benchmarking 总是针对一个自己定义的 peer group 进行的。例如，你可能会说要针对总部位于硅谷的 A 轮公司进行 benchmarking，或者针对总部位于“Tier 1 市场”之外的 B 轮公司（“Tier 1”本身也是一个模糊的术语）。你可以通过调整 peer group 来实现大多数薪酬目标：如果你想要更高的薪酬，就选择更有竞争力的 peer group；如果你想要更低的薪酬，就反过来。选择 peer group 更像是一门艺术而非科学，但如果你得到的数字感觉不对劲，这又是一个需要注意的细节。一旦有了 benchmark，你通常会使用 compa ratio（comparative ratio 的缩写）来讨论薪酬。某人工资是其职级 benchmark 的 90%，则 compa ratio 为 0.9；如果是 110%，则为 1.1。每家公司都会有一系列使用 compa ratio 描述的薪酬政策。例如，大多数公司对新员工的目标 compa ratio 大约为 0.95，并希望新晋升的人在晋升后达到新职级大约 0.9 的 compa ratio。另一个常见例子是，公司对某个职级的最高薪酬设定为 1.1 compa ratio：达到该比例后，你的薪酬只会随着市场调整区间而增长，或者在你晋升时增长。每家公司在其薪酬区间中都有地理调整部分。在美国，一个简单且较为常见的做法是设置三个层级的地区——Tier 1、Tier 2 和 Tier 3——Tier 2 薪酬降低 10%，Tier 3 降低 20%。Tier 1 可能是硅谷和纽约，Tier 2 可能是西雅图和波士顿，Tier 3 是其他所有地方。当然，有些公司会在这两个话题上做得更深入，但结构上大致就是这个样子。

无论薪酬系统确定了什么“正确”结果，最终都必须与公司实际预算进行核对。如果两个数字不匹配，几乎总是薪酬系统做出调整以符合预算。当你深入优化薪酬结果时，请记住这一点：如果预算不支持，再多的调整都没有意义。

无论最终数字是多少，请记住，对数字的 framing（表述方式）至少和数字本身一样重要。一个习惯了每年 5-7% 增长的团队，如果只涨 3%，即使市场数据显示当年薪酬区间整体下调，他们也会非常不满。如果你解释清楚数字背后的计算逻辑，就能给团队提供一个理解这些数字的框架，帮助他们接受你必须传达的任何意外。

周期应该多久运行一次？

每个人对公司绩效周期的频率都有强烈意见。如果你一年只跑一次，人们会不满那些刚好在周期结束后入职的新员工可能在第一年得不到任何正式反馈。如果你每个季度都跑，团队又会抱怨花在流程上的时间太多，哪怕流程已经很轻量。这种普遍的焦虑其实是一种解脱，因为意味着无论你怎么选都不会让所有人都满意，所以你可以直接做你认为最有效的事。

对大多数公司而言，我推荐一年两次的流程。有些公司一年做两次绩效评估，但晋升和薪酬调整只做一次，这样可以减少整体协调流程所需的时间。目前几乎没有证据表明更频繁的绩效评估是有价值的。

我唯一会坚定反对的是那些以每个员工的入职日期和后续周年为锚点的流程。例如，每个员工在入职周年纪念日收到绩效评估。这种流程的协调非常混乱，难以进行流程改进，也无法查看整个组织的评级、晋升或薪酬的整体分布。它在设计上很美观，但实际上行不通。

避免追求完美

在《工程高管在招聘中的角色》一文中，我的建议是追求有效的而非完美的招聘流程，这个建议在这里同样适用。你的绩效或薪酬流程总能再增加一步来提升完整性，但好的流程会时刻考虑每增加一步的成本。许多只有二十人的公司提供的反馈太少，而几乎所有拥有一千名员工的公司，都把大部分时间花在绩效相关的“ artifact”（产物）上，这些时间本可以用来给出更好的反馈，或者直接用于业务本身的工作，而不是关于工作的元讨论。工程高管在招聘中的角色

作为高管，你可能是唯一有位置在有用和完美之间做权衡的人，我鼓励你严肃对待这个责任。如果你放弃这个责任，你会逐步把中层管理变成一个官僚化的文件推动职能，而不是一个充满活力的枢纽，能够将公司战略转化为有效的战术。每一次增量变化可能都很小，但累积起来会产生重大影响。

如果你想快速检查，只需要问问你的团队——尤其是那些管理经理的经理——他们对当前流程的感受，你就会知道这个流程是否有效服务了他们。如果他们都描述它缓慢且痛苦，尤其是那些在多家公司见过不同流程的人，那就值得考虑你是否走到了错误的地方。

总结

本文涵盖了你在运营和发展工程组织绩效与薪酬流程时会遇到的核心挑战。有了这些背景，你将准备好解决第一批可能遇到的挑战，但请记住，这些都是极具深度的话题，存在大量分歧，而且十年前的许多最佳实践在今天已经被视为不良做法。
