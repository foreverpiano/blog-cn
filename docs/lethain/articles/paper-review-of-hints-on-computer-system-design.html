《Hints On Computer System Design》论文书评

2009-08-21 · 阅读原文

在我个人立志成为软件工程师的历程中，读到的第一篇论文（虽然是打算评的第二篇）是Butler Lampson于1983年发表的《Hints for Computer System Design》。这是一篇极好的论文，它让我对设计复杂系统这一目标充满希望，相信这并非遥不可及，同时也更加坚定了我一个逐渐形成的看法：真正 competent 的系统设计者其实相当稀有。

这篇论文非常务实，逐一阐述了一系列关于改进系统设计的小建议。其中几乎没有严格意义上的数学内容（L. Lamport 似乎认为，将计算机系统工程排除在外的“数学”定义其实是人为缩小的），提示之间也没有严密的逻辑结构。它仅仅是一份平易近人、充满实用智慧的软件工程好主意合集。

（以下提示背后的思想来自 Lampson，提示的表述是我修改后的版本，而每条之后的评注则完全是我自己的。）

编写接口

  • Interfaces seperate clients from implementation.
  • Interfaces's are hard to design (they constitute a mini-lanaguage).
  • Inaccurate assumptions can lead to inept interfaces.
  • Interfaces should be kept as stable as possible.
  • Interfaces should not expose the secrets of the underlying implementation.
  • Don't design an interface which contains functionality you don't know how to implement.
  • Interfaces shouldn't hide power.
  • Some functionality can be left to the client (i.e. don't solve a simple client problem with a complex server solution).

定义糟糕的接口会毁掉整个项目。我再强调一次——发自肺腑地重复一遍——定义糟糕的接口会毁掉整个项目。一个设计优良的接口能为使用者屏蔽大量复杂性和挫败感，而一个糟糕的接口却能把简单的事情变复杂，把快速的事情变缓慢。

接口编写的艺术还需要更多努力才能被提炼成一门科学，而这些提示正是迈向这个目标的一个良好开端，期待能有更彻底的后续研究。

系统恢复

  • Systems must support end-to-end recovery.
  • If you support end-to-end recovery, all other recoveries are optimization.
  • Actions should be either atomic or restartable.

这三句简洁有力的话让我真正开始重新思考系统的可靠性和恢复机制，并为我当前正在开发的系统制定了更系统化的方案，也让我在未来项目的一开始就把这些基本原则构建进去。

这些理念既适用于大型设计，也适用于小型细节。对比下面两段代码就能看出差异：

# snippet one
for file in files:
    try:
        with open(file, 'r') as in:
            data = in.read()
            # do something
            os.remove(file)
    except:
        attempt_recovery(file)
# snippet two
try:
for file in files:
with open(file, 'r') as in:
data = in.read()
# do something
for file in files:
os.remove(file)
except:
attempt_recovery(files)

第一段代码将每个文件的操作变成原子操作，但在过程中删除了重要的恢复上下文（即之前所有成功处理的文件内容），导致一旦在后期遇到错误，就无法重启整个操作。

只对失败的文件尝试恢复可能效率更高，但这样就失去了从头回滚并重新执行整个过程的选项。原本可以通过回到已知的可恢复代码路径（回到起点重试）来处理，现在却不得不编写专门的恢复代码路径。

泛化与抽象

  • Do one thing, do it well.
  • Don't generalize for generalization's sake.

程序需要在抽象与具体之间保持平衡，过于偏向任何一端都会带来明显的后果。需要理解某段代码路径的人越多，我就越倾向于选择简单而非灵活和强大（尽管这两者并非必然对立，但通常确实如此）。

人们常说泛化代码通常比专注代码效率低。如果具体实现能利用对每类子问题的额外知识（比如针对字符串加法和整数加法分别做优化），那确实如此。但我常常发现，良好的抽象能让单条代码路径写得更加精心。无论哪种方式，都可能把自己钉死在墙上。

性能

  • Handle the best case and worst case seperately. Best case must behave efficiently; worst case must make progress.
  • Use static analysis.
  • Cache answers to expensive questions.
  • Use hints to speed up calculation.
  • Use batch processing.
  • Safety first, speed afterwards.

我认为这些性能建议都相当直白，只有两条例外：把最佳和最坏情况分开处理，以及使用提示（hints）。

“使用提示”的意思是，你可以利用数据集中某些高度可能但无法保证的特性，来提供更快的操作。例如，如果你知道大部分数据已经是有序的，就可以选择插入排序而不是快速排序。

规划

  • When making changes, keep a place to stand.
  • Plan to throw one away.
  • Divide & conquer.

这三条建议与我们团队过去半年左右的设计决策高度契合。我们必须大幅升级一个接口，同时还要保持旧版本完全可用。系统的某些部分已经基于对问题更清晰的理解进行了重写。

根据我迄今为止的经验，最困难的部分始终是如何把项目切分得恰到好处——既让每个人都能分到适合自己技能水平和偏好的部分，又要确保项目真正能够完成。在我看来，系统设计与理解那些实际做实现的工程师密切相关。

高阶函数

  • 把过程当作函数参数使用。

这是一条极好的建议，但其价值常常被近年来只支持面向对象编程范式的语言所掩盖。

一个我个人的例子是：在对输入数据进行流式处理时，需要根据不同输入执行不同的操作（或不同的操作顺序）。

process_stream({json, Data}) ->
    process(Data, [fun convert_to_xml/1, fun validate_xml/1, fun send_to_server/1]);
process_stream({xml, Data}) ->
    process(Data, [fun validate_xml/1, fun send_to_server/1]).
process(Data, Funcs) ->
    lists:foldr(fun(NextFun, InData) -> NextFun(InData) end, Data, Funcs).

这带来了一种简洁、简单且可组合的流处理机制，未来修改起来也非常容易。当然不传函数作为参数也能实现，但这种方式相当干净优雅。

不过，Lampson当时真正想到的可能更接近编写一个通用的 filter 函数，并传入一个谓词函数作为参数。

def my_filter(lst, filter_fun):
    new_lst = []
    for obj in lst:
        if filter_fun(obj):
            lst.append(obj)
    return new_lst
filtered = my_filter([1,2,3,-1,5,-3,0], lambda x : x > 0)

这是一种非常实用的工具函数模式。

参考文献中值得一读的好东西

浏览参考文献时，有几篇论文看起来颇有价值，我以后会去找来读。不过我还没有读过这些论文，所以我的乐观可能站不住脚；如果你已经读过其中某一篇并且觉得一般，请指出我的疏漏。

最后感想

正如我在开头所说，这是一篇了不起的论文。它对普通开发者非常易读，提供了大量发人深省的想法，而且作者是一位极为成功的工程师。回顾这些提示，几乎每一条都直接对应了我团队在工作中已经做出或正在做出的决策。那些我们当初做出相反选择的地方，后来往往变成了泥沼般的代码坑。

这篇论文对经验丰富的开发者可能深度不够，但它的广度很大，非常适合作为软件工程决策的检查清单。
