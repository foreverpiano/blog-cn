口语、Blub 与便利性

2008-05-25 · 阅读原文

许多程序员都读过 Paul Graham 的文章《Beating the Averages》，该文提出了一套编程语言层级理论。习惯使用某种无法提供特定功能的编程语言的程序员，很难想象这种功能到底有什么用。毕竟，没有这个特性他们也一直过来了，所以它不可能那么重要，对吧？

用 Graham 的话来说：

只要我们假设中的 Blub 程序员是在向下看能力谱系，他就知道自己在俯视。比 Blub 弱的语言显然能力较弱，因为它们缺少他习惯使用的某些特性。但当这位假设中的 Blub 程序员反过来向上看能力谱系时，他却没有意识到自己在仰视。他看到的只是些奇怪的语言。他很可能认为这些语言和 Blub 的能力大致相当，只是额外添加了一堆乱七八糟的东西。对他来说 Blub 就足够好了，因为他是用 Blub 的思维方式思考的。

我认为还没有得到足够重视的一点是：这一推理同样以一种有趣的方式适用于人类自然语言。不同的口语在某些类型的表达上各有专长。英语是一种对时间极为执着的语言，拥有未来时、过去时、现在时、完成时、进行时等丰富时态。但英语在表达礼貌程度方面不如西班牙语或法语精确，后两者都将敬语形式融入到了动词变位中。而日语则比大多数西方语言更精确地规范了敬语体系。

日语与英语的另一个显著区别是它没有将来时：“我将要去学校”和“我去学校”的表达方式完全相同。不过，日语非常擅长表达情感上的细微差别，并且有一些小技巧来谈论时间相关的事件（比如 ototoi、asatte、saraisyuu，分别表示“前天”“后天”“下下周”——这些词真的非常好用，我希望英语也有对应的词汇）。

稍稍退后一步，让我们把 Graham 关于 Blub 语言的论点应用到口语的比较上。具体来说，我们是否能为口语之间建立一个能力层级？这是一个很难展开的思想实验，很大程度上是因为每种语言都有自己擅长的领域（礼貌、时间、情感细微差别等等），因此我们的能力层级将完全取决于我们如何定义“能力”。我们很容易论证英语比日语更强大——如果讨论的是时间的话——但只要改变“能力”的定义，我们很快就能把这个结论反转过来。

然而，我认为我们可以在现代意大利语和拉丁语之间提出一个相当清晰的能力层级。意大利语非常像拉丁语，只是它已经丢失了拉丁语的许多时态和复杂语法结构。正如 Lisp 悲剧性地败给了能力较弱的后继者并让自己的思想被后者吸收一样，拉丁语的结构和语法深度也让位于它那些能力较弱的子女（罗曼语族）。

为什么更强大的方案会被拒绝，转而选择能力较弱的？原因和拉丁语逐渐被人弃用一样：在达到一定程度之后，拥有更强大能力带来的好处（以及成本）会被便利性所超越。程序员们之所以蜂拥转向 Python 而不是 Common Lisp，是因为 Python 已经足够强大，而且便利得多。现代软件开发中大量的工作都是处理技术上相对简单的事情，额外能力带来的收益并不值得去忍受繁琐的包管理、别扭的字符串处理，或是各种实现之间差异导致的混乱。

在 CL 的不便之处得到解决之前，它在能力层级中的位置其实并不重要。如今所有被广泛使用的语言，对于它们所面对的常见任务来说都足够强大，而那些正在获得心智份额的语言，靠的是更便利，而不是更强大。

新兴的、希望成为主流的语言，必须首先在便利性上竞争，其次才是能力。这就是为什么我们看到大量基于 JVM 的语言涌现——它们借助现有的 Java 库和广泛部署的 JVM，即使自身渗透率不高也能提供极大的便利——这也是为什么那些没能照顾到便利性的语言会举步维艰，即便它们明显比当前流行的语言强大得多。

日语有普通语、礼貌语以及三种额外的敬语变体。通常日语教材会用部分重叠的圆圈来开始讲解，然后就越来越复杂了。↩ 网页服务通常编程都相当简单。扩展性这类难题需要特定领域的专业知识，但实际的代码实现很少成为瓶颈。许多桌面应用也是如此。虽然投入了大量工作和细节，但代码本身并不 inherently 困难。↩ ASDF 和 ASDF-INSTALL 是非常可用的工具，但它们缺乏 Python 的模块和 easy_install 那样的简洁性。↩ 也许我们已经被 Python、Ruby 和 Perl 这些以字符串为中心的语言宠坏了，但在 Common Lisp 中处理字符串要痛苦得多。↩ Common Lisp 实现之间的不一致，似乎是使用 CL 时几乎所有问题的根源。如果能持续积极地制定更新的 Common Lisp 规范，或许可以避免这种命运，但现在这已经成为一个相当致命的缺陷。当然，完全有可能开发出在大多数实现上都能良好运行的 CL 软件，但这种不便在近年来流行的语言中根本不存在——它们都只有一种官方实现。值得注意的是，这些语言也都有衍生项目在创建非官方实现（比如 JRuby for Ruby、Jython for Python 等等），但那些项目都把官方实现当作规范，因此它们有一个经常更新的规范可以跟踪，而不是一个不完整且过时的规范。↩ 这对 Python 这样的通用语言成立，对 Erlang 这样的特定领域语言也同样成立。我认为我们会看到更多在各自细分领域极为便利的领域特定语言（比如 PHP、Erlang），但要开发出比当前这一代明显更便利的通用语言将会非常困难。不过，押注变化不发生从来都是危险的，尤其是在编程语言这样一个充满变革历史的技术领域。沿着这个思路，我认为 Nu 语言会找到一个健康的小众市场，但它不太可能在与 Objective-C 共生关系之外独立存活。↩
