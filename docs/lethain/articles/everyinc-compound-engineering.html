从 Every 的复合工程中学习

2026-01-19 · 阅读原文

我使用的少数原生 AI 产品之一是 Cora.computer，它能为我总结个人的邮件收件箱。虽然它并不完美，但比我之前用的一堆过滤规则能更好地处理源源不断涌入的垃圾邮件和非 solicited 邮件。

我在使用 Cora 时遇到了一些问题，后来就去关注 Every 的团队成员来反馈这些问题。最近这让我看到了他们在复合工程（Compound Engineering）方面的工作，特别是 compound-engineering-plugin 这个项目。

复合工程包含两个极为知名的模式、一个中等知名的模式，以及一个很多从业者已经隐约感觉到但尚未找到一致实现机制的模式。这些模式分别是：

Plan（规划）是将实现与研究解耦。这一点已被广泛理解，比如 Claude 的 plan 模式，不过如果能更明确地指定要参考哪些资源（规格、PRD、RFC、Issue 等），效果会更好。Work（执行）是按照规划去实现。这一点也被广泛理解，是 agentic coding 的核心。同样，它可以做得更好或更差，但更多取决于你的代码库质量、测试和持续集成流水线，而不是 agent 本身。Review（评审）是让 agent 根据你的最佳实践来审查变更，并找出可以改进的地方。我认为大多数从业者都有某种形式的评审，但标准化程度很低，即使在一家公司内部也是如此。Compound（复合）是让 agent 将从特定任务中获得的经验总结成定义良好、结构化的格式（本质上就是一个 wiki），供后续的 plan 步骤参考。Compound 步骤与 Plan 步骤之间的这种互动，就形成了「复合」机制。很多从业者都在无意识地进行复合，但通常是靠自己手动完成。例如，我经常会让 agent 根据任务中遇到的具体问题去更新我们的 AGENTS.md 或技能库，但这需要我主动留意问题并建议将其纳入。

将这四个步骤放在一起并不令人惊艳，但却是一种极其有效的方式，能将这些凭直觉形成的最佳实践转化为公司内部具体、可执行、且基本自动化的机制——只需要增加几个命令（例如 workflow:plan、workflow:review 等），并更新 AGENTS.md 来指导 agent 在何时以及如何使用这些命令。

在 Imprint 的前端和后端 monorepo 中实现这个过程非常顺利，大约花了一个小时。大部分时间都花在最后一步的细节打磨上，比如我们希望把规划文件存成 .claude/plan-*.md 格式，以匹配现有的 .gitignore 规则，但整体都不复杂。最重要的是，这解放了一个让公司很多工程师（包括我）一直在寻找标准方案的话题。现在我们有了统一的方法，可以去解决下一个问题了。

如果最近的历史可以作为参考，那么可以很有把握地预测：复合工程中的许多实践将在未来几个月内被吸收到 Claude Code 和 Cursor 的底层框架中。到那时，显式使用这些技巧与完全不知道自己在使用它们的人将变得无法区分。但我们拭目以待。在此之前，这仍是一个成本低、收益高的实验，你可以在一小时内就把它实现起来。
