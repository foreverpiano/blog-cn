API 弃用的系统模型

2025-04-24 · 阅读原文

在 一文中，诊断结果基于这样一个论点：API 弃用是导致客户流失的重要原因。虽然内部数据可以用来关联弃用与流失的关系，但构建一个模型来帮助我们判断这种相关性是否等同于因果关系，同样极具价值。Stripe 应该如何废弃 API？(~2016)

本章将介绍以下内容：

  1. What we learn from modeling API deprecation’s impact on user retention
  2. Developing a system model using the lethain/systems package on GitHub. That model is available in the lethain/eng-strategy-models repository
  3. Exercising that model to learn from it

是时候深入调查，判断 API 弃用是否确实对用户留存和流失产生重大影响。

本章选自《Crafting Engineering Strategy》。

核心发现

在一个每轮 baseline churn 为 10% 的初始模型中，将每轮遇到 API 弃用的客户比例从 50% 降低到 10%，仅使稳定状态下的集成客户数量增加了约 5%。

然而，如果我们完全取消 baseline churn，则会看到 10% 和 50% API 弃用率之间存在巨大差异。

这个模型最大的启示是：仅仅消除因 API 弃用导致的流失，并不会显著增加集成客户的数量。但如果不同时减少 API 弃用，我们也无法充分受益于 baseline churn 的降低。要实质性地增加集成客户数量，必须同时降低这两种类型的流失。

草图

我们先从模型最理想的路径开始画起：潜在客户流入成为 engaged customers，然后转变为 integrated customers。这代表一位决定与 Stripe API 集成并成功完成集成流程的客户。

如果整个问题空间仅限于此，业务会非常理想。不幸的是，客户偶尔还是会流失。这种流失通过两种方式体现：

  1. baseline churn where integrated customers leave Stripe for any number of reasons, including things like dissolution of their company
  2. experience deprecation followed by deprecation-influenced churn, which represent the scenario where a customer decides to leave after an API they use is deprecated

此外还有一个再集成（reintegration）的流程，受到 API 弃用影响的客户可以选择更新自己的集成以符合新的 API 变更。

将所有部分组合起来，最终的草图包含五个存量（stock）和六个流量（flow）。

你可以想象为模型添加更多动态，例如流失客户的恢复，但这些因素不太可能显著改变我们对 API 弃用如何影响流失的理解。

分析

在获取客户方面，最重要的流量是客户获取和初始 API 集成。优化这些流量将增加现有集成的数量。

驱动流失的流量包括 baseline churn，以及 API 弃用与弃用影响流失的组合。对于支付 API 来说，降低 baseline churn 非常困难，因为许多流失客户是因为公司解散。从收入加权的角度来看，baseline churn 主要由非技术因素驱动，尤其是定价。无论哪种情况，要影响这个流量都极具挑战性，且往往需要显著降低利润率。

另一方面，工程决策对 API 弃用的数量以及迁移后重新集成的难易程度都有重大影响。由于支持重新集成的相关工作也能改善首次集成体验，这是一个非常值得投入的 promising 机会。

模型

你可以在 GitHub 上找到这个模型的完整实现，如果你想查看完整模型而非这些突出显示的片段。

现在我们已经确定了最值得实验的方向，是时候开发模型来评估哪些流量最具影响力了。

我们最初的模型参数设定为：

# User Acquisition Flow
[PotentialCustomers] > EngagedCustomers @ 100
# Initial Integration Flow
EngagedCustomers > IntegratedCustomers @ Leak(0.5)
# Baseline Churn Flow
IntegratedCustomers > ChurnedCustomers @ Leak(0.1)
# Experience Deprecation Flow
IntegratedCustomers > DeprecationImpactedCustomers @ Leak(0.5)
# Reintegrated Flow
DeprecationImpactedCustomers > IntegratedCustomers @ Leak(0.9)
# Deprecation-Influenced Churn
DeprecationImpactedCustomers  > ChurnedCustomers @ Leak(0.1)

这些数值是否合理，主要取决于我们如何定义每一轮的时长。如果一轮代表一个月，那么假设一半的集成客户会遇到 API 弃用就显得过于极端。如果假设一轮是一年，那么这个比例仍然偏高，但确实有一些 API 提供商经常以这个频率进行弃用。（根据我的个人经验，我可以确信 Facebook 的 Ads API 在 2012-2014 年期间至少每个季度都会弃用一个重要字段。）

诚然，对于支付 API 来说这个比率偏高，主要目的是与下面练习部分中更合理的值形成对比。

模型演练

我们运行这个模型的目标是理解 API 弃用对客户流失的影响程度。我们将从绘制初始 baseline 开始，然后逐步与各种场景进行比较，直到我们对曲线的变化建立直觉。

初始图表在大约四十轮后趋于稳定，维持约 1000 个集成客户和 400 个正在处理已弃用 API 的客户。现在我们将“experience deprecation”流量调整为影响更少的客户：

# Initial setting with 50% experiencing deprecation per round
IntegratedCustomers > DeprecationImpactedCustomers @ Leak(0.5)

# Less deprecation, only 10% experiencing per round
IntegratedCustomers > DeprecationImpactedCustomers @ Leak(0.1)

做出这些修改后，我们可以对比两种场景。

降低弃用率显著减少了任意时刻正在处理弃用问题的公司数量，但对提升集成客户的稳定状态数量影响相对较小。这意味着必然有另一个流量在显著影响集成客户这个存量的大小。

由于影响该存量的另一个流量只有 baseline churn，因此接下来我们要对它进行演练。让我们把 baseline churn 流量设为零，并与初始模型进行对比：

# Initial Baseline Churn Flow
IntegratedCustomers > ChurnedCustomers @ Leak(0.1)

# Zeroed out Baseline Churn Flow
IntegratedCustomers > ChurnedCustomers @ Leak(0.0)

这些结果有力地表明 baseline churn 的影响远远超过弃用。在没有 baseline churn 的情况下，集成客户数量稳定在约 1750 左右，而初始模型仅为约 1000。

接下来，让我们对比两个没有 baseline churn 的场景：一个具有高 API 弃用率（50%），另一个具有低 API 弃用率（10%）。

在没有 baseline churn 的两个场景中，我们可以看到 10% 的 API 弃用率最终会带来约 6000 个集成客户，而 50% 弃用率仅为 1750。更重要的是，在 10% 的场景中，集成客户的曲线没有显示出趋于平缓的迹象，而是会随着时间持续增长而非稳定。

这里的 takeaway 是：大幅降低 baseline churn 或 API 弃用中的任意一项，都会显著放大降低另一项所带来的收益。这些结果也再次强调了将降低流失视为系统层面的优化，而非仅仅一系列独立改进的重要性。
