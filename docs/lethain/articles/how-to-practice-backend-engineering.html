如何练习后端工程

2020-06-20 · 阅读原文

最近一次通话中，我和别人聊了软件工程中的后端职位，以及这个职位上的人们实际都在做什么。不只是他们具体做什么，更重要的是，你要如何练习这类工作，或者如何为面试做准备？

相比普通工程师可能会被要求承担的工作，后端工程师需要承担的工作中，有三类任务在我看来既常见又适合拿来练习：

数据建模与重构——如何为你的应用设计一个有效的数据模型，并在需求随时间变化时不断演进它？设计和演进接口——其他组件如何与你的服务集成？集成外部 API——如何将你的应用与 Twilio、Stripe 等第三方 API 集成？扩展容量——如何随着负载增长逐步演进你的架构？

在本文末尾，我为上述每个主题收集了一些书籍和博客，如果你习惯通过阅读来学习，它们可能会对你有帮助。同时，我也想设计一个项目，让大家可以用来实际练习这些技能。

关于学习项目的说明

在开始这个项目之前，我想先分享几点我认为能让这类项目更有效的通用建议：

这不是唯一的学习方式——我想先说明，这类学习项目对我一直很有效，但学习方法因人而异，而且这个项目特别耗时。缩小专注范围——不要试图一次学习太多新东西。例如，如果你主要想练习集成外部 API，那就用你已经熟悉的编程语言。这对后端和基础设施类的项目尤其重要，因为你很容易把所有时间都花在调试 Dockerfile 或 Vagrant 配置上，却一直没进入真正想学习的核心内容。使用代码仓库——用 GitHub 之类的工具保存代码，这样以后可以随时回头查看。自己真正理解的、可运行的代码示例是极好的调试和复习工具。使用临时环境——在自己笔记本电脑上开发完全没问题，但如果你能用 DigitalOcean Droplets（每月 5 美元）或 Amazon Lightsail（每月 4 美元）这类便宜的服务，就能避免花费时间去修复本地环境，而且如果出了严重问题，也可以直接删掉一切重新开始。Glitch 也是个不错的选择，不过做扩展性练习时不推荐使用它。

项目定义

对于这个项目，我会列出一系列步骤，并说明每个步骤希望达成的学习目标。这些步骤我故意写得比较模糊，方便你自己去探索和发挥。

脚手架搭建——把基础组件准备好 在 GitHub（或你选择的代码托管平台）上创建一个仓库，为这个新项目做准备，并用你熟悉的框架搭建一个 HTTP 服务。如果你用 Python，可以选择 Flask，在“/”路径上添加一个端点。 在仓库内创建一个名为“client”的目录，存放调用你服务的 HTTP 客户端。如果你用 Python，可以使用 requests 库。它应该能够调用你的“/”端点并打印出响应。 为 HTTP 服务添加一个你选择的数据库，创建一个表，并把所有对“/”的请求都写入这个表。你可以选择 SQLite、MySQL 或 PostgreSQL。 演进数据模型和接口——对已有应用进行迭代 更新你的服务，提供两个端点：一个用于发送消息，另一个用于获取最近发送的消息。API 应该支持指定要获取的最近消息数量。 更新客户端以使用这两个新端点。客户端应该能够发送和获取消息。 更新服务，让它能返回某个时间点之后发送的消息。例如“今天早上 10 点之后的所有消息”。这需要给数据模型增加一个新列，并在创建新消息时记录时间。同时你要想好如何把已有的消息迁移过去。你是给现有消息默认设置为当前时间吗？尽量不要直接删掉旧表，数据的迁移是这个练习的重要部分。 [Bonus 任务] 增加一个 API，支持对已有消息进行回复，并支持在返回某条消息时同时返回它的所有回复。更新客户端，让回复以不同方式展示，以便能区分哪些是回复消息，以及它们回复的是哪条消息。 集成外部 API——增加第三方集成 集成 Twilio，让你可以通过发短信的方式添加消息，就像通过客户端创建消息一样。 [Bonus 任务] 创建一个 Slack 应用，支持通过 Slack 向你的服务发送和获取消息。我去年写过一篇笔记 在 GCP 上用 Python 创建 Slack 应用。 扩展容量——如何演进你的服务以支持更高负载？ 下载 Locust 并配置它对你的服务产生压力。设置三种不同的负载测试：只读、只写，以及 50% 读 + 50% 写的混合负载。 对你的服务运行“仅读”负载测试。它能承受多大的规模？你如何找出时间主要花在哪里（提示：搜索“性能分析”）？如何修改服务以支持更高负载（提示：一个简单的初始方案是使用内存缓存，但一定要考虑缓存失效的问题）？ 对你的服务运行“仅写”负载测试。它能承受多大的规模？你如何保护整个服务的稳定性，避免被过多写操作压垮（提示：搜索“限流”）？ 对你的服务运行“读写混合”负载测试。它能承受多大的规模？你还能采用哪些其他技术来提升扩展性？是服务端慢还是数据库慢？你是怎么判断的？写一份清单，列出你可以用来判断瓶颈在哪以及如何解决的手段。（真正去实施这些修复可能会让你在托管费用上花费超出预算，所以不实际动手也没关系！）

完成上面所有步骤，应该能让你对从零创建一个应用、持续演进并维护它的整个生命周期有一个相当有代表性的认识。如果你觉得这些太简单，可以尝试引入新元素，比如换一个新的数据库、增加更多种类的负载、给 API 增加更复杂的需求等等。

推荐资源

除了这类实践项目，还有一些资源可能对你有帮助：

《Designing Data-Intensive Applications》——这本书最近很火，许多人都强烈推荐它作为设计和扩展应用的基础读物。 构建可扩展系统的架构导论——我写的一篇博客，总结了 Web 可扩展性的各种技术。 搞定你的架构面试——我写的另一篇博客，讨论了架构面试中可以使用的策略。 《Building Scalable Websites》——这本书现在看来有些过时，但它曾是我学习 Web 可扩展性的入门读物。如果你不想读《Designing Data-Intensive Applications》这样的大部头，它会比较容易上手。 《Web Scalability for Startup Engineers》——我自己没读过，也没见过太多人读过，但从我快速查阅和书评来看，它像是《Building Scalable Websites》的更新版本，值得一看。
