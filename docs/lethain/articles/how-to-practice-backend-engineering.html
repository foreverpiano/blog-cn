如何练习后端工程

2020-06-20 · 阅读原文

最近一次通话中，我和别人聊到软件工程中的后端职位，以及从事这些职位的人实际都在做什么。除了了解他们在做什么之外，更重要的是：你该如何练习这类工作，或是为面试做准备？

对比后端工程师常被要求承担的工作与普通工程师可能会接手的工作，我认为有三类任务既常见又适合练习：

数据建模与重构——如何为你的应用设计一个高效的数据模型，并在需求随时间变化时对其进行演进？设计与演化接口——其他组件如何与你的服务集成？集成外部 API——如何将你的应用与 Twilio、Stripe 等第三方 API 集成？扩展容量——如何随着负载增长演进你的架构以支撑更多流量？

在本文末尾，我为上述每个主题收集了一些书籍和博客文章，如果你习惯通过阅读学习可能会很有帮助。同时，我也想整理一个项目，让大家能够实际练习这些技能。

关于学习项目的说明

在开始这个项目之前，我想先分享几点我认为能让这类项目更有效的通用建议：

这不是唯一的学习方式——我想先说明，这类学习项目对我一直很有效，但学习方法有很多种，而且这个项目特别耗时。缩小专注范围——不要试图一次性学太多新东西。例如，如果你重点想练习集成外部 API，那就使用你已经熟悉的编程语言。这对后端和基础设施类项目尤其重要，因为你很容易把所有时间都花在搞定 Dockerfile 或 Vagrant 配置上，却一直没机会去学你真正关心的内容。使用代码仓库——用 GitHub 之类的工具存储你的代码，这样随着时间推移你能积累可供参考的例子。能看懂的工作代码是极好的调试和复习工具。使用临时环境——在自己笔记本电脑上开发完全没问题，但如果能用 DigitalOcean Droplets（每月 5 美元）或 Amazon Lightsail（每月 4 美元）这类便宜的服务，你就可以避免花时间维护本地环境，而且如果出了严重问题也能直接删掉一切重来。Glitch 也是个不错的选择，不过做扩展性练习时不推荐使用它。

项目定义

关于项目本身，我会列出一系列步骤以及每个步骤希望达成的学习目标。我故意写得比较模糊，让你有空间自己探索和发挥。

脚手架搭建——把基础组件准备好 在 GitHub（或你常用的代码托管平台）上创建一个新仓库，用你选择的框架搭建一个 HTTP 服务。如果你用 Python，可以选 Flask，在“/”路径上加一个端点。 在仓库里再创建一个名为“client”的目录，存放调用你服务的 HTTP 客户端。如果你用 Python，可以使用 requests 库。它应该能调用你的“/”端点并打印出响应。 给 HTTP 服务添加一个你选择的数据库，创建一个表，把所有对“/”的请求都写入这个表。你可以选择 SQLite、MySQL 或 PostgreSQL。 演进数据模型和接口——演化一个已有的应用 修改服务，增加两个端点：一个用于发送消息，另一个用于获取最近发送的消息。API 应该支持指定要获取最近几条消息。 更新客户端以使用这两个新端点。客户端应该能发送和获取消息。 修改服务，让它能返回某个时间点之后发送的消息。例如“今天早上 10 点之后的所有消息”。这需要给数据模型新增一列，并为新消息记录创建时间。你还需要制定一个方案来迁移已有的消息——是给现有消息默认当前时间吗？尽量不要直接删掉旧表，迁移数据是这个练习的重要部分。 [附加任务] 增加一个 API，支持对已有的消息进行回复，并支持在返回某条消息时同时返回它的所有回复。更新客户端，让回复的展示方式不同，以便能区分哪些是回复，以及它们回复的是哪条消息。 集成外部 API——增加第三方集成 集成 Twilio，让你可以通过发短信来添加消息，就像通过客户端创建消息一样。 [附加任务] 创建一个 Slack 应用，让你可以通过 Slack 向你的服务发送和获取消息。我去年写过一篇笔记 。 扩展容量——如何演进你的服务以支撑更大负载？ 下载 Locust 并配置它对你的服务产生负载。设置三种不同的负载测试：只读、只写，以及 50% 读 + 50% 写的混合。 对服务运行“仅读”负载测试。它能承受多大的规模？你如何找出大部分时间花在了哪里（提示：搜索“性能剖析”）？如何修改服务来支撑更大负载（提示：一个简单直接的办法是加入内存缓存，但一定要考虑缓存失效问题）？ 对服务运行“仅写”负载测试。它能承受多大的规模？你如何保护整个服务的稳定性，避免被过多写请求压垮（提示：搜索“限流”）？ 对服务运行“读写混合”负载测试。它能承受多大的规模？你还能用哪些其他技术来提升规模？瓶颈是在服务端还是数据库？你是怎么判断的？写一份清单，列出你会用哪些指标来判断，以及如何解决。（真正去实施这些优化可能会让你在服务器托管上花掉超出预算的钱，所以不实际动手也没关系！）在 GCP 上用 Python 创建 Slack 应用

完成上面所有步骤，应该能让你对从后端工程师视角创建、演化和维护一个应用的全生命周期有一个比较具象的了解。如果你觉得这些太简单，可以尝试引入新元素，比如换一个数据库、增加更多种类的负载、给 API 添加更复杂的需求等等。

推荐资源

除了这类实践之外，还有一些资源可能会对你有帮助：

《Designing Data-Intensive Applications》——这本书最近很火，很多人都强烈推荐它作为设计和扩展应用的入门读物。 构建可扩展系统的架构导论——我写的一篇博客，总结了 Web 可扩展性的各种技术。 搞定你的架构面试——我写的另一篇博客，讨论了架构面试中可以使用的策略。 《Building Scalable Websites》——这本书现在已经比较老了，但它是我最早接触 Web 可扩展性的入门读物。如果你不想读太厚的书，会觉得它非常平易近人。 《Web Scalability for Startup Engineers》——我自己还没读过，也不熟悉别人读它的反馈，但从我快速查阅和评论来看，它像是《Building Scalable Websites》的更新版本，值得一看。
