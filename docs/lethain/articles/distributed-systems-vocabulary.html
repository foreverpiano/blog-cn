分布式系统词汇表

2019-08-11 · 阅读原文

最近我花了不少时间讨论分布式系统是如何失效的，以及防止这些失效的策略。而缺乏一套共享的词汇体系，成为了高带宽沟通的重大障碍。

鉴于我接下来打算在这个领域写更多内容，我整理了这份自己认为最有效的词汇表。希望它本身就能提供价值，最坏的情况也是让我以后不用反复解释基础定义！

想要原始资料？当然可以！

CAP Twelve Years Later: How the “Rules” Have Changed, Brewer；Harvest, Yield, and Scalable Tolerant Systems, Fox, Brewer；The Transaction Concept: Virtues and Limitations, Gray；BASE: an ACID Alternative, Pritchett；Keeping CALM: When Distributed Consistency is Easy, Hellerstein, Alvaro；Eventually Consistent, Vogel；还有更多我最喜欢的一些技术论文。

CAP：一致性、可用性、分区

任何关于分布式系统的讨论，都要从 CAP 定理开始。该定理认为，你只能同时拥有以下三个属性中的两个：

一致性（C）：相当于拥有一份始终最新的数据副本；该数据的高可用性（A）（支持更新）；以及对网络分区的容忍度（P）。

需要注意的是，原作者后来强调“‘2 of 3’的说法有误导性”，特别是因为：（1）生产系统会在一致性和可用性之间做出许多不同的独立选择（而不是一个全局选择）；（2）“这三个属性都比二元选择更具有连续性。”

对一致性和可用性连续性的最有价值的探讨之一，是《Harvest, Yield and Scalable Tolerant Systems》。

Harvest 和 Yield

Fox 和 Brewer 撰写了《Harvest, Yield, and Scalable Tolerant Systems》，进一步细化了 CAP 的思想，以更好地应对其属性的非二元特性。

Yield 是完成请求的概率（也就是通常所说的可用性指标）；Harvest 则是响应中返回的数据量占理想情况下应返回数据量的比例。

使用这套词汇，我们可以更细致地讨论可用性权衡。例如，搜索引擎始终返回结果，但在某个节点不可用时可能不包含全部结果，这种情况被称为“harvest 降级”。

它还引入了正交机制的概念，主张移除系统间所有的运行时接口，转而依赖编译时接口，让它们能够独立运行。一个现实例子是在编译时构建一份最常用内容的静态缓存，定期重建并分发，而不尝试实时更新缓存。（这实际上就是本博客的工作方式——每个实例都拥有自己完整的数据快照，并定期拉取更新。）

ACID

ACID 由 Jim Gray 在 1981 年的论文《The Transaction Concept: Virtues and Limitations》中提出，它描述了一个事务的四个核心特性：

原子性（Atomicity）—— 要么全部变更发生，要么全部不发生；一致性（Consistency）—— 事务不能将数据库带入非法状态（注意这与 CAP 中的一致性含义有很大不同）；隔离性（Isolation）—— 并发执行不会改变结果；持久性（Durability）—— 变更在故障后依然有效。

这正是大多数 SQL 数据库（如 MySQL 和 PostgreSQL）所采用的模式，也被部分（但远非全部）NoSQL 数据库采用（例如 Neo4j 就遵循 ACID）。

BASE

BASE 是 ACID 的一种替代方案：

BASE 与 ACID 截然相反。ACID 是悲观的，在每个操作结束时强制保证一致性；而 BASE 是乐观的，它接受数据库的一致性会处于不断变化的状态。

BASE 中的字母分别代表：

Basically Available（基本可用）—— 通过优先 Yield 而非 Harvest 来提供 CAP 中的可用性；Soft state（软状态）—— 状态会随着时间因变更而演化，不存在某个时间点的“绝对正确”版本；Eventually consistent（最终一致性）—— 如果不再有新的更新，状态最终会达成一致。

许多 NoSQL 数据库都遵循这一模型，例如 Cassandra、Datomic、Dynamo、Riak 等等。

想了解更多细节的话，Brewer 的演讲《Towards Robust Distributed Systems》也是很好的资源。

CALM

最近我越来越多地听到 CALM，即 Consistency as Logical Monotonicity（一致性即逻辑单调性），其详细阐述见《Keeping CALM: When Distributed Consistency is Easy》。它的核心定理是：

一个程序若且仅若它是单调的，才能拥有一个一致的、无需协调的分布式实现。

Adrian Colyer 对《Keeping CALM》的总结是非常棒的补充阅读（他的所有总结都值得一看）。

可用性配置

可用性配置包括：

Active-active（双活）指请求可以被路由到任意节点并被正确处理；Active-passive（主备）指请求总是被路由到单个活跃节点，但在当前活跃节点出现问题时，能快速选举出一个新的活跃节点。

还有另一套使用“hot”、“cold”和“warm”的表述方式，有时“hot”表示“active”，“cold”表示“passive”。但这些术语有时也被用来描述数据访问频率，比如 Amazon S3 Glacier 提供的“cold storage”（冷存储）用于不经常访问的数据。

为避免混淆，我建议用“active”和“passive”来描述可用性特性，而用“hot”、“warm”和“cold”来描述数据访问频率。

算法

经常被提及的算法包括：

Paxos 是最早的分布式共识算法，其改进版本被 Chubby 以及许多其他系统采用（Zookeeper 的 ZAB 也与 Paxos 类似）；RAFT 是一种更简单的共识算法，被 Consul 采用；SWIM 是一种用于组成员管理的分布式 Gossip 协议（例如确定缓存环的成员等）；Two-phase commit（两阶段提交）是一种实现原子性分布式提交的协议。

一致性级别

来自 Werner Vogel《Eventually Consistent》的一致性级别定义如下：

Strong consistency（强一致性）—— 更新完成后，所有后续操作都能正确使用新值；Weak consistency（弱一致性）—— 更新完成后，后续操作可能无法正确使用新值；Eventual consistency（最终一致性）—— 如果不再对对象进行新的更新，最终它会返回正确的值；Inconsistency window（不一致窗口）—— 从更新发生到系统保证返回正确值之间的时间段；Casual consistency（因果一致性）—— 一旦某个更新版本被传递给一个进程，就保证不会再使用旧版本；Monotonic read consistency（单调读一致性）—— 类似于因果一致性，但从接收进程的角度看：一旦进程看到某个版本，就永远不会再使用旧版本；Monotonic write consistency（单调写一致性）—— 同一个进程内的写操作会被串行化；Read-your-writes consistency（读己之写一致性）—— 写操作之后的读能返回更新后的版本；Session consistency（会话一致性）—— 在同一个会话内，写之后的读总是正确的；Read level、write level 和 replica level 指的是分布式存储系统中参与读、写和复制某个数据的节点数量。Dynamo 论文对此有详细描述，Cassandra 和 MongoDB 也大量采用了这种方法（以及很多其他系统）。

冲突解决

分布式系统的冲突解决机制包括：

last writer wins（最后写入者胜出）—— 最近写入的版本被认为是正确的；read repair（读修复）—— 在读时修复不一致，会降低读性能；write repair（写修复）—— 在写时修复不一致，会降低写性能；asynchronous repair（异步修复）—— 在读写操作之外以其他方式异步修复不一致；vector clocks（向量时钟）—— 通过创建逻辑时钟来协调写入，详见 Dynamo 论文。

其他概念

Single point of failure（SPOF，单点故障）指一个组件失效会导致依赖它的服务全部失效；描述故障域（故障域）是一组共享同一 SPOF 的组件；Fault tolerant（容错）描述一个系统在同一功能层面拥有多个故障域；Replication（复制）是将变更从一个进程流式传输到另一个进程；Synchronous replication（同步复制）指在主节点提交变更的同时也在副本上提交（例如 MySQL 的半同步复制，通常非常非常慢）。

这远不是一套完整的术语，分布式系统领域还有非常非常多的概念。我会持续更新和迭代这篇文章。
