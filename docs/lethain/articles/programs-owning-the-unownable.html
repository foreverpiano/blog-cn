项目：掌控不可控之事

2019-06-25 · 阅读原文

良好的如何演进工程组织会最大限度减少实现团队目标所需的跨团队协作。那些几乎不需要协调就能推进的团队，往往在其他团队还在审批实施方案的时候，就已经完成了项目。

然而，复杂的组织不可能把每一个公司目标都装进一个简单易懂的盒子里。那些难以清晰归类的目标，往往包含了公司最有价值的目标，比如等等。基础设施：介于成本中心与自我陶醉之间

这些目标之所以难以归类，是因为它们是需要组织各个层面持续投入的属性，但又很难完全下放。因为它们存在规模经济效应和领域特定上下文，这使得把责任均匀分摊给每个团队变得不划算。难道每个六人工程师团队都要配备一名同时精通安全、云成本、性能、API设计等一长串领域的专家吗？恐怕不太现实。

当我开始负责越来越多无法归入单个团队范围的目标时，我越来越喜欢用「项目」（Programs）来达成这些目标。

项目是由一个专门团队牵头推动的举措，目标是在整个组织内维护某种属性。我见过的一些项目例子包括：事故处理项目、各种形式的技术架构评审、基础设施效率维护、用户体验一致性工作等等。

项目非常有意思，因为它们就像是为「属性」而非「任务」而设立的项目，而维护一个属性需要持续不断的投入。正因为它们永无止境，反而成了极佳的实验场；又因为它们支撑着关键目标，通常会被配置足够资源以确保成功。两者结合，使得项目成为组织快速学习和改进的独特机会。

虽然我仍在不断学习如何让项目成功，但我还是把目前学到的经验总结了出来。

一如既往，值得感谢的人远远多于任何有限名单能列出的，但特别要感谢我在 Stripe 的同事 Cecily、Charles、Grace、Davin、Drew、Erin、Roberto、Smruti 和 Taleena。

何时使用

运营一个成功的项目远比运营一个成功的团队更难。这意味着项目不应该是默认的策略，其较高的固定成本决定了它只适合在深思熟虑后使用。

一个成功的项目需要具备以下条件：具备系统性思维且有流程设计经验的人、拥有丰富领域专长的人，以及能让高层赞助人在自己不那么熟悉的领域保持投入的能力，同时大部分工作还要通过「无权势的影响力」来完成。如果你不具备这些条件，那大概率不应该启动项目。

反之，如果你需要在众多团队和项目中实现广泛且持续的改进，那么项目是为数不多真正有效的工具之一。只要资源到位、设计得当，我见过项目能推动并守住其他任何方法都无法撼动的巨大成果。

设计项目

假设项目是当前问题的最佳解决方案，下面我们来一步步讨论如何从概念到落地运行一个项目：（1）组建团队，（2）前期调研，（3）设计流程。

当你决定启动一个项目时，第一步是组建项目团队。一个即将成功的项目需要以下几类人：

项目设计师 / 系统思考者：有大规模影响力领导经验，懂得如何利用赞助人、如何调动合作伙伴团队，并且能以对项目团队和被引导的组织都最经济的方式完成上述所有事情。领域专家：能够引导政策决策、影响和教育其他团队，并凭借过往经验快速避开常见错误（尽快进入创造性犯错阶段）。系统和工具构建者：与项目其他成员合作，打造自动化和反馈循环，让项目在固定人力协调时间内就能成功（避免随着所支持组织的增长，投入支持的时间线性增加）。高层赞助人：确保项目获得成功所需的资源，并在项目工作需要优先级支持时充当升级通道。

团队组建完成后，下一步是对项目进行前期调研。目标是足够清晰地理解问题，以便开始设计解决方案，同时也要摸清组织在多大程度上愿意投入资源解决这个问题。以下是一些有助于学习的做法：

向合作伙伴团队学习。组织内各合作伙伴团队将提供大部分人力来实现项目目标，在他们愿意了解你的需求之前，你必须先理解他们的需求和优先级。尽早建立这些关系，你会持续获得反馈，知道如何减少他们的摩擦、让项目更有效。向高层赞助人学习。不善于利用高层赞助人的项目很难成功；同样，过度依赖赞助人的项目通常也不太理想，会被赞助人稀缺的时间所限制。提前花时间明确边界、升级机制等事项非常重要。向行业同行学习。大多数「规模化」公司都会有与你正在运行的项目类似的项目。尽可能多地与这些人交流，从他们的成功和失败中学习。向文献学习。虽然不是每个项目都有相关文献，但令人惊讶的是，相关书籍数量其实很多，其中很多隐藏在 DevOps 类别下。多向周围人请教推荐！

最后，有了团队和足够上下文，你就可以开始设计项目了。你需要创建的工具、系统和结构包括：

项目数据是成功项目的基础，也是构建其他大多数工具和系统的前提。拥有准确、有据可依的数据来支撑项目，是首先要重点建设的事情。在你构建好这个数据——并且项目团队对其非常熟悉之前——其他方法都不会特别有效。项目目标。项目需要有清晰的顶级目标，用于追踪项目方法是否成功。这些目标既要与用户和业务需求紧密相关，也要有中间目标来帮助你了解项目方法的健康状况。合作伙伴团队的子目标。每个合作伙伴团队都应对整体项目目标做出自己的贡献，并应有对应的子目标来确保他们对此负责。这些子目标应由项目方提出，然后与合作伙伴团队共同打磨，直到大家都愿意承诺为止。仪表盘。展示项目相对于目标的进展，并允许每个团队深入了解自己子目标的完成情况。最好的仪表盘能清晰地给出项目团队应重点关注的地方，以及各团队为达成目标应聚焦的领域。提醒机制。向在子目标上落后的团队推送更新。指望大家主动去看仪表盘发现自己落后是不现实的，因此需要把上下文主动送到他们面前。反过来，绝不要给不需要采取行动的人发提醒，否则他们会对之后所有的提醒都视而不见。项目状态评审。你需要一个定期会议来让自己对目标负责（建议按季度进行）。赞助人必须参与这些会议，以便在优先级发生变化时保持持续对齐。合作伙伴团队状态评审。你还需要另一套机制，确保每个合作伙伴团队对自己目标负责。这通常是把子目标加入他们已有的评审会议中，而不是新建一个会议。例如，可以为每个合作伙伴团队额外指定一个 OKR，在他们进行 OKR 评审时一起回顾。通常不可能参加所有这些会议，但参加那些在项目子目标上挣扎的团队的会议非常有价值，你会深刻了解他们面临的挑战，以及如何调整项目以适应他们的实际情况。团队运作会议。项目在运行过程中会学到大量东西，你需要一个场所来做出众多持续的调整——这些调整正是成功、高效项目的命脉。项目团队至少每两周应该开一次一小时的会议。项目复盘。你需要一个让项目团队共同学习和演进项目的论坛，或许一年一到两次。这些会议应比运作会议视野更广，根据组织不断变化的上下文来重塑你们的策略。

把这三部分结合起来，恭喜你，你就有了一个组织级项目的雏形，它能承担那些你之前只能在会议间隙零散推动的广泛目标。

如何让项目真正有效

除了上面设计和启动新项目的步骤之外，这里还有一些额外建议和技巧，帮助你的项目真正运转起来：

手动工作是原型，不是解决方案。让项目失败的最好方式，就是把手动流程当作长期解决方案。手动工作枯燥、容易出错，而且会把你的精力错误地投入到执行而不是演进上。在大规模推广前，手动完成项目工作的第一个版本以发现粗糙之处并修复它们，这一点极其重要。但你绝不应该依靠手动工作来进行大规模推广。相反，应该去自动化，即使这意味着前期推进得慢一些，因为自动化将在中期和长期带给你更大的收益。为初学者而构建。项目负责人必须把自己的方法和工具聚焦于支持初学者，而不是专家。这可能很难，因为带领一个项目本身就需要你成为该领域的专家。当与众多团队打交道时，大多数团队对你的项目领域关注得如此 infrequent，以至于他们下次再想起来时，已经忘了上次学过的东西。因此，在构建工具和指南时，要假设你的用户以前从未用过，而且以后也不会再用。要明确团队角色。每个项目团队的人员组成和优势兴趣都不一样，这意味着每个项目的角色划分也会略有不同。重要的是让团队坐下来共同明确各自的角色和职责。每个领域有不同的节奏。事故处理项目就是一个节奏非常快的领域例子，它需要在几小时或几天内从事故发生推进到修复和理解。而负责 API 设计一致性的项目节奏通常会慢一些，需要几天或几周来思考 API 规范演进带来的长期影响。管理云基础设施（AWS、GCP 等）支出的项目可能以月和季度为周期，因为资金是缓慢消耗的。你的项目设计需要在报告和评审机制中考虑这种节奏，确保它们与所处领域的特性相匹配。与赞助人的目标保持一致。有些项目因为把目标推进得超过了赞助人愿意支持的程度而陷入困境，同时也消耗了自己和合作伙伴团队的关系。每个项目都在与众多并行项目竞争资源，与赞助人在如何引导大家做权衡上保持一致，是成功的关键。如果你与赞助人始终保持一致，那么别人就不会轻易升级问题，因为他们知道那不会改变方向，你的生活也会轻松很多。快速迭代以减少摩擦。即使最好的项目也会给合作的团队带来摩擦，因为它们希望团队优先处理某些项目，而这些团队往往有互相冲突的优先级。成功的秘诀不是完全不产生摩擦，而是当合作伙伴团队提出问题时，非常迅速地做出响应。

这并不是让项目有效的全部思考清单，但已经是一个不错的开始了！如果你有更多建议，欢迎给我留言，我会补充进去。

下一步是什么？

没有「唯一正确」的项目设计。我发现自己参与过的每种项目，在细节上都差别很大。把这些想法当作一个框架，去调整，甚至偶尔去打破它。

如果你想阅读更多关于项目设计的资料，我推荐几本 loosely 相关的书：《The Deadline》（DeMarco 著）、《Peopleware》（DeMarco 和 Lister 著），以及《The Phoenix Project》（Kim、Spafford 和 Behr 著）。诚然，这些书并非真正关于项目管理，但我认为书中的思考能非常直接地迁移到项目中来。毕竟，如果一个项目的目标就是拒绝保持固定，那它和我们说的「项目」又有什么区别呢？
