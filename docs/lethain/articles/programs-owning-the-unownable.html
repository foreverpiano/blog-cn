程序：如何驾驭那些看似不可驾驭的目标

2019-06-25 · 阅读原文

优秀的如何演进工程组织会最大限度减少实现团队目标所需的跨团队协调。那些很少需要协调就能快速推进的团队，往往在其他团队还在审批实施方案的时候就已经完成了项目。

然而，复杂的组织不可能把每一个公司目标都装进一个简单清晰的盒子里。那些难以 neatly 映射的目标，往往正是公司中最有价值的目标，比如基础设施：介于成本中心与自我陶醉之间等等。

这些目标难以映射，是因为它们是需要组织内每个环节都持续投入的属性，同时又很难完全去中心化——它们存在规模经济和领域特定上下文，使得把责任均匀分配给每个团队并不划算。难道每个六人工程团队都要配备一名同时精通安全、云成本、性能、API 设计等所有领域的专家吗？恐怕不可能。

当我开始负责越来越多无法被单个团队完全承载的目标时，我越来越倾向于用「程序」（Programs）来达成这些目标。

程序是由一个专门团队牵头推动的长期举措，目标是在整个组织内持续维护某种属性。我见过的一些程序包括：事故响应程序、各种形式的架构评审、基础设施效能维护、用户体验一致性工作等等。

程序非常有意思，因为它们就像是为「属性」而非「任务」而设立的项目，而维护一个属性需要持续、长期的投入。正因为它们永不结束，才成为极佳的实验场；又因为它们支撑着关键目标，通常会得到足够资源来确保成功。这种结合让程序成为组织快速学习和改进的独特机会。

虽然我仍在不断学习如何把程序做好，但还是把目前学到的经验总结了出来。

一如既往，有太多人值得感谢，他们的贡献无法一一列举。特别感谢我在 Stripe 的同事 Cecily、Charles、Grace、Davin、Drew、Erin、Roberto、Smruti 和 Taleena。

何时使用程序

运行一个成功的程序远比管理一个成功的团队更难。这意味着程序不应该成为默认手段——它相对较高的固定成本决定了它只适合有意识、有针对性地使用。

一个成功的程序需要具备系统性思维、流程设计经验的人，需要有深厚领域专长的人，还需要能够让高管赞助人持续投入（即使他们原本并不直接参与），同时主要通过影响力而非权限来推动工作。如果你不具备上述这些条件，那大概率不应该启动一个程序。

反过来说，如果你需要在一系列团队和项目中实现广泛、一致性的推进，那么程序是为数不多真正有效的工具之一。只要资源到位、设计得当，我见过程序能推动并守住其他任何方法都无法企及的巨大成果。

设计程序

假设程序是解决当前问题的正确方案，接下来我们从概念到落地一步步拆解如何启动它：(1) 组建团队，(2) 进行初始探索，(3) 设计流程。

当你决定启动一个程序时，第一步是组建程序团队。一个即将取得成功的程序需要以下几类人：

程序设计师 / 系统思考者：有大规模影响力领导经验，懂得如何利用赞助人、如何与合作团队打交道，并且能以对程序团队和被引导的组织都最经济的方式开展所有工作。领域专家：能够引导政策决策、影响和教育其他团队，并凭借过往经验快速避开初期的常见错误（尽快进入发明新错误阶段）。系统和工具构建者：与程序其他成员合作，打造自动化和反馈循环，让程序在固定协调人力投入下就能成功，避免随着被支持组织规模扩大而线性增加支持耗时。高管赞助人：确保程序获得成功所需的资源，并在程序项目需要被优先考虑时成为升级通道。

团队组建完成后，下一步是对程序进行初始探索。目标是对问题有足够清晰的理解，以便开始设计解决方案，同时摸清组织愿意为解决这个问题投入到何种程度。以下是一些有助于学习的途径：

向合作团队学习。合作团队将提供完成程序目标所需的大部分人力，在他们愿意理解你的需求之前，你必须先理解他们的需求和优先级。尽早建立这些关系，你会持续获得如何降低他们摩擦、让程序真正落地的反馈。向高管赞助人学习。不能很好利用高管赞助人的程序不会成功；过度依赖赞助人的程序通常也不太行，会因为赞助人时间稀缺而成为瓶颈。提前花时间明确边界、升级机制等事项非常重要。向行业同行学习。大多数「规模化」公司都会有和你正在运行的程序类似的机制。尽可能多地与这些同行交流，学习他们的成功和失败经验。从文献中学习。不是每个程序都有相关文献，但市面上 surprisingly 有大量相关书籍，很多隐藏在 DevOps 类别下。可以到处问问推荐！

最后，有了团队和上下文之后，就可以开始设计程序了。你需要创建的工具、系统和机制包括：

程序数据是成功程序的基础，也是构建其他大多数工具和系统的先决条件。拥有准确、可验证的数据来支撑程序，是最先要专注构建的事情。在你建立起这些数据——并且程序团队对其非常熟悉——之前，其他方法都不会特别有效。程序目标。程序需要有清晰的顶级目标，用于追踪其方法是否成功。这些目标既要与用户和业务需求紧密相关，也要有中间目标来帮助你了解程序方法的健康程度。合作团队的子目标。每个合作团队都应对整体程序目标做出自己的贡献，并应拥有一个子目标来确保他们为此负责。这些子目标应由程序提出，然后与合作团队共同打磨，直到大家都能安心承诺。仪表盘。展示程序相对于目标的进展，并允许每个团队深入了解自己子目标的完成情况。最好的仪表盘会清晰指出程序团队应该把注意力放在哪里，以及各团队为达成目标应重点关注哪些领域。提醒机制。向那些在子目标上落后的团队推送更新。指望大家主动刷仪表盘发现自己落后是不现实的，因此需要把上下文主动送到他们面前。反过来，绝不要给不需要采取行动的人发提醒，否则他们会直接屏蔽后续所有提醒。程序状态评审。你需要一个定期会议来让自己对目标负责（建议每季度一次）。赞助人必须参加这些会议，以便在优先级发生变化时保持持续对齐。合作团队状态评审。你还需要另一套机制，确保每个合作团队对自己目标负责。通常不需要新建会议，而是把子目标加入他们已有的评审会议中。例如，可以为每个合作团队在 OKR 评审中增加一项额外的 OKR。通常不可能参加所有这些会议，但参加那些在程序子目标上挣扎的团队的会议非常有价值——你会深入了解他们面临的挑战，以及如何调整程序来适应他们的实际情况。团队运作会议。程序在运行过程中会学到非常非常多的东西，你需要一个地方来持续进行大量微调——这正是成功、高效程序的生命线。程序团队应该至少每两周开一次一小时的会议。程序复盘。你需要一个让程序团队共同学习和进化程序的论坛，大概一年举行一到两次。这些会议的视野应比运作会议更宏观，根据组织不断变化的上下文重新构建策略。

把这三部分结合起来，恭喜你，你已经初步拥有了一个能够扛起那些你之前只能在会议间隙零散推动的宏大目标的组织程序。

如何让程序真正有效

除了上面设计和启动新程序的步骤，这里还有一些额外的想法和建议，帮助你的程序真正发挥作用：

手动工作是原型，而非解决方案。让程序失败的最好办法，就是把手动流程当成长期解决方案。手动工作枯燥、容易出错，还会把你的精力错误地投入到执行而不是进化上。在大规模推广前，先手动完成程序工作的第一个版本来发现粗糙之处并修复它，这点极其重要；但你绝不应该依赖手动工作来进行大规模推广。相反，要去做自动化，哪怕这意味着前期推进得更慢——因为自动化会在中长期带给你更远大的成果。为初学者而构建。程序领导者必须把自己的方法和工具聚焦于支持初学者，而不是专家。这可能有些困难，因为领导一个程序的过程本身就会让你成为该领域的专家。但当你与许多团队合作时，大多数团队只会非常偶尔地关注你程序的领域，以至于他们下次想起这件事的时候，已经把上次学到的东西忘得差不多了。在构建工具和指南时，要假设你的用户是第一次使用，并且以后也不会再用。要明确团队角色。每个程序团队的人员构成和专长兴趣各不相同，这意味着每个程序的角色划分也会略有差异。重要的是团队坐下来一起澄清各自的角色和职责。不同领域有不同节奏。事故响应程序就是一个节奏非常快的例子，它需要在几小时或几天内完成从事故到修复再到总结的循环。而负责 API 设计一致性的程序节奏则会慢一些，需要几天或几周来思考 API 规范变更带来的长期影响。管理云基础设施（AWS、GCP 等）支出的程序可能以月和季度为节奏，因为资金是缓慢花出去的。你的程序设计需要在报告和评审机制中考虑这种节奏，确保它们与所处领域的特性相匹配。始终与赞助人的目标保持一致。有些程序因为把目标推进到赞助人愿意支持的限度之外而陷入困境，最终把自己和与合作团队的关系都耗尽。每个程序都在和众多并行项目争夺资源，与赞助人在「如何帮助大家做权衡」上保持一致，对成功至关重要。如果你和赞助人始终保持一致，那么别人就不会去升级问题，因为他们知道升级也不会改变方向，你的生活也会轻松很多。快速迭代以减少摩擦。即使最好的程序也会给合作的团队带来摩擦，因为它们要求团队把某些项目排在优先级前面，而这些团队往往有互相冲突的优先级。成功的秘诀不是完全不制造摩擦，而是当合作团队提出顾虑时，极其迅速地做出响应。

这并不是让你把程序做有效的全部清单，但已经是一个不错的开始了！如果你有更多建议，欢迎告诉我，我会补充进来。

下一步是什么？

世界上没有「唯一正确的程序设计」。我发现自己参与过的每种程序，在细节上最终都差别很大。请把这些想法当作一个框架，你可以根据实际情况调整，甚至有时可以违背。

如果你想阅读更多关于程序设计的资料，我推荐几本略微相关的书：《The Deadline》（DeMarco 著）、《Peopleware》（DeMarco 和 Lister 著），以及《The Phoenix Project》（Kim、Spafford 和 Behr 著）。诚然，这些书并非真正关于程序管理，但我认为其中的思考能非常直接地迁移到程序管理上。毕竟，如果一个项目的目标就是拒绝保持固定，那它不就成了一个程序吗？
