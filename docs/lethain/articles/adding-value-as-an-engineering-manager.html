作为工程经理如何创造价值

2015-09-26 · 阅读原文

我进入工程管理领域的方式和大多数人一样：进入新公司六个月后——经历了一轮裁员和人才流失之后——我莫名其妙地成了资历最老的软件工程师。然后，在我那无尽的幼稚中，我自以为很明智地接下了工程经理的职位，带领着一艘正朝着贪婪黑洞疾驰的火箭飞船。从这个不光彩的起点开始，我积累了足够多的失败和失误记录，对这个领域有了一个粗浅的认识。在我自己改变主意之前，我想在这里分享一下这些体会。

新工程经理最常见的失败模式，就是把太多时间花在技术工作上。确实有一些技巧可以帮助缓解这个问题——比如每周固定一天只做管理工作——但我认为真正的问题在于，许多经理并不相信管理者能真正为团队贡献多少价值。大多数工程经理以前都是工程师，他们接触到的工程管理大多也相当平庸，因此很容易理解这种观点的来源。但实际上，管理者绝对可以发挥重要作用。（下面是我的看法，同时也推荐看看 Slack 的另一视角。）

工程经理最有价值的贡献在于：

在系统上工作（而非在系统中工作）、培养团队、引导执行、管理沟通。

接下来这篇冗长的文章将逐一深入探讨这些方面。

在系统上工作，而非在系统中工作

《重塑自我》（The E-Myth Revisited）一书的核心观点是，作为企业主，你必须始终确保自己在为业务工作，而不是在业务中工作。我认为这也是成为有效管理者的根本原则。

作为管理者的成功标志是：你知道自己明天即使离开，也能确信团队在没有你亲自管理的情况下仍能保持高效（关于这一点可以参考《从优秀到卓越》）。这意味着日常运作不能依赖于你个人的判断。这是否意味着管理者就不应该努力工作？当然不是——在变革时期，你确实需要对团队或组织进行彻底改造以适应新的环境和约束——但如果你总是极其辛苦地工作，那么你的组织可能就过于依赖你了。

在系统上工作是一个相当简单的迭代循环：

衡量团队目前最主要的时间花在什么地方，识别你自己把大部分时间花在哪个领域，尝试一种方法来减少你在该领域花费的时间，然后回到第一步。

困难之处在于衡量团队的时间分配，以及挑选出好的实验来减少你在这个领域所花的时间。随着反复尝试，你会在这两方面都变得更好，但这里有一些指导原则：

自动化仪表和度量几乎总是最好的选择（因为你必须在完全脏的数据和不完整的干净数据之间二选一，那还不如选择占用团队时间更少的那一个）；需要团队投入更多工作的度量方法通常会失败（“太忙了，没时间思考”）；手动度量只要测量周期固定在以天为单位而非以周为单位，就能奏效；你可以通过为团队创建一个更好的接口来降低实验成本（这可以是一个供其他团队调用的 API、一个引导请求者的 UI，或者让人们通过提交工单而不是当面请求来完成）；需要其他团队改变行为的实验反馈周期非常慢，在内部进行实验迭代要容易得多。

这个简单的迭代过程就是管理的基本行为。当你越来越擅长它时，它就能让你通过一系列渐进式改进，完成真正了不起的事情。

（在你将要进行的所有实验中，组织架构调整是最痛苦和最具破坏性的之一。但另一方面，它们的潜在影响也可能是最大的，仅次于增加、更换或移除经理。我在这里无法详细展开，但总体而言，我认为组织架构调整被严重低估了。）

培养团队

当你在维护自己正在构建的系统时，最高杠杆的活动，就是确保你的团队由合适的人组成，并且这些人能很好地一起工作。

这包括三个部分：

为团队招聘新成员、为现有团队成员创造成长机会、确保团队中的每个人都适合留在团队。

招聘很难，这里无法深入讨论，但没有什么比引进一位出色的新人更能彻底改变你的团队了。（反之亦然。）

培养现有团队同样重要，这既有助于留住人才，也能确保在你身后有人才梯队，让你永远不会成为团队持续成功不可或缺的人。从哲学上讲，我更相信“培养”团队而不是“培训”团队：你可以向人们植入一些想法（最常见的方式是通过身体力行地展现这些价值观或理念），但我认为优秀的人足够有怀疑精神，他们必须从自己的经验中学习，而你能传递给他们的经验其实很有限（一位同事曾经把管理比作养育孩子：你告诉他们正确的方法，然后他们还是会按自己的方式去做……）。在这种自我引导的学习环境中，你能为团队成长做的最好的事，就是给他们越来越有挑战性的任务，赋予他们更大的自主权和发挥创造力的空间。

我必须承认，在这一点上我相当偏离主流。许多其他人认为更传统的培训形式（内部或外部培训）、参加会议、结对编程以及项目日（黑客马拉松等）极具价值。归根结底，我认为关键在于将学习机会与学习者的学习风格相匹配。

最后，你在培养团队方面还能做出的另一个重要贡献，就是确保团队中的每个人都真正适合留在团队，这有时也被称为绩效管理。

团队里有不合适的人，会比任何其他事情都造成更大的损害。而谁是“合适的人”，完全取决于具体情境。随着公司规模扩大，你往往需要 ——那些曾经是团队重要贡献者，但却无法放弃控制权、不愿让团队实现规模化的人。消灭英雄，停止蛮干

让一个人离开总是痛苦的，但至少在我有限的样本中，我从未见过有人在离开、被辞退或辞退他人之后变得更不快乐。到那个时候，情况通常已经非常有毒了。然而，这方面的精通在于，在情况变得有毒之前就识别出问题，然后尝试不同的做法：一个正在挣扎的人，换一个经理、换一个角色，甚至换一个项目，都有可能焕发生机。你必须在某个地方划清界限，但除非存在深层次的根本绩效问题或道德违规，否则这条界限应该是在两到三次尝试失败之后再划。

引导执行

最终，你和你的团队都是根据对公司的贡献来被评判的，而你通过成功执行有价值的项目来创造这种价值。这里成功的两个主要要求是：

你的团队正在做既有价值、也被认为有价值的事情；你的团队在项目上取得了显著进展，符合或超出预期。

当你开始领导一个团队时——以及之后定期进行——你需要审视团队的项目组合，思考其中哪些项目已经不再值得继续推进。团队在做一些曾经有意义、现在却已不再有意义的项目，或者团队认为有意义但实际上没有潜在客户的项目，或者与其他内部团队竞争同一个问题而最终只会“有一个胜出”的项目，这些情况都极为常见。及时砍掉组织永远不会欣赏的项目，是增加价值的最快方式。

有些项目极具价值，但由于设计和构建它的团队不了解公司更广泛的社会或技术背景而出现了错位。将这些项目重新与组织的其他项目、团队和价值体系对齐，同样能产生极高的影响。一个很好的例子是：一家不重视运维或系统管理工作的公司，你可以将一些脚本打包成带 UI 的服务，然后将其贡献重新定位为“构建自动化软件”而不是“管理”。工作本身并没有实质改变，但你将其重新包装成了公司所重视的东西。

一旦确认你的项目确实有价值，下一步就是帮助引导这些项目走向成功，同时又不让自己成为团队执行的瓶颈。随着时间推移，我逐渐将其理解为引入适当的控制机制：既防止自己过度介入细节，又确保自己能足够早地发现问题并进行纠正。

什么控制合适，很大程度上取决于你的团队规模和结构，但以下是我过去或现在使用过的一些控制手段，按照适用于小团队到适用于大型组织的顺序排列：

代码评审：审查代码 diff 是了解谁在做什么以及团队成员之间如何互动的绝佳方式。最适合团队负责人或一线经理。每日站会：让整个团队简要汇报当前工作，有助于发现原地打转的项目或需要更多指导的成员。需要注意的一个信号是，团队成员之间对彼此正在做什么完全缺乏相互了解。1:1 会议：每周或每两周与团队每个成员见面，如果他们信任你，这是一个获取反馈的绝佳机会。否则往往会变成状态更新会议。产品需求：一套清晰的产品需求，并频繁检查需求是否被满足，这是在团队和管理层之间设立的良好抽象层，让双方都能自由贡献，而不会过于频繁地互相干扰。状态报告：随着组织规模扩大，让团队负责人每周制作面向全组织的状态报告，是一个有用的机制，能让团队之间了解彼此的工作，也能识别出进展不大的团队或项目（这里的一个信号是，有些团队每周都说不出有什么工作可以汇报，或者每周都在重复同样的内容）。跨级 1:1：当团队规模变大后，你会逐渐与非直接下属的成员失去联系。你需要信任一线经理去管理他们的团队，但你也对这些团队负有责任，需要有一个安全机制来发现失控的经理或项目，这个机制就是跨级 1:1——与你下属的下属见面。这些会议能让你在更深的层面与扩展团队建立坦诚的关系。每季度路线图：如果说“没有计划能在与敌人交战后依然有效”，那么当然也没有路线图能在第一次接触现实后依然成立。但它们仍然是极好的对齐工具，能确保你和团队有相同的优先级，并对项目的价值有共同理解。

虽然没有万能解，但将这些技术适当组合，应该能让你对团队的执行有足够的洞察，同时也给团队留下足够的空间，让他们能够创新和发挥超出你贡献的价值。

管理沟通

管理中最困难的部分之一，是在团队与更大组织之间建立有效的双向沟通。几乎没有人能把这件事做好，不是因为他们不努力，而是因为存在一些根本性的障碍，让良好的意愿和英勇的努力都难以奏效。

然而，即便只是诚实地尝试，也能让你和你的团队脱颖而出。我的入门方法是：

明确团队的身份，以及你希望别人如何认知这个身份。你们是一个做基础设施的软件工程团队吗？是一个系统工程团队？还是一个产品团队？你们是精通某几个领域的专家，还是一个广泛的整合型团队，将其他团队的贡献整合成一个 cohesive 的产品？识别出团队为组织创造价值最多的三个方面，并找到一种与团队身份一致的表达方式。与团队讨论你们重点想要传递哪些贡献，以及为什么聚焦在这些领域。建立一致的沟通节奏。定期（每周或每两周）发送更新，介绍团队正在做的工作，用符合团队身份的方式来表述，并聚焦于读者感兴趣的内容（而不是你自己感兴趣的内容）。定期与其他组织的领导者进行 1:1 交流，讨论你们重点关注的领域，同时了解他们重点关注的领域。将其他团队的举措收集到一个跟踪文档中，并与团队一起讨论这些项目，以增加对其他团队工作的了解。

如果你将大约 20% 的时间花在沟通上，你可能会遇到收益递减，但大多数愿意倾听的人应该都已经听到你的信息，而那些不愿意听的人大概也不会改变——这可能已经是你能合理期待的最好结果了，除非你能和公司里每个人都进行 1:1 沟通。

结束语

这其实只是作为工程经理可以创造价值的众多方式的起点——你必须找到适合自己个性的管理风格——但希望它能给你一些值得思考的想法。如果我在三年前写这篇文章，内容会大不相同；而我确信如果三年后再写，我又会写出完全不同的东西。但就目前而言，这些内容大致是正确的。
