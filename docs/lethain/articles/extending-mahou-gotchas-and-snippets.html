扩展 Mahou：陷阱与代码片段

2008-09-12 · 阅读原文

昨天花了一些时间来美化 mahou.appspot.com。此前它只能进行图片搜索，但我决定再提升几个档次，充分利用 Yahoo! BOSS Search Mashup Framework 更多潜在的功能。

最明显的变化是它现在支持网页、图片和新闻搜索结果。从呈现效果来看，图片搜索仍然比另外两种更具吸引力，但我成功地对代码进行了大力重构，以便于进一步定制（WLWebResultsView.j——负责显示网页搜索结果——去除空白后约 100 行，而显示图片的 WLImageResultsView.j 约 65 行）。

我添加了几个菜单，“搜索”菜单允许你选择每次查询返回的结果数量，“网页”菜单则提供通过 Delicious 进行过滤的选项。启用 Delicious 过滤后，网页搜索结果将通过该主题的 Delicious 热门 RSS feed 进行筛选。

实际上，这种过滤会严重扼杀结果数量，但确实能提供高质量的内容。目前这还只是一个实验，而这正是 Mahou 的全部意义：Mahou 是我一个小小而有些偏差的尝试，旨在探索和实验搜索引擎的界面与功能。从现在起，尝试一个新想法应该只需 30 分钟的“假期”，或许一些有趣的想法会在这片贫瘠的园地里逐渐成长。

接下来我要谈谈开发过程中遇到的几个尴尬问题，同时分享代码中一些有趣的地方。

良好地显示文本并不容易

Cappuccino 在尝试显示文本时仍然显得笨拙。公平地说，Cocoa 在这方面也做得不够好。我认为 Cappuccino 有潜力在这方面超越 Cocoa，特别是如果他们能绕过 NSAttributedString 那种可怕的格式化方式，转而直接尊重格式化 HTML 标签的含义（尤其是 em 和 strong）。

朝着这个方向，我扩展了文本框，创建了 WLHTMLTextField.j 类，负责剥离 HTML 标签。未来我希望进一步扩展它以支持渲染，但目前它仅支持忽略或剥离 HTML。

使用方法非常简单。

这样做是必要的，因为 Yahoo! BOSS 返回的内容中带有 strong 和 emphasis 标签（用于高亮匹配搜索查询的字符串等），而 Cappuccino 不知道如何处理这些标签。因此，穷人的解决方案就是把标签剥掉。

我就是个穷人。

Collection View 的陷阱

CPCollectionView 是 CPView 的子类，它可以方便地显示多个较小的视图，并以行列方式排列以最大限度利用可用空间。它用很低的代价提供了大量功能，Flickr 示例代码是学习这个主题的绝佳教材。

尽管如此，情况并不完美。我特别遇到了两个尴尬的场景：

CPCollectionView 通过 CPCollectionViewItem 来填充内容，每个 item 包含一个视图来展示它所代表的对象。例如，Mahou 接收到一个包含搜索结果的字典数组。我将这个数组传给 collection view，然后 collection view 将每个字典分别传给对应的 view item。这工作得非常好。然而，要确定 view item 的视图可用空间却相当麻烦。我在这个问题上解释得不太清楚，主要是因为我怀疑自己犯了一个大错误，错过了一个显而易见的解决方案。尽管我尽力尝试，但在创建 collection view item 时还是无法获取 collection view 的大小。这使得相对定位 item 变得很 awkward。替代方案是你只能为 collection view item 定义一个较小的最小/最大尺寸范围，然后在 item 内部进行绝对定位。顿悟总是来得太晚，重新翻看文档后，我发现可以使用 setMaxNumberOfColumns 方法巧妙地解决这个问题。我还遇到了一个极其奇怪的缓存错误。如果我先搜索日本的图片，再搜索美国的图片，第一次的图片能被正确清除。但如果是网页搜索，同样的操作却无法正确显示美国的搜索结果。释放和重置 represented object 的代码都由这些类的父类处理，所以我完全搞不懂为什么网页视图不能正常工作。这里的陷阱在于 CPCollectionView 会复用 CPCollectionViewItem，因此你自定义的 CPCollectionViewItem 子类必须能够在 setRepresentedObject: 方法被调用时正确更新其内容。

结束思考
