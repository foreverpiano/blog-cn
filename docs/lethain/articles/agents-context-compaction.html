构建内部 Agent：上下文窗口压缩

2025-12-26 · 阅读原文

虽然我为大多数内部工作流选择的模型仍是 ChatGPT 4.1，因为它的速度稳定且高度遵守指令，但即使其 1,047,576 token 的上下文窗口也可能用尽空间。当上下文窗口空间耗尽时，你的 Agent 要么只能放弃，要么需要将庞大的上下文窗口压缩到更小的空间里。下面是我们实现压缩的笔记。

这是 构建内部 Agent 系列文章的一部分。

为什么压缩很重要

包含大量工具调用或用户消息的长期运行工作流，以及任何处理大文件的流程，通常都会耗尽上下文窗口的空间。虽然对大多数内部 Agent 场景来说，上下文窗口耗尽并不常见，但如果不解决这个问题，就无法构建一个稳健、可靠的 Agent，而压缩是一种直接有效的解决方案。

我们是如何实现的

起初，在我们天真地认为压缩对内部工作流无关紧要的时候，我们实现了一个极其简陋的压缩方案：如果 token 耗尽，就直接丢弃较旧的工具响应，直到腾出足够空间，然后继续。因为我们很少遇到需要压缩的情况，这个方案虽然效果不佳，但也没造成太大问题。不过，随着我们开始处理更多 ，这种粗糙的实现逐渐让我感到难以忍受。构建内部 Agent：渐进式披露与处理大文件

在第二次迭代压缩方案的头脑风暴中，我一开始执着于一个美好的想法——认为压缩应该在 之后进行，但始终无法为这个直觉找到具体的必要性理由。最后我们在没有子 Agent 支持的情况下实现了压缩功能。构建内部 Agent：子 Agent 支持

我们压缩方案的核心思路是：

<files>
  <file id='a' name='image.png' size='32kb'>
    <file_read />
  </file>
  <file id='a' name='image.png' size='32kb'>
    <file_read start_line=10 end_line=20 />
  </file>
</files>
  1. After every user message (including tool responses), add a system message with the consumed and available tokens in the context window. In that system message, we also include the updated list of available files that can be read from
  2. User messages and tool responses greater than 10,000 tokens are exposed as a new “virtual file”, with only their first 1,000 tokens included in the context window. The agent must use file manipulation tools to read more than those first 1,000 tokens (both 1k and 10k are configurable values)
  3. Add a set of “base tools” that are always available to agents, specifically including the virtual file manipulation tools, as we’d finally reached a point where most agents simply could not operate without a large number of mostly invisible internal tools. These tools were file_read which can read entire files, lines ranges within a file, or byte ranges within a file, and file_regex which is similar but performs a regex scan against a file up to a certain number of matches.Every use of a file is recorded in the files data, so the agent knows what has and hasn’t been read into the context window (particularly relevant for preloaded files), along the lines of:This was surprisingly annoying to implement cleanly, mostly because I came onto this idea after iteratively building the agent as a part-time project for several months. If I could start over, I would start with files as a core internal construct, rather than adding it on later.
  4. If a message pushed us over 80% (configurable value) of the model’s available context window, use the compaction prompt that Reddit claims Claude Code uses. The prompt isn’t particularly special, it just already exists and seems pretty good
  5. After compacting, add the prior context window as a virtual file to allow the agent to retrieve pieces of context that it might have lost

以上每一步都相当简单，但组合在一起后，为处理复杂、长期运行的工作流提供了相当强大的能力。我们仍然为单个工作流可调用的工具数量设置了可配置上限（以防止 Agent 无限循环），但这套机制让处理大型或复杂数据的 Agent 成功率显著提升。

实际效果如何？下一步是什么？

与我们大多数新的内部 Agent 功能不同，这个功能没有明显的问题或需要立即迭代的地方。它已经好到可以长期搁置不再关注。主要有两个原因：一是我们的大多数工作流并不需要很大的上下文窗口；二是老实说，这个方案效果相当不错。

如果未来上下文窗口显著变大（目前我还没看到太多这种迹象），我们只需要调高一些默认数值来使用更多 token 即可，而这里的 core 算法已经足够稳健。
