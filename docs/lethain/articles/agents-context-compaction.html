构建内部 Agent：上下文窗口压缩

2025-12-26 · 阅读原文

虽然我为大多数内部工作流选择的模型仍是 ChatGPT 4.1，因为它的速度稳定且高度遵守指令，但即使其 1,047,576 token 的上下文窗口也可能用尽空间。当上下文窗口空间耗尽时，你的 Agent 要么只能放弃，要么需要将庞大的上下文窗口压缩到更小的空间里。下面是我们实现压缩的笔记。

这是 构建内部 Agent 系列文章的一部分。

为什么压缩很重要

包含大量工具调用或用户消息的长期运行工作流，以及任何处理大文件的流程，通常都会耗尽上下文窗口的空间。虽然对大多数内部 Agent 场景来说，上下文窗口耗尽并不常见，但如果不解决这个问题，就无法构建一个稳健、可靠的 Agent，而压缩是一种直接有效的解决方案。

我们是如何实现的

起初，在我们天真地认为压缩对内部工作流无关紧要的时候，我们实现了一个极其简陋的压缩方案：如果 token 耗尽，就直接丢弃较旧的工具响应，直到腾出足够空间，然后继续。因为我们很少遇到需要压缩的情况，这个方案虽然效果不佳，但也没造成太大问题。不过，随着我们开始处理更多 ，这种粗糙的实现逐渐让我感到难以忍受。构建内部 Agent：渐进式披露与处理大文件

在第二次迭代压缩方案的头脑风暴中，我一开始执着于一个美好的想法——认为压缩应该在 之后进行，但始终无法为这个直觉找到具体的必要性理由。最后我们在没有子 Agent 支持的情况下实现了压缩功能。构建内部 Agent：子 Agent 支持

我们压缩方案的核心思路是：

<files>
  <file id='a' name='image.png' size='32kb'>
    <file_read />
  </file>
  <file id='a' name='image.png' size='32kb'>
    <file_read start_line=10 end_line=20 />
  </file>
</files>
在每条用户消息（包括工具响应）之后，添加一条系统消息，说明当前上下文窗口已消耗和可用的 token 数量。在这条系统消息中，我们还会附上最新的可读取文件列表。超过 10,000 token 的用户消息和工具响应会被转换成一个新的“虚拟文件”，只有前 1,000 token 会放入上下文窗口。Agent 如果需要读取超出这 1,000 token 的内容，必须使用文件操作工具（1k 和 10k 都是可配置的值）。为 Agent 增加一组始终可用的“基础工具”，特别包括虚拟文件操作工具，因为我们终于意识到，大多数 Agent 如果没有大量几乎隐形的内部工具就无法正常工作。这些工具包括 file_read（可读取整个文件、指定行范围或字节范围）和 file_regex（类似，但可对文件执行正则匹配，限制最大匹配次数）。每次使用文件都会记录在文件数据中，让 Agent 清楚哪些内容已被读入上下文窗口（对预加载文件尤其重要），大致结构如下：这个功能实现起来出乎意料地麻烦，主要是因为我是在这个兼职项目迭代了好几个月后才想到这个方案的。如果能重新开始，我会从一开始就把文件作为核心内部概念，而不是后来再叠加上去。当某条消息将上下文窗口占用推高到模型可用容量的 80%（可配置）以上时，触发 Reddit 上提到的 Claude Code 使用的压缩 prompt。这个 prompt 本身并不特别，只是现成的而且效果不错。压缩完成后，将之前的上下文窗口整体保存为一个虚拟文件，以便 Agent 后续可以找回可能丢失的上下文片段。

以上每一步都相当简单，但组合在一起后，为处理复杂、长期运行的工作流提供了相当强大的能力。我们仍然为单个工作流可调用的工具数量设置了可配置上限（以防止 Agent 无限循环），但这套机制让处理大型或复杂数据的 Agent 成功率显著提升。

实际效果如何？下一步是什么？

与我们大多数新的内部 Agent 功能不同，这个功能没有明显的问题或需要立即迭代的地方。它已经好到可以长期搁置不再关注。主要有两个原因：一是我们的大多数工作流并不需要很大的上下文窗口；二是老实说，这个方案效果相当不错。

如果未来上下文窗口显著变大（目前我还没看到太多这种迹象），我们只需要调高一些默认数值来使用更多 token 即可，而这里的 core 算法已经足够稳健。
