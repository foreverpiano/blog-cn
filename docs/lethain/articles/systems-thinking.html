系统思维导论

2018-09-04 · 阅读原文

我合作过的许多高效领导者都有一种不可思议的能力，擅长解决构建技术杠杆问题。在某些问题领域，问题探索、选择与验证对于发现有价值的问题极为有效，但系统思维是我所见过最普适有用的工具箱。

如果你想真正扎实掌握系统思维的基本原理，应该去读 Donella Meadows 的《Thinking in Systems: A Primer》，不过我也会尽力介绍一些基础知识，并结合最近一个让我觉得系统思维特别有价值的实际场景来展开说明。

存量与流量

系统思维最根本的观察是：事件之间的联系往往比表面看起来更加微妙。我们倾向于用因果关系描述事件——我们的经理太忙了，因为我们正试图交付当前的项目——但很少有事件是孤立发生的。

巨大的变化看似瞬间发生，但如果你仔细观察变化的背后，通常会发现有一个缓慢积累的小变化过程。在这个例子中，经理们之所以忙碌，可能是因为没有人招聘和培养足够支持今年项目截止日期的经理。这些积累被称为存量，是随时间变化的记忆。存量可以是公司里受过培训的经理人数。

对存量的改变称为流量，可以是流入也可以是流出。培训一位新经理是流入，一位受训经理离开公司则是流出。本文中图表的流量用实心深色线表示。

另一种关系在本文中用虚线表示，称为信息链。它表明存量的数值会影响流量的大小。本图中用虚线标注的链路显示，开发功能可用的时间取决于受训经理的数量。

图表范围之外的存量通常用云朵表示，说明那里发生了我们当前不打算深入探究的复杂情况。最佳实践是为每个流量都加上标签，并记住：每个流量都是一个速率，而每个存量都是一个量。

开发者速度

当我开始思考一个能说明系统思维用途的例子时，一个场景立刻浮现在脑海。自从今年早些时候读了 Forgren 的 Accelerate 对开发者生产力的定义 之后，我花了很多时间思考他们对速度的定义。

他们重点关注开发者速度的四个衡量指标：

交付前置时间是从代码写完到在生产环境上线的耗时。部署频率是你部署代码的频次。变更失败率是变更失败的频率。服务恢复时间是修复缺陷所花费的时间。

这本书通过对数万个组织的调研来评估它们的整体生产力，并展示这些生产力如何与它们在那四个维度上的表现相关。

这些指标作为生产力的衡量标准直观上很有道理，但让我们试着把它们建模成一个系统，以便我们可以据此推理开发者生产力：

Pull request 根据我们的代码审查速率转化为就绪的 commit，就绪的 commit 以部署速率转化为已部署的 commit，已部署的 commit 以缺陷率转化为 incident，incident 通过恢复速率被修复为已回滚的 commit，已回滚的 commit 又通过调试速率被转化为新的 pull request。

将这些环节连接起来，我们看到一个反馈循环，系统的下游行为会影响其上游行为。如果缺陷率过高或者恢复速率过慢，你很容易就会遇到每次部署都让你更加落后的情况。

如果你的模型足够好，改进机会应该会立刻显现出来，我认为在这个案例中确实如此。然而，要真正知道该往哪里投入，你需要确定这些存量和流量的真实数值！例如，如果你没有就绪 commit 的积压，那么加快部署速率可能并没有价值。同样，如果你的缺陷率已经非常低，那么缩短恢复时间对整个系统的影响也会很小。

系统思维最让我欣赏的一点，就是它创造了一个可以快速检验关于事物运作方式的假设的舞台，而不需要事先去做那些底层工作。

尽情建模吧

一旦你开始用系统的眼光思考问题，就会发现很难停下来。几乎任何棘手的问题都值得尝试将其表示为一个系统，即使不代入具体数字，我也会发现它们是非常强大的思考工具。

如果你想要完整的体验，目前支持这类工作的工具并不多。Stella 是行业标杆，但价格相当昂贵，非学术许可证比买一台新笔记本电脑还贵。我找到的最好的廉价替代品是 InsightMaker，虽然界面有一些小问题，但采用的是捐赠制的付费模式。
