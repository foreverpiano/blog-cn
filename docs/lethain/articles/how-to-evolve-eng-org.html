如何演进工程组织

2019-03-05 · 阅读原文

最近，我有机会向一群早期创业公司的 founder 介绍如何演进他们的工程组织。在准备过程中，我意识到尽管自己对这个话题充满热情，但之前只间接写过相关内容。

我写过最全面的相关文章是 。重组确实涉及大量组织设计，但它是一个很难展现最佳实践的环境。通常重组需要在短时间内完成，并受到业务需求、团队健康状况和可用领导者的重重限制。运行工程团队重组

好的组织设计是一种定向演进，它需要在追求明确目标的同时，愿意反复调整通往该目标的路径。

我发现行之有效的流程是：

在做出改变前，先衡量你希望改进的内容。将你的组织规模与同行、目标和绩效进行对比。将组织拆分为团队和组。对组织未来的增长进行预测。在两次调整之间留出休息时间，以培养掌握度。

组织设计是一个基础扎实就能取得惊人成效的领域，即使是最资深的人有时也会觉得困难。这个框架并不是组织设计的秘诀，但它会引导你提出所有正确的问题，以及这些问题的标准答案。

这不是最终定论，但是一个好的开始。

衡量

组织设计并非以接近某种意识形态理想为目标，而是以能否有效解决当前需求来评判。衡量是清晰理解现实的基础，也是良好组织设计的第一步。

第一步被跳过的频率高得惊人，后果也难以量化。被跳过的最主要原因是，衡量组织运作得好坏异常困难。

规模

一旦你开始衡量当前组织，下一步就是确定目标组织规模。需要展望多远的未来取决于你的阶段，从非常小的公司可能只需三个月，到成熟公司可能需要数年不等。

你的 速度决定了规划 horizon 的起点，而业务的 predictability 则决定了 horizon 的终点。你的招聘漏斗

一旦确定了 horizon，比如六个月，接下来就要计算组织结束时的规模。

大多数公司通过将势头和招聘速度合并成一个预测来确定规模，但这可能会产生一种投资惯性，初期看起来相当合理，却会慢慢滑向低效。

另外三种更有用的规模策略是：

与类似公司进行基准对比。与五家稍大一些的公司交流，建立一个关于他们如何确定组织规模的小数据集。每家公司都不一样：忠实复制另一家公司的做法属于 cargo cult。但从少数几家公司学习以找出有用的上下限，就是基准对比。基准对比是一种非常可靠、成本低廉的方法，可以用来确定合理方案的范围。我推荐把它作为解决几乎任何组织问题的首选方法，包括规模确定。使用系统模型进行前瞻预测。使用与衡量吞吐量时相同的 来预测未来的吞吐量。特别重要的是要将你的 考虑在内，因为招聘和培训更多招聘人员通常会对快速加速招聘产生阻力，而已经雇用的招聘人员又会对快速降低招聘速度产生类似阻力。根据目标和 roadmap 反向预测。基准对比和建模都容易过度拟合当前组织，但有时你想要实现的目标远远超出当前组织的能力。在这种情况下，从未来的目标出发，思考要达成那些目标需要什么，并非常谨慎地忽略你当前的配置。例如，你可以纯粹从财务预测的角度出发，然后思考公司需要什么样的产品或业务才能实现那些目标，再进一步从产品推导到公司规模。系统思维导论用 Systems 库建模招聘漏斗

每种方法都能暴露预测中的不同缺口，因此当你同时使用这三种方法时，估算结果会最有力。一旦你对这三个视角都感到满意，就可以将规模转化为结构了。

结构

一个组织的规模只是一个数字，它的结构才是这些部分如何组合在一起并发挥实际作用的方式。

组织原子

即使最复杂的组织也是由少数简单的组织原子组成的。我用来构建的三个组织原子是：

团队是由 组成的小组，他们有共同的目标、共同的 oncall，并紧密协作。每个团队由一到两个工作流组成，这代表他们并行执行项目的能力。通常我发现三到四名工程师的工作流效果最好，更小的工作流往往意味着未能 。每五个团队组成一个组，由相关且工作相近的团队构成。每个组由一名 group engineering manager 管理，该经理支持组内各团队的经理。在此基础上，以递归方式将每五个组收集到下一个容器中，你可以将其称为 pillar、组织或其他名称。每个容器都有一名工程经理，支持其容器内的各位经理。工程团队的规模设计为什么限制在制品数量有效

在组织设计阶段，你可以基本忽略工作流，因为它们在 roadmap 和 sprint 规划时更重要。我曾纠结是否值得在这里提及，最终决定值得引入，因为它们解决了建立六到八人这样“较大”团队的主要顾虑。即你需要关注的项目数量超过了妥善 sized 的团队数，这常常把人拉向更小的团队：与其这样，不如给一个规模合适的团队增加工作流。

从原子到结构

将规模转化为结构是一个简单过程：

teams  = size   / 8
groups = teams  / 5
org    = groups / 5
# and so on

例如，假设你有六十名工程师：

size   = 60
teams  = 60  / 8 # 7.5 teams
groups = 7.5 / 5 # 1.5 groups
orgs   = 1.5 / 5 # 0.3 orgs

从最大的容器（通常是 organization）开始，递归地在各个容器之间平衡责任范围。

你需要一个 organization，我们称之为工程组织。然后你需要两个组，或许从经典的产品和基础设施拆分开始。接着每个组需要四个团队，根据你的需求进行划分。

当然，这棵树不必任何时候都完美，大多数公司起步时都会更偏向产品工程。

人们很容易在如何精确定义这些组上投入过多精力，但我的经验是，这些决策很容易被过度优化。划分组的方式没有唯一正确答案，但有一些有用的规则可以帮助你找到合理的结构。

预测

现在你已经为接下来一年左右设计好了组织，稍微把规划 horizon 再往后延展一点，会产生惊人的价值。如果你只是为六个月做了规模和结构设计，那么可以尝试再预测到十二个月和十八个月。

预测越远，准确性就越低，因此这些额外规模预测的目标是进行一种粗略的敏感性分析，找出当组织不得不经历重大转型时的临界点。

这些转型通常是增加额外的管理层级，在均衡的工程组织中，大致会在 40 名、200 名工程师，以及后续 8 * 5^N 的序列点出现。

如果你的预测跨越了其中任何一个阈值，就要知道在那段时间你需要投入不成比例的更多时间来教练团队、重新设计流程，并可能需要招聘有经验的外部领导者。

休息

此时你已经完成了组织设计，只剩下一条戒律需要掌握：停止进行组织调整。虽然这些调整感觉有用，但生产力总是发生在组织调整之间，而不是调整期间。

只有在停止调整之后，人们才会开始练习在新结构中工作，慢慢在新的生产路径上建立掌握度。组织越大，需要适应的时间就越长，小团队一年可以承受几次调整，而较大组织有时需要数年的稳定期才能重新积累势头。

一条经验法则是：如果你还没来得及更新衡量指标，就又提出了新的调整方案，那说明你调整得太频繁了。学习需要时间，但这是持续改进组织的唯一方式。

如果说我的管理方法中有一个核心信念，那就是高质量的管理决策会对公司的健康和最终结果产生微妙、持久且决定性的影响。采用结构化、深思熟虑的方式来确定工程组织的规模和结构，并不需要独特的洞见，它是可以学习的，而且确实有效：不妨试试看。
