与 LLM 共同撰写策略

2025-03-15 · 阅读原文

在你的环境准备就绪后，最显而易见的第一件事就是与 LLM 共同撰写一份策略文档。一份好的策略文档不仅要可读，还必须对当前面临的挑战有清晰的认识，并明确如何应对。

本章将涵盖以下内容：

使用元提示（meta prompting）来优化我们撰写策略的初始提示；通过使用经过元提示优化的提示，逐步构建策略文档的每个部分，并利用前一步的输出；将生成的策略清理成格式良好、结构清晰的文档；牢记策略的质量取决于你的思考，快速生成糟糕的推理并不能解决实际问题。

到本章结束时，我们将能在极短的时间内完成一份相当不错的策略文档。

这是《The AI Companion to Crafting Engineering Strategy》中的一章草稿。本书讨论了如何在 LLM 中使用《Crafting Engineering Strategy》来起草、优化和改进工程策略。

完善我们的提示

要与 LLM 共同撰写策略，核心工作是逐步完成 构建工程策略的步骤 中的五个步骤：探索（exploration）、诊断（diagnosis）、细化（refinement）、策略制定（policy）和运营（operations）。在此之前，我们需要先开发用于这些部分的提示。

我们能想到的最简单的提示大致是这样的：

How should I explore a new engineering strategy that answers:
how do we make software architecture decisions in our company?

这个提示会给出一个答案，但根据我的经验，它对“探索策略主题”的过程描述会非常泛化。这在一定程度上是有用的，因为它能提醒我们策略流程，但并不能真正帮助我们共同撰写策略。

从这个基础起点出发，我们可以通过几种方式改进这个初始提示。首先，我们可以制定一个问题陈述，概括策略需要解决的问题。生成该问题陈述的一个有效提示是：

I want to write a 2-3 sentence problem statement for
a new engineering strategy. Asking me one question
at a time until you can write a complete statement for me.

这会引发一系列的来回问答，直到 LLM 收集到足够的信息来撰写它的问题陈述。

除了最初要求生成问题陈述的提示外，我需要回答三个问题才能得到这个更有帮助的问题陈述：

Our engineering organization lacks a clear, consistent process for
making software architecture decisions, leading to friction between
engineers who feel excluded from decisions versus those who feel
slowed down by lengthy approval processes. This ambiguity around
decision-making authority—particularly when a few highly opinionated
engineers can effectively overrule others' work—is reducing overall
engineering velocity and creating frustration across the team.

现在我们可以优化初始提示，用这个问题陈述替换上面临时写的一行字：

# Problem statement
{text of problem statement}

# Request
How should I explore an engineering strategy to solve the
above problem statement?

这往往会生成更有帮助的输出，例如给出具体建议——应该阅读哪本书，或向同事提出什么问题。

尽管如此，生成的文本仍然可以进一步改进。让我们按照 协作的基础（与 LLM 共同使用一本书） 中讨论的方法，进行元提示来提升输出质量。

改进后的提示相当长，因此我建议你自行创建，或者从这个 Gist 中获取。（这里是一个嵌入了问题陈述的版本。）现在我们有了改进后的提示，就可以开始策略创建的第一阶段：探索。

探索

探索的第一步是拿我们的提示，将其更新为专门用于探索：

{... updated prompt ...}

**Your request:** Write an exploration section to
address the above problem statement.

这生成了一个意想不到的全面总结，其完整文本可以在这个 Gist 中阅读。

值得注意的是，虽然这次探索相当有趣，但输出的某些部分听起来合理，却据我所知并不特别准确。例如，我熟悉 Amazon bar raiser 和 Amazon two-pizza teams 这两个概念的大致含义，但它们要么是 overload 的术语（很可能如此），要么只是与技术决策非常抽象地相关。

因此，下一步是将写出来的内容进行编辑，只保留你真正认同且能为其担保的部分。对于我无法担保的部分，我会花时间快速研究来验证或证伪它们。

在我的编辑中，最终只保留了大约一半的原始内容，但剩下的部分都很有价值。我特别欣赏的是，它对不同方法进行了大量综合，并为这些选项提供了一个相当好的框架。与 LLM 合作时，很容易陷入沉没成本谬误，即使你觉得输出并不那么好，也会勉强接受它。你的防御方式是保持对同伴所要求的同样质量标准，而不是降低标准去接受 LLM 生成的内容。

从诊断开始

完成探索后，下一步是回到我们优化后的提示，在问题陈述下方加入探索内容。这样就得到了这个提示。

总体而言，整个诊断是一组相当不错的因素，这些因素在处理这个问题时通常会出现。这就是上下文学习（in-context learning）通过相关示例来塑造更好内容的效果。当然，这并不意味着诊断是完美的，它仍然需要一次有意义的编辑，来使其符合你的具体情况，而不是 LLM 生成的更泛化的版本。

从诊断往后，策略制定（policy）和运营（operations）的步骤保持不变。将前一步编辑后的内容复制到你不断增长的提示中——包括最初的优化提示和所有后续部分——然后让它完成下一步。为了加快进度，我让它一次性生成策略制定和运营两部分，它完成了得相当不错。

总体来说，策略和运营机制都相当合理。它们很大程度上借鉴了《Crafting Engineering Strategy》中介绍的方法，这也是为什么我相信引入这类书籍——来自一位你信任其方法的作者——能让这种方法变得真正有价值。

总结

在本章中，我们与 LLM 共同撰写了一份有价值的策略。为此，我们先对初始提示进行元提示，使其成为一个更有用的工具。然后使用这个优化后的提示依次完成每个步骤，并在每完成一步后将其补充回提示中。最后，我们还使用 LLM 对策略文档进行了清理润色。

重要的是要认识到，策略的每个步骤都建立在前一步的基础之上。出色的探索会创造有力的诊断，而错误的诊断会毁掉后续的策略制定和运营步骤。虽然 LLM 能帮助你快速写作，但这并不意味着产出的质量值得采用。不过，它确实是一个强大的头脑风暴工具，而且——至少在这个例子中——表现得 surprisingly 好。
