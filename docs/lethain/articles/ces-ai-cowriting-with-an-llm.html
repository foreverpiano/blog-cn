与 LLM 共同撰写策略

2025-03-15 · 阅读原文

当你的环境准备就绪后，最显而易见的第一件事，就是与 LLM 共同撰写一份策略文档。一份好的策略文档不仅要易于阅读，还必须对当前面临的挑战有清晰的认识，并明确如何应对。

本章将涵盖以下内容：

使用元提示（meta prompting）来优化我们最初用于撰写策略的提示；通过元提示过的提示逐步构建策略文档，每一步都以前一步的输出为基础；将生成的策略整理成格式良好、结构清晰的文档；记住策略的质量最终取决于你的思考，快速生成糟糕的推理并不能解决真实问题。

到本章结束时，我们将能在极短的时间内写出一份相当不错的策略文档。

这是《The AI Companion to Crafting Engineering Strategy》中的一章草稿，该书讨论了如何在 LLM 中使用《Crafting Engineering Strategy》的方法，来起草、完善和改进工程策略。

完善我们的提示

要与 LLM 共同撰写策略，核心工作是逐步完成 构建工程策略的步骤 中的五个步骤：探索（exploration）、诊断（diagnosis）、细化（refinement）、策略制定（policy）和运营（operations）。在此之前，我们需要先开发将在这些部分使用的提示。

我们能想到的最简单的提示大致是这样的：

How should I explore a new engineering strategy that answers:
how do we make software architecture decisions in our company?

这个提示虽然能给出答案，但根据我的经验，它对“探索策略主题”这个过程的描述会非常泛化。这在一定程度上是有用的，因为它能提醒我们策略流程，但并不能真正帮助我们共同撰写策略。

从这个基础起点出发，我们可以通过几种方式改进这个初始提示。首先，我们可以制定一个问题陈述（problem statement），来概括策略需要解决的问题。创建一个有帮助的问题陈述的提示是：

I want to write a 2-3 sentence problem statement for
a new engineering strategy. Asking me one question
at a time until you can write a complete statement for me.

这会引发一系列来回的提问和回答，直到 LLM 收集到足够的信息来撰写它的问题陈述。

除了最初要求生成问题陈述的提示外，我需要回答三个问题才能得到这个更有帮助的问题陈述：

Our engineering organization lacks a clear, consistent process for
making software architecture decisions, leading to friction between
engineers who feel excluded from decisions versus those who feel
slowed down by lengthy approval processes. This ambiguity around
decision-making authority—particularly when a few highly opinionated
engineers can effectively overrule others' work—is reducing overall
engineering velocity and creating frustration across the team.

现在我们可以优化初始提示，将这个问题陈述替换掉上面那个临时的一行问题描述：

# Problem statement
{text of problem statement}

# Request
How should I explore an engineering strategy to solve the
above problem statement?

这往往会生成更有帮助的输出，例如给出具体建议——应该阅读哪本书，或向同事提出什么问题。

尽管如此，生成的文本仍然可以更加实用。让我们先按照 与 LLM 协作的基础（以一本书为例） 中讨论的元提示方法，来改进输出。

探索

探索的第一步是将我们的提示更新为专注于探索：

{... updated prompt ...}

**Your request:** Write an exploration section to
address the above problem statement.

这生成了一个 surprisingly 全面的总结，你可以在这个 Gist 中阅读完整文本。

值得注意的是，虽然这份探索内容相当有趣，但其中仍有一些地方听起来合理，却据我所知并不特别准确。例如，我熟悉 Amazon bar raiser 和 Amazon two-pizza teams 这两个概念的大致含义，但它们要么是被过度使用的术语（很可能如此），要么只是非常抽象地与技术决策相关。

因此，下一步是将写出来的内容进行编辑，只保留你真正认同且能为其担保的部分。对于那些我无法担保的内容，我会花时间快速研究来验证或证伪它们。

在我的编辑中，最终保留了大约一半的原始内容，但剩下的部分都很有价值。我特别欣赏的是，它对不同方法进行了大量综合，并为这些选项建立了一个相当好的框架。与 LLM 合作时，很容易陷入沉没成本谬误——即使你觉得输出并不是特别好，也会勉强接受它。你的底线应该是保持对同事输出的同等质量要求，而不是降低标准去接受 LLM 生成的内容。

总的来说，完整的诊断是一组相当不错的因素，这些是在处理此类问题时会自然浮现的。这就是“通过相关示例进行的上下文学习”在塑造更好内容方面的强大之处。当然，这并不意味着诊断是完美的，它仍然需要一次有意义的编辑来确保其符合你的具体情况，而非 LLM 生成的泛化版本。

从诊断开始，后续的政策和运营步骤保持一致。将前一步编辑后的内容复制到不断扩展的提示中——包括最初的优化提示和所有后续部分——然后让它完成下一步。为了加快进度，我一次性提示生成政策和运营部分，它完成得相当不错。

总体而言，政策和运营机制都相当合理。它们很大程度上依赖于《Crafting Engineering Strategy》中介绍的各种方法，这也是我相信包含这类书籍（前提是作者的方法你信任）能让这种方法变得有价值的原因。

总结

在本章中，我们与 LLM 共同撰写了一份有价值的策略。为此，我们先通过元提示将一个初始提示打磨成一个更有用的工具。然后使用这个优化后的提示完成每一个步骤，并在每完成一步后将其补充到提示中。最后，我们还使用 LLM 对策略文档进行了整理。

重要的是要认识到，策略的每一步都建立在前一步的基础上。一个优秀的探索会产生强有力的诊断。一个错误的诊断会毁掉后续的政策和运营步骤。虽然 LLM 能帮助你快速写作，但这并不意味着产出的质量就值得采用。不过，它确实是一个强大的头脑风暴工具，而且——至少在这个例子中——表现得 surprisingly 好。
