无服务器架构：把关机制与利润空间

2016-10-16 · 阅读原文

最初，我们使用的是放在负载均衡器后面的服务器。每台同类服务器（API 服务器、前端服务器等）都运行着相同的进程集合，而且每个应用都绑定到每台服务器上同一个静态分配的端口。

这套方案运行得很好！随着时间推移，我们希望能更好地利用那些经常未被充分利用的服务器，而在三年硬件折旧周期内调整 CPU、内存和 IOPS 的配比，速度已经跟不上系统架构快速演进的步伐。

这一需求，加上越来越容易获得的可靠云服务提供商，推动了虚拟机的普及。虚拟机保留了现有的服务器层级抽象，但允许多个虚拟服务器共同驻留在同一台物理服务器上。不过它并没有显著改变负载均衡机制和静态端口分配：所有同类服务器依然运行相同的进程。

虚拟机通过多租户提升了硬件效率，但你会面临两种情况：

如果跑在云上，那么更好的装箱策略带来的好处归云服务提供商所有，而不是你自己；如果跑在自己的硬件上，你很可能是在静态地将虚拟机映射到物理服务器上，优化虚拟机到服务器的分配非常耗时，而且在任何时刻你的分配都相当次优——虽然比虚拟机出现之前要好，因为现在你可以用更小的单元去填充资源池。

随着“开发面向服务的架构”和微服务等模式兴起，单个公司需要运行的定制化进程数量从寥寥数个爆炸式增长到几百甚至几千，手动装箱变得越来越困难。幸运的是，过去几年里，几股长期趋势开始汇聚，终于让手动装箱成为历史！

首先，etcd、Consul 等实时配置机制让刷新配置文件（比如 HAProxy 这类软件负载均衡器）的延迟从几分钟、几小时降低到几秒。这为动态进程调度奠定了重要基础——如果进程被调度到一台服务器后，需要很长时间才能给它发送流量，就无法实现高效的迁移。

接下来，rkt、Docker 等容器技术的出现，将进程的运行环境与所在的服务器清晰地解耦了。这使得基础设施工程师可以将任意无状态服务部署到集群中几乎任意一台服务器上。服务与服务器角色之间静态映射的概念因此被打破：过去你的应用服务器只能运行 Puppet 中定义的特定服务列表，现在一个服务器角色可以运行你所有的服务，而这些服务也不再需要写在配置管理系统里（当然，如果你没有使用调度器，它们还是得定义在某个地方，最终可能还是落在配置管理里）。

（在此郑重说明，我在这里基本忽略了有状态服务，包括数据库等。我的判断是，在大多数基础设施环境中，有状态服务在可预见的未来仍会继续静态映射到特定的服务器角色上。不过随着我们转向 EBS、GFS/Colossus 这类本地存储即服务的技术，或者有状态服务转向足够小的重叠分片模型，使得重建丢失节点成为一个可以在后台持续发生且不会影响系统行为的 trivial 事件，这种情况最终会改变。）

最后，在实时配置驱动服务发现和容器允许单一服务器角色承载所有无状态服务的基础上，我们正在进入进程调度技术的黄金时代——像 Kubernetes 和 Mesos 这样的系统，将我们从周期性的人工或脚本驱动的静态分配，提升到了接近实时的动态分配（可能每小时或每天发生一次，但肯定比手动重新平衡集群快得多）。

从基础设施角度看，这些趋势结合在一起，产生了相当惊人的效果！

首先，我们从静态端口分配转向了动态端口分配，因此可以在一台服务器上运行同一个应用的多个副本（你也可以一个实例都不跑，从而比静态映射服务到服务器角色时更少浪费资源在闲置服务上）。

接下来，我们能够动态扩展服务，把 AWS 自动扩缩组带来的优化（以及痛苦）带到自己的基础设施中，即使我们跑在物理硬件上。这提供了一个程序化接口来自动化高效的装箱，让我们无需伤害任何人就能获得可观的成本和效率收益。

最重要的是，我们在编写和维护进程的产品工程师，与提供调度这些进程的平台的基础设施工程师之间，实现了现象级的关注点分离。服务所有者可以为自己的需求选择合适的工具，基础设施团队则可以在完全不关心容器内容的情况下运行构建好的容器，双方依靠 QoS、成本与配额 产生的背压来共同引导出一个可持续的平衡，而无需静态服务到服务器映射模型所带来的前期把关和紧密协调。

上述模型仍然依赖能够接受路由请求的持久进程，或者让持久进程从队列中拉取任务，但无论哪种情况，进程都是长期运行的。当我们开始深入分析服务的实际使用模式时，会发现大量服务几乎没有流量，但我们仍然至少要为冗余而运行三个实例。

设想我们开发一个新的调度器，它不调度正在运行的进程，而是预先将容器分布到你的整个集群中，这样你就可以直接启动容器内的进程，而无需先把容器的内容复制到服务器上。再假设我们的服务器有本地 SSD，或者我们拥有足够快的网络本地存储，能在几毫秒内读出容器。这将让每台服务器都有潜力运行几百甚至几千个服务。

基于这些预置的容器，假设我们可以在几百毫秒内启动其中一个。现在，发送到负载均衡器的请求看起来会有些不同：

如果当前没有正在运行的实例，就请求调度器启动一个预置的容器；否则路由到已有的容器。

这样，我们只需要持久运行那些有频繁流入流量的进程。对于每秒请求数低于 2 次的服务，立即回收会更高效——虽然具体的数学模型还取决于我们对延迟成本的容忍程度。吞吐量应该不是大问题，因为如果出现流量峰值，我们可以将启动成本分摊到多个请求上。对于超过单个进程容量的吞吐量，我们可以让负载均衡器变得更智能——如果服务的延迟上升过高就自动增加容量（同时需要某种机制防止在异常情况下出现无限自动扩容）。

这相当棒，从调度基础设施和基础设施工程的角度看，我们将每个新服务的增量成本降低到了接近零。但这里也发生了两件有趣的事情：

首先，虽然我们把新服务的基础设施成本降到了接近零，但服务所有者维护大量服务的**人力成本**并没有下降。情况恰恰相反：历史上，引入更多基础设施的摩擦在一定程度上无意中限制了公司内部库和框架的数量。没有了这些约束，公司往往缺乏阻止引入新技术的“免疫系统”，技术的种类就会随着时间、开发者人数或者两者一起线性增长！

另一个问题是，虽然创建服务的摩擦降低了，而且根据你的工作负载，运行服务的成本现在更多受磁盘成本而非 CPU/内存限制，你仍然要为每个服务支付一定的固定成本。要把这个成本压到最低，主要取决于容器的大小，而容器大小差异极大。看看 Docker 的分层系统，如果你能推动框架和依赖的高度统一，就能把每个容器占用的空间缩小到惊人小的程度。

（在活跃负载方面，底层平台的成本效率也很大程度上取决于编程语言。因此我猜我们会看到大量无服务器应用转向 Go 这样 CPU 和内存效率极高的语言。Node.js 似乎是早期的关注点，尽管它在 CPU 和内存效率上并不突出，而且垃圾回收器的延迟也比较高，但它相对独立于底层操作系统，并且拥有庞大的库和开发者生态。在早期阶段，推动采用和效率可能确实更为重要。）

在我看来，这就是驱动无服务器架构被广泛采用的两个核心关切：一方面，企业希望在基础设施摩擦不再充当无意识把关者的情况下，重新获得对软件的集中控制；另一方面，云服务提供商则通过 AWS Lambda 和 Cloud Functions 等产品，在他们大规模多租户的云环境中进一步提升成本效率。

但这些都不是我们不应该转向无服务器架构的理由！

如果云能变得更具成本效率，那当然很好，尤其是当你自己在运行内部云的时候。虽然我对自上而下的架构把关模式持怀疑态度，但也很清楚，大多数公司都很难找到一种有效的替代方案，来引导团队做出对公司整体最优而非仅对团队局部最优的决策。（不过如果我们套用《创新者的窘境》的教训，似乎短期内对公司最优的选择，从长期来看可能反而对公司是次优的。）

我的最后一个想法是，我怀疑开发无服务器应用的感觉会更接近开发单体应用，而不是开发微服务。尽管它们作为独立的代码单元被调度，甚至可能被独立部署，但极致的精简会迫使它们严重依赖所运行的框架。你要么回到单体应用变更协调的挑战，要么陷入退化版的微服务场景——必须为每一个函数单独迁移到新版本。前者听起来要愉快得多。
