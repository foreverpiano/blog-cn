无服务器架构：守门机制与利润空间

2016-10-16 · 阅读原文

最初，我们有置于负载均衡器后面的服务器。每台同类服务器（API服务器、前端服务器等）都运行着相同的进程集合，每个应用都绑定到每台服务器上同一个静态分配的端口。

这种方式运行得很好！随着时间推移，我们希望更好地利用那些经常未被充分利用的服务器。而在三年硬件折旧周期内调整 CPU、内存和 IOPS 的比例，无法跟上系统架构快速演进的速度。

这种情况，加上越来越容易获取可靠的云服务提供商，共同推动了虚拟机的采用。虚拟机保留了现有的服务器级抽象，但允许多个虚拟服务器在一台物理服务器上共存。不过它并没有显著改变负载均衡机制或静态端口分配：所有同类服务器依然运行相同的进程。

虚拟机通过共存提升了硬件利用率，但你会面临两种情况：

在云上运行，这种情况下改进的装箱策略惠及的是云服务提供商，而不是你。在自有硬件上运行，这种情况下你很可能在静态地将虚拟机映射到服务器上，改进虚拟机到服务器的分配非常耗时，而且在任何时刻你的分配都相当次优——尽管比虚拟机出现之前要好，因为现在你可以用更小的单元来进行装箱。

随着 开发面向服务的架构 和微服务等模式兴起，手动装箱变得越来越有挑战性，它让一家公司需要运行的定制化进程数量从寥寥几个激增到数百甚至数千。幸运的是，过去几年里，几股长期趋势开始汇聚，共同让手动装箱变得过时！

首先，etcd 和 consul 等实时配置机制，让刷新配置文件（例如像 HAProxy 这样的软件负载均衡器）的延迟从几分钟或几小时缩短到几秒。这为动态进程调度奠定了重要基础，因为如果进程被调度到服务器和为其发送流量之间存在很长的延迟，你就无法高效地迁移进程。

接下来，rkt 和 Docker 等容器技术的兴起，清晰地将进程的运行环境与其所在服务器解耦，使得基础设施工程师可以将任何无状态服务部署到机群中几乎任意一台服务器上。这逐渐消解了服务与服务器角色之间的静态映射概念：过去你的应用服务器会运行由 Puppet 定义的特定服务列表，现在一个服务器角色可以运行你所有的服务，而且这些服务也不再需要定义在你的配置管理系统中（当然，如果你没有使用调度器，它们仍然需要在某个地方定义，可能最终还是落在你的配置管理中）。

（在此致歉，我在这里基本忽略了有状态服务，包括数据库等。我的感觉是，在大多数基础设施环境中，每个有状态服务在相当一段时间内仍会静态映射到某个服务器角色。这种情况最终会改变，当我们转向 EBS 和 GFS/Colossus 等本地存储即服务技术，或者当有状态服务采用足够小的重叠分片模型，使得重建丢失节点成为一个可以在后台持续发生的琐碎事件，而不会降低系统性能。）

最后，基于实时配置驱动服务发现和容器允许所有无状态服务共享一个服务器角色，我们正在进入进程调度的黄金时代，比如 kubernetes 和 mesos，它们将我们从周期性的人工或脚本驱动的静态分配，提升到接近实时的动态分配（也许是每小时或每天一次，但肯定比等待人工重新平衡集群快得多）。

从基础设施视角来看，这些趋势结合在一起，形成了相当了不起的结果！

首先，我们从静态端口分配转向动态端口分配，这样你就可以在一台服务器上运行某个应用的多个副本。（你也可以不运行任何实例，从而比静态映射服务到服务器角色时，在闲置服务上浪费更少的资源。）

接下来，我们能够动态扩展服务，将 AWS 自动扩容组的优化（以及随之而来的痛苦）带到我们的基础设施中，即使我们运行在物理硬件上。这为我们提供了一个程序化接口来自动化高效的装箱，让我们可以在不伤害任何人类的情况下获得可观的成本和效率收益。

最重要的是，我们在编写和维护进程的产品工程师与提供调度这些进程的平台的基础设施工程师之间，实现了出色的关注点分离。服务所有者可以为自己的需求选择合适的工具，基础设施可以运行构建好的容器而无需了解其内容，双方便依靠来自 QoS、成本与配额 的反压机制来引导双方达到可持续的平衡，而无需像静态服务到服务器映射模型那样引入前置的守门机制和紧密协调。

上述模型仍然依赖能够接受路由请求的持久化进程，或者也可以是持久化进程从队列中拉取消息，但无论哪种情况，进程都是长期运行的。当我们开始深入分析服务的实际使用模式时，会发现大量服务几乎没有流量，但我们仍然至少运行三个实例以实现冗余。

假设我们创建一个新的调度器，它不调度进程，而是预先在你的机群中放置好容器，这样你就可以直接启动容器内的进程，而无需先把容器内容复制到服务器上。现在再假设我们的服务器上有本地 SSD，或者我们有足够快的网络本地存储，能在几毫秒内读取容器。这将让你的每台服务器都有潜力运行数百乃至数千个服务。

如果当前没有正在运行的实例，就请求调度器启动一个预置的容器。否则路由到已有的容器。

如今，我们只需要持久运行那些有频繁传入流量的进程。对于每秒请求少于两次的服务，立即回收通常更高效，尽管具体计算还取决于我们对延迟成本的重视程度。吞吐量应该不是大问题，因为如果出现流量峰值，我们可以将启动成本分摊到多个请求上。对于超出单个进程容量的吞吐量，我们可以让负载均衡器变得更智能，在服务延迟过高时自动增加容量（同时要加上某种机制来防止在退化情况下发生无限自动扩容）。

这相当棒，从调度基础设施和基础设施工程的角度来看，它将每个新增服务的边际成本降低到了几乎为零，但这里发生了两件有趣的事情：

首先，虽然我们把新服务的基础设施成本降到了接近零，但服务所有者维护大量服务的**人力成本**并没有下降。情况恰恰相反：历史上，引入更多基础设施的摩擦在一定程度上无意中限制了公司内部库和框架的数量。在没有这些约束的情况下，公司往往缺乏阻止引入新技术的“免疫系统”，技术的数量便开始随着时间、开发者人数或两者同步线性增长！

另一个问题是，虽然创建服务的摩擦降低了，而且根据你的工作负载，运行服务的成本现在更多受磁盘成本而非 CPU/内存限制，你仍然要为每个服务支付一定的固定成本。要将这个成本降到最低，主要取决于容器大小，而容器大小差异很大。观察 Docker 的分层系统，如果你能推动形成高度统一的框架和依赖栈，那么每个容器的空间占用可以缩小到惊人的程度。

（在活跃负载方面，底层平台的成本效率也很大程度上取决于编程语言，因此我预计我们会看到大量转向 Go 这类高 CPU 和内存效率的语言来开发 serverless 应用。Node.js 似乎是早期的关注重点，虽然它在 CPU 和内存效率上并不突出，而且垃圾回收器的延迟也比较高，但它与底层操作系统耦合度较低，并且拥有庞大的库和开发者生态。在早期阶段，推动采用和效率可能更为重要。）

在我看来，这两点正是推动 serverless 采用的核心驱动力：一方面，公司希望在基础设施摩擦不再充当无意识守门人的情况下，重新获得对软件的集中控制；另一方面，云服务提供商通过 AWS Lambda 和 Cloud Functions 来提升其大规模多租户云的成本效率。

这些都不是我们不应该转向 serverless 的理由！

如果云能变得更具成本效率，那就太好了，尤其是当你自己运行内部云的时候。虽然我对自上而下的守门式架构持怀疑态度，但也很清楚大多数公司都在努力寻找一种有效的替代方案，来引导团队做出有利于公司的决策，而不是只考虑团队局部利益。（不过，如果我们应用《创新者的窘境》的教训，似乎短期内对公司最优的选择，长期来看可能对公司其实是次优的。）

我的另一个结尾想法是，我怀疑开发 serverless 应用的感觉会更像开发单体应用，而不是开发微服务。尽管它们作为独立的代码单元被调度乃至部署，但极致的极简主义会迫使它们严重依赖所运行的框架，你要么回到单体应用的变更协调难题，要么陷入退化的微服务场景——必须为每个新版本逐个迁移每一个函数。前者听起来要愉快得多。
