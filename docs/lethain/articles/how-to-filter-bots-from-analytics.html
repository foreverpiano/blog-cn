如何从分析数据中过滤掉机器人流量

2011-04-03 · 阅读原文

尽管已经有大量现成的方案，人们还是不断重复造分析数据的轮子。甚至可以说，这样做可能确实有一些充分的理由。但与其讨论自建分析系统的优缺点，我更想谈谈如何从你已经搭建好的自研方案中，过滤掉机器人和脚本产生的流量。

机器人流量的困扰

没有什么比发现自己网站的流量在过去几周翻了一倍更让人兴奋的了。然而，当你使用的是刚上线的手工打造的分析系统时，进一步挖掘很可能会发现，某些 IP 产生的请求量相当于其他 95% 的 IP 总和。（如果你的网站规模足够大，足以成为 SEO、社交媒体或普通垃圾信息的单独攻击目标，这种情况尤其常见。）

幸运的是，污染分析数据的自动化流量相对容易控制。具体的解决方案主要取决于你是想收集实时分析数据，还是定期对日志进行汇总处理（或者可能是某种混合模式）。

定期汇总

通过定期汇总生成分析数据是一个相当直接的过程。一个简单的方法是找出每个 IP 的请求数量中位数，并将该中位数作为汇总时可接受的请求上限。这种方法存在（至少）两个问题：首先，它会得出一个极为保守的数值；其次，它会掩盖你最活跃（但仍然合法）用户身上有趣的行为模式。

如果你假设总的唯一 IP 数量远多于非法 IP 的数量（实际情况通常如此：虽然每个非法 IP 产生的页面浏览量可能极高，但它们的数量相对较少），那么你可以采用更宽松的计算方式——将每个 IP 承认的最大页面浏览量上限设为平均值（而非中位数）加上一个标准差。这会引入少量异常行为，但当你看到极少数 IP 就产生了绝大多数自动化流量时，就可以计算出预期的超额部分，而这个数值通常会相当低。（如果你稍微懒一点，也可以只在有代表性的一天计算一次上限，然后将其视为常量，而不必每天都重新运行查询来更新它。）

做了这个简单的改动之后，你的分析数据就会变得更具可操作性。当然，某个黑客用四台 AWS 实例消耗了你网站 25% 的资源，但至少你不再 falsely 认为用户的参与度正在火箭式飙升。

MySQL、Hive 以及你用来存储分析数据的大多数其他数据库，都内置了计算均值和标准差的函数或 UDF，因此这些方法在实际中都很容易实现。

实时分析

对于从实时分析系统中过滤自动化流量，我们会采用与定期汇总类似的方法，但无法像汇总那样看到用户在整个周期内会执行的完整行为集合。我们也没有办法在周期结束后（例如一天结束之后）重新进行计算，这也是强烈建议采用混合模式——用定期汇总的结果逐步替换实时数据的一个重要理由。（隐含的代价是，变化的数字可能会把大多数分析用户搞得一头雾水。）

因此，我们的解决方案需要为每个被跟踪的指标维护滚动总额，同时记录每个 IP 在最近一段时间内的活动，以便知道何时开始丢弃它的数据。（值得一提的是 Interactive Advertising Bureau 关于这个主题的指南，我的一位老同事 Anton Kast 曾推荐我研究它。）由于自动化活动往往集中在短时间内爆发，一个好的起点是每分钟只统计某个 IP 的第一次行为。

这个方案可以用 Redis 来实现：用不过期的 Key 存储指标计数器，而用会在一分钟后过期的 Key 来跟踪 IP 活动。稍作调整，你就可以构建更复杂的过滤逻辑（比如每 IP 每天只统计 50 次行为），但通常来说，简单的“每分钟一次行为”方法就能很好地完成过滤工作，而且只需要记录一分钟内的唯一 IP，而非一整天的。
