先写五个，再提炼：好的工程策略其实很无聊。

2020-11-26 · 阅读原文
我一直觉得写工程策略很难，因为好的策略通常都很无聊，写起来也挺没意思的。而且人们一听到“策略”就容易联想到“创新”——Camille Fournier

很少有公司真正理解自己的工程策略和愿景。这种不确定性导致业界普遍认为这类文档很难写。有时候聊起来感觉像在讨论某种玄学，但其实它们只是非常普通的文档。现实是，好的工程策略往往很无聊，而且写一份有效的策略比写一份糟糕的策略要容易得多。

要写工程策略，先写五份设计文档，然后把其中的共性提炼出来，这就是你的工程策略。要写工程愿景，先写五份工程策略，然后推断它们在未来两年会产生什么影响，这就是你的工程愿景。

如果你忍不住想把最 brillante 的想法塞进这个过程，那就先在预备工作中处理掉。把所有最棒的想法都写进一个大文档里，然后删掉它，之后永远不要再提起。现在这些想法已经从你脑子里清空了，你可以专心做眼前的事。

真正持久有用的工程策略和愿景，来自迭代式的、自下而上的组织学习。因此，所有学习都在为组织的策略和愿景做贡献，但你的贡献不必那么抽象。即使你不是直接负责这项工作，你仍然可以采取一些实际行动来推进组织的策略和愿景，而且现在就可以开始。

这是对我之前文章的改写，工程策略。。特别感谢 Julia 和 Camille 给出的改进建议。

写五份设计文档

设计文档描述了你在具体项目中做出的决策和权衡。你公司可能把它们叫做 RFC 或技术规格书，也可能会有更奇怪的名字；Uber 曾经莫名其妙地把它们叫做 DUCKS，后来才统一改成 RFC。一份好的设计文档会描述一个具体问题，调研可能的解决方案，并详细解释最终选定的方案。有很多格式可以选择，你可以从《Design Docs, Markdown, and Git》和 Google 的《Design Docs at Google》开始了解。

一个项目是否需要写设计文档最终取决于个人判断，但我发现以下几条规则很有用：任何其能力会被后续多个项目复用的项目，都应该写设计文档；对用户有显著影响的项目也应该写；任何需要超过一个月工程时间的工作，都应该写一份设计文档。

五份设计文档是写出一份有效策略的理想材料，因为设计文档拥有糟糕策略所缺乏的东西：基于现实的详细具体内容。两个善意的工程师在同一团队里，很容易对一份抽象的策略产生不同解读；但当你们在实现一个具体方案时，要保持不一致就困难得多了。

以下是写作时的一些建议：

从问题开始。问题陈述越清晰，解决方案就越明显。如果解决方案不明显，就花更多时间把问题澄清。如果你卡在如何表述问题上，那就把你写的东西拿给五个人看，问他们还缺什么——旁观者清。保持模板简洁。大多数公司都有设计文档模板，这是个很好的模式。但这些模板常常为了满足太多目标而被过度扩展。过于繁重的模板反而会 discourage 人们写文档。优先选择极简的设计文档模板，让作者能挑选最有用的部分，只对风险最高的项目要求详尽细节。一起收集和评审，独自写作。你个人不太可能拥有写出某个主题最佳设计文档所需的全部上下文。在深入写作前，先从有相关视角的人那里收集输入，尤其是那些会依赖你这份设计文档输出的人。但要警惕把这种协作过程一直带到实际写作中。大多数人写作能力都强于编辑能力，这意味着把一份集体文档改成清晰的文字，通常比指定一个人写一份清晰文档更难。广泛收集视角，但独自写作。只是要注意，在和别人一起评审之前，不要太爱上自己写的东西。宁要良好，不要完美。写出一份好的文档并尽早给别人看，比拖延着追求稍微更好一点要强得多。这一点在给他人设计文档提反馈时尤其重要，我们很容易陷入要求别人的设计必须和自己最好水平一样高的陷阱。尤其是当你越来越资深时，把每个设计都推到你个人最佳水准是有害的。重点是把设计推向“良好”，而不是把你自己的最佳当成衡量标准。

写出优秀的设计文档需要大量练习。如果你想改进自己的文档，我最好的建议是：在项目实现完成后重新阅读你的设计文档，研究实现与原计划出现偏差的地方——是什么导致了这些偏差？当然，还有就是多写、多写、多写。

把这五份设计文档提炼成一份策略

当你的组织写完五份设计文档后，坐下来把它们放在一起读。寻找那些在多个文档中反复出现的争议性决策，尤其是那些很难达成一致的。我最近的一个例子是反复纠结 Redis 到底适合作为持久化存储，还是只能用作缓存。与其每次评审设计文档都从零开始讨论，不如把我们最近关于 Redis 的决策拿出来复习一下，思考当时是如何决定的，然后把结论写成一份策略？

好的策略会指导权衡，并解释这种指导背后的逻辑。糟糕的策略只陈述政策却没有解释，把策略和它产生的上下文割裂开来。没有上下文，策略很快就会变得难以理解——他们当时为什么要这么决定？——也难以随着底层上下文变化而调整。在思考如何写自己的策略时，可以读一些有意思的策略作为参考，比如《A Framework for Responsible Innovation》和《How Big Technical Changes Happen at Slack》。

如果你读过《Good Strategy, Bad Strategy》（这本书彻底改变了我对策略的看法），你会发现这里对策略的定义对应书中的“诊断”和“指导政策”部分，而把“连贯行动”留给了设计文档。

关于写策略文档，我最好的建议是：

从你现在所在的位置开始。在做策略工作时，很容易被固有的巨大模糊性所麻痹，但你必须一头扎进去开始写。等待缺失的信息是没用的：每个缺失的文档都是因为正当理由才缺失的。你写的任何东西将来都需要修改，如果你写得特别糟糕，你会很快意识到需要改。现在所在的位置永远是最好的起点。写具体的东西。写到你开始泛化的时候就停下来。如果你无法具体描述，那就等你写完更多设计文档再说。具体表述能创造真正的对齐；泛泛而谈只能制造对齐的幻觉。要有观点。好的策略都是有观点的。如果没有观点，就无法为决策提供清晰指引。不过，光有观点还不够，你还需要……展示你的推理过程。上学时上数学课，你必须展示解题过程才能拿满分。在这里也一样，你必须展示你观点背后的逻辑。展示推理过程能让文档的第一版建立信任，更重要的是，它让其他人能在底层上下文发生变化时，修改和扩展你的工作。

你写过的最好的某些策略，当时可能会觉得太显而易见，根本不值得写。“我们什么时候应该写设计文档？”是一份值得写的策略。“哪些数据库适合哪些使用场景？”也是一份值得写的策略。“哪些服务需要在非工作时间负责 oncall？”同样值得写。当我们放弃把策略看作永久的 brilliance 后，我们就可以写更多策略，而且可以写得更随意。如果最后没被用到，你随时可以弃用它。

把五份策略外推成一份愿景

随着你收集的策略越来越多，要理清不同策略之间如何相互影响会变得越来越困难。比如你的一个策略是“少跑自有软件，多依赖云服务”，但另一个策略是“尽可能把复杂度卸载到数据库”。如果出现了一个能帮你卸载大量复杂度的数据库，但它并不是你当前云厂商提供的服务，那你该如何协调这两个策略呢？

拿你最近的五份策略，推断它们的权衡在未来两到三年会如何演变。在编辑这些矛盾、把不同线索编织在一起的过程中，你就已经写出了一份工程愿景。最终版本会给你 Tanya Reilly 所说的“对未来的稳固信念”，这会让你更容易理解现有策略之间的关系，也会简化撰写新策略的工作，让它们更能经受时间的考验。

要写一份有用的愿景，需要重点关注以下几点：

写两到三年后的情况。公司、组织和技术变化都足够快，想得太远会有问题。如果你写的愿景六个月后就失效也不行——在那六个月窗口里你 realistically 能写多少策略呢？尽量把焦点放在两到三年后，如果你所在的公司已经相当成熟，可以把时间线稍稍拉长一些。植根于业务和用户。有效的愿景会把自己牢牢锚定在服务用户和业务上。这种紧密联系能让愿景与领导团队的核心价值观（用户和业务）保持一致。糟糕的愿景把技术 sophistication 当作自我正当化的 raison d’être——这种观点从来不会被公司领导层认同。要乐观，但不要狂妄。愿景应该有雄心，但不应该狂妄。它应该是可能的，但要是可能范围里最好的版本。可以写如果每个项目都按时完成且没有重大挫折，你能达成什么。不要写你认为用无限资源可能达成的目标。保持具体和明确。愿景越具体就越有用。泛泛而谈容易获得认同，但无法帮助协调相互冲突的策略。细节写得比你舒服的程度再多一点。愿景中的细节通常是说明性的而非宣告性的，是为了让人尝到未来的味道，而不是给出具有约束力的承诺。控制在一到两页以内。现实是大多数人不会读很长的文档。如果你写五六页，读者很可能还没读完就开始流失（或者快速扫读而不深入细节）。强迫自己写得精炼一些，并通过链接其他文档来提供额外上下文，给那些想要完整细节的人。

写完愿景后，人们通常第一步就是把它广泛分享给整个工程团队。愿景背后有那么多工作——每份策略背后有五份设计文档，五份策略才有一份愿景——写完的时候很难不兴奋。因此，当大家对它的反应几乎总是平淡的时候，很容易感到沮丧。

反应平淡有几个原因。首先，愿景的核心受众是那些写策略的人，这是一个相对较小的群体。其次，一份伟大的愿景通常会明显到让人觉得无聊，而不是兴奋。不要用它最初带来的兴奋程度来衡量愿景。而是去读两年前的一份设计文档，再读上周的一份；如果有明显进步，那么你的愿景就是好的。

什么时候写，为什么写

现在你有了一套做出有效策略和愿景的办法，一个很好的后续问题是：“我究竟应该什么时候、为什么要去创建它们？”策略是主动对齐的工具，它能让团队快速且自信地前进。策略让每个人——而不仅仅是少数被授权的人——都能快速、自信地做决策，而这些决策 otherwise 可能需要花一周时间讨论。策略也是砖块，它们把你众多可能的未来收窄到足够小的范围，让写一份现实的愿景成为可能。

当同一个讨论重复了三四次的时候，就是时候再写一份策略了。当未来太过模糊以至于无法判断哪些投资值得做的时候，就是时候再写一份愿景了。如果这两者听起来都不像你正在面临的问题——那就先去做其他工作，之后再回来。
