先写五个，再提炼：好的工程策略本就平淡无奇。

2020-11-26 · 阅读原文
我一直觉得写工程策略很难，因为好的策略往往相当平淡，写起来也挺无聊的。而且人们一听到“策略”就容易联想到“创新”。——Camille Fournier

很少有公司真正清楚自己的工程策略和愿景。这种不确定性导致行业里普遍认为这类文档很难写。有时候讨论起来仿佛在谈论某种神秘的东西，但实际上它们只是再普通不过的文档。现实是，好的工程策略本就平淡无奇，而且写一份有效的策略往往比写一份糟糕的更容易。

要写工程策略，先写五份设计文档，然后从中提炼出共性，那就是你的工程策略。要写工程愿景，先写五份工程策略，然后推演它们在未来两年的影响，那就是你的工程愿景。

如果你忍不住想把最 brilliant 的想法塞进这个过程，那就在前期准备里一次性写完吧。把你所有最好的想法都写进一个大文档，然后删掉它，之后再也不提起。现在这些想法已经从你脑子里清空了，你可以专心做眼前该做的事。

真正持久有用的工程策略和愿景，是通过迭代的、自下而上的组织学习产生的。因此，所有的学习都在为组织的策略和愿景做贡献，但你的贡献不必那么抽象。即使你不是直接负责这项工作的人，你依然可以采取一些实际行动来推动组织的策略和愿景，现在就可以开始。

这是我早期文章《工程策略。》的改写版本。特别感谢 Julia 和 Camille 给出的改进建议。

写五份设计文档

设计文档记录你在具体项目中做出的决策和权衡。公司可能把它们叫做 RFC 或技术规格书，也有些奇怪的名字；Uber 曾经令人困惑地称之为 DUCKS，后来才统一改用 RFC。一份好的设计文档会描述一个具体问题，调研可能的解决方案，并详细解释所选方案的细节。有很多格式可以选择，几个值得参考的起点是 Design Docs、Markdown、and Git 以及 Google 的 Design Docs。

一个项目是否需要写设计文档最终取决于个人判断，但我发现以下几条规则很有用：任何其能力会被后续多个项目使用的项目，都应该写设计文档；对用户有实质影响的项目，也应该写；任何耗时超过一个月工程时间的项目，都应该写一份设计文档。

五份设计文档是写出有效策略的最佳原料，因为设计文档具备糟糕策略所缺乏的东西：基于现实的详细具体内容。两个善意的工程师在同一个团队里，很容易对一份抽象的策略产生不同解读；但当他们在实现一个具体方案时，就很难继续保持不对齐。

以下是写作时的一些建议：

从问题开始。问题陈述越清晰，解决方案就越明显。如果解决方案不明显，就多花时间澄清问题。如果你卡在如何清晰表达问题上，那就把目前写的内容给五个人看，问他们还缺什么——旁观者清。保持模板简单。大多数公司都有设计文档模板，这是个很好的模式。但这些模板常常被扩展得承载了太多目标，导致人们一开始就不想写。建议使用极简的设计文档模板，让作者能选择最有用的部分，只对风险最高的项目要求详尽细节。一起收集和评审，独自写作。你个人几乎不可能拥有写出某个主题最佳设计文档所需的全部上下文。在深入写作前，先从有相关视角的人那里收集输入，尤其是那些会依赖你这份设计文档输出的人。但要警惕把这种协作过程带入实际写作环节。大多数人写作能力都强于编辑能力，这意味着把一份集体文档编辑成清晰的文字，通常比指定一个人写出一份更清晰的文档要难。广泛收集视角，但独自写作。只是要注意，在和别人评审之前，不要太迷恋自己写的东西。更看重良好而非完美。写出一份好的文档并尽早给别人看，比拖延着追求稍微好一点的版本要强。这一点在给别人设计文档提反馈时特别重要——我们很容易陷入要求别人的设计必须达到自己最好水平这样的陷阱。尤其是当你越来越资深时，把每个设计都推到你个人最佳水准是有毒的。应该把重点放在推动设计达到“良好”这个标准，而不是把你自己的最佳水平当作唯一质量标杆。

写出优秀的设计文档需要大量练习。如果你想改进自己的文档，我最好的建议是：在项目实现完成后重新阅读你的设计文档，仔细研究实现与计划不一致的地方——是什么导致了这些偏差？当然，还有就是持续多写。

把这五份设计文档提炼成一份策略

当你的组织已经写完五份设计文档后，坐下来把它们一起读一遍。寻找那些在多个设计中反复出现的争议性决策，尤其是那些很难达成一致的。我最近的一个例子是反复讨论 Redis 到底适合作为持久化存储，还是只能用作缓存。与其每次评审设计文档都从零开始辩论，不如把我们最近关于 Redis 使用所做的决策回顾一遍，思考当时是如何决定的，然后把结论写成一份策略，这样不是更容易吗？

好的策略会指导如何做权衡，并解释这样指导的理由。糟糕的策略只陈述政策却没有解释，把策略和它产生的上下文割裂开来。没有上下文，策略很快就会变得难以理解——他们当初为什么这么决定？——而且也难以随着底层上下文变化而调整。在思考如何写自己的策略时，值得一读的几个有趣策略包括《A Framework for Responsible Innovation》和《How Big Technical Changes Happen at Slack》。

如果你读过《Good Strategy, Bad Strategy》（这本书彻底改变了我对策略的思考），你会发现我这里对策略的定义对应书中的“诊断”（diagnosis）和“指导原则”（guiding policies）部分，而把“连贯行动”（coherent action）留给了设计文档。

关于如何写策略文档，我最好的建议是：

从你现在所处的位置开始。做策略工作时，很容易被工作中固有的巨大模糊性所麻痹，但你必须一头扎进去开始写。等待缺失的信息是没用的：每一份缺失的文档都有它缺失的正当理由。你写的东西将来都会需要修改，如果你写得特别糟糕，你会很快意识到必须改。现在所在的位置永远是最好的起点。写具体的内容。写到你开始泛化的时候就停下来。如果你写不具体，那就等你多写几份设计文档之后再说。具体陈述能创造真正的对齐；泛泛而谈只会制造对齐的幻觉。要有鲜明观点。好的策略都是有观点的。如果没有观点，就无法为决策提供任何清晰指引。不过，光有观点还不够，你还需要……展示你的推导过程。就像小时候上数学课必须写出解题步骤才能拿满分一样，在这里你也必须展示观点背后的理由。展示你的推导过程能让文档第一版就建立信心，更重要的是，它让其他人能在底层上下文发生变化时，得以修改和扩展你的工作。

你写过的最好的策略里，有些当时可能会觉得太过显而易见而不值得写。“我们什么时候应该写设计文档？”就是值得写成策略的内容。“哪些数据库该用在哪些场景？”值得写。“哪些服务需要在非工作时间负责 paging？”也值得写。当我们不再把策略当作某种永恒的智慧结晶时，我们就能写出更多的策略，而且可以写得更随意。如果后来发现没被用到，随时可以废弃它。

把五份策略外推成一份愿景

随着你积累的策略越来越多，理解不同策略之间如何相互作用也会变得越来越困难。比如你的某条策略是“少自己跑软件，多依赖云服务”，但另一条策略是“尽可能把复杂性卸载到数据库”。如果你发现有一个数据库能帮你卸载大量复杂性，但你的云厂商却没有提供，你该如何协调这两条策略呢？

拿五条你最近的策略，推演它们的权衡在未来两到三年会如何展开。当你梳理完其中的矛盾、把各种线索编织在一起时，你就已经写出了一份工程愿景。最终版本会给你带来 Tanya Reilly 所说的“对未来的坚实信念”（robust belief in the future），这会让你更容易理解现有策略之间的关系，也会让后续编写经得起时间考验的新策略变得更简单。

要写出有用的愿景，需要重点关注以下几点：

写两到三年后的情况。公司、组织和技术变化都足够快，思考太远的未来充满风险。同样，如果你的愿景只能维持六个月，那也不行——在那六个月窗口里你 realistically 能写出多少策略呢？尽量把焦点放在两到三年后，如果你所在的公司已经比较成熟，可以把这个时间 horizon 稍微拉长一点。扎根于你的业务和用户。有效的愿景会牢牢扎根于服务用户和业务。这种紧密联系能让愿景与领导团队的核心价值观（用户和业务）保持一致。糟糕的愿景把技术 sophistication 当作自我证明的目的和 raison d’être——这种观点从来不会被公司领导层认同。要乐观而不是狂妄。愿景应该有雄心，但不应该狂妄。它应该是可能的，但要是可能范围里最好的那个版本。可以写如果每个项目都按时完成且没有重大挫折，你能达成什么。不要写你认为在无限资源下可能达成的目标。保持具体和落地。愿景越具体就越有用。泛泛而谈很容易获得认同，但无助于协调冲突的策略。细节写得比你觉得舒服的程度再多一点。愿景中的细节通常是说明性的而非宣誓性的，目的是让人尝到未来的一点味道，而不是给出具有约束力的承诺。控制在一到两页的长度。现实是大多数人不会读很长的文档。如果你写五六页，读者可能会中途放弃（或者快速浏览而不深入细节）。强迫自己写得简洁，把额外上下文通过链接其他文档的方式提供给那些想要完整细节的人。

写完愿景后，人们通常的第一步是把它广泛分享给整个工程团队。愿景背后有那么多工作——每份策略对应五份设计文档，五份策略才形成一份愿景——写完的时候很难不兴奋。因此，当大家对你的策略/愿景的反应几乎总是平淡的时候，你也很容易感到沮丧。

反应平淡有几个原因。首先，愿景的核心受众是那些要写策略的人，而这个群体相对较小。其次，一份好的愿景通常会显得太过显而易见，以至于让人觉得无聊而不是兴奋。不要用它最初带来的兴奋度来衡量愿景的好坏，而应该拿两年前的一份设计文档和上周的一份对比阅读；如果有明显进步，那么你的愿景就是好的。

什么时候以及为什么

现在你已经有了制作有效策略和愿景的配方，一个很好的后续问题是：“我究竟什么时候、为什么应该去写它们？”策略是主动对齐的工具，它能让团队快速且自信地前进。策略让每个人——而不仅仅是少数被授权的人——都能快速、自信地做出原本可能需要讨论一周的决策。策略也是砖块，它把原本无数种可能的未来逐渐收窄到足够少的范围，让写出一份现实的愿景成为可能。

当同一个讨论已经被反复提起三四次的时候，就是该写一份新策略的时候了。当未来过于模糊以至于无法确定哪些投入值得做的时候，就是该写一份新愿景的时候了。如果这两点对你来说听起来都不熟悉——那就先去做其他工作吧，之后再回来。
