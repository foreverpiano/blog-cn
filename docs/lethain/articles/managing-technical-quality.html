管理代码库中的技术质量

2020-10-17 · 阅读原文

如果说工程师、工程经理和技术高管们能达成共识的一件事，那就是技术质量正面临危机。一个显而易见的诊断和解决方案是：我们的工程师没有优先考虑质量，我们需要招聘更好的工程师，或者重新培训现有人员。当然，如果你觉得更舒服，也可以把“工程师”换成“产品经理”或“高管”。这是一个有吸引力的叙事，里面有明确的反派，并且 conveniently 将责任从工程领导层转移出去。然而，像大多数将问责转向权力最小者身上的叙事一样，它既无益也是错误的。

当你接受“低技术质量源于糟糕决策”的前提时，你就会开始寻找判断失误，而公司里一定得有人是罪魁祸首。是前任 CTO 吗？是那个带着紧张微笑看着你的 Staff Engineer 吗？还是所有人？如果不是这些人呢？更奇怪的是，如果这甚至根本不是你的错呢？

在大多数情况下，低技术质量并非危机，而是预料之中的正常状态。工程师在做决策时，通常会做出合理的质量判断，而成功的公司会在规模扩大、业务转型或向上游转向企业用户时，逐步提高质量标准。在一家运转良好且成功的公司里，你过去的绝大多数技术决策都不会满足当前的 quality threshold。与其说这是失败，不如说缩小当前技术质量与目标技术质量之间的差距，是有效工程领导力常规且必不可少的一部分。

问题所在

作为工程领导团队，你的目标是在将尽可能多的精力投入核心业务的同时，维持适当的技术质量水平。你必须在多个时间尺度上平衡质量，而这些时间尺度通常存在相互冲突的需求。例如，你为下周截止日期推出的关键合作伙伴项目所做的工作，与构建一个能让下个季度发布速度提升十倍的平台所做的工作，会截然不同。

正如公司的技术质量标准会随着时间推移而变化，你管理技术质量的方法也会同步演进：

修复导致当下问题的热点 采用已知能提升质量的最佳实践 优先考虑那些能在软件变化时保护质量的杠杆点 在组织改变软件的方式上对齐技术向量 衡量技术质量以指导更深入的投资 组建一个技术质量团队来创建质量相关的系统和工具 运行一个质量项目来衡量、跟踪并建立问责制

当我们深入探讨这套方法工具箱时，请记住要选择最便宜、最直接、最可能有效的工具。技术质量是一场长期游戏。没有所谓的“胜利”，只有不断学习，并赢得继续玩下去的机会。

拾级而上

深入当前挑战直至找到一个值得解决的通用问题，会带来一种特别的喜悦。然而，同样重要的本能是快速解决当前情况，然后转向下一个迫切的问题。

当你思考应该为团队和组织做哪些质量改进时，通常最有效的方式是从最轻量级的解决方案开始，只有当早期努力因规模压力而崩溃时，才逐步转向大规模解决方案。如果你无法让团队采用正确的代码 linting，那么推出全面质量项目的尝试注定会失败。尽管后者在规模化时可能更有效，但执行难度要大得多。

所以，先做那些快速见效的事情！

即使它没成功，你也能从推广简单方案的失败中比从推广困难方案的失败中更快地学到更多。然后你就能更快地进入改进后的第二轮迭代。随着时间推移，你会逐渐转向全面的方法，但没必要着急。不要在没有真正需要的情况下，放弃早期组织的轻松、快乐和纯真，而去面对企业级协调的种种风险。

把这些阶段描述成一条可以拾级而上的线性阶梯很方便，但真实组织很少这样使用它们。你更可能先修复一个质量热点，然后推广一项最佳实践，接着启动架构评审，又废除那个架构评审，然后又回去热点修复一阵子。过早引入流程会增加摩擦而非价值，并且很快就会暴露出自己的无效性。如果某个做法行不通，就尝试一段时间去让它工作，然后庆祝它的消亡。

热点

当面对质量问题时，第一反应往往是找出流程失败，并因此认为必然需要一个流程解决方案。如果一次部署导致了 outage，那是因为作者没有正确遵循代码测试流程，所以现在我们要要求每次 commit 都带测试——这会教训那些懒惰的开发者！

有一个关于萨班斯-奥克斯利法案的老笑话：它没有降低风险，只是明确了出事时该怪谁。不幸的是，这个笑话毫无幽默感地适用于许多组织推广流程的方式。问责有其作用，但更重要的是理解眼前的问题并尝试直接修复它，而不是创造基于流程的问责。

推广流程需要人们改变工作方式，这件事不宜轻率对待。与其伸手去抓流程改进，不如先戴上性能工程师的心态。衡量眼前的问题，找出问题主要发生在哪里，然后精确聚焦于那个区域。

前面未测试部署的例子，或许可以通过直接给部署工程师反馈来改变他们的测试习惯来改善。或者，你也许更应该承认你的软件设计容易出错，并采用《软件设计哲学》中描述的“将错误定义在不存在”的方法。

如果你面临开发速度问题，或许可以优化测试运行时间，把 Docker 编译步骤移到 RAM disk 上，或者使用《Software Design X-Rays》中描述的技术来找出需要改进的具体文件。

是我职业生涯中遇到过的最具变革性的思考技巧。但有时它也会像塞壬一样，引诱你去修复一个当前系统，而你或许更应该直接丢弃它。当然，你可以推出一个新的培训项目来教团队如何写出更好的测试，但换一种方式，也许你只需要删除那个占了 98% 测试失败的测试文件。这就是优先处理热点的不可思议的效果，也是为什么它应该是你改善技术质量时首先使用的技巧。系统思维导论

在某个时刻，你可能会发现组织制造质量问题的速度超过了你修复热点的速度，这时就该转向采用最佳实践了。

最佳实践

我曾经在一家没有团队规划流程的公司工作。随着时间推移，工程负责人对无法预测目标日期越来越沮丧，于是强制要求我们使用 [Scrum](https://en.wikipedia.org/wiki/Scrum_(software_development))。强制令下达后，一位经理把 Scrum 流程写在了 wiki 上。公司宣布我们正在使用 Scrum。经理们告诉各自的团队要使用 Scrum。任务完成！

当然，没有人真正开始使用 Scrum。大家继续做着以前的事。因为承认错误很尴尬，所以工程负责人宣布采用取得了重大胜利，而没有人忍心说不一样的话。

这个悲伤的故事反映了许多公司尝试推广最佳实践的方式，这也是最佳实践名声不佳的原因之一。理论上，组织应该在修复质量热点之前就采用最佳实践，但我推荐在热点修复之后再采用实践。采用最佳实践需要一定程度的组织和领导力成熟度，而这需要时间来培养。

当你推广一项新实践时，请记住一个 ，而不是被强制要求的。研究其他公司如何采用类似实践，记录你打算采用的方法，与几个积极参与的团队一起实验，磨平粗糙的边缘，根据遇到的挑战改进文档，然后才进一步推广。仓促的流程就是失败的流程。好的流程是演化出来的，而非设计出来的。

同样重要的是要限制同时推广的流程数量。如果你试图让团队同时采用多个新实践，你就是在和自己争夺他们的注意力。这也会让你以后考虑回滚或修改其中一项新实践时，更难归因影响。虽然有点严苛，但我逐渐相信，在任何时候你都应该将自己限制在只推广一项最佳实践上。把所有精力都投入到让一项实践成功上，而不是把资源分散到好几项上。

一次只采用一项新实践，也会迫使你仔细思考应该优先选择哪一项。选择下一个流程听起来简单，但通常很难说清楚哪些最佳实践是真正的最佳实践，哪些只是熟悉或有名而已。真正的最佳实践必须有研究支持，而这个主题最好的研究来源是《Accelerate》。

虽然《Accelerate》的所有推荐都是数据驱动且相当好的，但我发现最早采用最有帮助的少数几项是：版本控制、基于主干的开发、CI/CD、生产环境可观测性（包括开发者对自己编写的系统值班），以及以小而原子化的变更进行工作。我还想大力推荐很多其他实践——谁没有经历过职业生涯中某个阶段大力倡导更好的内部文档呢——但我现在不再像以前那样相信自己的直觉了。

从修复热点转向采用最佳实践的时机，是当你被太多热点压得喘不过气的时候。下一个转变，从最佳实践转向杠杆点，则是当你发现自己想在当前最佳实践还没生效前就采用新的最佳实践时。与其 ，不如转向下一个工具。为什么限制在制品数量有效

杠杆点

在热点部分，我们谈到了用性能工程师的心态来识别正确的问题去修复。优化对已存在的问题效果很好，但它有意不适用于未来：性能工程最大的罪过就是把精力花在未被验证的问题上。

然而，当你观察软件如何随时间变化时，会发现有少数几个地方，额外的投入能够长期保护质量，既能防止严重的质量失败，也能降低未来质量投入的成本。

我把这些称为质量杠杆点，其中影响最大的三个是：接口、有状态系统和数据模型。

接口是系统之间的契约。有效的接口能将客户端与封装的实现解耦。持久的接口会暴露所有底层本质复杂度，而不暴露任何底层偶然复杂度。令人愉悦的接口则是“积极 discerning，discerningly eager”。

状态是任何系统中最难改变的部分，而这种对改变的抵抗使有状态系统成为另一个关键杠杆点。状态的惯性来自于它的规模，来自于它为了可用性、可靠性和合规性而不断累积复杂性的倾向，来自于其正确性是用概率而不是定理来描述的特性。（或者在分布式状态的情况下，既有概率也有定理。）

数据模型是接口和状态的交集，它将有状态系统的能力约束到你的应用认为合法的范围内。一个好的数据模型是严格的：它只暴露它真正支持的内容，并阻止无效状态的表达。一个好的数据模型能容忍随时间演化。有效的数据模型一点都不耍小聪明。

当你在工作中识别出这些杠杆点时，要花额外的时间慎重对待它们。如果是一个接口，就把六七个客户端集成到模拟实现上。如果是一个数据模型，就用六七个真实场景来表示。如果是一个有状态系统，就演练失败模式，检查一致性行为，并建立类似于生产环境的性能基准。

把你学到的一切，拉到一个技术规格文档中，并在团队内广泛传播。从同行那里收集行业反馈。即使在开始实施之后，也要倾听现实的声音，并对变化保持开放。

投资杠杆点的一个隐藏力量是，你不需要整个组织完全对齐才能做这件事。要写技术愿景或推广最佳实践，你需要那种认同，这也是我推荐从杠杆点开始的原因。然而，如果你已经用尽了杠杆点能带来的可及影响，也许是时候转向推动更广泛的组织对齐了。

技术向量

有效的组织会将大部分努力导向一个共享愿景。如果你把每个项目、每一个技术决策都画成网格上的向量，那么这些向量越是指向同一个方向，你长期能取得的成就就越多。反之，我合作过的一些最令人印象深刻的工程师，他们创造的向量虽然幅度惊人，但方向错位，最终在试图领导组织时反而伤害了组织。

一个确保技术方向对齐的万无一失的方案，是把所有相关决策都路由到同一个职称里带“Architect”的人那里。这很有效，但难以扩展，而且架构师决策的质量会随着他们远离真实代码、真实流程中的真实工作而下降。在另一个极端，你可以允许每个团队独立做决策。但一个允许使用任何工具的组织，最终会拥有完全无人支持的工具链。

给出直接反馈。当人们遇到不对齐的情况时，第一反应往往是改变流程，但与其这样，不如先直接给那些你认为不对齐的个人反馈。他们缺少你的上下文，你也同样缺少他们的上下文，一次善意、清晰的对话往往能避免多年不必要的流程。 从 来提炼你的工程策略。 把你的方法封装在工作流和工具中。清晰愿景的文档很有帮助，但有些人就是不会去研究你的文档。刻意设计的工具能创造工作流，比培训和文档更好地培养习惯。例如，provision 一个新服务可能需要访问一个网站，而该网站要求你为该服务添加一个指向技术规格的链接。另一种做法可能是阻止部署到生产环境，除非该服务已经建立了 on-call 设置，并且当前有人值班，且该人员必须开启推送通知。 在新成员 onboarding 时培训他们。在人们已经养成习惯后再去改变相当困难，这在你试图让大家采用新实践时会让人沮丧。然而，如果你在他们刚加入时就把方向指正，那么这种习惯惯性就会有利于保持对齐。 运用 Conway’s Law。Conway’s Law 认为组织构建的软件会反映其组织结构。如果你的组织结构不好，就会导致紧耦合或纠缠不清的软件。但如果你的组织设计是有效的，它也会成为质量的推动力量。 使用 、 以及采用新工具的结构化流程来 curation 技术变更。大多数不对齐都来自于缺失上下文，而这些正是向决策过程中注入上下文的组织杠杆点。许多组织从这里开始，但我推荐最后才打开这个工具箱。没有清晰表述的愿景，怎么能提供一致的架构评审呢？为什么要在他们已经设计好东西之后才告诉他们你的策略，而不是在 onboarding 过程中就告诉他们？工程策略。扩展技术一致性探索的量级

无论你使用哪些方法来对齐技术向量，这都是一项通常需要数月乃至数年的工作。不存在你写完愿景文档，组织就立刻被它的 brilliance 所吸引的世界。更可能的情况是，它会一直积灰，直到你投入精力去建立支持为止。

大多数公司可以将上述从修复热点到向量对齐的技术组合成管理技术质量的成功方法，希望你也是如此。然而，许多人发现这些还不够，于是转向更重的手段。在这种情况下，第一步一如既往是衡量。

衡量技术质量

软件工程中对衡量的渴望，通常超出了我们当前的衡量能力。《Accelerate》提出了一些衡量速度的指标，这些指标对定位流程和工具问题非常强大，但这些指标是在代码合并之后才开始的。你如何衡量代码库的质量，从而能够识别差距、提出行动计划，并评估你改进努力的效果呢？

有一些流程衡量指标与有效的变更相关。例如，你可以衡量每个 pull request 中变更的文件数，因为更小的 pull request 通常质量更高。你也可以衡量代码库中每个文件的代码行数，假设非常大的文件通常难以扩展。这些都可能很有帮助，我甚至会推荐去衡量它们，但我认为它们充其量只是代码质量的代理指标。

我的经验是，可以有效地衡量代码库质量，而这取决于制定一个极其精确的质量定义。你对质量的定义越详细，它在衡量代码库时就越有用，对于那些希望改进自己负责区域质量的人来说，也越具有指导意义。这种方法在《Building Evolutionary Architectures》和 收回不合理的软件 中有较为详细的描述。

一些可以考虑纳入你质量定义的代表性组成部分：

代码中有多大比例是静态类型的？ 有多少文件有关联的测试？ 代码库内的测试覆盖率是多少？ 模块间的公共接口有多窄？ 有多少比例的文件使用了首选的 HTTP 库？ 端点在冷启动后是否能在 500ms 内响应请求？ 有多少函数存在危险的 read-after-write 行为？或者对主数据库实例进行了不必要的读取？ 有多少端点在单个事务内完成所有状态变更？ 有多少函数获取了低粒度的锁？ 存在多少“热文件”，即在超过一半 pull request 中都被修改的文件？

你可以不同意其中某些属性应该出现在你代码库的质量定义中：你的定义应该针对你的代码库和你的需求。重要的是要制定一个精确、可衡量的定义。在制定这个定义的过程中会出现分歧，而且你必然会随着时间推移而修改这个定义。

制定定义之后，接下来是真正具有挑战性的部分——仪表化，而仪表化是产生有用指标的前提。仪表化的复杂性是这些技术在实践中采用的最大阻力，但如果你能突破这一点，你将解锁某种相当非凡的东西：一个真实的、动态的质量分数，你可以长期跟踪它，并用它在你的方法中创造出概念对齐无法达到的清晰一致性。

在质量被定义和仪表化之后，下一步是决定投资于一个质量团队还是一个质量项目。专用团队容易协调，带宽可预测，通常是更容易起步的选择。

技术质量团队

技术质量团队是一个专门致力于提升代码库质量的软件工程团队。你可能把这个团队叫做 Developer Productivity、Developer Tools 或 Product Infrastructure。无论叫什么，该团队的目标都是在公司所有软件中创造和维护质量。

这不是有时被称为 quality assurance 的团队。虽然两个团队都会在测试上投入，但技术质量团队的职责范围更广，从工作流到构建、测试，再到接口设计。

当你 bootstrapping 这样一个团队时，从一个固定规模的三到六人团队开始。小团队会迫使你无情地根据影响来优先排序他们的 roadmap，并确保你始终聚焦于可实现的目标。随着时间推移，这个团队会积累需要维护的系统，而这些系统又需要扩大投入（Jenkins 集群就是常见的例子），这时你需要根据更广泛的工程组织规模来 。这里的经验法则很难说准，但也许是每十五个产品工程师对应一位从事开发者工具的工程师，而且这还不包括你的基础设施工程投入。工程团队的规模设定

这些团队很少配备产品经理，通常由一位或多位 Staff-plus 工程师和工程经理共同承担该角色。有时他们会配备 Technical Program Manager，但通常是在他们开始运营下一节描述的质量项目之后。

相信指标而非直觉。你应该能衡量每一个项目。质量是一个复杂系统，很容易让你的直觉误导你。同样，当你在公司变得更资深时，你的经验将不再能反映大多数其他人的体验。你已经知道那些粗糙的边缘，如果发现新的还能获得优先帮助，但大多数其他人不能。指标让你保持诚实。 保持直觉新鲜。代码和流程会随时间变化，你每远离构建产品功能一周，直觉就会陈旧一点。大多数人发现团队嵌入和团队轮换是保持直觉相关性的最佳方式。也有人通过监控聊天中的问题，以及与产品开发者保持健康的 1:1 讨论来实现。最优秀的人会同时做这两件事，并随时备好他们的指标仪表盘。 倾听并向你的用户学习。有一个流行的“品味水平”概念，暗示有些人就是天生知道好东西长什么样。在设计有效质量投入的人之间存在巨大差异，但这通常不是天生技能，而是来自于深刻理解你的用户想要完成什么，并把这一点置于你的实现约束之上。 工具的采用度和可用性远比原始威力更重要。一个强大但难以使用的工具只会吸引少数 power user，而大多数人会绕道而行。慢下来，把这些细节做好。隐藏所有偶然复杂度。观察一个工程师第一次尝试使用你的工具，不要帮助他们。改进差距。重复十次以上！如果你没有对你的工具进行用户研究，那么作为一个质量投入团队，你注定会失败。 少做事情，但要把它们做好。当你为整个工程组织构建工具时，你做好了的任何事情都会加速整个组织。你做得不好的任何事情，包括那些几乎很好但粗糙边缘太多的事情，都会拖累所有人。虽然“做好少数最重要的事情比做很多平庸的项目贡献更大”几乎总是正确的，但在你试图向整个组织推广工具和工作流的情况下，这一点尤为正确（组织的 in-progress 流程限制在这里依然适用！）。 不要囤积影响。集中式质量团队和它们支持的团队之间存在根本性的张力。通常会出现全局最优的方法被集中式团队偏好，但严重影响了某些在非典型领域或负载上工作的团队。一个有代表性的例子是，一家公司用 JavaScript 写后端服务器，却不允许机器学习工程师使用 Python 生态，因为他们不想支持两个生态。另一个例子是公司统一要求所有 API 使用 REST/HTTP2/JSON，而某个特定团队想使用 gRPC。 这里没有完美的答案，但重要的是建立一个深思熟虑的方法，来 。探索的量级

一个成功运用上述方法的技术质量团队，其生产力无疑会高于同等数量工程师直接做产品工程工作的情况。事实上，折现后的开发者生产力（类似于折现现金流的概念）理论上是衡量这类团队影响的正确方式。只是理论上，因为这类计算大多是对你自信心的评估。

即使你非常成功，你也总会有一个高影响工作的 backlog，你想做却没有带宽去完成。组织不会做出纯粹理性的团队资源分配决策，你可能会发现自己没有带宽完成重要项目，同时也无法获得批准在团队中额外招聘。

质量项目

质量项目根本不是计算机代码，而是一项由专职团队领导的、在整个组织内维护技术质量的举措。质量项目承担着实现组织目标软件质量水平的广泛职责。这类项目相对少见，但你可能遇到过类似的东西——负责公司事故回顾和补救的 incident program。

鉴于本文是写给资深技术领导者的，我们假设你已经覆盖了技术视角。下一步是找到一位 Technical Program Manager，他可以共同领导这个项目并运营其机制。你可以在没有 Technical Program Manager 的情况下，在组织项目的 информа 方面取得可观进展；但这其实是个陷阱。在大型组织中独自驱动一个项目，你会被协调开销压垮。

确定项目赞助人。没有被赋能的赞助人，你无法改变一个组织的行为。组织之所以以当前方式运作，是因为这是它们当前约束下的最优解，而如果你没有一个有权力的人来倡导，你就无法改变那些约束。 生成可持续、可重复的指标。运行项目的人每周花四个多小时手动维护数据集是很常见的。这行不通。你的数据会有漏洞，你无法在后续步骤中将数据与自动化集成，而且你会耗尽推动真正改变的精力；刷新一个指标仪表盘本身没有内在价值。 为每个受影响的团队确定项目目标，并为他们提供达成这些目标的清晰路径。你的项目必须为每个受影响的团队确定具体目标，例如降低他们测试的 flaky 率，或更快地关闭事故补救项。然而，最关键的是你要提供通往成功的地图！太多项目只是对团队提出要求，却不提供如何达成这些目标的指引。项目负责人是主题专家，不要把你的策略甩给每个团队去独立重新发明。 构建工具和文档来支持团队达成目标。一旦你为团队确定了达成项目目标的清晰路径，就要想办法帮助他们做出这些改变！这可能是提供“黄金示例”来说明事情应该是什么样子，或者更好的是，提供一个重构困难代码段到新模式的示例 pull request。也可能是提供一个测试脚本，来验证迁移是否正确完成。还可以是自动生成转换 commit，让他们无需自己编写就能测试、验证和合并。尽可能多做这些事，以避免每个团队都必须深入理解你试图推进的问题空间。 创建一个目标仪表盘并广泛分享。一旦你向每个团队传达了项目目标，就必须提供仪表盘，帮助他们理解当前状态、他们的目标，并对他们（希望中的）进展给出强化反馈。最好的仪表盘既是每个团队工作的记分卡，也能为每个团队提供下一步应该关注什么的面包屑。 你的仪表盘应该支持三个不同的缩放级别。完全拉远级别帮助你评估项目的整体影响。完全拉近级别帮助单个团队理解他们剩下的工作。两者之间的第三个级别帮助组织领导者让他们的团队负责（并支持你的项目赞助人做出具体、明确的请求来让这些领导者负责）。 向落后于目标的人发送程序化的提醒。人们很忙。他们不会总是优先考虑你的项目目标。或者，他们可能出色地完成了你要求的改进，但后来又退回到已废弃的实践。用提醒来引导团队将注意力转向下一项应为项目目标做的工作。记住，注意力是一种稀缺资源！如果你用一封提醒邮件或 ping 浪费了别人的时间，他们就不会再注意下一个了。 定期与你的赞助人一起审查项目状态。项目试图在一个与团队目标天然不对齐的组织优先级上取得进展。许多团队难以从本地优先级中抽身去完成全局优先级。这时候，与你的赞助人一起审查整体进展，并向他指出那些优先处理项目工作的团队，就变得至关重要。有效地利用你的赞助人来弥合优先级错位，将是你成功的关键。

一个糟糕的项目很像一个低效的非营利组织：目标是正确的，但很少有资源真正到达预期的目标。无论你决定如何衡量技术质量，在运行你的质量项目时始终要记住的最重要一件事是：项目本身不是目标。目标是创造技术质量。组织项目规模庞大，会积累如此多的动量，以至于即使在它们不再有效之后，惯性仍会推动它们前进。保持你的项目足够精简以便可以取消，并保持足够的自我批判，以便在它不再能驱动质量创造时取消它。

从小处开始，慢慢添加

当你意识到实际技术质量已远远落后于目标技术质量时，自然的第一反应是惊慌，然后开始大规模推广各种技术和解决方案。把所有原料都倒进锅里，结果必然不好，而且更糟糕的是，你甚至不知道该保留哪些部分。

如果你发现自己在技术质量上挣扎——我们都会经常这样——那就从一个小事情开始，在它上面迭代直到它真正有效。然后再添加另一种技术，也对它进行迭代。慢慢构建出真正有效的东西，即使这意味着要承受“不够快”的指责。在复杂系统和相互依赖的关系中，快速行动只是表象，慢慢来才能真正把事情做好。
