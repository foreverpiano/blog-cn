管理代码库中的技术质量

2020-10-17 · 阅读原文

如果说工程师、工程经理和技术高管们能达成什么共识，那就是技术质量正面临危机。一种简单直接的诊断和解决方案是：我们的工程师没有优先考虑质量，我们需要招聘更好的工程师，或者重新培训现有的人员。当然，如果你觉得更舒服，也可以把“工程师”换成“产品经理”或“高管”。这是一个引人入胜的故事，有明确的坏人，而且很方便地将责任从工程领导层身上转移开。然而，就像大多数把责任推给权力最小者的叙事一样，它既无益也不正确。

当你接受“低技术质量源于糟糕决策”这个前提时，你就会开始寻找判断失误的地方，并认定公司里一定有人要为此负责。是前任 CTO 吗？是那个带着紧张笑容看着你的 Staff Engineer 吗？还是所有人都有责任？如果都不是，甚至更奇怪的是，这根本不是你的错呢？

在大多数情况下，低技术质量并不是危机，而是预料之中的正常状态。工程师在做决策时，通常会做出合理的质量选择，而成功的公司会在规模扩大、业务转向或向企业级用户转型的过程中，逐步提高质量标准。在一家运转良好且成功的公司里，你过去的大多数技术决策都不会满足当前的质量门槛。弥合当前技术质量与目标质量之间的差距，并非失败，而是有效工程领导力的常规且关键组成部分。

问题所在

作为工程领导团队，你的目标是在尽可能将精力投入核心业务的同时，维持适当的技术质量水平。你必须在多个时间尺度上平衡质量，而这些时间尺度通常存在相互冲突的需求。例如，为下周截止日期推出关键合作伙伴项目所做的工作，与构建一个能让下季度发布速度提高十倍的平台所做的工作，会大不相同。

正如公司技术质量标准会随着时间推移而变化，你管理技术质量的方法也需随之演进：

修复导致当前问题的热点区域；采用已知能提升质量的最佳实践；优先考虑那些能在软件变更时维持质量的杠杆点；在组织改变软件的方式上对齐技术向量；衡量技术质量以指导更深入的投资；组建一个技术质量团队来创建质量相关的系统和工具；运行一个质量计划来衡量、跟踪并建立问责机制。

当我们深入探讨这套方法工具箱时，请记住要选择最便宜、最直接、最可能奏效的工具。技术质量是一场长期博弈。没有“获胜”这回事，只有不断学习，并赢得继续玩下去的机会。

拾级而上

深入研究眼前挑战直到发现一个值得解决的通用问题，这其中有一种特别的乐趣。然而，同等重要的另一种本能是快速解决当前问题，然后转向下一个紧迫事项。

当你思考要为团队和组织做哪些质量改进时，通常最有效的方式是从最轻量级的解决方案开始，只有当早期努力在规模压力下崩溃时，再逐步转向更大型的方案。如果你连让团队采用正确的代码 linting 都做不到，那么推出全面质量计划的尝试注定会失败。虽然后者在规模化时可能更有效，但执行难度要大得多。

所以，先做那些快速见效的事！

即使没成功，你也会从“ rollout 简单方案失败”中学到比“ rollout 困难方案失败”更多、更快的东西。这样你就能更快进入改进后的第二轮迭代。随着时间推移，你会逐渐转向全面的方法，但无需急于求成。在没有真正需要的情况下，不要放弃早期组织的那份轻松、快乐和单纯，而去面对企业级规模协调的种种风险。

把这些阶段描述成一条可以逐级攀登的线性楼梯很方便，但真实组织很少会这样使用它们。你更可能先修复一个质量热点，再推行一项最佳实践，然后开始运行架构评审，接着废除那个架构评审，又回去热点修复一会儿。过早引入的流程往往弊大于利，而且很快就会暴露其无效性。如果某件事行不通，那就尝试一段时间去让它生效，如果还是不行，就庆祝它的消亡吧。

热点区域

当面对质量问题时，第一反应往往是找出流程上的失败，并认为必然需要一个流程解决方案。如果一次部署导致了故障，那是因为作者没有正确遵循代码测试流程，所以现在我们要要求每次提交都必须有测试——这下就能教训那些懒惰的开发人员了！

有一个关于《萨班斯-奥克斯利法案》的老笑话：它并不能降低风险，只是清楚地告诉大家出了问题该怪谁。不幸的是，这个笑话毫无幽默感地适用于许多组织推行流程的方式。问责有其作用，但更重要的是理解眼前的问题，并尝试直接修复它，而不是建立基于流程的问责机制。

推行流程需要人们改变工作方式，这件事不应该轻易尝试。与其伸手去抓流程改进，不如先戴上性能工程师的心态。衡量眼前的问题，找出问题主要发生在什么地方，然后精确地聚焦于那个区域。

前面那个未测试部署的例子，或许可以给部署工程师直接反馈，建议他们改变测试习惯。或者，也许更好的做法是承认你的软件设计容易出错，并采用《A Philosophy of Software Design》中提到的“把错误定义到不存在”的方法。

如果你面临开发速度问题，那可能是要优化测试运行时间、把 Docker 编译步骤移到内存盘上，或者使用《Software Design X-Rays》中描述的技术来找到需要改进的具体文件。

是我职业生涯中遇到过的最具变革性的思考技巧。但有时它也会像塞壬一样诱惑你去修复当前系统，而你其实最好放弃它。当然，你可以推行一个新的培训计划来教团队如何编写更好的测试，但另一种选择是，直接删除那个占了 98% 测试失败的测试文件。这就是优先处理热点区域所带来的惊人效果，也是为什么它应该成为你改进技术质量时首先使用的技术。系统思维导论

在某个时刻，你很可能会发现组织制造质量问题的速度超过了你修复热点的速度，这时就该转向采用最佳实践了。

最佳实践

我曾经在一家没有团队规划流程的公司工作。随着时间推移，工程负责人越来越受不了无法预测目标日期，于是强制要求我们使用 [Scrum](https://en.wikipedia.org/wiki/Scrum_(software_development))。强制之后，一位经理把 Scrum 流程写在了 wiki 上。公司发布了我们正在使用 Scrum 的公告。经理们告诉各自团队要使用 Scrum。任务完成！

当然，没有人真正开始使用 Scrum。大家还是继续做之前在做的事情。因为承认错误很尴尬，所以工程负责人宣布采用 Scrum 是一次重大胜利，而没有人忍心去说实话。

这个悲伤的故事反映了许多公司尝试推行最佳实践的方式，这也是最佳实践声誉不佳的原因之一。理论上，组织应该在修复质量热点之前就采用最佳实践，但我推荐在热点修复之后再采用最佳实践。采用最佳实践需要一定程度的组织和领导力成熟度，这需要时间来培养。

当你要推行一项新实践时，请记住 ，而不是被强制推行的。研究其他公司如何采用类似实践，记录你打算采用的方法，与几个积极参与的团队一起实验，磨平粗糙的边缘，根据遇到的挑战改进文档，然后再进一步推广。仓促的流程注定会失败。好的流程是演化出来的，而非设计出来的。

同样重要的是要限制同时进行的流程 rollout。如果你试图让团队同时采用多种新实践，你就是在和自己争夺他们的注意力。这也会让你在后续考虑回滚或修改其中某项实践时，更难归因其影响。虽然有点极端，但我逐渐相信，在任何时候你都应该限制自己只推行一项最佳实践。把所有精力集中于让一项实践成功，而不是把资源分散到好几项上。

一次只采用一项新实践，也会迫使你仔细思考该优先选择哪一个。选择下一个流程听起来简单，但常常难以分辨哪些真正是最佳实践，哪些只是熟悉或有名而已。真正的最佳实践必须有研究支持，而这个主题最好的研究来源是《Accelerate》。

虽然《Accelerate》的所有推荐都有数据驱动且相当优秀，但我发现早期最值得采用的少数几项是：版本控制、基于主干的开发、CI/CD、生产环境可观测性（包括开发者对自己编写的系统值班），以及以小而原子的变更进行工作。我还想大力推荐许多其他实践——谁没有经历过职业生涯中某个阶段大力倡导更好的内部文档呢——但我不再像以前那样相信自己的直觉了。

从修复热点转向采用最佳实践的时机，是当你被太多热点压得喘不过气来的时候。下一个转变——从最佳实践转向杠杆点——发生在你想在当前最佳实践生效前就采用另一项新最佳实践的时候。与其 ，不如转向下一个工具。为什么限制在制品数量有效

杠杆点

在热点区域一节中，我们谈到使用性能工程师的心态来找出正确的问题去修复。优化对已存在的问题很有效，但它有意不适用于未来：性能工程最大的罪过就是把精力花在未经验证的问题上。

然而，当你观察软件如何随时间变化时，会发现少数几个地方，额外的投入能在长时间内维持质量，既能防止严重质量问题，又能降低未来质量投入的成本。

我把这些称为质量杠杆点，其中影响最大的三个是：接口、有状态系统和数据模型。

接口是系统之间的契约。有效的接口能将客户端与封装的实现解耦。持久的接口会暴露所有底层本质复杂性，而不暴露任何底层偶然复杂性。令人愉悦的接口则是“主动辨识”且“辨识主动”的。

状态是任何系统中最难改变的部分，这种抗变性使有状态系统成为另一个关键杠杆点。状态的惯性来自其规模，来自它为了可用性、可靠性和合规性而不断积累复杂性的倾向，来自它那种用概率而非定理来描述正确性的特点。（而在分布式状态的情况下，则是概率和定理两者兼有。）

数据模型是接口和状态的交汇点，它将有状态系统的能力约束到你的应用认为合法的范围内。一个好的数据模型是严格的：它只暴露真正支持的内容，并阻止无效状态的表达。一个好的数据模型能容忍随时间演化。有效的数据模型绝不耍小聪明。

当你在工作中识别出这些杠杆点时，要额外花时间慎重地对待它们。如果是一个接口，就用模拟实现集成六七个客户端。如果是一个数据模型，就表示六七个真实场景。如果是有状态系统，就演练失败模式，检查一致性行为，并建立接近生产环境的性能基准。

把你学到的一切，拉到一个技术规格文档中，并在团队内广泛传播。从同行那里收集行业反馈。即使开始实现之后，也要倾听现实的声音，并保持对变更的开放态度。

投资杠杆点的一个隐藏力量是，你不需要整个组织完全对齐才能去做。要写技术愿景或推行最佳实践，你需要那种程度的认同，这也是我推荐从杠杆点开始的原因。然而，如果你已经用尽了杠杆点能带来的可及影响，或许就该转向推动更广泛的组织对齐了。

技术向量

有效的组织会将大部分精力集中于一个共同愿景。如果你把每个项目、每项真正的技术决策都画成网格上的向量，那么这些向量越是朝同一方向，你的长期成就就越大。相反，我合作过的一些最令人印象深刻的工程师，他们创造的向量幅度惊人，但方向却错位，最终在试图引领组织时伤害了它。

确保技术方向对齐的一个万无一失的方法，是把所有相关决策都路由给同一个职称里带“Architect”的人。这很有效，但难以扩展，而且架构师的决策质量会随着他们远离真实代码、真实流程中的真实工作而下降。在另一个极端，你可以让每个团队独立决策。但允许使用任何工具的组织，最终会拥有完全缺乏支持的工具。

你用来对齐技术向量的基本工具包括：

给出直接反馈。当人们遇到不对齐的情况时，第一反应往往是改变流程，但你应该先直接给那些你认为不对齐的人反馈。他们缺少你的上下文，你也同样缺少他们的。一个善意、清晰的对话往往能避免多年不必要的流程。，不断完善你的工程策略。将你的方法封装到工作流和工具中。对清晰愿景的文档很有帮助，但有些人就是不会去研究你的文档。精心设计的工具能创造出比培训和文档更好养成习惯的工作流。例如，配置一个新服务时，可能需要你访问一个网站，并要求你在那里添加指向该服务技术规格的链接。另一种方法是，如果服务没有建立 on-call 机制、当前没有人值班，或者那个人没有启用推送通知，就阻止其部署到生产环境。在新成员入职时对他们进行培训。改变已经形成习惯的人非常困难，如果你试图让他们采用新实践，这会令人沮丧。但如果你能在他们加入时就把方向指正，那么这种习惯惯性就会帮助他们保持对齐。运用康威定律（Conway’s Law）。康威定律认为，组织构建的软件会反映其组织结构。如果你的组织结构不好，这会导致紧耦合或纠缠不清的软件。但如果你的组织设计是有效的，它也能成为质量的力量。使用 、 以及采用新工具的结构化流程来管理技术变更。大多数不对齐都源于缺少上下文，而这些正是向决策过程注入上下文的组织杠杆点。许多组织从这里开始，但这是我推荐最后才打开的工具箱。连清晰的技术愿景都没有，怎么可能提供一致的架构评审？为什么要在他们设计完东西之后才告诉他们你的策略，而不是在入职流程中就告诉他们呢？工程策略。提升技术一致性。探索的量级。

无论你使用什么方法来对齐技术向量，这都是一项通常需要数月乃至数年才能完成的工作。不可能你写完愿景文档，组织就立刻被它的 brilliance 所折服并对齐。更可能的情况是，它只会积灰，直到你投入精力建立支持为止。

大多数公司都能将上述从热点修复到向量对齐的各种技术组合成一套成功的管理技术质量的方法，希望你也是如此。然而，许多人发现这些还不够，于是转向更重型的方法。在这种情况下，第一步一如既往是衡量。

衡量技术质量

软件工程中对衡量的渴望，通常超出了我们当前的衡量能力。《Accelerate》提出了一些衡量速度的指标，这些指标在定位流程和工具问题上非常强大，但它们是在代码合并之后才开始的。你如何衡量代码库的质量，从而能够发现差距、提出行动计划，并评估你改进工作的效果呢？

有一些流程指标与有效变更相关。例如，你可以衡量每个 pull request 中变更的文件数，因为较小的 pull request 通常质量更高。你也可以衡量代码库中每个文件的代码行数，因为非常大的文件通常难以扩展。这些指标都可能很有帮助，我也推荐去衡量它们，但我认为它们充其量只是代码质量的代理指标。

我的经验是，可以有效地衡量代码库质量，关键在于制定一个极其精确的质量定义。你对质量的定义越详细，它对衡量代码库就越有用，对那些希望改进自己负责区域质量的人也就越有指导意义。这种方法在《Building Evolutionary Architectures》和 收回不合理的软件 中有较为详细的描述。

以下是一些可以纳入你质量定义的代表性组成部分：

代码中静态类型化的比例是多少？有多少文件有对应的测试？代码库内的测试覆盖率如何？模块间的公共接口有多窄？有多少文件使用了首选的 HTTP 库？端点在冷启动后是否能在 500ms 内响应请求？有多少函数存在危险的读后写行为？或者对主数据库实例进行了不必要的读取？有多少端点在单个事务中完成所有状态变更？有多少函数获取了低粒度锁？有多少热点文件在超过一半的 pull request 中被修改？

你可以不同意其中某些属性应该出现在你代码库的质量定义中：你的定义应该针对你的代码库和你的需求。重要的是要制定一个精确、可衡量的定义。在制定这个定义的过程中会出现分歧，而且你必然会随着时间推移修改这个定义。

制定好定义之后，这个领域中真正具有挑战性的是插桩（instrumentation），而插桩是获得有用指标的必要条件。插桩的复杂性是实际采用这些技术时最大的阻力，但如果你能坚持下去，就会解锁一些非常了不起的东西：一个真实的、动态的质量分数，你可以长期跟踪它，并用它来创造一种概念对齐无法带来的清晰对齐感。

在质量被定义和插桩之后，下一步是在投资一个质量团队还是运行一个质量计划之间做出选择。 dedicated 团队更容易协调，带宽也更可预测，通常是更容易开始的地方。

技术质量团队

技术质量团队是一个专注于在你的代码库中创造质量的软件工程团队。你可能称它为 Developer Productivity、Developer Tools 或 Product Infrastructure。无论叫什么，其目标都是在公司软件中创造并维护质量。

这不是有时被称为质量保证（QA）的团队。虽然两者都会在测试上投入，但技术质量团队的职责范围更广，从工作流到构建、测试，再到接口设计。

质量计划

质量计划完全不是计算机代码，而是一项由 dedicated 团队领导的、旨在在整个组织中维持技术质量的举措。质量计划承担着实现组织目标软件质量水平的广泛职责。这类计划相对少见，但你可能遇到过的类似事物是负责公司事故回顾和修复的事故计划。

既然这篇文章是写给资深技术领导者的，我们假设技术视角已经覆盖了。下一步是找到一位能够共同领导该计划并负责其运作的 Technical Program Manager。你可以在没有 Technical Program Manager 的情况下，在组织计划的信息化方面取得可观进展；但这是一个陷阱。在大型组织中，一个人独自驱动一个计划会被协调开销压垮。

确定一个计划赞助人。没有被赋权的赞助人，你就无法改变组织的行为。组织之所以这样运作，是因为这是它们当前约束下的最优解，而如果你没有强大人物的倡导，就无法改变那些约束。生成可持续、可重复的指标。运行计划的人每周花四个多小时手动维护数据集是很常见的。这行不通。你的数据会有缺口，无法与后续步骤中的自动化集成，而且你会耗尽推动真正改变所需的精力；刷新一个指标仪表盘本身没有任何价值。为每个受影响的团队确定计划目标，并为他们提供达成这些目标的清晰路径。你的计划必须为每个受影响的团队确定具体目标，例如降低他们测试的 flake 率，或更快地关闭事故修复项。但至关重要的是，你要提供通往成功的地图！太多计划只对团队提出要求，却不提供如何达成目标的指引。计划负责人是领域专家，不要把你的策略卸载给每个团队让他们各自重新发明。构建工具和文档来支持团队达成目标。一旦你为团队确定了朝着计划目标前进的清晰路径，就要想办法帮助他们做出这些改变！这可能是提供“黄金示例”来说明事情应该是什么样子，或者更好的是，提供一个重构困难代码段到新模式的示例 pull request。也可能是提供一个测试脚本来验证迁移是否正确。甚至可以是自动生成转换提交，让他们只需测试、验证和合并，而无需自己编写。尽可能多做这些事，以避免每个团队都必须深入理解你试图推进的问题空间。创建一个目标仪表盘并广泛分享。一旦你向每个团队传达了计划目标，就必须提供仪表盘，帮助他们了解当前状态、他们的目标，并对他们（希望中的）进展给予强化反馈。最好的仪表盘既是每个团队工作的记分卡，也能为每个团队提供下一步重点关注方向的线索。你的仪表盘应该支持三个不同的缩放级别。完全拉远的一级帮助你评估计划的影响。完全拉近的一级帮助单个团队理解他们剩余的工作。两者之间的第三级帮助组织领导者让他们的团队负责（并支持你的计划赞助人提出具体、明确的诉求来让这些领导者负责）。向落后于目标的人发送程序化的提醒。人们都很忙。他们不会总是优先考虑你的计划目标。或者，他们可能出色地完成了你要求的改进，但之后又退回到已废弃的实践。用提醒来引导团队将注意力转向他们下一步应为计划目标做的工作。记住，注意力是一种稀缺资源！如果你用一封提醒邮件或 ping 浪费了别人的时间，他们就不会再注意下一个了。定期与你的赞助人一起回顾计划状态。计划试图在组织优先级上取得进展，而这个优先级并不天然与团队的目标对齐。许多团队难以从本地优先级中抽身来完成全局优先级。这时，与你的赞助人一起回顾整体进展，并向他指出哪些团队在优先考虑计划工作，就变得至关重要。有效利用你的赞助人来弥合优先级错位，将是成功的关键。

如果你发现自己在技术质量上挣扎——我们都会经常这样——那就从一些小事开始，然后不断迭代直到它起作用。然后再添加另一项技术，也对它进行迭代。慢慢构建起真正有效的东西，即使这意味着要承受“不够快”的指责。在复杂系统和相互依赖的情况下，快速行动只是表象，缓慢行动才能真正把事情做好。
