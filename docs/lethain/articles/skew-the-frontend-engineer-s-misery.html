偏差，前端工程师的痛苦

2009-04-28 · 阅读原文

关于前端工程师与后端工程师区别的一种流行解释是：前端工程师需要掌握更广泛的技术技能，而后端工程师则需要更专注的技能组合。这种将前端工程师视为技术通才的看法，导致一些人把前端工程师看作是后端工程师这位“工匠”的“技工”。但前端工程师作为通才的角色并不局限于技术层面，他们在更广泛的意义上也是通才。

在一个健康的团队中，后端工程师会频繁与产品经理沟通，偶尔也会和前端工程师交流，但后端工程师说话时通常带着权威感。当专家发言时，大家都会认真倾听。另一方面，几乎任何人都愿意站起来教清洁工怎么拖地。

由于影响力有限、无数人插手、批评门槛低以及被认为工作琐碎，前端工程师成了软件开发领域的清洁工。他们要推的不是垃圾，而是“偏差”（skew）这座大山——即团队成员对项目认知之间的差距。

用扫帚清理有毒废物

偏差与软件开发的关系，就像放射性废物与核能生产的关系：它是一种不受欢迎的副产品，难以处理。从项目构思的第一刻起，就会存在对项目目标和意图的不同看法。早期这些差异往往是宏大的、理想化的，但随着时间推移，这些不一致会逐渐演变成令人尴尬的具体障碍。

偏差的增长意味着——当你到了需要集成各个组件的时候——你会发现每个人都做了母接头，而且都确信别人在做公接头，但没有人确认到底是谁在做。

偏差就是痛苦。偏差就是你的痛苦。

困扰前端工程师的误解

你可能会说，对抗产品偏差不应该是前端工程团队的责任。那不是产品管理的工作吗？或者工程管理的工作？这不是我的职责，对吧？不幸的是，现实并不看工作描述，无论你是否应该负责，现实都会把偏差摆在你和成功之间。

有多种认知加剧了偏差对前端工程师的影响：

前端工程是……琐碎的。前端工程是……美化性的。前端工程是……只是实现设计。前端工程是……只是实现用户体验。前端工程是……解决后端不足的地方。前端工程是……即使非技术人员也能轻松理解。前端工程是……其他学科的技术人员也能轻松理解。

这些认知以阴险而可预测的方式发挥作用。

偏差场景 1

不知为何，你的后端存储的是 JSON 序列化数组的 Blob，但如果能单独编辑条目是不是很酷？有人抓住了这个想法，不知不觉中它就变成了产品需求。后端工程师进度已经落后，他们说重写系统以支持新的交互范式需要一周时间。没关系，前端可以用一些 JavaScript 来管理这个交互就行。

对前端工程师来说，甚至不值得争论，因为无论如何他们都得彻底重做他们的交互。实际上， sticking 到当前系统，他们可以和一个静态的 API 打交道，而不是一个不断变化、会以各种新奇方式出错的 API，所以前端工程师就去做了这个改动。

现在后端工程师认为产品是按 Blob 运作的，前端工程师理解它是一堆 Blob 和条目的混合，而其他所有人则认为它是按条目运作的。

恭喜，你刚刚被偏差刺穿了。

偏差场景 2

你的产品差不多快完成了，但关于文案和一些其他细节还有些讨论。你注意到有人有点安静，正在专注地盯着什么。或者他们可能在玩手机上的俄罗斯方块。你希望是后者，但他们开始试图插话。几分钟后他们成功了：我们真的应该把那些消息用弹窗显示。

“不行，”你争辩道，“那实际上是对架构的重大改动。”“什么？”他们轻笑，“现在大家都在用弹窗。用户喜欢弹窗。肯定很简单。”

你真正想说的是这样的：

但你实际说出来的更接近：

“用弹窗显示错误消息意味着我需要在离开当前页面之前就知道操作的影响。如果从一开始就按这种方式设计，这很容易做到，但它不是能事后随便加上的东西。”“大家都用弹窗。不会那么难的。我觉得我侄子在他网站上加过弹窗。他才五岁。”“呃，好吧，因为涉及复杂的应用逻辑，这比只是加个提示要复杂得多。”“嗯，我很确定大家真的很想要这些弹窗。”

又被刺穿了。这一次是因为前端工程师认为用弹窗管理提交错误是一个复杂的修改，但对其他人来说两者似乎可以互换。不仅两群人的视角存在偏差，而且前端的视角甚至不在其他群体的认知地图上。

为什么你还是会拿起那把拖把

不管你是否相信管理偏差是你的工作还是别人的工作，你最终还是会去对抗它。任何哲学上的顾虑，都会被最实际的老师——痛苦——所击败。

由于前端工作被认为相对琐碎（与后端工作相比），加上有那么多团队拥有前端的某一部分（设计师拥有外观，用户体验拥有交互机制，产品拥有其他部分），这意味着前端工程师会很早就从各个角度看到偏差。前端工程师必须和每个人沟通，他们必须深入细节，而这正是沟通不畅最明显的地方。如果你忽略设计师的偏差，你就没有实现他们的设计。如果你忽略产品管理的偏差，你就没有实现他们的愿景。以此类推。所有权的减少直接转化为对偏差的脆弱性增加。

前端工程师最终会去处理偏差，因为他们最无法回避或忽视它。前端工程师处理偏差，是因为他们厌倦了一再被偏差刺穿。

减少偏差

有一些减少偏差的方法，有些比其他更有效。虽然意识到这句话的讽刺意味，但防止偏差最无效的方式，远远是告诉其他人这件事。虽然讨论偏差的词汇在不同个人和群体之间有所不同，但每个人其实都已经知道它的存在，只是他们不像前端工程师那样强烈地感受到它的痛苦。教育是个崇高的理想，但当你的理智悬于一线时，你不能等着别人“明白”。

以下是一些对抗偏差的策略。你会注意到这些主要是组织层面的改变，而不是针对当前流程的临时创可贴；你不会在停尸房里做 triage。

工程师最后的防线通常是说“不”，或者“不可能”，或者对那些战术型的人来说，“这个需求有不小的影响”。我认为这对前端工程师来说效果不佳，因为他们的所有权较少，而且他们的工作总给人琐碎的印象。说“不”总是会招来指责你无能的眼光，但当人们认为你是在拒绝骑儿童三轮车、同时又在干涉他们的工作时说“不”……那就把痛苦提升到了另一个级别。对抗偏差最好的防御是拥有一个尽可能小的团队——并且团队内部的隔阂尽可能少。这就是为什么小型初创公司几乎没有偏差。当前端那个人同时是设计师和产品经理，他只需要和后端那个人沟通时，就没多少空间产生混淆，而清理混淆也相当直接。给予前端团队对其产品更大的所有权。偏差产生于群体之间，但当一个群体为另一个群体必须实现的东西做设计时，偏差会被放大。这不仅适用于设计师和产品经理来架构前端，也适用于软件架构师为其他工程师设计一个系统。把架构师和实现者分开，不仅让实现者感到沮丧，也是通往偏差的直通车。

逐步取胜

一个更好的作者可能会把顿悟留到最后。我没有。项目偏差短期内不会消失。在 Fred Brooks 之前它就在搞砸项目，从那以后一直如此。这是一场 uphill 的战斗，但有时你可以在对抗偏差的战斗中赢得一场小胜，即使你知道从长远来看你会输掉这场战争。

今天，我对此表示接受。
