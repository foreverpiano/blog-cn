偏差，前端工程师的苦难

2009-04-28 · 阅读原文

关于前端工程师与后端工程师区别的一种流行解释是，前端工程师需要掌握更广泛的技术技能，而后端工程师则需要更专注的技能组合。这种将前端工程师视为技术通才的观点，让一些人把前端工程师看作后端工程师这位“工匠”的“技工”。但前端工程师作为通才的角色并不局限于技术领域，他们在更广泛的意义上也是通才。

在一个健康的团队中，后端工程师会频繁地与产品经理沟通，偶尔也会与前端工程师交流，但后端工程师说话时通常带着权威的语气。专家发言时，大家都会倾听。另一方面，几乎任何人都愿意站起来教清洁工如何拖地。

由于影响力有限、无数人插手、批评门槛低，以及工作被视为琐碎，前端工程师成了软件开发中的清洁工。他们要搬动的不是垃圾，而是压在身上的巨石：偏差（skew），即团队成员对项目认知之间的差距。

用扫帚清理有毒废料

偏差与软件开发的关系，就像放射性废料与核能发电的关系：它是一种不受欢迎的副产品，难以处理。从项目构思的第一刻起，就存在对项目目标和意图的不同看法。早期这些差异往往是宏观而高远的，但随着时间推移，这些不一致会逐渐演变成令人不安的具体障碍。

偏差的增长意味着——当你到了集成各部分组件的时候——你会发现大家都在造母接头，而且都确信别人在造公接头，但没有人真正确认过是谁在做。

偏差就是痛苦。偏差就是你的痛苦。

困扰前端工程师的误解

你可能会说，对抗产品偏差不应该是前端工程团队的责任。那不是产品管理的工作吗？或者工程管理的工作？这不是我的职责，对吧？不幸的是，现实世界不看职位描述。不管你是否应该为此负责，现实都会把偏差摆在你和成功之间。

有一些认知加剧了偏差对前端工程师的影响：

前端工程是……琐碎的。前端工程是……装饰性的。前端工程是……仅仅实现一个设计。前端工程是……仅仅实现一个用户体验。前端工程是……解决后端不足的地方。前端工程是……即使非技术人员也能轻松理解的。前端工程是……其他领域技术人员也能轻松理解的。

这些认知以狡猾且可预测的方式发挥作用。

偏差场景 1

不知为何，你的后端存储的是 JSON 序列化数组的二进制块，但如果能单独编辑条目不是很酷吗？有人抓住了这个想法，突然间它就凝固成了产品需求。后端工程师已经落后于进度，他们说重写整个系统以支持新的交互范式需要一周时间。没关系，前端可以用一些 JavaScript 来处理这个交互。

对前端工程师来说，甚至不值得为此争论，因为无论如何他们都要彻底重做交互逻辑。事实上，继续使用当前系统的话，他们可以基于一个静态的 API 工作，而不是一个不断变化、会以各种新奇方式出错的 API，所以前端工程师就着手做了这个改动。

现在后端工程师认为产品是以“块”运作的，前端工程师理解它是一个块和条目的混合体，而其他所有人则认为它是在条目层面运作的。

恭喜，你刚刚被偏差刺穿了。

偏差场景 2

你差不多快完成产品了，但关于文案和其他一些细节还有些讨论。你注意到有人安静下来，专注在某件事上。或者他们可能在手机上玩俄罗斯方块。你希望是后者，但他们开始试图插话。几分钟后他们成功了：我们真的应该把那些消息用弹窗显示出来。

“不行”，你争辩道，“那实际上是对架构相当大的改动。”“什么？”他们轻笑，“现在大家都在用弹窗。用户喜欢弹窗。这肯定很简单。”

“用弹窗显示错误信息意味着我需要在离开当前页面之前就知道操作的影响。如果从一开始就这么设计，这很容易做到，但不可能作为一个事后补丁加上去。”“大家都在用弹窗，不可能那么难。我觉得我侄子给他网站加了弹窗。他才五岁。”“呃，好吧，因为涉及的应用逻辑，这比仅仅加一个提示框要复杂得多。”“嗯，我很确定大家都真的想要这些弹窗。”

再次被刺穿。这一次是因为前端工程师把用弹窗管理提交错误视为一项复杂的修改，但在其他人看来两者似乎可以互换。不仅两个群体的视角存在偏差，前端视角甚至不在其他群体的地图上。

为什么你最终还是会拿起那把拖把

不管你是否相信管理偏差是你的工作还是别人的工作，你最终都会去与之抗争。任何哲学上的顾虑，都会被最实际的老师——痛苦——所击败。

人们认为前端工作相对琐碎（与后端工作相比），加上有这么多不同群体拥有前端的一部分（设计师拥有外观，用户体验团队拥有交互机制，产品团队拥有其他部分），这意味着前端工程师会很早就从各个角度看到偏差。前端工程师必须和每个人交谈，必须深入细节，而这正是误解最容易显现的地方。如果你忽略设计师的偏差，你就没有实现他们的设计。如果你忽略产品管理的偏差，你就没有实现他们的愿景。以此类推。所有权减少直接转化为对偏差的脆弱性增加。

前端工程师最终会去处理偏差，因为他们最无法回避或忽视它。前端工程师处理偏差，是因为他们厌倦了被偏差反复刺穿。

减少偏差

有一些减少偏差的方法，有些比其他更有效。虽然认识到这句话的讽刺意味，但防止偏差最无效的方式，远远是告诉其他人这件事。虽然讨论偏差的词汇在不同个人和群体间有所不同，但每个人其实都已经知道它的存在，只是他们感受不到前端工程师所感受到的那种剧烈痛苦。教育是一个崇高的理想，但当你的理智悬于一线时，你不能等着别人“明白”。

以下是一些对抗偏差的策略。你会注意到这些主要是组织层面的改变，而不是针对当前流程的临时创可贴；你不会在停尸房里进行 triage（分诊）。

工程师最后的防线通常是说“不”，或者“这不可能”，或者对于战术型的人来说“这个需求有非 trivial 的影响”。我认为这对前端工程师效果不佳，因为他们的所有权较少，而且他们的工作总被笼罩在琐碎的印象之下。说“不”总是会招来指责你无能的目光，但当人们认为你是在拒绝骑儿童三轮车的同时还干扰他们的工作时说“不”……那就把痛苦提升到了另一个级别。对抗偏差最好的防御，是拥有一个尽可能小的团队——并且团队内部的分工尽可能少。这就是为什么小型初创公司几乎没有偏差。当前端那个人同时是设计师、产品经理，他只需要和后端那个人沟通时，就没有太多产生混淆的空间，而清理混淆也相当直接。赋予前端团队对他们产品的更大所有权。偏差产生于群体之间，但当一个群体设计出另一个群体必须实现的东西时，偏差会被放大。这不仅适用于设计师和产品经理为前端做架构设计，也适用于软件架构师为其他工程师设计一个系统。把架构师和实现者分开，不仅会让实现者感到沮丧，更是通往偏差的直达路径。

逐步取胜

一个更好的作者会在结尾留一个顿悟。我没有。项目偏差不会很快消失。在 Fred Brooks 之前它就在搞砸项目，从那以后也一直如此。这是一场 uphill 的斗争，但有时你能在明知长期会输掉战争的情况下，赢得一场对抗偏差的战斗。

今天，我对此感到释然。

就我的目的而言，前端工程师（frontend engineer）和网页开发者（web developer）之间存在区别。根据我的定义，网页开发者是在创建一个完整的产品，而前端开发者是在开发产品的前端部分，其他部分则由其他团队开发。对于 mashup 之类的项目，前端工程师和网页开发者在技术技能上的区别相当小；他们使用相同的技能集，都在和 API 打交道等等。然而，两者之间存在重要的区别：1. 网页开发者往往在小团队或作为个人工作，而前端工程师通常在大团队中工作；2. 网页开发者倾向于在现有后端服务（API 等）之上设计产品，而前端工程师通常是与正在开发的后端并行工作。因此，虽然技术技能大致相当，但社会和政治环境却完全不同。
