全局二级索引

2018-01-30 · 阅读原文

工作中我们一直在规划存储基础设施的下一阶段，其中很大一部分讨论都围绕全局二级索引（GSI）展开。这是一种被 Cassandra、DynamoDB 和 Couchbase 等水平扩展型数据存储所采用的技术。虽然我之前很习惯在一旁点头附和，但其实自己对这个概念理解得并不透彻，于是花了一些时间深入学习，并整理了这些笔记。

二级索引

大多数应用一开始都会把数据存放在某个单节点数据存储中，比如 MySQL 或 PostgreSQL。在读多写少的负载下，下一步通常是采用主从复制策略，将所有数据镜像到多个节点上。每个额外节点都保存完整的数据副本，并提供额外的 CPU、内存和磁盘资源，用于读取这些数据。

对主节点的读写可以做到强一致性，你甚至还能添加事务来原子性地增加或修改多行数据。在大多数数据库中，每张表都以 B+ 树的形式组织，这让你可以针对行的主键进行高效查询。

你可以为表添加额外的索引，这些索引会把更多列物化到新的 B+ 树中，从而支持对主键以外的其他列进行高效查询。更妙的是，因为所有写操作都发生在一台服务器上，你可以事务性地更新索引和对应的行。

由于数据和它的索引存储在同一地点，提供强一致性几乎不会带来延迟成本：一个简单的内存锁就能提供你所需的所有保证。

你通常不会想离开主从模型，但业务成功往往让你别无选择。一开始你可以通过升级更强大的服务器和数据压缩来垂直扩展，但最终写入吞吐量或数据规模会超出即使是最大服务器和最优配置的承受能力。

分片

将数据分区到多个节点的过程称为分片。大多数公司在开始分片时，首要目标是尽量少改动现有的应用逻辑，因此他们倾向于找出一个逻辑对象，用它来分片每一张表。例如在上面的表中，根据你的查询模式，你很可能选择按公司（company）进行分片。

假设你选择公司作为分片键（shard key）。那么对于每一次查询，你都要先确定哪个节点存储了该公司，然后将查询定向到那个数据库。负责路由到正确节点的机制有时被称为协调器（coordinator），也可以简单到让客户端对分片键进行一致性哈希。在某些实现中（包括本文的示意图），每个节点会同时承担存储数据和路由请求的双重职责。

一个节点会拥有某个公司的全部数据，可能还包括其他一些公司，但不会拥有西雅图（Seattle）的所有数据，因为数据是按公司而不是按城市分组的。

本地二级索引

这种将对象的数据和索引共同存放在同一节点上的模式，被称为本地二级索引（local secondary indexes）。根据你所使用的底层数据存储（如 MySQL 或 PostgreSQL），在单个节点上操作时你可以获得事务和强一致性。例如，你可以将允许搜索某公司职位的索引，与该公司的其余数据存放在同一个数据节点上，从而能够原子性地更新这个本地二级索引和数据。

缺点是这些索引的作用域仅限于给定的分片键，因此可以回答“Stripe 有哪些职位？”这样的问题，但无法回答“哪些公司在西雅图有职位？”这类问题，除非扫描所有节点，而这是一项代价很高的操作。

只要给定分片键的数据量保持较小，这种策略就可以通过不断增加数据节点来无限扩展。然而，许多人最终会遇到单个分片增长到超出单节点容纳能力的情况。还有人则厌倦了只能查询单个分片键数据的限制。

全局二级索引

这就是全局二级索引（global secondary indexes）发挥作用的地方。

其思路是创建一个使用不同列作为分片键的第二张表，并把主表的分片键存放在其中一列。这样就可以先去二级索引查询，拿到主键后再进行第二次查找来获取完整的行。

现在我们可以通过公司、城市或任何其他我们选择构建 GSI 的字段进行查询。同时我们还能将这些二级索引分片到所有节点上，从而减少单个分片需要存储的数据量。这让读、写和磁盘存储的水平扩展能力远远超越了本地二级索引模型。

但我们也引入了一个新的约束。

每个二级索引都使用不同的分片键进行分片，因此我们无法再保证某个公司的全部数据都在同一个节点上。对一个拥有多个二级索引的对象进行更新，很可能会需要在多个分片上执行写操作。这些写操作将在 CAP 定理的约束下进行，并受跨节点通信延迟的影响。数据本身仍然存储在单个节点上，只是它的索引不在，因此对对象本身的更新仍然可以做到强一致性。但大多数实现（例如 Cassandra、DynamoDB、Couchbase）选择对二级索引的更新采用最终一致性，以避免带来显著的延迟。

一些专有实现，特别是 Cosmos DB 和 Cloud Spanner，确实能在分片对象及其存储数据的 GSI 之间提供强一致性，但我还没有见过任何开源实现能做到这一点。

即使在这些专有系统中，也值得参考 Aphyr 的 Jepsen 系列文章，它们记录了许多分布式系统有时无法兑现其承诺的情况。
