探索 Contentful

2020-04-05 · 阅读原文

这篇内容与我之前稍有关联。上周末我特意花了些时间熟悉 Contentful，并在这里写下了一些笔记。自建还是采购。

为什么要用 Headless CMS？

市面上有许多 headless CMS，我个人用得最多的是 Airtable。你可以说 Airtable 不只是一个 headless CMS，这当然是个合理的观点。作为一个品类，我认为 headless CMS 在以下几个方面做得特别出色：

  • There are many of them, so it’s unlikely you’ll find your vendor shutting down without a “good enough” replacement to migrate to
  • Content management workflows are dynamic living things that change frequently, but generally it’s the steps in the process, not the representation of the process, that is the core competency. Offloading this to a flexible tool that is extensible without engineering investment is a big enabler for the teams operating the workflow and allows engineers to spend more energy on highest leverage work.
  • Because they’re headless, you own last mile delivery. This allows you to retain control of quality, latency and reliability. It also reduces switching costs, because you won’t require your users to perform a migration to a new URL, tool or whatnot. It further reduces switching costs because they require decoupling the last-mile from the workflow.
  • That same decoupling also means you can perform a incremental migration towards or away from the CMS, allowing you to move simple functionality early when you start migrating, and also to move your most sophisticated workflows onto custom tooling if/when you get around to building them.
  • The kind of content you store in a CMS is rarely sensitive. It’s usually marketing content or related to a content creation pipeline (say, articles for a magazine). This limits your exposure to risk from a security or privacy breach since you wouldn’t have user data there anyway.

onboarding 体验

在继续之前，必须说明我已经把文中提到的 API Key 都删掉了！

我通过创建一个新账号并完成他们的注册和 onboarding 流程，开始体验 Contentful。

我对他们的 onboarding 集成程度感到惊喜，承诺只需四个简单步骤：

git clone https://github.com/contentful/starter-gatsby-blog.git
cd starter-gatsby-blog
npm install
npm run setup -- \
--spaceId etc \
--deliveryToken etc \
--managementToken etc

不过我得承认，在跟着教程走的过程中确实遇到了一些问题。其中大部分问题都和我本地的环境有关，这当然是我的责任。但我的感受是，他们的 onboarding 主要聚焦在理想的集成路径上，几乎没有提及途中可能出现的问题。

首先，他们仓库里的弃用警告让人有点不安。

因为你用 Gatsby 生成的是静态站点，我知道这里的威胁面其实很小，但这也让我看到了维护这类集成所需要付出的持续成本。

其次，我家里的电脑装的是旧版本的 Node.js，导致报了一个不太友好的错误：

/Users/will/git/starter-gatsby-blog/node_modules/@hapi/joi/lib/types/object/index.js:255
!pattern.schema._validate(key, state, { ...options, abortEarly:true }).errors) {
  SyntaxError: Unexpected token ...

错误信息里没有明确说版本过时，但我根据之前的调试经验，以及它无法解析现代 JavaScript 语法，猜到可能是这个原因，于是用 brew 安装了最新版本。

brew upgrade nodejs

这引发了一场小小的升级 Node 的支线任务，因为我上次系统升级后 Homebrew 好像坏掉了，不过捣鼓一阵后总算搞定了。

升级完成后，我运行 npm run dev，结果又报了 spaceId 未设置的错误。

  TypeError: Cannot read property 'spaceId' of undefined

我以为是升级前运行 setup 导致的，于是重新跑了之前的 npm run setup 命令，结果发现问题一大堆，于是删掉 node_modules/ 重新开始。然后又报了另一个错，我只好把 package-lock.json、yarn.lock 和 node_modules/ 全部删掉，重新安装，这次终于成功了，虽然中间遇到了速率限制的错误：

12:07:08 - Rate limit error occurred. Waiting for 1532 ms before retrying...
The import was successful.

我不确定那个限流是否真的生效了。看起来是成功了，所以我假设没有影响。他们的安装流程非常强调使用 SDK，甚至完全没有提到或链接他们的直接 HTTP API。

我坚信 SDK 是现代第三方 API 的接口形式，最终会取代 HTTP/JSON 和 gRPC 接口。但我还是觉得完全不提供底层接口的链接有点不妥。通常从 API 规范入手比看 SDK 更容易理解整个 API 的数据模型和集成流程，而且当 SDK 不支持某种语言时（比如我感兴趣的 Go 语言就没有），API 就是最后的退路。

抛开对 API 文档的吐槽，接下来他们提供了非常有帮助的逐步说明，讲解 Gatsby 示例是如何与他们的 SDK 和 API 集成的。

内容都相当直白，基本就是使用你的 space 和 access token 导出所有 Contentful 数据。

之后它把我们带到一个示例应用的部署页面，要求我们选择 Netlify 或 Heroku。

Netlify 作为新兴热门的部署平台很有吸引力，Heroku 也是一个很棒的平台，但完全不提供 AWS、阿里云、Azure 或 Google Cloud 的部署说明，还是让人觉得有点奇怪。也许他们假设使用这些大厂平台的人自己能搞定，但我认为使用 Netlify 或 Heroku 的人也一样能搞定，而大多数人其实都在大型云厂商上。

话说回来，在 AWS 和 GCP 上部署其实挺简单的，你只要通过以下命令构建 Gatsby 站点：

./node_modules/.bin/gatsby build

然后把 public/ 目录放到 Firebase Hosting 或 Amazon S3 上就行了。

不管怎样，到这一步我就完成最初的教程了。

数据模型

Contentful 允许你创建不同的数据模型，本质上就是针对某类内容的数据库 schema 或电子表格表头。

你可以创建多种类型的字段，包括饱受诟病的 JSON 对象。

总的来说，这套字段和数据建模能力对一个 CMS 而言是非常合理的。虽然你可能还想到其他想要的类型，但他们支持的这些已经足够通用，我觉得几乎任何需要的内容都能比较轻松地建模出来。

工作流

我最后想做的事情是花些时间熟悉创建和编辑内容的工作流。

作为一个给 lethain.com 和现在的 staffeng.com 做过三四个版本自研 CMS 的人，我对很多细节设计都挺欣赏。比如支持预定未来发布时间就很棒，结合未来发布和 webhook 的设计，是一个巧妙地把内容创建者和工程师解耦，同时又能实现正确功能的接口。

编辑体验本身也算合理，尤其是如果你接入了内容预览集成的话。

不过，我确实觉得它提供的工作流比我预期的企业级 CMS 要简单一些。我想象中的典型工作流应该是：内容先被撰写，然后同行评审，再由编辑审核，最后发布。你可以实现其中部分环节，比如只给编辑“发布”内容的权限，但整体还是比较受限。更重要的是，它没有很好地支持工作流中各环节之间的轻松交接。

我猜你最终可能需要创建一个 workflow content type，在内容中引用工作流阶段，然后通过 webhook 根据当前阶段通知对应的人。但这对一个我认为相当常见的功能需求来说，显得有点笨拙——要求每个用户都自己建模和集成。

与 Airtable 对比

作为 Airtable 的长期用户，体验一个更专注的 headless CMS 解决方案很有意思。Airtable 有一篇博客教你如何用它配合 Gatsby 做 headless CMS，但很多时候我觉得 Airtable 自己都很难解释清楚自己是什么。连 Wikipedia 也纠结，说它是一个表格-数据库的混合体，具备数据库的功能，但以表格的形式呈现。

总的来说，我很享受这次对 Contentful 的探索，也完全能看出它对想基于它构建产品的人来说，是一个多么强大的工具箱。
