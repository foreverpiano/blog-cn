探索 Contentful

2020-04-05 · 阅读原文

这与我之前关于 有些关联。上周末我专门花时间体验了 Contentful，并在这里写下了一些笔记。自建还是采购。

为什么选择 Headless CMS？

市面上有许多 headless CMS，我个人用得最多的是 Airtable。你可以说 Airtable 并不仅仅是一个 headless CMS，这个观点完全没问题。作为一类产品，我认为 headless CMS 在以下几个方面做得特别出色：

它们数量众多，所以不太可能出现供应商突然关门，而你找不到足够好的替代方案来迁移的情况。内容管理流程是动态的、不断演变的活物，但其核心竞争力通常在于流程中的步骤，而不是流程的呈现形式。将这部分工作交给一个灵活、可扩展且无需大量工程投入的工具，能极大地赋能运营团队，同时让工程师可以将精力投入到更高杠杆的工作上。因为它们是 headless 的，你可以掌控最后一公里的交付。这让你得以控制质量、延迟和可靠性。同时也降低了切换成本，因为用户无需迁移到新的 URL、工具或其他东西。这种解耦还意味着你可以逐步向 CMS 迁移或从 CMS 迁出，允许你在迁移初期先处理简单功能，也可以在后续有能力时将最复杂的流程迁移到定制化工具上。CMS 中存储的内容通常不是敏感信息，一般是营销内容或与内容创作 pipeline 相关（如杂志文章）。这就限制了安全或隐私泄露带来的风险，因为里面本来就不会有用户数据。

onboarding 体验

在继续之前，必须说明一下，我已经把文中涉及的 API key 全部删掉了！

我通过创建一个新账号并完成他们的注册和 onboarding 流程，开始接触 Contentful。

我对他们的 onboarding 集成程度感到惊喜，他们承诺了四个简单的步骤：

git clone https://github.com/contentful/starter-gatsby-blog.git
cd starter-gatsby-blog
npm install
npm run setup -- \
--spaceId etc \
--deliveryToken etc \
--managementToken etc

不过我必须承认，在跟随教程操作的过程中还是遇到了一些问题。这些问题大多和我本地的环境有关，当然这是我的责任。但我的感受是，他们的 onboarding 主要聚焦在理想的成功路径上，并没有很好地帮助用户处理可能出现的各种问题。

首先，他们代码仓库里的弃用警告让我有些不安。

由于你用 Gatsby 生成的是静态网站，我知道这里的攻击面其实很小，但这也让我看到了长期维护这类集成的成本。

其次，我家里的电脑装的是旧版本的 Node.js，运行时报了一个不太有帮助的错误：

/Users/will/git/starter-gatsby-blog/node_modules/@hapi/joi/lib/types/object/index.js:255
!pattern.schema._validate(key, state, { ...options, abortEarly:true }).errors) {
  SyntaxError: Unexpected token ...

错误信息里并没有明确说版本过时，但我凭之前的调试经验，加上它无法解析现代 JavaScript 语法，就猜测是版本问题，于是用 brew 安装了最新版。

brew upgrade nodejs

这引发了一场升级 Node 的小支线任务，因为我上次升级操作系统后 Homebrew 似乎出了点问题，不过捣鼓一阵后还是搞定了。

升级完成后，我运行 npm run dev，却又报了 spaceId 未设置的错误。

  TypeError: Cannot read property 'spaceId' of undefined

我以为是因为升级前就跑了 setup，于是重新执行了之前的 npm run setup，结果发现问题更严重了，于是删掉 node_modules/ 重新开始。然后又出现了另一个错误，我只好把 package-lock.json、yarn.lock 和 node_modules/ 全部删掉，从头重装，这次终于成功了，不过中间遇到了速率限制的报错：

12:07:08 - Rate limit error occurred. Waiting for 1532 ms before retrying...
The import was successful.

我不确定那个限流有没有真正生效，看起来是成功了，所以我假设没有影响。他们的安装流程非常强调使用 SDK，甚至完全没有提及或链接他们的直接 HTTP API。

我坚信 SDK 是现代第三方 API 的发展趋势，最终会取代 HTTP/JSON 和 gRPC 接口，但完全不提供底层接口的链接还是显得有些不妥。从 API 规范本身去理解数据模型和集成流程往往更容易，而且当 SDK 不支持某种语言时（比如我感兴趣的 Go 语言就没有对应的 SDK），API 就是最终的 fallback。

好了，吐槽 API 文档就到这里。接下来他们提供了非常有帮助的逐步讲解，说明 Gatsby 示例是如何与他们的 SDK 和 API 集成的。

内容都相当直观，核心就是使用你的 space 和 access token 导出所有 Contentful 数据。

然后它带我们来到示例应用的部署页面，要求我们选择 Netlify 或 Heroku。

Netlify 作为一个新潮的部署平台让人眼前一亮，Heroku 也是很棒的平台，但完全不提供 AWS、阿里云、Azure 或 Google Cloud 的部署说明，还是让人觉得有点奇怪。也许他们假设使用这些大云平台的人能自己搞定，但我觉得使用 Netlify 或 Heroku 的人其实也一样能自己搞定，而大多数人其实都在用主流云服务商。

话说回来，在 AWS 和 GCP 上部署其实相当简单，你只需要通过以下命令构建 Gatsby 站点：

./node_modules/.bin/gatsby build

然后把 public/ 目录部署到 Firebase Hosting 或 Amazon S3 上即可。

不管怎样，到这一步我就完成初始教程了。

数据模型

Contentful 允许你创建不同的数据模型，本质上就是针对某类内容的数据库 schema 或电子表格表头。

你可以创建多种类型的字段，包括被很多人诟病的 JSON 对象字段。

总体来说，对于一个 CMS 而言，这是一套非常合理且功能完备的字段和数据建模能力。当然你还能想象出其他想要的类型，但他们已支持的类型已经足够通用，我认为可以比较轻松地建模出你需要的任何内容。

工作流

最后我想花些时间熟悉创建和编辑内容的工作流。

作为一个给 lethain.com 和现在的 staffeng.com 做过三四个版本自研 CMS 的人，我非常欣赏他们很多细微的设计。比如，支持设定未来发布时间就非常棒，而“未来发布 + webhook”的组合是一个聪明的接口，它能在解耦内容创建者和工程师的同时，依然提供正确的功能。

编辑体验本身也还不错，特别是如果你配置了内容预览集成之后。

然而，我确实觉得它提供的工作流比我预期中一个企业级 CMS 应该具备的要简单一些。我想象中典型的工作流应该是：内容被起草，然后同行评审，然后编辑审核，最后发布。你可以实现其中一部分，比如只允许编辑拥有“发布”内容的权限，但整体还是比较受限。更重要的是，它没有很好地支持工作流中各个步骤之间轻松的交接。

我猜你最终可能会创建一个 workflow content type，在内容中引用工作流阶段，然后通过 webhook 根据进入的阶段通知对应的人，但这对于一个我认为相当常见的需求来说，似乎有点笨拙——要求每个用户都自己建模和集成。

与 Airtable 相比

作为 Airtable 的长期用户，体验一个更专注的 headless CMS 解决方案很有意思。Airtable 有一篇博客介绍如何用它配合 Gatsby 实现 headless CMS，但在很多方面，我觉得 Airtable 对自己的定位解释得并不清晰。连 Wikipedia 也很难描述它，称其为“电子表格-数据库混合体”，具备数据库的功能，但以电子表格的形式呈现。

总的来说，我非常享受这次对 Contentful 的探索，也能清楚地看到它对希望在其上构建的人来说，是一个多么强大的工具包。
