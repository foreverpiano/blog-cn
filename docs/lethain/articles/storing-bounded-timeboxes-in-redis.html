在 Redis 中存储有界时间框

2011-04-07 · 阅读原文

假设你正在尝试编写一个简单的报表系统，用于追踪系统的错误率。然后呢——谁能想到呢？——你决定使用 Python 和 Redis。听起来轻松极了！

真的会是这样吗？

安装

首先，在本地机器上安装并启动 Redis。

curl http://redis.googlecode.com/files/redis-2.2.4.tar.gz > redis.tar.gz
tar -xzvf redis.tar.gz
cd redis-2.2.4
make
./src/redis-server

我们快速测试一下是否成功……

./src/redis-cli set a b
./src/redis-cli get a

如果第二条命令返回 b，那就说明一切就绪。很好，现在只需要安装 redispy。

virtualenv --no-site-packages zset
cd zset
. ./bin/activate
pip install redis

检查是否安装成功……

:::pycon
>>> import redis
>>> cli = redis.Redis()
>>> cli.get("a")
'b'

太好了，现在我们可以回到有界时间框的话题了。

什么是 Bounded Timeboxes？

和大家通常想象的不同，它并不是一台 DeLorean，而且这个术语可能是我自己编造的，不过我们还是继续往下说吧。在这篇文章中，“timebox”指的是一种包含某段时间内活动记录的结构，比如“1 分钟前有 100 个 Diggs”或者“2 分钟前有 200 条 tweets”。“bounded”（有界）的意思是你只想存储固定数量的时间框。下面通过一个例子来让这个概念更具体。

你正在为每个 URL 按分钟统计页面浏览量。你决定为每个 URL 使用一个 sorted set，key 是时间戳（秒数）对 60 取模，value 则是该分钟内的页面浏览次数。对这个 sorted set 的写入和读取操作如下：

:::python
import time, redis
PAGEVIEW_BUCKET = "pv.%s"

def increment_pageview(url):
    cli = redis.Redis()
    bucket = int(time.time()) % 60
    cli.zincrby(PAGEVIEW_BUCKET % url, bucket, 1)

def get_pageviews(url, bucket):
    cli = redis.Redis()
    return cli.zscore(PAGEVIEW_BUCKET % url, bucket)

这种方式还算合理，能让我们找到页面浏览量最高（或最低）的那些分钟，

:::python
# get top 10 buckets by num pageviews, include num pageviews
cli.revrange(PAGEVIEW_BUCKET % url, 0, 9, withscores=True)

# get bottom 10 buckets by num pageviews, don't include num pageviews
cli.range(PAGEVIEW_BUCKET % url, 0, 9)

但它不支持只保留最近 N 个时间桶，也不支持获取最近这些时间桶的总浏览量。

如果只使用一个 sorted set，当你需要清理时，就必须取出所有 key，在 Python 中排序后再进行裁剪。对于规模较小的集合来说，这可能是一个性能尚可——尽管有些折磨人——的解决方案。

:::python
MAX_BUCKETS = 10

def increment_pageview(url):
    cli = redis.Redis()
    bucket = (int(time.time()) * 60,)
    url_key = PAGEVIEW % url
    cli.zincrby(url_key, bucket, 1)
    num_keys = cli.zcard(url_key)
    if num_keys > MAX_BUCKETS:
        all_keys = cli.rank(url_key, 0, num_keys, withscores=True)
        # note that older buckets are always lower ranking ints,
        # although they are being stored as strings, so we have
        # to coerce them into ints
        sorted_keys = sorted((int(a), b) for a,b in x.iteritems())
        for key, score in sorted_keys[:num_keys-MAX_BUCKETS]:
            cli.zrem(url_key, key)

没错，它能工作。但该死，这方案实在难以让人喜欢，而且它把数据结构的维护逻辑从 Redis 推到了应用层。在这个场景下我们可能不在意，因为所有清理操作都是幂等的，不用担心竞态条件，但我们完全可以做得更好。

我们确实可以做得更好——如果“更好”的定义是：“占用两倍内存，但在概念上更清晰，并且在大规模 sorted set 上性能更好。”

WATCH、MULTI 和 EXEC

答案是使用两个 sorted set。第一个与之前一样存放数据，第二个则将时间名称作为 value，这样我们不仅能执行之前的操作，还能删除较旧的时间框。

我们还需要使用几个相对不那么常见的 Redis 命令，以便在面对并发请求时保持两个 sorted set 的同步：

WATCH 可以让事务变成有条件的：如果你正在 WATCH 的某个值被其他客户端修改，那么后续的事务将会失败。（你 WATCH A，然后用 GET A 获取它的值，接着执行 MULTI、INCR A 100、EXEC；如果在你 WATCH 之后、事务在 Redis 服务器执行完成之前，另一个客户端修改了 A，那么事务会失败，否则就会成功地执行自增。）MULTI 允许你将多个命令放入一个事务中，要么全部成功，要么全部失败。所有 WATCH 命令都必须在 MULTI 之前发出。EXEC 则会执行自 MULTI 以来所有的命令。

这些机制使得在 Redis 中执行较为复杂的事务操作成为可能。同时也能通过批量发送多个命令来提升性能。

redispy 通过 pipeline 来暴露 MULTI 和 EXEC。下面这个例子是以极高的“偏执度”从 sorted set 中弹出两个元素（如果元素不够它会失败，否则会一直请求服务器，直到读到 sorted set 的末尾并在其他客户端写入之前移除已读取的元素）：

:::python
cli = redis.Redis()
while True:
    try:
        cli.watch("a")
        (first, second) = cli.zrange("a", 0, 1)
        cli.pipeline().zrem("a", first).zrem("a", second).execute()
        break
    except redis.exceptions.WatchError:
        pass

如果存在大量的写竞争，这种方式可能会让服务器忙个不停，但它绝对是事务性的。好了，让我们用同样的思路来构建我们的有界时间框吧。

:::python
import time, redis
PAGEVIEW_BUCKET = "pv.%s"
TIME_BUCKET = "tb.%s"
MAX_BUCKETS = 1000

def increment_pageview(url):
    cli = redis.Redis()
    bucket = int(time.time()) % 60
    pv_key = PAGEVIEW_BUCKET % url
    cli.zincrby(pv_key, bucket, 1)

    # ensure that the bucket's KV exists in TIME_BUCKET
    tb_key = TIME_BUCKET % url
    cli.watch(tb_key)
    time_bucket_exists = cli.zscore(tb_key, bucket)
    if not time_bucket_exists:
        try:
            cli.pipeline().zadd(tb_key, bucket, bucket).execute()
        except redis.exceptions.WatchError:
            # somebody else already initialized the key,
            # we don't need to initialize it again
            pass

    # trim any excess values
    to_rem = cli.zrevrange(tb_key, MAX_BUCKETS, MAX_BUCKETS)
    if to_rem:
        # we aren't watching any values, so no need catch WatchError
        cli.pipeline().zrem(tb_key, bucket).zrem(pv_key, bucket).execute()

def recent_buckets(url, offset, limit):
    "Get the most recent time buckets and their pageviews for a URL."
    cli = redis.Redis()
    tb_key = TIME_BUCKET % url
    pv_key = PAGEVIEW_BUCKET % url

    # note that we are watching the time bucket key,
    # not the pageview key, so this watch will only fail
    # if executed while a call to ``increment_pageview``
    # trims one of the buckets, so we don't expect for
    # frequent failures here, but we can rest assured
    # we will never return data for a bucket whose data
    # we are no longer storing
    while True:
        try:
            cli.watch(tb_key)
            # end value is inclusive, so have to do limit-1 for
            # traditional offset/limit expectations
            recent_buckets = cli.zrevrange(tb_key, offset, limit-1)
            pipe = cli.pipeline()
            for bucket in recent_buckets:
                pipe.zscore(bucket)
            scores = pipe.execute()
            return zip(recent_buckets, scores)
        except redis.exceptions.WatchError:
            pass

多么简洁的改进！不是吗？好吧，我承认对于我们想要完成的目标来说它还是相当复杂的，但我敢说它满足了大多数希望维护固定数量时间桶的分析系统的需求。而且你很可能也学到了一些关于 WATCH、MULTI 和 EXEC 命令的知识。
