构建内部 Agent：提示词与技能的迭代优化

2026-01-01 · 阅读原文

我们内部的某些工作流使用频率相当高，而实际使用情况也暴露了当前提示词、技能和工具的不足。以下是我们迭代优化这些内部工作流的具体做法。

本文是 构建内部 Agent 系列的一部分。

为什么迭代优化如此重要？

当企业推动 AI 主导的自动化（特别是基于 LLM Agent 的自动化）时，通常有两个主要目标。首先是短期目标：提升生产力，这固然很重要。其次，我认为更重要的是长期目标：帮助员工建立起一种健康的直觉，懂得如何使用各种类型的 Agent 来完成复杂任务。

如果我们想从 LLM 这波技术中获得真正惊人的自动化收益，那么成果不会来自我们第一波构建的特定工具，而是来自一群受 LLM 启发的新型用户和开发者。这种人才无法简单地从外部招聘，只能通过内部培养。而让更多人参与到 LLM 驱动系统的迭代优化中，是我所见过的最有效的方法。

我们如何实现迭代优化？

我们采用了多种不同方法，目前都在使用中。按照从早到晚的顺序，我们的做法包括：

  1. Being responsive to feedback is our primary mechanism for solving issues. This is both responding quickly in an internal #ai channel, but also skimming through workflows each day to see humans interacting, for better and for worse, with the agents. This is the most valuable ongoing source of improvement.
  2. Owner-led refinement has been our intended primary mechanism, although in practice it’s more of the secondary mechanism. We store our prompts in Notion documents, where they can be edited by their owners in real-time. Permissions vary on a per-document basis, but most prompts are editable by anyone at the company, as we try to facilitate rapid learning.Editable prompts alone aren’t enough, these prompts also need to be discoverable. To address that, whenever an action is driven by a workflow, we include a link to the prompt. For example, a Slack message sent by a chat bot will include a link to the prompt, as well a comment in Jira.
  3. Claude-enhanced, owner-led refinement via the Datadog MCP to pull logs into the repository where the skills live has been fairly effective, although mostly as a technique used by the AI Engineering team rather than directly by owners. Skills are a bit of a platform, as they are used by many different workflows, so it may be inevitable that they are maintained by a central team rather than by workflow owners.
  4. Dashboard tracking shows how often each workflow runs and errors associated with those runs. We also track how often each tool is used, including how frequently each skill is loaded.

我猜测随着时间推移，我们会继续增加更多的优化技术，而无法舍弃任何现有的方法。这多少有些令人失望——我希望能用更少的方法达到同样的效果——但如果我们去掉其中任何一种，效果都会变差。

后续步骤

我们目前尚未做到、但却是让这项工作真正有价值的关键下一步，是加入主观的工作流后评估机制，用于判断该工作流是否有效。虽然我们已有 构建内部 Agent：用 Evals 验证工作流，但这里的想法是用评估机制来评价单个工作流的每次运行，这将提供非常有价值的细节洞察。

当前进展

根据我们目前的经验，工作流大致可以分为三种原型：聊天机器人、已被充分理解的迭代型工作流（例如对已合并 PR 使用 :merge: 反应，如 构建内部 Agent：代码驱动 vs LLM 驱动的工作流 中讨论的那样），以及尚未被充分理解的工作流。

一旦我们构建出代码驱动的工作流，它们一直都能很好地为我们工作，因为此时我们已经打造了一个高度聚焦、被充分理解的解决方案。相反，聊天机器人面对的是一个极其宽泛、模糊的问题空间，我认为运行后评估将为它们提供高质量的数据集，让我们能够以少量的人类在环（human-in-the-loop）方式，逐步迭代改进它们的提示词和技能。

对我们而言，仍然开放的问题是：如何更好地识别那些尚未被充分理解的工作流，并对其进行迭代。理想情况下，这一过程不需要每项工作流都由产品工程师单独去理解和实现。我们还没有找到可扩展的解决办法，但我确实认为，可扩展地解决这个问题，正是决定这些内部 Agent 究竟只是“有点用处”（频繁执行、由多人完成的任务最终被自动化），还是能够带来真正变革（大量任务，即使是不频繁、仅由少数人完成的任务也被自动化）的关键。
