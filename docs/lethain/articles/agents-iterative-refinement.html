构建内部 Agent：迭代优化 Prompt 与技能

2026-01-01 · 阅读原文

我们的一些内部工作流使用频率相当高，使用过程中也暴露出当前 Prompt、技能和工具的不足之处。下面是我们如何对这些内部工作流进行迭代优化的。

本文属于 构建内部 Agent 系列。

为什么迭代优化如此重要？

当企业推进 AI 主导的自动化（特指由 LLM Agent 驱动的自动化）时，通常有两个主要目标。首先是短期目标——提升生产力，这固然很重要。其次，也是我认为更重要的一点，是长期目标——帮助员工建立起使用各类 Agent 来完成复杂任务的健康直觉。

如果我们希望从 LLM 这波技术浪潮中获得真正了不起的自动化收益，那么这种收益不会来自我们第一波构建的那些特定工具，而是来自一批新型的、被 LLM 深刻影响的用户和开发者。这些人才无法简单地从外部招聘，只能通过内部培养。而让更多人参与到 LLM 驱动系统的迭代优化中，是我所见过的最有效的方法。

我们如何实现迭代优化？

我们采用了多种不同方法，所有这些方法目前都在使用中。按照从早到晚的顺序，我们的做法包括：

快速响应反馈是我们解决问题的首要机制。这既包括在公司内部 #ai 频道中快速回复，也包括每天浏览工作流日志，观察人类与 Agent 的交互情况——无论是好的还是坏的体验。这是我们持续改进最有价值的来源。 Owner 主导的优化原本是我们计划中的主要机制，但在实践中更多处于次要位置。我们将 Prompt 存储在 Notion 文档中，其所有者可以实时编辑。每个文档的权限不同，但大多数 Prompt 对公司任何人都可编辑，因为我们希望促进快速学习。 仅靠可编辑的 Prompt 还不够，这些 Prompt 还需要易于被发现。为此，每当某个操作由工作流驱动时，我们都会在其中加入 Prompt 的链接。例如，聊天机器人发送的 Slack 消息会包含 Prompt 链接，同时也会在 Jira 中添加评论。 通过 Datadog MCP 将日志拉取到存放技能的代码仓库中，借助 Claude 增强的 Owner 主导优化方式也相当有效，不过主要还是 AI Engineering 团队在使用，而非直接由工作流所有者使用。技能在一定程度上属于平台层，因为会被多个不同工作流复用，因此由中央团队维护可能也是不可避免的，而非由各个工作流所有者维护。 仪表盘会跟踪每个工作流的运行频率以及相关错误。我们还会跟踪每种工具的使用频率，包括每个技能被加载的次数。

我猜测随着时间推移，我们会继续增加更多优化技术，而无法放弃任何现有的方法。这多少有些令人失望——我当然希望用更少的方法就能达到同样效果——但如果我们砍掉其中任何一项，我认为整体效果会变差。

下一步计划

我们目前尚未做到、但却是让这件事真正有用的必要下一步，是引入主观的工作流后评估机制，用于判断该工作流是否真正有效。虽然我们已有 构建内部 Agent：用 Evals 验证工作流，但这里所说的是用评估机制来评价每一个具体的工作流运行实例，这将提供非常有价值的细节洞察。

当前进展

根据我们迄今的经验，工作流大致可以分为三种类型：聊天机器人、已经被充分理解的迭代型工作流（例如对已合并 PR 使用 :merge: 表情符号，正如 构建内部 Agent：代码驱动 vs LLM 驱动的工作流 中所讨论的），以及尚未被充分理解的工作流。

一旦我们构建出代码驱动的工作流，它们一直都能很好地运行，因为此时我们已经打造了一个高度专注、被充分理解的解决方案。相反，聊天机器人面对的是一个极其宽泛、模糊的问题空间，我认为运行后评估将提供高质量的数据集，让我们可以通过少量的人类在环（human-in-the-loop）方式，迭代改进它们的 Prompt 和技能。

对我们而言，目前的开放性问题是：如何更好地识别那些尚未被充分理解的工作流，并对其进行迭代优化。理想情况下不需要让产品工程师逐一去理解和实现每一个工作流。我们还没有找到可扩展的解决办法。而我认为，能否可扩展地破解这一难题，将决定这些内部 Agent 到底只是“有点用处”（最终把很多人频繁执行的任务自动化），还是真正具有变革性（让相当比例的任务——即使是那些不频繁、仅由少数人执行的任务——也能够被自动化）。
