预测合成指标。

2019-11-05 · 阅读原文

想象一下，你有一天醒来发现自己突然要负责一个站点可靠性工程（SRE）团队。上午10点，你已经下载了一本免费的SRE书籍，正在逐渐上手。这时发生了一次事故：糟糕！大家迅速集结以减轻对用户的影响，随后诊断并修复了根本原因。团队的响应非常出色，但你的用户依赖于你，你觉得今天让他们失望了。你的肩膀比几个小时前沉重了许多。你和团队坐下来，宣布了一个大胆的领导者目标：下个季度我们将实现零事故。

你的团队还不了解你，所以当你提出一个糟糕想法时，他们不会直接给你反馈，而是第二天带着一份项目清单回来，旨在实现你的目标。他们的提议从可靠的（删除所有软件然后回家）到风险较高的（添加大规模健康检查）不等。你张开嘴准备对他们的想法做出判断，停顿了一下，下巴半张着，然后又闭上了。一个小问题浮现出来：你不知道如何在这些项目之间做出选择。

使用用户影响、收入影响或SLO性能来衡量历史可靠性是直观的。然而，历史指标在决定未来要优先开展哪些工作时帮助不大。哪些工作最有影响力？需要完成多少工作才能让我们从依靠好运实现可靠，转变为可预测地可靠？

我最喜欢用来衡量复杂领域的工具之一是不可量化的度量指标。合成指标将多种输入指标组合成一个简化的视图。例如，你可以创建一个服务质量分数，它通过服务最近是否部署、是否存在未部署的CVE补丁、是否具备适当的健康检查、测试是否在十秒内完成等因素来计算。这样，你就不必逐一讨论每个方面，而是可以更笼统地谈论服务的状态。更有用的是，你可以开始描述公司所有服务的健康状况分布。

当我第一次尝试使用合成指标时，我读了Ryan McGeehan关于安全风险预测的一篇优秀文章。McGeehan讨论的技术并不完全解决优先排序未来工作的难题，但当我反复思考它们时，我产生了一个有趣的想法：我们能否利用合成指标的预测来确定和优先安排工作？

Brian Delahunty最近转任Stripe的可靠性主管，在此过渡期间，我有机会与他、Davin Bogan、Drew Fradette、Grace Flintermann以及其他许多优秀同事合作，重新思考我们应该如何选择最具影响力的可靠性项目。这里所写的内容反映了那些讨论中的大量集体思考，以及来自Niels Provos安全规划方法的启发。

我之前也写过关于使用制定可靠性策略：用系统模型思考复杂问题的文章，它与这里描述的方法有一些相似之处。

预测可靠性

让我们深入一个具体的例子，说明如何预测合成指标。我将重点放在可靠性上，但我相信这种技术适用于任何通常用滞后指标而非领先指标来评估执行效果的领域。它对于滞后指标方差较大的领域特别有价值，比如安全漏洞、重大事故等。

在预测合成指标之前，我们必须先设计这个合成指标本身。为了设计一个可靠性的合成指标，一个有用的问题是：什么必须为真，我们才会相信自己的系统是可预测地可靠的？

特别感谢David Judd，他花了大量时间深入研究这个问题，他的思考深深影响了我。

在计算可靠性时，你可能会考虑以下因素：

你进行变更的的安全程度如何？这当然包括部署代码变更，还包括功能开关、基础设施变更等。你有多少描述故障域仅由单个故障域支撑？你上次验证每个故障域内冗余机制已经过去多久？你有多少余量来应对流量峰值？你的on-call轮换在拥有足够熟练人员和适当报警频率方面是否可持续？

这里可以包含的因素是无限的，你选择哪些将取决于你特定的架构。最重要的是，对于每个输入，应该非常明显你需要开展什么样的项目来改进它。变更不够安全？构建更安全的变更管理工具。故障域冗余验证不够频繁？举办一次游戏日。远离输出指标，比如更少的事故，这会立刻迫使你回答宽泛的方法论问题。

为了让我们的例子保持简单，假设我们将可靠性指标的第一个版本聚焦在：进行安全的变更、消除单故障域的故障层级，以及验证故障层级内的冗余。

percent_safe_changes =
(percent_safe_feature_flag_changes * 0.3) +
(percent_safe_code_changes * 0.3) +
(percent_safe_infra_changes * 0.4)

percent_redundant_fault _levels = (some calculation)
percent_recently_exercised_domains = (some calculation)

reliability_forecast =
(percent_safe_changes * 0.4) +
(percent_redundant_fault_levels * 0.4) +
(percent_recently_exercised_domains * 0.2)

通过一些简单的算术和实验，你会计算出一个反映当前可靠性风险的分数。然后通过分析这些数字的变化趋势，你可以预测一年后这个分数会变成什么样子。如果你已经在收回不合理的软件上投入大量精力，那么你可能会发现，即使不启动任何新项目，明年的可靠性也会显著提升。

另一方面，你也可能发现自己正在走向灾难。无论哪种情况，这都是你规划的起点。

这个指标随后能让你计算每个考虑项目的 impact，并根据未来可靠性的投资回报率来 prioritization 它们。这也帮助你向其他团队提出更有效的请求。有了这个计算，你现在可以非常清楚地知道你希望其他团队重点关注什么，以及为什么这项工作很重要。

一个季度后，你可以衡量更新后的可靠性分数，并将其与你的预测进行比较，判断你的项目是否产生了预期影响。现在，你能够针对可预测的事物来审视和优化你的可靠性策略和执行，将你的方法从对侥幸逃脱的反应不足或对不幸失败的过度反应中解脱出来。

将分数转化为影响

现在你已经在预测可靠性，你可能会说你正朝着明年的52%可靠性和后年的40%可靠性的方向发展。有些人会被这些偏低的分数所激励，但这些数字还是相当抽象。公司应该在多大程度上更看重80%的可靠性预测，而不是79%？

将预测分数转化为预测结果是非常有力的。对于可靠性，我们可以计算一次严重事故的影响，并将该分数作为未来一年发生此类事故的概率。一个简单的版本可能是取下一年的平均每日收入，然后乘以1.0减去你的风险预测值。

impact = (1.0 - reliability_forecast) * avg_daily_revenue_next_year

这是一个特别严谨的计算吗？不，真的不是。但你是否正在就你的可靠性规划的美元影响进行对话？是的，没错。你正在这么做。

迭代以达成一致

人们最初会对你的预测和影响数字产生分歧。这正是重点！每次有人对你的预测或预计影响提出异议时，那恰恰是你用来完善方法论的机会。通过几个月内与一个成员稳定的中型群体反复接触，指标才会变得有价值。只有通过这种反复应用，才能将一个复杂的指标打磨成既反映你的世界观，也反映利益相关者世界观的指标。

从Perri在《Escaping the Build Trap》中关于产品管理的方法中可以学到很多。重要的是结果，而不是交付项目，而指标的第一个版本永远不会得到正确的结果。

变得有价值

有时，在安全或可靠性等领域工作的团队会感到被一种感觉所笼罩：要么（a）表现糟糕，要么（b）表现足够好以至于可以被忽略。在糟糕和被忽略之间的连续谱上，没有一个位置感觉特别好。

预测合成指标和将这些指标转化为影响的这两种技术，将扩展你的连续谱，将“为公司和用户创造公认的价值”包括进来。即使事情进展顺利，你也可以展示需要持续投入的潜在风险。当事情进展不佳时，你可以证明自己在做正确的工作，即使其影响尚未显现。

我非常期待听到更多尝试类似方法的人的看法！

顺便说一句，我也想提到这种方法在评估事故修复质量方面有多么有用。许多事故处理程序强调必须为每个事故制定修复措施，或许还强调了完成这些修复的严格期限，但通常并不清楚这些修复的质量是否高。一个好的可靠性合成指标能轻松回答这个问题：一项修复的质量就是它在多大程度上将可靠性分数向积极方向推动。
