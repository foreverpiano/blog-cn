重构 Notion 中的内部文档

2026-02-05 · 阅读原文

在我们最新的开发者生产力调查中，文档是收到反馈第二多的领域。本文详细记录了我采取的具体步骤，目的是看看一个人在严格坚持“只做真正有效改动，而非表面功夫”的高标准下，能为改善组织文档做出多少实际进展。

诊断分析

我们当时主要面临以下几个问题：

我们在 2025 年 1 月从 Confluence 迁移到 Notion，留下了一批明显过时且错误的旧页面。这些页面让其他文档也显得维护不善，产生了一种“文档很糟糕”的负面观感。我们在“用 Git 管理文件文档”和“用 Notion 管理文档”之间缺乏一致的方法，导致大量内容重复。重复又让人觉得与其费力找出已有 N 个版本中哪个正确，还不如干脆再创建一个 N+1 版。过去一年我们引入了很多新人，他们不确定自己是否有权限更新文档，也不知道某个文件是否由专人负责。我们开始主要依靠 Notion AI 来获取和呈现内容，这使得层级结构的重要性降低，而那些不准确的片段即使被藏在角落里，也会产生负面影响。

除此之外，Notion 本身还存在一些限制：

无法通过 API 判断非 wiki 页面是否经过验证。虽然可以通过 API 判断 wiki 页面是否验证，但没人使用 wiki 页面。无法通过 API 获取 Notion Teamspace 中的所有页面，必须手动列出该 Teamspace 的顶级页面，再逐层获取其子页面。Notion 没有“归档”功能，无法将文档从搜索结果中排除。除最近编辑时间外，无法通过 API 查看页面的浏览量或使用情况。

应对策略

针对上述诊断，我们 adopted 以下策略：

优先优化 Notion AI 结果，而非手动查找：我们现在使用 Notion 的主要方式是通过直接链接或 Notion AI，而不是手动浏览。这意味着那些容易过时的“FAQ”类重复页面反而有害，而以前它们很有价值。重复和过时内容比没有内容更糟糕：不要自己写一份流程指南，而是直接链接到原始文档，或者去更新源文档。优先采用版本控制中的自然文档：我们更倾向于链接到 GitHub 中的 README，而不是在 Notion 中重复这些内容，因为 README 更可能保持更新。人人都可以整理文档：我们宁愿大家积极尝试清理文档（即使犯一些小错），也不希望文档处于无人维护的状态。自动化永远优于手动：我们是一个忙碌的团队，同时要做很多事情，很难持续投入大量时间进行深度手动整理，针对性的 curation 很好，但全局性的手动维护不现实。

具体实施

基于上述策略，我们的具体实施方式如下：

创建了“Scheduled to Archive”和“Archive”两个 Teamspace。Archive 是私有 Teamspace，放入其中的文档不会污染搜索索引。Scheduled to Archive 则是公开的，任何人都可以把文档添加到其根页面下。我们有一个每周运行的脚本，将 Scheduled to Archive 中的所有内容迁移到 Archive。这是我们在 Notion 现有约束下能找到的最有效的归档方式。清理过期页面。编写了一个脚本，从根页面开始递归构建层级，为每个页面补充子页面的最后编辑日期，然后将自身及所有子页面最后编辑时间都在 N 天之前的页面全部归档。对 3-4 个最关键的顶级页面运行此脚本后，我们归档了约 1500 页过期的文档。压缩陈旧层级。编写了第二个脚本，用于发现深埋在陈旧层级中的当前有效页面（例如 15 个不准确文档中唯一被更新的那个）。找到“被埋藏的有效页面”后，将其提升到祖父页面层级，并把原父页面及其陈旧子页面移到 Scheduled to Archive。该脚本会找出所有候选页面，然后由我逐个审核通过或拒绝。最大的困难是 API 中缺少“验证”状态，无法为特定页面及其所有后代打上可信标记。失效链接检测器。编写了第三个脚本，递归遍历层级并找出返回 404 的链接。必须确保该脚本无法访问 Archive 中的内容，否则归档页面都会显示为 404，否则就得手动去已归档内容中排查。这两种方式都可以，属于偏好问题。在大规模迁移后运行此脚本，以确保不会留下大量指向已归档文档的“幽灵链接”，否则即使移除了很多坏内容，文档体验依然会很差。对关键页面进行人工审核。在完成上述所有步骤后，我又仔细检查了所有新员工文档，确保它们都链接到顶级入职指南、写明清晰的前置条件、标出遇到问题时可以求助的 Slack 频道，并且不重复 Git 管理的 README，而是适当地链接到它们。对顶级工程和技术页面，我也进行了较轻度的类似检查，因为这些页面整体已经比较好了。

总的来说，这项工作大概花了我八个小时，完全没有占用其他人的时间，希望能显著提升我们文档的质量。虽然特定领域仍有很多工作要做，但我乐观地认为，重复内容大幅减少，加上我们正在积极维护文档的明显迹象，也会让后续的改进变得更容易。
