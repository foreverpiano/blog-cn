解决工程策略危机

2023-09-23 · 阅读原文

以下是我 10 月 4 日在旧金山 QCon 大会演讲的发言稿。本次演讲的幻灯片。解决工程策略危机的演讲视频

在我的职业生涯中，我经常从同事、团队成员以及互联网上的陌生人那里听到同样的抱怨：公司没有工程策略。我认为这个问题并不仅限于工程领域，人们也常抱怨缺少产品、设计或业务策略。虽然我对为什么那么多公司缺乏清晰的业务或产品策略没有太多发言权，但我对为什么那么多工程团队没有成文的策略，已经形成了一些明确的看法。

我有幸在多家公司参与架构工作，包括设计了 Stripe 多版架构方法（）。基于这些经验，我多次尝试就这个主题写作：提升技术一致性。

探索的量级。记录了 Stripe 工程策略的公开版本先写五个，再提炼：好的工程策略本就平淡无奇。提出了一种作为个体贡献者也能推动工程策略的方法撰写工程策略描述了工程高管如何在公司中引领工程策略我还把其他人撰写的工程策略资源整理到了《Staff Engineer》的附录中

在这次演讲中，我希望将这些想法整合成一套统一的工程策略理论，并特别强调即使你不是公司的 CTO，也能推动策略的制定。换个角度理解这场演讲，我希望“解决工程策略危机”——这正是很多人不断给我发邮件抱怨的问题。

我将要讲述的内容

在这次演讲中，我将围绕工程策略的五个主题展开：

工程策略 = 诚实的诊断 + 务实的方案它非常有用（提升开发速度、减少摩擦）它无处不在，只是很少被写下来成文的策略效果好得多你可以在公司中推动策略工作

什么是工程策略？

每当我思考策略时，都会从 Richard Rumelt 的《Good Strategy, Bad Strategy》一书出发，其中提出了有效策略的三大支柱：

诊断——一种描述挑战本质的理论。它试图找出根本原因，例如“过高的工作在途量导致我们无法完成任何任务，因此每个 sprint 都越来越落后”就是一个好的诊断。指导方针——一系列用于应对挑战的通用政策。指导方针通常是隐性或显性的权衡。例如，一条指导方针可能是“只为最紧急的团队招聘，不要把招聘名额分散到所有团队”。如果一条指导方针没有体现权衡，你就应该对它保持怀疑（比如“更努力工作来完成任务”并不是真正的指导方针，相关的指导方针可能是“让员工高强度工作并接受高流失率”）。连贯行动——由指导方针引导的一组具体行动，用来解决挑战。这是最重要的部分，也是我认为最令人兴奋的部分，因为它明确指出，只有能带来一致行动的策略才有意义。

我发现这个定义极其有用，Rumelt 的观点深刻影响了我对工程策略的思考。特别是，我认为工程策略归结为两个核心组成部分：

诚实的诊断，真实面对组织当前的需求和挑战务实的方案，在解决诊断中提出的情况的同时向前推进

听起来不错，但具体是什么意思呢？为了进一步澄清，我们来分析一个很多人在职业生涯中都经历过的场景：

你加入了一家新公司你的团队使用 Python 单体应用来构建 Widget 产品CTO 讨厌单体架构，强制要求迁移到服务你加入了另一个团队，使用新服务构建全新的 Hammer 产品两年后，你原来的团队和 Widget 产品仍然留在单体中你不知道如何在 Widget 和 Hammer 之间共享代码

我认为这一系列事件反复出现，正是因为糟糕的策略，而好的策略可以防止它发生。让我们深入策略的各个组成部分，看看策略如何导致以及如何防止这种情况发生。

先从“诚实的诊断”开始，特别是看看在这个场景下，糟糕的诚实诊断会是什么样子。（顺便说一句，我不认为“不诚实”是“诚实”诊断的反义词，它们通常是“糟糕”而不是“不诚实”。）

这是一个糟糕的诊断：

“我们可以在三个月内从单体迁移到服务。”“我们已经通过把一个相当复杂的组件从单体中迁移出来，降低了方案的风险。”“我们愿意大力投资服务迁移，即使这意味着短期内产品速度会放缓。”“我们愿意扩充开发者工具团队，让他们除了支持现有单体之外，还要为服务构建新工具。”

好，现在我们来看看好的诊断可能是什么样子：

“我们可以在三个月内从单体迁移到服务。”“我们已经通过把一个相当复杂的组件从单体中迁移出来，降低了方案的风险。”“我们愿意大力投资服务迁移，即使这意味着短期内产品速度会放缓。”“我们愿意扩充开发者工具团队，让他们除了支持现有单体之外，还要为服务构建新工具。”

令人失望的是，这两个列表完全一样。在只有一个简单产品的小型初创公司里，你可能确实能在几个月内完成从单体到服务的迁移，甚至更快。但在规模较大的初创公司，这几乎肯定是不可能的。

诚实的诊断是对当前实际情况基于现实的评估。没有什么是普遍诚实的。（也没有什么是普遍糟糕的。）

一旦你找到基于现实的评估来形成诚实的诊断，策略的另一半就是务实的方案。最重要的是要记住，务实的方案会明确做出权衡，承认你真实的约束条件。例如，下面是一些好的方案，尽管写出来可能有点令人痛苦：

“我们想迁移到服务，但不愿意增加开发者工具团队的编制，所以迁移将在工具完成后 12 个月内进行。”“我们不采用额外的编程语言，即使我们更喜欢它们，因为我们没有能力去支持它们。”

这些方案的优点不在于它们是优美、雄心勃勃的工作方式宣言。它们不是高高在上的，而是对如何在约束条件下航行的具体承认。设定工程组织的价值观

回到我们 Hammer 和 Widget 产品的场景中，我们的务实方案可能是这样的：

明年将开发者工具团队扩充 2 名工程师这些新增工程师将专注于服务相关的工具在正式承诺服务迁移之前，我们会先把 Widget 产品迁移到一个服务中，并以服务方式运行它如果在 Widget 中无法超越单体的生产力，我们会迁回在此之前，不允许其他产品启动新的服务，直到我们验证 Widget 迁移是成功的且带来了显著改进（以产品工程团队花在功能开发上的时间百分比，以及相对于去年 major Widget 产品发布的数量来衡量）

再一次令人遗憾的是，务实的方案取决于你的公司和具体情况。你可能写出完全相同的务实方案，却得到非常糟糕的结果，这就是为什么。大型迁移

希望你能接受“工程策略 = 诚实的诊断 + 务实的方案”这个定义。接下来，我要试着说服你这个定义确实有用。

工程策略非常有用

让我们通过我职业生涯中遇到的一些实际工程策略案例，来证明工程策略的价值。

Stripe —— “我们在 monorepo 中运行一个 monolith。”

诊断：

我们所处的业务面临动态的外部力量——每个国家的监管机构、众多银行等金融合作伙伴，以及不断增长的企业客户——这些力量频繁且意外地变化我们与数千个外部金融基础设施集成，这些基础设施充满了糟糕、不一致、有 bug 的技术和大量人为驱动的流程我们内部有一个相当复杂的金融平台（例如资金流转），其他产品（例如 Stripe Connect）都是构建在它之上的

方案：

我们需要把全部风险预算用于应对外部变化我们通过在 monorepo 中运行 Ruby monolith 来降低技术风险我们的开发者工具团队大力投资于大规模运行 Ruby 和 monorepo对上述规则的例外情况非常少且范围很窄（数据工程、tokenization 环境）

Stripe 策略的影响：

创新预算（主要）投入到产品而非基础设施避免了让同时代大多数科技公司分心长达十年的（微）服务之旅狭窄的技术范围使得我们可以集中投资于 Sorbet（Ruby 的静态类型系统）等技术，而无需在开发者工具上投入过多的资源

Calm —— “我们是一家产品工程公司。”

诊断：

我们花了太多时间争论是否采用新技术我们采用新技术的动机似乎是为了使用和学习新技术我们有一个长期的服务迁移项目，但只有少量基础设施和平台组件被迁移出来，所有产品工程代码仍留在 monolith 中我们的开发者工具团队被拆分，一部分支持 monolith，一部分支持服务

方案：

1. 我们是一家产品工程公司2. 我们采用新技术是为了创造有价值的产品能力3. 我们不会因为其他原因采用新技术4. 我们把所有代码都写在 monolith 中，除非有功能需求导致这么做极其困难5. 上述规则的例外情况只能由 CTO 批准，且必须在 #engineering 频道以书面形式批准

Calm 策略的影响：

我们停止了关于技术投资的争论几位不愿意遵守策略的工程师离开了公司两者结合意味着我们可以将工具投资集中到 TypeScript monolith 上我们开始把创新资源投入到产品改进上，最终实现了基于用户行为的 ML 算法来推荐最佳内容、允许内容团队自助管理内容的 UI（不再需要工程支持）等等起初有些人觉得这让工作“没那么有趣”了，但最终我们把更多时间花在真正有趣的工作上——既挑战了我们作为工程师的能力，又真正帮助了用户

Uber —— “我们运行自己的硬件。”

诊断：

Uber 正处于快速地理扩张的阶段其中一些地区缺乏有意义的云基础设施我们在 X 万台服务器的规模下，自己管理硬件能带来 20-30% 的拥有成本降低，这在经济上非常有意义我们愿意承担无法使用云服务的成本

方案：

只在专用的 colo 机房运行自己的硬件不在云端存储数据或进行计算在云上做网络相关的工作（例如 TLS 终止）是可以的，类似 Point of Presence（POP）的形式任何超出 POP 范围的云实验都需要 CTO 批准

Uber 策略的影响：

我们能够进入并留在那些依赖云的竞争对手因数据本地化监管变化而无法维持运营的地区具体来说，我们能在约 6 个月内在中国的建立数据中心，而无需与我们在美国或欧洲的数据共置（题外话——这非常痛苦，我不推荐这么做）我们做了大量 NIH（Not Invented Here）工作来替换常见的云工具（生活就是权衡：即使是好的策略，也会有不好的后果！）

为什么这些策略有效？

这些策略之所以有效，有以下几个原因：

许多有趣的特性只有通过全公司统一采用才能实现（“我们运行自己的硬件”）将工具投资集中到更小的范围内（“我们在 monorepo 中运行”）减少因冲突而浪费的精力（“我们是一家产品工程公司”）控制你的创新预算（以上三者皆是）新员工，尤其是资深新员工，被迫明确地面对策略，而不是可以选择忽略它（以上三者皆是）

这就是在整个组织中做出明确、一致的权衡所拥有的力量。

缺失同样能体现价值

除了从这些正面例子论证策略的价值之外，也很容易找到负面例子：缺失或不一致的策略导致了巨大的痛苦：

Digg 耗时三年多迁移到 V4，使用全新的代码库、新的数据库、新的前端、新的后端和新的算法。虽然有对挑战的诚实诊断，但采用了极不务实的方案。Stripe 引入 Java 时评估标准不清晰，花费数年时间才评估其有效性，根源在于对当时问题的诊断不准确。Uber 在相互竞争的路由技术上投入大量资源，造成了显著的摩擦，根源在于同时遵循相互冲突的方案，却没有达成一致。

我相信你也能从自己的职业生涯中想到类似的例子！

策略无处不在，成文的策略却很少见

有趣的是，Uber 和 Stripe 都是知名科技公司，我之前也提到过它们的工程策略，但它们都没有特别积极地把策略写下来。

我逐渐相信：

大多数公司其实都有工程策略对该策略的认知往往不一致公司拥有成文工程策略的情况非常罕见

这是本次演讲第一个真正重要的 takeaways：你只要把现有的东西写下来，就能解决工程策略危机的一半问题。

我们马上会谈到如何解决另一半。

成文的策略威力更大

成文策略优于隐性策略的原因大概有无数个，但我见过特别重要的几个是：

你可以获得反馈你可以对其进行更新你可以解释为什么要做这些更新！你可以澄清困惑点细节很重要，而在未写下来的策略中几乎不可能做到它将技术决策权民主化，不再局限于一小群架构师你可以让不遵守策略的人承担责任新员工可以主动学习，而不是“通过失败来学习”

你可以在公司推动工程策略

主要有两种方式：

自下而上：如何在不是 CTO 的情况下推动策略自上而下：如果 CTO 已认可，该如何推动

自上而下

这个策略是基于撰写工程策略中描述的方法修改而来的。其核心在于：如果你写出的策略正是 CTO 想要的，那么获得 CTO 的认同就会很容易。

具体做法是：

频繁向上对齐，并花时间仔细理解他们的反馈保持真诚的好奇心：让别人知道你会认真倾听以理解他们的观点务实而非教条通过“把事情做好”的过往记录来建立信任把它框定为低风险的实验，“我们先试三个月，然后再评估”让 CTO 来决定如何打破僵局

如果你读到这里，最大的想法是“我的 CTO 永远不会让我这么做”，那么十有七次，我敢保证要么是你没有写出 CTO 真正想要的策略，要么是 CTO 无法或不愿解决的内部冲突，这会更棘手一些，但你可以通过下面的自下而上方法来处理。

自下而上

自下而上的推动方法在先写五个，再提炼：好的工程策略本就平淡无奇。中有详细描述：

写 5 篇设计文档将这些设计文档综合成一份“窄策略”重复上述过程五次，得到 5 份“窄策略”将这五份窄策略再综合成一份“宽策略”你就写出了一份非常好的工程策略

这个方法确实需要很长时间，但我见过它多次奏效。即使你当前的策略存在一些差距，把它变成一份明确的策略文档后，就会更容易去弥补那些差距。

回顾

以上是我们讨论的内容：

工程策略 = 诚实的诊断 + 务实的方案它非常有用（提升开发速度、减少摩擦）它无处不在，只是很少被写下来成文的策略效果好得多你可以在公司中推动策略工作

在这些主题中，有两个看似简单却非常有效的步骤，可以帮助你解决工程策略危机：

把现有的策略写下来使用自上而下或自下而上的方法来提升现有策略的质量

这可能不是你在年度目标中写下“变得更有策略性”时所期待的行动，但它才是真正有效的。
