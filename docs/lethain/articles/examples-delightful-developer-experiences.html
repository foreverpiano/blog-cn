2019 年一些令人愉悦的开发者体验。

2019-01-07 · 阅读原文

我曾经在一家公司工作，他们的大部分功能都是构建在 Facebook 的广告 API 之上的。当时 GraphQL 还没有公开，但他们的 API 设计或多或少等同于 GraphQL。各种属性会毫无征兆地出现或消失，而要对变化做出反应，就需要频繁地紧急应对。

一种结论可能是他们不太关心与自家 API 集成的开发者体验，但我相信另一个猜测更接近真相：为复杂且不断演化的系统提供集成支持极其困难，而 Facebook Ads 完全符合这些特征。

过去这一年在很多方面都可以说是 GraphQL 的正式亮相。虽然它的许多理念代表了对 HATEOAS 的代际改进，但这些想法本身并不算特别新。

那么，真正新颖的地方在哪里呢？

我想了解过去一年里哪些开发者体验让大家觉得最有收获，于是发推征集了更多有趣的开发者体验。从这些回复、浏览 Product Hunt 的发现以及我自己的记忆中，提炼出了以下对 2019 年令人愉悦的开发者体验的思考。

代码

一个越来越常见的范式是允许开发者直接在平台上编写运行的代码。这提供了一种强大且动态的接口，在很多情况下还能意外地降低复杂度。

平台可以把部署、操作系统管理等复杂工作抽象掉，让用户只专注于控制逻辑。全部是业务细节，没有胶水代码。这种方式在决策相对无状态的场景中尤为突出，不过有状态的例子也越来越常见。

以下是一些将“代码作为接口”的优秀例子：

“Serverless 计算”依然是主导主题，全球主要云厂商之间展开了一场功能竞赛，包括 Alibaba Cloud Function Compute、AWS Lambda、Microsoft Functions 和 Google Cloud Functions。语言支持持续扩展，Java、Python、NodeJS 已很普遍，而差异化则体现在更小众的语言上。例如 Alibaba 支持 PHP，AWS 支持 Go。更值得关注的是，越来越多细分领域的产品进入 Serverless 生态，要么填补易用性空白，要么专注于支持更窄的用例：Zeit Now 承诺只构建和部署修改过的代码路径（类似于你用 Bazel 自己实现的逻辑）。Firebase 专注于支持移动开发，为移动应用提供了一整套平台（主要通过特化或扩展现有的 Google Cloud 功能）。Twilio 传统上依赖 HTTP API，但在 2017 年推出了 Twilio Functions，允许用户在 Twilio 自己的服务器上运行代码来响应 Twilio 的事件，而不是在自己的服务器上运行。Cloudflare Workers 上的 WebAssembly（有时简称 Wasm）允许开发者编写 WebAssembly 并在 Cloudflare 的边缘计算基础设施上执行。Wasm 本身是个中规中矩的产品，但作为一个平台层却非常出色：我认为长期来看大家不会直接手写 Wasm，而是用更熟悉的语言编写后再编译成 Wasm。这种思路正在 Fastly 的 Terrarium 中被探索，我后面还会再提到。AWS Lambda@Edge 和 Cloudflare Workers 或 Fastly Terrarium 的思路类似，但它们是从不同方向达到这一点的。对 Fastly 来说，转向 Wasm 是比现有基于 VCL 的配置更灵活的方案。不过 Lambda@Edge 只支持 Node.js，功能远不如支持 Java、Node.js、C# 和 Python 的 AWS Lambda。从某种角度看，把 AWS Lambda 和 Lambda@Edge 放在一起比较并不公平，因为很明显它们的实现是不同的，名字相似更多是营销考虑。但无论如何，看到物理和效率约束如何在“代码即配置”产品中造成产品限制和特化，还是很有意思的。Chrome Extensions 是另一种通过代码进行集成的有趣角度，也代表了未来“边缘计算”可能包含的另一层含义。在这里你编写 JavaScript 应用，用户可以从 Chrome 网上应用店安装，并在由互联网浏览器构成的云上运行。

编写代码之所以成为如此强大的平台接口，是因为它独特地结合了极高的表达能力和平台层面的极强控制力。不过值得指出的是，这些产品大多属于 Infrastructure-as-a-Service（IaaS），它们可以假设用户具备一定程度的技术能力。我们是否会看到“代码作为集成”机制进一步扩展到 IaaS 之外呢？

容器

Docker 等容器是一种有趣的接口选择。它们允许极高的自定义和配置能力，同时通常会限制或消除运行完整虚拟机带来的有状态性。然而在多租户环境下，容器安全依然是一个紧迫问题，而且容器常常在平台和用户之间提供了一个不够理想的接口，迫使用户去处理操作系统升级，平台则要应付动辄几个 GB 的镜像。

尽管如此，我发现了一个特别有趣的把容器作为集成点的例子，值得深入探讨，那就是 Azure IoT Edge。

Azure IoT Edge 允许你创建并指定 Docker 容器，在你的物理物联网设备上处理数据，将一部分计算从云端卸载到由物理设备构成的“云”上。容器比代码代表了更高的抽象，因为你可以在下面控制整个虚拟机。在共享计算环境中容器存在一定的安全风险，但这不适用于在你自己的 IoT 设备上运行的情况，因此这个用例巧妙地提升了灵活性，却没有带来太多副作用。

我也认为这个产品很有意思，因为它引入了“边缘”是一个宽泛概念的观点——物理设备和 CDN 代表了边缘计算的不同侧面。

虽然如此，我依然相信容器在公司内部是一种有效的接口，因为它们在复杂度和灵活性的权衡上提供了一种有趣的可组合方式，但对外可能并不那么适用。

领域特定语言（DSL）

使用领域特定语言来描述集成行为，介于配置驱动集成和代码驱动集成之间。有些例子中的 DSL 是早期实现的副产品（类似 AWS Redshift 因为早期版本基于 Postgres 实现而使用 Postgres 协议），另一些则是为了提升正确性。

  action "Deploy to Production" {
    needs = "Provision Database"
    uses = "actions/gcloud"
    runs = "gcloud deploy"
  }

  sub pipe_if_local {
    if (client.ip ~ local) {
      return (pipe);
    }
  }

  resource "aws_elb" "frontend" {
    name = "frontend-load-balancer"
    listener {
      instance_port     = 8000
      instance_protocol = "http"
      lb_port           = 80
      lb_protocol       = "http"
    }
    instances = ["${aws_instance.app.*.id}"]
  }
GitHub Actions 允许你用一种简单的 DSL 编写命令来配置构建、测试和部署工作流：这种方式很好，因为它用 DSL 描述了各个 action 之间的关系，但并不试图描述 action 本身。相反，action 被描述为脚本或 shell 命令。我能看到 GitHub Actions 取代大范围的持续集成工具，而且它以一种非常灵活的方式实现，允许用户在平台之上创新，而不是试图定义所有可能的集成方式。Fastly 对 Varnish Configuration Language（有时简称 VCL）的使用是另一个有趣的领域特定语言例子。这是一个相当引人注目的选择，因为 VCL 是一种极为强大的语言，却被有意限制在高性能 Web 服务器所能做到的事情上，同时它的语法也相当晦涩。在这个特定案例中，我认为 VCL 对大规模采用来说还是太复杂了，我怀疑 Fastly 自己也这么认为，所以他们才实验了 Terrarium——将 Rust、C 和 TypeScript 编译成 WebAssembly 并在边缘运行。Terraform 是 HashiCorp 编写的一种 DSL，用于表示与阿里云、AWS、Azure 或 GCP 等第三方云供应商的集成。把你的产品做成构建在其他产品之上的 DSL，这个想法本身就很迷人，也有力地证明了优秀接口的重要性。在这个案例中，我认为 Terraform 最大的价值在于抽象（理论上解耦了供应商特定的配置，方便支持多云，虽然实际中这个优势有些脆弱）和可验证性（比 YAML 或 JSON 有好得多的工具来验证正确性）。

IDE 和开发环境

有几个例子是强大的 IDE 和开发环境。有些是非常专注的特定工具，有些是开发平台，还有一些介于两者之间。

Glitch 可以运行你的整个前端和后端 JavaScript 应用，提供了一整套在线 IDE、开发和部署环境。他们现有的示例中使用了 Airtable 的 API、Slack 的 API 和 Google Sheets 的 API。这有力地展示了 JavaScript 在安全和性能隔离方面已经做得多么出色。VSCode 是微软推出的免费开源 IDE，因其轻量、可配置且强大而得到广泛采用。除了免费之外，它还在很多方面做得很好：调试器、智能补全、Git 集成、扩展等等。不过它可能最出色的地方是 Language Server Protocol，它将语言支持从 IDE 本身的细节中抽象出来，让一个 LSP 集成就能支持多种 IDE。这是一种非常强大的鼓励采用 VSCode 的方式，同时也会降低未来 IDE 的准入门槛。这类平台让工具可以在质量上竞争，也让支持特定工作流的高度特化工具变得可行。我非常期待看到更多能成为平台病毒式传播载体的产品，让我们其他人也能使用。Google Cloud Shell 是个很强大的想法，允许每个人拥有一个专属的 VM 来交互和控制他们的 Google Cloud 环境。这很聪明，因为 Google 可以自动升级他们镜像中的客户端（减少向后兼容的负担），同时也提供了更好的安全和可审计原语。从用户角度，我还喜欢它避免了让人头疼的“共享管理服务器”反模式——大家在一台共享服务器上做大量关键工作，那台服务器永远磁盘不够用，CPU 被某个烂脚本跑满，或者宕机时导致整个业务中断。Hyper 是一款基于 HTML/CSS 的终端应用，允许高度自定义，同时使用熟悉的 Web 技术。这为将终端嵌入工具、打造强大 IDE 打开了大门，而无需（直接）依赖原生技术。Merlin 是 OCaml 编程语言的编辑器服务，支持自动补全等功能。默认支持 Emacs 和 Vim，但也已经集成到其他编辑器中，比如……VSCode。我觉得这个例子在三个方面都很有趣。首先，它提醒我们灵感可以来自很多地方。其次，它证明了 Emacs 和 Vim 的设计是多么优秀，在首次开发多年后依然被大量使用并持续扩展。真令人鼓舞！最后，它也证明了 Language Server Protocol 是个多么伟大的想法，因为它开启的未来将让这类工具能干净地集成到任何编辑器中。Pharo 是一个 Smalltalk 实现，将操作系统和 IDE 打包成一个整体。Pharo 对我们的要求远超大多数工具——要放弃我们整个操作系统——而我认为这正是它如此有趣的部分原因。我们为工具设置的许多障碍其实是社会建构，我们拥有的技术其实能让工具做得比现在多得多。

渐进式配置

实际上，很少有以开发者为中心的工具只提供单一的集成方式，而是提供从简单到相当复杂的多种集成能力。

当我们谈论渐进式配置时，Kubernetes 是一个有趣的讨论点。它是一个极其强大且复杂的系统，通过大量 YAML 来配置。它拥有极为强大的 HTTP API，但使用起来可能有些晦涩。在这种复杂性周围，涌现出了大量创新！有 API 客户端库的创新，有安全生成配置的创新，还有像 OpenShift、Google Kubernetes Engine 和 Amazon Elastic Container Service for Kubernetes（名字有点长）这样抽象部分复杂性的托管平台。Kubernetes 已经有了如此多层次的配置，令人印象深刻，我认为我们才刚刚开始。Google Cloud Build 是渐进式配置的一个好例子，它有一个简单的 UI 支持大部分配置，而更复杂的集成则依赖 REST API。
Clubhouse 是另一个标准且现代的例子。默认配置通过他们的 UI 完成，更强大的自定义则通过 REST API 和 Webhook 实现。

无代码编程

我就不多赘述了，但像 Airtable 和 If This Then That 这样的产品依然在我心中占有非常特殊的位置。它们是 HyperCard 在精神上的后继者，提供了相当简单的工具，让“非程序员”也能组合出功能强大的程序。

这些产品填补了标准 GUI 驱动集成和程序化集成之间的空白。它们与 GUI 驱动集成的不同之处在于，它们并不特别固执己见。它们不是为了解决某个特定问题而设计，而是一种可以通过提供可组合、开放式构建块来解决许多问题的工具。

库和工具

这算是一个杂项类别，包含了大家提到的提供特别好开发者体验、但未必完美归类到其他组的工具。

Flutter 是一个从单一代码库构建 iOS 和 Android 原生应用的工具。在某些方面类似 React Native，但似乎效果更好。pytest 是一个 Python 测试运行器，相比标准库的 Unittest，它简化了测试运行，尤其是测试编写。Laravel 和 Laravel Spark 是强大的 PHP 框架，用于开发 Web 应用。Gatsbyjs 把现代前端全家桶打包成一个既有全部能力、学习曲线又更平滑的工具。Elm 是一门用于编写可靠 Web 应用的语言，拥有类似 Haskell 的强大类型推断。React Hooks 是处理 React 中状态变更的更简单方式。Sourcegraph 是一个强大的代码搜索工具，能轻松搜索大型代码仓库。OASGraph 是一个将 OpenAPI Specification 转换为 GraphQL API 的工具，降低了开始使用 GraphQL API 的门槛。

没有被提到的东西

鉴于区块链无休止的炒作，我觉得简单提一下没人提到的几件事挺有意思的：

区块链整体，或者特别以 Ethereum 为例，作为优秀开发者体验的例子。根据不同用例，要么是钱包仍然难以安全使用，要么是交易成本依然高得离谱或波动极大。综合来看，区块链的开发者体验似乎仍有欠缺。聊天机器人也没被提及，尽管之前获得了很多关注。我想这很大程度上是因为我 Twitter 上认识的人主要关注美国和欧洲，而聊天机器人在其他市场似乎得到了大量使用。React 被提到的次数没有我预期得多，虽然 React Hooks 被提到了。也许 React 现在已经太普遍了，大家甚至不会想起要提它，就像没人提到 Python、Ruby 或 Node.js 一样。

总的来说，这是一种非常有趣的打发时间的方式！今天之前我对其中很多工具都不熟悉，这是一次很好的调研，帮助我重新思考开发者工具和出色开发者体验的未来方向。

非常期待听到大家最近遇到的其他令人印象深刻、受到启发的开发者体验的建议！
