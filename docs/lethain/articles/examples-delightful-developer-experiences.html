2019 年一些令人愉悦的开发者体验

2019-01-07 · 阅读原文

我曾经在一家公司工作，他们的大部分功能都是构建在 Facebook 的广告 API 之上的。当时 GraphQL 还没有公开，但那个 API 的设计基本等同于 GraphQL。各种属性会毫无征兆地出现或消失，应对这些变化常常需要频繁地紧急处理。

一种可能的结论是，他们不太关心开发者集成其 API 的体验，但我认为另一个猜测更接近真相：支持复杂且不断演进的系统集成极其困难，而 Facebook Ads 正是符合这些标准的典型。

过去这一年在很多方面都可以说是 GraphQL 的首秀。虽然它的很多理念相比 HATEOAS 代表了代际级的进步，但这些想法本身并不算特别新。

那么，真正新的是什么呢？

我想知道过去一年里哪些开发者体验让大家感到最有收获，于是我在 Twitter 上询问了大家最感兴趣的开发者体验。从这些回复、浏览 Product Hunt 的结果以及我自己的记忆中，提炼出了 2019 年一些令人愉悦的开发者体验反思。

代码

一种越来越普遍的范式是允许开发者编写直接在平台上运行的代码。这提供了一种强大且动态的接口，在很多情况下还能显著降低复杂度。

平台可以把部署、操作系统管理等复杂工作抽象掉，让用户只专注于控制逻辑。全是实质内容，没有胶水代码。这在决策相对无状态的场景中尤为突出，不过有状态的例子也正变得不再罕见。

一些将代码作为接口的优秀例子包括：

“Serverless 计算”依然是主导主题，各大云服务商之间展开了一场功能竞赛，包括 Alibaba Cloud Function Compute、AWS Lambda、Microsoft Functions 和 Google Cloud Functions。语言支持持续扩展，Java、Python、Node.js 已很常见，在长尾上也有差异化。例如 Alibaba 支持 PHP，AWS 支持 Go。更有趣的是看到更多细分产品进入 serverless 生态，它们要么试图填补易用性缺口，要么专注于支持更窄的使用场景：Zeit Now 承诺只选择性地构建和部署修改过的代码路径（类似你用 Bazel 自己实现的方案）。Firebase 专注于支持移动开发，为移动应用提供完整的平台（主要通过特化或扩展现有的 Google Cloud 功能）。Twilio 传统上依赖其 HTTP API，但在 2017 年推出了 Twilio Functions，允许用户在 Twilio 的事件上运行代码，这些代码在 Twilio 的服务器上执行，而不是用户自己的服务器。Cloudflare Workers 上的 WebAssembly 允许开发者编写 WebAssembly（有时缩写为 Wasm），并在 Cloudflare 的边缘计算基础设施上执行它。Wasm 本身是个平庸的产品，但却是一个出色的平台层：我认为长期来看人们不会想直接编写 Wasm，而是会用更熟悉的语言编写，然后编译成 Wasm。这种方法正在 Fastly 的 Terrarium 中被探索，我稍后会再多说一点。AWS Lambda@Edge 与 Cloudflare Workers 或 Fastly 的 Terrarium 思路类似，但他们是从不同方向实现的。对于 Fastly 来说，转向 Wasm 是比现有基于 VCL 的配置更大的灵活性。然而 Lambda@Edge 只支持 Node.js，功能远不如支持 Java、Node.js、C# 和 Python 的 AWS Lambda。在某些方面，把 AWS Lambda 和 Lambda@Edge 拿来比较是不公平的，因为很明显它们的实现是不同的，相似性主要是个营销问题，但无论如何，看到物理限制和效率约束如何在“代码即配置”产品中造成产品限制和特化，依然很有意思。Chrome Extensions 是通过代码进行集成的另一种有趣角度，也是未来“边缘计算”可能意味着的另一个方面。在这里你编写 JavaScript 应用，用户可以从 Chrome 网上应用店安装这些扩展，运行在由互联网浏览器组成的云上。

编写代码是一种强大的平台接口，因为它独特地结合了极高的表达能力和平台层面的极强控制力。不过值得指出的是，这些产品大多属于 Infrastructure-as-a-Service（IaaS），它们可以假设用户具备相当程度的技术专长。我们是否会看到“代码即集成”机制进一步扩展到 IaaS 之外？

容器

像 Docker 这样的容器是一种有趣的接口选择。它们允许极高的定制和配置，同时往往选择限制或消除运行完整虚拟机所带来的状态性。然而在多租户环境中，容器安全依然是一个迫切的问题，而且容器经常在平台和用户之间提供一个较差的接口，迫使用户去处理操作系统升级，而平台则需要应对多 GB 的镜像。

尽管如此，我发现了一个特别有趣的将容器作为集成点的例子，我认为值得深入探讨，那就是 Azure IoT Edge。

Azure IoT Edge 允许你创建并指定 Docker 容器，这些容器在你的物理物联网设备上处理数据，将部分计算从云端卸载到你的物理设备云上。容器代表了比代码更高的抽象，因为你可以在下面控制整个虚拟机。在共享计算环境中容器存在一定的安全风险，但这在运行于你自己的 IoT 设备上的场景中并不适用，因此这个用例巧妙地提升了灵活性，且几乎没有副作用。

我也普遍认为这是一个有趣的产品，因为它引入了“边缘”是一个宽泛概念的观点，物理设备和 CDN 代表了边缘计算的不同侧面。

尽管如此，我确实相信容器在公司内部是一种有效的接口，因为它们在复杂性和灵活性的权衡上提供了一个有趣的可组合接口，但在外部可能表现不佳。

领域特定语言

使用领域特定语言（DSL）来指定集成行为，介于配置驱动集成和代码驱动集成之间。有些例子中的 DSL 是其早期实现的产物（类似 AWS Redshift 使用 Postgres 协议，因为早期版本是用 Postgres 实现的），另一些则是为了提高正确性。

Github Actions 允许你用一个简单的 DSL 编写命令来配置构建、测试和部署工作流： action "Deploy to Production" { needs = "Provision Database" uses = "actions/gcloud" runs = "gcloud deploy" } 这是一种很好的方式，因为它在 DSL 中描述了各个 action 之间的关系，但并不试图描述 action 本身。相反，action 被描述为脚本或 shell 命令。我能看到 Github Actions 取代大量持续集成工具，而且它以一种非常灵活的方式做到这一点，让用户可以在其平台之上创新，而不是试图定义所有人可能想要集成的所有方式。Fastly 对 Varnish Configuration Language（有时缩写为 VCL）的使用是领域特定语言的另一个有趣例子。这是一个相当迷人的选择，因为 VCL 是一种极其强大的语言，被有意限制为高性能 Web 服务器所能做的事情，但语法也相当密集。 sub pipe_if_local { if (client.ip ~ local) { return (pipe); } } 在这种特定情况下，我认为 VCL 可能过于复杂，不适合广泛采用，我怀疑 Fastly 也同意这一点，因为他们正在用 Terrarium 做实验——它把 Rust、C 和 TypeScript 编译成 WebAssembly 并在边缘运行。Terraform 是 HashiCorp 编写的一种很有意思的 DSL，用于表示与第三方云提供商（如 Alibaba、AWS、Azure 或 GCP）的集成。 resource "aws_elb" "frontend" { name = "frontend-load-balancer" listener { instance_port = 8000 instance_protocol = "http" lb_port = 80 lb_protocol = "http" } instances = ["${aws_instance.app.*.id}"] } 把你的产品做成构建在其他产品之上的 DSL，这个想法本身就很迷人，也有力地证明了有效接口的重要性。在这个例子中，我认为 Terraform 最大的价值主张在于抽象（理论上与特定厂商的配置解耦，并容易支持多云，虽然实践中这有点牵强）和可验证性（比 YAML 或 JSON 有好得多的工具来验证正确性）。

IDE 和开发环境

有几个例子是强大的 IDE 和开发环境。有些是非常专注的特定工具，有些是开发平台，还有一些介于两者之间。

Glitch 可以运行你的整个前端和后端 JavaScript 应用，提供一个完整的在线 IDE、开发和部署环境。他们现有的一些示例使用了 Airtable 的 API、Slack 的 API 和 Google Sheets 的 API。这有力地展示了 JavaScript 在安全和性能隔离方面的沙箱技术已经发展到多么好的程度。VSCode 是微软的一个免费开源 IDE，因其轻量、可配置且强大而得到广泛采用。除了免费之外，它还在很多方面做得很好：调试器、智能补全、Git 集成、扩展等等。不过它可能做得最好的是 Language Server Protocol，它将语言支持从 IDE 细节中抽象出来，让一个 LSP 集成就能支持大量 IDE。这是一种非常强大的鼓励采用 VSCode 的方式，同时也会降低未来 IDE 的进入门槛。这类平台让工具可以在质量上竞争，也让支持特定工作流的超 specialization 工具变得可行。非常期待看到更多能成为平台病毒式传播载体的产品，让我们其他人也能使用。Google Cloud Shell 是一个相当强大的想法，允许每个人用一个专属的 VM 来交互和控制他们的 Google Cloud 环境。这很聪明，因为它让 Google 可以在自己的镜像上自动升级客户端（减少向后兼容的开销），同时也提供了更好的安全性和可审计性原语。从用户角度看，我也很喜欢它防止了令人头疼的“共享管理服务器”反模式的扩散——人们在一台共享服务器上做大量关键工作，那台服务器永远磁盘空间不够，CPU 被糟糕的脚本跑满，或者宕机时导致整个系统 outage。Hyper 是一个基于 HTML/CSS 的终端应用，允许深度定制，同时使用熟悉的 Web 技术。这为将终端嵌入工具以构建强大 IDE 打开了大门，而无需（直接）依赖原生技术。Merlin 是 OCaml 编程语言的一个编辑器服务，支持自动补全等功能。默认支持 Emacs 和 Vim，但也已集成到其他编辑器中，比如……VSCode。我认为这个例子在三个不同方面很有意思。首先，它提醒我们灵感可以来自很多地方。其次，它证明了 Emacs 和 Vim 的设计多么出色，能在首次开发多年后依然被大量使用并积极扩展。真是个启发！最后，它证明了 Language Server Protocol 是个多么伟大的想法，因为它所开启的未来将让这类工具能干净地集成到任何编辑器中。Pharo 是 Smalltalk 的一个实现，它把操作系统和 IDE 合并成一个 bundle。Pharo 对我们的要求远高于大多数工具——要放弃整个操作系统——我认为这正是它如此有趣的部分原因。我们为工具设置的许多障碍其实是社会建构，我们的技术其实能让我们在工具中做到比通常多得多的东西。

渐进式配置

在实践中，很少有以开发者为中心的工具只提供单一的集成途径，而是提供从简单到相当复杂的多种集成能力。

当我们谈论渐进式配置时，Kubernetes 是一个有趣的讨论点。Kubernetes 是一个极其强大且复杂的系统，通过大量 YAML 文件来配置。它拥有非常强大的 HTTP API，但使用起来可能有点晦涩。在这种复杂性周围，潜藏着大量创新！有 API 客户端库的创新，有安全生成配置的创新，还有托管平台来抽象部分复杂性，比如 OpenShift、Google Kubernetes Engine 和 Amazon Elastic Container Service for Kubernetes（念起来有点拗口）。Kubernetes 已有的配置层数量之多令人印象深刻，我认为我们可能才刚刚开始。Google Cloud Build 是渐进式配置的一个好例子，它有一个简单的 UI 支持大量配置，而更复杂的集成则依赖 REST API。
Clubhouse 是另一个标准、现代的例子。默认配置通过其 UI 完成，更强大的定制则通过 REST API 和 webhook 实现。

无代码编程

我不会在这上面花太多笔墨，但像 Airtable 和 If This Then That 这样的产品依然在我心中占据非常特别的位置。它们是 HyperCard 的精神继承者，提供了相当简单的工具，让“非程序员”也能组合出功能强大的程序。

这些产品填补了标准 GUI 驱动集成和编程式集成之间的空白。它们与 GUI 驱动集成的区别在于并不特别固执己见。它们不是为了解决某个特定问题，而是提供一些可组合、开放式的构建块，从而能解决很多问题。

库和工具

这算是一个杂项类别，包含了大家提到的提供特别好开发者体验、但也许不完全适合其他分组的工具。

Flutter 是一个从单一代码库构建 iOS 和 Android 原生应用的工具。在某些方面类似 React Native，但似乎效果更好。pytest 是一个 Python 测试运行器，相比标准库的 Unittest，它简化了测试运行，尤其是测试编写。Laravel 和 Laravel Spark 是强大的 PHP 框架，用于开发 Web 应用。Gatsbyjs 把完整的现代前端技术栈打包成一个既有全部威力、学习曲线又更平滑的东西。elm 是一种用于编写可靠 Web 应用的语言，拥有类似 Haskell 的强大类型推断。React Hooks 是处理 React 中状态变化的更简单方式。Sourcegraph 是一个强大的代码搜索工具，能轻松搜索大型代码仓库。OASGraph 是一个将 OpenAPI Specification 转换为 GraphQL API 的工具，降低了启动 GraphQL API 的门槛。

没有被提到的事情

鉴于无处不在的炒作，我觉得简单提一下没人提到的几件事也挺有意思：

区块链整体，或者特别是 Ethereum，作为伟大开发者体验的例子。根据不同用例，要么是钱包依然难以安全使用，要么是交易成本仍然高得离谱或波动剧烈。综合来看，区块链的开发者体验似乎依然不足。聊天机器人也没有被提及，尽管它曾经备受期待。我认为这很大程度上是因为我 Twitter 上认识的人主要关注美国和欧洲，而聊天机器人在其他市场似乎得到了大量使用。React 被提到的次数没有我预期中多，尽管 React Hooks 被提到了。也许 React 现在已经太过 commonplace，以至于人们甚至不会想到去提它，就像没人提到 Python、Ruby 或 Node.js 一样。

总的来说，这是一种非常有趣的消磨时间的方式！今天之前我对其中很多工具都不熟悉，这是一次很好的调研，帮助我刷新了对开发者工具以及伟大开发者体验未来方向的思考。

非常期待听到大家最近遇到过的其他令人印象深刻、鼓舞人心的开发者体验建议！
