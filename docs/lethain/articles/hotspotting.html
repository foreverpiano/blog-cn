热点优化开发者生产力

2020-03-17 · 阅读原文

去年年底，我和 Keith Adams 一起喝咖啡，最终我们聊了很多关于 迁移：解决技术债务唯一可扩展的办法。 的话题，焦点是如何让 收回不合理的软件。讨论延伸到了多个方向，包括稍稍聊到 构建演进式架构笔记。其中 Keith 提到的一个想法让我特别印象深刻：大部分修改都集中在少数几个相同的文件里，而这些文件正是投入质量改进时最具性价比的地方。

我记得 Keith 把这个想法归功于 Adam Tornhill 的《Software Design X-Rays》，书中 Adam 将其称为 hotspotting（热点分析）。他的建议是，处理代码质量问题应该像解决性能优化问题一样：衡量真正重要的事情，并优先在那些区域进行修改。这种聚焦于文件的方式特别出色，因为它涵盖了几类对开发生产力影响巨大、却很容易被忽略的变更——尤其是当你完全依赖 以编程方式重构 Ruby 代码 时：配置修改和测试。

这个看似显而易见的想法，实际上与我过去学到的关于大规模软件变更的经验存在一定冲突。我学到的是：旨在降低复杂度的努力，在进行过程中往往会先增加复杂度。更糟糕的是，如果在完成前被迫中止且没有彻底回滚，这些努力会永久性地增加系统的复杂度。

这就引出了核心问题：我们什么时候应该针对热点进行优化，什么时候又应该追求彻底完成？

你应该优先处理热点的情况包括：

  1. 你能衡量的是影响而非进度。例如：last byte 时间
  2. 对用户有直接、可衡量的影响。例如：错误率、转化率
  3. 不存在明确的终点，或者终点在两年及以后。例如：“代码库中零 bug”

你应该聚焦于完成的情况包括：

  1. 工作完成后能带来台阶式的开销或成本下降，通常是通过彻底废弃现有方案实现。例如：废弃一个昂贵或缓慢的数据管道
  2. 多种并存的方案会大大增加团队心智模型的复杂度。例如：在代码库中同时存在三种具有不同失败语义的 HTTP 客户端库
  3. 由临时项目组而非长期负责人负责。例如：组建一个“特战队”来迁移脱离某种失败的数据存储方案

不过，对我而言最大的收获是：与其让某一种策略占据主导，不如在面对每个项目时，同时考虑这两种选项，并做出有意识的选择。
