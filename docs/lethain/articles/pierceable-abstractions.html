提供可穿透的抽象层

2017-05-07 · 阅读原文

开放失败与分层策略 是一种基础设施设计原则，它强调构建灵活的系统，并通过一个解耦的策略执行层来约束使用。例如，构建一个基于 Dockerfile 的部署系统，它可以接受任意 Dockerfile，然后再增加一个验证步骤，只允许使用特定的一组基础镜像。

当把这种方法应用到一系列解决方案中时，它会变得更加强大，因为它允许你在某个特定平台上降低灵活性，同时又能保留用户的灵活性。

想象你正在领导一个“编排”团队，负责帮助公司工程师部署和运行他们的软件。你最初提供的服务可能是给团队分配服务器或虚拟机。这种方案效果很好，而且极具灵活性。

随着你所支持的公司不断发展，一些用户会开始询问你是否能减轻他们管理单个服务器的负担（特别是那些运行无状态应用的用户）。如果你关心用户——当然你会的——那么最终你会抽出时间，推出一个服务编排框架，比如 Kubernetes 或 Aurora，从而将用户从单个服务器故障中抽象出来。

再往后，你可能会遇到有人“只想运行一个函数”（好吧，，真正为自己提出这个需求的反而不多），甚至不在乎服务抽象所提供的瞬态状态和依赖管理，于是你又推出了 Lambda 平台（指 AWS Lambda 或 Google Cloud Functions 意义上的平台）。无服务器架构：守门机制与利润空间

这种分层效应让平台构建者能够打造带有明确意见的基础设施，同时赋予用户自主权，让他们在承担更多意外复杂性与获得项目所需控制度之间做出权衡。如果你需要持久化的本地磁盘存储，那就直接穿透到虚拟机层；但如果你能直接使用无状态服务，就可以避免大量意外复杂性。

这其实是一种相当显而易见的方法，看看各大云提供商就知道了。但我认为我们在内部构建系统时常常忘记这一点，结果打造出过于固执己见的解决方案，这些方案要么无法满足足够多的用户需求，要么堆积了太多功能而变得难以维护，最终老化得很快。能够良好老化对高质量基础设施至关重要，因为每一个老化不良的系统都会削弱我们面向未来投入的能力。

有些情况下确实难以构建出良好的基础设施，但只要有机会，就应该构建可以相互组合成完整解决方案的层，而不是试图让任何一个层去满足所有人的所有需求。

以下是一些可以应用这种方法的更多例子：

存储。你可能希望提供一个最终一致性的键值存储，支持多区域主动-主动复制，然后再提供另一个强一致性但复制程度或可用性较低的方案。

负载均衡。90% 的应用使用非常朴素的轮询负载均衡就足够了，而剩下 10% 中的 90% 可以使用最小连接数路由就够了，但还是有少数应用需要更定制化的方案（例如基于某个 key 做哈希以提升数据局部性等）。通过将控制面和数据面解耦，你可以让绝大多数应用直接使用负载均衡器，而让那些边缘情况直接与控制面通信，自己实现路由逻辑。
