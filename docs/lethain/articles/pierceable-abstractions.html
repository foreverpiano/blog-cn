提供可穿透的抽象层。

2017-05-07 · 阅读原文

开放失败与分层策略 是一种基础设施设计原则，它强调构建灵活的系统，并通过一个独立的策略执行层来约束使用。例如，构建一个基于 Dockerfile 的部署系统，它可以接受任意 Dockerfile，然后再增加一个验证步骤，只允许使用特定的基础镜像。

当把这种方法应用到一系列解决方案中时，它会变得更加强大，因为它允许你在特定平台上降低灵活性，同时保持用户的灵活性。

想象一下，你正在领导一个“编排”团队，负责帮助公司工程师部署和运行他们的软件。你们最初提供的服务可能是为团队授予服务器或虚拟机的访问权限。这种方式效果很好，而且极其灵活。

随着所支持的公司不断发展，一些用户会开始询问是否能减轻他们管理单个服务器的负担（特别是那些运行无状态应用程序的用户）。如果你热爱你的用户——当然你会的——那么最终你会抽出时间推出一个服务编排框架，比如 Kubernetes 或 Aurora，从而让用户不必再关心单个服务器的故障。

再往后，你可能会遇到有人“只想运行一个函数”（好吧，，我很少遇到自己提出这个需求的人），他们甚至不关心服务抽象层提供的瞬态状态和依赖管理，于是你又推出了 Lambda 平台（指 AWS Lambda 或 Google Cloud Functions 意义上的平台）。无服务器架构：把关机制与利润空间

这种分层效应让平台构建者能够打造带有鲜明意见的基础设施，同时赋予用户做出权衡的能力——是在项目中承担更多意外复杂性，还是获得他们想要的控制程度。如果你需要持久化的本地磁盘存储，那就直接穿透到 VM 层吧；但如果你能直接使用无状态服务，就能避免大量的意外复杂性。

这其实是一种相当显而易见的方法，看看各大云提供商就知道了。但我认为我们在内部构建系统时常常忘记这一点，结果造出了过于固执己见的解决方案，它们随着时间推移表现不佳（要么是没有满足足够多的用户需求，要么是功能堆积过多导致难以维护）。能够良好地老化对高质量基础设施至关重要，因为每一个老化不良的系统都会削弱我们向未来投入的能力。

有些情况下确实难以构建良好的基础设施，但当你有机会时，应该构建能够相互组合成完整解决方案的层，而不是试图让任何一个层为所有人解决所有问题。

以下是一些可以应用这种方法的例子：

存储。你可能希望提供一个最终一致性的键值存储，支持跨多个区域的主动-主动复制，然后再提供另一个强一致性但复制范围或可用性较低的方案。

负载均衡。90% 的应用可以使用非常简单的轮询负载均衡，剩下 10% 中的 90% 可以使用基于 least-conn 的路由，但少数应用需要更定制化的方案（例如基于某个 key 做哈希以提升数据局部性等）。通过将控制平面和数据平面解耦，你可以让绝大多数应用直接使用负载均衡器，同时允许那些边缘场景直接与控制平面通信并自行实现路由逻辑。
