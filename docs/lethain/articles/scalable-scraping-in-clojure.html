用 Clojure 实现可扩展的网页抓取

2009-11-24 · 阅读原文

Craigslist 是一个很棒的网站。它太棒了，以至于我听说有些人会花大量时间盯着它那源源不断的帖子。

想到这一点，我突然意识到，写一个脚本监控帖子流并将相关帖子保存到磁盘，或许是一个很好的项目，可以用来练习用 Clojure 进行并发抓取和并发处理。

前置条件

在开始之前，你需要

安装 Clojure（本教程基于 1.0 版本编写），安装 clojure-contrib（使用与 1.0 版本兼容的版本）。

如果你已经安装好了这些，那我们就可以开始了。如果你还没有安装好，那这篇教程会一直在这里等你忙完那些事情。

系统架构

从 Craigslist 抓取内容、解析内容，然后将其中一部分写入磁盘，有很多种实现方式。在这些方式中，有些简单而直接。而这个方案并不属于那一类。

相反，本教程旨在开发一种可扩展且易于扩展的方法，重点放在并发处理上。

系统被分为两个子组件：内容抓取和内容处理。两者通过一个共享队列进行通信（抓取组件将数据放入队列，处理组件从队列中读取数据）。首先，我们来看看内容抓取部分。

内容抓取的目标是将 Craigslist 的分类列表转换为一个装满每个帖子元数据的队列。

抓取流程为

拉取一个或多个 Craigslist 分类的最近帖子，提取每个帖子的 URL，将这些 URL 提交给一个工作者 agent 池，让工作者 agent 去抓取 URL 并将抓取到的数据放入 post-queue。

接下来是系统的内容处理部分。

内容处理的目标是

从 post-queue 中取出帖子，使用用户定义的过滤器（过滤器是一组必须出现的关键词）将它们归类到不同的桶中（一个帖子可能同时属于多个桶），然后将每个桶中的帖子写入单独的文件。

随着程序运行，这些过滤器对应的文件会不断增长，里面装满了满足各个主题要求的帖子。你再也不需要痴迷地刷新 Craigslist 了。

取而代之，你可以痴迷地刷新一系列文本文件。进步难道不伟大吗？

发现新帖子

当我们开始组装脚本的各个组件时，首先要编写代码来获取 Craigslist 某个分类中的最近帖子。

要实现这一点，我们首先需要能够获取列表页面的 HTML。duck-streams 对 HTTP 协议很了解，这使得获取网页变得极其简单：

lists:foreach(fun(Pid) ->
        Pid ! {self(), update, Key, Value}
    end, pg2:get_members(kvs)),
Sender ! {self(), received, {set, Key, Value}},

获取原始 HTML 之后，我们需要提取所有职位帖子的 URL。每个帖子的样子大致如下：

-define(KVS_WRITES, 3).
-define(KVS_READS, 3).
-define(TIMEOUT, 500).

因此我们可以使用 re-find 和正则表达式来提取 URL，如下所示：

-record(kvs_store, {data, pending_reads, pending_writes}).

然而，我们真正想要的是从文本中提取所有匹配项，而不仅仅是第一个。为此我们可以使用 re-seq：

% a brief interlude for record syntax
Store = #kvs_store{data=[], pending_reads=[], pending_writes=[]},
#kvs_store{data=D, pending_reads=R, pending_writes=W} = Store,
Writes = Store#kvsstore.pending_writes,
get_value(Key, S=#kvs_store{data=Data}) ->
proplists:get_value(Key, Data).
set_value(Key, Value, S=#kvs_store{data=Data}) ->
S#{data=[{Key, Value} | proplists:delete(Key, Data)]}.

在此基础上，我们可以将其包装成一个函数，以便支持任意的帖子分类：

-include("kvs.hrl").

实际上，我们只想要每个匹配的第二部分（即 URL，而不是整个匹配），这可以通过对结果使用 map 来实现：

%% @doc create N nodes in distributed key-value store
%% @spec start(integer()) -> started
start(N) ->
    pg2:create(kvs),
    lists:foreach(fun(_) ->
			  Store = #kvs_store{data=[],
					     pending_reads=[],
					     pending_writes=[]},
			  pg2:join(kvs, spawn(kvs, store, [Store]))
		  end, lists:seq(0, N)),
    started.

最后，我们想要完整的 URL，而不仅仅是相对 URL，可以通过在相对 URL 前面加上 http://craigslist 来生成。

% old definition
store(Data) -> term().
% new definition
store(Store = #kvs_store{data=Data, 
                         pending_reads=Reads,
                         pending_writes=Writes}) -> term().

至此，项目的第一部分就完成了。

从帖子中提取数据

下一步是编写一个函数，它接收帖子的 URL，获取该帖子的原始 HTML，然后提取帖子的元数据（在这里指标题和正文）。

从 HTML 中，我们要找的是下面这两段内容：

store(Data, Reads, Writes) -> term().

如果我们能把它们提取出来，就大功告成了。一个可行的尝试如下：

{Sender, set, Key, Value} ->
    % client interface for updating values
    lists:foreach(fun(Pid) ->
		  Pid ! {self(), update, Sender, Key, Value}
	  end, pg2:get_members(kvs)),
    Writes2 = [{ {Sender, Key}, ?KVS_WRITES} | Writes],
    store(Store#kvs_store{pending_writes=Writes2});

一个问题是提取出来的正文里还混杂着 HTML 标签，不过我们可以相当容易地解决这个问题（在此表示歉意，这确实比引入外部依赖要简短得多，而且如果效果还不错的话……可惜它并不完美）：

{Sender, update, Client, Key, Value} ->
    % sent to all nodes by first receiving node
    Sender ! {self(), updated, Client, Key, Value},
    store(Store#kvs_store{data=[{Key, Value} | 
		proplists:delete(Key, Data)]});

至此，我们已经组装好了项目的两个部分。继续前进。

过滤帖子

下一步是接收帖子数据的列表，然后找出我们感兴趣的那些帖子。最终目标是支持任意数量的过滤器，每个过滤器对应一个单独的文件，每个过滤器包含一组代表性关键词。（每个过滤器都会在每篇帖子上运行，这意味着一篇帖子可能被多个过滤器同时接受。）

作为开始，我们可以创建下面这两个过滤器：

{_Sender, updated, Client, Key, Value} ->
    Count = proplists:get_value({Client, Key}, Writes),
    case Count of
	undefined ->
	    store(Store);
	0 ->
	    Client ! {self(), received, {set, Key, Value}},
	    store(Store#kvs_store{
		    pending_writes=proplists:delete({Key, Value}, Writes)});
	_ ->
	    store(Store#kvs_store{
		    pending_writes=[{ {Client, Key}, Count-1} |
				    proplists:delete({Client, Key}, Writes)]})
    end;

过滤帖子的第一个简单尝试是只接受包含所有指定单词的帖子。实现单词检测的方式有很多，但最简单的方法之一是对字符串进行分词：

{Sender, get, Key} ->
    % client interface for retrieving values
    lists:foreach(fun(Pid) ->
	  Pid ! {self(), retrieve, Sender, Key}
    end, pg2:get_members(kvs)),
    % ?KVS_READS is required # of nodes to read from
    % [] is used to collect read values
    Reads2 = [{ {Sender, Key}, {?KVS_READS, []}} | Reads],
	    store(Store#kvs_store{pending_reads=Reads2});

然后，我们可以检查这个哈希表是否包含所有期望的单词。

{Sender, retrieve, Client, Key} ->
    Sender ! {self(), retrieved, Client, Key, proplists:get_value(Key, Data)},
    store(Store);

在这些组件的基础上，我们需要将 tokenize 和 has-keys? 组合成一个函数，用来判断一篇帖子是否匹配某个过滤器。

{_Sender, retrieved, Client, Key, Value} ->
    case proplists:get_value({Client, Key}, Reads) of
	{0, Values} ->
	    Freq = lists:foldr(fun(X, Acc) ->
		case proplists:get_value(X, Acc) of
		    undefined -> [{X, 1} | Acc];
		        N -> [{X, N+1} | proplists:delete(X, Acc)]
		     end
	        end, [], Values),
	    [{Popular, _} | _ ] = lists:reverse(lists:keysort(2, Freq)),
            Client ! {self(), got, Popular},
	    store(Store#kvs_store{
		pending_reads=proplists:delete({Key, Value}, Reads)});
	{Count, Values} ->
	    store(Store#kvs_store{
		pending_reads=[{ {Client, Key}, {Count-1, [Value | Values]}} | 
		    proplists:delete({Client, Key}, Reads)]})
    end;

好了，我们已经非常接近了，只剩最后一个部分要写，然后就可以开始把各个部分整合起来了。

将匹配的帖子写入文件

某个过滤器下的所有帖子都应该写入同一个文件，而且由于可能有多个工作者同时处理帖子，我们需要一种方式来对共享文件的写入操作进行排序。

最简单的方法是使用 agent 来保护这些文件。目前我们将过滤器定义为关键词列表，但让我们把它扩展为一个哈希映射，其中 :tags 键包含关键词列表，:file 键包含一个 agent，其值是一个文件名。

ts() ->
    {Mega, Sec, _} = erlang:now(),
    (Mega * 1000000) + Sec.

然后我们可以编写一个函数，接收一个过滤器和一篇帖子，并将其写入文件。

{Sender, set, Key, Value} ->
            lists:foreach(fun(Pid) ->
                             Pid ! {self(), update, Sender, Key, Value}
                          end, pg2:get_members(kvs)),
            Writes2 = [{ {Sender, Key}, {?KVS_WRITES, ts()}} | Writes],
            store(Store#kvs_store{pending_writes=Writes2});

（请注意，当我通过脚本运行器执行代码时，曾经遇到 append-spit 不是公开可用的错误，但使用 (load-file "cl.clj") 时则工作正常。为了控制复杂度，我决定不在本教程中重写一个 append-spit 的替代版本，但你可能需要这么做——或者对建议用于 Clojure 1.0 的 duck-streams 代码做一点小修改。）

使用 save-post 函数看起来像这样：

    case Count of

          pending_writes=[{ {Client, Key}, {Count-1, Timestamp}} |
            proplists:delete({Client, Key}, Writes)]})

现在我们已经把所有组件都准备好了，可以开始把它们组合成一个可运行的系统。

组装系统

我们正在构建的系统可以看作有两个独立子组件：填充帖子队列和清空帖子队列。

我们将利用这种解耦，将两部分独立实现。在一个原本可能只需五十行脚本就能完成的任务中使用这种程度的解耦肯定是杀鸡用牛刀，但通过与共享数据结构交互来解耦代码，正是团队软件开发中最困难任务的一个特例：定义接口。

看起来所有接口要么只是对某个数据结构的操作（像 Dynamo 这样的键值存储本质上就是哈希表），要么可以被视为简单算法上的简单算法（大多数 Twitter API 可以建模为对数组的过滤，尽管实际实现可能有所不同）。因此，宽容的读者可能会认为这种解耦设计是一个练习这项重要技能的机会。

我猜不太宽容的读者早就已经不读了。

将帖子放入 Post Queue

这里需要组合起来的组件包括：

将分类分散到一组 agent 上，将每个分类中的帖子再分散到另一组 agent 上，将抓取到的每个帖子存入 post-queue，接一个定时器定期触发分类抓取。

这听起来相当复杂，但得益于我们前面编写的所有函数，实现起来其实相当简洁。首先我们需要编写几个用于创建和使用 agent 池的函数。

    after
