向访问器和修改器致敬

2008-03-12 · 阅读原文

我还记得本科刚开始学习编程时，老师们反复强调，在面向对象代码中，始终应该使用 mutator 和 accessor 来获取和修改数据。当然，那时候我们管它们叫 setter 和 getter 方法，大多数学生都很讨厌它们。我特别记得有个学生坚决拒绝使用它们，理由是“太蠢了”。故事的结局是，他现在当然成了一名职业程序员。

我认为很多新手程序员对访问器和修改器存在误解，这可能是因为很少有清晰的解释说明为什么应该重视它们。教授们可能会告诉学生要始终使用 setter/getter 对来处理数据交互，但我从未听到过它们为什么重要的解释。当你刚开始学习编程时，脑海里会被各种新信息塞满，大脑会自动丢弃那些它不理解或认为无关紧要的东西。那个觉得它们很蠢的学生认为，这些只是传统遗留下来的冗余代码，不值得占用那些代码行。

然而，我编程的时间越长，就越能体会到 mutator 和 accessor 方法的微妙价值。

惰性初始化

我第一次发现 accessor 方法的价值，是在学习如何使用 Java 的 Swing 图形包时。当时我们使用 Visual Eclipse，它会为你生成大量代码，我注意到程序启动时很少有变量被初始化，大部分东西都是在它们的 accessor 中进行初始化的。

不再是过去那种毫无意义的访问器：

public JList getPersonList() {
    return personList;
}

我开始看到真正能做事的访问器：

public JList getPersonList() {
    if (personList == null) {
        personList = new JList(getPersons());
        personList.setCellRenderer(getMyCustomRenderer());
        personList.setPrototypeCellValue("Initial");
        personList.setPreferredSize(new java.awt.Dimension(100,200));
    }
    return personList;
}

突然间，accessor 的价值变得清晰多了。你可以用它来初始化对象中的变量，但只在真正需要它们的时候才初始化。如果你只在极少数情况下使用某个变量，那也没关系，除非真的进入那种罕见场景，否则它就不会被初始化。或者你有一大堆计算量很大的运算，但每次只需要其中一部分结果，这也没问题，因为惰性初始化——访问器的第一个福音——会帮你摊薄这些成本。

在更复杂的问题中，你可以实现动态规划算法，只生成并缓存你真正关心的那些值，然后把这一切都隐藏在访问器背后：

- (id) valueAtX: (int)x andY: (int)y {
    id val = [self cachedValueForX:x andY:y];
    if (val == nil) {
        // use dynamic programming to generate the value
    }
    return val;
}

这是一种在不增加类的公共 API 复杂性的前提下，大幅提升性能的绝佳方式。

访问控制

访问器的另一个用途是验证调用对象是否有权使用某个访问器。也许你只希望关联的主对象才能使用你的访问器方法：

-(NSNumber *)ssn: (NSObject *)sender {
    if (sender != [self masterObject]) return nil;
    return ssn;
}

这是一个很简单的例子，但你可以将其推演到更有用的场景。例如在多个程序之间共享的分布式对象，其中某些数据需要受到保护，不能被过于随意地访问。

修改器

好了，我们已经看了几个访问器为什么重要，现在来谈谈修改器。修改器的理由相对更直观一些，但仍然值得仔细分析。

数据验证

你通常希望在更新数据前验证更新是否有效，而修改器正是做这件事的完美场所。

def setName(self, newName):
    if len(newName) < 3:
        raise TooShortNameException, u"You name is too short!"
    elif newName in ["Bob", "Jim", "Joe"]:
        raise AwfulNameException, u"The quality of your name is substandard."
    elif newName.contains("teh"):
        raise IHateInternetSpellingException, u"Just go home."
    self.name = newName

清理和初始化工作

此外，当你使用修改器时，可以在更新为新值之前对旧值进行清理工作。比如你可能有一个频繁写入的文件流，需要先把它关闭，同时打开一个指向新文件的新流。

def setFile(self, newFile):
    if newFile != self.file:
        self.file.close()
        self.file = newFile
        self.file.open()

这在没有自动垃圾回收的语言中尤其重要，但即使是带垃圾回收的语言，有时也需要一些显式的清理操作（例如打破引用循环）。

继承

当你开始对对象进行子类化时，mutator 和 setter 的真正潜力才最明显显现出来——你可以复用已有的验证或初始化代码，只需添加少量额外逻辑即可。

例如，你可能希望子类返回与超类相同的结果，但要变成大写而不是小写：

def getName(self):
    return super.getName().upper()

或者你可能想创建一个会记录自身操作的子类。

-(NSString *)name {
    NSString * tmpName = [super name];
    NSLog(@"%@: Setting name to %@.", self, tmpName);
    return tmpName;
}

又或者，你可能想给修改器增加额外的验证逻辑：

def setName(self, newName):
    if newName.contains(u"McLovin"):
        raise TopicalButPredictableException, "A good try, but..."
    return super.setName(newName)

上述这些用途有的强一些，有的弱一些，但合在一起就形成了强有力的理由，说明为什么应该养成编写访问器和修改器的习惯。这远比最简单的辩护——直接访问对象的成员会将代码绑定到实现细节上，从而打破抽象层——更有说服力。

是我高估了访问器和修改器的价值吗？它们是否只在 Objective C、Java 或 C++ 这些老旧繁琐的语言中才有价值，而在如今充满动态脚本语言的乌托邦里就显得浪费呢？我知道自己以前也曾对它们感到恼火，但随着项目规模和复杂度的增加，我越来越难以忽视它们带来的帮助。
