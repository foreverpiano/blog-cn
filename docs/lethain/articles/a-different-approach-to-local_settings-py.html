local_settings.py 的另一种方法

2008-11-28 · 阅读原文

几周前我在 Django NYC 演讲时，在其中一张幻灯片中介绍了 Django 中使用 local_settings.py 的小技巧，而在下一张幻灯片里，我提到了这个标准技巧的一个轻微变体。我之前曾尝试介绍过这个想法，但它淹没在一篇较长的文章中，没能引起注意。

真正的 local_settings.py

这个技巧的原始版本简单且极其实用。在你的 settings.py 文件底部，添加以下四行代码：

try:
    from local_settings import *
except ImportError:
    pass

然后你就可以创建一个自定义的 local_settings.py 文件，里面存放针对你当前机器的配置覆盖，这样就大功告成了。

当你在创建公开仓库时，要确保不要把自己的 local_settings.py 提交到版本控制中，但你可以创建一个 local_settings.py.template 文件，让其他人通过 cp local_settings.py.template local_settings.py 来复制一份，然后根据自己的需求进行修改。

我所说的变体

我第一次使用这个变体时，正在开发一个需要部署到两个地方的应用：我的 VPS 和个人电脑。我希望能把两套配置都纳入版本控制，同时又不需要在每次更新代码后都进行修改。

我的解决方案是这样的：

try:
    from local_settings import *
except ImportError:
    pass

from devel_settings import *

from vps_settings import *
让 settings.py 文件包含所有共享的配置，并且在文件末尾仍然加上：将开发环境的配置保存在 devel_settings.py 中，将 VPS 的配置保存在 vps_settings.py 中。在每台开发机器上，创建一个 local_settings.py 文件，里面只包含一行代码。在我的开发服务器上，这一行是：而在 VPS 上则是：

这样一来，我就可以轻松修改两套配置，并将它们都纳入版本控制，以便将来想把项目部署到其他机器上时使用。

本质上，这种做法类似于对 settings 文件进行“子类化”，只覆盖需要修改的部分。如果你愿意，可以把这个思路玩得很花哨，做成一个 settings 自助餐，根据需要随意组合不同的配置片段。

举个例子，你可以创建一个名为 site_caching_settings.py 的文件，内容如下：

CACHE_BACKEND = "memcached://127.0.0.1:11211/"
CACHE_MIDDLEWARE_SECONDS = 60 * 30
CACHE_MIDDLEWARE_KEY_PREFIX = "scs"
CACHE_MIDDLEWARE_ANONYMOUS_ONLY = True
MIDDLEWARE_CLASSES = (
    'django.contrib.sessions.middleware.SessionMiddleware',
    'django.contrib.auth.middleware.AuthenticationMiddleware',
    'django.middleware.cache.CacheMiddleware',
) +  MIDDLEWARE_CLASSES

还可以创建一个名为 sqlite_settings.py 的文件：

ROOT_PATH = os.path.dirname(__file__)
DATABASE_ENGINE = 'sqlite3'
DATABASE_NAME = os.path.join(ROOT_PATH, 'db.sqlite')
DATABASE_USER = ''
DATABASE_PASSWORD = ''
DATABASE_HOST = ''
DATABASE_PORT = ''

最后，在你的 local_settings.py 中引入你需要的配置片段（同时覆盖你想修改的部分）：

from site_caching_settings import *
from sqlite_settings import *
CACHE_BACKEND = "localmem:///"

你说得对，它不能无限扩展。

我认为这个方法的明显缺点是它不能很好地扩展，而且它也不是标准 local_settings.py 技巧的替代方案。但对于那些只需要部署在少量环境中的项目，它对我帮助很大。比如工作项目和个人项目，那些不打算做成可复用或可插拔的 app。
