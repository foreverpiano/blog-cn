使用 CouchDB 与 Django 入门

2008-08-18 · 阅读原文

欢迎来到本系列的最后一篇文章。此前我们探讨了 Django 松散耦合哲学的优势。首先，我们用 Jinja2 替换了 Django 的模板系统；接着，用 SQLAlchemy 替代了 Django 的 ORM；在第三部分，也就是本文，我们将使用 CouchDB 来代替传统的对象关系型数据库进行数据存储。

CouchDB 是我在过去一年里接触到的最令人兴奋的项目之一——用它激发过的半靠谱白日梦数量来衡量也不为过。它是关系型数据库的理念对手，不再专注于高度细节化的 schema（什么长整型、长度 25 的 varchar 以及二进制 blob 之类），而是直接处理文档。这些文档可以包含相同的字段，也允许出现不同的字段，这带来了类似于 Google BigTable 的灵活性。除此之外，CouchDB 还带来了一些意想不到的好东西，比如文档版本控制。

在开始之前，你需要先安装 CouchDB，本教程不会详细介绍安装步骤（OS X 安装、Windows 安装、Ubuntu 安装）。

我们的项目

在本教程中，我们将使用 CouchDB 来存储一个简单 Django Web 应用的数据，该应用允许用户在线发布和编辑简单的文本文档。在正式开始前，我们需要做一些准备工作。

首先需要安装 Django。我们将使用 SVN 版本，安装方式如下（注意将 SITE-PACKAGES-DIR 替换为你 Python 的 site-packages 目录）：svn co http://code.djangoproject.com/svn/django/trunk/ django-trunk ln -s `pwd`/django-trunk/django SITE-PACKAGES-DIR/django 接下来，需要安装与 CouchDB 交互的 Python 库 couchdb-python：easy_install couchdb 第三步，创建一个 Django 项目（如果你不想一步步自己操作，可以下载本教程中创建的代码压缩包）。django-admin.py startproject comfy_django_example 如果你系统中没有 django-admin.py 在 PATH 里，可能需要从本地 Django 签出目录中运行。对我来说是这样：~/svn/django-trunk/django/bin/django-admin.py startproject comfy_django_example 现在，我们需要在 comfy_django_example 项目中创建一个 Django 应用。cd comfy_django_example python manage.py startapp couch_docs 准备工作就快完成了，只需再配置几个设置。打开 comfy_django_example 目录下的 settings.py 文件，修改如下：INSTALLED_APPS = ( 'comfy_django_example.couch_docs', ) 我们还要修改 comfy_django_example/urls.py 文件，让它变成这样：urlpatterns = patterns('comfy_django_example', (r'^', include('couch_docs.urls')), )

我们为什么要真的这么做？

这是一个重要的问题。是否真的存在这样的场景：使用 Django + CouchDB 比使用 PostgreSQL 或 MySQL 要合理得多？在我们放弃 Django Admin（以及 session 框架等）的情况下，是否真的获得了有价值的东西？

尽管存在一些不便，但 CouchDB 确实有不少值得考虑的理由。设想一个允许用户下载其内容副本并进行修改的 Wiki。如果使用 CouchDB 实现，用户就可以上传他们的内容并将其合并到数据库中。开发者不需要为此编写自定义代码，因为这本身就是 CouchDB 的功能之一。如果新数据中有错误，你还可以利用版本控制系统回滚到之前的版本（除非它已经被数据库压缩操作删除了……咳咳）。

再考虑一下类似 FreeBase 的系统，它可以根据不同类型的数据动态创建 schema。在关系型数据库中这样做会非常痛苦，因为你需要不断创建和修改表结构。但在 CouchDB 中，如果你想为某条数据增加一个字段，只需直接添加数据即可，它自然就能工作。拥有灵活的（或者说实际上不存在的）schema，能让某些类型的应用实现起来变得容易，而这些应用如果使用严格定义的 schema，可能需要天才般的灵感才能解决。

最后，还有 Damien Katz 反复提到的观点——一旦开始优化，CouchDB 可能会变得非常快。

我们能鱼与熊掌兼得吗？

可以，当然可以。你可以使用 SQLite 或 PostgreSQL 数据库来管理 session 和用户，只用 CouchDB 来存储文档数据。这样，你就能在大部分数据上继续使用 Django Admin，同时还能在应用中适合的部分利用 CouchDB 基于文档的存储特性。

这样做的额外复杂度对于最初的开发者来说不会太高。然而，扩展这样一个应用会比只使用关系型数据库或只使用 CouchDB 的应用需要更多的思考和努力。在资源有限的情况下（比如小型 VPS）高效部署这样的服务也会更困难。这些技术障碍并非不可逾越，但处理起来可能也不会特别愉快。

等等，这不是我想要的“鱼与熊掌”

哦，原来你是想在 CouchDB 之上实现 session 框架？你当然可以基于 CouchDB 自定义一套认证框架，而且理论上也可以（虽然可能需要超人般的努力，比如把 SQL 语句翻译成 CouchDB 的命令）创建一个 Django 后端，让它无缝地使用 CouchDB 而不是传统的关系型数据库。

如果有人真的想承担这个项目，可能应该等到 CouchDB 达到 1.0 版本并且 API 稳定下来之后再说。不过……即便如此，我还是觉得这个项目会像一个地狱般的泥潭，能把成年人变成小孩，让人的意志比被要求用下推自动机实现 Perl 正则表达式崩溃得还要快。

随着本文接近尾声，这个系列也随之结束。我们先后探讨了 Jinja2、SQLAlchemy，现在是 CouchDB，以及 Django 松散耦合的哲学如何让这些技术能够轻松地与 Django 集成。对我来说，写完这些文章后最持久的想法是：松散耦合当然不是完美的，但只要你愿意付出时间上的代价，它就能让你做任何你想做的事情。
