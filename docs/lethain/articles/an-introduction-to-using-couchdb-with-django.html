CouchDB 与 Django 结合使用入门

2008-08-18 · 阅读原文

欢迎来到本系列的最后一篇。在此系列中，我们探讨了 Django 松散耦合哲学的优势。首先，我们用 Jinja2 替换了 Django 的模板系统；接着，用 SQLAlchemy 替代了 Django 的 ORM；而在这第三部分，我们将了解如何使用 CouchDB 来代替传统的对象关系型数据库进行数据存储。

CouchDB 是我在过去一年里接触到的最令人兴奋的项目之一——以它激发出的半合理白日梦数量来衡量。它是关系型数据库的理念对手，不再专注于高度详细的模式（长整型、长度为 25 的 varchar，以及二进制 blob 数据等等），而是专注于文档。这些文档可以包含相同的字段，也允许包含不同的字段，从而提供了与 Google BigTable 相似的灵活性。除此之外，CouchDB 还带来了其他意想不到的特性，例如文档版本控制。

在开始之前，你需要先安装 CouchDB，本教程不会详细介绍安装步骤（OS X 安装、Windows 安装、Ubuntu 安装）。

如果我们想运行特定查询，需要编写一个 JavaScript 函数。例如，假设我们想要获取所有标题长度大于 4 的文档，可以这样写 JavaScript：

function(d) {
    if (d.title.length > 4) emit(d.name, null);
}

现在，要在 Python 中运行这个查询，需要这样做：

>>> func_str = "function(d) { if (d.title.length>4) emit(d.title,null); }" 
>>> for row in db.query(func_str):
...     print row.key

有了命令行实验的经验，我们很容易想象如何用 CouchDB 满足大多数数据存储、检索和操作需求。现在进入我们的压轴戏：将 CouchDB 与 Django 集成。

将 CouchDB 与 Django 集成

我们将构建一个非常简单的应用。它包含两个视图：index 视图将显示所有可用文档的列表，并允许创建新文档；detail 视图则允许编辑现有文档。

首先，创建 couch_docs/urls.py 文件。

from django.conf.urls.defaults import *
urlpatterns = patterns('comfy_django_example.couch_docs.views',
    (r'^doc/(?P<id>\w+)/','detail'),
    (r'^$','index'), 
)

接下来，我们需要编辑 couch_docs/views.py 文件。首先是导入语句，以及一些代码用于在不存在时创建一个名为 docs 的 CouchDB 数据库。

from django.http import Http404,HttpResponseRedirect
from django.shortcuts import render_to_response
from couchdb import Server
from couchdb.client import ResourceNotFound
SERVER = Server('http://127.0.0.1:5984')
if (len(SERVER) == 0):
SERVER.create('docs')

如果遵循最佳实践，你可能会希望在 settings.py 中添加一个 COUCHDB_SERVER 配置，然后这样写：

from django.conf import settings
SERVER = Server(getattr(settings,'COUCHDB_SERVER','http://127.0.0.1:5984'))

但目前我们先使用简单（虽然灵活性较差）的方式，直接在 views.py 中指定服务器。现在，来编写视图函数。

index 视图完成两件事。收到 GET 请求时，它会显示数据库中所有现有文档；收到 POST 请求时，它会创建一个新文档并重定向到该文档的详情视图。

def index(request):
    docs = SERVER['docs']
    if request.method == "POST":
        title = request.POST['title'].replace(' ','')
        docs[title] = {'title':title,'text':""}
        return HttpResponseRedirect(u"/doc/%s/" % title)
    return render_to_response('couch_docs/index.html',{'rows':docs})

注意，我们以完全相同的方式将 rows 作为额外上下文传递给 index.html 模板，就像使用 Django ORM 查询数据时一样。

detail 视图也有两个功能。如果收到 GET 请求，它会显示文档（同时提供编辑表单）；收到 POST 请求时，它会更新文档。如果有人请求一个不存在的文档，我们还会抛出 404 错误码。

def detail(request,id):
    docs = SERVER['docs']
    try:
        doc = docs[id]
    except ResourceNotFound:
        raise Http404        
    if request.method =="POST":
        doc['title'] = request.POST['title'].replace(' ','')
        doc['text'] = request.POST['text']
        docs[id] = doc
    return render_to_response('couch_docs/detail.html',{'row':doc})

请注意，docs[id] = doc 这行代码不是可选的。如果没有这一行，即使更新了文档的键，数据库中的条目也不会被更新。我不确定这是库的疏忽，还是有意减少 HTTP 请求的决定，但它确实是个容易让人困惑的陷阱。

我们为什么要这么做？

这是一个重要的问题。是否存在这样的场景，让使用 Django + CouchDB 比使用 PostgreSQL 或 MySQL 更有意义？在我们放弃 Django Admin（以及会话框架等）的同时，是否真正获得了有价值的东西？

尽管存在一些不便，但 CouchDB 确实有许多值得考虑的理由。设想一个允许用户下载内容副本并修改的 Wiki。如果使用 CouchDB 实现，用户就可以上传他们的内容并将其合并到数据库中。实现者无需编写自定义代码，因为这是 CouchDB 内置的功能。如果某些新数据有问题，你还可以利用版本控制系统回滚到之前的修订版本（除非它已经在压缩数据库时被删除了……咳咳）。

另外，考虑一下像 FreeBase 这样的系统，它可以根据不同类型的数据动态创建模式。在关系型数据库中这样做会非常痛苦，因为你需要不断地创建和修改表结构。但在 CouchDB 中，如果你想为某条数据添加一个新字段，只需直接添加数据，它就能正常工作。拥有灵活的（或者说根本不存在的）模式，使得实现某些类型的应用变得容易，而这些应用在严格定义的模式下可能需要几滴天才灵药才能解决。

最后，还有 Damien Katz 反复提到的观点——一旦开始优化，CouchDB 可能会变得惊人地快。

我们能鱼与熊掌兼得吗？

可以。当然可以。你可以用 SQLite 或 PostgreSQL 数据库来管理会话和用户，只用 CouchDB 来存储文档数据。这样，你就可以在大部分数据上使用 Django Admin，同时还能针对应用中适合的部分利用 CouchDB 基于文档的存储特性。

这样做的额外复杂性对于最初的开发者来说不会太高。然而，扩展这样一个应用将比只使用关系型数据库或只使用 CouchDB 的应用需要更多的思考和精力。在资源有限的情况下（例如小型 VPS），高效部署这样的服务也会更加困难。这些技术障碍并非不可逾越，但处理起来可能也不会特别愉快。

等等，这不是我想要的“鱼与熊掌”

哦。所以你想在 CouchDB 之上实现会话框架？你当然可以基于 CouchDB 自定义开发一个认证框架，而且很可能可以——虽然可能需要超人般的努力，比如把 SQL 语句翻译成 CouchDB 命令——创建一个 Django 后端，让它无缝地使用 CouchDB 而不是传统的关系型数据库。

如果有人想承担这个项目，他们最好等到 CouchDB 达到 1.0 版本且 API 稳定之后再动手。但是……即便如此，我还是觉得这个项目会是一个地狱般的泥潭，它会让男人变成孩子，并以比要求用下推自动机实现 Perl 正则表达式更快的速度摧毁人的精神。
