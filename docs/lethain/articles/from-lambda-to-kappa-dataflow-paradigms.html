从 Lambda 到 Kappa 以及数据流范式

2017-11-22 · 阅读原文

最近我花了不少时间了解现代数据基础设施的现状，并尝试将一路上记录的笔记梳理成一个连贯的故事。我很确定其中存在不少错误和遗漏，非常欢迎大家提出哪些部分可以进一步展开或修正！

Lambda 架构在 2013 年开始受到广泛关注，这得益于 Nathan Marz 的工作，随后迅速成为一种流行的架构方案。其核心优势在于：使用实时流处理来计算最近时间窗口的结果，同时依靠批处理来计算那些已过期窗口的最终准确值。批处理还用于回填新增或修改后的计算逻辑。

这一波浪潮中的核心技术之一是 Storm，它于 2011 年首次发布，作为 Lambda 架构的实时处理组件被广泛采用，通常与 Kafka 配合存储日志，并使用 Hadoop 生态系统负责批处理。

随着越来越多公司采用这些模式，三个主要问题逐渐浮现：

双重实现：流处理和批处理组件往往差异很大，导致同一逻辑需要在两种不同的编程范式中重复实现。实时正确性保证较弱：批处理计算不仅用于处理回填，还必须用来达到较高的数据正确性，因为实时组件当时仅支持 at-most-once 和 at-least-once 保证。运维负担：虽然 Hadoop 生态系统经过多年发展已趋向易于维护，但这些实时组件还不够成熟，往往带来显著的运维负担，尤其是 Storm 对 Mesos 和 ZooKeeper 的依赖让不少采用者感到头疼。

当 Lambda 架构在行业公开场合大行其道时，创新却在幕后悄然萌芽。两年后的 2015 年，至少有三条有趣的技术路线结出了果实：

Google 发表了 The Dataflow Model，提出了一种统一处理流处理、微批处理和批处理的方法，尤其提供了 exactly-once 处理的保证。Twitter 将 Lambda 模型投入实际生产，他们走了两条路线：一是开发 Heron——一个运维体验更好但正确性限制与 Storm 类似的版本；二是投资开发 Summingbird，它允许同一份代码既能在 Storm（或 Heron）上运行，也能在 Cascading（特别是 Scalding）这一基于 Hadoop 的批处理库上运行。大约同一时期，Jay Kreps 对日志的倡导逐渐成熟为 Kafka 的实现，最终提供 exactly-once 保证；同时还有流处理框架 Samza 提供了 exactly-once 的流计算能力，以及更具普适性的 Kappa 架构（所有流量都通过一个中心化的事件总线，而不是要求发布者了解下游消费者的行为和需求）。

在随后的两年里，数据基础设施领域迎来某种意义上的复兴，发展成一个充满活力的生态系统。新一代工具倾向于通过微批处理（例如 Spark Streaming）和原生流处理（例如 Flink Streaming）来构建低延迟的数据管道，并采用新的策略来强制实现 exactly-once 事件处理。这使得流处理能够达到之前只有批处理才能保证的正确性水平。

虽然大多数 Lambda 架构技术正在被逐渐减少采用（例如 Storm），但仍有部分成功跨越世代，成为标准构建模块。其中特别值得一提的是 Kafka、Hadoop YARN 和 HDFS 依然根深蒂固。YARN 和 HDFS 尤其有趣，因为它们最早是在更早的 MapReduce 浪潮中进入生态系统的，如今已历经两次世代更迭仍屹立不倒。

在这三者中，YARN 似乎是最脆弱的，大多数框架都提供了独立的运行模式，同时还面临来自更通用调度器（如 Mesos）的持续竞争，尽管 Mesos 本身也正在显著失去市场关注度，被 Kubernetes 抢走风头（尽管 Mesos 和 Kubernetes 是解决不同需求的差异化工具）。

在那些成功跨越世代的技术中，Kafka 尤其在不断扩展其功能集，以求差异化和提升市场影响力。最明显的例子是 Kafka Streams，它本质上是一个依赖更少、概念更简洁的 Apache Storm 竞争者（可以简单理解为消费一个 Kafka topic 并输出一个 compacted Kafka topic），并且提供了 exactly-once 保证。从设计上来看，它并不是那些功能更完整的流处理框架的直接竞争者：

我们看到 Kafka Streams 所填补的空白，并非这些框架所专注的分析领域，而是构建处理实时数据流的核心应用和微服务……构建这类流处理应用需要满足的需求，与典型的 MapReduce 或 Spark 作业所处的分析或 ETL 领域截然不同。它们需要经历与普通应用相同的配置、部署、监控等流程。简而言之，它们更像是微服务（我知道这个词已经被用滥了），只不过这类数据流应用处理的是来自 Kafka 的异步事件流，而不是 HTTP 请求。

除了 Kafka Streams 之外，Confluent 也在积极扩展 Kafka 生态系统，通过 Kafka Connect 等项目来填补工具链中的空白，试图解决 Kafka 部署中常见的依赖问题，比如 schema 管理和抽象 Kafka 的底层 API。

抛开 Kafka Streams 这种有意保持的狭窄定位不谈，在分析领域赢得这一代开发者心智份额的两个框架是 Spark 和 Flink。

这两个工具都获得了广泛采用，其中 Spark 在批处理/有界处理上更有优势，而 Flink 在流处理/无界处理上更胜一筹（特别是因为 Flink 支持原生流处理，而 Spark 依赖微批处理，会带来一定的延迟惩罚，可能限制某些使用场景）。从概念上看，Flink 是 Google Dataflow（现已更名为 Beam）模型的明确继承者，而 Spark 的创新则来自其弹性分布式数据集（RDD）。

与此同时，Google 通过其 Beam 库做出了一个有趣的尝试，试图将 Spark 和 Flink 都抽象掉。Beam 提供了一个库，用于实现数据流范式的程序，这些程序可以运行在多种执行引擎之上（包括 Flink、Spark，以及 Google Cloud 的 Cloud Dataflow 产品）。数据流方法中包含一些非常有趣的想法，我特别欣赏其中关于窗口（windowing）、快照以及会话窗口（session windowing）的解释。

总的来说，现在是关注数据基础设施领域的一个非常有趣的时刻，我很期待看到未来事态的发展。
