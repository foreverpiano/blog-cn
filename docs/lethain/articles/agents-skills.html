构建内部 Agent：为 Agent Skills 添加支持

2025-12-26 · 阅读原文

当 Anthropic 推出 Agent Skills 时，我最初对它解决的问题有些怀疑——我们不能直接用 prompt 和 tool 吗？但后来我逐渐理解了它的价值，并明确地在我们的内部 Agent 框架中实现了 Skills。本文将讨论 Skills 解决的问题、Imprint 工程团队如何实现它们、它们为我们带来的实际效果，以及未来可能的发展方向。

这是 构建内部 Agent 系列文章的一部分。

Agent Skills 解决了什么问题？

Agent Skills 是一系列技术，用于解决两个重要的工作流问题：

使用 构建内部 Agent：渐进式披露与处理大文件 更有效地利用受限的上下文窗口，尽量减少相互冲突或不必要的上下文；提供可复用的代码片段来解决重复出现的问题，避免每个工作流创建者都必须重复解决类似 Slack 格式化或处理大文件这样的常见问题。

这些问题在我们刚开始构建内部工作流时显得微不足道，但当内部工作流数量达到几十个后，两者都变得难以管理。没有可复用的代码片段，我就无法一次性改进所有工作流；而没有 progressive disclosure，Agent 就会接收到大量无关内容，导致它们感到困惑，尤其是在 Markdown 和 Slack 的 mrkdwn 格式语言不一致的情况下，而这两种格式对我们工作流所使用的不同工具都很重要。

我们如何实现 Agent Skills

首先需要声明，我知道实现 Agent Skills 并不是必需的，因为你可以直接集成 Claude 的 Agent Skills API 支持。不过，我们的一个核心设计决策是保持平台中立，以便能在不同模型提供商之间切换，因此我们决定在自己的框架内实现 Skills。

确定方向后，我们首先阅读了 agentskills.io 上的 Agent Skills 文档，并将他们的 Python 参考实现 skills-ref 克隆到我们的仓库中，以便 Claude Code 可以访问。

最终实现的方案包含以下核心特性：

---
name: pdf-processing
description: Extract text and tables...
metadata:
  author: example-org
  version: "1.0"
---
Skills 统一放在 skills/ 目录下，每个 Skill 都是一个独立的子目录，其中包含一个 SKILL.md 文件。每个 Skill 都是一个带有元数据的 Markdown 文件，格式大致如下：可用 Skill 列表（包含元数据中的描述）会在每个工作流开始时被注入到系统 prompt 中，同时提供 load_skills 工具供 Agent 将整个文件加载到上下文窗口。更新了工作流配置，允许可选地指定必需、允许和禁止的 Skill，从而调整注入到系统 prompt 中的 Skill 列表。我猜想为特定工作流强制要求某些 Skill 可能是一种反模式（“就让 Agent 自己决定吧！”），但实现起来非常简单，而且我觉得未来可能会很有用。使用 Notion MCP 检索我们 prompt 仓库中的所有现有 prompt，识别其中隐含的 Skill，编写最初的 Skill，并确定哪些 Notion prompt 需要修改以删除现在已经冗余的部分。

随后我们将其正式上线生产环境。

实际效果如何

人类总是会犯错。例如，我见过几十张人类创建的 JIRA ticket 没有说明他们遇到的实际问题。大家对此习以为常，当人类出错时，人们会责怪那个人。但当 Agent 出错时， surprising 比例的人会将其视为 Agent 这一类技术的根本性局限，而不是想“哦，我应该去更新那个 prompt”。

Skills 作为一种工具，在我们因为精确指定行为过于繁重而依赖隐式行为的情况下，对于持续细化这些边缘情况极为有用。举一个例子，我们要求每条 Slack 消息末尾都要附上生成该回复的 prompt 链接。这一点一直都能实现，但格式细节却会以一种令人烦躁且分散注意力的方式变化：有时是 [title](link) 的形式，有时是纯链接，有时又是 [link](link)。有了 Skills 之后，现在（几乎总是）保持了一致性，而无需任何人在工作流 prompt 中特意加入这些指令。

同样，处理大文件需要一系列不同的工具，这些工具非常受益于 In-Context Learning（简称 ICL，即在 prompt 中包含若干正确和错误使用示例），但几乎没有人会把这些内容加到自己的工作流 prompt 里，而 ICL 却能非常有效地提升工作流对这些工具的使用效果。

对于一项我最初深表怀疑的技术，现在我希望自己能更早地实现它。

未来可能的发展方向

虽然我们的 Skills 实现目前运行良好，但未来还有几个我想利用的机会：

添加一个 load_subskill Skill，以支持 skills/{skill}/* 目录下除了 SKILL.md 之外的其他文件。目前这还不是主要障碍，但随着某些 Skill 变得越来越复杂，将不同用例拆分成独立文件的能力将提升我们利用 Skills 实现 progressive disclosure 的效果。Anthropic 相比我们的一个显著优势是他们拥有沙箱化的 Python 解释器，这允许 Skill 中包含完整的 Python 脚本，并由工具指定和运行。例如，一个解析 PDF 的脚本可以放在 Skill 里，非常方便。我们目前还没有为 Agent 准备好沙箱解释器，但理论上这能大幅减少我们需要实现的自定义 Skill 数量。至少，它能在需要可靠数学运算的任务上表现更好，而不是依赖 LLM 尽力去完成数学相关的操作。

我认为这两件事实际上都相当容易实现。第一件事只是一个简单功能，Claude 几分钟就能搞定。第二件事实现起来有点麻烦，但也可以在不到一小时内完成——运行第二个 Lambda，用 Node.js 加载 Pyodide，然后把对该 Lambda 的访问暴露为一个 tool。只是让一个 Python 进程去调用 Node.js 进程来运行沙箱 Python，这听起来实在不够优雅，所以我暂时还没有动手。
