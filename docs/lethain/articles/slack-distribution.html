部署你的 Slack 应用。

2019-11-11 · 阅读原文

我们已经开发 reflect Slack 应用有一段时间了， 现在基本接近完成。我们只需要让其他人也能安装它。 最标准的部署方式是使用 Slack 的 App Directory， 它能让用户轻松发现和安装你的应用。

我们的这个玩具应用暂时还无法进入 App Directory，但我们会让其他人能够将其安装到自己的 workspace 中， 届时如果你愿意，就可以提交到目录里。

我们已经完成了大部分工作，现在只需集成 Slack 的 OAuth 机制， 获取 workspace 级别的 OAuth token，并将我们的 API 请求从之前硬编码的 token 改为使用这些动态 token。 希望这个过程能比较简单……

本文从 commit 4584 开始，到 commit 0fcc 结束。

Slack app in Python 系列

在 GCP 上用 Python 创建 Slack 应用在 Python Slack 应用中添加 App Home让 Slack 应用响应表情回应（reacji）。使用 Cloud Firestore 为 Slack 应用提供动力部署你的 Slack 应用。

部署 Slack 应用

要部署 Slack 应用，App 管理后台提供了一份实用的检查清单。 Google Cloud Functions 通过 HTTPS 运行，所以这一项我们已经满足。 如果你使用其他主机，可以考虑 LetsEncrypt 来获取免费 SSL 证书。

在这个系列文章中，我们已经逐步启用了大量功能， 包括 Slash Commands、App Home、部分 Events 等。 所以这部分我们也已经完成。

剩下的两项是“Add OAuth Redirect URLs”（我们接下来会处理）， 以及“Remove Hard Coded Information”。后者只是一个确认你已完成的勾选框， 但我们目前还没做到，因为 env.yaml 里还存着一堆 token，所以等 OAuth 流程完成后我们再回来处理。

集成 OAuth 的步骤

要集成 Slack 的 OAuth，我们需要：

实现一个 OAuth 重定向 URI，用于接收 OAuth 流程返回的 code，并用它换取长期有效的 OAuth token。 将新的重定向 URI 在 Slack 中注册。 将长期 token 存储到 Firestore，以便能根据请求的 team 检索到正确的 token。 在调用 Slack API 时使用对应 team 的 token，不再使用之前硬编码在 env.py 中的 token。 构造我们的授权 URL，用户将被重定向到这里进行认证。 验证整个 OAuth 集成流程是否正常工作。 更新现有的流程以使用存储的 token。

这里有很多细节需要理清，容易让人感到困惑， 但幸运的是我们实际需要编写的代码相对简单。继续吧！

OAuth 重定向 URI

我们将创建一个新的 Cloud Function 来处理重定向。 首先更新 reflect/storage.py，以支持存储获取到的 token。

DB = firestore.Client()

def credentials(team_id):
    return DB.collection('creds').document(team_id)

def set_credentials(team_id, data):
    creds = credentials(team_id)
    creds.set(data)

我很喜欢能直接把 JSON 响应塞进 Firestore 而不用拆解它。 诚然，在生产环境中我们可能需要更谨慎地验证内容，以防止未来数据格式发生变化。

接下来更新 reflect/api.py，以支持调用 oauth.access 接口， 这个接口需要的参数格式与我们之前做的另外两个 API 集成略有不同。

def oauth_access(code):
    url = "https://slack.com/api/oauth.access"
    client_id = os.environ['SLACK_CLIENT_ID'].encode('utf-8')
    client_secret = os.environ['SLACK_CLIENT_SECRET'].encode('utf-8')
    data = {
        'code': code,
    }
    auth = (client_id, client_secret)
    resp = requests.post(url, data=data, auth=auth)
    return resp.json()

然后更新 reflect/main.py，新增 oauth_redirect 函数， 稍后我们会把它部署为 Cloud Function。


from api import oauth_access
from storage import set_credentials

def oauth_redirect(request):
    code = request.args.get('code')
    resp = oauth_access(code)
    team_id = resp['team_id']
    set_credentials(team_id, resp)

要让它正常工作，我们需要在 reflect/env.yaml 中添加 SLACK_CLIENT_ID 和 SLACK_CLIENT_SECRET。 这些值可以在 App 管理后台的“Basic Information”标签页找到。

SLACK_CLIENT_ID: "your-client-id"
SLACK_CLIENT_SECRET: your-client-secret
SLACK_SIGN_SECRET: your-secret
SLACK_BOT_TOKEN: your-bot-token
SLACK_OAUTH_TOKEN: your-oauth-token
GOOGLE_APPLICATION_CREDENTIALS: ./gcp_creds.json

注意 Client ID 需要用引号括起来，否则 Cloud Functions 会尝试将其当作 float 处理，导致失败。

然后部署我们新的 Cloud Function，以便获取它的 URI。

cd reflect
gcloud functions deploy oauth_redirect \
--env-vars-file env.yaml \
--runtime python37 --trigger-http

接下来是注册这个 URL。

注册重定向 URL

创建 oauth_redirect endpoint 后获得的 URL 大概是这样的。

 https://your-url.cloudfunctions.net/oauth_redirect

现在我们需要进入 App 管理后台，在左侧导航栏点击“OAuth & Permissions”，然后进入“Redirect URLs”页面。

点击“Add Redirect URL”，粘贴刚才的 URL，然后点击“Save URLs”。

很好，我们又前进了一步。

创建 OAuth 授权 URL

为了让用户授权，我们需要将他们重定向到以下地址：

https://slack.com/oauth/authorize

我们需要传入两个 GET 参数：(1) client_id 用于标识我们的应用， (2) scope 表示我们请求的权限范围。 还有其他可用的参数，在“Using OAuth 2.0”文档中有说明，但我们暂时可以忽略。

还有一种更简便的“Direct Install URL”方式，仅适用于已在 App Directory 中的应用， 可惜我们目前不在其中。而且在完成 OAuth 集成之前，你也无法进入 App Directory， 所以这些步骤无法跳过。

我们先手动构造这个 URL。

首先进入 App 管理后台，在左侧导航选择“Basic Information”， 向下滚动到“App Credentials”部分获取 client_id。

在本例中，我们的 Client ID 是 808524337907.822205476262。

然后在 App 管理后台进入“OAuth & Permissions”，记下我们正在使用的四个 scopes：

bot
commands
channels:history
reactions:read

综合以上信息，我们就可以生成授权 URL 了。

https://slack.com/oauth/authorize
?client_id=808524337907.822205476262
&scope=bot,commands,channels:history,reactions:read

另外，当你添加完 Redirect URL 后（之前它不会显示）， 现在可以直接去 App Admin 的“Manage Distribution”页面获取自动生成的链接。 它还能帮你生成一个可嵌入的按钮，以及带有正确 scopes 的授权链接，非常方便。

验证流程

现在我们有了授权 URL，把它粘贴到浏览器里，看看是否能正常工作。

点击“Allow”后，它会重定向到我们上面的处理函数，然后你会看到一个几乎全白的页面，上面写着“OK”。 长期来看，你可能希望通过 301 响应将用户重定向到一个更有用的页面。 Slack 推荐使用他们的 deep linking 功能。

如果我们打开 Firestore，可以验证是否正确保存了我们想要的数据。

确实保存了，这非常令人兴奋：我们的 OAuth 集成已经接近完成。 接下来只需要更新调用 Slack API 的地方，使用这些获取到的 token，而不是之前硬编码的那些。

使用获取到的 token

我们已经从 OAuth 授权流程中获取了 OAuth token 和 bot token， 所以第一件事就是删除 reflect/env.yaml 中硬编码的 token。

delete -> SLACK_BOT_TOKEN: your-bot-token     <- delete
delete -> SLACK_OAUTH_TOKEN: your-oauth-token <- delete
SLACK_CLIENT_ID: your-client-id
SLACK_CLIENT_SECRET: your-client-secret
SLACK_SIGN_SECRET: your-secret
GOOGLE_APPLICATION_CREDENTIALS: ./gcp_creds.json

然后我们在 reflect/storage.py 中新增一个函数来获取凭证。

def get_credentials(team_id):
    creds = credentials(team_id).get().to_dict()
    return {
        'oauth': creds['access_token'],
        'bot': creds['bot']['bot_access_token'],
    }

接着修改 reflect/api.py，让它使用 get_credentials 来获取凭证。

# retrieving bot token previously
os.environ['SLACK_BOT_TOKEN'].encode('utf-8')
# updated
get_credentials(team_id)['bot']    

# retrieving oauth token previously
os.environ['SLACK_OAUTH_TOKEN'].encode('utf-8')
# updated
get_credentials(team_id)['oauth']

有一个小注意点：获取这些 token 需要把 team_id 传递到每个调用 Slack API 的函数中。 这需要对 reflect/events.py 做一些重构。幸运的是，我们订阅的所有事件都包含 team_id， 所以传递起来并不困难。

之后，部署最新版本的 dispatch，它应该就能正常工作了。 通过测试 /reflect、/recall、访问 App Home 以及使用 reacji 来验证。

启用分发功能

如果上面的一切都正常工作，现在回到“Manage Distribution”页面， 向下滚动到“Remove Hard Coded Information”，确认你已经完成。

此时“Activate Public Distribution”按钮就会变得可用，点击它即可。

启用分发后，你就能看到安装数量、禁用分发， 以及进入提交应用到 Slack App Directory 的流程。 但最重要的是：如果你把授权 URL 分享给别人，他们就可以安装你的应用了。

换句话说：我们完成了！

一些思考

在这五篇文章的过程中，我花了不少时间深入了解 Slack 的 API 和 Google 的函数即服务产品——Cloud Functions。 两者都让人相当愉悦。

Slack

我在开始这个系列时有一个假设：在 Slack 平台上构建应用会比构建一个同等功能的普通 Web 应用更简单。 最终，我认为这个假设在这个项目中是成立的。 启动一个新项目通常需要大量的脚手架工作，而 Slack 提供了非常优秀、易于实现的接口， 让你免于编写这些脚手架。即使我放弃使用他们的 Python SDK，转而编写原始集成（目的是更好地理解底层 API），也依然如此。

你可能会说，SDK 才是现代 API 的真正接口，因为绝大多数集成都是通过特定语言的 SDK 而非直接生成原始 API 调用。 不过这个讨论就留到另一篇文章吧。

Slash Commands 对于有文本界面使用经验的我来说非常熟悉， 我很好奇其他人是否也同样适应，或者是否存在 IRC 一代用户和非 IRC 一代用户之间的分歧。 我确实认为 Reacji 可以看作是经过现代化改进、发现性更好的 Slash Commands。

总体来说，我认为以 reacji 作为用户界面是 Slack 应用中一个特别有趣且值得探索的方向。 我猜 Slack 应该掌握着非常强大的使用模式数据。一个小遗憾是，我希望能根据特定 reaction 来过滤传入的事件， 比如只接收 :ididit: 这个 reaction 的事件，而不是必须自己过滤掉所有其他事件。 无关 reaction 的数量远远超过任何一个应用真正关心的数量，跳过这些不必要的网络流量会更好。

Slack API 和平台目前最像“进行中工作”的两个地方是：(1) 表达能力受限，(2) API 设计不一致。

当我开始格式化已完成任务列表时，遇到了一个有趣的问题：Block Kit 和 mrkdwn 都不支持列表。 你只能把每一项放在单独的段落里，制造出一种类似 Markdown 的列表，但效果并不理想， 更无法达到 Dropbox Paper 那种动态共享 checklist 的水准。 天才往往来自于限制，Slack 在表达上的限制催生了 reacji 这样的创新， 但不可否认的是，Web 或原生应用在表达想法上拥有大得多的灵活性，而目前的 Slack 应用还做不到。

长期存在的平台最终在 API 上出现一些不一致是自然现象， Slack 的 API 也清晰地反映了它的演进过程。 另外，API 设计的一致性也受限于 Web 标准的自身不一致：Slack 无法让 OAuth 流程和 Events API 保持完全一致， 因为 OAuth 是一个老旧的标准，他们必须遵守。 这种因实现 Web 标准而带来的本质不一致，同时又要提供现代 API 行为的挑战确实存在， 而 SDK 是目前绕过这个问题的主要途径，Slack 也正在这么做。

总的来说，我认为 Slack 平台的完整性和易用性非常令人振奋， 我已经迫不及待想看看几年后它会发展成什么样子。

GCP

在 Cloud Functions 上开发是我经历过脚手架开销最低的项目，几乎能让我瞬间开始工作。 运行 Python 服务一直是一件很烦人的事（我已经花了足够多的时间配置 uWSGI）， 而现在我可以跳过这一切，只需编写应用特定的代码。 添加 requirements.txt 依赖按预期工作，在目录中复制额外数据文件也正常，通过环境变量传递配置也很顺畅，等等。

Cloud Firestore 的设置和使用也出奇地简单。虽然它的查询模式受到较多限制， 但作为一个无需任何管理开销的文档存储，对于这个用例来说完全够用。 我有很多玩具项目因为存储麻烦或昂贵而从未真正上线， 我觉得未来很多这类项目可能会选择使用 Firestore。

Cloud Functions 当前最大的不足是：如果想把它放到负载均衡器后面而不自己写软件， 会出奇地困难（而在 AWS 上这非常简单）。 出于自动扩容的目的这可能不是必须的，因为函数调度器本身就是一个编排系统， 但如果你想使用统一的 SSL 连接、在单个 HTTP/2 连接上复用请求、展现运行在自己域名下的专业形象， 以及拥有一个干净的接口以便未来更换实现方式，那么它就很有必要。

总而言之，我非常享受这个项目，它也特别提醒我，用 Python 编写小型软件是多么快乐的一件事。 希望这些笔记对某些人有用，欢迎给我留言分享你的想法。
