“我们是一家产品工程公司！”——Calm 的工程战略

2025-01-23 · 阅读原文

在我的职业生涯中，我所做的大部分战略工作都是在非高管职位上完成的，比如 。加入 Calm 是我第一次担任高管角色，在这里我不仅能提出战略，还能将其确立为必须执行的方针。2014 年左右 Uber 的服务迁移策略。

和几乎所有初创公司一样，我加入时工程团队的工作方向十分分散。我们最重要的工作是构建更具扩展性的基础设施吗？我们最大的风险是没有采用主流编程语言吗？我们该如何挽救陷入停滞的 ？我们应该分解单体应用吗？

这份战略是工程团队与我在多轮迭代、辩论乃至一些分歧之后共同达成的共识。作为一份战略，它既朴实，又清晰地表明了我们的核心价值观。我认为，对于任何的消费类产品来说，这都是一个相当不错的起点。如何打造软件质量

Policy & Operation（政策与执行）

我们新的政策以及配套的执行机制如下：

我们是一家产品工程公司。 用户每天都会写信告诉我们，我们的产品如何切实改善了他们的生活。 我们的技术基础设施则很少收到此类来信——未来这种情况也不太可能改变，因为我们的基础设施复杂度较低、规模也较小。 与其试图改变这一点，我们更愿意把绝对最多的精力投入到产品工程中。 我们只在能够创造有价值的产品能力时，才会采用新技术。 我们相信，现有的技术栈足以应对当前及未来大部分的产品路线图。 在极少数情况下，如果不采用新技术就无法实现某项产品能力，我们才会引入新工具。除此之外，我们不会因为其他任何理由采用新技术。例如，我们不会因为有人想学习某项技术而采用它，也不会因为某项技术在某个任务上比现有方案好 30% 而采用它。 我们所有的代码都写在单体应用中。 此前一直存在一个模糊地带：新的代码（尤其是新的应用代码）是应该写在我们的 JavaScript 单体应用里，还是必须写在单体之外的新服务中。 现在这个答案已经明确：所有新代码都必须写在单体应用中。 如果确实存在功能性需求，导致无法在单体内实现，则应按下述流程申请例外。 例外只能由 CTO 批准，且必须以书面形式确认。 上述政策是故意设计得较为严格的。有时它们可能会出错，我们也会为此做出例外。但每一次例外都必须是经过深思熟虑的，并且要基于我们共同认可的具体问题以及解决方式。 如果我们各自奔向自己偏好的方案，最终只会给 Calm 带来负面杠杆，而不是成为推动产品前进的引擎。 所有例外都必须形成书面记录。如果没有书面记录，你就应当视为该例外未被批准。 我们的目标是消除围绕例外是否被批准产生的任何模糊空间。 如果没有 CTO 书面批准的记录，那就意味着没有获得批准。

为了印证关于例外的原则，当前已确认存在两项针对上述战略的例外情况：

我们正在逐步迁移到 TypeScript。 我们发现静态类型能够有效防止大量用户可见的 Bug。 TypeScript 为我们的 JavaScript 代码库提供了一条清晰、渐进的迁移路径，我们计划在未来六个月内完成整体迁移。 我们的 Web 工程团队正在主导这项迁移工作。 我们正在评估将 Postgres Aurora 作为主要数据库。 我们最近的多次生产事故都是由对高写入速度表（如记录用户登录的表）进行索引扫描导致的。 我们相信 Aurora 在这类负载下会表现得更好。 我们的 Infrastructure 工程团队正在主导这项工作。

Diagnose（诊断）

当前工程组织的现状：

我们的产品并未受限于基础设施能力的缺失。 回顾产品路线图，无论是现在还是未来一年，我们要构建的任何功能都没有受到现有技术基础设施的制约。 我们的可用性、稳定性和延迟表现还算过得去，但远未达到优秀。 我们的应用存在较为频繁的稳定性和延迟问题，所有问题都可归结为以下两类原因之一： 第一，在测试环境表现尚可但缺少必要索引的情况下部署新代码； 第二，对少量极大且字段极少的表进行写入，同时对这些表的索引进行扫描，导致成本显著升高。 我们的基础设施团队同时要支持单体应用和服务化两种工作模式。 衡量技术债的一种方式是看团队花在维护现有基础设施上的时间。目前，对于我们 3 人的基础设施团队和 30 人的产品工程师团队来说，这部分工作虽然重要，但尚未构成压倒性的负担。 然而，我们发现基础设施工程师越来越多地被拉入由单体拆分到服务架构的组件所引发的事故排查中。 这部分是因为服务的固有复杂度增加，但更多是因为缺少监控和责任界定不清，导致生产事故难以定位。 我们的产品和高层利益相关方认为我们是互相竞争的派系。 工程部门的存在是为了在公司内构建和运维软件。这其中很重要的一点是易于合作。我们不一定需要支持产品团队的每一个需求（如果我们认为它与工程目标不符，例如安全要求），但整个团队应该对外提供一致的视角。 今天，利益相关方觉得他们对同一个能力或方案问题得到的答案会因为询问对象不同而大相径庭。如果他们试图让一群工程师就某个方案达成一致，往往会发现我们陷入对实现方式的争论，而不是给出清晰的观点来推动对话前进。 我们在讨论技术采用和重写上花费了过多时间。 我们大部分的分歧都源于是否采用新技术，或是否将现有组件重写到新的技术栈上。例如，我们是应该扩展这个功能，还是必须先把它迁移成服务才能扩展？ 我们是应该把数据加到现有数据库，还是应该迁移到新的 Redis 缓存？ JavaScript 是否已经足够好，还是我们需要用 Go 重写这个功能？ 这与正在进行的服务迁移的下一步工作尤其相关——该迁移已经进行了一年多，却还没有迁移任何核心生产代码。 我们在基础设施和平台工作上花费的时间超过了产品工作。 这是上述所有问题的综合结果，从数据库设计引发的稳定性问题，到工程团队在执行上缺乏一致性。 这导致我们与利益相关方的期望产生矛盾——他们认为我们应该主要专注于新产品开发。

Explore（探索）

Calm 是一款移动应用，它引导用户建立并维持冥想或睡眠习惯。 针对不同用户的推荐和内容指导是个性化的，但内容本身在所有用户间共享，因此非常适合在内容分发网络（CDN）上进行缓存。 只要 CDN 可用，即使无法访问后端服务器，移动应用也能正常运行（例如，从用户视角看，即使非 CDN 的生产基础设施不可达，应用仍然可用）。

在 2010 年，要实现如此复杂度的产品，可能需要大量定制化基础设施，并且很可能需要在多个数据中心维护物理服务器来运行自己的软件。 到了 2020 年，同类应用普遍倾向于尽可能少地维护内部基础设施。 这种观点在 Intercom 的《Run Less Software》和 Dan McKinley 的《Choose Boring Technology》中得到了很好的总结。

在这个领域新成立的公司，基本上把所有基础设施都视为可以直接从云服务商那里购买的商品。 这种趋势甚至延伸到创新领域，例如机器学习：训练基础设施通常使用 AWS Bedrock 这类服务，而模型推理基础设施则由 Anthropic 或 OpenAI 提供。
