“我们是一家产品工程公司！”——Calm 的工程策略

2025-01-23 · 阅读原文

在我的职业生涯中，我所参与的大部分策略工作都是在非高管职位上完成的，比如 项目。加入 Calm 是我第一次担任高管角色，在这里我不仅能提出策略，还能将其确立为必须执行的方针。2014 年左右 Uber 的服务迁移策略。

和几乎所有初创公司一样，我加入时工程团队的工作方向非常分散。我们最重要的工作是打造更具扩展性的基础设施吗？我们最大的风险是没能采用主流编程语言吗？我们该如何挽救陷入停滞的 ？我们是否应该分解单体架构？

这份策略是工程团队和我经过多轮迭代、辩论乃至一些分歧后最终达成一致的结果。作为一份策略，它既简单明了，又清晰地表明了我们的核心价值观。我认为，对于任何 的消费类产品来说，这都是一个相当不错的起点。如何打造软件质量

这是《Crafting Engineering Strategy》中的一章。

策略与执行

我们新的策略及其配套执行机制如下：

我们是一家产品工程公司。 用户每天都会写信告诉我们，我们的产品切实改善了他们的生活。 我们的技术基础设施很少收到用户的来信——而且未来也不太可能改变，因为我们的基础设施规模较小、复杂度也较低。 与其试图改变这一点，我们更愿意把绝对最多的注意力投入到产品工程上。 我们只采用能创造有价值产品能力的新技术。 我们相信，现有的技术栈足以应对当前及未来大部分的产品 roadmap。 只有在极少数情况下，某项产品能力离开了新技术就根本无法实现，我们才会采用新技术。 我们不会因为其他理由采用新技术。例如，我们不会因为有人想学习某项技术而采用它，也不会因为某项技术在某项任务上“比现有方案好 30%”而采用它。 我们把所有代码都写在单体应用中。 之前对于新代码（尤其是新的应用代码）是应该写在我们的 JavaScript 单体应用中，还是必须写在单体之外的新服务中，一直存在模糊地带。 现在这个不再模糊：所有新代码都必须写在单体中。 如果确实存在功能性需求导致无法在单体中实现，则应按下述流程申请例外。 例外由 CTO 批准，且必须以书面形式确认。 上述策略是刻意设置了限制的。有时它们可能会出错，我们会为此做出例外处理。但每一次例外都必须是深思熟虑的，并且基于我们都认同的具体问题以及解决该问题的方法。 如果大家都分散去追求自己偏好的方案，那么我们带给 Calm 的将是负面杠杆，而不是推动产品前进的引擎。 所有例外都必须书面记录。如果没有书面记录，你就应该当作例外没有被批准来开展工作。 我们的目标是避免在“例外是否已被批准”这个问题上产生任何模糊。 如果没有 CTO 的书面批准记录，那就没有被批准。

为了印证例外机制的重要性，当前已有两项经确认的策略例外：

我们正在逐步迁移到 TypeScript。 我们发现静态类型能有效防止不少面向用户的 bug。 TypeScript 为我们的 JavaScript 代码库提供了一条清晰且可增量进行的迁移路径，我们计划在未来六个月内完成全部迁移。 我们的 Web 工程团队主导这项迁移工作。 我们正在评估将 Postgres Aurora 作为主要数据库。 我们最近的多次生产事故都是由对高写入速度表（例如记录用户登录的表）进行索引扫描导致的。 我们相信 Aurora 在这类工作负载下表现会更好。 我们的 Infrastructure 工程团队主导这项工作。

诊断

我们工程组织的当前状态：

我们的产品并未受限于基础设施能力的缺失。 回顾我们的 roadmap，无论是现在还是未来一年，我们要构建的功能都没有受到技术基础设施的制约。 我们的 uptime、稳定性和延迟表现还算过得去，但远谈不上优秀。 我们的应用存在较为频繁的稳定性和延迟问题，所有问题都可以归结为以下两类： 第一，在测试环境表现尚可但缺少必要索引的新代码上线部署； 第二，对少数极大型且字段很少的表进行写入时，配合这些表的索引扫描，成本变得非常高昂。 我们的基础设施团队同时要支持单体应用和服务化两种工作流。 衡量技术债务的一个方法，是看团队花在维护现有基础设施上的时间。目前，对我们 3 名基础设施工程师支持 30 名产品工程师的团队来说，这是一项有意义但还不算压倒性的工作。 然而，我们发现基础设施工程师越来越多地被拉去调试那些已从中央单体拆分到服务架构中的组件所引发的事故。 这部分是因为拆分后的固有复杂度增加，但更多是因为服务在生产环境中缺乏监控、权责不够清晰。 我们的产品和高层利益相关者认为我们是相互竞争的派系。 工程部门的存在是为了在公司内构建和运营软件。其中很重要的一点是易于合作。 如果我们认为产品提出的需求与工程目标不一致（例如安全需求），我们不必全部支持，但整个团队应该提供一致的观点。 如今，利益相关者觉得，对于基本的能力和方案问题，他们问不同的人会得到截然不同的答案。如果他们试图让一群工程师就某个方案达成一致，往往会发现我们陷入对方案本身的争论，而不是提出清晰的观点让讨论向前推进。 我们在技术采用和重写上花费了过多时间争论。 我们大部分的分歧都源于是否采用新技术或是否把现有组件重写到新的技术栈上。例如，我们是应该扩展这个功能，还是必须先把它迁移到服务里再扩展？ 我们是应该把这个加到现有数据库里，还是应该把它迁移到一个新的 Redis 缓存里？ JavaScript 是否已经够用了，还是我们必须用 Go 重写这个功能？ 这与我们正在进行的服务迁移的下一步尤为相关——该迁移已经进行了一年多，却还没有迁移任何核心生产代码。 我们在基础设施和平台工作上花费的时间已经超过了产品工作。 这是上述所有问题的综合结果，从数据库设计带来的稳定性问题，到工程团队在执行上缺乏一致性。 这导致我们与利益相关者的期望产生矛盾——他们认为我们应该主要专注于新产品开发。

探索

Calm 是一款移动应用，它引导用户建立和保持冥想或睡眠习惯。 针对不同用户的内容推荐和指导是个性化的，但内容本身在所有用户间是共享的，因此适合使用内容分发网络（CDN）进行缓存。 只要 CDN 可用，即使无法访问后端服务器，移动应用也能正常运行（从用户视角来看，即使非 CDN 的生产基础设施不可达，应用依然可用）。

在 2010 年，打造这样复杂度的产品需要大量定制基础设施，很可能还需要在一系列数据中心保持物理存在来运行软件。 而在 2020 年，同类应用普遍倾向于尽量减少内部基础设施。 Intercom 的《Run Less Software》和 Dan McKinley 的《Choose Boring Technology》很好地总结了这一观点。

在这个领域新成立的公司，基本上把所有基础设施都视为可以直接从云厂商购买的商品。 这种趋势甚至延伸到创新领域，例如机器学习：训练基础设施通常运行在 AWS Bedrock 这类服务上，而模型基础设施则由 Anthropic 或 OpenAI 提供。
