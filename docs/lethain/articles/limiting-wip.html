为什么限制在制品数量有效

2019-02-17 · 阅读原文

几年前，我的朋友 Bobby 给我看了一篇文章，讲的是一位 CEO 如何运用系统思维来识别公司中的瓶颈，最终他买断了联合创始人的股份——那位联合创始人当时负责销售团队。正如我们决定广泛传播的关于自己的故事一样，这个决定后来被证明是正确的，他们的业务也随之蓬勃发展。

我每次想找那篇文章都找不到，但它很好地体现了我最喜欢系统建模的一点：它是为实践者准备的工具。

最近，我用建模的方式梳理了自己对 的思考。这周我一直在思考《目标》（The Goal）这本书、如何完成更多工作，以及生产力模型应该是什么样子。撰写可靠性策略：用系统模型思考复杂问题

本文中用到的模型可以通过 systems 库直接运行，生成图表的 Jupyter notebook 已序列化在 Github 上，你也可以在 Binder 上与它们互动。

初始模型

为了让第一个版本保持简单，我们假设世界上有无限多的想法，我们会将其中一部分想法转化为项目。我们选择启动其中一些项目，并最终完成其中一部分已启动的项目。

[Ideas]  > Projects @ 1
Projects > Started  @ 1
Started  > Finished @ 1

当模型经过几轮运行达到均衡后，我们每个周期最终能完成一个项目。

我们不会积累想法 backlog，启动项目的速度与完成项目的速度保持一致。

招聘、招聘、招聘

情况发展得不错，但我们完成的工作量还是不够，于是我们开始招聘更多开发者。

[Hires]  > Developers @ 1
[Ideas]  > Projects   @ Developers
Projects > Started    @ Developers
Started  > Finished   @ Developers

每位开发者每个周期都能启动并完成一个项目，这意味着我们完成的工作越来越多，正欣喜若狂地朝着无限生产力加速前进。

这就是 。花点时间停下来，为这个模型所承诺的无限生产力而欢呼吧。超级增长时代的生产力

把所有事情都做完

遗憾的是，你很可能已经注意到，当你同时启动一大堆项目时，实际完成的反而更少。你会在不同任务之间切换，回答各种问题等等，随着未完成任务的增多，整体速度会越来越慢。

我们在模型中引入这个因素，将完成速率调整为受已启动任务数量影响。

[Hires] > Developers @ 2
[Ideas] > Projects   @ Developers
Projects > Started   @ Developers
Started > Finished   @ Developers - Started

现在我们启动的任务多于能够完成的数量，而每个已启动的任务又会进一步拖慢其他任务的完成速度，这导致我们迅速陷入完全无法完成任何工作的境地。

这个结果听起来有点极端，但我认为它相当常见。在较小的项目中很少会表现得如此明显，但在非常大型的项目中————这种情况几乎时刻都在发生。我怀疑大多数公司启动的迁移项目都超过了他们真正能完成的数量。迁移：解决技术债的唯一可扩展方案

限制在制品数量

经典的看板解决方案就是限制在制品（Work-in-Progress）。只有当一个现有项目完成后，才能启动新的项目，从而形成一个反馈环，防止我们被未完成的任务压垮。

[Hires] > Developers @ 2
[Ideas] > Projects   @ Developers - Started
Projects > Started   @ Developers - Started
Started > Finished   @ Developers - Started

即使是这个相当朴素的在制品限制，也足以产生反馈，让我们继续从增加招聘中获益。注意，从第四轮之后，已启动和已完成两条线几乎完全重合，这就是为什么“已启动”那条线看起来消失了。

之前，在没有在制品限制的情况下，我们在 100 轮中只完成了 12 个项目；而现在，有了在制品限制后，我们在同样的 100 轮中完成了 198 个任务。这是一个非常酷的结果，它表明启动工作比完成工作更快的做法，会严重阻碍整体吞吐量。

同时也要注意，过多的在制品数量仍然让我们离理想吞吐量有相当大的差距。我们可以通过增强对启动任务的“背压”来进一步实验。

[Hires] > Developers @ 2
[Ideas] > Projects   @ Developers - Started
Projects > Started   @ Developers - (2 * Started)
Started > Finished   @ Developers - Started

现在由于我们以更慢的速度启动项目，反而能够完成多得多的任务。

事实上，在 100 轮中，这个模型完成了 2520 个任务，是前面那个反馈较弱的模型的十倍以上。

你可能好奇如果我们把反馈再加强一些，把针对已启动任务的乘数从 2 改成 3 会怎样。结果发现那会造成过强的背压，导致我们无法启动足够多的任务来充分利用完成能力，最终在 100 轮中只能完成 2064 个任务。如果你多调整一下参数，会发现当乘数设为 1.75 时，我们能完成 2909 个任务，依此类推。

除非你用真实世界的数据来定义这些流动，否则优化这些模型通常没有太大价值，但它确实很好地展示了这些决策的影响有多大。

调整优先级

稍微换个方向思考一下：如果我们停止一些已经启动但尚未完成的工作——可能是因为优先级发生了变化——会发生什么，这点很有趣。我们先把它纳入到弱背压模型中。

Reprioritization(1)
[Hires]  > Developers @ 2
[Ideas]  > Projects   @ Developers - Started
Projects > Started    @ Developers - Started
Started  > Finished   @ Developers - Started - Reprioritization

我们设定了一个固定的项目重排优先级速率（每轮 1 个），并将这些被重排优先级的项目从完成速率中移除，因为我们不会完成那些已经停止推进的项目。

与没有重排优先级的版本相比，我们仍在取得进展，但吞吐量减半，在 100 轮中只完成了 101 个项目。

接下来，我们把同样的逻辑应用到具有强背压的模型上。

Reprioritization(1)
[Hires]  > Developers @ 2
[Ideas]  > Projects   @ Developers - Started
Projects > Started   @ Developers - (2 * Started)
Started  > Finished   @ Developers - Started - Reprioritization

重排优先级的速率相同，但结果却大不相同。

之前我们在 100 轮中完成了 2520 个任务，引入这个重排优先级速率后，我们只能完成 2485 个，但仍然相当接近。

把两个模型放在一起看就会发现：在执行力严重受限的场景下，调整优先级代价非常高昂；但在我们已经能完成大量工作的场景下，它的代价相当低。

模型毕竟只是模型，它们只会告诉我们所询问的内容。但对我来说，这又一次展示了模型如何能把人们的直觉从阴影中拉到台前，并促成一场丰富而深入的对话。
