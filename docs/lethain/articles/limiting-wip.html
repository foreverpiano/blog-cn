为什么限制在制品数量有效

2019-02-17 · 阅读原文

几年前，我的朋友 Bobby 给我看了一篇文章，讲的是一位 CEO 如何运用系统思维来识别公司的瓶颈，最终他买断了联合创始人的股份——那位联合创始人当时负责带领销售团队。正如我们决定广泛传播的关于自己的故事通常那样，这个决定被证明是正确的，他们的业务也随之蓬勃发展。

我每次想找都找不到那篇文章，但它很好地体现了我最喜欢系统建模的一点：它是一种给实践者使用的工具。

最近，我用建模的方式重新梳理了对我们 制定可靠性策略：用系统模型思考复杂问题 的思考。这周我一直在思考《目标》这本书、如何完成更多工作，以及一个生产力模型应该是什么样子。

本文中的模型可以通过 systems 库直接运行，生成图表的 Jupyter notebook 已序列化在 Github 上，你还可以在 Binder 上与所有内容进行交互。

初始模型

为了让模型的第一版保持简单，我们假设世界上有无限多的想法，我们会将其中一些想法转化为项目。我们选择启动其中一部分项目，并完成我们启动的其中一部分项目。

[Ideas]  > Projects @ 1
Projects > Started  @ 1
Started  > Finished @ 1

当模型经过几轮运行达到平衡后，我们每轮最终只能完成一个项目。

我们不会积累想法 backlog，启动项目的速度和完成项目的速度完全一致。

招聘，招聘，招聘

情况进展得不错，但我们完成的工作量还是不够，于是我们开始招聘更多开发者加入公司。

[Hires]  > Developers @ 1
[Ideas]  > Projects   @ Developers
Projects > Started    @ Developers
Started  > Finished   @ Developers

每位开发者每轮都能启动一个项目并完成一个项目，这意味着我们完成的工作越来越多，快乐地朝着无限生产力加速前进。

这就是 超高速增长时代的生产力。花点时间暂停一下，为这个模型所承诺的无限生产力欢呼吧。

什么都想做

不幸的是，你很可能已经注意到，当你同时启动一大堆项目时，实际完成的反而更少。你会从一个任务跳到另一个任务，还要回答各种问题等等，随着未完成任务越来越多，进度也越来越慢。

我们在模型中通过调整完成速率，让它受已启动任务数量的影响来体现这一点。

[Hires] > Developers @ 2
[Ideas] > Projects   @ Developers
Projects > Started   @ Developers
Started > Finished   @ Developers - Started

现在我们启动的任务多于能完成的任务，而每个已启动的任务又会进一步减慢其他任务的完成速度，这导致我们很快陷入完全无法完成任何工作的境地。

这个结果感觉有点极端，但我认为它相当常见。在较小的项目中很少会表现得如此极端，但在非常大型的项目中却时常发生，迁移：解决技术债务唯一可扩展的办法。，我怀疑大多数公司启动的迁移项目都超过了他们实际能完成的数量。

限制在制品数量

经典的看板解决方案就是限制在制品（Work-in-Progress）。只有当一个现有项目完成后，才能启动新的项目，从而形成一个反馈回路，防止我们被未完成的任务淹没。

[Hires] > Developers @ 2
[Ideas] > Projects   @ Developers - Started
Projects > Started   @ Developers - Started
Started > Finished   @ Developers - Started

即使是这个相当朴素的在制品限制，也创造了足够强的反馈，让我们能继续从增加招聘中获益。注意，从第四轮之后，已启动和已完成两条线几乎完全重合，这就是为什么“已启动”线看起来消失了。

之前，在没有在制品限制的情况下，我们在 100 轮中只完成了 12 个项目；而现在有了在制品限制后，我们在同样的 100 轮中完成了 198 个任务。这是一个非常酷的结果，它表明比完成速度更快地启动工作，会严重阻碍我们的整体吞吐量。

还要注意，大量在制品仍然会让我们离理想吞吐量有相当大的差距。我们可以通过加强启动任务时的背压来做实验。

[Hires] > Developers @ 2
[Ideas] > Projects   @ Developers - Started
Projects > Started   @ Developers - (2 * Started)
Started > Finished   @ Developers - Started

现在我们以较慢的速度启动项目，反而能够完成多得多的任务。

事实上，在 100 轮中，这个模型完成了 2520 个任务，是前面那个反馈较弱的模型的十倍以上。

你可能好奇如果我们把反馈再加强一些，把针对已启动任务的乘数从 2 改成 3 会怎样。结果是反馈太强了，导致我们无法启动足够多的任务来充分利用完成能力，100 轮中只能完成 2064 个任务。如果你再多调调参数，会发现如果把乘数设为 1.75，我们最多可以完成 2909 个任务，诸如此类。

除非你用真实世界的数据来定义这些流动，否则优化这些模型通常没有太大价值，但它确实很好地展示了这些决策的影响有多大。

调整优先级

稍微换个方向思考一下，如果我们停止一些已经启动但尚未完成的工作（可能是因为优先级发生变化），会发生什么，这一点很有趣。先把它纳入到弱背压模型中。

Reprioritization(1)
[Hires]  > Developers @ 2
[Ideas]  > Projects   @ Developers - Started
Projects > Started    @ Developers - Started
Started  > Finished   @ Developers - Started - Reprioritization

我们设定了一个固定的项目重排优先级速率——每轮一个，并将这些被重新排优先级的项目从完成速率中移除，因为我们不会完成那些已经停止投入工作的项目。

与没有重排优先级的版本相比，我们仍然在前进，但吞吐量被砍掉了一半，100 轮内只完成了 101 个项目。

接下来我们把它放到带有强背压的模型中对比。

Reprioritization(1)
[Hires]  > Developers @ 2
[Ideas]  > Projects   @ Developers - Started
Projects > Started   @ Developers - (2 * Started)
Started  > Finished   @ Developers - Started - Reprioritization

重排优先级的速率相同，但结果却大不相同。

之前我们在 100 轮中完成了 2520 个任务，加上这个重排优先级速率后，我们只能完成 2485 个，但仍然非常接近。

把这两个模型放在一起看会发现，重排优先级在执行资源严重受限的情况下代价非常高昂，但在我们已经能完成大量工作的场景下，代价则相对较小。

模型终归只是模型，它们只会告诉我们我们问它们的问题。但对我来说，这又一次证明了模型能够把人们的直觉从阴影中拉到台前，并促成一场丰富的对话。
