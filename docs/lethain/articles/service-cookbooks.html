服务手册。

2018-07-15 · 阅读原文

项目选择非常类似于优化系统性能：如果你不进行度量，就可能会去修复错误的问题。如果你的团队正深陷事务无法自拔，想要突围而出，第一件事就是建立分析机制来了解团队的时间都花在了哪里。

大多数跟踪时间分配的方法都需要团队投入大量时间来记录任务，这在一定程度上违背了节省他们时间的初衷。我发现一种非常有效的方法，既不需要团队对现有工作流程进行重大改动，又能达到目的，那就是创建一个简单的内部网站，其中包含你们团队的服务手册。

这本手册列出了团队负责的每一项任务或服务，可以提供文档说明，并收集每个任务所需的字段，从而减少询问者和被询问者之间因为信息缺失而产生的反复沟通。每一种请求都可以被埋点，以统计收到的请求数量，同时它也是一个自动化切入点，你可以逐步将每个任务的表单从提交工单转变为立即执行所请求的操作。

服务手册可能是我发现的在降低熵值方面影响最大的单一工具，因为它可以实现以下几点：

对所有传入请求进行分析，从而让你能够优先选择自动化项目。减少每个请求的来回沟通，进而减少并发请求，并最大化用于解决问题的时间。将所有请求都记录在案，迫使你在早期就进行棘手的权责讨论。一旦工程师习惯于来到你的手册提交请求，你就可以直接在那里嵌入自动化逻辑，完全将自己从循环中移除，甚至不需要让他们学习新的操作方式。

另一个好处是，你可以从将一个 JSON 或 YAML 文件编译成一个简单的 Bootstrap 网站开始，所以这是一个周末就能完成的事情。

总的来说，服务手册的概念很好地体现了如何设计能够在多代实现中持续可用的接口：对你自己来说简单，对用户来说简单，对所有人都有利。

这篇文章最初是 超级增长时代的生产力 中的一个章节，但它始终不太契合，所以我把它独立成篇。
