服务手册。

2018-07-15 · 阅读原文

项目选择非常类似于优化系统性能：如果你不进行测量，就会把精力花在错误的事情上。 如果你的团队已经深陷泥潭，正努力自救，第一步就是建立分析系统，搞清楚团队的时间都花在了哪里。

大多数跟踪时间分配的方法都需要团队投入大量时间来记录任务，这在一定程度上违背了节省时间的初衷。我发现一种效果很好的方法，既不需要团队大幅改变工作流程，也能达到目的，那就是创建一个简单的内部网站，里面放上你们团队的服务手册。

这本手册会列出团队负责的所有任务和可提供的服务，同时提供文档说明，并收集每个任务所需的字段，从而减少询问者和被询问者之间因为信息缺失而产生的反复沟通。每一种请求都可以被埋点统计，了解有多少流入请求，同时这也是自动化的切入点——你可以逐步把每个任务的表单从“提交工单”升级为“立即执行请求的操作”。

服务手册大概是我发现的、降低团队熵值效果最显著的工具，因为它能够：

  1. Analytics on all incoming requests, which allow you to prioritize automation projects.
  2. Reduces back-and-forth on each request, which reduces concurrent requests and maximizes time spent solving problems.
  3. Documents all your requests, forcing you to have messy ownership discussions early.
  4. Once engineers are used to coming to your cookbook to file requests, you can simply drop in automation there to fully cut yourself out of the loop, without even needing to have them learn a new behavior.

另一个好处是，你可以从最简单的形式开始——把一个 JSON 或 YAML 文件编译成一个 Bootstrap 网站，所以这是一件周末就能搞定的事情。

总的来说，服务手册的概念很好地体现了如何设计在多代实现中始终好用的接口：对你自己简单，对用户简单，对所有人都有益。
