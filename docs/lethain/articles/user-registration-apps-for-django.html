Django 用户注册应用

2008-10-25 · 阅读原文

许多 Web 应用的重要组成部分，是在无状态的 HTTP 协议之上营造出“有状态”的假象。虽然有一些比较幼稚的方法几乎能实现这一点（比如假设相同 IP 地址的就是同一个人等等），但归根结底，只有一个方案真正可靠：Cookie。

对很多应用来说，仅依靠基于 Cookie 的身份识别就已足够1，但也有不少场景下，用户会输入重要或私密的数据，我们需要在允许他们访问应用及其数据之前先完成用户认证。

随着 Django 框架的发展，可插拔的用户注册生态也逐渐壮大。这些注册应用都与 Django 的 auth 和 sessions 模块紧密集成，虽然它们功能上有不少重叠，但为你的应用选择最合适的一个，能让开发工作变得轻松许多。

自己实现注册系统

对于第一次使用 Django 的开发者，他们很可能直接基于 Django auth 模块自己实现一套用户注册功能。这种做法本身并没有太大问题，但它违背了“不要重复造轮子”（Don't Repeat Yourself）的原则，而且最终得到的方案通常功能不够丰富，测试也不如现成的可插拔后端充分。

如果你想在用户注册上做一些创新的事情，那么自己实现可能是唯一的选择。但通常情况下，只有当现有注册系统无法满足你的特定需求（且自己去给它们打补丁又不划算）时，才应该考虑从零开始搭建注册系统。

django-registration

Django 可插拔注册方案中的金标准是 django-registration 这个应用。 （如果你不同意，不妨搜索一下“django registration”试试 ;)） django-registration 实现了一个非常标准的注册流程：注册账户 → 通过邮件激活账户 → 登录。

对大多数网站来说，直接集成 django-registration 是实现注册功能最简单、最完整的方式。它唯一开箱不支持的功能是 OpenID 认证。

当然也可以将 OpenID 支持集成到 django-registration 中，这是一个合理的方案，只是需要花费一些精力2。

django-openid

如果你希望网站支持 OpenID，那么 django-openid 就是你的“罗马”。或者至少，它是你构建“罗马”的基础。django-openid 与 Django auth 模块非常相似。它提供了通过 OpenID 进行用户认证的基础支持，但你仍然需要编写一些自定义代码才能将其集成到自己的应用中。

如果你只关心支持 OpenID，那么这可能是你最想使用的方案。如果你非常坚持要用 django-registration，同时又需要 OpenID 支持，那么这个工具同样是你需要的。

django-authopenid

我要介绍的最后一个注册方案是 django-authopenid。它同时提供了 OpenID 和传统认证的插件支持，因此非常有吸引力。最近我开始在自己的项目中使用 django-authopenid，并且强烈推荐它。

话虽如此，它不像 django-registration 那样精致。虽然它可以直接即插即用，但你几乎肯定需要为自己的项目重写它的模板（特别是我觉得 fieldset 元素在跨浏览器体验上不够一致）。此外，它不像 django-registration 那样要求用户通过验证邮件确认邮箱，这可能是你认为很重要的一个特性。

尽管它有一些粗糙的地方，但它开箱即提供了账户管理功能，支持将 OpenID 登录与现有账户关联，或为 OpenID 登录创建新账户。如果你愿意针对自己的需求稍作调整，它是一个非常优秀的工具。
