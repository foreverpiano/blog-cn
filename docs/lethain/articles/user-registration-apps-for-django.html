Django 用户注册应用

2008-10-25 · 阅读原文

许多 Web 应用的重要组成部分，是在无状态的 HTTP 协议之上创建一种“有状态”的假象。虽然有一些幼稚的方法几乎能奏效（比如假设相同 IP 地址的人就是同一个人等），但归根结底只有一个解决方案足够可靠：cookie。

对于许多应用来说，仅依靠基于 cookie 的身份识别就足够了，但也有很多场景下用户会输入重要或私密数据，我们需要在允许他们访问应用及其数据之前对用户进行认证。

随着 Django 框架的发展，可插拔的用户注册生态也在不断壮大。这些注册应用都与 Django 的 auth 和 sessions 模块紧密结合，虽然它们之间存在许多重叠，但为你的应用选择最合适的那一个，能让开发工作变得轻松许多。

自己实现注册系统

对于第一次使用 Django 的开发者来说，他们很可能基于 Django auth 模块自己实现一套用户注册功能。这种做法本身并没有太大问题，但它违背了“不要重复造轮子”（DRY）的原则，而且最终得到的方案通常功能不够丰富，测试覆盖度也低于那些现成的可插拔后端。

如果你正在尝试一些用户注册领域的新颖做法，那么自己实现可能是唯一的选择。但通常情况下，只有当现有注册系统无法满足某个需求，且为其打补丁又不可取时，才应该考虑自己开发注册系统。

django-registration

Django 可插拔注册方案中的黄金标准是 django-registration。（如果你不同意，不妨搜索一下“django registration”看看。😉）它对一种非常标准的注册流程提供了极为稳固的实现：注册账户 → 通过邮件激活账户 → 登录。

对于多数网站来说，直接集成 django-registration 是实现注册功能最简单、最完整的方式。它唯一开箱不支持的功能是 OpenID 认证。

将 OpenID 支持集成到 django-registration 当然是可行的，也是一个合理的解决方案，只是需要花费一些精力。

django-openid

如果你希望网站支持 OpenID，那么 django-openid 就是你的“罗马”。或者至少，它是构建你“罗马”的基础。django-openid 与 Django auth 模块非常相似。它提供了通过 OpenID 进行用户认证的基础支持，但你还是需要编写一些定制代码才能将其集成到自己的应用中。

如果你只关心支持 OpenID，那么这可能是你想要使用的方案。如果你非常坚持使用 django-registration 但仍想加入 OpenID 支持，那么这个工具同样是你需要的。

django-authopenid

最后一个我要提到的注册方案是 django-authopenid。它同时为 OpenID 和传统认证提供插件支持，因此非常具有吸引力。最近我开始在自己的项目中使用 django-authopenid，它也得到了我由衷的推荐。

话虽如此，它没有 django-registration 那么精致。虽然它可以开箱即用，但你几乎肯定需要为自己的需求重写它的模板（特别是我认为 fieldset 元素无法提供一致的跨浏览器体验）。此外，它不像 django-registration 那样要求用户通过验证邮件确认邮箱，这可能是你认为重要的一个特性。

尽管存在这些粗糙之处，它还是开箱提供了账户管理功能，支持将 OpenID 登录关联到现有账户，或为 OpenID 登录创建新账户。如果你愿意为自己的需求稍作调整，它是一个非常优秀的工具。

还有其他值得一提的可插拔注册应用吗？

  1. I think that we've begun to see gradual improvement in this respect. More and more web applications are acknowledging the poor user interface created by mandating using registration and login, and are attempting to minimize or avoid registration/login completely. I hope the trend continues, but I'm even more hopeful we can find a compromise that allows a good user experience and still allows sites to perform some meaningful identity authentication.↩
  2. The whole OpenID can of words is both befuddling and bewildering. When Stackoverflow went live and became one of the few sites to only support OpenID, it was impressive to see a vocal minority of professional developers who were upset about having to use OpenID. This is scary, because professional developers are likely the group with the highest penetration of OpenID awareness. (Compared to Yahoo's research on OpenID awareness for the public, which essentially revealed that very few people have a clue what OpenID is.On the other side, there are OpenID fanatics who get equally upset about sites which require yet another login. If you can only support OpenID or non-OpenID, then clearly supporting OpenID is a suicidal choice unless your userbase is developers, and possibly a bad choice no matter what.For the time being, supporting both OpenID and traditional registration seems like the appropriate decision. However, as additional OpenID-like services sprout up, it'll further balkanize universal login services, and it'll become increasingly awkward to support all of them. It'll be an interesting area to watch.↩
