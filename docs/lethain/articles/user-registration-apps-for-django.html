Django 用户注册应用

2008-10-25 · 阅读原文

许多 Web 应用的重要组成部分，是在无状态的 HTTP 协议之上创建一种“有状态”的假象。虽然有一些幼稚的方法几乎能奏效（比如假设相同 IP 地址的人就是同一个人等），但归根结底只有一个解决方案足够可靠：cookie。

对于许多应用来说，仅依靠基于 cookie 的身份识别就足够了，但也有很多场景下用户会输入重要或私密数据，我们需要在允许他们访问应用及其数据之前对用户进行认证。

随着 Django 框架的发展，可插拔的用户注册生态也在不断壮大。这些注册应用都与 Django 的 auth 和 sessions 模块紧密结合，虽然它们之间存在许多重叠，但为你的应用选择最合适的那一个，能让开发工作变得轻松许多。

自己实现注册系统

对于第一次使用 Django 的开发者来说，他们很可能基于 Django auth 模块自己实现一套用户注册功能。这种做法本身并没有太大问题，但它违背了“不要重复造轮子”（DRY）的原则，而且最终得到的方案通常功能不够丰富，测试覆盖度也低于那些现成的可插拔后端。

如果你正在尝试一些用户注册领域的新颖做法，那么自己实现可能是唯一的选择。但通常情况下，只有当现有注册系统无法满足某个需求，且为其打补丁又不可取时，才应该考虑自己开发注册系统。

django-registration

Django 可插拔注册方案中的黄金标准是 django-registration。（如果你不同意，不妨搜索一下“django registration”看看。😉）它对一种非常标准的注册流程提供了极为稳固的实现：注册账户 → 通过邮件激活账户 → 登录。

对于多数网站来说，直接集成 django-registration 是实现注册功能最简单、最完整的方式。它唯一开箱不支持的功能是 OpenID 认证。

将 OpenID 支持集成到 django-registration 当然是可行的，也是一个合理的解决方案，只是需要花费一些精力。

django-openid

如果你希望网站支持 OpenID，那么 django-openid 就是你的“罗马”。或者至少，它是构建你“罗马”的基础。django-openid 与 Django auth 模块非常相似。它提供了通过 OpenID 进行用户认证的基础支持，但你还是需要编写一些定制代码才能将其集成到自己的应用中。

如果你只关心支持 OpenID，那么这可能是你想要使用的方案。如果你非常坚持使用 django-registration 但仍想加入 OpenID 支持，那么这个工具同样是你需要的。

django-authopenid

最后一个我要提到的注册方案是 django-authopenid。它同时为 OpenID 和传统认证提供插件支持，因此非常具有吸引力。最近我开始在自己的项目中使用 django-authopenid，它也得到了我由衷的推荐。

话虽如此，它没有 django-registration 那么精致。虽然它可以开箱即用，但你几乎肯定需要为自己的需求重写它的模板（特别是我认为 fieldset 元素无法提供一致的跨浏览器体验）。此外，它不像 django-registration 那样要求用户通过验证邮件确认邮箱，这可能是你认为重要的一个特性。

尽管存在这些粗糙之处，它还是开箱提供了账户管理功能，支持将 OpenID 登录关联到现有账户，或为 OpenID 登录创建新账户。如果你愿意为自己的需求稍作调整，它是一个非常优秀的工具。

还有其他值得一提的可插拔注册应用吗？

我觉得我们已经开始看到这方面的逐步改善。越来越多的 Web 应用认识到强制用户注册和登录所带来的糟糕用户体验，并试图最小化甚至完全避免注册/登录流程。我希望这个趋势能继续下去，但更希望我们能找到一种折中方案，既能提供良好的用户体验，又能让网站进行有意义的身份认证。 关于 OpenID 的整个话题既让人困惑又令人费解。当 Stack Overflow 上线并成为少数只支持 OpenID 的网站之一时，看到有一小群专业开发者对必须使用 OpenID 表示不满，令人印象深刻。这很可怕，因为专业开发者应该是 OpenID 认知度最高的群体。（相比之下，Yahoo 对普通公众的 OpenID 认知度调查显示，基本上没多少人知道 OpenID 是什么。） 另一方面，也有一些 OpenID 的狂热拥护者，他们对那些要求再创建一个登录账户的网站同样感到不满。如果你只能二选一，那么显然支持 OpenID 是一个自杀式的选择——除非你的用户群是开发者，而且可能不管怎样都是个糟糕的选择。 目前看来，同时支持 OpenID 和传统注册似乎是恰当的决定。然而，随着更多类似 OpenID 的服务出现，它将会进一步割裂通用登录服务，支持所有这些服务也会变得越来越 awkward。这将是一个值得持续关注的领域。
