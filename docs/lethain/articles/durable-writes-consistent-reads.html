持久化写入与一致性读取

2009-11-30 · 阅读原文

在用极简方式实现了一个键值存储之后，是时候朝着 Dynamo 的目标迈出前两步改进：实现持久化写入（Durable Writes）和一致性读取（Consistent Reads）。

W、R 和 N

在我们最初的实现中，收到更新请求后会立即通知客户端操作成功，并没有确认更新是否真正写入了远程节点。

这种方式虽然实现简单，但并不可靠，因为它假设写入一定成功。可能是其他进程已经宕机，但我们仍然会忠实地告知客户端他们的修改已被成功记录。

为了解决这个缺陷，我们将把读写操作改为“一阶段提交”（one-phase commit），而不是目前这种“零阶段提交”（zero phase commit，又称盲目发射）。在收到客户端的写请求后，接收节点会等待参与写入的节点返回成功确认，然后再响应客户端。

然而，一旦决定采用更复杂的提交协议，就会出现几个问题：

既然我们需要在告知客户端写入成功前进行等待，那么到底应该等待多少个节点呢？同样地，当读取数据时，我们应该查询多少个节点后再将结果返回给客户端？

Dynamo 并没有给出固定答案，而是将这两个值（以及第三个值——数据复制的节点数）设计成可配置的，从而使每个 Dynamo 集群都能根据使用者的需求进行高度定制。

这几个可配置的值分别是：

N 表示每份数据要复制到的节点数量（在我们当前的实现中，N 等于系统中的节点总数）。W 表示在通知用户写入成功前，必须完成写入的节点数（我们的实现目前是 W := N，某种程度上是这样）。R 表示读取一个 key 时需要咨询的节点数（当前实现中 R := 1）。

将这些值以不同方式组合，可以产生性质截然不同的数据存储系统。采用 W := N、R := 1 的系统会在通知用户成功前向所有节点写入数据，这是一个写入可用性较低的系统——单个节点宕机就会阻止后续写入。但由于它能保证更新被写入所有节点，所以只需从单个节点读取就能拿到最新值，因此读取可用性非常高。

另一个极端是 W := 1、R := N 的系统，它的写入可用性很高，但读取可用性很低。如果绝不能拒绝写入请求，那么这种低效的读取可能是可以接受的。

对大多数用户来说，W 和 R 的取值会介于 1 和 N 之间。根据 Dynamo 论文，Amazon 发现对大多数应用而言，N := 3、W := 2、R := 2 是一个性能和可靠性之间较为合理的折衷。

现在让我们来看看如何扩展键值存储，使其能够支持可配置的 W 和 R 值（N 的处理我们稍后再说）。

使用 record 的理由是，你只需要取出需要的数据，而不用去处理那些用不到的值。当 record 的元数从 1 增加到 3、从 3 增加到 6 乃至更多时，这一点会变得特别有意义。当然，最终这也是一个风格问题。

现在我们已经更新了函数定义，接下来该修改 receive 代码块了。我们将分别讨论 set、update 和 updated 消息，但请记住它们都是针对 store/1 邮箱的模式匹配。

set、update 与 updated

接收到 set 模式的消息是更新流程的起点，因此我们从这里开始。

之前 set 会把更新后的键值对广播给所有节点，然后立即通知用户写入成功。现在我们将记录来自写入节点的 ack 数量，等它超过 W 阈值后再通知用户写入成功。

经过这些修改后，所有节点都会在 pending_writes 中维护一个属性列表，里面存放所有已发起但尚未达到 W 阈值的持久化写操作。pending_writes 的 key 是由客户端进程 ID（即调用 kvs:set/2 的 pid）和被更新的 key 组成的二元组；value 则是计数器，表示还需要多少个额外确认才能超过写入阈值。

当节点收到 update 消息时，会通知最初接收 set 消息的那个节点，说自己已经成功更新了该 key 的值。

当其他节点确认写入成功后，对应的写入计数器会递减。一旦计数器减到 0，就会通知 Client pid 写入已持久化成功，并将该写操作从 pending_writes 列表中删除。后续再收到的关于该更新的确认将被忽略。

一致性读取（Consistent Reads）

实现一致性读取的模式与持久化写入类似，但增加了协调不一致读结果的复杂度（比如一个节点返回 5，另一个节点返回 16，该怎么办）。

首先我们实现读请求扇出（read fanout），它会将读请求发送给其他节点，然后把这次读操作加入 pending_reads。

接着是把本地该 key 的值发回给最初收到 get 消息的节点。

最后是处理 pending_reads 中计数器递减，以及通过 retrieve 消息收集各节点返回值的逻辑。

注意，我们目前使用的是一个非常简陋的算法来解决不一致读：选择出现次数最多的值（如果有多个值出现次数相同，则根据读节点响应的先后顺序间接选择一个）。如果我们暂时能忍受这个不太优雅的做法，那么下一篇将会探讨如何利用各种时钟来大幅提升读一致性。

失败的读写操作

除了解决不一致的算法比较弱之外，我们当前实现另一个不足之处是对失败或无法完成的读写操作的处理。

假设一个系统设置 W := 10，但由于节点故障当前只有 5 个可用节点。这时写入计数器永远不会归零，因此用户永远得不到响应，这显然不是一个可用的系统。

一个合理的解决方案是：将所有超过一定超时时间的待处理操作视为失败，并通知用户该读/写操作失败。
