YUI 对话框、IE z-index 与惨痛教训

2009-06-16 · 阅读原文

虽然我目前在工作中做了大量的前端开发，但从未真正将自己视为一名前端工程师。这 partly 是出于一点自负，但更重要的是，我仍在为真正配得上这个头衔而付出必要的努力。这是一个关于“交学费”的故事。

在工作中，我正在处理一个大型应用的多浏览器兼容阶段，刚刚确保 Firefox 和 Safari 都能正常运行，接下来就轮到 IE7 了。我启动 VirtualBox，选了一个装有 IE7 的 Windows XP 镜像，然后就迎头撞上了 IE z-index bug 这堵著名的砖墙。

但不幸的是，Internet Explorer 并不尊重 z-index 值，因此你会遇到各种尴尬的情况。我遇到的尴尬情况就是：我的模态 YUI Dialog 不再按预期渲染了。

相反，对话框被渲染到了其 underlay 的下方，导致文字难以阅读，也无法与之交互。

在 IE6 上情况更加惨烈，由于透明度 workaround 的影响，underlay 变成了纯黑色，于是使用对话框时整个屏幕都会变黑（除非页面里有个 <input> 标签，那就会变成被另一个 z-index bug 打断的黑色）。

在确认所有功能（哈哈……）都正常之后，我就去忙其他事情了。也许是在处理像癌细胞扩散一样越来越多的 bug 单，也可能是在吃晚饭，咱们别纠结这些细节了。

等我回来准备快速跑一遍应用测试时，灾难悄无声息却又确定无疑地发生了。我先把事实告诉你，然后你可以用几分钟时间试着找出问题所在。

首先让我描述一下出现 bug 的系统：

某个页面上有一个表单，包含两个输入框：一个是面向用户的 primary key，另一个用于存储 JSON blob。该 blob 在页面加载时由后端填充。当用户点击页面的“保存”按钮时，UI 的状态会被重新序列化成这个 JSON blob。这个页面中有一系列规则，可以有零条或多条。每条规则包含类型、key、value 以及零个或多个条件。你可以在弹出的对话框中创建新规则。在创建新规则时也可以创建新的条件。点击“添加规则”后，该规则会显示在主页面上。主页面上的规则可以通过“删除”按钮移除，也可以通过“编辑”按钮进行修改。存在一个用于编辑规则和创建新规则的弹出容器，删除规则时不会打开它。由于这些操作的复杂性，状态被维护在两个地方：一个包含每条规则信息的 JavaScript 数组。一个编辑界面维护着自己的一份字典，用于描述当前正在编辑的规则的变更，这样用户可以取消对某条规则的修改，或者保存修改并覆盖主规则列表中对应的那一条。点击“保存”时，主规则列表会被序列化为 JSON，注入到一个隐藏的表单输入框中，然后通过 JavaScript 调用表单的 submit 方法以 POST 方式提交。面向用户的 primary key 也包含在该表单中。如果你在访问页面时，GET 或 POST 中都没有这个面向用户的 primary key，那么你会被重定向到应用首页。（没有关联的 primary key 时，这个页面没有意义。）

接下来描述这个 bug。

如果你进入页面，添加一条新规则，然后点击保存，你会被错误地重定向到首页。如果你进入页面后不做任何修改直接点击保存，你会正确地留在当前页面。如果你进入页面，删除一条规则，然后点击保存，你会正确地回到同一页面，且被删除的条目已消失。

我在这个问题上卡了很久，非常久。如果你还没想出来，这里再给一些提示。

如果你进入页面，编辑一条规则，然后保存，你会被错误地重定向到首页。这个问题是在我为修复 IE z-index bug 做出调整之后才出现的。

还是没头绪吗？嘿，我当时也一样。

许多——也许是全部，但我需要进一步确认——YUI 对话框都包含一个 <form> 标签。

然后就是令人悲伤的结局。

我就这么浪费了四个小时的人生。
