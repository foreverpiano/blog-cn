双面 Django 第二部分：模型与 Django 测试

2007-12-04 · 阅读原文

在本教程的[第一部分][partone]中，我们已经搭好了[文件和文件夹结构][polling1]。现在我们要开始构建项目的核心功能和数据。让项目能快速开发、易于测试的关键之一，就是所有的核心功能只实现一次，即使它会被 Facebook 应用和 Web 应用以不同方式使用。在最理想的情况下（也就是我们正在努力实现的目标），我们在 fb 和 web 应用中编写的所有代码，都只是对 core 应用中核心功能的一层简单接口。

好，上一段抛出了很多看似奇怪的概念，现在我们来看看到底是什么意思。

接下来我们要开始编写模型，但首先需要明确这个程序具体要做什么。我说过它是一个投票程序，那么一个简单的投票应用应该具备什么功能呢？

创建投票。对投票进行投票。对参与投票的用户进行管理。如果创建者想要，允许删除投票。

User 类稍微复杂一些，因为我们希望应用不关心当前使用的是哪种界面（本项目中的 web 或 fb 应用）。因此我们有两种方式来标识一个 User：要么通过他们的 Facebook User ID，要么通过 django.contrib.auth.models.User 的实例。

提问时间：我们真的需要区分 Facebook 用户和 Web 应用用户吗？

是的，很遗憾，我们必须区分。当我们与 Facebook 用户交互时，实际上是通过一个中间人（Facebook）来进行沟通，没有直接连接，因此无法通过 cookie 来识别用户，在处理 Facebook 用户时也无法利用 Django 的 session 或认证框架。

setUp 方法会在 TestCase 中的每个测试方法运行前被调用。因此在每个单元测试（比如上面脚手架中的 test_function）执行之前，setUp 函数都会先运行。同理，每个单元测试结束后，tearDown 也会被调用。

tearDown 方法看起来可能有点多余。为什么我们要这么较真地在每个测试后删除数据库中的所有模型呢？虽然 Django 测试会创建一个专用的测试数据库，但这个数据库是在每次运行测试框架时创建的，而不是在每个单独的单元测试后重新创建。因此我们可能会遇到不确定测试数据库中模型数量和类型的情况。这对测试来说并不理想，所以我更倾向于在每个单元测试后清除测试数据库中之前的所有模型。由于我们使用的是 SQLite，这其实是一个非常快的操作，因为测试数据库是在内存中创建的，读写速度极快（当然持久性也几乎为零）。
