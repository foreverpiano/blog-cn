两面派 Django 第二部分：模型与 Django 测试

2007-12-04 · 阅读原文

在本教程的[第一部分][partone]中，我们已经完成了[文件和文件夹的配置][polling1]。现在我们要开始构建项目的核心功能和数据模型。让项目开发快速且易于测试的关键之一，就是让所有功能只实现一次，即使它会被 Facebook 应用和 Web 应用以不同方式使用。在最理想的情况下——也就是我们正在追求的目标——我们在 fb 和 web 应用中编写的所有代码，都只是对 core 应用中核心功能的一层简单接口。

好了，上一段抛出了不少看起来有点傻的概念，现在让我们来看看我具体在说什么。

将功能映射到模型上

我们打算开始编写模型，但首先需要明确程序实际要实现什么功能。我说过它是一个投票程序，那么一个简单的投票应用应该做什么呢？

  1. Make polls.
  2. Vote on polls.
  3. Make users who vote on polls.
  4. Delete polls if their creator wants to.

听起来够简单了。让我们来创建一些能够处理这些功能的模型：

from django.db import models
from django.contrib.auth.models import User as DjangoUser
class Poll(models.Model):
question = models.CharField(unique=True, max_length=200)
creator = models.ForeignKey('User')
up_votes = models.IntegerField()
down_votes = models.IntegerField()
class User(models.Model):
user = models.ForeignKey(DjangoUser, blank=True, null=True)
facebook_id = models.IntegerField(blank=True, null=True)
name = models.CharField(max_length=200)

查看我们的 Poll 类可以发现，我们将记录问题（question）、创建该 Poll 的 User，以及它收到的赞成票（up_vote）和反对票（down_vote）数量。

User 类稍微复杂一些，因为我们希望应用不感知当前使用的是哪种界面（项目中的 web 还是 fb 应用）。因此我们有两种识别用户的方式：要么通过他们的 Facebook User ID，要么通过 django.contrib.auth.models.User 的实例。

提问时间：我们真的需要区分 Facebook 用户和 Web 应用用户吗？

是的，很遗憾，我们必须区分。当我们与 Facebook 用户交互时，实际上是通过一个中间人（Facebook）进行交流，我们没有直接连接，因此无法使用 cookie 来识别用户，在处理 Facebook 用户时也无法利用 Django 的 sessions 或 auth 框架。

提问时间结束

好了，我们有了模型，现在让我们进一步完善它们：将其注册到 Django admin，并添加 __unicode__ 方法让 Django 知道如何表示它们。（再加上一些注释，因为我们是专业人士，对吧？）这样我们就得到了：

from django.db import models
from django.contrib.auth.models import User as DjangoUser
class Poll(models.Model):
"""
    Model used for tracking polls and responses to the poll.
    """
question = models.CharField(unique=True, max_length=200)
creator = models.ForeignKey('User')
up_votes = models.IntegerField()
down_votes = models.IntegerField()
class Admin:
pass
def unicode(self):
return "%s asked by %s" % (self.question, self.creator)
class User(models.Model):
"""
    Model used for associating Facebook User IDs or
    django.contrib.auth.models.User instances with
    actions performed on our system.
    Only one of 'user' and 'facebook_id' should have a
    non-null value. Facebook users will not have an
    associated User, and regular web users will not
    have a 'facebook_id'.
    """
user = models.ForeignKey(DjangoUser, blank=True, null=True)
facebook_id = models.IntegerField(blank=True, null=True)
name = models.CharField(max_length=200)
class Admin:
pass
def unicode(self):
return self.name

这就是我们的模型。大家干得漂亮。（请注意，本教程的所有代码可以从[这个 zip 文件][polling2]中下载。）

确保一切都能正常工作

到了这个阶段，比较一般的教程或者读者可能会开始奔向越来越复杂的远方。但我们不会，亲爱的读者，我们不会。我们要停下来，好好看看 Django 的测试框架，并“利用”它来……

我到底在说什么。咱们要写一些测试。

在 Django 测试框架中，与特定应用相关的测试放在该应用的文件夹中，文件名为 tests.py。让我们来创建它（从我们的 polling 项目文件夹开始）：

emacs core/tests.py

现在我们在 tests.py 中加入一些基本框架：

from django.utils import simplejson
from polling.core.models import Poll, User
MODELS = [Poll, User]
class CoreModelTest(unittest.TestCase):
"Test the models contained in the 'core' app."
def setUp(self):
'Populate test database with model instances.'
self.client = Client()
def tearDown(self):
'Depopulate created model instances from test database.'
for model in MODELS:
for obj in model.objects.all():
obj.delete()
def test_something(self):
"This is a test for something."
self.assertEquals(True, 1)

setUp 方法会在 TestCase 中的每个测试方法运行前被调用。因此在每个单元测试（如上面框架中的 test_function）之前，setUp 函数都会执行。同样，在每个单元测试之后，tearDown 也会被调用。

tearDown 方法看起来可能有点多余。为什么我们要这么执着地在每次测试后删除数据库中的所有模型？这是因为虽然 Django 测试会创建一个测试数据库，但它是在每次运行测试框架时创建的，而不是在每个单独的单元测试后重新创建。因此我们可能会遇到不确定测试数据库中模型数量和类型的情况。这对测试非常不利，所以我更喜欢在每个单元测试后清除测试数据库中的所有旧模型。由于我们使用的是 SQLite，这实际上是一个非常快的操作，因为测试数据库是在内存中创建的，访问速度极快（当然持久化能力也几乎为零）。

现在让我们运行这个测试框架。

好的。现在我们已经搭好了测试框架，接下来写一个更好的 setUp 方法，让它真正往测试数据库中填充一些数据。

用下面的代码替换原来的 setUp 方法：

def setUp(self):

现在让我们运行测试，确保 setUp 函数能正常工作。

python manage.py test

好吧，结果并不如人意。它应该抛出类似这样的错误：

IntegrityError: core_poll.up_votes may not be NULL

哎呀。我们需要在 Poll 模型的 *up_vote 和 down_vote* 字段中初始化一个值！写测试的好处之一就是它会迫使我们搞清楚自己在做什么，而且越早越好。这是一件好事。

快速修复 Poll 模型

为了给 Poll 中的两个字段初始化值，我们要重写 save 方法。这是一个很实用的技巧，因为它允许你在创建对象时动态确定数值，也可以对传入的值进行清理。（值得指出的是，在这个特定场景下，更合适的方式是给字段使用 default 参数，比如 “up_vote = IntegerField(default=0)”，但那样我们就错过了观察重写 save 这个常用技巧的机会。）

因此，在 polling/core/models.py 中 Poll 类的 __unicode__ 方法之前，插入以下代码：

def save(self):
    """Overriding save() to innitialize values for up_votes and down_votes."""
    if not self.up_votes:
        self.up_votes = 0
    if not self.down_votes:
        self.down_votes = 0
    return super(Poll, self).save()

阅读这段代码，如果我们在创建 Poll 实例时没有指定 *up_vote 或 down_vote* 字段的值，那么 save 方法会在调用默认的模型保存方法（model 是 Poll 的父类）之前帮我们设置它们。

保存 polling/core/models.py 文件，然后重新运行测试。

python manage.py test

然后，一切又正常工作了。

继续代码-测试的循环

好了，在本教程的第二部分，我们还剩下两个简短的“实现-测试”循环。我保证很快就可以休息了。

首先我想为 Poll 添加几个好用的方法，用于给投票加赞成票或反对票，同时还有一个计算当前总得分的函数。它们看起来会是这样的：

def score(self):
    return self.up_votes - self.down_votes
def up(self):
self.up_votes = self.up_votes + 1
self.save()
def down(self):
self.down_votes = self.down_votes + 1
self.save()

现在让我们写一些测试来确保它们能正常工作。重新打开 polling/core/tests.py：

    def test_poll(self):
        "This is a test for something."
        poll = Poll.objects.get(pk=1)
        up = poll.up_votes
        down = poll.down_votes
        self.assertEquals(up, poll.up_votes)
        self.assertEquals(down, poll.up_votes)
        self.assertEquals(up-down, poll.score())
        poll.up()
        up = up + 1
        self.assertEquals(up, poll.up_votes)
        poll.down()
        down = down + 1
        self.assertEquals(down, poll.down_votes)
        self.assertEquals(up-down, poll.score())

这应该是 CoreModelTest 类的一个方法。我们获取一个已经在 *setUp 方法中创建的 poll*，然后获取它初始的 up_votes 和 down_votes 值。接着进行一些合理性检查，然后调用 up、down 和 score 方法，并验证它们是否返回了我们期望的值。

现在运行测试看看结果：

python manage.py test

它们都通过了。非常好。

最后一个快速循环

好的，现在我们想给 User 类添加一点功能，以方便创建 Poll 实例。我们要创建一个 create_poll 方法，它会创建一个新的 Poll 实例，且该实例的创建者就是调用此方法的 User 实例。它看起来会是这样：

def create_poll(self, question):
    p = Poll(creator=self, question=question)
    p.save()
    return p

以及一个确保它能正常工作的测试：

def test_user(self):
    "This is a test for the polling.core.model.User model."
    user = User.objects.get(pk=1)
    p = user.create_poll("Is this actually working?")
    self.assertEquals(user, p.creator)

python manage.py test
