反对象与反射式决策（转载）

2007-06-07 · 阅读原文

这是从最初的《Irrational Exuberance》移植过来的文章，写于2007年年中：距今已近两年。

在这个时代学习编程，基本上就是彻底接受面向对象思想的灌输（除非你是从 PERL、Scheme 或 Haskell 开始的，但我们这里讨论的是普通人）。我在大学里学到的第一个——也是唯一一个——编程范式就是 OO，很容易理解为什么——如果你只能投入资源把一种范式教好——那肯定会教 OO。它擅长创建大型项目所需的多层抽象，也便于将代码分割成不同部分，让相对独立的团队可以分别实现（只要他们遵守事先约定的 API……哈哈……我当初应该去当诗人）。如果我们观察 OO 的潮流，有一种语言比其他任何语言都更猛烈地乘着这波浪潮前进：Java。诚然，Java 是 C++、垃圾回收、面向对象和平庸这四者四重奏的产物，但近年来几乎没有哪门语言不是对面向对象充满热忱的。Python 几乎完全是面向对象的（深入底层会遇到一些奇怪的实现细节），Ruby 是彻底面向对象的，Smalltalk（OO 之父）启发了 Objective C……很难找到任何用于开发大型项目的语言没有把 OO 作为首选范式。<!--more-->

背景说明

谁来做什么？

class Player
  attr :name, :objects
  def initialize(name)
    @name = name
    @objects = []
    @body = {"wielded" =&gt; nil, "torso" =&gt; nil}
  end
  def get(item)
    @objects << item
  end
  def wield(item)
    if @objects.index(item) and item.can?("wield")
      @body["wielded"] = item
    else      raise "Cannot wield #item}"
    end
  end
  def wear(item)
    if @objects.index(item) and item.can?("wear")
      wear_location = item.attributes["wear location"]
      @body[wear_location] = item
    else
      raise "Cannot wear #{item}"
    end
  end
end
class Item
attr_reader :name, :attributes
def initialize(name)
@name = name
@attributes = {"wear" =&gt; true}
end
def can?(action)
@attributes[action]
end
end
class Weapon < Item
def initialize(name)
super(name)
@attributes["wield"] = true
end
end
class Armor < Item
def initialize(name)
super(name)
@attributes["wear"] = true
end
end
class ChestArmor < Armor
def initialize(name)
super(name)
@attributes["wear location"] = "chest"
end
end
class LegArmor < Armor
def initialize(name)
super(name)
@attributes["wear location"] = "leg"
end
end

然而，当我坐下来考虑要用这种方式再实现几百个方法时，我意识到这是一种过于复杂的方法。当然，它完全符合直觉，但其乐趣程度大概和第五次重读《基地序曲》差不多。更糟糕的是，今后修改会非常痛苦，因为行为和行为所作用的数据被分开存放了。大约就在这个时候，那篇关于反对象的文章浮现在我脑海中，我决定尝试一种不同的实现方式。我决定把作用于物品的方法放在物品自己内部：我要看看如果把所有复杂性都移到物品内部，情况会如何。下面是我用这种方法实现的代码：

class Player
  attr :name, :inventory, :body
  def initialize(name)
    @name = name
    @inventory = []
    @body = {
      "wielded" => nil, 
      "torso" => nil,
      "legs" =>; nil
     }
  end
end
class Item
attr_reader :name
def initialize(name)
@name = name
end
def get(actor)
actor.inventory < self
end
end
class Weapon < Item
def wield(actor)
actor.body["wielded"] = self
end
end
class ChestArmor < Item
def wear(actor)
actor.body["torso"] = self
end
end
class LegArmor < Item
def wear(actor)
actor.body["legs"] = self
end
end

与之前的实现相比，这一版有若干好处：我们现在把某件物品是否可穿戴/可装备/可拾取，以及如何穿戴/装备/拾取的逻辑都放在同一个地方。这意味着修改时只需查看一处代码，而不必像之前那样查看两处。它还让我们能够利用多态（ChestArmor 和 LegArmor 对同名方法的响应各不相同）。此外，默认的物品初始化对所有子类都足够了，因为关于对象的其他所有数据都保存在其方法之中（很 Lispy 的感觉）。不用再串起一堆 super 调用，在我看来已是愉快的改进（随机问题：你觉得如果类层次足够深，会不会撑爆 Ruby 的调用栈？我想是会的）。我对第二种设计有一些顾虑，它似乎过于依赖 Player 类的具体实现；我内心的 Java 程序员很想构建一个庞大的 API 来彻底封装实现细节。而我稍稍更理智的那一半则认为保持现状更简洁。如果有必要，我可以通过在要替换 @body 哈希的任何数据结构之上创建一个类似哈希映射的 API 来修改实现。虽然我不是那种把代码行数当作质量标准的人，但第二版只有 41 行，而第一版有 68 行（不过我显然也是那种既要吃蛋糕又要留着蛋糕的人）。除了更短以外，它给我的感觉也更简单、更易于理解（没有流程控制，也不需要显式抛出任何异常，我们只需利用 Ruby 的反射能力去询问 item.respond_to?(“wield”)，如果物品没有对应玩家指令的方法，就返回一条简单的错误信息给玩家）。
