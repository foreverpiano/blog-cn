制定策略的政策。

2025-03-13 · 阅读原文

本书的引言以将策略定义为“做出决策”开始。 随后我们深入探讨了 探索策略空间（探索）、 工程策略中的诊断（诊断）以及 如何有效优化工程策略（完善）。 在这三章中，你可能会认为我们根本没有做出任何决策。 澄清待解决的问题是有效决策的前提，但最终还是必须做出决策。 在本章关于政策的讨论以及 策略的运营机制（下一章关于运作的章节）中，我们终于开始做出一些决策。

在本章中，我们将深入探讨以下内容：

我们如何定义政策，以及制定政策与下一章讨论的运作政策有何不同；制定政策的结构化步骤；你应该制定多少项政策？是制定一项政策、多项政策，还是两者差别不大？策略中经常出现的政策类型；为什么有意关注策略的高度（altitude）很有价值，以及工程师和高管通常如何在他们的策略中保持不同的高度；用于评估你的政策是否可能产生影响的标准；如何制定新颖的政策，以及为什么这种情况很少见；为什么拥有多组备选政策通常是策略制定过程中的一个阶段，这表明你的诊断存在差距；那些忽略约束条件的政策听起来鼓舞人心，但实际成效甚微；如何处理因跨职能利益相关者缺失策略而产生的模糊性和不确定性。

读完本章后，你将能够评估为什么现有策略的政策难以产生影响，并开始为自己的策略迭代制定政策。

这是《Crafting Engineering Strategy》中的一章。

什么是政策？

政策是将你的 工程策略中的诊断（诊断）转化为具体计划的过程。 该计划将是一系列决策、权衡和方法。 它们涵盖从编码实践、招聘要求、架构决策，到组织内如何做出选择的指导。

一项有效的政策应解决策略诊断的全部内容，尽管诊断本身鼓励明确指出哪些方面可以忽略。 例如，在其诊断中承认，他们对预期削减的程度没有明确指导：驾驭私募股权所有权

根据一般做法，我们新的私募股权所有者很可能期望我们通过裁员来降低研发人力成本。然而，我们没有任何具体细节来做出结构化决策，而且我们的方法会根据削减规模而有显著差异。

面对这种不确定性，政策只是承认了这种模糊性，并承诺在获得更多信息时重新考虑：

我们相信新的所有者将在即将到来的财年规划中为研发（R&D）运营费用提供具体目标。一旦我们获得明确目标，我们将再次修订这些政策，并推迟围绕削减的规划，以避免运行两个重叠的流程。

在制定政策时，有两个常见的困惑点值得直接说明：

政策是策略的子集，而非策略的全部，因为政策只有在策略诊断的背景下才有意义。 例如，在 的背景下是有意义的。 该政策在快速扩张的组织中可能效果不佳。任何没有政策的策略都是无用的，但你也会发现，没有上下文的政策同样价值不大。这尤其遗憾，因为策略常常在缺少这些关键部分的情况下被传达。政策描述了应该如何进行权衡，但它并不验证这些权衡在实践中是否真正被执行。 下一章关于运作的内容将介绍如何检查组织的实际行为，以确保政策得到遵守。在将策略 时，将政策和运作部分合并通常是合理的。 然而，在起草策略时，将它们分开很有价值。 是的，你可能会用周会来审查政策是否被遵守，但政策是否有效与是否有这样的会议无关，而且你使用的运作机制会根据你打算实施的政策数量而有所不同。工程组织的资历结构模型驾驭私募股权所有权让工程策略文档更易读

有了这个定义，我们现在可以转向更有趣的讨论：如何制定政策。

如何制定政策

撰写策略的每个部分在进行时都感觉很难，但我个人发现，撰写政策要么感觉不舒服地容易，要么痛苦地具有挑战性，从来没有中间地带。 幸运的是，探索和诊断通常会共同让撰写政策变得简单：尽管有时这个简单的结论可能很难接受。

我撰写策略政策的步骤如下：

回顾诊断，确保它捕捉到了最重要的主题。它不需要完美，但不能有明显到你能立即识别的遗漏。选择能够解决诊断的政策。明确地将每项政策与它所解决的一项或多项诊断进行匹配。持续添加政策，直到所有诊断都被覆盖。这是一条宽泛的指导，但实际上比听起来简单，因为你通常会从 政策中进行选择。不过，当然还有空间对那些政策进行调整，并将熟悉的政策重新应用到新的情境中。如果你确实发现自己在制定一项新颖的政策，本章后面的“Developing novel policies”（制定新颖政策）部分会更详细地讨论这个主题。将重叠或相邻的政策进行合并。例如，关于特定团队的两项政策可以泛化为一项关于整个工程组织的政策。针对你最近做出的决策对政策进行回测。如果你组织中维护了决策日志，这会特别有效。再次挖掘冲突，就像你在制定诊断时所做的那样。重点听取与你观点不同的团队和个人的反馈，但不要完全排除那些你同意的观点。正如如果你不征求反对意见，就很容易在诊断中排挤掉反对观点一样，如果你过于依赖他人的观点，也可能无意中排挤掉自己的观点。如果你写完后仍然不确定你的方法是否可行——没关系！返回到完善阶段，通过部署 来增强你的信心。记住，我们谈论策略时好像它是一次性完成的，但几乎所有真正的策略都需要多次完善迭代。探索策略空间如何有效优化工程策略

撰写政策的步骤相对平淡无奇，主要是因为你在探索、诊断和完善阶段已经做了大量工作。 如果你跳过这些阶段，你可能仍会遵循上述撰写政策的步骤，但政策本身的预期质量会低得多。

应该制定多少项政策？

要全面解决诊断通常很复杂，这就是为什么大多数策略包含一系列政策而非仅一项政策的原因。 并非一项决定不分解的政策，而是一系列四项政策：我们应该分解单体应用吗？

业务单元应始终在自己的代码仓库和单体中运行。跨业务单元单体的新的集成应使用 gRPC。除新的业务单元单体外，我们不允许新的服务。在可能的情况下，将现有服务合并到业务单元单体中。

四也不是 universally 正确的数字。 它只是解决该策略诊断所需的数量。 有了优秀的诊断，你的政策往往会显得不可避免，甚至可能有些乏味。 这很好：一项政策的好坏在于它是否有效，而不在于它是否新颖或鼓舞人心。

政策的类型

虽然你可以撰写的政策有很多，但我发现它们通常可以归为四大类：审批（approvals）、分配（allocations）、方向（direction）和指导（guidance）。本节将介绍这些类别。

审批定义了做出重复决策的流程。 这可能需要调用架构咨询流程，或者需要让高管这样的权威人物参与。

在 中，有许多复杂的决策需要做出，其审批机制是：如何整合 Stripe 收购的 Index？（2018）

升级事项提交给配对领导：鉴于团队之间共享上下文有限，所有升级都必须同时提交给 Stripe 的流量工程主管和 Index 的工程主管。

这让被收购团队和收购团队能够通过确保在任何决策最终确定前双方都参与咨询，从而开始建立彼此之间的信任。 另一方面，的审批策略则更侧重于管理企业风险：我们应该如何控制用户数据的访问权限？

例外必须由 CISO 以书面形式批准。虽然我们的总体工程策略规定我们遵循《Facilitating Software Architecture》中描述的顾问式架构流程，但客户数据访问政策是一个例外，必须由 CISO 明确批准并留下文档记录。从 #ciso 频道开始该流程。

这两种不同的审批流程有不同的目标，因此它们在进行权衡时也不同。有很多方法可以调整审批，从而在安全、生产力和信任之间实现多种不同的权衡。

分配描述了如何在多个潜在投资之间分配资源。 分配是对组织优先级最具体的声明，同时也阐明了组织对团队中生产力如何产生的信念。 有些公司相信，通过将更多人集中到关键问题上来加快速度。 另一些公司则相信，通过迫使团队在没有额外人手的情况下解决问题来加快速度。 两者都可以奏效，并能让你了解公司信念的重要信息。

关于 的策略中有两个具体的分配政策示例。 第一个描述了基础设施工程团队在手动配置任务和投资创建自助配置平台之间的分配：2014 年左右 Uber 的服务迁移策略。

限制手动配置的分配，以最大化对自助配置的投资。服务配置团队将保持固定分配一名全职工程师负责手动服务配置任务。我们将把剩余工程师转移到自动化工作上，以加快未来的服务配置。这将在短期内降低手动配置的质量，但另一种选择是，随着新招聘的产品工程师带来新的服务请求，会永久性地降低配置能力。

第二个分配政策隐含在该策略的诊断中，其中描述了工程组织更高高度策略中的分配政策：

在基础设施工程中，目前有一个由四名工程师组成的团队负责服务配置。虽然我们的组织与产品工程的增长速度相似，但没有将任何新增人力直接分配给负责服务配置的团队。我们预计这种情况不会改变。

分配政策往往能为团队带来惊人的清晰度，我几乎在自己写的每项政策中都会明确或隐含地在更高高度的策略中包含它们。

方向提供关于必须如何做出决策的明确指示。 当你知道自己想去哪里，以及 exactly 想要如何到达那里时，这是合适的工具。 方向适用于你清楚理解的问题，并且你更重视一致性而非赋权个人判断的情况。

当你需要一项不留解释空间的明确政策时，方向效果很好。 例如，：“我们是一家产品工程公司！”——Calm 的工程战略

我们所有代码都在单体中编写。之前对于新代码（尤其是新的应用代码）是应该写在我们的 JavaScript 单体中，还是必须写在单体之外的新服务中，一直存在模糊。现在不再模糊：所有新代码必须写在单体中。如果在极少数情况下存在功能性需求，使得在单体中编写代码不现实，则应按照下面描述的方式寻求例外。

在那种情况下，团队无法就什么应该进入单体达成一致。 个人常常会做出不兼容的决策，因此要创造一致性就需要从等式中移除个人判断。

有时判断力是问题，有时由于激励不一致，一致性也很难实现。 一个很好的例子来自 ：驾驭私募股权所有权

我们将转向“N-1”替补政策，即离职人员将由更低级别的人员替补。我们还将严格规定每个业务单元最多只能有一名首席工程师。

如果这条替补政策表述得更温和，招聘经理很可能就会直接忽略它，尽管有时力度较小的政策也是有用的。

指导提供关于应该如何做出决策的建议。 当存在足够多的细微差别、或复杂性，以至于你能解释期望的目标，但无法强制规定达到目标的路径时，指导就很有用。驾驭模糊性

来自 的一个指导示例是：如何整合 Stripe 收购的 Index？（2018）

最小化对 tokenization 环境的变更：因为销售点设备直接处理客户支付细节，直接支持销售点设备的 API 必须位于我们存储支付细节的安全环境中。然而，任何其他功能都不得添加到我们的 tokenization 环境中。

这读起来可能像方向，但它是在澄清避免 tokenization 环境中出现不必要复杂性的期望结果。 然而，它无法阐明什么是必要的复杂性，因此最终它是指导，因为它需要大量判断力来解释。

另一个指导示例来自 ：我们应该分解单体应用吗？

在可能的情况下，将现有服务合并到业务单元单体中。我们认为，每一个将现有服务移回单体的决定都应该“在细节中”做出，而不是从自上而下的策略角度。因此，我们通常鼓励团队逐步关闭其业务单元单体之外的现有服务，但将最终决定权留给团队，让他们根据本地上下文做出正确选择。

这又是一个知道期望结果，但由于存在太多不确定性而无法指导团队如何到达那里的例子。 如果你问五位工程师是否有可能将某个服务合并回单体代码库，他们很可能意见不一。 这没关系，也凸显了指导的价值：它使得在更具体的方向会导致困惑的领域能够取得渐进式进展。

当你在制定策略的政策部分时，考虑所有这些类别很重要。 哪种最自然适用会根据你的团队和角色而有所不同，但它们都是可用的：

如果你是开发者生产力团队，你可能需要在政策中 heavily 依赖指导，并在平台细节中加强对该指导的支持。如果你是高管，你可能会 heavily 依赖方向。事实上，你可能会过于依赖方向，而在你了解方向但不了解路径的领域，指导往往效果更好。如果你是产品工程组织，你可能需要将方向的范围缩小到该组织内的工程师，以应对复杂的跨组织动态现实。

最后，如果你有一个清晰的方法想采用，但它无法干净地归入这些类别中的任何一个，那就不要让这个框架阻止你。尝试一下，如果最初不奏效就进行调整。

保持策略的高度

那一章介绍了策略高度（strategy altitude）的概念，即有意决定组织内应在什么层级制定某些类型的政策。何时撰写策略，以及写多少？

在不完整重复那一节内容的前提下，当你制定政策时，特别需要考虑你的新政策如何消除组织内的灵活性。 考虑下面两个 somewhat 对立的策略：

仅在强制要求（几乎）所有团队使用单一编程语言的组织中才有效。知道资源分配必须由团队直接管理。如果试图在另一个层级解决问题，最终只会导致有人直接去找团队，重写他们的优先级以纳入新的紧急项目。Stripe 为什么要开发 Sorbet？（~2017）如何在 Calm 为工程驱动的项目分配资源？（2020 年）

Stripe 的组织级政策剥夺了个别团队选择 preferred 技术栈的自由。作为回报，他们解锁了以强大方式集中投资的能力。 Calm 则走向了相反的方向，认识到只有团队才有权管理其路线图的内容；高管虽然更资深，但经常被其他高管的场外指令所推翻。

这两种高度都是合理的。两者都有后果。

有效政策的评估标准

在《The Engineering Executive’s Primer》关于 的那一章中，我介绍了评估政策的三个标准。 它们应该是可应用的（applicable）、可执行的（enforced），并能创造杠杆（create leverage）。简单定义如下：撰写工程战略

可应用：能够用于导航复杂、真实的场景，尤其是在进行权衡时。可执行：团队将被问责是否遵循指导政策。创造杠杆：创造复合或倍增的影响。

这三者中的最后一项“创造杠杆”，在关于工程高管的书中是合理的，但在这里可能没那么合适。 某些政策确实应该创造杠杆（例如 会让其他客户留存机制更有效），但其他政策可能不需要（例如 ）。 在非高管语境下，重要的不一定是创造杠杆，而是一项政策能解决诊断的某一部分。Stripe 应该如何废弃 API？(~2016)驾驭私募股权所有权

这样就剩下另外两项——可应用和可执行——两者对于政策实际解决诊断都是必要的。 任何你无法确定如何应用，或者不愿意执行的政策，都不会有用。

让我们将这些标准应用到一些潜在政策上。 首先考虑我们可能为提升工程团队的人才密度而制定的政策：

“我们只招聘世界一流的工程师。” 这不可应用，因为“世界一流工程师”是什么意思并不清楚。由于这项政策中没有双方都能接受的定义，它也无法被一致地执行。“我们只招聘在记分卡中至少获得一个‘强烈推荐’的工程师。” 这是可应用的，因为有明确的定义。 这是可执行的，取决于组织是否愿意拒绝那些看似优秀但没有获得强烈推荐的候选人。

接下来，考虑一项关于代码库内代码复用的政策：

“我们在代码库中严格遵循 Don’t Repeat Yourself（不要重复自己）政策。” 团队内部对于两段代码是否真正重复可能存在争论，但总体上是可应用的。 因为存在争论的空间，决定如何执行该决策是一个非常依赖上下文的判断。“代码作者负责判断他们的贡献是否违反 Don’t Repeat Yourself，如果违反则进行重写。” 这要可应用得多，因为现在只需要评估一个人的判断。 在某种程度上，这项政策也更易于执行，因为不再存在谁来决定某段代码是否重复的模糊性。 挑战在于，可执行性现在依赖于单个个体，要让这项政策有效，就需要让个人为其判断质量负责。 一个不愿意区分好坏判断的组织将无法从这项政策中获得任何价值。 这是一个很好的例子，说明一项在某个组织中好的政策，在另一个组织中可能变成糟糕的政策。

如果你发现自己想包含一项由于某种原因无法应用或无法执行的政策，停下来问问自己你到底想达成什么，并思考是否有其他更适合该目标的政策。

制定新颖的政策

我的经验是，真正新颖的政策少之又少。 几乎总有其他人已经做过与你打算采用的方法类似的事情。 就是一个这样的例子：细节是公司特定的，但总体方法在行业中很常见。“我们是一家产品工程公司！”——Calm 的工程战略

最有可能找到真正新颖政策的地方，是在某项新的广泛技术采用阶段，例如无处不在的手机、云计算或大型语言模型的兴起。 即便如此，正如 中所探讨的那样，新技术可以作为一种通用技术来对待：如何采用大语言模型（LLMs）？
