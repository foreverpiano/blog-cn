读完本章后，你将能够评估为什么现有策略的政策难以产生影响，并开始为你自己的策略迭代制定政策。

什么是政策？

政策是将你的转化为具体计划的过程。该计划是一系列决策、权衡和方法。它可以涵盖编码实践、招聘要求、架构决策，以及关于组织内如何做出选择的指导。工程策略中的诊断

一项有效的政策应该解决策略诊断的全部内容，尽管诊断本身也鼓励明确指出哪些方面可以忽略。例如，在其诊断中承认，他们对预期减幅没有明确指导：驾驭私募股权所有权

根据一般做法，我们的新私募股权所有者很可能期望我们通过裁员来降低研发人力成本。然而，我们没有任何具体细节来做出结构化的决策，而且我们的应对方式会因裁员规模的不同而有很大差异。

面对这种不确定性，政策只是承认了这种模糊性，并承诺在获得更多信息后重新考虑：

我们相信新的所有者将在即将到来的财年规划中为研发（R&D）运营费用提供具体目标。一旦我们获得明确目标，我们将再次修订这些政策，并将推迟围绕裁员的规划，直到我们获得这些数字，以避免同时运行两个重叠的流程。

在制定政策时，有两个常见的混淆点值得直接说明：

政策是策略的一个子集，而非策略的全部，因为政策只有在策略诊断的背景下才有意义。例如，在背景下是有意义的。但这项政策在快速扩张的组织中可能效果不佳。任何没有政策的策略都是无用的，但你也会发现，没有上下文的政策同样价值不大。这尤其遗憾，因为策略在传达时常常缺少这些关键部分。政策描述了应该如何进行权衡，但它并不验证这些权衡在实践中是否真正被执行。下一章关于运营的内容将讨论如何检查组织的实际行为，以确保政策得到遵守。在将策略时，将政策和运营部分合并通常是合理的。但在起草策略时，将它们分开很有价值。是的，你可能会用周会来审查政策是否被遵守，但政策是否有效与是否召开这样的会议无关，而且你使用的运营机制会根据你打算实施的政策数量而有所不同。工程组织层级结构模型驾驭私募股权所有权让工程策略文档更具可读性

有了这个定义，我们现在可以转向更有趣的讨论：如何制定政策。

如何制定政策

撰写策略的每个部分在进行时都让人感觉很难，但我个人发现，撰写政策要么感觉容易得让人不安，要么痛苦得极具挑战性，从来没有中间地带。幸运的是，探索和诊断阶段通常会共同让撰写政策变得简单——尽管有时这个简单的结论可能很难接受。

我在撰写策略政策时遵循的步骤是：

回顾诊断，确保它捕捉到了最重要的主题。它不需要完美，但不应有明显到一眼就能看出的遗漏。选择能够解决诊断的政策。明确地将每项政策与其解决的一项或多项诊断对应起来。持续添加政策，直到所有诊断都被覆盖。这是一条宽泛的指示，但实际上比听起来简单，因为你通常会从中进行选择。当然，你也可以对这些政策进行调整，并将熟悉的政策重新应用到新的情境中。如果你确实需要制定一项新颖的政策，本章后面的“制定新颖的政策”部分将更详细地讨论这个话题。将重叠或相邻的政策进行合并。例如，关于特定团队的两项政策可以归纳为一项关于整个工程组织的政策。针对你最近做出的决策对政策进行回测。如果你组织内有决策日志，这会特别有效。再次挖掘冲突，就像你在制定诊断时所做的那样。特别强调来自与你视角不同的团队和个人的反馈，但也不要完全排除那些你认同的观点。正如在诊断时如果不征求反对意见就很容易排挤它们一样，如果你过于依赖他人的观点，也可能无意中排挤掉自己的视角。如果写完后你还是不确定自己的方法是否可行，没关系！返回到优化阶段，使用来增强你的信心。请记住，我们谈论策略时好像它是一次性完成的，但几乎所有真实的策略都需要多次优化迭代。探索策略。如何有效优化工程策略

撰写政策的步骤相对平淡无奇，这主要是因为你在探索、诊断和优化阶段已经完成了大量工作。如果你跳过这些阶段，你可能仍会遵循上述步骤来撰写政策，但政策本身的预期质量将会低得多。

应该制定多少项政策？

要全面解决诊断通常很复杂，这就是为什么大多数策略都包含一组政策而非仅仅一项。并不是一项“不进行分解”的政策，而是由四项政策组成：我们是否应该分解单体架构？

各业务单元应始终在自己的代码仓库和单体中运行。跨业务单元单体的新的集成应使用 gRPC。除新的业务单元单体外，我们不允许新建服务。将现有服务尽可能合并到业务单元的单体中。

四也不是一个放之四海而皆准的数字。它只是解决该策略诊断所需的数量。有了优秀的诊断，你制定的政策往往会显得理所当然，甚至有些无聊。这很好：一项政策的好坏在于它是否有效，而不在于它是否新颖或鼓舞人心。

政策的类型

虽然你可以撰写的政策有很多，但我发现它们通常可以归为四大类：审批、分配、方向和指导。本节将介绍这些类别。

审批定义了做出重复决策的流程。这可能需要启动架构咨询流程，也可能需要让高管这样的权威人物参与。

在中，有许多复杂的决策需要做出，其审批机制是：如何整合 Stripe 收购的 Index？（2018 年）

升级事项需提交给配对负责人：鉴于团队之间共享上下文有限，所有升级事项必须同时提交给 Stripe 的流量工程负责人和 Index 的工程负责人。

这让被收购方和收购方的团队能够在最终决策前都参与咨询，从而开始建立彼此之间的信任。另一方面，的审批策略则更侧重于管理企业风险：如何控制用户数据的访问权限？

例外情况必须由 CISO 以书面形式批准。虽然我们总体工程策略规定我们遵循《Facilitating Software Architecture》中描述的咨询式架构流程，但客户数据访问政策是个例外，必须由 CISO 明确批准并留下文档。该流程从 #ciso 频道启动。

这两种不同的审批流程有着不同的目标，因此它们在权衡时采取了不同的方式。审批流程可以有许多调整方式，从而在安全、生产力和信任之间实现多种不同的权衡。

分配描述了如何在多个潜在投资之间分配资源。分配是对组织优先级最具体的表述，同时也阐明了组织对团队生产力产生机制的信念。有些公司相信通过把更多人集中到关键问题上来加快速度。另一些公司则相信通过迫使团队在没有额外人手的情况下解决问题来加快速度。两者都可以奏效，并能让你了解公司信念的重要信息。

关于的策略中有两个具体的分配政策示例。第一个描述了基础架构工程团队在手动配置任务与投资构建自助配置平台之间的资源分配：2014 年左右 Uber 的服务迁移策略。

限制手动配置的资源分配，以最大化对自助配置平台的投入。服务配置团队将固定分配一名全职工程师负责手动服务配置任务。我们将把剩余工程师调去开发自动化，以加快未来的服务配置速度。这会在短期内降低手动配置的效率，但另一种选择是，随着新招聘的产品工程师带来的新服务请求不断涌入，永久性地降低配置能力。

第二个分配政策隐含在该策略的诊断中，它描述了工程组织更高高度策略中的分配政策：

在基础架构工程团队中，目前有一个由四名工程师组成的小组负责服务配置。虽然我们组织的增长速度与产品工程团队相当，但新增的人力并没有直接分配给负责服务配置的团队。我们预计这种情况不会改变。

分配政策通常能为团队带来出乎意料的清晰度，我在几乎每一项政策中都会明确或隐含地在更高高度的策略中包含它们。

方向为必须如何做出决策提供明确指示。当你清楚自己想要去哪里，并且明确知道该如何到达时，这是合适的工具。方向适用于你清晰理解的问题，并且你更看重一致性而非赋予个人判断力。

当你需要一个没有解释空间的明确政策时，方向效果很好。例如，：“我们是一家产品工程公司！”——Calm 的工程策略

我们所有的代码都在单体中编写。之前一直不明确的是，新代码（尤其是新的应用代码）是应该写在我们的 JavaScript 单体中，还是必须写在单体之外的新服务中。现在不再模糊：所有新代码必须写在单体中。如果在极少数情况下，由于功能需求导致无法在单体中编写，则应按照下面描述的方式申请例外。

在这种情况下，团队无法就什么应该进入单体达成一致。个人经常会做出不兼容的决策，因此要达成一致性，就必须将个人判断从等式中移除。

有时候问题是判断力，有时候一致性难以达成是因为激励机制不一致。一个很好的例子来自：驾驭私募股权所有权

我们将转向“N-1”替补政策，即离职岗位将由更低级别的人员替补。我们还将严格规定每个业务单元最多只能有一名 Principal Engineer。

如果这项替补政策表述得更温和，招聘经理很可能直接忽略它，尽管有时力度较轻的政策也有用。

指导为应该如何做出决策提供一项建议。当存在足够多的细微差别、或复杂性，以至于你能解释期望的目标，但无法强制规定到达该目标的路径时，指导就很有用。驾驭模糊性

一个指导的例子来自：如何整合 Stripe 收购的 Index？（2018 年）

最小化对 tokenization 环境的变更：由于销售点设备直接处理客户支付细节，直接支持销售点设备的 API 必须位于我们存储支付细节的安全环境中。但是，任何其他功能都不得添加到我们的 tokenization 环境中。

这读起来可能像是方向，但它实际上是在澄清期望的结果，即避免 tokenization 环境中出现不必要的复杂性。然而，它无法明确什么复杂性是必要的，因此最终它属于指导，因为它需要相当多的判断力来解读。

另一个指导的例子来自：我们是否应该分解单体架构？

将现有服务尽可能合并到业务单元的单体中。我们认为，每一个将现有服务移回单体的决定都应该“根据细节”做出，而不是从自上而下的策略角度做出。因此，我们总体上鼓励团队逐步停止使用其业务单元单体之外的现有服务，但最终由团队根据其本地上下文做出正确决策。

这又是一个知道期望结果，但由于不确定性太大而无法指导团队如何实现它的例子。如果你问五名工程师是否有可能将某个服务合并回单体代码库，他们很可能意见不一。这没关系，也凸显了指导的价值：它使得在如果给出更具体的方向可能会造成混乱的领域，仍能取得渐进式进展。

当你在撰写策略的政策部分时，考虑所有这些类别非常重要。哪种最自然取决于你的团队和角色，但它们都是可用的：

如果你在一个开发者生产力团队，你可能需要在政策中 heavily 依赖指导，并在平台细节中加强对该指导的支持。如果你是一名高管，你可能会 heavily 依赖方向。事实上，你可能会过于依赖方向，而在你知道方向但不知道路径的领域，指导往往更有效。如果你在一个产品工程组织，你可能需要将你的方向范围缩小到该组织内的工程师，以应对复杂的跨组织动态现实。

最后，如果你有一个清晰的方法想要采用，但它不能干净地归入这些类别中的任何一个，那就不要让这个框架阻止你。尝试一下，如果一开始不奏效就调整。

保持策略的高度

一章引入了策略高度的概念，即有意地在组织内特定层级创建某些类型的政策。何时编写策略，以及写多少？

在不重复整个章节内容的前提下，当你制定政策时，特别重要的是要考虑你的新政策如何消除组织内的灵活性。考虑下面两个有些对立的策略：

只有在基本上强制所有团队使用单一编程语言的组织中才能奏效。知道资源分配必须由团队直接管理。如果试图在其他层面解决问题，最终只会导致有人直接去找团队，改写他们的优先级以纳入新的紧急项目。Stripe 为什么开发 Sorbet？（~2017）如何在 Calm 为工程驱动的项目分配资源？（2020）

Stripe 的组织层级政策剥夺了个体团队选择自己偏好技术栈的自由。作为回报，他们解锁了以强大方式集中投入的能力。Calm 则走向了相反的方向，他们认识到只有团队才有权管理自己路标的內容；高管虽然层级更高，但经常被其他高管带外的指令所覆盖。

这两种高度都有道理，也都有后果。

有效政策的评估标准

在《The Engineering Executive’s Primer》中关于的章节里，我介绍了评估政策的三个标准。它们应该是可应用的、可执行的，并且能创造杠杆。对这些标准稍作定义：撰写工程策略

可应用：能够用于导航复杂的真实场景，尤其是在进行权衡时。可执行：团队会因遵循指导政策而被问责。创造杠杆：产生复合或倍增的影响。

这三者中的最后一项“创造杠杆”，在一本关于工程高管的书中是有道理的，但在这里可能就不那么合适了。有些政策确实应该创造杠杆（例如，会让其他客户留存机制更有效），但其他政策可能不需要（例如，）。在非高管语境下，重要的不一定是创造杠杆，而是一项政策能解决诊断的一部分。Stripe 应该如何弃用 API？（~2016 年）驾驭私募股权所有权

剩下的两个标准——可应用和可执行——两者对于政策真正解决诊断都是必要的。任何你无法确定如何应用，或者不愿意去执行的政策，基本上都不会有用。

让我们将这些标准应用到一些潜在的政策上。首先思考我们可能为提升工程团队的人才密度而制定的政策：

“我们只招聘世界一流的工程师。”这不可应用，因为不清楚“世界一流的工程师”是什么意思。由于这项政策中没有双方都能接受的定义，它也无法被一致地执行。“我们只招聘在记分卡上至少获得一个‘强烈同意’的工程师。”这是可应用的，因为有明确的定义。这也是可执行的，取决于组织是否愿意拒绝那些看似优秀但没有获得强烈同意的候选人。

接下来思考关于代码库内代码复用的政策：

“我们在代码库中严格遵循 Don’t Repeat Yourself（DRY）原则。”团队内对于两段代码是否真的重复可能存在争议，但总体上是可应用的。由于存在争议，决定如何执行就变成一个非常依赖具体上下文的判断。“代码作者负责判断他们的贡献是否违反 Don’t Repeat Yourself，如果违反则进行重写。”这要可应用得多，因为现在只需要评估一个人的判断。在某种程度上，这项政策也更易于执行，因为不再存在谁来决定一段代码是否重复的模糊性。挑战在于，可执行性现在取决于某一个人，要让这项政策有效，就需要让个人为其判断质量负责。一个不愿意区分好判断和坏判断的组织将无法从这项政策中获得任何价值。这是一个很好的例子，说明一项在某个组织中好的政策，在另一个组织中可能变成糟糕的政策。

如果你发现自己想要加入一项因为某种原因无法应用或无法执行的政策，请停下来问问自己你真正想达成什么，并思考是否有其他更适合该目标的政策。

制定新颖的政策

我的经验是，真正新颖的政策少之又少。几乎总是已经有人做过与你打算采用的方法类似的事情。就是一个这样的例子：细节是公司特定的，但总体方法在行业内很常见。“我们是一家产品工程公司！”——Calm 的工程策略

最有可能找到真正新颖政策的地方，是在某项新的广泛技术被采用的阶段，例如无处不在的手机、云计算或大型语言模型的兴起。即便如此，正如中所探讨的，新技术可以被当作一种通用技术来对待：如何采用大语言模型（LLMs）？
