构建内部 Agent：代码驱动 vs LLM 驱动的工作流

2025-12-31 · 阅读原文

当我开始这个项目时，我内心深处坚信，我们可以用 LLM 加上工具调用来解决任意复杂的业务流程。我至今仍然相信这是可行的，但我不再认为这一定是个好的解决方案。因为有些问题用传统软件来解决，会简单得多、成本低得多、速度也快得多。本文将分享我们如何同时支持代码驱动和 LLM 驱动的工作流，以及我们为什么认为这很有必要。

这是 构建内部 Agent 系列文章的一部分。

为什么确定性如此重要

我加入 Imprint 时，团队已经有一个频道，供大家分享需要 Review 的 Pull Request。虽然不是强制要求把 PR 贴到这个频道，但这通常是获得 Review 的最快方式，尤其是跨团队的 PR。

我经常在一天开始时浏览这个频道，查看哪些 PR 需要 Review，然后很快发现：很多 PR 其实已经被 Review 并合并了，却没有人给对应的消息加上 :merged: 表情。这让我觉得效率低下，但又实在太微不足道，不值得去抱怨。于是我开始思考，如何在不增加人工劳动的情况下解决这个问题。

于是，我加入了一个由 LLM 驱动的工作流来解决它。Prompt 非常直白：

  1. Get the last 10 messages in the Slack channel
  2. For each one, if there was exactly one Github pull request URL, extract that URL
  3. Use the Github MCP to check the status of each of those URLs
  4. Add the :merged: reacji to messages where the associated pull request was merged or closed

这个方案一开始运行得非常好！真的非常好。只是……偶尔它会给还没有合并的 PR 也加上 :merged: 表情，导致没人再去看那些 PR。从概念上讲，它很出色——多么聪明的工具调用啊！——但在实际使用中，它并没有真正解决我原本想解决的问题：错误添加的表情让大家无法再根据表情来判断是否需要查看频道里的某个 PR。

（顺便说一句，有些人真的很讨厌“reacji”这个词。别来找我抱怨，这是 Slack 自己这么叫的。）

我们如何实现对代码驱动工作流的支持

我们的 LLM 驱动工作流是由一个软件 Handler 来编排的。该 Handler 的工作流程大致如下：

  1. Trigger comes in, and the handler selects which configuration corresponds with the trigger
  2. Handler uses that configuration and trigger to pull the associated prompt, load the approved tools, and generate the available list of virtual files (e.g. files attached to a Jira issue or Slack message)
  3. Handler sends the prompt and available tools to an LLM, then coordinates tool calls based on the LLM’s response, including e.g. making virtual files available to tools. The handler also has termination conditions where it prevents excessive tool usage, and so on
  4. Eventually the LLM will stop recommending tools, and the final response from the LLM will be used or discarded depending on the configuration (e.g. configuration can determine whether the final response is sent to Slack)

我们更新了配置系统，允许以两种模式之一运行：

# this is default behavior if omitted
coordinator: llm

# this is code-driven workflow
coordinator: script
coordinator_script: scripts/pr_merged.py

当协调器被设置为 script 时，就不再由 Handler 来决定调用哪些工具，而是直接执行自定义的 Python 代码。这些 Python 代码可以访问与 LLM 处理代码完全相同的工具、触发数据和虚拟文件。它也可以使用 构建内部 Agent：子 Agent 支持 工具在需要时调用 LLM（该子 Agent 同样可以完全访问所有工具），但只有在明确需要时才会让 LLM 介入控制。

这意味着这些脚本——由我们的软件工程师编写、提交代码审查等——拥有与 LLM 相同的权限和能力，不过因为它是代码，任何一次提交也可能引入新的依赖等。

实际效果如何？下一步计划？

总的来说，这套方案在处理复杂工作流时表现非常出色。我把它称为“常用解决方案”，即在 LLM Prompt 和工具不够可靠或不够快的情况下，我们用代码驱动的工作流作为渐进式增强。我们仍然会用 LLM 启动所有工作流，这对很多场景已经足够。当需要改写时，Claude Code 几乎总能一次性把原来的 Prompt 改写成代码工作流。

即使模型变得越来越强大，我们也只在真正需要智能的场景下谨慎使用它们，而不是用于迭代式工作流。这似乎会成为我们工具箱中长期存在的一部分。
