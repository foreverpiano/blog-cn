构建内部 Agent：代码驱动 vs LLM 驱动的工作流

2025-12-31 · 阅读原文

当我启动这个项目时，我内心深处坚信，我们可以让 LLM 结合工具使用来解决任意复杂的 workflows。我至今仍然相信这是可行的，但我不再认为这实际上是一个好的解决方案。有些问题用传统软件来解决，会简单得多、成本更低、速度也更快。本文将讨论我们如何同时支持代码驱动和 LLM 驱动的工作流，以及我们为什么认为这是必要的。

这是 构建内部 Agent 系列文章的一部分。

为什么确定性如此重要

当我加入 Imprint 时，我们已经有一个频道，供大家分享需要评审的 pull request。虽然不是强制要求把 pull request 发到这个频道，但这通常是获得评审的最快方式，尤其是跨团队的 pull request。

我经常在一天开始时浏览频道中需要评审的 pull request，并很快发现，很多 pull request 已经被评审并合并，却没有人给聊天消息加上 :merged: 这个 reacji。这让我觉得低效，但又是一件特别小的事，我不想为此抱怨。相反，我开始思考如何在不增加额外人力成本的情况下解决这个问题。

于是，我添加了一个由 LLM 驱动的工作流来解决它。prompt 非常直白：

获取 Slack 频道中最近 10 条消息；对每条消息，如果其中恰好包含一个 GitHub pull request URL，则提取该 URL；使用 GitHub MCP 检查这些 URL 的状态；对于已合并或已关闭的 pull request，给对应消息加上 :merged: reacji。

这个方案一开始效果非常好！真的非常好。只是，啊，它有时会给尚未合并的 pull request 也加上 :merged:。结果就没人去看那些 pull request 了。所以，从概念上讲它很成功——多么聪明的工具使用啊！——但在实践中，它并没有真正解决我想解决的问题：错误添加的 reacji 让大家无法仅凭 reacji 是否存在来判断是否需要查看频道中的某个 pull request。

（顺便说一句，有些人真的很不喜欢“reacji”这个词。别来跟我抱怨，这是 Slack 自己这么叫的。）

我们如何实现对代码驱动工作流的支持

我们的 LLM 驱动工作流是由一个软件 handler 编排的。该 handler 的工作流程大致如下：

触发器进来后，handler 选择与该触发器对应的配置；根据配置和触发器拉取相应的 prompt、加载已批准的工具，并生成可用的虚拟文件列表（例如附加在 Jira issue 或 Slack 消息上的文件）；handler 将 prompt 和可用工具发送给 LLM，然后根据 LLM 的响应协调工具调用，包括将虚拟文件提供给工具使用；handler 还设置了终止条件以防止过度使用工具等；最终当 LLM 不再建议调用工具时，其最终响应会根据配置被使用或丢弃（例如配置可以决定是否将最终响应发送到 Slack）。

我们更新了配置，使其支持两种运行模式：

当 coordinator 被设置为 script 时，就不再由 handler 来决定调用哪些工具，而是使用自定义的 Python 代码。这些 Python 代码可以访问与 LLM 处理代码相同的工具、触发数据和虚拟文件。它可以使用 构建内部 Agent：子 Agent 支持 工具在需要时调用 LLM（该 subagent 也可以完全访问所有工具），但只有在明确需要时才会进行 LLM 控制。

这意味着这些脚本——由我们的软件工程师编写、提交并经过 code review 等流程——拥有与 LLM 相同的权限和能力，不过因为它只是代码，任意一次 commit 都可能引入新的依赖等。

实际效果如何？/ 下一步计划？

总的来说，这种方式对于复杂工作流效果非常好。我将其描述为“常用解决方案”，即在 LLM prompt 和工具不够可靠或不够快的情况下，我们会使用代码驱动的工作流作为一种渐进式增强。我们仍然会用 LLM 启动所有工作流，这对很多场景已经足够。当我们确实需要重写时，Claude Code 几乎总能一次性把原来的 prompt 改写成代码工作流。

即使模型变得越来越强大，在我们真正需要智能的场景下有针对性地使用它们，而不是用于迭代式工作流，似乎会成为我们工具箱中长期有价值的一部分。
