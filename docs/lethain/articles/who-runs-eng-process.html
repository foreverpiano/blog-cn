谁来负责工程流程？

2023-04-03 · 阅读原文

Uber 曾运行过一个名为 DUCK Review 的技术规格评审流程。“DUCK”并不代表任何含义——它是故意设计的一个非缩写——但除此之外，它是一个相当典型的评审流程。我刚加入时，我们每周会评审一到两个规格。随着评审请求量不断增加，六个月后，从提交评审请求到收到反馈之间出现了为一到两周的延迟。又过了一年，由于没有足够带宽处理所有 incoming 的规格，这个流程被废弃了。这对我来说是一次很有启发性的经历，因为 DUCK Review 确实提供了非常有价值的反馈，但最终还是失败了，因为它的运营成本超过了我们愿意为这些反馈付出的代价。

在我管理生涯的早期，我认为大多数流程失败是因为它们对当前问题的解决不够充分。我以为如果一个流程的结果不佳，那是因为流程需要更多的细微差别和复杂性。此后我通过设计那些考虑周全却依然失败的流程，学到的教训是：好的流程是在质量和开销之间有意识的权衡。比如，我们常看到一种快速运行但反馈质量较低的代码评审流程，要求在 pull request 提交后两个工作小时内完成评审。同样常见的是那种非常繁琐、高质量的流程，最终大家因为太慢而忽略它，包括前面提到的 DUCK Review 的故事。

要确定你的团队需要何种程度的流程复杂度，你必须先弄清楚谁来负责运行这些流程，然后从这个答案反向推导出你的组织能够持续支撑的流程复杂度。为了帮助你思考这个问题，我将逐一分析：

不同公司的典型流程模式演进路径是什么？这些模式各自的优缺点是什么？如何成功运作 baseline 模式？如何应对预算现实？如何应对潮流周期？

读完之后，你会对当今组织中应该由谁来负责流程、什么时候应该考虑切换模式，以及在人员配置上避免最常见错误的一些建议，形成清晰的认识。

这是 O'Reilly 出版的《The Engineering Executive’s Primer》中的一章，未经编辑。

典型的模式演进

我观察到组织在运行工程范围和公司范围的流程时，通常会采用五种常见模式。不管你今天使用哪种模式，很可能三年前你在用另一种；如果你增长迅速，那么三年后很可能又会采用第三种模式。没有绝对正确的模式，只有最适合你当前约束条件的模式。（有一种模式是错误的，那就是业务单元模式，它很少能运行得特别好。）

早期创业公司

所有新成立的公司都采用我所说的 Early Startup 模式：要么由创始人或职能高管为自己的职能做某件事，要么这件事就不发生。我在 Calm 担任 CTO 的第一年，公司没有共享的人员流程，我用一个 spreadsheet 运行工程的绩效评审流程。它需要被完成，而我处于可以去做的位置。这就是极小规模公司的工作方式，通常会持续到前 30-50 名员工入职，之后他们会转向稍微更有结构化的做法。

Baseline 模式

下一个阶段是 Baseline 模式，大约在 50 名员工左右开始采用，并且是大多数公司的最终模式。公司范围的流程（例如公司规划、绩效管理和预算）由中央 People（即人力资源）职能负责，而工程范围的流程（例如 Tech Spec Review、Incident Review 和开发者生产力调查）则由工程师和工程经理负责。没有专门的角色来支持工程流程，对公司流程针对工程的专门化程度也有限。

专业化工程角色

当公司规模超过 200 名工程师时，工程范围的流程往往会消耗足够多的时间，以至于受益于全职支持。这通常首先发生在 Incident Review 或 Tech Spec Review 上，但根据你公司的具体情况，任何一个流程都可能第一个变得足够昂贵而需要专人。我称其为 Specialized Engineering Roles 模式，因为大多数公司通过建立一个新职能来解决这个问题，通常是 Technical Program Management 或 Engineering Operations。

公司嵌入式角色

在许多科技公司中，工程是最大的职能，因此会比业务其他部分更早达到某些规模点。为了确保流程在所有这些扩展需求下仍能正常运作，往往会导致工程从公司默认的招聘、绩效管理等机制中分离出来，从而有专职的招聘人员和 People 团队成员与工程一起工作。我称其为 Company Embedded Roles 模式。

除了纯粹的规模因素外，工程还有其他几个因素会产生特别复杂的需求，并支持向这种模式的转变：

工程师和工程经理之间存在双轨职业阶梯，而其他职能通常只有一条。通常包含一个或多个专业化角色，例如 Developer Relations、Technical Program Management、Quality Engineering 或 Security Engineering。与大多数其他职能相比，工程师和工程经理的招聘和留存往往更慢、更昂贵。从开始到变得高效生产力的爬坡期较长，这使得留存的价值更高。

业务单元本地化

最后是 Business Unit Local 模式，即工程向每个业务单元的领导层汇报，不再有一个领导者对整个工程负责。这通常会导致工程回归由中央职能运行的标准化流程，或者接受不一致性，让每个业务单元的工程组织自行寻找前进的道路。

各种模式的优缺点

现在我们已经介绍了公司经历这些流程管理模式的典型序列，我想更深入地探讨这些模式本身的优缺点：

Early Startup：当你创办一家新公司时，它只是一个或多个创始人。早期雇员几乎总是专注于构建一个小产品来验证市场或日常运营业务，一般不会包括任何纯粹专注于流程的人。这是有道理的，因为流程是关于协调大群体的，而此时公司只有寥寥数人。任何你想运行的流程都需要由创始人或他们雇用的经理来运行。公司通常是因为有他们认为重要的流程想运行而退出这个模式，最开始往往是绩效管理，但他们觉得当前团队太忙而无法运行。优点：成本低、开销低，在小规模下几乎没有缺点，因为大多数流程都专注于支持大型团队。缺点：往往有价值的事情没有发生，因为每个人都太忙，有时由于时间或运行该流程的经验有限，流程质量非常低。Baseline：工程范围的流程由工程师或工程经理运行，公司范围的流程由中央职能运行，通常在 People 或 Human Resources 部门。大多数公司会在 baseline 模式中停留很长时间，可能只有一个小的例外是为工程招聘配备一个专职招聘人员。它通常能良好运作到 100 名以上工程师。它比早期创业模式显著更好的原因之一是，它明确了一个负责选择供应商的团队（例如用 Greenhouse 满足招聘需求，用 Lattice 做绩效管理）。这些工具并不完美，但比 spreadsheet 好得多，而 spreadsheet 是当七个经理各自独立运行去中心化流程时的默认工具。优点：一定程度的适度专业化，让工程可以专注于工程而不是基础的公司流程；此时 HR 任务的复杂度往往超过工程经理的能力范围（例如管理签证）；统一的系统让高管团队可以跨职能进行检查，而不仅仅是在自己职能内。缺点：结果高度依赖这些中央职能的质量，改变公司范围的流程会变得具有挑战性。Specialized Engineering Roles：通过雇佣专职、专业化角色来完成工作，从而提高工程范围流程的效率。通常是雇佣 Engineering Operations 或 Technical Program Management 团队。最早的投资领域通常是组织规划、事故管理以及 运行你的工程入职项目。优点：专业化角色通常会带来显著的效率提升，以更低的薪资水平提供更匹配任务的技能组合。引入这些角色通常会让不再做这些工作的人感到振奋。能够专注于某个流程的专家往往能在该流程上做出重大改进。缺点：虽然效率更高，但通常也更昂贵，因为这些角色会增加额外的人头。它需要 引入 SRE、TPM 及其他专业化角色，例如 engineering operations 或 technical program management。专业化角色往往会让公司固化在某种工作方式上——工程师被激励去消除一个流程，而专家则被激励去改进它。Company Embedded Roles：工程对公司范围流程的需求达到了足够的规模，或者与标准操作流程充分偏离，以至于支持职能如 People 和 Recruiting 会专门招聘人员来支持工程。这通常一个职能一个职能地发生，往往从 Recruiting 开始，接着是 People 和 Finance。虽然它往往最先在工程发生，但这种模式会在公司其他大型组织中重复出现，例如你会经常看到工程和销售有专职嵌入人员，而组织其他部分则与中央团队合作。在足够大的公司中，每个职能都会有专职支持。优点：赋予工程自定义流程和方法的能力。在职能之间建立更强的关系。缺点：运营成本高。质量高度依赖于嵌入的个人。Business Unit Local：公司中的每个业务单元都有自己独立的工程职能。这种拆分通常发生在组织大到拥有多个有意义的业务单元，并且认为跨业务单元的工程标准化是不必要或代价过高的时候。例如，一个业务单元可能需要 HITRUST 合规，而其他业务单元不需要，这可能导致显著不同的工程权衡。有时采用这种模式，但其中一个业务单元远大于其他，以至于它成为整个公司事实上的工程中心，包括领导跨组织的开发者工具和基础设施投资。优点：让工程与每个业务单元的业务优先级对齐。缺点：工程流程和战略往往停留在拆分发生时的状态。未来的变更需要众多工程领导者达成共识。跨工程的投资变得难以优先级排序。

所有这些模式都有缺陷，但都值得考虑。话虽如此，如果你在没有任何额外上下文的情况下让我选择一个，我总是会推荐 baseline 模式。它通常已经足够好，而且最容易管理。

运作 Baseline 模式

我所说的 Baseline 是运行流程最常见的方法，由中央 People 组织负责公司范围的流程，由工程师和工程经理混合负责工程范围的流程。

它常见有几个原因：

这是默认场景：只要不雇佣任何专业化角色，也不直接向工程嵌入支持，你就处于 baseline。它相对简单：你不需要学习如何招聘或管理任何新事物，也不需要将工程与其他职能区别对待。它看起来更便宜：当你提议转向另一种模式时，通常会被表述为释放现有产能去专注更高价值的工作，但这需要雇佣额外角色来支持该模式，例如 Technical Program Manager。这从预算角度看就更贵了，即使它在效果上明显更好，而大多数预算讨论都是成本驱动而非效果驱动的。

它常见的第四个原因是：它确实运行得相当好！我工作过的每家公司，包括 Uber 和 Stripe，都在这个模式下走了很远，远超一百名工程师才离开它。我个人认为许多公司切换到其他模式太早了，往往是因为他们在复制之前就职的、规模大得多的公司的 playbook。

如果你被诱惑要从 Baseline 切换出去，而且公司规模还在一百名工程师以下，我建议你先重点关注以下几件事，尝试让当前模式为你发挥作用：

轮换工作。Calm 在六个月轮换上取得了很大成功，个人以某种身份（例如运行 Incident Review）服务六个月后换岗。我们通过让两个人以重叠但错开的任期共同担任每个角色来增加连续性。让运行流程的人感到有趣。如果有人在领导你的 Incident Review，也让他们参与公司更广泛的规划流程，将可靠性项目考虑进去。如果有人在运行你的 Tech Spec Review，把他们拉进你每年修订 撰写工程战略 的工作中。你应该超越单纯的服务，让大家觉得这些是与高层领导合作、独特的学习机会。确保你的晋升标准（或者如果你还没有 rubric，就在实际晋升中）重视这类工作。你甚至可以试验在 rubric 中强烈倾向于让工程师在进入 Staff-plus 或管理角色前，先在某个流程中服务一届。人们很聪明，会倾向于去做你重视的工作。一定要在全员会议和问答会议等场合点名表扬那些在流程背后默默工作的人，特别是 打造高效工程组织的会议体系。

虽然没有保证，但我的亲身经历是，做这些相对小的调整就能让 Baseline 模式良好运转，并且能比你预期的更长时间地持续有效。

应对预算现实

虽然在不同模式之间迁移存在运营上的挑战，但这些挑战大多只有在事后回顾时才明显。相反，从 Early Startup 转向 Baseline 或从 Baseline 转向 Specialized Engineering Roles 的最大障碍是预算影响。即使你能证明三个 Technical Program Manager 会显著提升工程的影响力——这很可能正确，但你很难用 spreadsheet 证明——大多数预算流程还是锚定在相对美元数字上，而不是绝对影响上。

深入来看，面临的问题是：

大多数成功沿着模式成本曲线向上迁移的公司，都是在快速增长的时候这样做的。这类公司对快速增长的人头成本感到舒适，通常也能容忍增加角色来支持增长。在所有其他情况下，公司通常不能容忍增加新的角色和结构，即使它们可能提高效率。在后一种场景中，你更可能听到大家谈论“用更少资源做更多事”，而不是“设计我们的组织以高效运作”，而在执行团队处于成本削减心态时，基于效率的论点很难被接受。许多公司按照部门之间的投资组合分配目标来运作，例如 G&A 占 20%，Sales & Marketing 占 30%，R&D 占 50%。大多数模式转换都会侵蚀 G&A 预算，增加 G&A 成本，并阻止其他计划中的 G&A 招聘。这通常意味着你的许多同级高管会对提案持抵触态度。令人惊讶的是，许多预算流程是按人头而不是按预算运作的，这使得像“用三个中级 Technical Program Manager 替换两个高成本的 Staff 工程师”这样的想法很难直观地表达。以人头为锚点的预算流程会把后者描绘得比前者更贵，尽管事实并非如此。虽然可以推动克服这种困惑，但它会带来持续的沟通成本。

每一个这些顾虑都可以通过规划、耐心和信念来克服，但你必须自己决定是否值得这么做。我的一般建议是坚持使用 Baseline，除非收入或人头数正在显著增长，否则避免沿着模式成本曲线向上迁移。

应对潮流周期

存在许多流程潮流，例如行业曾一度痴迷于 Agile：我曾经和一位职位名称是 Agiletect 的人共事。同样，在谁来负责流程，以及演进流程是高度有影响力的、必不可少的工作，还是无聊、枯燥、不会帮助你晋升的“glue work”上，也存在潮流。在我自己的职业生涯中，我看到过从“技术管理”到“以人为中心的管理”的重大转变，以及同样突然的反向反应，从“以人为中心的管理”转向“管理是开销”。

如果我对每一种潮流都照单全收，那么我就会给我领导的团队带来持续的动荡，我们永远无法在任何一种工作方式上变得特别擅长。这并不是说潮流没有意义，每个潮流背后总有某些真实的东西。在行业 downturn 时，会有减少现金流的潮流；在行业 upturn 时，会有利用大量投资者资金的潮流。转向以人为中心的管理，部分是由美国员工的代际变化驱动的，千禧一代成为劳动力中更大的部分。从这些潮流中可以学到东西，但如果把它们当作绝对真理那就错了：迄今为止有效的东西不会在一夜之间变得无关紧要。

我的建议是，围绕某一组特定的基础信念来设计你的组织，并坚定地坚持这些信念至少三到四年，然后再考虑改变。改变可以是恢复性的，但如果你改变得太快，你就永远无法充分了解什么在起作用、什么不起作用，也就无法为未来的改变提供依据。
