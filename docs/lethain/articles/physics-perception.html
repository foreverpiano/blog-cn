物理与感知

2024-06-29 · 阅读原文

2019 年的时候，Stripe 工程团队的几个部分正陷入一场温和的内战。冲突源于一派人坚信应该用 Java 取代 Ruby。他们认为，面对业务和工程团队的快速扩张，Java 能帮助解决持续交付高质量平台的挑战。而另一派则认为，Stripe 的问题根源在于如何打造软件质量，以及来自用户、金融机构、政府等众多严苛的外部合作伙伴；更换编程语言并不能解决这些根本问题。我与人合写了内部版的探索的量级，试图为这场争论找到一个有用的分析框架，但双方依然很难真正理解彼此。

在阅读 Steven Sinofsky 的 Hardcore Software 中关于“创新与交付：Cairo 项目”那一章时，我又想起了那些讨论。

1993 年初，我桌上出现了一份又一份的 Cairo 计划和文档初稿。Cairo 继承了 NT 产品流程的成熟做法——注重文档和架构规划——并将其进一步强化。Cairo 团队像一台运转良好的机器，很快就产出了大量文档，装订成三英寸厚的活页夹，详细描述了产品的所有举措。每次我和 Cairo 团队的人开会，他们都对自己的规划和流程充满信心……任何旁观者都应该把文档的丰富程度和团队的自信视为积极信号，但缺乏可运行的代码以及不断膨胀的产品定义，却引发了一些小小的警报，尤其是对我这个曾经做应用的人来说。Cairo 项目虽然在文档上看起来很像 NT 项目，但似乎缺少日常严格的构建、持续的性能和基准测试，以及质量与兼容性测试。更隐蔽的问题是，这种动态后来成为公司许多后续产品（尤其是操作系统）的警示。

关于 Cairo 开发和 Java 迁移的简单叙事是：一组人在做“正确”的事，另一组人在做“错误”的事。Cairo 团队在交付 vaporware，Java 团队则错误地诊断了根本问题。这类描述让人安心，因为它营造出“善”与“恶”对抗的熟悉叙事结构。但不幸的是，我从未发现这类叙事对理解冲突成因有什么帮助，而在真正解决冲突上，它们更是毫无用处。

我发现真正有帮助的，是研究每一派知道而的东西，并努力。有时我将其概括为“同时解决物理和感知”。上下文的多个层次有价值的权衡是多维度的。

解决感知问题

Sinofsky 把 Cairo 描述成一个过于宽泛、最终未能交付的项目，但他也解释了它为什么会吸纳那么多特性：

Cairo 倾向于把这视为一种挑战，要不断纳入更多能力。新出现的东西会被迅速加入产品潜在特性列表。更糟糕的是，比尔·盖茨可能认为在概念上相关的功能，比如某个第三方用来搜索硬盘上所有文件的应用，也可能成为 Cairo 需要应对的竞争特性。或者更常见的情况是：“Cairo 就不能稍微多做点工作来实现这个吗？”于是那“一点额外工作”就成了修订后产品计划的一部分。

这并非出于恶意，他们只是想不辜负 CEO 的期望。他们希望在公司的价值体系中被视为成功，因为他们清楚地知道，否则自己的项目就会被取消。

许多新上任的领导者一进来就立刻陷入类似的困境。他们刚加入，对领域和团队还不太了解，却被告知必须立即在公司此前一直未能解决的一系列问题上取得进展。他们知道自己需要表现出在做有价值的事情，于是就会去做任何看起来像是在推进的事。在这种时刻，领导者特别容易启动一项，他们希望借此解决眼前的问题，但无论如何，它都会被视为一项勇敢而大胆的举措。大型迁移

这并非高管或产品工程师独有的问题，我经常看到平台团队在时犯同样的错误。许多平台迁移被设计成，由平台团队通知产品团队必须在某个日期前完成某项任务（例如“迁移到我们的 monorepo”），并通过仪表盘向高管汇报哪些团队已经完成、哪些尚未完成。这对给底层团队施加压力效果很好，也能很好地管理感知——看起来在强力推进。但这些迁移往往会失败，因为很少有人关注迁移本身的易用性。如果你告诉团队错过日期就是失败，他们就会努力赶日期；如果确实很难，他们还是会失败。这时平台团队常常责怪产品团队没有优先考虑自己的项目，而实际上平台团队应该有自知之明，认识到正是自己没有简化底层的物理问题，才让被要求迁移的产品团队举步维艰。迁移：解决技术债务唯一可扩展的办法。事件响应、程序与你（的初创公司）。

解决感知问题本身并没有错，事实上它是成为有效领导者必备的一项技能。这里的教训是：绝大多数有意义的项目，都需要同时解决感知和物理。

解决物理问题

我刚加入 Stripe 时，最想推动的项目之一是从手工管理虚拟机转到 Kubernetes。这很大程度上受我在 Uber 把单体 Python 应用迁移到多语言、多代码仓库的 polyglot 应用时学到的经验影响。在尝试了几个月、在工程团队内建立共识之后，我把 Kubernetes 迁移推迟了几年，因为我无法说服大家它能解决一个迫在眉睫的问题。（后来我确实又推动了，而且非常成功。）我本可以强行让团队做这个项目，但这违背我的直觉：通常当工程师对领导的想法提出反对时，总有其合理的理由。

类似地，我在 Stripe 最初推动的并不是后来成为 Sorbet 的 Ruby 类型化工作，而是设计一条逐步迁移到现有静态类型语言（比如 Java 或 Go）的路径。我得到的反馈是这不现实，因为迁移工作量太大，而 Facebook 的 Hack 已经证明了从 PHP 迁移到类似 PHP 的类型化语言是可行的。我花时间认真理解了这些反对意见，并逐渐调整了自己的想法，转而关注如何排序这些工作：即使我们最终想切换语言，也要先改进架构以支持模块化迁移，而这项工作会从 Ruby 类型化中受益。

我在这些案例中是幸运的，因为需要解决的感知问题很少，我得以主要专注在物理上。事实上，能够专注于物理问题，是基础设施工程中被低估的优势之一。在高级领导岗位上，你很少能幸运到只关注物理。

例如，我加入 Carta 时，行业内外都有压力要求加大对 LLM 的投入。大多数工程师对使用 LLM 的机会持相当怀疑的态度，如果我只听物理的声音，可能就会无视采用 LLM 的压力。但那样我会走入两个误区。首先，我会严重损害更广泛的高管团队对我接纳新想法能力的信任。其次，物理是建立在我们当下对世界的理解之上的，而 LLM 是一个发展极快的领域。我们最终采用的，远好于只解决物理问题所能达到的任何结果。（也远好于如果我们只解决感知问题所能想出的方案。）在产品中使用大语言模型（LLMs）的视频

我认为 LLM 的例子很有启发性，因为它打破了“物理是真实的、感知是虚假的”这种预期。它可以朝两个方向发展，取决于具体情境。一旦你自满地认为自己的视角就代表现实，很快就会被现实纠正。

平衡物理与感知

有效的领导者会将感知和物理融合成同时解决两者的方案。这很难做到，需要耗费大量精力，而且做得好时往往看起来你并没有做多少事。许多领导者试图同时解决两者，但最终还是屈服于只施加感知压力、却没有思考如何将压力转化为实际物理计划的诱惑。没有计划的施压，和基础设施迁移中出现的问题是一样的：你确实能建立问责，但极有可能失败。

在某些层级上，没有计划的施压是合适的。重要的是要理解在一个特定组织里，谁负责在压力之上附加一个计划。在一个小型创业公司（几十人），这大概是创始人；在一家中型公司（几百人），很可能是高管团队。随着公司规模扩大，计划会越来越多地由远离物理层的人来制定，但你始终需要决定应该从哪里开始规划。

任何一个组织都会有一个临界点，到了那里它会放弃规划，让压力不受阻挡地层层传递。在一个高效运转的组织中，这个压力临界点会很高。而在运转不佳的组织中，即使压力很小，这种情况也会频繁发生。

如果你把压力调得太低，也会有问题。我在 Stripe 期间最大的遗憾之一，就是让我的组织承受的压力太小，久而久之形成了一个——有清晰的计划，但压力有限。我离开后，压力调节器被拿掉，我的组织在适应新环境的过程中经历了一段艰难时期。困在价值观绿洲中

总的来说，这种平衡很难维持。我仍在随着时间慢慢进步，主要从错误中学习。最后想说的是，尊重物理并不一定意味着按工程师想要的方式去做：那些为物理说话的人并不一定是对的。关键在于，根据具体情境，在两者之间做出深思熟虑、经过计算的权衡。有时这意味着勇敢地顶回一个不可能完成的时间表，有时则意味着解雇一个坚称变革不可能的领导者。
