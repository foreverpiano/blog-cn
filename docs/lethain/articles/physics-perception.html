物理与感知。

2024-06-29 · 阅读原文

2019 年某个时期，Stripe 工程团队的几个部分正在经历一场温和的内战。冲突源于一组人坚信应该用 Java 取代 Ruby。他们认为，在业务快速扩张、工程组织也迅速壮大的情况下，Java 能解决持续交付高质量平台的难题。另一组人则认为，Stripe 的问题根源在于如何打造软件质量以及众多要求严苛的外部合作伙伴——从用户到金融机构，再到政府；更换编程语言并不能解决这些问题。我与他人共同撰写了内部版的《探索的量级。》，试图为这场争论找到一个有用的框架，但两个群体依然很难在相互理解上取得多少进展。

在阅读 Steven Sinofsky 的《Hardcore Software》中关于“创新 versus 出货：Cairo 项目”那一章时，我又想起了那些讨论。

1993 年初，我桌上出现了第一份（此后还有许多份）Cairo 的计划和文档。Cairo 继承了 NT 产品流程的成熟做法——高度重视文档和架构规划——并将其进一步放大。Cairo 团队像一台运转良好的机器，很快就产出了大量文档，装订成三英寸厚的活页夹，详细描述了产品的所有举措。每当我与 Cairo 团队的人会面时，他们都对自己的规划和流程充满自信……任何观察者都理应把丰富的文档和团队的自信视为积极信号，但缺乏可运行的代码以及不断膨胀的产品定义，似乎触发了一些轻微的警报，尤其是对有着产品背景的我来说。虽然 Cairo 项目在文档形式上与 NT 项目相似，但它似乎缺少日常严格的构建、持续的性能和基准测试，以及质量与兼容性测试。还存在一种更隐蔽的动态，这种动态后来成为公司许多后续产品（尤其是操作系统）的警示。

关于 Cairo 开发和 Java 迁移的简单叙事是：一组人在做“正确”的事，另一组人在做“错误”的事。Cairo 团队在出货 vaporware，Java 团队则错误地诊断了底层问题。这类描述让人感到安心，因为它们制造了“善”与“恶”冲突的熟悉叙事结构。不幸的是，我从未发现这类叙事对理解冲突成因有什么帮助，而在真正解决冲突上则更是毫无用处。

我发现真正有用的是去研究每个派系知道而对方不知道的东西多层上下文。，并努力。有时我将其概括为“同时解决物理与感知”。有价值的权衡是多维度的。

解决感知问题

Sinofsky 把 Cairo 描述为一个过于宽泛而最终未能出货的项目，但他也解释了为什么它会吸纳那么多特性：

Cairo 倾向于把这当作一项挑战，进而不断纳入更多能力。新出现的事物会被迅速加入产品潜在特性清单。更糟糕的是，比尔·盖茨可能认为概念上相关的东西，比如第三方用于搜索硬盘上所有文件的应用程序，就可能变成 Cairo 需要具备的竞争特性。更常见的情况则是“难道 Cairo 不能再多做一点工作就实现这个吗？”于是那“一点额外工作”就成了修订后产品计划的一部分。

这并非出于恶意，他们只是想不辜负 CEO 的期望。他们希望在公司价值观体系内被视为成功的项目，因为他们正确地认识到，否则自己的项目就会被取消。

许多新上任的领导者会立即发现自己陷入类似的处境。他们刚加入，对领域或团队还不太了解，却被告知必须立刻在公司迄今为止一直受挫的一系列问题上取得进展。他们知道自己需要表现得正在做有价值的事，于是就会去做任何看起来像是在推进的事情。领导者在这种时刻启动的现象尤其常见，他们希望借此解决眼前的问题，但无论如何，这都会被视为一项勇敢而大胆的举措。大型迁移

这并非高管或产品工程师独有的问题，我经常看到平台团队在时犯同样的错误。许多平台迁移被设计成，由平台团队告知产品团队必须在某个日期前完成某项任务（例如“迁移到我们的 monorepo”），并配以仪表盘向高管汇报哪些团队已经完成、哪些尚未完成。这很好地对底层团队施加了压力，也很好地管理了感知——显得自己在强力推动。但这类迁移常常失败，因为几乎没有关注迁移本身的可用性。如果你告诉团队错过日期就是失败，他们就会拼命赶日期；如果真的很难，他们最终还是会失败。在这种情况下，平台团队往往责怪产品团队没有优先考虑自己的计划，而其实平台团队应该有自我认知，意识到正是自己没有为要求迁移的产品团队简化底层物理条件，才把事情变得困难。迁移：解决技术债的唯一可扩展方案事件响应、程序与你（的初创公司）。

解决感知问题本身并没有错，事实上这是成为有效领导者必备的技能。这里的教训是，大多数有意义的项目都需要同时解决感知和物理。

解决物理问题

我刚加入 Stripe 时，最想推动的项目之一是从手工管理虚拟机转向 Kubernetes。这很大程度上受到我此前在 Uber 将单一 Python 应用迁移到多语言、多仓库架构时学到的经验影响。在花了几个月试图在工程团队内达成共识后，我把 Kubernetes 迁移推迟了几年，因为我无法说服他们这能解决一个紧迫的问题。（后来我确实又推动了它，并且取得了成功。）我本可以强迫团队去做这个项目，但这违背我的直觉：通常当工程师对领导的想法提出反对时，总是有充分理由的。

类似地，我在 Stripe 最初推动的并不是后来成为 Sorbet 的 Ruby 类型化工作，而是设计一条增量迁移路径，迁移到现有的静态类型语言，比如 Java 或 Go。我得到的反馈是这不切实际，因为迁移成本太大，而且 Facebook 的 Hack 已经证明了从 PHP 迁移到类似 PHP 的类型化语言是可行的。我花时间去理解这些反对意见，逐渐转变了自己的想法，转而关注如何排序这些工作：即使我们最终想迁移到另一门语言，首先也需要改进架构以支持模块化迁移，而这项工作会从 Ruby 类型化中受益。

在这些案例中我很幸运，因为需要解决的感知问题很少，我得以主要专注于物理。事实上，能够专注于物理问题，是基础设施工程被低估的优势之一。在高层领导职位上，你很少能有这样的好运。

例如，我加入 Carta 时，行业内外都面临着加大 LLM 投入的压力。大多数工程师对使用 LLM 的机会持相当怀疑的态度，所以如果我只听从物理，我可能会忽略采用的压力。然而，那样做会在两个方面让我误入歧途。首先，我会严重损害更广泛的高管团队对我接纳新想法能力的信任。其次，物理是基于我们今天对世界的理解，而 LLM 是一个快速演变的领域。我们最终采用的的方式，比只解决物理所能得到的任何方案都要好。（也远好于如果我们只解决感知所能想出的方案。）在产品中使用大语言模型（LLMs）的视频

我认为 LLM 这个例子很有启发性，因为它打破了“物理是真实的、感知是虚假的”这种预期。事情可以朝任何方向发展，取决于具体情境。一旦你自满地认为自己的视角就代表现实，很快就会被现实纠正。

平衡物理与感知

有效的领导者会将感知和物理融合成能同时解决两者的方法。这很难做到，需要花费大量精力，而且做得好时，往往看起来你并没有做多少事。许多领导者试图同时解决两者，但最终还是屈从于只施加感知压力的诱惑，而没有思考如何将这种压力引导到一个切实可行的物理计划中。没有计划的压力，和基础设施迁移中出现的问题是一样的——你当然可以建立问责，但极有可能失败。

在某些层级上，没有计划的压力是合适的，重要的是要清楚在特定组织中，谁负责为压力附加一个计划。在小型初创公司（几十人规模），这可能是创始人；在中等规模公司（几百人规模），很可能是高管团队。随着公司扩张，计划会越来越多地由远离物理的人来制定，但你始终需要决定规划应该从哪里开始。

任何组织都会有一个临界点，到了那里它会彻底放弃规划，让压力不受阻挡地层层传递。在运转良好的组织中，这个压力临界点非常高；在运转不佳的组织中，即使压力很小，这种情况也会频繁发生。

如果你施加的压力太小，当然不好，但施加太多压力也同样不好。我在 Stripe 期间最大的遗憾之一，就是让组织承受的压力太少，这逐渐形成了一个——它有清晰的计划，但压力也有限。我离开后，压力调节器被完全打开，我的组织在适应新环境时经历了一段艰难时期。困在价值观绿洲中

总的来说，这种平衡很难维持。我仍在随着时间慢慢进步，主要通过犯错来学习。最后想说的是，尊重物理并不一定意味着按照工程师希望你做的那样去做：为物理说话的人并不总是正确的。关键在于，根据具体情境，在两者之间做出深思熟虑、经过计算的权衡。有时这意味着勇敢地回拒一个不可能的时间线，有时则意味着解雇一个坚称变革不可能的领导者。
