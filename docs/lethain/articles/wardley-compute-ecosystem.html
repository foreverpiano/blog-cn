当前的工作方式

服务供应流程涉及三个主要内部团队。服务供应团队将产品工程团队开发的应用程序与服务器运维团队管理的服务器进行抽象。随着为支持应用扩展而不断增加服务器，这一过程对应用程序自身是透明的，从而让产品工程师能够专注于公司最重视的事情：开发更多应用功能。

当前价值链中的挑战包括成本高效的扩展、可靠的部署以及快速部署。这三个问题都根植于同一个底层问题——资源调度。我们希望对改进资源调度进行重大投入，并认为理解行业在资源调度上的趋势是做出有效选择的基础。

向未来状态过渡

大多数有趣的集群编排问题都围绕集群元数据和资源调度展开。请求路由（无论是通过 DNS 记录还是分配的端口）依赖于集群元数据。将服务映射到服务器集群依赖于资源调度对集群元数据的管理。部署和自动扩缩容也都依赖于集群元数据。

这也是我们在 2014 年看到发生重大变化的领域。

Uber 最初使用 Clusto 来解决这个问题，这是一个由 Digg 发布的开源工具，其目标与 Hashicorp 的 Consul 类似，但采用程度有限。我们还使用 Puppet 配置服务器，并辅以自定义脚本。这种方案虽然可行，但需要持续进行自定义的调度支持。我们面临的关键问题是：是自己构建调度算法（例如 bin packing），还是采用其他不同的方法。很明显，行业正打算通过两条路径直接解决这个问题：依赖云提供商进行编排（Amazon Web Services、Google Cloud Platform 等），以及采用 Mesos 和 Kubernetes 等开源调度框架。

拥有五年以上基础设施经验的行业同行几乎一致地采用开源调度框架，以更好地支持他们的物理基础设施。这将为他们提供一个工具，实现从物理基础设施到云基础设施的桥接式迁移。

基础设施存量较少的新兴公司则直接转向云，从而完全避开了编排问题。唯一没有采用这两种方法之一的公司，要么是规模极其庞大且复杂（比如 Google 或 Microsoft），要么是对任何技术变更都极为抗拒。

从这一分析来看，继续依赖 Clusto 和 Puppet 将是一项代价高昂的投资，而且与行业的演进方向并不特别一致。

用户与价值链

这张地图聚焦于单一公司内部的编排生态系统，特别关注从大约 2008 年到 2014 年期间保持不变和发生变化的部分。它重点关注三类用户：

产品工程师专注于供应新服务，并在做出修改后部署该服务的新版本。他们只关注自己的服务，完全 unaware 编排层之下的任何内容（包括任何服务器）。服务供应团队专注于供应新服务、为这些服务编排资源，并将流量路由到这些服务。该团队充当产品工程师与服务器运维团队之间的桥梁。服务器运维团队专注于增加可用于编排的服务器容量。他们与服务供应团队紧密合作，与产品工程师没有直接接触。

值得说明的是，在实际中，这些是多个底层团队的人为聚合。例如，服务与服务器之间的流量路由通常由流量或服务网络团队负责。然而，这些省略是为了清晰地突出与编排工具演进相关的关键区别。
