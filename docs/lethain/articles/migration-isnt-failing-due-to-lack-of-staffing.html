你的迁移项目卡住，可能并不是因为人手不足。

2022-05-05 · 阅读原文

最近和一位朋友聊天时，他所在的公司正陷入一个常见的开发者生产力陷阱。公司高层强制要求从单体架构和单体仓库转向新架构，但迁移工作却陷入停滞。为了加快过渡，负责的基础设施团队决定停止支持旧的单体系统，转而专注于新的服务环境。两年后，工程师们纷纷离职，只为逃离迁移的两边：既不完整的新服务生态系统，也停滞不前的旧单体生态系统。工程师们开始对基础设施团队及其艰难的迁移项目产生怨恨。基础设施团队也很恼火，尤其把矛头指向了工程领导层，认为他们通过资源投入不足在破坏这项关键迁移。

迁移故事对我来说特别有吸引力，因为我坚信迁移：解决技术债务唯一可扩展的办法。。它们也很有趣，因为一次糟糕的迁移可能会把事情搞得非常糟糕。在这个案例中，他们的工程组织仅仅用了两年时间，就损失了数十年积累的工程速度，而不断加速的人才流失又让他们面临失去更多十年积累的风险。数十年啊！

在大多数组织中，集中式的基础设施和开发者生产力团队承担了绝大部分迁移工作。当迁移出现问题时，我在负责这项工作的人中最常遇到的自我限制信念是：他们失败是因为人手或资源不足。我认为把问题归咎于人头数是一种自我限制的信念，因为这是最没有帮助的解释；即使它部分正确，也总能找到更有价值的解释。

好，让我们快速浏览几个主题：

为什么人手不足不是一个有用的解释 找到更好的方法来诊断陷入困境的迁移 作为负责棘手迁移的领导者，你有哪些选项

让我们深入探讨。

“我们需要更多人手”

我在领导大型组织时发现特别有用的一个工具是业务回顾模板。领导者会写一份自己领域的总结，并将当前进展与过去情况和现有目标进行对比。这些文档的大多数版本都会包含一个部分：“什么在拖慢你的速度？”我推行和运行这个流程的次数足够多，知道领域负责人最初回答这个问题时，常常会说他们“需要更多人手来完成目标”。

我的建议是：几乎说什么都行，就是别这么说。我认为把人头数当作答案没有帮助，有几个不同原因：

人头数不过是预算的另一种说法，所以这基本上等于在说，“如果我们在这里投入更多钱，就不会有问题了。”只有当你有充分理由相信自己当前的策略和执行都很出色时，这个答案才有趣。否则，投入更多钱是一种非常低效的做法。 同样，你的规划流程本应将目标与计划的人头数挂钩。如果你拥有规划目标时所预估的人头数，那么要求增加人手就等于承认你没有按计划推进。这意味着你的策略或执行在当前问题和人头限制下并不奏效。一定存在比单纯增加人手来强行推进当前方法更有价值的改变，无论是调整方法本身，还是重新定义问题。

根据我的经验，那些“资源不足”的基础设施团队领导者，要么不理解为什么迁移进展不佳（下一节会讨论），要么已经忘记了如何投资技术基础设施：

如果你没有做好挑选问题和解决方案的工作，那么一家运转良好的公司就会减少你团队的编制。拥有大量自由支配预算是一项需要努力争取并持续维护的机会。

如果你的基础设施组织资源太少，那么你很可能没有向制定组织预算的人展示出足够价值。他们知道你们在做什么吗？他们认同这很重要吗？你如何有意识地根据他们认为重要的事情来验证自己的计划？你如何努力从你的视角教育他们了解组织当前的需求？把大部分时间花在推动领导层关心的目标上，预算问题就会变得容易得多。

调试一次迁移

要求增加人手的另一个问题是，即使申请获得批准，短期内也不会有更多人来帮忙，而且你可能还会因为额外的面试和培训工作而变得更慢。无论如何，你都必须用现有的团队来调试和改进迁移工作。

如果你不确定迁移为什么进展不佳，这里有一些可以问的问题：

人们在迁移流程的哪个环节卡住了？如果你没有对迁移漏斗进行清晰的仪表化监控，就很难调试哪里出了问题。对于任何足够大的迁移，你都应该清楚迁移点的总数、有多少已经开始尝试迁移，以及整个漏斗的进展情况（搭建新的代码仓库、在开发环境中配置、建立值班轮换、在生产环境中配置等）。 人们是不是根本没有开始迁移？如果大家甚至没有开始迁移，那么他们要么不相信这对他们的需求有帮助，要么从某个地方收到了相反的信号，认为迁移是个坏主意（可能是以前尝试迁移却经历不佳的人）。 哪些群体成功迁移了，哪些没有？你通常会发现某些特定用例的群体迁移顺利，而另一些则不然。例如，那些习惯在生产服务器上实时调试的团队，往往会抵制任何迫使他们改用日志调试的迁移。当你理解了迁移成功和失败的群体后，就能更好地将精力集中在困难区域（加倍投入在已经进展顺利的领域可能会感觉更好，但并不能让你离完成目标更近）。 对于那些没有迁移的团队，他们现在在做什么？进展如何？当团队抵制采用某项迁移时，他们往往已经为自己的具体问题找到了更好的解决方案。也许这是你开始迁移时曾否决过的方案，也许是你最初认为迁移要解决的实际问题并没有你想象的那么重要。例如，也许你的单体系统其实对大多数产品代码来说仍是正确选择，只有高吞吐量、低延迟的组件才应该迁移到独立服务中。（这是一个可以利用开发者生产力调查来获取组织整体视图的好机会。） 对于正在迁移的团队，迁移的瓶颈在哪里？什么能解决这个瓶颈？在任何时候，迁移漏斗中通常都会有一两个环节在拖慢大家的速度。解决这些环节，你就能解锁整个迁移。例如，人们可能会请求你执行某个迁移步骤，却没有提供你解决问题所需的所有信息，导致长时间的反复沟通，而这可以通过更好的文档、结构化的工单字段，以及确保文档在请求处显著链接来避免。

当你找到这些问题的答案后，就可以提出更细致周到的求助请求：也许你需要组织批准一条修改后的迁移路径、放慢迁移速度、只迁移某些类型的工作负载，或者其他什么。你甚至可能根本不需要组织批准任何事情，而只需要调整团队每周的优先级来解决当前的瓶颈。

当你负有责任时

如果你在负责一项迁移，你唯一的选择就是诊断问题并根据当前约束调整策略，我把这称为“解决问题”。如果你是一个正面临迁移停滞的组织的领导者，你会有更多选项可以权衡。

好消息是，失败的迁移非常常见，因此有一套相当清晰的应对 playbook 可供选择。我见过最常见的四种迁移恢复 playbook 是：

“解决问题”。当你开始一项迁移时，你知道一定数量的事情，但随着推进会学到更多、更多。不断调整你的方法以融入你学到的东西。这就是我们当年在 Uber 处理自助迁移、摆脱单体系统的方式：我们尝试了“迁移试点”模式，由一个人在一周内处理所有迁移请求，以保护团队其他人的时间；我们推出了结合自助服务和自动化的模式，大幅降低了复杂度；我们创建了脚手架来减少新服务中的错误（例如缺失配置等）；我们开发了主动暴露常见错误的 linter，等等。我们持续快速迭代迁移工具，直到压力消退。负责这个自助供应和运维工具的核心团队在两年里只从两个人温和增长到大约四个人。 “不要迁移”。我在领导完 Uber 从单体系统迁移的工作后加入 Stripe，最初坚信类似的迁移对 Stripe 也会很有价值。然而，在我深入了解 Stripe 的情况期间，我对自己的雄心保持沉默，几个月后越来越清楚，这里的上下文完全不同。最后我采取了完全不同的迁移策略：根本不迁移。虽然这当然不是我一个人的决定，但我相当确信，如果我当时顽固地强推大型迁移 到服务架构，我会直接导致公司损失数十年工程生产力（需要说明的是，这绝不是说后来的 Stripe 转向服务架构是错误的，只是它需要在符合探索的量级原则的时机进行）。 “取消迁移”。我曾经加入过一个正在从 Node.js 单体系统迁移到 Go 微服务的组织。在深入细节后，我发现它陷入停滞、引发分歧，而且与我们最大的问题不匹配：它优先考虑的是我们本已成本低廉的基础设施的可扩展性，却忽视了我们最迫切的需求——提升产品开发速度。我取消了这项迁移，这是一个有争议的决定。取而代之的是，技术领导团队花时间重新思考他们的目标，最终采用了不同的方法，逐步从 JavaScript 迁移到 TypeScript，并在接下来的一年内成功完成。 “为当前迁移策略增加人手”。当然，你也可以按照拥有团队所要求的规模，为当前的迁移策略配备人员。我把这个策略包含进来是为了逻辑上的完整性，但我个人从未见过一个陷入困境的迁移通过这种方式恢复。从根本上说，选择一个依赖于并不存在资源的迁移策略的决策过程，通常不仅仅是单纯的人数问题，还涉及更深层的技术问题。

虽然我不能推荐第四种 playbook，但其他三种在经历最初的不适后都非常有效。停滞的迁移具有极强的破坏性，如果你是一名工程领导者，而你的组织正在进行一项失败的迁移，那么最终的责任在于你去调试和解决它。如果你不确定该怎么做，我想把早年职业生涯中得到的一条建议留给你：几乎在任何情况下，果断地在较早时候做出一个合理的决定，都比长时间拖延决策要好。
