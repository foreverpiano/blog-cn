描述故障域

2019-08-17 · 阅读原文

故障域 是我在架构可靠系统时发现的最有用的概念之一，却没有得到足够的重视。如果你希望让自己的软件可靠性可预测，包括衡量可靠性风险，那么这个概念非常值得花时间深入研究。

故障域是一组功能、服务或组件，它们共享同一个单点故障。故障层级则是由一个或多个服务相同目的的故障域组成的集合。例如，如果你跨多个 AWS Region 运行 active-active 架构，那么“AWS Region”就是你的故障层级，而具体的区域（如“us-east-1”和“us-east-2”）就是你的故障域。

每个故障层级都存在于一个故障层级结构中，其中较小的故障层级（例如数据库副本）嵌套在较大的故障层级（例如数据库集群）之下。这种嵌套让较大的层级能够为较小层级内部的故障提供深度防御。

每个故障层级都有三种故障策略之一，用于描述该层级发生故障时的正确行为：

冗余（redundant）意味着该层级内的故障域可以接管某个失败域的责任。例如 Cassandra 或 Memcache 集群中的节点，或是支持丢失一个 AWS Availability Zone 的架构设计。（如果冗余层级内只有一个或零个健康域，则其行为会遵循下面 cascade 策略所描述的情况。）可忽略（ignorable）要求故障层级结构中更高层的故障层级能够在该层级失败时继续运行。例如，一个网站可以在故事中用你朋友们的社交行为进行注释，但如果存储这些数据的数据库不可用，它会停止显示该社交上下文，同时继续渲染页面的其他部分。级联（cascade）则警告说，当该故障层级失败时，它既不是冗余的，也不是可忽略的，因此其上层的故障层级必须为该故障承担责任。任何单点故障都会以这种方式运行，例如没有自动 failover 的传统 MySQL 设置会发生级联；运行在 read-majority 配置下、无法完成多数派读操作的 Cassandra 集群也是如此。

示例：社交新闻网站

让我们从一个实际例子开始，来看如何将这些想法应用到一个应用上。以运行在 Amazon Web Services 上的类似 Reddit 或 Digg v4 发布：源于迫切的乐观。 的社交新闻网站为例。

当你原型开发这个应用且用户流量还不高时，初始设置可能包含两个组件：渲染页面的 Web 服务器和存储待渲染数据的数据库。

这两个组件对应四个故障层级（数据库、Web 服务器、可用区、区域），每个层级都由一个脆弱的单实例故障域组成，失败时会向上级联。在这种配置下，任何一个故障层级的任何故障都会导致整个故障层级结构全部失效。

这听起来不太好，因此下一步你会去修复最成问题的那个故障层级。对大多数公司来说，最简单的办法是运行多个 Web 服务器，并将它们分散到多个可用区。这样，你的 Web 服务器就能承受其中一个故障域的失败，甚至能承受整个可用区的失败。

这引入了几个新的故障层级，特别是每个可用区对应一个新层级，以及每个可用区的 Web 服务器对应另一个层级。这些新的层级都会向上级联到一个 Web 服务器故障层级，而这个层级不再是级联型故障层级，而是变成了冗余故障层级。如果 Web 服务器层级下的某个故障域失败，另外两个故障域会继续工作，从而阻止故障向上传播。（如果三个可用区全部失败，那当然，你就完蛋了。）

另一方面，我们的数据库仍然暴露在单个可用区故障的风险之下，这非常不可取。你可以切换到高可用数据库配置，比如使用 Cassandra，这样就能抵御任何可用区的故障。

现在你的架构已经相当稳固了，但工作永远不会结束。你总是可以在顶层添加更多故障层级（那个级联的 AWS Region 现在看起来有点吓人），而在底层添加更多层级也非常有价值，尤其是在故障率开始上升的时候。

箭头不应该指向相反的方向吗？

随着我绘制越来越多的故障层级结构图，我逐渐相信线条几乎可以朝任何方向绘制，而无论是哪个方向，都会让某些读者感到意外。

我用来决定箭头方向的指导原则是：较小的故障层级应该指向它们会级联的方向。如果你有两个故障域，其中一个失败时另一个可以不受影响地继续运行，那么能够承受对方失败的那个就是“父层级”，线条应该指向父层级。

相反，如果两个故障层级是相互失败的关系（例如其中任何一个失败都会导致另一个也失败），那么箭头指向哪个方向都可以：两个方向都能帮助你正确地理解底层系统。

为什么要关心小的故障层级？

一旦你在故障层级结构的较高层拥有了一个冗余故障层级，常见的问题就是是否值得继续投入精力让更低层的故障层级也实现冗余。因为每个冗余故障层级都会掩盖其下层故障，所以这是一个相当好的问题。

你应该继续在所有故障层级上投入的理由有两个：

即使在可忽略和冗余的故障层级中，当某个故障域失败时，也经常会出现短暂但明显的性能下降。（例如，从主数据库切换到备数据库可能需要 15 秒，这段时间短到可以认为你拥有冗余，但又长到足以影响用户。）较高层的故障域虽然可以掩盖其包含的较低层级的故障，但如果你想象有三个可用区，那么你总共只能容忍这三个可用区内所有下层故障层级的并发失败。当系统变得足够庞大和复杂时，这并不算多。通过拥有多层冗余，你能更好地应对那些意想不到的、并发且不相关的故障时刻。

综合来看，你绝对需要几个大型的冗余故障层级，但如果你不在整个层级结构上都进行投入，仍然会面临相当大的风险。

层级违反

故障层级常见的一个挑战是层级违反，即较高故障层级隐含地依赖于较低层级。一个典型的例子是迁移到多区域架构，但数据库复制方案却让数据库集群成为比区域更高的故障层级，导致集群故障会把所有区域全部拖垮。糟糕。

确保没有引入层级违反的方法是，定期演练你的每个故障层级，特别是那些构成你冗余核心的层级。如果你没有频繁演练这些层级，就很容易引入层级违反，从而导致意想不到的级联故障。

扩展技术一致性 是另一种减少层级违反的 somewhat 有效机制，但它依赖于人类始终保持完美，这很少是一种长期成功的策略。

衡量可靠性风险

故障层级的最后一个用途是，它可以作为一种有效方法来不可量化的度量指标，至少在可靠性方面是如此。

一旦你有了自己的故障层级结构，你就能明确说出自己有多少个级联层级，每个层级都代表一种可靠性风险来源。跟踪这个数字是衡量整体可靠性的第一个方面（本质上是以结构化的方式跟踪单点故障）。

第二部分是衡量你演练每个冗余和可忽略故障层级的频率。如果它们最近没有被演练过，那么实际出问题时很可能无法正常工作。

将这两者结合起来，你就得到了一个非常有用的指标来长期衡量可靠性：你有多少个级联故障层级？以及距离你上次演练冗余故障层级已经过去多久？

这让你摆脱了衡量“几个九的 uptime”等难题——那些是输出指标，可能只是运气好，而不是有效规划的结果，转而采用你可以直接投入资源并产生影响的度量方式。

如果你还没有使用故障域来思考自己的软件，我建议花几天时间画出你最初的故障层级结构，特别是理解每个域的策略，并检查你的层级违反情况。这会让你对自身风险有比以前清晰得多的认识，让你能够衡量进展，并获得一些非常需要的全局视角。
