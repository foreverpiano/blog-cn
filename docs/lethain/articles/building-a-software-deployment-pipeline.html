构建软件部署流水线

2014-03-30 · 阅读原文

当 Digg 的工程团队被并入 SocialCode 时，我们面临着一大堆技术和文化上的难题需要思考，但最紧迫的挑战是如何为一个一夜之间规模翻倍的工程团队扩展流程。

虽然我一直认为 ，但它可能并不是扩展团队和流程的首选机制。可重复的部署流水线才是扩展工程团队的第一选择，也是最佳工具。开发面向服务的架构

一个优秀的部署流水线应该：

让新员工第一天就能部署代码到生产环境，在有问题的变更集到达客户之前就将其拦截，用平凡、可预测的系统取代神秘的部署过程，并加快开发速度。

那么，这具体是什么样的呢？

[TOC]

我们的方法需要用到以下几种工具：

代码仓库（git、hg 等），带 hook 的代码审查机制（gerrit、bitbucket、github 等），构建服务器或服务（Jenkins、Travis CI 等），以及将代码部署到服务器的机制（chef、clusto 等）。

你选择的工具组合会产生重大影响，但任何合理的选择都能支撑起一个可行的部署流水线。我个人对 Git、Github、Jenkins 和 Chef 的组合有很好的使用经验，推荐作为起步点。

（除非你特别喜欢折腾，否则 Gerrit 可能不是一个好的起点。）

有了这些工具，让我们站在一位希望将代码部署到生产环境的工程师的角度来看。他们的工作流程大致是这样的（假设这次变更没有争议，也不会破坏任何测试）：

他们在个人代码仓库中开发变更。准备好审查后，他们将变更集推送到代码审查系统，系统会自动通知同事有新的变更集等待审查。代码审查通过后，提交者将变更集合并到权威代码仓库中。构建服务器在变更部署到 alpha 环境服务器后会发送邮件通知。QA 团队或工程师在 alpha 环境上简单验证后，在构建服务器上点击按钮部署到 staging。构建服务器在变更部署到 staging 后再次发送邮件通知。他们再点击另一个按钮，将代码推广到生产环境。当构建服务器通知他们代码已上线生产后，他们在生产环境中验证一切正常。成功。

提交者在整个部署过程中投入的时间和精力相当少，同样重要的是，这些步骤直截了当，既不需要非凡的判断力，也不需要死记硬背。

现在，让我们从工具的角度来看同样的流程：

代码审查工具接收变更并通知团队。代码审查完成后，代码审查工具将变更合并到 alpha 分支。构建服务器检测到 alpha 分支有新变更后：运行语法和风格检查器，运行单元测试，通知服务器配置工具将 alpha 部署到 alpha 服务器，部署完成后，对 alpha 环境运行集成测试。当有人手动触发 staging 构建时：将 alpha 合并到 staging，通知服务器配置工具将 staging 部署到 staging 服务器，部署完成后，对 staging 环境运行集成测试。当有人手动触发生产构建时：将 staging 合并到 production，通知服务器配置工具将 production 部署到生产服务器，部署完成后，对生产环境运行集成测试。成功。

工具链完成的每一步，都是工程师不再需要亲自执行的步骤，也是他们无法搞砸、遗漏或忘记的步骤。这就是部署流水线如何在提高开发者吞吐量的同时，提升可预测性的原因。

随着团队和组织的成长，事情会以你无法有效预见的方式发生变化：你可能会决定需要一个手动 QA 团队，你可能会采用另一种编程语言，你可能会转向使用独立代码库的静态 JavaScript 前端，或者其他十几种情况。

你的部署流水线需要能够适应这种不可知的未来。

你可以通过以下机制逐步引入更多工具，并管理速度与安全之间的权衡：

小型且经验丰富的团队可以跳过代码审查，直接合并到权威代码仓库。每个构建可以选择启用哪些工具：语法和风格检查器（例如 pylint、pep8 或 jshint）对新项目非常好，但对遗留项目可能过于严格；如果你使用 precommit hook 来运行测试，就可以跳过构建时的测试；你可以添加额外的验证工具和检查。每个项目为每个环境都有独立的构建，允许你根据以下情况运行不同的验证：你要部署到的环境（例如在 alpha 环境只对变更文件运行测试，但在合并到 staging 环境前运行完整测试套件）；项目类型：一个仅供内部使用的工具可能不需要太多验证。拥有三个环境（alpha、staging、生产）是很常见的，但也相当随意。一条经验法则：如果你有超过三名工程师，你可能需要两个环境；如果你有手动 QA，或者希望将生产发布错开超过几天，那么你可能需要三个环境。从 alpha 到 staging 以及从 staging 到生产的过渡可以是自动的。将过渡设为手动能更好地控制上线时机，也便于进行手动测试，但最终选择取决于你！

使用像 Jenkins 这样的构建服务器时，你的构建其实就是一个在满足特定条件时执行的脚本，这给了你极大的灵活性来针对自己的情况进行优化。因此，限制主要来自于想象力……或者因为你的构建服务器还运行着 Ubuntu 12.04。

以下是一些不需要单独成节的额外思考：

什么时候应该引入部署流水线？如果你是一个只有两三名工程师的创始团队，尤其是如果你们都不太擅长系统管理，那么维护流水线的开销可能会高到盖过其带来的收益。一旦你开始招聘非创始工程师，可能就是时候投入进去了。那紧急和紧急推送时要绕过防护措施怎么办？正常的部署路径应该始终是最佳路径，尤其是在紧急时刻。如果不是，那就思考如何调整你的部署流程，让它成为最佳路径。（你可能已经习惯了当前构建流水线中的某个严重性能问题，或者你的单元测试编写方式导致它们依赖外部资源。这两者都是不好的，应该修复。）为什么不采用持续部署？这种方法会对 alpha 环境进行持续部署，但后续需要人工审批才能继续。经验表明，将代码合并和部署到生产环境耦合在一起，会以最不愉快的方式验证你的测试质量。（如果责任人中途已经下班，这还能很好地帮你发现同事额头上的青筋。）自动化构建的一个意外好处是减少了你提供语法和风格反馈的义务，这类反馈有时会让你和接收反馈的人都质疑自己选择的职业。相反，你可以依靠构建服务器来当这个挑剔的人——作为一个没有灵魂的自动机，它在这方面做得极好。

我在这里描述的部署流水线只是基础版本，还有很大改进空间，但我亲眼见过推出一个舒适的部署流水线所带来的影响，它绝对是我在扩展团队和改善工程师生活质量时的首要 checklist 项目。

希望这里有些有用的内容，一如既往，我很乐意听到建议和替代方案！
