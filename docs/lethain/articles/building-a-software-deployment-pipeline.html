构建软件部署流水线

2014-03-30 · 阅读原文

当 Digg 的工程团队被收购并并入 SocialCode 时，我们面临大量技术和文化上的难题需要思考，但最紧迫的挑战是为一个成员数量一夜之间翻倍的工程团队扩展流程。

虽然我曾提出 ，但它们可能并不是扩展团队和流程的首选机制。可重复的部署流水线才是扩展工程团队的首要且最佳工具。开发面向服务的架构

一个优秀的部署流水线能够：

让新员工在入职第一天就能部署代码到生产环境，在坏的变更集到达客户前将其阻止，用平凡、可预测的系统取代部署的神秘感，并加快开发速度。

那么，这具体是什么样的呢？

[TOC]

我们的方法需要用到以下几种工具：

代码仓库（git、hg 等）、带钩子的代码审查机制（gerrit、bitbucket、github 等）、构建服务器或服务（Jenkins、Travis CI 等）、将代码部署到服务器的机制（chef、clusto 等）。

你选择的工具组合会产生显著影响，但任何合理的选择都能支撑起一个可行的部署流水线。我对 Git、Github、Jenkins 和 Chef 有丰富的使用经验，并推荐将其作为不错的起点。

（Gerrit 除非你特别擅长折腾，否则很可能不是一个好的起点。）

有了这些工具，让我们站在一位希望将代码部署到生产环境的工程师的角度来看。他们的工作流程大致如下（暂且假设这个变更没有争议，也不会破坏任何测试）：

他们在个人代码仓库中开发变更。准备好审查后，将变更集推送到代码审查系统，系统会自动通知同事有新的变更集等待审查。代码审查通过后，提交者将其变更集合并到权威代码仓库中。构建服务器在变更部署到 alpha 环境服务器后发送邮件通知。QA 团队或工程师在 alpha 环境上简单验证后，在构建服务器上点击按钮，将其部署到 staging 环境。构建服务器在变更部署到 staging 后再次发送邮件通知。他们再点击另一个按钮，将代码推送到生产环境。当构建服务器通知他们代码已上线生产环境时，他们在生产环境中进行验证。一切顺利。

提交者在整个部署过程中投入的时间和精力相当少，同样重要的是，这些操作直截了当，既不需要高超的判断力，也不需要死记硬背。

现在，让我们从工具的角度来看同样的流程：

代码审查工具接收变更并通知团队。代码审查完成后，代码审查工具将变更合并到 alpha 分支。构建服务器检测到 alpha 分支有新变更后：运行语法和风格检查器，运行单元测试，通知服务器配置工具将 alpha 部署到 alpha 服务器，部署完成后对 alpha 环境运行集成测试。当有人手动触发 staging 构建时：将 alpha 合并到 staging，通知服务器配置工具将 staging 部署到 staging 服务器，部署完成后对 staging 运行集成测试。当有人手动触发生产构建时：将 staging 合并到 production，通知服务器配置工具将 production 部署到生产服务器，部署完成后对 production 运行集成测试。成功。

工具链执行的每一步，都是工程师不再需要亲自完成的操作，也是他们无法搞砸、遗漏或忘记的步骤。这就是部署流水线如何在提升开发者吞吐量的同时提高可预测性。

随着团队和组织规模的扩大，事情会以你无法有效预见的方式发生变化：你可能会决定需要一个手动 QA 团队，可能会采用不同的编程语言，可能会转向使用独立代码库的静态 JavaScript 前端，或者其他十几种变化。

你的部署流水线需要能够适应这个未知的未来。

你可以通过以下机制逐步引入更多工具，并管理速度与安全性之间的权衡：

规模小且经验丰富的团队可以跳过代码审查，直接合并到权威代码仓库。每个构建可以选择自己启用的工具：语法和风格检查工具（例如 pylint、pep8 或 jshint）对新项目非常有用，但对遗留项目可能过于严格；如果你使用 precommit hook 来运行测试，则可以跳过构建时的测试环节；你可以添加额外的验证工具和检查。每个项目针对不同环境都有独立的构建，允许你根据以下因素运行不同的验证：你要部署的目标环境（例如在 alpha 环境只对变更文件运行测试，但在合并到 staging 环境前运行完整的测试套件）；项目类型：仅供内部使用的工具可能不需要太多验证。拥有三个环境（alpha、staging、生产）相当常见，但也相当主观。一条经验法则：如果团队超过三名工程师，你很可能需要两个环境；如果你有手动 QA，或者希望将生产发布错开超过几天，那么你很可能需要三个环境。从 alpha 到 staging 以及从 staging 到生产的过渡可以是自动的。将过渡改为手动能提供对发布时机的更多控制，也便于进行手动测试，但最终选择权在你！

使用像 Jenkins 这样的构建服务器时，你的构建其实就是一段在满足特定条件时执行的脚本，这赋予你极大的灵活性来针对自身情况进行优化。因此，限制主要来自想象力……或者因为你的构建服务器还运行着 Ubuntu 12.04。

以下是一些不值得单独成节的补充想法：

什么时候应该引入部署流水线？如果你是一个由两三名工程师组成的小型创始团队，尤其是在你们都不太擅长系统管理的情况下，维护流水线的开销可能会高到盖过其带来的收益。一旦你开始招聘非创始工程师，就差不多是时候投入进去了。那紧急和应急推送时该如何绕过安全机制呢？正常的部署路径应该就是最优路径，尤其是在紧急时刻也不例外。如果不是，那就好好反思如何调整你的部署流程以实现这一点。（你可能已经适应了当前构建流水线中某个严重的性能问题，或者你的单元测试编写方式导致它们依赖外部资源。这两种情况都很糟糕，值得去修复。）为什么不采用持续部署呢？这种方法会对 alpha 环境进行持续部署，但后续步骤需要人工审批。经验表明，将代码合并与部署到生产环境强绑定在一起，会以最令人不快的方式验证你测试的质量。（如果责任人在此期间已经下班回家，这还能很好地帮助你发现同事额头上的青筋。）自动化构建一个意想不到的好处是减少了你提供语法和风格反馈的义务，这类反馈有时会让你和接收反馈的人都质疑自己选择的职业。相反，你可以依靠构建服务器来做这个较真的工作——作为没有灵魂的自动机器，它在这方面做得非常出色。

我在这里描述的部署流水线是基础版的，还有很大的改进空间，但我亲眼见过推出一个令人愉快的部署流水线所带来的影响，因此它绝对是我在扩展团队和提升工程师生活质量清单上的第一项。

希望这里有一些有用的干货，一如既往，我很乐意听到大家的建议和替代方案！
