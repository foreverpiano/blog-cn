Ambush Code Review 学会了生成代码差异

2008-06-18 · 阅读原文

今天我花了几个小时重构了 Ambush Code Review，它已经变得比最初的实现好得多。主要有两个重要改进：

使用起来更方便了。它现在能做一些真正有趣的事情。

以前，对代码片段发表回复的操作相当别扭。我自己当然知道怎么用，但不确定其他人是否清楚，而且那本来就是一个不太理想的折中方案。现在，只需点击两下按钮，就能用你的修改更新已发布的片段。但真正有趣的新功能是：它现在可以生成同一片段不同版本之间的差异（diff），并将它们显示在当前版本的下方。

你可以去看截图对应的那个代码片段，我觉得这是一个相当吸引人的特性。因为 ACR 的核心目标就是让大家更容易对代码片段提出改进建议（比如，当有人把代码片段贴到 IRC 聊天室求助时，如果能直接向他们展示如何修复，岂不是很棒？）。

现在它已经从一个粗糙的“me too”服务向前迈了一步，变得稍微有趣了一些，我很乐意听到大家的反馈。

也就是说，我几乎什么都没做，只是简单地调用了模块提供的一个函数。但之后的事情就变得有点棘手了。

问题始于 BigTable 中用来描述字段的 db.ListProperty 属性，它需要一个类型参数。当然，没问题。它要求类型必须是特定列表中的一个。好吧，有一大堆可选类型，也没问题。它还要求列表中的所有条目必须是同一类型。嗯，我只想存 diff，所以类型肯定一致，也没问题。然后它在你设置了 db.Text 属性类型后却无视了它，并抱怨说 unicode 类型不能在数据库中存储超过 500 字节的内容。这就成了问题。

于是我用一些老派 ingenuity 和新派对后果的漠不关心，临时拼凑出了自己的列表方案——使用 simplejson 进行序列化和反序列化。

我不会说这是一个绝妙或甚至是好的方案，但它是一个足够好的方案，而这似乎正是 Web 应用最终都会回归的本质。数据库访问次数被降到了最低，而 CPU 在 Web 开发中几乎从来都不是瓶颈。你可能会问我为什么选择 simplejson 而不是 pickle，答案其实很简单：simplejson 用起来非常方便，省去了我必须用 StringIO 来模拟文件让 pickle 进行序列化和反序列化的麻烦。

希望这个代码解析还算有点意思，如果有任何问题，欢迎告诉我。
