有主见的编程语言、芸芸众生与精英主义

2008-01-19 · 阅读原文

Java 和 Scheme 有什么共同点？

嗯，它们之间差异很大。Java 是一门命令式语言，常引发人们对它的语法和表达力不足的愤怒吐槽。而 Scheme 是一门函数式语言，其缺乏语法这一点却常常被人写成深情款款的十四行诗。Scheme 作为函数式语言，并没有为命令式编程风格提供有效的支持；而 Java 作为命令式语言，也没有为函数式编程风格提供有效的支持。

那么，为什么 Scheme 被视为「聪明人的语言」，而 Java 却被当成「大众的语言」呢？

标准解释

在阅读关于 LFM 与 LFSP 的文章时，我们通常会看到一个听起来很舒服的解释：

LFM 的设计有意限制用户的能力，因为能力太危险；而 LFSP 则不会给用户施加不必要的限制。

然而，仔细审视这个解释，会发现其中存在一些漏洞。

首先，Java 的设计目标是可预测性和一致性，而不是出于对用户的恐惧而刻意限制其能力。Java 的限制是为了服务广大社区，它宁愿给个别用户带来不便也要达成这一目标。它把全局一致性看得高于个人能否使用自己偏好的抽象和构造。Java 希望你通过编写带有公共 API 的封装库来构建抽象。虽然我们很少从这个角度看待 Java，但它其实是一门执着于「Only One Way To Do It」（Python 流行起来的那句箴言）的语言。

这个总结的第二个漏洞在于，Scheme 以其对函数式编程风格的极致专注，有意限制了自己的功能。我们并不介意，因为 Scheme 是函数式语言，我们不会期望一门函数式语言能出色地支持命令式编程。不喜欢函数式风格的人会远离 Scheme，但从来不会把它贬低为「大众的语言」。

用流行语来说就是：Scheme 并不是被随意限制，它是有主见的。

理性分析

事实上，Scheme 同样被其设计中根深蒂固的「意见」任意地限制着。

那我们为什么愿意接受 Scheme 的主见，却不能接受 Java 的呢？因为我们更喜欢 Scheme 的那些意见。Scheme 对命令式编程的阻碍有一个「纯粹」的理由：它在宣称函数式编程是一种比命令式编程更优越的编码方式。但实际上，Java 只是做出了另一个陈述：命令式编程是一种可行的通用编程方法。

因为 Java 对函数式支持不足而对它发火，和抱怨 Scheme 不适合写命令式代码一样荒谬：这些都不是缺陷，而是主见。我们把不喜欢的意见贬低为「给不开化的大众准备的」，而把符合当下学术潮流的意见奉为「开明」的，这其实是在自欺欺人。

让我们回到直言不讳的状态吧。

与其把 Java 称为「大众的语言」，不如直接说：「我不喜欢写 Java，因为它过于强调命令式编程。」或者「Java 在构建抽象时，把社区的价值看得远高于个人。」与其得意地称自己喜欢的语言是「聪明人的语言」，不如直接说：「我真的很喜欢函数式编程」或者「我对宏的感情大概无法用文明语言表达。」否则，就是在助长精英主义幽灵的蔓延。

这里用 Scheme 和 Java 作为两类编程语言原型的具体例子。本文并非真的在讨论 Scheme 或 Java，把它们换成其他语言也只需对具体细节稍作修改即可。特别是 Haskell 可能比 Scheme 更能说明问题，但这里还是选择了我自己比较熟悉的语言来谈。↩我认为 Python 3000 通过简化语言来获得更高的整体一致性，也体现了类似的思路。最闪亮的例子就是去掉了魔法般的 print 语句，换成一个语法与其他语言特性保持一致的函数。↩必须承认，Java 为了保持自身相关性，不断在添加新的语言特性，随着时间推移，它已经变得不那么「Only One Way」了。↩如果 Scheme 勉强允许非函数式特性让你觉得这个论点不够有力，请换成 Haskell，或者想想它缺少一个标准的命令式 for 循环。↩
