搞定你的架构面试

2016-09-27 · 阅读原文

我印象最深的一次面试，一开始就遇到了一个完全意想不到的问题：“你还记得多少微积分？” 我笑了笑，说已经好几年没碰过了，相当生疏。尽管如此，我们还是花了接下来整整一个小时尝试做微积分题，而我表现得一塌糊涂。

很多人对“架构面试”都有类似的顾虑，而这类面试正是我最喜欢的用来考察来自互联网行业有经验候选人的方式之一。因此我决定写下自己应对这类问题的思考框架。

在正式开始之前，先来看几个典型的架构面试问题示例：

为 Facebook、Twitter、Uber 或 Foursquare 设计架构。为你选择的某个基础 Web 应用画出架构图。设计一个类似报纸网站那样可靠的网站。为一款手机游戏设计一个可扩展的 API。

从这个起点出发，面试官会继续给你增加更多约束条件（“你的数据库开始过载了”），或者让你思考系统可能会遇到哪些扩展性问题以及如何解决它们（“首先，我认为我们会耗尽处理传入请求的 worker”）。

这类面试的基本解题思路是：

画出你当前的设计。给你的设计施加一个新的约束。找出该约束导致的瓶颈。更新你的设计以解决这个瓶颈。

光这些可能还不足以帮你顺利通过下一次架构面试，因此本文接下来的部分将先简单介绍如何绘制架构图，然后深入探讨特定约束所带来的瓶颈。

绘制架构图

关于技术绘图，最重要的一点是：它更像是一门艺术，而非科学。只要你始终保持合理且一致的做法，就不会有问题。

面试过程中，你几乎总是在白板上作图。但如果你有机会在电脑上画图，我强烈推荐 Omnigraffle。虽然它价格不菲，但我认为值得投资（除了画架构图，我还用它来做线框图）。

下面我们来看几个例子。

左边是一台同时运行 Web 服务器和数据库的服务器，右边是两台服务器：一台运行 Web 服务器，另一台运行数据库。

虽然绘图规范很少，但通常来说，服务器用方框表示，进程也用方框表示，而数据库或其他存储机制用圆柱表示。不过全部都用方框也没问题。服务器命名一般采用“服务器类型 + 唯一编号”的方式，例如 frontend01 和 frontend02 分别表示 frontend 类型的第一台和第二台服务器。编号在你需要添加更多服务器时会很有帮助。用 01 而不是 1 来表示数字是非常随意的做法，但这也算是一种“信号”，暗示你曾经为超过九台服务器的组命名过（当然，你可以提出很多合理理由说明这种命名方式不好，但它更像是一种常见做法，而非最佳实践）。

接下来，我们展示两个数据中心，它们从代表互联网的那个神奇“云”中接收流量。

根据奇怪的约定，互联网总是用云来表示。如果你有一个移动设备连接到你的应用，通常会画出移动设备，连一条线到互联网，然后继续如上所示（网站也是同样画法）。

数据中心或地域是指物理上集中在一起的服务器组，通常用一个大方框把若干服务器围起来（就像服务器内的进程用方框画在服务器方框内一样。从这个角度看，认为数据中心之于服务器，就像服务器之于进程，也算合理）。

正如前端（fe）和应用（app）两层服务器之间那样，当连线会让图变得太乱时，我经常会省略连线。我个人认为，如果“清晰有效”和“完全准确”发生冲突，图应该优先选择前者。

总结来说：多用方框，少用连线，尽量保持简洁。现在，让我们继续进入问题解决部分！

画图、加约束、解决问题、重复

现在我们进入核心内容了。在每个小节中，我们会先展示一个起始架构图，然后给它施加一个约束，诊断该约束意味着什么，最后画出更新后的架构图来解决这个问题。可能的约束有很多，我们无法全部覆盖，但希望通过足够多的例子让你有所了解。

Web 服务器过载

你正在一台服务器上运行自己的博客，它是一个用 Python 编写的简单 Web 应用，底层使用 MySQL 数据库。

突然间，你的服务器“过载”了，该怎么办？首先要弄清楚“过载”到底是什么意思。以下是一些可能的原因（按概率从高到低大致排序）：

没有足够的 worker 来处理并发负载；内存不足以支撑当前工作负载；CPU 不足以快速完成工作负载；磁盘 IOPS 耗尽；文件描述符不够；网络带宽不足。

你应该询问面试官具体是哪种问题导致了过载，但如果他们让你预测，最有可能就是上面这些。我们来分别思考针对每种情况的垂直扩展和水平扩展策略（垂直扩展是指在现有硬件上提高吞吐量，比如增加内存或使用更快的 CPU；水平扩展则是增加更多服务器）。

许多（可能大多数）服务器使用线程来实现并发。这意味着如果你有十个线程，就能同时处理十个并发请求。假设平均每个请求耗时 250 毫秒，那么十个线程的最大吞吐量就是每秒 40 个请求。对服务器来说，最常见的第一类扩展问题是：传入请求远远超过了当前工作负载所能处理的量。

最简单的解决方案是增加更多 worker 线程，比如让 server02 的线程数远远多于 server01。

限制在于，每增加一个线程都会消耗更多内存和 CPU。在某个点（具体取决于你的进程），由于内存压力，你将无法再添加更多线程。还有一种可能是，你的服务器在线程之间存在某些共享资源，导致即使没有遇到内存或 CPU 限制，每增加一个线程也会让整体变慢。

如果你在遇到 CPU 限制之前先遇到了内存限制，那么另一个很好的选择是使用非阻塞 Web 服务器，它依赖异步 IO。非阻塞实现将服务器从“一个并发请求对应一个线程”的模式中解耦出来，这意味着你可能在一台服务器上同时运行成千上万的并发请求（比如 10,000 个！）。

一旦用尽了在单台服务器上处理更多请求的上述方法，下一步通常是将单一服务器拆分成多个专门的服务器（可能是一个 Web 服务器角色和一个数据库角色），并在 Web 服务器前面放置一个 构建可扩展系统的架构导论。

负载均衡器会将传入请求分发到你的各个 Web 服务器上，每台服务器都有自己的线程池来处理并发请求。（负载均衡器本身依赖非阻塞 IO，并且经过高度优化，因此它们的并发限制通常不是瓶颈。）这样你就能够近乎无限地添加更多服务器节点来提升并发能力。（通常在这个阶段数据库会先被打垮，我们后面会继续讨论。）

通过负载均衡器进行水平扩展，是解决所有主机层面问题的通用水平扩展方案——前提是你运行的是无状态服务。（如果你的服务的任何一个实例都能处理任意请求，那么它就是无状态的；如果你需要同一台服务器持续处理某个页面或某个用户的所有请求，那么它就不是无状态的。）

如果你只记住一件事，那就是使用负载均衡器进行水平扩展，然后直接跳到数据库部分。不过我们也会稍微深入探讨一下针对单台服务器其他常见扩展挑战的垂直扩展方法。

下一个最常见的情况是内存耗尽（可能是因为线程太多）。从垂直扩展的角度，你可以给服务器增加更多 RAM，或者花时间优化减少内存使用。

如果你的数据量太大，无法全部放入一台服务器的内存中，而所有数据又必须同时存在于内存里，那么你可以对数据进行分片（shard），让每台服务器只存放一部分数据，并更新负载均衡器，将特定分片的相关流量导向正确的服务器。

我们会在后面的数据库部分更详细地讨论这类方案。另一种选择是减少加载到内存中的数据量，把大部分数据存储在磁盘上。这意味着读写数据会变慢，但你将获得大得多的存储容量（1TB 的 SSD 很常见，但 Web 服务器很少有超过 128GB 内存的）。

对于读多写少的负载，一个折中方案是在内存中只加载“热数据”（即经常被访问的部分），其余数据仍然放在磁盘上（比如一家报纸可能会把今天的文章放在内存里，而把历史归档放在磁盘上，供偶尔想看老新闻的读者使用）。

CPU 耗尽的情况与内存耗尽非常类似，但有几个有趣的特点。

CPU 严重争用的服务器仍然能以降级的方式继续工作，而内存不足的服务器往往会非常明确地失败（软件在申请更多内存却得不到时通常会崩溃，而且 Linux 还有一个不太友好的 OOM killer，会自动杀死占用过多内存的进程）。

在很多情况下，如果你做的正当工作消耗了过多 CPU，你可以改用更 CPU 高效的语言中的库（比如 Python 或 Ruby 使用 C 扩展，simplejson 就是一个你可能已经在用的很好的例子）。生产环境中花费 20-40% 的 CPU 时间在 JSON 的序列化和反序列化上并不罕见，仅仅切换 JSON 库就能带来巨大提升！

如果你已经在使用高性能库，但仍然不够，那么你可以把部分代码重写成 Go、C++ 或 Java 等更高效的语言，但重写已经能正常工作的软件是一个充满风险的决定。

如果你的工作负载需要写入大量数据（甚至只是记录海量日志），或者从磁盘读取大量数据（可能是因为数据太多装不进内存），那么你往往会耗尽 IOPS。IOPS 指的是你的磁盘每秒能执行的读写操作次数。

你可以通过在内存中缓存或缓冲写操作、然后定期刷盘的方式，减少软件读写磁盘的频率。

或者，你可以购买更多或更好的磁盘。磁盘有趣的地方在于你选择的磁盘类型会产生非常显著的影响：机械硬盘（SATA 是较大较慢的磁盘，SAS 是较快较小的磁盘）最高通常不超过 200 IOPS，而入门级 SSD 可以达到 5000 IOPS，高端的甚至超过 10 万 IOPS。（还有像 FusionIO 这样更高阶的设备，能提供更高的性能，但价格也很昂贵。）

很常见的情况是，Web 服务器使用廉价的 SATA 硬盘，而数据库服务器则使用更昂贵的 SSD。

对于高并发的工作负载——例如你之前用非阻塞服务解决线程数限制问题时——最终你会遇到的一个有趣问题是文件描述符耗尽。

几乎每个人都有过与文件描述符相关的惨痛经历，但好消息是，这只是你需要在操作系统配置中修改的一个数值，改完之后你就能带着一点智慧继续工作了。（操作系统默认文件描述符上限设置得低得离谱，这是一个由来已久的故事。不过现在大多数系统都在设置越来越合理的默认值，所以你可能永远不会遇到这个问题。）

最后，如果你的应用非常消耗带宽——比如你的假设应用在做视频流传输——那么在某个时刻，你会开始耗尽网卡（NIC）的带宽。现在大多数服务器都配备 1Gbps 的网卡，但如果你真的需要，升级到 10Gbps 网卡其实相当划算，而大多数工作负载并不需要这么高的带宽。

好了，针对单台 Web 服务器的扩展方案就讲到这里！除了上面各种垂直扩展服务器以获得更多处理能力的策略之外，负载均衡器绝对是我们最强大的工具。

接下来我们看看这样一种场景：你的服务器根本没有过载，但响应却非常缓慢。

应用变慢

在这个部分，假设你正在运行一个 API，它接收一个 URL，然后返回该网页格式良好、易于阅读的版本（类似这样的服务）。你的初始架构很简单，包括一个负载均衡器、若干 Web 服务器和一个数据库。

突然间，用户开始抱怨你的应用变慢了。人类对 100 到 200 毫秒以上的延迟是有明显感知的，所以理想情况下你希望页面在 200 毫秒内加载完成，但现在你的应用却需要 1.5 秒才能加载。

你该如何修复这个问题？

对于任何性能问题，第一步都是做性能分析。在很多情况下，分析结果不会立刻告诉你该修复什么，但几乎总是会给你一条线索。你沿着这条线索走，直到对另一个组件进行分析，又得到新的线索，然后继续追下去。

在这个例子中，最有可能的首要问题是数据库读取变慢了。如果用户经常对同样的 URL 调用你的 API，那么一个很好的下一步是加入像 Redis 或 Memcached 这样的缓存。

现在每次 API 调用你都会检查：

数据是否已经在缓存中，如果在，就直接使用缓存中的数据；如果不在数据库中，就从数据库里读取，然后写入缓存并返回给用户；否则就去抓取网页，写入数据库，再写入缓存，最后返回给用户。

只要用户主要还是在访问同样的 URL，你的 API 应该就能再次变快。

另一个常见场景是，应用变慢是因为它正在做太多事情！也许每个传入请求都要从缓存读取一些数据，同时还要往数据库里写大量分析数据，并且向磁盘写日志。你对服务器进行分析后发现，它把大部分时间都花在了写入分析数据上。

解决这个问题的一个好办法是把耗时的代码放到不会影响用户的地方运行。在某些语言里，这简单到只需要先给用户返回响应，然后再做分析写入即可，但很多框架会让这件事变得出奇地麻烦。

在这些情况下，消息队列和异步 worker 就是你的好朋友。（一些流行的消息队列包括 RabbitMQ 和 Amazon Simple Queuing Service。）

（注意我已经把带名字的服务器替换成了代表多台服务器的方框，比如多个缓存方框等等。我这样做是为了降低整体图的复杂度，尽量保持简洁。对图进行重构往往很有用！一种折中的画法是画一个代表服务器组的大方框，然后在里面画出多台服务器，但连线只从大方框引出，这样你既能明确表示某个角色下有多台服务器，又不必画太多相互重叠的线。）

现在当请求到达你的服务器时，你会同步完成大部分工作，然后把一个任务放入消息队列（这个操作通常非常非常快，根据后端不同可能有所差异，但很可能小于 50 毫秒），这样你的 worker 进程就可以后续再取出任务并处理它，用户不需要等待它完成（也就是异步处理）。

最后，有时延迟根本与你的应用无关，而是因为用户离你的服务器很远。从美国东海岸到西海岸大约需要 70 毫秒，从东海岸到欧洲还要再多一些，所以从西海岸到欧洲很容易超过 160 毫秒。

解决这个问题最实际的方式通常是使用 CDN（Content Delivery Network），它就像一个地理分布式的缓存，能让常见的请求从离用户很近（乐观情况下只有 10 到 20 毫秒）的本地缓存中获取，而不是穿越全球。（AWS CloudFront、Fastly、EdgeCast 和 Akamai 都是一些流行的 CDN。）

规模更大的公司或者有特殊需求的公司——通常是带宽需求很高的场景，比如视频流——有时会建立自己的 PoP（Point of Presence，存在点），其作用类似 CDN，但可定制性更强。不过随着越来越多公司直接在 Amazon、Google 或 Microsoft 云上起步并保持，这种做法正变得越来越少见。

稍微重复一下，CDN 通常只适用于内容是静态的，或者可以定期重新生成的情况，比如面向未登录用户的报纸网站，并且你的内容中有一部分足够热门，以至于同一分钟内会有多个人想看到相同的内容（这里的一分钟只是个随意的时间单位，你可以根据需要缓存任意时长）。（这其实也忽略了 SSL 终结带来的延迟优势，本文对这一点有很好的介绍。）

如果你需要降低对用户的延迟，而你的工作负载又不适合使用 CDN，那么你就必须运行多个数据中心，每个数据中心要么拥有全部数据，要么拥有被路由到它的用户所需的所有数据。

（如果你碰巧在想或者被问到是用什么机制来选择正确的数据中心，通常答案是 Anycast DNS，这是一个非常巧妙的技术，如果你在面试中能恰当地提到它，一定会加分。）

运行多个数据中心通常相当复杂，具体取决于你的实现方式，这已经超出了本文所能覆盖的范围。只有相对少数的公司会运行多个数据中心（或者在云上使用多个地域），而且几乎都做了相当定制化的处理。

尽管如此，设计一个支持多个数据中心的系统，最终会和扩展数据库非常相似，而这正是我们下一节要讨论的内容。

数据库过载

假设你正在实现一个简化版的 Reddit，支持用户发帖和评论。

一开始一切正常，但随着读取量越来越大，你的数据库开始 CPU 受限。如果你使用的是 MySQL 或 PostgreSQL 这样的 SQL 数据库，最简单的修复方式是添加只读副本（replicas），这些副本拥有与主库（primary）完全相同的数据，但只支持读操作（这里的术语略有不同，现在更常用 primary 和 secondary 或 primary 和 replica，老一些的文档和系统倾向于称其为 master 和 slave，尽管这种用法多年来一直是默认和主流的，而且今天仍不罕见，但正逐渐被弃用）。

你的写负载仍然必须应用到每一台服务器（无论是主库还是副本），所以副本不会给你带来额外的写带宽。但每一次读操作都可以在任意一台服务器上完成（在复制延迟的限制范围内，只有当你写完立刻就要读数据时才需要特别注意，这种情况下你可能需要强制“读写一致”操作从主库读取，但其他所有读操作仍然可以路由到任意副本）。因此你可以在很长时间内水平扩展读能力（到某个阶段，你可能会受限于可用带宽而无法添加更多副本，但很多数据库支持从一个副本向另一个副本链式复制，这理论上能让你近乎无限地扩展）。

如果你是写负载过高，那么解决方案会略有不同。你不能依赖复制，而是需要使用分片（sharding）：把数据拆分，让每台数据库服务器只包含一部分数据，然后通过某种机制（通常就是在应用代码里实现）来为每个操作正确选择对应的分片。

由于这样每台服务器只需处理部分写操作，你就可以水平扩展以应对几乎任意规模的写负载。实践中人们不喜欢分片，是因为你无法再对所有数据执行统一的操作（比如统计所有已提交的帖子总数），而是必须对每个分片单独执行操作，然后自己把结果合并起来。

如果你的服务器正在耗尽 IOPS 或磁盘空间，分片同样是最佳解决方案。从某种意义上说，分片就是有状态服务的负载均衡。

分片在运维上也相当复杂，你需要花费大量时间维护路由到正确分片的机制，还要花更多时间思考如何对分片进行再平衡，以防止某个分片增长过大而无法处理所有路由给它的写操作。

如果你同时面临读和写都很重的场景，那么你完全可以像上面那样同时使用复制和分片。

虽然复制和分片是架构面试中最常见的两种扩展方案，但还有其他几种值得一提：

批处理（Batching）在你写操作太多但暂时还不想开始对数据库分片时非常有用。特别是对于分析类场景，比如统计某个页面一分钟内的浏览次数，批处理可以让你从每秒上万次写降低到每分钟一次写（当然，你需要把批处理的数据暂存到某个地方，比如消息队列，甚至直接放在应用的内存里）。

最后，我在这里要提到的最后一个策略是使用不同类型的数据库，特别是像 Cassandra 这样的 NoSQL 数据库，它们默认就设计为将读写分散到多台服务器上，而不需要你自己实现定制的分片工具。NoSQL 服务器典型的缺点是它们能高效支持的操作集合较小，因为每个分片只拥有一部分数据。

如果你想深入了解 NoSQL，我建议阅读相对易懂的 Dynamo Paper，它会给你提供相关的概念和词汇，让你能够就 NoSQL 数据库适用的场景进行有深度的讨论。

结束语

这篇文章比我预期得要长一点，而在写作过程中真正让我感慨的是，这其实是一种相当奇怪的面试形式。本质上，它是在测试一个人能否营造出自己曾经构建过大型或复杂系统的印象。

尽管奇怪，这种面试形式却能很好地重现现实中与他人一起共同设计系统，或者向新同事解释现有系统工作原理的真实体验。只要我们把它用在具有合适背景的候选人身上——也就是说，有几年互联网公司或使用类似技术的公司的经验——我认为它就是你工具箱里一个有用的工具。

如果不用这种形式，你又该如何去了解一个人的系统设计经验呢？
