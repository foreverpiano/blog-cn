搞定你的架构面试

2016-09-27 · 阅读原文

我印象最深的一次面试以一个完全意想不到的问题开始：“你还记得多少微积分？” 我笑了笑，说已经过去好几年了，我相当生疏了。尽管如此，我们还是花了接下来整整一个小时尝试做微积分题，而我则表现得一塌糊涂。

很多人对“架构面试”都有类似的顾虑，而这却是我最喜欢的用来面试互联网行业有经验候选人的面试形式之一。因此我决定写下自己应对这类问题的套路。

在正式开始前，先来看几个典型的架构面试问题示例：

为 Facebook、Twitter、Uber 或 Foursquare 设计架构。画出你选择的一个基本 Web 应用的架构图。设计一个类似报纸网站那样可靠的网站。为一款手机游戏设计一个可扩展的 API。

从这个起点出发，面试官要么会给你增加更多约束条件（“你的数据库开始过载了”），要么会让你思考系统可能会遇到哪些扩展问题，以及如何解决它们（“首先，我觉得我们会耗尽处理传入请求的工作线程”）。

这类面试的基本解题思路是：

画出你当前的设计。在你的设计上施加一个新的约束。找出该约束导致的瓶颈。更新你的设计来解决这个瓶颈。

光知道这些可能还不足以帮你搞定下一次架构面试，因此本文接下来会先简单介绍如何绘制架构图，然后深入探讨特定约束所带来的各种瓶颈。

绘制架构图

关于技术架构图，最重要的一点是要知道它更像是一门艺术而非科学。只要你始终画得合理且一致，就不会有问题。

面试时几乎总是要在白板上画图，但如果你有机会在电脑上画图，我强烈推荐 Omnigraffle。虽然它不便宜，但我认为这是一笔值得的投资（除了画架构图，我还用它来做线框图）。

下面我们来看几个例子。

左边是一台运行着 Web 服务器和数据库的服务器，右边是两台服务器：一台运行 Web 服务器，另一台运行数据库。

虽然并没有太多的约定俗成，但通常服务器用方框表示，进程也用方框表示，而数据库或其他存储机制则用圆柱体表示。不过全部都用方框也没问题。服务器命名一般是服务器类型加上唯一编号，例如 frontend01 和 frontend02 分别表示 frontend 类型的第一台和第二台服务器。随着例子中服务器数量增加，编号会很有帮助。用 01 来表示 1 其实非常随意，但这也算是一种“迹象”，暗示你曾经为超过九台服务器的服务器组做过命名（你完全可以提出很多合理论据来说明这种命名方式不好，但它更像是一种常见做法，而非最佳实践）。

接下来，我们展示两个数据中心，它们从代表互联网的神奇“云”中接收流量。

按照奇怪的惯例，互联网总是用一朵云来表示。如果你有一个移动设备连接到你的应用，通常会画出移动设备，连一条线到互联网，然后继续如上图所示（网站也是同样的画法）。

数据中心或区域是指物理位置集中在一起的服务器群，通常画成一个大方框把若干服务器围起来（就像服务器内的进程被画成服务器方框内的方框一样，一般来说，把数据中心比作服务器，就如同把服务器比作进程，是合理的）。

正如 fe 和 app 服务器层之间所见，当连线会让图变得太乱时，我经常会省略掉连线。我个人认为，如果“有效”和“准确”发生冲突，图应该优先追求有效性。

总结一下：多用方框，少用线条，尽量保持简洁。现在，让我们继续进入问题解决环节！

画图、加约束、解决问题、重复

现在我们进入正题了。在每个小节中，我们都会先展示一张起始架构图，然后给它施加一个约束，诊断该约束意味着什么，最后画出更新后的架构图来解决这个约束。可能的约束非常非常多，我们不可能全部覆盖，但希望通过足够多的例子让你有个大致的概念。

Web 服务器过载

你正在单台服务器上运行你的博客，这是一个运行在 MySQL 之上的简单 Python Web 应用。

突然，你的服务器“过载”了，你该怎么办？首先要弄清楚“过载”到底是什么意思。下面是一些可能的情况（按可能性从高到低大致排序）：

没有足够的工作线程来处理并发负载、没有足够内存来运行其工作负载、没有足够的 CPU 来快速运行其工作负载、磁盘 IOPS 耗尽、文件描述符不够、网络带宽不足。

你应该询问面试官是哪种情况导致了过载，但如果他们让你预测最可能发生哪种，那么大概率是上面几种之一。我们来分别思考每种情况下的垂直扩展和水平扩展策略（垂直扩展是指在现有硬件上提升吞吐量，比如增加更多内存或更快的 CPU；水平扩展则是增加更多服务器）。

许多（可能大多数）服务器使用线程来实现并发。这意味着如果你有十个线程，就能处理十个并发请求。假设平均每个请求耗时 250 毫秒，那么十个线程的最大吞吐量就是每秒 40 个请求。对于服务器来说，最常见的第一类扩展问题是：传入请求数量超过了当前工作负载的处理能力。

最简单的解决方案是增加更多工作线程，比如让 server02 的线程数远多于 server01。

限制在于：每增加一个线程都会消耗更多内存和 CPU。在某个临界点（具体取决于你的进程），你会因为内存压力而无法再添加更多线程。还有一种可能是，你的服务器在线程间存在某种共享资源，导致每增加一个线程整体性能都会下降，即使没有受到内存或 CPU 的限制。

如果你在 CPU 受限之前就遇到了内存受限，那么另一个很好的选择是使用非阻塞 Web 服务器，它依赖异步 IO。非阻塞实现将服务器从“一个并发请求对应一个线程”的模式中解耦出来，这意味着你可能在一台服务器上同时处理成千上万的并发请求（比如 10,000 个并发请求！）。

一旦用尽了在单台服务器上处理更多请求的上述方法，下一步通常就是把单台服务器拆分成多个专门的服务器（可能是一个 Web 服务器角色和一个数据库角色），并在 Web 服务器前面放置一个 构建可扩展系统的架构导论。

负载均衡器会将传入请求均衡地分发到你的 Web 服务器上，每台服务器都有自己的线程来处理并发请求。（负载均衡器依赖非阻塞 IO，并且经过高度优化，因此它们的并发限制通常不是瓶颈。）这样你就做好了准备，可以近乎无限地添加更多服务器节点来提升并发能力。（通常在这个阶段你的数据库会先被打垮，后面会继续讨论。）

通过负载均衡器进行水平扩展，是针对所有主机层面问题的水平扩展解决方案——前提是你运行的是无状态服务。（如果服务的任何一个实例都能处理任意请求，那么它就是无状态的；如果你需要同一台服务器持续处理某个页面或某个用户的所有请求，那它就不是无状态的。）

如果你只记住一件事，那就应该是：使用负载均衡器进行水平扩展，然后直接跳到数据库部分。不过我们也会稍微深入探讨一下单台服务器其他常见扩展挑战的垂直扩展方法。

下一个最常见的情况是内存耗尽（可能是因为线程太多）。在垂直扩展方面，你可以给服务器增加更多 RAM，或者花时间优化减少内存占用。

如果你的数据量太大，无法全部放入一台服务器的内存，而且所有数据必须同时存在于内存中，那么你可以对数据进行分片（shard），让每台服务器只保存一部分数据，并更新你的负载均衡器，将针对某个分片的数据流量导向正确的服务器。

我们在下面的数据库部分会更详细地讨论这类解决方案，但另一种选择是只把较少的数据加载到内存中，而将大部分数据存储在磁盘上。这意味着读写数据会变慢，但你将获得显著更大的存储容量（1TB 的 SSD 很常见，但 Web 服务器拥有超过 128GB 内存仍然不常见）。

对于读多写少的负载，一个介于“全部放磁盘”和“全部放内存”之间的折中方案是：将“热数据集”（经常被访问的部分）加载到内存中，而将其余数据保存在磁盘上（比如一家报纸可能会把当天的文章放在内存里，而把历史归档放在磁盘上，供偶尔想看旧闻的读者使用）。

CPU 耗尽与内存耗尽非常相似，但有几个有趣的特点。

CPU 严重争用的服务器会以降级的方式继续工作，而内存不足的服务器往往会非常明确地失败（软件在请求更多内存却得不到时往往会崩溃，而且 Linux 还有个不太友好的 OOM killer，会自动杀死占用过多内存的进程）。

在很多情况下，如果你正在做的是真正有用但消耗太多 CPU 的工作，你可以依赖用更 CPU 高效的语言编写的库（比如 Python 或 Ruby 使用 C 扩展，simplejson 就是一个你可能已经在用的很好的例子）。生产环境中花在 JSON 序列化和反序列化上的 CPU 时间占到 20-40% 并不罕见，仅仅更换 JSON 库就能带来巨大的性能提升！

如果你已经在使用高性能的库，那么你可以把部分代码重写成 Go、C++ 或 Java 等更高效的语言，但重写已经在工作的软件这个决定充满了风险。

如果你的工作负载需要写入大量数据（甚至只是记录海量日志），或者从磁盘读取大量数据（可能是因为数据太多无法全部放入内存），那么你往往会耗尽 IOPS。IOPS 指的是你的磁盘每秒能完成的读写次数。

你可以重写软件，通过在内存中缓存或缓冲写入然后定期刷盘等方式，减少磁盘读写的频率。

或者，你可以购买更多或不同类型的磁盘。磁盘有趣的地方在于你使用的磁盘类型会产生非常显著的影响：机械硬盘（SATA 是较大较慢的硬盘，SAS 是较快较小的硬盘）最高 IOPS 低于 200，而入门级 SSD 可以达到 5000 IOPS，最好的能超过 10 万 IOPS。（甚至还有像 FusionIO 这样更高阶的设备，虽然价格昂贵但性能远超。）

很常见的情况是，Web 服务器使用廉价的 SATA 硬盘，而数据库服务器则使用更贵的 SSD。

对于高并发的工作负载，比如你之前用来解决线程数限制问题的非阻塞服务，最终你会遇到的一个有趣问题是文件描述符耗尽。

几乎每个人都有一个关于文件描述符的惨痛经历，但好消息是，这只是需要在操作系统配置中修改的一个数值，改完之后你就能带着一点智慧继续工作了。（操作系统默认文件描述符数值低得离谱的历史由来已久，但现在它们的默认值越来越合理了，所以你可能永远不会遇到这个问题。）

最后，如果你的应用非常消耗带宽——比如你假设的应用在做视频流传输——那么在某个时刻，你会开始耗尽网卡（NIC）的带宽。现在大多数服务器都配备 1Gbps 的网卡，但如果你确实需要，升级到 10Gbps 的网卡也相当划算，而大多数工作负载其实并不需要。

好了，这就结束了我们对单台 Web 服务器扩展方案的讨论！除了上面各种能让这台服务器多干一点活的垂直扩展策略之外，负载均衡器确实是我们目前最好的工具。

接下来让我们看看另一种场景：你的服务器根本没有过载，但响应却非常慢。

应用变慢

在本节中，假设你正在运行一个 API，它接收一个 URL 并返回一个格式良好、易于阅读的页面版本（类似这样的东西）。你最初的架构很简单，包括一个负载均衡器、若干 Web 服务器和一个数据库。

突然，用户开始抱怨你的应用变慢了。人类对 100 到 200 毫秒以上的延迟就能明显感知，所以理想情况下你希望页面在 200 毫秒内加载完成，而现在你的应用却要花 1.5 秒才能加载。

你该如何修复这个问题？

对于任何性能问题，第一步都是性能剖析。在很多情况下，剖析不会立刻告诉你该修复什么，但几乎总是会给你一条线索。你沿着这条线索走，直到剖析另一个组件，它又给你另一条线索，你就这样一直追下去。

在这个例子中，最可能的第一问题是：从数据库读取数据变慢了。如果用户经常调用相同 URL 的 API，那么一个很好的下一步是增加一个像 Redis 或 Memcached 这样的缓存。

现在对于所有 API 调用，你会依次检查：

数据是否在缓存中，如果在，就直接使用缓存中的数据；如果不在缓存中但在数据库中，就把数据写入缓存然后返回给用户；否则你就去抓取网站，然后写入数据库，再写入缓存，最后返回给用户。

只要用户主要还是在抓取相同的 URL，你的 API 就应该再次变快了。

另一个常见场景是：你的应用变慢是因为它正在做太多事情！也许每个传入请求都要从缓存中读取一些数据，但同时还要往数据库里写大量分析数据，还要往磁盘写一些日志。你对服务器进行剖析后发现，它大部分时间都花在写入分析数据上。

解决这个问题的一个好办法是，把慢的代码放到不会影响用户的地方运行。在某些语言中，这简单到只需先把响应返回给用户，然后再做分析数据的写入，但很多框架会让这件事变得出奇地麻烦。

在这些情况下，消息队列和异步工作进程就是你的好朋友。（一些消息队列的例子有 RabbitMQ 和 Amazon Simple Queuing Service。）

（注意我已经把带名字的服务器换成了代表多个服务器的方框，比如多个缓存方框等等。我这么做是为了降低图的整体复杂度，尽量保持简洁。对图进行重构往往很有用！一种折中做法是画一个代表服务器群的方框，然后在里面画出多台服务器，但只从包含的大方框往外画连线，这样你就能更明确地表示某个角色下有多个服务器，而不必画太多重叠的线。）

现在，当请求到达你的服务器时，你会同步完成大部分工作，然后在消息队列中调度一个任务（这通常非常非常快，根据你使用的后端不同可能有差异，但很可能小于 50 毫秒），这样你的工作进程就可以稍后从队列中取出任务并处理它，而用户不必等待它完成（换句话说，就是异步处理）。

最后，有时延迟根本不是你的应用导致的，而是因为用户离你的服务器很远。从美国东海岸到西海岸大约需要 70 毫秒，从东海岸到欧洲还要再多一点，所以从西海岸到欧洲很容易超过 160 毫秒。

通常最实际的解决办法是使用 CDN（Content Delivery Network），它的行为就像一个地理分布式的缓存，能让常见的请求从本地的缓存中获取，这些缓存距离用户通常只有乐观估计的 10 或 20 毫秒，而不是穿越全球。（AWS CloudFront、Fastly、EdgeCast 和 Akamai 都是一些流行的 CDN 示例。）

更大的公司或者有非常特殊需求的公司——通常是高带宽需求如视频流传输——有时会建立存在点（Points of Presence）或 POP，它们的作用类似 CDN 但可定制性更强，但随着越来越多公司直接在 Amazon、Google 或 Microsoft 的云上起步和运营，这种做法正变得越来越不常见。

稍微重复一下，CDN 通常只在你的内容是静态的、或者可以定期重新生成的情况下才有用，比如面向未登录用户的报纸网站，而且你的内容中必须有一部分足够热门，使得在一分钟左右的时间内有多人想要看到相同的内容（当然，一分钟是任意的时间长度，你可以根据需要缓存任意时长）。（这确实忽略了 SSL 终止带来的延迟优势，本文对这一点有很好的介绍。）

如果你需要降低给用户的延迟，而你的工作负载又不适合使用 CDN，那么你就必须运行多个数据中心，每个数据中心要么拥有你全部的数据，要么拥有被路由到它的用户所需的所有数据。

（如果你正好在好奇或者可能会被问到，是什么机制帮你选择正确的数据中心，通常那是 Anycast DNS，它非常巧妙，如果你能在面试中恰当地提到它，肯定会加分。）

运行多个数据中心的复杂度取决于你的实现方式，通常相当复杂，超出了本文所能涵盖的范围。只有相对少数的公司会运行多个数据中心（或者在云中相当于多个区域），而且几乎所有这些公司做的都是相当定制化的方案。

尽管如此，设计一个支持多个数据中心的系统，最终会和扩展你的数据库非常相似，而这恰好是下一节的内容。

数据库过载

假设你正在实现一个简化的 Reddit 版本，支持用户发帖和评论。

一开始一切都很好，但后来读请求太多，你的数据库开始 CPU 受限。如果你使用的是 MySQL 或 PostgreSQL 这样的 SQL 数据库，最简单的修复方法是添加副本（replicas），这些副本拥有与主库（primary）完全相同的数据，但只支持读操作（这里的术语略有不同，primary 和 secondary 或 primary 和 replica 越来越常见，而较旧的文档和系统常称其为 master 和 slave，但尽管这种用法多年来一直是默认和主流的，而且今天仍然能听到——它正逐渐不再受欢迎）。

你的写负载仍然必须应用到每一台服务器（主库或副本）上，因此副本不会给你带来任何额外的写带宽；但每一次读操作都可以在任意一台服务器上完成（在复制延迟的限制范围内，只有当你试图在写入后立即读取数据时才需要关心，这时你可能需要强制“读后写”操作从主数据库读取，但你可以让所有其他读请求去任意一个副本），所以你可以在很长时间内水平扩展读能力（最终你可能会受限于可用带宽而无法添加更多副本，但许多数据库允许你将复制从一个副本链到另一个副本，从理论上来说，这能让你近乎无限地扩展下去）。

如果你是写负载过重，那么解决方案会有所不同。你将不再依赖复制，而是需要使用分片（sharding）：把数据拆分，让每台数据库服务器只包含一部分数据，然后通过某种机制（通常就是在你的应用代码中）来正确地为每个操作选择正确的分片。

因为这让每台服务器只需处理部分写操作，所以你可以水平扩展来应对几乎任意规模的写负载。实践中人们不喜欢分片，因为你无法再对所有数据执行操作（比如统计所有已提交的帖子总数），而是必须在每个分片上独立执行操作，然后自己想办法合并结果。

如果你的服务器正在耗尽 IOPS 或磁盘空间，分片同样是最佳解决方案。从某种意义上说，分片就是有状态服务的负载均衡。

分片在运维上也非常复杂，你需要花大量时间维护将请求路由到正确分片的机制，还要花更多时间想办法对分片进行再平衡，以防止某个分片变得过大而无法处理所有路由给它的写请求。

如果你同时面临繁重的读和写，那么你完全可以像上图那样将复制和分片组合使用。

虽然复制和分片是架构面试中最常见的两种扩展方案，但还有其他几种值得一提：

批处理（Batching）在你的数据库写压力太大，但由于某种原因你还不想立即开始分片时非常有用。特别是在分析类的场景中，需要统计某个页面在一分钟内的浏览次数，批处理可以让你从每秒上万次写入降低到每分钟一次写入（当然你需要把批处理的数据暂时存放在某处，或许是消息队列，或者甚至只是你应用自己的内存中）。

最后，我在这里要提到的最后一个策略是使用不同类型的数据库，特别是像 Cassandra 这样的 NoSQL 数据库，它们默认就被设计成在多个服务器之间分散读写，而不是让你自己去实现定制的分片工具。NoSQL 服务器典型的缺点是它们能高效执行的操作集合较小，因为每个分片只拥有一部分数据。

如果你想深入了解 NoSQL，我的建议是阅读那篇相当易懂的 Dynamo Paper，它会给你提供概念和词汇，让你能够有深度地讨论在哪些场景下使用 NoSQL 数据库是合适的。

尽管有点奇怪，这种面试形式却非常有效地重现了现实中与他人共同设计系统，或者向新团队成员解释现有系统工作原理的真实体验。只要我们将其用于具有合适背景的候选人——即在互联网公司或使用相同技术的公司有若干年经验的人——我认为它就是你工具箱里一个有用的工具。
