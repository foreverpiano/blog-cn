构建内部 Agent：日志记录与可调试性

2025-12-31 · 阅读原文

Agent 的能力令人惊叹，但它们也引入了大量非确定性，而非确定性往往会导致一些奇怪的问题。为了应对这一点，我们必须对工作流进行完善的插桩，以便能够调试出问题发生的原因。

本文是 构建内部 Agent 系列文章的一部分。

为什么日志记录如此重要

每当 Agent 做出了不够理想的行为，人们就会将其标记为 Bug。通常来说，这个“Bug”其实是 Prompt 中的模糊表述导致了次优的工具调用。这让我感觉好一些，但对于那些依赖这些工具的人来说并没有太大安慰：他们只希望工具能正常工作。

这意味着，调试意外行为是内部推广 Agent 的重要组成部分，必须让这项工作变得足够简单且可以频繁进行。如果调试需要耗费太多时间、精力或权限，那么你的 Agent 就很难被真正采用。

我们如何实现日志记录

我们的 Agent 运行在 AWS Lambda 上，因此最初的日志方案只是简单地将内容打印到标准输出，由 Lambda 的日志系统进行捕获。这在最初的几个迭代中表现尚可，但也意味着每次出问题我都得登录 AWS，而即使是很多工程师也不知道去哪里查看日志。

第二版方案是创建了一个名为 #ai-logs 的 Slack 频道，每次工作流运行都会在其中分享其配置信息、使用的工具，以及指向 AWS 日志页面的链接。这是一个进步，但要回答一些基本问题，仍然需要大量翻阅和挖掘日志。

第三版方案，也就是我们当前的实现，是集成了 Datadog 的 LLM Observability。它提供了一种简便的方式来查看 LLM 工作流中的每一个 Span，从而可以轻松调试复杂细微的问题，而无需在海量日志中苦苦搜寻。这是一个巨大的改进。

值得一提的是，Datadog 的集成还让我们能够轻松为内部项目引入仪表盘功能，这正是我们工作中一直缺失却非常有价值的一环。

实际效果如何？下一步计划是什么？

老实说：Datadog 的 LLM 可观测性工具集真的非常出色。目前我遇到的唯一问题是，我们主要将 Datadog 账号限制在技术组织内部的人员，因此工作流调试对团队以外的人来说并不容易获取。不过在实践中，需要主动调试这些工作流的人几乎都已拥有访问权限，所以这更多是一个理念层面的问题，而非实际操作上的障碍。
