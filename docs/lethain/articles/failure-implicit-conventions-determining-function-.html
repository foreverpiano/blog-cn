隐式约定的失败：判断函数是否具破坏性

2007-07-18 · 阅读原文

所有函数要么是破坏性的，要么是非破坏性的。二者有何区别？我们如何区分它们？为什么需要关心这些？这些都是重要问题。在开发语言、库、程序或函数时，如果忽略了破坏性的影响，将导致代码风格不一致，并产生令人费解的错误。

什么是破坏性函数

让我们试着弄清楚破坏性函数是什么样的：

def doSomething()
  "str"
end

非破坏性。

def doSomething(a, b)
   a * b
end

非破坏性。

def doSomething(a)
  a << "this"
end

破坏性。

def doSomething(a)
  b = a.clone()
  b << "this"
end

非破坏性。

irb(main):033:0> y = [1,2,5,1,2]
=> [1, 2, 5, 1, 2]
irb(main):034:0> y.sort()
=> [1, 1, 2, 2, 5]
irb(main):035:0> y
=> [1, 2, 5, 1, 2]

非破坏性。

def sort2(a)
  a = a.sort()
end

破坏性。

class Something
  def initialize(name)
    @name = name
  end

  def doSomething()
    @name = @name << " is a silly name"
  end
end

破坏性。

好的，到了这一步我们大概已经看出区别了：破坏性函数会对其函数词法作用域之外的某些内容造成修改，而非破坏性函数则不会对词法作用域之外的内容产生任何改变。

更简单地说，非破坏性函数不会修改并非由它创建的值。所有传入的参数都可以被检查，但不能被修改（如果确实需要修改，非破坏性函数会创建一份副本进行操作，而不是直接修改原始值）。

如何区分它们

判断一个函数是否具有破坏性有时相当困难。如果你能拿到源代码，可以通读一遍，寻找外部变量或传入参数被修改的位置。然而，当无法获取源代码时，事情就会变得更加棘手。

在没有源代码的情况下，我们只剩下两种工具：实验和约定。

实验的方法是对函数可能修改的任何变量，在执行前后分别进行评估，观察它们是否发生了改变。特别是要仔细检查参数是否被修改。这听起来是否不太可靠？确实如此。很容易构造出简单的测试用例，让一个破坏性函数看起来像是非破坏性的。一个常见的例子是这样的：

irb(main):037:0> def link(a,b)
irb(main):038:1>   [a, b]
irb(main):039:1> end
=> nil
irb(main):040:0> a = [1,2,3]
=> [1, 2, 3]
irb(main):041:0> b = [4,5,6]
=> [4, 5, 6]
irb(main):042:0> c = link(a,b)
=> [[1, 2, 3], [4, 5, 6]]
irb(main):043:0> a
=> [1, 2, 3]
irb(main):044:0> b
=> [4, 5, 6]
irb(main):045:0> c[0] << 10
=> [1, 2, 3, 10]
irb(main):046:0> a
=> [1, 2, 3, 10]

此时 a 和 b 表面上看似没有被修改，但后来我们才意识到，它们已经被回收用于构建 link 函数返回的值。在某些情况下，即使函数明确复制了传入的参数，你仍可能遇到这个问题（因为发生的是浅拷贝而非深拷贝）。

这就只剩下我们最后的工具：约定。

编程语言都有自己偏好的范式、惯用表达、良好实践，以及关于什么是良好编程风格的内在哲学。通常这些不成文的规则是通过阅读语言专家编写的代码而逐渐内化的。然而，这种隐式传授约定的教学方式本身就是一场悲剧。

说它是悲剧，是因为不成文的规则不可靠，而且会从一个短暂的潮流转向另一个短暂的潮流。我们不能指望库的作者在那些最佳实践定义模糊不清的情况下，完整地实现一套不断演变的最佳实践：隐式规则的持久性，就像一场醉酒后的一夜情一样短暂。

然而，并非所有语言都依赖不成文的约定来区分破坏性函数。那些鼓励函数式编程的语言往往非常明确：Scheme 会在所有破坏性方法名后附加一个感叹号。这体现了主动的语言设计者（或语言设计委员会）如何在不修改语法或定义标准库的情况下，提升语言的可用性：一些简单的约定——比如 Ruby 用问号表示布尔查询，或 Scheme 用感叹号表示破坏性函数——就能快速向阅读你代码的人传达重要信息。

为什么我们应该关心

好吧，在许多语言中，区分破坏性函数和非破坏性函数可能相当困难。这真的很重要吗？

如果你喜欢编写干净、高效且不冗余的代码，那么是的，这很重要。如果你希望代码能正常工作，或者珍惜自己的时间，这同样很重要。

如果你无法轻松区分破坏性和非破坏性函数，那么你就不得不偏向谨慎。这意味着你会遇到需要进行不必要冗余操作的情况：

def doSomething(x)
  y = x.clone()
  y << "some text"
end
z = "this is my precious string"
z2 = doSomething(z.clone())

这是一段低效的代码（更别提它还很难看），但如果你无法快速判断 doSomething 是否为非破坏性，那么这类情况会相当频繁地出现。关键在于“快速判断”：跟踪一连串库函数调用是对时间的极大浪费，你也清楚这一点，因此通常会采用快速修复，而不是去验证函数的真实行为。随着时间推移，这些快速修复不断累积，你的代码会变得比原本更长、更复杂，也更低效——如果区分两种函数是件轻而易举的事，情况就不会如此。

如果我们能快速区分，就知道在哪里为了安全而克隆数据，在哪里可以直接传入不做修改。我们可以做出明智的决策：是为了效率而销毁数据，还是为了后续使用而保持其原始状态。

归根结底就是：如果我们能够区分破坏性和非破坏性函数，就能更快、更轻松地写出更高效、冗余更少的代码。

该怎么做

在对抗破坏性歧义的斗争中，我们有几种可用的资源。我们可以开始使用那些真正做出了这种区分的语言（怎么，没人愿意把所有代码都用 Scheme 来写吗？），或者我们可以从 Scheme 的成功经验（在这一狭窄领域）中学习，制定明确的书面约定，而不是仅仅存在于社区的集体记忆中。

让我们来看看 Python 中区分破坏性和非破坏性函数的约定（虽然我没见过这个约定被正式写下来）：

  1. If a function returns None, then it is destructive.
  2. If a function returns a value other than None, then it not destructive.
  3. Rules #1 and #2 are optionally void at discression of programmer.

当你阅读文档中类似“此函数返回 None 以强调其破坏性本质”的表述时，就能看到这一约定的痕迹。

然后你会看到这样的方法：

def increment(self, inc_by):
    self.count = self.count + inc_by
    return self.count

它返回了一个非 None 的值。它是破坏性的。而且没有人会认为这是不好的做法。

从根本上说，Python 的这个约定也不理想，因为它要求程序员实际运行该方法（或者阅读其源代码）来确定它返回什么。仅仅看到方法名不足以判断其是否具有破坏性。

不过，这绝非 Python 独有的问题，几乎没有哪种语言全面地解决了这个重要的区分问题。每个编程社区都需要坐下来，找到一种符合自身语言哲学的方式来区分破坏性和非破坏性函数。Scheme 在破坏性函数后附加感叹号的方法并非适用于所有语言，但找到一种同样明确的约定，值得花一点时间进行社区讨论。
