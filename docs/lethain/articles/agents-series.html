构建内部 Agent

2026-01-01 · 阅读原文

几周前在在 Imprint 推动 AI 采用这篇文章里，我提到了我们正在开发的内部 Agent 工作流。这并不是 Imprint 的核心业务——我们的核心是驱动联名信用卡项目——但我还是想记录一下像我们这样的公司是如何逐步构建这些内部能力的。

基于那篇文章中提到的“公司级公开 Prompt 库”等想法，我打算写一系列更短的文章，分享我们在演进工作流过程中遇到的一些有趣问题和采取的解决方法：

构建内部 Agent：为 Agent Skills 添加支持构建内部 Agent：渐进式披露与处理大文件构建内部 Agent：上下文窗口压缩构建内部 Agent：用 Evals 验证工作流构建内部 Agent：日志记录与可调试性构建内部 Agent：子 Agent 支持构建内部 Agent：代码驱动 vs LLM 驱动的工作流构建内部 Agent：触发器构建内部 Agent：提示词与技能的迭代优化

和前一篇文章一样，我并不是以行业专家的身份来总结最佳实践，而只是分享我们一路走来学到的具体经验。如果你也在开发内部框架，希望这些内容能给你带来一些启发。

培养对 Agent 的直觉

随着越来越多的人读到这些笔记，我反复听到的问题是：“我该怎么学习这些东西？”虽然我没有专门评估这是否是最好的学习方法，但我可以分享自己觉得有效的途径：

阅读关于大语言模型工作原理的入门材料，比如 Chip Huyen 的《AI Engineering》。你也可以跟着做一些简短的教程，不需要自己训练一个 LLM，只需要建立起对它们能力的心理模型。用基础的 LLM API 写一个脚本，让它能响应 Prompt。扩展这个脚本，使其支持工具调用，比如搜索本地 Git 仓库中的文件（或其他类似功能）。实现一个类似 Anthropic Claude 的 tool_search 工具，它使用独立的上下文窗口来评估当前上下文窗口与可用技能的匹配度，只返回相关技能供主上下文窗口使用。实现一个虚拟文件系统，让工具能够操作那些不在当前上下文窗口中的文件引用。同时添加一系列操作该虚拟文件系统的工具，例如 load_file、grep_file 等。支持 Agent Skills，特别是 load_skills 工具，并将可用技能信息补充到 Prompt 中。编写工作流后评估机制，让它在每次工作流结束后自动运行，评估本次执行的质量。增加上下文窗口压缩功能，确保上下文窗口大小保持在设定上限之下。故意让某些工具的返回结果足够大，以至于威胁到上下文窗口的容量上限，从而迫使你去解决这个问题。

在逐一实现上述功能之后，我相信你会对如何构建和扩展这类系统有扎实的理解。唯一缺少的一环是支持构建内部 Agent：代码驱动 vs LLM 驱动的工作流，但遗憾的是，在简单示例中很难体现出代码驱动 Agent 的必要性，因为 LLM 驱动的 Agent 已经足以解决大多数人为构造的例子。

为什么不直接使用 X？

市面上已经有很多现成的 Agent 框架，包括 OpenAI Agents SDK 和 Claude 的 Agents SDK。归根结底，我认为这些框架大多只是比较薄的封装，自己动手实现一遍能学到更多东西。但长期来看，是否应该从零搭建自己的框架，我并没有那么确信。

我的通用建议是：先自己造一个轮子练手，如果之后发现现有框架存在明显局限，再尝试在它们之上继续构建。尽管如此，我一点都不后悔我们选择了自建，因为从代码角度看，它确实非常简洁。

最后的思考

我认为每家公司都应该在内部开展这类工作，即使那些产品中完全不涉及 AI 的公司也不例外。这是一项非常有趣的工作，有巨大的改进空间。只需投入一两名工程师，就能以相对低廉的成本为公司对冲风险——如果 AI 增强技术在 2026 年继续保持 2025 年那样的高速进步的话。
