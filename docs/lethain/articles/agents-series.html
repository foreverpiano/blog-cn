构建内部 Agent

2026-01-01 · 阅读原文

几周前在推动 Imprint 的 AI 采用这篇文章中，我提到了我们正在开发的内部 Agent 工作流。这并不是 Imprint 的核心业务——我们的核心是驱动联名信用卡项目——我希望记录一家像我们这样的公司是如何一步步构建这些内部能力的。

基于那篇文章中提到的公司级公开 Prompt 库等想法，我准备写一系列更短的文章，分享我们在演进工作流过程中遇到的一些有趣问题以及采取的解决方法：

构建内部 Agent：为 Agent Skills 添加支持构建内部 Agent：渐进式披露与处理大文件构建内部 Agent：上下文窗口压缩构建内部 Agent：用 Evals 验证工作流构建内部 Agent：日志记录与可调试性构建内部 Agent：子 Agent 支持构建内部 Agent：代码驱动 vs LLM 驱动的工作流构建内部 Agent：触发器构建内部 Agent：迭代优化 Prompt 与技能

和之前那篇文章一样，我写这些并不是以行业专家的身份来公布最佳实践，而只是分享我们一路走来具体学到的东西。如果你也在开发内部框架，希望你能从这些文章中找到一些有价值的内容。

培养对 Agent 的直觉

随着越来越多的人阅读这些笔记，反复出现的反馈是：“我该怎么学习这些东西？”虽然我没有花时间评估这是否是最好的学习方式，但我可以分享自己觉得有效的方法：

阅读关于大型语言模型工作原理的入门材料，比如 Chip Huyen 写的《AI Engineering》。你也可以做一个简短的教程，你不需要自己去训练一个 LLM，只需要对它们的能力建立一个心智模型。用一个基础的 LLM API 写一个脚本，让它能根据 Prompt 进行回复。扩展这个脚本，使其支持工具调用（tool calling），实现一些基础工具，比如在本地 Git 仓库中搜索文件（或者其他功能）。实现一个类似 Anthropic Claude 的 tool_search 工具，它使用一个独立的上下文窗口来评估当前上下文与可用技能的匹配度，只返回与当前任务相关的技能，以保持主上下文窗口的简洁。实现一个虚拟文件系统，让工具可以操作那些不在当前上下文窗口中的文件引用。同时增加一系列操作该虚拟文件系统的工具，比如 load_file、grep_file 等。支持 Agent Skills，特别是 load_skills 工具，并将可用技能信息增强到 Prompt 中。编写工作流后评估机制，让它在每次工作流结束后自动运行，评估本次执行的质量。增加上下文窗口压缩（context-window compaction）功能，确保上下文长度始终低于设定上限。故意让某些工具的返回内容足够大，以至于威胁到上下文窗口的限制，迫使你去解决这个问题。

在逐一实现上述每个功能之后，我相信你会对如何构建和扩展这类系统建立扎实的基础。唯一缺失的一环是支持构建内部 Agent：代码驱动 vs LLM 驱动的工作流，但遗憾的是，我认为在简单示例中很难展现代码驱动 Agent 的必要性，因为 LLM 驱动的 Agent 已经足以解决大多数人为构造的例子。

为什么不直接使用 X？

目前已经有很多现成的 Agent 框架，包括 OpenAI Agents SDK 和 Claude 的 Agents SDK。最终我认为这些框架大多只是比较薄的封装，自己动手实现一遍能学到更多东西。但我不太确定从长期来看，是否值得自己从零构建一个框架。

我的总体建议是：先自己造一个轮子用来丢弃，然后如果发现现有框架存在明显限制，再尝试在它们之上进行构建。尽管如此，我一点也不后悔我们选择自己开发，因为从代码角度来看，它真的非常简单。

最后的一些想法

我认为每家公司都应该在内部开展这项工作，即使是那些产品中完全不涉及 AI 的公司也不例外。这是一项非常有趣的工作，有巨大的改进空间。如果 AI 增强技术在 2026 年继续像 2025 年那样快速迭代，那么让一两个工程师投入在这上面，是一个相对低成本的去风险方式。
