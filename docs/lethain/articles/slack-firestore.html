使用 Cloud Firestore 为 Slack 应用提供动力

2019-11-10 · 阅读原文

接上篇 让 Slack 应用响应表情回应（reacji）。，现在是时候真正存储和获取真实数据，而不再依赖模拟数据了。我们将使用 Google Cloud Firestore，它是 GCP 提供的 NoSQL 数据库。

到本文结束时，我们的 /reflect 命令和 :ididit: 表情反应都将正确记录，每次调用 /recall 或访问 App Home 视图也都会返回真实数据。

本文从 commit 08eb 开始，到 commit 4584 结束

Slack 应用 Python 系列

在 GCP 上用 Python 创建 Slack 应用在 Python Slack 应用中添加 App Home让 Slack 应用响应表情回应（reacji）。使用 Cloud Firestore 为 Slack 应用提供动力部署你的 Slack 应用。

拆分文件

在开始集成 Cloud Firestore 之前，我对代码仓库进行了大量清理，为后续修改做准备。

我将 reflect/main.py 拆分成多个更小、更专注的文件。我把工具方法移到 reflect/utils.py，将 Slack API 集成代码移到 reflect/api.py。处理事件的端点移至 reflect/events.py，处理 Slash Command 的部分则移到 reflect/commands.py。


from api import get_message, slack_api
from utils import block, verify

最后，我还将存储和获取反思的功能移到了 storage.py，本文中大部分实现工作都将在这个文件中完成。

使用单个函数进行分发

添加存储功能需要修改 event_post、reflect_post 和 recall_post。在当前结构下，这意味着每次修改后都要部署这三个函数，感觉有些过于繁琐。

为了避免这种情况，我改用一个名为 dispatch 的单一入口点，并通过声明路由来确定每个请求对应的处理函数。

def dispatch(request):
    signing_secret = os.environ['SLACK_SIGN_SECRET'].encode('utf-8')
    verify(request, signing_secret)

    # events are application/json, and
    # slash commands are sent as x-www-form-urlencoded
    route = "unknown"
    if request.content_type == 'application/json':
        parsed = request.json
        event_type = parsed['type']
        route = 'event/' + event_type
        if 'event' in parsed and 'type' in parsed['event']:
            route += '/' + parsed['event']['type']
    elif request.content_type == 'application/x-www-form-urlencoded':
        data = request.form
        route = 'command/' + data['command'].strip('/')

    for path, handler in ROUTES:
        if path == route:
            return handler(request)

    print("couldn't handle route(%s), json(%s), form(%s)" % \
          (route, request.json, request.form))
    raise Exception("couldn't handle route %s" % (route,))

这样我们就可以在 ROUTES 这个全局变量中定义各种路由。

ROUTES = (
    ('event/url_verification', url_verification_event),
    ('event/event_callback/app_home_opened', app_home_opened_event),
    ('event/event_callback/reaction_added', reaction_added_event),
    ('command/reflect', reflect_command),
    ('command/recall', recall_command),
)

如果以后想添加更多路由，只需新增一条路由和对应的处理函数，无需去 Slack App 管理后台折腾，也不用新建函数之类的。

但我们确实需要为 dispatch 创建一个 Cloud Function，请使用 gcloud CLI 完成创建。

gcloud functions deploy dispatch \
--env-vars-file env.yaml \
--runtime python37 \
--trigger-http

然后记下新的路由 URL。

https://your-url-here.cloudfunctions.net/dispatch

接着我更新了 /reflect 和 /recall 两个 Slash Command，让它们指向新的 URL，同时也切换到 Event Subscriptions 页面更新了 Request URL。

清理工作完成后，现在我们可以开始做我们来这里的目的：添加存储功能。

准备 Firestore 数据库

由于我们在这个项目中已经深度使用 Google Cloud 的技术栈，我们将采用 Google Firestore 作为后端，主要参考 Firestore 的服务器端快速入门指南。

第一步是创建一个新的 Firestore 数据库。

请选择 Native Mode，这是较新的版本。旧版的 Datastore Mode 正在被弃用，且功能较少。

接下来需要选择数据库所在的区域，以及希望使用单区域还是多区域数据库。你应该选择多区域数据库，不过请阅读定价页面进行确认。两者的免费额度相同，多区域的价格略低于单区域的两倍，但依然很便宜。

此时 Firestore 将开始置备，这个过程需要几分钟时间。

身份验证凭证

接下来我们需要创建身份验证凭证，以便向 Firestore 发送请求。首先确认一下你项目的 project id。

gcloud projects lists

然后创建一个 service account。

gcloud iam service-accounts create reflectapp
gcloud projects add-iam-policy-binding reflectslackapp \
--member "serviceAccount:reflectapp@reflectslackapp.iam.gserviceaccount.com" \
--role "roles/owner"

接着生成密钥。这会在 reflect/ 目录下生成一个名为 gcp_creds.json 的 JSON 文件，其中包含你的凭证。

gcloud iam service-accounts keys create \
gcp_creds.json \
--iam-account reflectapp@reflectslackapp.iam.gserviceaccount.com

如果你在其他目录运行了命令，请将 gcp_creds.json 移动到 reflect/ 目录下。

然后我们需要更新 reflect/env.yaml，让它指向这个凭证文件。

SLACK_SIGN_SECRET: your-secret
SLACK_BOT_TOKEN: your-bot-token
SLACK_OAUTH_TOKEN: your-oauth-token
GOOGLE_APPLICATION_CREDENTIALS: gcp_creds.json

至此，你的凭证就准备好了。

在 Firestore 中建模数据

在开始集成之前，先简单介绍一下 Firestore 的数据模型。从宏观上看，Firestore 的 collection 类似于 SQL 的表，而 document 则类似于 SQL 的行。每份 document 包含一系列键值对，这些值可以是字符串、时间戳、数字等。

然而，这些 document 的能力远超普通的行记录，它们可以包含子 collection 和嵌套对象。我们的数据模型将是一个 users 的 collection，每个用户有一个 tasks 的子 collection，而每次调用 /reflect 都会创建一个新的 task。

读写 Firestore

让我们通过 Python 的 google.cloud.firestore 库来看看如何执行各种我们可能需要的操作，首先是从创建文档开始。注意，创建文档时会隐式创建所在的 collection，无需显式创建。

>>> from google.cloud import firestore
>>> db = firestore.Client()
>>> doc = db.collection('users').document('lethain')
>>> doc.set({'name': 'lethain', 'team': 'ttttt'})
update_time {
  seconds: 1573350318
  nanos: 108481000
}

你也可以不指定文档 ID 直接创建文档。

>>> col = db.collection('users')
>>> col.add({'name': 'lethain', 'team': 'ttttt'})
update_time {
  seconds: 1573370218
  nanos: 107401000
}

获取单个文档。

>>> db.collection('users').document('lethain').get().to_dict()
{'team': 'ttttt', 'name': 'lethain'}

获取 collection 中的所有对象。

>>> for doc in db.collection('users').stream():
...     print(doc.to_dict())
... 
{'name': 'another', 'team': 'ttttt'}
{'name': 'lethain', 'team': 'ttttt'}

接下来我们尝试获取子 collection，例如获取用户 lethain 创建的所有任务。


>>> tasks = db.collection('users').document('lethain').collection('tasks')
>>> tasks.document('a').set({'name': 'a', 'text': 'I did a thing'})
update_time { seconds: 1573350799 nanos: 411757000 }
>>> tasks.document('b').set({'name': 'b', 'text': 'I did another thing'})
update_time { seconds: 1573350807 nanos: 355376000 }
>>> for doc in tasks.stream():
...     print(doc.to_dict())
... 
{'name': 'a', 'text': 'I did a thing'}
{'text': 'I did another thing', 'name': 'b'}

那如何过滤获取部分文档呢？

>>> for task in tasks.where('name', '==', 'b').stream():
...     print(task.to_dict())
... 
{'name': 'b', 'text': 'I did another thing'}
>>> for task in tasks.where('name', '==', 'c').stream():
...     print(task.to_dict())
... 
>>>

我们可以在 where 子句中使用其他运算符，例如 >=、<= 等。在实际实现中，我们会使用 where 子句按时间戳过滤，默认只获取最近一周的任务，并根据用户提供的参数动态调整。

我们还可以对结果进行排序和限制数量。

>>> query = tasks.order_by('name', \
    direction=firestore.Query.DESCENDING).limit(5)
>>> for task in query.stream():
...     print(task.to_dict())
... 
{'name': 'b', 'text': 'I did another thing'}
{'text': 'I did a thing', 'name': 'a'}

删除对象的使用方式和你预想的差不多。

>>> db.collection('users').document('another').delete()
seconds: 1573351166
nanos: 188116000

删除 collection 中的所有对象会同时删除该 collection，但有一个奇怪的注意事项：删除一个文档并不会删除它的子 collection，因此很容易导致数据残留。

好了，我们已经有了足够多的示例，现在可以真正实现任务的存储和获取功能，替换那些存在已久的桩代码了。

实现 reflect

目前当用户通过 /reflect 记录任务时，我们只是把数据打印到日志中，并没有真正保存。

def reflect(team_id, user_id, text):
    print("Reflected(%s, %s): %s" % (team_id, user_id, text))

现在我们可以把它替换成真正能工作的代码。首先在 reflect/storage.py 中添加一个工具函数，用于获取指定用户的 tasks collection。

def tasks(team_id, user_id):
    key = "%s:%s" % (team_id, user_id)
    ref = DB.collection('users').document(key).collection('tasks')
    return ref

然后我们使用这个 collection 来实现 recall 功能。

def reflect(team_id, user_id, text):
    doc = {
        'team': team_id,
        'user': user_id,
        'text': text,
        'ts': datetime.datetime.now(),
    }
    col = tasks(team_id, user_id)
    col.add(doc)

部署更新后的版本，瞧，你的数据真的被存储起来了。在 Slack 中添加一个新任务试试。

/reflect I've added Firestore to this thing #slack #firestore

然后我们可以在 Firestore 数据浏览器中进行验证。

这太棒了！只用了短短几行代码，我们的 Slack 应用就开始做一些真正有用的事情了。

实现 recall

继续在 reflect/storage.py 中，我们使用相同的 tasks 函数获取用户的任务 collection，然后流式读取相关的任务文档。

def recall(team_id, user_id, text):
    col = tasks(team_id, user_id)
    for task in col.stream():
        yield task.to_dict()['text']

我们当然可以进一步完善，以完整支持 /recall 文档中暗示的查询语言，但我认为目前的实现已经足以展示基本框架，可以在此基础上继续迭代。

对 Cloud Firestore 的看法

这是我第一次使用 Cloud Firestore，用完之后我非常兴奋。诚然，它的查询模式相对受限，但在使用过早期版本的 Cassandra 之后，我对在严格约束下建模数据已经相当习惯。

总体来说，它启动快、响应迅速、表达能力足够，对于这类小型工作负载来说也非常便宜。有很多值得喜欢的地方。

我确实觉得 Firestore 的文档有些分散。我要找的内容通常都能找到，但位置往往和我预想的不太一样，而且我还遇到过至少一个指向 404 的文档页面，这有点让人意外。
