使用单个函数进行分发

添加存储功能需要修改 event_post、reflect_post 和 recall_post 三个函数。在当前结构下，这意味着每次修改后都要重新部署这三个函数，感觉过于繁琐。

为了避免这种情况，我改用一个统一的入口函数 dispatch，并通过声明路由的方式来确定每个请求应该由哪个处理函数来响应。

def dispatch(request):
    signing_secret = os.environ['SLACK_SIGN_SECRET'].encode('utf-8')
    verify(request, signing_secret)

    # events are application/json, and
    # slash commands are sent as x-www-form-urlencoded
    route = "unknown"
    if request.content_type == 'application/json':
        parsed = request.json
        event_type = parsed['type']
        route = 'event/' + event_type
        if 'event' in parsed and 'type' in parsed['event']:
            route += '/' + parsed['event']['type']
    elif request.content_type == 'application/x-www-form-urlencoded':
        data = request.form
        route = 'command/' + data['command'].strip('/')

    for path, handler in ROUTES:
        if path == route:
            return handler(request)

    print("couldn't handle route(%s), json(%s), form(%s)" % \
          (route, request.json, request.form))
    raise Exception("couldn't handle route %s" % (route,))

这样我们就可以在全局变量 ROUTES 中定义各种路由。

ROUTES = (
    ('event/url_verification', url_verification_event),
    ('event/event_callback/app_home_opened', app_home_opened_event),
    ('event/event_callback/reaction_added', reaction_added_event),
    ('command/reflect', reflect_command),
    ('command/recall', recall_command),
)

如果以后想添加更多路由，只需增加一条路由和对应的处理函数即可，不需要再去 Slack 应用后台操作、创建新函数之类的。

不过我们仍然需要为 dispatch 创建一个 Cloud Function，请使用 gcloud CLI 来创建它。

gcloud functions deploy dispatch \
--env-vars-file env.yaml \
--runtime python37 \
--trigger-http

然后记下新的路由 URL。

https://your-url-here.cloudfunctions.net/dispatch

接着我把 /reflect 和 /recall 两个 Slash Command 的请求地址都更新为新的路由地址，同时还进入 Event Subscriptions 页面更新了 Request URL。

清理工作完成后，现在我们可以开始做我们此行的目的：添加存储功能。

准备 Firestore 数据库

由于我们已经在 Google Cloud 技术栈中比较深入，所以后端将采用 Google Firestore，主要参考 Firestore 的服务器端快速入门文档。

第一步是创建一个新的 Firestore 数据库。

请选择 Native Mode（较新版本）。旧版本的 Datastore 模式正逐步被弃用，且功能较少。

接下来需要选择数据库所在地区，以及选择单区域还是多区域数据库。推荐使用多区域数据库，不过请务必阅读定价页面进行确认。两者的免费额度相同，多区域的价格略低于两倍，但依然非常便宜。

此时 Firestore 数据库开始创建，大约需要几分钟时间。

身份验证凭证

接下来我们需要创建访问 Firestore 的身份验证凭证。首先确认一下你项目的 project id。

gcloud projects lists

然后创建一个服务账号。

gcloud iam service-accounts create reflectapp
gcloud projects add-iam-policy-binding reflectslackapp \
--member "serviceAccount:reflectapp@reflectslackapp.iam.gserviceaccount.com" \
--role "roles/owner"

接着生成密钥，这会在 reflect/ 目录下生成一个名为 gcp_creds.json 的 JSON 凭证文件。

gcloud iam service-accounts keys create \
gcp_creds.json \
--iam-account reflectapp@reflectslackapp.iam.gserviceaccount.com

如果你在其他目录下执行了命令，请将 gcp_creds.json 移动到 reflect/ 目录中。

然后我们需要更新 reflect/env.yaml，让它指向这个凭证文件。

SLACK_SIGN_SECRET: your-secret
SLACK_BOT_TOKEN: your-bot-token
SLACK_OAUTH_TOKEN: your-oauth-token
GOOGLE_APPLICATION_CREDENTIALS: gcp_creds.json

至此，凭证配置就完成了。

在 Firestore 中建模数据

在开始集成之前，先简单介绍一下 Firestore 的数据模型。从宏观上看，Firestore 的 collection 类似于 SQL 的表，document 则类似于 SQL 中的一行。每份 document 包含一系列键值对，支持字符串、时间戳、数字等类型。

不过，这些 document 的能力远超传统数据库中的一行，它们可以包含子 collection 和嵌套对象。我们的数据模型将是一个 users 的 collection，每个用户拥有一个 tasks 子 collection，每次调用 /reflect 都会创建一个新的 task。

读写 Firestore

下面我们使用 Python 的 google.cloud.firestore 库，逐步演示可能用到的各种操作，首先是从创建文档开始。注意：创建文档时会隐式创建其所在的 collection，无需显式创建。

>>> from google.cloud import firestore
>>> db = firestore.Client()
>>> doc = db.collection('users').document('lethain')
>>> doc.set({'name': 'lethain', 'team': 'ttttt'})

  seconds: 1573350318
  nanos: 108481000
}

你也可以不指定文档 ID 来创建文档。

>>> col.add({'name': 'lethain', 'team': 'ttttt'})
update_time {
  seconds: 1573370218
  nanos: 107401000

...     print(task.to_dict())

我们可以在 where 子句中使用 >=、<= 等其他运算符。在实际实现中，我们会使用 where 子句按时间戳过滤，默认只返回最近一周的任务，并根据用户提供的参数动态调整。

我们还可以对结果进行排序和限制数量。

>>> query = tasks.order_by('name', \
    direction=firestore.Query.DESCENDING).limit(5)
>>> for task in query.stream():
...     print(task.to_dict())

删除操作和你预期的一致。

>>> db.collection('users').document('another').delete()
seconds: 1573351166
nanos: 188116000

删除 collection 中的所有文档会同时删除该 collection。但有个奇怪的注意事项：删除文档并不会删除它的子 collection，因此很容易导致数据残留。

实现 reflect 功能

目前当用户使用 /reflect 记录任务时，我们只是把数据打印到日志中，并没有真正保存。

def reflect(team_id, user_id, text):
    print("Reflected(%s, %s): %s" % (team_id, user_id, text))

现在我们可以替换它为实际可用的代码。首先在 reflect/storage.py 中增加一个工具函数，用于获取指定用户的 tasks collection。

def tasks(team_id, user_id):
    key = "%s:%s" % (team_id, user_id)
    ref = DB.collection('users').document(key).collection('tasks')
    return ref

然后我们使用这个 collection 来实现 recall 功能。

def reflect(team_id, user_id, text):
    doc = {
        'team': team_id,
        'user': user_id,
        'text': text,
        'ts': datetime.datetime.now(),
    }
    col = tasks(team_id, user_id)
    col.add(doc)

然后我们可以在 Firestore 数据浏览器中进行验证。

这真是太棒了！仅仅几行代码，我们的 Slack 应用就开始做真正有意义的事情了。

实现 recall 功能

继续在 reflect/storage.py 中，我们使用同样的 tasks 函数获取用户的任务集合，然后将相关的 task 文档流式读取出来。

def recall(team_id, user_id, text):
    col = tasks(team_id, user_id)
    for task in col.stream():
        yield task.to_dict()['text']

对 Cloud Firestore 的看法

这是我第一次使用 Cloud Firestore，用完之后相当兴奋。诚然，它的查询模式相对受限，但在经历过早期版本的 Cassandra 之后，我已经非常适应在严格约束下进行数据建模。

总的来说，它启动快、响应迅速、表达能力足够，对这种小型工作负载来说也非常便宜。有很多值得喜欢的地方。

我觉得 Firestore 的文档组织得有些零散。我要找的内容通常都能找到，但位置往往不是我预期的，还碰到过至少一个文档页面跳转到 404 的情况，有点意外。
