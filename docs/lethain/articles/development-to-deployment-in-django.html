三个仓库的故事

我整个开发-部署流程的基础是三个代码仓库（使用分布式版本控制会更简单一些，不过用 Subversion 或 CVS 也能实现类似效果）。

一个托管在非本地也非生产环境的主仓库。我用自己的 Slicehost 服务器来托管所有私有 git 仓库（它有每日和每周备份，如果出问题我也能自己修复），你也可以使用付费的 GitHub 账号或其他类似服务。每个开发者本地都有一个仓库，定期推送到主仓库。每台生产服务器上都有一个生产仓库。

开发者主要在本地机器上工作，将代码推送到主仓库的对应分支上。他们也会偶尔从主仓库拉取更新，以保持仓库同步。

生产服务器设置

我会把目录结构保持得非常简单且统一。所有生产服务器上都有一个名为 django 的用户，其密码已被禁用且没有 SSH 权限。开发者在生产机器上有账号，他们属于 django 用户组，因此可以修改 django 用户的所有文件（把 SSH 配置成免密登录能省掉你好几天的麻烦）。

我会根据版本控制系统将第三方库按文件夹组织，通常会有 git 和 svn 文件夹，根据实际情况也可能出现 hg 或 bzr 文件夹。（好吧，我承认我几乎没用过 bzr 文件夹，只是想说得更全面一些。）然后我把它们全部软链接到 /usr/python2.?/site-packages/ 目录下（最近几年我一直在用 Python 2.5，不过未来一两年如果 2.6 有显著性能提升，我可能会升级）。

我更喜欢直接链接到仓库的检出目录（而不是用 setup.py 安装），这样以后如果需要更新库，在所有生产服务器上操作会更方便。

对于静态资源，我会把项目或应用仓库中需要的文件夹软链接到 /var/www/example.com/media/，然后让 Nginx 负责提供服务。（我依然很满意 Nginx + Apache2 + mod_python 的组合，尽管它已经不太被最潮的开发者们青睐，他们现在都转投 WSGI 了。）

测试……

你可以在测试集成上做很多有创意的事情（比如只有所有测试通过才允许部署脚本推送到生产环境，或者在主仓库的 post-commit hook 中运行测试，并在测试失败时邮件通知开发者等等）。但我目前仍然是手动运行测试。这大概会是我接下来要改进的下一个环节。
