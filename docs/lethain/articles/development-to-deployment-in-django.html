从开发到部署：Django 实践

2008-11-03 · 阅读原文

我在 Django 开发过程中做过的最有价值的事情之一，就是建立了一套稳定一致的开发到部署流水线。下面我快速介绍一些让我工作更轻松的做法，同时也很想听听大家都在使用哪些技巧。

local_settings.py 进阶用法

使用 Django 进行部署时，最好用的技巧之一是在 settings.py 文件末尾加上下面四行代码：

try:
    from local_settings import *
except ImportError:
    pass

这样你就可以用 local_settings.py 的内容来覆盖 settings.py 中的设置。对于一个公开、可分享的项目，你最多只能做到提供一个 local_settings.py 模板供用户自行修改。但如果你控制着生产环境和开发环境（比如私有项目），就可以把这个技巧用得更深入。

我会创建一个 production_settings.py 文件存放生产服务器的配置，再创建一个 devel_settings.py 用于本地开发。两者都纳入版本控制，然后在本地代码仓库中创建一个 local_settings.py，内容如下：

from devel_settings import *

而生产环境的 local_settings.py 则是这样的：

from production_settings import *

最后，确保 local_settings.py 不被版本控制系统跟踪。

我喜欢这种设置，因为它（和标准的 local_settings.py 技巧一样）能方便地修改共享配置。此外，它还让我无需 SSH 到生产服务器就能调整生产环境的设置，而且比在仓库中维护 production 和 development 两个分支（需要大量无意义的合并操作）要简单得多。

devel_settings.py 和 production_settings.py 的内容

我的 devel_settings.py 文件几乎每次都长得一模一样，和具体项目无关。你的可能会有所不同，但我发现保持一个标准化的项目模板（而不是每次都用 django-admin startproject 创建新项目）能节省不少思考的时间。

我的 devel_settings.py 大致是这样的：

# Settings for devel server
import os
ROOT_PATH = os.path.dirname(__file__)
DEBUG = True
TEMPLATE_DEBUG = DEBUG
COMPRESS = False # django-compress setting
CACHE_BACKEND="locmem:///"
DATABASE_ENGINE = 'sqlite3'
DATABASE_NAME = os.path.join(ROOT_PATH, 'devel.sqlite')
DATABASE_USER = ''
DATABASE_PASSWORD = ''
DATABASE_HOST = ''
DATABASE_PORT = ''
MEDIA_ROOT = os.path.join(ROOT_PATH, 'media')
MEDIA_URL = 'http://127.0.0.1:8000/media/'
ADMIN_MEDIA_PREFIX = '/media/admin/'

production_settings.py 的内容则根据 Postgres 和 Memcached 的配置有所不同，但大体结构类似下面这样：

# Django settings for codernode.com project
COMPRESS = True # django-compress setting
COMPRESS_VERSION = True # django-compress setting
DEBUG = True
TEMPLATE_DEBUG = DEBUG
ADMINS = (('Mr Admin','admin@example.com'),)
MANAGERS = ADMINS
CACHE_BACKEND="memcached://127.0.0.1:11211"
EMAIL_SUBJECT_PREFIX = "[My Project]"
SERVER_EMAIL = "django@example.com"
DEFAULT_FROM_EMAIL = 'info@example.com'
DATABASE_ENGINE = 'postgresql_psycopg2'
DATABASE_NAME = 'some_database'
DATABASE_USER = 'some_user'
DATABASE_PASSWORD = 'some_password'
DATABASE_HOST = ''
DATABASE_PORT = ''
TIME_ZONE = 'America/Chicago'
LANGUAGE_CODE = 'en-us'
SITE_ID = 1
USE_I18N = True
MEDIA_ROOT = '/path/to/media/root/'
MEDIA_URL = 'http://example.com/media/'
ADMIN_MEDIA_PREFIX = '/media/admin/'
TEMPLATE_DIRS = ()

你的配置很可能会有很大差异。

三个代码仓库的故事

我整个开发-部署流水线的核心是三个代码仓库（使用分布式版本控制会更简单，但用 Subversion 或 CVS 也能实现类似效果）。

一个托管在非本地、非生产环境的主仓库。我用自己托管博客的 Slicehost 服务器来存放所有私有 Git 仓库（它有每日和每周备份，如果出问题我也能自己修复）。你也可以使用付费的 GitHub 账号或其他类似服务。 每个开发者本地都有一个仓库，定期推送到主仓库。 每台生产服务器上都有一个生产仓库。

开发者主要在本地机器上工作，并将代码推送到主仓库的对应分支。他们也会偶尔从主仓库拉取代码，以保持仓库同步。

生产仓库的更新方式有以下几种：

使用 Fabric 远程命令生产服务器拉取最新代码。这是大型、中型和小型部署的最佳选择。也就是说，这永远都是最好的方案，其他的不用再看了。 SSH 登录到生产服务器，手动拉取更新。或者写一个批处理脚本来完成。这种方式对于单机部署已经足够，但如果规模更大，就应该使用专业的部署方案。 设置定时任务（cronjob）定期拉取更新。这是最简单、最偷懒的方式，但在大多数情况下并不推荐。

使用这套方案，从开发环境推送改动到生产环境只需要两个步骤：

git push
fab deploy

我强烈建议再加一个 fab revert hash-to-revert-to 命令，以便在部署不顺利时能快速回滚。

生产服务器的设置

我会保持目录结构非常简洁且统一。所有生产服务器上都有一个名为 django 的用户，其密码已被禁用且没有 SSH 权限。开发者在生产机器上有账号，他们属于 django 用户组，因此可以修改 django 用户的所有文件（把 SSH 配置成免密登录能省掉你好几天的时间）。

我会根据版本控制系统的不同把各种库分别放在不同文件夹里，所以通常会有 git 文件夹和 svn 文件夹，根据使用的库可能还会有 hg 或 bzr 文件夹。（好吧，我承认我几乎没用过 bzr 文件夹，只是想显得更全面。）然后我把它们全部软链接到 /usr/python2.?/site-packages/ 目录下（最近我一直主要使用 Python 2.5，不过如果 2.6 有显著的性能提升，我可能一两年内会升级）。

我更喜欢直接链接到代码仓库的签出目录（而不是用 setup.py 安装），这样以后如果需要更新库，可以更方便地在所有生产服务器上统一操作。

对于静态媒体文件，我会把项目或应用仓库中对应的文件夹软链接到 /var/www/example.com/media/，然后让 Nginx 负责提供服务。（我依然很满意自己的 Nginx/Apache2/mod_python 组合，即使它已经不再被最潮的开发者们所青睐，大家都转向 WSGI 了。）

测试……

你可以在测试集成上做很多有创意的事情（比如只有所有测试通过时部署脚本才会推送到生产环境，或者在主仓库的 post-commit hook 中运行完整测试，如果失败就邮件通知开发者等等），但我目前还是手动运行测试。这大概会是我接下来要改进的地方。

你有没有使用这里没有提到的其他技巧？或者拥有更好的整体设计方案？我很想看看大家是如何解决这个普遍性问题的。
