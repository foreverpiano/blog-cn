用 Wardley Map 分析 LLM 生态系统

2024-12-24 · 阅读原文

在 如何采用大语言模型（LLMs）？ 中，我们探讨了一家理论上的网约车公司——Theoretical Ride Sharing——应该如何采用大型语言模型（LLMs）。该策略的诊断部分依赖于对 LLM 生态系统未来演进的理解，为此我们绘制了一张 用 Wardley Mapping 完善策略 来深入探讨。

这张 LLM 领域的 Wardley Map 重点关注产品型公司如何应对模型提供商（例如 Anthropic、Google 和 OpenAI）的激增，以及 LLM 产品模式（如智能体工作流、Retrieval Augmented Generation（RAG）以及通过运行评估来维持模型性能变化后的表现）的快速扩散。

当前的运行方式

如果说 Retrieval Augmented Generation（RAG）是 2023 年最流行的 LLM 模式，而你也可以合理地认为智能体（或称 agentic workflows）是 2024 年的主流模式，那么未来的模式会是什么虽然很难预测，但几乎可以肯定还会出现更多新的模式。如今 LLM 已被证明是一个成熟的平台，正在被广泛应用以发掘新的模式。可以肯定的是，验证这些新模式将继续推动产品公司去支持更多基础设施组件（例如支持 RAG 的搜索索引）。

这种模式的激增给产品公司带来了显著的成本问题，而市场力量很可能在产品演进过程中解决这一问题。

向未来状态的转变

观察 LLM 生态系统的演进，我认为有两个问题将决定这个领域的未来发展方向：

面向智能体、RAG 等场景的 LLM 框架平台是否会继续与 OpenAI、Anthropic 等模型提供商捆绑在一起？还是会与模型分离，平台和模型分别独立提供？LLM 框架中有哪些部分在短期内可以产品化？例如，运行评估（running evals）似乎是一个直接的打包机会，提供一定程度的智能体支持也是如此。相反，虽然把 RAG 打包看起来很简单，但大多数生产用例都需要实时更新，这会带来运营大规模搜索集群的全部复杂度。

根据对这些问题的不同回答，你可能会画出完全不同的地图。本图对第一个问题的回答是：LLM 平台将与模型提供商解耦，同时允许你通过该平台获得模型访问权限，而无需与每个模型提供商单独谈判。对第二个问题的回答是：除 RAG 之外的大部分功能将进入一个打包的平台提供商。鉴于当前领域投资的丰富性，可以合理认为各种可能组合都会在一定程度上存在，直到生态系统最终稳定在某一种主导配置上。

这种配置的核心驱动因素在于：LLM 生态系统每年都在推出新的模式，企业正在匆忙搭建内部解决方案来验证这些模式，但最终很少有产品公司能够长期有效负担这类内部解决方案。

如果这张地图是正确的，那么模型提供商（本质上只能提供自己那一小部分模型）和窄领域 LLM 平台提供商（只能服务部分 LLM 模式）最终都将面临阻力。在这种未来下，产品公司最好的选择是采用当前覆盖最广的 LLM 模式平台，并明确将模式平台与模型提供商解耦。

用户与价值链

LLM 领域正在快速发展，有些技术在短短一年内就从提出走向广泛采用。这些被广泛采用的技术有时确实是被真正落地，有时则更接近“会议演讲驱动开发”——拥有广泛影响力的平台夸大了行业采用的成熟度。

试图驾驭这种动态变化的三类主要用户是：

产品工程师希望找到更快、更简单的方案来部署 LLM，以应对不断变化的各种参数：新模型、智能体支持、卸载检索增强生成（RAG）中的搜索维度等。机器学习基础设施团队负责这些机制的有效使用，并引导产品开发者有效地采用这些工具。他们还与其他基础设施工程团队一起，负责支持 LLM 解决方案的公共组件，例如用于实现 RAG 的搜索索引。安全与合规——如何确保模型被安全可靠地托管，且我们只发送经过批准的信息？我们如何与快速演变的 AI 风险和要求保持一致？

为了让地图聚焦于演进而非组织动态，我对一些团队进行了略带人为的合并，并省略了几个确实值得考虑的团队。财务团队需要了解 LLM 的成本和使用情况。安全和合规实际上是不同的团队，二者既有重叠又有各自独特的需求。机器学习基础设施团队也可以拆分为两个观点有时相互冲突的团队，尤其是在搜索基础设施这类组件的归属权上。
