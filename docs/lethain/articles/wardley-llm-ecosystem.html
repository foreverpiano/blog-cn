Wardley 地图分析 LLM 生态系统

2024-12-24 · 阅读原文

在 如何采用大语言模型（LLMs）？ 中，我们探讨了一家理论上的网约车公司——Theoretical Ride Sharing——应该如何采用大型语言模型（LLMs）。该策略的诊断部分依赖于对 LLM 生态系统未来演进的理解，为此我们绘制了一张 使用 Wardley Mapping 优化策略 来更好地进行探索。

这张 LLM 领域的 Wardley 地图重点关注产品型公司如何应对模型提供商的激增（例如 Anthropic、Google 和 OpenAI），以及 LLM 产品模式（如智能体工作流、Retrieval Augmented Generation (RAG)）的激增，同时还要应对在模型不断更新时通过运行评估来维持性能的需求。

当前的运作方式

如果说 Retrieval Augmented Generation (RAG) 是 2023 年最热门的 LLM 模式，而智能体（或称 agentic workflows）可以合理地被视为 2024 年的主流模式，那么我们很难预测明天的模式会是什么，但可以肯定的是，会有更多新的模式不断涌现。如今 LLM 已被证明是一个成熟的平台，并正被广泛应用于发现新的模式。可以预见的是，对这些新模式的验证将继续推动产品型公司去支持更多基础设施组件（例如支持 RAG 的搜索索引）。

这种模式的激增给产品型公司带来了显著的成本负担，而市场力量很可能会随着产品演进而解决这个问题。

向未来状态的过渡

在观察 LLM 生态系统的演进时，我认为有两个核心问题将决定这个领域的未来走向：

支持智能体、RAG 等功能的 LLM 框架平台是否会继续与 OpenAI、Anthropic 等模型提供商绑定在一起？还是会发生拆分，让模型和平台分别独立提供？LLM 框架中有哪些元素在短期内可以被产品化？例如，运行评估（running evals）似乎是一个直接的打包机会，提供一定程度的智能体支持也是如此。相反，将 RAG 打包看似简单，但大多数生产用例都需要实时更新，这会带来运营大规模搜索集群的全部复杂性。

根据对这些问题的不同回答，你可能会画出完全不同的地图。本地图对第一个问题的回答是：LLM 平台将与模型提供商解耦，同时允许你通过该平台获得模型访问权限，而无需与每个模型提供商单独谈判。对第二个问题的回答是：除 RAG 之外的大多数功能将进入一个打包的平台提供商手中。鉴于当前领域投资的丰富程度，可以相信每一种合理的组合都会在一定程度上存在，直到生态系统最终稳定在某一种主导配置上。

形成这种配置的关键驱动因素在于：LLM 生态系统每年都在投入新的模式，企业纷纷建立临时性的内部方案来验证这些模式，但最终很少有产品型公司能够长期有效支撑这类内部解决方案。

如果这张地图是正确的，那就意味着模型提供商（本质上只能提供自己那一部分模型）和狭窄的 LLM 平台提供商（只能服务于 LLM 模式中的一部分）最终都会面临阻力。在这样的未来，对产品型公司而言，最佳选择是今天就采用覆盖最广的 LLM 模式平台，并明确地将模式平台与模型提供商解耦。

用户与价值链

LLM 领域正在快速发展，有些技术从提出到被广泛采用仅需一个日历年。有时候那些被广泛采用的技术确实在真正落地，而另一些时候则更接近于“会议演讲驱动开发”——拥有广泛平台影响力的人夸大了行业采用的成熟度。

试图驾驭这种动态环境的三类主要用户是：

产品工程师希望找到更快、更简单的方案来部署 LLM，以应对各种不断变化的参数：新模型、智能体支持、RAG 中搜索维度的卸载方案等等。机器学习基础设施团队负责这些机制的有效使用，并引导产品开发者进行高效采用。他们还与其他基础设施工程团队共同负责支持 LLM 解决方案的通用组件，例如用于驱动 RAG 实现的搜索索引。安全与合规——如何确保模型被安全可靠地托管，且我们只发送经过批准的信息？我们如何与快速演变的 AI 风险和要求保持一致？

为了让地图聚焦于演进而非组织动态，我对若干团队进行了略带人为的合并，同时省略了一些确实值得考虑的团队。财务团队需要了解 LLM 的成本和使用情况。安全与合规实际上是两个不同的团队，它们既有重叠的需求，也有各自独特的要求。机器学习基础设施团队可以拆分为两个具有不同视角的团队，在搜索基础设施等组件的归属问题上可能存在冲突。

根据你希望从这张地图中获得什么洞见，你可能更倾向于以不同于我的方式进行合并、拆分或引入其他组合。
