什么是 literate programming 的反面。

2019-07-14 · 阅读原文

编程领域我最喜欢却始终没有真正落地的一个想法是 literate programming。它探讨如果我们把代码和文档——也就是“怎么做”和“为什么”——更紧密地融合，通常放在同一个文件里，编写和阅读软件的过程会变成什么样子。

当我回顾 时，我希望自己当时能拥有相反的工具：强大、易于扩展的写书工具。如果非要紧急造一个名字的话，我们或许可以叫它“可编程读写能力”（programmable literacy）。我写书学到的东西

想象一下，你写的书里每个章节都标记了前置内容！这样就能轻松确保内容顺序正确，即使多次重构内容，也很容易避免引用尚未引入的概念。

我最近还发现了一种相当小众的奇幻/科幻子类型叫 LitRPG，我实在无法推荐（这个类型的写作质量本来就参差不齐，而这个子类型的质量更是明显偏低），但它的结构很有意思。特别是这类作品经常反复渲染相同结构化的内容（比如描述主角的状态表格），这让我开始思考：作者要在几百页的篇幅里维护那么多可变状态，有什么工具能帮助他们避免连续性错误呢？

把这些想法与我想初步接触 Rust 的愿望结合在一起，我在过去一周左右的时间里快速写出了 literal。说清楚一点，这不是高质量的 Rust 代码，因为我对 Rust 的工作原理还一知半解，但它确实是一个可运行的概念验证，展示了“可编程读写能力”的一个简单版本可以如何实现。

简而言之，你用 Markdown 语法写作，加入一些额外的指令，其中之一是渲染模板（使用 Tera 所支持的 Django 模板语言子集）。

你的文档文件可能长这样：

\init title My Cool Book
\init author Will
\init chapter 1
\init chapter_title First Chapter    
\render templates/chapter.md

This is an insightful chapter, filled with insight.

\incr chapter 1
\incr chapter_title Second Chapter
\render templates/chapter.md    

Honestly, not as good as chapter one.

然后你的 templates/chapter.md 会是这样的：

## Chapter {{ chapter }}: {{ chapter_title }}
*{{ title }} by {{ author }}.*

接着你运行 literal 来展开内容，或许再通过 pandoc 进行渲染。例如，你可以用下面命令把它转换成 epub 格式的电子书：

./literal book.md | pandoc -f gfm -o mybook.epub

我还添加了一些非常简单的断言支持，如果功能更强大，可以用来绘制书中预期状态并确保其前置条件得到满足。你可以想象一个完整版本，本质上就是写书的“测试驱动开发”。

\init chapter 1
\assert chapter 1

Do some stuff

\incr chapter 1
\assert chapter 2

这些断言都会成功，但如果你尝试一个错误的断言，比如：

\init chapter 1
\assert chapter 2

老实说，目前这个工具本身并没有那么实用，但它是一个很好的 Rust 学习项目。我认为如果继续构建一个更强大的工具包——支持渲染计算值、更实用的数据结构，甚至任意代码执行——你能做出非常强大（也非常小众）的东西。

总的来说，这是一次有趣的探索，我期待不久后能真正理解 Rust 的借用概念（我老是忍不住把它想成引用，这似乎微妙地错了）。这也是我写的最大的一个个人项目完全使用 VSCode，我正慢慢把它当成默认 IDE，用在那些让 Emacs 感到吃力的项目上。
