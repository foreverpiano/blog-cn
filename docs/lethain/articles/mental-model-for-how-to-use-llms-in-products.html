如何在产品中使用大语言模型的笔记

2024-04-08 · 阅读原文

我所知道的几乎每家公司都在寻找利用大语言模型（Large Language Models，简称 LLMs）的方式。即使高管们觉得没多少实际应用价值，他们的投资人很可能不这么想，于是他们盯着空白页面，紧张地试图想出一个点子。论证 LLMs 能在某种程度上提升内部效率相对容易，但要描述一种可信的方式，让 LLMs 让你的产品对用户更有价值，则要困难得多。

过去一年，我一直在直接研究如何将 LLMs 有意义地应用到现有产品中，并想把一些相对零散的笔记整理出来。这些笔记没有特别的顺序，目标读者是正在构建产品的行业从业者。

你可以在 Youtube 上观看基于这些笔记的演讲录像，或者查看幻灯片。

重建你的心智模型

行业中仍有许多人在构建自己对 LLMs 的心智模型，这导致他们在判断 LLMs 能做什么以及该如何使用它们时出现大量推理错误。我看到很多人对 LLMs 抱有的两种无益的心智模型是：

LLMs 是魔法：人类能做的任何事情，LLM 可能都能做到大致相当的水平，而且速度快得多。LLMs 和强化学习是一回事：当前出现的幻觉和准确性问题是由数据集太小造成的。准确性问题会随着更大训练集的出现而解决，我们可以依靠置信分数来降低不准确的影响。

这两种观点在不同但重要的方面都是错误的。 为了避免陷入这些心智模型的谬误，我建议采用以下几个支柱来构建一个有用的 LLMs 心智模型：

LLMs 可以针对任何提示预测合理的回应——无论你写出什么样的文本提示，LLM 都会自信地提供一个回应，并且越来越能针对文本加上图像或视频等其他媒体形式提供回应。你无法知道某个具体回应是否准确——LLMs 会生成意料之外的结果，也就是所谓的幻觉（hallucinations），你无法确切知道它们什么时候出错。它们不会生成置信分数来帮助你判断某个特定答案是否可靠。你可以通过评估（evals）来估计模型在给定一组提示下的准确性——你可以用评估的方法，即让 LLM 运行在一组已知的提示上，记录其回应并对这些回应进行评估，从而判断 LLM 在特定场景下表现良好的可能性。你通常可以通过使用更大的模型来提高准确性，但这会增加成本并带来更高的延迟——例如，GPT-4 比 GPT-3.5 模型更大，通常能提供更高质量的回应。然而，它的成本明显更高（约贵 20 倍），速度也明显更慢（慢 2-5 倍）。不过，在每个价格点上，质量、成本和延迟都在不断改善。你应该预期在未来五年内，在给定成本、延迟或质量水平下的逐年性能都会有显著提升（例如，你应该预期在 12-24 个月内，能以 GPT-3.5 的价格和延迟获得 GPT-4 的质量）。模型的准确性通常会随着其训练语料库的规模增长而提高——强化学习的准确性通常随着数据集增长而可预测地提升。这对 LLMs 大体上也是成立的，但可预测性较差。小模型通常表现不如大模型。大模型通常在配合更高质量数据时优于小模型。用特定数据来补充大型通用模型被称为“微调”（fine-tuning），目前尚不清楚在什么时候微调一个小模型会优于直接使用一个更大的模型。你真正能做的就是针对你的具体用例，基于可用的模型和微调数据集来运行评估。即使最快的 LLMs 也没那么快——即使是一个快速的 LLM，也可能需要 10 秒以上才能生成一个合理长度的回应。如果你需要多次迭代来优化初始回应，或者使用更大的模型，整个过程可能需要一两分钟。这些速度会越来越快，但目前还不够快。即使是最贵的 LLMs，对 B2B 使用来说也没那么贵。即使是最便宜的 LLM，对消费者使用来说也没那么便宜——因为定价由使用量驱动，这项技术对用户量较小且付费的 B2B 业务来说非常容易论证其合理性。相反，在消费者业务中，如果要承担大量 LLM 使用量，又不想显著压缩利润空间，就非常具有挑战性。

这些支柱并不完美，但希望它们能为你提供一个良好的基础，来思考将 LLMs 应用到产品中什么可行、什么不可行。有了这个基础，现在我们可以深入探讨一些更具体的子主题。

重新设计工作流

大多数现代软件中的工作流并非为最大化从 LLMs 中获益而设计的。这并不奇怪——它们在 LLMs 普及之前就已经构建好了——但这确实需要我们对工作流设计进行一些重新思考。

为了说明这一点，我们来想想一个抵押贷款提供商的软件：

用户创建账户产品要求用户填写大量数据，以了解用户想要什么样的抵押贷款以及用户是否符合资格产品要求用户提供文件来支持刚刚提供的数据，比如最近的工资单、银行账户余额等内部团队验证用户提供的数据与文件是否一致

在这个工作流中，LLMs 仍然能为企业提供显著价值，因为你可以提高验证用户提供的信息与文件是否匹配的效率，但用户自己除了可能更快获得申请验证结果外，并不会看到太多好处。

然而，你可以调整工作流，使其更有价值：

用户创建账户产品要求用户提供文件产品使用 LLM 从文件中提取数值用户验证提取的数据是否正确，并进行一些调整内部团队审查用户的调整，以及规则引擎提出的任何高风险问题

这两个产品的技术复杂度实际上是等同的，但用户体验却完全不同。内部团队的体验也得到了改善。我相信，许多现有产品只有通过重新思考它们的工作流，才能显著从 LLMs 中获益以改善用户体验。

检索增强生成（Retrieval Augmented Generation，简称 RAG）

模型在给定提示中能考虑的文本有一个最大的“token 窗口”。token 窗口的最大尺寸正在快速扩大，但更大的 token 窗口评估起来更慢、成本也更高，因此即使不断扩大的 token 窗口也无法完全解决问题。

在固定 token 窗口内处理大型数据集的一种解决方案是检索增强生成（RAG）。举一个具体的例子，你可能想创建一个约会应用，根据用户对以下问题的自由回答来匹配个人：“你与书籍、电视节目、电影和音乐的关系如何，它随着时间如何变化？”没有任何 token 窗口大到能把约会应用数据库中每个用户的回答都塞进 LLM 的提示里，但你可以先通过位置筛选找到二十个可能匹配的用户，然后把这二十个用户的自由回答包含进来，并在它们之间进行匹配。

这很有道理，先用一个不太复杂的算法找到可能的回应组件，再用 LLM 对这些可能的回应进行筛选和打包，形成最终的回应，这两阶段组合的效果相当不错。

我看到人们陷入麻烦的地方，是试图把 RAG 当作搜索问题的解决方案，而不是认识到 RAG 的实现本身就需要有效的搜索。一个有效的 RAG 方法依赖于高质量的检索和过滤机制，才能在非 trivial 的规模上良好运作。例如，从 RAG 的高层视角来看，有些人可能认为他们可以用 RAG 替换自己的搜索技术（比如 Elasticsearch），但这只有在你的数据集非常小，并且你能容忍明显更高的响应延迟时才成立。

在我看来，挑战在于，大多数偷工减料的方案在小数据集上看起来都能工作，同时让你假装搜索相关性这类事情不重要。但现实是，当你走出原型阶段后，相关性会显著影响回应的质量（无论这是字面意义上的搜索相关性，还是经过更好调优的 SQL 查询来检索更合适的行）。这会制造出一种关于原型如何转化为生产能力的错误预期，并带来所有可预见的后果：低估时间线、生产环境表现/性能不佳等等。

创新的速度

模型性能——本质上是在给定预算（无论是美元还是毫秒）下的回应质量——将会继续提升，但如果在创建或处理 LLMs 方面没有重大技术突破，它就不会以当前的速度持续提升。我预计这些突破会发生，但在最初几年之后，发生的频率会降低，并逐渐放缓。我们很难判断目前处于这个周期的哪个阶段，因为仍有大量资本持续流入这个领域。

除了技术突破，推动创新的另一个方面是构建越来越大的模型。目前还不清楚，今天限制模型规模的因素是 Nvidia GPU 的可用性、能否获得更大且法律上可接受的训练数据集、训练新模型所需的资本，还是财务模型显示训练更大模型的贴现未来现金流无法达到合理的回本周期。我的假设是，这些因素都会或已经先后成为限制 LLM 创新的瓶颈，而不同的竞争者会在最相关的约束条件下最有优势取得进展。（这里可以想象很多有趣但边缘的情景，例如，设想美国政府为了在 LLM 训练竞赛中不输给不尊重美国版权法的国家，而废除版权法以允许在更大数据集上训练。）

可以放心地假设模型性能会继续提升。在未来几年内性能会显著提升也很可能是真的。我认为我们不太可能看到类似摩尔定律的情景，让 LLMs 在几十年内持续大幅改进，但很多事情都可能轻易证明我错了。例如，核聚变在某个时刻会成为主流，并彻底改变我们对能源利用的看法，以真正重塑世界结构，而 LLM 的训练成本可能是其中一部分。

人参与循环（Human-in-the-Loop，简称 HITL）

因为你无法依赖 LLMs 提供正确的回应，也无法为任何给定回应生成置信分数，所以你要么接受潜在的不准确性（这在很多情况下是合理的，人类有时也会出错），要么保持一个人参与循环（HITL）来验证回应。

正如在工作流部分讨论的那样，许多公司已经有人在做验证工作，他们现在可以转向监督 LLM 的回应，而不是自己生成回应。在其他场景中，也可以调整产品的工作流，让外部用户来充当 HITL。我认为大多数产品都会同时依赖这两种技术，并辅以启发式规则来决定何时需要内部审查。

幻觉与法律责任

如前所述，LLMs 经常会自信地生成错误的回应。HITL 是防止根据这些自信的错误回应采取行动的设计原则。这是因为它将责任（特别是法律责任）从 LLM 本身转移到了具体的人身上。例如，如果你使用 Github Copilot 生成的代码导致了安全漏洞，那么你要对该安全漏洞负责，而不是 Github Copilot。今天所有大规模采用 LLMs 的方式，都是在将回应的责任转移给参与的人类。

许多早期创业者梦想着一个非常不同的循环，在其中可以不依赖 HITL 而直接依靠 LLMs，但我认为这只会在能够转移法律责任（例如 Github Copilot 的例子）或者本来就没有法律责任（例如根据用户头像生成一首有趣的诗）的场景中成立。

“从零到一”与“从一到 N”

人们强烈渴望一个 LLMs 可以取代软件工程师，或者软件工程师从编写软件转向监督角色的世界。例如，一位创业者想构建一个 Reddit 的复制品，并使用 LLM 来实现它。目前已经有足够证据表明，今天你可以用 LLM 和一些调试技能，在几周内从零到一地实现一个新的产品想法。

然而，大多数创业者对运营和演化一个拥有大量用户的软件缺乏深刻的直觉。以下是一些例子：

在改变 UI 后保持用户参与需要积极、刻意的工作确保用户数据安全并满足各种隐私合规义务提供满足 SOC2 的控制措施并提供可审计的证据证明持续维护这些控制将包含客户数据的数据库 schema 迁移以支持一组新的列将查询模式收紧到一组在更高规模下能有效运行的允许模式

所有这些都是扩展产品（即“从一到 N”）的简单、基本组成部分，而 LLM 根本无法有效完成这些工作。我也怀疑我们是否会看到特别可靠的、基于 LLM 的替代方案来取代熟练的人类智能。不过，看着人们如何努力推动 LLM 自动化能力的边界，以延迟需要聘请专业人才的项目到来，会是一件很有趣的事情。

版权法

版权的影响今天还非常不清晰，并且在可预见的未来仍将如此。今天所有使用 LLMs 完成的工作都必须考虑到不同的法律结果。我最好的猜测是，我们会看到一个关于 LLM 生成的内容是否可版权的法律碎片化时代，而从更长期来看，LLMs 将被视为和其他任何基本技术组件一样，例如运行拼写检查器不会撤销你对经过拼写检查的文档的版权。你可以提出各种好的论点来说明为什么这个观点对被用于训练的数据的版权持有人不公平，但从长期来看，我认为其他任何解释都行不通。

数据处理协议

今天在使用 LLMs 时一个细小但有趣的现实是，许多客户对 LLM 提供商（OpenAI、Anthropic 等）保持敏感，因为这些提供商是相对较新的公司，正在构建相对较新的东西，缺乏法律先例来降低风险。这意味着将它们加入你的数据处理协议（Data Processing Agreement，简称 DPA）可能会产生一些摩擦。解决这种摩擦最显而易见的方式，是通过你现有的云厂商（AWS、Azure、GCP 等）来使用 LLM 功能。

提供商可用性

我曾经认为这非常重要，但现在我的感觉是，LLM 托管已经基本上和其他云服务相当（例如，你可以通过 AWS 使用 Anthropic，或者通过 Azure 使用 OpenAI），很少有公司会从花费过多时间担心 LLM 可用性中获益。我确实认为，通过云提供商——那些非常熟悉可扩展性的公司——获得对 LLMs 的直接访问，很可能也是这里最优的选择。

外面有很多人比我花更多时间深入思考 LLMs——例如，去读读 Simon Willison 的文章——但希望这里的笔记对你有用。如果有人不同意其中任何观点，我很乐意讨论。
