如何在你的产品中使用大语言模型（LLM）的笔记

2024-04-08 · 阅读原文

我所知道的几乎每家公司都在寻找从大型语言模型（Large Language Models）中获益的方法。即使高管们认为适用性不大，他们的投资人很可能持不同看法，因此他们正紧张地盯着空白页，努力想出一个点子。论证 LLM 能在某种程度上提升内部效率相对容易，但要描述一种可信的方式，让 LLM 让你的产品对客户更有价值，则要困难得多。

过去一年，我一直在直接研究如何将 LLM 有意义地应用到现有产品中，并想整理一些较为零散的笔记。这些笔记没有特定顺序，目标读者是正在构建产品的行业从业者。

你可以在 Youtube 上观看基于这些笔记的演讲录像，或者查看幻灯片。

重构你的心智模型

行业中仍有许多人在构建关于 LLM 的心智模型，这导致了对 LLM 能做什么以及该如何使用它们产生许多推理错误。我看到许多人对 LLM 持有的两种无益的心智模型是：

LLM 是魔法：人类能做的任何事，LLM 可能都能做得差不多好，而且速度快得多。LLM 和强化学习是一回事：当前出现的幻觉和准确性问题是由数据集太小造成的。准确性问题将通过更大的训练集得到解决，我们可以依靠置信度分数来降低不准确性的影响。

这两种观点在不同但重要的方面都是错误的。为了避免陷入这些心智模型的谬误，我建议采用以下几点作为构建有用 LLM 心智模型的支柱：

LLM 可以针对任何提示预测合理的响应——无论你写下什么文本提示，LLM 都会自信地给出回应，并且越来越能针对文本加上图像或视频等其他媒体形式给出回应。你无法知道某个具体响应是否准确——LLM 会生成出乎意料的结果，即所谓的幻觉（hallucinations），你无法确切知道它什么时候出错。它不会生成置信度分数来帮助你判断某个 LLM 回答的具体可靠性。你可以通过评估（evals）来估算某个模型在给定一组提示下的准确性——你可以使用 evals，即让 LLM 针对一组已知的提示运行，记录响应并评估这些响应，从而判断 LLM 在特定场景下表现良好的可能性。通常使用更大的模型可以提高准确性，但成本更高，延迟也更高——例如，GPT-4 比 GPT-3.5 模型更大，通常能提供更高质量的响应。然而，它明显更昂贵（约贵 20 倍），也明显更慢（慢 2-5 倍）。不过，在每个价格点上，质量、成本和延迟都在不断改善。你应该预期在未来五年内，在给定成本、延迟或质量水平下的逐年性能会有显著提升（例如，你可以预期在 12-24 个月内，以 GPT-3.5 的价格和延迟获得 GPT-4 的质量）。模型的准确性通常会随着其构建语料库的规模增长而提高——强化学习的准确性往往随着数据集增长而可预测地提升。这对 LLM 大体上也成立，但可预测性较差。小模型通常表现不如大模型。大模型搭配更高质量的数据通常优于小模型。用特定数据来补充大型通用模型被称为“微调”（fine-tuning），目前尚不清楚在什么时候微调一个小模型会优于使用更大的模型。你真正能做的就是针对你的具体用例，基于可用的模型和微调数据集运行 evals。即使最快的 LLM 也没那么快——即使是一个快速的 LLM，也可能需要 10 多秒才能给出一个合理长度的响应。如果你需要多次迭代来优化初始响应，或者使用更大的模型，整个过程可能需要一两分钟。这些速度会越来越快，但目前还不够快。即使最昂贵的 LLM 用于 B2B 场景也没那么贵。即使最便宜的 LLM 用于消费者场景也没那么便宜——因为定价由使用量驱动，这种技术对拥有较少付费用户的 B2B 业务来说非常容易论证其合理性。相反，在消费者业务中，要想为大量 LLM 用量买单而又不大幅压缩利润，是非常具有挑战性的。

这些观点并不完美，但希望它们能为思考什么能或不能在产品中应用 LLM 提供一个良好的基础。有了这个基础，现在是时候深入探讨一些更具体的子主题了。

重新设计工作流

大多数现代软件中的工作流并不是为了最大化从 LLM 中获益而设计的。这并不奇怪——它们是在 LLM 普及之前构建的——但这确实需要我们对工作流设计进行一些重新思考。

为了说明这一点，我们来想想一个抵押贷款提供商的软件：

用户创建账户产品要求用户填写大量数据，以了解用户想要什么样的抵押贷款以及其资格产品要求用户提供文件来支持刚才提供的数据，例如最近的工资单、银行账户余额等内部团队验证用户的数据是否与其提供的文件一致

在这个工作流中，LLM 仍然能为企业提供显著价值，因为你可以提高验证文件与用户提供的信息是否匹配的效率，但用户自己除了申请验证可能更快之外，不会感受到太多好处。

然而，你可以调整工作流，使其更有价值：

用户创建账户产品要求用户提供文件产品使用 LLM 从文件中提取数值用户验证提取的数据是否正确，并进行一些调整内部团队审查用户的调整，以及规则引擎提出的任何高风险问题

这两个产品的技术复杂度在功能上是等价的，但用户体验却截然不同。内部团队的体验也得到了改善。我相信，许多现有产品只有通过重新思考其工作流，才能显著提升 LLM 带来的用户体验收益。

检索增强生成（RAG）

模型有一个最大的“token 窗口”，即在单个提示中会考虑的文本长度。token 窗口的最大尺寸正在迅速扩大，但更大的 token 窗口评估起来更慢，成本也更高，因此即使不断扩大的 token 窗口也无法完全解决问题。

在固定 token 窗口内处理大型数据集的一种解决方案是检索增强生成（Retrieval Augmented Generation，简称 RAG）。举一个具体的例子，你可能想创建一个约会应用，根据用户对以下问题的自由形式回答来匹配个人：“你与书籍、电视节目、电影和音乐的关系如何，它随着时间如何变化？”没有任何 token 窗口大到能把约会应用数据库中每个用户的回答都塞进 LLM 的提示里，但你可以先通过位置筛选出二十个可能匹配的用户，然后把这二十个用户的自由形式回答包含进来，并在它们之间进行匹配。

这很有道理，先用一个不太复杂的算法找出可能的响应组成部分，再用 LLM 对这些可能的响应进行筛选和打包，生成最终响应，这种两阶段组合的方法效果相当不错。

我看到人们陷入麻烦的地方是试图将 RAG 视为搜索问题的解决方案，而不是认识到 RAG 的实现本身就需要有效的搜索。一个有效的 RAG 方法依赖于高质量的检索和过滤机制，才能在非 trivial 的规模上良好工作。例如，从 RAG 的高层视角来看，有些人可能认为他们可以用 RAG 取代自己的搜索技术（例如 Elasticsearch），但这只有在你的数据集非常小，并且你能容忍高得多的响应延迟时才成立。

在我看来，挑战在于，大多数偷工减料的解决方案在小数据集上看起来是有效的，同时让你假装搜索相关性这类问题不重要，而实际上，当你从原型阶段走向生产环境时，相关性会显著影响响应质量（无论是字面意义上的搜索相关性，还是经过更好调优的 SQL 查询以检索更合适的行）。这会造成对原型如何转化为生产能力的错误预期，并带来所有可预见的后果：低估时间线、生产行为/性能不佳等。

创新速度

模型性能——本质上是以给定预算（无论是美元还是毫秒）所能获得的响应质量——将会继续提升，但如果在创建或处理 LLM 方面没有重大技术突破，这种提升速度就不会像现在这样持续。我预计这些突破会发生，但在最初几年之后发生的频率会降低，并逐渐放缓。我们很难判断目前处于这个周期的哪个阶段，因为仍然有大量资本流入这个领域。

除了技术突破，推动创新的另一个方面是构建越来越大的模型。目前模型规模的限制因素是 Nvidia GPU 的可用性、可用于训练且在法律上可接受的更大数据集、训练新模型的资本，还是财务模型显示训练更大模型的折现未来现金流无法满足合理的回本周期，目前尚不清楚。我的假设是，这些因素都曾经或将在未来成为 LLM 创新的限制约束，不同的竞争者将根据哪个约束最关键而最适合取得进展。（这里有很多有趣但边缘的场景值得思考，例如，想象这样一种情况：美国政府为了在 LLM 训练竞赛中不输给不尊重美国版权法的国家，而废除版权法以允许在更大数据集上训练。）

可以安全地假设模型性能会继续改善。在未来几年内性能会显著提升是很可能的。我认为我们不太可能看到类似于摩尔定律的情景，即 LLM 会在几十年内持续大幅改进，但很多事情都可能轻易证明我错了。例如，核聚变在某个时刻会成为主流，并从根本上改变我们对能源利用的看法，以真正重塑世界结构，而 LLM 训练成本可能是其中的一部分。

人机协同（Human-in-the-Loop，HITL）

因为你不能依赖 LLM 提供正确的响应，也无法为任何给定响应生成置信度分数，所以你要么必须接受潜在的不准确性（这在很多情况下是合理的，人类有时也会出错），要么就需要保持人机协同（Human-in-the-Loop，HITL）来验证响应。

正如在工作流部分讨论的那样，许多公司已经有人在从事验证工作，他们现在可以转向监督 LLM 的响应，而不是自己生成响应。在其他场景中，可以调整产品的工作流，转而依靠外部用户来充当 HITL。我认为大多数产品会同时依赖这两种技术，并辅以启发式规则来判断何时需要内部审查。

幻觉与法律责任

如前所述，LLM 经常会自信地生成错误的响应。HITL 是防止根据这些自信但错误的响应采取行动的设计原则。这是因为它将责任（特别是法律责任）从 LLM 本身转移到了具体的人身上。例如，如果你使用 GitHub Copilot 生成的代码导致了安全漏洞，那么你要为该安全漏洞负责，而不是 GitHub Copilot。今天所有大规模采用 LLM 的方式，都是在将响应的责任转移给参与的人类这一模式下进行的。

许多早期创业者梦想着一个非常不同的循环，在其中可以不依赖 HITL 而直接依靠 LLM，但我认为这只会在可以转移法律责任（例如 GitHub Copilot 的例子）或者原本就不存在法律责任（例如根据用户头像生成一首有趣的诗）的场景中成立。

“从零到一”与“从一到 N”

人们强烈渴望一个 LLM 可以取代软件工程师，或者软件工程师从编写软件转向监督角色的世界。例如，一位创业者想构建一个 Reddit 的复制品，并使用 LLM 来实现它。有足够证据表明，今天已经有可能在几周内，用 LLM 和一些调试技能，将一个新的产品想法从零做到一。

然而，大多数创业者缺乏对运营和演化拥有大量真实用户的软件的深刻直觉。一些例子包括：

在更改 UI 后保持用户参与需要主动、刻意的工作确保用户数据安全并满足各种隐私合规义务提供满足 SOC2 的控制措施并提供可审计的证据证明这些控制得到维持迁移包含客户数据的数据库 schema 以支持一组新的列将查询模式逐步收紧到一组在更高规模下能高效执行的允许模式

所有这些都是扩展产品（即“从一到 N”）的直观、基本组成部分，而 LLM 根本无法有效完成这些工作。对于是否能看到特别可靠的、基于 LLM 的、对熟练人类智能的替代方案，我持怀疑态度。不过，看着人们如何努力推动 LLM 自动化能力的边界，以延迟需要聘请专业人才的项目到来，将会很有趣。

版权法

版权的影响目前非常不清晰，并且在可预见的未来仍将如此。今天所有使用 LLM 完成的工作都必须考虑到法律结果的分歧。我最好的猜测是，我们将看到一个关于 LLM 生成的内容是否可被版权保护的法律碎片化时代，而从更长期来看，LLM 将被视为与其他任何基本技术组件一样，例如运行拼写检查器不会撤销你对经过拼写检查的文档的版权。你可以提出各种合理论据，说明这种观点对那些被用于训练的数据的版权持有人不公平，但长期来看，我认为其他任何解释都行不通。

数据处理协议

今天与 LLM 打交道的一个小但有趣的现实是，许多客户对 LLM 提供商（OpenAI、Anthropic 等）保持敏感，因为这些提供商是相对较新的公司，正在构建相对较新的东西，缺乏法律先例来降低风险。这意味着将它们添加到你的数据处理协议（Data Processing Agreement，DPA）中可能会产生一些摩擦。绕过这种摩擦最明显的方式是使用通过你现有的云厂商（AWS、Azure、GCP 等）提供的 LLM 功能。

提供商可用性

我曾经认为这非常重要，但现在我的感觉是，LLM 托管已经基本等同于其他云服务（例如，你可以通过 AWS 使用 Anthropic，或通过 Azure 使用 OpenAI），很少有公司会因为花太多时间担心 LLM 可用性而获益。我确实认为，通过云提供商——那些非常擅长可扩展性的公司——获得对 LLM 的直接访问，同样很可能是这里的最佳选择。

外面有很多人花了比我更多的时间深入思考 LLM——例如，去读读 Simon Willison 的文章——但希望这里的笔记对你有用。如果有人对其中任何观点有不同意见，我很乐意讨论。
