修复 LifeFlow 的痼疾

2008-12-03 · 阅读原文

如果你连门都不会开，那要怎么进入一栋建筑呢？最多你可能会砸破一扇窗户进去。之后你或许会学会那个棘手的开门技巧，但那扇窗户已经碎了。这正是中级开发者在项目中必然会遇到的情况：他们缺乏足够的知识和经验从一开始就把设计做好，因此只能在设计演进过程中不断犯错、再不断修正。

LifeFlow 是我仍在使用的最老的 Django 应用。任何和我聊过或看过这个仓库的人都知道，它已经膨胀成了一头有点难缠的怪兽。让我们快速盘点一下 LifeFlow 所拥有的各种功能、它的一些设计决策，以及将 LifeFlow 从“破碎”改造为“优雅”的路线图。

设计决策（破碎的窗户与门）

首先要承认的是，LifeFlow 确实存在一些糟糕的设计决策。正如我开篇用的那个比喻，这里确实有几扇破窗户。

一键部署。当我开始做 LF 时，我刻意对“应用（app）与项目（project）”的区分持乐观态度，因为我想让 LF 能做到一键部署。不幸的是，在 Django 上部署对 WordPress 用户群来说仍然过于复杂（我最初的目标用户是那些对 WordPress 略懂编程的人——其实就是我自己）。这既是个错误，也是一次失败。 到处都是灵活性。LifeFlow 提供了多到离谱的灵活性，但其中有很大一部分是误入歧途的灵活性——它们用任意的实现覆盖了最佳实践。 灵活性永远是 LF 的核心，但现有的一些机制需要大幅缩减。 到达同一篇文章有多种路径。不同的人有不同的需求，尤其是跨文化时，组织和定位内容的方式本就多种多样。 LifeFlow 希望提供广泛的标签和组织方式。

说到底，我认为“一键部署”这个想法是 LifeFlow 所有重大缺陷的根源。只要放弃这个想法，应该就有可能挽救出一些真正好的东西。

功能特性（有价值的与误入歧途的）

在开始之前，先说明几个缩写：

YAGNI：You Aren't Gonna Need It（你不会需要它）。用于那些看似贴心/有用、实际只是臃肿的功能。 AOBP：Arbitrary Over Best Practice（任意方案凌驾于最佳实践）。用于那些用没有明显优势的任意方案取代最佳实践的地方。

好了，下面是功能清单以及它们是否会被砍掉：

支持皮肤（skins），让用户能方便地注入自己的自定义 CSS 和 JS。 将被移除。（AOBP） 支持 mods，可为 LifeFlow 添加任意功能。示例 mod 用于设置 StaticGenerator。 将被移除。（YAGNI） 文本过滤器（Text filters），允许所有评论和文章被传递给任意过滤器进行修改。 此功能被用于渲染评论和文章，同时提供了极大的灵活性。你可以轻松实现评论脏话过滤器、把文章中第一次出现的 “Django” 变成链接，或者几乎做任何事情。 LifeFlow Editor（LFE），一个完全用 Ajax 实现的 LifeFlow 管理界面（类似 Django admin，但采用以博客为中心的工作流）。 LFE 中集成了大量功能：文章渲染预览、“草稿”概念（区分已发布和未发布的文章）等等。 简单的文件内容管理系统。 若干自定义 Markdown 增强功能，包括动态博客上下文、自定义语法高亮机制，以及允许在 Markdown 中注入 ReStructured Text、Textile 和原始标记的语法。 这些功能对我来说价值巨大，尤其是动态博客上下文，它包含了很多巧妙的设计（最有用的是，一旦你上传了文件或图片，它就能自动允许在不同文章中引用它们）。 将“博客”拆分为多个 flows，flows 是内容的元标签。其理念是在一个 LF 部署中托管多个主题各异、内容独立的博客，同时允许内容完全交叉融合（共享标签、共享归档、在首页相互混排等）。 Projects（项目），即非基于日期的数据。 这是我非常想要的功能，但我同样非常不喜欢自己当前的实现。 自实现的带反向验证码反垃圾评论的 threaded 评论系统。（我的评论完全开放，却几乎没有收到垃圾评论。我不会说自己的实现优于其他人，只是它足够不同，而且 LF 用户基数小到垃圾评论者还没研究透。） Article series 作为一等公民，提供了非常实用的组织方式。我认为这是一个非常有帮助的功能，比起以前在 WordPress 里的做法，它为我节省了大量时间。 基于通用日期视图的条目归档视图。 标签云。 集成在应用内的站点地图。 十种不同类型的 RSS feed（全部、作者、flow、标签、系列、翻译、项目、评论、某文章的评论、按语言）。 多作者支持，每篇文章可以关联 0 个或多个作者。 可在文章发布时通知任意列表中的站点。 BlogRoll，用于链接到其他作者。

变更计划（停止、创新与修复）

结合 LF 的目标与现实情况，以下是我计划进行的改动：

重置“向后兼容”保证。 将 LifeFlow 拆分为多个独立应用。 LifeFlow-Core 将包含核心可复用代码，其他所有 LifeFlow 应用都将依赖于 LF-Core。 LifeFlow-Blog 将包含博客专属代码。 LifeFlow-Projects 将接管项目的展示职责。 LifeFlow-API 将提供一个 RESTful API，用于管理 LifeFlow 的内容。 LifeFlow-Editor 将是一个完整的 Django Admin 替代品，专为 LifeFlow 打造。（基于 LF-API 实现。） 按照 Django 项目的最佳目录实践重新组织仓库结构。 编写更多测试、更好的测试。 大幅改进归档功能，这需要放弃现有的基于日期的通用视图，转而实现定制版本。 更好的翻译集成与支持。（我不希望翻译内容直接出现在主 feed 或浏览页面中，但我仍想保留翻译功能。） 重构若干模型： 将 SiteToNotify 的概念移到 settings.py 配置中，而不是作为模型存在。 将 Draft 和 Translation 模型合并到 Entry 模型中。

我马上就要在新的分支里开始这项工作了。让我们看看它会把我们带向何方。
