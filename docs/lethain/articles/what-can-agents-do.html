智能体究竟能做什么？

2025-07-06 · 阅读原文

关于AI（特别是最新一波以LLM为核心的AI）能做什么，以及AI优先的公司与前几代公司有何不同，人们充满兴奋之情。确实存在许多重要且真实的机会，但我发现很多这类讨论都发生在过于抽象的高度，以至于接近毫无意义。这就像说只要你多采用一些软件，公司就会好得多。这当然没错，但它并不是一个特别有帮助的论断。

这篇文章试图简洁地总结AI智能体的工作原理，将这个总结应用到一些真实世界的AI用例中，并大致说明智能体是你软件和系统设计质量的倍增器。如果你的软件或系统设计得很糟糕，智能体只会造成伤害。如果要给“AI优先公司”一个有意义的定义，那一定是那些对其软件和系统设计倾注了完美无缺注意力的公司。

在读完这篇文章后，我希望你能充分准备好进行一场具体的讨论——关于LLM和智能体如何改变你公司的形态，并避免陷入当今普遍存在的那些不必要的抽象讨论。

智能体是如何工作的？

从本质上讲，使用LLM就是一次包含提示（prompt）的API调用。例如，你可能会调用Anthropic的/v1/message接口，并提供这样一个提示：我应该如何在公司中采用LLM？这个提示会被用来填充LLM的上下文窗口，从而引导模型生成特定类型的响应。

这是智能体能做的第一件重要事情：使用LLM来评估一个上下文窗口并获得结果。

提示工程（prompt engineering），或者现在被称为上下文工程（context engineering），就是决定在上下文窗口中放入什么内容，以最好地生成你想要的响应。例如，上下文内学习（In-Context Learning，ICL）就是一种上下文工程的形式，你在提问前提供大量相似的示例。如果我想判断一笔交易是否欺诈，我可能会提供大量之前的交易及其是否欺诈的例子作为ICL示例。这些示例会让生成正确答案的可能性更高。

然而，构建完美的上下文窗口非常耗时，并且受益于元提示（metaprompting）等技术来改进你的上下文。事实上，创建初始上下文的人（或自动化程序）可能并不具备足够的知识来提供相关的上下文。例如，如果你提问“谁将成为纽约市下一任市长？”，那么你自己并不适合在提示中包含这个问题的答案。因为要做到这一点，你必须已经知道答案，而那正是你一开始提问的原因！

这就是为什么我们看到OpenAI和Anthropic的模型聊天体验会使用网络搜索来拉取你可能不具备的上下文。如果你询问关于纽约新市长的问题，它们会使用工具检索网络搜索结果，然后将这些搜索内容添加到你的上下文窗口中。

这是智能体能做的第二件重要事情：使用LLM来建议与上下文窗口相关的工具，然后用工具的响应来丰富上下文窗口。

然而，有必要澄清“工具使用”实际上是如何工作的。LLM本身并不真正调用工具。（如果你想看一个具体的真实世界例子，可以浏览OpenAI的函数调用文档。）实际上，调用工具是一个五步过程，这个过程可能有点反直觉：

 [{
     "type": "function_call",
      "name": "get_weather",
      "arguments": "{\"location\":\"Paris, France\"}"
 }]
  1. The program designer that calls the LLM API must also define a set of tools that the LLM is allowed to suggest using.
  2. Every API call to the LLM includes that defined set of tools as options that the LLM is allowed to recommend
  3. The response from the API call with defined functions is either:Generated text as any other call to an LLM might provideA recommendation to call a specific tool with a specific set of parameters, e.g. an LLM that knows about a get_weather tool, when prompted about the weather in Paris, might return this response:
  4. The program that calls the LLM API then decides whether and how to honor that requested tool use. The program might decide to reject the requested tool because it’s been used too frequently recently (e.g. rate limiting), it might check if the associated user has permission to use the tool (e.g. maybe it’s a premium only tool), it might check if the parameters match the user’s role-based permissions as well (e.g. the user can check weather, but only admin users are allowed to check weather in France).
  5. If the program does decide to call the tool, it invokes the tool, then calls the LLM API with the output of the tool appended to the prior call’s context window.

这个循环的重要之处在于，LLM本身仍然只能做一件有趣的事情：接收一个上下文窗口并返回生成的文本。而是更广泛的程序——此时我们可以开始称之为智能体——负责调用工具，并将工具的输出发送给LLM以生成更多上下文。

奇妙之处在于，LLM加上工具开始真正改善你生成上下文窗口的方式。你不再需要有一个定义非常明确的初始上下文窗口，而是可以使用工具来注入相关上下文，从而改进初始上下文。

这就引出了智能体能做的第三件重要事情：它们管理工具使用的流程控制。让我们思考三种不同的场景：

  1. Flow control via rules has concrete rules about how tools can be used. Some examples:it might only allow a given tool to be used once in a given workflow (or a usage limit of a tool for each user, etc)it might require that a human-in-the-loop approves parameters over a certain value (e.g. refunds more than $100 require human approval)it might run a generated Python program and return the output to analyze a dataset (or provide error messages if it fails)apply a permission system to tool use, restricting who can use which tools and which parameters a given user is able to use (e.g. you can only retrieve your own personal data)a tool to escalate to a human representative can only be called after five back and forths with the LLM agent
  2. Flow control via statistics can use statistics to identify and act on abnormal behavior:if the size of a refund is higher than 99% of other refunds for the order size, you might want to escalate to a humanif a user has used a tool more than 99% of other users, then you might want to reject usage for the rest of the dayit might escalate to a human representative if tool parameters are more similar to prior parameters that required escalation to a human agent

LLM本身绝对不能被信任。任何时候你依赖LLM来强制执行重要的事情，你都会失败。使用智能体来管理流程控制是能够用LLM构建安全、可靠系统的机制。每当你发现自己面对一个不可靠的基于LLM的系统时，你总是可以找到一种方法，将复杂性转移到工具上以避免这个问题。例如，如果你想用LLM做代数，解决方案不是让LLM直接进行代数运算，而是提供一个能够进行代数运算的工具给LLM，然后依赖LLM用正确的参数调用该工具。

到了这一步，还有一件智能体做的最终重要事情：它们是软件程序。这意味着它们可以做任何软件能做的事情，来构建更好的上下文窗口传递给LLM进行生成。这是一个无限的类别，但通常包括：

  1. Building general context to add to context window, sometimes thought of as maintaining memory
  2. Initiating a workflow based on an incoming ticket in a ticket tracker, customer support system, etc
  3. Periodically initiating workflows at a certain time, such as hourly review of incoming tickets

好了，我们现在已经将AI智能体能做的事情总结为四个一般能力。稍微回顾一下，这些能力是：

  1. Use an LLM to evaluate a context window and get a result
  2. Use an LLM to suggest tools relevant to the context window, then enrich the context window with the tool’s response
  3. Manage flow control for tool usage via rules or statistical analysis
  4. Agents are software programs, and can do anything other software programs do

有了这四个能力，我们就能思考如何以及在哪些方面可以将AI智能体应用到各种机会上，以及在哪些方面不能。

用例1：客户支持智能体

人们经常谈论部署AI智能体的首批场景之一就是客户支持，所以我们从这里开始。一个典型的客户支持流程会有多层级的智能体，处理日益复杂的客户问题。因此，让我们设定一个目标：先接管最简单的层级，随着我们展示出效果，再逐步向上移动层级。

我们的方法可能是：

  1. Allow tickets (or support chats) to flow into an AI agent
  2. Provide a variety of tools to the agent to support:Retrieving information about the user: recent customer support tickets, account history, account state, and so onEscalating to next tier of customer supportRefund a purchase (almost certainly implemented as “refund purchase” referencing a specific purchase by the user, rather than “refund amount” to prevent scenarios where the agent can be fooled into refunding too much)Closing the user account on request
  3. Include customer support guidelines in the context window, describe customer problems, map those problems to specific tools that should be used to solve the problems
  4. Flow control rules that ensure all calls escalate to a human if not resolved within a certain time period, number of back-and-forth exchanges, if they run into an error in the agent, and so on. These rules should be both rules-based and statistics-based, ensuring that gaps in your rules are neither exploitable nor create a terrible customer experience
  5. Review agent-customer interactions for quality control, making improvements to the support guidelines provided to AI agents. Initially you would want to review every interaction, then move to interactions that lead to unusual outcomes (e.g. escalations to human) and some degree of random sampling
  6. Review hourly, then daily, and then weekly metrics of agent performance
  7. Based on your learnings from the metric reviews, you should set baselines for alerts which require more immediate response. For example, if a new topic comes up frequently, it probably means a serious regression in your product or process, and it requires immediate review rather than periodical review.

请注意，即使你已经将“客户支持交给AI智能体”，你仍然有：

  • a tier of human agents dealing with the most complex calls
  • humans reviewing the periodic performance statistics
  • humans performing quality control on AI agent-customer interactions

你绝对可以用它自己的AI智能体替换每一个下游步骤（审查性能统计等），但这样做需要为每个这样的流程开发一个AI产品。这里有一个递归过程，随着时间推移，你可以消除业务中许多人类组件，以换取随着复杂性层级增加而带来的更大脆弱性。复杂系统最有趣的部分不是它们如何工作，而是它们如何失败，而智能体驱动的系统偶尔也会失败，就像所有系统一样，包括人类驱动的系统。

谨慎应用，上述一系列行动会成功运作。然而，重要的是要认识到，这是在构建一个完整的软件管道，然后学习如何在生产环境中运行这个软件管道。这两件事都是非常可行的，但它们是有意义的工作，它将客户支持领导者转变为产品经理，并需要一个工程团队来构建和运营客户支持智能体。

用例2：对传入的错误报告进行分诊

当公司内部提出一个事件，或者你收到一个错误报告时，当天的第一个问题就是确定这个问题可能有多严重。如果它可能相当严重，那么你希望值班工程师立即进行调查；如果肯定不严重，那么你希望以某种不那么紧急的流程对其进行分诊。思考AI智能体如何支持这个分诊工作流是很有趣的。

这个过程可能按如下方式工作：

  1. Pipe all created incidents and all created tickets to this agent for review.
  2. Expose these tools to the agent:Open an incidentRetrieve current incidentsRetrieve recently created ticketsRetrieve production metricsRetrieve deployment logsRetrieve feature flag change logsToggle known-safe feature flagsPropose merging an incident with another for human approvalPropose merging a ticket with another ticket for human approval
  3. Redundant LLM providers for critical workflows. If the LLM provider’s API is unavailable, retry three times over ten seconds, then resort to using a second model provider (e.g. Anthropic first, if unavailable try OpenAI), and then finally create an incident that the triaging mechanism is unavailable. For critical workflows, we can’t simply assume the APIs will be available, because in practice all major providers seem to have monthly availability issues.
  4. Merge duplicates. When a ticket comes in, first check ongoing incidents and recently created tickets for potential duplicates. If there is a probable duplicate, suggest merging the ticket or incident with the existing issue and exit the workflow.
  5. Assess impact. If production statistics are severely impacted, or if there is a new kind of error in production, then this is likely an issue that merits quick human review. If it’s high priority, open an incident. If it’s low priority, create a ticket.
  6. Propose cause. Now that the incident has been sized, switch to analyzing the potential causes of the incident. Look at the code commits in recent deploys and suggest potential issues that might have caused the current error. In some cases this will be obvious (e.g. spiking errors with a traceback of a line of code that changed recently), and in other cases it will only be proximity in time.
  7. Apply known-safe feature flags. Establish an allow list of known safe feature flags that the system is allowed to activate itself. For example, if there are expensive features that are safe to disable, it could be allowed to disable them, e.g. restricting paginating through deeper search results when under load might be a reasonable tradeoff between stability and user experience.
  8. Defer to humans. At this point, rely on humans to drive incident, or ticket, remediation to completion.
  9. Draft initial incident report. If an incident was opened, the agent should draft an initial incident report including the timeline, related changes, and the human activities taken over the course of the incident. This report should then be finalized by the human involved in the incident.
  10. Run incident review. Your existing incident review process should take the incident review and determine how to modify your systems, including the triaging agent, to increase reliability over time.
  11. Safeguard to reenable feature flags. Since we now have an agent disabling feature flags, we also need to add a periodic check (agent-driven or otherwise) to reenable the “known safe” feature flags if there isn’t an ongoing incident to avoid accidentally disabling them for long periods of time.

这是另一个只要你将其视为软件产品就绝对能正常工作的AI智能体。在这种情况下，工程团队可能是产品所有者，但它仍然需要经过深思熟虑的迭代来随着时间推移改进其行为。要让这个流程工作，一些持续的验证包括：

  1. The role of humans in incident response and review will remain significant, merely aided by this agent. This is especially true in the review process, where an agent cannot solve the review process because it’s about actively learning what to change based on the incident.You can make a reasonable argument that an agent could decide what to change and then hand that specification off to another agent to implement it. Even today, you can easily imagine low risk changes (e.g. a copy change) being automatically added to a ticket for human approval.Doing this for more complex, or riskier changes, is possible but requires an extraordinary degree of care and nuance: it is the polar opposite of the idea of “just add agents and things get easy.” Instead, enabling that sort of automation will require immense care in constraining changes to systems that cannot expose unsafe behavior. For example, one startup I know has represented their domain logic in a domain-specific language (DSL) that can be safely generated by an LLM, and are able to represent many customer-specific features solely through that DSL.
  2. Expanding the list of known-safe feature flags to make incidents remediable. To do this widely will require enforcing very specific requirements for how software is developed. Even doing this narrowly will require changes to ensure the known-safe feature flags remain safe as software is developed.
  3. Periodically reviewing incident statistics over time to ensure mean-time-to-resolution (MTTR) is decreasing. If the agent is truly working, this should decrease. If the agent isn’t driving a reduction in MTTR, then something is rotten in the details of the implementation.

即使是非常有效的智能体，也不能减轻精心设计系统的责任。相反，智能体是你系统设计质量的倍增器：做得好，智能体可以让你显著更有效率。做得差，它们只会将你的问题放大得更广泛。

AI智能体是否代表了这一代AI的全部？

如果你接受我对AI智能体的定义——即LLM与软件的任何组合，那么我认为这一代AI能表达的东西几乎没有不适合这个定义的。我很愿意接受LLM这个术语太窄的论点，或许基础模型（foundational model）会是一个更好的术语。我的感觉是，这是一个前沿定义与日常用法已经有些偏离的地方。

结束语

LLM和智能体是强大的机制。我认为它们将真正改变产品被设计的方式以及产品的工作方式。整整一代软件制作者和公司高管，都正在学习这些工具如何运作。

对于AI智能体能做的每件事，都有同样重要的它们不能做的事情。它们不能让数据库恢复速度超过网络带宽所支持的水平。对基于文本的判断的访问确实会创造缺失的工具。但基于文本的判断也不能解决访问控制问题，无法立即让缺失的文档存在，或者解决你业务中今天存在的许多真实系统问题。只有智能体、伟大的系统设计和伟大的软件设计的结合，才能让智能体真正发挥光彩。

一如既往，软件不是魔法。软件是非常符合逻辑的。然而，如果我们有效使用它，软件所能完成的事情却是神奇的。
