你只会学到第一次

2008-11-06 · 阅读原文

你第一次接触函数式编程是什么时候？ 对我来说，那是在大学大三或大四的时候，一次相当令人困惑的入门经历。当你开始采用一种新的问题解决方法——或者学习一门新的编程语言——通常会把新概念一个个分离出来，逐个玩转它们。开始接触函数式编程之所以困难，是因为你几乎总是要同时学习一门新语言（Haskell、Scheme、Erlang）和一套新的编程技巧。

过去两周里，我在工作中用到的语言有 Java、Python、JavaScript、PHP、Objective-C 和 Perl。这里的重点并不是说我掌握了很多语言（事实上并非如此，其中一半的语言如果不打开好几份参考资料我根本用不了），而是尽管我对它们的语法和标准库只有一知半解，我依然能在这些语言中保持生产力。

如果你理解了自己正在处理的根本问题，那么在上面叠加一套新语法并不会特别困难。反之，当你并不理解底层问题（因为你把主动权让给了某个友好的库，它把细节全部抽象掉了，或者因为你选择的语言有意把你与这些概念隔离开来，比如 ORM 让你绕过学习 SQL，又或者 Erlang 把信号量严格放在“你根本不用操心”的角落），那你就会被锁定在特定的语言或平台里。

现在你可能在等着我把这个精彩的观察再补充一句让人安心的金句，比如“要成为伟大的程序员，就要学习很多编程语言！”但这也不是正确答案。把注意力放在学习语言上的问题在于，它鼓励你一遍又一遍地用略有不同的形式重复学习同样的内容。当然，能够把

人们很容易陷入语言学习的循环，原因和大家一看到新语言就急着用它重写 Web 服务器一样：这些都是有趣、好玩、具有一定挑战性的问题，能让我们获得“做了新东西”的快感，同时又不用面对真正困难的问题带来的挫败感。我们沉醉于那种全新的感觉，即使实际上只是在原地倒退。

与其陷入语言学习循环或库翻译循环，我们需要走第三条路——正中间的那条：你想用什么语言就用什么语言，但要深入了解其内部实现，真正吃透你所依赖的库和语言特性。正是通过理解这些底层概念，我们才能成为更好的程序员，而不是成为更好的 Java 程序员、.NET 程序员或 Pythonista。

我认为一个很好的例子，就是把 Scheme 和 Haskell 中的函数式编程风格反向移植到 Python、Ruby 这样的多范式语言，甚至（以一些相当笨拙的方式）移植到 Java 和 C 这样的命令式语言。程序员们没有把 Haskell 或 Erlang 当成解决编程问题的唯一答案，而是把其中蕴含的优秀思想提取出来，并开始在其他编程语言中加以应用。

对于“退回基础”这个想法，应该如何反应其实有些模糊。我一方面说人们不应该反复重复实现同样的代码，另一方面又说我们应该回归基础，从最底层开始，一步步向上走到顶端。我们该如何调和这两个看似矛盾的观点呢？

我认为我们应该同时维护两类不同性质的项目，对每一类采用不同的方法：

一类是小型个人项目，通过重新创造和重新实现编程与计算机科学的核心思想来帮助我们学习。这类项目里，你应该去写自己的服务器、写自己的编译器、实现 A* 算法、写一个图形库。把这些项目当作素描来看待，因为它们本来就是素描。不必过于追求完美，享受实验和玩耍这些想法的过程就好。 另一类是参与那些激动人心、没有重复造轮子、专注于创造新事物或以新方法解决现有领域问题的项目。“没有重复造轮子”很难严格定义，但我认为一个合适的判断标准是：它是否解决了尚未被满足的需求。我完全同意我们有 Nginx、Apache 和 Mongrel 是更好的，但 Nginx 和 Lighttpd 是否在满足不同需求就没那么清晰了。现在我们已经有了这么多选择，我们真的还需要更多强调简洁性的 C 语言服务器吗？也许需要——我不想鼓吹停滞不前——但我觉得在投入多年开发者时间去做出 Lightginx 0.1 之前，应该先给出一个清晰的理由，说明它到底满足了什么尚未被满足的需求。

我对程序员有一个相当浪漫的想象：我们作为专业人士，有义务不断提高自己的水平，也有义务去构建值得构建的东西。我认为，维持一批健康的小型概念性项目和一批更大的、能解决未解之题的复杂项目，正是同时履行这两种义务的方式。

对我个人而言，这意味着我应该更好地去为现有项目做贡献，而减少从零开始写东西。这是一颗有点苦的药丸，但我认为把它吞下去，对我们所有人都是最好的。
