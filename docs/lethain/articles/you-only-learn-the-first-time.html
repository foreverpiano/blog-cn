你只学一次

2008-11-06 · 阅读原文

你第一次接触函数式编程是什么时候？对我来说，那是在大学大三或大四的时候，一次相当令人困惑的入门经历。当你接触一种新的问题解决方法——或者学习一门新的编程语言——时，通常会把新概念一个个分离出来，逐个玩转它们。而函数式编程的入门之所以困难，是因为你几乎总是要同时学习一门新语言（Haskell、Scheme、Erlang）和一套新的编程技巧。

过去两周里，我用 Java、Python、JavaScript、PHP、Objective-C 和 Perl 编写了和工作相关代码。这里的重点并不是说我精通很多语言（事实并非如此，其中一半的语言我不用查一大堆参考资料根本写不下去），而是说即使我对它们的语法和标准库只有粗浅了解，仍然可以在其中保持生产力。

如果你理解自己正在处理的根本问题，那么在上面叠加一套新语法并不会特别困难。反之，当你不理解底层问题（可能是因为你把主动权让给了那个帮你抽象掉细节的“友好”库，也可能是因为你选择的语言刻意屏蔽了这个概念，比如 ORM 让你绕过学习 SQL，或者 Erlang 把信号量严格塞到你大脑“我根本不在乎”那个角落），那你就会把自己锁定在特定的语言或平台上。

现在你可能在等我把这个精彩的观察用一句安慰人的金句收尾，比如“要成为优秀程序员就得多学几门语言！”但那也不是答案。把注意力集中在学习语言上的问题在于，它鼓励你一遍又一遍地用略有不同的外衣重新学习同样的材料。当然，能够把

x = {"a":1, "b":2}
x["c"] = 10
del x["b"]
for key in x:
    val = x[key]
    print "%s => %s" % (key, value)

翻译成

my %x = ('a' => 1, 'b' => 2);
%x->{'c'} = 10;
delete $x{'b'};
for my $key (keys(%x)) {
    my $value = %x->{$key};
    print "$key => $value\n";
}

很重要，但能写出两个版本并不意味着你能区分链表和哈希表。而且当你学会把 del x["b"] 写成 delete $x{'b'}; 的时候，你也确实没有学到任何真正根本性的新东西。

人们很容易陷入语言学习的循环，原因和大家每次看到一门新拼凑出来的编程语言就急着用它重写一遍 Web 服务器一样：这些都是有趣、有挑战性、又不会太难的问题，能给我们带来“做了新东西”的快感，却不用面对真正棘手的问题带来的低谷。我们沉醉于那种新鲜感，即使实际上是在原地倒退。

与其陷入语言学习循环或库翻译回路，我们需要走一条居中的第三条路：随便用你喜欢的语言，但深入钻研其内部原理，真正理解你所依赖的那些库和语言特性。正是通过理解底层概念，我们才能作为程序员不断进步，而不是作为 Java 程序员、.NET 程序员或 Pythonista 进步。

我认为这方面一个很好的例子，就是把来自 Scheme 和 Haskell 的函数式编程风格反向移植到 Python、Ruby 这样的多范式语言，甚至（在一些相当笨拙的尝试中）移植到 Java 和 C 这样的命令式语言。程序员们没有把 Haskell 或 Erlang 本身当成解决编程问题的万能钥匙，而是把它们所体现的优秀思想提取出来，并开始在其他编程语言中加以应用。

对于“退回到基础”这个想法，该如何反应其实有点模糊。我一方面说人们不应该反复重写同样的代码，另一方面又说我们应该回归基础，从最底层开始一路向上学习。我们要如何调和这两个看似矛盾的观点呢？

我认为我们应该同时维护两类不同性质的项目，对每类项目采用不同的态度：

小型个人项目，通过重新创造和重新实现编程与计算机科学的核心思想来帮助我们学习。在这类项目中，你应该去写自己的服务器、自己的编译器、实现 A* 算法、写一个图形库。把这些项目当作素描来看待，因为它们本质上就是素描。不要太纠结于把事情做得完美，只管享受实验和玩耍的过程。同时，去参与那些令人兴奋且非重复性的项目，它们要么在创造新事物，要么在用全新的方法解决某个已有领域的问题。“非重复性”很难精确定义，但我认为一个合适的思考方式是：它是否解决了某个尚未被满足的需求。我完全同意我们有 Nginx、Apache 和 Mongrel 是件好事，但同时维护 Nginx 和 Lighttpd 是否真的满足了不同的需求，就没那么明确了。现在我们已经有了这么多选择，我们真的还需要更多强调简洁性的 C 语言服务器吗？也许需要——我不想鼓吹停滞不前——但我觉得在投入多年开发者时间去做出 Lightginx 0.1 之前，应该先有一个清晰的理由，说明它到底满足了什么尚未被满足的需求。

我对程序员有一种相当浪漫的想象：我们是专业人士，有义务让自己越做越好，也有义务去建造值得建造的东西。我认为，同时维护一批小型概念验证项目和一批更大的、能解决尚未解决的问题的复杂项目，正是履行这两项义务的最佳方式。

对我个人而言，这意味着我应该更好地去为现有项目做贡献，而少从零开始自己造轮子。这是一剂有点苦的药，但我觉得我们所有人把它吞下去才是最好的选择。
