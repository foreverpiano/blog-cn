回调是一种非正式的流水线

2010-03-07 · 阅读原文

过去八个月左右，我在工作中一直负责工作流软件的开发。最简单的工作流例子就是流水线：接收一个任务，执行它，把输出作为下一个任务的输入继续执行，然后继续传递……如此反复。昨晚我尝试重构一个 Node.js 项目不断演化出的复杂逻辑，终于意识到编写工作流和串联一长串回调之间存在非常强的相似性。

在工作中，我一直使用 [Erlang gen_fsm](gen_fsm) 来引导工作在流水线中流动（同时在每一步处理失败恢复），但在这个 Node.js 的场景中，我希望使用更轻量级的方案，因为它需要为我正在开发的 Web 应用中的每个视图至少建模一个流程。例如，下面是我尝试为「创建新项目」建模的早期流程之一（其中一些细节与使用 Redis 作为后端、redis-node-client 作为接口有关，但这本质上是一个基于回调的流水线所面临的通用问题）：

get new unique id key from a counter
create new project using unique key as part of key
add the new key to a list of projects which is stored in a second key

如果上面的流程执行成功，我们希望以「显示成功」流程结束：

get projects for user
render "project_creaed" template
send back to user

如果上面的流程在任何一步失败，我们希望以「显示失败」流程结束：

get projects for user
render "project_failed" template
send back to user

我仍在继续探索这个想法以及其他几个想法，同时尝试开发一个相对复杂的 Node.js 应用。我觉得这里面有些有价值的东西，尽管这个第一版实现还非常粗糙。

作为结束语，完全可以用一个更复杂的有限状态机来解决这个问题（比如我上面简要提到的 Erlang gen_fsm 实现），但那样做无疑会更复杂，而且通常也没有必要。尤其是合理利用 JavaScript 的异常机制，就可以在需要的时候实现类似 FSM 的复杂行为，而在简单场景中又不必承担 FSM 带来的复杂性。
