为什么 Digg 的分页实现如此困难

2012-08-25 · 阅读原文

我以前的同事 Can Duruk 最近发表了一篇很棒的文章，分享他在 Digg 工作时积累的一些 Web 开发经验。其中关于分页的评论在 Hacker News 上引发了一些困惑。人们坐在舒服的椅子上可能会想：在一家所谓的“互联网公司”工作的人，怎么会连分页都搞不定，至于这么无能吗？

首先，我们来看看 Can 的原话：

计数很难。分页更难。因此，别在分页里显示总数。逻辑完美。

从根本上说，有两种直观的方式来描述一个内容列表（这里说的列表是个抽象概念，通常对应数据库中的行）的起始位置：

  1. an integer offset which is an index in a list
  2. a unique cursor (probably a string, but maybe a timestamp or some such), which can uniquely describe an item to start at (or after), probably a primary key or identifier or some kind.

这两种方式都需要搭配一个整数 count，来表示要返回多少条数据。

偏移量方式在用户体验上有很大优势，它允许用户直接跳到列表的任意位置，而不需要强迫用户一直滚动（可能还是无休止地）才能到达某一页。同时，它的分页逻辑也极其简单：下一页永远从 offset + count 开始，上一页从 offset - count 开始。

游标方式则几乎没什么优势。它很笨拙，因为你无法跳到列表中的任意位置；而且如果你用的游标和数据的唯一标识符不是同一个东西，很容易把自己搞晕，尤其是当两者都是时间戳加 UUID 的组合时（我们可没这么干过）。（好吧，我们确实这么干过。）

你唯一能为游标方式辩护的一点是：在某些限制条件下，它是唯一可行的方案。在我们当时的情况下，大部分内容列表都存储在 Cassandra 中，其可用的数据结构是 ColumnFamily 里面装着 Row，Row 里面又装着 Column。

在标准的 Cassandra 配置中，Row 是随机分布的，以便通过哈希将数据分散到一圈节点上；而 Row 内部的 Column 则按键排序。从这个角度看，你可以把 ColumnFamily 想象成一个以字符串为键、Row 为值的无序字典，而 Row 则是一个以字符串为键、字符串为值的有序字典。（好吧，它们实际上可能都是字节数组，回头再找我算账吧。）

在用 Cassandra 存储故事列表的限制下，如果你面对的是频繁写入的场景（我们当时基本都是这种情况），你就只能使用游标而非偏移量。如果写入量很低，你可以想出各种奇葩办法来绕过这个限制。但当写入量很大时，我能想到的任何基于索引访问 Cassandra 的方案，都会撞上 tombstone（墓碑）的实现。（谁知道呢，也许现在有新的 API 已经能解决这个问题了。）

最终，我们成功摆脱了游标，统一改用基于偏移量的分页。我们把动态计算的故事列表迁移到 Redis 的 Sorted Set 中，这和 Cassandra 是绝佳的组合：Redis 适合处理动态排序的内容（用唯一标识符作为 key），排序后的结果再存回 Cassandra，通过从 Redis Sorted Set 里拿到的唯一标识符来访问。

我们唯一保留在 Cassandra 里的故事列表是 Top News，它只定期重新计算。我们为每一种筛选条件组合（内容类型、话题等）都预先生成好列表，并把整个列表作为一个巨大的 JSON blob 存进 Cassandra 的一个 Column 里。要评价这个实现，你只能说：“它能用。”

总之，这就是为什么 Digg 的分页曾经那么难。

关于分页和不一致排序的后续说明

分页另一个让人头疼的地方是，当你按动态分数对内容进行排名时，一条内容可能会从第 3 位掉到第 10 位，随后又因为突然受欢迎而冲到第 2 位。

在这种情况下，使用偏移量容易导致同一内容在不同页面重复出现（因为在加载第一页和第二页之间，内容的位置发生了变化）；而使用游标则容易完全丢失位置（如果某条内容从第 10 位掉到第 15 位，当你加载下一页时，第 10 到 15 位的内容就全部被跳过了）。

我们通常不会试图解决这个问题，但在第三版 MyNews 中，由于故事列表变化得过于剧烈，我们确实实现了一种保证分页一致性的方案。那版 MyNews 会把你朋友正在 Dig、提交或评论的内容，加上你最常参与的 Newsroom 的内容，再加上 Digg 全站的 trending 内容，混合在一起，根据多种因素进行排序。在最初的内部版本中，这导致内容在不同页面之间跳动得非常厉害。

我们的解决方案是：

  1. If offset was zero, then generate the first 225 items in the MyNews storylist, store that ordered list of item_ids as a JSON blob inside Redis, and return the first count item_ids.
  2. If offset was not zero and the MyNews JSON blob existed in Redis, retrieve the blob and slice the offset:count item_ids from within.
  3. If the osset was not zero, and the MyNews JSON blob did not exist, then generate it, store it, and retrieve the offset:count item_ids. (This was an edgecase for people refreshing old pages or if the blob got evicted from the cache, which in general shouldn’t happen in a short period of time, but could happen.)

这个方案的缺点是，非首页的内容可能会变“陈旧”，但根据我们对用户行为的观察，这并不重要——想看新内容的人会直接去第一页，而不是在后面的页面里闲逛。

关于不一致物化视图的再后续说明

Can 在文章里提到“我们因此不在分页中显示总数”，这也暗示了我们在用 Cassandra 实现故事列表时遇到的另一个问题。

这个问题其实完全是我们自己的错。随着我们物化越来越多的故事列表，经常会跟丢其中一部分。当一篇故事被删除（比如提交者注销账号）或者因为被识别为垃圾信息而隐藏后，它仍然会出现在后端返回给前端的列表里。前端会把这条隐藏掉，结果原本请求 15 条，却只拿到 12 条有效内容。

当物化视图的数量增长到每个 Newsroom 半打、每个用户的 MyNews 有六个等等之后，我们最终采取了一个尴尬的折中方案：我们在读取时修复故事列表（去掉无效、过期、垃圾等内容）。在大多数情况下，这只是一个备份机制，而非保持视图一致性的主要手段，但它确实会导致某些读取返回少于预期数量的结果。

和 Digg 的很多其他方案一样，你只能说它能用，而且在中等偏高的规模下能用。如果我们维护一个注册表，记录每篇文章出现在哪些故事列表里，然后在内容修改时主动清理，会优雅得多。但如果一篇故事出现在几十万个故事列表中，其中很多可能永远不会被读取，那么“读取时修复”的机制反而更可取（它还能在系统出错时自我修复，这在存在一定错误率的分布式系统中是个加分项）。

Like a lot of our solutions at Digg, all you can say is that it worked, and worked at a moderately high scale. Maintaining a registry of all the storylists a given article was in and then cleaning them up on modification would have been much prettier, but if a story was in several hundred thousand storylists, many of which will never actually be read, then the repair-on-read mechanism may be preferable (it also self-repairs in the case of failures, which is a bonus when dealing with distributed systems with non-zero error rates).
