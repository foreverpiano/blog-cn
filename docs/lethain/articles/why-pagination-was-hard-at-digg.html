为什么 Digg 的分页实现如此困难

2012-08-25 · 阅读原文

我之前在 Digg 的同事 Can Duruk 最近发表了一篇很棒的文章，分享了他在 Digg 工作期间积累的一些 Web 开发经验。他在文章中关于分页的评论在 Hacker News 上引发了一些困惑。人们坐在舒服的椅子上可能会想：一个在所谓“互联网公司”工作的人，怎么会连分页都搞不定，简直太无能了吧？

首先，我们来看看 Can 的原话：

计数很难。分页更难。所以，别在分页里显示总数。逻辑完美。

从根本上说，要描述一个内容列表（这里的列表是抽象概念，通常对应数据库中的行）的起始位置，有两种直观的概念方式：

一个整数偏移量（integer offset），即列表中的索引；一个唯一游标（unique cursor）（通常是字符串，也可能是时间戳之类的），它能唯一标识从哪个条目开始（或之后开始），通常是主键或某种标识符。

两种方式都会搭配一个整数 count，表示要返回的数量。

偏移量方式在用户体验上有很大优势，它允许用户直接跳到列表中的任意位置，而不需要强迫用户一直滚动（可能没完没了）才能到达目标页面。而且它的分页逻辑也极其简单：下一页永远从 offset + count 开始，上一页从 offset - count 开始。

游标方式则几乎没什么优点。它很笨拙，因为你无法跳到列表中的任意位置；如果你用的游标和条目的唯一标识符不同，还很容易把自己搞晕，尤其是当两者都是“时间戳 + UUID”这种格式的时候（我们确实这么干过）。（没错，我们就是这么干的。）

你唯一能为游标方式辩护的一点是：在某些限制条件下，它是唯一可行的方案。在我们当时的情况下，大部分内容列表都存储在 Cassandra 中，可用的数据结构是 ColumnFamily 里面装着 Row，Row 里面再装着 Column。

在标准的 Cassandra 配置中，Row 是随机分布的，以便通过一致性哈希将数据分散到节点环上；而同一个 Row 内的 Column 则按 key 排序。从这个角度看，你可以把 ColumnFamily 想象成一个以字符串为 key、Row 为 value 的无序字典，而 Row 则是以字符串为 key、字符串为 value 的有序字典。（好吧，它们实际上大概率都是字节而不是字符串，吐槽我好了。）

在使用 Cassandra 存储故事列表的限制下，如果你面对的是频繁写入（我们当时基本都是这种情况），就通常只能使用游标而非偏移量。如果写入量很低，你可以用各种奇奇怪怪的办法绕过这个限制。但当写入量很大时，我能想到的任何基于索引的访问方案，都会撞上 Cassandra 的墓碑（tombstone）实现。（谁知道呢，也许现在有新的 API 能解决这个问题了。）

最终，我们成功摆脱了游标，统一改用基于偏移量的分页。实现方式是将动态计算的故事列表迁移到 Redis 的 Sorted Set 中。Redis Sorted Set 是 Cassandra 的绝佳补充，能很好地处理动态排序的内容（用唯一标识符作为 score），并将结果存回 Cassandra，通过从 Redis 中取到的唯一标识符来访问。

我们唯一保留在 Cassandra 中的故事列表是 Top News，这个列表只定期重新计算。我们为每一种过滤组合（内容类型、话题等）都预先生成结果，并把整个列表存成一个 JSON blob，放在 Cassandra 的一个 Column 里。就实现方式而言，对这个方案唯一的评价就是“它能用”。

总之，这就是分页当时为什么那么难。

分页与不一致排序的后续讨论

分页中另一个棘手的地方是，当你按动态分数对内容进行排名时，某个内容可能会从第 3 位掉到第 10 位，后来又因为人气暴增冲到第 2 位。

在这种情况下，使用偏移量可能会导致同一内容在不同页面重复出现（因为在加载第一页和第二页之间，内容的位置发生了变化）；而使用游标则可能完全丢失某些位置（如果某个内容从第 10 位掉到第 15 位，当你加载下一页时，第 10 到 15 位的内容就全被跳过了）。

我们通常没有尝试解决这个问题，但在 MyNews 的第三个版本中，由于故事列表变化得非常剧烈，我们确实实现了一个保证分页一致性的方案。该版本的 MyNews 会收集你朋友正在 Dig、提交或评论的内容，加上你最常参与的 Newsroom 的内容，再加上 Digg 全局的趋势内容，然后根据多种因素进行综合排序。在最初的内部版本中，这导致内容在不同页面之间跳动得非常厉害。

我们的解决方案是：

如果 offset 为 0，则先生成 MyNews 故事列表的前 225 条内容，把这个有序的 item_id 列表以 JSON blob 的形式存入 Redis，然后返回前 count 条 item_id。如果 offset 不为 0 且 Redis 中存在对应的 MyNews JSON blob，则取出该 blob，从中切片取出 offset:count 的 item_id。如果 offset 不为 0 但 Redis 中没有对应的 blob，则先生成、存储它，然后再取出 offset:count 的 item_id。（这是针对刷新旧页面或者 blob 被缓存淘汰的情况。通常短时间内不会发生，但确实有可能。）

这个实现有一个缺点，就是非首页的内容可能会变得过时。但根据我们对用户行为的观察，这并不重要，因为想看新内容的人会直接去首页，而不是在后面的页面到处翻。

关于不一致物化视图的再后续讨论

Can 在评论中还提到了我们在故事列表实现上遇到的另一个问题，当时我们大量依赖 Cassandra，他说：

所以，别在分页里显示总数。

这完全是我们自己的锅。随着我们物化的故事列表越来越多，我们经常跟不上某些列表的更新。比如当一篇故事被删除（提交者注销账号等）或者因为被识别为垃圾信息而隐藏后，它仍然可能被后端返回给前端。前端会隐藏这些无效故事，但当它向后端请求 15 条时，可能最终只拿到 12 条有效内容。

随着物化视图数量激增——每个 Newsroom 有半打，每个用户的 MyNews 有六个等等——我们最终采取了一个尴尬的折中方案：我们在读取时修复故事列表（移除无效、过期、垃圾内容等）。在大多数情况下，这只是一个后备机制，而不是保持视图一致性的主要手段，但这意味着某些读取操作会返回少于预期数量的内容。

和 Digg 的很多其他解决方案一样，对这个方案唯一的评价就是“它能用”，而且是在中等偏高的规模上能用。如果为每篇文章维护一个它所在的所有故事列表的注册表，然后在内容修改时清理它们，那会优雅得多。但如果一篇文章出现在几十万个故事列表中，而其中很多列表可能永远不会被读取，那么“读取时修复”的机制反而更可取（它还能在出现故障时自我修复，这在存在非零错误率的分布式系统中是个加分项）。
