构建内部 Agent：子 Agent 支持

2025-12-31 · 阅读原文

我们对内部 Agent 的大部分扩展，都是因为在现有框架内无法优雅地解决问题而直接产生的。Evals、压缩、大文件处理都属于这一类。而子 Agent（允许一个 Agent 启动其他 Agent）则属于不同类别：我虽然经常觉得我们需要子 Agent，但每次都能找到感觉更自然的替代方案。

最终，我还是决定实现它，因为这看起来是个值得深入思考的有趣问题。反正我迟早会需要它们……对吧？（题外话：后来我确实用子 Agent 来支持 构建内部 Agent：代码驱动 vs LLM 驱动的工作流 中调用 LLM 的功能。）

本文是 构建内部 Agent 系列的一部分。

为什么子 Agent 很重要

“子 Agent”指的是允许你的 Agent 调用其他 Agent，这些子 Agent 拥有独立的系统提示、可用的工具以及上下文窗口。你可能会考虑使用子 Agent 的几个原因如下：

为上下文窗口管理提供有效的策略。你可以让子 Agent 访问上传的文件，然后要求它们从中提取特定数据，而不会用这些文件的内容污染主 Agent 的上下文窗口。 你可以使用子 Agent 来支持并发工作。例如，你可以允许同时调用多个子 Agent，然后等待所有子 Agent 完成后再继续。如果你的 Agent 工作流主要受网络 IO 限制（例如调用模型评估 API），那么这能显著减少工作流完成的实际耗时。 你也可以说服自己，在权限较少的子 Agent 中执行某些操作能带来一些安全收益。虽然我并不认为这能带来实质性的提升，但至少可以通过强制要求外部资源获取和内部资源访问必须在相互隔离的子 Agent 中进行，从而增加操作的摩擦。

在所有这些理由中，我认为前两条对大多数内部工作流开发者而言会是最相关的。

我们在 subagents/*.yaml 中定义子 Agent，每个子 Agent 都有自己的 prompt、允许使用的工具（或选择继承父 Agent 的所有工具），以及部分来自主 Agent 配置的可配置字段。 每个 Agent 都被配置为允许使用特定的子 Agent，例如规划子 Agent。 Agent 通过 subagent(agent_name, prompt, files) 工具来调用子 Agent，该工具允许它们决定哪些虚拟文件可在子 Agent 中访问，同时还能指定传递给子 Agent 的用户提示（子 Agent 在其配置中已拥有默认的系统提示）。

这种实现运行得相当不错。例如，它支持快速添加 planning 和 think 子 Agent，供父 Agent 用于完善自己的工作。我们还进一步重构了运行 Agent 的 harness 实现，使其等价于子 Agent——本质上每个 Agent 都是一个子 Agent，以此类推。

实际效果如何 / 下一步

老实说，我目前并没有发现子 Agent 对我们现有的工作流特别重要。不过，用户侧的延迟是一个隐形特性——在某个临界点之前它完全无关紧要，但一旦超过就会悄然导致不良的用户行为（例如在检查回复前就开始另一项任务）。因此我相信，从长期来看，这将是我们能获得的最大优势。

附记：正如引言中所暗示的，当我们引入 构建内部 Agent：代码驱动 vs LLM 驱动的工作流 时，子 Agent 功能最终变得极其有用，因为它允许将控制权交给 LLM 进行非常具体的判断，之后再将控制权交还给代码。
