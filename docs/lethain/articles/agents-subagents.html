构建内部 Agent：子 Agent 支持

2025-12-31 · 阅读原文

我们对内部 Agent 的大多数扩展，都是在现有框架内无法优雅解决某个问题时直接催生的。Evals、压缩、大文件处理都属于这一类。而子 Agent（允许一个 Agent 启动其他 Agent）则不同：我虽然经常觉得我们需要子 Agent，但每次都能找到感觉更自然的替代方案。

最终我还是决定实现它，因为这看起来是个值得深入思考的有趣问题——我总有一天会需要它的，对吧？（题外话：后来我确实用子 Agent 来支持 构建内部 Agent：代码驱动 vs LLM 驱动的工作流 中调用 LLM 的场景。）

本文是 构建内部 Agent 系列的一部分。

为什么子 Agent 很重要

“子 Agent”指的是允许你的 Agent 调用其他 Agent，这些子 Agent 拥有独立的系统提示、可用工具和上下文窗口。你可能会考虑使用子 Agent 的几个原因如下：

为上下文窗口管理提供有效策略。你可以让子 Agent 访问上传的文件，然后要求它们从中提取特定数据，而不会用文件内容污染主 Agent 的上下文窗口。 你可以用子 Agent 来支持并发工作。例如，允许同时调用多个子 Agent，然后等待它们全部完成。如果你的 Agent 工作流主要受网络 IO 限制（如调用模型评估 API），那么这种方式可以显著缩短整个工作流的实际完成时间。 你也可以说服自己，在权限较少的子 Agent 中执行某些操作能带来安全收益。虽然我并不认为这能带来实质性提升，但至少可以通过强制要求外部资源获取和内部资源访问只能在相互隔离的子 Agent 中进行，从而制造一些摩擦。

在所有这些理由中，我认为第一条或第二条对大多数内部工作流开发者来说最为相关。

我们如何实现子 Agent

我们的子 Agent 实现相当直截了当：

我们在 subagents/*.yaml 中定义子 Agent，每个子 Agent 都包含一个系统提示、允许使用的工具（或选择继承父 Agent 的所有工具），以及从主 Agent 配置中继承的部分可配置字段。 每个 Agent 被配置为允许调用特定的子 Agent，例如 planning 子 Agent。 Agent 通过 subagent(agent_name, prompt, files) 工具来调用子 Agent，该工具允许它们决定哪些虚拟文件可在子 Agent 中访问，同时还能自定义传递给子 Agent 的用户提示（子 Agent 已在配置中拥有默认的系统提示）。

这种实现运行得相当不错。例如，它让我们可以快速添加 planning 和 think 子 Agent，供父 Agent 用于优化自身工作。我们进一步将运行 Agent 的 harness 重构得与子 Agent 等价，最终让每个 Agent 本质上都是一个子 Agent，依此类推。

实际效果如何 / 下一步

老实说，我目前并没有发现子 Agent 对我们现有的工作流特别重要。不过，用户侧的延迟是一个隐形特性——在它真正造成问题之前，你完全感觉不到它的存在，直到某天它开始悄无声息地导致不理想的用户行为（比如还没等回复就启动另一个任务）。因此我相信，从长期来看，这将是我们最大的收益点。

附记：正如引言中提到的，当我们引入 构建内部 Agent：代码驱动 vs LLM 驱动的工作流 时，这个子 Agent 功能最终发挥了极大作用，它允许将控制权交给 LLM 进行非常具体的判断，之后再将控制权交还给代码。
