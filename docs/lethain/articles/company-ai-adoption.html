在 Imprint 推动 AI 采用

2025-12-07 · 阅读原文

过去 18 个月左右，我一直在公司内部推动“AI”采用——更准确地说，是 LLM 工具和 Agent 的采用。这是我认为当下每位工程领导者至少应该当作支线任务去解决的问题。鉴于有这么多人在各自公司里研究这个问题，我想把自己的“工作笔记”整理出来，分享一下学到的东西。

这不是一份“你应该怎么做”的建议，而只是我迄今为止处理这个问题的方式，以及通过持续迭代所获得的经验总结。我希望这里的思考对你有帮助，或者至少能印证你在推广过程中遇到的一些感受。文章越往后越具体，最后会谈到一些近乎“廉价松节油”级别的话题，比如让 Agent 可靠地将人类可读的 Slack 实体文本表示，转换成正确底层实体的 mrkdwn 格式。

我正在招人： 如果你有兴趣和我一起在 Imprint 推动内部 Agent 和 AI 采用，我们正在招聘创始 Senior Software Engineer, AI。理想候选人是一位产品工程师，曾花时间尝试过 Agent，并且愿意在接下来一两年深入钻研这个领域。

前期准备：建立直觉

作为技术人员，我认为我们对团队的基本责任之一，就是花时间亲自使用新工具，从而建立对它们能做什么、不能做什么的直觉。AI 采用也不例外。

为此，我先读了一些书，尤其是 Chip Huyen 的《AI Engineering》，然后投入到几个有边界的小项目中：用 Claude 代码构建了我们自己的智能体及其专属工具，创建了一个，以及。library-mcp：使用 Markdown 知识库一个利用 Notion 文档作为 Prompt 来评论其他 Notion 文档的 Agent。

每个项目耗时两到十小时，却带来了极大的启发。特别是工具调用，在我自己实现一个简单的工具调用 Agent 之前，它看起来像魔法；实现之后，它就变成了我能理性分析和理解的普通机制。

我们的 AI 采用策略

Imprint 在优化 AI 采用方面的总体方法是：确定几个目标，选定初始方法，然后在细节上快速迭代，直到方法真正有效。在这个看重表面形象的时代，高级领导者沉浸到细节中是我们为数不多的防御手段之一。策略测试：通过迭代优化避免瀑布式策略陷阱

入职后不久，我就与高管团队合作起草了上述 AI 采用策略。经过适度讨论，我们最终确定的支柱是：

通过消除采用障碍来铺平采用道路，尤其是那些需要明确申请工具权限之类的麻烦。无论公司内部还是行业整体，对 AI 采用都有很高的热情，我们应该相信自己的团队。如果他们没有采用工具，我们应该主要专注于让使用变得更容易，而不是花时间质疑或否定他们的采用努力。采用机会无处不在，而非局限于工程、客服或其他特定部门。要成为一家能广泛从 AI 中获益的公司，我们需要在所有团队中解决采用问题。我不是说每个团队都要用完全相同的方法，但我们需要为每个团队找到适用的方法。由高层领导从前线带头，确保我们做的事情真正有用，而不是陷入我们正在衡量的指标里。

从这些原则以及我之前的评论可以看出，我对 AI 采用最大的担忧是：人们可能只注重制造“在采用 AI”的表象，而不是真正创造额外的生产力。表象是任何工作的核心部分，但几乎所有有价值的工作都发生在表象与现实的交汇处，而这些支柱正是为了支持这一点。

顺便一提，按照《Crafting Engineering Strategy》中的框架，这其实只是。此外，我们还用来持续优化方法，定义了一组具体的初始行动来落地执行（这些内容太具体，这里不便对外分享），并做了一些简短的，以确保我没有过度依赖在 Carta 的过往经验。构建工程策略的步骤制定策略的政策。策略测试：通过迭代优化避免瀑布式策略陷阱探索策略空间

记录tips & tricks

我推动采用的第一步，是把公司内部尽可能多的 tips 和 tricks 例子收集到一个统一的 Notion 数据库中。我对收录标准的定义非常宽泛，相信展示各种使用工具的例子——尤其是来自不同职能的例子——既实用又能带来启发。

我一直在扩展这个数据库，来自公司各部门的贡献越来越多，它已经成为人类和机器人 alike 都喜欢参考的资源，用来为如何用 AI 工具解决问题提供建议。

集中管理我们的 Prompt

我对我们方法的核心信念之一是：在公司内部让 Prompt 可被发现具有极高价值。可发现性解决了四个不同问题：

让人看到 Prompt 能做什么（从而启发别人在类似场景中使用）。例如，我们的 Agent 可以 在 Notion 文档创建时自动评论、在 Slack 频道中有效回复、为 Jira ticket 做 triage 等。展示好的 Prompt 长什么样（让别人可以改进自己的 Prompt）。例如，可以把复杂的配置从难以阅读和准确修改的列表形式，改成表格形式。作为可复制片段的仓库，方便在不同 Prompt 之间复用。例如，你可以复制我们现有的“Jira issue triaging prompt”来开始为新的 Jira 项目做 triage。Prompt 是团队或职能的共同财产，而不是某一个人的不可修改的专属构造。例如，我们 Helpdesk 团队的任何人都可以改进用于回复 Helpdesk 请求的 Prompt，而不只是拥有权限的那一个人；它也不需要依赖熟悉 Git 或 GitHub 的能力（尽管我预计随着时间推移，我们会对编辑最重要的内部 Agent 增加更多限制）。识别重复出现的 Prompt 子组件，这可能暗示存在缺失或难以使用的工具。例如，我们早期版本的 Prompt 中有大量关于如何指定 Slack 用户和频道的困惑，我自己已经习惯了绕过去，但其他人并不适应。

我的核心做法是：把每个 Agent 的 Prompt 都存放在一个公司全体可读的 Notion 数据库中。大多数 Prompt 每个人都可以编辑，但部分会设置编辑权限。

采用标准平台

除了收集 tips 和 Prompt，下一个推动 AI 采用的明显步骤是确定公司在内部使用的标准 AI 平台，例如 ChatGPT、Claude、Gemini 等。

我们选择了 OpenAI 供全公司使用。除了统一平台，我们还确保账户开通是自动化的，从第一天起就已就位。任何在 IT 或 IT 相关领域工作过的人都不会意外：很多革命性的通用 AI 采用……其实主要就是账户开通和访问控制。这些小细节如果不深入处理，很容易让整个大计划脱轨。

在工程团队，我们还同时提供了 Cursor 和 Claude。不过，我们绝大部分 Claude 用量都是通过 AWS Bedrock 完成的，我们用它来驱动 Claude Code……而且我们用 Claude Code 的频率相当高。

其他 AI 工具

虽然行业普遍在推动采用更多 AI 工具，但我发现很大一部分“AI 工具”其实只是 SaaS 厂商在营销文案里塞了 AI 两个字。我们继续在采用厂商工具，但也在内部帮助团队评估哪些“AI 工具”是真正有意义的。

我们在聊天和 IVR 工具的 AI 集成上花了不少深入功夫，但那是另一篇文章的内容了。

指标

衡量 AI 采用情况和所有衡量话题一样，充满陷阱。总体而言，我发现衡量工具采用情况对提出正确的问题非常有帮助。你为什么还没用 Cursor？或者 Claude Code？或者其他工具？这些都是值得深挖的有趣问题。我至少每月看一次使用数据，特别关注两个问题：

对于深度采用者，他们实际在用这些工具做什么？为什么他们觉得有用？对于低采用者或未采用者，他们为什么不用这些工具？我们怎样才能帮助他们解决这个问题？

在核心层面，我相信没有采用工具的人是理性的非采用者，花时间去理解他们（表面上的）抗拒，比自上而下的强制命令更有用。我认为这往往是一个教育差距，很容易通过教育来弥合。可以想象，未来某个时候我会遇到收益递减点——要么是因为不进步的人在坚决拒绝 AI 工具，要么是因为 AI 工具本身并不真正有用——但目前我还没遇到那个点。

构建内部 Agent

接下来的几节是关于构建内部 Agent 的。核心实现是一个无状态的 Lambda，它可以处理各种各样的 HTTP 请求，类似 Zapier。目前用 Python 实现，大约 3000 行代码，其中很大一部分用于处理 Slack 消息格式化之类的奇怪细节。

声明一下，我最初确实尝试过，但我发现 Zapier 无法提供我认为有效完成这件事所需的精度。我也认为 Zapier 对非工程背景的用户不够友好。通过 OpenAI 和 Zapier 在 Notion 文档中添加评论

什么在推动采用（尤其是 Agent）

作为曾在平台工程领域工作很久的人，我仍然希望你能构建一个平台，然后用户就会来。确实，如果问题对他们足够痛苦，那么少数早期采用者是会来的，就像那样。2014 年左右 Uber 的服务迁移策略。

然而，我们发现真正有效的推动采用的方式，基本上与此相反。真正奏效的是平台工程与传统产品工程的结合：

（产品工程）找到一个具有很多挑战或潜在影响的工作流 （产品工程）与领域专家紧密合作，让第一个版本跑起来 （平台工程）确保这个可用的解决方案能被使用它的团队进行扩展 （两者共同）以采用情况作为问题-解决方案匹配度的指标，否则就调整

以下是一些我们在内部取得 traction 的项目例子：

用有效的 AGENTS.md 文件指导测试、类型检查和 linting 来编写软件 通过聊天和 IVR 处理初始客户问题 路由聊天机器人，将问题引导至解决问题、提供答案，或通知正确的负责人 对 incoming ticket 进行 issue triaging：打标签并分配给合适的团队 对常规合规和法务问题提供实时的初始反馈（例如那些频繁出现且变化不大的问题） 拉取 Git commits、Slack 消息等各种资源后，自动撰写每周优先事项更新

所有这些取得成效的项目，其公式都与“建好平台，他们就会来”完全相反。它需要有构建 AI Agent 经验和使用 AI 工具经验的人深度参与才能取得进展。在重要或接近生产环境的工作流中，有效采用 AI 的学习曲线仍然相当陡峭。

配置 Agent

使用强大工具的 Agent 代表了一个复杂的配置问题。首先，暴露太多工具——尤其是 Prompt 作者自己都没完全掌握的工具——会让创建可靠工作流变得非常困难。例如，我们有一个 exit_early 命令允许提前终止 Agent，这在很多情况下非常有效，但也很容易把你的 bot 搞坏。同样，我们有一个 slack_chat 命令允许跨频道发消息，这能支持很多有用的工作流（比如把一个频道的问题 warm-handoff 到更合适的频道），但也可能造成骚扰。其次，工具越强大，就越可能引入复杂的安全场景。

解析外键

说起来有点好笑，但实际中严重干扰我们轻松编写有效 Prompt 的一件事，是如何方便地写出类似 @Will Larson 这样的文本，然后让它被正确转换成 <@U12345> 或者对应用户、频道、用户组的 Slack identifier。Jira group、Notion 页面和数据库等也存在同样的问题。

这是一个很好地体现了集中管理 Prompt 价值的例子。我自己已经习惯了手动拉取这些唯一标识符，但很明显大多数其他人并不适应。这最终演变成了三个 Slack 解析工具：slack_lookup（接受一个引用列表进行查找）、slack_lookup_prefix（查找以某个前缀开头的所有 Slack 实体，例如找出所有以 @oncall- 开头的频道或组，而不需要在 Prompt 里硬编码列表），以及 slack_search_name（使用字符串距离来寻找可能的匹配，同样对处理拼写错误很有用）。

如果这听起来令人困惑，很大程度上是因为 Slack 没有为这类查找暴露合适的 API。Slack 的 API 希望你用 ID 来获取用户、组和频道，因此你必须维护自己的一份这些实体的缓存来进行查找。而查找本身，尤其是用户查找，也很 messy。Slack 用户至少有三种可能的引用方式：user.profile.display_name、user.name 和 user.real_name，但对任意给定用户来说，只有其中一部分是设置了的。我目前能想到的正确逻辑是：先尝试匹配 user.profile.display_name，如果存在就使用它；然后是 user.name，最后是 user.real_name。如果你只是取第一个匹配其中任意一个的用户，在某些场景下你会选到错误的用户。

除了给 LLM 提供解析名称的工具外，我还为每个响应加入了一个最终的强制检查，确保返回的引用指向真实存在的实体。如果不是，我就把哪些是无效的注入到上下文窗口中，并使用仅包含实体解析工具的额外 Agent 循环再跑一次。这听起来很荒谬，但只有到这一步之后，事情才真正开始稳定工作。

顺便说一句，我之前对这些截图感到尴尬，今天早些时候我已经为 Notion 页面和数据库做了和之前对 Slack 一样的改进。

格式化

与外键解析类似，Slack 的 mrkdwn 版 Markdown 和 JIRA 的 Atlassian Document Format 也存在同样的问题：两者都非常严格。

调用这些 API 的工具现在都有关于格式化的严格指示。这些指示曾经分散在各个 Prompt 里，但后来它们开始在每个 Prompt 里反复出现，我就知道必须把它们纳入 Agent 框架本身，而不是强迫每一位 Prompt 作者都去理解这个问题。

我猜测我需要增加一个类似实体解析的验证步骤，在此之前，我会继续遇到少量但非常烦人的渲染问题。老实说，我个人并不介意这些渲染问题，但这会给其他使用 Agent 的人带来很多不确定性，因此我认为解决它们是必须的。

日志和调试

目前，所有日志——尤其是工具使用日志——会被发送到两个地方。首先是 Datadog，用于完整的日志可见性。其次，或许对非工程师更有用的是，它们会被发送到一个 Slack 频道 #ai-logs，这个频道能让人清楚看到使用了哪些工具以及对应的（可能被截断的）参数。

从长期来看，我设想会通过一个专用的内部 Web UX 来暴露这些信息。但总体而言，我发现那些正在积极开发 Agent 的人相当愿意忍受一点粗糙。而那些不直接开发 Agent 的人并不关心日志，他们只希望它每次都能完美工作，也不会花时间去看日志。

目前最大的差距：通用的用户域 MCP Server 访问平台

我目前看到的最大的内部机会，是如何让非工程师也能获得类似于本地运行 Claude Code 并接入他们所有喜欢的 MCP Server 的体验。我一直希望 ChatGPT 或 Claude.ai 能提供这个功能，但它们还没有完全做到。Claude Desktop 比较接近，但配置起来还是有点 messy，我们需要的是一个能让公司每个人都容易自定义并每天使用的工具。

我还在寻找合适的工具。如果有人有任何好的建议，既能让我们比较放心它在两年后还会存在，又不需要把大量内部数据发送给一个非常早期的公司，我很乐意听听！

下一步是什么？

写一个好的结论通常应该以一个有力的轶事开头，用新的角度照亮你的核心论点。我不确定自己能不能达到这个标准，但对我来说最重要的四个想法是：

我们仍处于 AI 采用的非常早期阶段，因此专注于学习速度比其他任何事情都更有价值。如果你想领导内部 AI 计划，你必须亲自使用这些工具，而且不只是用 ChatGPT，而是仅用 LLM API 去构建你自己的工具调用 Agent。根据我的经验，在真实问题上的真实 AI 采用，是领域上下文、AI 工具使用经验和传统 IT 问题的复杂混合。我对任何不同时 anchor 在这三者的内部 AI 采用计划都深表怀疑。这是早期公司的优势，因为你常常能在一个人身上（或至多两个人之间）找到这三者的结合。而在更大公司里，你需要三个不同的组织一起做这件事，这客观上非常困难。我认为模型选择很重要，但在任何给定时刻，你只需要 2-3 个模型，而且会有人直接告诉你当前那 2-3 个模型是什么。例如，GPT-4.1 就特别擅长快速遵循规则。它是大多数对延迟敏感的 Agent 的绝佳选择。

我很好奇其他人有哪些发现！
