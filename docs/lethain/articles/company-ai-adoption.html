推动 Imprint 的 AI 采用

2025-12-07 · 阅读原文

过去 18 个月左右，我一直在推动公司内部“AI”采用工作，准确来说是 LLM 工具和 Agent 的采用。 我认为，这件事至少是当下每一位工程领导者都应该当作支线任务去解决的问题。 鉴于有这么多人在各自公司里攻克这一难题，我想把自己的“工作笔记”整理出来，分享我学到的东西。

这篇文章并非在告诉你应该怎么做，而只是复盘我目前为止处理这个问题的方法，以及在持续迭代中获得的经验。我希望这里的思考对你有帮助，至少能印证你在推行过程中遇到的一些情况。文章越往后越具体，最后会谈到一些类似“廉价松节油”的细节话题，比如让 Agent 可靠地将人类可读的 Slack 实体文本转换成正确的 mrkdwn 格式及其背后的实体。

我正在招聘： 如果你有兴趣和我一起在 Imprint 推动内部 Agent 和 AI 采用，我们正在招聘创始 Senior Software Engineer, AI。 理想候选人是一位产品工程师，曾花时间试验过 Agent，并希望在接下来一两年深入这个领域。

前置准备：建立直觉

作为技术人员，我认为我们对团队的基本责任之一，就是花时间亲自使用新工具，从而建立对其工作原理和局限性的直觉。 AI 采用也不例外。

为此，我先做了一些阅读，特别是 Chip Huyen 的《AI Engineering》，然后投入到几个有边界的小项目中：用 Claude 代码构建了 我们自己的智能体，以及它们自己的工具。，创建了一个 library-mcp：使用 Markdown 知识库，以及 。一个利用 Notion 文档作为提示词来评论其他 Notion 文档的 Agent。

每个项目耗时两到十小时，却带来了极大的启发。尤其是工具调用，在我自己实现一个简单的工具调用 Agent 之前，它看起来像魔法；实现之后，它就变成了我能够理性分析和理解的普通机制。

我们的 AI 采用策略

Imprint 在优化 AI 采用上的总体方法是 ：确定几个目标，选择一个初始方案，然后在细节上快速迭代，直到方案真正有效。在这个注重表面形象的时代，高级领导者亲自深入细节是我们为数不多的防御手段之一。策略测试：避免瀑布式策略陷阱，通过迭代优化。

加入公司不久，我就和管理团队一起起草了上述 AI 采用策略。经过适度讨论，我们最终确定的核心原则是：

通过消除采用障碍来铺平采用道路，尤其是那些需要明确申请工具访问权限之类的麻烦。我们对 AI 采用有强烈的内部和行业热情，应该信任自己的团队。如果他们没有采用工具，我们的主要精力应该放在让使用变得更简单，而不是花时间质疑或否定他们的采用努力。采用机会无处不在，而非局限于工程、客服等特定部门。要成为一家能广泛从 AI 中获益的公司，我们需要在所有团队中解决采用问题。我并非认为所有团队都要用同一套方法，但每个团队都需要有一个适用的方法。高级领导者要身先士卒，确保我们做的事情真正有用，而不是陷入对指标的盲目追求。

从这些原则以及我之前的评论可以看出，我对 AI 采用最大的担忧是，人们可能只关注制造“已经在采用 AI”的表象，而不是真正创造额外的生产力。表象是任何工作的核心组成部分，但几乎所有有意义的工作都发生在表象与现实的交汇处，而这些原则正是为了支持这一点。

记录 tips & tricks

我推动采用的第一步，是把公司内部尽可能多的 tips 和 tricks 例子收集到一个统一的 Notion 数据库中。我对收录的标准采取了非常宽泛的态度，相信展示大量来自不同职能的使用工具的例子，既实用又鼓舞人心。

我持续在扩展这个数据库，来自公司各部门的贡献不断增加，它已经成为人类和机器人 alike 都乐于参考的资源，用于获取如何用 AI 工具解决问题的建议。

集中管理我们的 Prompt

我对我们方法的 core belief 之一是，让公司内部的 Prompt 可被发现具有极高价值。 可发现性解决了四个不同的问题：

让大家看到 Prompt 能做什么（从而启发别人在类似场景中使用）。例如，我们的 Agent 可以 在 Notion 文档创建时自动评论、在 Slack 频道中有效回复、为 Jira ticket 做 triage 等。展示什么是好的 Prompt（让其他人能改进自己的 Prompt）。例如，可以把复杂的配置从难以阅读和准确修改的列表形式，改成表格形式。作为可复制片段的仓库，能在不同 Prompt 间复用。例如，你可以复制我们现有的“Jira issue triaging prompt”来开始为新的 Jira 项目做 triage。Prompt 是团队或职能的共同财产，而不是某个人不可更改的私有产物。例如，我们 Helpdesk 团队的任何人都可以改进回应 Helpdesk 请求的 Prompt，而不需要只有一个人有权限，也不需要必须熟悉 Git 或 GitHub（尽管我预计随着时间推移，我们会对最重要的内部 Agent 的编辑权限施加更多限制）。识别重复出现的 Prompt 子组件，这些往往暗示存在缺失或难以使用的工具。例如，我们早期版本的 Prompt 在如何指定 Slack 用户和频道上存在大量困惑，我自己已经习惯了 workaround，但其他人并不适应。

我的核心做法是：所有 Agent 的 Prompt 都存储在一个统一的 Notion 数据库中，公司每个人都可以阅读。大多数 Prompt 每个人都可以编辑，但部分有编辑限制。

采用标准平台

除了收集 tips 和 Prompt，AI 采用的下一个明显步骤是确定公司在内部使用的标准 AI 平台，比如 ChatGPT、Claude、Gemini 等。

我们选择了 OpenAI 供所有人使用。除了统一平台，我们还确保账户开通在第一天就实现自动化。对任何在 IT 或相邻领域工作过的人来说，这一点都不令人意外：很多革命性的通用 AI 采用……其实主要就是账户开通和访问控制。这些小细节如果不深入处理，很容易把整个大计划搞砸。

在工程团队，我们还同时提供 Cursor 和 Claude。不过，我们绝大部分 Claude 用量都通过 AWS Bedrock 实现，我们用它来驱动 Claude Code……而且我们用 Claude Code 的频率相当高。

其他 AI 工具

虽然行业普遍在推动采用更多 AI 工具，但我发现很大一部分“AI 工具”其实只是 SaaS 厂商在营销文案里塞了 AI 两个字。我们继续在采用厂商工具，但内部也在帮助团队判断哪些“AI 工具”是真正有意义的。

我们在聊天和 IVR 工具的 AI 集成上投入了相当多精力，但那是完全另一篇文章的话题。

指标

衡量 AI 采用情况和所有衡量话题一样，充满陷阱。 总的来说，我发现衡量工具采用对找出正确的问题非常有用。你为什么还没用 Cursor？或者 Claude Code？或者别的什么？这些都是值得深挖的有趣问题。我至少每月看一次使用数据，特别关注两个问题：

对于重度采用者，他们真正在用这些工具做什么？他们为什么觉得有用？对于低度或未采用者，他们为什么不用这些工具？我们怎样才能帮助他们解决这个问题？

我核心的信念是，没有采用工具的人是理性的非采用者，花时间理解他们（看似）的抵触，比自上而下的强令更有效。我认为这往往是一个教育差距，相对容易弥合。可以想象，未来某个时候我会遇到收益递减点，即缺乏进展是因为有人在拒绝 AI 工具——或者因为 AI 工具本身没有真正价值——但目前我还没有遇到那个点。

什么推动了采用（尤其是 Agent）

作为一个长期在平台工程领域工作的人，我仍然愿意相信你可以构建一个平台，然后用户就会来。 确实，如果问题对他们足够痛，我认为一小部分早期采用者会来的，就像 那样。2014 年左右 Uber 的服务迁移策略。

然而，我们发现真正能驱动采用的做法基本上和这个相反。真正有效的是平台工程和传统产品工程的结合：

（产品工程）找到一个充满挑战或潜力巨大的工作流（产品工程）与领域专家紧密合作，把第一个版本做可用（平台工程）确保这个可用的方案能被使用它的团队扩展（两者共同）以采用情况作为问题-解决方案匹配度的指标，否则就调整

以下是一些我们在内部取得 traction 的项目例子：

编写软件时使用有效的 AGENTS.md 文件来指导测试、类型检查和 linting 通过聊天和 IVR 处理初始客户问题 路由聊天机器人，将问题引导到解决问题、提供答案，或通知正确负责人 Incoming ticket 的 issue triaging：打标签并分配给合适团队 对常规合规和法律问题提供实时的初步反馈（例如那些频繁出现且变化不大的问题） 拉取 Git commits、Slack 消息等各种资源后，自动撰写每周优先事项更新

所有这些取得成效的项目，其公式都与“建一个平台，他们自然会来”完全相反。它需要有构建 AI Agent 经验和使用 AI 工具经验的人深度参与合作。在重要或接近生产的工作流中，有效采用 AI 的学习曲线仍然相当陡峭。

配置 Agent

使用强大工具的 Agent 代表了一个复杂的配置问题。 首先，暴露太多工具——尤其是 Prompt 作者自己都没有很好理解的工具——会让创建可靠工作流变得非常困难。例如，我们有一个 exit_early 命令允许提前终止 Agent，这在很多情况下非常有效，但也很容易把 bot 搞坏。类似地，我们有一个 slack_chat 命令允许跨频道发消息，这能支持多种有用工作流（比如把一个频道的问题 warm-handoff 到更合适的频道），但也可能造成 spam。 其次，工具越强大，就越可能引入复杂的安全场景。

解析外键

说起来有点好笑，但实际中严重影响轻松编写有效 Prompt 的一件事，是如何方便地写出类似 @Will Larson 这样的文本，然后把它正确转换成 <@U12345> 或者对应 Slack 用户、频道、用户组的正确标识符。Jira 组、Notion 页面和数据库等也存在同样的问题。

这是一个很好的例子，说明集中管理 Prompt 为什么有用。我自己已经习惯手动拉取唯一标识符，但很明显大多数其他人并不适应。 最终我们开发了三个 Slack 解析工具：slack_lookup，接受一个引用列表进行查找；slack_lookup_prefix，查找所有以给定前缀开头的 Slack 实体（例如找出所有以 @oncall- 开头的频道或组，而不需要在 Prompt 里硬编码列表）；以及 slack_search_name，用字符串距离来寻找可能的匹配（同样对处理拼写错误很有用）。

如果这听起来令人困惑，很大程度上是因为 Slack 没有暴露适合这种查找的相关 API。Slack 的 API 希望用 ID 来获取用户、组和频道，因此你必须自己维护这些条目的缓存才能进行查找。查找过程本身，尤其是针对用户，也很麻烦。Slack 用户至少有三种可能的引用方式：user.profile.display_name、user.name 和 user.real_name，但对任何一个用户来说都只有部分是设置好的。 据我所知，正确的逻辑是：先尝试匹配 user.profile.display_name，如果存在就用它；然后是 user.name，最后是 user.real_name。如果你只是取第一个匹配其中之一的用户，在某些场景下会选错人。

除了为 LLM 提供解析名称的工具外，我还为每个响应增加了一个最终的强制检查，确保返回的引用都指向真实存在的条目。如果不是，我会把无效的那些注入到上下文窗口中，并用仅包含实体解析工具的 Agent 再跑一轮。 这听起来很荒谬，但只有做到这一步，事情才真正开始稳定工作。

顺便说一句，我之前对这些截图感到尴尬，今天早些时候我已经为 Notion 页面和数据库做了和之前对 Slack 一样的改进。

格式化

与外键解析类似，Slack 的 mrkdwn 版 Markdown 和 JIRA 的 Atlassian Document Format 也存在类似问题：它们都非常严格。

调用这些 API 的工具现在都有严格的格式化指令。这些指令以前分散在各个 Prompt 里，但后来它们开始出现在每个 Prompt 中，我就知道必须把它们纳入 Agent 框架本身，而不是强迫每个 Prompt 作者都理解这个问题。

我猜测我需要增加一个类似实体解析的验证步骤，在此之前，我仍会遇到少量虽然不频繁但很烦人的渲染问题。 老实说，我个人并不介意渲染问题，但这会给其他使用 Agent 的人带来很多不确定性，因此我认为解决问题是必要的。

日志和调试

目前，所有日志（尤其是工具使用日志）会被发送到两个地方。首先是 Datadog，用于完整的日志可见性。其次，或许对非工程师更有用的是，它们会被发送到一个 Slack 频道 #ai-logs，让大家看到使用了哪些工具以及对应的（可能被截断的）参数。

长期来看，我设想会通过一个专用的内部 Web UX 来展现，但总体上我发现那些 actively 开发 Agent 的人相当愿意忍受一点粗糙。而那些不直接开发 Agent 的人其实并不关心，他们只希望每次都完美工作，也不会花时间去看日志。

目前最大的差距：访问用户范围 MCP 服务器的通用平台

我目前看到的最大的内部机会，是如何让非工程师获得类似于本地运行 Claude Code 并接入他们所有喜欢的 MCP 服务器的体验。 我一直希望 ChatGPT 或 Claude.ai 能提供这个功能，但它们还没有真正做到。Claude Desktop 比较接近，但配置起来有些 messy，我们需要一个能让公司每个人都容易自定义并每天使用的工具。

我还在寻找合适的工具。如果你有任何好的建议，我们能比较确信它在两年后还会存在，并且不需要把大量内部数据发送给一个非常早期的公司，我很乐意听听！

下一步是什么？

写一个好的结论通常应该以一个有力的轶事开头，以新的方式照亮你的核心论点。我不确定自己能否达到这个标准，但对我来说最重要的四个想法是：

我们仍处于 AI 采用的非常早期阶段，因此把重点放在学习速度上，比其他任何事情都更有价值。如果你想领导内部 AI 计划，你必须亲自使用这些工具，而且不只是用 ChatGPT，而是只用 LLM API 去构建你自己的工具调用 Agent。我的经验是，真正的问题上的真实 AI 采用，是领域上下文、AI 工具领域经验和传统 IT 问题的复杂混合。我对任何不同时锚定这三者的内部 AI 采用计划都深表怀疑。这也是早期公司的优势，因为你经常能在一个人身上，或者最多两个人身上，同时找到这三方面的能力。在大公司里，你需要三个不同的组织一起做这件事，这客观上非常困难。我认为模型选择很重要，但在任何给定时刻，你只需要 2-3 个模型，而且会有人直接告诉你当下那 2-3 个模型是什么。例如，GPT-4.1 在快速遵循规则方面就特别出色，它是大多数对延迟敏感的 Agent 的绝佳选择。

我很好奇其他人都在发现什么！
