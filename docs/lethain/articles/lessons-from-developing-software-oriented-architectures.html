开发面向服务的架构

2014-06-01 · 阅读原文

在过去四年里，我一直致力于推出和维护面向服务的架构，希望自己在这方面积累的经验教训足够多，能算得上有些心得。这篇文章就是我尝试分享一些实用经验。

我会先简要介绍自己参与过的两个不同的 SOA，以提供一些背景，然后再深入讨论从中吸取的教训和观察到的现象。

Digg

在 Digg，我们的 SOA 由多个 Python 后端服务组成，它们相互通信，同时也被 PHP 前端服务器和 Tornado API 服务器所使用。这些服务使用 Apache Thrift 来定义接口、客户端以及底层协议。我们有三个主要服务（用户、故事、评论），以及若干个较小的服务。

所有后端服务都部署在同一类机器上——前端服务器则是另一类——并且所有后端服务都从同一个 Git 仓库统一部署。

SocialCode

从 Digg 的 SOA 经验中吸取教训后，我们在构建 SocialCode 的 SOA 时做了一些调整。后端服务和 API 依然使用 Python，但我们放弃了 Thrift，转而选择 HTTP 作为协议。同时，我们将前端产品实现为 JavaScript 应用，让它们直接与 HTTP API 通信，从而使浏览器成为原生的 API 客户端。

各个 API 被隔离到独立的服务器上，以便解耦调试和扩容；它们拥有独立代码库，并可独立部署。

有了这两个不同方法的对比，是时候来梳理一下在开发和维护这些系统过程中学到的经验教训了：

SOA 是为了扩展团队规模

SOA 并不是万能药，相反，它会显著增加架构的复杂性。它也不是本质上的高性能架构，反而因为引入了更多组件而阻碍了性能。

它真正提供的唯一价值，是为大型团队提供一种有效的协作抽象，通过两种机制实现：定义清晰的接口可以降低沟通和破坏成本；将内部实现隐藏在接口之后，使得团队可以在不增加跨团队协调成本的情况下，逐步投入精力提升质量（只要不修改接口，你就可以重写内部实现以获得各种改进，而不会影响 API 的客户端）。

这些优势对大型团队而言能发挥巨大作用。

对于非常小的团队，它们未必能提供太多价值。我的直观感受是，小团队如果通过转向 SOA 获得了巨大的性能提升，那么他们通过任何系统的重写或优化可能也能获得同样的收益，在这种情况下 SOA 反而有点像转移注意力的红鲱鱼。

采用 SOA 需要缓慢推进

如果不应该一开始就采用 SOA，那该如何过渡到 SOA 呢？答案是“缓慢而谨慎地进行”。你要么是在一次完整的重写中完成迁移——祝你好运！——要么就是从现有的单体架构开始逐步过渡。

如果你运营的是一家成功且持续增长的公司，需要在开发新功能和基础设施投入之间分配时间，那么增量迁移很可能就是你的策略。

从添加简单且无争议的服务开始，比如用户身份和认证服务，在添加下一个服务之前，先将每个服务全面推广到所有应用中。然后再继续添加下一个、下一个，直到达到期望的一致性。（早期可能只需要几个服务。不要害怕慢慢来。）

在迁移过程中，一个值得考虑的有趣模式是：创建新的服务 API，但让它先共享现有的数据库，让现有客户端逐步迁移到新 API。一旦它们完全迁移到新 API（此时仍在使用同一个旧数据库），再迁移到独立的数据库。特别是在面对四五个不同团队且开发进度各不相同的情况下，这种技术能帮助你在漫长的切换过程中避免数据不一致的问题。

协议很重要

从 Digg 到 SocialCode，我们做出的最重要的决策之一，就是从 Thrift 协议切换到 HTTP。这不仅让浏览器能够成为直接使用 API 的原生客户端，更重要的是，它让调试和实验变得更加容易，因为大多数软件开发者都非常熟悉 HTTP 和 HTTP 服务器，而熟悉 Thrift 的人相对较少。（这也让他们能够复用已有的经验来优化和调试 Web 服务器及请求。）

另一方面，Thrift 具有极强的自描述性，这使得它在使用上可能比许多 HTTP API 更令人愉快（我们曾使用 tastypie 来创建一致的 API，效果非常好，但它的 API 和数据结构仍然比使用 Thrift 构建的同类 API 更加隐式和“魔法”）。

根据你所使用的语言，Thrift 和 HTTP 在“每小时优化所能获得的性能提升”上会有所不同。对于 Python，我发现使用 HTTP 更容易获得高性能，主要是因为其生态系统极为健壮，而 Python 的 Thrift 服务器并未获得社区同等程度的性能投入。反之，我很容易想象，对于更成熟的 Thrift 实现（比如 Java 实现），Thrift 协议固有的紧凑性可能会带来优于 HTTP 的性能。

最后一点需要考虑的是，即使使用 HTTP，也不会免费获得浏览器支持。如果你希望允许 Web 浏览器直接访问你的 API，那么每一个 API 端点都需要实现请求认证和授权机制。这完全可行（举个例子：我们正在这么做），但需要投入一定的时间和思考，而不能像以前那样把 authn 和 authz 卸载到授权层（在 Digg，这是由我们的 PHP 和 Tornado 服务来完成，它们对请求进行认证授权，然后作为可信用户去调用内部 API）。

笨拙的 API 客户端，还是聪明的 API 客户端

紧接着选择 SOA 协议之后，就是决定使用哪种类型的 API 客户端来与你的 API 交互。大体上，这里存在一种权衡：使用复杂的客户端来尽可能隐藏复杂度（以牺牲控制力和感知度为代价换取易用性），还是使用笨拙的客户端来暴露底层 API 所有丑陋的细节（以牺牲“常规情况”下的实现速度为代价换取控制力和感知度）。

就我个人而言，我强烈支持使用笨拙的 API 客户端。

我认为聪明的客户端会鼓励工程师把 SOA 当成一个单体应用来对待，而这是一个具有泄漏性的抽象。在我们当前的环境中，即使是在同一个机房内，我们执行的每一次 API 请求也会因为 uWSGI 处理请求而带来大约 20ms 的开销（还不包括在 API 内部执行逻辑或查询所需的时间）。

这是一笔相当大的开销，不应该被抽象掉。

如果你和你的团队已经积累了丰富的 SOA 经验，那当然可以使用聪明的客户端。但如果你还没有，我倾向于认为，让大家先直面底层实现的成本是很重要的，直到你们能为这种新的开发方式建立起心智成本模型为止。

跨团队的热点是糟糕的服务

如果你的组织更多是通过自愿协作和布道、而不是行政命令来管理系统架构，那么阻止服务被采用的最简单方法，就是创建一个服务来统一多个团队正在积极实现的能力。

乍一看，这似乎明显是错的：当然应该避免重复实现相同的组件。

但在实践中，如果多个团队已经在实现类似的功能，并且都已承诺了各自的进度，那么试图强行统一实现很可能为时已晚，这会迫使其中一个或两个团队放弃自己项目的进度或设计。在各种实现都稳定之后，再以它们作为具体需求来构建共享服务，才是合适的时机。

把这条经验归类为“避免无谓的争论，从而更快地到达目的地。”

总的来说，我认为转向面向服务的架构，是将工程团队从大约五人扩展到二十人左右的重要阶段。它很可能也伴随着从寻找产品市场契合转向规模化发展成熟业务的过渡。

在写这篇文章的过程中，我还思考了以下几个问题：

还有哪些其他方法可以高效扩展工程团队？在创建优秀的 SOA 方面，还有哪些重要的建议？度量和监控可能是一个值得深入探讨的话题。

我还遗漏了什么？
