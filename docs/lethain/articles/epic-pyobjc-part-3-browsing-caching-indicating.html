将结果缓存到磁盘

接下来我们要为 metaweb.py 返回的结果添加一个简单的缓存层。它包含两种相对简单的情况，我们现在来分别考虑：处理有缓存的搜索，以及处理没有缓存的搜索。

处理有缓存的结果。当点击搜索按钮时，我们要检查一个缓存清单（一个字典，以搜索词作为 key，对应值是一个包含文件名和时间戳的二元组）。如果结果已被缓存，清单中就会有对应的 key，我们就能拿到那个二元组。首先检查时间戳是否超过一天。如果已经超过一天，我们就丢弃缓存的值，像没有缓存一样处理。否则，如果没有超过一天，就把 MWController 的 results 字段更新为缓存的数据，这些数据我们会根据二元组中的文件名从磁盘加载。处理没有缓存的结果。当我们搜索一个没有缓存的结果时，先确认它不在缓存中，然后通过 metaweb.py 获取数据，接着把新获取的结果存入缓存。最后我们将其当作有缓存的结果来处理。

为了支持这些情况，我们需要创建一个持久化的缓存清单，在程序关闭时保存到磁盘，在程序启动时从磁盘加载。你还记得我们在 MetaWindowAppDelegate 中实现的 applicationDidFinishLaunching_ 和 applicationWillTerminate_ 这两个方法存根吗？现在终于要用上它们了。

关于 PyObjC 中序列化选项的简短说明。

Python 的 pickle 模块可能是你见过的最简单的数据序列化方式。当然，你也可以在 Cocoa 中通过实现 NSCoder 类方法来实现类似功能，但代码量要多得多。

然而，pickle 无法序列化继承自 NSObject 的对象。这意味着它无法序列化任何 Cocoa 或 Objective-C 的类。虽然有些不便，但通常可以找到变通办法。

最简单的解决办法是将对象转换成原生的 Python 类型。例如，如果你有一个 NSMutableDictionary，只需要把它转成 Python 的 dict 再序列化（反序列化时再转回 NSMutableDictionary）。

不过最后，如果你发现自己正在处理一个特别庞大或复杂的继承自 NSObject 的类，可能还是直接使用 NSCoder 更好。最终你那些取巧的方案往往会变得足够复杂，让你觉得还不如直接用 NSCoder，所以不如现在就为将来的自己省点麻烦。

还要记住，还有其他持久化数据的方案，比如 CoreData 和 SQLite，它们提供了不同于传统序列化的替代方式。

关于 Objective-C 中修改器和访问器的简短说明。当你阅读（或编写）Objective-C 代码时，你会遇到比一生中写 Python 代码时多得多的访问器和修改器。这是一种非常实用的模式，尤其适合实现懒初始化或动态值。

除了这种模式本身的实用性之外，它在 Objective-C 中频繁出现还有一个原因：一个对象可以同时拥有同名的字段和方法（即字段和方法处于不同的命名空间）。这是受 Smalltalk 启发的方法调用语法带来的副作用，它能清楚地表明你是在访问字段还是调用方法：

不幸的是，随着 Objective-C 2.0 的出现，这种区分在一定程度上被模糊了。有了 ObjC 2.0 之后，Apple 引入了与 Python 的 property 非常相似的属性机制，现在已经无法一眼看出 myObject.name 到底是在访问一个字段，还是隐藏了访问器/修改器对。

新语法的支持者认为，如果你正确地封装了类并且不依赖实现细节，这种区分就无关紧要。但老一辈的开发者仍然为失去的优雅感到惋惜，直到今天，他们依然会在 Objective-C 1.0 的“坟前”献上鲜花。
