史诗级 PyObjC 教程第四部分：拖放功能与多 Nib 文件

2008-08-26 · 阅读原文

欢迎来到 Epic PyObjC 教程系列的第四篇。在教程的第三部分，我们重点完成了三个较小的任务：处理双击事件、将数据缓存到磁盘，以及添加进度指示器。

这一次，我们将聚焦于 Cocoa 应用开发中两个稍显棘手、但极其重要的模式。我们首先实现拖放功能，最后学习如何在程序运行时使用第二个 nib 文件来创建新窗口。

在第三篇文章中，我曾说会在本篇提供一份资源列表，但后来想到应该介绍使用第二个 nib 文件（理解它能大大拓宽你的 Cocoa 视野），我觉得这是一个真正值得深入的话题。如果把拖放、多 nib 文件和资源列表放在一篇文章里，内容就太多了。

如果你之前没有跟上进度，可以下载当前项目的 zip 压缩包。

既然这是我们在这个系列中的最后一曲，那就来点有趣的吧。

拖放功能：一种哲学，一种风格

我本想以自己长期对拖放概念的执着开始讨论，但在 Cocoa 和 PyObjC 领域，这其实是谎言。大约一年半前（别告诉招聘人员），当我刚开始接触 PyObjC 和 Cocoa 时，做出了第一个相当复杂的应用，并为此颇为自豪。我记得最清楚的两个批评是：不要使用金属质感外观（我至今仍未从反金属外观阴谋中恢复过来），以及“在两个列表之间传输内容，用拖放不是比双击更好吗？”

我当时大概咕哝了一些蹩脚的借口，说自己没做是因为它比想象中更难理解，但谁又真正需要拖放呢？

好吧，不管之前如何，现在我和你都需要拖放功能。拖放是少数几个你可以在用户界面上大胆实验、做出真正有趣事情的地方，而不会打破太多惯例导致用户咒骂你。拖放就是 Cocoa 编程中的西部荒野。

拖放的巨大潜力之所以没有被充分探索，仅仅是因为它并非必需。大多数应用都可以不用或只用很少的拖放功能，因此也就这么实现了。但是，我要说，这种情况该结束了！

使用拖放的方式有无数种直观、有趣且实用的方法。下面这份列表绝不全面，仅作为一个起点：

允许将文本和内容拖放到 Dock 图标上。这是促进应用间通信的绝佳方式。在 MetaWindow 中，我们可以让它自动搜索拖到 Dock 图标上的字符串。（我在这里写过一篇简短的实现细节文章。）让数据导出变得像拖放一样简单。假设你想通过邮件发送一份报告，如果能直接把表格拖到 Mail.app 中，让它自动转换为 PDF，那该多好？但如果你拖到的是纯文本邮件呢？那它可能会以文本格式导出数据。如果导出数据能始终这么简单，而且应用之间真正相互配合，那该有多棒？要善于根据上下文进行数据的拖放操作。如果用户正要输入一个电话号码，能用正则表达式从一段文字中自动解析出号码就太好了。如果拖进来的是一个电话号码列表，它能自动识别并全部添加进去，那就更好了。我们已经习惯了给应用提供严格格式的输入，但那些允许用户随意扔数据并自动处理细节的应用，真正有潜力让用户爱上它们。当然，我们必须让用户知道他们可以随意操作，因为他们已经被训练成计算机的秘书，除非你的应用解放他们，否则他们不会主动这么做。

总而言之，拖放就是 Cocoa 编程中的 Unix 管道。它是应用之间协作最简单、最无缝的方式，一旦我们开始发挥创意，它将开启一个充满意外组合和实用价值的新世界。

拖放功能：在搜索窗口中通过拖放搜索

在 MetaWindow 中，我们将实现两种拖放操作，首先是允许将文本拖入搜索窗口来进行搜索。不仅仅是搜索文本框，而是包含它的整个窗口。这样能创造更大的有效目标区域，使用起来也更快。

我们首先需要打开 MWController.py，创建一个辅助函数，它接受一个搜索字符串作为参数，然后执行搜索（同时更新文本框以提供视觉反馈）。我们需要这样做，因为接下来我们要子类化 NSWindow 来监听拖放操作，如果把搜索逻辑写在那个子类里，就得重复实现搜索逻辑。我们通过给 NSWindow 子类添加一个 IBOutlet，并将其连接到 MWController 的 search_ 方法来避免重复代码。

因此，我们在 MWController 中添加了 dragSearch 方法。

def dragSearch(self,searchString):
    self.textField.setStringValue_(searchString)
    self.search_(self)

dragSearch 其实只是把子弹装进 search_ 的枪膛，然后扣动扳机。

现在，我们需要创建一个新文件。前往“文件”菜单，选择“新建文件”（Command-N）。我们真正想子类化的是 NSWindow，但没有现成的模板，所以我们先创建一个 Python 的 NSObject 子类文件，然后根据需要修改它。将文件命名为 MWDragWindow.py，并将其拖到 Xcode 侧边栏的“Classes”分组中（纯粹为了组织目的）。

接下来——这个容易忘记但至关重要的步骤——打开 main.py，添加对 MWDragWindow 的 import，让它看起来像这样：

# import modules containing classes required to start application and load MainMenu.nib
import metaweb
import MetaWindowAppDelegate
import MWController
import MWDragWindow

现在打开 MWDragWindow.py 文件，我们可以开始工作了。

在文件顶部，你需要导入 from AppKit import * 和 import objc，让导入部分变成这样：

import objc
from Foundation import *
from AppKit import *

接下来我们要把 MWDragWindow 从继承 NSObject 改为继承 NSWindow。同时给它添加一个名为 controller 的 IBOutlet。

class MWDragWindow(NSWindow):
    controller = objc.IBOutlet()

继续，我们开始让它支持拖放操作。第一步是注册它将响应的粘贴板类型。在本例中，我们只想监听 NSStringPboardType，这是文本的粘贴板类型。

要注册拖放类型，需要调用对象的 registerForDraggedTypes_ 方法，并传入一个要监听的类型列表。通常最简单的方法是在 awakeFromNib 方法中完成，这会在对象初始化时被调用。

对于 MWDragWindow，代码非常简单：

def awakeFromNib(self):
    self.registerForDraggedTypes_([NSStringPboardType])

注意要给 registerForDraggedTypes_ 传递一个类型列表，而不是直接传入 NSStringPboardType。

关于用户自定义粘贴板类型的简要说明。

Cocoa 已经支持许多不同类型的粘贴板。我们正在使用 NSStringPboardType，但还有很多其他现成的类型可供选择：NSURLPboardType、NSColorPboardType、NSFilenamesPboardType、NSFileContentsPboardType 等等。

然而，有时你要拖放的内容超出了现有粘贴板类型的范围。在这种情况下，你可以创建自己的粘贴板类型。粘贴板类型实际上只是一个字符串，因此创建一个粘贴板类型就像创建一个模块级变量并将其导入到使用同一粘贴板的其他模块一样简单。

## Some Module A
MWRowPboardType = u"MWRowPboardType"
class MyWindow(NSWindow):
def awakeFromNib(self):
self.registerForDraggedTypes_([MWRowPboardType])

在另一个模块中使用它的方式如下：

from module_a import MWRowPboardType
class AnotherWindow(NSWindow):
    def awakeFromNib(self):
        self.registerForDraggedTypes_([MWRowPboardType])

通常，用户自定义的粘贴板类型只能在声明它的应用内使用，因为其他应用不会知道它的存在。不过，如果开发者主动公开他们的粘贴板字符串，那就不一定了。

现在 MWDragWindow 已经注册了 NSStringPboardType，我们还需要实现两个方法来告诉它如何处理传入的拖放操作。

第一个是 draggingEntered_，它用于决定用哪种视觉效果来表示正在进入的拖放。例如，如果你正在把文本拖入一个文本框，可能希望使用 NSDragOperationAdd；但如果你是在将对象链接在一起，则更适合使用 NSDragOperationLink。然而，最重要的操作可能是 NSDragOperationNone，当你拒绝一个传入的拖放事件时就返回它。

当你返回 NSDragOperationNone 时，就不会有任何视觉反馈，表示对象拒绝处理该拖放类型。这为用户提供了视觉提示，告诉他们应用/窗口/字段能接受哪些类型的数据。

在 MWDragWindow 中，我们这样实现 draggingEntered_：

def draggingEntered_(self,sender):
    pboard = sender.draggingPasteboard()
    types = pboard.types()
    opType = NSDragOperationNone
    if NSStringPboardType in types:
        opType = NSDragOperationCopy
    return opType

如果粘贴板包含 NSStringPboardType，我们就处理它，否则就不处理。我们使用 NSDragOperationCopy 的视觉效果，因为这是文本框响应 NSStringPboardType 时使用的效果，在不同拖放效果之间切换可能会让人感到不安（除非你想表示如果在不同位置释放会有不同行为，那样的话就完全合适）。

draggingEntered_ 负责接受或拒绝拖放，以及显示拖放时的视觉效果，但目前我们还没有处理传入拖放的内容。这是通过实现 performDragOperation_ 来完成的。

def performDragOperation_(self,sender):
    pboard = sender.draggingPasteboard()
    successful = False
    if NSStringPboardType in pboard.types():
        txt = pboard.stringForType_(NSStringPboardType)
        self.controller.dragSearch(txt)
        successful = True
    return successful

如果我们从 performDragOperation_ 返回 False，应用会视觉上表示拖放被拒绝——如果返回 True，则表示拖放成功——但真正处理传入数据的工作由我们自己完成。

这里我们只是调用 MWController 的 dragSearch 方法，传入粘贴板中 NSStringPboardType 类型对应的字符串，然后让 MWController 来处理后续工作。

最后要做的事情是打开 Interface Builder 并做一些修改，所以请打开 MainMenu.xib。

打开 Inspector，选择 Window (Window)，然后切换到第六个标签页。此时 Inspector 的标题会变为“Window Identity”。

在 Inspector 顶部“Class Identity”部分，在“Class”字段中把 NSWindow 替换为 MWDragWindow。然后在包含所有对象的窗口中，按住 Control 键，从 Window (Window) 拖到 Controller 上并释放。在弹出菜单中选择 controller。

现在把一些文本拖到窗口中，释放鼠标，它就会开始搜索，就像我们在文本框中输入文本并点击搜索一样。

拖放功能：通过拖拽导出数据

既然我们已经在窗口中实现了拖放，接下来我们要看看另一个常见的拖放场景：在 NSTableView 中实现拖放。

传统上，拖放操作是在 NSTableView 的 datasource 中处理的，但如果你还记得第二部分，我们还没有指定 datasource，所以知道处理方式会有所不同。事实上，我们将通过子类化 NSArrayController 类，并在 MainMenu.xib 中把控制器对象的类改为我们的自定义类来实现拖放功能。

让我们先在项目中创建一个新文件，从 NSObject 子类化，命名为 MWDragArrayController.py，并将其导入到 main.py 中，让 main.py 中的导入部分变成这样：

# import modules containing classes required to start application and load MainMenu.nib
import metaweb
import MetaWindowAppDelegate
import MWController
import MWDragWindow
import MWDragArrayController

现在回到 MWDragArrayController.py，我们把 MWDragArrayController 从继承 NSObject 改为继承 NSArrayController，同时从 AppKit 导入 NSStringPboardType。

from AppKit import NSStringPboardType
from Foundation import *
class MWDragArrayController(NSArrayController):
pass

让我们快速绕道一下，打开 Interface Builder 中的 MainMenu.xib。选择 Array Controller 实例，打开 Inspector，选择 Identity 标签页（第六个），将类从 NSArrayController 改为 MWDragArrayController。

然后，这个很容易忘记但非常重要的步骤：你需要选中 table view（不是包含它的 scroll view，所以要点击两次），并将其 delegate 和 datasource outlet 都连接到 Drag Array Controller。

保存并关闭 Interface Builder，然后回到编辑 MWDragArrayController.py。

令人惊讶的是，我们几乎已经完成了！我们只需要在 MWDragArrayController 中添加以下方法：

def tableView_writeRows_toPasteboard_(self,tv,rows,pb):
    arranged = self.arrangedObjects()
    data = ",".join([ arranged[x]['name'] for x in rows ])
    pb.declareTypes_owner_([NSStringPboardType],self)
    pb.setString_forType_(data,NSStringPboardType)
    return True

保存并构建应用，搜索一些内容，然后把表格中的一行拖出去。很酷吧，但有些问题：你无法拖到其他应用程序中。这非常不方便，也大大降低了拖拽的实用性。

要修复这个问题，打开 MWController，进入 awakeFromNib 方法，添加下面这行代码：

self.tableView.setDraggingSourceOperationMask_forLocal_(NSDragOperationCopy, False)

综合起来，MWController 的 awakeFromNib 方法是这样的：

def awakeFromNib(self):
    if self.tableView:
        self.tableView.setTarget_(self)
        self.tableView.setDoubleAction_("open:")
        self.tableView.setDraggingSourceOperationMask_forLocal_(NSDragOperationCopy, False)

现在保存并重新构建 MetaWindow。你应该能够把表格行中的内容拖到其他应用程序中了。

这就总结了我们在 MetaWindow 中对拖放功能的探索。我们不会讨论如何把数据拖入我们的表格视图，主要是因为我无法想象在当前场景下有什么合理的用途——我们把 Metaweb 返回的结果当作不可变数据来展示。如果 MetaWindow 以后扩展到支持修改数据，那么这种操作可能会有价值（比如作为一种导入数据的方式）。

使用第二个 Nib 文件

是时候开始探讨 Epic PyObjC 教程系列的最后一个主题了，这也是一个非常重要的主题：在同一个项目中使用多个 nib 文件。对于许多应用，你可以避免使用多个 nib 文件。例如，如果你看看 iTunes 处理播放列表的方式，默认情况下点击播放列表时，它只是在主窗口的列表中显示。

这用一个 nib 就能做到。没问题。但如果你双击一个播放列表，它会打开一个新窗口。而这一点，用单个 nib 是无法实现的（除非你用代码手动创建并填充窗口，虽然可行，但通常要多做很多工作）。

一旦你从简单应用升级到更复杂的应用，你不可避免地需要学习如何在同一个项目中使用多个 nib 文件——就像我们在本教程中看到的所有内容一样，一旦你坐下来认真去做，其实并没有那么难。

目前，当你双击一行时，它会在网页浏览器中打开该条目的页面，但如果能打开一个新窗口，向我们展示关于该条目的更多细节，那就更好了。目前我们只是浅尝辄止地展示了 metaweb.py 返回的数据，如果为每个结果专门分配一个窗口，我们可以展示多得多的内容。

我们将通过以下三个步骤将额外的 nib 集成到项目中：

创建一个继承自 NSWindowController 的自定义 Python 类，在初始化时传入特定行的字典。创建一个新的 nib 文件，我们称之为 RowWindow.xib，在其中将 File's Owner 的类设置为我们自定义的 NSWindowController 子类。更新 MWController 中的 open_ 方法，让它使用 RowWindow.xib 创建新窗口，而不是在浏览器中打开条目页面。

子类化 NSWindowController

首先，我们创建一个名为 MWRowWindowController.py 的新文件。最初它会继承自 NSObject，但我们将其父类改为 NSWindowController，并添加一个名为 rowDict 的字段。

class MWRowWindowController(NSWindowController):
    rowDict = None

然后像往常一样在 main.py 中导入它：

# import modules containing classes required to start application and load MainMenu.nib
import metaweb
import MetaWindowAppDelegate
import MWController
import MWDragWindow
import MWDragArrayController
import MWRowWindowController

就这样。

创建 RowWindow.xib

创建一个新文件，这次选择 Window XIB 模板，并将其命名为 RowWindow.xib。然后在 Interface Builder 中打开它。

首先，打开 Inspector 并选择 File's Owner，然后切换到 Identity 标签页，将其类从 NSObject 改为 RowWindowController。接下来在 nib 的窗口中创建一个 NSTextField，选中它，切换到 Bindings 标签页。

对于 Value 绑定，将其绑定到 File's Owner，在 Model Key Path 中输入 rowDict.name。

这是另一个使用 Cocoa bindings 来避免重复代码的例子。它们是你的好朋友。

最后，我们需要点击 File's Owner，并将其 window outlet 连接到 Window (Window)。

除了两个大问题

嗯……“完成”可能是个比较强的词。我们当前的实现存在两个明显的问题。首先是我们对 rwc 调用了 retain，但从未调用 release，因此没有让垃圾回收器释放那个窗口。

第二个问题是，如果你连续两次点击同一行，就会为那一行打开两个窗口。如果它能把已有的窗口带到最前面，而不是创建第二个窗口，那就优雅多了。

好消息是，解决这两个问题的方案是重叠的，而且不会花费太多时间。

首先在 MWController 中添加一个名为 rowCache 的字段，初始化为一个空字典。

class MWController(NSObject):
    tableView = objc.IBOutlet()
    textField = objc.IBOutlet()
    arrayController = objc.IBOutlet()
    indicator = objc.IBOutlet()
    results = []
    rowCache = {}

现在来解决“没有调用 release”的问题。

认识 dealloc

到目前为止，在我们探索 PyObjC 和 Cocoa 的旅程中，我们已经接触了许多 Cocoa 主题和概念：release、retain、Cocoa Bindings、NSArrayController 以及拖放。我要添加到你武器库的最后一个工具是 dealloc。dealloc 是在继承自 NSObject 的对象即将被垃圾回收器释放时调用的方法。这是你在那些被 retain 的引用变成内存泄漏之前最后一次清理的机会。

每个 dealloc 方法都有两个步骤（顺序非常重要）：

释放所有被 retain 的对象。调用父类的 dealloc 方法。

第二步很容易忘记，但它是导致内存泄漏的常见原因之一。

MWController 的 dealloc 方法将是这样的：

def dealloc(self):
    for key in self.rowCache:
        value = self.rowCache[key]
        value.release()
    super(MWController,self).dealloc()

以后你应该阅读《Cocoa 内存管理指南》，它是对深入内存管理时遇到的各种细微差别的全面介绍。
