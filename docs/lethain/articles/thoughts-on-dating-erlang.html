使用 Erlang 开发的一些思考

2008-04-30 · 阅读原文

最近我正在用 Erlang 开发一个项目，目前体验还算不错。这个项目需要搭建一个服务器来解析我自定义的数据包格式，下面是一些使用心得。

消息传递

在解析完收到的数据包后，服务器需要将解析结果写入数据库。由于各种原因，我希望整个系统中只有一个进程负责和数据库（一个 SQL 数据库，可能是 Postgres，应该不会是分布式数据库）打交道。以前我用 Python 尝试过类似做法，结果很快就变得一团糟。幸运的是，Erlang 的消息传递机制让这件事实现起来非常轻松。

我编写了一个循环的数据存储进程，它会持续等待传入的消息，然后将数据存入数据库。

%% Listens for messages, and then stores contained data.
data_store() ->
    receive
	{store, Packet} ->
	    store(parse(Packet))
    end,
    data_store().

接着我需要在启动代码中注册这个进程，以便其他进程能够找到它并与之通信。

register(data_store_PID, spawn(fun() -> data_store() end)).

有了这样的架构后，任何需要存储数据的进程只需向数据存储进程发送一条消息即可，队列管理和并发控制全部由 Erlang 底层处理，完全不需要 mutex 或 semaphore。

handle_data(Data) ->
    data_store_PID ! {store, Data}.

消息传递为（某些类型的）并发问题提供了一种透明的解决方案，在经历过传统的线程编程后，这简直像一股清新的空气。当然，这种实现的简洁性很大程度上得益于 Erlang 的消息传递是基于进程（process）而非线程（thread）。两者的核心区别在于：进程之间不能共享数据，而线程可以共享数据。

如果你还没有太多正面、愉快的并发编程经历，我强烈推荐你试试 Erlang，哪怕你并不打算严肃地使用它。当你看到并发可以如此简单且高效地工作时，那种感觉真的很棒。

简洁的服务器循环

在网上搜索“Erlang socket tutorial”或者“Erlang gen_tcp man”，你会找到一些几乎一模一样的示例代码，它们实现了一个相当强大的服务器循环。（我最早找到的那个示例在这里，我在它的基础上做了少量修改，下面展示的代码中的所有错误都由我自己负责。）

-define(TCP_OPTIONS,[list,{packet, 0},{active, false}]).
listen(Port) ->
    LSocket = gen_tcp:listen(Port,?TCP_OPTIONS),
    accept(LSocket).
accept(LSocket) ->
case gen_tcp:accept(LSocket) of
{ok, S} -> spawn (fun() -> handle(S) end);
Other -> ok
end,
accept(LSocket).
handle(Socket) ->
case gen_tcp:recv(Socket, 0) of
{ok, Packet} ->
data_store_PID ! {store, Packet};
{error, Error} ->
io:format("error: wn", [Error])
end.

这是一个相当精简的服务器，但功能却非常强大。它循环等待新的连接到来，每当有新连接时就创建一个新的进程来处理它。由于 Erlang 的进程要比大多数语言的线程实现轻量得多， 这实际上是一个切实可行的方案，而非遥不可及的空想（我一边说一边默默交叉手指，而且没有任何实际数据支持）。

字符串即列表

Erlang 没有针对字符串的专门工具或支持，字符串本质上只是数字列表。这意味着你可以使用所有操作列表的函数来处理它们（prefix、nthtail、map、foreach、fold，应有尽有）。但考虑到每个字符要占用 8 字节内存，它在字符串处理上的表现并不算特别强。不过，它当然是可以胜任的。

在我的项目中，服务器需要从收到的数据包中解析出数据。我必须承认，大学时修的那门网络课程在心理上为我做好了准备——当时我们就是用有限状态机来解析数据包，而不是用正则表达式之类的更简单的方法。

下面是一段解析代码的片段，它负责构造一个以两个换行符“\n\n”结尾的 token。

-define(NEWLINE, 10). %% Ascii value for '\n'.
next_value_token(Packet) ->
next_value_token(Packet, []).
next_value_token([], Acc) ->
{not_found, lists:reverse(Acc)};
next_value_token([First, Second|Rest], Acc) when First == Second ->
case First of
?NEWLINE -> {lists:reverse(Acc), Rest};
Other -> next_value_token([Second|Rest], [Other|Acc])
end;
next_value_token([First|Rest], Acc) ->
next_value_token(Rest, [First|Acc]).

我当然不会说这段代码一眼就能看懂，但它确实展示了 Erlang 的模式匹配（pattern matching）如何让你相对轻松地描述复杂逻辑（我强烈怀疑存在比我写的更清晰的写法，我这个版本多少有点初期混乱的痕迹）。

把这段代码大致翻译成 Python（忽略“先反向构建链表再翻转”这种函数式编程习惯），结果会大不相同。

def next_value_token(packet, acc=[]):
    if packet == []:
        return ('not_found', acc)
    first = packet[0]
    second = packet[1]
    if first == second == "\n":
        return (acc, packet[2:])
    else:
        acc.append(first)
        return next_value_token(packet[1:],acc)

所谓大不相同，就是指它更容易阅读。公平地说，我在写 Erlang 版本时故意没有使用变量（给自己施加限制以寻找更优雅的解法，但目前还没完全成功）。不过，我实际用 Python 写这个功能时会更简单（其中一个重要原因是缺乏尾递归优化，让上面的方案更像一个玩具而非实用工具）。

def next_value_token(packet):
    index = packet.find("\n\n")
    if index == -1:
        raise MalformedPacketException(packet)
    return (packet[index:], packet[:index+2])

Python 版本明显简单得多，如果用正则表达式实现可能会稍微啰嗦一点，但可读性也差不多。我就不继续强调这一点了（意思是我不会再贴 Objective-C 的版本了），因为我相当确定这段 Erlang 代码的丑陋主要是我自己的问题，最坏的情况也只是它与函数式编程风格不太契合而已。

一些小牢骚

每当我学习一门新语言时，总有两件事让我持续感到恼火，而 Erlang 和绝大多数其他语言一样没能免俗：大多数语言都会发明自己的一套字符串格式化 mini-language，以及一套列表推导式的 mini-language。我知道有人会说，如果我们停止寻找更好的方案，就会失去一些东西，但我希望读者想想 Perl 的正则表达式。它们很棒，不是吗？更棒的是，你只需要学会一次，就能在几乎所有语言里使用这个强大的工具，难道不是更好吗？

如果列表推导式和字符串格式化的 mini-language 也能在不同语言间标准化，让它们同样成为我们跨语言的强大概念工具库的一部分，岂不是更好？

继续前行

大约一年前我曾短暂接触过 Erlang，但最终一无所成。当时我觉得它的语法有点刺眼，文档也很糟糕，等等等等。从那时到现在，Erlang 本身并没有发生根本性的改变，但这次重新接触却让我感觉愉快得多。语法不知不觉就适应了，函数式编程也没有让我感到困扰，学习曲线也并不算陡峭。

我可能会说自己终于为 Erlang 做好了准备，但这话听起来有点俗气。我真正想说的是：Erlang 是一门值得去了解的有趣语言，对于某些特定问题领域，它能提供极其优雅的解决方案。它不会像花几周时间学 Scheme 那样彻底改变你的世界观，但也许有时候，我们的世界需要的改变也就这么多。

  1. 没有可变共享数据这一点确实有点奇怪，但并没有给我造成太多麻烦。我不能说自己在严格的函数式编程风格下开发过大型系统，但熟悉这种思维方式后，我通常发现同样的事情还是可以完成，只是实现方式不同而已。一旦找到，函数式的解决方案往往更令人愉快，但我相信在某些情况下，这种限制带来的不是优雅，而是额外的复杂性。
  2. 它们（指 Erlang 进程）比 Java 线程以及任何通过原生线程实现并发的编程语言（比如 SBCL 等）的线程都要轻量得多。我很好奇它们与 Stackless Python 的线程或 Ruby 的 green threads 相比如何。作为有点相关的趣闻，Scala 的消息传递实现——其语义模仿了 Erlang——实际上使用固定数量的线程（我记得是四个，但可能记错了）来模拟轻量级特性。当然，在使用原生线程的语言中也可以实现类似的东西，只要有人愿意花精力去编写相应的库。（我自己尝试写过一个 Common Lisp 的 actor 库，后来不了了之，偶尔仍觉得可惜。）
  3. 我看到有两个因素阻碍了这一点。首先，目前还没有出现一个在字符串格式化或列表推导式上明显碾压其他方案的实现。就我个人而言，我觉得 Python 的列表推导式已经相当优秀（如果采用类似 Common Lisp 的 Loop mini-language，我大概会泪流满面）。至于字符串格式化，没有哪个方案让我觉得特别出色，但如果能标准化到其中一种，也会大大减轻我的痛苦。
