关于使用 Erlang 开发的一些想法

2008-04-30 · 阅读原文

最近我正在一个项目中使用 Erlang，目前体验还算不错。这个项目需要搭建一个服务器，用于解析我自定义的数据包格式，下面是一些使用过程中的感想。

消息传递

在解析完收到的数据包后，服务器需要将解析后的数据写入数据库。由于各种原因，我希望尝试让整个系统中只有一个进程负责与数据库（一个 SQL 数据库，很可能是 Postgres，而且不是分布式数据库）进行交互。我以前用 Python 尝试过类似的做法，结果很快就变得一团糟。幸运的是，Erlang 的消息传递范式让这个需求实现起来非常简单。

我实现了一个循环运行的数据存储进程，它持续等待传入的消息，然后进行存储操作。

接着，我需要在启动代码中注册这个进程，以便其他进程能够找到并与之通信。

有了这个设置之后，任何需要存储数据的进程只需向数据存储进程发送一条消息即可，队列管理、并发处理全部由系统负责，完全不需要使用互斥锁或信号量。

消息传递为（某些类型的）并发问题提供了一种透明的解决方案，在经历过传统的线程编程之后，这简直让人耳目一新。当然，这种实现的简洁性很大程度上得益于 Erlang 的消息传递是基于进程（process）而非线程（thread）。两者的核心区别在于：进程之间不能共享数据，而线程可以共享数据。

如果你还没有太多积极的并发编程经验，我强烈推荐你试试 Erlang，哪怕你并不打算严肃地使用它。当你看到并发编程竟然可以如此简单且高效时，那种感觉真的很棒。

字符串即列表

Erlang 没有专门的字符串类型和工具，字符串本质上就是数字列表。这意味着你可以使用所有操作列表的函数来处理它们（prefix、nthtail、map、foreach、fold，应有尽有）。但考虑到每个字符要占用 8 个字节的内存，它在字符串处理方面的表现并不算出色。不过，完成任务是完全没问题的。

小吐槽

每当我学习一门新语言时，总有两个问题让我持续感到烦躁，而 Erlang 和其他大多数语言一样也没能幸免：我不太喜欢大多数语言都自己发明一套字符串格式化的迷你语言，同时还各自搞一套列表推导式的迷你语言。我知道有人会说，如果我们停止探索更好的方案，就会失去一些东西，但我希望读者想想 Perl 的正则表达式。它们很强大，对吧？更棒的是，你只需要学会一次，就能在几乎所有语言里使用这个强大的工具，不是吗？

如果列表推导式和字符串格式化这些迷你语言也能在不同语言间标准化，让它们同样成为我们跨语言工具箱中的强大概念，那该有多好？

继续前进

大约一年前，我曾短暂接触过 Erlang，但没坚持下去。当时我觉得它的语法有点刺眼，文档也不好，等等等等。从那时到现在，Erlang 本身并没有发生根本性的变化，但这次再次尝试却让我感觉愉快得多。语法不知不觉就适应了，函数式编程也没有让我感到困惑，学习曲线也没有特别陡峭。

我可能会说自己终于为 Erlang 做好了准备，但这话听起来有点矫情。我真正想说的是，Erlang 是一门值得去了解的有趣语言，对于某些特定问题领域，它能提供优雅而精妙的解决方案。它不会像你花几周时间学习 Scheme 那样彻底改变你的世界观，但有时候，我们的世界也许只需要这样的改变就足够了。
