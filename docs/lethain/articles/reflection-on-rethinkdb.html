对 RethinkDB 的思考

2012-12-02 · 阅读原文

自从第一次读到 RethinkDB 的相关资料，我就一直想试用一下。这个周末我终于付诸行动，快速搭起了一个非常简单的示例，用 RethinkDB 来存储爬取的页面和提取的元数据。

这篇文章包含了一些初步的、不够严谨的思考。

每款数据库都有其适合的定位

过去五年左右的时间里，不少开源 NoSQL 数据库声名鹊起：Cassandra、CouchDB、MongoDB、Voldemort 等等。在我看来，RethinkDB 汲取了 Cassandra 和 CouchDB 的一些最佳理念。

来自 Cassandra 的目标包括：

  1. easy system maintence,
  2. simple sharding, and
  3. reaching beyond a key-value store to a key-value-plus store.

来自 CouchDB 的理念则有：

  1. storing data in JSON documents,
  2. the ability to create indexes against those JSON documents,
  3. JavaScript powered map-reduce against your data, and
  4. feature-rich UI for interacting with the database.

RethinkDB 还避开了一些代价高昂或概念上很强大、但最终影响有限的功能，例如：将 HTTP API 作为核心特性、将 Java 作为核心特性、将 Erlang 作为核心特性、将“同步优于一致性”作为特性，以及“必须把所有数据放在一台服务器上”作为特性。

使用 Python 客户端

RethinkDB 的 API 令人印象深刻且文档详尽。在构建这个简短示例的过程中，我了解了其中一小部分功能及其 Python 驱动程序。在此过程中遇到了一些问题，或许值得改进。

我最大的挫败感在于，推荐的使用方式会让客户端在幕后隐式地管理连接，你必须阅读一部分源代码才能搞清楚如何用更安全的方式来操作（当然，这也不是什么世界末日）。

示例中推荐的写法是：

:::python
from rethinkdb import r
r.connect('localhost', 28015)
r.db_create('crawl').run()
r.db('crawl').table_create('pages').run()

但在这种情况下，默认会在不同模块间共享同一个连接，这意味着你的连接可能会被其他人悄无声息地关闭，而你对此一无所知。我认为如果初始化时出现竞争条件，还可能导致默认数据库被意外修改，从而产生一些难以调试的奇怪现象。

如果不想共享连接，要实现同样的功能，写法明显没那么优雅：

:::python
from rethinkdb import r
from rethinkdb.net import Connection
conn = Connection("localhost", 28015, "crawl")
r.db_create('crawl').run(conn=conn)
r.db('crawl').table_create('pages').run(conn=conn)

需要特别提醒的是，如果其他代码使用了 from rethinkdb import r 的方式，它就会通过模块变量知道你创建的连接，并直接使用它。根据我快速阅读源代码的经验，只要有代码采用默认做法，你就面临一定的混淆风险。如果可能，我建议重写 Python 客户端，彻底移除这个快捷方式，或者至少修改为只有在使用快捷方式时才更新 rethinkdb.net._last_connection，手动创建连接时则不更新。

我之所以比较重视显式暴露连接池机制，是因为根据你是使用线程、多进程还是 gevent，所需的连接管理方式可能完全不同。而用错方式往往会以系统性能或开发者的心智模型为代价。

我在客户端遇到的另一个问题是，异常的粒度不够细，导致客户端很难根据抛出的异常做出针对性的反应，除非你事先就知道可能抛出哪种错误以及原因。

from rethinkdb import r
from rethinkdb.net import ExecutionError

# if a primary key you retrieve doesn't exist, ExecutionError
try:
    found = self.client.db(self.db).table(self.html_table).get(url).run()
except ExecutionError, ee:
        print ee

# if a db already exists, ExecutionError
try:
    self.client.db_create(self.db).run()
except ExecutionError, ee:
    print ee

# if a table already exists, ExecutionError
try:
    self.client.db(self.db).table_create(table).run()
except ExecutionError, ee:
    print ee

拥有各自独立的异常（继承自一个公共的父异常）会带来很大帮助，尤其是在某些失败可以合理重试、而另一些则不行的情况下。

在合理错误处理这个话题上，db_create、table_create 和 get 操作在失败时会抛出 ExecutionError，而插入操作却使用返回状态码：

:::python
success = self.client.db(self.db).table(
    self.page_table).insert({'id': 'hi'})
if 'first_error' in success :
    raise Exception("num errors %s, first error %s" % \
                    (success['errors'], success['first_error']))

我当然理解为什么插入操作更适合用返回状态码（因为可能同时插入多条文档，其中部分成功、部分失败），但我不太喜欢这种不一致的情况。或许可以考虑让抛出异常的接口也支持返回类似插入操作的状态码。

我真正想要的功能

第一次使用之后，可以肯定地说我非常喜欢 RethinkDB。它几乎满足了我大部分常规需求：

  1. it’s a scalable key-value store,
  2. it can index its key-value data,
  3. you can do some lightweight analysis across your dataset.

RethinkDB 目前缺少两个功能——当然，任何系统都必须有所取舍，否则就会什么都做却都做不好——如果加上这两个功能，它就非常适合我之前参与过的那些较大规模的应用了。

首先是与更完整的数据仓库集成。我希望能有一种方式将 RethinkDB 中的数据对接到 HDFS，让分析师和数据科学家能够使用他们熟悉的工具来处理这些数据。

其次——这已经是路线图上的功能了——是二级索引。目前可以通过创建更多表来模拟（这正是早期使用 Cassandra 的做法），但原生支持二级索引无疑能节省大量时间（在我看来，这也是 MongoDB 如此受欢迎的关键“魔法”之一）。

总的来说，只要可扩展性和性能在更大规模数据量下表现符合预期，那么即使没有上面提到的额外特性，我也很愿意在新项目中转向 RethinkDB。我非常希望它的性能和稳定性能够如承诺的那样出色，那将是一个非常棒的选择。
