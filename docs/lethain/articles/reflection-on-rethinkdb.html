对 RethinkDB 的思考

2012-12-02 · 阅读原文

自从第一次读到 RethinkDB 的介绍，我就一直想着要试一试，这个周末终于动手了。我快速搭建了一个非常简单的示例，使用 RethinkDB 来存储爬取的网页和提取的元数据。

这篇文章记录了一些初步的、不够深入的想法。

每款数据库都有其合适的定位

在过去五年左右的时间里，不少开源 NoSQL 数据库都声名鹊起：Cassandra、CouchDB、MongoDB、Voldemort 等等。在我看来，RethinkDB 吸取了 Cassandra 和 CouchDB 的一些最优秀的理念。

来自 Cassandra 的目标包括：

简便的系统维护、简单的分片，以及超越单纯键值存储的“键值增强型”存储。

来自 CouchDB 的理念则有：

以 JSON 文档形式存储数据、能够针对这些 JSON 文档创建索引、使用 JavaScript 实现数据的 map-reduce，以及提供功能丰富的 UI 来与数据库交互。

RethinkDB 还避开了那些项目中一些代价高昂或概念上强大但实际影响较小的特性，比如：将 HTTP API 作为一大卖点、将 Java 作为一大卖点、将 Erlang 作为一大卖点、优先考虑同步而非一致性、必须把所有数据塞进一台服务器等。

使用 Python 客户端

RethinkDB 的 API 设计出色且文档详尽。我在构建这个简短示例的过程中，初步了解了其中一小部分功能及其 Python 驱动。在此过程中发现了一些可能值得改进的问题。

让我最郁闷的是，官方推荐的使用方式会在背后自动管理连接，你必须去翻看一些源代码才能搞清楚如何用得更安全（当然，这也不是什么世界末日）。

示例中推荐的写法是：

:::python
from rethinkdb import r
r.connect('localhost', 28015)
r.db_create('crawl').run()
r.db('crawl').table_create('pages').run()

但这样就默认在不同模块间共享同一个连接，意味着你的连接可能会被其他人悄无声息地关闭。我认为如果你在初始化时存在竞态条件，还可能导致默认数据库被意外修改，从而产生一些难以调试的诡异现象。

如果想实现同样的功能但不共享连接，写法就会明显不够优雅：

:::python
from rethinkdb import r
from rethinkdb.net import Connection
conn = Connection("localhost", 28015, "crawl")
r.db_create('crawl').run(conn=conn)
r.db('crawl').table_create('pages').run(conn=conn)

需要提醒的是，如果其他代码使用了 from rethinkdb import r 的方式，它就会通过模块变量知道你的连接，并直接借用它。根据我快速阅读代码的结果，只要有任何代码使用了默认做法，你就面临一定的混乱风险。如果可能，我建议重写 Python 客户端，彻底移除这个快捷方式，或者至少修改为仅在你使用快捷方式时才更新 rethinkdb.net._last_connection，而手动创建连接时不要更新它。

我之所以比较坚持要显式暴露连接池机制，是因为不管你是用线程、多进程还是 gevent，不同场景下需要的处理方式不一样，而用错方式往往会牺牲系统性能或开发者的心智模型。

我在客户端中遇到的另一个问题是，抛出的异常不够细粒度，因此客户端很难根据具体异常类型做出恰当反应，除非你事先就知道可能会抛出哪种错误以及原因。

from rethinkdb import r
from rethinkdb.net import ExecutionError

# if a primary key you retrieve doesn't exist, ExecutionError
try:
    found = self.client.db(self.db).table(self.html_table).get(url).run()
except ExecutionError, ee:
        print ee

# if a db already exists, ExecutionError
try:
    self.client.db_create(self.db).run()
except ExecutionError, ee:
    print ee

# if a table already exists, ExecutionError
try:
    self.client.db(self.db).table_create(table).run()
except ExecutionError, ee:
    print ee

拥有明确的异常类型（继承自同一个父异常）能极大改善这种情况，尤其是在某些失败可以合理重试而另一些则不能的时候。

同样在合理错误处理这个主题下，db_create、table_create 和 get 操作在失败时会抛出 ExecutionError，而插入操作却使用返回状态码：

:::python
success = self.client.db(self.db).table(
    self.page_table).insert({'id': 'hi'})
if 'first_error' in success :
    raise Exception("num errors %s, first error %s" % \
                    (success['errors'], success['first_error']))

我当然理解为什么插入操作使用返回状态码更合理（因为可能同时插入多条文档，其中部分成功、部分失败），但我不太喜欢这种不一致。或许可以把抛出异常的接口也改成类似插入那样的返回状态码形式。

我真正想要的功能

在第一次使用之后，可以肯定地说我相当喜欢 RethinkDB。它满足了我大部分日常需求：

它是一个可扩展的键值存储，能对键值数据建立索引，也能对数据集进行一些轻量级分析。

不过 RethinkDB 目前还缺少两项功能——当然，你必须有所取舍，否则系统就会什么都做却什么都做不好——如果加上这两点，它就会非常适合我之前参与过的大规模应用。

首先是与更完善的数据仓库集成。我希望能有一种方式将 RethinkDB 中的数据接入 HDFS，这样分析师和数据科学家就能用他们熟悉的工具来处理这些数据。

其次——这也是官方路线图上的功能——是二级索引。目前你可以通过多建几张表来模拟（早期的 Cassandra 就是这么做的），但真正的二级索引能节省大量时间（在我看来，这也是 MongoDB 如此受欢迎的重要魔法之一）。

总的来说，只要扩展性和性能在更大规模数据量下表现符合预期，我完全可以想象将新项目迁移到 RethinkDB 上，即使没有上面提到的额外特性也行。我非常希望它的性能和稳定性能如承诺的那样出色，那将会是一个非常棒的选择。
