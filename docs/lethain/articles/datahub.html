重写 Yahoo! BOSS Datahub

2019-08-31 · 阅读原文

2008 年，我对博客的理解就是：针对前沿技术狂轰滥炸式地输出内容，希望借此获得知名度、页面浏览量，或者至少能找到一份比 更好的工作。我先后用这种方式尝试过 PyObjC、Processing.js、Why the Lucky Stiff 开发的 在 OS X 上开始使用 Shoes，以及其他几个项目，程度各有不同。加入 JET 项目的旅程

这种方法效果还不错——密度、新颖度和时效性正是取悦搜索引擎相关性之神的蜜露——最终也帮我叩开了技术领域的第一份工作大门：加入 Yahoo!，参与 Yahoo! Build Your Own Search Service（简称 BOSS）项目。

BOSS 发布的那一周，我连写了多篇相关博客：1. 用 Django 构建自己的 Yahoo 搜索服务，2. 用 Python 为 Yahoo 的 BOSS 搜索食谱，3. 完善我们的 Django & BOSS 搜索服务，4. 用 BOSS Mashup 剔除 Hacker News 中的 Reddit 内容。发文量之大，以至于团队都感到疑惑，于是主动联系我讨论。

经过六个月的沟通、躲过几轮裁员、熬过招聘冻结期后，他们终于把我作为小时工承包商招了进来，我在东海岸远程工作。那时的我还非常青涩，但只要能重新获得医疗保险，我就已经迫不及待地想投入工作，做任何事情都行。

BOSS 的第一个版本允许通过 API 查询 Yahoo! 的搜索结果并对其进行重新组合。我加入团队时，这个版本已经在运行，我们刚刚开始开发第二个版本：允许用户提交自己的数据，然后同时查询用户数据和 Yahoo! 的结果，并将两者合并。从某种角度看，这和后来 Swiftype 的产品非常相似。

其实产品本身对我来说没那么重要，我只是很高兴能在科技公司工作。没人愿意写 YUI、Flash 和 APC 集成来显示文件上传进度？交给我！没人愿意碰前端，因为它既“low”又要在 Mozilla 1.5 和 IE6 之间解决跨浏览器兼容性问题，极其烦人？交给我！没人愿意去学怎么调试 Erlang 工作流管理器？还是交给我！

这个团队是只有在一家正在收缩的公司里、且其流程仍为高增长时期设计的情况下，才可能出现的奇特组合。团队中有三个人之前负责 del.icio.us，后来 Yahoo! 将其转入维护模式；另外十个人则在为一个 Vespa 的自定义扩展项目寻找内部客户，这一追逐已经持续了好几年。

你可以把 Vespa 理解为当时的 ElasticSearch，最接近的对比是 Solr。而那个叫 Hosted Vespa 的自定义扩展，实质上是一个运行在 Vespa 之上的外壳，为原本一直是单租户的系统提供了多租户能力。

Hosted Vespa 背后的技术实现，可能比一个被团队鼓吹多年的技术听起来要更加直白。你会创建一个包含若干字段的集合，大致如下：

int1, int2, ... intN
float1, float2, ... floatN
str1”, str2, ... strN

然后我们为每个用户的字段和底层 schema 建立映射，大致是这样的：

age => int1
name => str1
city => “str2

在查询和索引时，用户字段会被翻译成集合中的字段，而底层的 Vespa 实例则完全不知道自己正在为多个租户提供服务。如果真正被大规模采用，这套方案会面临很大挑战，但过度采用从来不是我们面临的核心难题。

新用户可以上传任意格式的 XML 文件，系统会将其送入我们的 Datahub 进行格式标准化，再把标准化后的数据发给 SchemaInference。后者通过对每个字段的值进行正则表达式匹配，来推断字段类型并映射到底层的 Vespa 字段。

随着 beta 用户越来越多，我们收到的文件也越来越大。这些大文件开始导致 Datahub 出现内存溢出错误。一个 800MB 的文件会消耗 8GB 内存，而我们当时使用的是能拿到的最大物理机，我记得大概也只有 12GB 内存。后来我们收到超过 800MB 的文件，却无法申请更大的机器，因为 dreaded hardware review process 由 Yahoo! 联合创始人 David Filo 亲自把关，他认为我们的服务器利用率太低，不值得增加容量。

这成了一个大问题。

导致内存膨胀的原因有两个。首先，现有实现无意中创建了多份已加载数据的副本——当一群习惯于修改状态的工程师开始使用 Erlang 这样的函数式编程语言时，这是很容易犯的错误。其次，它采用的是 DOM 解析器，而不是 SAX 解析器来解析和写入 XML 文件。

虽然当时敏捷开发正流行，但我们团队实际上有着强烈的个人代码所有权文化，大多数组件都只有一个所有者，只有他会修改或运维那部分代码。这意味着修复问题时，最耗时的往往是说服代码所有者，而真正实现方案反而很少成为瓶颈。对我这个只有一年经验的工程师来说，尤其如此——团队里其他人已经写了六到二十年的代码。

我开始尝试说服 Datahub 的所有者：SAX 解析器会比 DOM 解析器消耗更少的内存。但出乎我意料的是，我完全无法动摇他。我的说服尝试反而被视为冒犯。我们讨论了为什么增量解析部分数据会比一次性加载整个文件更省内存的理论。我们一起看了对比两种方法的基准测试，证明 SAX 内存占用更低。我还写了一个示例实现，展示了内存使用量的减少。

这些都没用。我的 teammate 坚定地认为 DOM 解析器内存占用更少，并指出可能存在某个内核 bug 导致了内存膨胀。

为了解决 OOM 问题——或许在几周争执后，我也多少带点想证明自己正确的执念——我尝试把实现中的 DOM 解析器换成 SAX 解析器。但那个组件完全没有测试，很难确认替换后是否正常工作。而且更换解析器只能解决一半的内存问题，那些意外产生的内存副本依然存在。

就像老梗说的那样，有一个周末我自己干了起来。我先写了一套全面的测试套件，然后从零开始重写了一个新实现。这个系统本身不算复杂，顶多两千行代码，但据我记忆，重写后的版本包括测试在内只有大约九百行。新实现通过了所有测试，提供完全相同的接口，可以直接插回现有的工作流管理器，处理文件速度更快，最重要的是，基准测试显示它的内存占用与文件大小无关，每个并发文件只占用大约几百 MB。它简单、快速、有效，而且是即插即用的替代品。

我把代码提交到 svn 分支，并把结果分享给了团队。

如果你期待这是一个英雄故事，那恐怕要失望了。那是一个不同的工程管理时代。在超过两年的时间里，我只记得和经理有过三次一对一会议。而你，亲爱的读者，一定不会感到意外地知道，第二次一对一是在第二天早上，我被经理从五英尺隔板的小隔间里叫走，这次会议完全不在计划之内。

谈话很简短。“如果你经验再多一点，我现在就会把你炒掉。删除重写代码，删除测试，以后永远不要再做这种事。”于是我删掉了重写代码，删掉了测试。不久之后，微软与 Yahoo! 的搜索协议让我们的 v2 发布暂停，一年后整个团队被解散。

Datahub 从未处理过超过 800MB 的文件，也从未获得过测试，但我明白了其中的意思。六个月后，我离开 Yahoo!，去 。Digg v4 发布：源于迫切的乐观。

我花了好几年时间，才想清楚从 Yahoo! 的这段经历，特别是 Datahub 这个寓言里，我真正应该吸取什么教训。现在回看自己的行为，我充满遗憾：我无法想象还有什么举动比重写别人的工作更损害团队心理安全了。同时我也清楚那是什么：一个毫无经验、缺乏觉察、工具也远不如今天的我，在试图帮助一个陷入困境的团队时，所做出的错误尝试。

最让我难以忘怀的，是一句回响——我在申请大学时，教堂里的一位长者给我的建议：“不要只关注老师的质量，好的老师哪里都有，要关注你身边同伴的质量。”我认为公司领导层的质量和特质差异，比本科教育的差异要大得多，但有一点已被反复证明：我所学到的和所取得的成就，与我能够共事的团队直接相关。
