重写 Yahoo! BOSS Datahub

2019-08-31 · 阅读原文

2008 年，我写博客的方式就是针对新兴技术狂轰滥炸般地输出内容，希望借此获得知名度、页面浏览量，或者至少能找到一份比 加入 JET 项目的旅程 更好的工作。我在 PyObjC、Processing.js、Why the Lucky Stiff 的 在 OS X 上开始使用 Shoes 以及其他几个项目上都不同程度地尝试过这种方法。

这个策略效果还不错——内容密度、新颖性和时效性正是取悦搜索排序之神的蜜露——最终帮我推开了科技行业的第一扇门：加入 Yahoo!，参与 Yahoo! Build Your Own Search Service（简称 BOSS）项目。

BOSS 发布的那一周，我写了一系列相关博客：1. 用 Django 构建你自己的 Yahoo 搜索服务，2. 用 Python 为 Yahoo 的 BOSS 编写搜索代码实例，3. 完善我们的 Django 与 BOSS 搜索服务，4. 用 BOSS Mashup 从 Hacker News 中剔除 Reddit 内容。文章数量之多，以至于他们都被这个“产量”搞糊涂了，于是主动联系我讨论。

经过六个月的沟通、躲过几轮裁员、熬过招聘冻结期后，他们终于把我作为小时工承包商招了进来，我在东海岸远程工作。那时的我还非常青涩，但既然重新有了医疗保险，我就迫不及待地想干活，做什么都行。

BOSS 的第一个版本允许通过 API 查询 Yahoo 的搜索结果，并对结果进行再加工。我加入团队时这个版本已经在运行，我们刚开始开发第二个版本——它允许用户提交自己的数据，然后同时查询用户数据和 Yahoo 的结果，并将两者融合。从某些角度看，这和后来的 Swiftype 非常相似。

产品本身对我来说并不那么重要，我只是很高兴能在科技公司工作。没人愿意写 YUI、Flash 和 APC 集成来显示文件上传进度？交给我！没人愿意碰前端，因为它既“太低端”又要解决 Mozilla 1.5 和 IE6 的跨浏览器兼容性难题，烦得要死？交给我！没人愿意学怎么调试 Erlang 工作流管理器？还是交给我！

这个团队是只有在一家正在收缩的公司里、其流程原本为高速增长期设计时，才可能出现的奇特组合。团队中有三个人刚刚结束对 del.icio.us 的支持（Yahoo! 已将其转为维护模式），另外十个人则多年来一直在为 Vespa 的一个定制扩展寻找内部客户。

你可以把 Vespa 理解为当时的 ElasticSearch，虽然当时最接近的对比是 Solr。而那个定制扩展叫 Hosted Vespa，它是一个运行在 Vespa 之上的适配层，为原本一直是单租户的系统提供了多租户能力。

Hosted Vespa 背后的技术可能比人们对一个被团队苦苦推销多年的产品的预期更加“字面”。你会创建一个具有若干字段的集合，大致如下：

int1, int2, ... intN
float1, float2, ... floatN
str1”, str2, ... strN

然后我们为每个用户的字段建立到底层 schema 的映射，大致如下：

age => int1
name => str1
city => “str2

在查询和索引时，用户的字段会被转换为集合的字段，让底层的 Vespa 实例完全不知道自己正在服务多个租户。如果真正大规模采用，这套方案会面临不小挑战，但过度采用从来不是我们面临的核心难题。

新用户可以上传任意格式的 XML 文件，文件会经过我们的 Datahub 进行格式标准化，然后将标准化后的数据发送给 SchemaInference，后者通过对每个字段的值进行正则匹配来判断字段类型，并映射到底层的 Vespa 字段。

随着我们引入 beta 用户，收到的文件越来越大。这些文件开始引发 Datahub 的内存溢出错误。一个 800 MB 的文件会消耗 8 GB 内存，而我们当时使用的已经是能拿到的最大物理机，我记得大概只有 12 GB 内存。后来我们收到了超过 800 MB 的文件，却无法申请更大的机器，因为要经过 David Filo（Yahoo! 联合创始人之一）主持的硬件审批流程，他认为我们的服务器利用率太低，不值得增加容量。

这成了一个大问题。

导致内存膨胀的有两个原因。首先，实现代码在加载数据时无意中产生了多次副本——当一群习惯修改状态的工程师开始使用 Erlang 这种函数式语言时，很容易出现这种情况。其次，它依赖 DOM 解析器而不是 SAX 解析器来解析和生成 XML 文件。

那时敏捷开发正流行，但实际上我们团队有着强烈的个人代码所有权文化，大多数组件都只有一个所有者，只有那个人会修改或运维那部分代码。这意味着修复问题时最耗时的往往是说服代码所有者，而真正实现方案很少成为瓶颈。对当时的我来说尤其如此——一个只有一年经验的工程师，和一群写了六到二十年软件的人共事。

我开始努力说服 Datahub 的所有者，认为 SAX 解析器比 DOM 解析器内存占用更低。但出乎我意料的是，我完全无法说服他。我的说服尝试甚至被视为一种冒犯。我们讨论了为什么增量解析部分数据比一次性加载整个文件内存消耗更少的理论依据。我们一起看了对比两种方法的基准测试，证明 SAX 内存占用更低。我还写了一个样例实现，展示了更低的内存使用。

这些都没有用。我的 teammate 坚持认为 DOM 解析器内存占用更少，并指出可能存在某个内核 bug 导致了内存膨胀。

为了解决 OOM 问题——也可能是在几周争执后我有点想证明自己是对的——我尝试把实现中的 DOM 解析器换成 SAX 解析器。但那个组件没有测试，很难确认替换后是否正常工作。而且更换解析器只能解决一半的内存问题，还存在那些意外的内存副本需要处理。

就像老梗说的那样，有个周末我自己动手了。我先写了一套全面的测试套件，然后从零开始写了一个新的实现。这个系统其实并不复杂，最多两千行代码，但据我记忆，重写后的代码连同测试一共只有大约九百行。新实现通过了所有测试，暴露了完全相同的接口，可以直接插回现有的工作流管理器，处理文件速度更快，最重要的是基准测试显示它的内存占用与文件大小无关，并发处理每个文件只需大约几百 MB。它简单、快速、有效，而且是即插即用的替代方案。

我把代码提交到 svn 的一个分支里，并把结果分享给了团队。

如果你期待这是一个英雄故事，那恐怕要失望了。那是一个不同的工程管理时代，在两年多的时间里，我只记得和经理有过三次一对一谈话。而你，亲爱的读者，不会惊讶地知道，第二次一对一谈话是在第二天早上，我的经理把我从五英尺高的小隔间里叫了出去。

谈话很简短。“如果你经验再多一点，我现在就会立刻开除你。把重写的代码删掉，把测试删掉，以后永远不要再做这种事。”于是我删掉了重写代码，删掉了测试。不久之后，微软与 Yahoo! 的搜索协议让我们 v2 版本的发布暂停，一年后整个团队被解散。

Datahub 从未处理过超过 800 MB 的文件，也从未获得测试，但我明白了那个信息。六个月后，我离开 Yahoo!，去 。Digg v4 发布：源于迫切的乐观。

我花了好几年时间才想清楚，从在 Yahoo! 的这段经历，特别是 Datahub 这个寓言故事里，我真正应该带走什么。现在回看自己的行为，我充满遗憾：我无法想象还有什么比重写别人代码更损害团队心理安全的举动。同时我也清楚那是什么：一个毫无经验、缺乏觉察、工具也远比今天匮乏的年轻人，想帮一个陷入困境的团队脱困而采取的错误方式。

最让我难以忘怀的，是一位教会长者在当年我申请大学时给我的建议：“不要只关注老师的质量，好的老师哪里都有，要关注你身边同学的质量。”我怀疑公司领导力的质量和特质比本科教育的差异要大得多，但有一点已被反复证明：我所学到的和所取得的成就，都与我有幸共事的团队直接相关。
