技术传承

2017-03-07 · 阅读原文

曾经有人告诉我，人们在公司之间跳槽时往往采用“飞楔阵型”：先由侦察兵前来了解文化和机会，随后越来越多之前的老同事和朋友便会陆续跟进。

这与我的经历不谋而合，很可能是因为大多数招聘系统都严重依赖员工推荐（顺便说一句，我认为 Slack 试图减少招聘对推荐依赖的做法，是当今技术招聘领域最有趣的想法之一）。

群体性流动的一个有趣副作用是，他们往往会带上意想不到的“偷渡客”：自己最喜欢的技术栈。这导致某些技术栈在公司之间不断传播。

有谁用过 Clusto 吗？除非你的公司继承了 Digg 的基础设施栈，否则你几乎不可能听说过这个工具（我相信 Linden Lab 是少数几个自然采用它的公司之一）。如果你在那类公司工作过，尤其是在 2011 到 2014 年间，那么你极有可能用过它，或者至少认真考虑过！

（如果用过，你可能对 Clusto 已经形成了某种感情。）

Clusto 只是继承的技术栈冰山一角！ 大致如下：Digg v4 的架构与开发流程

用 Python 写脚本、用 Clusto 管理基础设施元数据、用 Puppet 做角色配置、用 FAI（Fully Automatic Installed）来自动安装服务器、在每台节点本地运行 HAProxy 作为 ，以及对 DNS 保持健康的怀疑态度。对 Envoy 设计的思考

我乐观地认为，现在已经很少有新公司会直接采用这套特定的技术栈了。但如果你去看那些早期加入的 Digg 离职工程师所在的公司，你仍会发现其中一些特征仍在传播，只是随着时间推移逐渐淡化。

这并非 Digg 独有的现象（如果你用过 NSQ，那么你遇到 Bitly 前同事的概率会相当高）。当你开始留意时，会发现这是一个普遍存在的大模式。我认为，从选择自己熟悉且用得顺手的工具，而不是在那些对早期公司成败影响不大的技术决策上过度投入的角度来看，这甚至是一种最优行为。

不过对于某些技术，我认为 Clusto 在 2017 年很可能属于这一类，它为那些从未获得自然采用的开源技术创造了模糊的“第二生命”。最终它们的采用回报曲线与风险投资人的财务回报颇为相似：可能 90% 使用 Clusto 的工程师都在 Uber（尽管我相当确定那里已经没有 Digg 的前员工了），而在更广阔的想法市场中，其存活范围相当有限。（相比之下，Consul、Etcd，以及 Puppet、SaltStack 和 Chef 相关的工具，才是当今的胜利者。）

你们团队的技术传承是什么呢？
