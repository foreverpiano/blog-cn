Redis 内存使用笔记

2010-08-22 · 阅读原文

昨天我和一位同事在设计一个很有意思的解决方案时发现，我们需要更深入地了解 Redis 中各种数据类型的内存占用情况，以便尽可能多地压榨 Redis 的存储容量。除此之外，我们还想验证 Redis 文档中的一些说法，例如：哈希（hashes）是否真的比通过键名空间（namespacing keys）来创建伪哈希（pseudo-hashes）更优？

理解 Redis 数据结构的内存成本非常重要，它能让应用设计者在面对相同大 O 复杂度的操作时，根据实际的存储成本来选择合适的数据结构。对我们来说，这些额外的信息除了对容量规划的明显价值外，还对系统设计产生了意想不到的影响。（Redis 文档已经在每个可用操作上明确标注了大 O 复杂度，如果能同样形式化地给出每种数据结构的存储成本，那就更加完美了。）

闲话不多说，下面来看看 Redis 中集合（sets）、有序集合（sorted sets）、哈希（hashes）、列表（lists）和字符串（strings）的内存增长情况。（我很想在“look”前面加上“casual”以避免因为基准测试中的必然缺陷而被喷，但实际上你怎么做都免不了被喷。）

测试方法

对于每种数据结构的测试用例，在每组输入组合下的流程如下：

使用 FLUSHALL 清空 Redis 中的所有数据。等待一秒钟。加载数据。获取 Redis 的最终 INFO 信息。再使用 FLUSHALL 清空所有数据。

我发现初始内存占用并不是一个有价值的讨论指标，因为 Redis 不会立即归还所有未使用的内存，但它会持续重用这些内存。例如下面这些我在每次运行前后都执行 r.flushall() 的测试：

(virt)will:redis_benchmark lethain$ python set_memory.py

Memory: 7.14M => 14.09M
(virt)will:redis_benchmark lethain$ python set_memory.py
Keys: 0 => 100
Memory: 7.14M => 14.09M
(virt)will:redis_benchmark lethain$ python set_memory.py

配置详情

以下是与本次基准测试相关的不完整信息列表：

这些测试运行在一台配备四核 2.66 GHz Intel Core i5、4 GB 内存、OS X 10.6.4 的 iMac 上。使用的 Redis 版本为 redis-2.0.0-rc4，并使用默认的 Makefile 编译 redis-server。除非特别说明，这些测试均使用 64 位可执行文件，其内存开销明显高于 32 位版本。我正在用 32 位版本重新运行测试，并会在数据可用时更新对应章节（32 位版本通过 make ARCH="-m32" 编译，其他使用默认 Makefile）。粗略的经验法则是：64 位版本的内存占用大约是 32 位版本的 1.5 倍。所有操作均使用 Redis-Py 客户端完成，具体使用的是 commit 16c0eff87e7762d82fdd37d9949e33a7376d5357 的代码。

字符串 vs 哈希

我们先来对比三种存储 100 万个键值对的方式：

1000 个哈希，每个包含 1000 个键值对，共占用 207M。100 个哈希，每个包含 10000 个键值对，共占用 218M。100 万个字符串，共占用 207M。

当对比之前“哈希在内存消耗上优于字符串”的说法时，这个结果有点出乎意料，但我依然认为哈希在整体上更胜一筹，理由有以下几点。

首先，哈希实际上存储了更多数据——它不仅存储了与字符串完全相同的键值对，还存储了哈希内部的字段名本身。因此在某些使用场景下，哈希会更节省内存（例如当哈希内部的字段名非常短，而需要生成大量带命名空间的长键名时）。其次，哈希提供了更加丰富的接口，能以较低的算法复杂度完成某些任务（例如获取一个哈希中的所有值）。

如果哈希能在提供更多功能的同时，在最坏情况下内存消耗相当、最好情况下更优，那么在许多场景下，它确实比字符串更值得选择。

哈希 vs 字符串 vs 有序集合

基于上面的列表，我们再加入有序集合来对比存储 100 万个键值对的情况（需要说明的是，有序集合实际存储的是分数-成员对；需要再次说明的是，在某些场景下你可以把这个分数-成员对当作键值对使用）：

1000 个哈希，每个包含 1000 个键值对，共占用 207M。100 个哈希，每个包含 10000 个键值对，共占用 218M。100 万个字符串，共占用 207M。100 个有序集合，每个包含 10000 个分数-成员对，共占用 226.36M。1000 个有序集合，每个包含 1000 个分数-成员对，共占用 216.34M。10000 个有序集合，每个包含 100 个分数-成员对，共占用 234.18M。

字符串、哈希和有序集合之间的内存占用差异比预期小得多。这可能是因为它们在底层使用了相同的数据结构。不幸的是，在这些数据结构之间切换并不能获得太多内存收益。
