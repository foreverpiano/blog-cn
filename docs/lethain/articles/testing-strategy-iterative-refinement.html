策略测试：通过迭代优化避免瀑布式策略陷阱

2024-09-25 · 阅读原文

如果我只能推广一个关于技术策略的想法，那就是：在策略推出初期就过早施加压力，会阻碍我们真正判断该策略是否有效。压力会深刻改变人们的行为，其中许多改变是为了让你相信策略正在奏效，同时尽量少改变现状（如果你是高管），或者试图让你的策略被废止（如果你不是高管）。这两种情况都没有太大帮助。

虽然有些策略从一开始就明显错误，但更常见的情况是，看似合理的策略却因为没有把小细节处理好而失败。过早施加压力是导致一个更普遍现象的常见原因：大多数策略都是用瀑布模型制定的，在将策略付诸实践并从现实中吸取教训之前，就已经把方法 finalized 了。

避免瀑布式策略陷阱的有效方法之一，就是明确地对你的策略进行测试并优化细节。本章将介绍策略测试的具体操作方法：

什么时候需要测试策略（什么时候不需要）、如何测试策略、什么时候应该停止测试、策略测试中的角色：发起人（sponsor）与引导者（guide）、用于运行策略测试的指标与会议、如何识别跳过测试的策略、当策略已经推进太远却未经过测试时该怎么办。

让我们进入细节部分。

这是《Crafting Engineering Strategy》中的一章。

本章中的许多想法是在与 Carta Engineering 的 Shawna Martell、Dan Fike、Madhuri Sarma 以及其他众多同事共同工作期间逐渐成形的。

什么时候需要测试策略

策略测试的目的是确保一个策略能够以你愿意承担的成本实现其预期目标。因此，它必须在策略实施之前进行，通常是在策略早期制定阶段。

以下是针对常见策略主题进行测试的几个例子：

整合近期收购的公司时，可以先专注于让一个单一的 API 集成正常工作，再最终确定整体方案。针对 Python 代码库要求使用类型系统的开发者生产力策略，可以先让一位经验丰富的团队成员为一个重要模块添加类型。服务迁移策略可以先尝试迁移一个简单组件（测试迁移工具）和一个高度复杂的组件（测试集成复杂度），然后再进行更广泛的推广。

在所有这些案例中，最重要的两点是：在最终确定策略之前进行测试，并且进行窄而深的测试，重点关注方案的底层机制。不要陷入解决广泛问题，比如如何推动采用、如何处理冲突的激励机制等。

这并不是说所有策略都需要测试。以下是一些常见的无需测试的情况：

当你面对的是 何时撰写策略，以及写多少？（高度宽松的策略），实施成本非常低时，测试通常没那么重要；事实上，你可以把大多数高度宽松的策略视为一次测试，看看未来实施一个类似但限制更严格的版本是否有效。由于某些原因无法进行测试时，例如将招聘转向特定地区的招聘策略，在大多数情况下是无法测试的，你可能需要运行好几年才能获得有意义的结果。还有一种情况是你对某个策略有极高的信心，认为不值得测试，或许是因为你在同一家公司已经做过几乎完全相同的事情。不过，骄兵必败，所以我对这一类情况通常持怀疑态度。

尽管如此，根据我的经验，你应该尽力为每个策略找到测试的方法。绝不应该努力说服自己测试不值得。测试的成本远远低于实施一个糟糕策略的代价，几乎总是值得投入时间和精力。

如何测试策略

作为一个经常被忽略却极具价值的方法，策略测试其实相对简单。我发现有效的方法是：

找到你的策略中范围最窄、深度最够的切片，然后反复在该切片上应用你的策略，直到你确信这个方法行之有效。例如，如果你正在测试产品工程团队的新发布策略，那就决定用新方法完整发布一个重要版本。在迭代过程中，确定能够验证方法是否有效的指标；注意，这些指标不是用来衡量采用率的，而是衡量变更带来的影响。例如，衡量新发布流程是否减少了客户影响，或者是否带来了更多顶部漏斗访客。要相信人们是善意的，策略失败通常是因为摩擦太大或人体工学设计不佳。例如，如果人们没有使用发布工具，就假设是工具太复杂（绝对不要假设人们抗拒变化）。持续优化，直到你确信策略的细节在实践中有效，或者确信需要换一个全新的方向。例如，如果你之前确定的指标显示，新发布流程大幅降低了客户受到的影响。

最重要的反而是你不应该做的事情。不要追求宽泛的范围，尽管感觉影响力更大，但迭代周期会变慢。不要执着于强迫采用，以至于忽略了改进底层机制。最后，不要太执着于当前的方法，以至于无法接受它可能行不通。策略测试之所以有价值，正是因为很多策略并不像预期那样有效，而及早发现这一点成本要低得多。

测试中的角色：发起人（Sponsor）与引导者（Guide）

有时候，策略测试过程由一个人主导，他既能作为发起人支持这项工作（在较小的公司可能是首席工程师，在大公司可能是高管），也能协调日常验证工作（在较大公司可能是首席工程师、工程经理或技术项目经理）。更常见的情况是，这两项职责由两个角色分担：发起人和引导者。

发起人的职责包括：

作为升级点，快速做出决策，避免卡在开发阶段；突破历史决策和信念，使有意义的测试得以进行；调动跨组织支持；向利益相关者，尤其是管理层讲述故事，避免项目被砍；防止策略被过度加载（别人想让策略解决他们半相关的问题）；控制节奏，避免陷入停滞；识别能量下降的时机，及时转换策略阶段（从开发转向实施）。

引导者的职责包括：

当测试卡住时，把策略转化为具体细节；识别放缓和阻塞项；频繁向发起人升级问题；跟踪目标和工作流；维持发起人设定的节奏。

在担任这些角色方面，我随着时间积累了一些经验。对发起人来说，最重要的是他们真正被公司授权做出正在做的决策，并且足够关心最终影响，愿意快速做出艰难决定。发起人的价值只体现在引导者能够向其升级问题，而发起人必须迅速解决这些问题。如果他们无法及时响应升级或不能快速解决，他们就不是一个好的发起人。

对引导者来说，需要的是能够快速执行、不被各种组织混乱所干扰，并且对正在测试的策略有良好、细致的判断力。最差的引导者要么是意识形态化的（他们拒绝测试产生的反馈），要么是容易被干扰的（你之所以要做测试，往往是因为某处存在摩擦，因此一个无法驾驭摩擦的人默认会失败）。

会议与指标

策略测试阶段唯一绝对的要求是：发起人、引导者以及任何关键参与者必须每周固定一起开会。在会议中，你们要迭代哪些指标能最好地反映当前正在优化的领域，讨论从之前的指标或数据中学到了什么，并安排一次性跟进工作以确保取得进展。

这个会议的最佳形式是调试为主、演示为辅。如果某一周你没有学到任何能指导后续测试的新知，或者没有做出任何修改测试方法的决策，那就应该引起警惕。这可能意味着你对测试的资源投入不足，或者测试方案过于宏大，但它是一个重要信号，说明测试收敛得太慢，难以维持关注。

如果这一切听起来像是过大的投入，我建议你重新审视自己的 何时撰写策略，以及写多少？，调整正在制定的策略的容量或宽松程度。如果一个策略不值得测试，那么它要么已经非常优秀（这一点应该被其作者以外的人广泛认可），要么可能只值得以高度宽松的形式推出。

识别跳过测试的策略

虽然并非所有策略都需要经过测试阶段来打磨，但几乎所有失败的策略都是跳过了测试阶段，直接进入了实施。跳过测试的策略听起来正确，却做不成多少实事。在公司范围内完全统一授权和认证实现方案听起来是对的，但如果每个团队仍负责自己决定采用什么标准，那么它仍然可能失败。

一个特别明显的模式是我所说的“有压力但没有计划”。这类策略只有“听起来正确”的部分，却缺乏具体细节。服务迁移尤其容易陷入这种情况，或许是因为人们对 2000 年代亚马逊服务迁移的传说描述——通常被概括为自上而下、零细节地要求从单体架构中迁移出来。

判断是否跳过测试，主要看两点：

是否有数据表明策略正在产生预期影响？例如，新认证服务的 API 请求占所有认证请求的比例，要比一张记录各团队承诺迁移的表格更有意义。尽量避免使用代理指标，而是去看真正重要的事情。如果数字没有变化，是否有一个清晰的机制在调试和解决这些问题？这个团队是否真的在取得进展？例如，一个帮助集成新认证服务的团队，他们会去了解哪些限制阻碍了有效采用，并且正在交付可用的代码。因为数字没有变化，你需要找到其他有意义的证据来验证进展是否发生。通常最好的办法是看到在新环境中（例如生产环境中的产品代码）运行的新软件。与持怀疑态度的人或失败的集成案例交流也很有用，但要小心不要只和怀疑者一起调试。他们几乎总是正确的，但往往信息已经过时——他们说得对，却没有描述当前的问题。

除非上面这两点中有一点明显成立，否则你很可能发现了一个跳过测试的策略。

从跳过测试中恢复

一旦你意识到某个策略跳过了测试并且正在挣扎，下一个问题就是该怎么办。我们应该分解单体应用吗？ 一文讨论了如何从失败的服务迁移中恢复，其内容部分基于我在 Calm 和 Carta 处理类似卡住的服务迁移的经验。对于一个陷入困境的策略，答案始终是：写一个新的策略，并且这次不要跳过测试。

通常，这个新策略的第一步是明确暂停当前挣扎中的策略，同时启动新的测试阶段。这么做很痛苦，因为投入当前策略的人会不满，但无论你做什么，总会有人反对。从长远来看，能让大多数人满意的只有成功的策略，任何拖延成功的事都是糟糕的投资。

有时候很难正式暂停一个挣扎中的策略，这种情况下你就需要寻找间接机制，在不公开承认的情况下隐性暂停。例如，在花一个月时间改进服务供给能力期间，暂缓新服务上线，这可以给你足够的喘息空间来测试策略中缺失的机制，而不需要任何人因为失败的迁移丢面子。如果能把这些事情公开说出来当然很好，但管理人的情绪是领导力中永恒的挑战；即使你是高管，也只是面对另一群棘手的利益相关者而已。

总结

测试并不能决定一个策略是否可能优秀。它会暴露那些缺失的细节，这些细节是将一个方向正确的大致策略转化为真正可行的策略所必需的。读完本章后，你已经知道如何作为发起人或引导者来主导这个转化过程。你能够组织并运行必要的会议来测试策略，也能够建立一套指标，用来判断策略是否已经准备好离开打磨阶段，进入更广泛的推广。
