策略测试：避免瀑布式策略陷阱，通过迭代优化。

2024-09-25 · 阅读原文

如果我只能推广一个关于技术策略的理念，那就是：在策略推出初期就施加过大压力，会让你无法真正判断这个策略是否有效。压力会深刻改变人们的行为，而其中许多改变的目的，是让你以为策略正在奏效，同时尽可能少地改变现状（如果你是高管），或者让你把策略废除（如果你不是高管）。这两种情况都毫无帮助。

虽然有些策略从一开始就明显错误，但更常见的情况是：那些听起来合理的策略，最终失败是因为没有把细节处理好。过早施压是更普遍现象的一个常见诱因——大多数策略都是用瀑布模型开发的，在将策略投入实践并从现实中吸取教训之前，就已经把方案彻底定死了。

避免瀑布式策略陷阱的一个有效方法，就是明确地对你的策略进行测试。本章将介绍策略测试的具体操作方式：

什么时候需要测试策略（什么时候不需要）、如何测试策略、什么时候应该停止测试、策略测试中的角色：发起人（sponsor）与引导者（guide）、用于运行策略测试的指标和会议、如何识别一个跳过测试的策略、当策略已经推进太远却没有经过测试时该怎么办。

让我们进入细节部分。

本章选自《Crafting Engineering Strategy》。

这里许多想法是在与 Shawna Martell、Dan Fike、Madhuri Sarma 以及 Carta Engineering 的许多其他同事合作期间逐渐成形的。

什么时候需要测试策略

策略测试是为了确保一个策略能够达成预期目标，且成本在你愿意承受的范围内。这意味着测试必须在策略正式实施前进行，通常是在策略早期开发阶段。

以下是针对常见策略主题进行测试的几个例子：

整合最近收购的公司时，可以先把单个 API 集成跑通，再最终确定整体方案。一项针对 Python 代码库要求使用类型系统的开发者生产力策略，可以先让一位经验丰富的老员工去给一个重要模块添加类型。一个服务迁移项目，可以先尝试迁移一个简单组件（测试迁移工具）和一个高度复杂的组件（测试集成复杂度），然后再进行更大范围的推广。

在所有情况下，最重要的两点是：在最终确定策略之前进行测试，并且进行窄而深的测试，重点关注方案的底层机制。不要陷入解决“如何推动采用”“如何处理冲突的激励机制”这类宽泛问题。

这并不是说所有策略都需要测试。以下是一些常见的不需要测试的情况：

当你面对的是何时编写策略，以及写多少？且实施成本很低时，测试通常没那么重要；实际上，你可以把大多数高度宽松的策略视为一次测试，看看未来是否值得推行一个类似但更严格的版本。由于某些原因无法进行测试的情况。例如，改变招聘地域的招聘策略，在大多数情况下是无法测试的，你可能需要运行好几年才能获得有意义的结果。还有一种情况是你对某个策略有极高的信心，认为不值得测试——可能是因为你在同一家公司已经做过几乎一模一样的事情。不过，骄兵必败，所以我对这一类情况一般持怀疑态度。

尽管如此，我的经验是：你应该努力为每个策略找到可测试的方式。你绝不应该努力说服自己测试不值得。测试的成本远远低于推行一个糟糕策略的成本，几乎总是值得投入时间和精力。

如何测试策略

作为一个经常被跳过的、有价值步骤，策略测试其实相对简单。我发现有效的做法是：

找出你的策略中可用范围最窄、深度最够的切片，然后反复在该切片上应用你的策略，直到你确信这个方法行之有效。例如，如果你正在测试产品工程团队的新发布策略，那就决定只用新方法完成一次重要发布。在迭代过程中，确定一些能帮你验证方法是否有效的指标；注意，这些不是用来衡量采用率的指标，而是用来衡量变更带来的实际影响。例如，能显示新发布流程减少了客户影响、或带来了更多顶部漏斗访客的指标。要相信人是善意的，策略失败通常是因为摩擦太大或人机交互体验太差。例如，如果大家不用发布工具，就假设是工具太复杂。（绝对不要假设大家抗拒变化。）持续优化，直到你确信策略的细节在实践中可行，或者需要换一个全新的方向。例如，如果你之前确定的指标显示，新发布流程显著降低了客户受影响的程度。

最重要的反而是你不该做的事。不要追求宽泛的范围（虽然感觉影响更大，但迭代周期会变慢）。不要纠结于强迫大家采用，从而忽略了改进底层机制。最后，不要过于执着于当前方案，以至于无法接受它可能行不通。策略测试之所以有价值，正是因为很多策略并不像预期那样有效，而及早发现问题要便宜得多。

测试中的角色：发起人（sponsor）与引导者（guide）

有时策略测试由一个人主导，他既能为工作提供支持（小公司里的首席工程师、高管等），也能协调日常验证工作（大公司里的首席工程师、工程经理、技术项目经理等）。更常见的情况是，这两部分职责由两个角色分担：发起人和引导者。

发起人的职责包括：

作为升级通道，快速决策以避免卡在开发阶段；突破历史决策和固有观念，使有意义的测试得以进行；调动跨团队支持；向利益相关者，尤其是高管团队讲好故事，避免项目被砍掉预算；防止策略被过度加载（别人想让你的策略去解决他们半相关的问题）；掌控节奏，避免项目停滞；发现精力下滑时，及时切换策略阶段（从开发转向实施）。

引导者的职责包括：

当测试卡住时，把策略细化为具体可执行的细节；发现减速点和阻塞项；频繁向发起人升级问题；跟踪目标和工作流；维持发起人设定的节奏。

在角色配置方面，我积累了以下经验。对发起人来说，最重要的是他们真正被公司授权做出正在做的决策，并且足够关心最终影响，愿意快速做出艰难决定。发起人是否有价值，取决于引导者能否向其升级问题，而发起人必须迅速解决这些升级事项。如果他们无法及时响应升级或解决得太慢，那就是不称职的发起人。

对引导者来说，需要找一个能快速执行、不被各种组织问题拖垮，并且对所测试策略有良好、细腻判断力的人。最糟糕的引导者要么是意识形态驱动的（他们拒绝测试产生的真实反馈），要么是容易被干扰的（你之所以要做测试，往往是因为某个地方存在摩擦，一个无法应对摩擦的人默认就会失败）。

会议与指标

策略测试阶段唯一必须的要求是：发起人、引导者以及任何关键执行人员必须每周都一起开会。在会议中，你们要迭代哪些指标能反映当前正在优化的领域，讨论从之前的指标或数据中学到了什么，并安排一次性的跟进事项，以确保取得进展。

这类会议的最佳形态是：以调试为主，演示为辅。如果你连续一周都没有学到任何能指导后续测试的东西，或者没有做出任何会改变测试方法的决策，那就应该引起警惕。这可能意味着你给测试分配的资源不足，或者测试范围定得太宏大，但无论如何，它都是一个明确信号——测试收敛得太慢，无法维持大家的注意力。

如果这一切听起来像是一项过于庞大的投入，我建议你重新审视自己的何时编写策略，以及写多少？，调整正在制定的策略的体量或宽松程度。如果一个策略不值得测试，那么它要么已经非常优秀（这一点应该被作者之外的人广泛认同），要么只值得以高度宽松的形式推广。

识别跳过测试的策略

虽然并非所有策略都必须经过测试阶段来打磨，但几乎所有失败的策略都是跳过了测试，直接进入了实施阶段。那些跳过测试的策略听起来很正确，却没取得什么实际成果。在全公司把鉴权和认证统一到一种实现上，听起来很正确，但如果每个团队仍负责自行决定如何采用标准，最终仍可能失败。

一个特别明显的模式，我称之为“有压力但没有计划”。这类策略只有“听起来正确”的部分，却缺乏具体细节。服务迁移项目尤其容易出现这种情况，或许是因为大家对亚马逊 2000 年代服务迁移的传说描述——通常被简化为一个自上而下、零细节的命令：离开单体系统。

判断是否跳过测试，主要看两点：

是否有数据表明该策略正在产生期望的影响？例如，新认证服务的 API 请求量占所有认证请求的比例，要比一张记录各团队承诺迁移进度的表格更有意义。尽量避免使用代理指标，而是直接看真正重要的事情。如果数字没有变化，是否有一个清晰的机制在调试和解决这些问题，并且这个团队是否真的在取得进展？例如，有一个团队专门帮助集成新认证服务，以发现哪些限制阻碍了有效采用，并且他们在持续交付可用的代码。因为数字没动，你需要找到其他有意义的证据来验证进展是否真的在发生。通常最好的证据是：在真实环境中运行的新软件（例如，产品代码在生产环境）。与持怀疑态度的人或失败的集成案例交流也很有用，但要谨慎不要只和怀疑者一起调试。他们几乎总是对的，但常常信息已经过时——他们说得对，却没有描述当前真正的问题。

除非以上两点中有一点明显成立，否则你很可能发现了一个跳过测试的策略。

从跳过测试中恢复

一旦你意识到某个策略跳过了测试且目前陷入困境，接下来的问题是该怎么办。我们是否应该分解单体架构？ 一文讨论了如何从失败的服务迁移中恢复，内容部分基于我在 Calm 和 Carta 处理类似卡住的服务迁移的经验。对于一个卡住的策略，答案始终是：写一份新的策略，并且这次一定不要跳过测试。

通常，这份新策略的第一步是明确暂停当前陷入困境的策略，同时启动新的测试阶段。这么做很痛苦，因为投入当前策略的人会不满，但无论你做什么改变，总会有人反对。从长期来看，能让大多数人满意的只有成功的策略，任何拖延成功的事情都是糟糕的投资。

有时很难正式暂停一个陷入困境的策略，这时候你需要寻找间接机制，在不公开承认的前提下隐性暂停。例如，在花一个月时间改进服务供给能力期间，暂缓新服务上线，这可以给你足够的喘息空间去测试策略中缺失的机制，而不需要任何人因为迁移失败丢面子。能把这些事情公开说出来当然最好，但管理不同性格的人始终是领导力面临的持久挑战；即使你是高管，也只是面对另一批同样复杂的利益相关者而已。

总结

测试并不能决定一个策略是否可能好。它能暴露那些缺失的细节，这些细节是将一个方向大致正确的策略转化为真正有效的策略所必需的。读完本章后，你已经知道如何作为发起人或引导者来主导这个转化过程。你能够建立并运行必要的会议来测试策略，也能够整理出一组指标，用来判断策略是否已经准备好离开打磨阶段，走向更大范围的推广。
