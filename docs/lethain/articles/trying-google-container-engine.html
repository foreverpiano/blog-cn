试用 Google Container Engine

2017-05-14 · 阅读原文

阅读新闻时，有时会感觉初创公司 CTO 面临的核心挑战是，应该先推行服务编排策略，还是先搞自动驾驶汽车策略。尽管如此，我确实认为任何拥有超过几名工程师的技术公司都应该制定一套编排策略。为此，我最近花了不少时间来熟悉 Kubernetes，尤其是 Google Container Engine（GKE）。

我心里具体的问题是：我个人能否在几乎零成本的情况下，获得我在工作中所享有的那种自动化、集成度和灵活性——在公司里，我受益于对 AWS Auto Scaling Groups 工具、Jenkins 集成以及整个开发生态系统的巨额投入，同时又不会给自己带来太多的维护负担。

为了回答这个问题，我在这个周末把这个博客迁移到了 Kubernetes 和 GKE 上。目前它已经完全由 GKE 提供服务，原有的 AWS 基础设施也已关闭。（我将在未来一两周内迁移 systemsandpapers.com。）

（这个举动多少有点讽刺，因为我。）第五次博客重写的笔记

我采取的步骤如下：

  1. Create a GKE hosted Kubernetes cluster, using three n1-standard-1 instances (each has 1.8 GB RAM).
  2. Write a Dockerfile, initially a transliteration of my existing Packer configuration which ran Nginx and the Go binary in the same VM. (Previously I had been baking AMIs.)
  3. Sync my blog’s shoddy codebase, named daedalus, from Github to Google Source Repositories, on the reasonable but unvalidated assumption that it’ll reduce build latencies to have it locally.
  4. Create a build trigger in Container Builder to automatically build Daedalus’ Dockerfile each time I push to the master branch, and upload the resulting image into Container Registry, where it can be used by GKE. (I had a short detour into tagging container images with branch instead of tag, and it became clear that Kubernetes does not care for that approach, plus it breaks rollbacks.)
  5. Get this approach working fully, including creating an ingress resource with an HTTP(S) Google Load Balancer routing traffic to daedalus.
  6. It was at this point that things detoured slightly, as GLBs don’t provide automatic SSL certificate management capabilities similar to AWS ALBs, and it became clear that I would need to manage my own certificates.
  7. Let’s Encrypt is the obvious solution, and it seemed like kube-lego was the most common integration, so I set that up. It did work, but the specific behavior I want ended up being harder to model: I want all non SSL traffic to get passed through, and all SSL traffic to get terminated and passed through. kube-lego wanted specific routing rules for every domain and protocol (sort of necessary following from its approach to capturing the /.well-known/* path as required for answering Let’s Encrypt’s domain ownership challenges), and it claimed the route for unmatched traffic, directing it to a default Nginx config as opposed to letting me point it to my daedalus nodes. This didn’t work well given the number of domains I wanted to handle (mostly just redirecting them to lethain.com, but enough that having a rule per domain was going to exceed my understanding of GLB’s restrictions), so I was back at the drawing board.
  8. After some thought, I decided the best solution was to split out my Nginx and SSL termination work into its own deployment, such that I have two: frontend that hosts Nginx and does SSL termination, and daedalus which only runs the Go binary. It took a bit of configuration, but I was able to get this working, with a loadbalancer type service that directed TCP traffic to my frontend deployment, which in turn reverse-proxied to the daedalus deployment’s ClusterIP. I updated the Nginx configurations to serve the Let’s Encrypt challenge tokens directly, and was able to pass the challenges. (I wanted to get a new cert to lethain.com before switching DNS, so I actually ended up hacking my AWS’ instances’ Nginx configs to reverse proxy to my GCP load balancer for the challenge files, although in later readings I believe a 301 redirect would have worked just as well and been a bit less annoying.)
  9. This was working pretty well, with the caveat that I only had a single frontend pod, a necessary simplification because certbot was writing local files and if we had multiple pods then some wouldn’t have the file to respond to the challenge accurately. After some reading, the simplest solution was to create a cert-refresh deployment, which I run with a single instance, and then have the frontend pods reverse-proxy /.well-known/* back to that instance. For the things that really matter, e.g. serving traffic, there is high availability; cert renewal is technically no longer highly available, but the requirements are that it runs a refresh script once a day, so it can fulfill its needs even with extraordinarily poor uptime.
  10. Victory!

这个过程虽然涉及了不少调试和 hack，但最终只用了六个 YAML 文件（三个 Deployment、三个 Service）和三个 Dockerfile。如果需要，我可以在几分钟（好吧，算它三十分钟）内把整个环境重新搭建起来。

更有意思的是，这成了我个人基础设施迄今为止最成熟、最方便的环境。从 push 到 Git 到容器上传，整个流水线都是自动化的，而我的部署现在只需要更新 deployment.yaml，把镜像 tag 指向新的版本，Kubernetes 就会执行一次增量 rollout，同时尊重健康检查，如果健康检查失败就会暂停 rollout。

我甚至可以通过命令行进行回滚，这对我的个人基础设施来说是个全新的概念。

容器构建过程中会向 Google Pub/Sub 发送事件，所以我猜再花一两个小时 hack 一下，我就能把 wiring 加上去，搭建一个完整的持续集成流水线。令人兴奋的是，这不仅适用于 daedalus 这样的个人应用，也适用于 frontend 节点这样的支撑性基础设施。如果我写错了 Nginx 配置，就不会再把网站搞挂了！（我之前待过的真正公司里，有些还做不到这一点！）

总的来说，我非常 impressed，接下来一两周会把剩下的基础设施也迁过来，这样我就有一个稍微复杂一点的环境可以管理了。深入了解 Kubernetes 过程相当有趣，Google Cloud 整体也非常优秀，尽管它仍然给人一种感觉：虽然理念可能比 AWS 更简洁，但执行上还是有些粗糙（比如 gsutil 的使用体验就明显比 awscli 更让人困惑）。
