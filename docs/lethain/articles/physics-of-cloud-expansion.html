云扩张的物理学

2018-01-16 · 阅读原文

你在新公司遇到的第一个谜题，就是推断这家热门初创公司是在哪个时代创立的。Ruby on Rails？用了 MongoDB 或 Riak？啊，Clojure，那可是个激动人心的时代。技术栈甚至是。技术传承

虽然每年都有大量新技术发布，按理说应该更难把公司归到特定时代，但我觉得实际上变得越来越容易了。JavaScript 框架此起彼伏的节奏有所帮助，但最近最好的指标是哪些组件仍在内部管理，哪些已经迁移到云端。最近，从虚拟机到容器的转变，就像之前从物理服务器到虚拟机的转变一样，给公司打上了清晰的时代烙印。

特别有趣的是，这种趋势如何重新定义了那些构建在云上的公司的基础设施工程师角色。云的稳步前进将如何塑造我们未来的工作？我们今天能做些什么来为这些变化做准备？

云扩张的原则

云正按照以下原则发展：

云提供商将推出数量不断加速的探索性产品，以测试其价值和产品市场契合度。这些探索性方案需要架构决策，新公司很容易采用，但对现有公司来说却很难 retrofitting。几年前的 ECS 就是一个探索容器机会的好例子，它推出时价值主张并不稳定，后来才逐渐成熟。AWS Lambda、Azure Functions 和 Google Functions 则是当下这个领域的典型代表。大多数探索性方案最终都会变得足够通用且易用，让许多现有公司也能采用。如今，从探索到成熟的演化周期大约是三年。随着云提供商自身规模的扩大，他们会越来越难优先考虑小机会（包括他们目前支持的某些机会变得太小而不值得继续支持）。随着时间推移，云提供商将解决任何可泛化的问题，哪怕它极其困难，但不会去解决任何特定领域的问题，哪怕它们非常简单。正面的例子是 AWS KMS 提供了硬件安全模块，负面的例子则是 Lambda 的语言支持仍然非常受限。注意：他们非常愿意为大客户做定制工作，所以当你的云支出增加时，这条原则会变得模糊。随着云采用率的增长，云提供商未来大部分增长机会将来自说服公司从现有云提供商迁移。这已经剧烈地改写了他们的优先级：降低迁移成本，特别是通过 Kubernetes API、Envoy 等通用接口；提供最佳价值，尤其是在可靠性、安全性、延迟和成本方面；提供差异化能力来激发内部推动迁移的拥护者，例如 GCP 以 Beam 为核心的机器学习策略。

内部基础设施的竞争优势

虽然云提供商相对于内部基础设施提供商有诸多优势，但负责单一公司特定基础设施需求仍然带来一些结构性优势：

我们不需要云提供商所需的规模经济；我们有自由去做定制化和专门化的工作。Azure Functions、AWS Lambda 和 Google Functions 就是很好的例子：由于需要支持语言和语言沙箱，他们只能为少数语言提供实现。而我们能支持公司想要的任何语言。我们有机会深入理解自己的业务领域。我们可以针对公司业务独特的合规制度、威胁模型、测试及其他方面进行优化。我们能直接且频繁地接触用户。我们可以投入更多时间去理解并专门化我们的工作，以支持更小、更特定的用户群体。

我们应该继续在哪些领域投入？

基于云和内部提供商的竞争优势，让我们来探讨一些常见的基础设施领域。对每个领域的问题是：是否还值得投入？如果不值得，我们该如何开始逐步退出。

网络

网络极为复杂，以至于云似乎不太可能复现其全部功能。这在很大程度上是正确的（云上的组播，有人试过吗？），但结果并不像网络设备厂商曾经希望的那样：历史上属于网络层的关注点，正越来越多地向上层移动到应用层（例如 Envoy 除了 DNS 之外还提供“服务发现服务”）。现在已经有可能在对底层网络几乎不了解的情况下，构建和维护复杂的基础设施。

云在网络配置上的僵硬不灵活（尤其是在早期云时代，虽然随着 AWS VPC、GCP VPC 等产品的能力扩展，这种情况略有改善）促成了这一转变，迫使基础设施提供商围绕新的网络约束进行创新，并减少了对网络配置的依赖。

总体而言，我预计未来几年云将吸收大部分网络功能：

云已经在核心网络质量上获胜，尤其是 GCP，提供了快速、可靠的连接，入口点比大多数公司能合理维护的还要多，对路由问题的响应也比你自己能提供的更快。基础 CDN 功能在云上一直更简单、更便宜，比自己搭建或大多数专用 CDN 提供商都划算。云正在竞相增加边缘计算能力，比如 Lambda@Edge，其便利性意味着像 Fastly 和 Cloudflare Workers 这样的专用边缘计算提供商，必须提供显著更多的价值或便利才能留住用户，这看起来相当困难。DDoS 缓解长期以来是 Prolexic 等公司的专长，现在似乎正转向云产品，如阿里云的 Anti-DDoS、AWS Shield、Azure 的 DDoS 防护。云本身就需要这种能力来缓解针对自身资产的 DDoS 攻击，这意味着他们提供这些产品的增量成本，远低于需要维护专用缓解机群的专用公司。因为网络正日益成为一种商品而非云的差异化点（而且他们的竞争对手越来越多是彼此，而非客户的现有物理基础设施），他们会提供云无关的接口和工具，比如 CNI，来简化跨网络环境的迁移。我期待 Kubernetes 所展示的模式——最终落地到一个通用的编排接口——在这里重演，也许是类似 Istio 的东西。即使你拥有自己的硬件，云也拥有独特的规模经济，能在基础性能上不断突破边界：例如 Azure 使用 FPGA 在 VM 之间实现 30Gbps 的 TCP/IP 吞吐，这不是你可能去做的事情。

内部基础设施提供商仍然可以提供价值，特别是去处理那些云故意回避的、规模化难度较高的复杂问题：

编写和维护健康检查仍将足够复杂且特定于单个应用，难以被云产品商品化。用户身份、服务身份及其周边问题空间（认证、授权、SSO）的巨大复杂性，持续抵制向云端的整体迁移，我认为这种情况未来几年仍会持续。AWS IAM 和 GCP IAM 会继续逐步靠近，但会受限于企业需要无限可配置性与小型公司需要简单性之间的矛盾。多区域冗余仍将继续需要应用层变更，而跨区域的延迟将继续受限于光速。一些前时代开发的企业软件（如 Vertica）需要网络调优才能按设计运行。云是否会提供这种调优能力，或者这些产品在现有云上的次优性能是否会先将它们淘汰，这将是一场有趣的竞赛。

总体来说，网络、路由及相关问题在未来几年将被显著商品化。

计算

计算大致可以拆分为编排、构建和部署。虽然每个公司都必须提供某种解决方案，但大多数小公司的需求很简单，很长时间以来它们的需求已经被 Heroku 等高度主观的 PaaS 提供商满足了。而大公司则不断从大多数 PaaS 提供商中成长出来，寻求更高的可配置性、更低的成本，以及足够的移植性以避免厂商锁定。

云提供商已经达到足够的规模，能做出很少公司能做到的优化，他们的采购规模也让他们得以主导 SSD 市场。最近，Amazon 宣布了 AWS EKS，与 Azure AKS 和 GKE 一起，成为第三个承诺支持 Kubernetes 作为接口的主要云提供商，并提供统一的云计算接口。这个统一接口将降低跨云迁移成本，并表明云提供商将计算视为一种商品，他们将在价值上展开竞争。这种接口层面的简化在 virtual kubelet 等项目中尤为明显，它将 Kubernetes 接口与 Azure ACI 或 AWS Fargate 的隔离性和可扩展性相结合（例如，如果你不用在 Kubernetes 集群中解决网络安全问题呢？也许很快你就不需要了！）。

云提供商已经赢得了编排，但其他领域仍值得投入。

构建与配置相结合的问题，尤其是容器镜像管理，仍将是一个重大挑战。保持镜像更新、安全地部署新版本、在能快速下载的地方（特别是跨地理区域）存储镜像，都是难题。云提供商将在未来几年解决这个问题的部分环节（尤其是镜像存储），但其复杂性将阻止完全商品化。我预计云端会涌现一些非常受限的新模式，让新开发的应用程序能减轻负担，但这些模式需要足够广泛的变更，以至于无法迁移现有软件。这里的防御护城河在于：快速的构建通常是危险的，而安全的构建通常是缓慢的——我们需要看到这个领域有改进的技术，才能被云商品化。例如，现在大多数云构建系统不缓存 Docker 层，因为创建它们的操作并非始终可重现，这使得层缓存很容易被以微妙方式污染。这种无法激进缓存的情况，让通用方案比定制构建方案慢得多。看到 Bazel 的理念作为安全且快速的应用构建路径参与竞争，尤其是与容器化结合、将应用和环境构建合并为原子产物时，会非常令人兴奋。应用配置（如 Consul 或 Etcd 提供的）将继续与应用代码和行为紧密耦合，难以被云商品化。预计像 AWS KMS 这样的密钥管理工具会逐渐向解决整个应用配置领域演进。多区域冗余继续需要应用层面的架构和设计，我预计这种情况会持续下去，直到它最终在存储层被商品化。GCP 正在尝试“默认多区域”的策略，最明显的是 Cloud Spanner，但目前采用它需要完全买入他们的平台并接受厂商锁定。我目前也不熟悉有多少公司在使用这个产品，毕竟它还很新。最终，我认为 GCP 的默认多区域策略在其他云提供商提供类似产品以减轻锁定风险之前难以成功，因此我认为这是未来几年内部基础设施值得投入的安全领域。

存储

AWS 最早的成功之一就是他们的 Simple Storage Service，能便宜且可靠地存储文件。此后产品持续扩展到 NoSQL、关系型数据库，最近又扩展到队列（Kinesis、Pub/Sub）。

仍然有相当多领域适合内部投入：

虽然键值点查询将被商品化，但管理二级索引仍将与应用逻辑紧密耦合，难以被云吸收。（我认为键值点查询尚未完全商品化，因为自己运行例如 Cassandra 集群相比使用 Dynamo 仍有价格优势，但我预计云提供商将在未来五到十年内侵蚀这一价格优势，而且老实说，我怀疑他们已经侵蚀了完全加载成本。）在大规模下保持强一致性在云上仍然难以实现，除了 Cloud Spanner。在非结构化数据上的 schema 注册/强制/迁移，尤其是在进入队列的数据上。图数据库对于某些类别的机器学习和网络问题仍然极其有用，而云上目前还没有强大的产品（例如 Titan）。存储是现有多区域产品最受限制的地方。任何合理的多区域存储方案都将继续需要大量的内部投入。Cloud Spanner 和 CosmoDB 是值得注意的例外，虽然我还没有看到大规模的广泛采用。像 GDPR 这样的合规和数据本地化要求，其演进速度仍快于云目前所能支持的。从长期看，我预计云提供商会将其商品化。即使在今天，他们也更有条件在引入新数据和合规立法的国家快速开通新区域，但他们尚未大力抓住这个机会（尽管 Azure 似乎略微领先）。管理数据库快照也仍然是一个复杂、细致入微的领域。云提供了基础组件，但仍然需要拼接和维护，例如跨环境的管理。

批处理、流处理和机器学习

机器学习最近获得了大量关注，云提供商也渴望服务于此。但这并不意味着更传统的数据处理领域没有快速演进，批处理和流计算也在快速发展。

也许共同的主题是它们发展得太快，实验多于标准：

AWS 推出了几十种产品，GCP 推出了更多，Microsoft Azure 则更多。Google Dataflow 是一个强大且低维护的解决方案，用于有界和无界事件计算。AWS Ironman 是一个完整的机器学习生态系统。我认为 AWS Deep Learning AMIs 值得特别提及，它是一个有趣的举措，也是 API 标准化的好例子，因为它支持 Google 的 TensorFlow API。自己管理镜像，尤其是每月或每两个月就要升级几十个底层库，这是一项挑战且繁重的工作，是一个比表面看起来更有趣、可能更有影响力的实验。定制硬件，比如 Google 的 TPU，是云提供商将深度投入以相互竞争的领域，而内部提供商根本无法获得相应的规模经济来竞争。

尽管如此，这些平台大多仍然非常主观、受限或缺乏广泛采用。，而大数据迁移往往又非常缓慢，我认为这个领域将继续为内部投入敞开大门。（即使是你非常希望完全商品化的东西，比如 Hadoop 生态系统的管理，在大规模下仍需要内部关注。）从 Lambda 到 Kappa 以及数据流范式

这里还有一些有趣且快速变化的外部因素，比如前面提到的 GDPR，并由此催生了一波相关解决方案，如 Apache Atlas。当你将这些因素与数据的边界去向（如调优机器学习模型）结合起来时，数据领域仍然非常适合内部投入。

工作流、工具和用户

把所有这些综合起来，我想强调的信息不是云正在吞噬我们的职业，而是我们有一个非常特别的机会去演化我们的关注点和策略，以利用云的优势。通过今天选择正确的策略和投资领域，我们将让自己明天从事更有趣的工作，并在整个过程中对我们的用户和公司更有价值。

通过聚焦于工作流（告警、事件管理、调试、部署、构建、应用的供应/扩缩容/下线……）、接口（容器、协议、CLI、GUI……）以及我们用户的需求：最有趣的问题仍然在前面。
