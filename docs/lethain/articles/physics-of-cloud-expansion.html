云扩张的物理学

2018-01-16 · 阅读原文

你在新公司的第一个谜题是调试他们是在哪个喧闹的创业时代创立的。Ruby on Rails？还是用了 MongoDB 或 Riak？啊，Clojure，那可是个激动人心的时代。技术栈甚至是。技术传承

随着每年都有大量新技术发布，将公司归入其所属时代本应变得越来越难，但我发现这其实越来越容易了。JavaScript 框架此起彼伏的鼓点帮了不少忙，但最近最好的指标变成了哪些组件是内部管理的，哪些已经迁移到了云上。最近，从虚拟机到容器的转变，像之前从服务器到虚拟机的转变一样，清晰地给公司打上了时代烙印。

特别有意思的是思考这一趋势如何重新定义了构建在云上的公司的基础设施工程师角色。云的稳步前进将如何塑造我们未来的工作，我们今天能做些什么来为这些变化做好准备？

云扩张的原则

云正按照以下原则发展：

云提供商会推出数量不断加速的探索性产品，以测试其价值和产品市场契合度。这些探索性方案需要架构决策，新公司很容易采用，但对现有系统进行改造则充满挑战。ECS 是几年前探索容器机会的一个好例子，推出时价值主张还很生硬，后来才逐渐成熟。AWS Lambda、Azure Functions 和 Google Functions 是当今这个领域的一个绝佳示例。大多数探索性方案最终都会演变为足够通用且易用的产品，连许多现有公司都能采用。如今，从探索到成熟的演化时间大约是三年。随着云提供商自身规模的增长，他们会发现越来越难优先考虑小型机会（包括他们目前支持的某些机会变得太小而不值得继续支持）。随着时间推移，云提供商将解决任何可泛化的问题，哪怕它极其困难，但不会解决任何专门化的问题，哪怕它非常简单。正面例子是 AWS KMS 提供硬件安全模块，负面例子是 Lambda 的语言支持仍非常有限。注意：他们非常愿意为大客户提供定制工作，因此当你的云支出增加时，这条原则会变得模糊。随着云采用率的增长，云提供商越来越多的增长机会将来自说服公司从现有云提供商迁移。这以一种令人不安的方式重写了他们的优先级：降低迁移成本，特别是通过 Kubernetes API、Envoy 等通用接口；提供最佳价值，尤其是在可靠性、安全性、延迟和成本方面；提供差异化能力以激发内部倡导者，比如 GCP 以 Beam 为核心的机器学习策略。

内部基础设施的竞争优势

虽然云提供商相对于内部基础设施提供商有许多优势，但只负责一家公司特定基础设施需求这件事本身，也带来了一系列结构性优势：

我们不需要云提供商所需的经济规模；我们有自由去做定制和专门化的工作。Azure Functions、AWS Lambda 和 Google Functions 就是一个很好的例子：由于需要对语言和语言沙箱提供支持，他们只能为少数几种语言提供实现。而我们可以支持公司想要的任何语言。我们有机会深入理解自己的业务领域。我们可以针对公司业务特有的合规制度、威胁模型、测试及其他方面进行优化。我们能直接且频繁地接触用户。我们可以投入更多时间去理解并专门化我们的工作，以支持更小、更特定的用户群体。

我们应该继续在哪些领域投资？

基于云和内部提供商的竞争优势，让我们探讨一些常见的基础设施领域。对每个领域的问题是：是否仍然值得投入，如果不值得，我们该如何开始逐步退出。

网络

网络如此复杂，以至于云似乎不可能复现其功能。这在很大程度上是正确的（云上的组播，有人试过吗？），但结果并不像我猜想网络设备供应商所希望的那样：历史上属于网络层的问题，正越来越多地上移到应用层（例如 Envoy 除了 DNS 之外还提供“服务发现服务”）。现在已经可以构建和维护复杂的基础设施，而对底层的网络几乎不需要多少了解。

云在网络配置上的僵硬 inflexible（尤其是在早期云时代，虽然随着 AWS VPC、GCP VPC 等产品的能力扩展而略有改善）推动了这一转变，迫使基础设施提供商围绕新的网络约束进行创新，并减少了对网络配置的依赖。

总体而言，我预计云将在未来几年吸收大部分网络功能：

云已经在核心网络质量上获胜，尤其是 GCP，它提供了快速、可靠的连接，入口点比大多数公司能合理维护的更多，对路由问题的响应也比你可能提供的更快。基础 CDN 功能在云上已经并且将继续比自己搭建更简单、更便宜，也比大多数专用 CDN 提供商更便宜。云正在竞相增加边缘计算能力，比如 Lambda@Edge，其便利性意味着专用边缘计算提供商如 Fastly 和 Cloudflare Workers 必须提供显著更多的价值或便利性才能留住用户，这看起来相当不可能。DDoS 缓解长期以来是 Prolexic 等公司的专长，现在似乎正转向云产品，比如阿里巴巴云的 Anti-DDoS、AWS Shield、Azure 的 DDoS 防护。云本身就需要这种能力来缓解针对自身资产的 DDoS 攻击，这意味着他们提供这些产品的边际成本相对于必须维护专用缓解机群的专业公司要低得多。由于网络正日益成为一种商品而非云的差异化因素（它们的竞争越来越多是彼此之间，而不是客户的现有物理基础设施），它们将提供云无关的接口和工具，比如 CNI，来简化跨网络设置的迁移。我期待 Kubernetes 所展示的模式——落地到一个通用的编排接口——在这里重复出现，或许类似于 Istio。即使你拥有自己的硬件，云也拥有独特的经济规模来推动基础性能的边界：例如 Azure 使用 FPGA 在 VM 之间通过 TCP/IP 实现 30Gbps，这不是你可能做得到的事情。

内部基础设施提供商仍然可以提供价值，特别是去处理那些云刻意回避的、不那么可扩展的复杂性：

编写和维护健康检查仍将足够复杂且特定于单个应用，难以被云产品商品化。用户身份、服务身份及其周边问题空间（认证、授权、SSO）的巨大复杂性一直抵制整体迁移到云，我认为这种情况在未来几年仍将持续。AWS IAM 和 GCP IAM 会继续逐步靠近，但会受限于企业需要无限可配置性与小公司需要简单性之间的矛盾。多区域冗余将继续需要应用层面的变更，区域间的延迟也将继续受限于光速。上一代开发的企业软件（如 Vertica）需要进行网络调优才能按设计运行。这将是一场有趣的竞赛——看云是否会提供这种调优能力，还是这些产品在现有云上的次优性能先把它们淘汰。

总体来说，网络、路由及相关问题将在未来几年被大幅商品化。

计算

计算大致可以拆分为编排、构建和部署。虽然每家公司都必须提供某种解决方案，但大多数小公司的需求很简单，很长一段时间以来它们的需求都被 Heroku 等观点鲜明的 PaaS 提供商满足了。大公司则继续从大多数 PaaS 提供商中成长出来，寻求更高的可配置性、更低的成本，以及足够的移植性以防止厂商锁定。

云提供商已经达到足够的规模，能够做出很少公司能做到的优化，而它们的采购规模使它们得以掌控 SSD 市场。最近，Amazon 宣布了 AWS EKS，与 Azure AKS 和 GKE 一起成为第三个承诺支持 Kubernetes 作为接口的主要云提供商，并提供统一的云计算接口。这个统一接口将降低跨云迁移成本，并表明云提供商将计算视为一种商品，它们将在价值上展开竞争。这种向接口的简化在 virtual kubelet 等项目中尤其明显，它将 Kubernetes 接口与 Azure ACI 或 AWS Fargate 的隔离性和可扩展性结合起来（例如，如果你在 Kubernetes 集群中不必解决网络安全问题呢？也许很快你就不必了！）。

云提供商已经赢得了编排，但其他途径仍然值得投入。

构建与配置的连带问题，尤其是容器镜像管理，仍将是一个重大挑战。保持镜像更新、安全地部署新版本、在能快速下载的地方（尤其是跨地理区域）存储镜像，都是难题。云提供商将在未来几年解决这个问题的一部分（特别是镜像存储），但其巨大的复杂性将阻止完全商品化。这是一个我预计云会推出一些非常受限的新模式的领域，这些模式能让新开发的应用程序减轻负担，但需要足够广泛的变更，以至于现有软件无法迁移。这里的防御护城河在于：快速的构建通常是危险的，而安全的构建通常是缓慢的——我们需要看到这个领域技术的改进，才能被云商品化。例如，目前大多数云构建器不缓存 Docker 层，因为创建它们的操作不是一致可重现的，这使得层缓存很容易被以微妙方式污染。这种无法激进缓存的情况让通用解决方案比定制构建方案慢得多。看到 Bazel 的理念作为安全且快速的应用构建路径参与竞争将会很令人兴奋，特别是当容器采用将应用和环境构建合并为原子产物时。由 Consul 或 Etcd 提供的应用配置将继续与应用代码和行为紧密耦合，阻止云对其进行商品化。预计像 AWS KMS 这样的密钥管理工具会随着时间推移逐步扩展，解决整个应用配置领域。多区域冗余继续需要应用层面的架构和设计，我预计这种情况会持续下去，直到它最终在存储层被商品化。GCP 正在尝试“默认多区域”策略，最明显的是 Cloud Spanner 产品，但目前采用它需要完全买入他们的平台并接受厂商锁定。我目前也不熟悉有多少公司在使用该产品，因为它还很新。最终，我认为 GCP 的默认多区域策略在其他云提供商提供类似产品以减轻锁定风险之前无法成功，因此我认为这是未来几年内部基础设施值得投入的安全领域。

存储

AWS 最早的成功之一是其 Simple Storage Service，能便宜且可靠地存储文件。随后产品不断扩展到 NoSQL、关系数据库，最近还有队列（Kinesis、Pub/Sub）。

仍然有不少领域适合内部投入：

虽然键值点查询将被商品化，但管理二级索引仍将与应用逻辑充分耦合，难以被云吸收。（我认为键值点查询尚未完全商品化，因为自己运行例如 Cassandra 集群相对于使用 Dynamo 有价格优势，但我预计云提供商将在未来五到十年侵蚀这一价格优势，而且老实说我怀疑它们已经侵蚀了完全加载成本。）在大规模下实现强一致性在云中仍难以捉摸，除了 Cloud Spanner。在非结构化数据上进行 schema 注册/强制/迁移，尤其是进入队列的数据。图数据库对于某些类别的机器学习和网络问题仍极为有用，而云中目前还没有强大的产品（例如 Titan）。存储是现有多区域产品最受限的地方。任何合理的多区域存储方案都将继续需要大量的内部投入。Cloud Spanner 和 Cosmos DB 是值得注意的例外，尽管我尚未看到大规模的广泛采用。GDPR 等合规和数据本地化要求的发展速度仍快于云目前所能支持的速度。长期来看，我预计云提供商会将其商品化。即使在今天，它们也更有能力在新出台数据和合规立法的国家快速开通新区域，但它们尚未采取多少行动来抓住这个机会（尽管 Azure 似乎略领先）。管理数据库快照也仍然是一个复杂而微妙的领域。云已经构建了基础组件，但仍需要拼接和维护，例如跨环境的管理。

批处理、流处理和机器学习

机器学习最近获得了大量关注，云提供商也渴望提供服务。但这并不意味着更传统的数据处理领域没有快速发展，批处理和流计算也都在快速演进。

或许共同的主题是它们演进得太快，实验多于标准：

AWS 有几十种产品，GCP 有更多，Microsoft Azure 甚至更多。Google Dataflow 是一个强大且低维护的方案，用于有界和无界事件计算。AWS Ironman 是一个完整的机器学习生态系统。我认为值得特别指出 AWS Deep Learning AMIs，这是一个有趣的举措，也是 API 标准化的好例子，因为它们支持 Google 的 TensorFlow API。自己管理镜像，尤其是每月或每两个月就要升级数十个底层库，这是一项具有挑战性且繁重的工作，而且是一个比看起来更有趣、可能更有影响力的实验。像 Google 的 TPU 这样的定制硬件是云提供商将深度投入以相互竞争的领域，而内部提供商根本无法获得与之竞争的经济规模。

尽管如此，这些平台大多仍然非常固执己见、受限，或缺乏广泛采用。，而大数据迁移往往又非常缓慢，我认为这个领域将继续为内部投入敞开大门。（即使是你非常希望完全商品化的东西，比如 Hadoop 生态系统管理，在大规模下仍然需要内部关注。）从 Lambda 到 Kappa 及 Dataflow 范式

这里还有一些有趣的、快速变化的外部因素，比如前面提到的 GDPR，并由此催生了 Apache Atlas 等相关解决方案。当你将这些因素与数据的边界走向（例如调优机器学习模型）结合起来时，数据领域继续适合内部投入。

工作流、工具和用户

把这一切合在一起，我想强调的信息不是云正在吞噬我们的职业，而是我们有一个非常特别的机会来演进我们的关注点和策略，以利用云的优势。通过今天选择正确的策略和投资领域，我们将使自己明天能够从事更有趣的工作，并在过程中对我们的用户和公司更有价值。

通过聚焦于工作流（告警、事件管理、调试、部署、构建、Provisioning/扩缩容/下线应用……）、接口（容器、协议、CLI、GUI……）以及我们用户的需求：最有趣的问题还在后面。
