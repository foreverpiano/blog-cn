2014 年 Uber 的服务上线模型。

2025-01-09 · 阅读原文

的核心在于理解服务上线流程，并找出能够加速该流程的杠杆。本文我们将构建一个来刻画这个上线过程，并通过运行该模型来验证一系列关于如何最有效地加快服务开通的假设。2014 年左右 Uber 的服务迁移策略。用系统建模来完善策略

本章将涵盖以下内容：

服务上线模型提示我们应该将精力重点放在哪些地方；使用 Github 上的 lethain/systems 包来构建系统模型，该模型已开源在 lethain/eng-strategy-models 仓库中；通过运行模型从其中学习洞见。

让我们来看看这个模型能告诉我们什么。

本章选自《Crafting Engineering Strategy》。

核心洞见

即使我们将模型设置为 100% 成功率（即完全没有错误），新服务请求的积压量仍会随时间持续增长。这清晰地表明，真正需要解决的问题并非服务开通团队当前流程的效率，而是根本的处理方式已经失效。

虽然招聘看起来很有吸引力，但模型显示在当前场景下这并非特别有效的解决方案。即使将服务开通团队中负责手动开通的人力增加 500%，也无法解决不断涌入的请求积压。

如果降低错误率不能解决问题，增加团队招聘也不能解决问题，那么我们必须彻底消除手动服务开通。最有前景的方案是转向自助服务开通模式，模型显示这种方式能够有效解决积压问题。

完善我们之前的结论：如果新招聘的人员能够专注于构建自助服务开通系统，并且我们能，那么增加招聘对团队是有帮助的。超级增长时代的生产力

草图

我们对服务开通的初始草图是一个简单的流水线：从服务请求开始，一步步推进直至分配服务器容量。其中某些步骤可能比其他步骤慢得多，但它让我们对各个阶段以及可能出错的地方有了直观认识。同时也让我们明确了需要衡量哪些指标来评估开通方法是否有效。

值得一提的是，从“招聘速率”到“产品工程师”，以及从“产品工程师”到“服务请求”之间的虚线。这些被称为“链接”（links），它们是会影响另一个存量但不直接流入的存量。

纯粹主义者可能会正确地指出，链接应该连接到“流”而不是“存量”。确实如此！然而，正如我们后面将草图转化为模型时会遇到的那样，这里实际上存在几个反直觉的元素，它们对准确建模这个系统是必要的，却会让草图的可读性降低。作为建模者，你会经常遇到这类权衡，必须决定在当下哪些选择最符合你的需求。

初始模型中最大的缺失是错误流——除了顺利通过的情况，还可能在某些步骤出错。我们将重点建模三种主要的错误流：

“信息缺失/不正确”在模型中会出现两次，并会将开通请求退回到最初收集信息的阶段。如果发生在端口分配阶段，这只是相对较小的一次回退；但如果发生在 Puppet 配置阶段，则是一次大幅度的倒退。“Puppet 错误”发生在倒数第二个存量“Puppet 配置已测试并合并”，会将请求退回上一个步骤。

将这些错误流加入草图后，我们就得到了一个相当完整且带有一定细微差别的服务开通流程视图。

注意，这两种错误流的组合意味着，一个服务可能已经接近完全开通，却因为 Puppet 错误从测试阶段退回到配置阶段，然后又因“信息缺失/不正确”被退回到最初步骤。这意味着如果出错，几乎所有的开通进度都可能丢失。

我们还可以引入更多细微差别，但目前的复杂度已经足以让我们从这个模型中获得大量洞见。

分析

研究我们的草图，有几点非常突出：

产品工程师的招聘将随着时间推移不断增加服务开通请求，但却没有相应增加负责服务开通的基础设施工程师招聘。这意味着存在一个隐含但真实的截止期限——必须在基础设施工程团队规模之外独立扩展这个流程。即使不构建完整模型也很明显，我们要么停止招聘产品工程师，要么将其转化为自助服务方案，否则就需要找到新的机制来抑制服务开通请求。错误率的大小将极大影响最终结果，尤其是“信息缺失/不正确”的错误率。这可能是寻找效率改进的最有价值起点。信息缺失错误比模型显示的代价更高，因为解决它们需要跨团队协调。相反，Puppet 测试错误可能比模型显示的代价更低，因为它们可以在同一团队内部解决，从而受益于快速的迭代循环。

现在我们需要构建一个模型，来帮助我们深入探究这些问题。

模型

你可以在 Github 上找到这个模型的完整实现，如果你想查看全部内容而非这些重点片段的话。

首先，我们先让成功状态运行起来：

HiringRate(10)
ProductEngineers(1000)
[PotentialHires] > ProductEngineers @ HiringRate

[PotentialServices] > RequestedServices(10) @ ProductEngineers / 10
RequestedServices > InflightServices(0, 10) @ Leak(1.0)
InflightServices > PortNameAssigned @ Leak(1.0)
PortNameAssigned > PuppetGenerated @ Leak(1.0)
PuppetGenerated > PuppetConfigMerged @ Leak(1.0)
PuppetConfigMerged > ServerCapacityAllocated @ Leak(1.0)

运行这个模型后，我们可以看到请求的服务数量随时间显著增长。这在意料之中，因为我们每轮最多只能开通 10 个服务。

然而，这也是最佳情况，因为我们尚未纳入三种错误状态：

唯一端口和名称分配可能因信息缺失或错误而失败；Puppet 配置也可能因信息缺失或错误而失败；Puppet 配置模板本身可能存在错误，需要返工。

让我们更新模型以包含这些失败模式，首先从唯一端口和名称分配开始。无错误版本如下：

InflightServices > PortNameAssigned @ Leak(1.0)

现在我们加入一个错误率，假设 20% 的请求因信息缺失而返回到“进行中的服务”存量。

PortNameAssigned > PuppetGenerated @ Leak(0.8)
PortNameAssigned > RequestedServices @ Leak(0.2)

接着我们对 Puppet 配置错误做同样处理：

# original version
PuppetGenerated > PuppetConfigMerged @ Leak(1.0)

# updated version with errors
PuppetGenerated > PuppetConfigMerged @ Leak(0.8)
PuppetGenerated > InflightServices @ Leak(0.2)

最后，我们对 Puppet 模板本身产生的错误也做类似修改：

# original version
PuppetConfigMerged > ServerCapacityAllocated @ Leak(1.0)

# updated version with errors
PuppetConfigMerged > ServerCapacityAllocated @ Leak(0.8)
PuppetConfigMerged > PuppetGenerated @ Leak(0.2)

即使错误率相对较低，我们也能看到引入这些错误后，系统的整体吞吐量受到了显著影响。

现在模型的基础已经建立，是时候开始运行它来更好地理解问题空间了。

实验

我们已经知道错误会影响吞吐量，但先从确定哪类错误影响最大开始——我们将每种错误的错误率单独从 20% 提高到 50%，并比较其影响。

为此，我们创建三个新的规格，每个规格将其中一种错误的错误率从 20% 提高到 50%，然后观察系统整体吞吐量受到的影响：

# test 1: port assignment errors increased
PortNameAssigned > PuppetGenerated @ Leak(0.5)
PortNameAssigned > RequestedServices @ Leak(0.5)

# test 2: puppet generated errors increased
PuppetGenerated > PuppetConfigMerged @ Leak(0.5)
PuppetGenerated > InflightServices @ Leak(0.5)

# test 3: puppet merged errors increased
PuppetConfigMerged > ServerCapacityAllocated @ Leak(0.5)
PuppetConfigMerged > PuppetGenerated @ Leak(0.5)

对比三种错误循环中将错误率从 20% 提高到 50% 的影响，我们可以了解模型对每种错误的敏感程度。

这张图解释了为什么“实验”如此重要：在画草图时我们曾经以为 Puppet 生成阶段的错误最重要，因为它会导致较长的回退；但实际上，流程早期出现极高错误率的影响更大，因为后面还有多个其他可能的错误，会使其影响进一步叠加放大。

接下来我们可以看看增加服务开通团队人手以手动开通更多服务的影响，这可以通过将“进行中的服务”存量的最大容量从 10 提高到 50 来建模。

# initial model
RequestedServices > InflightServices(0, 10) @ Leak(1.0)

# with 5x capacity!
RequestedServices > InflightServices(0, 50) @ Leak(1.0)

不幸的是，我们可以看到即使将团队容量提高 500%，也无法解决服务请求的积压问题。

虽然有一定改善，但积压量依然非常高。我们可以得出结论：单纯增加基础设施团队的招聘不是我们需要的解决方案，但让我们看看转向自助服务是否可行。

我们可以通过完全移除“进行中的服务”的最大容量限制来模拟转向自助服务的影响：

# initial model
RequestedServices > InflightServices(0, 10) @ Leak(1.0)

# simulating self-service
RequestedServices > InflightServices(0) @ Leak(1.0)

可以看到这样终于解决了积压问题。

至此，我们已经充分运行了这个模型，对它想告诉我们的内容有了清晰的认识。我们知道了哪些错误是最需要尽早投入改进的，也明确必须在不久的将来转向自助服务平台。
