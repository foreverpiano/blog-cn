核心发现

即使我们将该问题建模为 100% 成功率（即完全没有错误），新服务请求的积压量仍会随时间持续增加。这清楚地表明，需要解决的问题并非服务开通团队执行当前流程的效率，而是根本的运作方式本身已经失效。

虽然增加招聘看起来很有吸引力，但我们的模型显示这并不是特别有效的解决方案。即使将服务开通团队中负责手动开通服务的人员规模扩大 500%，也无法解决不断涌入的请求积压。

如果降低错误率无法解决问题，增加团队招聘也无法解决问题，那么我们必须彻底消除手动服务开通。 最有前景的方案是转向自助服务开通模式，模型显示这一方式能有效解决积压问题。

进一步细化我们先前的结论，如果能让新招聘的人员专注于构建自助服务开通平台，并且能，那么增加招聘对团队是有帮助的。超高速增长时代的生产力

初始草图

我们对服务开通的初始草图是一个简单的流水线：从服务请求开始，一步步推进直到最终分配服务器容量。其中某些步骤很可能比其他步骤慢得多，但它让我们对整个阶段和可能出错的环节有了直观认识，也让我们明确了可以衡量哪些指标来评估开通方法是否有效。

值得一提的是，从招聘速率到产品工程师，以及从产品工程师到服务请求之间的虚线。这些被称为“链接”（links），它们是会影响另一个存量（stock）但不直接流入其中的存量。

纯粹主义者会正确地指出，链接应该连接到“流”（flows）而不是存量。这没错！然而，正如我们将草图转化为实际模型时会遇到的那样，这里实际上存在几个反直觉的元素，它们对准确建模这个系统是必要的，却会让草图的可读性变差。作为建模者，你会经常遇到这类权衡，必须决定在当下什么选择最能满足你的需求。

初始模型中最大的缺失元素是错误流——除了顺利推进的情况，有时还会出现出错的情况。出错的方式有很多，但我们将重点建模以下三种错误流：

“缺失/错误信息”在模型中出现了两次，会将开通请求打回最初收集信息的开通阶段。如果发生在端口分配阶段，这只是一个相对较小的回退；但如果发生在 Puppet 配置阶段，则是一个大幅度的后退。“Puppet 错误”发生在倒数第二个存量“Puppet 配置已测试&合并”中，会将请求回退一步。

将这些错误流更新到草图中后，我们就得到了一个相当完整且细致的服务开通流程视图。

注意，这两种错误流的组合带来了这样一种可能：一个服务几乎完成开通，却因为 Puppet 错误从 Puppet 测试阶段退回到 Puppet 配置阶段，然后又因“缺失/错误信息”被打回初始步骤。这意味着如果出问题，几乎所有的开通进度都可能丢失。

我们还可以引入更多细节，但目前的复杂度已经足以让我们从这个模型中学到很多东西。

分析推理

研究我们的草图，有几点特别突出：

产品工程师的招聘会随着时间推移不断增加服务开通请求，但却没有相应增加负责服务开通的基础设施工程师招聘。这意味着这个流程存在一个隐含但真实的截止期限——它必须独立于基础设施工程团队的规模实现扩展。即使不构建完整模型也很明显，我们要么必须停止招聘产品工程师，要么将其转变为自助服务方案，否则就需要找到新的机制来减少服务开通需求。错误率的大小会对结果产生巨大影响，尤其是“缺失/错误信息”相关的错误。这可能是寻找效率改进的最有价值起点。缺失信息错误比模型显示的代价更高，因为解决它们需要跨团队协调。相反，Puppet 测试错误可能比模型显示的代价更低，因为它们应该可以在同一团队内解决，从而受益于快速的迭代循环。

现在我们需要构建一个模型来指导我们对这些问题的深入探究。

模型构建

如果你想查看完整实现而非这里强调的片段，可以在 GitHub 上找到该模型的完整代码。

首先，我们先让成功状态部分运作起来：

HiringRate(10)
ProductEngineers(1000)
[PotentialHires] > ProductEngineers @ HiringRate

[PotentialServices] > RequestedServices(10) @ ProductEngineers / 10
RequestedServices > InflightServices(0, 10) @ Leak(1.0)
InflightServices > PortNameAssigned @ Leak(1.0)
PortNameAssigned > PuppetGenerated @ Leak(1.0)
PuppetGenerated > PuppetConfigMerged @ Leak(1.0)
PuppetConfigMerged > ServerCapacityAllocated @ Leak(1.0)

运行这个模型时，我们可以看到请求的服务数量随时间显著增长。这很合理，因为我们每轮最多只能开通 10 个服务。

然而，这也是最佳情况，因为我们尚未纳入三种错误状态：

唯一端口和名称分配可能因缺失或错误信息而失败；Puppet 配置也可能因缺失或错误信息而失败；Puppet 配置模板本身可能包含错误，需要返工。

让我们更新模型以包含这些失败模式，首先从唯一端口和名称分配开始。无错误版本如下：

InflightServices > PortNameAssigned @ Leak(1.0)

现在我们加入错误率，假设 20% 的请求因缺失信息而返回到“进行中的服务”存量。

PortNameAssigned > PuppetGenerated @ Leak(0.8)
PortNameAssigned > RequestedServices @ Leak(0.2)

接着我们对 Puppet 配置错误做同样的处理：

# original version
PuppetGenerated > PuppetConfigMerged @ Leak(1.0)

# updated version with errors
PuppetGenerated > PuppetConfigMerged @ Leak(0.8)
PuppetGenerated > InflightServices @ Leak(0.2)

最后，我们对 Puppet 模板本身的错误做类似修改：

# original version
PuppetConfigMerged > ServerCapacityAllocated @ Leak(1.0)

# updated version with errors
PuppetConfigMerged > ServerCapacityAllocated @ Leak(0.8)
PuppetConfigMerged > PuppetGenerated @ Leak(0.2)

即使错误率相对较低，我们也能看到引入这些错误后，系统的整体吞吐量受到了显著影响。

现在模型的基础已经建成，是时候开始运行模型以更好地理解问题空间了。

模型演练

我们已经知道错误会影响吞吐量，但先让我们通过分别提高每种错误的发生率，找出哪种错误影响最大，并比较其影响。

为此，我们将创建三个新的规格说明，每个将其中一种错误的发生率从 20% 提高到 50%，然后观察系统整体吞吐量受到的影响：

# test 1: port assignment errors increased
PortNameAssigned > PuppetGenerated @ Leak(0.5)
PortNameAssigned > RequestedServices @ Leak(0.5)

# test 2: puppet generated errors increased
PuppetGenerated > PuppetConfigMerged @ Leak(0.5)
PuppetGenerated > InflightServices @ Leak(0.5)

# test 3: puppet merged errors increased
PuppetConfigMerged > ServerCapacityAllocated @ Leak(0.5)
PuppetConfigMerged > PuppetGenerated @ Leak(0.5)

比较将三种错误循环的错误率从 20% 提高到 50% 后的影响，我们可以了解模型对每种错误的敏感程度。

这张图说明了为什么运行模型如此重要：在画草图时我们曾假设 Puppet 生成阶段的错误最重要，因为它会导致大幅回退，但实际上早期阶段出现很高错误率的影响更大，因为后续仍存在多个其他可能的错误，会使其影响进一步放大。

接下来，我们可以看看增加服务开通团队人力以手动开通更多服务的影响，这可以通过将“进行中的服务”存量的最大容量从 10 提高到 50 来建模。

# initial model
RequestedServices > InflightServices(0, 10) @ Leak(1.0)

# with 5x capacity!
RequestedServices > InflightServices(0, 50) @ Leak(1.0)

遗憾的是，我们可以看到即使将团队容量提高 500%，也无法解决请求积压的问题。

虽然有一定效果，但积压的服务请求量依然极高。我们可以得出结论，增加基础设施团队招聘并非我们需要的解决方案，但让我们看看转向自助服务是否可行。

我们可以通过完全移除“进行中的服务”的最大容量限制来模拟转向自助服务的影响：

# initial model
RequestedServices > InflightServices(0, 10) @ Leak(1.0)

# simulating self-service
RequestedServices > InflightServices(0) @ Leak(1.0)

可以看到这样终于解决了积压问题。

至此，我们已经充分运行了模型，对它想告诉我们的内容有了很好的理解。我们知道了应该优先投资解决哪些错误，也明确了我们需要尽快转向自助服务平台。
