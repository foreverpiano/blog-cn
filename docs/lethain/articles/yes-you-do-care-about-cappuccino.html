是的，你确实在意 Cappuccino

2008-09-12 · 阅读原文

Cappuccino JavaScript 框架已经开源整整一周了。你浏览过教程，也试过让 280 Slides 出 bug，同时还狂热地低声念叨着那个玷污了 jQuery 官网的 JavaScript 摇滚明星。

然而在你脑海深处，却有一个疑问。这是个重要的问题。其实，该死的，你的问题不止一个，但我不知道是谁吃了最后一块芝士蛋糕，也不知道为什么现在还没到午饭时间。我在这里是要回答另一个问题：你在意 Cappuccino 吗？

是的，你确实在意。这并不是说你以后会使用 Cappuccino。你很可能不会，但你确实在意。

你为什么在意

Cappuccino 不仅鼓励，更要求以 API 为中心进行开发。由于大部分应用逻辑都在客户端处理，你的服务器只需要实现一个简单的 API，来服务那些无法在客户端完成的应用少量功能。想象一个获取 Flickr 图片并允许用户对其评分的应用程序。你可以在客户端获取 Flickr 图片、在客户端显示图片、也在客户端处理评分。你的服务器唯一需要做的就是记录图片的评分。实现这个功能的 API 会非常简单（一个 POST 请求，包含图片 ID、评分分数以及用于追踪用户的某个值），而且比传统 Web 应用所需服务器资源少得多。此外，这种以 API 为中心的方法还支持在多个平台上开发应用程序。该 API 可以同时服务 Cappuccino 应用和 iPhone 应用。灵活性是一件好事。Cappuccino 提倡代码复用。通过简化将代码拆分成多个文件——并让传统的面向对象继承更容易被利用——Cappuccino 让设计可复用的代码块变得更加容易。这意味着你很容易在其他项目中复用自己的组件，也更容易将他人的工作融入自己的项目。JavaScript 的单一命名空间——以及除了简单加载文件之外缺乏导入机制——在这方面存在不足，而 Cappuccino 在这方面迈出了宝贵的一步。Cappuccino 不仅提倡代码复用，还帮助管理复杂性。大型 JavaScript 项目可能会变得难以掌控，你常常需要编写自定义构建脚本来管理这种复杂性，但 Cappuccino 会帮助你降低复杂性。Cocoa——Cappuccino 所基于的 Objective-C 框架——反复使用一系列设计模式来无情地管理复杂性。委托模式能减少你需要执行的子类化工作，单例模式能让你轻松访问重要实例而无需直接引用，丰富的超类则暴露出大量可重写的方法来定制行为。这些加在一起，让遵循“一次且仅一次”原则变得比传统 JavaScript 容易得多。Cappuccino 在处理那些用传统 JavaScript 开发就会变得笨重的大型项目时，将会大放异彩。280 North 的创建者们在 Cappuccino 上重点强调的一点是，它能让你绕过 CSS 和 HTML 的跨浏览器地狱。这是一项重要优势，但就我个人而言，我不认为这是它最吸引人的地方。处理跨平台问题确实令人沮丧，但随着越来越多设计师和公司开始忽略 IE6，这个过程已经显著减轻了负担。Cappuccino 面向的是未来，而跨平台问题属于正在远去的过去，因此过分强调这一点似乎是对 Cappuccino 真正吸引力的不公。虽然很多人传统上对 JavaScript 重度框架（比如 YUI 或 ExtJS）感到不安，但我们终于来到了这样一个时刻：令人印象深刻的快速 JavaScript 性能正在变得无处不在。即使就在一年前，JavaScript 实现缓慢的问题还会更加棘手，但 Firefox、WebKit 和 Chrome 都拥有出色的 JavaScript 引擎，而且每个月都在变得更快。Internet Explorer 的 JavaScript 实现在原始速度上仍稍显落后，但 IE8 在这方面似乎也展现出了令人兴奋的前景（而且 Windows 用户还可以选择使用 WebKit 或 Firefox），因此我们可以说 JavaScript 已经足够快了。

你为什么很可能不会使用它

使用 Cappuccino 有许多令人信服的理由，但尽管如此，我还是怀疑大多数开发者永远不会接触到它（除了在个人时间里做些实验）。

你永远不会使用 Cappuccino 的最大原因，是它与其他人正在使用的技术差异太大。这也是 Lisp 始终无法在主流中流行起来的关键原因之一，最终我认为这也会阻止 Cappuccino 从小众走向普通。将 Cappuccino 建模成桌面应用工具包的一个副作用是，功能很廉价，但表现力却很昂贵。尽管存在种种问题，HTML 和 CSS 在展示内容方面却极为出色，而桌面应用在展示内容上通常采用简单得多的方式。我甚至要说，过去十年里 Web 设计的标准一直在不断提高并变得更加细腻，而桌面应用的设计进步却小得多，目前对桌面应用的期望远远低于对网站的期望。在 Web 设计的高标准下，廉价的功能只能做到这一步，大多数项目还需要廉价的表现力。HTML 和 CSS 是 Web 的通用语言，许多现有服务都以它们的形式提供数据。由于 Cappuccino 无法流利地使用这种通用语言，它在复用现有代码和与现有服务互操作方面的能力较弱（尽管它能很好地处理 JSON，因此那些以数据而非格式化数据为主的服务可以很好地互操作）。

正如我告诉你的，你确实在意 Cappuccino。它令人兴奋，而且在未来几个月乃至几年里，它将会激发一批跟风项目。这些项目能否进入主流使用，很可能取决于它们与现有 HTML/CSS 基础设施共存的能力。

在这条道路上，存在着功能易用性与表现易用性之间的平衡，以及强大的 Web 开发新途径。
