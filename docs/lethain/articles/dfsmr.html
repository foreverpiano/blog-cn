分布式有限状态机的实验

2018-06-02 · 阅读原文

现代大多数任务系统（如 RabbitMQ 或 Celery）都专注于任务排队，并由分布式的消费者集群主动拉取任务。这种方式效果非常好，但也把任务工作流的表达责任转嫁给了应用程序本身。如果你想要复杂的工作流，最终就会进入 Airflow 这类工具的平行宇宙——它们很优秀，但也相当笨重，并且是为协调批处理工作流而设计的，而非任务工作流。Erlang 的 gen_fsm 也有一些有趣的前人成果，但它被限制在单一语言环境中。

我想探索这个想法，于是原型化了一个名为 dfsmr（Distributed Finite State Machine Runner，分布式有限状态机运行器）的接口。这里的实验完全集中在接口设计上，具体实现只是为了能跑通接口而做的最小化版本（也就是说，实现质量并不高）。dfsmr 的 README 已经解释了其设计细节，因此这篇文章只会做一些更高层次的点评。

我发现，专注于纯粹的接口设计、完全脱离实现细节，是一件出乎意料地有收获的事。不久以前，我还会把接口设计当作最后才需要关注的部分。当年的 NoSQL 运动就以这一点闻名——强迫用户先去了解系统的各种约束，才能开始使用它，从而确保其接口只支持高度可扩展的模式，哪怕这要求每个用户都必须掌握大量概念。如今的基础设施设计则倾向于在系统内部承担巨大的复杂度，从而为用户提供简单、直观的接口（例如 Cloud Spanner）。我认为，替用户吸收复杂度确实是未来的方向。

gRPC 是一个特别有帮助的工具，它帮助我专注于接口设计，尤其是不让我“作弊”——把越来越多的键值对塞进定义模糊的 JSON Blob 里。特别是其中的流式方法，让我能够轻松实现类似 Redis MONITOR 命令的流式变更日志，这对理解和调试来说是不可或缺的辅助手段。

在开源生态中，确实存在这类工具的生存空间。最好它能高效支持延迟重试（大致来说是基于优先级队列的调度，而非 FIFO），能在多台服务器上分布式运行，并且运维开销很低。嗯，都是些简单的东西。
