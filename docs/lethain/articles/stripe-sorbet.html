Stripe 为什么要开发 Sorbet？（~2017）

2025-04-17 · 阅读原文

2010 年代许多高速成长的公司都通过来应对代码库日益增加的复杂度。而 Stripe 是个例外，它将单体分解的工作推迟到团队规模超过三千名工程师、核心 Ruby 单体也积累了十年开发历史之后。即使到现在，他们产品中很大一部分仍然在单体代码仓库中维护。可以毫不夸张地说，这一切之所以成为可能，完全得益于 Sorbet 的影响。我们应该分解单体应用吗？

Sorbet 是 Stripe 产品基础设施团队的工程师自主设计和实现的、专为 Ruby 打造的静态类型检查器。Stripe 的产品基础设施团队与其他公司的开发者体验（Developer Experience）或开发者生产力（Developer Productivity）团队有着相似的目标，但它更侧重于通过改进代码库自身的内部架构来提升生产力，而不是仅仅依赖外部工具或流程。

这一策略解释了 Stripe 为什么能将单体分解推迟这么久，也说明了产品基础设施团队如何通过投入开发者生产力，来应对一个由大量软件工程师维护的大型 Ruby 代码库所面临的挑战——由于快速招聘导致团队平均任职年限较低。

在结束这段引言之前，我想明确说明，这个策略是由 Stripe 的产品基础设施团队主导推动的，并非我个人的功劳。虽然我最终负责了该团队，但我不能把这个策略的思考归功于自己。实际上，我一开始对此持怀疑态度，更倾向于逐步迁移到现有的强类型编程语言——要么选择 Java 以获得更好的库支持，要么选择 Golang，因为 Stripe 团队已经比较熟悉。尽管我最初有所疑虑，但 Sorbet 项目最终用无可辩驳的成果说服了我。

这是《Crafting Engineering Strategy》中的一章。

策略与执行

产品基础设施团队正通过以下方式投资 Stripe 的开发者体验：

产品基础设施团队每六个月会选出三个最高优先级的领域，并将绝大多数精力投入其中。对其他领域我们只会提供最基本的支持。我们承诺在每次开发者生产力调研结束后，及时更新我们的优先级，并在每个季度的业务回顾（Quarterly Business Review）中分享我们的成果和最新优先级。本半年的三个最高优先级领域是：为 Ruby 代码库中价值最高的部分添加静态类型支持，以便我们能在本地和测试机器上运行类型检查器，更快地发现错误。支持选择性测试执行，让工程师能够在自己的机器上快速判断并运行最合适的测试，而不必等到测试在构建服务器上运行后再反馈。检测测试失败情况，以便我们获得更好的数据来指导未来的优先级排序。静态类型并不是提升开发者生产力的常规方案，因此当我们说这是最高优先投资领域时，需要做一些解释。更何况我们也承认，要让类型检查器达到实用水平，可能需要投入团队大量时间，耗时 12 到 24 个月。我们计划将这个类型检查器命名为 Sorbet，它能让我们继续在现有的 Ruby 代码库中进行开发。同时，它还能让产品工程师继续专注于开发新功能，而不是被迫将现有功能迁移到新的服务或编程语言。相反，我们的产品基础设施团队将集中负责类型检查器的开发以及在代码库中的初步推广。尽管团队规模固定，但产品基础设施团队有能力同时承担这两项工作。我们将采用混合策略：对特别复杂的区域进行深度介入添加类型，对较简单的部分则通过脚本改写代码的抽象语法树（AST）。如果这种方法最终失败（概率较低），对 Stripe 而言代价也是明确且可控的：大约相当于产品基础设施团队一半人力投入六个月，这是我们预估用来验证该方法是否可行的成本。根据我们对 Facebook Hack 项目的了解，我们相信能够构建一个可在本地运行、速度明显快于测试套件的静态类型检查器。虽然现在很难给出精确数字，但我们估计即使代码库规模很大，类型检查整个代码库的时间也能控制在 30 秒以内。这将带来极高的本地开发体验，即使我们没能加快本地测试的速度。即便我们确实加快了本地测试，类型检查还能帮助我们消除测试一直无法覆盖的一类错误——即在已针对预期场景进行测试、但未覆盖完全意外场景的代码路径中，传递了不符合预期的类型。一旦类型检查器得到验证，我们就可以逐步优先为代码库中价值最高的部分添加类型。我们无需把整个代码库全部加上类型，就能开始获得显著价值。为了支持这些静态类型工作，我们将推动 Stripe 的产品工程师开始采用命令查询职责分离（Command Query Responsibility Segregation，CQRS）设计模式。我们相信这能提供高杠杆的接口，帮助我们逐步向代码库中引入静态类型。选择性测试执行将允许开发者在本地快速运行合适的测试。这能让工程师保持紧凑的本地开发循环，从而加快高质量代码的开发。由于我们的代码库目前尚未采用静态类型，推断应该运行哪些测试相当具有挑战性。但凭借我们极高的测试覆盖率，以及所有测试在部署到生产环境前仍会全部执行的事实，我们相信可以依靠统计推断来判断修改某个文件时哪些测试最有可能失败。对测试失败进行检测是我们本半年的第三个、也是优先级最低的项目。本半年的重点纯粹是对那些我们对错误来源有较高把握的情况进行标注，无论是基础设施问题还是测试本身的问题。如有升级或问题，请在 #product-infra 频道中联系我们。

现状诊断

2017 年，Stripe 是一家约有 1000 名员工的公司，其中包括 400 名软件工程师。我们计划以每年约 70% 的速度扩张团队，以满足更广泛的产品组合需求，并扩展现有产品和基础设施来支撑用户增长。随着过去几年生产稳定性的提升，我们现在将重点转向提升开发者生产力。

我们对当前开发者生产力的诊断如下：

我们主要通过产品基础设施团队来为编写 Ruby 代码的软件工程师提供开发者生产力支持。该团队中专注于 Ruby 的部分目前约有十名工程师，未来也不太可能显著扩张。（如果我们确实要扩张，更可能会投入非 Ruby 生态，例如 Scala 或 Golang。）我们有两种主要机制来了解工程师的开发者体验。第一种是围绕部署时间、部署稳定性、测试覆盖率、测试耗时、测试不稳定性等标准生产力指标。第二种是每年两次的开发者生产力调研。从生产力指标来看，我们的测试覆盖率仍然极高，覆盖超过 99% 的代码行，但本地运行测试相当慢。在我们的基础设施中，测试运行速度较快，因为它们被分发到大量测试执行器上并行处理。本地测试已经慢到让越来越多的开发者只运行极小范围的测试子集，甚至完全跳过本地测试，直接把改动 push 上去。他们转而依赖我们的测试服务器对 pull request 分支运行测试。这种方式效果还不错，但显著拖慢了开发者的迭代速度，因为合并、构建和测试的完整周期需要二三十分钟才能完成。等到构建-测试周期完成时，他们往往已经失去专注力，可能需要几个小时才能重新回来处理结果。对于测试是否因为测试基础设施问题或测试本身的质量问题而变得越来越不稳定，团队内存在较大分歧。目前还没有可信的数据集能让我们在这两个原因之间做出归因。每半年一次的开发者生产力调研反馈支持了上述诊断，并增加了一些细微差别。最令人担忧的是，虽然在 Stripe 工作多年的老员工觉得在我们的代码库中仍然非常高效，但调研中越来越多来自其他公司、有较长工作年限的新员工却表示在我们的代码库中效率低下。具体来说，他们发现很难判断如何安全地对代码库进行修改。我们的产品代码完全实现在一个单一的 Ruby 单体应用中。只有一个例外是一个处理支付 tokenization 的窄范围 Golang 服务，我们认为它不在讨论范围内，原因有二。首先，它被有意保持得很窄，以承担我们的 SOC1 合规义务。其次，在那个环境工作的开发者并未对他们的生产力提出过担忧。我们的数据基础设施使用 Scala 实现。虽然这些开发者也有顾虑——主要是构建时间过长——但他们独立管理自己的构建和部署基础设施，而且这个团队规模相对较小。Ruby 并不是一门高性能的编程语言，但我们发现它对我们的需求来说已经足够高效。同样，其他语言在计算资源成本上可能更具优势，但我们绝大部分的支出都花在实时存储和批处理计算上。仅凭这些理由，我们也不会考虑替换 Ruby 作为核心编程语言。我们的产品基础设施团队约有十名工程师，支持大约 250 名产品工程师。我们预计这个团队会随时间适度增长，但肯定会显著低于产品工程师整体的增长速度。使用 Golang 和 Scala 的开发者经常请求更多的集中支持，但我们很难优先考虑这些需求，因为我们必须权衡为 240 名 Ruby 产品工程师改进体验，与为 10 名 Golang 工程师或 40 名 Scala 数据工程师改进体验之间的回报。如果引入更多编程语言，这个优先级排序问题会变得越来越困难，而我们实际上已经无法很好地支持额外的语言了。
