使用 Apache Beam 分析跨服务请求

2017-11-26 · 阅读原文

在对之后，我想在每种技术上都写几个简单的程序，来更好地理解它们的工作原理。我决定从 Apache Beam 开始，因为它允许你编写可以在其他多个平台上运行的程序，这样我有望复用同一个程序来评估多种不同的引擎。从 Lambda 到 Kappa 及 Dataflow 范式

作为一个玩具项目，我选择了在一个假设的微服务架构中分析跨服务请求。我选择这个问题有几个原因，首先是它不太适合使用固定大小的窗口，更适合采用 Google Dataflow 论文中描述的会话窗口（session windowing）策略来建模。它还很有趣，因为许多公司已经在所有请求中传递 request_id，如果 Apache Beam 能够成功提供实时的请求追踪分析，那将是对其方法的一个很有意思的验证。

环境准备

要跟着实践，最简单的方法是安装 Docker，克隆包含本示例代码的 Git 仓库，然后执行以下命令进入一个可以运行后续指令的终端：

git clone https://github.com/lethain/learning-beam
cd learning-beam
docker build -t "learning-beam" .
docker run -it learning-beam /bin/bash
cd /tmp
python traces.py --input logs/output.* --output output
cat output*

你也可以只使用 virtualenv 来完成，但调试时需自行承担风险！

git clone https://github.com/lethain/learning-beam
cd learning-beam
virtualenv env
. ./env/bin/activate
pip install apache_beam
python traces.py --input logs/output.* --output output
cat output*

如果你遇到问题，欢迎提交 Pull Request 或给我留言！

除了配置环境之外，其他细节与我们为本次分析生成的合成数据有关。我们生成的是以 JSON 表示的日志条目，每个日志条目对应跨服务请求中的一个 span。

{
  "time": 0,
  "id": "236ed3a7-5e13-4b4f-81c4-9b0f46a1e37f",
  "trace": "b8c9e238-0310-492d-9a5d-137acd552354",
  "origin": {
    "service": "app",
    "server": "app-1",
  },
  "destination": {
    "service": "user",
    "server": "user-1",
  }
}

作为一个简化假设，我们使用一个逻辑时钟，它在假设的基础设施开始发送请求时从 0 启动，其余行为与普通时钟一致（例如，时间 10 表示自基础设施启动以来已经过去了 10 秒）。

你可以使用 generate_logs.py 工具来生成样本日志，但更方便的做法是直接使用 logs 目录中预先生成的内容，这些日志已按五秒的桶进行分组。

将多个 span 组合成一个 trace

这个任务的目标是将一系列如下格式的日志行：

{
  "time": 0,
  "id": "236ed3a7-5e13-4b4f-81c4-9b0f46a1e37f",
  "trace": "b8c9e238-0310-492d-9a5d-137acd552354",
  "origin": {
    "service": "app",
    "server": "app-1",
  },
  "destination": {
    "service": "user",
    "server": "user-1",
  }
}

转换为如下格式的完整 trace：

[ebcf] 6 spans: cache (t: 0) -> app (t: 1) -> posts (t: 2) -> ...
[b6a1] 5 spans: search (t: 0) -> db (t: 1) -> queue (t: 2) -> ...
[325a] 2 spans: cache (t: 0) -> frontend (t: 1)

完整代码已在 Github 上开源，因此我将重点介绍两个有趣的部分：定义 Pipeline，以及编写用于将 span 组装成 trace 摘要的 DoFn 函数。

去掉配置部分后，整个 Pipeline 定义如下：

with beam.Pipeline(options=opts) as p:
    lines = p | ReadFromText(args.input, coder=JsonCoder())
    output = (lines
              | beam.Map(lambda x: (x['trace'], x))
              | beam.GroupByKey()
              | beam.ParDo(AssembleTrace())
   )
   output | WriteToText(args.output)

这段代码展示了：

创建一个 beam.Pipeline，读入我们的日志（JSON 格式），使用 trace key（本例中为 request_id）将其转换为 (key, value) 对，按 key 对数据进行分组（本例中是 trace），使用我们接下来会介绍的 AssembleTrace（继承自 beam.DoFn）来将分组后的 span 组装成一个 trace，最后将结果输出为文本文件。

（Github 中的代码还展示了窗口相关的处理，但本例并未使用该功能，因此它实际上是一个空操作。）

这个示例中另一个重要的代码是 AssembleTrace 类，接下来我们重点看看它：

class AssembleTrace(beam.DoFn):
    "DoFn for processing assembled traces."
        def fmt_span(self, span):
            "Format a span for joining."
            vals = (span['destination']['service'], span['time'])
            return "%s (t: %s)" % vals

        def process(self, element, window=beam.DoFn.WindowParam):
            "Take traces grouped by trace id and analyze the trace."
            trace = element[0]
            spans = list(element[1])
            spans.sort(key=lambda x: x['time'])
            services = " -> ".join([self.fmt_span(span) for span in spans])
            return ["[%s] %s spans: %s" % (trace, len(spans), services)]

其中的 process 方法是核心，它先解包 key 和分组后的值，对值进行排序，然后将它们拼接成一个表示 trace 的字符串。

就是这么简单：现在你有了一个能从包含 span 的日志中构建请求 trace 的简单 Beam 程序。这显然是一个非常简单的例子，也没有实现实时构建 span，但总体来说，我对写出一个还算有用的程序所需要的代码量之少（以及需要理解的概念之少）印象深刻。

接下来，我希望把它跑起来，并在流式 runner（可能是 Apache Flink）上实现 span 的实时组装！

我主要参考了以下资源：

Apache Beam Programming Guide，它比 WordCount Example Walkthrough 更新得多，后者经常会告诉你某些功能在 Python SDK 中不存在，但 SDK 文档却显示它们是存在的。读取 JSON 日志行时，我参考了这个例子，它工作得很好。窗口相关的处理参考了 Windowed wordcount 示例，以及一个编写 beam.DoFn 子类的例子。

总的来说，一旦我克服了对重载 | 运算符的烦躁，我对 Beam 的易用性还是相当满意的！

后来我为这个任务写了一个 Spark 版本作为快速对比，它甚至更短，而且同样简单：

import json
from pyspark.sql import SparkSession

def fmt_span(span):
    "Format a span for joining."
    vals = (span['destination']['service'], span['time'])
    return "%s (t: %s)" % vals

def build_trace(kv):
     trace, spans = kv
     spans = list(spans)
     spans.sort(key=lambda x: x['time'])
     services = " -> ".join([fmt_span(span) for span in spans])
     return "[%s] %s spans: %s" % (trace, len(spans), services)

def run():
    log_dir = 'logs/*'
    spark = SparkSession.builder.appName("RequestSessions").getOrCreate()
    lines = spark.read.json(log_dir).cache().rdd
    traces = lines.map(lambda x: (x['trace'], x)) \
                  .groupByKey() \
                  .map(build_trace)
    output = traces.collect()
    spark.stop()

if __name__ == '__main__':
    run()

我觉得避开 Beam 中的 parDo 术语会更简单一些，那感觉像是多余的概念负担，但整体上两者还是相当相似的。
