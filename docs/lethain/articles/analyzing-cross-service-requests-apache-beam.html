使用 Apache Beam 分析跨服务请求

2017-11-26 · 阅读原文

在对之后，我想用每种技术编写几个简单程序，以便更好地理解它们的工作原理。我决定从 Apache Beam 开始，因为它允许你编写可在许多其他平台上运行的程序，而这些平台正是我接下来希望深入研究的。这样我就能复用同一个程序来评估多种不同的引擎。从 Lambda 到 Kappa 以及数据流范式

作为一个玩具项目，我选择了在一个假设的微服务架构中分析跨服务请求。我选择这个问题有几个原因，首先是它不太适合使用固定大小的窗口，而更适合用 Google Dataflow 论文中描述的会话窗口（session windowing）策略来建模。它还很有意思，因为许多公司已经在所有请求中传递 request_id，如果 Apache Beam 能够成功提供实时的请求追踪分析，那将是对其方法论的一次有趣验证。

环境准备

要跟着实践，最简单的方式是安装 Docker，克隆包含本示例代码的 Git 仓库，然后执行以下命令进入一个可以运行命令的终端：

git clone https://github.com/lethain/learning-beam
cd learning-beam
docker build -t "learning-beam" .
docker run -it learning-beam /bin/bash
cd /tmp
python traces.py --input logs/output.* --output output
cat output*

你也可以只用 virtualenv 来完成，但调试时需自行承担风险！

git clone https://github.com/lethain/learning-beam
cd learning-beam
virtualenv env
. ./env/bin/activate
pip install apache_beam
python traces.py --input logs/output.* --output output
cat output*

如果遇到问题，欢迎提交 Pull Request 或给我留言！

除了配置环境之外，其他细节与我们为本次分析生成的合成数据有关。我们生成的是以 JSON 表示的日志条目，每个日志条目对应跨服务请求中的一个 span。

{
  "time": 0,
  "id": "236ed3a7-5e13-4b4f-81c4-9b0f46a1e37f",
  "trace": "b8c9e238-0310-492d-9a5d-137acd552354",
  "origin": {
    "service": "app",
    "server": "app-1",
  },
  "destination": {
    "service": "user",
    "server": "user-1",
  }
}

作为一个简化假设，我们使用了一个逻辑时钟，当假设的基础设施开始发送请求时，时钟从 0 开始，否则表现得像一个普通时钟（例如，时间 10 表示基础设施启动后已经过去了 10 秒）。

你可以使用 generate_logs.py 工具来生成示例日志，但直接使用 logs 目录中预先生成的内容会更方便，这些日志已经按五秒一个桶进行了分组。

将多个 span 组合成一个 trace

这个任务的目标是将一系列格式如下的日志行：

{
  "time": 0,
  "id": "236ed3a7-5e13-4b4f-81c4-9b0f46a1e37f",
  "trace": "b8c9e238-0310-492d-9a5d-137acd552354",
  "origin": {
    "service": "app",
    "server": "app-1",
  },
  "destination": {
    "service": "user",
    "server": "user-1",
  }
}

转换为格式如下的完整 trace：

[ebcf] 6 spans: cache (t: 0) -> app (t: 1) -> posts (t: 2) -> ...
[b6a1] 5 spans: search (t: 0) -> db (t: 1) -> queue (t: 2) -> ...
[325a] 2 spans: cache (t: 0) -> frontend (t: 1)

完整代码已上传到 Github，因此我将重点介绍两个有趣的部分：定义 pipeline，以及编写用于将 spans 组装成 span 摘要的 DoFn 函数。

去掉配置部分后，整个 pipeline 定义如下：

with beam.Pipeline(options=opts) as p:
    lines = p | ReadFromText(args.input, coder=JsonCoder())
    output = (lines
              | beam.Map(lambda x: (x['trace'], x))
              | beam.GroupByKey()
              | beam.ParDo(AssembleTrace())
   )
   output | WriteToText(args.output)

这段代码向我们展示了：

  1. creating a beam.Pipeline,
  2. reading in our logs (in their JSON format),
  3. transforming them into (key, value) pairs using the trace key (the request_id in this example),
  4. grouping the data by keys, in this case trace,
  5. using the AssembleTrace subclass of beam.DoFn, which we’ll cover next, to compile the grouped spans into a trace,
  6. outputting the resulting lines to text.

（Github 中的代码还展示了窗口相关的处理，但本例并未使用该功能，因此它实际上是一个空操作。）

本例中另一个重要的代码是 AssembleTrace 类，接下来我们就来看看它：

class AssembleTrace(beam.DoFn):
    "DoFn for processing assembled traces."
        def fmt_span(self, span):
            "Format a span for joining."
            vals = (span['destination']['service'], span['time'])
            return "%s (t: %s)" % vals

        def process(self, element, window=beam.DoFn.WindowParam):
            "Take traces grouped by trace id and analyze the trace."
            trace = element[0]
            spans = list(element[1])
            spans.sort(key=lambda x: x['time'])
            services = " -> ".join([self.fmt_span(span) for span in spans])
            return ["[%s] %s spans: %s" % (trace, len(spans), services)]

其中 process 方法是关键，它会解包 key 和分组后的值，对值进行排序，然后将它们拼接成一个表示 trace 的字符串。

就是这样：现在你有了一个简单的 Beam 程序，它可以从包含多个 span 的日志中构建出请求 trace。这显然是一个非常简单的例子，并且没有实现实时构建 span，但总体而言，我对它能如此轻松地写出一个多少有些用处的程序印象深刻（包括我需要理解的概念竟然如此之少）。

接下来，我希望能让这个程序在一个流式 runner（可能是 Apache Flink！）上运行并实时组合 spans。

我主要参考了以下资源：

  • Apache Beam Programming Guide which is significantly more up-to-date than the WordCount Example Walkthrough, to the extent that the walkthrough will often tell you that things don’t exist in the Python SDK, but the SDK documentation shows they do.
  • For reading in the JSON log lines, I followed this example, and it worked as advertised.
  • The Windowed wordcount example for windowing, and an example of writing a beam.DoFn subclass.

总的来说，一旦我克服了对重载 | 操作符的不适之后，我对 Beam 的易用性印象非常深刻！

后来我还为这个任务写了一个 Spark 版本作为快速对比，它甚至更短，而且差不多一样简单：

import json
from pyspark.sql import SparkSession

def fmt_span(span):
    "Format a span for joining."
    vals = (span['destination']['service'], span['time'])
    return "%s (t: %s)" % vals

def build_trace(kv):
     trace, spans = kv
     spans = list(spans)
     spans.sort(key=lambda x: x['time'])
     services = " -> ".join([fmt_span(span) for span in spans])
     return "[%s] %s spans: %s" % (trace, len(spans), services)

def run():
    log_dir = 'logs/*'
    spark = SparkSession.builder.appName("RequestSessions").getOrCreate()
    lines = spark.read.json(log_dir).cache().rdd
    traces = lines.map(lambda x: (x['trace'], x)) \
                  .groupByKey() \
                  .map(build_trace)
    output = traces.collect()
    spark.stop()

if __name__ == '__main__':
    run()

我觉得避开 Beam 中的 parDo 术语会稍微简单一些，那个术语感觉增加了不必要的概念负担，但整体来说两者还是相当相似的。
