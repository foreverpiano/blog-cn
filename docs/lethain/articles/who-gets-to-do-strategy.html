谁能参与制定战略？

2025-03-06 · 阅读原文

如果你和足够多有抱负的领导者交流过，就会发现一个普遍的观念：他们认为自己必须先获得晋升，才能开始参与战略工作。 这个想法被广泛接受，但在我看来，它从根本上是错误的：你可以在组织的任何位置上参与战略工作。 只是需要采取不同的策略和方法。

《Staff Engineer》和《The Engineering Executive’s Primer》两本书中都有关于战略的章节。虽然两章内容差异很大，但都为推动组织对复杂问题的思考提供了切实可行的路径。本章将阐述我的观点：组织中的任何人都能为战略工作做出有意义的推进，前提是你要诚实地面对自己能掌握的工具，并认真思考如何运用它们。

我们将深入探讨的主题包括：

作为工程师（尤其是没有被明确授予战略权限的工程师）如何制定战略；作为工程高管，如何在负责组织决策的同时制定战略；即使在困难环境中——例如没有现有战略、承认某些问题在政治上敏感，或是激励机制不一致导致难以达成共识——你依然能如何制定工程战略；如果本书的观点是“每个人都应该参与战略制定”，那么是否仍然存在一些人不应该这么做？

读到最后，你 hopefully 会认同：尽管总是会受到各种约束，工程战略其实对每个人都是可及的。

本章选自《Crafting Engineering Strategy》。

作为工程师制定战略

人们很容易被高管自上而下的战略方式所吸引，以至于相信不存在其他可行的战略机制。但实际上是存在的！

《Staff Engineer》一书中介绍了一种我称之为“先取五例，再做综合”的方法，它通过以下方式来制定战略：

记录组织中五个当前和历史相关决策的制定过程。这是一个扩展的探索阶段；将这五个文档综合成一份诊断和政策。你在命名组织中隐含的战略，因此别人很难合理地质疑你没有权限做战略——你只是在描述已经发生的事情。

到了这一步，组织要么对你的描述感到舒服——也就是他们当前的战略，要么感到不舒服，那么你就推动了一场关于如何修正方法的对话。唤起意识往往就足以驱动战略变革，而且这样做并不需要高管给予任何明确的授权。

当仅仅唤起意识还不够时，我在低权限场景下发现另一种非常有效的方法，就是我在《An Elegant Puzzle》中写过的“”：示范、记录与分享。

示范你希望他人采用的方法，让他们容易观察到你如何改变了自己的做事方式；记录这种方法、背后的思考以及如何采用它；将文档分享出去。如果人们看到你用这种方法取得了成功，他们就很可能去效仿你。

你可能会对这种基于影响力的方法持怀疑态度。不过，正如我们在下一节将讨论的，即使是高管推动的战略，也高度依赖于影响力。

战略考古学

Vernor Vinge 1999 年出版的《A Deepness in the Sky》引入了“软件考古学家”这个概念，指那些通过拼凑数千年软件残片来创造功能的人。

虽然用法略有不同，但我有时会把“先取五例，再做综合”的方法视为进行战略考古学。仅仅通过记录过去发生的事情，我们就能更容易理解现在，并影响未来。

作为高管制定战略

关于高管职位最大的误解——无论是非高管还是即将犯下一系列令人后悔错误的新高管——就是认为高管可以不受约束地工作。这是错误的：高管面临的约束极多。他们有预算、CEO 的愿景、需要取悦的同级，以及需要激励的团队。他们可以暂时让其中任何一方失望，但长期来看必须全部满足。

尽管如此，高管确实拥有更大的自由度来要求和敦促他人参与他们支持的战略。《The Engineering Executive’s Primer》中关于战略的章节（撰写工程战略）是对本书的简要总结，但并未详细说明高管战略与非高管战略的区别。

高管制定战略的方式与工程师的区别可以归结为以下几点：

高管可以强制要求遵守他们的战略，这极大地扩展了他们的政策选项。工程师无法阻止拒绝遵守其政策的人获得晋升，但高管可以；强制要求只有在有后果的情况下才有意义。如果高管不愿意为不遵守强制要求的行为实施惩罚，那么下达强制要求的权力就毫无意义；如果因为得不到同级高管的支持而无法执行强制要求，也是如此；即使高管不愿意使用强制手段，他们在组织中也拥有极高的可见度和接触面，可以大力倡导自己偏好的战略；无论是接触面还是强制权力，都不能提升高管诊断问题的能力，但两者往往会制造出“正在取得进展”的假象。这就是为什么高管的战略有时会失败得如此惨烈，却又能长期存在。

因此，我的经验是：高管做战略相对容易，但学会把战略做好的难度要大得多，而且避免严重错误的安全网也更少。此外，高管糟糕战略的后果通常比工程师的影响范围大得多。等到成为高管再去做战略，是一条通往灾难的道路——哪怕从远处看它好像更容易。

在其他角色中制定战略

即使你既不是工程师也不是工程高管，你依然可以参与制定工程战略，只不过需要采取更加依赖影响力的方法。

工程组织通常认为自己最懂工程，这大体上是正确的，但并非总是如此。有时候产品经理曾经是工程师，拥有大量相关经验；还有些时候，比如在中，工程师们也所知有限，反而能从外部视角中获益。如何采用大语言模型（LLMs）？

在充满挑战的环境中制定战略

好的战略通过准确诊断环境，并选择能够应对这些环境的政策来取得成功。你很可能会在组织内部限制导致这两件事都充满挑战的环境中工作，因此值得承认这一点，并讨论如何应对这些挑战。

低信任环境

有时候，诊断问题的困难源于能力不足。战略能力差在某种程度上是比较容易解决的问题：只要多做战略工作就能积累专业能力。但在另一些情况下，你可能把问题看得相当清楚，却不知道如何公开承认这些问题，因为组织文化会对此表示不满。后一种是根植于低信任的诊断问题，会让事情变得更加困难。

关于的那一章认识到了这个问题，并承认有时你必须对战略中有争议的部分“低声细语”：工程策略中的诊断

当你撰写战略时，经常会发现自己要在两个尴尬选项中做出选择：说出关于公司或公司内某人的尴尬或不舒服的事实，或者省略诊断中某个关键部分，而这个部分对理解整体思考至关重要。每当遇到这种两难，我的建议是：找到一种方式把诊断包含进去，但要重新表述成更容易接受的陈述，避免过于狭隘地指责某人。

简而言之，解决低信任问题的方法，就是把难处理的信息翻译成更温和、更委婉、可以公开表达的版本。如果你目标是追究责任，这可能会让人感觉不诚实或道德妥协，但战略的目标是做出更好的决策，这和追究过去责任是完全不同的两回事。

Karpman 戏剧三角

有时候，当诊断看起来特别明显，而人们却不同意你时，原因可能是你错了。当我对自己非常熟悉的事情明显判断错误时，通常是因为我陷入了 Karpman 戏剧三角，把所有参与者都映射成了迫害者、拯救者或受害者的角色。

判断力低下的环境

即使你出色地完成了诊断挑战的工作，要在组织内推动大家就如何应对达成一致也可能非常困难。有时这是因为确实存在复杂的权衡。例如在的案例中，关于如何处理 Index 基于 Java 的技术栈产生了激烈争论，最终达成了一项让任何一方都不特别满意的妥协：如何整合 Stripe 收购的 Index？（2018）

将是否引入 Java 的决策推迟到以后：引入 Java 与我们现有的工程战略不符，但目前我们也无法让利益相关者就如何处理这个决策达成一致。此外，我们认为尝试解决这个问题会分散精力，影响我们在六个月内推出联合产品的及时目标。我们将在首次发布之后再继续讨论这个问题。

这个妥协就是一个困难权衡的好例子：虽然各方都不完全同意这个做法，但大家都理解必须面对相互冲突的优先级。

但在其他情况下，有些政策选择根本说不通，通常是因为组织内的判断力较差。有时这不是技术判断的问题，而是把个人利益置于公司需求之上的糟糕判断。Calm 的战略就处理了这类问题的一部分，并在诊断中明确承认：“我们是一家产品工程公司！”——Calm 的工程战略

我们正在大量争论是否采用新技术和重写代码。大部分分歧都围绕采用新技术或将现有组件重写到新的技术栈上展开。例如，我们是应该扩展这个功能，还是必须先把它迁移到一个服务里再扩展？我们是应该把数据加到现有数据库里，还是应该把它移到一个新的 Redis 缓存中？JavaScript 是否已经够用，还是我们需要用 Go 重写这个功能？

在这种情况下，你的战略是在尝试教育同事认识他们正在做的权衡，但最终有时人们还是会不同意你的战略。这时请记住，大多数有趣的问题都需要迭代解决。写下你的战略并分享它，会开始改变组织的想法。即使这种改变一开始很慢，也不要气馁。

处理缺失的战略

关于的战略引入了一个常见问题：不清楚公司其他部门到底想要什么。在那个案例中，看起来很可能会发生裁员，但不清楚规模会有多大：驾驭私募股权所有权

根据一般做法，我们新的私募股权所有者很可能希望我们通过裁员来降低研发人力成本。但我们没有任何具体细节来做出结构化的决策，而且我们的应对方式会根据裁员规模有很大差异。

许多领导者遇到这种模糊性后，会认为在该决策做出之前，自己无法推进战略。虽然不知道细节确实不方便，但被模糊性卡住永远是错误的选择。

相反，你应该像那份私募股权战略所做的那样：接受模糊性是一个需要绕过去的事实。它没有放弃，而是采取了一系列新的政策，通过改变来开始降低成本增长，并认识到一旦裁员目标明确，还会有进一步的行动需要采取。工程组织的资历结构模型

每当你在处理棘手问题时，总能找到很多理由来解释为什么无法取得进展。领导力的关键就是找到方法，尽管存在这些问题，依然能够向前迈进。缺失战略永远应该是你诊断的一部分，但绝不是你不能做战略的理由。

谁不应该做战略

根据我的经验，几乎从来不存在你不能做战略的理由，但有两个特定场景下做战略可能没有意义。第一个不是关于“谁”，而是关于的问题：有时候组织里已经有太多战略工作，再去做更多反而会分散注意力。如果组织的其他部分已经在处理同一个问题，请尽量直接与他们合作，而不是制造竞争性的工作。何时撰写策略，以及写多少？

另一种应该避免做战略的情况是，你试图满足一种情感需求——想要做出直接、立即的影响。分享一份深思熟虑的战略总是会推动进展，虽然它通常是改变组织信念这种缓慢、渐进的进展。即使是高管自上而下的明确战略，也常常在组织的某些角落被忽视，而自下而上的战略则通过示范、记录和分享慢慢传播。投入战略工作需要你有长期取胜的耐心，哪怕这一周或这一季度几乎看不到进展。

总结

当你读完本章时，我希望你也相信：无论你是工程师还是高管，你都可以在自己的组织中参与战略工作。我还希望你认识到，你所使用的工具会因为你在组织中的位置和所处的文化环境而有很大差异。无论你是需要通过示范，还是可以直接强制，总有一种机制适合你。
