Python 处理大型 CSV 和 XML 文件

2009-01-22 · 阅读原文

和大多数人一样，我从未意识到自己会需要处理大型文件。 我知道会有一些包含数兆字节数据的文件，但从未料到我会恳求 Perl 处理数百兆字节的 XML，更没想到这周我竟然要让 Python 把 6.4 GB 的 CSV 转换成 6.5 GB 的 XML。

几次内存溢出的经历会教会你，处理大型文件的核心技巧其实很简单：使用把所有内容当作流来处理的代码。 对于输入，从磁盘分块读取；对于输出，频繁地写入磁盘，让系统内存保持轻负载继续运行。

当你亲自读写文件时，这一点相对容易正确实现……

from __future__ import with_statement # for python 2.5
with open('data.in','r') as fin:
with open('data.out','w') as fout:
for line in fin:
fout.write(','.join(line.split(' ')))

……而比错误实现要容易得多……

with open('data.in','r') as fin:
    data = fin.read()
data2 = [ ','.join(x.split(' ')) for x in data ]
with open('data.out','w') as fout:
fout.write(data2)

……至少在简单情况下是这样的。

在 Python 中加载大型 CSV 文件

Python 拥有一个优秀的 csv 库，开箱即用就能处理大型文件。算是吧。

>> import csv
>> r = csv.reader(open('doc.csv', 'rb'))
>>> for row in r:
...     print row
... 
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
_csv.Error: field larger than field limit (131072)

盯着模块文档看了半天，我没找到任何有用的内容。于是我打开了 csv.py 文件，证实了错误信息中 _csv 的暗示：该模块的大部分代码（尤其是输入解析部分）是用 C 而非 Python 实现的。

盯着那个错误看了一会儿，我开始幻想如何用 StringIO 做一个流预处理器，但很快意识到，为了实现这个，我得自己重新写一个 csv 版本。

于是我又回去翻博客，其中一篇终于给了我一直在找的那粒魔法信息：csv.field_size_limit。

>>> import csv
>>> csv.field_size_limit()
131072
>>> csv.field_size_limit(1000000000)
131072
>>> csv.field_size_limit()
1000000000

没错。就这么简单。之后这个家伙就正常工作了。

好吧，几乎是这样。我确实在处理到 1.5 GB 处遇到了一个 NULL 字节的问题。因为流处理代码使用的是基于 C 的 IO，NULL 字节会导致数据读取突然中断且无法恢复。为了解决这个问题，我们需要对流进行预处理。你可以在 Python 中通过封装文件对象用自定义类来清理每一行后再返回，但我为了简便选择了命令行工具。

cat data.in | tr -d '\0' > data.out

之后，那个 6.4 GB 的 CSV 文件就没有任何问题地处理完成了。

在 Python 中创建大型 XML 文件

这一步——把 CSV 的每一行转换成 XML 元素——进行得相当顺利，这要归功于 xml.sax.saxutils.XMLGenerator 类。创建元素的 API 算不上简洁，但它——不像许多更具创造性的方案——行为可预期，并且有一个杀手级特性：它能正确地将输出写入流。

正如我之前提到的，创建元素的机制比较啰嗦，所以我写了几个包装函数来简化（注意我把输出发到标准输出，这样我就可以直接 print 字符串到正在生成的文件中，例如创建 XML 文件的版本声明）。

从这里开始，使用方式是这样的：

print """<?xml version="1.0" encoding="utf-8'?>"""
start_tag(u'list', {u'id':10})
for item in some_list:
start_tag(u'item', {u'id': item[0]})
tag(u'title', body=item[1])
tag(u'desc', body=item[2])
end_tag(u'item')
end_tag(u'list')
g.endDocument()

我在数据中遇到的唯一问题是有些换页符（^L 即 12 即 x0c）到处飘，它们会干扰 XML 编码器，但你可以在很多地方把它们去掉，例如重写主循环：

for item in some_list:
    item = [ x.replace('\x0c','') for x in item ]
    # etc

真的，XMLGenerator 就这么顺利地工作了，即使在处理相当大的文件时也是如此。

性能表现

虽然我的脚本生成的 XML 元素种类与上面的例子有所不同，但复杂程度差不多，性能也相当合理。将 6.4 GB 的 CSV 处理成 6.5 GB 的 XML 花了 19 到 24 分钟，这意味着它每秒大约能读-处理-写 5 兆字节的数据。

从原始速度来看，这算不上特别惊人，但用 Perl 的 XML::Twig 做类似操作（实际上是 XML 到 XML 而非 CSV 到 XML）时，处理一个约 100 兆字节的文件需要 8 分钟，所以我对 Python 标准库的质量及其处理大型文件的能力还是相当满意的。

标准库的广度和深度真的让 Python 成为编写这类一次性简单脚本的乐事。 要是它有 Perl 那样更易用的正则表达式语法就好了……

这就是数据的奇特本质，它与媒体文件不同：数据文件在拥有足够强大的系统时，可以变得无限大。而媒体文件虽然可以非常庞大（一部高质量电影可能有几个 GB），但始终有可预测的上限。如果你正在处理大型文件，那很可能是在处理一家公司过去十年的日志，或者他们整个 MySQL 数据库的转储。↩我真的很想喜欢新的 Python 文档。 我是说，它看起来确实好多了，但我认为它实际上让我更难找到想要的东西。 我觉得他们遇到了和 Django 文档一样的问题：越是定制化文档，使用文档的学习曲线就越陡峭。我认为最主要的问题还是文档的不完整性让我头疼。他们肯定覆盖了所有重要和常用的组件（还附有有用的概述和示例），但新文档往往连不那么重要的方法和对象都不提及。 目前，我只好频繁地使用 dir 命令来探索了。↩
