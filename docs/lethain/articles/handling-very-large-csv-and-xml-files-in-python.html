Python 处理超大 CSV 和 XML 文件

2009-01-22 · 阅读原文

和大多数人一样，我从未想过自己会需要处理超大文件。 我知道会有一些几兆字节的数据文件，但从未预料到我会求着 Perl 处理几百兆的 XML，更没想到这周我会让 Python 把 6.4 GB 的 CSV 转换成 6.5 GB 的 XML。

几次内存溢出的经历会教会你，处理大文件的核心技巧其实很简单：使用把一切当作流来处理的代码。 对于输入，从磁盘分块读取；对于输出，频繁写入磁盘，让系统内存保持轻松。

当你亲自读写文件时，正确实现这一点其实更容易……

from __future__ import with_statement # for python 2.5
with open('data.in','r') as fin:
with open('data.out','w') as fout:
for line in fin:
fout.write(','.join(line.split(' ')))

……比错误实现要容易得多……

with open('data.in','r') as fin:
    data = fin.read()
data2 = [ ','.join(x.split(' ')) for x in data ]
with open('data.out','w') as fout:
fout.write(data2)

……至少在简单情况下是这样的。

在 Python 中加载大型 CSV 文件

Python 有一个非常优秀的 csv 模块，开箱即用就能处理大文件。算是吧。

>> import csv
>> r = csv.reader(open('doc.csv', 'rb'))
>>> for row in r:
...     print row
... 
Traceback (most recent call last):
  File "<stdin>", line 1, in <module>
_csv.Error: field larger than field limit (131072)

盯着模块文档看了半天，我没找到有用的信息。于是我打开 csv.py 文件确认了错误信息中 _csv 所暗示的内容：该模块的大部分代码（尤其是输入解析部分）是用 C 而非 Python 实现的。

盯着那个错误看了一会儿，我开始幻想如何用 StringIO 做一个流预处理器，但很快意识到，要做到这一点，我几乎得自己重写一个 csv 版本。

于是继续翻博客，其中一篇终于提供了我苦苦寻找的关键信息：csv.field_size_limit。

>>> import csv
>>> csv.field_size_limit()
131072
>>> csv.field_size_limit(1000000000)
131072
>>> csv.field_size_limit()
1000000000

没错，就是这么简单。设置之后，这家伙就正常工作了。

嗯，差不多吧。我确实在处理到 1.5 GB 处遇到了一个 NULL 字节的问题。因为底层的流式代码使用的是基于 C 的 IO，NULL 字节会导致数据读取突然中断且无法恢复。要解决这个问题，我们需要对流进行预处理。你可以在 Python 中通过封装文件对象、用自定义类在返回每一行前清理内容来实现，但我为了简单起见，直接用了几个命令行工具。

cat data.in | tr -d '\0' > data.out

处理完这个问题后，6.4 GB 的 CSV 文件就顺利无误地处理完了。

在 Python 中生成大型 XML 文件

这部分工作——把 CSV 的每一行转换成 XML 元素——进行得相当顺利，这要感谢 xml.sax.saxutils.XMLGenerator 类。创建元素的 API 算不上简洁，但它——和许多更花哨的方案不同——行为可预测，而且有一个杀手级特性：能正确地将输出写入流。

正如我提到的，创建元素的代码比较繁琐，所以我写了几个包装函数来简化（注意我把输出发送到标准输出，这样我就可以直接打印字符串到正在生成的文件中，例如创建 XML 文件的版本声明）。

使用方式如下：

print """<?xml version="1.0" encoding="utf-8'?>"""
start_tag(u'list', {u'id':10})
for item in some_list:
start_tag(u'item', {u'id': item[0]})
tag(u'title', body=item[1])
tag(u'desc', body=item[2])
end_tag(u'item')
end_tag(u'list')
g.endDocument()

我实际遇到的唯一问题（在我的数据中）是一些四处游荡的换页符（^L 即 12 即 0x0c），它们会干扰 XML 编码器。你可以在很多地方把它们过滤掉，比如改写主循环：

for item in some_list:
    item = [ x.replace('\x0c','') for x in item ]
    # etc

真的，XMLGenerator 就这么正常工作了，即使面对相当大的文件也一样。

性能表现

虽然我的脚本生成的 XML 元素种类和上面的例子不同，但复杂度差不多，性能也相当不错。将 6.4 GB 的 CSV 处理成 6.5 GB 的 XML 花了 19 到 24 分钟，也就是大约每秒能读-处理-写 5 兆字节左右。

从原始速度来看，这不算特别惊人，但用 Perl 的 XML::Twig 做类似操作（实际上是 XML 到 XML 而不是 CSV 到 XML）时，处理一个约 100 兆的文件就花了 8 分钟，所以我对 Python 标准库的质量以及它处理大文件的能力还是相当满意的。

标准库的广度和深度真的让 Python 成为编写这类一次性简单脚本的乐趣之选。 要是它能有 Perl 那种更易用的正则表达式语法就好了……

这就是数据的奇特之处，也正是它与媒体的不同：数据文件——借助足够强大的系统——可以变得无限大。而媒体文件虽然可以非常庞大（一部高质量电影可能有几个 GB），但总有可预期的上限。如果你正在处理大文件，那你很可能面对的是公司过去十年的日志，或者他们整个 MySQL 数据库的转储。↩我真的很想喜欢新的 Python 文档。 我是说，它的外观确实好看多了，但我认为它实际上让我更难找到想要的东西。 我觉得他们遇到了和 Django 文档同样的问题：对文档自定义得越多，使用这份文档的学习曲线就越陡。我认为最主要的问题还是文档的不完整性让我头疼。他们肯定覆盖了所有重要和常用的组件（还附带了有用的概述和示例），但新文档往往连不太重要的方法和对象都不提及。目前，我不得不频繁地使用 dir 命令。↩
