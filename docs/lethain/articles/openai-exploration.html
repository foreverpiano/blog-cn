探索 OpenAI

2023-04-12 · 阅读原文

我一直没有花太多时间去尝试最新的 LLM，于是决定抽时间好好玩玩。我特别感兴趣的是用 embeddings 来为用户 prompt 补充额外相关数据这个场景（比如在用户询问工单进度时，把他们最近工单的当前状态插入到 prompt 中）。这个用法很有意思，因为现有公司和产品非常容易落地，我猜 Stripe 的 GPT-4 文档集成大概也是这么实现的。

为了实际尝试，我写了一个脚本：把我的所有文章转换成 embeddings，对用户输入的 prompt 进行 tokenization，找出我内容中最相关的部分，把它们注入到扩展后的 prompt 中，最后把这个扩展 prompt 发送给 OpenAI 的 API。

你可以在 Github 上看到代码，下面是这个项目的笔记。

这次探索受到了 Eugene Yan 和 Simon Willison 最近工作的启发。我要特别感谢 Eugene Yan，他提出的建议显著提升了回答质量。

我发现这些示例没有一个能完全按照文档运行，但经过一番摸索、重温 Pandas 之后，最终还是让它们工作起来了。

项目

我的项目目标是让 OpenAI API 在回答问题时，能了解我个人在博客、StaffEng 和 Infrastructure Engineering 上的所有写作内容。具体来说，就是把 Hugo 博客的 Markdown 文章转换成 embeddings，然后供 OpenAI 使用。

你可以在 Github 上阅读代码。我完全没有花功夫让它易读，但它是一个完整的例子。你只需把第 112 行的路径改成你自己博客的内容目录，就能用在自己的文章上。（另外记得把第 260 行的 prompt 也改一下。）

下面是这个程序运行时的截图。

这个项目挺有意思的，因为它确实能跑起来。整个过程比我预想的要久一些，大概花了三个小时（中间有些中断），主要原因是文档里的例子都或多或少有问题，没法直接拼成能运行的代码。跑通之后，我又忍不住多花了几个小时到处玩。我的仓库代码写得很糟糕，但如果你在用 embeddings 实现问答时遇到困难，它确实是一个能完整运行的例子。

对这个项目的另一个看法是，我并不认为这是解决我原本想解决的问题的特别有效方案。它本质上只是用了一个比较基础的 k-means 算法，把我博客文章的分词版本和查询进行匹配，然后把最匹配的内容作为上下文塞进 GPT 的查询里。开始做之前，我其实期待能看到一些更复杂、更高级的东西。这是一个合理且成本效率很高的方案，因为它完全不需要对模型进行（重新）训练，但感觉比我想象的要更基础一些。

另外值得一提的是，开发这个应用并运行几十次，总共花费了 0.5 美元。

感想

这是一个很有趣的项目，一方面是因为它让我暂时从过去几个月主要在做的事情——写下一本书——中抽身出来。写书和编辑是一项很有价值的工作，但它缺少那种随意折腾一个小项目、完全没有用户压力的自由快乐。在不过度思考和过度结构化的前提下，下面是一些关于这个项目以及 AI 在行业中扩展的零散想法：

作为一个已经在行业里工作了挺长时间的人，很容易对新事物产生疲惫感。我对最近 AI 热潮的第一反应，和当年对加密货币热潮的第一反应非常相似：我们见过太多 hype 了，初期的 hype 很少能和它对行业或社会的长期影响成正比。换句话说，我一开始并不信服。反过来说，我认为长期的工程领导力的一部分，就是保持对新事物的开放心态。行业在过去二十年里已经发生了翻天覆地的变化，最明显的例子就是移动开发。大多数东西都不会对行业产生太大改变，但总有一些会彻底改变它，我们应该对这些潜在的变革性项目保持谨慎的兴趣。我个人的判断是，这次新的 AI 浪潮会带来中度的变革，但不会是颠覆性的。再展开说说我的思考：LLM 在为非常通用的问题提供“还不错”的解决方案方面展现出了显著潜力。硅谷有一个常见但经常不被说破的模式：雇佣工程师，假装他们在解决问题，然后雇一大堆非工程师来真正解决问题，“直到技术能自动化它”，快速扩大业务，然后寄希望于未来某一年自动化能改善利润率。在这类业务中，采用 LLM 应该是提升利润率的有力工具，理论上能通过改善潜在利润空间来催生新的业务。然而，我们已经经历了十年的零利率政策，这意味着当下的利润率其实没那么重要，这也意味着过去十年里那些本应因利润率改善而诞生的想法，其实大部分都已经在那个对利润不敏感的时代被尝试过了。这意味着 LLM 会让那些业务变得更好，但那些业务本身其实已经被尝试过了，而且其中很多最终失败的原因更多是市场规模不足以产生所需回报，而不是因为缺乏能提升利润率的技术来掩盖大型内部团队的运营成本。如果你忽略 LLM 所代表的利润率提升机会——我认为这不会催生全新的商业想法，而是会改善过去十年已经被尝试过的现有商业想法——那么思考这些工具的甜蜜点就变得很有意思。我的看法是，它们非常擅长辅助领域专家，在这种情况下，不准确带来的潜在损害是可控的。例如 Github Copilot 对熟练程序员来说是一种非常可行的赋能方式，但如果用来训练新手、且代码能访问敏感资源或数据时，则会非常危险。然而，如果我们因此把专家从作者推向编辑，我不确定这对当前这一代已经精通写作、但编辑能力通常较弱的专家来说，是否真的带来了速度上的提升。也许会诞生新一代先精通编辑、再精通写作的专家，而这些工具会促成这一点。如果这是真的，那么很可能当前这一代领导者无法恰当地评估这些工具，但是……我认为大多数人都会对大多数新技术提出类似的论点，而它只在某些时候成立。（加密货币就是一个明显的例子，它在现实世界中并没有凭借显著的监管成本就取代现有技术。）

总之，这是一个有趣的项目，在花时间实践之后，我对这个领域的可能性有了更直观的认识，这也是我的初衷。随着时间推移，我会一直好奇地关注这里会诞生出什么东西。
