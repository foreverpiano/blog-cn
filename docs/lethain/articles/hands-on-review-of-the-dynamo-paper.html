Dynamo 论文动手实践评测

2009-11-30 · 阅读原文

最近我有幸阅读了 Amazon Dynamo 论文，本打算整理一些结构化的笔记，却发现颇有难度，因为论文的话题切换得相当快。

我认为一个很好的记录想法（同时加深自己理解）的方式，就是动手实现一个分布式键值存储，然后逐步加入 Dynamo 论文中讨论的各种改进。通过这个系列，最终我们会在一个分布式 Erlang 系统中重新实现 Dynamo 的大部分核心思想。

每一篇文章都会介绍一个概念，并将其应用到一个随着系列不断演化的分布式键值存储示例中。（有些文章可能会包含多个概念，目的是让每篇文章既有足够的分量值得拥有独立 URI，又足够简短，能在一次阅读中消化。）

为什么选择 Dynamo 论文？

因为它涵盖了大量主题。其中涉及虚拟节点（virtual nodes）、一致性哈希（consistent hashing）、Merkle 树、增量扩容、向量时钟（vector clocks）、gossip 协议、种子节点（seeds）和松散法定人数（sloppy quorums）等。任何一个主题都足以单独成文，因此这篇 27 页的 Dynamo 论文不得不略过许多细节。

而系列文章则有更多空间来深入探讨这些想法；通过构建实际项目能增加动手实践的感觉，我认为这是呈现材料最有启发性的方式。

为什么选择 Erlang？

Erlang 是设计分布式系统的绝佳选择。这并不是特别推崇消息传递，而是更多地致敬 pg2 模块，以及它能够在其他主机上注册并与进程交互，就像它们运行在本地一样的能力。

我一直很享受对 Clojure 的实验，也长期是 Python 的粉丝，但无论是它们还是绝大多数编程语言，都无法像 Erlang 这样以如此轻松随意的方式抽象跨机器操作。

这是一个重要观点，请允许我再说一遍：对于分布式系统，Erlang 的核心优势在于 OTP 应用平台和 Erlang 虚拟机。模式匹配、消息传递和函数式编程范式都是强大的语言特性，但它们是可以被替代的；而 OTP 和 Erlang VM 则无法替代。1

前置知识？

本系列的目标读者是热爱编程的人，但不一定是热爱 Erlang 编程的人。阅读本系列，你只需要一点点坚持。如果要动手实践，你需要熟悉 Erlang 语法并安装好可用的 erl，但不需要特别熟悉 pg2 等模块。

除了讨论 Dynamo 的实现之外，本系列的另一个目标是尽可能多地介绍实现和部署 Erlang 应用的重要概念，因此它非常适合 Erlang 新手作为一篇启发性的读物。

我们的原型

在本系列第一篇文章中，我们将构建分布式键值存储的初始版本。

我们定义的初始接口如下：

start(N) -> started.
stop() -> stopped.
get(Key) -> {ok, Value}.
get(Key, Timeout) -> {ok, Value}.
set(Key, Value) -> {ok, updated}.
set(Key, Value, Timeout) -> {ok, updated}.

这些函数定义大部分不会改变，但 start 函数会随着我们增加更多配置选项而需要一些改进。现在让我们来看看初始实现（这些实现在整个系列中会发生很大变化）。

2> kvs:start(5).
started
3> kvs:get(a).
{ok,undefined}
4> kvs:set(a, 10).
{ok,updated}
5> kvs:get(a).
{ok,10}
6> kvs:get(a).
{ok,10}
7> kvs:stop().  
stopped

For the most part these function definitions won't change, but start will need some improvements as we add more configuration options. Now let's work through the initial implementations (which will change quite a bit over the series).

start 和 stop

在整个系列中，我们会大量依赖 pg2 模块。pg2 是一个用于创建全局进程组的模块，进程可以在其中注册自己，从而可以被其他进程轻松发现。

它的真正价值在于，已注册的进程不仅能被同一节点上的其他进程发现，也能被运行在其他节点上的进程发现。由于节点可以运行在不同的物理机器上，pg2 让我们能够以最小的麻烦实现跨机器扩展。

使用 pg2 时，第一步是通过 pg2:create/1 创建一个进程组（这是一个幂等操作，对已存在的组再次调用不会产生副作用），之后通过 pg2:join/2 将进程加入组中。随后，可以通过 pg2:leave/2 将进程从组中移除。（进程组本身可以通过 pg2:delete/1 删除。）

因此，我们可以按如下方式实现 start/1（其中参数是一个整数，表示要创建的节点数量）：

%% @doc create N processes in distributed key-value store
%% @spec start(integer()) -> started
start(N) ->
    pg2:create(kvs),
    lists:foreach(fun(_) ->
			  pg2:join(kvs, spawn(kvs, store, [[]]))
		  end, lists:seq(0, N)),
    started.

需要注意几点：

  1. We haven't described the kvs:store/1 function yet, so the above code won't yet compile successfully.
  2. spawn/3 is used to create processes using the specified function and parameters, and returns a process identifier.
  3. The second parameter of pg2:join/2 takes a process identifier returned by spawn/3.2
  4. You can run start/1 multiple times, and on multiple nodes, where all created processes would join the same process group. As such, this start function already supports utilizing process across multiple physical hosts.

比 start/1 更简单的是我们的 stop/0 实现：

%% @doc stop all pids in KVS process group
%% stop() -> stopped.
stop() ->
    lists:foreach(fun(Pid) ->
			  pg2:leave(kvs, Pid),
			  Pid ! stop
		  end, pg2:get_members(kvs)),
    stopped.

注意 stop/0 会从 kvs 进程组中移除所有进程，这意味着它会移除其他物理主机上创建的进程。目前这是合理的，但随着系列推进，我们可能需要设计一个更细致的停止策略。3

stop/0 的另一个有趣之处在于，它展示了本系列中消息传递的第一个例子。4 Erlang 中消息传递的语法是：

ReceiverPid ! TermToSend.

其中 ReceiverPid 是接收者的进程标识符，TermToSend 是任意的 Erlang 项。下面都是合法的消息传递示例：

Pid ! ok.
Pid ! {ok, [{a, 10}, {b, 20}]}.
Pid ! [a,b,c,d].
Pid ! dict;store(name, <<"Will">>, dict:new()).

现在我们已经写好了 start/1 和 stop/0 函数，是时候编写包含真正键值存储逻辑的 store/1 函数了。

键值存储 store/1

store/1 函数是实现的核心。它维护键值存储，处理值的更新和传播，并负责为客户端检索值。

在这个初始实现中，我们做了几个策略性的决定：

  • We are storing values in a property list, because it is very simple. It goes without saying that a property list is not a suitable datastructure for large numbers of values (average complexity of O(N/2) for both reads and updates, worst case complexity of O(N)). We'll address this later.
  • We are storing all data in every processes. That is, we're doing replication instead of sharding. This is a temporary condition, which we'll improve on throughout the series.
  • Reading always reads from a single process, which would be appropriate if we verified all other processes had successfully updated before reporting that a write succeeded. This'll improve over time as well.

考虑到这些前提，以下是我们 store/1 的初始实现：

%% @doc implementation of distributed key-value store
%% @spec store(proplist()) -> term()
%%       proplist = [{term(), term()}]
store(Data) ->
    receive 
	{Sender, get, Key} ->
	    % client interface for retrieving values
	    Sender ! {self(), got, proplists:get_value(Key, Data)},
	    store(Data);
	{Sender, set, Key, Value} ->
	    % client interface for updating values
	    lists:foreach(fun(Pid) ->
				  Pid ! {self(), update, Key, Value}
			  end, pg2:get_members(kvs)),
	    Sender ! {self(), received, {set, Key, Value}},
	    store(Data);
	{Sender, update, Key, Value} ->
	    % sent to all nodes by first receiving node
	    Sender ! {self(), updated, Key, Value},
	    store([{Key, Value} | proplists:delete(Key, Data)]);
	{_Sender, updated, _Key, _Value} ->
	    store(Data);
	stop ->
	    ok
    end.

store/1 有几个方面值得简要讨论：

% in the Sender process
Receiver ! {set, a, "b"}.
% in Receiver process
receive
    {set, Key, Val} ->
        io:format("Received ~p => ~p~n", [Key, Val]),
end.   

% in Sender process
Receiver ! {self(), get, name}.
% in Receiver process
receive
{Sender, get, Key} ->
Value = get_from_somewhere(Key),
Sender ! {got, Key, Value)
end.
  • This is the first occurrence of receive keyword, which is the second half of using message passing in Erlang (the first half is the ! operator). receive and ! work together as follows:Also note that the self/0 function returns the pid of the process where it is called, so it is frequently used when the sender wants the receiver to respond.
  • pg2:get_members/1 takes a process group name and returns a list of all pids which are currently members. It, along with pg2:get_closest_pid/1 are the two mechanisms for getting a pid from a process group.
  • Note the distinction we're making between set and update: set is the external interface for updating values, and update is the internal interface for propagating values.(Also note that we're ignoring the updated message at this point.)

现在 store/1 实现已经完成，是时候编写一些便捷的包装函数并从 kvs 模块导出，它们可以简化与 store/1 函数的交互。

get 和 set 接口

虽然可以直接与进程通信，但这需要了解很多细节。你需要知道它们注册在 kvs 进程组中，需要知道它们期望的消息格式，还需要确保交互是同步的（默认情况下 Erlang 消息传递是异步的，但我们下面会看到同步消息传递的标准模式）。

我们可以通过编写接口函数来缓解这些问题，用于执行键值存储中两个最重要的操作：设置和获取。

首先来看 get/1 和 get/2 的实现。

%% @doc retrieve value for key
%% @spec get(term()) -> value() | undefined
%%       value = term()
get(Key) -> get(Key, ?TIMEOUT).
%% @doc retrieve value for key, with timeout
%% @spec get(term(), integer()) -> val() | timeout()
%%       val = {ok, term()} | {ok, undefined}
%%       timeout = {error, timeout}
get(Key, Timeout) ->
Pid = pg2:get_closest_pid(kvs),
Pid ! {self(), get, Key},
receive
{Pid, got, Value} ->
{ok, Value}
after
Timeout ->
{error, timeout}
end.

这个例子中出现了一些新内容：首先是 pg2:get_closest_pid/1，它会随机选择指定进程组中的一个进程，并优先选择与当前节点在同一节点上运行的 pid。这有助于在进程组中的各个 pid 之间均匀分配工作。5

其次，注意这里使用的“发送消息，然后用 receive 阻塞等待响应”的模式，这是在两个进程之间进行同步通信的常用方式。

set/2 和 set/3 函数与 get/2 非常相似；它们遵循相同的模式，区别仅在于发送的消息和期望的响应。

%% @doc update value for key
%% @spec set(term(), term()) -> {ok, updated} | {error, timeout}
set(Key, Val) -> set(Key, Val, ?TIMEOUT).
%% @doc update value for key, with timeout
%% @spec set(term(), term()) -> {ok, updated} | {error, timeout}
set(Key, Val, Timeout) ->
Pid = pg2:get_closest_pid(kvs),
Pid ! {self(), set, Key, Val},
receive
{Pid, received, {set, Key, Val}} ->
{ok, updated}
after
Timeout ->
{error, timeout}
end.

set/3 中应该没有什么我们没见过的内容，所以我们可以继续进行实现这个最简单分布式键值存储的最后一步任务。

kvs 模块

最后，我们需要编写 kvs 模块的头部，这只需要几行代码。

-module(kvs).
-export([get/1, get/2, set/2, set/3, start/1, stop/0, store/1]).
-define(TIMEOUT, 500).

注意我们定义了 TIMEOUT，它表示等待响应的毫秒数。你可能也想把 500 改成 infinity，这意味着不设置超时。不过目前 500 毫秒在功能上等同于 infinity，所以 500 是一个合理的默认值。6
