Dynamo 论文动手实践评测

2009-11-30 · 阅读原文

最近我有幸阅读了 Amazon Dynamo 论文，本打算整理一些结构化的笔记，却发现很难下笔，因为论文的话题切换得相当快。

我认为一个很好的记录思路（同时也能加深理解）的方式，就是动手实现一个分布式键值存储，然后逐步加入 Dynamo 论文中讨论的各项改进。通过这个系列文章，最终我们将在一个分布式的 Erlang 系统中重新实现 Dynamo 的大部分核心思想。

每一篇文章都会介绍一个概念，并将其应用到一个随着系列不断演进的分布式键值存储示例中。（某些文章可能会包含多个概念，目的是让每篇文章既有足够长度值得拥有独立 URI，又足够简短可以在一次阅读中消化。）

为什么选择 Dynamo 论文？

因为它涵盖了大量主题。其中包括 virtual nodes、consistent hashing、merkle trees、incremental scaling、vector clocks、gossip protocols、seeds 和 sloppy quorums。这些主题任何一个都足以单独成文，因此这篇 27 页的 Dynamo 论文不得不对许多细节一带而过。

而一系列文章则有更多空间来深入探讨这些想法；通过动手构建项目，能带来一些实践的感觉，我认为这是呈现材料最有教益的方式。

为什么选择 Erlang？

Erlang 是设计分布式系统的绝佳选择。这并不是特别为消息传递唱赞歌，而更多是对 pg2 模块的致敬——它能够注册运行在其他主机上的进程，并像本地进程一样与之交互。

我一直很享受用 Clojure 做实验，也长期是 Python 的忠实用户，但无论是它们还是绝大多数编程语言，都无法像 Erlang 这样以如此轻松的方式抽象掉跨机器操作。

这是一条重要信息，所以请允许我再说一遍：对于分布式系统来说，Erlang 的核心优势在于 OTP 应用平台和 Erlang 虚拟机。模式匹配、消息传递和函数式编程都是强大的语言特性，但它们都可以被替代；而 OTP 和 Erlang VM 则不可替代。

前置要求？

本系列的目标读者是热衷编程的人，但不一定是热衷 Erlang 编程的人。阅读本系列，你只需要一点点坚持精神。如果要跟着动手实践，你需要熟悉 Erlang 语法，并安装好可运行的 erl，但并不需要事先熟悉 pg2 等模块。

除了讨论 Dynamo 的实现之外，本系列的另一个目标是尽可能多地介绍实现和部署 Erlang 应用的各种重要概念，因此它非常适合 Erlang 新手作为启发性的阅读材料。

start 和 stop

在整个系列中，我们会大量依赖 pg2。pg2 是一个用于创建全局进程组的模块，进程可以在其中注册自己，从而可以被其他进程轻松发现。

其真正价值在于，注册的进程不仅能被同一节点上的其他进程发现，也能被运行在其他节点上的进程发现。由于节点可以运行在不同的物理机器上，pg2 让我们能够以最小的麻烦实现跨机器扩展。

使用 pg2 时，第一步是通过 pg2:create/1 创建一个进程组（这是一个幂等操作，对已存在的组再次调用不会产生副作用），之后通过 pg2:join/2 将进程加入该组。后来，可以通过 pg2:leave/2 从组中移除进程。（进程组本身可以通过 pg2:delete/1 删除。）

键值存储 store/1

store/1 函数是整个实现的核心。它维护键值存储、处理值的更新和传播，并负责为客户端检索值。

在这个初始实现中，我们做了几个战略性的决定：

我们把值存储在属性列表（property list）中，因为它非常简单。不用说，属性列表并不适合存储大量数据（读写平均复杂度为 O(N/2)，最坏情况为 O(N)）。我们稍后会解决这个问题。我们把所有数据都存储在每个进程中，也就是说我们在做复制而不是分片。这只是暂时的状态，我们会在整个系列中逐步改进。读取总是从单个进程读取，如果我们能在确认其他所有进程都成功更新后再报告写入成功，这样做是合适的。这一点也会随着时间推移而改进。

这是第一次出现 receive 关键字，它是 Erlang 中使用消息传递的后半部分（前半部分是 ! 操作符）。receive 和 ! 一起工作的方式如下： % 在发送者进程 Receiver ! {set, a, "b"}. % 在接收者进程 receive {set, Key, Val} -> io:format("Received ~p => ~p~n", [Key, Val]), end. 还要注意 self/0 函数会返回调用它的进程的 pid，因此当发送者希望接收者回复时经常使用它。 % 在发送者进程 Receiver ! {self(), get, name}. % 在接收者进程 receive {Sender, get, Key} -> Value = get_from_somewhere(Key), Sender ! {got, Key, Value} end. pg2:get_members/1 接受一个进程组名称，并返回当前所有成员的 pid 列表。它和 pg2:get_closest_pid/1 是在进程组中获取 pid 的两种机制。注意我们对 set 和 update 做了区分：set 是更新值的外部接口，而 update 是传播值的内部接口。（同时注意我们目前忽略了 updated 消息。）
