如何构建可靠性程序

2019-06-30 · 阅读原文

这篇文章写得还挺粗糙的。

可靠性程序是一种学习引擎，它把事故转化为可靠性。任何提供关键基础设施的公司都应该拥有这样一个程序。当然，即使你不是做基础设施的，只要你认为自己在做有价值的事情，并且已经达到一定规模，也很可能需要这样一个程序。

你会看到一些公司试图绕过构建完整可靠性程序的细节，直接成立一个 Software Reliability Engineering（SRE）组织，但这有点像：字面差距很小，但实际鸿沟巨大。逃离构建陷阱笔记

在这个领域，我每年都觉得自己比前一年懂得多一倍。即使从以来，我也学到了足够多的东西，值得再尝试一次，系统地描述一种有效的方法。制定可靠性策略：用系统模型思考复杂问题

价值的前提

是的，这确实很重要，而且随着公司规模增长会越来越重要。

很少有业务一开始就把可靠性放在优先位置：在小规模、面对小客户时，可靠性很容易保证，它不是你的核心价值，而是交付价值的先决条件。

但对于大型用户或企业客户来说，可靠性是你核心价值主张的重要组成部分（你的用户极易受到市场、用户、声誉等因素的影响）。

这时，可靠性成了用户从你的产品中获取价值的唯一保障——所以，可靠性现在就是你的核心业务价值。

这对某些产品来说不是自然成立的，但比如 Twitter 的可靠性不足就极具破坏性，因为它打破了用户对这类产品的“上瘾”……呃，“参与循环”。

从简单开始

后面我们会讨论如何在大型、复杂的组织中培养可靠性，但如果你是一家较小的公司，没必要直接跳到那个阶段。

在工程师人数达到一百人左右之前，掌握以下几个基本要素就能走得很远：

对核心业务流程设置告警；一个全公司任何人都能用来触发告警的邮件列表；on-call 轮值（https://increment.com/on-call/on-call-at-any-size/）；针对核心业务流程健康度和 on-call 轮值健康度的指标与目标；定期回顾这些指标和目标，启动可靠性冲刺；几位高级工程师负责安排事故回顾会，来缓解特别严重的事故，大致遵循 2012 年 Allspaw 那篇经典文章的思路。

走向一致性

上面那种做法是不够的，必须要扩大规模。为什么不呢？——决定值得拥有一个可靠性程序。

正确的前瞻性工作比被动反应工作的 ROI 高得多，而错误的前瞻性工作 ROI 为零。

有用的目标

在逃离构建陷阱笔记一书中，Melissa Perri 说：“在以产品驱动的组织中，人们因为学习和达成目标而获得奖励。”衡量可靠性程序的目的也非常类似：我们希望了解自己的学习速度，以及是否正在变得更加可靠。

以用户目标为中心；不要衡量事故数量，要衡量事故的严重程度，影响应该逐步下降；高维度挑战；分群，分群，再分群。

战略

指导你的事故程序的是写作策略与愿景

学习（与影响）的引擎

https://melissaperri.com/blog/2015/07/22/the-product-kata

根据我设计以及的经验，成功程序的核心节奏是：项目：掌控不可控之事培养项目的参与度

根据用户反馈、利益相关方需求和你的领域专业知识，确定程序当前面临的最重要问题。构建可重复、持续的数据集，用于理解该问题并设定目标（关键是不能是一次性的，也不能是手动操作）。设定你希望如何影响该问题的目标，同时很可能还需要设定维护健康数据集的目标。用一个仪表盘让问题变得易于理解，用数据清晰定义问题。为团队创建可复用的 playbook，让他们在发现自己的数据贡献或对问题本身的贡献存在问题时使用。创建提醒机制，让他们知道应该采取哪些行动来支持目标。如果提醒不够，就为团队设定支持该目标的具体目标。如果目标还不够，就建立升级循环，让团队能与利益相关方对齐优先级。回到起点，找到下一个新问题。用指标引导大规模变革

构建数据集

Pagerduty 的事故响应文档

研究事故；设计可靠性程序；开始从事故中收集数据；创建跟踪仪表盘来检查数据质量并从中学习；创建提醒机制来推动数据收集；设定目标以确保数据被持续收集。

服务手册。

事故主题；用这些数据创建主题；缓解模式；用这些主题创建缓解模式；创建提醒机制推动使用缓解模式；设定目标确保缓解模式被遵循；预防模式；用这些主题创建预防模式。

预防模式的传播

扩展仪表盘以包含预防模式；衡量缓解和预防模式的质量；文档化可靠性的最佳实践以及如何实施它们；建立反馈循环来推动大家采用可靠性实践；设定目标确保可靠性实践被执行；将可靠性融入架构。

解散乐队

什么时候可以取消这个程序？当预防模式和故障注入已经固化并正常运转，事故率和用户影响已经非常低的时候。这种情况在快速增长的公司几乎永远不会发生，但在增长放缓的公司是有可能的。
