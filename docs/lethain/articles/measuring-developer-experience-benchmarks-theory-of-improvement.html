衡量开发者体验、基准测试，以及提供改进理论。

2024-12-08 · 阅读原文

早在2020年，我写过一篇文章，标题是 我对当前开发者元生产力工具的怀疑。， 文中列出了我当时对开发者生产力衡量工具的三个核心问题：

将生产力指标用于评估而非学习；需要对过多不同工具进行调整才能采集指标；总体上我发现这些工具强行给问题套上了一个随意且存疑的模型。

两年半后，我天使投资了 DX，当时我主要认为它采取了一种以调研驱动、研究为支撑的方法来衡量开发者生产力。最近我和 DX 的联合创始人 Abi Noda 聊天时，觉得这是一个很好的时机来修订我最初的论点——既包括总体看法，也针对 DX 最近发布的 DX Core 4。

开发者元生产力工具的 checklist

在2024年，我认为一个世界级的开发者元生产力工具应该满足以下 checklist：

自动从大多数厂商（例如 Github）拉取指标。支持从主要可观测性系统（例如 Datadog）转换指标。支持自定义发送指标。自动以一致的方式绘制这些指标的图表，这包括跨厂商对数据进行反规范化处理，让那些使用标准厂商的用户几乎无需定制。（这也隐含着要拒绝那些本质上过于复杂的度量，比如 lead time。）将数值与可比的基准数据进行对比，确保所有这些数值都具有很高的“可判断性”，让你、你的 CTO 或董事会能够判断自家公司在同行中的表现。为你提供“改进理论”，让你能够大致将分数转化为应该投入的具体项目。这些理论应当尽可能具体。一个极好的例子是：你90%的事故都涉及到这五个文件之一，那你就应该优先加固这些文件的内容。一个更宽泛的例子可以是：通常在这个维度上得分高的团队会采用这些实践（例如基于主干的开发），而得分较低的团队则采用另一些实践（例如长期分支开发）。

我认为如果你能提供以上全部四点，那就等于提供了一个极具价值且有效的产品。

天然是一个网络型产品

这算是一个题外话，但我特别相信，只提供前两点（数据摄取和图表绘制）的产品，与提供第三点（基准测试）的产品之间存在一个重要的分界点。因为我越来越认为，开发者数据只有在基准的背景下才能被判断，而只有当你拥有一个在同一平台共享数据的公司网络时，才能提供基准。此外，这些数据还需要以相对可验证的方式共享（历史上有很多基于不准确的自报数据集的产品，最终逐渐破坏了用户的信任）。

如果你认同基准是基础，那么下一代领先的开发者元生产力工具就是一个网络型产品，这意味着生态系统中只会存在一两个赢家。（因为只有少数公司能成为足够多公司的供应商，从而构建出良好的基准。）这与我早前的想法相比是一个重大转变，因为现在有了一个底层机制来推动这个市场收敛，而不是让成千上万个小供应商保持碎片化。

从2020年到2024年的进展

在用我新的四个标准去检验开发者生产力领域的最新进展之前，我想先做一个 Wardley Map，来更好地说明我在这些工具上看到的挑战，以及为什么我认为 DX 的方法相对新颖。

这里有三类用户需要考虑：工程师、开发者生产力团队，以及工程高管。工程师只希望开发者生产力团队为他们做有用的事，并且希望花最少的时间去维护开发者生产力相关的数据集成。工程高管希望获得能帮助他们评估整个工程组织效率的报告，这些报告将用于资源分配决策，以及向上向董事会汇报进展。开发者生产力团队则希望提供上述所有服务，并有针对性地投入资源来改善开发者体验。

在2020年，我的观点是仪表盘和埋点仍然是定制化的工作，而当时那波工具试图通过更好的数据摄取来解决这个问题，这就把我们带到了 Wardley Map 的第二个阶段。

随着仪表盘创建和指标采集变得更加标准化，你会以为这些工具的价值显著提升了。这看起来像是很大的进步，但在我看来，它暴露了对这些指标如何发挥作用的误解。

把目标定为“本半年将每位工程师的 PR 数提升10%”其实没太大意思：你从孤立地尝试操纵这些曲线中能获得的洞察非常有限。但如果你知道自己每位工程师的 PR 数明显落后于同规模的公司，那就非常有意义了。（如果能看到自己在同规模公司的散点图中所处的位置，那就更有意思了。）

重要的是，当你站在工程高管的角度思考时，只有基准数据才能真正帮助他们向董事会汇报工程团队执行力的影响——其他所有报告其实都完全没有解决工程高管的问题。通常，你可以衡量工程组织。，因为董事会更关心的是你是否有能力去采集和维护某项指标，而不是你具体采集了什么。但有了基准之后，你就能真正提供一种有意义的衡量和评估团队工作的方式！而且，如果基准是由供应商维护的，而不是你自己非正式地从同行那里收集的，那么提供一个有意义的同行比较就会比提供一个意义不大的比较容易得多。

第一波工具厂商以为他们能通过更好的仪表盘来解决工程生产力问题，但真正对最重要的工程高管用户有价值的，其实是对基准创建的中心化。

简而言之，DX 方法背后的核心洞见是：在公司之间标准化基准流程，让客户无需自己收集就能从这些基准中受益，这比仪表盘或数据采集本身要有价值得多。从很多意义上说，这是在一个新领域应用 CultureAmp 的经验。这也意味着，作为一个独立的产品，而不是 Google 或 Github 内部某个大型指标平台的一部分，它能够覆盖更多可以纳入基准的公司。

最后，如果你接受基准是最重要的特性，那就意味着你选择要衡量哪些指标的首要标准，是你能否在众多不同公司之间持续、可靠地将它们纳入同一个基准。

指标是否应该提供“改进理论”？

我之所以如此喜欢基准，是因为任何拥有良好基准的指标都具有很高的“可判断性”。可判断性是指你能否通过理解该指标随时间的变化来判断事情是否进展良好。几乎所有指标，只要你把它放在同行公司的散点图中展示，就都能满足这个标准。例如，DX Core 4 建议用“每位工程师的 diff 数”来评估工程速度，虽然这个指标孤立来看极难评估，但只要把你组织的每工程师 diff 数与同行公司的进行对比，就很容易做出一个有根据的判断——事情对你来说是否进展顺利。

相反，我对“每工程师 diff 数”的“可设定目标性”就没有那么有信心。可设定目标性是指你能否基于当前数值有效地设定一个目标。例如，我们现在每周每工程师产出2.5个 diff，我们想把它提高到3.5个。这是一个好的目标吗？我们是否拥有一个能指导我们如何开展工作的改进理论？

我认为这可能不是一个好的目标，我们也可能没有一个清晰的改进理论，因为这是一个输出指标（也称为滞后指标）。输出指标非常擅长衡量某件事是否已经改善，但非常不擅长把注意力引导到如何改进该指标上。收入是终极的输出指标：没错，如果你的新产品功能带来了收入，它就是在创造有价值的东西，但仅仅设定一个收入目标，并不会告诉你如何有效地去实现它。

这意味着，如果你的开发者生产力指标全是输出指标，那你仍然没有为那些试图规划路线图来改善自身指标的团队提供一个“改进理论”。（总体来说，缺乏改进理论就相当于没有解决工程策略危机来应对手头的问题。）

DX Core 4 的所有指标都是很好的输出指标，它们让你能够跨多个维度评估自己的组织是否高效运行，但它们都没有强烈地指出你应该具体做什么。这正是《Accelerate》这本书的伟大之处——它不仅提供了用于评估组织的输出指标，还提供了一组与更高绩效高度相关的实践。

提供改进理论可能是对一组指标要求太高了。例如，过去一年我在 Carta 花了不少时间和一个跨团队的工程师小组一起改善代码质量。我们采用了我在策略测试：避免瀑布式策略陷阱，通过迭代优化。中描述的工作方法，花了一段时间才聚焦到我们认为的根本问题：我们代码库中某一部分的前端测试支持太困难，导致前端测试数量不足以在复杂产品中维持高质量的代码。我们花了大约三个月的时间做假设形成和验证，才确信这就是需要重点解决的基础问题，而我们早期的一些改进理论实际上是明显错误的——这也正是需要在投入任何具体方法之前先进行策略测试的原因。

也许越来越标准化的生产力指标带来的最大好处，是让开发者生产力团队能够摆脱“维护这些指标就是核心工作”的观念，转而认识到：为公司提炼出关于开发者生产力的改进理论，才是更有价值的工作机会。

对实际指标本身的评论

花些时间评论这些核心指标时，我想起 Reddit 上有个帖子，有人说他们一看到我第一本书里建议把“每工程师 PR 数”作为一个虽不完美但可用的起点，来理解工程师的工作方式，就立刻停止阅读了。现在看到 DX Core 4 的第一个指标竟然是“每工程师 diff 数”，感觉有点好笑。

总体而言，我觉得这些核心指标非常合理。我唯一会直接提出异议的顶级指标是“花在新能力上的时间百分比”，根据我的个人经验，这是一个追踪起来相当麻烦的指标，但如果你相信它的准确性，那它确实是一个很有力的指标。

还有一些我之前没见过的指标，但事后看来显然很有用而且容易衡量，比如：

“到达第10个 PR 的时间”是一个极好的入职指标，我之前从未考虑过。特别是它非常容易衡量，也很容易在众多不同公司之间进行基准对比。“研发占收入的百分比”是一个董事会喜欢用来评估你的基础图表，你也应该用它来衡量自己。

使用预测合成指标的“开发者体验指数（DXI）”既是一个聪明的做法，也是一个代价高昂的做法。好处在于，它允许把许多不同的组成部分纳入其中，并且可以随着研究的发展而修订这个复合指标。例如，他们可以在后续调研中加入新问题，并将这些结果纳入首次包含这些问题的调研之后计算的 DXI 数值中，而不会影响他们基准的有效性。

坏处则是没人真正理解复合指标，这意味着团队将不得不反复、反复地解释这个指标的含义。即使如此，持怀疑态度的人还是不太信任复合指标，而高管和董事会里恰恰充斥着持怀疑态度的人。不过，把数据放在散点图的背景下呈现，应该能解决关于复合指标的很多疑虑，所以从我的角度看，这是一个合理的尝试。

2025年及以后

思考当前开发者生产力领域的现状，我对未来几年有几点希望。首先，我希望框架泛滥的情况能稍微缓和一些。DORA、SPACE、DX Core 4 等都是很好的框架，但希望我们能达到这样一个点：再创造一个新框架明显是不值得的。我认为 DX Core 4 可以通过强调 DXI 的计算机制，并确保即使是竞争对手的公司也能可预测地使用该计算方法，来特别推动这一目标的实现。

其次，我很希望看到我提出的世界级开发者元生产力工具的四个标准全部进入 Wardley Map 的“产品”阶段，并完全脱离“定制”阶段。这意味着这些工具不仅要开箱即用地提供指标采集、仪表盘和基准，还需要提供改进理论。我不认为这遥不可及，例如你可以对那些在每个指标上从低分提升到高分的公司进行一系列研究，了解他们当时优先做了什么，并由此生成广泛的建议。然后你可以逐步打磨这些建议，使其越来越能直接适用于每个客户。

如果这一切能够实现，我认为我们会进入一个相当了不起的阶段：开发者生产力团队主要成为执行团队而非分析团队，这将是该团队在行业中角色的一次根本性转变。
