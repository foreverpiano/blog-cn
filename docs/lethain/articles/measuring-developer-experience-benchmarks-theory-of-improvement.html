衡量开发者体验、基准测试，以及提供改进理论。

2024-12-08 · 阅读原文

早在2020年，我写过一篇文章，标题是 我对当前开发者元生产力工具的怀疑。， 文中提出了当时开发者生产力衡量工具存在的三个核心问题：

  1. Using productivity measures to evaluate rather than learn
  2. Instrumenting metrics required tweaks across too any different tools
  3. Generally I found tools forced an arbitrary, questionable model onto the problem

两年半后，我天使投资了 DX，当时我主要将其视为一种基于调研、经过研究验证的开发者生产力方法。最近我和 DX 的联合创始人 Abi Noda 聊天时，觉得这是一个很好的时机，来修订我最初的论点——既包括总体看法，也针对 DX 最近发布的 DX Core 4。

开发者元生产力工具的检查清单

到了2024年，我认为世界级的开发者元生产力工具应满足以下检查清单：

  1. Pull metrics in from most vendors (e.g. Github) automatically. Support converting metrics from primary observability systems (e.g. Datadog). Support custom emitting metrics.
  2. Automatically graph those metrics in a consistent fashion. This includes denormalizing the data across vendors, such that those relying on standard vendors do near-zero customization. (Implicitly this also means rejecting measurements that are inherently complex, looking at you, lead time.)
  3. Plot values against comparable benchmark data, ensuring that all these values have high “judge-ability” such that you, your CTO, or your Board, can judge your company’s performance relative to peer companies.
  4. Provide a “theory of improvement” such that you can roughly translate your scores into the projects to invest in. These should be as narrow as possible. A great example would be: 90% of your incidents involve one of these five files; you should prioritize hardening their contents.A broader example could be along the lines of: generally teams that score highly on this dimension utilize these practices (e.g. trunk-based development), and those that score lower use these other practices (e.g. long-lived branch development).

我认为如果你能同时提供以上四点，就等于提供了一个极具价值且高效的工具。

隐含的网络产品属性

这算是一个题外话，但我特别相信，只提供前两项（数据摄取和图表绘制）的产品，与提供第三项（基准测试）的产品之间存在一个重要的分界点。因为我越来越认为，开发者数据只有在基准数据的背景下才具有可判断性，而只有当你拥有一个在同一平台共享数据的公司网络时，才能提供基准数据。此外，这些数据还需要以相对可验证的方式共享（历史上有很多不准确的自我报告数据集驱动的产品，最终逐渐削弱了用户信任）。

如果你认同基准测试是基础性的，那么下一代领先的开发者元生产力工具就是一个网络型产品，这意味着生态系统中只会存在一两个赢家。（因为只有少数公司能作为足够多公司的供应商，从而构建出高质量的基准。）这与我之前的想法有了重大转变，因为现在存在一种底层机制，能促使这个市场收敛，而不是分散在成千上万个小供应商之间。

从2020年到2024年的进展

在用我新提出的四条标准去检验开发者生产力领域的最新进展之前，我想先做一点 Wardley Mapping，来更好地说明我在这些工具中看到的挑战，以及为什么我认为 DX 的方法相对新颖。

这里需要考虑三种用户：工程师、开发者生产力团队，以及工程高管。工程师只希望开发者生产力团队为他们做有用的事，并希望花最少的时间来维护开发者生产力的数据集成。工程高管希望获得能帮助他们评估整个工程组织效率的报告，这些报告将用于资源分配决策，以及向上向董事会汇报进展。开发者生产力团队则希望提供上述所有服务，并针对性地投资于改善开发者体验。

2020年时，我的观点是仪表盘和指标采集仍然属于定制化工作，而当时的那一波工具试图通过更好的数据摄取来解决这个问题，这就把我们带到了 Wardley 地图的第二个阶段。

随着仪表盘创建和指标采集变得更加标准化，你会以为这些工具的价值显著提升了。这看起来是巨大的进步，但在我看来，它也暴露了对这些指标如何发挥作用的误解。

把每个工程师的拉取请求数量在本半年提升10%作为目标，并不是特别有意思：你从孤立地操纵这些曲线中能获得的洞察非常有限。但如果你知道自家每个工程师的拉取请求数量显著落后于规模相似的公司，那就非常有意思了。（而在这些规模相似的公司的散点图中看到自己所处的位置，则更有意思。）

重要的是，当你站在工程高管的角度思考时，只有基准测试能帮助他们充分向董事会汇报工程团队执行力的影响——其他所有报告都完全无法解决工程高管的问题。一般来说，你可以衡量工程组织，因为董事会更关心你是否有能力建立和维护某种度量系统，而不是你具体度量什么。但有了基准测试，你就能真正提供一种有意义的方式来衡量和评估团队的工作！而且，如果基准测试是由供应商维护的，而不是你自己非正式地从同行那里收集的，那么提供一个有意义的组织间比较就会比提供一个不那么有意义的比较来得更容易。

第一波工具供应商以为他们能通过更好的仪表盘来解决工程生产力问题，但真正对最重要的工程高管用户有价值的部分，其实是基准创建的集中化。

简单总结一下，DX 方法背后的核心洞见在于：跨公司标准化基准创建流程，让客户无需自行收集就能从中受益，这远比仪表盘或数据采集本身有价值得多。从很多意义上说，这是在一个新领域应用了 CultureAmp 的经验。这也意味着，作为一个独立产品，而不是 Google 或 GitHub 内部大型指标平台的一个自有组件，它能够覆盖更多可以纳入基准测试的公司。

最后，如果你认同基准测试是最重要的特性，那就意味着你衡量事物的首要标准，是能否将其稳定地纳入跨越许多不同公司的基准之中。

指标是否应该提供改进理论？

我最喜欢基准测试的一点是，任何拥有良好基准的指标都具有很高的可判断性。可判断性是指你能否通过理解该指标随时间的变化来判断事情是否进展顺利。几乎所有指标只要放在同行公司数值的散点图中展示自己的数值，都能满足这一标准。例如，DX Core 4 建议用“每个工程师的 diff 数”来评估工程速度，虽然这个指标孤立来看极难判断，但在把自家组织的每个工程师 diff 数与同行公司的每个工程师 diff 数放在一起对比时，就很容易做出 informed 判断，知道自己情况是否良好。

相反，我对“每个工程师 diff 数”的可目标性（goal-ability）就没有那么有信心。可目标性是指你能否基于当前数值有用地设定一个目标。例如，我们当前显示的是每周每个工程师 2.5 个 diff，我们想把它提高到 3.5 个。这是一个好的目标吗？我们是否拥有能指导如何开展工作的改进理论？

我认为这可能不是一个好的目标，我们也可能没有改进理论，因为这是一个结果指标（也称为滞后指标）。结果指标非常擅长衡量某件事是否已经得到改善，但非常不擅长将注意力聚焦到如何改进该指标上。收入是终极的结果指标：没错，如果你的新产品功能带来了收入，它就创造了有价值的东西，但仅仅设定一个收入目标并不会告诉你如何有效地实现它。

这意味着，如果你的开发者生产力指标全都是结果指标，那么你仍然没有为那些试图确定改进路线图的团队提供“改进理论”。（一般来说，缺乏改进理论就等于没有针对手头问题的。）解决工程策略危机

DX Core 4 的所有指标都是良好的结果指标，它们让你能够跨不同维度评估组织是否高效运作，但其中没有一个对“你应该为此做什么”给出强有力的观点。这是《Accelerate》这本书的成功之处之一——它不仅提供了用于评估组织的输出指标，还提供了一组与更强绩效高度相关的实践。

提供改进理论可能对一批指标来说要求太高了。例如，过去一年我在 Carta 花了不少时间和一个跨团队的工程师小组一起改善代码质量。我们遵循了我称为的工作模式，花了一段时间才聚焦到我们认为的根本问题上：我们代码库中某一部分的前端测试支持过于困难，导致前端测试数量不足以在复杂产品中维持高代码质量。我们花了大约三个月的时间形成和验证假设，才确信这就是需要重点关注的基础问题，而我们早期的一些改进理论明显是错误的——这也说明了在投入任何一种方法之前进行策略测试的必要性。策略测试：通过迭代优化避免瀑布式策略陷阱

也许越来越标准化的生产力指标的最大赢点在于，它让开发者生产力团队能够摆脱“维护这些指标就是核心工作”的观念，转而认识到：完善公司关于开发者生产力的改进理论，才是更具价值的工作机会。

对实际指标本身的点评

花点时间评论这些核心指标时，我想起 Reddit 上有个帖子，有人说他们一看到我第一本书里建议把“每个工程师的 PR 数”作为一个虽然糟糕但可用的起点，来理解工程师的工作方式，就立刻停止阅读了。看到 DX Core 4 的第一个指标居然是“每个工程师的 diff 数”，还真有点好笑。

总体而言，我觉得这些核心指标非常合理。我唯一想直接挑剔的顶级指标是“花在新能力上的时间百分比”，根据我的个人经验，这是一个相当棘手的跟踪噩梦，但如果你相信它的准确性，它确实是一个很有力的指标。

还有一些我之前没见过的指标，但事后看来显然非常有用且容易衡量，例如：

  • Time to 10th PR is a fantastic onboarding metric, and not one that I’d considered before. In particular it’s quite easy to measure, and easy to benchmark across many different companies.
  • R&D as a % of revenue is a foundational chart that boards like to use to evaluate you, you should be measuring yourself on it as well.

使用的“开发者体验指数（DXI）”既是一个聪明的做法，也是一个代价高昂的做法。其好处在于，它允许将许多不同组成部分纳入其中，并随着研究的发展而修订这个复合指标。例如，他们可以在调研中提出新问题，并在首次包含这些结果的调研之后，将其权重纳入 DXI 计算中，等等，而不会影响其基准的有效性。预测合成指标。

缺点则是没有人真正理解复合指标，这意味着团队将不得不反复、反复地解释这个指标的含义。即使如此，持怀疑态度的人还是不太信任复合指标，而高管和董事会里恰恰充满了持怀疑态度的人。不过，把数据放在散点图的背景下呈现，应该能解决关于复合指标的许多顾虑，所以从我的角度看，这是一个合理的实验。

2025年及以后

思考当下开发者生产力领域的现状，我对未来几年有几点希望。首先，我希望框架泛滥的现象能稍微放缓一些。DORA、SPACE、DX Core 4 等都是很好的框架，但我们最好能达到这样一个阶段：再创造一个新框架显然是不值得的。我认为 DX Core 4 可以通过强调 DXI 的计算机制，并确保即使是竞争对手的公司也能可预期地使用该计算方法，来特别推动这一点。

其次，我希望看到我提出的世界级开发者元生产力工具的四条标准全部进入 Wardley 地图的“产品”阶段，完全脱离“定制”区域。这意味着这些工具不仅要开箱即用地提供指标采集、仪表盘和基准测试，还必须提供改进理论。我不认为这遥不可及，例如你可以对那些在每项指标上从低分提升到高分的公司进行一系列研究，了解他们优先做了什么，据此生成宽泛的推荐。然后你可以逐步打磨这些推荐，使其越来越直接地适用于每个客户。

如果这一切能够实现，我认为我们将进入一个非常了不起的阶段：开发者生产力团队主要成为执行团队而非分析团队，这将是该团队在行业中角色的一次根本性转变。
