异步处理，却要同步语义？

2018-01-15 · 阅读原文

最近我一直在更多地思考 ，特别是如何设计一个中等复杂度的 Web 应用，让它完全依赖于不可变日志，并通过日志处理器来维护物化视图。从 Lambda 到 Kappa 及 Dataflow 范式

其中一些有趣的问题包括：

是否有好的实现方式？能否在不让发布事件和处理事件的进程实现紧密耦合的情况下完成？发布者能否完全不感知写入逻辑，同时仍能提供同步的行为？

这似乎是个学习 docker-compose 的好机会，于是在周末我花了些时间，用 Docker 容器搭了一个运行 Kafka、Redis 和若干 Python 进程的简单集群。代码和 Docker 配置都放在了 Github（https://github.com/lethain/example-kappa-arch），下面是一些笔记和思考。

同步方式

首先，我实现了一个基础案例：一个 Python 应用直接向 Redis 写入数据。

对应的时序图非常简单。

一个略微简化的版本（完整版本在这里）大致如下：

@app.route('/<path:path>')
def hello(path):
    r = redis.Redis(host='redis')
    ts = int(time.time())
    r.zadd(RECENT_KEY, path, ts)
    r.zincrby(TOP_KEY, path, 1)
    recent = r.zrange(RECENT_KEY, 0, 10, desc=True, withscores=True)
    top = r.zrange(TOP_KEY, 0, 10, desc=True, withscores=True)
    now = datetime.datetime.now()
    return render_template('index.html', path=path, recent=recent,
                           top=top, elapsed=elapsed, now=now)

这运行得很好！所有逻辑都收敛在一个地方，但我们直接修改了状态，而且没有事件日志。很容易再加上一个事件日志（真实函数如下）：

publish(client, VIEW_TOPIC, path)

这时候我们的图变得稍微有趣了一些：

但整体依然很简单，所有操作仍是同步的。

现在我们有了事件日志，但状态并不是从日志中计算生成的。这意味着我们无法通过重放日志来重建状态，这完全违背了核心目标。（不过至少把数据送进了你的数据生态，方便后续处理！）

异步方式

要进入“事件日志驱动数据计算”的世界，最简单的方法就是把所有处理逻辑都移到消费者里。

这很简单，但我们无法再控制返回给客户端的响应顺序，无法保证它发生在处理完成之后。

现在的 Web 应用变成了这样：

@app.route('/<path:path>')
def hello(path):
    publish(client, VIEW_TOPIC, path)    
    r = redis.Redis(host='redis')
    recent = r.zrange(RECENT_KEY, 0, 10, desc=True, withscores=True)
    top = r.zrange(TOP_KEY, 0, 10, desc=True, withscores=True)
    now = datetime.datetime.now()
    return render_template('index.html', path=path, recent=recent,
                           top=top, elapsed=elapsed, now=now)

而写入逻辑则被移到了 Kafka consumer 中：

cli = get_client()
topic = cli.topics[VIEW_TOPIC]
consumer = topic.get_simple_consumer(reset_offset_on_start=True,
                                     queued_max_messages=1)
for message in consumer:
    path = message.value.decode('utf-8')
    r = redis.Redis(host='redis')
    ts = int(time.time())
    r.zadd(RECENT_KEY, path, ts)
    r.zincrby(TOP_KEY, path, 1)

我们不仅失去了对时序的控制，还造成读写逻辑被割裂的尴尬局面。虽然我们获得了一个不可变事件日志可以重放生成状态这一激动人心的特性，但整个应用已经无法正常工作，而且变得更难理解。

解耦且同步

我们真正想要的是：从客户端视角来看，Web 进程的行为仍是同步的——必须等到下游所有处理都完成后才返回——同时又不引入任何紧耦合。

嗯，这不就是那种罕见的“远程作用”（action at a distance）场景吗？

你可以想到一些特定于实现的方案，比如用 Redis Pub/Sub，让 Web 进程订阅一个频道，等待对应事件的写入确认。这虽然是个有趣的做法，但会在 Web 进程和消费者进程之间产生实现上的强耦合，从而抵消了 Kappa 架构的很多优势。

老实说，我目前还没看到能完全满足我需求的现成工具，但你可以大致想象一个这样的（有点模糊的）实现思路：

Web 把消息发给一个“同步协调进程”（sync process）；该进程把消息推入 Kafka，同时为每条消息注入一个唯一标识，并保持与 Web 的连接不关闭；下游各个消费者进程在完成处理后向 sync 进程“ack”；sync 进程要么维护一份需要确认的消费者清单（最好通过静态分析自动生成，而不是手动维护），要么通过采样系统行为来学习预期需要多少个 ack。采样听起来有点过度设计，但实际中你可能会用 p99 延迟来快速失败并继续处理。更有趣的一个轻量级 hack 是：你可能只需要依赖 p95 延迟，完全不实现“ack”机制也能工作。

这里提到的“ack”概念，本质上可以看作异步处理中实现背压（back pressure）的一个具体例子。你真正希望的是：同步阻塞 Web 进程，直到所有下游消费者都处理完在当前消息发布时刻或之前产生的所有消息。（这让我想起水位线 watermark 的概念。）

结束思考

总的来说，我认为“让发布者和消费者的实现强解耦，同时还能进行时序协调”这个问题，目前还没有被现有工具很好地解决，但也看不出有什么根本性的障碍，只是现在做起来还有点别扭。

我相信很快就会出现一些有趣的探索和实验！
