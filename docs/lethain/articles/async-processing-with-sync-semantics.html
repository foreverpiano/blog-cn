使用同步语义的异步处理？

2018-01-15 · 阅读原文

最近我一直在更多地思考 从 Lambda 到 Kappa 以及数据流范式，特别是如何设计一个中等复杂度的 Web 应用程序，让它完全依赖于不可变日志，并由日志处理器来维护物化视图。

其中一些有趣的问题包括：

是否有好的实现方式？能否在不让发布事件和处理事件的进程实现紧密耦合的情况下做到这一点？发布者能否不感知写逻辑，同时还能提供同步行为？

这似乎是个学习 docker-compose 的好机会，于是我周末花了些时间，用 Docker 容器搭了一个简单的集群，里面跑着 Kafka、Redis 和 Python 进程。代码和 Docker 配置都放在了 Github](https://github.com/lethain/example-kappa-arch)，下面是一些笔记和思考。

同步方式

首先，我实现了一个基础案例：一个 Python 应用直接写 Redis。

对应的时序图非常简单。

一个稍微简化的版本（完整版本在这里）大致如下：

@app.route('/<path:path>')
def hello(path):
    r = redis.Redis(host='redis')
    ts = int(time.time())
    r.zadd(RECENT_KEY, path, ts)
    r.zincrby(TOP_KEY, path, 1)
    recent = r.zrange(RECENT_KEY, 0, 10, desc=True, withscores=True)
    top = r.zrange(TOP_KEY, 0, 10, desc=True, withscores=True)
    now = datetime.datetime.now()
    return render_template('index.html', path=path, recent=recent,
                           top=top, elapsed=elapsed, now=now)

这运行得很好！所有逻辑都集中在同一个地方，但我们直接在修改状态，而且没有事件日志。添加一个事件日志其实很简单（实际函数如下）：

publish(client, VIEW_TOPIC, path)

这时候我们的图就变得有点意思了：

但整体依然简单，所有操作都是同步的。

现在我们有了事件日志，但状态并不是从日志中生成的。这意味着我们无法通过重放日志来重建状态，这就违背了整个架构的初衷。（不过至少把数据送进了你的数据生态系统，方便后续处理！）

异步方式

要进入“用事件日志计算出数据”的世界，最简单的方式就是把所有处理逻辑都移到消费者里。

这很简单，但我们无法控制返回给客户端的时机，无法保证在处理完成后再响应。

现在的 Web 应用变成了：

@app.route('/<path:path>')
def hello(path):
    publish(client, VIEW_TOPIC, path)    
    r = redis.Redis(host='redis')
    recent = r.zrange(RECENT_KEY, 0, 10, desc=True, withscores=True)
    top = r.zrange(TOP_KEY, 0, 10, desc=True, withscores=True)
    now = datetime.datetime.now()
    return render_template('index.html', path=path, recent=recent,
                           top=top, elapsed=elapsed, now=now)

而写逻辑则被移到了 Kafka 消费者中：

cli = get_client()
topic = cli.topics[VIEW_TOPIC]
consumer = topic.get_simple_consumer(reset_offset_on_start=True,
                                     queued_max_messages=1)
for message in consumer:
    path = message.value.decode('utf-8')
    r = redis.Redis(host='redis')
    ts = int(time.time())
    r.zadd(RECENT_KEY, path, ts)
    r.zincrby(TOP_KEY, path, 1)

我们不仅失去了对时序的控制，还制造了一个相当别扭的情况——读写逻辑被拆分了。虽然我们获得了一个可以重放生成状态的不可变事件日志这一激动人心的特性，但应用已经无法正常工作，而且变得更难理解。

解耦且同步

我们真正想要的是：从客户端视角看，Web 进程表现得像同步的一样——必须等下游处理全部完成后才能返回，同时又不引入任何紧耦合。

嗯，这可是难得的“远程作用”场景啊？

你可以想到一些具体实现方式，比如在这个场景中可以使用 Redis 的 pubsub，订阅一个频道来接收特定事件的写完成确认。这是一个有趣的思路，但它让 Web 和消费者进程的实现产生了紧耦合，从而抵消了 Kappa 架构的一些重要优势。

老实说，我目前还没见过能完全满足我需求的现成工具，但你可以想象一个大致如下（有点模糊）的实现方案：

Web 向一个同步协调进程发送消息；该进程把消息推入 Kafka，并在每条消息中注入一个唯一标识，同时保持与 Web 的连接不关闭；各个消费者进程在完成处理后向同步进程“ack”；同步进程要么维护一份需要确认的消费者清单（最好通过静态分析生成，而不是手动维护），要么通过采样系统行为来学习预期需要多少个 ack。采样听起来有些过度设计，但在实践中你可能会希望使用 p99 延迟来快速失败并继续处理。实际上，作为一个轻量级实现的小技巧，我觉得可能只需要依赖 p95 延迟，甚至完全不用实现“ack”机制。

这里所说的“ack”概念，大概可以看作是在异步处理中实现背压（back pressure）这一挑战的一个具体例子。举例来说，你真正希望的是同步阻塞 Web 进程，直到所有下游消费者都处理完在当前消息发布时刻或之前产生的所有消息。（这让我想起水位线 watermark 的概念。）

结束思考

总的来说，我认为解决这个问题——即在发布者和消费者实现之间实现强解耦的同时，还能进行时序协调——现有工具做得并不好，但也没有明显的理由说这不可能做到，只是目前实现起来还有点别扭。

我猜很快就会出现一些有趣的实验！
