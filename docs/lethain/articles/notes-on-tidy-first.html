《Tidy First?》笔记

2023-11-19 · 阅读原文

Kent Beck 的《Tidy First?》既捕捉到了 John Ousterhout《软件设计的哲学》中的精髓，又深刻认识到了在团队和业务环境中开发软件所固有的张力。而且这本书大约两个小时就能读完。强烈推荐！

John Ousterhout 的 《软件设计哲学》笔记 是我最喜欢的软件设计书籍之一。当我听说 Kent Beck 新书《Tidy First?》出版时，它有意与类似主题展开对话，但采用了截然不同的教学方式，我就知道自己必须读一读。（当我意识到这本书只有大约一百页、两三个小时就能读完时，就更坚定了这个想法。）

《Tidy First?》从解释 Guard Clauses 开始，认为与其这样写：

if (condition):
  if (not other condition):
      ...some code...

不如这样写会更好：

if (not condition) return
if (other condition):
    ...some code...

在此基础上，Beck 构建了一套软件开发方法：要有意识地将“整理”（修改结构）的变更与修改应用逻辑的变更区分开来，并安排好它们的顺序。

以下是我对这本书内容的最佳 bullet point 总结：

做事没有唯一正确的方法，只有在特定上下文中合理的方法，而你最了解自己的上下文；有许多不同的整理代码的方式，它们都能让代码更易于维护：比如使用 guard clauses、移除死代码、规范化对称结构等等；整理代码和修改逻辑是两种不同类型的工作，应该放在不同的 pull request 中；这能加快代码审查速度，而且在高凝聚力的团队中，整理提交甚至不需要代码审查；整理工作应该小步进行，而不是大规模进行；整理通常最好在修改应用逻辑之前完成，只要它能降低后续逻辑变更的成本；在变更之后整理、以后有时间再整理、甚至永远不整理（针对那些不怎么变化的代码）也都是可以的；耦合对可维护的代码来说是非常糟糕的。

我非常喜欢这本书，阅读过程中脑子里反复出现三个主要想法：

我从未见过按这种方式工作的团队——真的有团队是这样工作的吗？我见过的大多数团队工作方式都属于“从不整理”阵营，它们隐含的信念是：软件除了完全重写之外几乎不可能变得更好。如果你认真思考一下，这其实挺令人沮丧的。生活在一个团队相信软件无需彻底替换就能持续改进的世界，难道不是一件很鼓舞人心的事吗？

任何一本书，如果能让你重新审视某个相当坚定的信念，尤其是在行业中工作了相当长时间之后，都说明它做对了什么，而《Tidy First?》无疑属于这一类。

我很好奇最终会有多少团队采用这种方法，什么因素会让团队更可能或更不可能采纳。它是否主要适用于已经模块化的小型团队？适用于小型单体应用？还是大型 monorepo？未来几年我们会看到业界会从中吸取什么经验。
