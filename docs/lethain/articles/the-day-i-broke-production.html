我把生产环境搞崩的那一天

2010-02-14 · 阅读原文

作为开发人员，我经历过的最刺激的一天，莫过于把生产环境搞崩的那次。 虽然最后我幸运地全身而退，但那次经历对我影响深远；从此以后，我在生产环境中敲键盘和思考时，再也不敢像以前那样粗心大意了。

我们的产品融合了 Erlang、Java 和 PHP，要找出一种合理的部署方式，着实经历了一段不小的学习曲线。 PHP 升级通常什么都不用做，有时只需要重启一下 Apache。 Java 升级则需要先杀死正在运行的进程，再用更新后的代码启动一个新的。 Erlang 组件的升级是杀死 beam 进程，然后重新运行启动脚本。 而被 Erlang 包裹的 Java 服务，则需要杀死并重启 Erlang 进程。

至少，理论上是这样工作的。

问题来了

在部分（但并非全部）部署之后，我们遇到一个奇怪的问题：pg2 中会残留一些僵死的进程。 这会导致 gen_server:call 在 pg2:get_closest_pid 碰巧选中某个已经死掉的进程时失败，进而让调用方崩溃。 通常这些部署就像往我们用纸牌搭的房子上泼汽油，而下一个进来的请求就是那点燃一切的火花。

在部署一个 Alpha 产品时出现一些磕磕绊绊本不奇怪，但问题总是在部分而非全部部署后冒出来，还是让人越来越烦躁。 虽然我们后来找到了更好的临时方案，也最终理解了根本原因（后面会再提到），但在那之前，我们只能靠手动清理。

头几次出现这个问题时，清理工作完全是手动的——在 Erlang shell 里敲命令，然后狂按回车键。 说来也巧，这就把我们带入了“我把生产环境搞崩的那一天”的故事。

比疾病更糟糕的“治疗”

有一次部署之后，明显能看出“僵尸进程瘟疫”又来拜访我们的系统了。当时另外两名工程师中，一个正在度一个月的长假，另一个一时联系不上。于是我面临两个选择：悄悄地去吃一顿长长的午饭，或者自己动手解决。

于是我动手修复了这个问题——算是吧。我写下的代码大致是这样的：

RemoteIsAlive = fun(Pid) ->
    rpc:call(node(Pid), erlang, is_alive, [Pid])
  end,
lists:foreach(fun(Group) ->
Pids = pg2:get_members(Group),
Filtered = lists:filter(RemoteIsAlive, Pids),     
lists:foreach(fun(Pid) -> pg2:leave(X, Group) end, Filtered)
end, pg2:which_groups()).

这段代码有个小小的缺陷：它把所有存活的进程都从进程组里移除了，只留下死进程来处理请求。 Oops。

之后我给 QA 负责人发了消息，请他无视即将到来的一波测试失败，然后开始修复我的修复。首先，我在所有节点上删除并重新创建了现有的进程组，以清理掉死进程；接着我逐个节点重启了上面运行的应用（这样它们就会重新加入新的进程组，从而用存活进程把组填满）。

当时我们只有大约八个节点，所以整个过程只花了几分钟，但那真是无比紧张的几分钟。

各种各样的解决方案

那次事件之后，我们从多个方面改进了这种情况，特别是：

立即采取的修复措施是：通过包装 gen_server:call 来过滤掉 pg2 中的死进程，做法类似这篇关于在进程组间做负载均衡的文章所描述的，同时增加在选择最佳进程路由请求之前先清理进程组中死进程的逻辑。 在深入调查根本原因时，我们发现我们的一些 gen_server 实现没有 trap_exit，因此它们的 terminate 函数没有被调用，导致进程停止后从未离开进程组。

很多经验丰富的 Erlang 开发者可能会认为，根本问题在于我们以错误的方式部署 Erlang 代码。简单的方法是使用 l 函数重新加载模块，更完善的方式则是使用 appup 来管理 Erlang 应用的升级。

我认为，我们当时的做法对于纯 Erlang 系统，或者整个团队/公司都精通 Erlang 的情况来说，无疑是错误的。但我不太愿意承认，在一家拥有自己熟悉的部署机制的大型企业里，这种做法毫无道理。大公司总是很在意采用新事物的成本，而加快采用的关键就是降低采用成本，这往往要以牺牲纯粹性为代价。（这个话题可能值得认真讨论，而不只是作为事后补记。）

虽然系统最终安然无恙，但那一天对我来说绝对是一堂深刻的学习课。 即使是简单而显而易见的方案，在生产部署的熔炉里也可能炸裂。 如果当时能采用更多防御性编码和更全面的故障测试（很多开发者在这类测试上常常疏忽到离谱的地步），整个事故本来是可以避免的。
