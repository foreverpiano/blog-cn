邮件袋：如何鼓励写出好的文档，而不是完美的文档？

2021-02-15 · 阅读原文

最近在 Staff Engineer 上收到的一个很棒的问题：

在你写文档（以及评审文档）的时候，我非常认同“追求良好而非完美”的理念。好奇的是，除了自己这样做之外，你如何在团队中培养这种文化？我感觉自从我们转向远程办公后，文档打磨的程度达到了历史最高点。你是否也感受到了这一点？

现在有一种越来越普遍的信念，认为书面沟通是“显然最佳”的沟通文化。这最初源于 Amazon 备忘录文化的对外输出，最近又因疫情推动的远程办公转变而得到进一步加强。我个人非常喜欢书面沟通，但这是一种具有挑战性的转变。这个问题恰好指出了这种转变可能走偏的一个方向：对完美的强调而非对良好的追求，从而拖慢了讨论进程。

这对工程团队来说是一个相当常见的问题。它经常出现在系统设计中，体现在 YAGNI 原则与“不希望六个月后重写系统”之间的张力。更常见的是，大多数工程师都经历过这样的团队：在代码评审中，如果给出过多吹毛求疵的反馈，会导致大家只有在方案完全定型、无法再修改时，才会提交 Pull Request 供评审。

代码评审的例子可能是最大家熟悉的，因此我们可以思考一下：那些用于修复低效代码评审流程的策略，如何应用到文档写作文化中：

人们会因为感到不舒服而隐藏自己的工作。如果文档分享得很晚，通常是因为分享过程中的某些环节让作者感到不适。通常这是因为他们收到的反馈没有帮助他们达成目标。可能是反馈太多，大家为了减少回复数量而等到很晚才分享；也可能是反馈没有用处，所以大家干脆等到无法轻松采纳新想法的时候才请求反馈。你公司里可能有四个人让写文档变得令人不舒服。在你开始考虑系统层面的解决方案之前，我猜实际上只需要对极少数人进行直接 coaching，告诉他们如何对文档提供反馈。如果你让他们对如何参与他人文档评审负责，这可能就足以解决整个问题。提供结构化的模板和文档生命周期。一个灵活的文档模板可以消除关于结构问题的争论。文档生命周期流程则能明确什么时候应该提供哪种类型的反馈。模板和生命周期就像代码评审中的代码 linter，让反馈从关注风格转向关注实质。文档评审是一项可以教授的技能。如果你请人编辑一份文档，会有惊人数量的人立刻开始修改措辞或提供语法建议。有时候这很有用，但通常没有。工程师通过频繁重复能逐渐擅长代码评审，但大多数人没有足够多的文档评审机会来变得熟练。幸运的是，这是一项可以教授的技能。让大家在留下任何评论前先完整阅读一遍文档（避免那种可怕的“但这个后面已经讲到了……”的回复）。将反馈重点放在想法上，而不是格式上。指定一位友好的评审人 / 写作教练。更进一步说，大多数人其实也没有太多写文档的经验！你可以通过提供一位写作教练（最好是他们领域内有经验的工程师）来降低分享文档的感知风险，这位教练可以提供非常早期的反馈。这位教练也能很好地推动大家在文档“足够好”时就发布，而不是继续无休止地打磨。此外，这个人还能为分享文档的作者提供“社会证明”，借用自己作为资深工程师的信誉，向作者担保他们的文档确实已经可以分享了。提供一个“黄金文档”仓库，展示恰到好处的质量水平。我猜你已经有一个“示例文档”清单，供大家效仿，而我猜那些文档都极其出色。也就是说，如果当前对完美的强调太过，那些文档恰恰不是你希望大家去模仿的榜样。创建一个新的“黄金文档”清单，这些文档不一定是最好的，而是质量水平恰到好处的。你甚至应该特意指出哪些文档是“太好了”。是的，它们很漂亮，但那不是我们在这里想要达成的目标。

在所有这些方法中，我认为最有效的方式是：自己持续以身作则地展现“良好而非完美”的行为，推动其他领导者，并将自己作为资深者的特权借给那些敢于发布不够完美的文档、从而承担更大风险的作者。示范、记录与分享。
