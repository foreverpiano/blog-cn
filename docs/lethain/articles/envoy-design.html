对 Envoy 设计的思考

2016-09-18 · 阅读原文

几天前 Lyft 发布了 Envoy，这是一个在七层代理领域相当令人兴奋的创新。我最近一直在思考这个领域，既包括如何大规模部署QoS、成本与配额，也包括在多语言（polyglot）环境中进行请求路由的问题。

在分享我的看法之前，我们先简单回顾一下常见的负载均衡策略。

历史上，最常见的负载均衡方式是使用某种集中式负载均衡器，将所有流量都路由到它。这些负载均衡器可以是像 ELB 这样按服务划分的，也可以是 F5 这类非常复杂的高端硬件设备。

如今，这种方式似乎越来越过时了。

部分原因是其成本和复杂性，但在我看来，更主要的原因是缺乏灵活性和控制力。作为程序员，以编程方式管理 HAProxy 相对直观，而大多数集中式负载均衡器并不提供这种能力。（即使是 HAProxy，以编程方式管理也并不容易，不过它正稳步进步。）

在另一个极端，是像 Finagle 这样的进程内负载均衡，每个进程都维护自己的健康检查和路由表。这种方式能提供极高的定制化和控制力，但要求你解决相当棘手的库管理问题。

对于只使用一种语言或运行时（通常是 JVM）、并且采用 monorepo 的公司来说，库管理问题还比较容易处理。而对其他大多数人——使用三种或更多语言，或者按仓库拆分服务——这些问题则需要投入大量生态系统建设工作。

一些致力于支持多语言和多仓库的公司（比如 Netflix、Uber）正在逐步构建所需的基础设施，但总体而言，这不是你想自己承担的问题，这也正是 Sidecar 模式出现的主要原因。

Sidecar 模式是指在每台服务器上运行一个代理进程，让该服务器上的所有其他进程都通过这个本地进程进行通信。很多公司——包括任何曾经雇佣过 Digg 系统工程师的公司——已经用 HAProxy 以这种模式运行了很长时间，它很好地平衡了灵活性，同时又无需解决库管理问题。

Sidecar 路由器的传统缺点之一是对 HTTP/1.0 和 HTTP/1.1 以外协议的支持较差，而且很少有既高性能又高度可定制的选项（HAProxy 性能出色，但在尝试做更复杂的事情时会变得相当脆弱）。

这正是 Envoy 的用武之地。

好了，让我们先说说 Envoy 做得特别出色的地方。

首先，它的文档非常优秀。尤其是在解释高层架构、以及引导读者理解设计约束方面做得很好。我猜他们当时一定经过艰难的讨论才决定推迟发布，直到文档打磨到这个水平，但我很高兴他们这么做了。

其限流支持方式也非常棒。很多系统都要求你采用它们自己的配套工具生态（比如 Kafka 需要同时部署 Zookeeper），但 Envoy 定义了一个 gRPC 接口，限流服务器只需实现该接口，从而将自身与限流实现的具体细节解耦。我希望更多系统能采用这种方式，以实现更好的互操作性。（从长远来看，我期待未来我们能有针对限流、更新路由表、登录、追踪等常见功能的共享标准接口。）

使用异步 DNS 解析也是一个非常聪明的设计决策。同步 DNS 解析可能会很慢，而且如果 DNS 解析服务不可用（我确实遇到过好几次，主要是 bind 把 CPU 核心跑满了），你就会继续使用上次解析的结果。这种方式还能让你避开各种语言 DNS 解析器那些独具特色且令人头疼的缺陷和不一致性。

通过 Unix Domain Socket 实现的热重启也很有意思，特别是容器已被视为首要的设计约束之一。在新的系统设计之初，就已经把“如何与容器部署配合工作”作为一个核心问题来考虑，而不是事后才去修补。

很长一段时间里，Thrift 似乎是领先的 IDL，但最近越来越难反驳 gRPC 的优势：它有良好的多语言支持，而且基于 HTTP/2 的决定使其能够将双向流式通信作为服务的基础构建块。看到 Envoy 如此看好 gRPC，我感到非常兴奋，这将大大降低已经在使用 Sidecar 路由器的公司采用 gRPC 和 HTTP/2 的门槛。

除了这些优秀特性外，我认为最有趣的是有可能在 HTTP 和 TCP 过滤器机制之上发展出一个更广泛的生态系统。这种设计足够通用，别人可以添加更多协议，或根据自身需求定制行为（比如把集中式限流换成本地限流器，或把本地熔断器换成集中式熔断器等）。

你可以想象这样一个生态系统：支持 MySQL 和 PostgreSQL 协议的 TCP 过滤器、更全面的背压工具（用于延迟注入）、类似 Hystrix 的全局熔断机制（如果能直接集成 Hystrix 的仪表盘，而不是重新开发类似功能，那会非常棒），甚至还能手动封禁特定 IP，以更方便地保护系统免受行为异常的客户端影响（当然不是应对 DDoS，而是防止失控脚本之类的）。

关于初始版本中一个具体缺失功能的例子，根据我的经验，分布式健康检查——即使做了本地缓存——在某些规模下成本仍然过高（随便猜一下，大概在每台服务器跑 10 个服务、总共 1 万台服务器的规模左右）。为此提供一个集中式的健康检查缓存，将是对 Envoy 非常有价值的大型部署扩展。（很多人永远不会遇到这个问题，要么因为不需要那么多服务器和服务，要么因为把故障域控制得比较小。一个有足够资源且前瞻性的工程团队可能也永远不需要这个功能。如果你想尝试解决这个问题，RAFT 协议在去中心化健康检查方面有一些不错的思路。）

另一个简短的想法是，我没有看到任何关于在健康检查之外同时检查身份（identity）的讨论。糟糕的部署和错误的配置有时会导致服务运行在意料之外的地方，而最坏的情况下，这个意料之外的地方正好是另一个无关进程应该运行的位置。理想情况下，你的负载均衡器应该能让服务表明自己的身份（包括某种唯一标识符及其版本），从而帮助避免一些非常特定且难以调试的问题。

总的来说，随着 Twitter 和 Google 的许多有趣想法逐渐成为主流，服务发现和路由领域正变得越来越热闹，我非常期待看到 Envoy 留下自己的印记。
