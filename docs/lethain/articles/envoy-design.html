对 Envoy 设计的思考

2016-09-18 · 阅读原文

几天前 Lyft 发布了 Envoy，这是一个针对七层代理（layer 7 proxy）非常令人兴奋的实现。我最近一直在思考这个领域，既包括大规模部署 QoS、成本与配额，也包括在多语言（polyglot）环境中的请求路由问题。

在谈我的看法之前，我们先快速回顾一下常见的负载均衡策略。

历史上，最常见的负载均衡方式是使用某种集中式负载均衡器，并将所有流量都路由到它。这些 LB 可以在每个服务层面实现，比如 ELB，也可以是像 F5 这样非常复杂的硬件设备。

如今，这种方式似乎越来越不受欢迎。

部分原因是它们的成本和复杂度，但在我看来，它们逐渐失宠更多是因为缺乏灵活性和控制力。作为程序员，以编程方式管理 HAProxy 相对直观，而大多数集中式负载均衡器无法提供这种能力。（其实即使是 HAProxy，用程序化方式管理也并不容易，不过它一直在稳步进步。）

在这个谱系的另一端，是像 Finagle 这样的 per-process 负载均衡，每个进程都维护自己的健康检查和路由表。这种方式能提供极高程度的定制和控制，但要求你解决相当棘手的库管理问题。

对于只使用一种语言或运行时（通常是 JVM）、并且采用 monorepo 的公司来说，库管理问题相对容易解决。而对其他大多数公司——那些使用三种及以上语言，或采用“每个服务一个仓库”模式的公司——这类问题需要投入大量的生态系统建设。

一些致力于支持多语言和多仓库的公司（比如 Netflix、Uber）正在缓慢构建必要的基础设施，但总体而言，这并不是你想自己承担的问题，这也正是 sidecar 模式出现的主要原因。

sidecar 模式是指在每台服务器上运行一个代理进程，服务器上的所有其他进程都通过这个本地进程进行通信。许多公司——包括所有曾经雇佣过 Digg 系统工程师的公司——已经用 HAProxy 以这种模式运行了很长时间。它很好地平衡了灵活性，同时又无需解决库管理问题。

sidecar 路由器传统上的一个缺点是，对 HTTP/1.0 和 HTTP/1.1 之外的协议支持较差，并且很少有既高性能又高度可定制的选项（HAProxy 性能出色，但在做更复杂的事情时会变得相当脆弱）。

这正是 Envoy 的用武之地。

好了！让我们先来看看 Envoy 做得特别出色的地方。

首先，它的文档非常优秀。尤其是在解释高层架构和阐述引导他们采用该架构的设计约束方面，做得非常出色。我猜他们当初决定推迟发布项目，直到文档打磨到这个水平，一定经过了艰难的讨论，但我很高兴他们这么做了。

其限流（ratelimiting）支持方式也非常棒。很多系统都要求你采用它们自己的配套工具生态（比如 Kafka 需要同时部署 Zookeeper，就是一个典型的例子），而 Envoy 定义了一个 gRPC 接口，限流服务器只需实现该接口，从而将自己与限流的具体实现细节解耦。我希望看到更多系统采用这种方式，以实现更好的互操作性。（从长远来看，我期待未来我们能有针对限流、更新路由表、登录、追踪等常见功能的共享标准接口。）

使用异步 DNS 解析也是一个非常聪明的设计决定。同步 DNS 解析可能会很慢，而且一旦 DNS 解析不可用（这种情况我遇到过好几次，主要是 bind 把 CPU 核心跑满的时候），你就会一直路由到上次解析的结果。这种异步方式还能让你避免深究各种语言 DNS 解析器的复杂细节——那些解析器常常以独特而有趣的方式出错或不可用。

使用 Unix domain socket 实现的热重启（hot restart）也很有意思，特别是容器已经被当作一项一流的设计约束来对待。不再是事后补救的方案，而是在新系统设计之初就提出：“这个该如何与容器部署配合工作？”

很长一段时间里，Thrift 似乎是领先的 IDL，但最近越来越难反驳 gRPC 的优势：它有良好的语言支持，而且基于 HTTP/2 的决定使其能够将双向流式通信作为服务的基础构建块。看到 Envoy 以这种方式押注 gRPC，我感到非常兴奋，这将大大降低已经在使用 sidecar 路由器的公司采用 gRPC 和 HTTP/2 的门槛。

除了这些优秀特性，我认为最有趣的是有可能在 HTTP 和 TCP 过滤器机制之上发展出一个更广阔的生态系统。这种设计看起来足够通用，别人可以添加更多协议，并根据自身需求定制行为（比如把集中式限流换成本地限流器，或把本地熔断器换成集中式熔断器等等）。

你可以想象这样一个生态系统：支持 MySQL 和 PostgreSQL 协议的 TCP 过滤器、更全面的背压工具（用于注入延迟）、类似 Hystrix 的全局熔断机制（如果能直接集成 Hystrix 的仪表盘，而不是重新做一个类似的东西，那就太棒了），甚至能够手动封禁特定 IP，从而更轻松地防范行为异常的客户端（当然不是应对 DDoS，而是防止失控的脚本之类的）。

关于初始版本中一个具体的功能缺失，根据我的经验，分布式健康检查——即使本地缓存了检查结果——在达到一定规模后仍会过于昂贵（随便猜一个数字，大概在每台服务器跑 10 个服务，总共 10000 台服务器左右的规模）。提供一个集中式的健康检查缓存，将会是对 Envoy 非常有价值的扩展，尤其适合超大规模部署。（很多人永远不会遇到这个问题，要么是因为不需要那么多服务器和服务，要么是因为把故障域控制在较小的范围内。资源充足的主动型工程团队可能也永远不需要这个功能。如果你想尝试解决这个问题，RAFT 协议在去中心化健康检查方面有一些相当不错的思路。）

另一个简短的想法是，我没有看到任何关于“除了检查健康状态，还要检查身份”的讨论。不良的部署和错误的配置有时会导致服务运行在意外的位置，而最坏的情况下，这个意外位置正好是另一个无关进程应该所在的位置。理想情况下，你的负载均衡器应该能让服务表明自己的身份（包括某种唯一标识符及其版本），从而避免一些非常特定且难以调试的问题。

总的来说，随着 Twitter 和 Google 最有趣的想法逐渐成为主流，服务发现和路由领域正变得越来越热闹。我非常期待看到 Envoy 留下自己的印记。
