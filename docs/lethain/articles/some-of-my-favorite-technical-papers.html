我最喜欢的一些技术论文。

2018-04-07 · 阅读原文

我长期以来一直是 主持技术论文阅读小组 的粉丝，这种活动让一群人坐下来一起讨论有趣的技术论文。要开展这类活动，第一步通常是找到值得讨论的论文，这里列出了一些我见过能引发精彩讨论的论文！

Dynamo: Amazon’s Highly Available Key-value Store

如果只读摘要，你可能会对 Dynamo 这篇论文不够兴奋：本文介绍了 Dynamo 的设计与实现，这是一个高可用性的键值存储系统，Amazon 的部分核心服务用它来提供永不宕机的体验。为了达到这种可用性水平，Dynamo 在某些故障场景下牺牲了一致性。它大量使用对象版本化和应用辅助的冲突解决机制，为开发者提供了一种新颖的接口。

尽管如此，从某些意义上说，这仍是现代系统领域的“经典”论文。我不止一次遇到过一些工程师，他们职业生涯中只读过一篇系统论文，而那篇就是 Dynamo。它是一篇极好的入门读物，介绍了最终一致性、在分布式存储中协调状态、跨副本数据分歧时的调和等诸多内容。

Hints for Computer System Design

Butler Lampson 是 ACM 图灵奖得主（以及其他奖项），曾在 Xerox PARC 工作。这篇论文简洁地总结了他关于系统设计的许多想法，非常值得一读。

用他自己的话来说：

对众多计算机系统的设计和实现进行研究后，我们得出了一些系统设计的一般性建议。本文将对这些建议进行描述，并通过大量示例加以说明，示例范围从 Alto 和 Dorado 等硬件，到 Bravo 和 Star 等应用程序。

这篇论文本身承认它并不打算开辟新领域，但它是一篇极好的综述。

Big Ball of Mud

这是一篇针对那些热情洋溢地讨论宏大设计模式的论文的回应，它将最常见的架构模式称为“大泥球”（Big Ball of Mud），并探讨了为什么优雅的初始设计在系统从概念走向解决方案的过程中很少能保持原样。

摘自摘要：

虽然人们对高级软件架构模式给予了很多关注，但实际上被广泛采用的软件架构却很少被讨论。本文考察了这种最常被部署的软件架构：大泥球（BIG BALL OF MUD）。大泥球是一个随意、甚至是随意拼凑而成的系统。它的组织结构——如果能称之为组织的话——更多由权宜之计而非设计决定。然而，它持久的受欢迎程度不能仅仅表明大家普遍忽视架构。

虽然这篇论文充满幽默，但它也指出软件设计往往非常糟糕，很少有系统真正经历过设计阶段，即使有也很少能与最初设计保持一致（文档也很少更新以反映后续决策），因此这是一个值得认真考虑的重要话题。

The Google File System

摘自摘要：

该文件系统成功满足了我们的存储需求。它在 Google 内部广泛部署，作为我们服务生成和处理数据以及需要大规模数据集的研究和开发工作的存储平台。迄今为止最大的集群在超过一千台机器上提供了数百 TB 的存储空间，跨越数千个磁盘，并同时被数百个客户端访问。
在这篇论文中，我们介绍了为支持分布式应用而设计的文件系统接口扩展，讨论了设计的诸多方面，并报告了微基准测试和实际使用场景下的测量结果。Google 在定义硅谷乃至整个技术行业的技术主题方面做了相当了不起的工作（过去十多年里只有最近 Facebook 和 Twitter 在达到一定规模后才在较小程度上加入），而这很大程度上是通过他们出色技术论文实现的。Google File System（GFS）论文是这一策略的早期代表之一，也正是它在很大程度上启发了 Hadoop File System（HFS）。

On Designing and Deploying Internet-Scale Services

我们并不总是记得要把微软视为最大的互联网技术玩家之一，尽管 Azure 越来越让这种对比变得显而易见，但在 2007 年它还不是一个必然会想到的名字。这篇来自 James Hamilton 的优秀论文探讨了在极大规模下构建可运维系统的经验，它清楚地表明，不把微软视为大型互联网玩家是我们集体判断上的疏忽。

摘自摘要：

系统与管理员的比例通常被用作粗略衡量高规模服务管理成本的指标。对于规模较小、自动化程度较低的服务，这个比例可能低至 2:1，而在业界领先、高度自动化的服务中，我们见过高达 2500:1 的比例。在微软的服务中，Autopilot [1] 经常被认为是 Windows Live Search 团队实现高系统与管理员比例的魔法。虽然自动管理很重要，但最重要的因素实际上是服务本身。这个服务是否易于自动化？它是否是我们通常所说的“运维友好”？运维友好的服务需要很少的人工干预，并且能在几乎所有非极度隐晦的故障中自动检测和恢复，而无需管理员干预。本文总结了多年来在 MSN 和 Windows Live 上扩展一些最大规模服务时积累的最佳实践。

这是一份真正用于设计和评估大规模系统的检查清单（几乎就像 The Twelve Factor App 希望成为可运维应用的检查清单一样）。

CAP Twelve Years Later: How the Rules Have Changed

Eric Brewer 在 2000 年代初提出了 CAP 定理，十二年后他写了这篇优秀的概述和回顾，部分原因在于：

自引入以来十年间，设计师和研究者们使用（有时滥用）CAP 定理作为理由去探索各种新颖的分布式系统。NoSQL 运动也将其作为反对传统数据库的论据。CAP 有趣之处在于没有一篇“开创性的 CAP 论文”，但这篇文章很好地充当了它的替代品。这些想法在 Harvest and Yield 那篇论文中得到了进一步扩展。

Harvest, Yield, and Scalable Tolerant Systems

这篇论文基于 CAP Twelve Years Later 中的概念，引入了 harvest 和 yield 的概念，为 AP 与 CP 的讨论增添了更多细微差别：

将一致性和状态管理与高可用性调和的代价，由于当今互联网应用前所未有的规模和鲁棒性要求而被极大放大。我们提出两种策略，使用简单的、可在大规模应用上扩展的机制来提升整体可用性，这些应用的输出行为能够容忍优雅降级。我们用 harvest 和 yield 来刻画这种降级，并直接将其映射到通过提升故障隔离来增强可用性的工程机制，在某些情况下还能简化编程。通过收集文献中相关技术的例子，并展示这些方法可以惠及的惊人广泛的应用范围，我们希望能激发该领域更广泛的研究计划。

harvest 和 yield 的概念特别有趣，因为它们既显而易见却又很少被明确使用，相反分布式系统仍然在以大多未定义的方式失败。希望随着我们反复重读这篇论文，我们也能开始将其设计理念融入后续构建的系统中！

MapReduce: Simplified Data Processing on Large Clusters

MapReduce 论文是一个极好的例子，它所代表的想法已经如此成功，以至于现在看起来不言自明。将函数式编程概念应用到大规模场景的想法成为了一个号角，促使数据仓库转向一种新的数据分析范式：

MapReduce 是一种编程模型及其相关实现，用于处理和生成大规模数据集。用户指定一个 map 函数来处理键/值对并生成一组中间键/值对，以及一个 reduce 函数来合并所有与同一中间键关联的中间值。许多现实世界的任务都可以用这个模型表达，正如论文中所展示的那样。

正如 Google File System 论文启发了 Hadoop File System 一样，这篇论文本身也是 Hadoop 的重要灵感来源。

Dapper, a Large-Scale Distributed Systems Tracing Infrastructure

Dapper 论文介绍了一种在多个服务间追踪请求的高性能方法，随着越来越多公司将核心单体应用重构为数十乃至数百个微服务，这一点变得越来越重要。

摘自摘要：

在这里我们介绍了 Dapper 的设计，它是 Google 的生产级分布式系统追踪基础设施，并描述了我们如何实现低开销、应用层透明以及在超大规模系统上普遍部署的设计目标。Dapper 在概念上与其他追踪系统（特别是 Magpie 和 X-Trace）有相似之处，但我们做出了一些设计选择，这些选择对它在我们环境中的成功至关重要，例如使用采样和将插桩限制在数量较少的常用库上。

Dapper 的思想后来进入了开源领域，尤其体现在 Zipkin 和 OpenTracing 中。

Kafka: a Distributed Messaging System for Log Processing

Apache Kafka 已经成为许多互联网公司的核心基础设施之一。它的多功能性使其适用于多种角色，对一些公司来说是进入“数据大陆”的入口，对另一些来说是持久化队列，而这仅仅触及皮毛。

Kafka 不仅是你工具箱中有用的补充，它还是一个设计精美得令人惊叹的系统：

日志处理已成为面向消费者的互联网公司数据管道中的关键组件。我们介绍了 Kafka，这是一个我们为收集和交付高吞吐量、低延迟日志数据而开发的分布式消息系统。我们的系统融合了现有日志聚合器和消息系统的思想，适用于离线和在线的消息消费。我们在 Kafka 中做出了不少非常规但实用的设计选择，以使其高效且可扩展。实验结果表明，与两种流行的消息系统相比，Kafka 具有显著的性能优势。我们已经在生产环境中使用 Kafka 一段时间了，每天处理数百 GB 的新数据。

特别是，Kafka 的分区机制出色地迫使应用设计者明确在性能与可预测的消息顺序之间做出权衡。

Wormhole: Reliable Pub-Sub to Support Geo-replicated Internet Services

在很多方面与 Kafka 类似，Facebook 的 Wormhole 是另一种高度可扩展的消息传递方法：

Wormhole 是一个发布-订阅（pub-sub）系统，专为 Facebook 地理复制的数据中心开发。它被用于在包括 TAO、Graph Search 和 Memcache 在内的多个 Facebook 服务之间可靠地复制变更。本文描述了 Wormhole 的设计和实现，以及在 Facebook 部署的多个数据存储系统上扩展该系统所面临的运维挑战。我们在生产环境中部署的 Wormhole 在稳定状态下每秒传输超过 35 GB 的数据（5000 万消息/秒或每天 5 万亿条消息），在故障恢复期间峰值可达 200 GB/秒。我们证明了 Wormhole 能够以低延迟向可能失败或以不同速率消费更新的订阅者发布更新，同时不牺牲效率。

特别值得注意的是它在支持滞后消费者时不牺牲整体系统吞吐量的做法。

Borg, Omega, and Kubernetes

虽然 Google 每个编排系统（Borg、Omega 和 Kubernetes）的单独论文都值得单独阅读，但这篇文章是对三者的绝佳概述：

虽然对软件容器的广泛兴趣是相对较近的现象，但在 Google，我们管理 Linux 容器已经超过十年，并在此期间构建了三个不同的容器管理系统。每个系统都深受其前任影响，尽管它们开发的初衷各不相同。本文描述了我们从开发和运维这些系统中吸取的教训。

幸运的是，并非所有编排都发生在 Google 的羽翼之下，Mesos 的两层调度架构同样是一个引人入胜的读物。

Large-scale cluster management at Google with Borg

Borg 已经为 Google 的基础设施编排了很长时间（远早于 Omega，不过有趣的是 Omega 论文比 Borg 论文早两年发表）：

Google 的 Borg 系统是一个集群管理器，它运行来自数千种不同应用的数十万个作业，横跨多个集群，每个集群最多可达数万台机器。

这篇论文审视了 Borg 的中心化调度模型，该模型既有效又高效，尽管随着时间推移它变得越来越难以修改和扩展，从而在 Google 内部催生了 Omega 和 Kubernetes（前者是为了乐观地替换它，后者似乎是为了将他们的经验商业化，或者至少防止 Mesos 占据太多心智份额）。

Omega: flexible, scalable schedulers for large compute clusters

Omega 在很多方面都是“第二系统效应”的绝佳例子，即试图用一个优雅得多的方案替换一个复杂现有系统的努力，最终比预期更具挑战性。

Omega 特别针对的是扩展老化 Borg 系统的现实问题：

不断增长的规模以及对快速响应不断变化的需求，用当前单体集群调度器架构很难满足。这限制了新功能部署的速度，降低了效率和利用率，并最终会限制集群的增长。我们提出了一种新方法，使用并行、共享状态和无锁乐观并发控制来满足这些需求。

这或许也是“更糟即更好”再次获胜的例子。

Mesos: A Platform for Fine-Grained Resource Sharing in the Data Center

这篇论文描述了 Apache Mesos 的设计，特别是它独特的双层调度器：

我们介绍了 Mesos，这是一个在多个不同集群计算框架（如 Hadoop 和 MPI）之间共享商用集群的平台。共享提高了集群利用率，并避免了每个框架的数据复制。Mesos 以细粒度方式共享资源，允许框架通过轮流读取每台机器上存储的数据来实现数据局部性。为了支持当今框架复杂的调度器，Mesos 引入了一种称为资源提供（resource offers）的分布式两级调度机制。Mesos 决定向每个框架提供多少资源，而框架决定接受哪些资源以及在上面运行哪些计算。我们的结果表明，当在不同框架间共享集群时，Mesos 可以实现接近最优的数据局部性，能够扩展到 5 万个（模拟）节点，并且对故障具有弹性。

Mesos 被 Twitter 和 Apple 大量使用，曾一度是唯一具有显著采用率的开源通用调度器，现在正与 Kubernetes 展开一场有趣的心智份额竞争。

Design patterns for container-based distributed systems

转向基于容器的部署和编排引入了一整套新词汇，如 sidecar 和 adapter，这篇论文对过去十年随着微服务和容器成为越来越重要的基础设施组件而演化出的模式进行了调研：

在 1980 年代末和 1990 年代初，面向对象编程彻底改变了软件开发，普及了将应用构建为模块化组件集合的方法。今天我们正在分布式系统开发中看到一场类似的革命，基于容器化软件组件的微服务架构越来越受欢迎。容器特别适合作为分布式系统中的基本对象，因为它们在容器边界上竖立的“墙”。随着这种架构风格的成熟，我们正在看到设计模式的出现，就像面向对象程序那样，原因相同——以对象（或容器）为思考单位抽象掉了代码的底层细节，最终揭示出在各种应用和算法中常见的高层次模式。

“sidecar”这个术语很可能起源于 Netflix 的这篇博客文章，它本身也值得一读。

Raft: In Search of an Understandable Consensus Algorithm

我们经常看到第二系统效应，即第二个系统相对于简单初始系统变得臃肿和复杂，但在 Paxos 和 Raft 的情况下，角色发生了反转。虽然 Paxos 常被认为超出人类理解范围，但 Raft 是一篇相当易读的论文：

Raft 是一种用于管理复制日志的共识算法。它产生的结果与（multi-)Paxos 等价，并且效率与 Paxos 相当，但其结构与 Paxos 不同；这使得 Raft 比 Paxos 更容易理解，也为构建实际系统提供了更好的基础。为了提升可理解性，Raft 将共识的关键元素（如领导者选举、日志复制和安全性）分开，并强制更高的连贯性以减少需要考虑的状态数量。用户研究的结果表明，学生学习 Raft 比学习 Paxos 更容易。Raft 还包括一种新的集群成员变更机制，使用重叠多数来保证安全性。

Raft 被 etcd、influxdb 等众多系统使用。

Paxos Made Simple

作为 Leslie Lamport 众多有影响力的论文之一，《Paxos Made Simple》既是一篇解释 notoriously 复杂的 Paxos 算法的珍品，也因为即使在最简单形式下，Paxos 其实也并不那么简单：

用于实现容错分布式系统的 Paxos 算法一直被认为难以理解，或许是因为最初的表述对许多读者来说如同天书。事实上，它是分布式算法中最简单、最显而易见的一种。其核心是一种共识算法——主教算法（synod algorithm）。下一节将展示这种共识算法几乎不可避免地从我们希望它满足的属性中推导出来。最后一节解释了完整的 Paxos 算法，它是通过将共识直接应用于状态机方法构建分布式系统而得到的——这种方法应该众所周知，因为它是分布式系统理论中最常被引用的文章的主题。

Paxos 本身仍然是一个深刻创新的概念，是 Google Chubby 和 Apache Zookeeper 等众多系统的背后算法。

SWIM: Scalable Weakly-consistent Infection-style Process Group Membership Protocol

大多数共识算法都专注于在分区时保持一致性，而 SWIM 则走向了另一个方向，专注于可用性：

许多分布式对等应用需要在所有参与进程上维护弱一致的进程组成员信息。SWIM 是一个通用软件模块，为大规模进程组提供这种服务。SWIM 的努力源于传统心跳协议的可扩展性问题，这些协议要么造成随组规模二次增长的网络负载，要么在检测进程崩溃的响应时间或误报频率上做出妥协。本文报告了在大型商用 PC 集群上 SWIM 子系统的设计、实现和性能。

SWIM 被用于 Hashicorp 的软件以及 Uber 的 Ringpop。

The Byzantine Generals Problem

另一篇 Leslie Lamport 关于共识的经典论文，《拜占庭将军问题》探讨了如何处理有意或无意提交错误消息的分布式参与者：

可靠的计算机系统必须处理给出相互冲突信息的故障组件。这种情况可以用拜占庭军队的一群将军带着部队在敌城周围扎营的抽象方式来表达。他们只能通过信使通信，必须就共同的作战计划达成一致。然而，其中一人或多人可能是叛徒，试图迷惑其他人。问题是要找到一种算法，确保忠诚的将军们能达成一致。结果表明，仅使用口头消息，这个问题只有在超过三分之二的将军忠诚时才能解决；因此单个叛徒就能迷惑两个忠诚的将军。如果使用不可伪造的书面消息，这个问题对任意数量的将军和可能的叛徒都可解决。随后讨论了这些解决方案在可靠计算机系统中的应用。

这篇论文主要关注形式化证明，这是 Lamport 的一贯主题（他开发了 TLA+ 来简化形式化证明），但它也是一个有用的提醒：我们仍然倾向于假设我们的组件会可靠且诚实地运行，而也许我们不应该这样假设！

Out of the Tar Pit

《Out of the Tar Pit》痛惜软件中不必要的复杂性，并提出函数式编程和更好的数据建模可以帮助我们减少偶然复杂性（认为大多数不必要的复杂性来自状态）。

摘自摘要：

复杂性是成功开发大规模软件系统的唯一主要困难。遵循 Brooks 的观点，我们区分偶然困难和本质困难，但不同意他认为当代系统中剩余的大多数复杂性都是本质的这一前提。我们指出了复杂性的常见原因，并讨论了可以采取的一般方法，在它们是偶然性的时候消除它们。为了使事情更具体，我们随后给出了一个潜在的基于函数式编程和 Codd 关系数据模型的减少复杂性的方法大纲。

当然是一篇很好的读物，尽管十年后再读，会发现有趣的是这两种方法都没有特别流行起来，相反，最接近“通用”减少复杂性方法的是转向大量基本无状态的服务，这也许更多是减少局部复杂性，却以更大的系统性复杂性为代价，而其维护则被委托给了更专业化的系统工程师。

（这又是另一篇让我希望 TLA+ 能足够自然地成为常用工具的论文。）

The Chubby lock service for loosely-coupled distributed systems

分布式系统已经够难了，如果还得频繁重新实现 Paxos 或 Raft 就更不用说了，Chubby 提出的模型是在一个共享服务中实现一次共识，从而让构建于其上的系统能够通过大大简化的模式来共享分布式的弹性。

摘自摘要：

我们描述了在 Chubby 锁服务上的经验，该服务旨在为松耦合的分布式系统提供粗粒度锁以及可靠（尽管低容量）的存储。Chubby 提供的接口很像带有建议锁的分布式文件系统，但设计重点在于可用性和可靠性，而不是高性能。该服务的多个实例已经运行超过一年，其中几个每个同时处理数万个客户端。本文描述了最初的设计和预期用途，将其与实际使用进行比较，并解释了设计如何被修改以适应这些差异。

在开源世界中，Zookeeper 在 Kafka 和 Mesos 等项目中的使用方式扮演了与 Chubby 相同的角色。

Bigtable: A Distributed Storage System for Structured Data

Google 最杰出的论文和技术之一是 Bigtable，它是早期（至少在互联网时代早期）的 NoSQL 数据存储，在极高规模下运行，并构建在 Chubby 之上。

Bigtable 是一个用于管理结构化数据的分布式存储系统，设计目标是扩展到非常大的规模：在数千台商用服务器上存储 PB 级数据。Google 的许多项目都在 Bigtable 中存储数据，包括网页索引、Google Earth 和 Google Finance。这些应用对 Bigtable 的要求差异极大，既有数据规模（从 URL 到网页再到卫星图像），也有延迟要求（从后端批量处理到实时数据服务）。尽管有这些多样的需求，Bigtable 还是为所有这些 Google 产品提供了灵活、高性能的解决方案。在本文中，我们描述了 Bigtable 提供的简单数据模型，它让客户端能够动态控制数据布局和格式，并介绍了 Bigtable 的设计和实现。

从 SSTable 设计到布隆过滤器，Cassandra 大量继承自 Bigtable 论文，并且可能被合理地视为 Dynamo 和 Bigtable 论文的融合。

Spanner: Google’s Globally-Distributed Database

许多早期的 NoSQL 存储系统用最终一致性换取更高的弹性，而构建在最终一致性系统之上可能会令人不安。Spanner 代表了 Google 提供强一致性和分布式可靠性的方法，部分依赖于一种管理时间的新颖方法。

Spanner 是 Google 可扩展、多版本、全球分布式且同步复制的数据库。它是第一个在全球规模下分布数据并支持外部一致分布式事务的系统。本文描述了 Spanner 的结构、功能集、各种设计决策背后的理由，以及一种暴露时钟不确定性的新颖时间 API。这个 API 及其实现对于支持外部一致性以及各种强大特性至关重要：过去的非阻塞读取、无锁只读事务，以及跨整个 Spanner 的原子 schema 变更。

我们还没有看到任何开源的 Spanner 等价物，但我猜我们会在 2018 年开始看到它们。

Security Keys: Practical Cryptographic Second Factors for the Modern Web

像 YubiKey 这样的安全密钥已成为最安全的第二认证因素，这篇来自 Google 的论文解释了促使它们诞生的动机，以及让它们得以工作的设计。

摘自摘要：

安全密钥是能够保护用户免受钓鱼和中间人攻击的第二因素设备。用户携带单个设备，并可以自行将其注册到任何支持该协议的在线服务。这些设备实现和部署简单、使用简单、保护隐私，并且能抵御强大的攻击者。我们已经在 Chrome 浏览器和 Google 的在线服务中提供了对安全密钥的支持。通过分析一项始于 Google 内部并扩展到我们面向消费者的 Web 应用、为期两年的部署，我们展示了安全密钥同时提升了安全性和用户满意度。安全密钥的设计已被 FIDO 联盟标准化，该组织拥有超过 250 家覆盖整个行业的成员公司。目前，安全密钥已被 Google、Dropbox 和 GitHub 部署。

它们也非常便宜！订购几个，花一两天时间就开始保护你的生活吧。

BeyondCorp: Design to Deployment at Google

在 2014 年最初的 BeyondCorp 论文基础上，这篇论文稍详细一些，并且得益于两年迁移所积累的智慧。不过，核心思想基本保持一致，相对最初的 BeyondCorp 论文并没有太多新内容（尽管那也是一篇极好的论文，如果你还没读过，这同样是一个很好的起点）：

Google BeyondCorp 计划的目标是改进员工和设备访问内部应用时的安全性。与传统的边界安全模型不同，BeyondCorp 不根据用户的物理位置或源网络来控制对服务和工具的访问；相反，访问策略基于设备及其状态以及关联用户的信息。BeyondCorp 将内部网络和外部网络都视为完全不可信，并通过动态断言和强制执行访问层级（或层）来控制对应用的访问。

Availability in Globally Distributed Storage Systems

这篇论文探讨了如何思考复制分布式系统中的可用性，对于那些试图确定如何正确衡量其存储层或其他足够复杂系统 uptime 的人来说，是一个有用的起点。

摘自摘要：

我们基于对 Google 主要存储基础设施为期一年的广泛研究，刻画了云存储系统的可用性属性，并提出了统计模型，这些模型能让我们进一步洞察多种设计选择（如数据放置和复制策略）的影响。利用这些模型，我们根据在我们的机群中观察到的真实故障模式，比较了在各种系统参数下的数据可用性。

特别有趣的是它对相关故障的关注，建立在分布式系统的用户只有在多个组件同时发生重叠故障时才会感知到故障这一前提上。另一个预期但令人安心的观察是，在 Google 的规模下（资源分布在机架和区域之间），大多数故障来自调优和系统设计，而不是底层硬件。

我也惊讶于他们在这个案例中对可用性的定义是多么简单：

当存储节点未能对我们的监控系统定期发送的健康检查 ping 做出积极响应时，它就变得不可用。该节点会一直不可用，直到它恢复响应能力，或者存储系统从其他幸存节点重建数据为止。

关于可用性的讨论常常变得任意复杂（“其实应该是响应率超过 X，且结果正确且在我们的延迟 SLO 内！”），看到最简单的定义仍然可用，令人安心。

Still All on One Server: Perforce at Scale

随着公司成长，代码托管性能成为整体开发者生产力的关键因素之一（与构建和测试性能并列），但这个话题并不经常被讨论。这篇来自 Google 的论文讨论了他们扩展 Perforce 的经验：

Google 运行着地球上最繁忙的单个 Perforce 服务器，也是任何源码控制系统中最大的仓库之一。从这个高水位线出发，本文审视了服务器性能和其他规模问题，并顺便谈了我们现在的位置、如何走到这里，以及如何继续领先用户一步。

Large-Scale Automated Refactoring Using ClangMR

大型代码库往往会随着时间推移而老化，尤其是那些存储着数百或数千个不同团队在不同项目上协作的 monorepo。这篇论文介绍了 Google 试图通过工具减轻维护大型 monorepo 负担的一种尝试，这些工具可以轻松地在整个代码库中重写抽象语法树（AST）。

摘自摘要：

在本文中，我们展示了一个在现实世界中高效重构大型 C++ 代码库的系统实现。ClangMR 结合了 Clang 编译器框架和 MapReduce 并行处理器，使代码维护者能够轻松且正确地转换大量代码。我们描述了开发这样一个工具的动机、它的实现，然后分享了我们在最近一次使用它对 Google C++ 代码库进行 API 更新时的经验。

Source Code Rejuvenation is not Refactoring

这篇论文引入了“代码焕新”（Code Rejuvenation）的概念，这是一个朝着更干净抽象演进的单向过程，随着新语言特性和库的出现而进行，特别适用于庞大、较老的代码库。

摘自摘要：

在本文中，我们提出了源代码焕新的概念，即自动迁移遗留代码，并简要提到了我们用来实现它的工具。虽然重构改进的是结构不佳的源代码，但源代码焕新通过寻找和替换可以用更高级软件抽象表达的编码模式，利用了增强的编程语言和库设施。提升抽象层次有利于软件的可维护性、安全性和性能。

这项工作与 Google 的 ClangMR 论文有强烈的呼应。

Searching for Build Debt: Experiences Managing Technical Debt at Google

这篇论文有趣地介绍了如何在活跃的代码库中进行大规模迁移。以构建失败作为贯穿始终的例子，他们将策略分解为三个支柱：自动化、让做正确的事变得容易，以及让做错的事变得困难。

摘自摘要：

面对庞大且快速变化的代码库，Google 的软件工程师不断为各种形式的技术债支付利息。Google 工程师也努力偿还这些债务，无论是通过特别的 Fixit 日，还是通过被称为看门人、耕耘者或拆除专家的专门团队。我们描述了几项相关工作，旨在衡量和减少 Google BUILD 文件中以及相关死代码中的技术债。我们处理了依赖规范、不可构建目标和不必要的命令行标志中发现的债务。这些工作常常会暴露其他形式的技术债，必须先对其进行管理。

No Silver Bullet - Essence and Accident in Software Engineering

这篇来自《人月神话》作者的开创性论文，“没有银弹”扩展了关于偶然与本质复杂性的讨论，并认为偶然复杂性已经不再足够多，以至于单个减少偶然复杂性的行动无法显著提升工程师的生产力。

摘自摘要：

过去软件生产力的大部分重大提升都来自于移除人为障碍，这些障碍使偶然性任务变得异常困难，例如严重的硬件约束、别扭的编程语言、机器时间不足。现在软件工程师所做的工作中，还有多少仍然致力于偶然性，而不是本质性？除非它超过全部工作的十分之九，否则将所有偶然性活动缩减到零时间也不会带来数量级的提升。

有趣的是，我认为我们确实看到大型代码库中的偶然复杂性已经大到足以产生数量级改进（这推动了例如 Google 对 ClangMR 等工具的投资），所以也许我们在转向本质复杂性方面的进展，并没有我们自以为的那么领先。

The UNIX TimeSharing System

这篇论文描述了 1974 年时 UNIX 的基本原理，真正令人惊叹的是其中有多少设计决策至今仍在使用。从我们都用 chmod 操作过的权限模型，到用于操作文件的系统调用，令人惊讶的是这么多东西仍然完好无损。

摘自摘要：

UNIX 是一个通用、多用户、交互式的操作系统，适用于 Digital Equipment Corporation PDP-11/40 和 11/45 计算机。它提供了许多即使在更大操作系统中也很少见的功能，包括：(1) 包含可卸载卷的分层文件系统；(2) 兼容的文件、设备和进程间 I/O；(3) 启动异步进程的能力；(4) 可按用户选择系统命令语言；(5) 超过 100 个子系统，包括十几种语言。本文讨论了文件系统和用户命令接口的性质及实现。

同样令人着迷的是他们的观察：UNIX 之所以部分成功，是因为它的作者设计它是为了解决一个通用问题（使用 PDP-7 令人沮丧），而不是为了一个更具体的目标。
