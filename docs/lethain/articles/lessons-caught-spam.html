从垃圾信息中吸取的教训

2008-01-22 · 阅读原文

据我所知，LifeFlow 至今还没有任何评论垃圾信息成功突破其防护机制1。其防护的核心是一个反向验证码（reverse-captcha），关于这方面的优质讨论已经很多，我就不在此赘述了。让我们把注意力放在从捕获的垃圾信息中意外获得的一些智慧和失败教训上。

LifeFlow 的评论系统期望接收 Markdown 格式的文本，而当输入极其糟糕时——比如几百个垃圾链接的列表——渲染过程就会彻底崩溃。令人惊讶的是，垃圾评论竟然糟糕到能把 Markdown 库直接逼到最大递归深度而崩溃。这是一个有趣的点：正常用户根本没有理由把系统推到这个极限，因此它的局限性反而成了意料之外的好处。

不像人类

如果你不通过正常途径（即点击真实文章中的链接）而是直接导航到评论创建页面，会发生以下情况：

这意味着你必须像人类一样，按相同的流程操作：阅读文章、点击回复链接，并在合理时间内填写完成，否则系统将缺少必要的信息来处理评论。

当然，你可以把这个流程做得更智能，尝试预测用户正在查看哪篇文章，或者让他们选择要评论的条目，但那不是人类用户会遇到的真实情况。这又是一个“更糟即更好”的例子，尽管和这个词通常的含义不太一样。

撰写真实的故事

最终我认为这里最有价值的教训是，我们需要把时间集中在撰写真实用户真正想做的事情的故事上。有时我们会在假设的边缘情况上花费大量时间，这些情况虽然给程序增加了很多复杂性，也消耗了大量精力，但实际上并没有提升系统对真实用户的体验质量。

这里的垃圾信息算是一个不太寻常的例子，因为更好的实现所带来的负面后果通常不会像这个案例中那样清晰2，但它确实说明了一个有趣的现象：如果我们去实现那些对合法用户无关紧要的故事，可能会产生意想不到的后果。

另一方面，它也妨碍了一些善意使用 Internet Explorer 6 的真实评论者。目前它已经能很好地支持 Camino、Safari、Firefox 和 Internet Explorer 7，也有可能支持 IE6，但我还没有机会测试。↩诚然，即使在这里，这些教训也并不那么清晰，因为自从评论实现的质量提升之后，垃圾信息的数量并没有增加。真正发生的情况是，之前存在一个非正式的垃圾干扰层（也就是糟糕的实现），它与正确工作的垃圾防护层（反向验证码）形成了冗余。↩
