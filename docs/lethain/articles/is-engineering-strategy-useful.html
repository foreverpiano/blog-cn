工程策略有用吗？

2025-01-30 · 阅读原文

我经常听到工程师抱怨缺少策略，但他们的抱怨很少清楚说明为什么缺少策略如此重要。相反，这更像是一种老生常谈：经济以前更好，孩子以前更尊重父母，而工程团队以前都有工程策略。

本章首先探讨一个我坚信的观点：即使没有书面记录，也始终存在工程策略。在此基础上，我们将讨论为什么策略——尤其是书面策略——对认真对待它的组织而言是一次极具价值的机会。

我们将深入探讨：

为什么即使人们说没有策略，也始终存在策略；策略在我的职业生涯中如何产生重要影响；不合适的策略如何在没有多少补偿收益的情况下给组织带来巨大痛苦；书面策略如何推动组织学习；不把策略写下来的代价；即使你没有被授权自己“制定策略”，策略如何支持个人学习和发展。

希望到本章结束时，你会同意我的观点：策略值得你和你的组织投入时间。

这是《Crafting Engineering Strategy》中的一章。

始终存在策略

我从未在任何一个地方工作时，人们不声称那里没有策略。在其中许多公司里，他们会说没有工程策略。当我成为高管并能够记录和发布工程策略后，指责缺少策略的声音并没有消失，只是转移到了缺少产品或公司策略上。

这甚至发生在明确拥有工程策略的公司，例如 2016 年的 Stripe，他们有一个清晰的工程策略，其中包含多个支柱，例如：

几乎不惜任何代价维护向后 API 兼容性（例如，强制从 TLS 1.2 升级到 TLS 1.3 以保持 PCI 合规，但不会强制从 /v1/charges 端点升级到 /v1/payment_intents 端点）；在 monorepo 中使用 Ruby，除非是 PCI 环境、数据处理或数据科学工作；工程师对其工作的可用性负完全责任，即使有产品或工程经理参与。

在那里工作时，通常很清楚公司在任何给定主题上的工程策略是什么。当然，有时需要四处询问，而且随着时间推移，某些决策变得足够有争议，以至于很难明确回答策略是什么。例如，采用 Ruby 还是 Java 变得极具争议，我因此发布了一份试图调解分歧的策略（探索的量级。），尽管这并不是特别成功的努力（事后看来原因很明显，尤其是完全缺乏任何执行机制）。

正如 William Gibson 所说，“未来已经到来——只是分布不均”，组织决策中始终嵌入着某种策略，尽管在许多组织中，这种策略只对一小群人可见，而且可能很快被遗忘。

如果你发现自己认为不存在策略，我建议你换个角度，问问自己如果找不到，它到底存在于哪里。一旦找到，你可能会发现这个策略其实相当无效，但我从未发现它不存在。

策略具有影响力

在《》一文中，我们讨论了 Calm 的工程策略如何解决工程团队中普遍存在的摩擦。该策略的核心是明确 Calm 如何做出重大技术决策，并记录引导这些决策的根本目标：最大化投入到产品创造上的时间和精力。“我们是一家产品工程公司！”——Calm 的工程策略

该策略通过消除持续争论的根源来减少摩擦。它成功地重置了团队的关注点，也导致几位工程师离开公司，因为这与他们的优先事项不符。人们很容易把这视为缺点，但我并不这么认为。一个清晰、书面的策略让所有人清楚我们正在玩什么样的游戏、游戏规则，并第一次让他们能够准确判断自己是否想和整个团队一起玩这个游戏。

创造一致性是策略产生影响的方式之一，但肯定不是唯一方式。策略支持组织的方式包括：

将公司投资集中到更小的领域。例如， 能让你将大部分工具开发工作集中于一种语言、一个测试套件和一种部署机制；只有通过普遍采用才能实现的许多有趣特性。例如，采用是管理成本的重大机会，但只有一致采用才能生效。再比如，许多灾难恢复或多区域策略只有在所有基础设施都采用相同配置机制时才可行；将执行力集中在真正重要的事情上。例如，让一个十人工程师团队能够逐步将公司的 Ruby monolith 转向静态类型，而不会让整个组织被推动工作分心。这是一个困难的项目，本可能消耗整个组织好几个月，但专注让一个小团队完成了早期的大部分工作；创造一个关于组织思维方式的知识库。对新员工，尤其是高级新员工而言，有书面策略的入职会高效得多。例如，要求所有访问用户数据的行为都必须有清晰、用户可理解的理由。虽然这对来自大公司的新员工可能是显而易见的，但只有小公司经验的人很可能完全不知道这是必要的。如果没有书面记录，对该政策的遵守很快就会下降。我们是否应该分解单体架构？工程组织层级结构模型Stripe 为什么开发 Sorbet？（~2017）如何控制用户数据的访问权限？

有些事情即使是巧妙写成的策略也无法做到。然而，我的经验始终是，制定策略会带来进步，即使这种进步只是对固有分歧的理解。

不合适的策略尤其有影响力

虽然好的策略能成就很多事情，但有时感觉不合适的策略影响力要大得多——当然，是在所有错误的方向上。Digg v4 发布：源于迫切的乐观。 是我个人参与过的最糟糕的策略。它将 Digg V3.5 的 PHP monolith 代码库完全重写为 PHP 前端加上十几个 Python 服务的后端，还将数据库从分片的 MySQL 迁移到早期版本的 Cassandra。最糟糕的是，它用在发布前几天才写出的一个 hack，取代了经过十年打磨的细致算法。

尽管 Digg 很可能因为严重依赖搜索引擎优化获取流量，以及当时 Google 频繁变化的搜索算法而难以盈利，但工程策略确保了我们迅速死去，而不是获得慢慢爬出来的机会。

重要的是，这不只是 Digg。几乎你深入研究的每个工程组织，都有自己那份未被使用的平台项目，它们消耗了数十年的工程师时间，却损害了重要机会。数量惊人的高级领导加入新公司后，会发起一场，试图完全重写架构、切换编程语言，或者把新组织改造成他们之前更熟悉的样子。大型迁移

不合适而非糟糕

我第一次写这个部分时，直接把这类策略称为“糟糕”。这个词的难点在于，同样的策略在另一套环境下可能非常有效。例如，如果 Digg 是一家三人公司且没有收入，从零重写可能就是正确的决定！

因此，我更倾向于使用“不合适”而不是“糟糕”，以避免纠结于某种方法在其他环境下是否可行。毫无疑问，每种方法在某个组织里都会有效。

书面策略推动组织学习

刚加入 Carta 时，我注意到我们在一些重要问题上方法不一致。各个团队对新项目有自己不同的标准工具包；对现有内部平台的采用程度不一，决定是否投资新的内部平台时的决策也不一致。大家普遍同意我们正在分解 monolith，但对如何分解却没有共识。

在这样一个环境中，面对强大而不同的观点，我最早的项目之一就是与新成立的 Navigators 团队一起，写下一份明确的工程策略，而这个团队本身也是我们新工程策略的一部分。何时编写策略，以及写多少？

Carta 的 Navigators

正如导航者一文所述，我们在 Carta 建立了一个项目，让明确指定的人员作为技术领导者，代表工程组织的关键部分。这个代表性领导团体使我们能够用大约十名代表整个组织的工程师组成的小团队来迭代策略，而不是去面对与 400 名工程师直接谈判这个不可能的任务。

这份书面策略让我们能够明确描述我们看到的问题，以及我们希望如何应对这些问题。更重要的是，它成为一个可以在小群体中迭代，然后广泛分享以获取可能被遗漏的团队反馈的成果。

首次发布后，我们广泛传播，并在工程全员会议上频繁讨论。然后我们每年都会回顾，或者当内容不再合理时进行修订。例如，我们最初的策略完全没有提到人工智能。几个月后，我们扩展了它，提到了一个非常保守的使用大型语言模型的方法。最近，我们又再次修订了人工智能部分，因为我们正在深入研究 agentic workflows。

很多人对策略的某些部分有不同意见，这很好：这正是书面策略的关键好处之一——可以精准地表达异议。从这些异议中，我们能够进化自己的策略。有时是因为新信息，比如人工智能实践目前的快速发展；有时是因为我们最初的方法可以改进，比如我们如何限制最初 Navigators 团队的成员资格。

新员工也能提出异议，而且是基于充分信息，而不是显得只是执着于他们前公司的做法。特别是，他们能够理解驱动我们决策的历史思考，即使那种上下文如今已不再显而易见。当我们暂停 monolith 分解时，服务供给存在显著摩擦，但今天情况已大为改善，这可能让当时的决策显得有些随意。只有书面文档才能在不断成长、变动和变化的组织中持续传递这些上下文。

在口头历史中，你相信什么高度依赖于你和谁交谈，这塑造了你对历史和现在的看法。而在书面历史中，更有可能在更大规模上达成一致，这是实现规模化增长而非把增长局限在少数高级领导小圈子里的前提。

隐性策略的代价

我们刚刚讨论了书面策略，这本书也花了很多篇幅在这个主题上，包括。这不仅是因为书面策略带来的好处，也是因为未书面化的策略所造成的损害。让工程策略文档更具可读性

容易被误解。在依赖口头沟通的组织中，信息流动取决于某个人是否在决策现场，然后准确地把信息转述给需要的人。然而，我们经常看到这些人未能把信息传递到其他地方。有时他们的理解本身也有偏差。这两者都会给执行策略带来严重问题。

双头组织

几年前，我开始采用一种模式：我合作过的大多数工程组织都有两位领导者——一位是经理，另一位是资深工程师。这部分是为了确保高级决策包含工程上下文，也部分是为了减少沟通错误。

点对点沟通中的错误非常普遍，以至于对于那些不倾向于书面沟通的人，我能找到的唯一解决方案就是确保我把策略（和其他更新）至少传达给两个人。

团队间的不一致。在我工作过的一家公司，基础设施工程团队晋升到 Staff-plus 职级的比例远高于产品工程团队。这导致产品工程团队的人才不断流失，去做基础设施相关的问题，即使这些问题对业务价值不大。新领导者不知道这个非正式政策存在，他们经常在中遇到麻烦。他们也不知道需要去争取更好的政策。更糟的是，没有人确定这是否真的是政策，所以最终是否有人为某个晋升提出这个视角完全是随机的：有时好的晋升会被挡住，有时边缘情况却被通过。时间上的不一致。实施新政策通常是持续行动和一次性行动的混合。例如，假设你想把所有 HTTP 操作统一为使用同一个库。你可能会加一个 linter 检查来拒绝已知的替代方案，并大概率会做一次全代码库的统一工作。然而两年后，代码库里又会出现另外三个随机的 HTTP 库，悄悄钻进 linter 规则的空隙。如果政策是写下来的，并且有几个人读过，那么有很多方法可以阻止这种情况。如果没有写下来，就不太可能有人记得，而且更不可能记得住理由来为此争论。对新领导的危害。当一位新的 Staff-plus 工程师或高管加入公司时，人们常常责怪他们未能理解现有决策背后的上下文。这是公平的：高级领导的重要工作之一就是发掘和理解上下文。但这也不公平：如果之前的思考被明确记录下来，他们会容易得多。我见过每一个特别糟糕的新领导入职案例，都涉及新人接手一个空缺职位，而他的经理也不知道该怎么做。在这些情况下，成功完全取决于新人自己学习的能力和意愿。职级、绩效评定与校准机制

在大多数方面，记录策略的做法与有许多共同之处，其全部好处都归于组织，而不是执行这项工作的个人。当原始作者还在时，事情可以维持下去；要真正欣赏其价值，需要暂时跳出自己，去重视那些在你不再是组织一员后仍对组织最重要的事情。继任规划

信息的群体免疫

对书面策略的一个常见反对意见是没人会读东西。这有一定道理：让组织里的每个人都知道某件事极其困难。然而，我从未觉得这个目标特别重要。

我对组织中信息传播的看法与群体免疫（Herd immunity）类似：你不需要每个人都知道，只要有足够多的人知道，就能防止困惑传播得太远。

因此，虽然不可能让所有工程师都了解策略细节，但你完全可以让每一位 Staff-plus 工程师和工程经理都知道这些细节。

策略支持个人学习

虽然我相信策略的最大好处归于组织而非制定它的个人，但我同样认为策略是一条被低估的自我发展途径。

我见过策略支持个人发展的方式包括：

制定策略能建立自我认知。从一个具体例子来说，我曾与几位工程师共事，他们认为自己极为资深，却经常要求项目使用新的编程语言或技术，仅仅因为他们个人想学习这些技术。他们内心的策略很清楚——想做有趣的事——但如果遵循，他们自己也会同意得出的策略并不合理。策略帮助你在新环境中获得情境意识。用 Wardley Mapping 完善策略 反复强调情境意识是良好策略的前提。这意味着你必须理解自己所处的现实，而这正是新任高级工程领导者最容易犯的毁灭性错误。通过明确陈述策略适用的诊断，你就能更容易地调试为什么在新的团队或公司复用之前的策略可能行不通。策略作为你的个人档案。正如书面策略是机构的记忆，它同样可以作为个人记忆，帮助你理解过去方法的实际影响。我们每个人都是自己过往工作的档案管理员，会抽出最有价值的部分来解决当前问题。在漫长的职业生涯中，记忆会淡化——动机性推理也会悄悄出现——但明确的书面记录不会。构建工程策略的步骤

事实上，我现在而不是以后开始写这本书的部分原因，是我意识到自己已经开始忘记职业生涯早期所做策略工作的细节。如果我想保留那个时代的智慧，并确保自己以后不用重蹈覆辙，就必须现在把它写下来。

总结

我们已经阐述了为什么策略对你所在的工程组织和你个人而言，都是一种有价值的学习机制。我们展示了策略如何帮助组织处理服务迁移、monolith 分解和合理化职位回填。我们也讨论了不合适的策略如何促成了 Digg 的消亡。

然而，如果在本章结束时我必须强调两件事，那不会是上面这些。而是两个我发现最常被忽视的主题：

始终存在策略，即使它没有被写下来。你能为组织中的策略做出的最大贡献，就是把策略写下来，让它能够被辩论、被认同，并被明确地进化。

关于策略之类的讨论常常陷入追求高 prestige 的活动，比如做出有争议的决策，但据我观察，最有效率的策略制定者是通过切实做好基础工作来取得更多进展：把事情写下来、广泛探索其他公司如何解决同样的问题、从持不同意见的人那里接受反馈来改进自己的草案。策略是有用的，而制定策略也可以很简单。
