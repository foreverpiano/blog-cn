我对当前开发者元生产力工具的怀疑。

2020-11-18 · 阅读原文

2020 年讨论工程领导力时，很难不提到 Accelerate 对开发者生产力的定义 和 DORA 的研究成果。它们以数据驱动的方式阐述如何提升开发者生产力，这是一件相当神奇的事。但为什么这些方法没有得到更广泛的应用呢？

我认为其中存在三个核心问题：

将生产力指标用于评估而非学习的恶性陷阱；为生产力流水线做埋点需要横跨太多不同工具；大多数埋点和仪表盘工具都会迫使你以不合理的方式对问题进行建模。

这三点共同制造了足够多的摩擦，导致大多数团队即使知道应该使用这些指标，最终也从未真正落地。

学习而非评估

市面上有不少工程生产力测量初创公司，其中很多都是过去两三年内成立的。作为工程经理，你难道不想知道谁的提交频率在下滑吗？当你拥有团队过去一个季度每人每月的提交数量时，下一次校准会议的堆栈排名岂不是变得轻而易举？

我个人坚信，这些公司销售的产品对使用它们的企业弊大于利。以这种方式用生产力指标来衡量个人，类似于事后复盘把“人为失误”当作根本原因一样。这只是一种表演，如果你想责怪某个人，那就直接去责怪好了，不要浪费时间去收集一堆随意挑选的指标来支撑你的结论。

真正需要的是收集数据来支持学习，而学习是成批进行的。比较不同团队之间的缺陷率是有价值的，前提是你深入去了解这些团队在做法上有什么不同：或许他们的测试或代码审查流程不一样，或许团队的任职年限或资历结构不同。

只要工具持续偏向那些想给团队打分而不是从开发过程中学习的经理，这些工具就会被实际做埋点的工程师所不信任，同时也会给使用它们的管理者制造虚假的信心。正确的工具应该完全从学习的角度来设计。

为如此多的工具做埋点

Buritica 的《工程交付指标入门》（A primer on engineering delivery metrics）这类资源为我们描绘了大致的方案轮廓，但其中仍有大量细节需要逐一解决。生产力流水线涉及太多工具，以至于很难用一致的方式对它们全部进行埋点。一家小型初创公司可能在使用 Github、Docker、Terraform、Jenkins 和 Kubernetes，每一种工具都会带来复杂的问题需要回答：唯一标识符是 Pull Request 吗？如果构建出现积压，我们在一个构建里部署了两个 Pull Request 怎么办？如何区分 Jenkins 因为磁盘空间不足崩溃，还是因为测试失败而崩溃？Kubernetes 部署在所有 Pod 都升级完成后才算完成吗？如果有一个 Pod 失败了呢？如果后来发现那个失败其实是节点故障而与代码无关呢？我们如何获得 Pull Request 创建之前的工作流洞察？

这些问题每一个都能找到答案，但都需要花费大量时间去梳理，并把它们拼接成一个连贯的现实视图。同时也很容易因为埋点方式不当而对实际情况产生细微的误解。如此庞杂的细节让很多团队在完成这项工作前就已望而却步。

最好的工具应该能自动集成大多数常见工具，同时提供完全可定制的客户端，类似 Datadog 的集成策略。即使只是提供一套经过验证的、在整个流程中该使用哪些唯一标识符的推荐，也会非常有帮助。

需要可观测性而非监控

在监控和可观测性领域，Honeycomb 和 Lightstep 推动了一种以支持临时查询而非预计算查询为核心的可观测性定义。Grafana/Graphite/Statsd 这类监控工具可能会促使你发出预先聚合的指标，以支持“按服务、按数据中心查看 p50 延迟”这样的查询。而 Honeycomb 和 Lightstep 这类可观测性工具则鼓励你发出原始事件，在查询时再进行聚合，从而不仅能回答 Grafana 能回答的问题，还能回答“正在灰度这个新提交的服务器收到的请求延迟分布如何？”甚至“展示所有运行这个提交的请求的完整 Trace”这样的问题。

太多开发者元生产力工具都聚焦于监控式的解决方案，这对于衡量生产力来说契合度一般，对于支持学习则更加不适合。这很可惜，因为推动基础设施监控走向“监控”模式的那些规模挑战，在面对人类规模的事件时根本不存在。

举例来说，如果你正在测量一个 Kubernetes 集群的服务器响应时间，该集群每个节点跑 10 个 Pod，一共有 1000 个节点和 3 个可用区，那么你可能需要记录 100 请求/秒 × 10 Pod/节点 × 1000 节点 × 3 可用区，也就是每秒 300 万次测量。这会迫使你在存储数据量上做出权衡。可观测性基础设施若要在合理价格内存储所有这些未经聚合的事件，会变得非常复杂且需要定制化。（我粗略的理解是，大多数可观测性工具会先把事件放在环形缓冲区中，当事件从缓冲区中被淘汰时，再将其中有价值的事件和汇总数据迁移到更持久的存储中。）

然而，开发者元生产力工具所面对的规模要小得多，因此完全不需要去解决那些底层基础设施问题。只需写入 MySQL 或 Kafka（再把历史数据流式传输到 S3）之类的系统即可。没有理由不让底层事件保持可查询，以便支持更深入的理解。

我希望这些系统能提供的最根本工作流，与请求 Trace 是一致的。每个 Pull Request 都带有一个唯一标识符，并在整个开发者生产力工具链中传递，你可以在仪表盘工具中看到它们旅程的每一步。关键在于，这让你可以遵循典型的 Trace 埋点流程：先从宽泛的范围开始（也许只是 PR 被创建、被合并、然后被部署），随后逐步向 Trace 中添加更多 Span，以获得对有问题环节更深刻的洞察。

那又怎样？

我写这篇文章，一是希望正在从这个角度解决这个问题的人能看到，二是作为一个可复用的解释——当人们写邮件向我征求反馈、寻求天使投资等时，我对什么样的开发者元生产力工具感到兴奋。

说实话，我并不一定认为这会是一门好生意。我确信这是工程领导力团队需要用来更有效投资开发者生产力的工具，但我对人们是否愿意为它付费没那么确定；找到合适的市场进入和分发策略可能是这类产品最难的部分。这也展示了可观测性/Trace/Span 方法的另一个优势：你可以导入历史事件，立即展示价值，而不需要让大家先使用工具去构建新的指标聚合。

不过最终，我认为像 Github 这样的公司最有条件在这个方向取得进展，尤其是随着 Github Actions 在开发者工作流中占据越来越大的份额。（我不太清楚 Nicole Forsgren 在 Github 的新职位具体做什么，但我有一个梦想——她做的事情至少与此相关。）
