我对当前开发者元生产力工具的怀疑。

2020-11-18 · 阅读原文

在2020年讨论工程领导力时，很难不提到 Accelerate 对开发者生产力的定义 和 DORA 的研究成果。它们以数据驱动的方式阐明了如何提升开发者生产力，这是一件相当神奇的事。但为什么这些方法没有得到更广泛的应用呢？

我认为其中存在三个核心问题：

  1. The nefarious trap of using productivity measurements to evaluate rather than learn
  2. Instrumenting productivity pipeline requires operating across so many different tools
  3. Most instrumentation and dashboarding tools force you to model the problem poorly

这三者共同制造了足够多的摩擦，导致大多数团队即使知道应该使用这些指标，也始终没有真正付诸实践。

学习而非评估

市面上有不少工程生产力测量初创公司，其中许多是过去两三年内成立的。作为工程经理，你难道不想知道谁的提交速度在落后吗？当你手里掌握着所有人过去一个季度每月提交次数的数据，下一次校准会议上的堆栈排名是不是会变得格外轻松？

我个人坚信，这些公司销售的产品对使用它们的企业弊大于利。以这种方式用生产力指标来衡量个人，类似于在事故复盘中将“人为失误”认定为根本原因。这只是做做样子，如果你想责怪某人，那就直接去责怪好了，别浪费时间去搞一堆随意挑选的指标来支持你的结论。

真正的需求是采集数据来支持学习，而学习是成批发生的。比较不同团队之间的缺陷率是有价值的，前提是你深入挖掘这些团队在做法上的差异——也许他们的测试或代码审查流程不同，也许团队的任职年限或资历结构不同。

只要工具持续偏向那些想给团队打分而不是从开发过程中学习的经理，这些工具就必然会被实际操作检测的工程师所不信任，同时也会给使用它们的管理者制造虚假的信心。正确的工具应该完全从学习视角来设计。

对众多工具进行检测

Buritica 的《工程交付指标入门》（A primer on engineering delivery metrics）这类资源为我们描绘了大致的思路，但其中仍有很多细节需要逐一解决。生产力管道涉及大量工具，以至于很难用一致的方式对它们全部进行检测。一家小型初创公司可能会同时使用 Github、Docker、Terraform、Jenkins 和 Kubernetes，每一种工具都会带来复杂的问题需要回答：唯一标识符是 Pull Request 吗？如果构建排队导致我们在一次构建中部署了两个 Pull Request 怎么办？我们如何区分 Jenkins 因为磁盘空间不足崩溃和测试失败导致的崩溃？Kubernetes 部署在所有 Pod 都升级完成后才算完成吗？如果其中一个 Pod 失败了呢？如果后来发现那个失败其实是节点故障而与代码无关呢？我们如何获得 Pull Request 创建之前的工作流洞察？

这些问题每一个都有答案，但需要花费大量时间去梳理，并将它们整合成一个连贯的现实视图。同时也很容易因为检测方式不当而对实际情况产生细微的误解。这种需要处理的大量细节让许多团队难以完成这项工作。

最好的工具应该能自动与这些常见工具中的大多数集成，同时提供完全可定制的客户端，类似 Datadog 的集成策略。即使只是提供一套经过验证的、在整个流程中应该使用哪些唯一标识符的推荐，也会非常有帮助。

需要可观测性而非监控

在监控和可观测性领域，Honeycomb 和 Lightstep 推动了一种以支持临时查询而非预计算查询为核心的可观测性定义。Grafana/Graphite/Statsd 这类监控工具可能会促使你发出预先聚合的指标，以支持特定查询，例如“按服务和数据中心统计的 p50 延迟是多少？”而 Honeycomb 和 Lightstep 这类可观测性工具则鼓励你发出事件，然后在查询时进行聚合，这不仅能回答你在 Grafana 上会问的问题，还能回答类似“正在金丝雀发布这个新提交的服务器上的请求延迟分布如何？”甚至“给我看所有运行这个提交的请求的完整 Trace”这样的问题。

太多开发者元生产力工具聚焦于监控风格的解决方案，而这对于衡量生产力来说是相当平庸的匹配，对于支持学习则更加不合适。这很可惜，因为驱动基础设施监控走向“监控”模式的基础设施挑战，在面对人类规模的事件时根本不存在。

举例来说，如果你正在测量运行在 Kubernetes 节点上的服务器响应时间，每个节点运行十个 Pod，那么你可能需要记录 100 请求/秒 × 10 Pod/节点 × 1000 节点 × 3 个可用区，也就是每秒三百万次测量。这会迫使你在存储数据量上做出权衡。可观测性基础设施若要以合理价格存储所有这些事件而不进行聚合，复杂且高度定制化。（我粗略的理解是，大多数可观测性工具会先将事件捕获到一个环形缓冲区中，当事件从缓冲区中被逐出时，有趣的事件和汇总数据才会被转移到更持久的存储中。）

然而，这些开发者元生产力工具所处的规模要小得多，因此完全不需要解决底层基础设施问题。只需写入 MySQL 或 Kafka（并将历史数据流式传输到 S3）之类的系统即可。底层事件完全应该可以被获取，以支持更深入的理解。

我希望这些系统能提供的基础工作流和请求 Trace 是一样的。每个 Pull Request 都有一个贯穿整个开发者生产力工具链的唯一标识符，你可以在仪表盘工具中看到它们旅程的每一步。关键在于，这让你能够遵循典型的 Trace 检测工作流：先从宽泛的范围开始（也许只是 PR 被创建、被合并、然后被部署），然后随着时间推移向 Trace 中添加更多 Span，从而对有问题的环节获得更多洞察。

那么，这又有什么意义呢？

我写这篇文章，一方面是希望有团队正从这个角度在解决这个问题；另一方面，也是为了给出一个可复用的解释——当有人发邮件向我征求反馈、天使投资意见等时，我究竟对什么样的开发者元生产力工具感到兴奋。

说实话，我并不一定认为这会是一门好生意。我确信这是工程领导团队更有效地投资开发者生产力所需要的工具，但我对人们是否愿意为它付费没那么有信心；找到合适的市场策略和分发渠道可能是这类产品最难的部分。这也显示了可观测性/Trace/Span 方法的另一个优势：你可以导入历史事件并立即展示价值，而不需要让大家先使用工具来构建新的指标聚合。

不过最终，我认为像 Github 这样的公司最有条件在这个方向上取得进展，特别是随着 Github Actions 在开发者工作流中占据越来越大的份额。（我不太确定 Nicole Forsgren 在 Github 的新职位具体在做什么，但我有一个梦想——至少和这件事有关。）
