JSON、面向对象的视图，以及启动一个真正的应用

2008-06-22 · 阅读原文

欢迎来到 Wielding Django 的第三期，由 Will Larson 友情主持。正如我在第一期中所承诺的，从这一期开始，有过 Django 经验的读者可以正式加入我们了。本期我们会先讨论 JSON 和面向对象视图，然后开始构建一个真正（虽然很小）的应用。

我们将使用来自 django-webapp 中的一些代码。django-webapp 是我在 Web 应用开发过程中积累的有用代码和设计模式的集合。我从中提取了一些作为代码片段，但你可能会发现直接获取整个代码库会更方便：

svn checkout http://django-webapp.googlecode.com/svn/trunk/ django-webapp

JSON

上次我们只返回了一个原始数字，但返回更结构化的数据其实非常简单。我们可以使用 XML，但它是一种较为笨重且（在某些实现中）较慢的编码方式。目前快速、轻量级编码的非官方标准是 JSON，而且在 Python 中生成 JSON 非常容易。下面是上次那个 compute 函数，现在改成了返回 JSON。

from dwa.serialize import JsonResponse
def compute(request, op):
import operator
operation = getattr(operator, op)
a = float(request.GET['a'])
b = float(request.GET['b'])
result = operation(a, b)
return JsonResponse(dict(
op=op, a=a, b=b,
result=operation(a, b)))

对于大多数包含多个键值的字典，我更喜欢使用 dict(abc=de) 这种写法。它不需要给键加引号，而且这也是关键字参数的常规写法，我个人非常喜欢。当然，它和 {'op': op, 'a': a} 的写法完全等价。

dwa.serialize 是 django-webapp 的一部分，也是代码片段 801（它依赖代码片段 800）。而 JsonResponse 只是进行 JSON 编码，然后把结果包装成一个 HttpResponse。（默认情况下，它会在结果外包裹 JavaScript 注释以提高安全性，大多数 JavaScript 框架都能处理这种情况。）请注意，JSON 的顶层对象必须是一个 dict（甚至不能是数组）。

但还有更简单的方法。Django 支持“中间件”（middleware），它提供了一组钩子，可以介入请求和响应的各个处理阶段。我们可以拦截响应处理过程，在必要时自动进行 JSON 编码。这正是代码片段 803 所做的事情（它同样包含在 django-webapp 中）。要启用该中间件，请在 settings.py 中添加以下内容：

MIDDLEWARE_CLASSES = (
    'dwa.middleware.JsonEncodingMiddleware', # Keep this last!
    )

这样你的视图函数就可以直接返回 dict，它们会被自动编码为 JSON。

Ajax 错误中间件

当服务器在处理 AJAX 请求时发生错误时，即使是可靠的 Firebug 也很难看到实际的错误信息。因此你可能会想添加 AjaxErrorMiddleware 来解决这个问题。我的 MIDDLEWARE_CLASSES 配置如下：

MIDDLEWARE_CLASSES = (
    'dwa.middleware.AjaxErrorMiddleware',
    'dwa.middleware.JsonEncodingMiddleware',
    )

记住要把 JsonEncodingMiddleware 放在最后，这样它才能最先处理视图返回的内容。

面向对象的视图

Django 的视图本质上就是一个可调用对象，它接收一个 HttpRequest 作为第一个参数。那么哪些东西符合这个要求呢？

1. 函数：

def my_view(request, **kwargs)

2. 类：

class MyView(YourView):
    def __call__(self, request, **kwargs):
         return super(MyView, self)(request, **kwargs)

3. 实例方法：

class MyResource(Resource):
    def list(self, request):
        return {'contents': list(self.queryset)}

可能还有其他我没想到的形式。总之，Django 的教程（包括本系列）通常都从视图函数开始讲起。有时视图类会被当作一种进阶技巧介绍。我还没见过有人在实际项目中使用实例方法作为视图，但我发现它非常有用，所以在这里给它一些展示空间。

几点观察：

1. 我们干净利落地把这个 API 相关的所有 URL 规则都分离了出来。对于更通用的解决方案，我们可能需要添加一个 prefix 参数，以便轻松修改 API 的挂载路径。我们甚至可以子类化 Django 内部的 URL 解析器，但它并不是为了便于扩展而设计的。

2. 实际的计算逻辑（perform_operation）与面向 Web 的接口（compute）被清晰地分开了，因此你可以独立地对其中任何一个进行子类化。举一个有趣的例子：

class HtamAPI(MathAPI):
    def perform_operation(self, op, a, b):
        return super(HtamAPI, self).perform_operation(op, a, b)
urlpatterns = HtamAPI().url_patterns()

一个真正的 Web 应用

本系列接下来的内容将专注于将这些想法发展成实用的技巧，以支持快速应用开发。但为了不纸上谈兵，我们应该做一个比简单数学运算更有挑战性、也更有趣的东西。而且它还不能是又一个博客、Wiki 或 Reddit 克隆……

于是我决定做一个简化版的应用，这个想法我已经想了好一阵子了。我热爱上帝的话语，因为它向我显明了祂是谁（祂实在美好！）以及我自己是谁。我也常常非正式地背诵其中的段落，因为在很多情况下回想起来都很有帮助。但我经常会忘记某些词句，或者记不清一段经文的具体位置，所以我想要一个能帮助我复习的工具。它需要能在任何地方使用，所以这个工具的最佳实现形式是……打孔卡。好吧……那就用 HTML、CSS、JavaScript、DOM、DHTML、JSON、AJAX、Django 这些 Web 应用时髦词的组合吧。

只要提到“上帝”，无论持何种观点，许多人都会情绪激动。如果你确实有话想说，（a）请先想清楚再发帖，（b）请发到我的博客上。因此，在 Will 的这个博客上，我们还是把注意力集中在 Django 本身。
