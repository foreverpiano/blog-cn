如何编写包装库

2008-08-04 · 阅读原文

在我上一篇博文中，有读者留言询问如何编写包装库，我想以较为系统的方式来回应。因此，这里分享我编写现有库上层包装库的方法和思考。

编写包装库，就是在已有功能基础上创建一层抽象。每增加一层抽象，都会引入额外的出错空间，而典型的包装库通常不会增加任何新功能。想到这两点，敏锐的读者可能会问：“这他妈有什么意义？”好吧，敏锐的读者先生，意义在于我们正在重新定义一个库的接口。一个构思良好的接口 redesign，能将一个 awkward 的库变成令人愉悦的使用体验；但如果执行不当，包装库也可能限制原库的功能，或掩盖其操作的代价。

为什么要编写包装库

给一个库增加额外的抽象层本身并不是什么好事。每层抽象都会带来更多可能搞砸的交互、容易被误解的复杂度，以及需要维护的代码行数。因此，和其他任何抽象层一样，包装层必须有充分的存在理由。

一般来说，编写包装库有两个正当理由：

  1. To eliminate pain points. Often times a library will be extremely useful, but will be sabotaged by one or two extremely awkward points. For example, your library might be returning its data in a giant XML document, when you really want a list of dictionaries. Or the querying language might be more complex than necessary for standard usage (like the helpful ORM layers over interactions with SQL databases).
  2. To expose functionality in a better suited design. Some libraries will lie to you in their interface. Not a blatant act of malicious deception, but instead just poor design choices. For example, an interface might suggest that the underlying operations are tree-like (cheap lookup) when its actual operations are more similar to an unsorted array (expensive lookup).That makes it difficult to make efficient usage of the library, because you are making seemingly reasonable decisions on how to use the library, but are unknowingly using a great deal of inefficient operations.Sometimes, too, the initial interface isn't brutally poor or deceptive, but it doesn't quite mesh with the general language philosophy, and is inflicting a bit of mental entropy on seasoned language practictioners (for example, if a Python library is not 'Pythonic', or if a Scheme library is not written in a functional style).

选择你的毒药

现在你需要决定要包扎哪些痛点，或设计怎样的接口来暴露功能。发现痛点通常相当直观（你第一次弄明白它的时候有没有骂人？那就是痛点），但接口设计的改进并不总是那么明显（如果明显的话，库的原作者大概早就改了）。

一个有用的通用原则是，寻找用户已经熟悉的常见概念和数据结构。特别要选择那些操作代价相似的数据结构（大量添加操作便宜但移除廉价，或按位置查找便宜但按值查找昂贵等等），这样用户就能更容易凭直觉正确使用这个库。

实现与创新

当你找到了想要解决的几个问题，并确定了一个直观的接口来访问库的功能之后，就可以开始动手实现了。先从简单入手，把东西跑起来，然后逐步演进。在演进接口的过程中，你可能会发现有些额外功能能很自然地融入进来。那就加上它！编写包装库的乐趣之一就在于即兴发挥。你只需要重新创建接口，而不是整个底层功能的深度，因此实验过程相对快速且无痛。

案例研究：BossArray 包装库

作为例子，我们来看看 BossArray，这是我围绕 Yahoo 的 BOSS Mashup Framework 编写的一个包装库。Yahoo BOSS 可以方便地获取 Yahoo 搜索结果，而 Yahoo BOSS Mashup Framework 是一个非常灵活的 Python 库，用于与 Yahoo BOSS 交互。它确实很有帮助，但我有几点想要改进。

  1. The simplest use case (searching for a search term) was a bit complex.
  2. Wasn't easy to deal with more than 50 search results at a time.
  3. Had created its own API, but I felt that mimicking the Python List api would be more intuitive.

在决定模仿列表 API 之后，结果发现通过完全拥抱列表 API，很容易就能同时简化最简单的用例，并优雅地处理大量搜索结果。因此，所有改进都融入到新的接口中，事情一下子变得非常简单。

在实现新接口的过程中，我还想到可以在这里加入一个缓存层，于是也把这个功能加了进去。总的来说，这个包装库大约只有一百行代码（大部分是缓存机制），却为那些有简单需求的用户提供了一个更自然的 BOSS 服务接口。

总结

包装库通过替换接口来改进一个库。有时候新的接口会自然催生一些新功能，从而让整体大于原有库接口之和；但很多时候，即使不在功能上创造额外价值，而只是在可用性上提供帮助，包装库也非常有价值。编写包装库是一种有趣、简单且相对快速的贡献方式，能让你参与到感兴趣的项目中，并可能在项目社区中开启有趣的讨论和争鸣。希望这篇文章对你多少有些帮助，如果有任何问题，或者觉得我有哪些方面没有讲清楚，欢迎告诉我。
