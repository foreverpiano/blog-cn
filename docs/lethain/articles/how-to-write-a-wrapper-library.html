如何编写包装库

2008-08-04 · 阅读原文

在我上一篇文章的评论区，有人问到如何编写包装库，我想以比较系统的方式来回应这个问题。下面就是我对在现有库之上编写包装库的思路和看法。

编写包装库本质上是在现有功能基础上创建一个抽象层。每增加一层抽象，都会引入额外的出错空间，而典型的包装库通常不会增加任何新功能。想到这两点，细心的读者可能会问：“这到底有什么意义？”好吧，敏锐的读者先生，意义在于我们是在重新定义一个库的接口。一个构思良好的接口重构可以将一个 awkward 的库变成令人愉悦的工具；但如果执行不当，包装库也可能限制原库的功能，或掩盖库操作的真实代价。

为什么要编写包装库

给一个库增加额外的抽象层本身并不是一件好事。每一层都会带来更多可能出错的交互、容易被误解的复杂度，以及需要维护的代码行数。因此，和其他任何抽象层一样，包装层必须有充分的存在理由。

一般来说，编写包装库有两个正当理由：

消除痛点。很多时候一个库非常有用，却被一两个极其别扭的设计所拖累。例如，库可能以一个巨大的 XML 文档返回数据，而你真正想要的是一份字典列表。又或者查询语言对常规使用场景来说过于复杂（比如那些在 SQL 数据库之上提供便利的 ORM 层）。以更合适的设计暴露功能。有些库的接口其实是在“欺骗”你——不是恶意欺骗，而是设计选择不当。比如，一个接口可能暗示底层的操作是树状结构（查找很便宜），而实际操作却更接近无序数组（查找很昂贵）。这就导致开发者很难高效地使用该库，因为你根据接口做出的看似合理的决策，实际上正在执行大量低效的操作。有时候，原始接口也不是特别糟糕或具有欺骗性，只是它与所在语言的整体哲学不够契合，会给有经验的开发者带来一定的思维负担（例如，一个 Python 库不够“Pythonic”，或者一个 Scheme 库没有采用函数式风格）。

选择你的“毒药”

现在你需要决定要修复哪些痛点，或者要以怎样的接口来暴露功能。发现痛点通常比较直观（你第一次弄明白它的时候有没有骂人？那就是痛点），但接口设计的改进却不总是那么明显（如果很明显的话，库的原作者大概早就改好了）。

一个有用的通用原则是，寻找用户已经熟悉的常见概念和数据结构。特别要选择那些操作代价相近的数据结构（例如大量添加但移除很便宜，或者按位置查找便宜而按值查找昂贵等等），这样用户就能更容易地凭直觉正确使用这个库。

实现与创新

当你确定了想要解决的几个问题，并设计好一个直观的接口来访问库的功能后，就可以开始动手实现了。先从简单的入手，让它能跑起来，然后在此基础上逐步演进。在打磨接口的过程中，你可能会发现某些额外功能可以很自然地融入进去。那就加上它吧！编写包装库的一大乐趣就在于即兴发挥。你只需要重新创建接口，而不是重新实现全部底层功能，因此实验起来相对快速且无痛。

案例研究：BossArray 包装库

作为一个例子，我们来看看 BossArray，这是我围绕 Yahoo 的 BOSS Mashup Framework 编写的一个包装库。Yahoo BOSS 可以方便地获取 Yahoo 搜索结果，而 Yahoo BOSS Mashup Framework 是一个功能丰富的 Python 库，用于与 Yahoo BOSS 交互。它非常有用，但我还是有几点想要改进。

最简单的用例（搜索一个关键词）稍微有点复杂。一次处理超过 50 条搜索结果不太方便。它创建了自己的 API，但我认为模仿 Python List 的 API 会更直观。

在决定模仿列表 API 之后，我发现可以非常轻松地同时简化最简单的用例，并通过完全拥抱列表 API 来解决处理大量搜索结果的问题。于是，所有改进都与新的接口融为一体，事情变得相当简单。

在实现新接口的过程中，我还想到可以在这里加入一个缓存层，于是就把这个功能也加进去了。总的来说，这个包装库大约只有一百行代码（主要是缓存机制），却为那些有简单需求的用户提供了一个更自然的 BOSS 服务接口。

总结

包装库通过替换接口来改进一个库。有时候新的接口会自然催生一些新功能，从而让整体大于原有接口各部分之和；但同样常见的情况是，包装库无需增加新的功能性价值，仅仅在易用性上就能带来很大帮助。编写包装库是一种有趣、简单且相对快速的贡献方式，能帮助你参与感兴趣的项目，也可能为项目社区开启有趣的讨论和争鸣。希望这篇文章对你有些帮助，如果你有任何问题，或者觉得我有哪些方面没有讲清楚，欢迎告诉我。
