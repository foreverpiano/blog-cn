判断力和创造力是你所需要的一切。

2026-03-11 · 阅读原文

大约一年前我加入 Imprint 时，我们的部署还是手动完成的，需要投入大量人力密切关注才能完成。数据库迁移同样也要手动执行。在那种环境下，开发出优秀的软件当然是可能的，但这需要极强的细致度和专注力。用 Subversion 进行开发、通过 SSH 登录远程服务器去修改 PHP 文件，也能做出好软件，但我们的目标是让事情变得轻松，而不是仅仅“可行”。

十个月后，我们绝大部分的变更（包括数据库迁移）在初始的 Pull Request 被审查合并后，就能持续部署到生产环境，且无需人工介入。大声朗读持续部署的“圣经”相关章节就会知道，以这种方式部署变更并不会降低可靠性，反而会让系统更加可靠。过去人类可能执行的每一步验证，现在都会在每次部署中一致性地完成，其中许多步骤因为太过繁琐，以前常常被从标准操作流程中省略，比如每次部署后每分钟都仔细检查生产金丝雀的运行状况，持续半小时。

这次迁移让我想起 Uber 的服务迁移，那次经历促使我在 2018 年写下了《迁移：解决技术债的唯一可扩展方案》，特别是与如今编码代理（coding agents）时代相比，这两种迁移的感受有多么不同。我越是思考这两者之间的对比，就越坚定了我对这项技术在未来几年将如何影响软件开发的看法。

迁移作为隐喻

虽然我很想直接讨论编码代理如何正在改变软件开发，但我还是想先详细说说最近 Imprint 的这次迁移，以及它与 Uber 那次迁移的对比。

Uber 的那次迁移是：

从零开始搭建一个新的自助式服务开通平台，大致相当于一个极简版的 Heroku，包括跨集群的实际调度算法等。很多边缘情况处理得比较粗糙，例如我已经不记得当时服务数据库迁移是怎么做的，但我猜我们只是把它留给用户自己解决。挑战之一在于当时的环境非常异构，有 Python、NodeJS、Go，还有一长串稀奇古怪的技术（R、Elixir 等）。（从历史背景看，2014 年我们做这件事时 Kubernetes 还处于非常早期阶段，基本上不存在。）服务迁移是迭代进行的，几乎完全由平台团队推动，产品工程团队几乎没有提供多少支持。（大家都太忙了，而且我们的时间表被即将到来的数据中心迁移所驱动。）一个大约 3 名工程师的小团队迁移了数百个服务，这其中包括夏晓剑（Xiaojian Huang），他至今仍然是我职业生涯中遇到过的最具生产力的工程师之一，所以把这叫做“大约 3 人团队”可能不太公平。我们还要为负责逐步淘汰 Python 单体应用的核心产品工程团队的同事默哀，他们要把那个庞大的单体应用作为一个沉重的单个服务完成迁移。这件事从开始到结束不到六个月，但在那六个月里我几乎没有一天停止过工作。

Imprint 的这次迁移感受则相当不同：

我们依托的基础设施已经强大得多，拥有 Kubernetes、ArgoCD 等。我们的问题不再是从零构建平台，而是如何将我们的软件和工作流与这些平台组合起来。我们把所有服务和数据库都迁移到了持续部署模式，大部分工作在 3 个月内完成。同样，绝大部分工作是由一个约 3 人的团队完成的。2014 年，我们把绝大多数时间花在实现各种决策上：调度器如何工作、服务开通的用户体验如何设计等等。到了 2026 年，我们几乎把所有时间都用在设计方案、审查编码代理生成的 Pull Request，以及当设计与现实无法如预期般顺畅结合时修订我们的方案。狂热冲刺式的开发被大幅增加的设计时间所取代。

迁移的所有根本挑战依然存在，但在 2026 年，我们得以只专注于解决那些挑战，而不是去应付那些必要却琐碎的实现细节。（好吧，老实说，我们还得不断迭代如何使用编码代理的方法，以获得更长的无需人工介入的工作周期，但我们现在是在讲一个故事，就不跑题了。）

当今的生产力最受判断力制约

这次迁移让我清楚地看到，编码代理已经基本为我们的团队解决了“时间”这个问题。我们实际上拥有几乎无限的时间，而且价格非常便宜，可以用来完成工作。

它们在“注意力”问题上也取得了长足进步。当我同时推进五个以上的项目时，我往往会跟不上需要跟进的各项工作，以确保项目顺利完成。但我越来越相信，这正如 LLM 社区会俏皮地说的那样，是一个“技能问题”——是我在使用工具时的组合方式问题。我相当有信心，我会逐步进化我的工作方法，让注意力不再成为主要的瓶颈。我不认为这个问题会彻底消失，因为在团队中工作就必须进行协调，但它会显著减轻。

下一个制约因素，我认为也是当今构建真正重要软件时面临的最大问题，就是判断力。有了几乎无限的时间，而注意力又更多地成为我个人工作流的问题而非固有极限，我几乎可以做任何事情。但我如何以一种可维护、安全且可靠的方式来做呢？如何确保即使某位关键工程师离职后，系统依然能持续运行？

我在《大语言模型时代，作者的竞争优势是什么？》中提出了“数据包”（datapacks）的概念，它至今仍让我觉得是规模化判断力的核心机制：我们可以通过引入针对当前任务的专家上下文来补充判断力。今天，这件事实际上正在编码代理开发层、社区共同开发的共享代理技能，以及公司内部开发的专有技能中发生。我猜测，行业会发展出一个高质量技能的生态系统，例如针对安全工程、产品工程等领域的详细且持续维护的技能。你可以很容易想象 O’Reilly 或其他技术出版商会开发一个“受祝福技能”的包管理器，成为向任务中注入判断力的首选之地。（这就是我为最新一本书制作 LLM 优化版本时尝试过的想法，但真正最有价值的是那个分发平台。）

一旦我们解决了判断力问题——我确实相信我们会通过各种开源和商业管理的技能包管理器来实现，而这些管理器会与编码代理紧密集成——那么摆在我们面前的最后一个制约因素就是创造力。这是一个足够遥远的问题，我目前并不太担心，但它感觉像是一个经典的创业问题，会像今天一样，可以用同样的方法来解决。

我承认这里忽略了财务约束，但相对于当今企业花在软件工程预算上的金额，这并不是一个特别重要的制约因素。随着工程成本可能变得更低，财务约束或许会变得更有趣，但当我们思考如何注入判断力时，成本也会相应上升，所以最终结果仍有待观察。
