2017 年我在工程管理中学到的东西。

2017-12-29 · 阅读原文

2017 年，我一直在 Stripe 的基础设施工程团队工作（旧金山和东南亚远程），接触到越来越有意思的问题，规模也越来越大，合作的同事也越来越优秀。

以下是我在过去一年里学到的一些心得。

管理篇

有相当大的一类工作，只要安排一个专注的人去负责，就能避免后续多人手忙脚乱浪费好几年时间：比如确保系统能够持续扩展（而非退化）、成本核算、构建工具、代码托管等等。最好安排两个人，因为“一个人”仍然是最孤独的数字。管理中最宝贵的技能之一，是在管理层和团队的期望之间搭建桥梁，而且这种桥梁必须对双方价值观都真实可信。如果你从不向团队说“不”，那你就不是真的在管理他们；如果你从不改变管理层的想法，那你也算不上真正的管理者。
拥有广泛技能的一个不那么显而易见的好处是，你能在更多不同情境下取得成功——无论是经理换人、跳槽，还是其他情况。我希望大家能更多地强调：一线经理和“管理经理”其实是两种截然不同的工作。所需技能不同，而一线管理是一门极其丰富、深刻的领域，我们应该给予更多认可。刻板印象威胁（stereotype threat）——即仅仅意识到别人对你的刻板印象，就会显著降低你在相关任务上的表现——对我来说是一个全新且震撼的认知（推荐阅读 Claude Steele 的《Whistling Vivaldi》）。我和几乎所有共事过的经理都曾坚信，冷启动 sourcing（主动挖掘简历）是无效且浪费时间的。但我们后来制定了一套流程并严格执行，结果令人尴尬的是，它对我们所有人都持续有效。这是一个让人谦卑的例子：我们曾对一个合理但完全错误的信念抱有强烈信心。最有效的包容性举措是什么？建立一套结构化的流程，让大家可以私下申请重要角色和机会。不过大家学得很快：只有通过这个流程获得的机会真正取得成功并得到认可，大家才会继续申请。每次组建评审组、工作组、团队时，都要养成习惯，审视这个组的成员构成以及你选择他们的方式。（这正是我们开发角色/机会申请流程的初衷和原因。）为公司里的 underrepresented minorities（URM）组建多元团队和小组，很容易变成他们的“第二班工作”。当我们要求某人参与时，我们在道德上就有义务把这份工作转成“第一班工作”，并在绩效评估、晋升等环节给予认可。对齐（alignment）和共识（consensus）是完全不同的两件事。共识是一种缓慢的达成对齐的机制；而对齐的核心是沟通和倾听各方观点，如果已经建立了信任关系和沟通机制，对齐可以非常迅速。在一个快速扩张的组织里，是否能在团队内部和跨团队之间持续保持对齐，是衡量卓越程度的重要标志。“达成对齐所需的时间”就是你衡量重组是否成功的指标。

基础设施篇

AWS 和 GCP 正在吞噬传统内部基础设施，我们必须提供超越云服务的差异化价值。目前的机会有哪些？安全、合规、语言专项工具、维护的基础镜像、CI 的易用性和速度、多地域部署、架构模式（例如 Kappa 架构）等。
其中大部分机会在 2-3 年内就会消失：CI 的易用性和速度（所有云厂商都在大力投入）、多地域（GCP 正在推行“多地域优先”）、架构模式（新应用默认就会采用）。相比之下，安全、合规和语言专项工具较难被单一方案解决，暂时仍能保持差异化。当前把 GCP 和 AWS 相互竞标似乎已成为 GCP 的核心营销策略之一：他们希望在商品化功能的质量上取胜。GCP 的流式处理服务看起来是业界最佳，但作为内部基础设施提供者，我们仍然不应该轻率采用有差异化的云服务，这导致其采用速度受限于 AWS 是否能提供有竞争力的替代方案。gRPC/Protobuf 生态已经抢走了 Thrift/Finagle、AVRO 等方案的大部分关注度。gRPC，以及随之而来的 HTTP/2，将是未来的主流库和协议。HTTP/2 依然是最酷却最少被充分利用的新基础设施原语之一。我们现在有了双向流（bi-directional streams）！应该更多地用起来。CloudFlare、Akamai 等公司似乎正面临着与云服务同质化的严重风险。Fastly 目前仍然提供功能完整的 VCL，这在当下仍是一个有趣且具有工艺感的差异化护城河。非常令人兴奋的是，DDoS 防护正在成为云服务的标配能力。我不太确定这种能力如何与现有产品有效结合（比如你真的能单独卖 DDoS 防护吗？），但如果云厂商无论如何都要提供这项能力，那么转售现有容量几乎是零成本的。Kubernetes 生态正在胜出，而且非常出色，但编排（orchestration）似乎正被云服务商品化。容器生命周期管理依然是最困难的部分。我依然坚信 k8s 是实现云无关性的关键工具。（GCP 的策略是靠价值取胜，因此降低迁移成本是其重要一环。）（Julia Evans 写过一篇很棒的文章，讲述我们在 Stripe 如何推广 Kubernetes。）Terraform 是个优秀的工具，但它不够有主见、约束也不够强，难以实现我曾经对跨云可移植性的那些美好期望。我认为这个领域还有很大的空白，甚至可以基于 TF 再造一个工具来填补。（顺便说一句，AWS 或 GCP 怎么还没收购 HashiCorp？）Envoy 是我 2017 年意外发现的新技术，也是 Xoogler（前 Google 员工）和前 Twitter 员工想要重现他们过往工具梦想的最后几个基础设施组件之一。开发者生产力相关的组件仍然被封闭在墙后，这可能是高采用率开源项目里最大的机会之一。流式计算似乎注定会成为。只要不可变事件（immutable events）能够获得 traction，流式处理就会成为可扩展计算的统一范式。（另一种说法是：流式处理就是新的 NoSQL。）从 Lambda 到 Kappa 以及数据流范式
